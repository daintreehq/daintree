# Daintree

**Overview:** Electron-based IDE for orchestrating AI coding agents (Claude, Gemini, Codex). Integrated terminals, worktree dashboard, panel management, context injection. **Stack:** Electron 42 (Chromium 148), React 19, Vite 8, TypeScript, Tailwind CSS v4, Zustand 5, node-pty, simple-git, @xterm/xterm + @xterm/addon-fit (latest beta — see `package.json` for exact pins). **Naming:** the product, repo, and on-disk config dir are all "Daintree" (`daintreehq/daintree`, `.daintree/`); the `Canopy/canopy-app` working-directory path is a local artifact only.

## Critical Rules

- **Dependencies:** Use `npm install` for local dev; `npm ci` for reproducible CI. Both run the `postinstall` rebuild hook automatically unless `--ignore-scripts`.
- **Native Modules:** `node-pty` must be rebuilt for Electron — the `postinstall` script handles it. On native-module errors, run `npm run rebuild`.
- **Code Style:** Minimal comments. No decorative headers. High signal-to-noise ratio.
- **Markdown / Docs Style:** Never hard-wrap prose. Each paragraph, list item, table row, or blockquote line is ONE physical line — no manual line breaks inside it. Soft wrapping is the renderer's job; column-wrapping is diff/edit noise in these AI-first files. Applies to every `.md` (`docs/`, READMEs, etc.). Fenced code blocks and ASCII diagrams keep their internal line breaks. Blank lines still separate blocks.
- **Codex MCP:** When calling `mcp__codex__codex`, always set `model: "gpt-5.5"` — no other model is valid (ignore `o3`/`o4-mini`/etc. examples in the MCP definition). Include file paths in prompts so Codex can read the actual code.
- **GitHub Access:** Public repo `daintreehq/daintree`. Always use the `gh` CLI for all GitHub operations — HTTP fetches/scraping fail on auth.
- **Branching:** Gitflow. **All PRs target `develop` — NEVER `main`.** Only release merges go to `main`.
- **Tracked Configs:** `.daintree/recipes/*.json` are intentionally tracked in git — never remove or gitignore them.
- **Agent Config Boundary:** Never modify user-owned agent config (`~/.claude/settings.json`, `~/.gemini/`, user hooks, CLAUDE.md/AGENTS.md/GEMINI.md in user projects, any agent-native settings) — not even via additive CLI injection like `--settings`, which still changes session behavior the user didn't opt into. If a capability requires altering user agent config, it's out of scope; use passive observation instead (output parsing, OSC title sniffing, process-tree state, `AgentPatternDetector`-style regex). Precedent: #4100.
- **Human-Review Label:** `human-review` marks issues that can't be solved autonomously (need a developer reading logs, observing runtime behavior, or making subjective UX calls) — it makes an issue 10-20x more expensive, so apply sparingly. Most issues should NOT have it. Skip any labeled `human-review` when working issues.
- **Research Versions:** When researching, always specify the exact versions we run — Electron 42 / Chromium 148 (`build.target` is `chrome148` in `vite.config.ts`; bump in lockstep on each Electron major), @xterm/xterm + addon-fit (current beta from `package.json`), React 19. Major versions carry significant breaking changes (Electron 33→41: `console-message` signature, `WebRequestFilter` empty-`urls`, macOS 11 drop, utility-process unhandled-rejection behavior; Electron 41→42: macOS notifications require code-signing — `UNNotification` migration silently emits `failed` on unsigned dev builds, `Session.clearStorageData` drops `quotas`, `ELECTRON_SKIP_BINARY_DOWNLOAD` removed, better-sqlite3 needs a V8 14.8 patch; xterm 6.x: canvas renderer addon and `windowsMode`/`fastScrollModifier` removed, VS Code viewport/scrollbar, new event system). Don't assume older docs apply.

### Design & UX Rules

These are hard constraints. Keep CLAUDE.md to the rule itself; the full catalogs and worked examples live in the linked docs.

- **Accent Color Restraint:** The accent color (`--color-accent-primary`, `text-accent-primary`, `outline-daintree-accent`) is scarce, not a default highlight. Reserve it for _one_ load-bearing signal per active focus region (independent focus trap / arrow-key domain: macro zone, modal, popover, dropdown) — a strong focus anchor or primary CTA. Do NOT use it for multi-select state, membership markers, secondary emphasis, "also selected" indicators, arming badges, or anything applied to multiple elements at once; for those use the title-bar lift (`bg-overlay-subtle`), focus styling, or neutral surface differences. When in doubt, no accent. See the design-review checklist in `docs/themes/theme-system.md`.
- **Motion Timing:** Use the shared tiers unless the animation encodes semantic state. **Tier 1 — state changes (150ms `ease-out`):** hover/focus/active/selected/group-hover, toggle thumbs, drop-target rings, hover scrims. Bare `transition-colors` inherits the 150ms default; use `duration-150` when a duration is required. **Tier 2 — entry/exit (200ms enter / 120ms exit):** modals, popovers, dropdowns, dialogs. **Tier 2-fast — palette/tooltip (150ms enter / 100ms exit):** snappier for typed-input flow. **Tier 3 — panel motion (200ms restore / 120ms minimize):** large choreographed reflow. In TypeScript, use the constants from `src/lib/animationUtils.ts`: Tier 1 → `UI_ANIMATION_DURATION` / `TERMINAL_ANIMATION_DURATION`; Tiers 2/3 → `UI_ENTER_DURATION`, `UI_EXIT_DURATION`, `UI_PALETTE_ENTER_DURATION`, `UI_PALETTE_EXIT_DURATION`, `PANEL_RESTORE_DURATION`, `PANEL_MINIMIZE_DURATION`. **Semantic exceptions** (durations that encode meaning, not motion — `ActivityLight` decay, progress-bar width, `FileChangeList` row-recency, `SettingsSwitch` asymmetric track/thumb, etc.) must NOT be force-fixed to a tier; the decay/width/sequencing IS the signal. **Property stacking:** use the narrowest property set — never widen scoped transitions (`transition-[width]`, `transition-colors`, `transition-transform`) to bare `transition`/`transition-all`. Keep `transform` out of press snaps: either omit it from the CSS property list (toolbar style — `src/styles/components/toolbar.css`) or collapse its duration on press (button style — `src/components/ui/button.tsx` uses `transition duration-150` + `active:scale-[0.98] active:duration-[1ms]`). Box-shadow either interpolates in its own named 150ms slot or snaps with `active:shadow-none`, never both. Focus-ring transitions are wired once globally in `src/index.css` `*:focus-visible` (reduced-motion/forced-colors handled there) — components must not add per-element `outline-*` focus transitions. Full catalog: motion section in `docs/themes/theme-system.md` and `docs/themes/interaction-state-recipes.md`.
- **High-Contrast Dual-Block Guard:** The `@media (prefers-contrast: more)` and `@media (forced-colors: active)` blocks in `src/index.css` are both mandatory and must NEVER be consolidated. macOS "Increase Contrast" fires only `prefers-contrast: more` (macOS has no forced-colors mode); Windows forced-colors swaps in system colors. Consolidating would break Mac users (if forced-colors-only) or produce wrong visuals on Windows (if prefers-contrast-only with theme colors overriding the system palette). Rationale is documented inline in the `prefers-contrast: more` block comment in `src/index.css`.
- **Loading Indicators:** 400ms Doherty anti-flicker gate. **<400ms:** show nothing. **400ms–1s:** skeleton (`animate-pulse-delayed`) when the layout shape is predictable, `Spinner` only when the shape is unknown. **>1s:** skeleton mandatory for predictable shapes. **>5s:** persistent skeleton + "Still working…" placeholder. `animate-pulse-delayed` (in `src/index.css`) enforces the 400ms gate automatically via `animation-delay`; `prefers-reduced-motion`, `data-reduce-animations`, and `data-performance-mode` bypass it (force `opacity: 1` / `animation: none`). `animate-pulse-immediate` skips the gate — only for data already known to exceed the threshold (in-flight fetches). `Spinner` (`src/components/ui/Spinner.tsx`) has no built-in delay — never use it for sub-400ms waits or predictable shapes. `useDeferredLoading(isPending, UI_DOHERTY_THRESHOLD)` (`src/hooks/useDeferredLoading.ts`) is the canonical programmatic gate. Canonical example: `BrowserPaneSkeleton`. **Settings tabs:** render section chrome (header, labels, empty/disabled controls) immediately from safe defaults and populate when the bridge call resolves — never a full-area `Spinner`.
- **UI Microcopy:** Sentence case; no period on titles/buttons/labels or single-clause subtitles (periods only on multi-sentence body). Unambiguous contractions (couldn't, can't); drop "we" ("Couldn't connect", not "We couldn't connect"). **Error toasts = Title-Message-Action:** title is a verb-noun ("Connection failed"); message is 1-2 sentences on why/how-to-fix; action is a single contextual recovery button (no "Dismiss"). **Destructive buttons** use verb-noun labels ("Delete worktree", not "Delete"/"Confirm"). **Toggle labels never change with state** — title names the thing, switch position conveys state. **Confirmation dialogs:** title is a sentence-case question naming the entity (`Delete 'foo'?`); body states the specific consequence (never "Are you sure"); button is verb-noun (`Delete recipe`). **Recovery verbs:** error-boundary fallbacks use `Try again`; inline banners use `Retry`. **Toast title form:** verb-led past tense for discrete actions ("Token saved" — drop "successfully"), noun phrase for ambient state ("Connection lost"). Body never restates the title; omit it if it adds nothing. **Action-free error toasts** (the surrounding UI is itself the retry surface): opt out of lint with `// eslint-disable-next-line no-restricted-syntax -- notify-no-action: ok`.
- **Empty States:** First-run empty states name the next action — not what's absent. When two regions are empty at once (sidebar + grid), only the canvas owns the primary CTA. Completed-work states stay quiet (no quick-start lists competing with `WelcomeScreen` + `GettingStartedChecklist`); the `user-cleared` variant of `src/components/ui/EmptyState.tsx` nulls its action. **Non-obvious gotcha:** `RecipeRunner` is the first-run discovery path — gate it on `useRecipeStore((s) => s.currentProjectId) !== null && !useRecipeStore((s) => s.isLoading)`, NOT on `hasEverLaunchedAgent`. The `isLoading` half is essential: `loadRecipes()` sets `currentProjectId` synchronously before IPC resolves, so the `!== null` check alone flashes `RecipeRunnerEmpty` while in-repo recipes are still loading. Gate teaching content (tips, shortcut carousels) on `hasEverLaunchedAgent` instead — derive it from `usePanelStore` (`launchAgentId | detectedAgentId | everDetectedAgent` across `panelIds`; mirrors `useGettingStartedChecklist` in `src/hooks/app/useGettingStartedChecklist.ts`).
- **notify() Usage:** Only emit for events the user couldn't otherwise observe (completion, failure, required action). Forced-choice checklist before any `notify()`: (1) Timely — needed now? (2) Helpful — concrete next step? (3) Visible another way — already self-evident in the UI? (4) Ignorable — can the user still finish if they ignore it? If yes to ignorable, it's diagnostic — `console.warn` instead (precedent: `c41d0ab50` demoted the FD-leak warning). Four delivery surfaces, least→most restricted: **frame indicator** (`panel-state-*` on `ContentPanel` borders), **grid-bar inline** (`placement: "grid-bar"` — bypasses priority routing, subject to quiet-mode), **notification inbox** (durable bell), **toast** (default `notify()` placement — the MOST restricted, not the default of convenience). Pick the least-restricted surface that conveys the signal. `priority: "low"` skips toasts → inbox; `notify({ type: "error", priority: "low" })` is **banned** (lint-enforced) — the toast is silently dropped. A `ReactNode` `message` requires `inboxMessage` (compile-enforced by the `NotifyPayload` union in `src/lib/notify.ts`) so the persistent inbox row (the WCAG 2.2.1 alternative to the time-limited toast) stays intact. **grid-bar vs component banner:** use `notify({ placement: "grid-bar" })` for signals from outside the visible UI (background sync, app-wide state, onboarding) or with recovery elsewhere; ship a component-owned `InlineStatusBanner` (`src/components/Terminal/InlineStatusBanner.tsx`) when the signal and its recovery live in one component. `GridNotificationBar` renders above component-shipped banners in every grid layout and is single-slot (first `grid-bar` notification only; others queue). Worked examples and routing decision tree: `docs/architecture/notification-system.md` (canonical references — `useAgentWaitingNudge`, `TerminalCountWarning`, `HostCrashBanner`).
- **Runtime Signals:** Use the lowest visibility tier that keeps the signal actionable. **Tier 0 — silent log:** user can't act differently (e.g. FD-leak warning, demoted in `c41d0ab50`). **Tier 1 — ambient indicator:** non-blocking pane-chrome state (flow-status pill in `TerminalHeaderContent.tsx` for `paused-backpressure` / `suspended`; toolbar pips — vocabulary in `src/styles/components/toolbar.css` under "Pip conventions"). **Tier 2 — inline warning banner:** non-blocking risk/threshold, no failure yet (`TerminalCountWarning`). **Tier 3 — inline error banner:** pane-local failure with recovery context (`TerminalRestartStatusBanner` exit-error variant, `TerminalErrorBanner`, `SpawnErrorBanner`, `ReconnectErrorBanner` in `src/components/Terminal/`). **Tier 4 — global banner with recovery action:** multi-terminal / host-level. **Tier 4a — coordinator-arbitrated globals:** top-of-app banners competing for one slot via `useGlobalBannerPriority`, rendered through `GlobalBannerCoordinator.tsx` (mounted once in `src/App.tsx`); only the highest-priority active banner mounts, suppressed ones are unmounted. New top-of-app globals go here, not as `App.tsx` siblings; precedence ordering lives in the coordinator. A suppressible global must also route a `priority: "low"` inbox `notify()` (project-scoped `supersedeKey`) so it stays findable. When host-crash is active (`backendStatus !== "connected"`), suppress per-pane duplicate error banners with no distinct recovery. **Tier 4b — region-scoped globals:** banners owned by one surface (settings, dashboard) that mount in their own region. **Heuristic:** demote a tier if ignoring the signal changes nothing the user could do; escalate a tier if it affects multiple terminals. **Promote-trigger:** auto-recovering states stay Tier 1 (`paused-backpressure`, `paused-resource-governor`); if recovery stalls beyond 30s or exhausts retries, promote to Tier 3 with a recovery action button; multi-terminal failures go to Tier 4.
- **Destructive Action Tiers:** Calibrate safeguards to reversibility × blast radius (incident #7880). **D0 — reversible local:** no confirmation, but the inverse must exist and be discoverable (stage/unstage, dock/maximize, commit before push). **D1 — local irreversible:** `ConfirmDialog` with a verb-noun button — pane-local loss git/reflog can't recover (`terminal.kill`, `terminal.killAll`, `worktree.sessions.endAll`, `git.snapshotDelete`, recipe delete, project remove). **D2 — shared-state mutation:** `ConfirmDialog` + change preview before the mutation — anything touching remote/filesystem that needs coordination to undo (`git.push`, `worktree.delete`, `worktree.resource.teardown`, force-push, merge PR, close issue, shared-branch delete). The preview MUST show actual content (diff, message, file list, target branch); a count alone is insufficient — #7880's silent-fallback commit message wouldn't have been caught by a count. **D3 — catastrophic:** `ConfirmDialog` with `typedNameTarget` (delete repo, delete project with worktrees, teardown cloud env, cross-worktree bulk delete). **Hard rules (non-negotiable):** (1) **No silent fallback defaults** — never substitute a derived value (commit message, branch, path) without showing it first; commit submission gates on an explicitly authored message, not an "ai-note OR last-commit-message" silent chain (the #7880 root cause — treat any "if X empty, use Y" on a destructive submit as a review blocker). (2) **`danger:"confirm"` classifies the action's tier** and produces two real effects: exclusion from `ActionService.repeatLast` and from the `useActionPalette` MRU rail. Any wired `ConfirmDialog` MUST carry `danger:"confirm"` (else the action leaks into MRU); gaps in the reverse direction are tracked in the audit, not silent contradictions. (3) **Direct `window.electron.*` IPC bypasses `ActionService`** — for any D1–D3 action called directly, wire the confirm dialog in the component, flag at review, and document the IPC path in the audit. (4) **Bundled multi-step ops** (stage + commit + push) need either a preview/edit step between phases or one explicit confirmation that names both operations and shows both message and diff — never a single button chaining silent writes. Canonical surface: `src/components/ui/ConfirmDialog.tsx`. Living per-action audit + follow-up index: `docs/architecture/destructive-action-safeguards.md`.

### CI Testing Strategy

- **No tautological assertions:** Never write a test whose expected value is a literal copied from the source-of-truth with no logic between definition and assertion — these are change-detectors, not regression guards (they only "fail" when someone deliberately changes the value, then must be edited in lockstep). **Banned:** asserting a color/token/class/constant equals its own hardcoded literal (`expect(theme.background).toBe("#1e1e1e")`, `toHaveClass("text-accent-primary")`, `expect(DEFAULT_TIMEOUT).toBe(5000)`). **Test behavior instead:** computed function output (interpolation, contrast math, OKLCH), invariants/relationships (all required keys present, IDs unique, focused differs from unfocused, value within a threshold), determinism, and conditional logic (a class/state appears only when a prop warrants it). Rule of thumb: if changing the implementation value forces the same change in the test, delete the test.
- **PRs / pushes:** Typecheck, lint, format, unit tests, build on **Ubuntu only** (smoke on push only; no E2E). The five perf/size budget scripts are intentionally NOT run in CI pre-1.0 (see the dormancy note in `.github/workflows/ci.yml`) — they remain available to run locally on demand and will be reintroduced as gates once the 1.0 feature set is frozen. `ci-ok` is the sole required status check.
- **Stabilize (on demand, agent-driven):** The full cross-platform surface — check + test + build + smoke + E2E core + all seven `full-*` buckets + online + the memory-leak `nightly` suite — lives in `stabilize.yml` (`workflow_dispatch` only, input `platform` defaulting to `linux-windows`; also `windows` | `linux` | `all` | `non-windows` | `macos`). It opens NO issues; the `stabilize` skill (`.agents/skills/stabilize/`) drives it, triages flakes vs real failures from the `failed-specs-*` / `failure-report-*` artifacts, and re-runs intelligently. Watch the `stabilize-ok` gate for the verdict. The skill always runs the full gate LOCALLY first, and the dev machine is macOS — so CI normally skips macOS and only runs `linux-windows` (Windows is the usual lone straggler → iterate `platform=windows` alone). `platform=all` (adds macOS-on-CI) is rare — only when a macOS issue can't be reproduced locally. This replaced the old scheduled test-nightly and its `nightly-failure` issue noise — do not re-add a cron-driven test run or issue-creation step.
- **Nightly publish (2 AM UTC):** `nightly-publish.yml` is the ONLY thing still on a nightly cron. It builds and publishes the macOS + Linux nightly auto-update binaries to `updates.daintree.org/nightly/` (the channel users opt into in Settings → General) and runs NO test suites (only a launch smoke before publishing). It is not a validation surface; never drive it to "green."
- **Releases:** Three per-OS workflows (`release-macos.yml`, `release-linux.yml`, `release-windows.yml`, #8052), each triggered by the same `v*` tag, each a full vertical slice (checks → unit → e2e → build → R2 upload → website notify). A failure in one OS only delays that OS. E2E core + online + all seven `full-*` buckets gate each OS's publish — including Windows, because each bucket auto-shards 4 ways in `e2e.yml` (#8053), cutting a ~39min serial Windows bucket to ~10min wall-time. Failures are isolated per-OS and per-bucket.
- **E2E tiers:** `e2e/core/` smoke gates releases. The `full` tier is seven domain buckets, each its own Playwright project (`full-terminal`, `full-worktree`, `full-presets`, `full-platform`, `full-panels`, `full-resilience`, `full-plugins`); specs live in `e2e/full/<bucket>/*.spec.ts`. `e2e/online/` runs agent-integration tests against real model APIs (gates releases). `e2e/nightly/` runs memory-leak detection (the project name predates the retired test-nightly; it runs in the `stabilize` sweep and on demand). Bucket boundaries (which specs go where) are documented in `docs/e2e-testing.md`.
- **Unified E2E runner:** `.github/workflows/e2e.yml` runs every suite. Inputs: `suite` (the Playwright project) and `test_file` (optional single spec). Valid `suite` values: `full` (meta — all seven buckets sequentially; dispatch default), `core`, the seven `full-*` buckets, `online`, `nightly`.
- **Single-file E2E:** `gh workflow run "E2E Tests" --ref develop -f platform=linux -f suite=full-terminal -f test_file=e2e/full/terminal/core-terminal-search.spec.ts` — for a specific flaky test. Pass the bucket whose `testDir` contains the file as `suite`.
- **Local E2E before push:** When adding or modifying a feature with an existing E2E test, run that test (or its bucket) locally first — `npx playwright test e2e/full/terminal/core-terminal-search.spec.ts` for a single file, `npm run test:e2e:full-terminal` for the bucket.

## Architecture

Three process boundaries — `ls` shows the folder names; what matters is which process owns what and where each kind of code conventionally lives:

- **Main (`electron/`):** node-pty, git, and OS access. Backend services in `services/`; IPC handlers by domain in `ipc/handlers/` (channels in `ipc/channels.ts`); window/multi-window in `window/`; the PTY and worktree-monitoring subprocesses in `pty-host/` and `workspace-host/`.
- **Renderer (`src/`):** React 19 UI, talks to Main only via `window.electron`. Conventional homes: action definitions → `services/actions/definitions/`; per-kind panel modules → `panels/<kind>/`; Zustand stores → `store/`; UI → `components/` (by domain); React hooks → `hooks/`; IPC client wrappers → `clients/`.
- **Shared (`shared/`):** cross-process code only. Types in `types/` (incl. `ipc/`); registries and config in `config/` (`panelKindRegistry`, `agentRegistry`, …); the theme system in `theme/`.

### Actions System

Central orchestration layer for all UI operations — a unified, typed API for menus, keybindings, context menus, and agent automation.

- `ActionService` (`src/services/ActionService.ts`) — registry and dispatcher singleton.
- Action definitions live in `src/services/actions/definitions/`, grouped into functional domains registered by `actionDefinitions.ts`.
- Built-in action IDs are in `BUILT_IN_ACTION_IDS` (`shared/config/actionIds.ts`); `BuiltInActionId`, `ActionDefinition`, `ActionManifestEntry` types in `shared/types/actions.ts`.
- `dispatch(actionId, args?, options?)` executes an action; `list()` / `get(id)` introspect the MCP-compatible manifest.
- `ActionSource`: `"user" | "keybinding" | "menu" | "agent" | "context-menu"`. `ActionDanger`: `"safe" | "confirm" | "restricted"`.

### Panel Architecture

Discriminated unions for type safety:

- `PanelInstance = PtyPanelData | BrowserPanelData | DevPreviewPanelData | ReviewPanelData` (`shared/types/panel.ts`).
- `panelKindHasPty(kind)` — does a panel kind need a PTY process.
- Panel Kind Registry (`shared/config/panelKindRegistry.ts`) — config/metadata shared between processes.
- Panel Kind Modules (`src/panels/<kind>/`) — per-kind serializer, defaults factory, component; unified in `src/panels/registry.tsx`.

### Multi-Window & Project Views

Each project gets its own `WebContentsView` with an independent V8 context, managed by `ProjectViewManager` (`electron/window/ProjectViewManager.ts`). LRU eviction reclaims views under memory pressure. Per-window services are scoped via `WindowContext.services` (PortalManager, EventBuffer, MessagePorts); global services (PtyClient, WorkspaceClient) are shared across windows.

### IPC Bridge (`window.electron`)

Native features are exposed as a namespaced API via `contextBridge` in `electron/preload.cts`. Methods return Promises or Cleanups. Representative namespaces: `worktree`, `terminal`, `files`, `system`, `app`, `project`, `forge`, `git`, `portal`, `commands`, `appAgent`, `agentCapabilities`, `mcpServer`, `plugin`.

## Key Features & Implementation

- **Panels:** `PtyManager` (Main) manages node-pty processes; `terminalInstanceService` (Renderer) manages xterm.js instances.
- **Worktrees:** `WorkspaceService` polls git status; `WorktreeMonitor` tracks individual worktrees; per-view stores are backed by dedicated MessagePorts (`WorktreePortBroker`).
- **Agent State:** `AgentStateMachine` tracks idle/working/waiting/directing/completed/exited via output heuristics. `running` is a terminal runtime status, not an agent state.
- **Context:** `CopyTreeService` generates agent context and injects it into terminals.
- **Resource Profiles:** `ResourceProfileService` adaptively selects Performance/Balanced/Efficiency based on memory pressure, event-loop lag, battery state, and worktree count.

## Icons

Daintree's UI runs on Lucide icons (`lucide-react`); we don't draw bespoke glyphs for app concepts. For a Daintree-specific concept, pick the closest Lucide icon and add it to the curated alias list in `src/components/icons/index.ts` (e.g. `Plug` for agents, `FolderGit2` for worktrees, `Activity` for project pulse). The only bespoke components are the brand mark (`DaintreeIcon.tsx`), the `AgentStateCircles.tsx` indicator, `McpServerIcon.tsx`, and third-party brand marks in `src/components/icons/brands/`. See `src/components/icons/README.md`.

## Common Tasks

**Adding a new action:** add the ID to `BUILT_IN_ACTION_IDS` (`shared/config/actionIds.ts`) → create the definition in the right `src/services/actions/definitions/*.ts` → it auto-registers via the `useActionRegistry` hook.

**Adding an IPC channel:** define in `electron/ipc/channels.ts` → implement in `electron/ipc/handlers/` (domain file) → expose in `electron/preload.cts` → type in `src/types/electron.d.ts`.
