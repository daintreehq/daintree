# Daintree

**Overview:** Electron-based IDE for orchestrating AI coding agents — many agent terminals in parallel across git worktrees, with fleet broadcasting, a worktree dashboard, context injection, and an MCP control surface. Supports 15+ agent CLIs (Claude Code, Codex, Gemini, Grok, Cursor, Copilot, Aider, OpenCode, …); `shared/config/agentRegistry.ts` + `shared/config/agents/` are the roster. **Stack:** Electron 42 (Chromium 148), React 19, Vite 8, TypeScript, Tailwind CSS v4, Zustand 5, node-pty, simple-git, @xterm/xterm + addons (latest beta — see `package.json` for exact pins). Product, repo, and on-disk config dir are all "Daintree" (`daintreehq/daintree`, `.daintree/`).

## Critical Rules

- **Dependencies & Native Modules:** `npm install` for local dev; `npm ci` for reproducible CI. Both run the `postinstall` hook that rebuilds `node-pty` for Electron (unless `--ignore-scripts`). On native-module errors, run `npm run rebuild`.
- **Code Style:** Minimal comments. No decorative headers. High signal-to-noise ratio.
- **Markdown / Docs Style:** Never hard-wrap prose. Each paragraph, list item, table row, or blockquote line is ONE physical line — no manual line breaks inside it. Soft wrapping is the renderer's job; column-wrapping is diff/edit noise in these AI-first files. Applies to every `.md` (`docs/`, READMEs, etc.). Fenced code blocks and ASCII diagrams keep their internal line breaks. Blank lines still separate blocks.
- **Codex MCP:** When calling `mcp__codex__codex`, always set `model: "gpt-5.5"` — no other model is valid (ignore `o3`/`o4-mini`/etc. examples in the MCP definition). Include file paths in prompts so Codex can read the actual code.
- **GitHub Access:** Public repo `daintreehq/daintree`. Always use the `gh` CLI for all GitHub operations — HTTP fetches/scraping fail on auth.
- **Branching:** Gitflow. **All PRs target `develop` — NEVER `main`.** Only release merges go to `main`.
- **Tracked Configs:** `.daintree/recipes/*.json` — recipes are saved, parameterized agent-launch configurations (surfaced by `RecipeRunner`) — are intentionally tracked in git; never remove or gitignore them.
- **Agent Config Boundary:** Never modify user-owned agent config (`~/.claude/settings.json`, `~/.gemini/`, user hooks, CLAUDE.md/AGENTS.md/GEMINI.md in user projects, any agent-native settings) — not even via additive CLI injection like `--settings`, which still changes session behavior the user didn't opt into. If a capability requires altering user agent config, it's out of scope; use passive observation instead (output parsing, OSC title sniffing, process-tree state, `AgentPatternDetector`-style regex). Precedent: #4100.
- **Human-Review Label:** `human-review` marks issues that can't be solved autonomously (need a developer reading logs, observing runtime behavior, or making subjective UX calls) — it makes an issue 10-20x more expensive, so apply sparingly. Most issues should NOT have it. Skip any labeled `human-review` when working issues.
- **Research Versions:** When researching, always specify the exact versions we run — Electron 42 / Chromium 148 (`build.target` is `chrome148` in `vite.config.ts`; bump in lockstep on each Electron major), @xterm/xterm + addon-fit (current beta from `package.json`), React 19. Major versions carry significant breaking changes (Electron 33→41: `console-message` signature, `WebRequestFilter` empty-`urls`, macOS 11 drop, utility-process unhandled-rejection behavior; Electron 41→42: macOS notifications require code-signing — `UNNotification` migration silently emits `failed` on unsigned dev builds, `Session.clearStorageData` drops `quotas`, `ELECTRON_SKIP_BINARY_DOWNLOAD` removed, better-sqlite3 needs a V8 14.8 patch; xterm 6.x: canvas renderer addon and `windowsMode`/`fastScrollModifier` removed, VS Code viewport/scrollbar, new event system). Don't assume older docs apply.

### Design & UX Rules

These are hard constraints. Where a rule links a doc, that doc owns the full catalog/audit; rules with no pointer live only here.

- **Accent Color Restraint:** The accent color (`--color-accent-primary`, `text-accent-primary`, `outline-daintree-accent`) is scarce: at most _one_ load-bearing signal (focus anchor or primary CTA) per active focus region (independent focus trap / arrow-key domain — macro zone, modal, popover, dropdown). Never for multi-select state, membership markers, secondary emphasis, arming badges, or anything applied to multiple elements at once — use the title-bar lift (`bg-overlay-subtle`), focus styling, or neutral surface differences instead. When in doubt, no accent. Full checklist: design-review section of `docs/themes/theme-system.md`.
- **Motion Timing:** Use the shared tiers unless the animation encodes semantic state. **Tier 1 — state changes (150ms `ease-out`):** hover/focus/active/selected/group-hover, toggle thumbs, drop-target rings, hover scrims; bare `transition-colors` inherits the 150ms default. **Tier 2 — entry/exit (200ms enter / 120ms exit):** modals, popovers, dropdowns, dialogs. **Tier 2-fast — palette/tooltip (150ms enter / 100ms exit).** **Tier 3 — panel motion (200ms restore / 120ms minimize).** In TypeScript use the constants from `src/lib/animationUtils.ts`: Tier 1 → `UI_ANIMATION_DURATION` / `TERMINAL_ANIMATION_DURATION`; Tiers 2/3 → `UI_ENTER_DURATION`, `UI_EXIT_DURATION`, `UI_PALETTE_ENTER_DURATION`, `UI_PALETTE_EXIT_DURATION`, `PANEL_RESTORE_DURATION`, `PANEL_MINIMIZE_DURATION`. **Semantic exceptions** (the duration IS the signal — `ActivityLight` decay, progress-bar width, `FileChangeList` row-recency, `SettingsSwitch` asymmetric track/thumb) must NOT be force-fixed to a tier. **Property stacking:** narrowest property set — never widen scoped transitions (`transition-[width]`, `transition-colors`, `transition-transform`) to bare `transition`/`transition-all`. Keep `transform` out of press snaps: omit it from the CSS property list (toolbar style — `src/styles/components/toolbar.css`) or collapse its duration on press (button style — `src/components/ui/button.tsx` uses `transition duration-150` + `active:scale-[0.98] active:duration-[1ms]`). Box-shadow either interpolates in its own named 150ms slot or snaps with `active:shadow-none`, never both. Focus-ring transitions are wired once globally in `src/index.css` `*:focus-visible` (reduced-motion/forced-colors handled there) — components must not add per-element `outline-*` focus transitions. Transition-pattern catalog: `docs/themes/interaction-state-recipes.md`.
- **High-Contrast Dual-Block Guard:** The `@media (prefers-contrast: more)` and `@media (forced-colors: active)` blocks in `src/index.css` are separate on purpose and must NEVER be consolidated — macOS "Increase Contrast" fires only the former (macOS has no forced-colors mode); Windows forced-colors swaps in system colors. Merging breaks one platform or the other; rationale is inline in the block comments.
- **Loading Indicators:** 400ms Doherty anti-flicker gate: **<400ms** show nothing; **400ms–1s** skeleton (`animate-pulse-delayed`) when the layout shape is predictable, `Spinner` only when it isn't; **>1s** skeleton mandatory for predictable shapes; **>5s** add a "Still working…" placeholder. `animate-pulse-delayed` (in `src/index.css`) enforces the gate via `animation-delay`; `prefers-reduced-motion`, `data-reduce-animations`, and `data-performance-mode` bypass it. `animate-pulse-immediate` skips the gate — only for waits already known to exceed the threshold (in-flight fetches). `Spinner` (`src/components/ui/Spinner.tsx`) has no built-in delay — never use it for sub-400ms waits or predictable shapes. `useDeferredLoading(isPending, UI_DOHERTY_THRESHOLD)` (`src/hooks/useDeferredLoading.ts`) is the canonical programmatic gate; canonical example: `BrowserPaneSkeleton`. **Settings tabs:** render section chrome (header, labels, empty/disabled controls) immediately from safe defaults and populate when the bridge call resolves — never a full-area `Spinner`.
- **UI Microcopy:** Sentence case; no period on titles/buttons/labels or single-clause subtitles (periods only on multi-sentence body). Unambiguous contractions (couldn't, can't); drop "we" ("Couldn't connect"). **Error toasts = Title-Message-Action:** verb-noun title ("Connection failed"), 1-2 sentence message on why/how-to-fix, single contextual recovery action (no "Dismiss"). **Destructive buttons** are verb-noun ("Delete worktree", never "Delete"/"Confirm"). **Toggle labels never change with state** — the title names the thing; switch position conveys state. **Confirmation dialogs:** sentence-case question naming the entity (`Delete 'foo'?`); body states the specific consequence (never "Are you sure"); verb-noun button (`Delete recipe`). **Recovery verbs:** `Try again` in error-boundary fallbacks, `Retry` in inline banners. **Toast titles:** verb-led past tense for discrete actions ("Token saved" — drop "successfully"), noun phrase for ambient state ("Connection lost"); body never restates the title — omit it if it adds nothing. **Action-free error toasts** (the surrounding UI is itself the retry surface) opt out of lint with `// eslint-disable-next-line no-restricted-syntax -- notify-no-action: ok`.
- **Empty States:** First-run empty states name the next action — not what's absent. When two regions are empty at once (sidebar + grid), only the canvas owns the primary CTA. Completed-work states stay quiet (no quick-start lists competing with `WelcomeScreen` + `GettingStartedChecklist`); the `user-cleared` variant of `src/components/ui/EmptyState.tsx` nulls its action. **Non-obvious gotcha:** `RecipeRunner` is the first-run discovery path — gate it on `useRecipeStore((s) => s.currentProjectId) !== null && !useRecipeStore((s) => s.isLoading)`, NOT on `hasEverLaunchedAgent`. The `isLoading` half is essential: `loadRecipes()` sets `currentProjectId` synchronously before IPC resolves, so the `!== null` check alone flashes `RecipeRunnerEmpty` while in-repo recipes are still loading. Gate teaching content (tips, shortcut carousels) on `hasEverLaunchedAgent` instead — derive it from `usePanelStore` (`launchAgentId | detectedAgentId | everDetectedAgent` across `panelIds`; mirrors `useGettingStartedChecklist` in `src/hooks/app/useGettingStartedChecklist.ts`).
- **notify() Usage:** Only emit for events the user couldn't otherwise observe (completion, failure, required action). Forced-choice checklist before any `notify()`: (1) Timely — needed now? (2) Helpful — concrete next step? (3) Visible another way — already self-evident in the UI? (4) Ignorable — can the user still finish if they ignore it? If yes to ignorable, it's diagnostic — `console.warn` instead (precedent: `c41d0ab50` demoted the FD-leak warning). Four delivery surfaces, least→most restricted: frame indicator (`panel-state-*` borders), grid-bar inline (`placement: "grid-bar"`), notification inbox, toast (the default placement — and the MOST restricted, not the default of convenience); pick the least-restricted surface that conveys the signal. `priority: "low"` skips toasts → inbox; `notify({ type: "error", priority: "low" })` is **banned** (lint-enforced) — the toast is silently dropped. A `ReactNode` `message` requires `inboxMessage` (compile-enforced in `src/lib/notify.ts`) so the persistent inbox row stays intact. Use `placement: "grid-bar"` for signals from outside the visible UI or with recovery elsewhere; ship a component-owned `InlineStatusBanner` (`src/components/Terminal/InlineStatusBanner.tsx`) when the signal and its recovery live in one component (`GridNotificationBar` is single-slot and renders above component banners). Surface taxonomy + routing matrix: `docs/architecture/notification-system.md`; canonical code: `useAgentWaitingNudge`, `TerminalCountWarning`, `HostCrashBanner`.
- **Runtime Signals:** Use the lowest visibility tier that keeps the signal actionable: **Tier 0** silent log (user can't act differently) → **Tier 1** ambient pane-chrome indicator (flow-status pill in `TerminalHeaderContent.tsx`, toolbar pips — vocabulary in `src/styles/components/toolbar.css`) → **Tier 2** inline warning banner (risk/threshold, no failure yet) → **Tier 3** inline error banner with recovery context (pane-local failure) → **Tier 4** global banner with recovery action (multi-terminal / host-level; coordinator-arbitrated top-of-app or region-scoped). Demote a tier if ignoring the signal changes nothing the user could do; escalate if it affects multiple terminals. Auto-recovering states stay Tier 1; if recovery stalls beyond 30s or exhausts retries, promote to Tier 3 with a recovery action. Top-of-app globals compete for ONE slot via `useGlobalBannerPriority`, rendered through `GlobalBannerCoordinator.tsx` (mounted once in `src/components/Layout/AppLayout.tsx`) — new globals register there, never as layout siblings; a suppressible global must also route a `priority: "low"` inbox `notify()` (project-scoped `supersedeKey`). When host-crash is active (`backendStatus !== "connected"`), suppress per-pane duplicate error banners with no distinct recovery. Full tier table with enforcing code: `docs/architecture/notification-system.md`.
- **Destructive Action Tiers:** Calibrate safeguards to reversibility × blast radius (incident #7880): **D0** reversible local — no confirmation, but the inverse must exist and be discoverable; **D1** local irreversible (`terminal.kill`, recipe delete, …) — `ConfirmDialog` with a verb-noun button; **D2** shared-state mutation (`git.push`, `worktree.delete`, merge PR, …) — `ConfirmDialog` + a preview showing actual content (diff, message, file list, target branch — a count alone is insufficient); **D3** catastrophic (delete repo, delete project with worktrees) — `ConfirmDialog` with `typedNameTarget`. **Hard rules:** (1) **No silent fallback defaults** — never substitute a derived value (commit message, branch, path) without showing it first; treat any "if X empty, use Y" on a destructive submit as a review blocker (the #7880 root cause). (2) Any wired `ConfirmDialog` MUST carry `danger:"confirm"` — it excludes the action from `ActionService.repeatLast` and the `useActionPalette` MRU rail. (3) Direct `window.electron.*` IPC bypasses `ActionService` — for any D1–D3 action called directly, wire the confirm dialog in the component and document the IPC path in the audit. (4) Bundled multi-step ops (stage + commit + push) need a preview/edit step between phases or one explicit confirmation naming all operations with message and diff. Canonical surface: `src/components/ui/ConfirmDialog.tsx`; per-tier action lists + living audit: `docs/architecture/destructive-action-safeguards.md`.

### CI Testing Strategy

- **No tautological assertions:** Never write a test whose expected value is a literal copied from the source-of-truth with no logic in between (`expect(theme.background).toBe("#1e1e1e")`, `toHaveClass("text-accent-primary")`, `expect(DEFAULT_TIMEOUT).toBe(5000)`) — these are change-detectors, not regression guards. Test computed output, invariants/relationships (keys present, IDs unique, focused ≠ unfocused), determinism, and conditional logic instead. Rule of thumb: if changing the implementation value forces the same edit in the test, delete the test.
- **PRs / pushes:** Typecheck, lint, format, unit tests, build on **Ubuntu only** (smoke on push only; no E2E). The five perf/size budget scripts are intentionally NOT run in CI pre-1.0 (see the dormancy note in `.github/workflows/ci.yml`) — run them locally on demand. `ci-ok` is the sole required status check.
- **Stabilize (on demand, agent-driven):** The full cross-platform surface — check + test + build + smoke + E2E core + all seven `full-*` buckets + online + the memory-leak `nightly` suite — lives in `stabilize.yml` (`workflow_dispatch` only; input `platform` defaults to `linux-windows`, also `windows` | `linux` | `all` | `non-windows` | `macos`). The `stabilize` skill (`.agents/skills/stabilize/`) drives it: full gate locally first (the dev machine is macOS, so CI normally runs `linux-windows`; Windows is the usual lone straggler → iterate `platform=windows` alone), triage flakes vs real failures from the `failed-specs-*` / `failure-report-*` artifacts, re-run intelligently, verdict on the `stabilize-ok` gate. It opens NO issues. This replaced the scheduled test-nightly — do not re-add a cron-driven test run or issue-creation step.
- **Nightly publish (2 AM UTC):** `nightly-publish.yml` is the ONLY thing still on a nightly cron: it builds and publishes the macOS + Linux nightly auto-update binaries to `updates.daintree.org/nightly/` with a launch smoke only, no test suites. Not a validation surface — never drive it to "green."
- **Releases:** Three per-OS workflows (`release-macos.yml`, `release-linux.yml`, `release-windows.yml`), all triggered by the same `v*` tag, each a full vertical slice (checks → unit → e2e → build → R2 upload → website notify); failures are isolated per-OS. E2E core + online + all seven `full-*` buckets gate each OS's publish — buckets auto-shard 4 ways in `e2e.yml`, keeping Windows at ~10min wall-time per bucket.
- **E2E tiers:** `e2e/core/` smoke gates releases. The `full` tier is seven domain buckets, each its own Playwright project (`full-terminal`, `full-worktree`, `full-presets`, `full-platform`, `full-panels`, `full-resilience`, `full-plugins`); specs live in `e2e/full/<bucket>/*.spec.ts`. `e2e/online/` runs agent-integration tests against real model APIs (gates releases). `e2e/nightly/` runs memory-leak detection (in the stabilize sweep and on demand). Bucket boundaries: `docs/e2e-testing.md`.
- **Unified E2E runner:** `.github/workflows/e2e.yml` runs every suite — inputs `suite` (`full` meta-suite [dispatch default], `core`, the seven `full-*` buckets, `online`, `nightly`) and optional `test_file`. Single flaky spec: `gh workflow run "E2E Tests" --ref develop -f platform=linux -f suite=full-terminal -f test_file=e2e/full/terminal/core-terminal-search.spec.ts` (pass the bucket whose `testDir` contains the file as `suite`).
- **Local E2E before push:** When touching a feature with an existing E2E test, run that test or its bucket locally first — `npx playwright test <spec>` for a single file, `npm run test:e2e:full-terminal` for a bucket.

## Architecture

Three process boundaries — what matters is which process owns what and where each kind of code conventionally lives:

- **Main (`electron/`):** node-pty, git, and OS access. Backend services in `services/`; IPC handlers by domain in `ipc/handlers/` (channel registry in `ipc/channels.ts`); window/multi-window in `window/`. Utility subprocesses with crash recovery: the PTY host (`pty-host/`), worktree monitoring (`workspace-host/`), the crash watchdog (`watchdog-host*`), and the plugin dev worker (`plugin-dev-worker*`) — see `docs/architecture/crash-recovery-and-safe-mode.md`.
- **Renderer (`src/`):** React 19 UI, talks to Main only via `window.electron`. Conventional homes: action definitions → `services/actions/definitions/`; per-kind panel modules → `panels/<kind>/`; Zustand stores → `store/`; UI → `components/` (by domain); React hooks → `hooks/`; IPC client wrappers → `clients/`.
- **Shared (`shared/`):** cross-process code only. Types in `types/` (incl. `ipc/`); registries and config in `config/` (`panelKindRegistry`, `agentRegistry`, …); the theme system in `theme/`.

**State & persistence:** the renderer runs ~100 Zustand stores in two flavors — app-global vs per-project-view (`docs/architecture/state-management.md`); cross-store reads go through `src/store/storeAccessors.ts`, never a direct partner-store import at module-eval time (TDZ cycles — `docs/architecture/store-init-order.md`). Durable state spans two engines with separate migration stories: better-sqlite3 + drizzle-orm (`drizzle.config.ts`, `npm run db:generate`) and electron-store JSON (`electron/store.ts`) — `docs/architecture/persistence-and-migrations.md`.

### Actions System

Central orchestration layer for all UI operations — a unified, typed API for menus, keybindings, context menus, and agent automation.

- `ActionService` (`src/services/ActionService.ts`) — registry and dispatcher singleton; `dispatch(actionId, args?, options?)` executes, `list()` / `get(id)` introspect the manifest.
- Built-in action IDs in `BUILT_IN_ACTION_IDS` (`shared/config/actionIds.ts`); definitions in `src/services/actions/definitions/`; types in `shared/types/actions.ts`.
- `ActionSource`: `"user" | "keybinding" | "menu" | "agent" | "context-menu" | "plugin"`. `ActionDanger`: `"safe" | "confirm" | "restricted"`.
- The action manifest is also the tool surface of the local MCP server (`electron/services/mcp-server/`) — external agents and the in-app assistant drive the IDE through it under tiered authorization (`docs/architecture/mcp-server.md`).

### Panel Architecture

- `PanelInstance = PtyPanelData | BrowserPanelData | DevPreviewPanelData | ReviewPanelData` (`shared/types/panel.ts`), discriminated for type safety.
- Panel Kind Registry (`shared/config/panelKindRegistry.ts`) — cross-process config/metadata; `panelKindHasPty(kind)` answers whether a kind needs a PTY.
- Panel Kind Modules (`src/panels/<kind>/`) — per-kind serializer, defaults factory, component; unified in `src/panels/registry.tsx`.

### Multi-Window & Project Views

Each project gets its own `WebContentsView` with an independent V8 context, managed by `ProjectViewManager` (`electron/window/ProjectViewManager.ts`). LRU eviction reclaims views under memory pressure. Per-window services are scoped via `WindowContext.services`; global services (PtyClient, WorkspaceClient) are shared across windows.

### IPC Bridge (`window.electron`)

Native features are exposed as a namespaced API (~75 namespaces) via `contextBridge` in `electron/preload.cts`. Methods return Promises or Cleanups. Representative namespaces: `worktree`, `terminal`, `files`, `system`, `app`, `project`, `forge`, `git`, `portal`, `commands`, `appAgent`, `agentCapabilities`, `mcpServer`, `plugin`.

### Plugins

Manifest-driven extensions run in sandboxed utility subprocesses and contribute actions, panels, agents, toolbar buttons, and forge providers, gated by a capability + consent trust model. Host runtime in `electron/services/plugin/`; registries in `shared/config/plugin*.ts`; builtin plugins in `plugins/builtin/` — GitHub itself ships as a builtin forge plugin, keeping the host forge-neutral (`docs/architecture/forge-provider-abstraction.md`). The author-facing SDK is the npm workspace `packages/*` (`@daintreehq/plugin-sdk`, `@daintreehq/plugin-testing`, `@daintreehq/plugin-vite`, the `daintree-plugin` CLI, `create-daintree-plugin`) — build with `npm run packages:build`. Author docs: `docs/plugins/`.

## Key Features & Implementation

- **Panels:** `PtyManager` (Main) manages node-pty processes; `terminalInstanceService` (Renderer) manages xterm.js instances.
- **Worktrees:** `WorkspaceService` polls git status; `WorktreeMonitor` tracks individual worktrees; per-view stores are backed by dedicated MessagePorts (`WorktreePortBroker`).
- **Agent State:** `AgentStateService` (`electron/services/pty/AgentStateService.ts`; FSM in `shared/utils/agentFsm.ts`) tracks idle/working/waiting/directing/completed/exited via passive output heuristics. `running` is a terminal runtime status, not an agent state.
- **Context:** `CopyTreeService` generates agent context and injects it into terminals.
- **Resource Profiles:** `ResourceProfileService` adaptively selects Performance/Balanced/Efficiency based on memory pressure, event-loop lag, battery state, and worktree count.

## Icons

Daintree's UI runs on Lucide icons (`lucide-react`); we don't draw bespoke glyphs for app concepts. For a Daintree-specific concept, pick the closest Lucide icon and add it to the curated alias list in `src/components/icons/index.ts` (e.g. `Plug` for agents, `FolderGit2` for worktrees). The only bespoke components are the brand mark (`DaintreeIcon.tsx`), `AgentStateCircles.tsx`, `McpServerIcon.tsx`, and third-party brand marks in `src/components/icons/brands/`. See `src/components/icons/README.md`.

## Common Tasks

**Adding a new action:** add the ID to `BUILT_IN_ACTION_IDS` (`shared/config/actionIds.ts`) → create the definition in the right `src/services/actions/definitions/*.ts` → it auto-registers via the `useActionRegistry` hook.

**Adding an IPC channel (codegen path — the default):** write a `defineIpcNamespace` handler in `electron/ipc/handlers/<domain>.ts` with a paired `<domain>.preload.ts` (method channels + preload-bindings factory) → assign the namespace in `electron/preload.cts` → run `npm run codegen:ipc && npm run codegen:ipc-renderer` (enforced by `check:ipc` / `check:ipc-renderer`). Generated types land in `shared/types/ipc/generated*.ts`; hand-maintained shapes live in `shared/types/ipc/api.ts` / `maps.ts` (`src/types/electron.d.ts` is only the `window.electron` global shim). Legacy hand-wired channels (`electron/ipc/channels.ts` + inline preload wiring) still exist, but the `check:ipc-handwritten` ratchet blocks new ones.
