## Context

Bulk worktree creation from the GitHub issues panel was failing for the last several items in large batches (10+), because concurrent `git worktree add` runs competed for `.git/` lock files.

## Problem

#3807's fix lived entirely in the renderer: it throttled the bulk-create `PQueue` to `concurrency: 2` plus a 300ms minimum spacing (`intervalCap: 1`, `interval: 300`, `strict: true`). This put the rate-limiting decision on the wrong side of the IPC boundary — the renderer guessed at a safe git cadence with no knowledge of actual lock state, and any other producer of `worktree:create` (recipes, single-create) was unthrottled.

## Root cause

Two real causes were misattributed to "renderer queue too fast." First, the lock contention itself: issue-mode `git worktree add` was acquiring `.git/config.lock` to set up branch tracking. Second, the rate limiter that did exist was a sliding window (max=2/2s) that released both slots simultaneously every 2s — a feast/famine burst (#5098), not smooth pacing. Renderer-side interval pacing was a band-aid stacked on top of a bursty backend limiter.

## Lesson

This change was superseded. The cadence now lives in the backend and the contention was removed at the source — both as of `13703ae0f` (#5098) and `7e3c80148` (#5161):

- **Backend leaky bucket is the sole throttle.** `waitForRateLimitSlot(WORKTREE_RATE_LIMIT_KEY, WORKTREE_RATE_LIMIT_INTERVAL_MS)` (1000ms strict interval, `electron/ipc/handlers/worktree/lifecycle.ts` + `constants.ts`) reserves slots synchronously via a per-key `nextAvailableMs` (`electron/ipc/utils.ts` `leakyBucketQueues`), serializing every producer at a fixed interval. Renderer interval pacing was deleted — a second producer-side rate limiter would only conflict with it. The bulk-create `PQueue` is now `concurrency`-only (`QUEUE_CONCURRENCY = 3` in `plugins/builtin/github/renderer/components/bulkCreateUtils.ts`).
- **`--no-track` removed the lock contention at the source.** Issue-mode `git worktree add -b <branch> --no-track` (`WorkspaceService.ts:1867`) skips the `.git/config.lock` acquisition that tracking setup required. PR-mode keeps `--track` because ahead/behind badges (`WorktreeMonitor.ts`) depend on `@{u}` resolving.

Pace shared-resource operations at the single chokepoint they all flow through (the IPC handler), not in one of several UI producers. And when you can eliminate the contention itself (`--no-track`), do that before tuning queue knobs around it.

## Applies when

- Touching `BulkCreateWorktreeDialog` / `bulkCreateUtils` `PQueue` config — do NOT re-add `interval`/`intervalCap`/`strict`; cadence is owned by the backend leaky bucket.
- Adding a new producer of `worktree:create` — it inherits the `worktreeCreate` leaky-bucket slot automatically; don't add producer-side throttling.
- Tempted to fix git lock contention by slowing the queue — first check whether the git flag itself (`--no-track`, `--no-checkout`) can avoid the lock.
