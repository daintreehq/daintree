## Context

Dev preview panels whose server was running when Daintree quit hydrate with status `restored-stopped` (from the last-session manifest via `DevPreviewSessionService`); #9094 blocked those from auto-ensure so a fresh app launch never silently respawns dev servers — the panel shows a restart CTA instead. Issue #9859: the same CTA also appeared on the first mid-session switch to a project, where the user expects the server back automatically.

## Problem

The #9094 guard in `useDevServer` was `if (status === "restored-stopped") return` — it could not tell cold launch from a live switch. The obvious fix was to consult the existing `PROJECT_ON_SWITCH` provenance event, but wiring a renderer guard to it exposed the real trap: in the production multi-view world the event never arrived at all. It was only emitted by the legacy single-renderer `ProjectSwitchService.switchProject` (via `broadcastToRenderer`); the production `activateProjectView` path in `electron/ipc/handlers/projectCrud/switch.ts` (used whenever a `ProjectViewManager` resolves, i.e. always in practice) and the menu open-directory path (`handleDirectoryOpen` in `electron/menu.ts`) sent nothing.

## Root cause

The single-renderer→multi-`WebContentsView` migration replicated the switch flow into `activateProjectView` but not every renderer-bound event the old flow emitted. Because IPC events fail silent — a subscribed listener that never fires throws nothing — the omission was invisible: `projectClient`'s `ensureSubscribed()` settings-cache invalidation and `usePollingLifecycle`'s `fanOutProjectSwitch` were subscribed to an event production never sent. Nobody noticed until #9865 tried to build NEW behavior on the event and it didn't fire.

The fix couldn't be a naive port of the legacy `broadcastToRenderer` call either: in the multi-view world a broadcast reaches every `WebContentsView` including LRU-cached views for OTHER projects, which would falsely mark them as switched-to. The correct shape is a targeted `view.webContents.send(CHANNELS.PROJECT_ON_SWITCH, { project, switchId: randomUUID() })` to the activated view only — safe to send immediately because `switchTo` already awaited `did-finish-load` (same guarantee the targeted `PROJECT_WORKTREE_LOAD_STATUS` send relies on). The renderer guard used `lastSwitchId: string | null` in `projectStore` — `null` at cold launch (no switch event yet), UUID after any live switch, explicitly never hydrated from persisted storage so a stale id couldn't defeat the launch guard.

Coda: two days after merge, commit `1c30610e4` (2026-06-08) deleted `lastSwitchId` and the entire #9094 no-respawn-on-launch restriction — restored-stopped panels now auto-start unconditionally, gated only by `useDevServer`'s `initialStateResolved`. The main-process emissions were deliberately KEPT because the pre-existing `onSwitch` consumers legitimately need them. The event plumbing is the lasting artifact of #9865; `lastSwitchId` does not exist in the current codebase.

## Lesson

- **A renderer-bound event that "already exists" may only exist on the dead path.** Before building on any project-switch/lifecycle event, grep for its emit sites and check each reachable activation path emits it: `activateProjectView` (production PVM), `handleDirectoryOpen` in `electron/menu.ts`, and legacy `ProjectSwitchService` (still the `if (pvm)` fallback). The migration left `PROJECT_ON_SWITCH` wired only on the legacy path and no consumer errored — subscribed IPC listeners fail silent.
- **New switch-time signals must be added to ALL emit paths, and per-path shape differs.** The legacy broadcast carries extras (`hydrateResult`, `worktreeLoadError`) the targeted PVM send does not — consumers must survive the minimal `{ project, switchId }` payload, and anything that must reach production has to go in `activateProjectView` + `menu.ts`, not just `ProjectSwitchService`.
- **In multi-view, per-switch events are targeted sends, never `broadcastToRenderer`.** Broadcast reaches LRU-cached other-project views and falsely flags them as switched. Send to `view.webContents` after `switchTo` (which awaits `did-finish-load`, so the listener is registered).
- **Cold-launch-vs-live-switch provenance = a transient `null`-at-launch store field set only by the live IPC event, with hydration explicitly blocked** — #9865's `lastSwitchId` pattern, including a storage-poisoning test proving a persisted forged id can't survive relaunch. Reusable if the distinction is ever needed again — but it was removed by `1c30610e4` when the product decision reversed to always-auto-start; the status (`restored-stopped`) was correct in both scenarios, only the provenance differed, so fix provenance rather than widening the status enum.

## Applies when

- Building any renderer behavior on `PROJECT_ON_SWITCH` / `projectClient.onSwitch`, or adding a new renderer-bound event to the project switch/reopen/open-directory flow.
- Debugging a subscribed IPC listener that never fires in production but works in tests or looks correctly wired — check whether its emit site lives only in `ProjectSwitchService` (legacy) rather than `activateProjectView`.
- Choosing between `broadcastToRenderer` and a targeted `view.webContents.send` for anything switch-scoped in the multi-`WebContentsView` world.
- Touching the `restored-stopped` flow in `useDevServer` / `DevPreviewSessionService` — the #9094 restart-CTA-on-launch contract no longer exists (removed `1c30610e4`); do not resurrect it from old PR descriptions.
- Auditing for other single-renderer→multi-view migration gaps: any `broadcastToRenderer` or renderer event emitted only from `electron/services/ProjectSwitchService.ts` is a candidate silent no-op on the production path.
