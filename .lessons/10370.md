## Context

`DevPreviewPane` surfaces guest-renderer crashes and hangs as inline recovery banners (Reload / Hard restart), introduced in #8338. A `crashState: "none" | "crashed" | "unresponsive"` drives the banner; a "clear crash state on successful navigation" effect resets it when the user actually navigates. That effect was deliberately keyed to `[currentUrl]` only, with an explicit `eslint-disable` note ("clear on URL change only"), because it also _reads_ `crashState` inside as an early-return guard.

## Problem

The crash and unresponsive banners appeared and vanished in the same frame — the recovery buttons were never reachable, and on a repeat crash the user got only the toast with no inline recovery surface. The banner state was being set correctly; it was cleared again a render later while nothing about the URL had changed. Nothing in `handleRenderProcessGone` looked wrong, which is what made it slippery — the bug lived in an unrelated-looking navigation effect.

## Root cause

A lint-cleanup commit (`11f2d99fe`, part of PR #8338) added `crashState` to the effect's dependency array to resolve an `react-hooks/exhaustive-deps` warning. The warning fired because the effect _read_ `crashState` — but only as a bail-out guard (`if (crashState === "none") return;`), not as a trigger. Exhaustive-deps cannot distinguish "read as trigger" from "read as guard," so the mechanical fix turned the guard into a trigger. Now every `setCrashState("crashed")` re-fired the effect on the next render; `currentUrl` still held the live proxy URL (not `about:blank`), so the body's `if (currentUrl && currentUrl !== "about:blank") setCrashState("none")` passed and instantly reset the banner to `"none"`. The dependency edit silently inverted the effect's intent from "clear on URL change" to "clear the moment a crash is recorded."

The correct fix removes the state read from the effect entirely rather than feeding it to the dep array: a `lastClearedCrashUrlRef` captures the URL the effect last ran for, it early-returns when `currentUrl === lastClearedCrashUrlRef.current`, and only a genuine URL transition clears crash state (plus the 60s `crashTimestampsRef` crash-loop history). With no `crashState` read left, exhaustive-deps has nothing to flag and the deps are honestly `[currentUrl]`. This mirrors the guard already in the sibling `BrowserPane.tsx` (same comment, same `lastClearedCrashUrlRef`) — DevPreview had diverged from it. The fix (originally in `DevPreviewPane.tsx`) now lives in the extracted `useDevPreviewCrashRecovery.ts` hook; `BrowserPane.tsx` still carries the inline copy.

## Lesson

- **When exhaustive-deps flags a state your effect reads only as a bail-out guard, do NOT add it to the dep array — the guard becomes a trigger and the effect starts firing on the transitions it was meant to ignore.** Instead remove the read: derive the real trigger from a ref (`lastClearedCrashUrlRef` gating on `currentUrl === ref.current`), so the lint rule has nothing left to flag and the deps become honest. Adding the state was the entire regression.
- **Treat an `eslint-disable react-hooks/exhaustive-deps` with a "fire on X only" comment as a load-bearing invariant, not lint debt.** Mechanically "resolving" it by completing the dep array can invert the effect's intent with zero type or build error; the code compiled and shipped. Read the comment before satisfying the linter.
- **Cross-check the sibling pane before diverging.** `BrowserPane` and `DevPreviewPane` implement the same crash-banner state machine; BrowserPane already had the `lastClearedCrashUrlRef` guard with a comment naming the "instant-reset loop" exact trap. When two components mirror a pattern and one has a defensive guard the other lacks, the missing one is usually the bug.
- **A crash/error banner needs a test that asserts it stays visible across the post-set render flush, not just that the state was set.** The existing suite covered the crash-loop `notify()` but never that the banner survived — so the self-clear slipped through. #10370 added `DevPreviewPane.webview.test.tsx` tests asserting the banner text persists while `currentUrl` is unchanged (the three core ones fail against the broken effect).
- **Clear crash state on eviction outside the `webviewRef` guard.** The pane had no eviction crash-clear, so a restored panel could surface a stale banner; the fix calls `resetCrashHistory()` when `isEvicted` regardless of whether `webviewRef.current` exists (the eviction placeholder owns the visual signal in that window).

## Applies when

- Resolving a `react-hooks/exhaustive-deps` warning by adding a variable to a dep array — first check whether the effect reads that variable as a trigger or only as a bail-out guard; if it's a guard, refactor the read out instead of completing the array.
- Touching `useDevPreviewCrashRecovery.ts`, the DevPreview/Browser crash or unresponsive banners, or any effect gated by `lastClearedCrashUrlRef` / a "fire on URL change only" comment.
- Diagnosing a banner, toast, or overlay that appears and instantly disappears in the same frame while the value it keys on (URL, id) hasn't changed — suspect an effect that sets-then-clears via a dependency it shouldn't depend on.
- Reviewing a "lint cleanup" or "resolve ESLint warnings" commit that edits `useEffect`/`useCallback` dependency arrays — these are behavior changes disguised as no-ops; verify each added dep isn't a value the effect itself sets.
- Editing one of two sibling components (`BrowserPane` / `DevPreviewPane`) that share a state machine — port the guard, don't reinvent it.
