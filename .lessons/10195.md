## Context

`.github/workflows/stale-quarantine.yml` is a weekly cron that scans `e2e/` for `type: "quarantine"` test annotations older than 30 days and files/updates a per-spec `[Quarantine] Stale annotations in <path>` tracking issue via `actions/github-script@v8`. To avoid spam it dedups: fetch "the most recent comment" and skip if it already matches the report body. #10195 fixed the dedup; companion #10202 rewrote the scan/parse layer (`scripts/quarantine-scan-lib.mjs`) and added close-the-loop reconciliation.

## Problem

Every open `[Quarantine]` issue accumulated a near-identical comment every week forever — noisiest for exactly the long-unresolved quarantines the cron exists to surface (#10055); the skip path was only reachable on a same-day re-dispatch. Separately (#10040) the scan could silently _miss_ a valid quarantine and never closed a tracking issue after its annotation was fixed, so `test-quarantine` rotted with resolved-but-open entries — the exact stale-tracking failure the system exists to prevent.

## Root cause

Three independent bugs stacked into a guard that "can never match." (1) **The per-issue `GET /issues/{n}/comments` endpoint does not support `sort`/`direction` — those params are silently ignored and comments always come back ascending (oldest-first).** The code passed `per_page: 1, sort: 'created', direction: 'desc'` expecting the newest comment; it got the _oldest_ one and compared against it forever. (2) The report body embeds a **moving threshold date** (`(threshold: \`<now-30d>\`)`) recomputed each run, so raw string equality failed week-to-week even when the stale set was byte-identical. (3) **The first report for a new issue lives in the issue *body*, not a comment**, so the run right after issue creation saw zero matching comments and re-posted. Fix: `github.paginate(listComments, { per_page: 100 })`then`.filter(c => c.user?.type === 'Bot').at(-1)`, a `normalize()`stripping the`(threshold: …)`parenthetical from both sides, and an added`normalize(existing.body) === normalize(body)`check (body is already fetched by the`listForRepo` paginate).

#10202's parse bug is the same class: date extraction was a **forward line-scan** (`for i = matchLine … matchLine+4`, first quoted ISO date wins) assuming `description` follows `type:` within five physical lines. But the source-of-truth ESLint rule `scripts/eslint-rules/structured-test-skip-annotations.js` parses these via AST with **no property order and no adjacency** — `description` may precede `type`, sit lines away, or be array-form. So a quarantine valid by lint could have its date fall outside the window and hit `continue`, escaping a detector whose job is to not miss things. Replaced with `findEnclosingObjectRange`: brace-match the innermost `{…}` around the matched line (ignoring braces in strings/comments) and read _that object's own_ `description`.

## Lesson

- **The per-issue comments endpoint (`GET /issues/{n}/comments`, `octokit.issues.listComments`) ignores `sort`/`direction`; results are always oldest-first.** For the latest comment you must `github.paginate(...)` and take `.at(-1)` — `per_page: 1` gives the _oldest_, not the newest, whatever direction you pass. `listCommentsForRepo` _does_ support sort; don't copy sort params between the two.
- **A bot that posts a first report then comments on updates must dedup against `issue.body`, not just comments** — the opening report lives in the body. Filter the comment list to `c.user?.type === 'Bot'` before matching so a human reply doesn't make the bot re-post.
- **Never dedup on a body that embeds a value that moves every run** (dates, counts, timestamps). Strip the volatile part with a `normalize()` before comparing, or the guard silently never fires. Here the `(threshold: …)` date advanced 7 days weekly and defeated equality even when the payload was unchanged.
- **Don't re-derive a structured contract with a positional line-scan when an AST/lint rule already defines it.** The `+4` forward window assumed a `description` adjacency `structured-test-skip-annotations.js` never guaranteed — a latent false-negative. Extract structurally (`findEnclosingObjectRange`) and read the field by name.
- **A reconciliation loop that closes/deletes on absence must fail closed, not open.** #10202 gates the close loop on a `scanCompleted === true` sentinel and `core.setFailed()`s if the artifact is missing/unreadable; the rg step treats exit `>1` as a real error (not "no matches") — an empty match file read as "zero stale" would mass-close every open issue. Only close titles starting with the machine prefix `[Quarantine] Stale annotations in ` so hand-filed issues survive.

## Applies when

- Writing/reviewing any `actions/github-script` or octokit workflow that fetches "the latest comment" on an issue or PR — paginate; never trust `sort`/`direction` on the per-issue comments endpoint.
- Building a bot that dedups its own posts (stale trackers, changelog/status comments) — check the issue body, filter to Bot author, normalize away any per-run moving value first.
- Parsing structured annotations/config out of source text when an ESLint/AST rule already owns that contract — reuse structural extraction, don't hand-roll a fixed-line-window regex re-inventing order/adjacency assumptions.
- Adding any "close/delete when no longer present" reconciliation — prove a missing/empty/errored scan can't read as "nothing present" (sentinel + fail-closed + exit-code check + machine-owned title guard).
- Touching `.github/workflows/stale-quarantine.yml` or `scripts/quarantine-scan-lib.mjs` (`parseRipgrepMatches`, `findEnclosingObjectRange`, `scanStaleQuarantines`).
