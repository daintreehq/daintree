## Context

`AppLayout` fires a single authoritative geometry repaint on the Assistant sidebar's `transitionend` (added in #10693 to replace a per-frame `ResizeObserver` storm): `repaintAssistantAfterTransition()` read `useHelpPanelStore.getState().terminalId` and called `terminalInstanceService.repaintForReveal(id)`. This is the analogous trigger to the project-view switch-back sweep (`repaintActiveWorktreeTerminals` in `src/store/wakeActiveWorktreeTerminals.ts`), but scoped to one terminal on one DOM transition instead of a whole grid.

## Problem

On the very first cold open of the Assistant sidebar, the terminal's footer never painted. Switching to another project and back "fixed" it, which made the bug look intermittent and pointed investigation at project-switch code that was actually innocent.

## Root cause

The repaint was written as a one-shot: read state, act if present, otherwise silently return. But on a cold open the Assistant's PTY session is still provisioning when the slide transition settles, so `terminalId` is genuinely null at that instant — and nothing ever retried once it arrived. The sole authoritative geometry pass was dropped for good; the footer stayed unpainted until an unrelated geometry pass (a project switch-back) happened to fire one. That round-trip is what made the bug look non-deterministic instead of a plain missing-retry.

A second, subtler trap sits behind the fix: `terminalId` being set is not the same as the terminal being paintable. `setTerminal` publishes a **reserved** id synchronously, before `addPanel` is even awaited (#6953) — so a naive "retry once `terminalId` exists" still races the actual xterm `open()`/attach. The fix routes the retry through `terminalInstanceService.waitForAttachSettled(id, { timeoutMs })`, which resolves immediately for an already-attached terminal (free on the warm path) and only truly waits on the cold path — then drives a bounded, frame-by-frame `revealUntilStable` loop (`src/services/terminal/revealUntilStable.ts`, new — extracted out of `wakeActiveWorktreeTerminals.ts` so both callers share one retry engine) that requires `REVEAL_CONFIRM_PAINTS = 2` paints on separate frames before calling the obligation discharged, because a single paint can land before the compositor presents the frame and silently not stick.

## Lesson

- **A one-shot effect gated on `if (!stateThatMayNotExistYet) return;` triggered by a DOM lifecycle event (transitionend, animationend, load) is a latent drop bug**, not just here — turn it into a durable obligation: a flag that survives past the trigger and a store subscription that discharges it the moment the awaited state actually lands. See `createAssistantRevealCoordinator` in `src/lib/sidebarToggle.ts` for the shape (`pending`, `visible`, `generation`, `inFlight`).
- **An id/field being set is not proof the thing it names is usable.** `terminalId` publishes on reservation, well before the terminal attaches; treat "exists" and "ready" as two separate gates and wait on the actual readiness primitive (`waitForAttachSettled`) rather than the presence of the id.
- **Stamp async obligations with a monotonic generation, bumped on hide/re-settle/re-bind, and check it before every side effect.** Without it, a stale in-flight discharge from a superseded binding (a relaunch that rebinds the panel to a new terminal mid-attach-wait) can repaint a dead terminal or wrongly retire a still-live obligation.
- **Two "reveal" entry points that look interchangeable often aren't — read what each does on a missing/hidden instance before swapping one for the other.** `revealTerminal` (project-view sweep) trusts DOM visibility and reports `true` for a missing instance ("gone, nothing to retry"); `repaintForReveal` (assistant transition) keeps the `isVisible` WebGL gate (#10671) and reports `false` for missing. Using `revealTerminal` here would bank a false confirm-paint against a reserved-but-unregistered id and silently re-drop the repaint — the exact bug being fixed, reintroduced through the "equivalent" helper.
- **A single timed-out wait must be re-armed, not treated as final**, when nothing else will re-trigger the caller. `waitForAttachSettled` deregisters a timed-out waiter, so one attempt can miss a terminal that attaches a moment after the deadline with no further store edge coming; the fix retries up to `ASSISTANT_ATTACH_WAIT_ATTEMPTS = 3` (~7.5s) before finally giving the obligation up (still armed, not cancelled) for a later re-bind.
- **A drag-resize can share a code path's trigger condition (`noTransition`) without sharing its semantics.** `isAssistantResizing` also strips the CSS transition, so the settle path briefly treated a drag frame like a reveal — but `reconcileGeometryFresh` is lock-exempt, so it resized xterm/PTY mid-drag against a width the cursor had already moved past, fighting the resize lock. Guard with `!isAssistantResizing`; a drag owns its own geometry pass.

## Applies when

- Writing any repaint/reflow/geometry-sync effect fired from a CSS `transitionend`/`animationend` handler that reads Zustand/store state which may still be mid-provisioning.
- Touching `src/lib/sidebarToggle.ts`, `src/services/terminal/revealUntilStable.ts`, or `src/store/wakeActiveWorktreeTerminals.ts` — both reveal callers share `revealUntilStable` but inject different `RevealAttempt`s (`repaintForReveal` vs `revealTerminal`) for real reasons documented at each call site.
- Diagnosing an intermittent UI paint bug that "fixes itself" on an unrelated navigation/round-trip — that's usually a dropped one-shot obligation, not a race in the navigation code that appears to repair it.
- Reasoning about whether an id or reference existing in a store means the underlying resource is usable — check for a dedicated readiness/attach signal instead of trusting presence.
- Adding a second trigger path to something that already has "the sole authoritative" repaint/reconcile owner — cross-reference `HelpPanel`'s #10863 guard (a competing geometry cascade there previously corrupted xterm's line-wrap metadata racing live PTY output) before adding a parallel one.
