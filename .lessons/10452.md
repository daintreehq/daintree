## Context

The content grid derives its layout from `getTabGroups()`. When exactly two ungrouped single-panel groups exist and two-pane split is enabled (on by default, `twoPaneSplitStore.ts`), the memoized predicate `useTwoPaneSplitMode` in `src/components/Terminal/useContentGridContext.tsx` activates `TwoPaneSplitLayout`, which renders two plain `GridPanel`s with no group/tab metadata. "Duplicate panel as new tab" runs `addTabForPanel` (module-level, line 108), a multi-step Zustand mutation: `createTabGroup(...)` makes a one-panel **explicit** group for the original, then `await addPanel(...)` commits the duplicate, then `addPanelToGroup(...)` folds it in.

## Problem

With a single grid panel and split mode on (the default), clicking "Duplicate as new tab" could crash the renderer. It was masked in CI: the e2e suite `core-panel-tab-groups.spec.ts` seeded `localStorage["daintree-two-pane-split"] = false` before the store hydrated specifically to dodge this — a workaround that quietly hid a real user-facing crash (#10438). Real users with the default-on setting hit it every time.

## Root cause

The crash lives in the **gap between the two synchronous store writes of one logical mutation**, widened by the `await addPanel` in the middle. React re-renders on every store update, so `useTwoPaneSplitMode` runs against the intermediate `getTabGroups()` shape: the original panel is now a one-panel **explicit** group (`id: tabgroup-${uuid}`), and the not-yet-folded duplicate surfaces as a one-panel **virtual** group (`id === panelId`). The old predicate `twoPaneSplitEnabled && tabGroups.length === 2 && allGroupsAreSinglePanel && !maximizedId && !showPlaceholder` counted panels per group but never distinguished an explicit singleton from a virtual one, so both matched and split layout activated mid-transition. `TwoPaneSplitLayout` then rendered pane 0 as a bare `GridPanel` while that panel was already a member of an explicit tab group — the metadata mismatch crashed the renderer.

The distinguishing invariant already existed and is load-bearing: in `getTabGroups` (`src/store/slices/panelRegistry/tabGroups.ts`) a virtual single-panel group is constructed with `id: t.id` (line 375) while `createTabGroup` mints explicit groups as `tabgroup-${crypto.randomUUID()}` (line 126). The fix (line 1011) adds `allGroupsAreVirtual = tabGroups.every((g) => g.id === (g.panelIds[0] ?? ""))` to the predicate, so split mode activates only for genuinely ungrouped virtual singletons and skips the transient explicit-plus-virtual pair. The mutation was left non-atomic on purpose — the `await addPanel` can't be collapsed and the explicit group must exist before the duplicate can join it — so the resolution hardened the _observer_ rather than the _mutation_.

## Lesson

- **A multi-step store mutation with an `await` in the middle is observable by every reactive selector between the writes — treat each intermediate `getTabGroups()`/derived shape as a state the UI will actually render.** `addTabForPanel` looks atomic at the call site but re-renders fire after `createTabGroup` and again after `addPanelToGroup`; any predicate keyed off group count/shape must be valid for the in-between shape too.
- **Prefer a transient-state-proof predicate over forcing atomicity when the mutation is inherently multi-step.** Here the explicit group _must_ be created before the duplicate exists to join it, so the two-groups window is unavoidable; strengthening `useTwoPaneSplitMode` with `allGroupsAreVirtual` was lower-risk than restructuring the async flow. When a derived-layout activation is too permissive, add the term that excludes the transient shape rather than serializing the writes.
- **Use the `id === panelId` invariant to tell a virtual single-panel group from an explicit one.** Virtual groups get `id: t.id` in `getTabGroups`; explicit groups get `tabgroup-${uuid}`. `panelIds.length === 1` is NOT enough to prove a group is "just an ungrouped panel" — a freshly-created explicit singleton also has length 1. Any predicate that means "genuinely ungrouped" must check group identity, not just member count.
- **An e2e test that disables a feature "for isolation" may be hiding a crash — read the comment.** The pre-fix suite seeded `daintree-two-pane-split=false` before hydration; the comment admitted it was dodging the #10438 crash. The fix keeps split disabled for the bulk suite but adds a dedicated block that leaves split _enabled_, with a positive control (two independent panels DO activate split) so the regression assertion can't pass vacuously with the feature off.
- **`addTabForPanel` is module-level, not a hook closure, on purpose** — a statement-level try/catch inside `useContentGridContext` bails React Compiler memoization for the whole hook (#8593); it reads store actions via `panelStoreApi.getState()` at call time. Don't inline it back to "simplify."

## Applies when

- Touching `useTwoPaneSplitMode` or any derived-layout activation predicate in `useContentGridContext.tsx`, or adding a new layout that keys off `getTabGroups()` group count/shape.
- Adding or reordering steps in `addTabForPanel` (`createTabGroup` → `await addPanel` → `addPanelToGroup`) or any multi-step panel-registry mutation that reactive selectors observe between writes.
- Writing a predicate meaning "these panels are ungrouped" — assert virtual-singleton identity (`g.id === g.panelIds[0]`), never just `panelIds.length === 1`.
- Diagnosing a renderer crash on "Duplicate as new tab", tab-group creation, or split-layout activation — suspect a transient two-single-panel-group state (one explicit, one virtual), not a bug in `TwoPaneSplitLayout` itself.
- Reviewing an e2e spec that seeds `localStorage` to disable a default-on feature "for isolation" — confirm it isn't papering over a crash, and that a positive control proves the feature is exercised elsewhere.
