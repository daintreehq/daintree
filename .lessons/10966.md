## Context

The paint-fabric arc (#10954 data-plane pty-host sharding, #10955/#10961/#10962 compositor phases, #10966/#10967 this substrate) splits one project's terminals across multiple render surfaces to escape two per-`WebContentsView` ceilings: Chromium's 16-live-WebGL-context cap and the WebGL addon's module-global glyph atlas (`CharAtlasCache`, the #8080 hazard). #10966 lands the Phase 1V substrate — `SurfaceViewManager` hosts each aux surface as its own `WebContentsView`, with `SurfacePortBroker` giving it a direct pty-host `MessagePort`. Everything sits behind `DAINTREE_PAINT_FABRIC_VIEWS` (default off); the feature is still mid-build (live-wiring — registering view-backed surfaces with the compositor — is explicitly deferred), so this is forward-looking substrate a future agent will extend.

## Problem

The whole point of splitting terminals across N `WebContentsView`s is that each one gets its own 16-context WebGL budget and its own glyph atlas. The naive version of that split — just create N views loading the same app bundle URL — does not deliver this, and gives no error when it fails: Chromium's same-origin process consolidation can collapse those N views into a single renderer process, silently re-merging the very budgets the split was supposed to separate. You'd ship the feature, see no crash, no warning, and just quietly still be capped at 16 total contexts across every "isolated" surface.

## Root cause

Electron/Chromium's process-model reuses a renderer process across `WebContentsView`s that resolve to the same site/storage partition — loading the identical bundle URL from the default (or a shared) session is exactly the same-origin case the consolidation logic optimizes for. There is no visible signal when this happens; the views still render, still respond, they just share one V8/GPU process underneath. Two more Electron 42 specifics compound the hosting design: `WebContentsView`s must attach as **direct siblings** of `win.contentView` — nesting one inside another has z-order/render glitches (electron#47990) — and there is **no per-pixel input pass-through** across stacked/overlapping views (electron#49039), so two surfaces can never share a screen region and rely on "whichever is visually on top" getting the click; bounds must be geometry-disjoint by construction.

`SurfaceViewManager` closes the consolidation hole by minting a unique **non-persist** session partition per surface, nonce'd per creation: `paint-surface:{windowId}:{surfaceId}:{nonce}` (`surfaceViewPartition()` in `shared/types/paintFabricSurface.ts`). Non-persist because a paint surface has no storage worth keeping; nonce'd so a surface recreated under the same logical id never reattaches to a dead/stale session. Each view still needs the app's protocol handlers (`app://`, `daintree-file://`) re-registered on its own session (`registerProtocolsForSession`) and the CSP re-applied (`applyDaintreeAppCspToSession`) — a fresh session starts with none of that.

## Lesson

- **Any time you split a UI across multiple `WebContentsView`s to isolate a per-renderer-process resource (GPU contexts, glyph atlas, memory, crash blast radius), give each view a unique non-persist partition.** Same-origin views on a shared/default session can be silently consolidated into one process — the isolation you designed for evaporates with zero error signal. Verify with `webContents.getOSProcessId()` per view, not by assuming N views means N processes.
- **Nonce the partition per creation, not just per surface id** (`paint-surface:{windowId}:{surfaceId}:{nonce}`) — reusing a bare id-only partition across a destroy/recreate cycle risks the new view resolving to the old, possibly still-tearing-down, session. A fresh session also has nothing pre-registered: re-run protocol registration and CSP application per session (`registerProtocolsForSession`, `applyDaintreeAppCspToSession`), don't assume boot-time setup covers sessions minted later.
- **Attach new `WebContentsView`s as direct siblings of `win.contentView`, never nested inside another `WebContentsView`** — Electron 42 has documented z-order/render glitches for the nested case (electron#47990).
- **Don't design overlapping/stacked view bounds expecting per-pixel input routing** — Electron has no such pass-through (electron#49039). Validate bounds disjoint at the window boundary (`findBoundsConflicts` / `boundsAreValid` in `shared/utils/paintSurfaceGeometry.ts`) rather than relying on z-order for input correctness.
- **Tier crash recovery instead of retrying forever:** `SurfaceViewManager` reloads once on a normal crash, then flips to `crash-loop` state after `SURFACE_CRASH_LOOP_THRESHOLD` (3) crashes inside `SURFACE_CRASH_LOOP_WINDOW_MS` (60s) and hands off to the compositor's `retireSurface` instead of reloading again; a hung (not crashed) renderer is force-crashed via `forcefullyCrashRenderer()` rather than `reload()`-ed, since `reload()` on an unresponsive renderer hangs waiting on unload.

## Applies when

- Adding any auxiliary `WebContentsView` (not just paint-fabric surfaces) meant to isolate GPU budget, memory, or crash radius from the main project view — dev-preview panels, review panels, or future paint-fabric live-wiring.
- Debugging why a "per-surface" ceiling (WebGL contexts, atlas memory, crash isolation) doesn't behave as isolated as designed — check whether the views actually landed in separate OS processes before suspecting the budget math.
- Touching `SurfaceViewManager`, `SurfacePortBroker`, or the `paintSurface` IPC namespace, or wiring the deferred live half of Phase 1V (compositor registration, terminal hosting in the surface root, crash-loop → `retireSurface` notification).
- Building any feature that stacks or overlaps multiple `WebContentsView`s and assumes visual z-order implies input routing.
- Reviewing a multi-`WebContentsView` design that reuses the default/persist session across views — that reuse is itself the consolidation risk.
