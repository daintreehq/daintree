## Context

`WorkspaceHostProcess` supervises the workspace-host utility process (git status polling, worktree watching) and has a burst crash guard: give up and emit `host-crash` after `CRASH_THRESHOLD` (3) crashes inside a fixed `CRASH_WINDOW_MS` (30 min), otherwise auto-restart with capped exponential backoff.

## Problem

Issue #10729: a real machine accumulated 103 `heap-*.heapsnapshot` files totaling 5.6GB in `~/Library/Logs/Daintree/` over 10 days, one per workspace-host OOM crash at the 256MB `--max-old-space-size` cap.

The user-visible symptom pointed the wrong way: the app never showed a fatal error, it just sat stuck on the "Reconnecting…" badge (#10727) — looking like a hung connection, not a crash loop, because the burst guard's give-up path never fired.

## Root cause

V8's `setHeapSnapshotNearHeapLimit` instrumentation writes a ~55MB heap dump to disk on every near-limit crash (this is the same instrumentation #10732 found was never pruned). Writing that snapshot plus GC during the dump adds jittery extra latency to each crash, spacing consecutive OOM crashes 6-11 minutes apart in practice rather than in a tight burst. The burst guard's `crashTimestamps` array is filtered against a fixed 30-minute window on every crash (`this.crashTimestamps.filter((t) => crashAt - t < CRASH_WINDOW_MS)`), so by the time a third crash lands, the first timestamp has already aged out — the array never holds 3 entries, `CRASH_THRESHOLD` is never reached, and the host restarts forever. The diagnostic instrumentation added to catch OOM causes the exact crash cadence that evades the guard built to catch crash loops.

The fix is a second, independent detector keyed on inter-crash _interval_ rather than a fixed window: `OOM_LOOP_INTERVAL_MS = 20 * 60 * 1000` and `OOM_LOOP_THRESHOLD = 2` — two consecutive crashes each under 20 minutes apart trips `host-crash` regardless of what the burst window's `crashTimestamps.length` says. 20 minutes is deliberately wider than the burst guard's own effective reach (~15 min cadence, past which the 30-min/3 window can no longer hold three entries) so the two detectors' coverage doesn't overlap. `consecutiveShortCrashIntervals` resets on a long gap and on `manualRestart()` (mirroring #8553) but deliberately NOT on `ready` — a loop that intermittently reaches ready between crashes must still count, or the detector never trips. The heap cap was also raised 256→512MB since 256 was independently marginal for large multi-worktree projects — a mitigation, not a fix for the still-unidentified retainer (the PR says finding it needs loading a real `.heapsnapshot` into Chrome DevTools, not static analysis).

## Lesson

- **A crash-loop/burst guard keyed on a fixed time window silently stops working if something makes crashes slower** — before trusting a "N crashes in M minutes" guard, ask what could space out the crashes it's supposed to catch (a snapshot write, a core dump, GC pause, disk flush) and whether that latency can exceed `window / (threshold - 1)`.
- **Detect by inter-event interval, not just a rolling window, when the failure mode itself perturbs timing.** `OOM_LOOP_INTERVAL_MS`/`consecutiveShortCrashIntervals` in `WorkspaceHostProcess.ts` is the reusable pattern: track the gap since the previous event, increment on short gaps, reset on long gaps or explicit user action — orthogonal to any fixed-window burst counter, so it catches what the window-based one misses without needing to touch the window's own thresholds.
- **When adding a second detector alongside an existing one, size its window to not overlap the first's effective reach**, and say so in a comment — here 20 min is chosen because it's wider than the burst guard's own ~15 min effective cadence, keeping `crashGuardAlignment.test.ts` (which checks the _original_ CRASH_WINDOW_MS/CRASH_THRESHOLD pair stays internally consistent) green without needing to know about the new constants at all.
- **Reset crash-loop counters on explicit user/manual action, never on transient healthy signals like `ready`.** A process that OOMs, restarts, briefly reaches `ready`, and OOMs again is still a loop — resetting on `ready` would make the detector permanently blind to exactly the pattern it exists to catch.
- **Diagnostics that write to disk on crash (heap snapshots, core dumps) need their own retention story from day one** — #10732 (same arc) had to retroactively add `pruneHeapSnapshots`/`pruneHeapSnapshotsAsync` (`MAX_HEAP_SNAPSHOTS = 10`, strict `*.heapsnapshot` extension filtering) to `electron/utils/logger.ts` because nothing pruned the near-heap-limit dumps and one user's disk absorbed 5.6GB before anyone noticed.

## Applies when

- Adding or tuning any crash-loop / burst-restart guard (`WorkspaceHostProcess`, `PtyHostLifecycle`, `CrashLoopGuardService`, `PluginDevWorkerHost`) — check whether a slow-but-real failure mode could space events past the window's reach.
- Diagnosing a process stuck in a reconnect/restart loop that never surfaces a hard error — grep for the supervisor's crash-window filter logic and check whether the observed crash cadence actually falls inside it.
- Adding any `setHeapSnapshotNearHeapLimit`, core-dump, or other crash-triggered disk-write diagnostic — pair it with a retention/prune policy in the same PR, not as a follow-up.
- Touching `electron/services/WorkspaceHostProcess.ts` crash/restart logic or `electron/services/__tests__/crashGuardAlignment.test.ts` — the interval detector and the burst guard are intentionally decoupled constants; don't merge them into one threshold.
- Raising a utility-process `--max-old-space-size` cap to "fix" OOMs — confirm whether this is headroom for a legitimately larger workload or papering over an unidentified leak (the retainer here was left unidentified, requiring a real heap snapshot load in Chrome DevTools to find).
