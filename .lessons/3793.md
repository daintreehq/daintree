## Context

Daintree runs three V8 tiers — main process, per-project renderer WebContentsViews, and the PTY-host utility process — each tuned independently for memory footprint.

## Problem

PR #3793 added `--optimize-for-size` to the renderer js-flags and `nodeV8.setFlagsFromString("--optimize_for_size")` to the main process, betting that compact code/data would cut heap. PR #3794 separately tried to make the PTY host's `global.gc()` calls actually fire by exposing GC there. Both directions turned out to be the wrong levers and were reversed in `4b43022f7` ("perf(v8): reduce heap limits and remove --optimize-for-size").

## Root cause

`--optimize-for-size` trades JIT throughput for marginal heap savings, but the real footprint win came from simply _capping_ the heaps, not changing the compiler strategy. The revert lowered the renderer old-space limit (4096→1536 then 768 MB) and the PTY host default `memoryLimitMb` (4096→512), which dominated any optimize-for-size effect. Separately, the PTY host is forked with `execArgv: ['--max-old-space-size', '--diagnostic-dir', '--report-exclude-env']` only (`PtyHostLifecycle.ts:309`) — never `--expose-gc` — so `global.gc` is `undefined` inside the host. The `if (global.gc) global.gc()` in `stateConfig.ts:31` is a deliberate guarded no-op, not a live GC call.

## Lesson

Tune V8 memory with heap-LIMIT flags, never `--optimize-for-size`. The live flags are `--max-old-space-size` + `--max-semi-space-size` for the renderer (`main.ts:140`, plus `--expose-gc`), `setFlagsFromString("--expose_gc")` for the main process (`environment.ts:32`), and `--max-old-space-size=512` for the PTY host. `environment.test.ts:109` actively asserts `--optimize_for_size` is NOT set — treat re-adding it as a regression.

`--expose-gc` lives in the main process and renderers only. The main process surfaces it via `exposeGc` / `globalThis.__daintree_gc` (`environment.ts:30-34`). The PTY host has NO `--expose-gc` in its execArgv, by design — manual `global.gc()` was never wired into a real GC there, and execArgv flags cannot be set after fork. Do NOT assume the PTY host can force-collect after bulk terminal kills; rely on its 512 MB cap and natural GC instead. If you see `if (global.gc)` in PTY-host code, know the branch never executes.

## Applies when

- Tempted to add `--optimize-for-size` to any Daintree V8 tier (it was tried and reverted; the test guards against it)
- Profiling main/renderer/PTY-host memory and deciding which V8 flag to reach for — use heap limits
- Debugging why a `global.gc()` call in the PTY host (`stateConfig.ts`, `ResourceGovernor`) does nothing — `--expose-gc` is absent from `PtyHostLifecycle.ts` execArgv
- Adjusting utility-process `execArgv` or `memoryLimitMb` and needing to know what flags are actually present
