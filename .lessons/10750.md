## Context

Each project gets its own `WebContentsView` via `ProjectViewManager`; switching away CPU-throttles and eventually freezes it (Chromium can freeze a hidden view after ~5 min or under memory pressure). Terminal panes track WebGL eligibility (then `TerminalWebGLManager`/`shouldRestoreWebGL`, now split into `TerminalWebGLPolicy`) and repaint on switch-back via `repaintForReveal` (now `TerminalRevealController`) driven by the `wakeActiveWorktreeTerminals` sweep. PR #10750 is a six-fix batch from one investigation into "switch back to a project and the terminals look wrong," following #10632, #4935, #10671, #10362, and the hibernation-removal (#4213) lineage, each of which had patched one symptom of this same subsystem before.

## Problem

After a warm switch-back, non-focused agent panes showed mangled block glyphs for seconds (stuck on the DOM renderer instead of WebGL); a window resize during the switch was silently lost, leaving stale geometry until the next distinct resize; the reveal sweep could stop partway or hang outright; and the WebGL watchdog burned a "heavy repair slot" plus logged a spurious warning every tick for panes it could never repair. Each symptom had previously been chased and fixed in isolation — this PR is what happens when the same mechanism keeps producing new symptoms.

## Root cause

Backgrounding a `WebContentsView` doesn't just pause its work, it freezes every signal that work was updating. `requestAnimationFrame` stops firing, so a bare `new Promise(r => requestAnimationFrame(r))` — the old `nextFrame()` — can hang forever once the view is hidden, not just return stale data. `managed.isVisible`, the flag an `IntersectionObserver`/`visibilitychange` callback drives, freezes at whatever it read before the pause; on warm resume it can read stale-false even though the pane is genuinely on-screen, so anything gated on it (`wantsWebGLAtTier`, `shouldRestoreWebGL`) skipped the WebGL reattach and stranded the pane on DOM rendering. Timers/rAFs armed for "the view I'm about to leave" (`WorktreeStoreContext`'s wake/repaint backstops) have no way to know a freeze is imminent, so without an explicit signal they fire against a now-hidden view or survive to interleave with the next reactivation's sweep. A resize landing while `TerminalResizeController.isResizeLocked` (the project-switch suppression window) was previously just dropped (`return null`). And the watchdog re-checked eligibility every tick without distinguishing "not yet attached" from "can never attach here" — in DOM-mode fallback only the focus-pinned pane ever gets a context, so every other eligible-looking pane was retried and warned-about forever.

Same fix shape six times over: stop trusting a value that "should" reflect the present, substitute DOM ground truth, bound the wait, or add an explicit signal. `wantsWebGLAtTier` → `shouldRestoreWebGL` → `repaintForReveal` thread a `{ trustDomVisibility: true }` opt-in, set only by the warm-reveal sweep (`revealTerminal`) after independently proving the pane on-screen via `isConnected` + `checkVisibility` + a measured box — the assistant show/hide path omits it, since trusting DOM-truth there would accumulate a fleet-wide WebGL want and re-trip #10671's count-based DOM-flip bug. `nextFrame()` (now in `revealUntilStable.ts`) races rAF against a 250ms `setTimeout` fallback. A new `app:view-cached` IPC (now sent from `ProjectViewLifecycleController`, before the CPU throttle applies) tells the renderer to cancel in-flight wake/repaint rAFs. `resizePtyOnly` stashes a locked-out resize into `managed.pendingBackgroundResize` and replays it the instant `lockResize(id, false)` runs. `shouldHaveActiveWebGL` split off from `shouldRestoreWebGL` as a watchdog-only predicate, additionally false for a non-pinned pane while `getMode() === "dom"`.

## Lesson

- **Treat every reactive flag as potentially frozen-stale on any path reviving a backgrounded view.** Don't gate a repair on `isVisible` without a DOM-ground-truth escape hatch — `trustDomVisibility` in `TerminalWebGLPolicy`, opted into only by the warm-reveal caller, never the assistant transition path (which keeps the stale-flag gate for a different reason, #10671).
- **A bare `await requestAnimationFrame` wait must race a timeout** — rAF is fully paused on a backgrounded view. `nextFrame()` in `revealUntilStable.ts` races rAF against `setTimeout(..., 250)`; the fallback never wins foreground but is the only thing that unblocks a background wait.
- **When main knows a renderer is about to freeze, tell it before the freeze.** `app:view-cached` fires ahead of the CPU throttle so in-flight rAFs/timers can be cancelled instead of firing stale or against a hidden view; it's since become load-bearing infra reused beyond this PR (`src/lib/viewCacheState.ts`).
- **Stash-and-replay beats drop for events during a suppression window.** The old `if (isResizeLocked(id)) return null` silently lost a resize; `pendingBackgroundResize` remembers it and replays on unlock.
- **In a watchdog loop, separate "hasn't succeeded yet" from "can never succeed."** `shouldRestoreWebGL` (keep retrying, keep the pane in `wants`) vs `shouldHaveActiveWebGL` (watchdog-only, false for a non-pinned DOM-mode pane) — collapsing them either burns cycles forever or drops a pane from `wants` so it can't be pinned+attached later.
- **A hidden/visibilitychange event mid-sweep must abort the WHOLE sweep, latched.** `repaintActiveWorktreeTerminals` sets a sweep-wide `aborted` flag on the first hidden event, checked before each worker claims its next target — the switch-back starts a fresh sweep, so the old one straggling through just races it.

## Applies when

- Touching `TerminalWebGLPolicy`, `TerminalRevealController`, `revealUntilStable.ts`, or `TerminalResizeController` — split out of the single `TerminalInstanceService.ts` this PR touched, in a later oversized-file refactor; the mechanisms still live there.
- Diagnosing "switch back to a project and the terminal panes look wrong" — mangled glyphs, stale geometry after a mid-switch resize, or a reveal sweep that stalls or hangs.
- Adding an `await requestAnimationFrame`-based wait to code that can run against a backgrounded/occluded `WebContentsView` (project switch, assistant show/hide, panel reactivation).
- Writing or reviewing a watchdog loop that periodically re-checks eligibility for a repair — confirm it tells "not yet" from "never," or it spins forever.
- Reviewing a timer/rAF armed by a component that assumes its own view stays foreground — check whether it needs `app:view-cached` (or an equivalent pre-freeze signal) to cancel cleanly.
