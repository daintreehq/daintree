## Context

The settings sidebar shows a per-tab error dot driven by `SettingsValidationRegistry.tsx`: tab components call `useSettingsTabValidation(tab, hasError)`, which publishes into a context provider via a `useEffect`, and `SettingsDialog.tsx` renders the dot from `tabsWithErrors.has(tabId)`. Before #10107 the provider stored a flat `Set<SettingsTab>` with `setTabHasError(tab, bool)` / `clearTab(tab)` semantics, and each hook's effect cleanup cleared the whole tab key on unmount. About ten components publish through this hook (`CodeForgeSettingsTab`, `McpServerSettingsTab`, `WorktreeSettingsTab`, `AutomationTab`, …).

## Problem

Issue #9988: the Code Forge sidebar dot vanished while the tab body still showed its `SettingsLoadErrorBanner` — the summary surface and the detail surface contradicted each other. Two components published under the same `"code-forge"` key: `CodeForgeSettingsTab` (parent, forge-providers load error) and its conditionally-rendered child `GitHubSettingsTab` (its own load/timeout error from the GitHub config store). Every other caller used a unique key exactly once, so "one publisher per tab" was an implicit, unenforced invariant — and this nested parent+child pair was its only violator, making the bug look like a one-off instead of a class.

## Root cause

A flat `Set` keyed by tab is last-writer-wins with no notion of who registered. Two distinct wipe paths existed, and unmount is only the obvious one: (1) the child unmounts (user switches subtab) → its effect cleanup runs `clearTab("code-forge")`, deleting the parent's still-active flag; (2) the child's `hasError` transitions true→false → React runs the old effect's cleanup (`clearTab`) then the new setup (`setTabHasError(tab, false)`) — both delete the whole key, so even a perfectly well-behaved state transition in one publisher destroys the other's state. Crucially, the wipe is permanent, not transient: the parent's effect deps (`tab`, `hasError`) haven't changed, so React never re-runs its setup to restore the flag. Effect-published external state does not self-heal.

The fix refcounts publishers: a `useRef Map<SettingsTab, Set<symbol>>` is the source of truth; each hook instance holds a per-instance token from `useState(() => Symbol("settings-tab-validation"))` and only ever adds/removes its own symbol (cleanup calls `setPublisherHasError(tab, publisherId, false)`). The derived boolean is computed from `publishersByTab.current.has(tab)` and mirrored into `tabsWithErrors` React state behind an equality guard (`if (prev.has(tab) === tabHasError) return prev`) so publisher chatter doesn't churn renders. Identity is deliberately NOT `useId()` — it can change across Strict Mode renders (react#27103, cited in the code comment) — while the `useState` lazy initializer runs once per mounted instance and survives StrictMode's double render. Refcounting also makes StrictMode's mount→cleanup→remount effect cycle idempotent (cleanup removes only its own symbol, re-setup re-adds it); `SettingsValidationRegistry.test.tsx` pins this with an explicit `<StrictMode>` harness. The old wipe primitives `setTabHasError`/`clearTab` were removed from the context API entirely rather than kept alongside. Since then `GitHubSettingsTab` moved into the plugin-owned GitHub settings panel (`017aefdb1`), so the original co-publisher pair is gone — but the registry keeps multi-publisher semantics and the hook contract explicitly allows shared keys.

## Lesson

- **Any shared boolean registry keyed coarser than its publishers is a wipe waiting to happen.** If two components can publish under one key, `(key, false)`/`clear(key)` semantics let the last writer or the first unmount erase another publisher's live state. Track publisher identity and derive the key's state as OR-over-publishers (`Map<key, Set<symbol>>`), never a bare `Set<key>`.
- **Effect-published external state does not self-heal.** After a sibling wipes the flag, the victim's effect deps are unchanged, so React never re-runs the setup to restore it — the corruption persists until an unrelated dep change. Never reason "the other publisher will just re-report".
- **A true→false transition wipes too, not just unmount.** React runs old-cleanup then new-setup on a dep change; with flat semantics both calls delete the whole key. Auditing only the unmount path misses half the bug.
- **Per-instance identity in React = `useState(() => Symbol())`, not `useId()`.** `useId` exists for DOM id attributes and can differ across Strict Mode renders (react#27103), so it must never key an external registry; the lazy `useState` initializer yields a token stable for the mounted instance's lifetime and GC'd with it.
- **Keep the refcount in a `useRef` and mirror a derived value into state behind an equality guard.** The ref is authoritative and mutation-safe inside the stable callback; state updates only when membership actually flips, so N publisher calls don't cause N re-renders.
- **When generalizing a registry, delete the old wipe primitives.** #10107 removed `setTabHasError`/`clearTab` from the API instead of deprecating them — a surviving whole-key clear is an escape hatch that reintroduces the bug.

## Applies when

- Adding a `useSettingsTabValidation` call, especially a second component reporting under an existing `SettingsTab` key (a subtab, section, or conditionally-rendered child inside a parent tab).
- Building or reviewing any renderer registry where multiple components publish a boolean/flag via effects — error dots, badges, banner eligibility, suppression/focus flags — and the API shape is `(key, bool)` with no publisher identity.
- Diagnosing a contradiction between a summary indicator and its detail surface ("sidebar dot gone but the tab still shows the error banner") — suspect a co-publisher clearing the shared key.
- Reaching for `useId()` as a stable identity or key into any external store, registry, or subscription map — it is not stable under Strict Mode (react#27103).
- Assuming an unmount cleanup that clears shared state is safe because "this component owns that key" — grep for co-publishers under the same key first; the invariant is implicit and nothing enforces it.
