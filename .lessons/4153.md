## Context

Agent state is a finite-state machine driven by PTY output heuristics (busy/prompt/completion) plus a few high-confidence events (input/exit/kill/respawn). Originally the FSM had a `failed` sink, and an `error -> failed` transition plus an `isRoutineExit()` allowlist tried to decide which exits were "real" failures.

## Problem

Three iterations of the same mistake, each fixing the previous one. (1) Any `error` event drove the agent to `failed`, but agents emit noisy non-fatal stderr constantly → false failures. (2) `failed` was a terminal sink: once an agent errored, typing a new prompt left it stuck on `failed` forever even though the agent was responding. (3) The "routine exit" allowlist was hand-tuned — PR 4153 added codes 1 and 137 to it; that was wrong, because 137 (= 128 + SIGKILL) is exactly the OOM-killer/crash signature, while exit 1 (rate limit, context exhaustion) is routine.

## Root cause

The FSM was conflating two orthogonal concerns: agent lifecycle state and exit-cause diagnostics. Heuristic events are too noisy to drive a terminal failure state, and a code-by-code allowlist inverts the natural logic — crash signals are the small closed set, not routine exits.

## Lesson

There is no `failed` state. `AgentState = idle | working | waiting | directing | completed | exited` (`shared/types/agent.ts`); every exit goes to `exited` and `error` events are pure no-ops. The FSM lives once in `shared/utils/agentFsm.ts` (`nextAgentState`), re-exported by both the main process (`AgentStateMachine.ts`) and the renderer worker (`WorkerAgentStateService.ts`) — change it in one place. No state is a true sink: `exited` is escaped by `respawn`, and `input` always drives `waiting|idle|completed → working` (explicit user action flows through; heuristic signals never clear a terminal state). Exit-cause classification is decoupled into `terminalForensics.ts`, where it only decides whether to _log_, never agent state: `isRoutineExit()` is a blocklist of `CRASH_SIGNALS` (SIGILL 4, SIGABRT 6, SIGBUS 7, SIGFPE 8, SIGKILL 9, SIGSEGV 11), checked against both the raw signal and `code - 128`. So exit 137 = crash, exit 1 = routine — the opposite of what PR 4153 encoded.

## Applies when

- Touching `nextAgentState` / `VALID_TRANSITIONS` in `shared/utils/agentFsm.ts`, or assuming a `failed` agent state exists (it doesn't).
- Classifying terminal exit codes/signals as crash vs routine — use the `CRASH_SIGNALS` blocklist and the `code - 128` rule in `terminalForensics.ts`, don't reintroduce an allowlist.
- Debugging "agent stuck" or false-failure reports — check the `input → working` and `respawn → idle` escapes, and remember exit cause only affects logging, not state.
