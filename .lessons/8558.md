## Context

`WorkspaceHostProcess` supervises the per-project workspace-host utility process: on crash it schedules an auto-restart with backoff, and after too many crashes it gives up and emits `host-crash` (Tier 4a global banner) instead of respawning forever. The PTY host has the same shape in `PtyHostLifecycle`. Both follow a "three crashes within the window trip the cap" policy.

## Problem

The workspace host could respawn indefinitely in a tight crash loop. A host that crashes, boots far enough to emit `ready`, then crashes again — repeating every cycle — never accumulated toward the restart cap, so the give-up branch never fired and the user never got the `host-crash` recovery banner. The watchdog was effectively defeated by partial successes.

## Root cause

The old guard was a cumulative `restartAttempts` counter that was reset to zero on every `ready` event. Reaching `ready` between crashes — which a crash-boot-crash loop does on every cycle — zeroed the counter right before the next crash, so the count never reached the threshold. A monotonic counter only catches loops that never reach `ready`; it is blind to "boots, then dies" loops, which are the common failure mode (bad config, a poisoned project state replayed on each boot).

## Lesson

For any process supervisor that auto-respawns and must eventually give up, count crashes by **timestamp within a rolling window**, not with a counter reset on success:

- Keep `crashTimestamps: number[]`. On each crash, lazily prune entries older than `CRASH_WINDOW_MS` (`Array.filter`), push the current time, then compare `length` to `CRASH_THRESHOLD`. No proactive reset timer needed — the window decays at crash-record time.
- **Never clear `crashTimestamps` on `ready`/success.** This is the whole point: clearing on ready re-opens the exact loop you are guarding against. Both `WorkspaceHostProcess.processHostEvent` (`case "ready"`) and `PtyHostLifecycle.markReady()` carry an explicit "Do NOT clear here" comment — preserve it. Decay must be purely time-based.
- Pair it with `child-process-gone` for authoritative crash detection. Because of the Electron `exit`/`child-process-gone` ordering race (electron/electron#42283, `exit` often fires first for utility processes), defer the restart decision one tick via `setImmediate` so the authoritative `exitCode`/reason can arrive; fall back to the `exit` code if none was captured. Filter the app-global `child-process-gone` listener by the per-instance `serviceName` (matching either `details.name` or `details.serviceName`) so sibling hosts don't cross-trigger.
- In the defer window, bail if `this.child !== null` — a `manualRestart()` may have already spawned a host, and a second auto-restart would orphan it.

## Applies when

- Touching `WorkspaceHostProcess.ts`, `PtyHostLifecycle.ts`, `CrashLoopGuardService.ts`, or any new utility-process / child-process supervisor that auto-restarts on crash.
- Reviewing or adding a "max restart attempts" / "give up after N crashes" cap, restart backoff, or watchdog give-up logic.
- A bug report of "host respawns forever", "crash banner never appears", or a process that flaps (boots then dies repeatedly) without the supervisor ever giving up.
- Wiring `app.on("child-process-gone")` for crash detection, or debugging why `exit` and `child-process-gone` arrive in unexpected order (electron/electron#42283).
- Tempted to reset a crash/restart counter on a `ready`/`connected`/`healthy` event — stop and use a time-windowed count instead.
