## Context

When a terminal panel is rehydrated on project switch / reconnect, `buildArgsForBackendTerminal` and `buildArgsForReconnectedFallback` in `src/utils/stateHydration/statePatcher.ts` merge two title sources into the restored panel: the live backend/reconnected PTY record (`backendTerminal.title` / `reconnectedTerminal.title`) and the persisted `saved.title` from the on-disk panel snapshot.

## Problem

The builders assigned `title: backendTerminal.title` (and `reconnectedTerminal.title ?? saved.title`) unconditionally, letting the runtime title win. A user who renamed a session ("My Custom Name") lost the name on project switch — the panel reverted to the backend's auto/OSC-derived title ("Shell", "claude"), because the live record carries the derived title, not the user's intent.

## Root cause

The two title sources mean different things and the merge precedence was wrong for the display purpose. The backend/reconnected `title` is the _runtime_ title — auto-derived from the shell, the agent name, or an OSC 0/2 sequence the program set. `saved.title` is the _persisted user intent_ — the only place a deliberate rename survives a process restart. For the displayed panel name, persisted intent must win; the live title is a fallback for when nothing was saved. The fix is `title: saved.title ?? backendTerminal.title` on both paths (statePatcher.ts:224, :290). The non-obvious trap: the _same_ `title` field feeds a second consumer with the opposite need. `inferAgentIdFromTitle` (statePatcher.ts:144) sniffs the title for "claude"/"gemini"/etc. to recover agent identity, and there the call deliberately passes the _runtime_ title (`reconnectedTerminal.title`, statePatcher.ts:210/276) because the live title is the more reliable identity signal. So within one builder the precedence is intentionally split: runtime-title for identity inference, persisted-title for display. Collapsing them to one precedence either discards renames or misclassifies agents.

## Lesson

When a hydration builder merges a persisted snapshot with a live process record, classify each field by which side is authoritative for _that field's purpose_ — do not pick one global precedence. User-authored values (renames, pinned flags, manual ordering) are authoritative from `saved.*`; runtime-observed values (cwd the process actually has, OSC titles, detected agent identity) are authoritative from the live record. A field that serves two purposes (display name vs. identity probe) may legitimately use opposite precedence at its two call sites — keep both and comment the asymmetry, don't unify it.

## Applies when

Editing the hydration builders in `src/utils/stateHydration/statePatcher.ts`, or any merge of persisted panel/session snapshot with a live PTY-host/reconnect record where a user could have overridden a field that the runtime also derives (title, cwd, worktree binding, agent id).
