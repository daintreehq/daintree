## Context

Issue #10755 diagnosed the unit suite taking ~20 minutes on the 2-core `ubuntu-latest` CI runner versus ~80s on a 16-core dev machine, and proposed a ranked list of fixes: shard the suite into its own job, switch Vitest's `pool` from `forks` to `threads` to cut per-file process-spawn overhead, drop the counterproductive `minWorkers: 3`, and cache the Vite transform step across shards. PR #10758 implements this list against `vitest.config.ts` and `.github/workflows/ci.yml`.

## Problem

The PR's own description (`gh pr view 10758`) still reads "Threads pool: switched pool from forks (default) to threads" — but the merged `vitest.config.ts` diff shows the pool left on `forks`, with a comment explaining threads was rejected. **The PR body and title are stale relative to what actually shipped.** A future agent reading only the PR description or re-reading issue #10755's "switch to threads" recommendation would reasonably retry a change that was already attempted and reverted inside this same PR's commit history (`8b684952d` tried threads, `eb62621da` reverted it 37 minutes later, both landed before merge).

## Root cause

`@parcel/watcher`'s native addon — pulled in transitively by Daintree's file-watching services — is not context-aware. Loading it into a second `worker_thread` on Linux throws `"Module did not self-register"`. Vitest's `threads` pool shares one Node process across workers via `worker_threads`; `forks` gives each worker its own OS process. The native addon only breaks under `threads`, so the fix was to keep `pool` at its default (`forks`) rather than switch it, and get the wall-clock win from the 4-way `test` job matrix in `ci.yml` (`vitest run --shard=N/4`) instead. This is why `packages/daintree-plugin/src/__tests__/new.test.ts` still stubs `process.cwd()` via `vi.spyOn` instead of calling `process.chdir(tmpDir)` even though threads was abandoned — `chdir` is process-global and unsafe if files ever do run in shared-process parallelism, and the safer stub costs nothing under forks either, so it was kept as defense-in-depth rather than reverted alongside the pool. The `isolate: false` idea from #10755 (share the module registry across files) was never attempted at all — `ProjectStore`'s load-time `app.getPath()` side effect makes it unsafe regardless of pool. A later commit (`b1411421e`, PR #11093, three weeks after this one) shows the `minWorkers` removal wasn't the end of the story either: leaving workers uncapped at `availableParallelism()` let `maxWorkers: 8` (added for a different, dev-host RPC-teardown reason) oversubscribe the 4-core CI shards 2x and start timing out import-heavy suites — fixed by `maxWorkers: Math.min(availableParallelism(), 8)`, capping only the upper bound so it never re-forces a fixed worker count onto small runners.

## Lesson

- **Do not trust a PR's title/body as the ground truth for what shipped — read the merged diff.** #10758's title says "switch to threads pool"; the shipped `vitest.config.ts` keeps `forks`. The description wasn't updated after an in-review revert. Verify claims like "switched pool to X" against the actual current file, every time.
- **`@parcel/watcher`'s native addon cannot load into a Vitest `threads`-pool worker on Linux** (`"Module did not self-register"`, not context-aware). If a future perf pass proposes `pool: "threads"` again, this is already a closed question here — check `vitest.config.ts`'s comment block before re-attempting it.
- **On a CI runner with N physical cores, the sharding (splitting the job across N matrix runners) is what parallelizes wall-clock — the intra-process worker pool only cuts per-file overhead within one shard.** Don't conflate the two levers when diagnosing slow CI: `.github/workflows/ci.yml`'s 4-way `test` matrix did the heavy lifting here, not the pool choice.
- **A worker-count fix needs both a floor and a ceiling.** Dropping a fixed `minWorkers` fixes small runners; an unrelated later `maxWorkers` cap (added for dev-host RPC teardown) can silently oversubscribe those same small runners again. Use `Math.min(availableParallelism(), N)`, not a bare `maxWorkers: N`, whenever both a small-CI-runner and a big-dev-host constraint exist simultaneously.
- **A "deliberate non-change" called out in a PR body is a signal, not decoration** — the double `better-sqlite3` native rebuild in `vitest.global-setup.ts` (rebuild for system Node at setup, rebuild back for Electron at teardown) looks redundant but exists specifically because a `child_process`-based probe sidesteps thread-level native-module finalizer races. Don't "clean up" call-outs like this without re-deriving why they're there.

## Applies when

- Proposing or reviewing a Vitest `pool` change (`forks` → `threads`, or `isolate: false`) anywhere in this repo — check `vitest.config.ts`'s comment block first; the threads attempt and its failure mode are already documented there.
- Diagnosing slow CI unit-test wall-clock and about to propose sharding vs. pool vs. worker-count changes — these are three independent levers with different trade-offs, not one fix.
- Reading a PR description or issue proposal (`gh pr view`, `gh issue view`) to decide what to implement — cross-check the actual diff/current file before trusting prose that may predate an in-review reversal.
- Touching `vitest.config.ts` `maxWorkers`/`minWorkers`, or `.github/workflows/ci.yml`'s `test` job shard count — changes here affect both the 2-4 core CI runners and higher-core dev/stabilize hosts differently; verify against both.
- Seeing a "Module did not self-register" native-addon error inside a Vitest run — check whether `pool` is set to `threads` before assuming it's an install/build problem.
