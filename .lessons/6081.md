## Context

The PTY host is spawned via `utilityProcess.fork` in `PtyHostLifecycle.ts` (`startPtyHost`, ~line 305). node-pty 1.x hangs intermittently on modern Linux kernels when libuv batches epoll through io_uring (microsoft/node-pty#630, closed as not-planned). The documented permanent workaround is `UV_USE_IO_URING=0` in the PTY host's environment.

## Problem

The instinct is to set the workaround once on the parent — `process.env.UV_USE_IO_URING = "0"` somewhere in main-process bootstrap — and assume the forked child inherits it. It does not. `utilityProcess.fork(modulePath, args, { env })` treats `env` as a full **replacement** for the child's environment, not a merge over the parent's. If you pass an `env` object at all, anything not in it is gone — so a mutation on `process.env` made after (or even before) the fork that isn't re-spread into the explicit `env` never reaches the child.

## Root cause

Electron's `utilityProcess.fork` env semantics mirror Node's `child_process` `env`: provide it and you replace, omit it and you inherit. Daintree already passes an explicit `env` (for `DAINTREE_USER_DATA`, `DAINTREE_UTILITY_PROCESS_KIND`, perf timestamps), which is exactly why `...(process.env as Record<string, string>)` is spread first inside that object — the spread is load-bearing, not decorative. Any new variable the child needs (the io_uring workaround, a locale, `NODE_EXTRA_CA_CERTS`) must be added as a sibling key inside that same literal, gated by platform where appropriate:

```ts
env: {
  ...(process.env as Record<string, string>),
  DAINTREE_UTILITY_PROCESS_KIND: "pty-host",
  ...(process.platform === "linux" ? { UV_USE_IO_URING: "0" } : {}),
},
```

io_uring is a no-op on macOS/Windows, so the workaround is Linux-gated to avoid setting a meaningless var elsewhere.

## Lesson

When a forked Electron utility process needs an environment variable, set it inside the explicit `env` object passed to `utilityProcess.fork`, never via a `process.env` mutation in the parent — the `env` option replaces, it does not augment. The presence of `...process.env` inside that literal is the tell that the override is total. The `PtyClient.adversarial.test.ts` `FORK_ENV_DISABLES_UV_IO_URING_ON_LINUX_ONLY` case asserts both halves: present on linux, absent elsewhere — assert env vars on the actual fork call's options, not on `process.env`.

## Applies when

Forking a utility-process host (pty-host, workspace-host) and adding any environment variable it depends on — libuv/V8 flags, locale, CA bundles, feature gates — or debugging "the child doesn't see the env var I set on the parent" on the PTY/workspace hosts.
