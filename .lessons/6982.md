## Context

Toggling focus mode / the sidebar animates a sidebar slot's width. Since `<main>` (the panel grid, `flex:1`) became a flex sibling of the sidebar (#6619/#6956), it reflows every frame as the flex container redistributes space during the animation. `suppressSidebarResizes()` (`src/lib/sidebarToggle.ts`) already gated the PTY path — `terminalInstanceService.suppressResizesDuringLayoutTransition()` holds xterm `fit()`/`SIGWINCH` for the transition duration (see lesson #4170).

## Problem

The panel grid edge visibly jittered/re-snapped throughout the sidebar animation even though the PTY suppression was working correctly (#6979). The grid's `grid-template-columns` re-computed on every animation frame.

## Root cause

There were **two independent sources** of resize-driven layout work, and only one was gated. Besides the PTY `fit()` path, a React `ResizeObserver` in `useContentGridContext.tsx` observes the reflowing `<main>` and feeds its `contentRect.width` straight into `setGridWidth` → `computeGridColumns()` (`src/lib/terminalLayout.ts`) → `grid-template-columns`. Each mid-transition fractional width re-snapped the columns. Suppressing xterm/PTY resizes does nothing for these — they are pure React state updates driving CSS grid math, a completely separate code path from the PTY host. The `<main>`-is-a-flex-sibling change is what turned this observer from "fires on settled layout" into "fires every animation frame." (`useGridNavigation.ts` is no longer one of these consumers — it now reads authoritative column counts from `useContentGridContext`'s `useSyncExternalStore` snapshot rather than measuring the DOM itself, per the comment at `useGridNavigation.ts:100`; the second live gated observer today is `TwoPaneSplitLayout.tsx`, which measures `containerWidth` for divider clamping.)

## Lesson

When you gate resize work during an animated layout transition, enumerate **every** consumer that derives geometry from the animating element — not just the obvious one. A PTY/xterm resize lock and a React-layout lock are orthogonal; gating one leaves the other live.

- Use a module-level transition lock (`src/lib/layoutTransitionLock.ts`: `lockSidebarLayoutTransition(ms)` / `isSidebarLayoutTransitionLocked()` / `subscribeSidebarLayoutTransitionUnlock()`). Module scope is correct here because each project view is its own `WebContentsView`/V8 context (one grid per module scope).
- Every ResizeObserver-driven geometry consumer must `if (isSidebarLayoutTransitionLocked()) return;` in its observer callback AND skip its **initial-mount measurement** when the effect re-runs mid-lock (a dep like `gridTerminals.length` changing during the lock would otherwise commit a mid-animation width).
- The observer may emit no further entry once geometry settles, so subscribe to unlock and force one final measurement; re-check the lock inside the rAF — a second toggle can start in the ~16ms gap and you'd capture the new transition's mid-animation width.
- Keep the lock TTL synced to `SIDEBAR_TOGGLE_LOCK_MS` (CSS transition duration). New geometry consumers (e.g. `TwoPaneSplitLayout.tsx` already adopted this) must opt into the lock, not reinvent gating.

## Applies when

- Adding or reviewing any ResizeObserver that derives `gridWidth`/`gridDimensions`/column count from the panel grid `<main>` or any element that reflows during a sidebar/focus-mode/panel-split animation.
- Symptom: grid edge "jitter", column re-snap, or layout flicker during a sidebar/focus-mode toggle even though PTY/xterm resize suppression is confirmed working.
- Touching `suppressSidebarResizes()` / `sidebarToggle.ts` / `terminalLayout.ts` `computeGridColumns`, or adding a new layout that contends with the animating sidebar flex slot.
- Any time you add a second consumer of a layout dimension and only the original consumer was gated against transitions.
