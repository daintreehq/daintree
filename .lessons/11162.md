## Context

Each project gets its own `WebContentsView` (`ProjectViewManager`), cached up to a RAM-scaled limit and reclaimed by `evictStaleViews` in `ProjectViewEvictionController` when a project switch pushes the cache over that cap. Ordinary grid terminals tolerate this fine: their PTY lives in the separate pty-host process and reconnects over a MessagePort when the view is recreated. The Daintree Assistant panel is different — `HelpSessionService` spawns its PTY and pins the session to the exact `webContents.id` that provisioned it, and `onViewEvicted` calls `revokeByWebContentsId` on that pin, which `gracefulKill`s the PTY.

## Problem

Switching projects while the Assistant had dispatched a background sub-agent or long-running shell silently killed that work. The session's own transcript reported the tasks as "stopped, no completion record — may have been running when the process exited," which read like an Assistant/harness bug, not a host-side eviction. Only the conversation's resume id survived; nothing about in-flight background work did (#11157).

## Root cause

`gracefulKill` on a revoked help session doesn't just close a pty — `ProcessTreeKiller` SIGTERMs the entire process tree the Assistant spawned, so every sub-agent and shell dies with it. That kill-on-revoke policy is not an oversight: #7509 added it deliberately to stop an orphaned backend from dispatching MCP calls under a revoked token. The real bug was scope, not intent — routine LRU eviction was reusing a teardown meant for "this session is no longer trusted" against "this view just aged out of an unrelated cache," with no distinction between the two.

The fix adds a third eviction bucket in `evictStaleViews`: a view backing a **live** Assistant PTY is pulled out of the routine candidate pool entirely (a hard floor, not a sort-last preference like the existing active-agent-fallback tier). Protection needs two signals, not one: `HelpSessionService.getAssistantBackend(projectId)` resolves the _binding_ (an unrevoked session with a spawned terminal, scoped to the exact `projectViewWebContentsId` it was pinned to), and `PtyClient.hasTerminal(terminalId)` resolves _liveness_ (a main-local registry written synchronously on spawn, dropped on exit/kill). The binding alone isn't liveness — nothing clears it when the PTY exits on its own (the orphan sweep skips bound sessions), so without the liveness half a quit Assistant would pin its view forever. Agent FSM state is excluded from the check too: a dispatched sub-agent can leave the Assistant reading `idle` while the sub-agent still runs, exactly the case being protected.

## Lesson

- **A destructive teardown reused across contexts needs to know which context it's in.** `revokeByWebContentsId → gracefulKill → ProcessTreeKiller` was correct for "session revoked, no longer trusted" (#7509) and wrong for "view aged out of an LRU cache" — the fix keeps routine eviction from reaching that path for a live backend, not relaxing the kill itself.
- **When protecting a resource from an eviction/reclaim pool, "binding exists" and "resource is still live" are two different facts — require both.** `getAssistantBackend` (binding) can be stale for a PTY that already exited; only cross-checking `PtyClient.hasTerminal` (liveness, updated synchronously on spawn/exit/kill) prevents a dead assistant from permanently pinning its view.
- **Don't assume uniform PTY lifecycle across the app.** Grid-terminal PTYs live in the pty-host and reconnect over MessagePort on view recreation; the Assistant's PTY is spawned through `HelpSessionService`, pinned to a specific `webContents.id`, and dies with that view. Eviction/reclaim logic touching `ProjectViewManager` must check which kind of PTY backs a view before treating it as disposable.
- **A rejected "cheaper" fix (detach instead of kill) had concrete, checkable reasons — verify those still hold before reaching for it again.** The MCP session-to-`webContents` pin is a deliberate security boundary from #7509; repointing it needs a full token re-handshake, not a field mutation. The help/Assistant panel is also excluded from the generic panel-persistence/orphan-adoption model, so a surviving orphan backend would just get killed on the next cold provision anyway.
- **A hard floor on an eviction pool needs an escape valve and observability, or it trades one failure for another.** `lowMemoryOverride` still evicts assistant-protected views, but last, after every ordinary one; `projectview.eviction-skipped` logs the resulting cache overflow with `protectedProjectIds` so it's attributable instead of reading as a leak.
- **Don't key liveness/protection checks off agent FSM state (`idle`/`working`).** The FSM tracks the Assistant's own foreground turn, not sub-agents or shells it dispatched — an idle Assistant can still own live child processes that must not be killed.

## Applies when

- Touching `ProjectViewEvictionController.ts` (`evictStaleViews`, `hasLiveAssistantBackend`) or any LRU/reclaim pass over `ProjectViewManager`'s cached views.
- Adding a "protect this resource from eviction" bucket anywhere — check whether you need a binding check, a liveness check, or (as here) both.
- Diagnosing "Assistant/agent background work disappeared after switching projects" — the transcript resume only restores conversation history, never in-flight sub-agent or shell work.
- Considering detach-instead-of-kill for any PTY or session tied to a `WebContents` lifecycle — check for an MCP/security pin (`HelpSessionService`, #7509) and whether panel-persistence/orphan-adoption actually covers that panel kind before assuming detach is cheaper than a floor.
- Working on `HelpSessionService` (`getAssistantBackend`, `revokeByWebContentsId`) or `PtyClient.hasTerminal` and reasoning about what each one actually proves.
