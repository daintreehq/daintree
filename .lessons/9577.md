## Context

Every project gets its own `WebContentsView` via `ProjectViewManager`, and both it and the app window (`createWindow.ts`) hang recovery off `render-process-gone`: a crash-loop guard (`CRASH_LOOP_THRESHOLD` within `CRASH_LOOP_WINDOW_MS` → recovery page), an OOM path that destroys and recreates the whole window, and a default reload. #9577 (issue #9572) fixed how exit reasons route into those paths. The view-side handler has since moved from `ProjectViewManager.ts` into `electron/window/ProjectViewHandlers.ts` (#11017 file split) — the logic is intact there.

## Problem

Real out-of-memory crashes skipped the OOM recreate path and instead reloaded the view into the same memory pressure that had just killed it, which tends to OOM again immediately. Separately, OS-pressure `memory-eviction` was lumped into the generic crash branch: it incremented the crash-loop counter, fired the "crashed" toast, and consumed `getCrashRecoveryService().recordCrash()`. The code looked correct — it matched `details.reason === "oom"`, which reads like exactly the right check.

## Root cause

Chromium's reason taxonomy does not put OOM under `"oom"`. That literal reason is effectively Windows-specific (pagefile/commit exhaustion). V8/Blink heap exhaustion surfaces as `"crashed"`, and the OS OOM-killer / Linux cgroup kills surface as `"killed"` (Electron issue #40426). `exitCode` cannot disambiguate either — sources disagree on the V8-OOM value (5 vs 132), so it is kept diagnostic-only and never branched on. The fix is a probable-OOM heuristic: `reason === "oom" || (("crashed" || "killed") && availableMb < lowMemoryFreeThresholdMb)`. The threshold is resource-profile-owned (`shared/types/resourceProfile.ts`): performance = `null` (heuristic deliberately disabled on memory-unconstrained sessions), balanced = 768MB, efficiency = 1024MB. The probe is `readAvailableSystemMemoryMb()` (`electron/utils/systemMemory.ts`), which on macOS counts free + purgeable — Darwin parks reclaimable pages as purgeable, so `free` alone false-positives on every healthy Mac.

`memory-eviction` is a different animal again: the OS proactively reclaims the renderer with no V8 abort. The view goes blank and never auto-recovers — an explicit `wc.reload()` is required for the active view. And because repeated evictions under pressure are the OS working as intended, not a looping crash bug, eviction must not increment the crash-loop counter and must skip `recordCrash()` — the crash log is one-shot per session, so recording an eviction burns the slot a genuine crash needs.

## Lesson

- **Never branch OOM recovery on `details.reason === "oom"` alone.** Match `"crashed"` and `"killed"` too, gated on an available-memory probe below the profile threshold. The literal match compiles, tests green, and silently misses the two most common OOM presentations on macOS/Linux.
- **`exitCode` is diagnostic-only for OOM classification** — log it, never branch on it (V8-OOM exit code is disputed: 5 vs 132 depending on source/platform).
- **`memory-eviction` needs an explicit reload for visible surfaces and total exclusion from crash accounting.** A blank evicted view never self-heals; counting eviction as a crash both trips the loop guard falsely and pollutes the one-shot `recordCrash()` log. The same split exists in `useWebviewEvents.ts` / `BrowserPane.tsx` for webviews and `PtyHostLifecycle.ts` — new WebContents surfaces should copy this taxonomy, not the naive match.
- **Exempting a reason from the crash-loop guard removes its loop backstop — make the exempted path convergent.** #10426 had to change cached-view eviction from reload to `evictDeadView`: background-reloading an evicted renderer respawns ~100-500MB under the exact scarcity that triggered the eviction, and with the guard exemption the evict→reload→evict cycle had no bound. Eviction frees memory (convergent); reload doesn't.
- **Reuse `readAvailableSystemMemoryMb()`, don't hand-roll a probe** — the macOS free+purgeable subtlety is baked in there, and a `free`-only probe makes the OOM heuristic fire on healthy machines. A `null` threshold (performance profile) means the heuristic is intentionally off — don't "fix" the null branch.
- **The OOM recreate path must preserve the `window-all-closed` replay guard** (`beginWindowRecreating`/`endWindowRecreating` around `win.destroy()`, replay + `app.quit()` on non-darwin when recreation fails) — Electron emits `window-all-closed` synchronously inside `destroy()`, and without the replay the process hangs headless with no quit path on Windows/Linux.

## Applies when

- Touching `render-process-gone` handling in `electron/window/ProjectViewHandlers.ts`, `createWindow.ts`, `SurfaceViewManager.ts`, or any code branching on `details.reason` / `details.exitCode`.
- Adding crash recovery to a new WebContents surface (plugin panel, browser pane, dev-preview) — the reason taxonomy and eviction/crash split must be copied, not re-derived.
- Diagnosing "view crashed, reloaded, crashed again immediately" or a crash-loop recovery page appearing on a machine that was merely low on RAM.
- Assuming Chromium reason strings or exit codes are reliable OOM discriminators, or that a machine with lots of total RAM can't be memory-pressured.
- Reviewing anything that increments crash counters or calls `getCrashRecoveryService().recordCrash()` — check the memory-eviction exemption and the one-shot-log semantics survive.
