## Context

Forge PR polling (`PullRequestService.checkForPRs` / `revalidateResolvedPRs`) had a two-layer cross-window dedup pair introduced by #9077. Layer 1 = a cross-host singleflight in `forgeRpcServer.dispatchForgeRpc` that collapses concurrent identical forge RPCs. Layer 2 = a per-project poll lease (`forgePollLeaseService.ts`) meant to elect one workspace-host as the sole poller among sibling windows on the same project; non-elected siblings would short-circuit and rely on the elected host's `sys:pr:detected` / `sys:pr:cleared` fan-out. #10272 deleted layer 2 entirely.

## Problem

The lease's denial branch never executed, but it wasn't free dead code. Every `checkForPRs()` and `revalidateResolvedPRs()` cycle paid an async main↔workspace-host IPC round-trip (`forge:poll-lease-acquire`) plus 5s-timeout machinery to answer a question with exactly one possible answer ("acquired"). Worse, the carefully documented "sibling window holds poll lease" comments and single-owner ETag-baseline rationale described protection against a race that could not occur — which is why #9978 was filed on the premise of a lease-denied sibling pinned to a 5s poll cadence forever, a state that is unreachable in the real topology.

## Root cause

`WorkspaceHostPool.entries` is a `Map<string, ProcessEntry>` keyed by **normalized project path** — one workspace-host per project. `loadProject` reuses the existing entry for a project and just adds the new window to `existingEntry.windowIds` (bumping `refCount`); it does not fork a second host. The lease key was derived from the same `projectPath`, and the holder identity was the host's deterministic `serviceName`. So for any given lease key there is exactly one possible `holderId`. `acquirePollLease`'s denial guard was `existing.holderId !== holderId && expiresAt > now` — with a single possible holder per key, `holderId !== holderId` is structurally always false, so it never denied. Different projects produce different keys, and `app.requestSingleInstanceLock()` rules out a second app instance. No two live holders can ever contend on one key.

The mechanism was built against a topology that had already been retired. Per-window hosts were consolidated to per-project pooling in `d0f876691` (2026-03-30); the lease landed two months later in #9077 / `75c19c148` (2026-05-25), whose commit message still claimed "each Electron window forked its own workspace-host UtilityProcess," while `docs/architecture/process-and-window-model.md` already documented one host per open project. The author's mental model of the process model was stale at write time, and the stale claim was baked into the layer's own comments.

## Lesson

- **Before adding a lease/lock/leader-election, prove two distinct holders can actually contend on the same key under the current process topology.** `WorkspaceHostPool` pools one host per normalized project path, so the lease key (project) and the holder (`serviceName`) were 1:1 — the whole election was structurally impossible, not merely unused.
- **A coordination layer that never fires is worse than ordinary dead code when it sits on a hot path.** This one paid an IPC round-trip plus a 5s timeout every poll to answer a one-valued question. Dead code you ignore; dead coordination you pay for every tick.
- **Match the mechanism to the topology at write time, not from a remembered model.** Pooling consolidated per-window→per-project two months before #9077 landed, yet the lease's comments still said "each window forks its own host." Re-read `docs/architecture/process-and-window-model.md` before adding any cross-process arbitration to forge/workspace-host code.
- **Stale protective comments breed phantom bug reports.** #9978 ("non-elected sibling pinned to 5s cadence forever") was filed against a lease-denied-sibling state the topology makes unreachable; its root cause evaporated when the layer was removed, so #10272 superseded the pending fix. When a report describes an unreachable state, interrogate the mechanism, not the symptom.
- **Keep the dedup the topology DOES permit.** Layer 1 — the cross-host singleflight in `forgeRpcServer` (`dispatchForgeRpc` / the `inFlight` map) — still collapses concurrent identical forge RPCs across distinct-project hosts and during restart/handoff overlap. That dedup is earned; the per-project lease stacked on top of it was redundant.
- **When a regression is a subsystem's entire premise, delete the subsystem, don't patch it.** #10272 removed `forgePollLeaseService.ts`, the `forge:poll-lease-*` IPC types + handlers, the `ForgeBridge` lease methods, and all `PullRequestService` gating — rather than fixing the resolution-vs-gate ordering #9978 flagged.

## Applies when

- Adding a lease/lock/leader-election/mutex across Electron windows or utility subprocesses — first confirm two holders can contend on the same key given `WorkspaceHostPool`'s one-host-per-project pooling.
- Touching `PullRequestService.checkForPRs` / `revalidateResolvedPRs` polling, or `forgeRpcServer`'s cross-host singleflight (`dispatchForgeRpc`, the `inFlight` map).
- Diagnosing a forge bug report about a "sibling window" or multi-poller race — verify the multi-holder state is reachable before treating it as real; one host per project can make it impossible.
- Reviewing any dedup/gate that pays IPC or a timeout on a hot path — check the branch it guards can ever be taken.
- Encountering comments that say "each window forks its own workspace-host" — that per-window model was retired for per-project pooling (`d0f876691`); treat such comments as stale.
