## Context

The Context settings tab's "Test Config" button (`src/components/Project/ContextTab.tsx`, `handleTestConfig`) previews which files context generation would include using the current, possibly-unsaved form values. The renderer builds a `CopyTreeOptions` object and sends it via `copyTreeClient.testConfig` → IPC → `mergeCopyTreeOptions` (`electron/ipc/handlers/copyTree.ts`), which layers the SAVED project `settings.json` UNDER the runtime options (`runtime > project`) before running the dry run.

## Problem

Clearing a field in the unsaved form — emptying `maxContextSize` (→ unlimited), removing every excluded path, clearing `alwaysInclude` — then clicking Test Config previewed the OLD saved value, not the cleared state. Tightening a limit previewed correctly; loosening or removing one silently did not — exactly the case where a preview matters most. The dry run showed `unsaved-non-empty-fields + saved-values-for-everything-cleared`. Issue #10004.

## Root cause

The original renderer set a key only when the form had a value (`if (excludedPaths.length > 0) testOptions.exclude = ...`), so a cleared field was never added — it arrived at main as an ABSENT key. `mergeCopyTreeOptions` back-fills from saved settings whenever the runtime field is `=== undefined` (line 189: `if (copyTreeSettings.maxContextSize !== undefined && merged.maxTotalSize === undefined)`). At that guard "absent because cleared" and "absent because no override" are both `undefined`, so cleared fields were indistinguishable from "no override" and got back-filled. `undefined` was overloaded to mean two opposite intents.

The fix sends the COMPLETE form state every time, using `null` as an explicit "cleared" sentinel (`maxTotalSize: copyTreeSettings.maxContextSize ?? null`, `exclude: patterns.length > 0 ? patterns : null`). `null !== undefined`, so the `=== undefined` back-fill guards skip it; a new `stripClearedFields()` helper then deletes the null keys at EVERY return path of `mergeCopyTreeOptions`, so downstream `CopyTreeService` only ever sees `T | undefined`. The operative reason the sentinel must be non-`undefined` is this `=== undefined` merge guard — NOT the reason the code comments give. The comments and PR body claim `null` is required because "Electron's structured clone drops `undefined` keys in transit"; that is a common misconception. Verified against Electron 42 (this repo's current version): both `ipcRenderer.invoke` (V8 `ValueSerializer`) and `contextBridge` PRESERVE `undefined`-valued own properties — only `JSON.stringify` strips them. Even if you sent an explicit `maxTotalSize: undefined` and it survived the wire (it does), the `=== undefined` guard would still treat it as "no override" and back-fill. So `null` is right, but because of the defaults layer's guard, not the wire.

## Lesson

- **When a layer merges caller input over defaults using `x === undefined` as the "apply default" trigger, neither `undefined` nor an absent key can represent "explicitly cleared" — both mean "apply the default."** Send the complete state with a non-`undefined` sentinel (`null`) for cleared, so the guard sees a present value and skips back-fill. The bug class is "absent-vs-cleared collapse"; grep for `=== undefined &&` back-fill guards when a "cleared field reverts to saved value" symptom appears.
- **Strip the sentinel at the boundary so it never leaks downstream.** `stripClearedFields()` deletes `null` keys at every `return` in `mergeCopyTreeOptions`, keeping the downstream contract `T | undefined`. A sentinel that escapes its merge scope becomes a second overloaded value.
- **Do NOT cargo-cult "Electron IPC drops `undefined` keys" — modern Electron (V8 ValueSerializer + contextBridge) preserves `undefined`-valued object properties; only `JSON.stringify` strips them.** The wire-drop rationale in this PR's code comments is inaccurate; `null` is still correct, for the `=== undefined` merge-guard reason. `undefined` survives IPC — but a downstream `=== undefined` check collapses it into the default anyway, which is usually the real reason to reach for `null`.
- **Give the sentinel a scoped schema so the strict shared schema stays strict.** A dedicated `CopyTreeTestConfigOptionsSchema` (`CopyTreeOptionsSchema.unwrap().extend({...}).optional()`, `.nullish()` on the 6 clearable fields) carries `null` for test-config calls ONLY; the shared `CopyTreeOptionsSchema` used by generate/inject is untouched and can never receive a `null`. Widen validation on the one channel that needs the sentinel, never globally.
- **A dry-run/preview must reflect on-screen state, not persisted state.** Any layer that silently re-merges saved settings under a preview defeats its whole purpose. When adding "test/preview with current settings," trace whether a downstream merge re-introduces persisted values.

## Applies when

- Building or debugging any "test / preview / dry-run with current (unsaved) form values" flow where a cleared field shows a stale saved value — start at the merge/back-fill layer, not the form.
- Touching `mergeCopyTreeOptions`, `stripClearedFields`, `CopyTreeTestConfigOptions(Schema)`, or `ContextTab.handleTestConfig`, or adding a clearable field (thread it through the renderer payload, the `.nullish()` schema, and the `Omit`-based type, and confirm `stripClearedFields` removes its null).
- Designing an IPC/form payload where "cleared to empty/unlimited" must be distinguishable from "no override," and a defaults layer merges with `=== undefined` guards.
- Assuming Electron IPC / contextBridge drops `undefined` object keys (it does not), or reviewing a merge/defaults function that uses `=== undefined`/`??` to decide back-fill — check whether any caller needs to express "explicitly none."
