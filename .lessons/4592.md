## Context

Daintree runs many agent terminals concurrently. After an agent session completes, its xterm.js instance stayed at the VISIBLE tier indefinitely, holding scrollback buffers, addons (fit, search, weblinks), and canvas allocations in memory.

## Problem

Completed agent terminals were never downgraded from VISIBLE to BACKGROUND tier. At the time, BACKGROUND had a lower scrollback limit and was eligible for full hibernation (destroying the xterm instance and reclaiming all memory). With 10+ completed agents, this held tens of MB of xterm state unnecessarily.

Update: per-terminal hibernation was fully removed in PR #10811 — `TerminalHibernationManager` and `scheduleHibernation` no longer exist. `src/services/terminal/TerminalInstanceService.ts` now carries `EXPERIMENT (hibernation removal)` comments, and its `subscribeHibernation` is a stub that always reports "no hibernation occurred" because the xterm instance is kept fully live in the background regardless of tier. BACKGROUND today governs refresh throttling and WebGL context budget only — it no longer reclaims scrollback/addon memory by itself. The push-model teaching below (react to lifecycle events, not idle timers) is what survives; the specific "hibernation reclaims memory" mechanism it originally fed does not.

Additionally, `ProcessMemoryMonitor` thresholds were too relaxed, giving too little headroom before the renderer approached OS memory limits. (Thresholds have since been refactored from absolute MB values to fractions of total device RAM in `electron/services/ProcessMemoryMonitor.ts`, so they scale across machines.)

## Root cause

The hibernation system used an idle timer approach: terminals were only considered for downgrade after a period of inactivity. Completed agent terminals were not treated as a special case that should immediately drop to BACKGROUND tier regardless of their last activity time.

The fix wires agent completion directly into the refresh-tier computation: `getTerminalRefreshTier` in `src/store/panelStore.ts` keeps active agent terminals at `VISIBLE` but drops `completed`/`exited` agents to `BACKGROUND`. This is a **push** model rather than a **poll** model — the store knows exactly when an agent finishes (via `agentState`) and triggers the downgrade proactively instead of waiting for an idle timer. At the time this shipped, the BACKGROUND downgrade also made a terminal eligible for the per-terminal hibernation that `TerminalHibernationManager`/`scheduleHibernation` scheduled in `TerminalInstanceService`; that hibernation system was fully removed in PR #10811, so today the same downgrade only affects refresh throttling and WebGL budget — the push-vs-poll lesson still applies to whatever consumes the tier.

## Lesson

- xterm.js instances are expensive: each holds scrollback (configurable line buffer), addon state, and canvas context.
- Don't rely solely on idle timers for memory/resource reclamation when you have precise lifecycle events (agent completed, panel hidden) — use those events to trigger immediate tier downgrades.
- Drop completed/exited agent terminals to the `BACKGROUND` tier in the refresh-tier computation (`getTerminalRefreshTier` in `src/store/panelStore.ts`) in response to any agent lifecycle event (completion, exit, error). The store already tracks `agentState` per terminal session; use it.
- Memory monitor thresholds should scale with device RAM (fractions of `os.totalmem()`, as `ProcessMemoryMonitor` now does) so headroom holds across machines, rather than hard-coding absolute MB limits.
- Don't assume a tier/state name keeps its original meaning: BACKGROUND once implied "hibernation-eligible"; PR #10811 removed per-terminal hibernation entirely, so BACKGROUND now means "throttled refresh + capped WebGL budget," not "reclaims memory." Check what a tier currently drives before reusing it as a memory-reclamation lever.

## Applies when

- Adding new agent lifecycle events (completion, cancellation, error)
- Any code that checks `AgentStateMachine` state transitions
- Tuning `ProcessMemoryMonitor` thresholds for different workloads
- Reasoning about what the `BACKGROUND` refresh tier actually does today (refresh throttling / WebGL budget, not hibernation)
