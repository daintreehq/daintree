## Context

GitHub enforces two distinct rate limits: a primary quota (`x-ratelimit-remaining`/`x-ratelimit-reset` headers) and a secondary/abuse limit (signalled by `retry-after`, or a 403/429 body with no header at all). Blindly retrying through a _secondary_ limit can escalate to a permanent token ban — GitHub documents this. Daintree polls GitHub from two processes (main `getRepoStats`/`getProjectHealth`/`batchCheckLinkedPRs`, and the workspace-host `PullRequestService` revalidation loop), so the rate-limit state must be observed everywhere a request is issued and shared across the process boundary. Implemented in `plugins/builtin/github/main/GitHubRateLimitService.ts` (rehomed from `electron/services/github/` by #8060; a 2-line compat shim remains at the old path).

## Problem

There is no clean place to read GitHub rate-limit headers. `@octokit/graphql` v9 resolves the promise to the parsed `data.data` payload and drops the raw `Response` (and its headers) before you ever see it — so you cannot read `x-ratelimit-*` from the awaited result. Worse, classification can only happen on the body for secondary limits, and reading the body blocks the response from flowing back. And once you do propagate "blocked" across processes, a 403 emitted by the _old_ token can arrive at main _after_ a credential rotation has cleared state, re-blocking the freshly-valid token with a phantom limit.

## Root cause

(1) Octokit strips the `Response` before resolving, so the only reliable observation point for headers on _every_ call (2xx and error) is a custom `fetch` wrapper installed via `graphql.defaults({ request: { fetch } })` — see `rateLimitAwareFetch` in `plugins/builtin/github/main/GitHubAuth.ts`. (2) Secondary-limit detection needs the response _body_, which is async; doing it inline would stall every GitHub call behind a slow/stuck stream — hence two-phase classification: Phase 1 header-only runs immediately, Phase 2 reads `response.clone().text()` only on 403/429 (small, already-buffered) before releasing the request slot. (3) Cross-process rate-limit events carry no notion of _which token observed them_; a stale "blocked" event is indistinguishable from a fresh one once it crosses the MessagePort.

## Lesson

Intercept rate limits at the `fetch` wrapper, not the Octokit result — it is the only layer that still has the headers and covers both success and error paths uniformly. Classify primary vs secondary explicitly and _park_ (set `nextRetryAt = resumeAt`) instead of retrying; never increment the circuit-breaker for a secondary limit (`PullRequestService.handleError` takes a `rateLimit` marker captured _synchronously alongside the failing request_ via `rateLimitMeta()`, because re-reading the mutable singleton in the handler races a concurrent 2xx clearing state between the 429 and the handler). Add a clock-skew buffer (7s, `PRIMARY_RESET_BUFFER_MS`) to `x-ratelimit-reset` so a poll doesn't slip in a tick before the server actually clears the quota. For cross-process propagation, stamp the time of the last credential change (`forgeCredentialChangeAt` in `WorkspaceHostEventRouter.ts`) and _suppress_ any forwarded `remaining === 0` block event arriving within a guard window (`RATE_LIMIT_TOKEN_CHANGE_GUARD_MS = 5s`) of a rotation — unblock events are always safe to apply, only stale _blocks_ corrupt state. The same shape now generalises to any forge provider keyed by `providerId`.

## Applies when

Wrapping any third-party HTTP client (Octokit, SDKs) that hides the raw response and you need response headers or status for throttling/observability — wrap `fetch`, not the result. Also when propagating throttle/block state across the main/utility-process boundary while credentials can rotate underneath: guard against stale blocks predating the rotation, and capture the block marker synchronously with the failing request rather than reading shared mutable state in a later handler.
