## Context

Forge PR polling lives in the workspace-host: `PullRequestService.scheduleNextPoll()` clamps the poll interval to `FOCUS_CATCHUP_THROTTLE_MS` (5s) whenever `providerNamespacedId` is null and `consecutiveErrors === 0`. That clamp is a deliberate cold-start catch-up — the forge provider registry lives in main and is populated asynchronously by `PluginService.initialize()`, so the host's first poll routinely beats it, and without the clamp a blurred-cadence (120s) project would show empty PR sub-rows for two minutes after every launch. Resolution crosses the process boundary via `forgeBridge.resolveProvider()` → `invokeResolveProvider` in `electron/services/forgeRpcServer.ts`, which matches the remote hostname against descriptors registered at manifest scan-time.

## Problem

For any project whose remote matched no registered provider (GitLab/Bitbucket/self-hosted before the GitLab builtin #11062, or no remote at all), PR polling never settled: every 5s tick ran an `acquirePollLease` IPC round-trip, a `resolveProvider` bridge RPC into main, and 1–2 `git config` subprocess spawns — roughly 17k git subprocesses per day per affected project, indefinitely (#9997). Blurring the app didn't help: the clamp is applied after focused/blurred cadence selection (`Math.min(interval, 5000)`), so only a full background `pause()` stopped it. The cost was invisible in the UI — nothing was broken, the poller just could never produce anything.

## Root cause

`invokeResolveProvider` collapsed four distinct failure modes — no registry entry, descriptor matched but no impl bound after activation, no remote URL, remote parse failure — into a single `null`, byte-identical to "the plugin scan hasn't populated the registry yet". The cold-start clamp had exactly two exits: resolution succeeds, or `consecutiveErrors > 0` engages the circuit-breaker backoff. A permanent miss triggers neither — it never resolves and never throws — so the 5s "brief catch-up" applied for the life of the window. The fail-open ambiguity is the whole bug: the retry cap was correct for the transient case it was designed for and pathological for the permanent case it couldn't distinguish.

The fix (#10169) made the miss carry its own diagnosis. `ForgeResolveProviderResult` became a discriminated union: `{ status: "resolved", namespacedId, repo } | { status: "no-match" } | { status: "not-ready" }`. The definitiveness gate is `PluginService.isPluginScanComplete` (backed by `initialized`, distinct from `waitForInit` which also waits for activation): provider descriptors register at manifest scan-time, so the moment `initialize()` settles, a hostname miss is definitive — no need to wait for plugin activation. Every post-scan failure mode maps to `no-match`; a thrown resolution (git read or IPC failure) deliberately leaves `providerResolutionStatus` null so the transient retry stays in effect. On `no-match`, `scheduleNextPoll` returns without arming a timer (`isPolling` stays true — same shape as the existing all-candidates-resolved pause), and the miss is cached so the debounced worktree-update path guards `providerResolutionStatus !== "no-match"` before re-running `resolveProvider()` — without that second guard, every worktree update would keep re-spawning the git-config reads even while "paused". The pause's re-arm surfaces are explicitly enumerated: `setForgeSettings` + `refresh`, manual refresh, service restart, and a new `forge:provider-registry-updated` main→host push broadcast from `PluginService.loadPlugin()` after `registerForgeProviders` (since extended to plugin unload too), applied in the host only when status ≠ `resolved`.

## Lesson

- **Never return one sentinel for both "not ready yet" and "will never succeed"** from any resolver a retry loop consumes. A cap/clamp keyed on "still unresolved" inherits the ambiguity and turns the permanent case into an unbounded hot loop. Return a discriminated status (`not-ready` / `no-match` / `resolved`), not `null`.
- **Audit every exit of a retry cap against the permanent-miss case.** The 5s clamp's exits were "resolved" and "consecutiveErrors > 0"; a definitive no-match hits neither because it neither succeeds nor errors. If a loop's only escapes are success and thrown failure, a clean permanent miss loops forever.
- **Definitiveness comes from lifecycle knowledge, not extra retries.** The permanent verdict is gated on `isPluginScanComplete` because descriptor registration is scan-time — the earliest phase after which the miss cannot self-heal. Find that phase in your registry's lifecycle and gate on it; don't approximate with attempt counts or timeouts.
- **A pause on a cached negative must enumerate its re-arm surfaces, one per way the world can change.** Here: settings change, manual refresh, restart, and a registry push for runtime plugin install/enable (and later unload). Any missed surface strands the project until restart — the `forge:provider-registry-updated` push exists precisely because plugin install is the surface nothing else covers.
- **Cache the negative on ancillary trigger paths too.** Pausing the timer wasn't enough: debounced worktree updates independently called `resolveProvider()`. Every path that can re-trigger the expensive resolution needs the same `!== "no-match"` guard.
- **Test absence-of-work with fake time.** The pause tests advance `vi.advanceTimersByTimeAsync(60 * 60 * 1000)` and assert the `resolveProvider` call count is unchanged — an hour of fake time with zero calls proves no timer is armed, which a "waits 5s" assertion cannot.

## Applies when

- Touching `PullRequestService.scheduleNextPoll`, the `FOCUS_CATCHUP_THROTTLE_MS` clamp, `providerResolutionStatus`, or any poller whose interval is conditioned on "not yet resolved".
- Designing or reviewing a resolver/lookup API that returns null for a miss and has retrying callers — especially cross-process bridges (`forgeBridge`, `forgeRpcServer`) where the caller can't inspect why it missed.
- Diagnosing runaway `git config` subprocess spawns, steady 5s IPC ticks from a workspace-host, or unexplained per-project background CPU on non-GitHub projects.
- Adding a consumer of any registry populated asynchronously at startup (plugin scan, forge descriptors) — decide what the pre-settle answer looks like and gate permanent verdicts on the scan-complete signal, not on the miss itself.
- Caching any negative result — enumerate the invalidation events (settings, manual refresh, restart, runtime plugin install/enable/unload) and verify each actually reaches the cache holder as a push, not a hope.
