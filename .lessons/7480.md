## Context

`TerminalWebGLManager` attaches `@xterm/addon-webgl` (0.20) to agent terminals. Chromium hard-caps active WebGL contexts at 16 per renderer and silently evicts the oldest on overflow via `webglcontextlost` (see #3358). Bulk worktree creation spawns several agent panels at once, so many terminals call `ensureContext()` in the same frame.

## Problem

During bulk worktree creation (3-5 issues, recipe spawning agent panels), agent terminals landed blank and stayed blank for ~3 seconds before painting. Headroom alone (the #3358 fix) did not prevent it — the contexts came up, then got evicted, then sat blank.

## Root cause

Three compounding, non-obvious mechanisms — all platform/library behavior, not app logic:

1. **Synchronous burst over-subscribes the GPU budget.** Firing N `getContext()`/`loadAddon(new WebglAddon())` calls in one frame requests N contexts before any of the GPU-process IPC roundtrips complete, blowing past Chromium's 16-context cap and triggering its own LRU eviction of contexts that were just created.

2. **xterm's `webglcontextlost` handler arms a 3-second restore timer.** When the context is lost, `@xterm/addon-webgl` listens on the canvas element in the **bubble phase** and waits up to 3s for `webglcontextrestored` before giving up and notifying via `onContextLoss`. That 3s is the visible blank window — the app's own `onContextLoss` callback can't react until xterm's timer fires.

3. **Chromium does not reclaim an evicted context's slot until GC runs the WebGL teardown.** Disposing the addon (`addon.dispose()`) is not enough; the 16-slot budget stays occupied until garbage collection, so the next attach immediately over-subscribes again.

## Lesson

When attaching multiple WebGL contexts in a renderer that shares Chromium's 16-context budget:

- **Stagger attaches through a `requestAnimationFrame` drain queue — one attach per frame** so each `getContext()` finishes its GPU IPC roundtrip before the next is requested. Never attach a burst synchronously. In `TerminalWebGLManager` this is `pendingEnsures` + `scheduleDrain()` + `drainOne` (one entry dequeued per rAF). The same drain pattern paces fleet-wide DOM→WebGL mode flips (`flipToWebgl`) and DOM downgrades (`drainOneRelease`).
- **Register a capture-phase `webglcontextlost` listener on `terminal.element`** so you drop the pool entry and force a DOM repaint _before_ xterm's bubble-phase handler can start its 3s restore timer. `element.addEventListener("webglcontextlost", h, { capture: true })`. A bubble-phase listener fires after xterm's and is too late.
- **Explicitly call `WEBGL_lose_context.loseContext()` before `addon.dispose()`** to free the slot synchronously rather than waiting for GC. Reach the context via the pinned-version internal `(addon as any)._renderer?._gl` and wrap in try/catch so a future addon-shape change degrades gracefully (`forceGpuSlotRelease()`). Call it on every release path: LRU/mode-flip release (`dropPoolEntry`) **and** terminal teardown (`onTerminalDestroyed`) — otherwise a hibernate-then-bulk-recreate cycle stalls on the same budget.
- **Test gotcha:** JSDOM/node env has no `requestAnimationFrame`, and `vi.useFakeTimers()` replaces rAF with its own queue. Tests that expect `ensureContext()` → `isActive()` to resolve inline must reinstall a synchronous rAF shim (`cb(0)`) **after** `vi.useFakeTimers()` in `beforeEach`, or the drain never runs. See `vitest.setup.ts` and the WebGL test files.

## Applies when

- Adding or modifying WebGL/WebGPU context attach logic in `TerminalWebGLManager.ts`, or any renderer code that holds multiple long-lived GPU contexts in one document.
- Symptom: terminals (or any WebGL surface) land blank and recover after ~3 seconds, especially during bulk/burst creation (bulk worktree spawn, recipe-driven multi-panel open, fleet-wide DOM→WebGL mode flips).
- Touching `webglcontextlost` / `onContextLoss` handling, or anywhere xterm's internal restore timer could delay your own context-loss recovery.
- Freeing a WebGL slot to stay under Chromium's 16-context cap — disposing the addon is insufficient; you must `loseContext()` to reclaim the slot before the next `getContext()`.
- Writing vitest tests for any rAF-driven coalescing/drain queue under `vi.useFakeTimers()` — reinstall a sync rAF shim after enabling fake timers.
