## Context

`restoreSessionFromFile` (`electron/services/pty/terminalSessionPersistence.ts`) replays a serialized terminal snapshot back into a `@xterm/headless` `Terminal` on hibernate/restore. The serialize addon captures buffer content plus the DECSET sequences for whatever modes were active at snapshot time, so it already re-applies mouse tracking and bracketed paste on replay.

## Problem

After a hibernate/restore cycle on a terminal that had been inside an alt-screen app (vim, htop), parser modes leaked across the cycle — mouse capture, bracketed paste (`2004`), focus events (`1004`), Kitty keyboard protocol, and cursor style — even though the visible content looked right. The restored terminal behaved as if it were still inside the old TUI.

## Root cause

The serialize addon snapshots _content_ and the modes that were active when the snapshot was taken; it does not snapshot — and replay cannot undo — drift the parser accumulated independently, and the headless `Terminal` is reused across cycles so stale parser state carries forward. Replaying the captured stream re-applies the captured modes on top of whatever the parser already held, rather than starting from a known-clean baseline.

Two further non-obvious points:

- **DECSTR (`\x1b[!p`) is not a full reset.** It clears DEC private modes the parser holds (bracketed paste, focus events) without touching scrollback, but it does NOT cover the Kitty keyboard protocol stack or cursor style. Those need explicit sequences: Kitty keyboard pop `\x1b[=0u` and DECSCUSR default `\x1b[0 q`. The fix is the combined preamble `RESTORE_PARSER_RESET_PREAMBLE = "\x1b[!p\x1b[=0u\x1b[0 q"`, written before the content replay.
- The original code called `readFileSync` and only then checked the decoded content's byte length against `SESSION_SNAPSHOT_MAX_BYTES`, so an oversized/corrupt session file was fully loaded into memory and then discarded. The size guard now runs on `statSync().size` (`> SESSION_SNAPSHOT_MAX_BYTES + SESSION_HEADER_BYTES`) _before_ the read, with the post-decode check kept only as a belt-and-suspenders guard against a stat→read growth race.

## Lesson

When replaying a serialized terminal stream into a reused headless xterm, emit a parser-reset preamble first — and do not assume DECSTR alone is sufficient. DECSTR covers DEC private modes but not Kitty keyboard or cursor style; combine `\x1b[!p` + `\x1b[=0u` + `\x1b[0 q`. This is defence-in-depth: the serialize addon reapplies the captured modes after the reset, so the preamble's only job is to clear drift, not to reconstruct intended state. Keep the preamble write strictly before the content write (the tests assert call order via `toHaveBeenNthCalledWith`).

Separately, gate file size on `statSync().size` before `readFileSync`, not on decoded byte length after the read, so oversized files are rejected without being loaded. Treat `ENOENT` from `statSync` (and a stat→read race) as the normal "no prior session" path and stay quiet; only `console.warn` (Tier 0) on a genuine oversize rejection.

## Applies when

- Touching `restoreSessionFromFile` / `terminalSessionPersistence.ts` or any code that replays a serialized `@xterm/xterm` / `@xterm/headless` buffer (session restore, hibernation wake, session recording/playback, worktree history injection).
- Debugging "mouse/paste/focus/cursor behaves wrong after restore", a terminal that acts like it's still in vim/htop after wake, or stale parser modes surviving a hibernate cycle.
- Choosing a terminal reset sequence — recall that DECSTR (`\x1b[!p`) is not a full reset and misses Kitty keyboard (`\x1b[=0u`) and DECSCUSR cursor style (`\x1b[0 q`). Distinct from #3186 (alt-screen _content_ detection on restore) and #1074 (DECSTR to fix a render glitch after crash-recovery renderer reset).
- Adding a size/validity guard in front of a `readFileSync` of an untrusted-size on-disk artifact — guard on `statSync().size` before the read, not on the decoded payload after it.
