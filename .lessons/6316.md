## Context

The Daintree Assistant (Help Panel) launches an agent terminal via `actionService.dispatch("agent.launch", …)` and, on success, commits the returned `terminalId` into `helpPanelStore`. Each project runs in its own `WebContentsView` with an independent V8 context; switching projects hides/caches the outgoing view and shows the incoming one.

## Problem

Selecting an agent from the picker left the panel stuck on the picker state with no terminal and no diagnostic — the launch had succeeded in main, but the renderer silently discarded the result. It reproduced specifically when the panel briefly lost visibility (project switch) while the `agent.launch` IPC was in flight.

## Root cause

The original code guarded the success branch with `if (document.hidden) return;` inside the launch result callback. During an Electron 41 `WebContentsView` swap (and on minimize/sleep), `document.hidden` flips to `true` _transiently_ — being hidden is NOT a teardown signal. The renderer is merely cached, about-to-be-evicted, minimized, or sleeping; the PTY/MCP lifecycle is owned by main and survives all four. So a perfectly good launch result arrived while `document.hidden === true`, hit the guard, and was dropped on the floor — no commit, no error, no notification.

## Lesson

- `document.hidden` is a legitimate gate for _initiating_ speculative/auto work (don't auto-spawn a terminal into a hidden renderer) — keep it in the decision gate. In the live code that is `HelpSessionController._maybeAutoLaunch` (`if (typeof document !== "undefined" && document.hidden) return;`).
- `document.hidden` must NEVER gate the _commit_ of an already-resolved async result. By the time an IPC promise resolves, the side effect already happened in main; dropping the result on visibility loss orphans backend state and produces a silent dead-end.
- For "is this async result still wanted?" use a real staleness signal, not visibility: the current code uses a monotonic `_launchGen` counter (every async checkpoint compares its captured `gen` against `this._launchGen` and bails + cleans up if superseded). The PR's first cut compared `useHelpPanelStore.getState().preferredAgentId`; the gen counter generalizes it.
- Put lifecycle/visibility defence in a `visibilitychange` listener that _re-arms_ work on restore (HelpPanel bumps `visibilityEpoch` only when `!document.hidden`, re-running `_maybeAutoLaunch`), not as an inline early-return inside callbacks.
- Always make launch/spawn failure paths visible (`notifyLaunchFailed`) — a silent `return` on a destructive/stateful operation is a debugging black hole.

## Applies when

- Adding or editing any `agent.launch` / spawn / async-IPC result handler in `HelpSessionController.ts` or `HelpPanel.tsx`.
- Writing `if (document.hidden) return` (or any visibility check) anywhere inside an `await`-resolution callback, `.then()`, or post-dispatch block — especially in code that runs inside a per-project `WebContentsView`.
- Debugging "the operation succeeded in main but the renderer never reflected it" symptoms that correlate with project switching, window minimize, or system sleep.
- Implementing staleness/cancellation for in-flight async work — reach for a generation counter or captured identity check, not `document.hidden`.
- Any renderer code that treats `document.hidden` / `visibilitychange` as a teardown or cancellation signal in the multi-WebContentsView architecture (hidden means cached/evicting/minimized/asleep, all survivable).
