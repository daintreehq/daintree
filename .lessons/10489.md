## Context

Plugin danger classification answers one predicate — "does this capability grant an irreversible side effect?" — in two independent places: `PluginService`'s per-action `effectiveDanger` elevation (forces a plugin's contributed actions up to `"confirm"` regardless of what they self-declared) and `PluginMcpTierAuth.deriveCapabilityCap` (the maximum MCP danger tier a plugin's tool surface may _reach_). Before #10489 each site held its OWN hardcoded Set — `CONFIRM_TRIGGERING_CAPABILITIES` inline in `PluginService.ts` and `HIGH_RISK_CAPABILITIES` in `PluginMcpTierAuth.ts` — kept aligned only by a `// Keep in lockstep` comment. Part of the plugin 1.0 capability-vocabulary freeze (#10459, resolves #10470).

## Problem

The two lists silently disagreed: `agent:register` was present in the `PluginService` copy but missing from the MCP-auth copy. So `deriveCapabilityCap(["agent:register"])` returned `D1` instead of `D2`, and a plugin that declared only `agent:register` and exposed a `destructiveHint: true` MCP tool had its call **denied** (annotation floor `D2` > cap `D1`) instead of allowed at the `D2` shared-state-mutation confirm tier. Nothing type-checked wrong, nothing threw — invisible until someone diffed the two Sets by hand.

## Root cause

A "keep in lockstep" comment is documentation, not enforcement — nothing links two hardcoded Sets in separate files, so editing one (adding `agent:register` to the action-danger set) leaves the other stale. This particular drift failed _closed_ on the MCP side (over-deny a legitimate `D2` op — `deriveDangerTier` deliberately denies rather than downgrades, so the model can't pretend a mutation was read-only). But a duplicated classification list is silently wrong in whichever direction it drifts: had the capability instead been in the MCP cap but absent from `PluginService`'s set, the action elevation would fail _open_ — an irreversible plugin action rendered with no confirm dialog. #10489 deleted both literals, moved the set to `shared/config/pluginCapabilities.ts` as the sole `CONFIRM_TRIGGERING_CAPABILITIES`, and made all consumers (`PluginService`, `PluginMcpTierAuth.deriveCapabilityCap`, `pluginDangerLattice.computePluginDanger`) import it — so structural divergence is now impossible by construction.

## Lesson

- **A "keep in lockstep" / "keep in sync" comment spanning two files is a latent divergence, not a safeguard** — treat any duplicated security-classification list (danger tiers, high-risk capability sets, allow/deny lists) as guaranteed to drift and consolidate it into one exported constant in `shared/config/`. Here the drift under-tiered the MCP cap (`agent:register` → `D1` instead of `D2`); because a duplicated predicate is silently wrong in whichever direction it drifts, you cannot rely on the harm landing fail-closed.
- **A drift-guard test must iterate the ACTUAL constant, not re-list its members** — `PluginMcpTierAuth.test.ts` uses `it.each([...CONFIRM_TRIGGERING_CAPABILITIES])` so a new member auto-extends coverage, whereas `PluginService.core.test.ts` hand-lists `["git:write", …, "agent:input"]`, which only guards the members it happens to name and can itself go stale. Prefer the iterate-the-constant form — a test that copies the list is just a third copy that also drifts.
- **Once both consumers import one constant, they can no longer diverge structurally** — so the drift-guard test's real job shifts from catching cross-file divergence (now impossible) to asserting each consumer's _logic still honors every member_: every cap reaches `D2`, every cap elevates the action to `"confirm"`. That catches a consumer whose branch quietly stops respecting the set, or a member silently dropped from the constant.
- **Consolidate lists that answer the SAME predicate, not every list that mentions capabilities** — the compound-capability lattice (`SENSITIVE_READ_CAPABILITIES` / `REMOTE_MUTATION_SINK_CAPABILITIES` in `pluginDangerLattice.ts`) deliberately stays a separate set: it classifies a _different_ threat (compound exfiltration / remote-controlled mutation), and its own comment calls it "belt-and-suspenders if the flat set ever drifts." Merging those into `CONFIRM_TRIGGERING_CAPABILITIES` would collapse two distinct predicates and would be wrong.
- **The pattern paid off:** #10558 later added `agent:input` to the single constant and every consumer plus the iterate-the-constant test picked it up with zero per-file edits — the exact edit that had previously been forgotten for `agent:register`.

## Applies when

- Adding or reclassifying a plugin capability, or touching `CONFIRM_TRIGGERING_CAPABILITIES` / `deriveCapabilityCap` / `computePluginDanger` / the per-action `effectiveDanger` elevation — never hardcode the high-risk set locally; import it from `shared/config/pluginCapabilities.ts`.
- Reviewing any two code sites that classify the same thing (danger tiers, high-risk / allow / deny lists) joined only by a "keep in sync" comment — that comment is the review flag; require one shared constant instead.
- Writing a drift-guard test for a security-relevant set — iterate the real constant (`it.each([...CONST])`), don't paste its members into the test.
- Diagnosing a plugin whose destructive MCP tool is wrongly denied, or whose dangerous action shows no confirm dialog — check whether the capability is in `CONFIRM_TRIGGERING_CAPABILITIES` and whether every classifier reads that one set.
- Deciding whether to merge two capability lists — merge only if they answer the same predicate; the compound-exfiltration lattice stays separate.
