## Context

The pty-host's `ResourceGovernor` (`electron/pty-host/ResourceGovernor.ts`) is the subprocess's self-declared memory authority: it samples every 2s, EMA-smooths, and drives a warning/engage/critical ladder that trims per-terminal analysis buffers and — if pressure holds — pauses PTY reads across all terminals. Before #10302 its only pressure signal was V8 heap utilization: `process.memoryUsage().heapUsed / v8.getHeapStatistics().heap_size_limit`. Every threshold (70% warn, 85% engage, 95% critical bypass) hung off that one ratio.

## Problem

A host whose RSS ballooned from scrollback or queue growth never tripped any threshold — the governor reported "healthy" while memory climbed (issue #9905). Worse, the pre-pause `trimBuffers` reclaim frees mostly external memory, then the escalation logic waited a tick and rechecked _heap_ utilization to decide whether to pause: it was evaluating the wrong meter for the very memory it had just released. Because `--max-old-space-size` bounds only the heap and external growth degrades the system rather than crashing V8, there was no OOM crash to point at — just an authority silently policing the wrong number.

## Root cause

The dominant per-terminal data in the pty-host does not live on the V8 heap. Headless-xterm buffer lines are `Uint32Array(3 * cols)` typed arrays; queued PTY output on the MessagePort path is `Uint8Array` — both are ArrayBuffer backing stores accounted as `external`/`arrayBuffers`, not `heapUsed`. Measured ratio is ~10:1 external:heap. At max scrollback (~24MB per terminal) a 10-terminal session holds a couple hundred MB the heap meter never sees, so the heap-ratio signal under-reads _exactly_ the workload the governor exists to police.

The fix removes `import v8` / `getHeapStatistics()` entirely and makes utilization the binding constraint of two terms: `max((heapUsed + external) / TOTAL_PROCESS_BUDGET_MB, heapUsed / HEAP_BUDGET_MB) * 100`, where `HEAP_BUDGET_MB = 512` (matching the `--max-old-space-size` cap the host is forked with) and `EXTERNAL_HEADROOM_MB = 256`, `TOTAL = 768`. Both terms are required and neither subsumes the other: the combined ratio alone can never reach engage on _pure heap_ pressure (heap is capped at 512, only ~67% of the 768 budget), so a runaway JS heap must be measured against its own ceiling; the combined term catches external growth the heap term is blind to. `max()` fuses them into one continuous signal feeding one EMA, and disengage hysteresis then requires _all_ ratios to clear resume. Critically, external is used raw and `arrayBuffers` is NOT added — it is a subset of `external`, so summing both double-counts.

## Lesson

- **A memory governor keyed to `heapUsed / heap_size_limit` measures the wrong thing whenever its workload is typed arrays or Buffers.** Those live in `external` (outside `--max-old-space-size`), so heap utilization stays flat while RSS climbs. Any Node process managing xterm buffers, decoded media, wasm, or queued IPC slabs must fold `external` into its pressure signal.
- **Use `external` alone; never `external + arrayBuffers`.** `arrayBuffers` is a subset of `external` in `process.memoryUsage()` — adding them double-counts the same backing stores. The code comment in `ResourceGovernor.ts` is load-bearing; don't "fix" it by summing both.
- **A single ratio can't police both heap and external — you need two terms under `max()`.** The combined `(heap+external)/total` term can never reach engage on pure heap pressure because heap is only ~67% of the total budget, so a separate `heap/heapCap` term is required for a runaway JS heap; conversely the heap term is blind to external. One `max()` keeps it a single signal feeding one EMA while hysteresis demands _all_ terms clear resume.
- **After a trim, recheck the same meter the trim frees.** The pre-#10302 loop trimmed external buffers then rechecked heap utilization to decide whether to escalate — the trim released memory the recheck couldn't see. Reclaim feedback loops must measure the resource they reclaim.
- **The budget must track the real `--max-old-space-size` cap, and `external` is separately budgeted headroom, not part of the heap cap.** `HEAP_BUDGET_MB` mirrors the fork flag; `EXTERNAL_HEADROOM_MB` sits _between_ the heap cap and the total process budget. If you change one, keep it in sync with `PtyHostLifecycle`'s `memoryLimitMb`.

## Applies when

- Touching `ResourceGovernor.ts` `checkResources` / the utilization formula — it has since grown a third `maxWorkerHeapMb / HEAP_BUDGET_MB` term (#10920 moved mirrors into worker isolates) and a RAM-scaled per-shard `DAINTREE_PTY_HEAP_BUDGET_MB` budget under the PTY fabric, but the heap+external design is unchanged.
- Writing or reviewing any Node/Electron memory governor, watchdog, or eviction trigger that reads `process.memoryUsage()` — confirm it accounts for `external` when the workload is typed arrays / Buffers, and that it doesn't sum `external + arrayBuffers`.
- Diagnosing "the pty-host's RSS climbs but the governor never warns / never trims" or "trim runs but pressure doesn't clear" — suspect a heap-only signal or a trim/recheck meter mismatch.
- Consuming the `host-memory-warning` event (`shared/types/pty-host.ts`) — it carries optional `heapMb`/`externalMb`, forwarded through `PtyEventRouter` and `perWindowInit`'s manual event reconstruction; new forwarding paths must carry both.
- Assuming `--max-old-space-size` bounds a subprocess's total memory — it bounds only the V8 heap; ArrayBuffer backing stores grow outside it and degrade the system without an OOM crash.
