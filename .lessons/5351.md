## Context

App startup restores N panels by calling `addPanel` once per saved panel. Each `addPanel` is `async` (it awaits PTY spawn, `globalEnv.get()`, etc.), and each fired its own Zustand `set()`.

## Problem

N panels produced N separate renders of every high-fanout subscriber — worktree dashboard, dock, grid — plus N `saveNormalized` persistence writes. React 19 auto-batching does NOT coalesce these because the `set()` calls happen across `await` boundaries (auto-batching only collapses synchronous updates within one task), and Zustand 5 has no native batch/transaction API.

## Root cause

The naive fix — defer ALL store writes until a flush — breaks correctness: IPC event listeners (`onAgentStateChanged`, `onExit`, `onAgentDetected`, activity/flow updates) fire during hydration and look panels up by id. If nothing is committed until flush, those updaters silently no-op on a missing panel. The insight is that the two store fields have different consumers: `panelsById` is a lookup map read by event handlers (must be live immediately), while `panelIds` is the ordered array that drives the expensive list renders (only it needs to be batched).

## Lesson

Split the commit: write the per-item lookup-map entry (`panelsById`) eagerly on every `addPanel` so by-id lookups stay correct mid-batch, but collect the ids in a module-level singleton and append them to the fanout array (`panelIds`) once at flush — collapsing N renders + N persists into one. The batch state lives in `src/store/slices/panelRegistry/hydrationBatch.ts` (a process-global singleton, NOT store state — it must survive across the `await` points that defeat React batching); `beginHydrationBatch`/`flushHydrationBatch` open/close it with an opaque token. Token semantics matter: `flushHydrationBatch(token)` no-ops on a stale/mismatched token (a superseded or cancelled batch from a project the user left), and `commitPendingIds` re-filters against `panelsById[id] !== undefined` so a failed `addPanel` or a reset store drops orphaned ids instead of appending dead entries to `panelIds`. Anything that reads a derived "current" value during the batch (here, `panelStore.addPanel` setting `focusedId` to the last-added grid panel) must guard on `isHydrationBatchActive()` and resolve deterministically after flush — `useAppHydration` re-picks focus as the first grid panel in the active worktree, since "last added under async scheduling" is arbitrary. This generalized into spawn batches too (`beginSpawnBatch`), with `beginHydrationBatch` draining any in-flight spawn batch first so its panels aren't orphaned (#9165).

## Applies when

- Restoring/spawning N items via repeated `async` store mutations where each awaits (PTY, IPC, env) and you see N renders
- Any Zustand 5 store where you want to batch updates but React 19 auto-batching can't help because the `set()` calls cross `await`
- A store field is both read by mid-operation event listeners AND drives expensive list re-renders — split eager lookup-map from deferred fanout array rather than deferring everything
