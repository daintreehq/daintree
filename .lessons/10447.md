## Context

Grid panel headers are draggable to move the panel, and their tab strip is independently draggable to reorder tabs — two nested dnd-kit `DndContext`s. The outer panel-move drag uses `NoDndMouseSensor` + `NoDndTouchSensor` (`DndProvider.tsx`), which arm on `onMouseDown`/`onTouchStart` and short-circuit when `isNoDndTarget(target)` is true (`target.closest("[data-no-dnd]") !== null`). The inner tab-reorder context (`PanelHeader.tsx`) uses a plain `PointerSensor` (distance 5) + raw `TouchSensor` + `KeyboardSensor`. Each `TabButton` is a `useSortable` node that spreads dnd-kit's activator listeners onto its tab `div`.

## Problem

Starting a drag on a tab also armed the parent panel's move-drag (#10443), so a tab-reorder gesture fought a panel-move gesture. `TabButton` already had a `handlePointerDown` doing `e.stopPropagation()` specifically to keep tab interactions off the header drag surface — and it looked correct — yet the panel still picked up. The guard appeared to be running and doing nothing.

## Root cause

Two independent looks-correct API misuses stacked. **(1) Event-family mismatch.** The outer sensor is `NoDndMouseSensor`, whose activator is `onMouseDown`. `e.stopPropagation()` on a React `PointerEvent` does not stop the separate `MouseEvent` the browser dispatches for the same gesture — pointer and mouse are distinct synthetic-event families with independent propagation, so a pointerdown guard can never block a mousedown-based sensor. **(2) JSX props-spread clobber.** The guard usually didn't run at all: `onPointerDown={handlePointerDown}` was rendered _before_ `{...sortablePointerListeners}`, and dnd-kit's own `onPointerDown` lives inside that spread. In React the last prop wins, so the spread overwrote the handler and the `stopPropagation` was dropped; the pointerdown bubbled to the header. Fix is two layers: `data-no-dnd` on the `PanelTabList` outer container so `NoDndMouseSensor`/`NoDndTouchSensor` refuse to arm for _any_ tab-strip mouse/touch input (the correct mechanism for the mouse family), plus a composed `handleTabPointerDown` rendered _after_ the spread that `stopPropagation`s then hands off to the captured `sortablePointerDown`. Tab reorder is unaffected because the inner `PointerSensor` never checks `[data-no-dnd]` — only the `NoDnd*` subclasses do.

## Lesson

- **A `stopPropagation` guard only works against a sensor listening on the SAME event family.** dnd-kit's `MouseSensor`/`NoDndMouseSensor` arm on `onMouseDown`, `PointerSensor` on `onPointerDown`, `TouchSensor` on `onTouchStart`. Stopping a `pointerdown` does nothing to a `mousedown`-based activator (and vice versa) — the browser dispatches those events independently. Identify the ancestor's sensor class before writing a propagation guard; if it's the mouse/touch family, use the `[data-no-dnd]` opt-out instead.
- **`[data-no-dnd]` is the real disarm for the `NoDnd*` sensor family, and it is selective by design.** `isNoDndTarget` (`DndProvider.tsx`) is checked _only_ inside `NoDndMouseSensor`/`NoDndTouchSensor`; plain `PointerSensor` and raw `TouchSensor` ignore it — which is why marking the tab strip disarms the panel-move drag while `PointerSensor`-based tab reorder keeps working. Put the attribute on the outermost container of the opt-out subtree (`PanelTabList` outer div) so buttons rendered as siblings of the tablist (add-tab, overflow trigger) stay inside the boundary.
- **Any handler you attach to a `useSortable` node must render AFTER `{...listeners}`, or the spread silently clobbers it.** dnd-kit's activator listeners (`onPointerDown`, `onKeyDown`, `onTouchStart`) are all inside the spread object; React's later-prop-wins means an earlier `onPointerDown={mine}` vanishes. Compose instead: capture the listener (`sortablePointerListeners.onPointerDown`), then render your own handler after the spread that does your work and calls the captured one (`e.stopPropagation(); sortablePointerDown?.(e)`).
- **The keyboard activator hides in the same spread and needs the same composition.** `sortableListeners.onKeyDown` is the `KeyboardSensor` activator and collides with tab Space/Enter activation. `TabButton` destructures it out of the spread and composes in `handleKeyDown`: Space/Enter activates an inactive tab, on the active tab it falls through to `sortableKeyDown` for mouse-free reorder. `[data-no-dnd]` does NOT gate keyboard drags (activation is explicit on a focused node, not bubbling input), so keyboard collisions are solved by composition, not the attribute.
- **A nested raw `TouchSensor` re-opens the touch path even under `[data-no-dnd]`.** The rename input needs its own `handleInputTouchStart` `stopPropagation` because the inner tab-reorder context's plain `TouchSensor` doesn't honor the opt-out — a long-press to select text would otherwise start a tab drag. When you add `[data-no-dnd]`, audit every sensor that could still fire on that subtree, not just the one you targeted.

## Applies when

- Wiring any dnd-kit surface where a sortable/draggable nests inside another draggable (tabs in a movable header, cards in a movable column, badges on a sortable row) and inner interactions leak into the outer drag.
- Writing a `stopPropagation` guard against a drag activator — first confirm the ancestor sensor's event family (`MouseSensor` vs `PointerSensor` vs `TouchSensor`); a cross-family guard is a silent no-op.
- Touching `TabButton.tsx`, `PanelTabList.tsx`, `PanelHeader.tsx`, or `[data-no-dnd]` (`isNoDndTarget`, `NoDndMouseSensor`, `NoDndTouchSensor` in `DndProvider.tsx`) — the attribute gates only the `NoDnd*` sensors, never plain `PointerSensor`/`TouchSensor`/`KeyboardSensor`.
- Attaching an `onPointerDown`/`onKeyDown`/`onTouchStart` handler to a node that also spreads `{...listeners}` from `useSortable`/`useDraggable` — render yours after the spread and compose the captured listener, or it disappears.
- Reviewing a "click/drag on child also triggers the parent gesture" bug where the existing guard looks correct — check both the event-family match and the JSX ordering of handler vs listeners spread.
