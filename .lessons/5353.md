## Context

PR #5353 migrated ~378 raw `ipcMain.handle(...)` calls across 56 handler files to `typedHandle`/`typedHandleWithContext` in `electron/ipc/utils.ts`, enforcing compile-time `IpcInvokeMap` typing and auto-activating the perf-tracing infrastructure. A regression guard (`electron/ipc/__tests__/ipcHandleCoverage.test.ts`) greps handler sources for raw `ipcMain.handle(CHANNELS.` and fails unless the channel is in `RAW_HANDLE_ALLOWLIST`. Two non-obvious mechanics inside the wrapper are easy to break.

## Problem

Two traps that a competent senior would hit while writing or "cleaning up" a typed handler:

1. **Returning `{ ok: false }` (or `{ success: ... }`) from a handler silently swallows the failure.** The security layer wraps every handler return in an outer `{ ok: true, data: <yourReturn> }` envelope, and the preload's `_unwrappingInvoke` (`electron/preload.cts:635`) unwraps based on the OUTER `ok`. A handler that returns its own `{ ok: false, error }` shape gets double-wrapped — the outer envelope still says `ok: true`, so the renderer sees success and reads the inner failure object as if it were data.

2. **Wrapping every handler in `async` for perf-tracing converts synchronous handlers to async.** The natural implementation of "trace every IPC call" is a single `ipcMain.handle(ch, async (...) => { mark(); try { return await handler() } finally { mark() } })`. That forces every handler — including synchronous ones that returned a value directly under raw `ipcMain.handle` — to return a Promise, breaking sync return semantics and the test mocks that assert synchronous returns.

## Root cause

`ForbidIpcEnvelopeKeys<T>` (`shared/types/ipc/errors.ts:115`) is a distributive conditional that rejects any return object carrying `ok` or `success` in any union branch, substituting `IpcHandlerEnvelopeViolation` — an interface whose single key IS the remediation message ("IPC handler must throw new AppError(...) instead of returning {ok|success: ...} — see #6020"), so the compile error reads like documentation. It constrains the return position of `typedHandle`/`typedHandleWithContext` (`utils.ts`) and `PlainHandler`/`ContextHandler` via `SafeResult` (`electron/ipc/define.ts:22`). The contract is: handlers signal failure by `throw new AppError(...)`, never by returning an envelope shape. The double-wrap is invisible at runtime because both layers use the same `ok` discriminator and only the outer one is read.

For the sync issue, `typedHandle`/`typedHandleWithContext` branch on `isPerformanceCaptureEnabled()`: when capture is OFF they register a NON-async handler (`ipcMain.handle(ch, (_event, ...args) => handler(...))`) so a synchronous handler stays synchronous; only when capture is ON do they install the `async` perf-tracing wrapper (`utils.ts:376` / `utils.ts:460`). The fast-path exists specifically to preserve pre-migration sync behavior and the existing test expectations.

## Lesson

- Handlers registered through `typedHandle`/`typedHandleWithContext`/`op` must NEVER return `{ ok: ... }` or `{ success: ... }`. Signal failure with `throw new AppError(...)`. If TS rejects your return type with the `IpcHandlerEnvelopeViolation` message, that's the guard — rename the field or throw instead; do not cast it away.
- The renderer's success/failure decision is made on the OUTER envelope only. An inner `{ ok: false }` is data, not an error, and will be silently delivered as success.
- When adding cross-cutting behavior (tracing, timing, logging) to the IPC wrapper, gate the `async` form behind a feature flag and keep a synchronous fast-path. Blindly `async`-wrapping every handler changes sync→async semantics and breaks mocks asserting synchronous returns.
- Don't reintroduce raw `ipcMain.handle(CHANNELS.X, ...)` in `electron/ipc/handlers/` (or the three `EXTRA_HANDLER_FILES`) — `ipcHandleCoverage.test.ts` fails unless X is allowlisted. Allowlist entries are for channels genuinely inexpressible via `IpcInvokeMap`: variadic `...args` + `senderFrame.url` trust checks (`plugin:invoke`), `event.sender`-coupled window commands, and handlers registered lazily by service constructors outside `handlers/`.

## Applies when

- Writing or refactoring any handler in `electron/ipc/handlers/` and deciding how to signal an error to the renderer (throw vs return).
- You see a renderer receive a `{ ok: false, ... }` object as a successful result, or `_unwrappingInvoke` returning data that looks like an error envelope.
- TypeScript flags an IPC handler return with the cryptic `IpcHandlerEnvelopeViolation` / "must throw new AppError" missing-property error.
- Adding tracing/timing/logging to `typedHandle`/`typedHandleWithContext` or `electron/ipc/define.ts`, or a sync handler under test suddenly returns a Promise.
- A channel can't be expressed through `IpcInvokeMap` (variadic args, sender-origin trust, lazy service registration) and you're tempted to drop back to raw `ipcMain.handle` — add it to `RAW_HANDLE_ALLOWLIST` with a documented reason instead.
