## Context

The MCP server runs in the main process but needs the renderer's Zustand-backed state (action manifest, `worktree.list`, `terminal.list`) to answer tool calls. It does this with a request/response _IPC bounce_: `webContents.send("mcp:get-manifest-request", { requestId })` to the renderer, the renderer replies on `mcp:get-manifest-response`, and a `pendingManifests`/`pendingDispatches` Map correlates the reply back to a pending promise (`electron/services/mcp-server/rendererBridge.ts`).

## Problem

The bounce was sending to `BrowserWindow.webContents` (via the old `getLiveWebContents`). In the WebContentsView-per-project architecture that webContents is the empty host shell — the project's React app and stores live in a child `WebContentsView`. Tools resolved against host state, returning empty/wrong results. Two further holes: any renderer that knew a `requestId` could resolve a pending promise (no sender check), and if the target view was torn down mid-flight the promise just hung until the 5s/30s timeout.

## Root cause

Same `BrowserWindow.webContents`-is-an-empty-shell trap as #4799 (menu roles), but on the _outbound_ IPC path instead of menu dispatch. After the #4672 WebContentsView migration, project state only exists in `ProjectViewManager.getActiveView().webContents` — `BrowserWindow.webContents` renders nothing. A request/response bounce additionally has no built-in correlation safety: `ipcMain.on` fires for _any_ sender, so a `requestId` match alone is spoofable, and a sent request has no automatic rejection when its target view dies.

## Lesson

For any main-process code that does a request/response IPC bounce into a renderer, all three pieces are mandatory:

- **Outbound target = active project view, not the host shell.** Resolve `ctx.services.projectViewManager?.getActiveView()?.webContents` (with `getProjectViewManager()` from `windowRef.js` as the no-window-context fallback), never `BrowserWindow.webContents`. Throw "MCP renderer bridge unavailable" when no view exists rather than falling back to the shell.
- **Pin the response sender.** Capture `webContents.id` as `webContentsId` in the pending entry, and in the response handler drop (`console.warn`, don't resolve) any reply where `event.sender.id !== pending.webContentsId`. A `requestId` match is not sufficient identity.
- **Fail closed on teardown.** Register `webContents.once("destroyed", ...)` per request to reject the pending promise immediately, and stash a `destroyedCleanup()` that removes the listener on every resolve/reject/timeout/stop path so listeners don't leak. Don't rely on the timeout to eventually clear a request whose view is already gone.

Per-session pinning (#7002, `getPinnedWebContents`/`SessionBindingError`) is the same fail-closed principle for a session bound to a specific view: throw a no-retry error rather than silently routing to a different window.

## Applies when

- Adding or reviewing any main-process feature that `webContents.send(...)`s a request and awaits a correlated reply over `ipcMain.on` (MCP tools, agent capability probes, plugin bridges, any "ask the renderer for its store state" path).
- Touching `electron/services/mcp-server/rendererBridge.ts` or anything routing IPC to a project renderer.
- Symptoms: tools/queries returning empty or stale data that doesn't match the visible project; main-process promises that hang until a timeout after a project/window is closed; a renderer resolving a request it didn't originate.
- Any code still calling `BrowserWindow.webContents` to reach the live UI after the WebContentsView migration (#4672) — it is an empty host shell.
