## Context

Agent state (idle/working/waiting) is inferred from passive output: the pty-host samples the headless-mirror viewport every ActivityMonitor tick, diffs consecutive snapshots, and feeds `changedChars` into a decaying "activity temperature". Separately, `ProjectViewManager`'s Efficiency resource profile CDP-freezes cached background views to save CPU, and `agent:state-changed` is broadcast to every view so backgrounded worktree dashboards track their agents. Both paths were "optimized" for v0.19.0 and each independently broke detection; #10487 was the 0.19.1 hotfix.

## Problem

Two distinct symptoms. Bug A: a genuinely-working TUI agent (Claude/Gemini/Codex) flipped to "waiting" during long low-output thinking, and waiting→working recovery was starved — visible even in the foreground. Bug B: spawning many worktrees at once left every background dashboard frozen on its pre-freeze state (usually "waiting"). Bug B misled: detection ran perfectly main-side and the event was broadcast unscoped to all views, so it looked like a fan-out/scoping bug, not a delivery bug.

## Root cause

Bug A (`4211fbf86`, from the #10426 perf audit): the viewport activity scan was narrowed from full-viewport to a cursor-anchored bottom-15-row window. TUI agents park the cursor in a pinned bottom input box and animate the spinner / "esc to interrupt" / elapsed-time line ABOVE it (re-rendered via DECSC/DECRC so the cursor stays low). With the cursor pinned low the window collapsed onto static bottom rows, the changing rows above fell outside it, `changedChars` stayed 0, and the temperature decayed to "waiting". The fix restores a full-viewport scan (`start = viewportTop`); the real allocation saving was always the blank-cell skip, and the viewport is bounded by `terminal.rows` (never scrollback) so full scans cost bounded reads, not allocations.

Bug B: `freezeWebContents` issues CDP `Page.setWebLifecycleState("frozen")`, which suspends the renderer's JS entirely — a frozen renderer never runs the `agent:state-changed` handler, so the IPC queues in Mojo and never applies until foregrounded (Chromium does not auto-resume a frozen renderer on focus/re-attach). CPU throttle (`Emulation.setCPUThrottlingRate`, rate 4 for cached views) only slows the V8/Blink clock — queued events still drain. It is a freeze-vs-throttle semantics trap: freeze suspends, throttle merely slows. The fix guards `freezeAllCached` and the inline deactivation freeze with `hasActiveAgent(projectId)` so a live-agent project is throttled but never frozen, plus wake paths (`unfreezeActiveAgentViews` on seed/reseed; an unfreeze inside `onStateChanged` when a mapped terminal enters `ACTIVE_AGENT_STATES`) for views frozen before their agent went active.

## Lesson

- **A "narrow the scan window" optimization on terminal output must model where TUIs actually paint, which is NOT at the cursor.** TUI agents pin the cursor in a bottom input box and stream live status ABOVE it; any cursor-anchored or bottom-N window silently misses exactly the rows that signal "working". The saving that mattered was the per-cell blank-cell skip, not the row count — a full-viewport scan bounded by `terminal.rows` is cheap because blank cells never allocate.
- **CDP `Page.setWebLifecycleState("frozen")` and `Emulation.setCPUThrottlingRate` are NOT interchangeable throttles.** Freeze suspends JS — any IPC queued for that renderer sits in Mojo indefinitely and never applies; throttle only slows the clock, so queued events still drain. Never freeze a renderer that must still apply queued state (a live agent's dashboard); throttle it instead. And a frozen renderer is invisible in main-side logs: detection, FSM, and broadcast are all correct, only delivery is dead, so a stale background view with a healthy producer is renderer suspension, not misrouting.
- **Freeze + async agent activation is a race needing a wake path, not just a freeze guard.** A view can freeze while `hasActiveAgent` is still false (maps not yet seeded, or the agent activates after the debounced freeze fired); the guard alone strands it, so the fix also wakes on `agent:state-changed`→active and on seed/reseed via `unfreezeActiveAgentViews`. It only compounds on a backgrounded Efficiency-profile view, so single-project/foreground testing passes — reproduce under a real multi-worktree spawn.

## Applies when

- Touching the activity/temperature scan in `electron/services/pty/analysis/headlessViewport.ts` (`buildViewportUnitsSnapshot`; formerly `getVisibleActivityCells` in `TerminalProcess.ts`, moved by the PERF-035 fused-snapshot refactor) or any change that windows/samples the headless viewport for state detection — and when a working agent decays to "waiting" during low-output thinking (cursor-in-bottom-input TUIs).
- Adding or reviewing any renderer freeze/suspend optimization in `ProjectViewManager` / `webContentsLifecycle.ts` — confirm the target has no live agent (or other queued IPC it must apply) before `freezeWebContents`; prefer `throttleCpuWebContents` when events must drain. Both the freeze guard (`freezeAllCached`/`hasActiveAgent`) and the wake path (`unfreezeActiveAgentViews` + the `onStateChanged` handler in `ProjectViewAgentStateCache.ts`) must exist to cover the freeze-before-active race.
- Diagnosing background dashboards stuck on a stale agent state while main-side detection looks correct — suspect a CDP-frozen renderer, not fan-out scoping.
