## Context

The trusted app renderer CSP (now in `shared/config/csp.ts`, applied at both the `<meta>` and HTTP-header layers) included `'unsafe-eval'` in `script-src`, originally added because older Vite versions used eval-based HMR. The permission handler (in `electron/setup/security.ts`) used a flat list without explicit categorization, with unknown permissions falling through without an explicit deny.

## Problem

Modern Vite (no longer requires `'unsafe-eval'` for HMR — it switched to a non-eval approach) makes the entry unnecessary; the current prod CSP keeps only `'wasm-unsafe-eval'`. Keeping `'unsafe-eval'` in the trusted-renderer CSP unnecessarily broadens the attack surface.

Also, the permission handler lacked a default-deny clause for unknown permission types. New Electron permission types added in future versions would be implicitly allowed rather than denied.

## Root cause

CSP entries added for a transient requirement (eval-based HMR) were never removed when the requirement went away. Permission handlers without explicit default-deny are open by default rather than closed.

## Lesson

**CSP**: Periodically audit `'unsafe-eval'` in the trusted-renderer CSP (`getDaintreeAppProdCSP` / `getDaintreeAppDevCSP` in `shared/config/csp.ts`). Modern Vite HMR no longer requires it; the prod policy now carries only `'wasm-unsafe-eval'`. Note the separate embedded-`<webview>` CSP (`getLocalhostDevCSP` in `electron/utils/webviewCsp.ts`) deliberately keeps `'unsafe-eval'` for untrusted guest frameworks (e.g. Next.js dev) — that is a different, intentional surface. Removing `'unsafe-eval'` from the trusted renderer is a safe, high-value hardening step with no functional regression.

**Permission handlers**: Structure Electron `setPermissionRequestHandler` and `setPermissionCheckHandler` per-session with allowlist sets and explicit default-deny — `lockdownUntrustedPermissions` (always `callback(false)` / `return false`) and `lockdownTrustedPermissions` (gate on an `allowed` Set) in `electron/setup/security.ts`. New Electron permission types should require explicit opt-in, not implicit allow; a `session-created` listener default-locks any dynamically created partition.

Log all permission denials with partition context — this is critical for debugging CSP-related issues where silent failures are hard to trace.

## Applies when

Upgrading Vite (check if `'unsafe-eval'` was added for HMR and can be removed from the trusted-renderer CSP); reviewing Electron permission handlers; adding new webview features that request new permission types.
