## Context

Before #10979, `electron-builder.config.cjs` declared only the `daintree://` URL scheme and a `.dntr` fileAssociations entry (added in #9293, gated on `process.env.CSC_LINK`) — no document type for folders. `electron/setup/environment.ts` had a single macOS `open-file` handler that routed every incoming path straight into the `.dntr` plugin-archive installer. Issue #10976 asked for folders dropped on the Dock icon (or opened via Finder's "Open With") to open as a project through the existing `handleDirectoryOpen` (`electron/menu.ts`), the same routine already reused by the Open Directory menu item and `--cli-path`.

## Problem

Dragging a folder onto the Dock icon did nothing, and the Dock icon would not even highlight during the drag — a symptom that reads like a missing drop-event listener, pointing an investigator toward Electron's window/dock event wiring rather than the actual gap, a packaging declaration. Even if a folder had somehow reached the process, the one `open-file` handler would have misidentified it as a `.dntr` plugin archive to install.

## Root cause

macOS Launch Services decides whether an app is even offered as a drop target or "Open With" entry purely from the UTIs the app declares in `CFBundleDocumentTypes` (Info.plist) — Electron has no generic "accept any dropped path" fallback; if a UTI isn't declared, the OS discards the drop before any app code runs, which is exactly why the Dock icon never highlighted. The fix declares `public.folder` (the Finder-facing folder UTI — distinct from the abstract `public.directory`) with `CFBundleTypeRole: "Viewer"` / `LSHandlerRank: "Alternate"` so Finder stays the default folder handler and Daintree is only an alternate. `electron-builder` concatenates `mac.fileAssociations` (the existing `.dntr` entry from #9293) with `mac.extendInfo.CFBundleDocumentTypes` into a single `CFBundleDocumentTypes` array — a merge behavior established by #8035 — so the two declarations coexist; nothing about the config shape guarantees that on its own, and a naive reader would reasonably expect one to clobber the other.

Two mechanisms compound to make this both easy to get wrong and hard to verify. First, the new declaration must be gated behind `process.env.CSC_LINK`, mirroring the `.dntr` guard from #9293: Launch Services reads the UTI declaration from the _signed_ app bundle at registration time, so an unsigned dev build that declares itself a folder-viewer pollutes the developer's machine-wide LS database with a mapping that outlives even uninstalling the app. Second, and more fundamentally, Launch Services never re-reads Info.plist for an `npm run dev` / unpacked Electron process at all — document-type registration only happens from a signed, packaged build. That makes the entire OS-level behavior (dock highlight, Open With menu entry, default-vs-alternate resolution) impossible to observe with any amount of dev-build testing; the PR's own testing note says so explicitly, and ships 109 unit tests over the routing/serialization logic instead, deferring the OS-level check to a manual packaged-build smoke test.

Once a folder does reach the process, the `open-file` handler branches on `fs.statSync(filePath).isDirectory()` before any consumer sees the path — added precisely because the pre-existing handler routed everything unconditionally into the `.dntr` plugin queue, so without that branch a dropped folder is misidentified as a plugin archive install attempt.

## Lesson

- **A macOS "make Finder/Dock treat this as ours" feature (document type, folder viewer, new file extension) requires a `CFBundleDocumentTypes`/`fileAssociations` UTI declaration in `electron-builder.config.cjs`** — Electron's `open-file` only fires for paths the OS already decided to hand over; there is no app-level catch-all for unregistered content types.
- **Registration-level behavior for these features cannot be verified in a dev build, full stop** — budget a signed, packaged smoke-test step; `npm run dev`, however thoroughly driven, will never show a Dock highlight, an Open With entry, or correct default/alternate handler resolution, because Launch Services only registers document types from a signed bundle.
- **Gate every new Launch-Services-facing declaration behind `process.env.CSC_LINK`**, following the `.dntr` precedent from #9293 — this isn't a security control, it's to stop unsigned dev builds from writing an LS database entry that's awkward to remove and outlives the app.
- **`electron-builder` merges `fileAssociations` and `extendInfo.CFBundleDocumentTypes` into one array (#8035)** rather than one replacing the other — safe to add a second UTI declaration alongside `.dntr`, but verify this per config key rather than assuming; other electron-builder keys do overwrite.
- **When one `open-file`/`open-url` handler serves multiple content kinds, branch on `fs.statSync(...).isDirectory()` (or equivalent) before any content-specific consumer runs** — the pre-#10979 handler routed every path unconditionally into the `.dntr` installer, so a folder without that branch gets misrouted as a plugin archive.
- **Serialize pre-window-ready OS handoffs through one promise chain** (see `openDirHandler.ts`'s `openChain`, covering both a cold-launch drain and warm live-consumer drops) rather than firing opens concurrently — `handleDirectoryOpen` mutates shared project/window state, so concurrent opens race on which project ends up focused.

## Applies when

- Touching `electron-builder.config.cjs`'s `mac.fileAssociations` / `mac.extendInfo.CFBundleDocumentTypes`, or adding any new macOS document type, URL scheme, or Quick Action registration.
- Adding a new macOS `open-file`/`open-url` handler or content-type branch in `electron/setup/environment.ts`.
- Diagnosing "Dock icon doesn't highlight / won't accept the drop" or "Open With doesn't list Daintree" for a new content type on macOS — the cause is almost always a missing UTI declaration, not event wiring.
- Deciding test coverage for Launch-Services-dependent behavior — unit-test the routing/queue/serialization logic, but treat actual OS registration as only checkable via a signed packaged build.
- Wiring a new pre-window-ready OS event queue (compare `pendingCliPath`, `pendingDntrPaths`, `_pendingOpenDirPaths` in `environment.ts`) — check whether concurrent consumption needs the same serialized-chain treatment as `openDirHandler.ts`.
