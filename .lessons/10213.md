## Context

Dev-preview panels render a live dev server inside a guest webview behind a stable `dp-*.localhost` proxy origin (`DevPreviewProxyService`, a passthrough that rewrites only `Host`/cookie headers, never the page body). Guest console output is already streamed to the renderer over CDP via `useDevPreviewConsoleCapture`, keyed per-pane by `row.paneId`. #10213 (resolves #9975) added a Tier 3 "Live reload disconnected" banner when Vite's HMR socket dies silently.

## Problem

With a custom `server.hmr.*` config (`hmr.host` / `hmr.clientPort` point the browser socket off the proxy origin; `hmr.protocol: 'wss'` fails the handshake because the proxy serves plain HTTP), live reload dies but nothing signals it. Worse, the existing signal actively misleads: Vite keeps logging `[vite] hmr update` on every save, `UrlDetector`'s compile markers (`electron/services/UrlDetector.ts`) fire the pane's "Compiling" phase, and the pane reads as "just updated" while the webview is stale. The server compiled; the browser never received it.

## Root cause

This is a detection-BOUNDARY decision, not a bug fix, and the boundary is dictated by a hard constraint chain a future agent will otherwise re-break. Three channels could in principle detect a dead HMR socket, and two are unavailable: (1) **`executeJavaScript` into the guest is off the table** — docked/hidden dev-preview webviews are CDP-frozen via `Page.setWebLifecycleState`, and `executeJavaScript` queues as a freezable task that hangs until thaw (the #8310 trap; that PR read `scrollY` through raw CDP instead, and `useDevPreviewScrollCapture.ts` still carries the warning). (2) **Native Chromium socket errors (`net::ERR_CONNECTION_REFUSED`) bypass the JS console channel entirely** — they never arrive as guest console rows. That leaves one signal: **Vite's own failure log lines**, matched with `VITE_HMR_FAILURE_PATTERN = /\[vite\] (failed to connect to websocket|server connection lost)/i` against `row.summaryText` in the stream we already capture. No new IPC, no main-process change.

The second subtlety is a generation race. A dev-server restart leaves the OLD guest page polling and logging `[vite] server connection lost` from its now-defunct navigation generation, while a healthy reload loads the fresh server. Flipping `hmrDead` on those stale rows would resurrect the banner over a working preview. The fix gates the set on generation: `setHmrDead(true)` only when `row.navigationGeneration >= currentGenerationRef.current`, and `onConsoleContextCleared` advances the ref FIRST (then clears `hmrDead`) so old-page stragglers can't re-arm it. `hmrDead` is sticky component state cleared on three transitions: context-clear (reload/nav), `resetHmrDead()`, and the pane's dev-server leaving `running` (`DevPreviewPane` effect on `status`).

## Lesson

- **Detecting anything inside a dev-preview guest webview is restricted to the passive CDP console stream — never reach for `executeJavaScript`.** Docked/hidden panels are CDP-frozen, so `executeJavaScript` hangs until thaw (#8310). If you need guest state (scroll, HMR liveness, DOM), it must come through an already-captured CDP channel or a raw CDP domain call, not an injected JS eval.
- **The CDP console channel only sees what the guest logs to `console.*`; native network failures never appear there.** `net::ERR_CONNECTION_REFUSED` and other Chromium socket errors bypass the JS console entirely, so console-stream detection depends on the framework reaching the point of logging its own failure. Dead-HMR detection is best-effort by construction — document the gap rather than pretending it's complete.
- **A framework's "success" log is not proof the browser applied it.** `[vite] hmr update` fires from the server on every save regardless of whether the browser socket delivered it, and it drives `UrlDetector`'s "Compiling" phase — a false-positive that points diagnosis the wrong way. When a signal comes from the server side, don't treat it as client-side liveness.
- **Sticky detection state fed by a per-navigation stream must be generation-gated in BOTH directions.** Gate the set (`navigationGeneration >= currentGenerationRef.current`) so a defunct page's straggler logs can't arm the banner, and advance the generation ref BEFORE clearing on context-cleared so the reset wins the race. Ungated, a dev-server restart flickers the warning back over a healthy reload.
- **This is a Tier 3 running-state failure with a pane-local recovery** (`DevPreviewHmrDeadBanner`, now in `DevPreviewBanners.tsx`, gated on `status === "running" && hmrDead`, Reload reconnects the socket) — matching CLAUDE.md's escalate-a-stalled-auto-recovering-state rule, not a global banner.

## Applies when

- Adding any browser-side detection (HMR, network, DOM, error) to a dev-preview guest webview — the channel is the passive CDP console stream; `executeJavaScript` hangs on CDP-frozen docked panels (#8310).
- Diagnosing "the dev-preview shows Compiling / looks updated but edits don't appear" — the `[vite] hmr update` server log and `UrlDetector` compile phase mislead; the real signal is `[vite] failed to connect to websocket` / `[vite] server connection lost` in the console capture.
- Touching `useDevPreviewConsoleCapture.ts`, `VITE_HMR_FAILURE_PATTERN`, `hmrDead`/`resetHmrDead`, or the `navigationGeneration` gating on `onConsoleMessage` / `onConsoleContextCleared`.
- Assuming native Chromium socket errors (`net::ERR_CONNECTION_REFUSED`) are catchable from the renderer, or wiring sticky state off a per-navigation console/event stream where a stale generation can resurrect a cleared warning.
