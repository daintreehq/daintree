## Context

The builtin GitHub forge plugin normalizes GitHub's GraphQL/REST payloads into the forge-neutral `PR`/`Issue` contract; it went forge-neutral in #10343 / #10347. Two independent code paths feed the PR dropdown from the SAME `LIST_PRS_QUERY` response: `listPRs` (`readOps.ts`) maps each raw node through `toForgePR`, while the stats subsystem separately builds and caches a first page through a different chain — `parsePRNode` → legacy `GitHubPR` → `gitHubPRToForgePR` → `PR`. The dropdown paints the cached page first, then replaces it with the fresh list.

## Problem

CI status icons appeared next to PRs in the GitHub PR dropdown for a moment when it opened, then vanished once the list finished refreshing (#10357). The sidebar CI kept working because it flows through the worktree store's `pr-detected` events, not the forge list path. It worked in 0.18.2 and broke after the forge-neutral refactor. The misleading part: the flash made "fresh data" look like the fix arriving, but fresh was the regression — the correct cached value was being overwritten by an impoverished fresh fetch.

## Root cause

`LIST_PRS_QUERY` fetches `commits(last: 1) → statusCheckRollup.state`, but the two mapper chains over that node had drifted. `parsePRNode` (`GitHubPRs.ts`) read `commits.nodes[0].commit.statusCheckRollup.state` into `GitHubPR.ciStatus`, so the stats first-page cache (via `gitHubPRToForgePR`) carried `ciStatus`. The direct list mapper `toForgePR` never read `node.commits` at all, so every fresh list PR came back with `ciStatus` absent. Cache-then-refresh did the rest: the dropdown first rendered the cached page (has `ciStatus` → icons), then the fresh list replaced it (no `ciStatus` → icons gone). **The fresh response was strictly worse than the cache it replaced.** It was non-obvious because the query still fetched the field, the `PR` type still allowed it, and no error fired — the field just silently stopped being mapped on one of two paths that a user cannot tell apart.

The fix taught `toForgePR` to read the rollup via the same optional chain and map it through the shared `mapListCIStatus` helper, spreading `...(ciStatus ? { ciStatus } : {})` so an absent rollup leaves the field absent (no CI configured is not the same as passing). Since #10359 the code was refactored — `toForgePR` and `gitHubPRToForgePR` now both live in `plugins/builtin/github/main/mappers.ts` — but the fix is intact and both go through `mapListCIStatus`.

## Lesson

- **When a field flashes then disappears on refresh in a cache-then-fetch UI, the fresh fetch is the suspect, not the cache** — the mapper on the refresh path is dropping a field the cache path preserved. Diff the two mappers; don't re-audit the renderer (the renderer here was fine — `GitHubListItem` shows the icon whenever `item.ciStatus` is present).
- **The GitHub plugin has at least four parallel node→contract mappers** — `toForgePR`, `gitHubPRToForgePR`, `restToForgePR`, and the legacy `parsePRNode` chain — over overlapping PR shapes, and nothing enforces parity between them. Any field added to `LIST_PRS_QUERY` or the `PR` contract must be wired into every mapper a given surface can reach, or that surface silently under-populates. The #10359 tests only cover the `listPRs`/`toForgePR` path, so drift can still recur.
- **The GraphQL query is the source of truth for what SHOULD be mapped, not the TypeScript type.** These mappers take `node: Record<string, unknown>`, so an unmapped-but-fetched field produces no type error. Grep `GitHubQueries.ts` for the field (`statusCheckRollup`, `reviewDecision`, `comments.totalCount`) and confirm each relevant mapper actually reads it.
- **Absence is not a default: use the conditional spread `...(x ? { x } : {})`** so a null/missing rollup leaves `ciStatus` absent rather than defaulting to a state. "No CI configured" must not collapse to "passing" — the renderer branches on presence, so a spurious value would paint a green check on a PR that has no checks.
- **`mapListCIStatus` is deliberately lossy** (`ERROR`→`failure`, `EXPECTED`→`pending`, non-string/unknown enum→`undefined`) — unknown rollup states fall through to absent rather than a guessed mapping. Keep that conservative default if GitHub ever widens the rollup enum; don't invent a fallback state.

## Applies when

- Adding or renaming a field on the forge `PR`/`Issue` contract or in `LIST_PRS_QUERY` — wire it into every parallel mapper (`toForgePR`, `parsePRNode`, `gitHubPRToForgePR`, `restToForgePR`), not just the one your test hits.
- Diagnosing any forge value (CI status, review decision, comment count) that flashes then disappears, or is richer in the cached first page than after the list refresh, in the PR/issue dropdown.
- Touching `plugins/builtin/github/main/mappers.ts`, `GitHubPRs.ts` (`parsePRNode`), `GitHubQueries.ts`, or the stats first-page cache path.
- Reviewing any GraphQL→contract mapping where the node is typed `Record<string, unknown>` — the compiler will not catch a dropped field, so parity must be checked against the query.
- Mapping a boolean-ish status where "unset" and "negative" genuinely differ (CI configured vs passing, review requested vs approved) — confirm absent stays absent through the conditional spread.
