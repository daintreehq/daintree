## Context

Each project window owns a `ProjectViewManager` (PVM) that governs cached `WebContentsView` count, efficiency freeze, and the low-memory free threshold. `ResourceProfileService` (`electron/services/ResourceProfileService.ts`) is a single global service that, under memory pressure, clamps cached views to 1, freezes renderers, and arms the low-memory floor. It reached the PVM through `getProjectViewManager()` from `electron/window/windowRef.ts`.

## Problem

In multi-window sessions the cached-view limit, efficiency freeze, and low-memory threshold only ever reached one window — the most recently created one — or nothing if that window had already closed. The memory controls looked fully wired (the calls existed, tests passed) but silently governed a single window while every other open window kept full cached-view limits and stayed unfrozen under pressure.

## Root cause

`windowRef.ts` holds `projectViewManager` as a module-level mutable singleton. `main.ts` calls `setProjectViewManager(pvm)` on every window create (line ~359) and `setProjectViewManager(null)` in that window's cleanup (line ~377). So the ref is last-write-wins: opening a second window overwrites the first window's PVM, and closing the most-recent window nulls it back to `null` even while older windows are still open. A global service reading this single ref therefore controls an arbitrary/stale window, not all of them. The fix: `ResourceProfileService` takes `getAllProjectViewManagers(): ProjectViewManager[]` instead of `getProjectViewManager()`, and `globalServicesInit.ts` builds the array from `windowRegistry.all().map((w) => w.services.projectViewManager).filter(Boolean)`, then loops, applying controls per-PVM with per-call try/catch so one window's failure doesn't skip the rest.

## Lesson

- A module-level singleton ref set on window-create and nulled on window-close (the `windowRef.ts` `setProjectViewManager`/`getProjectViewManager` pattern) is last-write-wins and is correct only for "act on the current/primary window" semantics. Any global service whose effect must reach _every_ window must NOT resolve through this singleton.
- For all-window operations, enumerate live instances from `WindowRegistry.all()` and read the per-window service off `WindowContext.services` (`w.services.projectViewManager`), filtering out `undefined`. `getPrimary()` is the right call when you genuinely want one window; `all()` when you want fan-out.
- When fanning a control out across windows, wrap each instance's calls in their own try/catch — a throw on one window (e.g. an `onViewEvicted` callback failing inside `evictStaleViews`) must not abort the loop and leave later windows in a half-applied state (e.g. frozen-but-not-unfrozen).
- The residual `getProjectViewManager()` callers — `ipc/utils.ts`, `createWindow.ts`, `menu.ts`, `mcp-server/rendererBridge.ts`, `PluginRendererDispatcher.ts` — are "active/most-recent window" fallbacks, which the singleton happens to satisfy; do not blindly migrate them, but do audit any NEW caller against the all-vs-one question before reaching for the singleton.

## Applies when

- Adding or changing a global main-process service (resource governance, hibernation, broadcast, telemetry) that must take effect across all open project windows.
- Touching `electron/services/ResourceProfileService.ts`, `electron/window/globalServicesInit.ts`, or anything in `electron/window/` that resolves a per-window service.
- Reaching for `getProjectViewManager()` / `getMainWindow()` / any `windowRef.ts` accessor — stop and decide whether you need the current window (singleton OK) or every window (use `WindowRegistry.all()` + `WindowContext.services`).
- A multi-window bug where a memory/performance/lifecycle control "works" in single-window manual testing but silently affects only one window, or stops working after a window is closed.
- Reviewing per-window services scoped into `WindowContext.services` (#4624) and verifying their global consumers iterate the registry rather than a stale module ref.
