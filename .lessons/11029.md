## Context

`WorktreeMonitor` and `WorkspaceService` (workspace-host utility process) run the pipeline that turns a file edit or an external `git worktree add`/`remove` into a sidebar update: `gitFileWatcher.ts` debounces per-worktree fs events before a git-status poll, and `TopologyWatcher.ts` debounces fs events signaling worktree add/remove, then reconciles against `git worktree list`, rate-limited by a post-reconcile cooldown. PR #11029 first added a benchmark suite (PERF-130 to PERF-141, `scripts/perf/scenarios/worktreeSidebar.ts`) that measures this propagation end-to-end through the real `WorktreeMonitor`/`WorkspaceService`/`TopologyWatcher` plus a headless `createWorktreeStore`, then used those numbers to drive the fix in the same branch.

## Problem

Sidebar updates lagged far behind the actual cost of the work: one file edit took 279ms p50 (PERF-130) and one `git add && git commit` took 377ms (PERF-131) to reach the sidebar-bound snapshot, while a full git-status pass on a single worktree costs 8.2ms (PERF-100). Separately, an external `git worktree remove` landing right after other topology activity (PERF-139) sometimes took over 2 seconds to drop the row — a symptom that reads like a poll-interval or fs-watcher-liveness bug (both real, documented elsewhere as #8510's FSEvents-silence case) rather than what it actually was.

## Root cause

Two independent mechanisms produced the two symptoms.

Latency: every debounce in the pipeline was trailing-only. `gitFileWatcher.handleWorktreeChange` computed its flush delay purely from burst count and a fixed ramp, so an isolated single edit waited out the same `worktreeMinDebounceMs` (250ms) as the first event of a real storm. `TopologyWatcher` had a flat 300ms event debounce and a flat 2000ms post-reconcile cooldown, for the same reason: nothing distinguished "one thing happened" from "many things are happening."

Stranded events: `TopologyWatcher.scheduleReconcile()`'s cooldown guard — `if (!force && Date.now() < this.watchCooldownUntil)` — before this PR just set `this.watchCooldownDirty = true` and returned, with no timer ever armed to recheck that flag. The _other_ deferral branch (`reconcilePending` already true) drained fine because its `finally` block rescheduled after the cooldown elapsed, but the cooldown-guard branch had no equivalent — a topology event landing inside the ~500-2000ms cooldown, with nothing else touching that worktree afterward, had no path back to a reconcile except the 90-second `TOPOLOGY_SAFETY_INTERVAL_MS` sweep. The pre-existing test for this path masked the gap: it manually reset `(watcher as any).reconcilePending = false` mid-test instead of letting the cooldown branch run to expiry, so the untested branch never actually executed.

## Lesson

- **Give a trailing debounce a leading-edge fast path keyed off a quiet baseline**, not off burst state alone: `gitFileWatcher` tracks `lastWorktreeFlushAt` and, if a burst starts after `worktreeQuietWindowMs` (2000ms) of silence, flushes at `worktreeLeadingDebounceMs` (50ms, later retuned to 25ms in #11039) instead of the trailing minimum; any further event in that burst overwrites the timer back onto the normal ramp so real storms still coalesce (PERF-133: 50 rapid edits still coalesce to one emit, 73ms not 833ms). Use this pattern anywhere one debounce serves both "user did one isolated thing" and "user is mid-batch" — don't force both through the same trailing wait.
- **Every cooldown/rate-limit gate that defers work must arm its own drain timer**, not rely on the in-flight-work branch's `finally` or a later unrelated event to rediscover the dirty flag. The fix is `armCooldownDrain()`: a one-shot `setTimeout` for `watchCooldownUntil - now + 5ms` that flips `watchCooldownDirty` false and re-enters `scheduleReconcile()`. Any `if (Date.now() < cooldownUntil) { dirty = true; return; }` needs that same timer or the dirty state can strand.
- **A small epsilon on a drain timer is load-bearing.** The `+ 5` in `watchCooldownUntil - Date.now() + 5` stops an early-firing timer from re-checking the guard microseconds before expiry and deferring itself a second time.
- **A test that manually mutates private state to skip a timing branch flags that branch as untested**, not as a shortcut. `(watcher as any).reconcilePending = false` in the old cooldown test bypassed the exact cooldown-guard return that had the missing-drain bug; the fixed test instead advances fake timers through the real window and asserts the deferred reconcile fires on its own.
- **When "X feels slow" is pure debounce/cooldown wait, not the underlying operation, prove it by benchmarking the pipeline against the atomic op**: PERF-100 (8.2ms git status) vs PERF-130 (279ms sidebar propagation) is the shape of that comparison, and it's what told this PR to touch timers, not the git-status code path.

## Applies when

- Touching `gitFileWatcher.ts`, `TopologyWatcher.ts`, or `WatcherController.ts` debounce/cooldown constants (`worktreeMinDebounceMs`, `worktreeLeadingDebounceMs`, `worktreeQuietWindowMs`, `TOPOLOGY_EVENT_DEBOUNCE_MS`, `TOPOLOGY_RECONCILE_COOLDOWN_MS`).
- Diagnosing "sidebar/worktree row didn't update" or "external worktree add/remove shows up late or not at all" — check whether the event landed inside `watchCooldownUntil` before assuming a poll-interval or fs-watcher-liveness bug (#8510 is the other known cause of stale rows).
- Adding or reviewing any debounce that must serve both isolated single events and rapid bursts — leading-edge-with-reset-to-trailing is the applicable fix, not a flat delay.
- Reviewing any rate-limit/cooldown gate that only sets a dirty flag on its deferred branch — verify a timer drains it; "the next event will pick it up" is not proof.
- Writing perf benchmarks for a propagation/pipeline path — pair the end-to-end scenario with an atomic-operation one (PERF-130-style vs PERF-100-style) to see whether latency is timers or real work.
