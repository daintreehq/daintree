## Context

When a session dies without writing a crash log (external kill, OOM, watchdog SIGKILL, power loss), the next launch finds only the `running.lock` marker and synthesizes a `CrashLogEntry` via `buildCrashEntryFromMarker` in `electron/services/CrashRecoveryService.ts`. That timestamp feeds three consumers: the recovery dialog's "ended unexpectedly on {date}" line, the GitHub crash report's "Crashed at" / "Session duration" lines, and the `SUSPECT_WINDOW_MS = 30_000` panel-suspect check in `extractPanelSummaries` (`Math.abs(crashTimestamp - t.createdAt) < SUSPECT_WINDOW_MS`), which is the sole input to the #8704 repeat-suspect quarantine in `PanelSuspectLedgerService`. #10120 closed issue #10062 inside the crash-recovery hardening arc #10114/#10117/#10118 (cause classification, panel-count freshness, failed-restore propagation).

## Problem

Marker-only entries stamped `timestamp: Date.now()` and `sessionDurationMs: Date.now() - marker.sessionStartMs` at relaunch. An overnight crash read as having happened the next morning, session duration silently included the whole dead interval, and — the worst part — the 30s suspect window compared panel `createdAt` against relaunch time, so `isSuspect` essentially never fired for these crash classes. Since the quarantine ledger only increments from `isSuspect`, the repeat-suspect machinery was dead for exactly the classes it was built for: OOM kill loops, where an in-process recorder can never run.

## Root cause

The dying process cannot stamp its own death time, so the relaunch must reconstruct it — and `Date.now()` at reconstruction is the one value guaranteed wrong by the entire dead interval. The fix is `resolveMarkerCrashTimestamp`: a priority chain of `watchdogAnnotation.killedAt` (exact SIGKILL time) > `marker.lastSuspendStart` (power loss during sleep) > `cachedBackupSnapshot.capturedAt` > `marker.lastHeartbeatMs` (ticked every backup interval, so at most ~60s stale), each candidate gated by `typeof === "number" && Number.isFinite && > 0`, with the winner clamped to `[marker.sessionStartMs, nowMs]` — never before the session (negative `sessionDurationMs` breaks `formatDuration` in the dialog) and never after relaunch (future-dated report, dead suspect window).

Two follow-up commits killed traps in the "obvious" implementation. First, the backup timestamp was initially `fs.statSync(parseableBackupPath).mtimeMs` — but the Windows/EPERM copy-fallback in `preserveBackupForRecovery` writes a NEW `crashed-*` file at relaunch, so its mtime IS the relaunch time and would out-rank the heartbeat, silently re-introducing the bug on Windows only. The correct source is the in-memory `cachedBackupSnapshot.capturedAt`, stamped pre-crash by `captureSessionSnapshot`. Second, `JSON.parse('{"killedAt":1e309}')` returns `Infinity`, which passed the watchdog flag's `typeof === "number" && > 0` validation and rendered as `"Infinity"` in the GitHub crash URL and `"Invalid Date"` in the dialog — `Number.isFinite` now gates `killedAt`, `missedBeats`, and `mainPid`, and `isValidMarker` requires a finite positive `sessionStartMs` since the clamp uses it as the floor.

## Lesson

- **Never stamp Date.now() on an event reconstructed after the fact.** Resolve from recorded evidence in precision order and clamp to the knowable interval; the honest fallback when no evidence exists is the clamped relaunch time, stated as such.
- **Disk mtime is not pre-crash evidence.** Any fallback/copy/repair path that rewrites a file (here the Windows EPERM copy-fallback in `preserveBackupForRecovery`) resets mtime to now. Prefer an application-level timestamp written inside the payload (`capturedAt`) over filesystem metadata.
- **`typeof x === "number" && x > 0` does not exclude Infinity.** `JSON.parse` of an oversize number literal (`1e309`) yields `Infinity`, which sails through sign checks and then corrupts downstream rendering. Validate every JSON-sourced number with `Number.isFinite` — the codebase now does this for the watchdog flag and marker fields.
- **A timestamp bug can silently disable a safety system.** The #8704 quarantine gates on a 30s window; feeding it relaunch time didn't error, it just never matched. When reviewing time-window logic, ask what supplies the timestamp on every path, not just the happy one.
- **A test whose "event time" and "now" share the same tick can't catch relaunch-time bugs.** The pre-existing test created the marker and initialized the service in one instant, collapsing crash time and relaunch time to the same value. Regression tests must model the dead interval — fake timers including `"Date"` in `toFake` (lesson #7917), marker at T0, `vi.setSystemTime(T0 + DEAD_MS)` before init.

## Applies when

- Touching `consumeMarker`, `buildCrashEntryFromMarker`, `resolveMarkerCrashTimestamp`, or anything in `CrashRecoveryService` that dates or measures the previous session.
- Adding a timestamp source for any post-mortem reconstruction (crash, kill, session journal) — check whether the source survives the death/relaunch boundary unmodified, especially on Windows.
- Validating numbers parsed from JSON flag/marker/IPC payloads — `> 0` alone admits Infinity.
- Diagnosing "panel quarantine / isSuspect never triggers for OOM or external kills" or wrong dates in the recovery dialog and GitHub crash report.
- Writing tests for any code comparing a stored timestamp against `Date.now()` — verify the test separates the two clocks.
