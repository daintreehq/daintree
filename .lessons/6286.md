## Context

The main-process and preload bundles are produced by esbuild (`scripts/build-main.mjs`), which writes to `dist-electron/electron` and applies a `define` block that constant-folds runtime-critical env reads (`process.env.SENTRY_DSN`, and in prod the E2E-strip defines `DAINTREE_E2E_*` that dead-code-eliminate the `contextBridge.exposeInMainWorld` test backdoors). Separately, `npm run typecheck` runs `tsc -b electron/tsconfig.json`, and `-b` (build mode) always emits `.js` to disk.

## Problem

Running `npm run check` after `npm run build` overwrote esbuild's `main.js` / `bootstrap.js` in `dist-electron/electron` with tsc's plain transpiled output. tsc does no define substitution, so the runtime defines esbuild had inlined were gone. The app launched against the build artifacts and crashed — but only at launch, never at typecheck time, because tsc itself was happy.

## Root cause

`tsc -b electron/tsconfig.json` and esbuild both targeted `dist-electron/electron` as `outDir`/`outdir`. tsc's emit lacks every transform esbuild owns (define inlining, constant-folding, dead-code elimination of E2E branches). The two steps silently shared an output directory, so whichever ran last won. The earlier lesson #4893 had explicitly carved out the _preload_ as the special case ("the main electron tsconfig correctly uses `tsc -b` because it intentionally emits `.js` files") — but once esbuild became the producer of the _runtime_ main bundle too, that carve-out became wrong: an intentionally-emitting tsconfig is still dangerous if a bundler owns the same directory. Fix: redirect both tsconfigs' `outDir` to a separate `dist-typecheck/` tree esbuild never touches (and ignore it in `.gitignore`/`.prettierignore`/eslint).

## Lesson

- A tsconfig that "intentionally emits" is NOT automatically safe to point at the dist dir. The question is not "does this target emit?" but "does any bundler step ALSO write here?" If yes, the tsc emit must go to a throwaway dir (`dist-typecheck/`), even for main-process code.
- Keep `tsc -b` for type-checking targets that need project-reference build ordering, but never let its `outDir` overlap an esbuild/Vite `outdir`. Use a dedicated `dist-typecheck/` and ignore it everywhere.
- esbuild `define` substitutions are invisible to tsc. Any pipeline where typecheck and bundle can run in either order against the same dir will produce a define-less artifact that passes typecheck and only fails at runtime/launch.
- When verifying such a fix, shasum the dist artifacts before and after `npm run check` — identical hashes prove no clobber.

## Applies when

- Touching `electron/tsconfig.json`, `electron/tsconfig.preload.json`, or any tsconfig whose `outDir` could land in `dist-electron/` / `dist/`.
- Editing the `typecheck` or `check` npm scripts, or adding a new `tsc -b` / `tsc -p` target to the build chain.
- Adding or changing esbuild `define` entries in `scripts/build-main.mjs` (SENTRY*DSN, DAINTREE_E2E*\* strips) — anything that relies on constant-folding being present in the shipped main/preload bundle.
- Diagnosing a crash that only reproduces after running `npm run check` (or any typecheck) following a build, with no source change — suspect a clobbered, define-less artifact before module resolution.
- Adding a new utility-process or main-process entry point bundled by esbuild that is also type-checked.
