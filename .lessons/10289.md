## Context

Fleet broadcasting cross-wires several renderer Zustand stores: `useFleetArmingStore.armedIds` drives auto-clear of `useFleetFailureStore` failure pills (#9923) and pruning of `useFleetTargetOverridesStore` per-pane skip/payload overrides (#9973), and a main-process broadcast-write result IPC (`terminalClient.onBroadcastResult`) writes back into the arming/failure stores (#9967). These subscriptions were originally wired at module scope — a top-level `useFleetArmingStore.subscribe(...)` or an IIFE deduped across re-evaluations by a `globalThis` flag (`__daintreeFleetFailureSubscription = { registered }`). This three-PR wave (#10275, #10287, #10289) moved all of them under the renderer store orchestrator, following the pre-existing `subscribeFleetArmingPanelPruning` model.

## Problem

Fleet lifecycle-edge state silently desynced: failure pills didn't auto-clear when the armed set drained, broadcast-write results applied to the wrong store instance, and a pane disarmed-then-rearmed while the drafting popover stayed open was silently excluded from the next broadcast, with `FleetDraftingPill` showing ghost divergence counts (#9973). The desync was intermittent and mostly surfaced in unit tests (`vi.resetModules()`) and under Vite HMR; a full page reload always looked clean, which pointed diagnosis away from the subscription wiring.

## Root cause

Two independent mechanisms. (1) Module-scope subscription + `globalThis` dedupe guard vs. fresh store instances. HMR and `vi.resetModules()` re-evaluate the module: Zustand `create()` produces FRESH store singletons, but the `globalThis.registered` flag is already `true`, so the re-import does NOT re-subscribe. The ORIGINAL subscription — closed over the now-orphaned first-import instances — keeps firing and mutating those dead stores, while the live stores the UI reads never receive an event. A guard meant to prevent double-registration instead pins the wiring to garbage. The broadcast IIFE compounded this by discarding the unsubscribe from `onBroadcastResult`, so re-registration stacked stale IPC callbacks. (2) Per-id derived state has no membership owner. `disarmId` only mutates the arming store, and no lifecycle-edge `clear()` fires while the drafting popover stays open, so `skippedIds`/`payloadOverrides` and `failedIds` keyed by pane id linger after a pane leaves `armedIds` — a stale `skippedIds` entry is what silently drops a re-armed pane from the broadcast.

The fix pattern (sections 5a–5e in `rendererStoreOrchestrator.ts`): each module exports a `subscribeX(): () => void` factory registered via `disposables.add(toDisposable(subscribeX()))`, so the `DisposableStore` tears it down on `destroyStoreOrchestrator()` and re-wires against current singletons on re-init. Critically, each factory runs an initial reconciliation pass BEFORE subscribing (`reconcileFleetFailures(initialArmed)` in `fleetFailureStore.ts`) — unlike a never-torn-down module-scope sub, an orchestrator-scoped sub has a torn-down window and would otherwise miss a drain or partial disarm.

## Lesson

- **Never wire a cross-store Zustand subscription at module scope.** Export a `subscribeX(): () => void` factory and register it through `initStoreOrchestrator()` via `disposables.add(toDisposable(subscribeX()))`. Canonical model: `subscribeFleetArmingPanelPruning` in `fleetArmingStore.ts`; the wave added `subscribeFleetTargetOverridesPruning`, `subscribeFleetBroadcastResult`, and `subscribeFleetFailureAutoClear` as sections 5b–5d.
- **A `globalThis`/module-level "already registered" boolean guarding a `.subscribe(...)` call is the anti-pattern, not the fix.** It is exactly what pins the old subscription to orphaned store instances under HMR and `vi.resetModules()`. If you find one, that IS the bug — delete it and move the subscription under the orchestrator.
- **An orchestrator-scoped subscription MUST run an initial reconciliation pass before subscribing.** It has a torn-down window (destroy → mutate → re-init, or an HMR gap) that a never-disposed module-scope sub never had. Compute current state and reconcile once, THEN subscribe — `rendererStoreOrchestrator.test.ts` covers the drain/partial-disarm-during-teardown paths this recovers.
- **Any IPC/event subscription registered this way must return its real unsubscribe** so the `DisposableStore` can drop it — `terminalClient.onBroadcastResult(...)` returns one. Discarding it stacks stale callbacks on every re-register (the #9967 IIFE bug).
- **Per-id derived state (failure pills, target overrides) needs a pruning subscription on the OWNING membership store, or ids linger.** `disarmId` doesn't touch overrides, so a disarmed-then-rearmed pane keeps a stale `skippedIds` entry and is silently excluded from the next broadcast (#9973). Prune on `armedIds` change: clear-all on a full drain, per-id `delete`/`dismissId` otherwise; allocate a replacement Set/Record only when a field actually loses an entry so untouched-field subscribers keep their ref-equality fast path.

## Applies when

- Adding or reviewing any cross-store Zustand subscription (one store's changes mutating another store) — it belongs in `rendererStoreOrchestrator.ts` as a `subscribeX()` factory, never at module scope.
- You see a `globalThis`-flag or module-level boolean guarding a `.subscribe(...)` registration — it will desync under HMR and `vi.resetModules()`.
- A subscription-driven behavior works after a full reload but breaks in unit tests or after an HMR edit — suspect stale store instances captured by a never-re-wired subscription.
- Store-derived per-id UI (failure dots, override/skip badges, `FleetDraftingPill` divergence counts) shows ghost or stale entries after a pane is removed, disarmed, or re-armed.
- Touching `fleetArmingStore`, `fleetFailureStore`, `fleetTargetOverridesStore`, `fleetRawInputBroadcast`, or the 5a–5e block of `rendererStoreOrchestrator.ts`.
