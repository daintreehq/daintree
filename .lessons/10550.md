## Context

The plugin host loads manifest-driven extensions. Before this arc, production user plugins were `import()`ed in-process in the main process (`PluginService.runImport`); only _dev_ plugins ran in a `utilityProcess.fork` hot-reload worker (`PluginDevWorkerHost`, #9304). Three PRs moved everything: #10540 converted the entire host API surface to Promise-returning (enabling prep), #10494 built the `daintree-plugin dev` CLI and closed the FileDecorationProvider dev-worker gap, and #10550 routed ALL user plugins (dev + prod) through the worker while keeping built-ins in-process.

## Problem

Two verified consequences of in-process loading (issue #10526): (1) uninstall/disable/reload never truly unloads — the disposer cascade and `fs.rm` run, but the plugin's module-scope state, timers, and closures stay resident until app restart; (2) dev/prod divergence — `host.process.spawn`, `host.fs.watch`, and `registerForgeProvider` were dev-only-unavailable, so the most powerful surfaces only worked after packaging ("works in dev, breaks in prod"). A crashing/looping plugin could also freeze the main process.

## Root cause

Two platform-level constraints, each discovered the hard way.

1. **There is no in-process API to evict V8's ES-module cache.** Once `import(fileURL)` resolves a module it is cached by URL for the realm's lifetime and cannot be dropped; cache-busting query strings (`?t=`) just accumulate MORE copies. Any in-process loader thus leaks on reload no matter how correct the disposer cascade is; the only clean eviction is discarding the whole realm — a fresh child process per lifecycle. `utilityProcess.fork` was chosen over `vm`/`vm2` (not security boundaries), WASM/QuickJS (break Node compat), `ShadowRealm` (not an OS boundary), and `worker_threads` (shares the process) because it alone preserves full npm/Node/native-addon compatibility AND gives OS-level crash isolation — VS Code's extension-host model. Killing the worker on unload is what finally makes uninstall reclaim memory.

2. **A host method whose contract is required-synchronous and consumed synchronously can never move across the async MessagePort.** `registerForgeProvider`'s `ForgeProviderImpl` exposes `parseRemote` (the routing gate the host calls to decide whether a remote belongs to this provider), the URL builders, and `classifyPushError` — the host invokes them and uses the return value _immediately_. Over the port every call is async, so `parseRemote` would resolve to a `Promise` and the provider would never become routable (#8879). This is structural, not a fixable bug: `pluginDevWorkerHostProxy` stubs `registerForgeProvider` in BOTH dev and prod (the one permanent dev/prod-identical gap), and built-in forge plugins (GitHub) stay on the in-process loader precisely because they rely on that synchronous surface.

## Lesson

- **In-process `import()` leaks the module realm on every uninstall/reload — there is no eviction API.** When memory grows across plugin/module reload cycles, don't re-audit the disposer cascade for a stray timer or listener; the module-scope state itself is unreclaimable in-process. The only clean fix is a fresh realm per lifecycle (`utilityProcess.fork`), killed on unload.
- **Before moving any host across a process boundary, audit every method for a required-synchronous contract.** #10540 first made the ENTIRE host API Promise-returning — a boundary can't carry sync calls. A method the host consumes synchronously (`parseRemote` returning a routing decision, not a Promise of one) is a hard blocker that can't be faithfully proxied; identify these first, because they decide what MUST stay in-process.
- **When a capability can't cross the boundary, keep its provider in-process rather than ship a silent-async stub.** The worker's `registerForgeProvider` logs an honest "not supported" and returns a no-op disposer; a partial async-only proxy would be worse, since the provider would register but never route. Built-ins keep the in-process `runImport` path via the `!plugin.isBuiltin` fork — trusted, never uninstalled, never dev-symlinked, so the unload/divergence problems don't apply.
- **When converting a sync API to async ahead of a boundary move, keep registry mutation synchronous BEFORE the resolved Promise.** #10540's rule: every `registerAction`/`registerHandler`/`registerForgeProvider` mutates the contribution registry and captures its unload disposer synchronously, then `return Promise.resolve(dispose)`. This preserves synchronous revoke-guard throws (calling after `activate()` closed still throws at the call site) and unload-cascade integrity; async registration would let an unload race it.
- **A killed-and-respawned worker needs a reload-generation guard so late host-results can't mis-deliver.** `PluginDevWorkerMainBridge.reloadGeneration` increments on each reload; every host-call captures the generation and drops the result if `disposed || generation !== this.reloadGeneration` — otherwise an in-flight host-result from the prior worker generation lands in the new realm's fresh proxy.

## Applies when

- Moving any subsystem across a `utilityProcess`/`worker_threads` boundary — audit for required-synchronous methods the host consumes immediately before assuming it can be proxied over MessagePort.
- Diagnosing memory that grows across plugin uninstall/disable/reload (`PluginService`, `runImport`) — suspect the un-evictable V8 ES-module cache, not the disposer cascade.
- Touching plugin activation routing (`activateViaWorker`, `plugin.isBuiltin`, `PluginDevWorkerHost` `mode: "dev"|"prod"`, `PLUGIN_PROD_WORKER_KIND`).
- Wondering why `registerForgeProvider` is unavailable to user plugins / why GitHub forge is a built-in — the synchronous `parseRemote`/URL-builder contract, permanent until the forge API's sync surface changes (#8879).
- Converting a synchronous host/service API to Promise-returning (#10540) — keep registry mutation synchronous before resolve; add a generation guard if the far side can respawn.
