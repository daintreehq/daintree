## Context

Daintree exposes ~308 actions as MCP tools. Destructive ones (`danger === "confirm"` in the `ActionManifestEntry` manifest — `worktree.delete`, `git.push`, `terminal.sendCommand`, etc.) must get explicit user approval before `dispatchAction` runs them. The MCP server lives in `electron/services/mcp-server/` (split out of the old `McpServerService.ts`); the per-session `Server` is built in `sessionServer.ts`.

## Problem

The original gate was homegrown: every destructive tool's description appended "Requires explicit confirmation via \_meta.confirmed=true", and `buildToolInputSchema` injected a `_meta.confirmed` boolean into the input schema. The model was expected to read the description and self-confirm by sending `_meta.confirmed=true`. This burns description/schema context on every `tools/list`, depends on the model honoring prose, and a model that fabricates `confirmed=true` self-authorizes a destructive action with no human in the loop.

## Root cause

Confirmation was a model-honored convention, not an execution-pausing primitive. The MCP SDK (`@modelcontextprotocol/sdk`) ships `elicitation/create` (`server.elicitInput`), which pauses tool execution server-side and asks the _client_ (not the model) for input — Cursor and similar clients render it as a native confirm UI. But elicitation is a negotiated capability: not all clients advertise it, so you cannot unconditionally rely on it. Two further traps the migration had to solve:

- Clients are not required to call `tools/list` before `tools/call`, so the destructive-action gate can't depend on a manifest populated by ListTools — it must lazy-fetch (`lookupManifestEntry` → `requestManifest`). Pinned sessions (#7002) deliberately skip the shared `cachedManifest`, so re-reading the cache would return null and silently drop the confirmation entirely.
- Once a capable client is in the elicitation path, a `decline`/`cancel` must NOT fall through to the renderer-modal fallback — that would re-prompt and let a second surface override the user's explicit "no."

## Lesson

For MCP destructive-action confirmation in `sessionServer.ts`:

- Gate on capability negotiation: `server.getClientCapabilities()?.elicitation?.form !== undefined`. If supported, drive `server.elicitInput({ message, requestedSchema })`; otherwise fall through to `dispatchAction(actionId, args, confirmed=false)`, which triggers the renderer-modal fallback. Keep both paths — uneven client support is permanent.
- Do NOT advertise the bypass: the ListTools handler sets the tool description inline as the bare `entry.description` (`sessionServer.ts:185`) with no confirmation hint, and `buildToolInputSchema` injects no `_meta` property. `parseToolArguments` strips and ignores any inbound `_meta.confirmed`. The model can no longer self-confirm.
- Map elicitation outcomes deterministically: `cancel` → `CONFIRMATION_TIMEOUT_CODE`, `decline`/non-`accept` → `USER_REJECTED_CODE`, SDK throw → `ELICITATION_FAILED_CODE` (all in `mcp-server/shared.ts`). Surface each as `isError: true` and record the `confirmationDecision` in the audit log.
- Within the elicitation branch, treat the elicit result as final — never silently retry through the modal. The renderer modal is the fallback for clients that _never entered_ elicitation, not a recovery for a decline.
- Lazy-fetch the manifest at CallTool time (`lookupManifestEntry`) using the value `requestManifest()` returns directly, not a cache re-read, so the gate still fires for ListTools-skipping and pinned (#7002) sessions.

## Applies when

- Adding a new destructive (`danger: "confirm"`) action that will be exposed as an MCP tool, or wiring confirmation for one.
- Touching `electron/services/mcp-server/sessionServer.ts` `CallTool` handler, `runElicitationConfirmation`, `lookupManifestEntry`, or `tierAuth.ts` `buildToolInputSchema` / `parseToolArguments`.
- Any work on MCP client capability negotiation, `elicitation/create` / `server.elicitInput`, or deciding whether a tool surface should embed confirmation hints in descriptions/schemas vs. a protocol primitive.
- Debugging why a destructive MCP tool either confirmed without a prompt, double-prompted, or returned `USER_REJECTED` / `CONFIRMATION_TIMEOUT` / `ELICITATION_FAILED`.
- Reviewing changes that add a "silent fallback" between two confirmation surfaces (relevant to the codebase's no-silent-fallback destructive-action rule).
