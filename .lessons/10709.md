## Context

`HelpPanel` / `HelpSessionController` auto-launch the Daintree Assistant (a billed provider-CLI session) when the panel becomes visible and a preferred or sole-installed agent is available (`HelpSessionController._maybeAutoLaunch`). Issue #10699 reported that this made opening the panel to "look around" silently start and bill an agent session with zero explicit user action — a real cost surprise, not a cosmetic complaint. PR #10709 added a persisted `autoLaunchEnabled` flag to `helpPanelStore` (bumping its `persist` version 4 → 5) and made `_maybeAutoLaunch` return early unless it's true.

## Problem

The fix needed a migration decision: `helpPanelStore` already had real users with a persisted `preferredAgentId` who were relying on (accidentally) getting auto-launch today. The reflexive migration instinct is "don't break existing users' current behavior" — which here means defaulting the new flag to `true` for anyone who already had a `preferredAgentId` set, and `false` only for fresh installs. That instinct is exactly backwards for this flag.

## Root cause

The bug being fixed WAS the existing behavior. `autoLaunchEnabled` isn't a new independent preference bolted onto old state — it's the retroactive gate on the behavior #10699 reported as broken. If the v4→v5 `migrate`/rehydrate path had special-cased "returning user with a `preferredAgentId`" to `autoLaunchEnabled: true`, every user who had already been silently billed once would keep being silently billed on every future panel open, while only brand-new installs got the fix. The migration would ship a PR titled "gate auto-launch behind consent" that gates it for nobody who currently needs gating.

The actual rehydrate logic in `helpPanelStore.ts` treats the flag as consent, not preference: `autoLaunchEnabled: persisted.autoLaunchEnabled === true` — strict equality against the literal `true`, so a v4 blob (field doesn't exist → `undefined`), a fresh install (no blob), and a malformed persisted value (e.g. the string `"true"`) all normalize to `false`. There is no carve-out branch keyed on `preferredAgentId` or any other pre-existing field. Re-enabling costs one click (the "Start assistant" CTA calls `setAutoLaunchEnabled(true)` before launching); a silent recurring charge does not — that asymmetry should drive the default, not migration-compatibility habit.

A second, related detail: `_maybeAutoLaunch` checks `if (!inputs.autoLaunchEnabled) return;` FIRST, before `if (typeof document !== "undefined" && document.hidden) return;`. The panel re-evaluates auto-launch eligibility on a `visibilityEpoch` bump (panel hidden → shown again). If the consent check were ordered after the visibility guard, a future refactor of the visibility-restore path could re-arm auto-launch on a background→foreground transition without re-checking consent — guard ordering here is load-bearing, not stylistic.

## Lesson

- **When migrating a persisted field that gates a harmful default, ask what the field actually represents before choosing a migration default** — if the "preserve existing behavior" migration would preserve the reported bug for exactly the users who hit it, that's proof the instinct is wrong for this field, not proof the migration is incomplete.
- **Consent/gate flags default to the safe state for ALL pre-existing state, with no field-keyed carve-out** — `autoLaunchEnabled: persisted.autoLaunchEnabled === true` treats `undefined` (missing field), a stale version's absence, and a malformed non-boolean the same way: off. Don't write a migration branch that infers consent from an unrelated field like `preferredAgentId` just because it correlates with "this user probably wants it."
- **Weigh the migration default by re-enable cost vs harm cost, not by minimizing user-visible change.** Re-enabling here is a single click on a CTA that's already the primary empty-state affordance; the harm avoided is a recurring silent charge. When those two costs are this lopsided, the lopsided side wins even though it changes behavior for existing users.
- **Order a consent/permission gate before any other early-return in the same function**, especially one tied to a re-evaluation trigger like `visibilityEpoch`. Put the gate first specifically so a later change to the OTHER guards (visibility, ready-state, terminal-id) can't accidentally create a path around consent — see `_maybeAutoLaunch`'s comment: "Placed ahead of the visibility check so a visibility-restore epoch bump can't bypass consent on a restore."
- **Test the negative migration path explicitly**, not just "fresh install defaults to X" — PR #10709's store tests cover a v4 blob with `preferredAgentId: "claude"` set (the exact "returning user who'd expect the old behavior" case) and assert `autoLaunchEnabled` still comes back `false`, plus a malformed-type case. That's the test that would have caught a wrongly-scoped carve-out.

## Applies when

- Adding a persisted flag to any of the ~13 `persist`-wrapped stores (`docs/architecture/state-management.md`) that gates a side-effect users didn't ask for on this screen — billing, network calls, external process launches, notifications.
- Writing a `migrate`/rehydrate function for a version bump and reaching for "preserve current behavior for existing users" as the default justification — check first whether current behavior is the bug.
- Reviewing any consent-gate `if (!consent) return` placement relative to other early-return guards in the same function, especially ones keyed on a re-evaluation epoch or visibility restore.
- Touching `HelpSessionController._maybeAutoLaunch`, `helpPanelStore.autoLaunchEnabled`, or the HelpPanel empty-state CTA/starter-prompt chips (note: Daintree Assistant itself is internally supported but not yet publicly released, per current release notes policy).
- Designing any "opt back in with one click" affordance meant to replace a removed silent default — confirm the affordance is reachable from the exact empty state a returning user will land on post-migration.
