## Context

The `app://` scheme serves the entire renderer bundle — handler `createAppProtocolHandler` in `electron/setup/protocols.ts`, URL→path resolution and headers in `electron/utils/appProtocol.ts`. Before #9783, the handler built a `file://` URL with `pathToFileURL`, called `net.fetch` on it, and buffered `response.arrayBuffer()` into a fresh `Response` — a pattern that reads as idiomatic Electron and mirrors many official examples. The sibling `daintree-file://` and `plugin://` handlers in the same file already read from disk directly.

## Problem

Every asset load — the ~21 modulepreloaded JS chunks plus everything else in the first-render closure, on every single launch — paid a Chromium network-service round trip plus a second full in-memory copy of the bytes. Nothing was visibly broken, which is why it survived so long: the implicit justification "route through net.fetch so Chromium's cache handles it" sounds right and is silently false, turning the overhead into a permanent startup tax rather than a one-time cold-start cost (issue #9768).

## Root cause

Chromium's HTTP disk cache (`HttpCache::Transaction`) handles http/https only — responses produced by a custom-scheme `protocol.handle` handler never enter it, so the handler re-runs for every chunk on every launch and `net.fetch(file://)` buys zero caching. #9783 replaced it with `fs.open(filePath, O_RDONLY)` + `fileHandle.readFile()`. The subtle part is what had to be KEPT: the `If-Modified-Since` → 304 short-circuit and the cacheable `buildHeaders` output (Cache-Control + Last-Modified validator), because the V8 bytecode cache (#8624) is a _separate_ mechanism that DOES work on custom schemes (`codeCache: true` + `standard: true` on the registered scheme) — but Chromium stores compiled bytecode as metadata on the resource's cache entry and only persists it when the response is cacheable AND revalidatable; without the 304 path, every reload's fresh 200 invalidates the bytecode entry and the renderer recompiles from source each launch. The body also stays buffered rather than streamed: Electron #42612 ("protocol.handle is very slow") was still open at Electron 41 and streamed custom-protocol responses were slower than buffered ones at our chunk sizes — re-verify against the current Electron before switching.

Three secondary mechanics were baked into the rewrite. (1) On macOS/Linux, `fs.open()` on a _directory_ SUCCEEDS with `O_RDONLY`; `EISDIR` only surfaces later at `readFile` — so the handler maps EISDIR→404 in both catch blocks, or a directory URL returns 500 on POSIX. (2) `fs.stat()` also succeeds on directories, so a `stats.isFile()` guard runs BEFORE the 304 short-circuit — without it, a directory URL carrying `If-Modified-Since` returns a spurious 304. (3) `O_NOFOLLOW` is deliberately omitted: `resolveAppUrlToDistPath` does lexical containment (`path.resolve` + `startsWith`, no `realpath` call), so there is no realpath/open TOCTOU window for the flag to close — unlike `daintree-file://` / `plugin://`, which resolve via realpath and therefore open with `O_RDONLY | O_NOFOLLOW`.

## Lesson

- **Never route a custom-protocol response through `net.fetch` expecting Chromium to cache it.** The HTTP disk cache is http/https-only; on a custom scheme, `net.fetch(pathToFileURL(...))` adds a network-service hop and a second in-memory copy per request with zero caching benefit. Read the bytes off disk (`fs.open` + `readFile`) like the sibling handlers.
- **Custom schemes bypass the HTTP cache but NOT the V8 bytecode cache — keep the header/304 machinery.** The tempting follow-on cleanup ("caching doesn't apply here, strip Cache-Control/Last-Modified/the 304 path") breaks bytecode persistence: the code cache rides the cache-entry metadata and a fresh 200 per load invalidates it (#8624). Verify via `<userData>/Partitions/daintree/Code Cache/js/` populating on launch 1 and being reused on launch 2.
- **EISDIR is platform-split: on macOS/Linux it appears at `readFile`, not `open`.** Any open-then-read file-serving path needs the directory→404 mapping in both catch blocks, plus a `stats.isFile()` guard before any conditional-request short-circuit so directories can't 304.
- **`O_NOFOLLOW` pairs with realpath-based containment, not lexical containment.** Add it only where a realpath→open TOCTOU window exists (the `daintree-file://` / `plugin://` pattern); on a lexically-contained handler it implies a defense that isn't set up. When copying one protocol handler to make another, copy the _matching_ containment+flags pair, not a mix.
- **Prefer buffered bodies in `protocol.handle` at bundle-chunk sizes** — streamed responses were the slower path per Electron #42612 (open as of Electron 41); confirm the issue's status before introducing streaming.

## Applies when

- Writing, modifying, or reviewing any `protocol.handle` handler in `electron/setup/protocols.ts` (`app://`, `daintree-file://`, `plugin://`) or registering a new custom scheme.
- Tempted to serve custom-scheme content via `net.fetch` "so Chromium handles caching", or reviewing a diff that removes Cache-Control/Last-Modified/304 handling from `app://` responses as dead code.
- Diagnosing slow cold launches / `RENDERER_READY` perf marks, or the V8 code cache directory not persisting between launches.
- Mapping fs error codes in any file-serving or file-reading path — deciding where EISDIR can surface, or whether an `fs.open` needs `O_NOFOLLOW`.
- Touching `buildHeaders`, `isNotModified`, or `resolveAppUrlToDistPath` in `electron/utils/appProtocol.ts`.
