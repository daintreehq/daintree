## Context

`AgentVersionService.runVersionProbe` spawns each agent CLI with `--version` to populate the update-check UI, detached on POSIX so a daemon grandchild that inherits the stdout fd can't stall the probe forever (some agent CLIs fork a background daemon on first run). A prior same-day rewrite replaced `execFile` with `spawn` and added an `EXIT_DRAIN_MS` (200ms) grace window: settle on `close` when possible, else on `exit` plus the drain, else a hard wall-clock deadline — fixing the promise-hang bug that motivated the rewrite.

## Problem

The rewrite fixed the hang but the process the probe exists to kill still leaked on every normal run. Issue #10697 traced it: the exit-grace path — foreground CLI exits, a grandchild still holds the inherited stdout pipe, which is the _common_ case, not an edge case — settled by calling `finish()` → `cleanup()`, and `cleanup()` just cleared the deadline timer. `killTree()` was wired only to the hard deadline and the `MAX_BUFFER` cap, both failure paths. So the one path every probe actually takes never reaped anything, and a detached process group leaked once per version check.

## Root cause

Teardown logic gets written against the failure paths you're staring at while debugging (hang, runaway buffer) and never gets asked "does this also need to run when things go _right_?" The grace-timer settle exists specifically to stop waiting on `close`, which means it is definitionally the path where a grandchild is still holding the pipe open — the exact condition `killTree()` exists for — yet the call was never wired to that callback, only to the hard deadline and `MAX_BUFFER` cap. Fixing that one line exposed five more latent gaps in the same teardown once the reap path actually started running: Windows' `child.kill("SIGKILL")` only terminates the direct child (needs `taskkill /T /F`), nothing was `.unref()`'d so an in-flight probe could pin `app.quit()`, the bare `catch {}` around `process.kill(-pid)` hid real `EPERM`/`EINVAL` failures alongside benign `ESRCH`, an unconditional `inFlightChecks.delete()` let a `refresh=true` probe's dedup entry get evicted by an unrelated earlier settle, and `cleanup()`'s `removeAllListeners()` on the destroyed streams stripped the error sinks that #5648 requires. None of these six is safe in isolation — they're one coupled teardown, not six independent bugs.

The PR also documents a declined fix worth the same weight as the applied ones: register the probe's detached PID with `HelpSessionJobService` for crash-safe reaping. That service's POSIX side (`posix-pty-reaper`) is an ADD-only protocol with no per-PID REMOVE — every registered PID gets SIGKILL'd on main-process death for the app's whole lifetime. A version probe's PID lives under 10 seconds; registering it opens a window where the OS recycles that PID onto an unrelated process, and a later crash makes the reaper tear down the wrong tree. The reaper stays scoped to long-lived PTY sessions (`HelpSessionService.isHelpTerminal`) precisely because it has no way to un-register something short-lived.

## Lesson

- **A reap/cleanup routine wired to a hard-deadline or buffer-cap backstop covers failure paths only — verify it also fires on the common/success settle path**, or the resource it exists to reclaim leaks on every normal run while looking "handled" in code review.
- **`child.kill()` on Windows kills one process, not a tree.** Any detached/grandchild-spawning child on win32 needs `taskkill /T /F /PID <pid>` via `spawnSync` (repo precedent: `ProcessTreeKiller.ts`, `PtyClient`) — `child.kill("SIGKILL")` silently orphans everything the child forked.
- **`.unref()` is an event-loop ref-count trick, not disposal** — unref the detached child and any timer that could outlive its operation (`deadlineTimer`, `exitGraceTimer`) so an in-flight probe never pins `app.quit()`; callbacks still fire normally.
- **Don't register short-lived PIDs with an ADD-only crash reaper that has no REMOVE** (`HelpSessionJobService` / `posix-pty-reaper`) — a PID that exits in seconds creates a recycled-PID hazard where a later crash reaps whatever process the OS handed that PID to next. Only register PIDs whose lifetime you actively track and can DISARM.
- **A dedup map keyed by ID needs a promise-identity check before deleting, whenever any caller can bypass the dedup and overwrite the entry** — `getVersion(id, refresh=true)` skipping the in-flight check meant an unconditional `.delete(agentId)` in the losing probe's `finally` could evict the _surviving_ probe's entry, breaking dedup for a third caller with no visible error.
- **When `cleanup()` calls `stream.destroy()`, keep a no-op `'error'` listener alive across that call** — destroy can surface a pending `EBADF`/`EIO` next tick, and an unhandled stream error is a fatal `uncaughtException` in Electron's main process (repo history: #5648); scope listener removal to `"data"`, never a bare `removeAllListeners()`.

## Applies when

- Touching `AgentVersionService.runVersionProbe`, or any other spawn-and-timeout probe pattern with a `close`/`exit`/deadline three-way settle race.
- Adding or reviewing teardown/kill logic for a `detached` child process — check every settle path (success, drain-grace, deadline, buffer-cap) calls the same reap function, not just the ones you were debugging.
- Writing Windows-side process-tree termination — `child.kill()` alone is a known trap; grep for `taskkill.*\/T.*\/F` (`ProcessTreeKiller.ts`) for the established pattern before reinventing it.
- Considering registering a new PID source with `HelpSessionJobService`'s crash-safe reaper — confirm the PID's lifetime is long-lived and actively disarmed, not a short probe.
- Reviewing an in-flight-request dedup `Map` where any caller path can bypass the dedup check (a `refresh`/`force` flag) — confirm deletions check promise identity, not just key presence.
