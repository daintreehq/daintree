## Context

When `ProjectViewManager` deactivates a project view (switching to another project), the view is detached from the window but kept alive in an LRU cache. React unmounts components, but V8's lazy GC doesn't immediately reclaim the freed memory from orphaned closures, detached DOM refs, and stale Zustand subscriptions.

## Problem

10-30MB of memory per deactivated view stayed on the heap indefinitely after `deactivateEntry` (extracted from `ProjectViewManager` into `electron/window/ProjectViewLifecycleController.ts`, #11004) detached the view and the React tree unmounted.

## Root cause

V8's incremental/lazy GC is tuned for throughput, not for tight memory budgets — it defers collection of now-unreachable objects (orphaned closures, detached DOM refs, stale Zustand subscriptions) from an unmounted React tree until heap pressure forces a cycle. A deactivated-but-cached view sits idle and off-screen, so nothing in the renderer triggers that pressure, and the freed memory lingers on the heap.

## Lesson

After a predictable "large deallocation event" — React tree unmount, route change, tab switch — trigger a GC cycle explicitly via `window.gc()` (requires `--expose-gc`, set in Daintree via the `js-flags` switch in `electron/main.ts:170-171`: `--max-old-space-size=768 --max-semi-space-size=16 --expose-gc`; the semi-space value has since been tuned down from an earlier 64MB — smaller nursery, more frequent but sub-millisecond scavenges — the `--expose-gc` requirement this lesson depends on is unchanged).

In `deactivateEntry(host, current)` (`electron/window/ProjectViewLifecycleController.ts:40`), after detaching the view, schedule the GC inside a `requestIdleCallback` via `webContents.executeJavaScript("requestIdleCallback(() => { if (window.gc) window.gc(); }, { timeout: 1000 })")` (line 146). The idle callback defers the GC until the renderer is otherwise quiet, making any pause imperceptible; the 1s `timeout` guarantees it still runs even under background CPU throttling, while being short enough to reclaim memory before the user switches back. (The original PR used a 500ms `setTimeout` defer; the current implementation uses `requestIdleCallback`.)

Schedule the GC BEFORE freezing the renderer via `Page.setWebLifecycleState`/`freezeWebContents` — freezing suspends the renderer event loop, so the idle callback would never fire if you froze first.

Guard the call: re-fetch the live entry (`host.views.get(capturedProjectId)`) and check that it still maps to the same `view`, is still in the `cached` state, and its `webContents` are not destroyed before calling `executeJavaScript`. Use `webContents.executeJavaScript()` — not `webContents.send()` — because `gc()` is a synchronous V8 call that doesn't require a renderer IPC handler.

## Applies when

- `WebContentsView` LRU caches in Electron
- Tab-switching architectures where large React trees unmount
- Any scenario where predictable large allocations are freed at a known point
