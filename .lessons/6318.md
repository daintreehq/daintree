## Context

Daintree exposes its Actions system over an MCP server so LLM clients can introspect and invoke app operations. The action registry holds ~308+ built-in action IDs (`shared/types/actions.ts`, `BuiltInActionId`). The MCP `ListToolsRequestSchema` handler turns the manifest into the `tools` array that clients see and that `tool_choice: "auto"` selects from.

## Problem

The handler originally advertised every non-`restricted` action (`.filter((entry) => entry.danger !== "restricted")`) — ~380 tools. Exposing the complete registry is a liability, not a feature: past ~50 tools `tool_choice: "auto"` selection accuracy degrades, and the tool definitions alone consume 60-90k tokens of input context on every request before the model does any work. A "complete" MCP surface actively makes the agent worse and more expensive.

## Root cause

The instinct is that more exposed capability is strictly better — the registry is already complete, so advertise all of it. But for an LLM consumer the manifest is a prompt, not an API surface: every tool definition is tokens the model must read and a candidate it must discriminate against. UI-plumbing actions (`panel.gridLayout.setStrategy`, etc.) are noise to an agent and crowd out the ~55 actions it actually uses (introspection, git, terminal, worktree, files, recipes). The fix decouples _visibility_ from _invokability_: a curated allowlist gates what's advertised, while dispatch stays reachable by ID for callers that already know what they want.

## Lesson

- Treat the MCP `tools` array as a curated, default-deny allowlist — never project the whole action registry into it. The current implementation lives in `electron/services/mcp-server/shared.ts` (`MCP_TOOL_ALLOWLIST_ENTRIES`, typed `satisfies readonly BuiltInActionId[]` so renamed/removed IDs fail the build) and `TIER_ALLOWLISTS`, enforced by `shouldExposeTool()` in `tierAuth.ts`.
- Separate visibility from invokability. Adding an action to the registry must NOT auto-expose it over MCP; advertising is opt-in via the allowlist. (Dispatch reachability is now also gated per-tier by `isTierPermitted()` after #8442's layered auth, but the visibility allowlist is the primary token/accuracy control.)
- There is no opt-out. `mcpServer.fullToolSurface` used to promise one; it was defanged in #10701 and deleted in #11537 (it had no UI, no IPC setter, and an empty add-on list, so it never exposed a single extra tool). `MCP_TOOL_ALLOWLIST_ENTRIES` is the only lever — widening the external surface means editing that list. `restricted` danger and `mcpVisibility: "hidden" | "discoverable"` are always excluded on top of it.
- When adding an agent-facing action, ask "does an LLM client need to _select_ this?" If it's UI plumbing, leave it off the allowlist — keeping the surface near ~55 tools is the design budget, not an accident.

## Applies when

- Adding or modifying any action exposed over MCP, or touching `electron/services/mcp-server/` (`shared.ts`, `tierAuth.ts`, `sessionServer.ts`, `McpServerService.ts`).
- Wiring a new `BuiltInActionId` and wondering why it doesn't appear to an MCP/agent client — check `MCP_TOOL_ALLOWLIST_ENTRIES` / `TIER_ALLOWLISTS`, not just the registry.
- Reviewing changes that filter the MCP manifest or the `ListToolsRequestSchema` handler.
- Any work on agent tool-selection accuracy, MCP token/context cost, or `tool_choice: "auto"` reliability.
- Debugging "the agent picks the wrong tool" or "MCP requests are huge" — suspect an over-broad tool surface.
