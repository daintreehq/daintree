## Context

`ContentGrid` renders only the maximized panel/group while `maximizedId`/`maximizeTarget` (in `terminalFocusSlice.ts`) are set; everything else in the grid is hidden behind it. Before #11061, `addPanel` (`panelStore.ts`) never touched maximize state — a comment in `terminalFocusSlice.ts` explicitly documented a panel created while fullscreen as "focused in the background without ever being displayed," treating the hidden-focus outcome as intended. #11060 argued that's wrong for the user: opening a new agent terminal should return you to the grid so you can see it, not silently focus it out of view.

## Problem

Opening a new terminal while a panel or tab group was maximized created and focused the terminal, but it stayed hidden behind the maximized cell — the user asked for a terminal and visibly got nothing. The misleading part: this wasn't an oversight so much as a codified assumption, since the slice's own doc comment described the hidden-focus behavior as correct, so a shallow read of the code confirmed the bug instead of flagging it. The same defect reproduced through recipe/fleet spawns, trash restores, background restores, and dock-to-grid moves — anywhere a panel lands in the grid and takes focus, not only `terminal.new`.

## Root cause

Two independent gaps had to both be closed. First, no code path cleared maximize state on panel landing at all — the invariant "a panel that takes grid focus must not be hidden by fullscreen" had never been established anywhere. Second, the obvious existing tool for exiting fullscreen, `toggleMaximize`, is conditional, not a reliable forced-exit: for a group target its `shouldUnmaximize` only flips true if `getPanelGroup(id)` resolves and its `.id` still matches `state.maximizeTarget.id`. If the maximized group has since dissolved (e.g. down to one member), that lookup fails, `shouldUnmaximize` stays false, and the code falls through to the _maximize_ branch — re-maximizing with a new target instead of exiting. This was a real, live misfire in `focusOrMaximizeByIndex`'s force-exit for the Cmd+1..9 index hotkeys, which called `toggleMaximize(maximizedId, ...)` assuming it always unmaximizes.

The fix, `exitMaximize()`, is deliberately unconditional: it always clears `maximizedId`/`maximizeTarget` regardless of whether the old target still resolves, but preserves `preMaximizeLayout` so the grid's column count restores exactly as a manual unmaximize would — the documented sibling of `clearMaximize` (which also drops `preMaximizeLayout` and is reserved for teardown: trash, reset, project switch, per the `#9935` staleness guard already in the same file), not a replacement for it. Establishing the invariant then meant enumerating every path that lands a panel in the grid and focuses it, because `addPanel` can only see its own callers: trash restores (`restoreTerminal`, `restoreTrashedGroup`), background restores (`restoreBackgroundTerminal`/`restoreBackgroundGroup` — the registry doesn't focus, so callers like `BackgroundContainer` activate right after), dock-to-grid moves (`moveTerminalToGrid`, `moveTabGroupToLocation`), and batched recipe/fleet spawns whose per-panel focus is suppressed during the batch and reapplied once at the end (`recipeStore.ts`, `panelSpawning.ts`) — those last two had to call `exitMaximize()` themselves since `addPanel`'s wrapper never observed their post-batch focus set.

## Lesson

- **A focus-visibility invariant belongs at every `focusedId`-setting path, not just the common entry point.** `addPanel` covers direct creates; it is structurally blind to restores, dock moves, and batch spawns that set focus afterward — grep every call site that sets `focusedId`/`activateTerminal` when adding this kind of invariant, not just the constructor.
- **Never reuse a conditional toggle as a forced one-directional exit.** `toggleMaximize`'s unmaximize branch depends on resolving the current target (`getPanelGroup(id)?.id === maximizeTarget.id`); once that target can go stale (a group dissolving), the "exit" call can flip into the opposite action. Build a dedicated unconditional method (`exitMaximize`) for call sites that need "leave, period," and audit existing callers for the same assumption — `focusOrMaximizeByIndex`'s index-hotkey force-exit had exactly this latent bug.
- **Distinguish "exit and keep resume state" from "clear including resume state."** `exitMaximize` preserves `preMaximizeLayout` (grid column count restores correctly); `clearMaximize` also drops it and is only for teardown. Using the teardown variant on a landing path would corrupt the next manual maximize's remembered layout.
- **A batch that suppresses per-item focus to avoid intermediate renders must carry every invariant tied to that focus, not just focus itself.** `recipeStore`'s spawn batch suppresses `addPanel`'s focus set for performance, then reapplies focus once at the end — and had to reapply `exitMaximize()` there too, since the suppressed calls never ran it either.
- **Guard invariant application with a liveness check when the state read is async-adjacent.** `recipeStore` re-reads `panelsById` fresh (not the pre-spawn snapshot) and requires the panel to still exist as a non-dock grid panel before calling `exitMaximize()`, because the panel can be removed during `addPanel`'s async tail.

## Applies when

- Adding a new path that lands a panel in the grid and sets `focusedId` (restore, dock-to-grid move, spawn batch, recipe/fleet launch).
- Touching `maximizedId`/`maximizeTarget`/`toggleMaximize`/`clearMaximize`/`exitMaximize` in `src/store/slices/terminalFocusSlice.ts`, or `addPanel` in `src/store/panelStore.ts`.
- Diagnosing "I opened/restored/moved a panel and nothing appeared" while any panel or group is maximized.
- Reviewing a batch operation that suppresses per-item side effects (focus, notifications) for performance — check whether a downstream invariant needs the same suppress-then-reapply treatment.
- Reusing a toggle-style state method as a forced directional call — verify its "already in state X" detection can't silently fail and flip into the opposite branch.
