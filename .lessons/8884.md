## Context

Bulk recipe launches and fleet broadcasts can add many terminal panels at once. `addPanel` (`src/store/slices/panelRegistry/addPanel.ts`) commits each panel to the Zustand store optimistically with `spawnStatus: "spawning"` (#5789), then fires backend PTY spawn + visible `xterm.open()` so the panel chrome paints before the ~200-500ms IPC round-trip resolves. `TerminalInstanceService` (renderer) owns the xterm/WebGL instances.

## Problem

Bulk-open caused blank/stalled panes during the burst. The earlier framing treated this as a WebGL repaint race to fix _after_ the layout settled (force a repaint once everything mounted). That mistargeted the symptom: committing every panel and mounting every `XtermAdapter`/WebGL context in the _same_ grid layout pass overwhelms Chromium's render lifecycle and xterm's open/attach/fit, so no amount of post-burst repainting fixes the frame in which everything tried to realize at once.

## Root cause

The real bottleneck is the simultaneous mount/attach burst, not a late repaint. Optimistic store commit (synchronous) is correct and should stay parallel — six clicks should surface six placeholders instantly. But the _heavy_ work (PTY spawn + `xterm.open()` + WebGL context creation + fit) must be serialized. The fix moves backpressure to startup _admission_:

- A module-level `TerminalStartupQueue` (`addPanel.ts:60`) drains one task at a time; each enqueued task does env fetch → `terminalClient.spawn` → promote `spawnStatus` to `"ready"`.
- For visible grid terminals in the active worktree (`shouldWaitForVisibleAttach = location === "grid" && isInActiveWorktree`), the queue task additionally `await`s `terminalInstanceService.waitForAttachSettled(id, { timeoutMs })` so the _next_ terminal does not start until the current one's `open()`/attach/fit has fully settled.
- `waitForAttachSettled` (`TerminalInstanceService.ts:1150`) resolves only when `isAttachSettled` is true (`isOpened && isAttaching !== true && hostElement.isConnected && terminal.element !== undefined`); `notifyAttachSettledWaiters` is fired at every terminal point of the post-attach `requestAnimationFrame` fit pass.
- Panels render `TerminalStartupPlaceholder` (lightweight spinner) while `spawnStatus === "spawning"` (`TerminalPane.tsx:1276`) instead of mounting `XtermAdapter`, so chrome is optimistic but the expensive xterm DOM is gated.
- Supporting correctness fix: `prewarmTerminal` no longer attaches to an offscreen DOM node during burst (`offscreen: false`), and cold-mount IntersectionObserver flaps are ignored while `isAttaching` (`TerminalInstanceService.ts:~608`) — a transient "not intersecting" report during grid insertion would otherwise persist `isVisible=false` and strand renderer recovery behind visibility guards.

## Lesson

When many heavyweight UI instances are created in one burst, separate the _cheap optimistic commit_ (parallel, synchronous store insert + placeholder chrome) from the _expensive realization_ (serialize through a queue). Put the backpressure at admission — gate each instance's mount/attach on the previous one _settling_ — rather than trying to repair the frame after everything mounts. For terminals specifically: keep `addPanel` store commits parallel, but run PTY spawn + `xterm.open()` through `terminalStartupQueue`, and gate the next visible grid terminal on `waitForAttachSettled` (open + attach + fit), not just on `spawn()` resolving. Always re-check `spawnStatus === "spawning"` inside the queued task before each side effect — the panel may have been removed mid-queue. Never trust IntersectionObserver visibility while a terminal `isAttaching`; cold-mount flaps are not authoritative and persisting them strands recovery.

## Applies when

- Adding panels in bulk: recipe launches, fleet broadcast, multi-agent spin-up, session restore that re-creates many grid terminals at once.
- Touching `addPanel` / `panelRegistry` optimistic spawn (`spawnStatus: "spawning" | "ready" | "failed"`), or the `TerminalStartupQueue` drain logic.
- Working on `TerminalInstanceService` attach/fit lifecycle, `waitForAttachSettled` / `isAttachSettled` / `attachSettledWaiters`, `prewarmTerminal`, or the post-attach `requestAnimationFrame` fit pass.
- Diagnosing blank/stalled/flashing terminal panes, dropped initial output, or jank specifically during _simultaneous_ terminal creation (not steady-state).
- Tempted to "fix it with a repaint/reflow after the burst" — reconsider: serialize the mount instead.
- Modifying xterm/WebGL mount cost under load, or any feature that mounts many WebGL-backed components in one layout pass.
- Handling IntersectionObserver-driven visibility for terminals during mount; deciding whether a `!isVisible` report should be persisted.
