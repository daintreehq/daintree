## Context

`XtermAdapter` installs a `customKeyEventHandler` on the xterm instance to give the app first crack at keydown events before xterm transmits them to the PTY. An earlier change (#8935) added a `resolveTerminalTabEscape` helper so plain Tab / Shift+Tab inside a focused terminal would dispatch `nav.focusRegion.next`/`prev` — an "additive" keyboard escape so keyboard-only users weren't trapped in the terminal.

## Problem

Tab and Shift+Tab never reached the PTY. Shell tab-completion, agent autocomplete (Claude/Codex/Gemini menus), and any TUI that uses Tab were silently broken inside terminals. The breakage was invisible in normal review because nothing errored — Tab just got swallowed into focus-region cycling.

## Root cause

Tab is a key the PTY owns (xterm transmits it as `\t`/HT, Shift+Tab as CSI Z). Intercepting it for focus navigation looked free because F6/Shift+F6 _already_ provided the exact same focus-region escape, so the Tab path was pure redundancy that added a regression with no new capability. A keybinding that steals a PTY-owned key produces no visible signal until someone actually exercises the shell/TUI feature that depends on that key — so it ships and lurks. The fix was a pure deletion: remove `resolveTerminalTabEscape` + its intercept block, and update `aria-keyshortcuts` from `"F6 Tab Shift+Tab"` to `"F6 Shift+F6"`.

## Lesson

- Inside a focused terminal pane, do NOT intercept keys the PTY consumes (Tab, Shift+Tab, function keys, etc.) for app-level navigation or shortcuts. The terminal is a sink for those keys.
- Before adding any terminal-pane keybinding, ask: does the PTY/shell/TUI/agent need this key? If yes, leave it alone.
- A "free" intercept that duplicates an existing escape path (here F6) is not free — it is a silent regression with zero upside. Prefer the single non-PTY-colliding binding (F6) and delete the colliding one.
- Keyboard-trap accessibility concerns are real, but solve them with keys the PTY does not own (F6), and keep `aria-keyshortcuts` in sync with what actually escapes.
- Note: simply removing the intercept and returning `true` is necessary but in xterm v6 not always sufficient — see #9124, where xterm v6 screen-reader mode leaves handled keys uncanceled and Chromium native focus traversal / the Electron menu accelerator still steal Tab and bare F11, requiring an explicit `preventDefault()` + `stopPropagation()` + `return true` guard for those keys.

## Applies when

- Adding or reviewing any keybinding, action, or `customKeyEventHandler` branch in `XtermAdapter.tsx` / `terminalFocus.ts` or anything that runs while a terminal pane has focus.
- A bug report says shell autocomplete, agent menu navigation, or a TUI key "does nothing" / "moves focus instead" inside a Daintree terminal.
- Considering routing Tab, Shift+Tab, arrow keys, function keys, or other terminal-input keys to focus-region navigation or app shortcuts.
- Wiring `aria-keyshortcuts` on the terminal `role="application"` container — it must list only keys that genuinely escape, not PTY-owned keys.
- Any change that adds a "redundant but harmless" key escape alongside an existing one (F6) — verify it doesn't collide with PTY input.
