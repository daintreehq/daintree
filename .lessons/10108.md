## Context

Each project's durable UI state (panel layout, tab groups, terminal sizes, focus mode, draft inputs) lives in one JSON file owned by `ProjectStateManager` (atomic writes via `resilientAtomicWriteFile`, 60s TTL read cache). Five `set*` handlers in `electron/ipc/handlers/terminalLayout.ts` each wrote it by read-merge-write: `getProjectState` → spread existing → overwrite own field → `saveProjectState`. The renderer's `PanelPersistence` (`src/store/persistence/panelPersistence.ts`) drives those handlers through equal 500ms trailing debounces for terminals and tab groups.

## Problem

After a restart, users saw the wrong panel layout or missing tab groups; tab-group sanitization then pruned groups referencing the reverted-away panels, compounding the loss. Intermittent and misleading: every individual write was atomic and correct-looking on disk, and re-testing the same drag/close usually worked, so the write path looked innocent. Diagnosed in #9913, fixed here.

## Root cause

`ipcMain.handle` registers plain async handlers with no queueing. The main process being single-threaded does NOT serialize them — each handler yields at every `await`, so two invokes in the same tick interleave their read-modify-write cycles. And same-tick pairs are guaranteed in normal use: `PanelPersistence` schedules `setTerminals` and `setTabGroups` with the same 500ms trailing debounce, so any mutation touching both (drag a panel into a group, close a grouped panel, every `flushPanelPersistence()`) dispatches both invokes together. Both read `{terminals: T0, tabGroups: G0}`; `setTerminals` writes `{T1, G0}`; `setTabGroups` writes `{T0, G1}` — whichever lands second silently reverts the other's field. Per-write atomicity is irrelevant: the violated invariant is that each cycle sees its predecessor's committed state, and the manager's TTL cache only advances post-write, so the concurrent reader always got the stale snapshot.

The renderer then made the transient race persistent: after the IPC resolved, `persistedTerminalsByProject` recorded `T1` as persisted, so identical re-saves early-return via `snapshotsEqual` — the reverted on-disk state survived until the layout next genuinely changed, i.e. across restarts. The fix is `ProjectStateManager.enqueueProjectStateUpdate(projectId, updater)`: a per-project promise-chain tail queue (same keyed-tail pattern as `RepoFetchCoordinator`) where each updater receives its predecessor's committed state. All five `terminalLayout` handlers, the four `app:hydrate` migration writes in `electron/ipc/handlers/app/state.ts`, and the shutdown `agentSessionId` patch (`electron/lifecycle/shutdown.ts`) were migrated; `projectCrud/switch.ts` and the app-state MRU write adopted it later, so it is the standing convention for this file.

## Lesson

- **`ipcMain.handle` handlers are not serialized — treat any handler-side read-then-write on shared state as a lost-update race.** Single-threaded main ≠ sequential handlers; they interleave at every `await`. If two channels can fire in one tick (paired debounces make this the common case, not the rare one), the last write reverts the other's field with no error.
- **Per-write atomicity is not read-modify-write serialization.** `resilientAtomicWriteFile` made every write atomic and the race fired anyway. The invariant to enforce is predecessor visibility: each updater must see the previous update's committed state, which the queue provides (and post-save it is served from the committed cache — one disk read per chain, verified by test).
- **Route every whole-object project-state write through `ProjectStore.enqueueProjectStateUpdate(projectId, updater)` — never a bare `getProjectState` + `saveProjectState` pair.** The `ProjectStore` delegate also calls `invalidatePrefetchCache(projectId)` before committing (same contract as `saveProjectState`), which a hand-rolled pair would forget. Returning `null` from the updater skips the save (used by shutdown when a project has no terminals).
- **The keyed-tail queue has three load-bearing subtleties — copy them, don't re-derive:** (1) each link starts `current.catch(() => {})` so one failed write can't poison later updates while still rejecting its own caller; (2) cleanup runs via `next.then(cleanup, cleanup)`, NOT `.finally()`, because `.finally()` on a rejected promise mints a new unhandled rejection; (3) cleanup checks `this.writeQueues.get(projectId) === next` before deleting so a newer tail isn't dropped.
- **A downstream idempotence cache turns a transient race into persistent corruption.** `persistedTerminalsByProject` skips identical re-saves, so the reverted file stays wrong across restarts — when diagnosing "state file wrong on disk", the clobbering write may be long past, with every save since silently no-oping. Check the dedupe caches before assuming the writer is currently broken.
- **Field-scoped keys sidestep this class entirely.** The global app-state handler writes `store.set("appState." + field)` per field and never had the bug — the whole-object project-state merge was the anomaly. New persistence surfaces should prefer field-scoped writes or a keyed queue over whole-object merges.

## Applies when

- Writing or reviewing any `ipcMain.handle` / `defineIpcNamespace` op that reads shared main-process state (file, electron-store, cache) and writes back a merged object.
- Touching the `terminalLayout` `set*` handlers, `app/state.ts` hydrate migrations, `shutdown.ts`, `projectCrud/switch.ts`, or anything else that persists `ProjectState`.
- Diagnosing missing tab groups, reverted panel layout, or stale draft inputs that appear after restart and survive further sessions.
- Assuming Electron's single-threaded main process serializes IPC handlers, or that atomic file writes make concurrent read-merge-write safe.
- Building a per-key serialization queue anywhere — reuse the `enqueueProjectStateUpdate` / `RepoFetchCoordinator` keyed-tail pattern including its `.catch` anti-poisoning and `.then(cleanup, cleanup)` details.
