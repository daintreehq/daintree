## Context

The PTY pool (`electron/services/PtyPool.ts`, macOS/Linux only — disabled on Windows for the ConPTY guard) pre-spawns shells so the first terminal skips fork + rc-file evaluation. Slots are keyed by the exact tuple `(cwd, envHash)`: `acquirePtyProcess` (`electron/services/pty/terminalSpawn.ts`) computes `envHash = computePoolEnvHash(options.env)` and calls `pool.acquireByKey(cwd, envHash)`. On `set-active-project` the pty-host handler (`electron/pty-host/handlers/connection.ts`) drained and refilled the pool at the project root path.

## Problem

The first terminal after every session restore always cold-spawned — the pool never served its primary use case (issue #9774). Nothing looked broken: spawns succeeded, no errors were logged, and the hit/miss log line was gated behind `DAINTREE_VERBOSE`. A miss IS the fallback path, so "pool warmed the wrong key" is behaviorally identical to "pool working" minus the latency win it exists to provide.

## Root cause

Key-shape mismatch between warm site and lookup site, on BOTH axes of the tuple, discovered in two passes. Axis 1 (cwd, #9790): `set-active-project` warmed only `projectPath`, but restored panels spawn at per-worktree cwds — `acquireByKey("/repo/.worktrees/feature-a", …)` can never hit a slot warmed at `"/repo"`. Axis 2 (envHash, #9849 / issue #9810): even after #9790, warms used only `POOL_ENV_EMPTY_HASH`, but any user with global or project env vars produces a non-empty `envHash` at spawn (the store merges `globalEnvVars` + `projectEnvVars` into `options.env`) — for those users the hit rate was STILL 0% after the first fix.

The fix threads the real lookup keys from the consumer side through the IPC: `extractRestorePanelCwds` (`electron/window/restorePanelCwds.ts`) pulls plain-shell panel cwds from saved state (agent/command panels filtered — they set `options.shell`/`options.args` and never pool, #7961), sorted active-worktree-first then `lastActiveAt` desc, exact strings with no normalization (#5102 — the lookup is a string-equality map hit). #9849 adds `mergeProjectEnv` and sends the RAW merged env over `set-active-project`; the pty-host computes the hash itself via the same `computePoolEnvHash` module the `acquireByKey` call site uses, so warm key and lookup key come from one function in one process and cannot drift. Two load-bearing details: warms fire only after `drainAndRefill` resolves, because the drain epoch is bumped synchronously at drain start — a warm racing the drain carries the stale epoch and gets rejected; and the warm set is capped at `floor(maxEntries / poolSize) - 1` distinct cwds, because an uncapped warm list would LRU-evict the highest-priority (active-worktree) entries warmed first — the warming would evict itself.

## Lesson

- **Warm a keyed cache with the exact tuples the acquire path will ask for, enumerated from the consumer side** — not the "obvious" key the producer has at hand. The pool warmed the project root because that's what `set-active-project` carried; the fix extends the IPC payload (`panelCwds`, then `projectEnv`) so the warm site knows the real future lookups. A key-shape mismatch means a silent 0% hit rate: no error, just the slow path every time.
- **When a cache key contains a derived component (hash), compute it at the lookup site's process from raw inputs** — never pre-compute it at the sender and ship the hash. #9849 ships raw `projectEnv` over IPC and lets the pty-host call `computePoolEnvHash`, guaranteeing the warm key matches `acquireByKey` byte-for-byte; the test locks the hash VALUE against `computePoolEnvHash(projectEnv)`, not merely "two warm calls agree", so hash-function drift (e.g. dropping `filterSensitiveOnly`) fails a test instead of silently zeroing the hit rate.
- **Auditing a compound-key cache means auditing every axis.** #9790 fixed cwd and looked complete; anyone with env vars configured still missed 100% until #9810 was spotted and #9849 landed. After fixing a key mismatch, re-derive the full key the lookup site builds and diff it component-by-component against what the warm site produces.
- **Sequence warms after epoch-bumping operations resolve.** Entries warmed before `drainAndRefill` resolves carry the old epoch and get rejected as stale. Chain the warm in `.then()` of the drain, and test the ordering (the connection.test.ts case holds the drain promise open and asserts zero warms).
- **Cap predictive warm sets below the eviction threshold.** With LRU eviction at `maxEntries`, warming N low-priority keys evicts the N high-priority ones warmed first. The cap `floor(maxEntries/poolSize) - 1` reserves the root's slots and bounds panel keys so priority ordering survives.
- **A cache whose miss is a silent fallback needs hit/miss telemetry as part of the fix, not later.** `POOL_HIT`/`POOL_MISS` perf marks (`shared/perf/marks.ts`, emitted from `acquireByKey` under host perf capture) exist because this miss was invisible for the pool's whole life; `perf:cold-start` can now measure restore hit rate.

## Applies when

- Touching `PtyPool` warm/acquire paths (`warmForKey`, `acquireByKey`, `drainAndRefill`, `refillPool`), `computePoolEnvHash`, or the `set-active-project` handler in `electron/pty-host/handlers/connection.ts`.
- Diagnosing "first terminal after session restore / project switch is slow" or verifying pool effectiveness — check `POOL_HIT`/`POOL_MISS` marks in `perf:cold-start` before assuming the pool helps.
- Building or reviewing any keyed warm/predictive cache where warm site and lookup site are different modules or processes — verify key shapes match byte-for-byte and derived key parts are computed by the shared function at the lookup side.
- Assuming a cache "works" because nothing errors — when a miss falls back to the slow path, only hit-rate telemetry distinguishes working from never-hitting.
- Extending the `set-active-project` payload or warm hints: `panelCwds`/`projectEnv` are transient first-send hints, deliberately NOT stored in `windowProjectContexts` for host-restart resync (a restarted host has a fresh pool and no pending restore spawns); keep new hints transient unless a resync genuinely needs them.
