## Context

The renderer panel store (`usePanelStore`) tracks per-terminal activity headlines, flow-status, and agent-state. With 3-10 agents running, terminal output listeners in `src/store/listeners/panel/` (activity, lifecycle `onStatus`) each fired a separate `setState` per event per frame. Zustand 5 runs its subscriber notify loop synchronously on every `setState`, so N events per frame meant N store writes and N selector re-runs across every subscribed component.

## Problem

Under multi-agent load the renderer did one store write — and one full subscriber/selector pass — per activity or flow-status event per frame. The per-frame write count scaled linearly with agent count, producing redundant selector executions and re-render churn that had nothing to do with the number of distinct frames actually painted.

## Root cause

Zustand 5's `setState` is eager and synchronous: it folds the patch and immediately fires every subscriber before returning. There is no built-in per-frame batching. The only fix is to coalesce on the producer side. `src/store/panelStatusBuffer.ts` maintains module-level `Map`s keyed by terminalId for activity and flow-status patches and schedules a single `requestAnimationFrame` flush; the flush builds one merged `panelsById` object and issues exactly one `setState`, collapsing N notifications/frame to 1 regardless of agent count.

The non-obvious half is what must NOT be routed through the buffer. Agent-state writes in `identity.ts` stay direct because:

- After `updateAgentState`, the same handler synchronously calls `usePanelStore.getState().processQueue(terminalId)`, which reads `terminal.agentState` live and gates dispatch on `isAgentReady(agentState)` (`terminalCommandQueueSlice.ts`). Deferring the write a frame would make `processQueue` observe the stale prior state and refuse to flush queued commands.
- Agent-state transitions fire non-coalescable side-effects: `changedFileCount` baseline snapshots on first `working`, and completion-edge logic on `completed`. Last-write-wins frame coalescing would silently drop intermediate transitions these depend on.

Even within the batched buffer, ordering correctness required a guard at _enqueue_ time, not just at fold time: IPC can deliver flow-status events out of chronological order within one frame (backpressure, multi-source, reconnect), so `enqueueFlowStatusUpdate` rejects a later-arriving older timestamp (`timestamp < existing.timestamp`). The fold's persisted-store timestamp guard alone can't catch this — nothing is committed yet for that terminal mid-frame.

## Lesson

- To kill per-event Zustand re-render churn, coalesce on the write side with a shared module-level rAF buffer that issues one merged `setState` per frame. Reading-side fixes (`useShallow`, memoized selectors — #3464/#3683) don't help when the write count itself is the problem.
- Only batch writes that are pure last-write-wins state with no ordering dependency. A write is NOT batchable if a same-tick reader reads it back (e.g. `processQueue` reading `agentState`) or if intermediate transitions trigger side-effects (snapshots, notifications, completion edges). Coalescing those corrupts ordering and drops transitions.
- When buffering events that can arrive out of order (IPC under backpressure/reconnect), guard monotonicity at enqueue time, not only at flush time — the flush can't see other in-buffer patches for the same key.
- Make the buffer a module-level singleton owned/torn-down by the parent listener setup (`panelStoreListeners.ts` registers `cancelPanelStatusBuffer`), not per sub-listener, since it must outlive any single sub-store. Snapshot-and-clear the buffer Maps _before_ running the `setState` updater so re-entrant enqueues during subscriber callbacks land in the next frame instead of being dropped.

## Applies when

- Adding or modifying high-frequency writes to `usePanelStore` from terminal output listeners (activity, flow-status, backpressure, resize) under multi-agent load.
- Investigating renderer re-render storms or selector hot-paths that scale with the number of running agents/terminals rather than with painted frames.
- Tempted to route agent-state, command-queue, or any same-tick-read-back store mutation through `panelStatusBuffer` or a similar rAF batch — don't; verify whether a synchronous reader or side-effect depends on the write landing immediately.
- Designing any rAF/timer-coalesced write buffer for Zustand 5 where source events (IPC, MessagePort) may arrive out of timestamp order within a frame.
- Touching `processQueue` / `terminalCommandQueueSlice` ordering, or `changedFileCount` baseline/completion-edge logic in `identity.ts`.
