## Context

The plugin build pipeline compiles each plugin's `main/` with esbuild, copies static assets into `dist-electron/plugins/{builtin,sample}/`, and at runtime `PluginService` reads `plugin.json`, registers contributions, and lazily `import()`s command handlers on first dispatch. Issue #10620 (1.0 hardening #10511) catalogued three ways a _green_ `build:main` still ships an unrunnable plugin; the arc fixed them across #10590 (asset copy + asar), #10594 (typecheck), and lead PR #10624 (handler extensions + manifest integrity).

## Problem

Every gap failed only at runtime, after a clean build. A manifest naming a `./bin/*.mjs` agent command or `./mcp/*.mjs` server hit `ENOENT` at spawn (the file was dropped from the bundle). Type errors in plugin main code shipped with no diagnostic. A `.ts`/`.tsx` handler was discovered at load, then threw at first dispatch. Duplicate contribution ids and dangling view→panel refs passed validation, then silently first-won or no-op'd. Each "build succeeded" was a separate lie about a different runtime property.

## Root cause

**Copy + asar (#10590).** esbuild only touches `main/`; the copy step in `scripts/build-main.mjs` previously shipped only `plugin.json` plus a hardcoded `view/` dir, silently dropping `bin/` and `mcp/`, so a `./bin/*.mjs` / `./mcp/*.mjs` path spawned via node-pty or the MCP supervisor ENOENTs. Packaged builds add a subtler layer: node-pty uses **native OS spawn, which bypasses Electron's asar filesystem patch**, so a `./bin/*.mjs` packed _inside_ `app.asar` ENOENTs even when it IS in the bundle — the fix required `dist-electron/plugins/builtin/**/*` in `asarUnpack`. New `copyPluginExtraAssets` mirrors every subdir except `PLUGIN_EXTRA_ASSET_SKIP_DIRS` (`main`/`renderer`/`shared`/`__tests__`), and `findMissingPluginAssets` fails the build on any `./`-relative `command`/`args` path missing from output (with an `isInsideDir` `..`-traversal guard, since `mcpServers[].command` is not refined the way agent commands are).

**Typecheck (#10594).** Plugin main code (`plugins/{builtin,sample}/*/main`) sat in NO tsconfig — esbuild compiled it, so type errors were invisible until `npm run check`. New `tsconfig.plugins.json` (strict, `NodeNext`, `noEmit`) is wired into both `typecheck:projects` and `build:main`. It must use `tsc --noEmit`, never `tsc -b`: a composite build emits `.js` into the source tree and clobbers the esbuild output that ships.

**Extensions + manifest integrity (#10624).** `COMMAND_HANDLER_EXTENSIONS` accepted `.ts`/`.tsx`. Under the type-stripping in Electron 42's Node, a `.ts` handler _appears_ to work for erasable syntax but throws `SyntaxError` at first `import()` on any non-erasable construct (enum, parameter properties, decorators), and `.tsx` never runs because JSX is not erasable — validation-time acceptance of a runtime-fatal extension. The list is now `[".js", ".mjs"]` and a fatal build scan (`findTypeScriptCommandHandlers` → `validateCommandHandlerExtensions`) rejects any `.ts` handler in a built-in/sample plugin lacking a loadable `.js`/`.mjs` sibling. The PR also moved duplicate-id and cross-reference checks into the manifest `superRefine` (`electron/schemas/plugin.ts`): duplicate ids first-win silently (registries key on `.set()`/`.find()`-first) and a view whose `id` matched no panel was silently ignored at load — both are now hard parse errors (`duplicate_contribution_id`, `view_panel_ref_unknown`, plus `forge_*_ref_unknown`/`settings_token_*` for dangling refs and `${settings:*}` tokens).

## Lesson

- **"Compiles" and "copies" are separate lies — a green `build:main` proves neither asset presence nor type correctness.** esbuild strips types (never checks) and touches only what it's told. Any step that both compiles and copies needs a validation pass over what it copied: `findMissingPluginAssets` resolves every `./`-relative `command`/`args` path against real output and fails the build, because the copy ships whole dirs but a manifest can still name a path the author never created.
- **node-pty spawns via native OS spawn, bypassing Electron's asar filesystem patch — any `./`-relative path a plugin spawns must be in `asarUnpack` or it ENOENTs in packaged builds even when bundled.** Dev build works, packaged build fails; `dist-electron/plugins/builtin/**/*` is the unpack entry. Check `asarUnpack` in `electron-builder.config.cjs` whenever native spawn (node-pty, MCP supervisor) reaches a file inside `app.asar`.
- **Node's built-in type-stripping is erasable-syntax-only and `.ts`-only.** A `.ts` file with an enum / parameter property / decorator throws `SyntaxError` at first `import()`; a `.tsx` file never runs. Never accept `.ts`/`.tsx` as a runtime-loadable extension on the reasoning "Node strips types now" — it strips _some_ types for `.ts` and none of JSX. Author in TS, ship compiled `.js`.
- **Typecheck side-project code with `tsc --noEmit -p`, never `tsc -b`.** A composite/`-b` build emits `.js` into the source tree and clobbers the esbuild/vite output that ships (`tsconfig.plugins.json` uses `noEmit` for exactly this). A new side-tsconfig for a path esbuild/vite compiles but `tsc` doesn't must be wired into BOTH `typecheck:projects` and `build:main`.
- **Manifest cross-references and duplicate ids fail silently at runtime — validate them in `superRefine`, not at load.** Duplicate ids first-win via `.set()`/`.find()`; dangling `view→panel`, `forgeProvider.settingsScopeRef`/`viewRefs`, and `${settings:*}` tokens no-op or resolve to empty string. A gate that accepts what the runtime silently rejects is worse than none; make the parse-time schema reject exactly what the loader can't wire.

## Applies when

- Touching `scripts/build-main.mjs` copy/validate steps, or authoring a plugin that spawns a `./`-relative `bin/`/`mcp/` script — confirm it survives the copy AND `findMissingPluginAssets`.
- Adding a natively-spawned or fs-read file to a packaged build — verify `asarUnpack` in `electron-builder.config.cjs`; node-pty and the MCP supervisor bypass Electron's asar patch.
- Deciding whether a `.ts`/`.tsx` file will "just run" under Node's type-stripping — it won't for non-erasable syntax or JSX.
- Adding a tsconfig for code esbuild/vite compiles but `tsc` doesn't cover — use `tsc --noEmit -p`, wired into both `typecheck` and the build.
- Adding contribution arrays or id cross-references in `electron/schemas/plugin.ts` — put duplicate-id and cross-ref checks in `superRefine`.
