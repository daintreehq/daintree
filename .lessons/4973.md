## Context

On app startup, `stateHydration` restores panels from the previous session. Agent terminals attempt to reconnect to their PTY processes. A "phantom agent guard" was added to filter out stale agent panels that no longer have a live PTY.

## Problem

All agent terminal panels were silently dropped on cold app restart. Users lost their entire saved layout on every restart.

## Root cause

The phantom-agent guard checked `reconnect === "not_found"` and discarded the panel. During cold start, _every_ PTY reconnect returns `not_found` because the PTY host hasn't started yet — but `not_found` on cold start means "needs to be respawned", not "this panel is phantom/stale". The guard had no way to distinguish cold-start `not_found` from live-switch `not_found`.

The fix: check `_switchId !== undefined` before activating the guard. `_switchId` was only set during a live project switch, not during initial hydration.

Update (2026-06-07, per-project WebContentsView migration): once each project got its own persistent `WebContentsView` that hydrates only once on creation, live project switches became view swaps — the previously-running terminals stay alive and are just re-shown, with no second hydration pass to re-run reconnect against. The `_switchId`/`isCurrent` supersede machinery and the guard branch gated on it became unreachable dead code and were deleted (`refactor(hydration): remove dead supersede and deferred-restore machinery`). The context-collision this lesson describes can no longer happen through that mechanism, because there is no longer a second hydration context for `_switchId` to distinguish from cold start.

What survives: `src/utils/stateHydration/panelRestorePhase.ts` (~line 368) still carries the load-bearing comment and branch — "`not_found` on cold app restart means the PTY process was killed on quit and needs to be respawned" — and `src/utils/stateHydration/reconnectManager.ts` still returns a `"not_found"` status from `reconnectWithTimeout`. The discriminator today isn't a runtime parameter at all: it's structural — this code path only ever runs during the once-per-view cold hydration, so `not_found` here is unambiguous by construction rather than by an explicit check.

## Lesson

When the same status/signal (like PTY `reconnect: "not_found"`) can arise from two different contexts with opposite correct responses, don't infer the context from the signal itself — gate on an explicit discriminator instead. That discriminator can be a runtime parameter (as `_switchId` was), or it can be architectural: restructuring the system so the ambiguous code path is only ever reachable from one context in the first place (as happened here once project switches stopped re-running hydration at all). Either way, the moment you collapse two contexts onto one code path without one of those, a status meaning "needs respawn" in context A silently means "discard as phantom" in context B.

PTY `reconnect: "not_found"` meant different things depending on context when both were reachable:

- **Cold start**: PTY host not running yet → panel needs respawning
- **Live project switch** (no longer possible via hydration — see update above): PTY genuinely gone → panel should be discarded (phantom guard fires)

## Applies when

- Modifying the cold-restart respawn branch or the dead-agent-backend phantom check in `src/utils/stateHydration/panelRestorePhase.ts`, or the reconnect-status logic in `src/utils/stateHydration/reconnectManager.ts`
- Any hydration path that could differentiate cold-start from another restore context
- Adding new reconnect states to the agent state machine
- Reintroducing any code path that runs hydration/reconnect more than once per project view — check whether it needs an explicit context discriminator before assuming `not_found` means one thing
