## Context

`extractPluginArchive` in `electron/services/PluginArchive.ts` streams each entry of a `.dntr` plugin archive out of yauzl with `stream.pipe(out)`, and `PluginInstaller.installPlugin` (`electron/services/plugin/PluginInstaller.ts:308`) awaits it under a `proper-lockfile` install lock before promoting the temp dir. Issue #11227 reported that installing a real plugin archive would hang mid-extraction with no error, no timeout, and no way to recover short of quitting the app.

## Problem

Extraction silently stopped writing bytes partway through a large entry (65,516 of 70,025 bytes in the repro) and never progressed, errored, or finished. `install.lock.lock` and the `.install-tmp-*` directory stayed held indefinitely because `installPlugin` had no timeout around the await — only a full app quit released them. The symptom pointed at "our install logic is broken," but a synthetic 3-entry archive with no third-party plugin code reproduced it identically, and it even reproduced under `ELECTRON_RUN_AS_NODE=1` with no Electron app lifecycle at all — proof the bug lived below the plugin system entirely.

## Root cause

Node 24.16 (nodejs/node#62557) made `Readable.pause()`/`resume()` a no-op once the stream's internal `destroyed` flag is already set. `fd-slicer` 1.1.0 — yauzl 2.x's read-stream layer — ends a slice the old way, by setting `self.destroyed = true` directly and calling `self.push(null)` instead of calling `destroy()`. If write-side backpressure happens to be active at that exact instant, the `resume()` that the pipe's drain handler would normally fire does nothing, and the final chunk plus EOF are stranded forever — no `finish`, no `error`, no exit. That is why the failure is byte-exact at the default 64KiB `highWaterMark` (the point backpressure kicks in) — the issue's own test matrix isolated it to the Node version (Electron 42's embedded Node 24.16.0 hung on a 70,025-byte entry; a standalone Node 22.13.1 run with the same fixture passed). The only platform tested was macOS; macOS's lack of io_uring is a plausible reason the fs-completion race lands in the vulnerable window reliably there, but that platform explanation is this lesson's own inference, not something confirmed against a Linux repro. The regression was reverted in nodejs/node#63834 and shipped in Node 24.18.0 / Electron 42.6.0+ (verified against Electron's v42.6.0 release notes); the repo's `^42.4.0` range already permitted the fix, the lockfile just hadn't moved.

Two more facts compound the stuck-forever part: `installPlugin` awaits `extractPluginArchive` with no timeout, so its `finally` cleanup (temp-dir removal, lock release) never runs when the promise never settles — and `proper-lockfile`'s `stale: 20_000` doesn't rescue it either, because `updateLock` re-arms every 10s and `utimes`s the lockfile, so a hung-but-alive process keeps refreshing its own mtime and never looks stale. Stale-lock reclamation only helps when the holder is dead, not when it's wedged live.

## Lesson

- **When a hang reproduces byte-exact at a stream watermark (64KiB `highWaterMark`) and only on one OS, suspect a Node/stream internals regression before the app-level pipe/await code** — strip the repro down with `ELECTRON_RUN_AS_NODE=1` (or plain Node) to prove the bug is below your application and your Electron version, not in it.
- **A silent stream hang can only be fixed defensively at your own layer, even when the true fix is upstream** — the PR bumped Electron `^42.4.0`→`^42.7.0` for the Node revert AND added an app-side per-entry inactivity `AbortController` (`PLUGIN_ARCHIVE_ENTRY_INACTIVITY_MS`, 30s, reset on every `data` chunk) around `stream.pipeline`, because relying on the upstream fix alone leaves you exposed to the next regression of the same shape.
- **`await`-ing a stream operation with no timeout means your lock/cleanup `finally` never runs if the stream never settles** — `installPlugin`'s lock and temp-dir release depend entirely on `extractPluginArchive` resolving or rejecting; a stall with no abort path leaves `install.lock.lock` and `.install-tmp-*` held until the whole app quits.
- **A lockfile's `stale` threshold does not save you from a wedged-but-alive holder** — `proper-lockfile`'s `stale: 20_000` combined with a periodic `updateLock` `utimes` refresh only reclaims locks from a dead process; a hung process that's still running keeps renewing its own lock forever. If a resource needs recovery from "stuck," it needs its own timeout, not just staleness detection on the holder.
- **Pin security-relevant options explicitly across a major dependency bump instead of inheriting new defaults** — the PR set `strictFileNames`, `decodeStrings`, `validateEntrySizes` explicitly on `yauzl.open()` when bumping yauzl 2.10→3.4, so a future yauzl release changing its defaults can't silently weaken the zip-bomb/path-traversal guards this code depends on.
- **A major version bump that drops a problematic transitive dependency can BE the fix** — yauzl 3.x vendors its own copy of `fd-slicer` with a proper `_destroy` instead of depending on the external 1.1.0 package, which is what makes the abort path release the shared zip file descriptor cleanly; check the dependency's own issue tracker (thejoshwolfe/yauzl#169) before assuming only the Node-level fix is needed.

## Applies when

- Debugging any promise/stream `await` that hangs with no error and no timeout, especially one gated by a lock or temp-state cleanup in a `finally` block.
- A hang or stall reproduces at a suspiciously exact byte boundary (a stream `highWaterMark`, buffer size, or similar power-of-two/kilobyte threshold) — that specificity is a strong signal of stream backpressure/internals, not application logic.
- Touching `electron/services/PluginArchive.ts` (`extractPluginArchive`, `openZip`) or `electron/services/plugin/PluginInstaller.ts`'s install/upgrade lock and temp-dir lifecycle.
- Bumping Electron, Node, or any package with a native stream/pipe layer (yauzl, fd-slicer, or similar) — check the target version's release notes for stream-behavior fixes, not just API changes, and re-verify security-relevant options are still passed explicitly rather than defaulted.
- Reviewing any `proper-lockfile`-style stale-reclaim mechanism — confirm it can actually recover from a wedged-alive holder, not just a dead one.
