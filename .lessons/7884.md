## Context

Worktree cards expose a commit-and-push surface. Originally a one-click button ran `git.stageAll` → `git.commit` → `git.push` inline with no review step, pre-filling the commit message from an attached AI note. The flow now lives in the Review Hub `CommitPanel` (`CommitComposerDialog` from this PR was later consolidated into `ReviewHub` in commit `b995947f3`), but the safeguards this PR introduced survived intact.

## Problem

When no AI note was present, the message logic fell through a `aiNote ?? lastCommitFirstLine` chain and silently reused the _previous_ commit's subject. A real incident on `origin/develop` pushed a commit carrying three unrelated UI files but wearing a merge commit's subject line — it looked like a duplicate PR merge while actually containing unrelated work. A count-only preview ("3 files") would not have caught it; only showing the actual message would have.

## Root cause

The `if message is empty, use Y` fallback reads as harmless defensive code, but on a _destructive submission_ (push to a shared remote) it manufactures a plausible-but-wrong value with no user in the loop. The previous-commit subject is never the correct message for new staged work — there is no scenario where reusing it is right. The defensive default converts "user forgot to write a message" (recoverable, blocking) into "wrong commit silently pushed to origin" (an incident).

## Lesson

- On any destructive submission (commit, push, force-push, anything touching the remote/filesystem), **never substitute a derived default**. Gate on an explicitly authored value. Live gate: `canCommit = stagedCount > 0 && commitMessage.trim().length > 0 && ...` in `CommitPanel.tsx` — an empty message is a hard blocker, not a thing to backfill.
- Seed the editor from at most one _intentional_ source (the AI note) falling back to **empty string**, never to a derived value: `initialCommitMessage ?? ""` in `ReviewHubContent.tsx`. Treat any `?? lastCommit*` / `if X empty use Y` chain on a destructive path as a review blocker (this is the #7880 root cause, codified in the "Destructive Action Tiers" hard rules in CLAUDE.md).
- A preview must show the **actual content** (the real message text + target branch + per-file diff), not a count — a count cannot reveal a wrong-but-plausible value. The D2 push-confirm in `CommitPanel.tsx` renders the full `commitMessage` and target branch before the push fires.
- Treat remote-touching writes as Tier D2: explicit `ConfirmDialog` + content preview. Protected-branch pushes (`isProtectedBranch` from `shared/utils/gitConstants.ts` — `main`/`master`/`develop`/`development`) add the extra confirm step; the opt-out is per-worktree and persisted only on confirm.

## Applies when

- Adding or reviewing any commit / push / force-push / merge UI, especially one-click "commit and push" buttons on worktree cards or the Review Hub.
- You see a `?? lastCommit`, `|| previousSubject`, `if (!message) message = ...`, or any "if X is empty, use Y" chain feeding a destructive IPC call (`git.commit`, `git.push`, `git.stageAll`).
- Building a confirmation/preview dialog for a shared-state mutation and deciding whether a count is sufficient — it is not; show the actual message/diff/branch.
- Touching `CommitPanel.tsx`, `ReviewHubContent.tsx` commit-message seeding, `isProtectedBranch`/`PROTECTED_BRANCHES`, or any new caller of the stage→commit→push sequence.
- Classifying a destructive action's tier (D0–D3) and wiring its `ConfirmDialog` + `danger` metadata.
