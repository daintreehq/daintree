## Context

`ResourceGovernor` (`electron/pty-host/ResourceGovernor.ts`) polls `process.memoryUsage()` every tick to decide when to warn, trim scrollback, or pause PTY output — it is the pty-host's only defense against unbounded memory growth. #10920 moved the CPU-heavy per-terminal analysis (headless xterm mirrors used for agent-state detection, ~18MB per full 10,000-line terminal) off the pty-host's main thread and into a persistent `worker_threads` pool (`AnalysisWorkerPool`/`AnalysisWorkerRuntime`), a good responsiveness win. The same week, #10951 built a broader `WorkerGovernanceService` abstraction for trimming/disposing idle workers across several subsystems, but that layer is policy-level and doesn't touch `ResourceGovernor`'s own memory read.

## Problem

After #10920, the governor's memory signal went quiet exactly when it mattered most. With 8 full terminals streaming through real workers, the worker isolates measured 189MB while the host isolate measured 14MB — but the governor's `utilizationPercent` read 1.9%, so there was no warning band, no targeted trim, and no pause protection. Left unaddressed, a worker isolate hitting its own V8 cap dies with `ERR_WORKER_OUT_OF_MEMORY`, which is exactly the terminate/recreate failure mode (`!flush_tasks_` Electron crash) the persistent-worker pool existed to avoid — the fix #10920 shipped for responsiveness could silently reintroduce the crash it was designed to prevent.

## Root cause

`process.memoryUsage()` is isolate-scoped: called from the pty-host main thread, it reports only that thread's V8 heap and external (ArrayBuffer-backed) memory. It cannot see a `worker_thread`'s heap at all — that's a separate V8 isolate with its own memory space. #10920 moved the dominant per-terminal memory cost (the headless mirror buffers) into those worker isolates, but `ResourceGovernor`'s signal computation — `combinedMb = heapUsedMb + externalMb` and `heapUsedMb / HEAP_BUDGET_MB` — kept reading only the host isolate. This is the identical blindness class #9905 fixed once already, one layer down: #9905 taught the governor that `external` (ArrayBuffer backing stores) matters as much as V8 heap _within_ one isolate; #10920 then created a second isolate boundary the governor didn't know to cross. There was no build-time signal for this — the governor kept compiling and running, just against numbers that no longer meant what they used to. A second, subtler trap layered on top: analysis workers are forked as plain `worker_threads` and inherit the parent's `execArgv`, so each worker isolate independently carries the same `--max-old-space-size` cap as the host (`HEAP_BUDGET_MB` doubles as a per-isolate constraint, not just a slice of a shared budget) — a single hot worker can hit its own ceiling even while the combined-process ratio looks fine.

## Lesson

- **A memory governor that reads `process.memoryUsage()` is blind to any work moved into a `worker_thread`** — there is no way to introspect another isolate's heap from outside it. Any move of persistent buffers/state off the thread a governor watches (as #10920 did) needs a matching self-report channel wired into that governor before merge, not discovered by later measurement.
- **This blindness recurs at every isolate boundary, so expect it again.** #9905 fixed heap-vs-external within one isolate; #10953 fixed host-vs-worker across isolates. The next persistent worker pool added to Daintree (plugin dev workers, DB worker, copytree worker — several already exist per #10951) needs its own memory self-report wired into whichever governor is supposed to bound it, or it inherits the same gap by default.
- **Treat a stale sample as UNKNOWN, never as zero pressure.** `AnalysisWorkerRuntime.collectMemorySample()` self-reports every 2s (`MEMORY_SAMPLE_INTERVAL_MS`, unref'd timer) and `WORKER_SAMPLE_MAX_AGE_MS` (10s TTL) makes a stale sample contribute 0 to `combinedMb` — correct for the pause-engage side. But a parse-saturated worker stops posting exactly when its memory is peaking, so contributing 0 there would let the resume path falsely clear threshold. `hasStaleAliveWorkerSample()` gates threshold-based resume on every _alive_ worker having a fresh reading; the bounded `FORCE_RESUME_MS` force-resume is deliberately left unaffected so a wedged worker can delay resume but never block it forever.
- **A `worker_thread` forked without its own `execArgv` still inherits the parent's V8 flags**, so if the parent models `HEAP_BUDGET_MB` as a per-isolate cap, every worker isolate has that same cap independently. `ResourceGovernor` folds `maxWorkerHeapMb / HEAP_BUDGET_MB` into the `Math.max(...)` binding-constraint signal alongside the combined-process ratio specifically because one hot worker can trip its own ceiling while the process-wide ratio still looks safe.
- **Rank trim/reclaim targets by measured occupancy, not configured capacity.** A terminal's scrollback cap (e.g. 10,000 lines) says nothing about how many lines it actually holds. `getActualBufferLines()` now sources real `bufferLines` from the workers' own self-reports so `performPrePauseTrim` and the buffer-memory gauge score terminals by what they actually consume, falling back to the cap estimate only when no fresh worker sample exists (in-thread mode, or a worker mid-respawn).

## Applies when

- Moving CPU- or memory-heavy work into a `worker_thread` pool when a resource governor or memory monitor already watches the thread you're moving work off of — check what it reads and whether it needs a new self-report channel.
- Diagnosing "the memory governor never triggers" or an `ERR_WORKER_OUT_OF_MEMORY` crash despite visible memory pressure — suspect an isolate-scoped read that can't see where the memory actually lives.
- Touching `electron/pty-host/ResourceGovernor.ts`, `AnalysisWorkerPool.ts`, or `AnalysisWorkerRuntime.ts`, or adding a new persistent worker subsystem alongside the ones #10951 already wired into `WorkerGovernanceService`.
- Designing any staleness-tolerant signal aggregation — decide explicitly what a missing/expired sample contributes; defaulting it to zero is rarely safe for a pressure signal, only for the engage side, not the resume/clear side.
- Reviewing eviction, trim, or reclaim logic that ranks candidates by a configured limit/cap rather than their actually measured usage.
