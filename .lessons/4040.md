## Context

Browser panels and other panel types would jump to different grid positions when switching projects and returning.

## Problem

During hydration, panels are replaced with fresh instances that receive new IDs. The terminal registry's ordering array still referenced the old IDs. When old IDs were no longer found, the store fell back to default ordering — losing the user's saved arrangement.

## Root cause

Hydration creates a semantic break: old IDs → new IDs with same labels. The ordering array was ID-based but hydration didn't remap it. Any ID-based data structure must be treated as stale after hydration and remapped using stable identifiers (labels, panel kinds, etc.).

## Lesson

After hydration that replaces panel instances (app startup, per-project view creation), remap the saved ordering to the freshly created IDs. In `panelRestorePhase.ts`, panels are restored in three phases (non-PTY, priority PTY, background PTY) so they end up in execution order, not saved order; the fix captures each restored ID against its saved-order index (`restoredIdsByIndex`), sorts by index, then calls `restoreTerminalOrder(orderedIds)` with the new IDs in saved order. The principle: any ID-based ordering array is stale after hydration and must be rebuilt from a stable anchor (here, the saved-order position) rather than the old IDs.

Note: with per-project `WebContentsView`s, each view hydrates exactly once on creation via `useAppHydration`. There is no in-place re-hydration on project switch — `useProjectSwitchRehydration` is now a no-op — so the remap only needs to run on the `useAppHydration` path.

## Applies when

- App startup / per-project view hydration (`useAppHydration` → `panelRestorePhase.ts`)
- Any panel ordering state that must survive ID changes across hydration
