## Context

Cold start batches `crash-recovery` + `app:hydrate` + `terminal-config` into one `app:boot` IPC round-trip (#8620). To overlap that round-trip with React parse/commit, #8848 fires the promise at module-eval time in `src/main.tsx` (`void getSafeBootPromise()`, before `createRoot`) and consumes it with React 19's `use()` behind a `<Suspense>` boundary in `src/App.tsx`, replacing the old `useEffect` + `{result,error,settled}` state machine and the `useRef` Strict-Mode firing guard in `useAppBoot`.

## Problem

A module-scope promise (`let bootPromise` in `src/lib/bootPromise.ts`) is the React 19 idiom for overlapping IO with first render, but the cache outlives the V8 context in two ways that silently serve a stale resolved boot payload: (1) Vite HMR re-evaluates a module while the context stays alive, and (2) any future dev-reload path that reuses the context. Additionally, naively calling `window.electron.app.boot()` at module-eval runs _before_ any React error boundary or `bootstrap().catch()` exists, so a synchronous throw from a partially-initialized bridge would be uncaught, and a rejected boot promise would surface as an unhandled rejection.

## Root cause

`use()` requires a _stable_ promise reference (a fresh reference re-suspends on every render) and reads non-standard `status`/`value`/`reason` fields off the thenable synchronously when present. So the design has hard constraints that aren't obvious:

- The promise must be cached at module scope AND that cache must be explicitly invalidated whenever the renderer logically restarts without a new V8 context. `import.meta.hot.dispose()` clears both `bootPromise` and `safeBootPromise`; a crash-resolve reboot uses `webContents.reload()` which destroys the context outright, so no manual reset is needed there — but the HMR path absolutely is.
- `annotate()` manually sets `thenable.status = "pending"` then `"fulfilled"/"rejected"` with `value`/`reason` in a `.then`. This is what lets a _later_ caller (the `App` render) read an already-settled boot payload with zero Suspense tick. The annotation `.then` also marks the promise handled, preventing an unhandled-rejection warning.
- Boot failure is graceful degradation, not a render error: `getBootPromise()` may reject, but `getSafeBootPromise()` wraps it to a `{ ok: false }` sentinel that never rejects, so `use()` returns instead of throwing into the error boundary — the app still renders cold-start chrome and falls back to live `app:hydrate`.
- The module-eval call is wrapped in `try/catch` converting a synchronous bridge throw to `annotate(Promise.reject(...))`, because there is no error boundary at module-eval time.
- `notifyViewPainted()`'s double-rAF effect was moved to the Suspense _parent_ (`App`, not `AppInner`) so the first-frame paint signal still fires the moment the boundary commits even while `AppInner` is suspended on `app:boot`, preserving the pre-#8848 ordering guarantee regardless of IPC latency.

## Lesson

When fetching data at module scope to consume via React 19 `use()`:

- Cache the promise in a module-level `let` and provide an explicit reset wired to `import.meta.hot.dispose()` (and a test-only `resetBootPromiseForTests()`); a long-lived V8 context + HMR will otherwise serve a stale resolved value.
- Annotate the thenable with `status`/`value`/`reason` at settle time so later callers read synchronously without a Suspense tick, and so the `.then` marks the rejection handled.
- Module-eval fetches run before any error boundary or global catch — wrap the call in `try/catch` and convert synchronous throws to a rejected promise.
- Decide deliberately whether a fetch failure should throw into the error boundary or degrade: here a "safe" wrapper (`getSafeBootPromise`) returns an `{ ok: false }` sentinel so boot failure renders fallback chrome rather than an error screen.
- If an effect depended on commit ordering (e.g. paint signals), move it to the Suspense _parent_ so it fires when the boundary commits, not when the suspended child resolves.

## Applies when

- Adding or changing any module-scope promise fed to React 19 `use()` (cold-start `app:boot`, or any future `getXPromise()` in `src/lib/`).
- Touching `src/lib/bootPromise.ts`, `src/hooks/app/useAppBoot.ts`, `src/hooks/app/useCrashRecoveryGate.ts`, the boot `<Suspense>` in `src/App.tsx`, or the module-eval warm-up in `src/main.tsx`.
- Symptoms: a dev reload (HMR) showing stale boot/hydration data; `use()` re-suspending every render; an unhandled-rejection warning from a prefetch; a synchronous bridge throw at startup escaping uncaught; or `notifyViewPainted`/first-frame ordering breaking when a Suspense boundary is introduced.
- Reviewing any prefetch-before-render optimization that fires IPC outside a React effect, or any change to cold-start boot sequencing / crash-recovery gating.
