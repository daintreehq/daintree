## Context

#10962 lands Phase 4 of the paint-fabric arc (#10954/#10955/#10961/#10966/#10967): a `ParseAuthority` — a second, headless xterm (`@xterm/headless` + `@xterm/addon-serialize`) — absorbs a flooding background terminal's bytes off the main thread at input rate, so the visible main-thread terminal can become a lightweight "mirror" repainted from bounded snapshots on a fixed cadence instead of parsing every byte itself. This is still behind `DAINTREE_PAINT_FABRIC` / `DAINTREE_PAINT_FABRIC_WORKER_INGEST` (both default off), with #10967 wiring it into the live ingest path since. `mirrorApply.ts` is the small module that turns one authority snapshot into the payload actually written to the mirror.

## Problem

A snapshot from `SerializeAddon.serialize()` looks self-contained — it's a full escape-sequence dump of the authority's current buffer and modes — so the obvious first implementation is to just `mirror.write(serialized)` every tick. That leaks state across ticks: if the authority entered the alternate screen and later exited it, or turned on bracketed paste / mouse tracking and later turned it off, the mirror keeps whatever it last had, because nothing in the new snapshot ever says "turn this off." The equally obvious fix — reset the mirror with RIS (`ESC c`) before every apply — creates a different, visible bug: a one-frame flash of the blank reset state on every repaint tick, because RIS resets more than intended.

## Root cause

`SerializeAddon` assumes it is writing into a terminal that starts from Terminal defaults: it only emits sequences for modes/styles that are currently **non-default** on the source, never explicit resets for modes that have gone back to default. So if the mirror is not independently reset before each apply, whatever alt-screen/paste/mouse-tracking state a _previous_ snapshot left behind survives untouched by the _current_ one — the snapshot format has no concept of "unset this."

The natural full reset is RIS (`ESC c`), but the repaint is also wrapped in DEC synchronized-output mode 2026 (`\x1b[?2026h` / `\x1b[?2026l`, which xterm honors) specifically so the renderer never paints an intermediate blank frame between clearing and rewriting — a cadence tick must land as one visually-atomic repaint. RIS itself resets mode 2026, so using it as the in-band reset collapses the very bracket meant to hide the transition, and the blank state flashes on screen. The fix in `mirrorApply.ts` is a narrower, hand-picked reset that stays inside the 2026 bracket: DECSTR soft reset (`\x1b[!p`) plus explicit exits for the stateful modes DECSTR leaves alone — alternate screen (`\x1b[?1049l`), bracketed paste (`\x1b[?2004l`), and the mouse-tracking family (`\x1b[?9;1000;1001;1002;1003;1005;1006;1015l`). The full payload — `SYNC_OUTPUT_START + MIRROR_RESET + CLEAR_ALL (3J 2J H) + serialized + SYNC_OUTPUT_END` — is written to the mirror in one `write()` call, so the reset-then-repaint is one atomic frame from xterm's perspective, not a reset frame followed later by a content frame.

## Lesson

- **Never apply a raw `SerializeAddon` snapshot directly onto a persistent mirror terminal.** The addon only encodes non-default state relative to an assumed-default terminal, so anything left over from a _previous_ snapshot (alt-screen, bracketed paste, mouse tracking, other DEC private modes) is never explicitly cleared by a _new_ one and will silently persist.
- **Do not use RIS (`ESC c`) as that in-band reset if the repaint is also bracketed in synchronized-output mode 2026** — RIS resets mode 2026 itself mid-sequence, breaking the atomic bracket and producing a visible flash of the intermediate blank frame. Use a targeted reset instead: DECSTR (soft reset) plus explicit disables for exactly the stateful modes DECSTR doesn't touch (alt screen, bracketed paste 2004, mouse tracking 9/1000-1003/1005/1006/1015 — see `MIRROR_RESET` in `mirrorApply.ts` for the exact sequence).
- **Send reset + clear + content as one `write()` call**, not three — xterm's synchronized-output support only hides intermediate frames if they're inside the same write between `2026h` and `2026l`; splitting the sequence across writes reintroduces the flicker even with a correct reset.
- **This "headless xterm + SerializeAddon as a second parse authority" pattern is reusable** (`ParseAuthority` in `parseAuthority.ts`) — any future feature that projects an off-thread or otherwise decoupled xterm's state onto a live on-screen terminal (session-replay reconstruction, terminal thumbnails/previews) needs this same reset discipline, not just worker-parse.
- **The ack boundary must move with the bytes.** When #10967 wired this into the live ingest path, the completion ack for a diverted chunk fires from `ParseAuthority.write()`'s own callback, not from a main-thread receipt — this is the fix for the exact failure mode that got the earlier SharedArrayBuffer/worker ingest path disabled (`TerminalOutputIngestService.ts`: per-view workers racing one ring buffer dropped output). Moving parse off-thread without moving where the ack fires drops bytes.

## Applies when

- Building or extending any headless-xterm "shadow"/parse-authority terminal whose serialized state gets periodically projected onto a visible xterm instance.
- Debugging a mirror/preview terminal that gets stuck in the alternate screen, keeps reacting to mouse movement, or ignores normal paste after the source has moved past that state — that's stale VT mode leaking across repaints, not a bug in the source terminal.
- Seeing a one-frame flash/flicker on a periodic full-repaint that's supposed to be atomic under synchronized output (mode 2026).
- Touching `src/services/terminal/workerParse/` (`mirrorApply.ts`, `parseAuthority.ts`, `WorkerParseSession.ts`, `LiveWorkerIngest.ts`) or wiring any new off-main-thread ingest/parse path for terminal bytes.
