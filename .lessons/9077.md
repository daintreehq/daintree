## Context

Forge (GitHub) PR polling runs inside the per-project workspace-host UtilityProcess (`PullRequestService.checkForPRs` → `ForgeBridge` → main's `forgeRpcServer.dispatchForgeRpc` → provider GraphQL). PR #9077 (`75c19c148`, 2026-05-25) added a per-project poll lease in main on the premise that "since #4647 each Electron window forks its own workspace-host per project," so N windows on one project would fire N identical polls. That premise was already false when the PR was written: `d0f876691` ("spawn per-project workspace host processes", 2026-03-30 — the very commit `#4647` refers to) had consolidated workspace-hosts to one per normalized project path two months earlier. `WorkspaceHostPool.entries` (`electron/services/workspace-client/WorkspaceHostPool.ts`) is a `Map<projectPath, ProcessEntry>` — a second window on the same project reuses the existing host instead of forking a new one.

## Problem

The lease (`forgePollLeaseService.ts`) could never actually deny anything: same project → same pooled host → same deterministic holder id (`serviceName`), so its denial branch (`existing.holderId !== holderId && expiresAt > now`) was unreachable in the shipped topology. It still cost every `checkForPRs()`/`revalidateResolvedPRs()` cycle a lease-IPC round-trip plus 5s-timeout machinery that could only ever answer "acquired," and its comments (plus a "sibling window holds poll lease" log branch) described a race that could not occur — misleading enough that issue #9978 was filed against a scenario the lease could never produce. Issue #9996 ("Forge poll lease can never deny — one host per project") traced this, and PR #10272 (`588087ddd`, "remove unreachable per-project poll-lease layer") deleted the entire lease layer: `forgePollLeaseService.ts`, its lease IPC types in `shared/types/workspace-host.ts`, and the acquire/release methods in `forgeBridge.ts`/`PullRequestService.ts` are all gone.

## Root cause

Two things, worth separating:

- Architecturally, the fan-out this lesson set out to fix never reached main-visible traffic: `WorkspaceHostPool` pools workspace-hosts by normalized project path, not by window, so N windows on the same project already shared one `PullRequestService` instance and poll cycle before the lease ever landed. Pooling the shared resource is a stronger fix than arbitrating between callers of it — there was nothing left to arbitrate.
- Process-wise, PR #9077 cited a pre-pooling architecture (`#4647`) as the current state without checking that `#4647` was itself the commit that had already fixed it — the arbitration was built to guard against a topology the codebase had left two months earlier.

What actually survives in main today:

- **Cross-host singleflight** (`electron/services/forgeRpcServer.ts`) — its own header comment now calls it "the sole dedup layer main owns." The `inFlight` Map keyed by `method\0namespacedId\0stringifyArgs(args)` (deterministic `safe-stable-stringify`, `bigint:false`) collapses concurrent identical RPCs, evicted on settle, under a 35s `FORGE_INVOKE_TIMEOUT_MS` ceiling (above the bridge's own 30s `FORGE_RPC_TIMEOUT_MS`) so a hung provider can't wedge the entry and leak waiters. Its job changed shape, though: since same-project multi-window calls never reach it as duplicates, what it absorbs now is fan-in from _distinct_ projects whose calls happen to collapse on args, plus transient overlap during a host restart/handoff.
- **`ForgeBridge`'s own `inFlightByArgs`** (`electron/workspace-host/forgeBridge.ts`) — unchanged in shape, still a host-local singleflight; "host-local" now means "shared by every window on that project" rather than "one window."
- A separate, unrelated gate: **`PRIntegrationService.isWorker`** (`electron/workspace-host/PRIntegrationService.ts`, #10123) makes `startPolling()` a no-op when the whole Daintree instance was launched with `DAINTREE_INSTANCE_ROLE=worker` (resolved in `electron/window/skeletonCss.ts`'s `resolveInstanceRole`). This is an app-instance-level switch for headless/automation instances conserving GraphQL quota — it does not elect a poller among peer windows on one project. Don't confuse it with the deleted lease; it solves a different problem on a different axis.

## Lesson

Before building cross-process arbitration (a lock/lease/election) to fix "N processes are hitting one shared upstream," verify the fan-out still exists in the CURRENT topology — the issue number you're citing as evidence of it may itself be the commit that already fixed it. Check the pooling/allocation layer first (`docs/architecture/process-and-window-model.md`'s ownership table, or here, `WorkspaceHostPool.entries` keyed by project path): if callers already share one process/instance, there's nothing to arbitrate, and the arbitration code will sit there passing tests while its denial branch never fires in production — as this lease did for two months before #9996 caught it.

- Pooling the shared resource itself (one workspace-host per project, not per window) is a stronger fix than arbitrating between callers of it — it removes the duplication instead of managing it.
- An issue/PR number cited as "why N copies exist" can itself be the commit that already fixed it; `git log --oneline -- <path>` or the architecture doc's ownership table settles it in seconds, before you write a lease.
- A denial branch that never fires under any production-shaped test scenario is a smell to chase immediately — don't file an issue asking "why is this always true" against it (#9978's mistake) instead of asking whether it can ever be false.
- When arbitration genuinely is still needed — concurrent identical calls from processes that legitimately can't share state, like `forgeRpcServer.ts`'s cross-host singleflight — keep it main-owned, since main is the one boundary every isolated peer crosses, and cap it with a timeout above the caller's own timeout so a hung upstream can't leak waiters.
- Keep the singleflight-key caveat: a deterministic serializer (`safe-stable-stringify`) is required so property order can't split the key, but it renders `Map`/`Set` args as `{}` — a future arg of that shape needs an explicit key.
- Don't conflate a per-project multi-window concern with a per-instance one: `PRIntegrationService.isWorker`/`DAINTREE_INSTANCE_ROLE` gates whole headless app instances out of background polling for quota reasons — a different axis from "which of these peers polls," and not a substitute for it.

## Applies when

- Reaching for a lock/lease/election to arbitrate "N of something is hitting one shared upstream/API/rate limit" — first confirm N actually reaches main-visible traffic in the current topology, not the topology an old issue number described.
- Touching `forgeRpcServer.ts` (`inFlight`/`dispatchForgeRpc`/`buildSingleflightKey`), `forgeBridge.ts` (`inFlightByArgs`), `WorkspaceHostPool.ts` (pooling key/eviction), or `PRIntegrationService.ts`/`PullRequestService.checkForPRs`.
- Adding a new `ForgeRpcMethod` whose args include a `Map`/`Set` (the singleflight key will silently collide).
- Designing "one elected worker, others stand down" coordination across processes — check whether pooling the resource (one process per key, shared by all callers) is already available before building election/lease machinery on top of it.
- Gating background polling for headless/automation instances vs. per-project multi-window sharing — these are separate mechanisms (`DAINTREE_INSTANCE_ROLE` vs. `WorkspaceHostPool`); don't wire one where the other applies.
