## Context

Sidebar header secondary controls (overview, refresh) are hidden by default and revealed on hover/focus via a Tailwind named-group reveal cluster (`group-hover/header:` / `group-focus-within/header:`) in `src/components/Sidebar/SidebarContent.tsx`. The original cluster used `opacity-0 pointer-events-none` and toggled to `opacity-100 pointer-events-auto` on hover.

## Problem

The "hidden" buttons were still reachable by keyboard Tab even while invisible — a sighted keyboard user would Tab into controls they couldn't see and that gave no visual focus context. `pointer-events: none` blocks the mouse but does nothing to the accessibility/focus tree.

## Root cause

In Chromium 146, an element with `opacity: 0` and `pointer-events: none` is still laid out and rendered, so it stays focusable and in the Tab order. `pointer-events` only gates pointer hit-testing; it has no effect on keyboard focusability. The CSS property that actually removes an element from the Tab order is `visibility: hidden` (or `display: none`). A naive fix of swapping to `visibility:hidden` alone breaks the fade because `visibility` is not smoothly interpolatable. The fix keeps all three: `invisible` removes it from the Tab order, `opacity-0` drives the visible fade, and `pointer-events-none` gates the mouse — coordinated by `transition-[opacity,visibility]` (the discrete `visibility` flip is sequenced with the opacity fade so the element fades out before becoming `hidden`).

## Lesson

For any hover/focus-reveal control cluster, do NOT rely on `opacity-0 pointer-events-none` to hide it — those controls remain Tab-reachable. Use the layered pattern in `SidebarContent.tsx:1451`:

- `invisible` + `group-hover:visible` / `group-focus-within:visible` to actually remove from / restore to the Tab order.
- Keep `opacity-0` / `opacity-100` for the visual fade and `pointer-events-none` / `pointer-events-auto` for mouse gating.
- Transition both with `transition-[opacity,visibility]` so the `visibility` toggle is sequenced with the fade instead of snapping.
- Include `group-focus-within:` (not just `group-hover:`) so keyboard users get the reveal — and bias a hover-intent `delay-75` to hover while letting focus reveal feel instant.
- Add `motion-reduce:transition-none`. A source-level regression test (`SidebarContent.headerReveal.test.ts`) asserts both `invisible ... group-hover:visible` and `invisible ... group-focus-within:visible` are present — mirror that guard for similar reveal clusters.

## Applies when

- Building or reviewing any hover-reveal / focus-reveal toolbar, header, card, or list-row action cluster (Tailwind `group-hover:` / `group-focus-within:` patterns).
- A control "looks hidden" but is reported by keyboard Tab, screen readers, or focus-order audits.
- Reaching for `opacity-0 pointer-events-none` (or `pointer-events-none` alone) as a hide mechanism in any component under `src/components/`.
- Adding `visibility`-based hiding and seeing the fade snap instead of animate — reach for `transition-[opacity,visibility]`.
