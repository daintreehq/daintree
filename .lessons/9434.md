## Context

Destructive confirm dialogs (`TerminalContextMenu`, `TerminalDestructiveActionConfirmDialog`, `WaitingContainer`, `BackgroundContainer`, `useWorktreeActions`) close on confirm and then announce a result ("Terminal killed", "Trashed all sessions") to assistive tech via `useAnnouncerStore.getState().announce(...)`. The announcer store delivers either through the native `document.ariaNotify` API (Chrome 141+ / Chromium 146) or a `sr-only` `aria-live` region fallback.

## Problem

On macOS VoiceOver the confirmation announcement was silently dropped. The result message never reached the screen reader even though it worked fine for sighted users — the dialog closed and the visible UI updated, but blind users got no feedback that the destructive action completed.

## Root cause

Chromium bug 354736464: while focus is trapped inside an `aria-modal="true"` subtree, VoiceOver ignores `aria-live` updates whose live region lives _outside_ that subtree. The intuitive order — announce, then close — fires the announcement while the modal still holds focus, so the live-region mutation (in the main tree, outside the modal) is suppressed. This is a platform/screen-reader scoping bug, not app logic: the DOM mutation happens, VoiceOver just refuses to read it. Announce-then-close passes every sighted test and every non-VoiceOver AT.

## Lesson

- When dismissing a modal/dialog/popover and announcing a result, **close FIRST, then announce** — so focus returns to the main tree before the live-region update fires. Use `closeAndAnnounce(closeFn, message, priority?)` in `src/lib/accessibility.ts`; never hand-roll the close-then-announce sequence inline.
- `closeAndAnnounce` skips the announcement if `closeFn` throws, so a failed close can't emit a misleading success message.
- The announcer store (`src/store/accessibilityAnnouncerStore.ts`) is the only delivery path — it prefers `document.ariaNotify` (which queues directly with the platform AT and **bypasses the subtree filter entirely**) and falls back to an `aria-live` DOM mutation. Never call `document.ariaNotify` directly; feature-detection and the fallback live in the store.
- For modals that announce from _inside_ the still-focused subtree (no close happens, e.g. `ThemeBrowser` live preview, `WebviewDialog`), co-locate `<AccessibilityAnnouncer />` **inside** the `aria-modal` element so its live regions are in-subtree and survive even when `ariaNotify` is unavailable.
- Toasts/announcers that fire from outside any `aria-modal` subtree need none of this — they aren't affected by the scoping bug.

The announcer infrastructure this builds on (the `document.ariaNotify` API choice, the co-located in-subtree fallback, and the delivered-id dedup guard) is #9387 — that lesson covers how the announcer is built; this one covers the close-before-announce call-site ordering.

## Applies when

- Adding or refactoring a confirm/destructive dialog that announces a result on dismiss (terminal kill, worktree teardown, snapshot delete, any `ConfirmDialog`-driven flow).
- A screen-reader / VoiceOver report says an announcement is "missing" or "not read" after closing a modal, while sighted behavior looks correct.
- Building any `aria-modal="true"` surface that needs to push `aria-live` updates while it holds focus (live-preview, inline validation inside a modal).
- Touching `src/lib/accessibility.ts`, `src/store/accessibilityAnnouncerStore.ts`, or `AccessibilityAnnouncer`, or wiring up `document.ariaNotify`.
