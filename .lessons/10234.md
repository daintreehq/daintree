## Context

`FileTreeService.getFileTree` lists one directory level of a worktree for the file picker / file browser, filtering out gitignored entries by calling `git check-ignore` once with every entry in the directory. The original code used `simple-git`'s `createHardenedGit(...).checkIgnore(pathsToCheck)`, then `try { … } catch (_e) { /* ignore */ }`. This path is reached by the `copyTree.getFileTree` action and (now) the file-browser UI via `workspace-host.ts` → `WorkspaceClient.getFileTree` → `FileTreeService`.

## Problem

In a directory with thousands of entries (a flat generated-output or data folder), gitignored entries — build output, dependency folders, `.env`-shaped secret-like files — silently appeared in the tree instead of being hidden. Nothing errored visibly; the tree just leaked. Small directories looked perfect, so the bug only surfaced on pathological folders and was easy to miss in review (issue #10003).

## Root cause

Two mechanisms compound. (1) `simple-git`'s `checkIgnoreTask` builds the command as `["check-ignore", ...paths]`, so **every path becomes its own argv entry**. A flat folder with thousands of long paths exceeds the OS argument-length limit (`ARG_MAX` — ~256KB–1MB on macOS, ~2MB on Linux) and the spawned `git` fails with **`E2BIG`** (or `ENOMEM`). (2) The catch-all was empty, so `ignoredPaths` stayed empty and the downstream filter hid nothing — the function **failed open**. Fail-open is the unsafe direction for a visibility filter: the error path decided whether ignored content is shown, and it chose "show everything."

The fix replaces `simple-git`'s argv-based call with a direct `child_process.spawn` of `git check-ignore --stdin -z` in `electron/utils/gitCheckIgnore.ts` (`checkIgnoredPaths`). Pushing NUL-separated paths over **stdin** makes argv constant-size regardless of entry count. The empty catch in `FileTreeService` became a **fail-closed** handler: on any error it adds _every_ checked path into `ignoredPaths`, so the filter hides all of them (same shape as "everything here is gitignored"); a transient failure self-heals on the next successful call. Bypassing `simple-git` meant re-applying the hardening it gave for free — `buildHardenedGitEnv` was extracted from `createHardenedGit` and the `-c` flags are spread into argv (originally `HARDENED_GIT_CONFIG`; now `getHardenedGitConfig(platform)`, which also appends an app-owned `core.hooksPath` per commit `26b40008e`).

## Lesson

- **Passing an unbounded list of paths as argv to any spawned command is an `E2BIG` trap.** `simple-git`'s `checkIgnore` (and any command built as `[verb, ...paths]`) breaks on large flat directories. When the path count is user-data-driven, stream over `--stdin` (git speaks `--stdin -z` for `check-ignore`, `hash-object`, `update-index`, etc.), or chunk to a safe argv budget — never assume the list is small.
- **A swallowed catch on a visibility/ignore filter is a fail-OPEN security hole, not a nicety.** The catch decides whether gitignored build output / secret-like files are shown. Fail closed: on error, treat everything as ignored/hidden. Here that means seeding `ignoredPaths` with _all_ checked paths so `getFileTree` returns `[]` for that call. `git check-ignore` erroring is the _same observable shape_ as "everything is ignored" — lean into that.
- **When you bypass `simple-git` with a raw `spawn`, you inherit ALL of its hardening obligations, silently.** `createHardenedGit` applies `-c` config (`core.fsmonitor=false`, `protocol.ext.allow=never`, credential-blocking, `core.hooksPath`), a sanitized/locale env, and a `block` timeout. The wrapper re-applies each: spread `getHardenedGitConfig(platform)` into argv, use `buildHardenedGitEnv(platform)` for env (extracted so both paths stay byte-identical), and enforce `GIT_BLOCK_TIMEOUT_MS` with a `SIGTERM` kill — a hung git (broken FUSE mount, hostile shim on PATH) must not pin the request forever.
- **`git check-ignore` exit codes: 0 = some paths ignored (stdout lists them), 1 = NONE ignored, >1 = real error.** Treat exit 1 as an empty result, not a failure — mapping it to `reject` would make every all-visible directory fail closed and hide legitimate files. Only `code > 1` (and spawn `error`) should reject.
- **Fail-closed error paths on a hot, retried request need log throttling.** A refresh storm over a broken repo would emit one `console.warn` per `getFileTree` call; `FileTreeService` throttles to one warn per 30s (`WARN_THROTTLE_MS`) keyed by `resolvedBasePath`. Also swallow stdin `EPIPE` — when git exits early (bad flag), the stdin write races the dead process; `close` is the source of truth.

## Applies when

- Filtering, hiding, or gating anything on `git check-ignore` / gitignore status — or writing any error path that decides whether content is _shown_ (fail-open vs fail-closed is a security decision, default to hidden).
- Passing a directory's worth of user-driven paths to a spawned CLI (`git`, `rg`, `find`, …) — check for the `E2BIG` argv-limit trap and prefer `--stdin`/`-z` or chunking.
- Bypassing `createHardenedGit` / `simple-git` with a direct `child_process.spawn` of `git` — re-verify you carried over `getHardenedGitConfig`, `buildHardenedGitEnv`, and the `GIT_BLOCK_TIMEOUT_MS` kill (electron/utils/hardenedGit.ts).
- Touching `FileTreeService.getFileTree`, `electron/utils/gitCheckIgnore.ts` (`checkIgnoredPaths`), or the file-browser / `copyTree.getFileTree` path, and seeing gitignored entries appear or a `try/catch` around the ignore check.
- Reviewing an empty `catch (_e) {}` around a filter, permission check, or ignore lookup — ask what the _absence_ of the filter leaks.
