## Context

Daintree's `ProjectViewManager` throttles deactivated `WebContentsView` instances to reduce CPU usage for cached-but-hidden views. (It originally used `setBackgroundThrottling(true)`; since Electron 28 that API is window-wide and unsuitable, so throttling now goes through CDP `Emulation.setCPUThrottlingRate` per-renderer — see `electron/utils/webContentsLifecycle.ts` and #8599.) Two global Chromium flags had been set at app startup:

- `disable-renderer-backgrounding`
- `disable-background-timer-throttling`

## Problem

Background throttling set via `setBackgroundThrottling(true)` had no effect on cached views. Deactivated project views continued consuming CPU as if they were active.

## Root cause

`app.commandLine.appendSwitch('disable-renderer-backgrounding')` is a process-wide flag applied before app ready. It overrides any per-renderer throttling APIs, including `setBackgroundThrottling()`. The per-view call was silently a no-op.

## Lesson

Global Chromium command-line switches applied via `app.commandLine.appendSwitch()` take precedence over per-instance WebContents APIs. If you use `setBackgroundThrottling()`, `Emulation.setCPUThrottlingRate`, or `Page.setWebLifecycleState` (CDP) for per-view throttling, you must NOT have `disable-renderer-backgrounding` or `disable-background-timer-throttling` set globally.

These flags were likely added to prevent UI jank during development but became counterproductive once per-view throttling was implemented. Remove them and rely on `ProjectViewManager` to handle throttling at the correct granularity. There is now an explicit audit guard documenting this in `electron/utils/webContentsLifecycle.ts` ("If either is reintroduced, CDP freeze silently no-ops (lesson #4683)").

## Applies when

- Per-view throttling via `setBackgroundThrottling()` in Electron
- Using CDP `Page.setWebLifecycleState` for freeze/resume
- Any global Chromium flag that may interact with per-instance behavior
