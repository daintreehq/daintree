## Context

The pty-host `PtyPauseCoordinator` is a reference-counted PTY pause: subsystems each hold a named `PauseToken` and the raw PTY stays paused while any hold exists. Live holders: `ResourceGovernor` (`"resource-governor"`), the IPC ingest queue (`"ipc-queue"`, `ipcQueue.ts`), the per-window MessagePort queue (`"port-queue"` / `` `port-queue-${number}` `` / #10960 worker variant, `portQueue.ts`), and sleep (`"system-sleep"`). The union also declares `"backpressure"`, taken only on the FUTURE*SAB (SharedArrayBuffer) transport, which is dead in production (`backpressure.ts` gates it behind `FUTURE_SAB_MAX*\*`, never wired to a live `pause()`). When the governor engages under memory pressure it overwrites each terminal's flow status to `paused-resource-governor`via`emitTerminalStatus`; on disengage (`disengageThrottle`) it restores status. #7934 added that restore branch.

## Problem

A terminal paused by queue backpressure and then also by the governor kept showing the "Paused (memory) — recovers automatically" pill after the governor disengaged — even though the remaining live hold was renderer backpressure, which has its own distinct pill. Pause/resume itself was correct (the PTY stayed held while the queue token existed); only the attribution was wrong, and it self-corrected up to ~10s later when the queue path's own resume or safety timeout fired `running`. Nothing errored or type-failed, and it reproduced only when governor and queue holds overlapped — so it read as a flaky renderer glitch.

## Root cause

`disengageThrottle`'s restore branch was `else if (coordinator.hasToken("backpressure"))` — re-emitting `paused-backpressure` only when the FUTURE_SAB token was held. But no production path takes `"backpressure"`; live backpressure holds are `"ipc-queue"` and the `port-queue*` family, so for every real overlap the branch was false and re-emitted nothing. The failure was silent because `BackpressureManager.emitTerminalStatus` dedupes on last status (`if (previousStatus === status) return`, `backpressure.ts:233`): engage had stamped the map to `paused-resource-governor`, and with no restore re-emit it stayed stale. The queue path won't re-announce (it emitted `paused-backpressure` once at pause time, before the governor overwrote it), so the pill sticks until the queue path emits `running`. #10267's fix: `PtyPauseCoordinator.hasAnyBackpressureToken()` matching the live family (`token === "ipc-queue" || token === "backpressure" || token.startsWith("port-queue")` — `startsWith` covers `port-queue`, `port-queue-${number}`, and the worker variant), called in the restore branch. The bug read as correct because `"backpressure"` is a real typed union member — the name says "the backpressure token" but it points at a reserved-future path, not the live ones.

## Lesson

- **A guard over a token/lease/capability family must enumerate the whole live family, never one member.** `hasToken("backpressure")` type-checks and reads as "is backpressure active," but backpressure is expressed by several tokens (`ipc-queue`, `port-queue*`); checking one no live path takes is a dead branch. When a `PauseToken`/lease union has multiple members meaning the same class, add a family predicate (`hasAnyBackpressureToken`) and route guards through it, so a new token later updates one place.
- **Forward-compat reserved names mask dead checks.** `"backpressure"` exists in the union only for the not-yet-wired FUTURE_SAB transport ("dead in production" per the `getQueueDepthSnapshot` doc comment). A check against a reserved-future token looks intentional and passes review, but fires on a path that never executes. When a union mixes live and forward-compat members, comment which are live and never guard live behavior on a reserved one.
- **A missing re-emit is silent when the emit path dedupes on last value.** `emitTerminalStatus` early-returns on `previousStatus === status`, so the status the governor stamped (`paused-resource-governor`) stays latched until something emits a _different_ status; a no-op guard leaves it stuck with no error. When you overwrite shared dedup'd state on acquire, prove the release path re-asserts the correct prior state for every live case.
- **Separate held-token correctness from status-attribution correctness.** The coordinator's refcount kept the PTY correctly paused throughout; only the emitted flow status was wrong. A green pause/resume suite does not cover the pill — assert the exact `emitTerminalStatus` tuple per live token (why #10267 parameterized over `ipc-queue`/`port-queue`/`port-queue-5` and added a dispose-path guard test: teardown deliberately skips the restore branch since queue managers emit their own events and renderers disconnect first).

## Applies when

- Touching `electron/pty-host/ResourceGovernor.ts` engage/`disengageThrottle` or any branch that reads `PtyPauseCoordinator` tokens to decide what status to emit.
- Adding a new `PauseToken` (queue, transport, or pause source) — update `hasAnyBackpressureToken()` if it's backpressure-class, and check every `hasToken(...)` guard that should include it.
- Reviewing any `hasToken(X)` / single-member lease or capability check where the concept has multiple live token names or a reserved forward-compat name — confirm the guard covers the tokens actually taken in production.
- Diagnosing a terminal flow pill (`paused-backpressure` vs `paused-resource-governor`, `TerminalHeaderContent.tsx`) stuck on a stale value that self-corrects seconds later — suspect a missing re-emit against the `emitTerminalStatus` dedup map, not a renderer bug.
