## Context

Saved fleets (`FleetSavedScope[]`) live in project settings and are recalled from a dropdown. #8692 added `lastUsedAt` / `usageHistory` frecency fields and stamped them on every `fleet.recallNamedFleet`, but nothing read them (#9955 — written-but-unread dead data). #10308 wired the reader (`src/components/Fleet/fleetRanking.ts` ranks scopes via the same `computeFrecency` recipes use), and in doing so closed a lost-update race in the recall/save persistence path.

## Problem

Two near-simultaneous recalls (or a `saveNamedFleet` interleaved with a `recallNamedFleet`) could silently drop one operation's write. The old recall did a naive read-modify-write across an await boundary: `const current = await projectClient.getSettings(projectId)` (IPC), mutate `scope.lastUsedAt` / `scope.usageHistory` on the returned object, then fire-and-forget `projectClient.saveSettings(projectId, current)` plus a write-through `setSettings(current)`. `saveNamedFleet` had the same shape for appends. Because the frecency data was unread before #10308, the race produced no visible symptom — it was a latent lost-update the moment a ranking consumer started depending on the stamps being accurate.

## Root cause

Project settings straddle two layers: the in-memory `useProjectSettingsStore` (a Zustand cache that is the source of truth for the UI) and an IPC round-trip (`projectClient.getSettings` / `saveSettings`) that reconciles disk. `getSettings` returns a fresh, detached copy. Read-modify-write on that copy is unsafe because, across the `await`, a concurrent action can mutate the in-memory store, and the naive path reads a stale detached snapshot and writes it back wholesale — last writer wins, clobbering the other's `fleetSavedScopes` append or stamp. Critically, even the write-through `setSettings(nextSettings)` **after** an awaited save re-introduces the clobber: the awaited gap is a race window where a concurrent recall's stamp may already have landed on the store, so re-setting the whole object overwrites it (hence the explicit `Do NOT call setSettings(nextSettings) here` comment). The fix mirrors `src/store/recipeStore.ts` (`runRecipeWithResults`): fold read+write into one `set((state) => …)` updater that closes over the freshest state, then persist a snapshot from that updated state so any racing contribution survives.

## Lesson

- **Never mutate a fetched settings snapshot and save it back — route the mutation through `useProjectSettingsStore.setState((state) => …)`, which closes over the freshest in-memory state, then persist the object that updater produced.** #10308 replaced both fleet paths with `appendFleetScopeInMemory` / `stampFleetUsageInMemory`, each an atomic functional `setState` that merges into `state.settings.fleetSavedScopes` and captures the merged snapshot for `saveSettings` — the same shape as `recipeStore.ts`'s `set((state) => apply(...))` then `get().recipes.find(...)` persist.
- **The in-memory Zustand store — not the IPC read — is the source of truth; read from it first and hit IPC only to hydrate on cold start.** `findFleetScope` reads `useProjectSettingsStore.getState().settings.fleetSavedScopes` when `store.projectId === projectId`, falling back to `projectClient.getSettings` only when unhydrated — then writing the result back so the subsequent stamp uses the in-memory path. An IPC read used as the mutation base is a stale detached copy by definition.
- **After an awaited persist, do NOT re-`setSettings(wholeObject)` — the awaited gap is a race window and the atomic updater already committed the change.** Re-setting the whole settings object overwrites a concurrent recall's stamp that landed during the await. Only the functional updater is safe; a wholesale replacement is a clobber.
- **Match persist durability to the write's value: fire-and-forget for cheap recency stamps, awaited-with-rollback for structural appends.** `stampFleetUsageInMemory` persists fire-and-forget (`.catch(warn)`) since a lost stamp is invisible and disk reconciles on the next save/switch. `saveNamedFleet` awaits the save and, on failure, rolls the optimistic append back to a captured `previousSettings` — a phantom fleet row the user can't recall after restart is worse than a dropped stamp.
- **This pattern generalizes to any store pairing an in-memory Zustand cache with an IPC disk round-trip** (`recipeStore.ts` is the reference). When you see `await client.getSettings(...)` → mutate → `client.saveSettings(...)`, treat it as a lost-update race regardless of how rare the concurrency looks.

## Applies when

- Touching `fleetActions.ts` `saveNamedFleet` / `recallNamedFleet`, or `findFleetScope` / `appendFleetScopeInMemory` / `stampFleetUsageInMemory`, or any `useProjectSettingsStore` mutation.
- Adding a path that does `await projectClient.getSettings()` → mutate → `saveSettings()` — that read-modify-write is the trap; convert to a functional `setState` updater + snapshot persist.
- Writing frecency / `lastUsedAt` / `usageHistory` stamping for any orderable list (recipes, fleets, presets) — reuse `computeFrecency` and the atomic-append pattern, not a fresh RMW.
- Reviewing anything that calls `setSettings(wholeObject)` (or an equivalent whole-object store replacement) after an `await` — check whether the awaited gap can drop a concurrent write.
- Note the ranking half of #10308 survives (`fleetRanking.ts` + `computeFrecency`), but its extracted `fleetStaleness.ts` (`isSnapshotStale`) was later removed by `24a1c988d` and inlined into `SavedFleetsSection.tsx` as `(countById[scope.id] ?? 0) === 0` — don't grep for `fleetStaleness.ts`.
