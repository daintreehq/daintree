## Context

`WorkspaceService` (workspace-host utility process) discovers worktrees by shelling out to `git worktree list --porcelain` via `WorktreeListService`, maps the output to store entries, and spawns a `WorktreeMonitor` per entry. `deleteWorktree()` runs `git worktree remove <path>` to tear one down from the UI.

## Problem

A worktree deleted outside the app (`rm -rf`, Finder, an agent script) got stuck in the sidebar. Refreshing was a no-op — the phantom entry kept coming back, even across an app restart — and clicking delete failed because `git worktree remove` errored on a path that no longer exists.

## Root cause

Since Git 2.31, `git worktree list --porcelain` does NOT drop a worktree whose directory has been deleted; it keeps reporting the entry with a `prunable`/`prunable <reason>` marker until `git worktree prune` runs. `WorktreeListService` parses that marker into `prunableReason` but `mapToWorktrees` does not filter prunable entries out, so the phantom flows straight into the store and `syncMonitors` re-creates a monitor for the now-missing path — the entry never clears, and survives restart because nothing ever prunes the stale `.git/worktrees/<name>` metadata. On the delete path, `git worktree remove` on a vanished directory fails with `fatal: '<path>' is not a working tree`, so the one explicit recovery action also fails.

## Lesson

For any flow built on `git worktree list --porcelain`, treat `prunable` entries as already-gone, not present:

- Run `git worktree prune` BEFORE listing (in the refresh/discovery path) and at project load, so stale metadata is cleared before it hits the store. `prune` skips locked worktrees, so it is safe on every refresh.
- Make every prune best-effort (`try/catch`, `console.warn`). A prune failure (e.g. EPERM on `.git/worktrees/`) must never block list/load — otherwise you recreate the original "refresh is a no-op" symptom under a different trigger.
- In the delete path, `fs.access(path)` first: route ONLY `ENOENT` to `git worktree prune` (skip the doomed `remove`). Let EPERM/EACCES/ENOTDIR fall through to the normal `remove` so you don't skip cleanup on transient permission errors.
- Guard the `remove` call itself for the access-check race: if it throws and the message includes `is not a working tree`, fall back to prune rather than surfacing the error. This is a different error string than #3033's `not a git repository` — both mean "git already dropped this worktree", and the delete path must accept both.

## Applies when

- Phantom / stale worktree cards that won't clear on refresh or survive an app restart.
- Touching `WorkspaceService.discoverAndSyncWorktrees`, `loadProject`, `deleteWorktree`, or `WorktreeListService.list` / `mapToWorktrees`.
- Any code consuming `git worktree list --porcelain` output that assumes a deleted directory disappears from the list.
- Handling `git worktree remove` failures, or distinguishing "already gone" (ENOENT / `is not a working tree`) from a real removal failure.
- External-deletion detection for worktrees (companion to #3033 error-shape enumeration and #3332 circuit-breaker pre-check, but distinct: this is about list/load prune placement and the prunable marker, not the monitor poll loop).
