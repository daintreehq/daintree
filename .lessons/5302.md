## Context

Each project's renderer talks to its `workspace-host` utility process over a `MessagePort`, brokered through `WorktreePortClient` in `electron/preload.cts`. Requests are fire-a-message-and-await-a-reply with a per-action timeout (default 10s, longer for create/delete via `resolveWorktreePortTimeout`). When the host crashes, every in-flight request would otherwise hang until its individual timeout fired — a ~10s dead UI per request.

## Problem

The renderer needs to learn "the host just died" within milliseconds, not seconds, and it needs to distinguish two cases that look identical at the message layer: (a) the host crashed but will be auto-restarted with a fresh port coming (transient — show a "Reconnecting…" spinner), versus (b) the host exhausted its restart budget and no port will ever arrive (fatal — show a terminal error, not an infinite spinner). A naive "reject pending requests on any disconnect IPC" also clobbers the new port during a normal port replacement (host restart, project switch), because the old port's `close` fires after a replacement has already been attached.

## Root cause

There are two independent disconnect signals and they are deliberately split by reliability and by the information each can carry:

1. **The MessagePort `close` event is the authoritative transient signal.** Electron delivers `port.addEventListener("close", …)` to the renderer end even on `SIGKILL` of the peer utility process, via the Mojo channel underneath — so it arrives in ~10ms with no main-process round-trip. `_handlePortClose` (`preload.cts:398`) closes the port, rejects every pending request via `this.broker.clear(encodeBrokerError(new BrokerError("HOST_EXITED", …)))` (`preload.cts:408`), and fires `disconnectedCallbacks`. This is why the per-request 10s timeout never gets a chance to bite.
2. **The parallel IPC broadcast (`worktree:host-disconnected`) exists only to carry `{ fatal }`** — the one fact the port-close event structurally cannot encode. A port closing tells you "the peer is gone"; it cannot tell you "and the supervisor has given up." Main emits `host-recovering` (fatal:false) on every unexpected exit (`electron/services/WorkspaceHostProcess.ts:597`) and `host-crash` (fatal:true) on fork failure and budget/cap exhaustion (`:532`, `:548`, `:656`). The preload IPC handler (`preload.cts:541`) **ignores the non-fatal broadcast entirely** — the port `close` already covers the transient case — and acts only on `fatal`, calling `_handleFatal` so the UI leaves the reconnecting spinner for a terminal error. Routing the transient case through IPC too would just duplicate the port signal with a slower, main-process-mediated path.
3. **A monotonic `portGeneration` guard prevents a stale `close` from clobbering a fresh port.** `attach` bumps `++this.portGeneration` _before_ `detach()` and captures it in the close listener's closure (`preload.cts:313,326`). `_handlePortClose(generation)` returns early if `generation !== this.portGeneration` (`:399`). Without this, the old port's `close` event — fired during/after the replacement is already wired — would reject the new port's pending requests and fire disconnect callbacks during a perfectly normal restart/switch.

The renderer consumer (`src/contexts/WorktreeStoreContext.tsx:556,567`) maps `onDisconnected` → `setReconnecting(true)` and `onFatalDisconnect` → terminal error; `applySnapshot` clears `isReconnecting` when the replacement port delivers fresh state.

## Lesson

When a renderer awaits replies from a crashable utility-process peer over a MessagePort, do not rely on per-request timeouts to detect host death — subscribe to `port.addEventListener("close")` and reject all pending requests immediately; Electron fires it even on `SIGKILL`. Use a side IPC channel only for information the port-close event cannot carry — here, the single `fatal` bit meaning "restart budget exhausted, no replacement port is coming." Ignore the side channel for anything the port signal already covers; duplicating the transient case through main is slower and invites double-handling. Any consumer that re-attaches ports must guard close handlers with a monotonic generation captured at attach time, so a stale `close` from a replaced port cannot reject the successor's pending requests or fire disconnect callbacks during normal port replacement. Distinguish transient (spinner, port will return) from fatal (terminal error) at the signal level, not by guessing in the UI — an infinite reconnecting spinner is the failure mode when the fatal case has no dedicated signal.

## Applies when

- Editing `WorktreePortClient` in `electron/preload.cts` — `attach`, `detach`, `_handlePortClose`, `_handleFatal`, `portGeneration`, or the `worktree:host-disconnected` IPC handler.
- Adding a new MessagePort-brokered request/response client between a renderer and a utility-process host (workspace-host, pty-host) where the host can crash mid-request.
- Wiring `host-recovering` / `host-crash` broadcasts in `electron/services/WorkspaceHostProcess.ts` and deciding which exits are fatal vs transient.
- Symptom: UI hangs ~10s after a host crash (pending requests waiting on their own timeout), or an indefinite "Reconnecting…" spinner that never resolves because the budget-exhausted/fatal case has no signal.
- Symptom: a normal host restart or project switch spuriously rejects requests on the freshly-attached port — a missing or mis-captured generation guard on the old port's `close` listener.
- Designing dual-signal disconnect detection for any renderer↔utility-process channel: decide which signal is authoritative for "peer gone" (the port) and reserve the slower side channel strictly for metadata the port can't express.
