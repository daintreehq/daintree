## Context

The dock rail (`ContentDock.tsx`) is an ARIA toolbar with a roving tabindex over `[data-dock-item]` chips: one tab stop, Arrow/Home/End move focus. The roving logic was hand-copied from the canonical implementation in `Toolbar.tsx` (per #8170) and is deliberately NOT lifted into a shared hook — the issue rules that out until a fourth use case appears, so every rail carries its own copy. Chips mount and unmount constantly: terminals close, groups collapse, agent-state polling reshapes the rail.

## Problem

Focus a dock chip, have that chip unmount (its terminal evicted), and dock keyboard navigation silently died — arrows and Enter went nowhere. The misleading part: the roving `useLayoutEffect` looked correct. It clamped `activeDockIndexRef`, promoted a surviving chip, and reassigned `tabIndex=0` via `syncDockTabStops` — every attribute was right, yet the keyboard was dead (#9681).

## Root cause

When a focused DOM element unmounts, the browser drops active focus to `document.body` before React's effects run. `tabIndex` attributes only decide where the NEXT Tab press lands; they never move current focus. So after the eviction the tab stop was correctly re-homed but `document.activeElement` was `<body>`, and roving keydown handlers — which fire on the focused chip — had no focused chip to fire from. The fix (mirroring `prevFocusedToolbarItemRef` in `Toolbar.tsx`) records the live focused chip in a focus-capture ref (`prevFocusedDockItemRef`, set in `handleDockFocusCapture`) and, in the layout effect, when that element is no longer in `getDockItems()`, calls `.focus()` on the promoted chip. Two guards are load-bearing: the redirect only runs when `document.activeElement === document.body` — that condition is the discriminator between "focus fell out because of the unmount" and "focus intentionally lives elsewhere"; Radix portal content (tooltip, context menu, popover rendered to `document.body`) holds `activeElement` on the portal node, not body, and an unguarded recovery would hijack it. And the ref is cleared unconditionally BEFORE the body guard — a stale ref left set would fire a phantom focus steal on a later unrelated render.

The dock's copy of the roving pattern had simply dropped this whole recovery branch. It was not the last piece it dropped either: a year of the same rail later, #11156 found that `handleDockKeyDown` also lacked Toolbar's DOM-containment target guard, so arrows typed into a docked terminal (whose body portals through a Radix popover back into the React tree) roved the rail and yanked focus off the terminal mid-type — fixed in #11160 with `scrollContainerRef.current?.contains(e.target)`. Two independent dock focus bugs, both pieces of `Toolbar.tsx` that a copy omitted.

## Lesson

- **Reassigning `tabIndex` is not focus recovery.** Attributes pick the next Tab landing spot; when the focused item unmounts, the browser has already dropped focus to `<body>` and roving keydown handlers are dead. Any roving container with dynamic membership must track the focused item in a focus-capture ref and call `.focus()` on the promoted item when the tracked element leaves the item list.
- **Gate the redirect on `document.activeElement === document.body`.** Body is the signature of "focus fell out from the unmount"; Radix portals hold `activeElement` on the portal node, so an unguarded `.focus()` recovery hijacks open tooltips/menus/popovers. Never reclaim focus the user (or another surface) legitimately owns.
- **Clear the recovery ref unconditionally, before the body guard.** When eviction happens while focus is legitimately elsewhere, skip the redirect but still null the ref — a stale ref triggers a phantom redirect on a later unrelated render.
- **The roving pattern is deliberately duplicated, so copy the WHOLE checklist from `Toolbar.tsx`.** Both dock focus bugs (#9681 here; #11156/#11160 later) were omissions from an incomplete copy. A new roving rail needs: focus-capture ref + eviction recovery + body guard + keydown DOM-containment guard (`container.contains(e.target)` — portaled/bubbled keydowns must not rove the rail) + decorative controls out of the tab order.
- **Conditionally-rendered scroll chevrons are pointer-only, and scrims need scroll-padding.** Overflow chevrons appear/vanish mid-interaction — give them `tabIndex={-1}` + `aria-hidden="true"` (arrow roving + `scrollIntoView` already reach every chip; Material UI `TabScrollButton` precedent). A focused edge chip parking under the gradient scrim is fixed declaratively with `scroll-px-4` on the overflow container (W3C technique C43), not a scroll handler.

## Applies when

- Adding a new roving-tabindex rail/strip/chip-row or copying the toolbar pattern — diff against `Toolbar.tsx`'s complete implementation (focus-capture, recovery, both guards), not just the arrow-key switch.
- Diagnosing "keyboard navigation died" or "focus vanished" after an item disappeared (terminal closed, panel evicted, list reshaped by polling) in `ContentDock.tsx`, `Toolbar.tsx`, or `DockedTabGroup.tsx`.
- Tempted to fix a focus loss purely by rewriting `tabIndex` in an effect — attributes don't move focus; only `.focus()` does.
- Writing any automatic focus-restoration near Radix portals — an unconditional `.focus()` will hijack tooltip/context-menu/popover focus unless gated on `activeElement === document.body`.
- Reviewing changes to `handleDockKeyDown`, `handleDockFocusCapture`, `syncDockTabStops`, `getDockItems` filtering, or their Toolbar equivalents.
