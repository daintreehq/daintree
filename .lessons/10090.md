## Context

GitHub token expiry had three independently-mounted reaction surfaces: a persistent banner, an always-mounted backstop hook writing a durable inbox row for the no-project case via raw `useNotificationHistoryStore.getState().addEntry({ correlationId: "github-token-health", ... })`, and a project-mounted toolbar hook firing `notify({ priority: "high", correlationId: "github:token-expiry", supersedeKey: "github.token" })`. Issue #9961 documented the overlap; #10090 fixed it. The code has since been generalized forge-neutral: the pattern now lives in `src/hooks/useForgeTokenHealth.ts` (`forgeTokenSupersedeKey(providerId)`), the toolbar expiry hook was removed entirely, and `GitHubTokenBanner` became `src/components/Recovery/ForgeTokenBanner.tsx`.

## Problem

One token expiry produced two durable inbox rows with two different titles plus a toast plus the banner — and neither row ever archived the other. Separately, the banner's "Reconnect" button was the only recovery entry point dispatching a raw `daintree:open-settings-tab` CustomEvent without `sectionId`, dropping the user at the top of the Code Forge tab instead of the token field.

## Root cause

The history store dedupes on exactly one thing: `supersedeKey` (or an explicit `supersedes` id). `addEntry` in `src/store/slices/notificationHistorySlice.ts` archives the prior non-archived entry with the same `supersedeKey` atomically in the same `set()` — but it never matches on title or `correlationId`. `correlationId` is a _threading_ key (grouping, snooze, re-toast), not an identity key; per the `notify.ts` doc: "`correlationId` threads conversational entries; `supersedeKey` retires them." The backstop's raw `addEntry` carried only a `correlationId`, so the two writers for the same logical event were invisible to each other.

The non-obvious second half: the obvious fix — add the shared `supersedeKey` to the backstop and keep its `correlationId` — would have introduced a NEW bug. `notify()` evaluates `shouldReToast(type, getEntriesByCorrelationId(correlationId), urgent)` (`src/lib/notificationSeverity.ts`): a thread whose entries are ALL archived returns true (the "un-snooze" case), and `shouldToastThread` then promotes even a `priority: "low"` inbox-only payload into a toast. Once the toolbar path can supersede-archive the backstop's row (which the shared key enables), the backstop's correlationId thread is fully archived — so on the SECOND expiry cycle the backstop re-fires into a dead thread and re-promotes itself into an unwanted toast. The two changes are coupled: sharing the `supersedeKey` armed the re-toast trap that dropping the `correlationId` defuses. The fix routes the backstop through `notify({ type: "warning", priority: "low", supersedeKey: "github.token", countable: false })` with no `correlationId` at all.

## Lesson

- **Every code path that writes a durable row for the same logical event must share one `supersedeKey` and route through `notify()`.** The store dedupes on nothing else — not title, not `correlationId`. A raw `addEntry` beside a keyed `notify()` yields permanent duplicate rows. Today only `notify.ts` and `e2eNotificationBackdoor.ts` call `addEntry` directly; keep it that way (there is no lint ban, only convention).
- **`correlationId` is not an inert grouping tag — it opts the row into thread re-promotion.** `shouldReToast` returns true on severity escalation OR when the thread is fully archived, and that promotes `priority: "low"` payloads into toasts (`shouldToastThread` in `notify.ts`). A row that a peer path routinely archives via supersession must omit `correlationId`, or its second occurrence toasts.
- **When adding dedup between two existing notification paths, audit the re-toast interaction in the same change.** Enabling supersession is what creates the fully-archived thread; a `correlationId` that was harmless before the dedup fix becomes a live toast trigger after it. Ship both or neither.
- **Backstop signals are `priority: "low"` + `countable: false`** — inbox-only, no badge bump, with the persistent banner/toolbar as primary surfaces. The current incarnation (`useForgeTokenHealth`) also emits a `supersedeKey`-shared recovery row ("token validated") so one resolved row remains per expiry/recovery cycle.
- **Recovery entry points route through `actionService.dispatch("app.settings.openTab", ...)`, never a raw `daintree:open-settings-tab` CustomEvent.** #10090 also added `sectionId: "github-token"` to land on the token field; the sectionId itself did not survive the forge generalization (provider settings are now whole plugin-owned subtabs in `ForgeTokenBanner`), but the action-service routing did.

## Applies when

- Adding a second notification writer (backstop, replay-on-mount, cross-window mirror) for an event that already notifies somewhere else — check whether an existing `notify()` carries a `supersedeKey` and share it.
- Reviewing any direct `useNotificationHistoryStore.getState().addEntry(...)` call outside `src/lib/notify.ts` — it bypasses priority routing, rate limits, snooze clearing, and quiet hours, and its rows only supersede if the key is passed explicitly.
- Deciding whether a `notify()` payload should carry `correlationId`, `supersedeKey`, or both — threading vs retiring are independent axes with a coupling: correlationId + routine supersession by a peer = second-cycle re-toast.
- Diagnosing "the same event shows two inbox rows" or "an inbox-only notification suddenly toasted the second time" — grep the writers for mismatched `supersedeKey`s and for a `correlationId` on a superseded row.
- Touching `src/hooks/useForgeTokenHealth.ts`, `forgeTokenSupersedeKey`, `ForgeTokenBanner`, or `shouldReToast`/`shouldToastThread` in `src/lib/notify.ts` / `src/lib/notificationSeverity.ts`.
