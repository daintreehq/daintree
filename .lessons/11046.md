## Context

`SlashCommandService.list()` hardcoded three `agentId === "claude"|"gemini"|"codex"` branches, each re-deriving its own search paths, file parser, and label derivation by hand (issue #11043, triggered by a screenshot of Codex's native `$` picker surfacing Skills/Apps/Plugins that Daintree showed nothing for). #11046 replaced all three with a declarative `completionSources` array on `AgentConfig` (`shared/types/completionSources.ts`) resolved by a generic `CompletionDiscoveryEngine` (`electron/services/completions/`), byte-parity proven against 20 pre-existing tests. #11050 extended the renderer item model, #11051 added Codex Plugins via a new discovery method, and #11056 unified the renderer completion contexts. One arc, keyed here because #11046 set the constraints the other three worked inside.

## Problem

Two traps hid inside "make discovery data instead of code." First, `completionSources.ts` isn't shared by convention only, the renderer reads the live `AgentConfig.completionSources` array at runtime (`HybridInputBar.tsx` calls `getAgentConfig(agentId)?.completionSources` to decide which triggers even open a picker) while Main's engine reads the same array to scan disk. Second, two of the three new Codex `$` capabilities (Apps, Plugins) had zero documented on-disk format; #11043's own research flagged "I couldn't confirm the exact on-disk manifest name/location... don't invent it" for both.

## Root cause

The schema comment states the constraint directly: "MUST stay pure data... No `fs`/`path`, no regexes, no functions." Not stylistic, it's load-bearing: the object crosses the Main/renderer boundary at runtime, so a function or `fs` call embedded in it silently no-ops (or throws) on whichever side didn't expect it, with no compiler error to catch it. Every real filesystem/registry operation lives in `electron/` behind a closed named-parser allow-list (`CompletionParserName = "markdown-frontmatter" | "toml" | "skill-dir" | "codex-plugin-registry"`), referenced from data by string, so "add a source" means "add one reviewed parser," never "add a function to config."

That allow-list design is also why #11051 could add Codex Plugins (cross-referencing `$CODEX_HOME/config.toml`'s enabled `[plugins."name@market"]` tables against manifests under `plugins/cache/*`) without touching `CompletionDiscoveryEngine.compute()`. `CompletionRegistryDiscovery` is structurally identical to `CompletionDirectoryDiscovery` (same `parser`/`derive`/`locations` shape); the engine only special-cases `discovery.method === "static"` and falls through to one shared scan path otherwise, so `method: "registry"` is documentation, not a dispatch branch. Zero-engine-change extension holds only when the new variant narrows structurally into an existing arm.

The second half is a research discipline, not code: before writing the Plugins parser, #11051 confirmed the format against `codex-rs` source (`chat_composer.rs::mention_items`) **and** a live installed Codex (v0.144.1), landing on `config.toml` for the enabled set and `plugins/cache/<marketplace>/<plugin>/<version>/.codex-plugin/plugin.json` for the manifest. Apps got the opposite, equally valid outcome: confirmed to resolve entirely server-side (an MCP server hitting `chatgpt.com/backend-api/wham/apps`), so the deliverable was zero code — `CompletionKind` still carries `"app"` with a comment explaining no discovery method exists, rather than a guessed scan against the wrong path.

## Lesson

- **A `shared/` type isn't just compile-time shared, check who reads it at runtime before adding logic to it.** `completionSources.ts` is read directly by both the renderer (`HybridInputBar.tsx`, no Node APIs) and Main (`CompletionDiscoveryEngine.ts`, full `fs`), so a function or regex placed there breaks or silently no-ops on one side, with no shared type error to flag it.
- **Before adding a variant to a union an engine switches on, check if it narrows structurally into an existing arm first.** `CompletionRegistryDiscovery` reuses `CompletionDirectoryDiscovery`'s exact shape, so the engine never grew a `"registry"` branch. If your variant needs new fields the engine must branch on, you don't get zero-engine-change for free.
- **Wiring a new external CLI's on-disk convention (this repo integrates 15+ agent CLIs) requires confirming the format against BOTH the upstream source AND a live installed instance before writing a parser** — #11051 did this for Codex Plugins (`codex-rs` tag `rust-v0.144.1` plus an actual `~/.codex` install), not from memory of how Codex "probably" works.
- **"Format unconfirmed" is a valid final answer, and the deliverable is no code, not a best-guess parser.** Codex Apps got a documented `CompletionKind` member and a comment, never a directory scan — a scan against a guessed path returns nothing (or scans the wrong thing) silently, and nobody notices until a user reports the feature missing.
- Companion #11056 fixed a related trap: a single global `isResultsStale` boolean dimmed the _entire_ menu whenever the debounced `@file` search lagged, even with fresh `$`/static `/` items present; now `staleKeys: ReadonlySet<string>` keyed by `item.key`, so only the genuinely stale provider's rows dim. Any list composed from providers with different freshness semantics needs per-item, not per-menu, staleness.

## Applies when

- Adding a new completion source, agent, or discovery method to `shared/config/agents/*.ts` / `shared/types/completionSources.ts` / `electron/services/completions/`.
- Touching any `shared/` file imported by both `src/` and `electron/` — verify it stays free of functions, regex literals, and Node built-ins; the constraint is convention, not the type system.
- Wiring a new external agent CLI's config/plugin/skill format — replicate the "source + live install, or no code" gate from #11049/#11051 instead of guessing from memory.
- Reviewing a PR that adds a tagged variant to an engine-dispatched union — confirm whether it truly needs a new engine branch or reuses an existing arm.
- Diagnosing an autocomplete/search UI where unrelated, already-resolved items dim whenever one async provider is slow — look for a single global stale/loading boolean instead of per-item tracking.
