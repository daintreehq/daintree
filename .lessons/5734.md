## Context

Daintree broadcasts main→renderer events (agent state, worktree updates, terminal exit/spawn-result, window/system signals, plugin changes) over IPC, and the count keeps growing. PR #5734 collapsed 18 dedicated `ipcMain`/`ipcRenderer` channels onto a single multiplexed envelope channel `CHANNELS.EVENTS_PUSH` (`{ name, payload }`), removing ~20 channel constants from `electron/ipc/channels.ts` and its preload mirror. The renderer subscribes via `window.electron.events.on(name, cb)` plus migrated per-domain helpers (`terminal.onExit`, `window.onFullscreenChange`, `system.onWake`, …) in `electron/preload.cts`.

## Problem

The obvious migration — have each `*.on*` preload helper call `ipcRenderer.on(CHANNELS.EVENTS_PUSH, …)` with its own handler that filters by `envelope.name` — is wrong twice over. First, every subscriber adds a real listener to the same channel, so Node trips `MaxListenersExceededWarning` at 10 listeners; with 18+ events and multiple React subscribers per event you blow past it immediately. Second, events have two different delivery origins, and conflating them either duplicates or drops renderer delivery: some are emitted on the main-side `TypedEventBus` (`events.emit`) and need a bridge to relay them, while window-scoped ones (`worktree:update`, `terminal:backend-crashed`, `window:*`) are sent directly to a specific window's `webContents` to preserve per-window routing — relaying those again would double-deliver.

## Root cause

A multiplexed channel changes the listener-fan-out math: N logical event types times M subscribers all land on ONE physical channel, so the per-channel listener cap and the relay topology must be managed centrally, not per-helper.

## Lesson

Wire exactly ONE `ipcRenderer.on(CHANNELS.EVENTS_PUSH, …)` (`_ensureEventBusWired` in `electron/preload.cts`) and fan out in userland through a ref-counted `Map<keyof IpcEventBusMap, Set<callback>>` (`_eventBusSubscribers` / `_eventBusOn`); the physical listener stays at 1 regardless of subscriber count. Snapshot the Set (`[...subs]`) before dispatch — a subscriber may unsubscribe itself or a sibling mid-dispatch, and iterating the live Set would make delivery order-dependent — and wrap each callback in try/catch so one thrower can't starve the rest. On the main side, classify every event in `EVENT_BUS_BRIDGED_MANIFEST` (`electron/ipc/handlers/events.ts`) as `"bus"` (relayed by the bridge loop from `TypedEventBus`) or `"external"` (producer sends the envelope itself via `sendToRenderer`/`broadcastToRenderer`); the bridge loop relays ONLY `"bus"` entries so `"external"` events aren't double-emitted. Enforce both maps with `satisfies Record<keyof IpcEventBusMap, "bus" | "external">` so adding an `IpcEventBusMap` key without classifying it is a tsc failure — the type is the lockstep enforcement, not a comment. Keep high-frequency/binary channels (`terminal:data`, `terminal:resource-metrics`, `logs:batch`) OFF the bus — the envelope/JSON overhead isn't worth it for hot paths.

## Applies when

Adding a new main→renderer broadcast event (decide bus vs external, classify it in the manifest, never add a second `ipcRenderer.on` on `events:push`), debugging duplicate or missing renderer event delivery, chasing a `MaxListenersExceededWarning` on an IPC channel, or migrating another dedicated channel onto the multiplexed envelope.
