## Context

The renderer is bundled by Rolldown (Vite 8). `vite.config.ts:600-602` enables the experimental `lazyBarrel: true` optimization, which is supposed to prune unused re-exports from barrel files (`index.ts` that re-export a directory) so that importing one symbol from a barrel doesn't drag the whole directory into the eager startup graph. A byte-budget gate (`scripts/check-renderer-import-budget.mjs`) tracks the eager-import closure walked from `src/main.tsx`.

## Problem

`lazyBarrel` was already enabled but doing nothing. Barrels like `src/hooks` were being pulled into the eager startup graph in full — every re-exported module loaded eagerly even when only one symbol was used. Eager gzip was ~887KB / raw ~2.96MB. The regression was invisible because nothing gated the eager byte total.

## Root cause

Two-part coupling that is easy to miss:

1. **Tree-shaking conservatism without `sideEffects`.** With no `sideEffects` field in `package.json`, Rolldown (like Rollup) must treat _every_ module as potentially side-effectful. A barrel re-export can therefore never be dropped — pruning a re-export might skip a module whose mere evaluation has an observable effect. So `lazyBarrel` had nothing it was allowed to prune. Enabling the optimization in `vite.config.ts` is necessary but not sufficient; the bundler also needs `package.json` to declare which modules are pure.

2. **No byte gate.** The existing budget script gated eager _chunk count_, but `lazyBarrel`'s payoff is parse/eval cost (bytes), not chunk count — chunk count can even _rise_ (44→61 here) while bytes fall. A count-only ratchet would let bytes silently regress.

The fix adds a `sideEffects` allowlist (`package.json:7-16`) — `**/*.css` plus the handful of modules that _do_ have module-level side effects (e.g. `src/clients/terminalClient.ts` registers a `window` `'message'` PTY MessagePort handshake at import time and is reachable only via a barrel, so dropping it would break the handshake). Everything not listed is declared pure and becomes prunable. It also adds an independent `eagerGzip`/`eagerRaw` byte gate (`BYTE_GROWTH_THRESHOLD = 0.05`) so the win can't silently regress. Result: eager gzip 887KB→844KB (-4.9%).

## Lesson

- Enabling a tree-shaking / barrel-pruning optimization in the bundler config does **nothing** until `package.json` declares `sideEffects`. The two must ship together. If you turn on `lazyBarrel` (or any Rolldown/Rollup pruning) and see no byte reduction, the missing `sideEffects` field is the first suspect.
- The `sideEffects` field is an **allowlist of impure modules** (false = no side effects anywhere; an array = these paths have side effects, prune everything else). Get this wrong in the _exclusion_ direction and you silently drop a module whose import-time effect was load-bearing. Audit any module reachable only through a barrel for module-level work: `window`/`document` event registration, MessagePort handshakes, self-registering stores, polyfill installs (`trustedTypesPolicy`), font config. Those must be listed in `sideEffects` or imported directly (not via barrel).
- Gate the actual payoff metric. `lazyBarrel` saves bytes, not chunk count, so gate eager gzip/raw bytes independently of chunk count — see the eager-closure walk in `scripts/check-renderer-import-budget.mjs` (`collectEagerChunks` walks `imports[]` but deliberately NOT `dynamicImports[]`). A chunk-count-only budget gives false safety.

## Applies when

- Editing `package.json` `sideEffects`, or adding/removing modules from it.
- Touching `vite.config.ts` Rolldown `experimental` options (`lazyBarrel`) or `treeshake` config.
- Adding a new barrel file (`index.ts` re-exporting a directory) under `src/`, or importing from `@/hooks`, `@/clients`, `@/components/icons`, or any other barrel and worrying about eager startup cost.
- Adding a module with a module-level (import-time) side effect — `window`/`document` listeners, MessagePort handshakes, store self-registration, polyfill installation — especially when that module is only reachable through a barrel.
- Investigating why a tree-shaking/dead-code optimization produced no measurable bundle reduction.
- Working on `scripts/check-renderer-import-budget.mjs`, the `renderer-import-baseline.json` / `first-render-chunk-baseline.json` baselines, or startup eager-import-budget regressions.
