## Context

`usePanelStore` (`src/store/slices/terminalFocusSlice.ts`) holds `maximizedId` / `maximizeTarget` / `preMaximizeLayout` as flat, singular fields — "which panel/group is maximized right now." `ContentGrid.tsx` renders the grid from worktree-scoped inputs (`ctx.gridTerminals`, `ctx.maximizedGroup`), and `worktreeStore.ts` already had one precedent for a per-worktree shadow map, `lastFocusedTerminalByWorktree`, used to restore terminal focus across a switch.

## Problem

Maximize a panel in worktree A (Cmd+1 or the maximize toggle), switch to worktree B, and the grid renders blank — not B's panels, not an empty state, nothing. Switch back to A and the maximize is gone too. Nothing crashed and no error logged, which made it look like a grid-layout or panel-visibility bug rather than a state-scoping one (filed as #11183).

## Root cause

`ContentGrid`'s maximize branch guards only on `ctx.maximizedId && ctx.maximizeTarget` — both fields being non-null — with no worktree check, because the fields were never worktree-tagged in the first place. Since they're global, the guard is true in every worktree once any worktree has maximized something. In worktree B, the lookup (`gridTerminals.find` or the tab-group lookup for `maximizeTarget.type === "group"`) misses because A's panel isn't in B's grid, and the branch falls through to `return null` — the blank grid.

The reason nothing self-healed on switch is that the existing repair path, `validateMaximizeTarget`, only clears the trio when the maximized panel **no longer exists anywhere** (checked via `getPanelGroup`/`getTerminal` callbacks). A panel that moved out of view by virtue of a _worktree switch_ still exists in the global `panelsById` — it just belongs to a worktree that isn't active. Existence-only validation is blind to scope, so the stale pointer survived indefinitely. `setActiveWorktree` reset its own worktree-store fields on switch but never touched the panel-store maximize trio, because nothing had ever needed it to.

## Lesson

- **A pointer into worktree-scoped data must itself carry a worktree dimension, or it will eventually be read against the wrong worktree's data.** The fix added `maximizeByWorktree: Map<string, WorktreeMaximizeSnapshot>` to `worktreeStore.ts`, following the `lastFocusedTerminalByWorktree` precedent — check any new flat/global field for whether the data it names is actually worktree-scoped before assuming a singleton is fine.
- **"Does it still exist" is not the same invariant as "is it still valid in this scope."** `validateMaximizeTarget` correctly detects deletion but has no way to detect scope drift, since existence is checked with no worktree parameter. When adding a scoped shadow map, add a scope-aware resolver (`resolveMaximizeForWorktree`) rather than trusting the existing existence-only validator to cover the new case.
- **Validate before writing, not after painting.** `validateMaximizeTarget` runs from a render effect — already too late to stop one blank frame. The restore path in `prepareWorktreeMaximizeSwap` validates the stashed snapshot against the incoming worktree's `panelsById`/`tabGroups` _before_ it ever reaches the panel store, so a stale target is caught pre-write instead of repaired post-render.
- **A half-written multi-field pointer is its own bug class — write the whole tuple atomically or not at all.** `maximizedId`/`maximizeTarget`/`preMaximizeLayout` were previously de-synced by #9935 (PR #10115: trashing a maximized panel cleared `maximizedId` but left `maximizeTarget` stranded, so the next maximize toggle silently no-op'd as an unmaximize). #11184 repeats the same three-field group and treats every read/write as one atomic patch (`CLEARED_MAXIMIZE`, `WorktreeMaximizeSnapshot`) precisely to not reintroduce that class.
- **A "reveal this panel" focus promotion and a "restore prior view" worktree switch are different operations that share a code path — don't let one silently break the other.** `prepareWorktreeMaximizeSwap` takes a `source: "user" | "focus"` distinction: a `"focus"` promotion (quick switcher, `HelpPanel`, `useTypeAnywhere`, panel spawning) means "make this panel visible," so a stashed maximize that would bury the just-focused panel is dropped instead of restored, while a plain worktree switch restores it unconditionally.
- **A scoping fix needs its own scope-crossing e2e regression, not just unit tests.** The 254-test unit suite covers stale/moved/docked/trashed targets, but the blank-grid symptom itself was only proven fixed via `e2e/full/worktree/core-worktree-cross-boundary.spec.ts`, validated red-before-green against a literal zero-panel grid with the fix reverted.

## Applies when

- Adding a new flat/singular field to `usePanelStore` or any per-project-view store and the data it names (a panel, a group, a terminal) is worktree-scoped — ask whether the field needs a `*ByWorktree` shadow map like `maximizeByWorktree` or `lastFocusedTerminalByWorktree` before it ships.
- Diagnosing a blank/empty grid, panel, or view that appears only after switching worktrees (or projects) and clears or reappears on switching back — suspect a global pointer being read against scoped data, not a rendering bug.
- Touching `ContentGrid.tsx`'s maximize branch, `terminalFocusSlice.ts`'s `maximizedId`/`maximizeTarget`/`preMaximizeLayout`, or `worktreeStore.ts`'s `setActiveWorktree`/`selectWorktree`/`exitFleetScope` switch sites.
- Writing or reviewing any multi-field pointer/snapshot pair — check it is always read and written as one atomic unit, per the #9935 stale-target bug class this PR deliberately avoids repeating.
- Extending fleet-scope handling (`enterFleetScope`/`exitFleetScope`) — `activeWorktreeId` can move mid-scope via focus promotion, so any per-worktree shadow state must be reconciled on exit, not assumed stable across the scope's lifetime.
