## Context

`WorkspaceService.createWorktree` (`electron/workspace-host/WorkspaceService.ts`) spins up a worktree and must install a `WorktreeMonitor` for it before emitting `create-worktree-result`. The pre-#5165 path did this by re-running `git worktree list --porcelain` (`listService.list({ forceRefresh: true })`) to rediscover the new worktree, then calling `syncMonitors(worktreeList, ...)` to install its monitor.

## Problem

Two compounding costs under bulk creation (the GitHub "create N worktrees" flow). First, every single create shelled out a full `git worktree list` over the whole repo — O(N) per create, O(N²) across a batch of N. Second, and worse: the obvious "minimal" fix — call `syncMonitors([createdWorktree], ...)` with just the new worktree — would have silently removed every other non-main monitor and fired a `worktree-removed` event for each, because `syncMonitors` treats its array as the authoritative set. Bulk-creating 30 worktrees would converge to "main + last-created".

## Root cause

`syncMonitors` (`WorkspaceService.ts:507`) is a full reconcile, not an upsert. Its remove-stale loop builds `currentIds = new Set(worktrees.map((wt) => wt.id))` and stops + deletes + emits `worktree-removed` for any monitor whose id is absent (`WorkspaceService.ts:557-586`). It is correct only when passed the complete, authoritative worktree list. Handing it a one-element array is interpreted as "these are the only worktrees that exist now" — so it prunes all the others. The per-create `git worktree list` existed only to feed this reconcile a complete array, which is what made it O(N²).

## Lesson

Split single-worktree registration out of the reconcile. `#5165` added `addNewWorktreeMonitor(wt, isActive, skipInitialGitStatus)` (`WorkspaceService.ts:798`) — an add-only path that touches no other monitor and no-ops if `this.monitors.has(wt.id)` (race safety for overlapping create/delete). `createWorktree` calls it directly (`WorkspaceService.ts:1919`) and never reconciles.

Two non-obvious invariants ride on this:

- **Build the `Worktree` object from known inputs, don't re-list.** A freshly-created, attached, non-main worktree has fully derivable fields (`id`/`path`/`name`/`branch` from args, `isDetached:false`, `isCurrent`/`isMainWorktree:false`, `gitDir` from `getGitDir`), matching `WorktreeListService.mapToWorktrees` output (`WorkspaceService.ts:1890-1904`). This kills the per-create list entirely. The cache is still invalidated (`listService.invalidateCache`) in the fire-and-forget tail so a racing `list()` doesn't return a stale snapshot.
- **The add-only path must still EMIT a snapshot, or the worktree never appears.** The renderer's worktree store only grows on `worktree-update` events. `monitor.start()` emits that via `updateGitStatus`; the perf-optimized `startWithoutGitStatus()` (`WorktreeMonitor.ts`, fresh worktrees are clean by definition) must replicate that contract minus the git call — it sets `_hasInitialStatus = true`, calls `emitUpdate()`, then `scheduleNextPoll()`. Skip the emit and the new worktree stays invisible in the UI until the next poll/watcher fire.

Registration is synchronous before the success event so any caller doing `this.monitors.get(worktreeId)` right after `create-worktree-result` finds a live monitor.

## Applies when

- Adding/installing a monitor for a single worktree (create, restore, import) — use `addNewWorktreeMonitor`, NEVER `syncMonitors([...])` with a partial array; the latter prunes every monitor not in the array.
- Symptom: bulk-creating worktrees converges to "main + last-created", or spurious `worktree-removed` events fire during creation.
- Replacing a `git worktree list --porcelain` call inside a per-item loop — for a just-created attached worktree you can construct the `Worktree` from inputs instead (match `mapToWorktrees` field shape) and invalidate the list cache for racing readers.
- Adding a "skip the expensive git status" fast path to monitor startup — it must still `emitUpdate()` and `scheduleNextPoll()`, because the renderer store only adds worktrees on `worktree-update` and only stays current via polling.
