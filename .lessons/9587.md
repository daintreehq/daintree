## Context

Since #3508 the renderer has a visibility-aware timer family: `useGlobalMinuteTicker` (ref-counted 30s singleton driving relative-time labels) and `useVisibilityAwareInterval(cb, intervalMs, enabled)` (per-component, for genuine per-second fidelity; it replaced the removed always-on `useGlobalSecondTicker`). #9587 swept three bare `setInterval` sites that had escaped the pattern — `SidebarContent`'s 1Hz "Reconnecting… last updated X ago" tick, `TerminalInfoDialog`'s 250ms BSU/ESU sync-mode poll, `NotificationCenter`'s minute-aligned quiet-hours tick — and sibling #9585 migrated the three settings audit-log viewers off hand-rolled 30s timestamp refreshers onto `useGlobalMinuteTicker`.

## Problem

Relative-time labels and polled state silently went stale whenever the owning renderer was hidden, then stayed wrong for up to a full interval after it became visible again. Nothing errors and every dev test passes, because the timer works perfectly while you're looking at it — the degradation only exists in views you are not watching, which is exactly where "last updated X ago" copy matters most.

## Root cause

Chromium's intensive wake-up throttling batches a hidden page's timers to one wake-up per minute once timer nesting level reaches 5, and since Chrome 108's "quick intensive throttling" that starts after only ~10 seconds hidden (down from 5 minutes). A `setInterval` crosses nesting level 5 after five firings, so any fast interval qualifies within seconds of hiding; the PR verified ~1/min on Chromium 146 (current pin: 148). The Daintree amplifier: hidden is the common case, not the minimized-window edge case — `ProjectViewLifecycleController` parks every non-active project view with `setVisible(false)` (making `document.hidden === true` inside that renderer) and additionally applies a per-renderer CDP CPU throttle (`Emulation.setCPUThrottlingRate`, rate 4, via `electron/utils/webContentsLifecycle.ts`), with Chromium free to freeze the renderer entirely after ~5 min hidden. A multi-project session runs most of its renderers in the throttled regime continuously.

The tempting escape hatches are structurally banned. `WebContents.setBackgroundThrottling(false)` is window-wide since Electron 28 — it silently un-throttles every cached sibling view (#8599) — and the `disable-background-timer-throttling` / `disable-renderer-backgrounding` switches make the CDP freeze/throttle machinery silently no-op (#4683; audit note in `webContentsLifecycle.ts`). Renderer code must tolerate throttling, not fight it: pause while hidden, snap to wall-clock truth on reveal.

## Lesson

- **Never write a bare `setInterval` in renderer components.** Pick from the family: `useGlobalMinuteTicker` for relative-time labels, `useVisibilityAwareInterval(cb, ms, enabled)` for per-second/fast per-component ticks scoped to mount + `enabled`, `usePollingLifecycle` for data fetches needing reactivate/scheduled/manual reason semantics. Don't resurrect an always-on global second ticker — it was deliberately removed.
- **Snap-tick on restore is the load-bearing half of the pattern.** Pausing alone leaves the UI wrong for up to one full interval after project switch-back; both hooks fire the callback immediately on `visibilitychange` → visible. Hand-rolled minute-aligned schedules (`NotificationCenter`) must `clearAll()` and reschedule inside the visibility handler because the boundary alignment computed while hidden is stale.
- **A refresh interval is data cadence, not animation timing — never route it through `getUiAnimationDuration`/`getPerformanceModeFloor`** (`src/lib/animationUtils.ts`). Performance mode collapses durations toward 0, which turns a poll into a hot loop or breaks it outright instead of pausing it; issue #9583 calls this out explicitly.
- **Never "fix" a stale background timer by disabling throttling.** `setBackgroundThrottling(false)` is window-wide in Electron 28+ and un-throttles all cached sibling `WebContentsView`s (#8599); the global Chromium switches no-op the per-view CDP freeze (#4683). If a timer must be correct while hidden, it belongs in main or a utility process, not the renderer.
- **When migrating onto a shared ticker, derive every "now" from the tick.** #9585 found `McpAuditLogViewer`'s one-hour anomaly cutoff computed from a free-variable `Date.now()`, stale by up to 30s relative to the ticker; the sanctioned shape is `const tick = useGlobalMinuteTicker(); const now = useMemo(() => { void tick; return Date.now(); }, [tick])`.
- **The pattern decays — lock it in with source-pattern tests.** `SidebarContent.reconnecting.test.ts` and `AuditLogViewers.globalTicker.test.ts` regex-assert the hook wiring and ban bare-`setInterval` reintroduction (modeled on the freshness test now at `ForgeStatsToolbarButton.freshness.test.ts` after the forge-neutral rename). Extend one when adding a tick site.

## Applies when

- Adding any `setInterval`, poll, countdown, or relative-time ("X ago") refresh to renderer components — anything under `src/` that runs inside a per-project `WebContentsView`.
- Diagnosing labels or polled state stale right after switching back to a project, self-correcting within a minute — that signature is throttled timers, not a data bug.
- Tempted to add `backgroundThrottling: false`, `disable-background-timer-throttling`, or `disable-renderer-backgrounding` to make a background timer keep firing.
- Wiring any interval duration through performance-mode helpers in `src/lib/animationUtils.ts` — refresh cadence must not be collapsible to 0.
- Touching `useVisibilityAwareInterval`, `useGlobalMinuteTicker`, `NotificationCenter` quiet-hours scheduling, or the audit-log viewers — `document.hidden` is transiently true during view swaps, so it may gate tick scheduling but never async-result commits (#6316).
