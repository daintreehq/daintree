## Context

Dock chips come in two mirror variants — the single-terminal pill (`DockedTerminalItem.tsx`) and the grouped tab pill (`DockedTabGroup.tsx`) — and both visually recede when their terminal(s) are deprioritized (agent state `idle` / `completed` / `exited`, or no agent state) so active work stands out. The original treatment was `isDeprioritized && "opacity-50"` on the whole chip button. Issue #9683 flagged it; #9691 fixed the single chip.

## Problem

Deprioritized chips looked "dimmed" as intended, but the text was nearly unreadable — and the chip is a live control (click opens the preview popover, double-click moves to grid, drag reorders), not a disabled one. Each individual class looked fine in isolation: `opacity-50` is the idiomatic Tailwind dim, and `text-daintree-text/70` is the chip's normal text token. The failure only exists in their product.

## Root cause

CSS `opacity` composites the entire subtree at the element's alpha, so it multiplies with every descendant's own reduced alpha rather than replacing it. The chip's base text runs at `text-daintree-text/70` and its command text at `/50`, so container `opacity-50` yields ~0.35 and ~0.25 effective text alpha — a likely WCAG AA failure on an interactive control. The per-state status glyphs (working/waiting/idle/completed/exited each have a distinct muted color) got double-dimmed the same way, eroding the state signaling the dock exists to provide. The trap is that `opacity-50` reads as idiomatic because `disabled:opacity-50` is the standard treatment in `src/components/ui/button.tsx` et al. — but that idiom is for dead hit targets; a deprioritized-but-clickable control needs de-emphasis that leaves interaction affordances intact. Bonus hazard: `opacity < 1` creates a stacking context, which can silently reorder z-layering of chip internals (called out when the group variant was fixed in `8153597dc`).

The fix is per-property token overrides — `isDeprioritized && "text-daintree-text/40 border-[var(--dock-item-border)]/50"` — dimming exactly text and border while background fill, icon color, hit target, and glyph colors stay intact. #9691 only fixed the single chip; `DockedTabGroup` kept `opacity-50` for two more days until `8153597dc` unified them and extracted the shared recede predicate `isDockAgentStateDeprioritized` / `isGroupDeprioritized` into `useDockBlockedState.ts` so the two variants "dim under identical conditions and cannot drift apart" (comment in the file). The other half of #9691 — a reveal-on-hover `SquareArrowOutUpRight` pop-out button on the chip — was removed the same day (`90abb32a1`, from both chip and tab group); double-click plus the context menu is the sole move-to-grid gesture today.

## Lesson

- **Never de-emphasize a live control with container `opacity`** — the alpha multiplies through the subtree, so any descendant already on a `/NN` token drops below its designed contrast (0.5 × `/70` = 0.35 effective). Dim per-property instead: text token alpha + border alpha, leaving background, icons, and hit target untouched.
- **`opacity-50` is the disabled idiom, not the deprioritized idiom.** Reserve whole-element opacity for controls with dead hit targets (`disabled:opacity-50`); anything still clickable gets token-level de-emphasis. Also remember `opacity < 1` creates a stacking context — a z-order side effect nobody audits for.
- **Mirror-variant surfaces must share BOTH the predicate and the treatment.** Single chip and tab group computed "deprioritized" and styled it independently, and drifted for two days. The predicate now lives once in `useDockBlockedState.ts` (`isDockAgentStateDeprioritized`, `isGroupDeprioritized`); the class string is still duplicated at `DockedTerminalItem.tsx:357` and `DockedTabGroup.tsx:619` — changing the dim treatment means changing both, and a parity test covers the predicate side.
- **Do not resurrect the hover pop-out button from #9691's diff.** It was reversed same-day in `90abb32a1`; the current, intended gesture set is double-click (via `handleMoveToGrid`) + right-click context menu. A PR diff is not evidence of current behavior — check the file.
- **The pre-#9691 test file was the extreme tautology case**: it `readFileSync`'d the component source and asserted substrings like `toContain("onClick={")` — asserting the source contains itself. #9691 replaced it with a render-harness behavioral test (mocked stores, `fireEvent`), the pattern the CI "no tautological assertions" rule mandates.

## Applies when

- Adding or reviewing any dimmed / deprioritized / receded / "quiet" visual state on an element that remains clickable — dock chips, sidebar rows, panes, list items.
- Reaching for `opacity-*` (or `disabled:opacity-*` copied onto a non-disabled state) on a container whose descendants use Tailwind `/NN` alpha color tokens.
- Touching dock chip styling or the recede logic in `DockedTerminalItem.tsx`, `DockedTabGroup.tsx`, or `useDockBlockedState.ts`.
- Diagnosing a contrast/readability complaint where every individual class looks correct — check for multiplied alphas across the ancestor chain.
- Reading #9691 (or #9683) and assuming the dock chips have a visible move-to-grid button.
