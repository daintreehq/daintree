## Context

The cast replay harness (`electron/services/__tests__/replay/castReplayHarness.ts`) regression-guards agent-state detection by replaying asciinema `.cast` recordings through a real `@xterm/headless` terminal and the real `ActivityMonitor`, asserting the exact transition sequence against `*.expected.json` fixtures. Production builds every agent monitor's options via one function — `buildActivityMonitorOptions` (`electron/services/pty/terminalActivityPatterns.ts`) — the single source of truth for `simpleOutputState`, the debounce floors, and the accessors `TerminalProcess` wires.

## Problem

The suite was green while the path it guarded was the wrong one. The harness hardcoded `simpleOutputState: false`, `idleDebounceMs: 6000`, and `promptFastPathMinQuietMs: 6000`, never wired the cell-based `getVisibleContentSnapshot`, and silently discarded OSC 9;4 progress sequences. Every production agent monitor runs `simpleOutputState: true` with an 8000ms floor. So all eight `.expected.json` fixtures were calibrated against a code path production never executes — and a change to the path production _does_ run could not fail any replay test.

## Root cause

`ActivityMonitor`'s constructor derives `simpleOutputState = options?.simpleOutputState ?? options?.agentId !== undefined` and `IDLE_DEBOUNCE_MS = idleDebounceMs ?? (simpleOutputState ? 8000 : 4000)` (`ActivityMonitor.ts:313-314`); `buildActivityMonitorOptions` sets `simpleOutputState: effectiveAgentId !== undefined`, so every agent gets `true` + an 8000ms floor. By overriding all three knobs to legacy values the harness exercised the _non_-`simpleOutputState` branch — and since `simpleOutputState` short-circuits the pattern/prompt detection paths, the fixtures validated transitions that never fire for real agents. Two accessors were also missing: the cell-snapshot path (`AgentActivityTemperature`) fell back to text-only because `getVisibleContentSnapshot` wasn't passed, and OSC 9;4 heartbeats — which Claude Code emits constantly (#8701) to hold an agent "busy" while the viewport is quiet — were dropped. Production feeds every raw PTY chunk to an `Osc94Parser` _upstream_ of `activityMonitor.onData()` (`TerminalProcess.ts:1649`), routing working/idle into `onOscProgressWorking`/`onOscProgressIdle`.

The divergence had a downstream cost: a parallel fix PR (#10306) built on the stale calibration was abandoned after #10301 rewrote the same files with the opposite calibration. #10312 is the fresh rework — it inherits production config, wires `Unicode11Addon` (before any write, #7403), the cell snapshot, and the `Osc94Parser` feed-before-onData, then recalibrates all eight fixtures against the real path.

## Lesson

- **A harness that pins its own copy of production config tests a path production never runs — derive options from the production builder, don't re-declare them.** The fix replaced the three literal pins with `opts.X ?? baseOptions.X` where `baseOptions = buildActivityMonitorOptions(agentId, {...})`. When a harness constructs a production object (monitor, service, parser), have it _inherit_ config from the builder production uses; a hand-supplied config silently forks the code path under test.
- **Per-fixture overrides are fine; harness-wide overrides are the trap.** Keeping `opts.idleDebounceMs ?? baseOptions.idleDebounceMs` lets a single fixture pin a knob via its `.expected.json` (aider/goose still pin 6000ms), but the _default_ is the production path — make it the path users run and force every override to be explicit per fixture.
- **When production routes an input through a parser upstream of the monitor, the harness must too — else the input is invisible.** OSC 9;4 heartbeats never reach `onData`; they only affect state via `Osc94Parser.feed(data, now)` → `onOscProgressWorking`. Likewise any accessor production wires (`getVisibleContentSnapshot`, `Unicode11Addon` widths) must be wired, or the branch stays on a fallback no fixture exercises.
- **Prove a wiring is load-bearing with a differential assertion, not an absolute timestamp.** The new OSC 9;4 test replays the same cast twice (`routeOsc94` true vs false) and asserts the idle-deadline delta `>= 2500ms` (routed ~9.5s vs unrouted ~6.4s): absent routing collapses the delta to 0 and fails, while a generous floor survives fake-timer jitter. Pair it with an upper bound (`<= 12000ms`) so a runaway `resetDebounceTimer` loop fails cleanly instead of blowing the settle budget.

## Applies when

- Touching `castReplayHarness.ts`, the `ActivityMonitor.replay.test.ts` suite, or any `activity-monitor` `.expected.json` fixture — verify options flow from `buildActivityMonitorOptions`, not local literals.
- Writing or reviewing any test harness that instantiates a production object with hand-supplied config — check whether production derives that config from a builder the harness bypasses; a green suite guarding a forked branch is the failure mode.
- Adding a new agent-state detection branch (`simpleOutputState`, cell-snapshot temperature, OSC 9;4 progress) and expecting the replay suite to guard it — confirm the harness wires the accessor/parser production uses.
- Diagnosing "replay tests pass but the real path regressed," or fixtures whose asserted timestamps don't match a manual replay under production options.
- Proving an input-routing wiring is load-bearing under fake timers — use a two-run differential assertion with a jitter-tolerant floor plus an upper bound.
