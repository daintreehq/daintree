## Context

The graceful-shutdown chain — agent session journaling, the DB WAL checkpoint/backup, audit-ring flushes, subprocess teardown, telemetry close — lived entirely inside the `app.on("before-quit")` listener in `electron/lifecycle/shutdown.ts`. `AutoUpdaterService.ts` calls `autoUpdater.quitAndInstall()` to install a staged update. #11129 (companion #11141 in the same arc) fixes issue #11104.

## Problem

Installing an update on macOS silently skipped the entire shutdown chain — no crash, no error, just lost agent-session journal and DB state on every update install. It was well hidden: `AutoUpdaterService` already hand-copied three clean-exit markers (`cleanupOnExit`, `markCleanExit`, `markCleanLaunch`, added for #9638) in two separate call sites, so a post-mortem looking for "did we mark clean exit" found yes — while everything else the real chain does (WAL checkpoint, journaling, audit flush) was simply never run.

## Root cause

`autoUpdater.quitAndInstall()` on macOS reaches native Squirrel.Mac, which **closes every BrowserWindow first and only then calls `app.quit()`**. Electron's own docs confirm `before-quit` "is not emitted before all windows are closed" for this path — so the listener that owned 100% of the graceful-shutdown chain never fires for an update install. `before-quit-for-update` looks like the obvious substitute hook, but its listener signature is `() => void`: no `Event` argument, so no `preventDefault()`, nothing to gate anything on from inside that handler. There is no event to intercept on the way out — the only place left to gate is the call site of `quitAndInstall()` itself, before it's invoked, which is a structural constraint of the platform API, not a code-quality gap.

The fix extracts the chain into `runShutdownChain()` and registers it with a new leaf module, `electron/lifecycle/shutdownCoordinator.ts`, via `setShutdownRunner()`. Both the `before-quit` listener and `AutoUpdaterService.startQuitAndInstall()` now call `startShutdown()` / `requestGracefulShutdownForUpdate()`, which run the identical chain and track a `phase` of `"cleaning"` → `"handoff"`. `before-quit` `preventDefault()`s while `phase === "cleaning"` (a Cmd+Q must not tear the process down mid-chain) but lets the quit through once handed off, because on the update path that later quit **is** Squirrel's own post-install `app.quit()` — blocking it would strand every install behind the 5s force-exit watchdog. The phase flips to `"handoff"` synchronously with the chain settling, in the same tick as the terminal action, so no deferred tick (the old `setImmediate` around `quitAndInstall()` was deleted for this) reopens a window where a concurrent quit slips through and ends the process without installing.

## Lesson

- **A native platform API that embeds its own process-teardown (Squirrel.Mac inside `quitAndInstall()`) can bypass your app's lifecycle events entirely** — verify against platform docs whether the exit path you're relying on can be skipped by a different one, rather than assuming `before-quit` is universal.
- **A callback with signature `() => void` (no `Event` argument) cannot gate or cancel anything** — `before-quit-for-update` looked like a fix but there's nothing to `preventDefault()` on; check the listener's actual type before designing a "prevent this" flow around it.
- **Extract shared cleanup into a runner callable from any exit trigger**, not re-implemented per call site — `shutdownCoordinator.ts`'s `setShutdownRunner()`/`startShutdown()` replaced the #9638 hand-copied-markers approach, which had already drifted (only 3 of the chain's many steps were replicated).
- **Phase transitions around a shared shutdown owner must flip synchronously with the terminal action**, in the same turn — any deferral (a `setImmediate`, an extra microtask) reopens a race where a second trigger's quit lands in the gap and ends the process on the wrong branch.
- **A chain that can block subsequent quits (`preventDefault` while `"cleaning"`) needs a hard absolute deadline that resolves, never rejects**, so the terminal action always fires — `SHUTDOWN_DEADLINE_MS` (`CLEANUP_TIMEOUT_MS + SHUTDOWN_TAIL_TIMEOUT_MS + 2s` in `shutdownConfig.ts`) is the structural backstop; without it, one hung `await` anywhere in the ~540-line chain makes the app permanently unquittable.
- **A "successful" install path needs a watchdog even when it never used to fail** — gating install behind full teardown means a _failed_ install (previously survivable, app just stayed live) now leaves a torn-down process with no DB/PTYs/IPC and nothing to end it; the force-exit watchdog stands between that and a zombie.

## Applies when

- Wiring cleanup/teardown work to `app.on("before-quit")` and assuming it's the only process-exit path — auto-update installs, forced quits, and OS session-end can all bypass it on macOS.
- Touching `electron/services/AutoUpdaterService.ts`'s install/`quitAndInstall` path or `electron/lifecycle/shutdown.ts`'s `before-quit` listener.
- Adding a new "must run before the process dies" requirement (journaling, checkpoint, flush, marker write) — check it against every terminal-action call site (`app.exit`, `app.quit`, `quitAndInstall`), not just the primary quit listener.
- Seeing an Electron `-for-update`-style companion event and assuming it supports `preventDefault()` — check the listener signature first; a `() => void` callback has nothing to gate on.
- Diagnosing lost session/DB/journal state specifically around update installs (not ordinary quits) on macOS, or auditing whether a shutdown-adjacent redesign could make the app unquittable.
