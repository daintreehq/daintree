## Context

The builtin GitHub forge plugin normalizes GitHub responses into the neutral forge contract `Issue`/`PR` (`shared/types/forge.ts`) through three hand-maintained mapper families that all emit the same contract type from different source shapes, now in `plugins/builtin/github/main/mappers.ts`: `toForgeIssue`/`toForgePR` map GraphQL node projections (list/search/single/batch endpoints in `readOps.ts`); `restToForgeIssue`/`restToForgePR` map REST create/edit responses; `gitHubIssueToForgeIssue`/`gitHubPRToForgePR` map the legacy stats first-page list shape. (At #10504 all sat in `forgeProvider.ts`; the mappers were later extracted to `mappers.ts` in the oversized-file split batch — the fix persists unchanged.)

## Problem

The comment-count badge disappeared from the issues and PR dropdown rows (issue #10502) — rendering intermittently, present on some rows and absent on others, which reads to users as flakiness. The GraphQL queries already fetched `comments { totalCount }` and the row component already knew how to render it, so the data looked present end to end; nothing errored.

## Root cause

Two independent couplings, both silent, combined.

First: `toForgeIssue`/`toForgePR` (the GraphQL node family) simply omitted `commentCount`, while the sibling `gitHubIssueToForgeIssue`/`gitHubPRToForgePR` (list-shape family) carried it. So whether a row got a count depended purely on which mapper family produced it. This drops with **no type error**: the mapper source is `Record<string, unknown>`, the contract field is `commentCount?: number` (optional), and it is assembled by conditional spread (`...(commentCount !== undefined ? { commentCount } : {})`), so omitting it is legal TypeScript. The renderer gate `(item.commentCount ?? 0) >= 1` then treats `undefined` as "zero comments" and silently renders nothing — absence, not a crash.

Second, and the deeper trap: the same node mapper `toForgePR` is fed by **multiple query builders that project different field subsets**. `buildBatchPRQuery` fetched `comments { totalCount }`; `buildBatchBranchPRQuery` (which feeds `findPRsByBranches`) did not. So even after adding extraction to `toForgePR`, results flowing from the batch-branch path still had `node.comments` undefined and produced no count. A field the mapper reads only materializes for the callers whose query actually projected it — fixing the mapper is necessary but not sufficient. The fix therefore touched both `mappers.ts` (extract `node.comments.totalCount` in both node mappers, preserving `0`, omitting on absent/malformed) and `GitHubQueries.ts` (add `comments { totalCount }` to `buildBatchBranchPRQuery`).

## Lesson

- **Adding or preserving a field on the forge `Issue`/`PR` contract means auditing all three mapper families in `mappers.ts` (`toForge*`, `restToForge*`, `gitHub*ToForge*`), not just the one in front of you.** Each is hand-assembled from a different source shape; the optional-field-plus-conditional-spread pattern means a dropped field is invisible to the compiler. This is the same duplicate-transform drift genre as the split agent-FSM (#6670) and the hibernate-wake listener set (#6674) — parallel producers of one shape diverge silently because each is exercised by a different code path.
- **A GraphQL node mapper is only as complete as the query that projected the node — and several queries feed the same mapper.** `toForgePR` is fed by list, search, single-PR, `buildBatchPRQuery`, and `buildBatchBranchPRQuery`. Before assuming a mapper handles a field, grep every query builder in `GitHubQueries.ts` that feeds it and confirm each projects it; the batch-branch query under-projected and that alone broke `findPRsByBranches`.
- **Preserve a real `0`, omit on absent/malformed.** Use `typeof comments?.totalCount === "number" ? comments.totalCount : undefined` then conditional-spread — never `?? 0`. A count of `0` is meaningful and must survive; `undefined` must mean "the query didn't fetch it," so the render gate distinguishes "zero comments" from "unknown." Coercing absent to `0` makes every un-projected row claim zero comments.
- **`restToForgeIssue`/`restToForgePR` still omit `commentCount`, deliberately** — REST create/edit responses never feed the dropdown lists and a fresh item has no comments. Blind find-replace-for-parity across the three families is wrong; each maps only the fields its callers surface.
- **Because nearly every field on `Issue`/`PR` is optional, the compiler will not flag a mapper that forgets one** — the guard is a per-family test asserting the field survives the map (#10504 added present/zero/absent/malformed cases for both node mappers plus a `buildBatchBranchPRQuery` field-shape assertion).

## Applies when

- Adding, renaming, or debugging any field on the forge `Issue`/`PR` contract (`shared/types/forge.ts`) — check all of `toForge*`, `restToForge*`, and `gitHub*ToForge*` in `plugins/builtin/github/main/mappers.ts`.
- A forge dropdown/list value (comment count, CI status, review decision, labels) shows on some rows but not others, or only from one endpoint — suspect a mapper family that drops it or a query builder that under-projects it, not a render bug.
- Editing any query in `GitHubQueries.ts` (`buildBatchPRQuery`, `buildBatchBranchPRQuery`, list/search projections) — the field set must match every mapper consuming the returned nodes; leaner batch queries silently starve the shared mapper.
- Reviewing any change that touches one of several parallel transform functions emitting a common shape — confirm the others were updated too, since optional-field contracts hide the drift from the compiler.
