## Context

`ProjectViewManager` (PVM) owns one `WebContentsView` per open project per window, in `ProjectViewManager.ts` (later split across `ProjectViewLifecycleController.ts`, `ProjectViewSwitchController.ts`, `ProjectViewEvictionController.ts` by an oversized-file refactor — mechanisms below unchanged). Views are created, cached, evicted under memory pressure, and hibernated by `HibernationService`; `ResourceProfileService` fans profile changes out to every PVM. #10931 was a hardening pass, written after auditing for exactly the class of race that recurs whenever teardown paths multiply.

## Problem

No single user-visible crash — three latent races plus a silent-truncation bug, reachable only under timing pressure (window close mid-switch, hibernation racing an active paint, eviction firing during a profile change). Symptoms when they fired: entries stranded in `views`, breaking later eviction/dispose loops; a dead renderer's webContents re-registered as a live cached view; a view created that no sweep would ever reach again; a profile change silently never reaching the renderer broadcast or pty/workspace/hibernation pushes.

## Root cause

The unifying trap is electron#50249: on Electron 41+, once a `WebContentsView` is destroyed, its `.webContents` getter returns `undefined` instead of throwing or keeping the last value. `cleanupEntry` read `entry.view.webContents.id` unguarded — under a genuine teardown race (window-close ordering, OS-level view destruction) that turned a plain property read into a `TypeError` mid-iteration, stranding the entry in the `views` map and aborting `dispose()` partway through. Fix: resolve the webContents defensively (try the getter, fall back to a reverse lookup in `webContentsToProject` keyed by `projectId`) so cleanup always completes even when the live reference is gone.

The second race is structural, not version-specific: `destroyView` (the path `HibernationService` calls) runs **outside** `switchChain`, the queue that serializes every switch/activate/deactivate — so it can tear an entry down while it's still referenced as a paint-gate bridge elsewhere in the switch flow. When the gate settled, `deactivateEntry` ran on the dead reference and would have re-registered its closing webContents as a cached view, with no destroy listener left to clear that registration. Fix: an identity guard, `if (this.views.get(current.projectId) !== current)` — if the map no longer points at _this_ entry, someone already tore it down; detach best-effort and return. Third, `performSwitch` can be queued behind `switchChain` and land after `dispose()` (window closed mid-queue); nothing ever sweeps a disposed manager, so it would silently build a permanently unreachable view — fixed with a `throw` at entry if `this.disposed`.

Separately, `ResourceProfileService.start()`/`applyProfile()` iterate `getAllProjectViewManagers()` in the SAME loop that also triggers the renderer broadcast and pty/workspace/hibernation pushes — one throw from that dependency-injected provider aborted the whole function, silently skipping every downstream consumer.

## Lesson

- **Never read `.webContents` off a possibly-destroyed view unguarded on Electron 41+** — the getter can return `undefined` post-destroy (electron#50249) rather than throw predictably; wrap the read, fall back to a reverse map (`webContentsToProject`) keyed by the ID already tracked. Load-bearing in `ProjectViewLifecycleController.ts`, `ProjectViewHandlers.ts`, `SurfaceViewManager.ts`, `webContentsRegistry.ts` — any new teardown code touching `.webContents` needs the same guard.
- **A teardown path that bypasses the object's normal serialization queue can race the object's own state machine.** `HibernationService`'s `destroyView` runs outside `switchChain` on purpose (must not wait behind pending switches), but that means code assuming "the entry in `views` is who I last touched" is wrong — check identity (`this.views.get(id) !== entry`) before mutating or re-registering, not just liveness.
- **A queued operation needs a disposed-check at the point it executes, not just at enqueue time** — `performSwitch` can land after `dispose()` if the window closed mid-queue; guard with `if (this.disposed) throw` right before creating new state, since nothing will ever sweep it otherwise.
- **In a fan-out loop over independent consumers, isolate each call, not the loop.** `ResourceProfileService` wraps only the throwable dependency call (`getProjectViewManagersSafe()`, returns `[]` on throw) so a failure there can't skip the renderer broadcast or other pushes sequenced after it — apply whenever one entry in a multi-consumer push (`for (const x of getAll())`) can fail independently.
- **Report the count actually achieved from a partial-failure batch op, not the input size** — `WorktreePortBroker.reBrokerForHost` now returns the real re-brokered count so logs read `re-brokered/snapshot` instead of claiming success for entries silently skipped (e.g. an LRU-evicted view mid-restart).

## Applies when

- Touching `ProjectViewManager.ts`, `ProjectViewLifecycleController.ts` (`deactivateEntry`, `cleanupEntry`), `ProjectViewSwitchController.ts` (`performSwitch`), or `ProjectViewEvictionController.ts` — any path that creates, caches, evicts, or destroys a project's `WebContentsView`.
- Adding a teardown/cleanup trigger that runs outside the main switch/activation queue (mirroring `HibernationService`'s `destroyView`) — it will race whatever the queue assumes is stable.
- Diagnosing views stranded in a cleanup/eviction loop, a `dispose()` that aborts partway, or a dead renderer that still appears "cached" — check for an unguarded `.webContents` read or a missing entry-identity check first.
- Adding or reviewing a loop that fans a value out to independent consumers (profile changes, broadcasts, per-window pushes) — verify one consumer's throw can't suppress the rest.
- Bumping past Electron 42 — re-check whether `view.webContents` post-destroy semantics changed again; the electron#50249 workaround is baked into five files, so any upstream reversal needs those call sites revisited.
