## Context

The bulk worktree creation dialog shows a list of planned worktrees with their creation status. The `planned` array was derived via `useMemo` from `worktreeMap`.

## Problem

As each worktree was created and landed in `worktreeMap`, the `useMemo` recomputed. The recomputation logic treated worktrees already in `worktreeMap` as "skipped" (since they already exist). The render filter then removed them from the visible list, causing completed items to disappear from the progress view immediately after creation.

## Root cause

The `planned` memo's purpose before execution (compute the plan) and during execution (track progress) are fundamentally different. Before execution, items in `worktreeMap` should indeed be excluded (they already exist). During execution, items should be kept visible regardless of whether they appear in `worktreeMap`.

Using a single reactive `useMemo` for both phases meant the "already exists" check that was correct for pre-execution planning became destructive during execution.

## Fix

Capture per-item status into dedicated reducer state at execution start instead of re-deriving it from the live store each render. The dialog now drives progress through `bulkCreateReducer` (`plugins/builtin/github/renderer/components/bulkCreateReducer.ts`): the `START_EXECUTION` action seeds a `progress.items` Map keyed by issue number with a `stage` per item (pending/executing/succeeded/failed). The pre-execution preview still uses the live `useMemo` over `worktreeMap` (it computes `planned` with the `skipped` "already exists" check), but during/after the run the progress list renders by filtering `planned` to entries present in `progress.items` and reading each item's status from the reducer Map — never re-checking `worktreeMap`. The reducer state is the stable snapshot; reactive recomputation of `planned` can no longer remove completed items.

## Lesson

When a derived value is used for both planning (pre-execution) and progress display (during execution), the computation logic for each phase may be mutually exclusive. The pre-execution "already exists in the store" check is destructive once execution starts, because completed items land in the store and would be filtered out. Capture per-item status into stable state at execution start — a `useReducer`-managed status Map seeded on the START action, or a `useRef` snapshot of the plan — and render from that during the run rather than re-deriving from the mutating store. This prevents reactive recomputation from invalidating the display mid-run.

## Applies when

- Any progress dialog or multi-step wizard that derives its item list from a store that is mutated as the operation proceeds
- Bulk create/delete flows where the source collection changes as items are processed
