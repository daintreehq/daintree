## Context

The bulk worktree creation dialog (`BulkCreateWorktreeDialog.tsx`) shows a list of planned worktrees with their creation status. The `planned` array was derived via `useMemo` from `worktreeMap` (`useWorktreeStore((s) => s.worktrees)`).

## Problem

As each worktree was created and landed in `worktreeMap`, the `useMemo` recomputed. The recomputation logic treated worktrees already in `worktreeMap` as "skipped" (since they already exist). The render filter then removed them from the visible list, causing completed items to disappear from the progress view immediately after creation.

## Root cause

The `planned` memo serves two fundamentally different purposes. Before execution it computes the plan; during execution the same value drives the progress list. Before execution, items already present in `worktreeMap` should be excluded (they already exist, so they are marked `skipped`). During execution, items should stay visible regardless of whether they appear in `worktreeMap`.

Using a single reactive `useMemo` over `worktreeMap` for both phases meant the "already exists" check that was correct for pre-execution planning became destructive during execution: completed items land in `worktreeMap`, the memo recomputes, marks them `skipped`, and the render filter drops them.

## Lesson

When a derived value is used for both planning (pre-execution) and progress display (during execution), the per-phase computation logic may be mutually exclusive. The pre-execution "already exists in the store" check is destructive once execution starts, because completed items land in the store and would be filtered out. Capture per-item status into stable state at execution start — a `useReducer`-managed status Map seeded on the start action, or a `useRef` snapshot of the plan — and render from that during the run rather than re-deriving from the mutating store.

Concretely, the dialog drives progress through `bulkCreateReducer` (`plugins/builtin/github/renderer/components/bulkCreateReducer.ts`). The `START` action seeds a `progress.items` Map keyed by issue/PR number, each entry carrying a `stage` (`pending` → `worktree-creating` → `worktree-created` → `terminals-spawning` → `assigning` → `verifying` → `succeeded`, or `failed`), and sets `progress.phase` to `"executing"`. The pre-execution preview still uses the live `useMemo` over `worktreeMap` (it computes `planned` with the `skipped` "already exists" check, rendered via `planned.map(...)`), but during/after the run the progress list renders `planned.filter((p) => progress.items.has(p.item.number))` and reads each item's status from the reducer Map — never re-checking `worktreeMap`. The reducer state is the stable snapshot, so reactive recomputation of `planned` can no longer remove completed items.

## Applies when

- Any progress dialog or multi-step wizard that derives its item list from a store that is mutated as the operation proceeds
- Bulk create/delete flows where the source collection changes as items are processed
