## Context

`SAFE_GIT_CONFIG_BASE` (named `SAFE_GIT_CONFIG` before this PR renamed it) in `electron/utils/hardenedGit.ts` passes a fixed list of `-c` flags to every git invocation via `createHardenedGit` / `createAuthenticatedGit` / `createWslHardenedGit`, taking precedence over repo `.git/config` because `-c` always wins. The #3742 hardening pass added `core.hooksPath=` (empty value) to that list specifically to stop a repo's own `.git/hooks/*` from executing when Daintree runs git commands against it — a real security boundary, since a cloned or forge-fetched repo can ship a malicious `post-checkout`. That line shipped and looked correct for roughly a year.

## Problem

Issue #11226: every branch/worktree created through Daintree in a Git LFS repo dropped four untracked files — `post-checkout`, `post-commit`, `post-merge`, `pre-push` — straight into the new worktree root, which users then deleted by hand each time. It only affected LFS repos, which pointed away from `hardenedGit.ts` as the suspect at first — the natural read was "something in our worktree-creation path is writing files," not "our security hardening flag is malformed."

## Root cause

`core.hooksPath=` (empty string) is not "no hooks" to every consumer of that config key — it's a _relative path_, and git's own hook-dispatch logic happens to treat empty as "nothing configured" (verified against real git 2.55.0), but git-lfs does not share that special case. git-lfs reads `core.hooksPath` as its install directory and joins it with each hook name; with an empty value that join resolves against **git-lfs's own current working directory**, not the repo's `.git` dir. During `git worktree add`, that working directory is the new worktree root — so git-lfs's self-install-hooks-if-missing behavior (triggered by the LFS smudge filter running on checkout) wrote its four hook files directly into the worktree the user just created. `/dev/null` isn't a fix either: it stops the litter and blocks every hook, but `pre-push` is exactly the hook that uploads LFS objects, so it would silently start shipping LFS pointers with no object content. The actual fix is an absolute, app-owned directory (`userData/git-hooks`) — absolute still blocks any repo-supplied hook (the #3742 invariant is unaffected), while giving git-lfs a stable non-repo location to install into so `pre-push` keeps working. Three more non-obvious pieces make the absolute path safe, all in the current `electron/utils/hardenedGit.ts`: resolution is lazy (`resolveUserDataDir()` / `selectUserDataDir()`), never captured at module eval, because `hardenedGit.ts` is imported before `electron/setup/environment.ts` rewrites `userData` for dev, and the workspace-host `UtilityProcess` has no `app` API at all — it only sees `DAINTREE_USER_DATA` from its fork env; the hooks entry is appended _after_ `extraConfig` in `getAuthenticatedGitConfig()` so a caller-supplied config can never displace it, since git takes the last `-c` for a single-valued key; and WSL git runs inside the Linux distro where a Windows `userData` path has no leading `/` and would itself resolve as relative (the same bug, different shape), so `createWslHardenedGit` uses a hardcoded `~/.daintree/git-hooks` that git tilde-expands at dispatch time instead of the Windows-side path.

## Lesson

- **An empty git config value is not a neutral "off" — check what a relative path means to every consumer of that key, not just git core.** `core.hooksPath=` disabled git's own hook dispatch but was a live relative path to git-lfs, which resolves it independently. Any `key=` (blank) used as a disable idiom needs the same audit if a component other than git core plumbing might read that key.
- **`/dev/null`-style "block everything" fixes can break an unrelated required side effect.** Here `pre-push` doubles as LFS's object-upload mechanism — blocking all hooks silently converts LFS pushes into pointer-only pushes with no error. Check what a hook name is used FOR before nulling out hook execution wholesale.
- **Resolve app-owned paths lazily, never at module scope, when the module is imported broadly and early.** `hardenedGit.ts` predates the dev `userData` rewrite in `electron/setup/environment.ts`; a module-level `path.join(app.getPath("userData"), ...)` would have frozen the wrong directory. Utility processes (workspace-host) additionally have no `app` API and must go through an explicit env var (`DAINTREE_USER_DATA`) instead.
- **When appending a security-enforcing `-c` flag alongside caller-supplied config, order matters — git takes the last `-c` for a duplicate key.** `getAuthenticatedGitConfig()` places `extraConfig` before the hooks entry specifically so no caller can override enforcement by passing their own `core.hooksPath`.
- **A cross-platform path fix needs a per-transport check, not one code path.** The same "relative path resolves against the wrong cwd" defect reappears for WSL git (Windows path meaningless inside the distro) and required its own `~`-relative constant rather than reusing the native absolute path.
- **A bug like this can be invisible to CI:** it depends on a real git-lfs binary self-installing hooks, which the suite doesn't have — provable in isolation (planted hook doesn't run under hardened config; a hook placed in the app-owned dir does, see `hardenedGit.hooks.test.ts`) but the original litter needs manual confirmation against a real LFS repo.

## Applies when

- Touching `electron/utils/hardenedGit.ts`, `SAFE_GIT_CONFIG_BASE` / `HARDENED_GIT_CONFIG_BASE`, or any `-c` flag passed to `createHardenedGit` / `createAuthenticatedGit` / `createWslHardenedGit`.
- Diagnosing stray untracked files appearing in newly created worktrees or branches, especially in repos using Git LFS — check `GIT_TRACE` output for `git-lfs: Install hook:` before assuming Daintree's own worktree code wrote the files.
- Adding or changing any git config override meant to "disable" a repo-controllable feature via an empty value — verify every tool that reads that key (not just git core) treats empty the same way you intend.
- Adding a new app-owned filesystem path that must be resolved consistently across the main process, a `UtilityProcess` (workspace-host), and WSL's `wsl.exe git` — each has a different way of learning `userData` (Electron `app.getPath`, `DAINTREE_USER_DATA` env, or a distro-relative `~` path).
- Reviewing any `extraConfig`/override-merging function for a security-enforcing config list — confirm the enforced entry is appended last, not first, so callers can't shadow it.
