## Context

`terminal.waitUntilIdle` is a native MCP long-poll tool (`electron/services/mcp-server/waitUntilIdle.ts`) the assistant uses as an await primitive: it blocks until the agent in a given `terminalId` transitions out of `working`, or until timeout/cancellation. It subscribes to the `agent:state-changed` event bus (`electron/services/events.ts`) and reads current state from `AgentAvailabilityStore`.

## Problem

The store exposes state keyed by `agentId` (`store.getState(agentId)`), and the wait must decide which incoming state-change event satisfies the caller. The obvious choice — match the event by `agentId` — silently resolves the wait on the wrong terminal: a second Claude terminal finishing falsely satisfies a wait on the first.

## Root cause

`agentId` is the agent _type/preset_ identifier (`"claude"`, `"gemini"`, `"codex"` — sourced from `launchAgentId` in `TerminalProcess.ts`, see `shared/config/agentRegistry.ts`), NOT a per-terminal handle. Multiple terminals running the same agent type share one `agentId`. `AgentAvailabilityStore.agentStates` is keyed by `agentId`, and its `agentToTerminal`/`terminalToAgent` maps are 1:1 — so when a second same-type terminal spawns, `agentToTerminal[agentId]` is overwritten (acknowledged limitation in the regression test at `McpServerService.test.ts:5283`). The `agent:state-changed` payload carries BOTH `agentId` and `terminalId`; only `terminalId` is unique per pane. Filtering on `agentId` resolves on cross-terminal collisions; filtering on `payload.terminalId !== terminalId` is what makes the poll correct.

## Lesson

For any long-poll / wait-for-state primitive over the agent event bus:

- Key the resolution predicate on `terminalId`, never `agentId`. `agentId` identifies the agent type and is shared. Reads from `AgentAvailabilityStore` by `agentId` are inherently ambiguous across same-type terminals; the per-terminal event filter is the disambiguator.
- Subscribe to `agent:state-changed` BEFORE reading current state. If you read first, a transition firing in the gap before the listener is wired is lost and the wait hangs until timeout (classic missed-event race).
- Settle exactly once (a `settled` boolean guarding `resolve`) and race four outcomes: already-non-working (immediate), transition, timeout (`setTimeout`), and client cancel (`extra.signal` `abort` listener). Tear all of them down in a single `finally`-block `cleanup()` — unsubscribe, `clearTimeout`, `removeEventListener` — so no leak survives whichever outcome wins.
- Fall through immediately for terminals with no `agentId` (plain shells): `getAgentIdForTerminal` returns `undefined`, so return idle rather than waiting forever on an agent that will never report.

## Applies when

- Adding or reviewing any MCP native tool or IPC handler that waits on / correlates `agent:state-changed`, `agent:spawned`, `agent:completed`, or agent idle/working transitions.
- Any code that reads `AgentAvailabilityStore` (`getState`, `getAgentIdForTerminal`, `getLastStateChange`, `isAvailable`) and needs per-terminal precision — remember its agentId-keyed maps collide across same-type terminals.
- Implementing long-poll / blocking-await primitives over an EventEmitter where the event payload carries multiple IDs and you must pick the unique one (here `terminalId` over `agentId`).
- Symptom: a wait/await resolves too early, or fires for the wrong pane, when two terminals run the same agent type (`claude`/`gemini`/`codex`); or a wait never resolves because the transition fired between read and subscribe.
- Writing cleanup for promise-wrapped event waits with timeout + AbortSignal — verify single-settle and single `finally` teardown.
