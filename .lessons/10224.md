## Context

`src/workers/semantic.worker.ts` is the per-terminal Web Worker that scans streamed PTY output. Each poll it appends the freshly ANSI-stripped chunk to a per-terminal `analysisBuffer`, then re-runs `extractArtifacts` (code blocks + patches, `shared/utils/artifactParser.ts`) over the whole window. Anything it finds is posted as `ARTIFACT_DETECTED` straight into `useArtifacts` — there is NO other artifact source and no second extraction pass. The window was capped at 5KB (`MAX_ANALYSIS_BUFFER_SIZE = 5000`) via a plain tail cut: `state.analysisBuffer = (state.analysisBuffer + cleanData).slice(-5000)`.

## Problem

Fenced code blocks and unified diffs larger than ~5KB — a 200-line source file, a long patch, i.e. exactly the artifacts users most want captured — never appeared, silently and permanently, with no error or fallback. Small blocks worked fine, so it read like a flaky parser bug. But `artifactParser.ts` was correct and unchanged; the loss was entirely upstream in how the window was trimmed (#9999).

## Root cause

The code-block extractor regex `/```([^\n`]_)\n([\s\S]_?)```/g`needs BOTH the opening and closing fence present in the same string at match time. Terminal output streams in small chunks, so for any block over the window size the sequence is: opening fence enters the window → body streams in → the body pushes total length past 5000 → the plain tail cut evicts the opening fence → the closing fence finally arrives → the regex can no longer match (opener is gone) → and no later poll can recover the evicted prefix. The block is dropped forever. The invariant a windowed buffer must preserve for a paired-delimiter parser — "never evict an opener whose closer hasn't arrived" — was never stated, so a naive`slice(-N)` violated it invisibly.

The fix (`src/workers/WorkerBufferService.ts`) replaces the tail cut with `trimAnalysisBuffer`, which anchors the cut to the START of the nearest still-open structure: an unclosed code fence (`findFenceLineStarts` returns all line-start ``` offsets; odd count ⇒ the last one opened a block that hasn't closed) or an open patch (`findOpenPatchStart`). A `MAX_ANALYSIS_BUFFER_HARD_CAP = 1_000_000`bounds a fence that never closes — past 1MB it falls back to the plain tail (that one block is lost, but memory stays bounded, matching pre-#9999 behavior).`appendToAnalysisBuffer`normalizes CRLF→LF first so the line-anchored`^[ \t]{0,3}````detection works on Windows PTY output and survives a CRLF pair split across a chunk boundary. The worker computes`combined = appendToAnalysisBuffer(...)`, synchronously assigns `state.analysisBuffer = trimAnalysisBuffer(combined)`, and only then awaits `extractArtifacts(combined, ...)`— extraction reads the untrimmed local`combined`, never the just-trimmed `state.analysisBuffer`, so storing the trim first costs nothing as long as extraction keeps using the pre-trim variable.

## Lesson

- **A plain `slice(-N)` on a sliding window that feeds a parser needing BOTH delimiters at once will silently destroy every artifact larger than the window.** Anchor the trim to the start of the nearest still-open structure (open fence by ``` parity, open patch by a diff state machine), not to a fixed byte offset. The parser being correct tells you nothing — audit the buffer feeding it.
- **Extract from the untrimmed local buffer, never from the just-trimmed field.** On the poll where a block's closing fence arrives, the fence count goes even and the open-fence anchor releases — trimming to `state.analysisBuffer` on that poll would evict the very block that just closed. In `semantic.worker.ts` the order is `combined = append(...)` → `state.analysisBuffer = trim(combined)` → `extractArtifacts(combined)`: the trim assignment runs first, but extraction still reads the untrimmed local `combined`, so the block survives regardless of statement order.
- **Trim synchronously before the `await`, never after.** `extractArtifacts` is async (Web Crypto) and can throw; trimming first keeps the buffer bounded even on the throw path — a retry the error path can't actually deliver is not worth the unbounded growth. This ordering is deliberate and load-bearing, not incidental.
- **Bound the anchor with a hard cap.** Without `MAX_ANALYSIS_BUFFER_HARD_CAP`, a fence that never closes (or a false-positive open fence) grows the buffer without limit. Past the cap, fall back to the lossy plain tail — bounded memory beats a perfect capture you can't afford.
- **`.slice()` in V8 returns a SlicedString that retains the whole parent** — trimming a 500KB buffer down to a 5KB tail frees nothing. Force a flat copy with `(" " + buffer.slice(trimStart)).slice(1)` when the POINT of the slice is to drop the parent's memory (this is the entire reason to trim at all).
- **Bias the anchor detector toward over-retention.** A false-positive fence/patch (a line-start ``inside block content flipping parity) only over-retains bounded memory; a false negative drops a user artifact. `findFenceLineStarts` deliberately accepts that asymmetry. The stranded-closer fixup keeps the kept buffer starting OUTSIDE any block so`` parity stays meaningful on the next round.

## Applies when

- Touching `src/workers/WorkerBufferService.ts` or the `analysisBuffer` handling in `src/workers/semantic.worker.ts` — preserve the extract-on-`combined`, trim-then-store ordering and the sync-before-`await` placement.
- Building any sliding window over streamed/chunked data that feeds a regex or parser requiring a matched open+close pair (fences, brackets, diff hunks, XML tags) — a tail trim will eat oversized artifacts.
- Diagnosing "large code blocks / long diffs never show up as artifacts but small ones do" — the loss is in the window trim upstream of `artifactParser.ts`, not the parser.
- Slicing a large string down to a small tail specifically to reclaim memory in V8 — the SlicedString retains the parent unless you force a flat copy.
