## Context

`CrashRecoveryService` (`electron/services/CrashRecoveryService.ts`) writes a `session-state.json` backup that is restored after an unclean exit. Originally the only backup trigger was a `BACKUP_INTERVAL_MS = 60_000` interval timer. App state mutations flow through `handleAppSetState` in `electron/ipc/handlers/app/state.ts`, which writes individual fields into electron-store under `appState.*`.

## Problem

A crash between interval ticks restored a snapshot up to 60s stale. This bites hardest during active setup — open several agent panels, crash, and you get back whatever the last tick happened to capture, losing the panels you just created. The interval is a coarse safety net, not a real capture-on-change mechanism.

## Root cause

The backup cadence was decoupled from the events that actually change recoverable state. The fix is event-driven triggers, but the non-obvious part is _which_ events:

- **Mutation trigger must be gated on a curated field set, not "any write."** `CRASH_CRITICAL_FIELDS` (`state.ts:13`) is an explicit `Set` of 10 fields (`terminals`, `panelGridConfig`, `focusMode`, `focusPanelState`, `activeWorktreeId`, `recipes`, `mruList`, `actionMruList`, `developerMode`, `fleetScopeMode`). High-frequency drag fields (`sidebarWidth`, `diagnosticsHeight`) and cosmetic fields (`hasSeenWelcome`) are deliberately excluded — they fire on every drag frame and would cause backup write storms. `handleAppSetState` checks `Object.keys(updates).some(k => CRASH_CRITICAL_FIELDS.has(k))` and only then calls `scheduleBackup()` (1.5s debounce).
- **The mutation backup is wired in a `try/finally`** so it fires even if a partial store write throws mid-loop — a crashing field must not silently skip the backup.
- **Window blur is a strong pre-crash signal.** `registerBlurListener` (`CrashRecoveryService.ts:213`) listens to app-level `browser-window-blur` and takes an _immediate_ (100ms-debounced) backup, capturing state right before a potential crash. The 100ms `setTimeout` debounce plus a `browser-window-focus` listener that clears the timer means a quick refocus (or focus moving between the app's own windows) cancels the write before it fires. The fire path also re-checks `!BrowserWindow.getFocusedWindow()` inside the timeout, so transient app-internal focus shuffles don't trigger a backup.

## Lesson

For crash-recovery / durable-state backups, don't rely on a periodic interval alone — it bounds data loss to the interval length, which is too coarse for active workflows.

- Add a **mutation trigger** but gate it on an explicit allowlist of state-bearing fields. Never trigger on every store write — high-frequency UI fields (drag widths, resize heights) will storm the disk. Maintain the set as a named constant next to the mutation handler and unit-test its membership/size.
- Add a **window-blur trigger** as a cheap pre-crash signal, debounced short (~100ms) and **cancelled on refocus**. Re-verify `!BrowserWindow.getFocusedWindow()` at fire time so focus shuffling between your own app windows doesn't write.
- Wrap the trigger in `try/finally` around the store write so a partial/throwing write still schedules the backup.
- Keep the interval as a fallback; the event triggers are the primary mechanism.

## Applies when

- Touching `CrashRecoveryService`, `session-state.json`, `scheduleBackup`/`takeBackup`, or the `CRASH_CRITICAL_FIELDS` set.
- Adding a new field to app state (`handleAppSetState` / `appState.*`) and deciding whether a crash should recover it — add it to `CRASH_CRITICAL_FIELDS` only if it's state-bearing, never if it's a high-frequency drag/cosmetic field.
- Designing any debounced persistence/backup that currently fires only on a timer and loses recent changes on crash.
- Wiring Electron `app.on("browser-window-blur"/"browser-window-focus")` listeners for save-on-blur, especially in a multi-window app where blur fires on inter-window focus moves.
- Reviewing a "backup on every store write" approach — flag it for write-storm risk and ask for a curated field gate.
