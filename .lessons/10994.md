## Context

Grid panels get a draggable title bar because `SortableTerminal` wraps its own children directly in `DragHandleProvider` (`src/components/DragDrop/SortableTerminal.tsx`), so `PanelHeader`'s `useDragHandle()` resolves the dnd-kit `listeners`/`setActivatorNodeRef` from context. Docked panels mount differently: `TerminalDockRegion` renders `DockPanelOffscreenContainer` once, which takes `ContentDock` (and, inside it, `SortableDockItem` per chip) as `children`, but separately `createPortal`s each panel's actual body (`DockedPanel`) to the popover DOM node — not through `children`. `PanelHeader` already had `(location === "grid" || location === "dock") && dragHandle?.listeners` wired up (issue #10990); the dock branch had simply never been fed a handle.

## Problem

Dragging a docked terminal's title bar did nothing, while the same title bar worked fine in the grid. The fix looked trivial — the `location === "dock"` drag-enabling branch already existed in `PanelHeader.tsx` — which made it easy to assume a small prop was missing, not that the whole context chain was structurally absent.

## Root cause

`SortableDockItem` and the portaled `DockedPanel` body are **both descendants of `DockPanelOffscreenContainer`, but in disjoint branches of the React tree** — one comes from `children` (`ContentDock` → `SortableDockItem`), the other is created directly by `DockPanelOffscreenContainer`'s own render and portaled elsewhere. `createPortal` changes DOM location, not React-tree ownership, but that's exactly the trap: both branches render into what looks like "the same docked panel" in the UI, so it's natural to assume shared ancestry. They don't — `SortableDockItem`'s `DragHandleProvider` (from `useSortable()`) wraps only the chip's own JSX, so the popover body it never surrounds sees `useDragHandle() === null`. This offscreen-container-portal split exists specifically so the docked terminal's xterm instance never remounts when the popover opens/closes (`DockPanelOffscreenContainer`'s "stable-wrapper relocation," #9927) — the same structural split that buys terminal-instance stability is what severs any context provided at the grid-wrapper level.

The fix is a manual registry bridge, not a context-nesting fix: `dockPanelPortalContext.ts` adds `registerDragHandle(panelIds, handle) => disposer`; `SortableDockItem` registers its live dnd-kit handle (keyed by the panel's own id, or every tab-group member id so whichever tab is active resolves it); `DockPanelOffscreenContainer` re-wraps the portaled body in a **second** `DragHandleProvider` sourced from that registry, gated to `terminal.id === activeDockTerminalId` (parked/background tab members must not claim a group's shared `setActivatorNodeRef`). The provider is present unconditionally (`EMPTY_DRAG_HANDLE` when inactive) so the wrapper's element type never toggles and the hosted terminal subtree still never remounts.

A second, independent trap rides along: dnd-kit's shared `DndContext` (`DndProvider.tsx`) recreates `listeners` on effectively every drag frame anywhere in the app, not just for the dragged item. Registering the raw `{ listeners, setActivatorNodeRef }` object each time would re-fire `SortableDockItem`'s registration effect and re-render `DockPanelOffscreenContainer` on every frame — a global drag-perf regression for an unrelated dock feature. The fix keeps the latest handle in a `useRef` (updated every render via a bare `useEffect`) and registers a `useMemo`'d **getter-proxy** (`{ get listeners() { return handleRef.current.listeners } }`) that stays referentially stable forever; the registration effect keys on `dragHandleIdKey` (`groupPanelIds?.join(",")`, a primitive string), not the array reference, so a fresh-but-equal array on an unrelated render doesn't re-fire it either.

## Lesson

- **A shared DOM-adjacent container does not imply a shared React ancestor.** Before assuming a grid-level `*Provider` reaches a docked/portaled/offscreen-relocated counterpart, trace the actual component tree: is the target rendered via `children` (real descendant) or via a sibling `createPortal` call inside the same wrapper (cousin branch, invisible to `useContext`)?
- **Any context added to `SortableTerminal`-wrapped grid panels needs an explicit dock-parity audit**, because `DockPanelOffscreenContainer`'s stable-wrapper-relocation pattern (what keeps xterm from remounting on popover open/close) structurally isolates the popover body from anything the dock chip (`SortableDockItem`) provides — `dockPanelPortalContext.ts`'s `registerDragHandle` is the reusable bridge shape (id-keyed registry + disposer) to copy for the next one.
- **When bridging a value sourced from a per-frame-churning upstream object (dnd-kit's `listeners`), register a `useRef` + `useMemo`'d getter-proxy, not the raw object**, so consumers read live data through a referentially-stable wrapper — this is what stops an unrelated feature (dock drag) from re-rendering on every drag frame app-wide.
- **Key effects that fan out over an id array on a joined primitive string (`groupPanelIds?.join(",")`), not the array reference** — a semantically-equal-but-freshly-allocated array otherwise re-fires registration/cleanup every render.
- **Gate a shared/group handle to the single active member (`terminal.id === activeDockTerminalId`), not "any registered"** — otherwise every parked tab in a group inherits the same keyboard `setActivatorNodeRef` and becomes a stray tab-focus target.

## Applies when

- Adding any React context/provider to `SortableTerminal` or other grid-level panel wrappers and expecting docked panels to automatically pick it up.
- Touching `DockPanelOffscreenContainer.tsx`, `dockPanelPortalContext.ts`, or `SortableDockItem.tsx` — or building a similar offscreen-container-portal relocation pattern elsewhere to avoid remounting an expensive child (terminal, iframe, canvas).
- Debugging "works in the grid, silently no-ops when docked" for any interaction gated by `useContext` (drag, focus, keyboard shortcuts, hover state).
- Publishing a value into context/a registry from inside a component subscribed to a high-frequency-churning source (dnd-kit, animation frame, resize observer) and needing to avoid downstream re-render storms.
- Reviewing a fix that keys a `useEffect` dependency array off an array prop — check whether a joined/sorted primitive key would be more stable than the array reference.
