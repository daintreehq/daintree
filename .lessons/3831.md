## Context

Multiple UI components (AppDialog, AppPaletteDialog, SearchablePalette, FixedDropdown) each registered independent `window.addEventListener('keydown')` handlers for Escape. This worked by accident in most cases due to `stopImmediatePropagation`, but was fragile and could close multiple layers on a single keypress.

## Problem

With no coordination between overlay layers, pressing Escape could close both a palette AND a dialog simultaneously. `uiStore.overlayCount` tracked how many overlays existed but not which was topmost. If two `AppDialog` instances were open, both Escape handlers fired on the same keypress.

`SearchablePalette` had a two-step Escape pattern (clear search first, then close) implemented via `stopImmediatePropagation` — this was brittle and not composable.

## Root cause

No central dispatch; each component assumed it was the only overlay. The overlay counter provided quantity but not ordering.

## Lesson

Use a LIFO stack (not a counter) for layered UI dismissal. The stack lives in `src/lib/escapeStack.ts`: `registerEscape(handler)` pushes and returns `{ id, unregister }`; `updateHandler(id, handler)` swaps a live entry's callback; `dispatchEscape()` fires the topmost handler and returns whether anything ran; `hasHandlers()` reports stack depth. A single global `window` keydown listener — `useGlobalEscapeDispatcher` (`src/hooks/useGlobalEscapeDispatcher.ts`), mounted once in `App.tsx` — runs `dispatchEscape()` and `preventDefault()`s when it consumed the key. Components subscribe via `useEscapeStack(enabled, handler)` (`src/hooks/useEscapeStack.ts`), which registers when `enabled` flips true, keeps the entry's callback fresh through `updateHandler` on every render (the handler is read from a ref, so stale closures don't leak), and unregisters on disable/unmount. Key integration points:

- `useGlobalKeybindings` (`src/hooks/useGlobalKeybindings.ts`) consumes Escape at capture phase to cancel a pending chord, taking priority over the bubble-phase stack dispatcher.
- AppDialog no longer uses a Radix `Dialog` — it renders via `createPortal` and self-coordinates. Modal dialogs (AppDialog, AppPaletteDialog) register a close handler in a separate document-bubble backstop (`src/lib/dialogEscapeBackstop.ts`) so layered dialogs (e.g. Settings under an Action Palette) close one at a time even when a Radix `DismissableLayer` (Popover/Select/DropdownMenu, still in use elsewhere) preempts the regular stack dispatcher in capture phase. A capture-phase probe snapshots whether any Radix layer was OPEN when Escape entered the chain, so the bubble backstop can distinguish real Radix handling (don't fire) from a spurious `preventDefault` by a stale `data-state="closed"` layer (do fire).
- Coordination hazard: a synchronous dialog close (Zustand/`useSyncExternalStore` flushing inside the event handler) unregisters the dialog from the escape stack mid-event. If the backstop already closed the topmost dialog, `useGlobalEscapeDispatcher` must NOT also dispatch — it would walk one layer deeper and close the dialog underneath. The dispatcher guards on `backstopAlreadyConsumedEscape()`; the backstop signals via `markBackstopConsumedEscape()` rather than `e.preventDefault()`, because some focus-restoration paths skip when the event was preventDefault'd.
- `SearchablePalette`'s two-step pattern works naturally: first press calls the clear-search handler, second press fires the close handler.
- When the stack is empty, Escape falls through to default terminal behavior.

Tests: `src/lib/__tests__/escapeStack.test.ts`, `src/lib/__tests__/dialogEscapeBackstop.test.ts`, `src/hooks/__tests__/useEscapeStack.test.tsx`. Each module exposes `_resetForTests()` to clear module-level state between cases.

## Applies when

- Adding any new overlay, dialog, dropdown, or popover that responds to Escape
- Any new component that would have used `window.addEventListener('keydown')` for Escape handling
- Wiring a synchronous-close overlay where a mid-event unregister could cause the dispatcher to skip a layer
