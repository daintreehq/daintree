## Context

`ProjectViewManager` keeps an LRU cache of per-project `WebContentsView` renderers. When a project is switched away from, `deactivateEntry` puts its view into the `cached` state and reduces its resource footprint: CDP `Emulation.setCPUThrottlingRate` (per-renderer, since `setBackgroundThrottling` is window-wide in Electron 28+ — #8599/#4683), a scheduled `window.gc()`, and an explicit `Page.setWebLifecycleState("frozen")` via `freezeWebContents` when efficiency mode is on. The cached renderer still has live `MessagePort`s feeding it: the worktree port (brokered by `WorktreePortBroker`) and the workspace direct port (`WorkspaceClient`), both originating in the workspace-host utility process.

## Problem

Cached views could accumulate unbounded queued messages and OOM the renderer (#6273). A frozen or heavily CPU-throttled renderer stops draining its task queue, but the upstream producers in main/workspace-host had no idea the renderer was frozen and kept calling `postMessage` into ports whose other end could no longer pump them.

## Root cause

Throttling/freezing a renderer is a purely _consumer-side_ control — it slows or suspends the receiver's event loop but sends no signal upstream. `MessagePort.postMessage` has no native backpressure: the sender always succeeds and the payload sits in the receiver's pending task queue. So a frozen view is the worst case — producers run at full speed, the consumer drains nothing, and the queue grows until OOM. The only hard upstream limit is to **close the producer ports**, which `ProjectViewManager` can't do itself (it doesn't own the broker/client). The fix adds an `onViewCached(webContentsId)` callback fired in `deactivateEntry` **before** the throttle/freeze, wired in `main.ts` to `WorkspaceClient.removeDirectPort` + `WorktreePortBroker.closePortsForView` (each in its own try/catch, mirroring `onViewEvicted`). Ordering matters: close while the renderer is still responsive enough to participate in port teardown. Because the ports are gone, reactivation must re-broker fresh ports — done in `activateProjectView` (`electron/ipc/handlers/projectCrud/switch.ts`) for the IPC switch path and mirrored manually in `electron/menu.ts handleDirectoryOpen` (`loadProject` + `attachDirectPort` + `brokerPort` + `distributePortsToView`) for the menu path, which would otherwise leave a cached view portless.

## Lesson

- Reducing a renderer's resource footprint (CPU throttle, `Page.setWebLifecycleState` freeze, `backgroundThrottling`) does NOT pause anything posting into it. Anything upstream of a `MessagePort`/IPC channel will keep filling a queue that the frozen consumer never drains — straight to OOM. Treat freeze/throttle as consumer-only and pair it with an explicit upstream stop.
- Close producer ports **before** flipping the view freeze-eligible, while the renderer is still live — not after. Symmetrise this with eviction: the cache path (`onViewCached`) needs the same producer cleanup as the destroy path (`onViewEvicted`).
- Closing ports on cache creates a debt: every reactivation path must re-broker fresh ports. There are TWO reactivation entry points (IPC `projectCrud/switch.ts` and `menu.ts handleDirectoryOpen`) — fixing only the IPC path leaves the menu path with a portless cached view. Audit all reactivation paths when you add a cache-time teardown.
- Isolate each producer's teardown in its own try/catch; a throw closing one port must not leave the other producer alive posting into a soon-to-freeze renderer.

## Applies when

- Adding throttling, `Page.setWebLifecycleState("frozen")`, `setBackgroundThrottling`, or any "background/hibernate this renderer" behavior to a cached/backgrounded `WebContentsView` (project views, portal tabs, dev-preview).
- Diagnosing OOM or unbounded memory growth in a background/cached project view, especially with live worktree/workspace `MessagePort`s from workspace-host.
- Touching `ProjectViewManager.deactivateEntry` / `activateView`, the `onViewCached`/`onViewEvicted` callbacks in `main.ts`, or `WorktreePortBroker`/`WorkspaceClient` port lifecycle.
- Adding any new cache-time resource teardown — you must find and patch every reactivation path that re-establishes the torn-down resource (IPC switch handler AND the menu directory-open path).
- Wiring any new long-lived `MessagePort` into a renderer that can be frozen/cached: confirm the producer side is told to stop, since the port gives no native backpressure.
