## Context

The embedded side-panel browser feature was originally called "Sidecar" — a name that conflicts with Apple's Sidecar feature (iPad as external display). It was renamed to "Portal" across 87 files (~1179 additions, ~1195 deletions), touching shared types, IPC channels, the Zustand store, the Electron session partition, and components.

## Problem

A rename this broad in an Electron app is not a find-and-replace: the old name is embedded in a cross-layer contract that spans process boundaries and survives across launches. Three concrete hazards surfaced.

- It cannot land incrementally. Action IDs in `shared/types/actions.ts`, IPC channels in `electron/ipc/channels.ts`, type imports, store references, preload bridge namespaces, and component imports form a connected graph; a partial rename leaves the codebase broken at every intermediate state.
- The Zustand persisted store key changed, so existing on-disk state keyed under the old name is no longer found and the user's open Portal tabs disappear on first launch after the rename.
- The Electron `WebContentsView` session partition name changed, so the old partition's cookies, cache, and storage (potentially including auth tokens for web apps) become dead data in the userData directory.

## Root cause

A feature name in this codebase is not a single identifier — it is a string that is duplicated as a literal across layers that cannot import each other. TypeScript types and IPC channel string constants reference each other across the main/renderer boundary, so TypeScript will not even compile a half-renamed graph. Worse, two of the name's incarnations are persistence keys, not symbols: the Zustand `persist` middleware looks up state by its `name` field (now `"portal-storage"` in `src/store/portalStore.ts`), and Electron resolves `session.fromPartition("persist:portal")` by string. Renaming the key changes the lookup, but nothing rewrites the data already written under the old key — so old state is silently orphaned rather than errored on. `portalStore`'s `migrate` is a version-0 pass-through with no old-key remap, confirming the tabs-loss trade-off was accepted, not handled.

## Lesson

Large mechanical renames in Electron apps must be atomic, because IPC channel strings, TypeScript types, Zustand store keys, Electron partition names, and CSS custom properties are all part of a cross-layer contract that does not compile (or behave) at intermediate states. When planning one:

1. Land it in a single PR — TypeScript types and IPC channel constants reference each other across process boundaries, so any partial state fails to compile.
2. Decide the Zustand persistence-key policy explicitly: migrate old state via the `persist` `migrate()` function, or accept data loss and document it. For ephemeral UI state (open tabs) data loss is usually fine — that is the trade-off taken here, where the key moved to `"portal-storage"` and old `"sidecar"`-keyed state is orphaned. For settings or persistent user data, write a real migration.
3. Account for the Electron session partition. `PortalManager.createTab` defaults to `"persist:portal"` (was `"persist:sidecar"`), and the classifier/CSP paths in `electron/setup/security.ts`, `electron/utils/webviewCsp.ts`, and `electron/ipc/handlers/portal.ts` all match that exact string. The old partition's cookies/cache/storage are orphaned, not deleted; document that users may need to re-authenticate, and for security-sensitive state consider explicit partition cleanup instead of silent orphaning.
4. Chase the non-TypeScript references the compiler won't catch: DOM element IDs, `data-testid` attributes, E2E selectors, and the IPC-namespace descriptions in CLAUDE.md / docs that future agents read.

## Applies when

- Renaming any cross-cutting feature that spans shared types, IPC channels, stores, and components
- Any Zustand store with `persist` middleware being renamed (the `name` field is a data lookup key, not just a symbol)
- Any `WebContentsView` with a named Electron session partition
