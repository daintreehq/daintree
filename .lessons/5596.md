## Context

`createHost(pluginId)` (`electron/services/plugin/PluginHostFactory.ts`, imported into `PluginService.ts` as `createPluginHost` and wrapped by a private `PluginService.createHost` passthrough) builds the `PluginHostApi` object passed to a plugin's exported `activate(host)`, and `PluginService.runActivate` runs that callback under a `Promise.race` timeout (`ACTIVATE_TIMEOUT_MS`). The host is the only capability surface a plugin gets — `registerHandler`, `broadcastToRenderer`, `registerAction`, `onDidChangeActiveWorktree`, plus runtime helpers `showToast`, `dispatch`, `logger`, `invalidateFileDecorations`. IPC handlers receive a synthesized `PluginIpcContext` (`{ projectId, worktreeId, webContentsId, pluginId }`), never the raw `IpcMainInvokeEvent`.

## Problem

A plugin's `activate(host)` returns, but the plugin captured `host` in a closure (a `setInterval`, an event callback) and keeps calling it later — possibly after the plugin was unloaded. The naive fix is to revoke the whole host uniformly once `activate()` resolves. That breaks every legitimate runtime callback: a plugin that calls `host.showToast` from a worktree-change subscription would suddenly throw. The opposite naive fix — never revoke — lets a plugin keep registering handlers/actions long after activation, defeating the single-window registration contract and stranding registry entries on unload.

## Root cause

The host has two distinct method classes with opposite liveness semantics, and treating them the same is wrong either way. Registration-surface methods (`registerHandler`, `broadcastToRenderer`, `registerAction`, `onDidChange*`, `registerForgeProvider`, `registerFileDecorationProvider`) are only valid during the activation window; calling them after defeats the design, so they close over a `revoked` flag (declared in `PluginHostFactory.createHost`) that the activation call site flips inside a `finally { revoke() }` wrapping its `runActivate` call, and hard-throw `host revoked: X called after activate() returned or timed out`. Runtime-surface methods (`showToast`, `dispatch`, `logger`, `invalidateFileDecorations`) are legitimately called from post-activation timers/callbacks, so they are explicitly NOT revoke-guarded — their liveness check is `this.plugins.has(pluginId)`, silently no-oping after unload instead of throwing. Separately, `PluginIpcContext` exists so the plugin never sees `IpcMainInvokeEvent`/`BrowserWindow`: the handler derives `webContentsId` from `event.sender.id` and hands the plugin a narrow, host-controlled struct (`projectId`/`worktreeId` still `null` — main has no webContentsId→worktree map).

## Lesson

When designing a capability object handed to untrusted/extension code with an activation lifecycle, classify every method by liveness BEFORE wiring guards: "valid only during activation" → revoke-flag + hard-throw; "valid for the plugin's whole lifetime" → membership check + silent no-op. A uniform guard is wrong for one half no matter which you pick. Set the revoke flag in `finally` so it fires on both normal return and timeout. Never pass the raw IPC event into extension code — synthesize a minimal context struct from `event.sender.id`; it keeps `BrowserWindow`/`webContents` references out of plugin reach and gives you a documented extension point for fields you can't resolve yet. Guard the post-`activate` write-back of the cleanup disposer with `this.plugins.has(pluginId)` — a concurrent `unloadPlugin` can clear `cleanupMap` while `runActivate` is still awaiting, and writing the disposer back after that strands a `setInterval` the plugin created in `activate()`.

## Applies when

Adding a method to `PluginHostApi` (decide revoke-guarded vs membership-no-op and annotate why, matching the existing "NOT revoke-guarded" comments in `PluginHostFactory.ts`), changing `PluginHostFactory.ts`'s `createHost`/`revoke` semantics or `PluginService.ts`'s `runActivate`, resolving real `projectId`/`worktreeId` into `PluginIpcContext`, or designing any other activation-scoped capability surface handed to extension code.
