## Context

AI agents run long tasks (code generation, test runs) that can take many minutes. If the system sleeps mid-task, the PTY process may pause or disconnect, breaking the agent's workflow.

## Problem

No mechanism existed to prevent system sleep while agents were actively working. A naive implementation has two leak traps: the blocker's resource handle is an opaque integer that is trivially lost, and a single boolean "is any agent working?" flag releases the blocker as soon as the first of several concurrent agents finishes — letting the system sleep while others are still running.

## Root cause

Electron's `powerSaveBlocker.start('prevent-app-suspension')` acquires a system resource and returns an integer ID; the only way to release it is `powerSaveBlocker.stop(id)` with that exact ID, so losing the ID leaks the blocker until process exit. Because multiple agents share one process-wide blocker, correctness requires reference-counting active work — `PowerSaveBlockerService` keeps a `Map<terminalId, AgentState>` (`terminalStates`) and `recompute()` derives the active count by counting entries in `ACTIVE_STATES` (`["working"]`). The blocker starts when the count crosses 0→positive and stops only when it returns to 0, with `stopBlocker()` guarding the release behind `powerSaveBlocker.isStarted(this.blockerId)`.

## Lesson

Any Electron API that acquires a system resource by ID (blocker, wake lock, global shortcut) needs explicit, paired start/stop with the ID stored on the owning service — never fire-and-forget.

Track concurrent work by counting, not a boolean. `recompute()` only releases the blocker when the derived active count reaches 0, so the last agent to finish — not the first — clears it.

A safety timeout is mandatory as a leak backstop. If agent state tracking gets stuck (the state machine never transitions out of `working`), the blocker would prevent sleep indefinitely. `startBlocker()` arms a 4-hour `SAFETY_TIMEOUT_MS` timer that logs a warning, force-releases via `stopBlocker()`, and clears `terminalStates`.

Subscribe to the main-process event bus, not renderer/React state. The service reads agent transitions from `events` (`agent:state-changed`, `agent:completed`, `agent:killed`, `agent:exited`) rather than polling the renderer store, and `dispose()` tears down those subscriptions plus any live blocker.

## Applies when

- Any Electron API that acquires a system resource by ID (blocker, wake lock, keyboard shortcut)
- Services that track "active count" of concurrent operations
- Any long-running operation where silent resource leaks have user-visible consequences
