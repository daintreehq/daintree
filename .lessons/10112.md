## Context

The Browser panel (`src/components/Browser/BrowserPane.tsx`) rendered its `<webview>` on a hardcoded `partition="persist:browser"`, so every project shared one Chromium session — while Dev Preview already isolated per project/worktree/panel via `buildDevPreviewPartition`. #10112 (issue #9965) scoped the browser session per project: `buildBrowserPartition(projectId)` → `persist:browser-<projectId>` in `shared/utils/partitionUtils.ts`. Scope is deliberately project-level (not per-worktree/panel like dev-preview) because browser cookies are project-wide state.

## Problem

Cookies, localStorage, and IndexedDB are keyed by partition, and dev servers cluster on the same origins (`localhost:3000`, `5173`, `8080` — the ones the empty state suggests), so logging into project A's app surfaced that session in project B's Browser panel; cookies aren't port-scoped so the bleed reaches further. `browserAllowedHosts` gates navigation, not storage, so it never mitigated this. The misleading part: the fix looks like a one-line attribute change, but the `partition` attribute is write-once and the singleton-session assumption was load-bearing in four other main-process locations.

## Root cause

Two stacked mechanisms.

First, Electron ignores `partition` changes once a `<webview>` is attached — no error, the old session just persists. So `partition={derivedFromStore}` alone is insufficient: `useProjectStore.currentProject` resolves asynchronously, and a first render before it resolves would attach on `persist:browser-default` and silently keep it, reintroducing the cross-project leak under a scoped-looking string. The fix needs the id synchronously at first render: `storeProjectId ?? window.__DAINTREE_INITIAL_PROJECT__?.id`, where the global is seeded by `electron/preload.cts` reading `--daintree-initial-project-id=` from `process.argv` (main passes it via `additionalArguments`; `process.argv` is readable even under `sandbox: true`). For the residual case where the partition changes later anyway, `key={webviewPartition}` forces a full remount — the only way to "change" an attached webview's partition.

Second, the singleton partition was an identity anchor throughout the main process. `electron/setup/security.ts` eagerly locked down `session.fromPartition("persist:browser")` at startup — impossible when partition names aren't known until a project opens — so lockdown moved into the lazy `app.on("session-created")` handler, classifying by partition string. `electron/setup/protocols.ts` nav handlers compared `contents.session === browserSession` object identity — replaced by `isBrowserPanelContents` matching `isBrowserPartition((contents.session as any)?.partition ?? "")` (Electron's types don't expose `Session.partition`). And the `will-attach-webview` allowlist is duplicated in `electron/window/createWindow.ts` AND `electron/window/ProjectViewManager.ts` (this logic was later extracted into `electron/window/ProjectViewHandlers.ts` by the #11004 file-split — same duplication, new home); both carried `allowedPartitions = ["persist:browser", ...]` literals and both had to move. Pattern details that matter: `BROWSER_PARTITION_PATTERN = /^persist:browser(-[a-z0-9_-]+)?$/` is anchored — `startsWith` would over-match `persist:browserish` in a security allowlist; the optional group keeps the legacy bare form recognized so sessions from older builds still get classified and locked down (storage itself was a clean break, orphaned on disk); and `isBrowserPartition` deliberately returns plain `boolean`, not `value is string` — in an `||` chain of partition checks a negative type-guard branch narrows `string` to `never`.

Follow-up interaction (#10185, commit `27c463824`): the `key={partition}` remount collides with the seed-only `src` pattern (#9940 — `src` is captured once in `initialUrlRef` because rebinding it turns guest navigations into redundant full reloads). A partition-change remount would reload the first-mount URL, so `lastPartitionRef` re-seeds `initialUrlRef.current = history.present` during render, before the remounting element reads it.

## Lesson

- **Treat a `<webview>`'s `partition` as write-once**: Electron silently ignores changes after attach. Any per-scope partition must be correct on FIRST render — derive it from a synchronously-available id (`window.__DAINTREE_INITIAL_PROJECT__`, seeded via `additionalArguments` in `electron/preload.cts`), never solely from an async Zustand store; and add `key={partition}` so a late change remounts instead of silently no-oping.
- **Before scoping a shared session, grep every consumer of the old partition literal.** The singleton `persist:browser` was load-bearing in four places beyond the webview tag: eager lockdown in `security.ts`, session object-identity checks in `protocols.ts`, and the duplicated `will-attach-webview` allowlists in both `createWindow.ts` and `ProjectViewManager.ts` (now `ProjectViewHandlers.ts` post-#11004).
- **Dynamic partitions force lazy lockdown.** You can't eagerly `session.fromPartition()`-and-lockdown a session whose name is unknown at startup; enforcement belongs in `app.on("session-created")` keyed on partition-string classification (`classifyPartition` in `electron/utils/webviewCsp.ts`), with the legacy bare form kept in the pattern so cached old sessions stay locked down.
- **Anchor partition patterns and return `boolean`, not a type guard.** `/^persist:browser(-[a-z0-9_-]+)?$/` with explicit over-match tests (`persist:browserish`) because the allowlist is a security boundary; and a `value is string` predicate chained with `||` narrows `string` to `never` on the negative branch (rationale documented on `isBrowserPartition`).
- **A `key`-forced remount replays mount-time seeds.** Any ref captured "once at mount" (here `initialUrlRef` from the seed-only `src` pattern) is stale for the remounted element — re-seed it during render when the key input changes (`lastPartitionRef` in `BrowserPane.tsx`, added by #10185).
- **Storage migration can be a clean break when the state is non-critical** — old `persist:browser` data was orphaned on disk rather than migrated; the security value outweighed keeping browser cookies.

## Applies when

- Touching `partition` on any `<webview>` or `WebContentsView` (`BrowserPane.tsx`, `DevPreviewPane.tsx`, portal promotion), or adding a new partition family to `shared/utils/partitionUtils.ts`.
- Scoping any shared Chromium session per project/worktree/panel, or diagnosing cookies/localStorage/auth bleeding between projects that hit the same localhost origin.
- Reviewing code that compares `contents.session === someSingletonSession` or eagerly calls `session.fromPartition()` at setup for a partition family that is (or may become) dynamic.
- Deriving a webview attribute from async store state — anything that must be right at attach time needs the synchronous `window.__DAINTREE_INITIAL_PROJECT__` seed path, not `useProjectStore`.
- Editing `will-attach-webview` validation — the handler logic is duplicated in `createWindow.ts` and `ProjectViewHandlers.ts` (extracted from `ProjectViewManager.ts` by #11004) and both copies must change together.
