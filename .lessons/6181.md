## Context

`TerminalWebGLManager` attaches `@xterm/addon-webgl` to agent terminals and recovers from GPU context loss: when `onContextLoss` (or the capture-phase `webglcontextlost` listener) fires, it drops the dead pool entry but keeps the terminal in `wants`, so a later consumer event (visibility/tier/mode flip) reacquires WebGL. The whole fleet flips between `webgl` and `dom` mode via a hysteresis threshold.

## Problem

On systems with a _persistent_ GPU fault — canonically M-series Macs driving an external display at fractional scaling, where Chromium emits `GL_INVALID_OPERATION` every time a context is created — the reacquisition path itself becomes the bug. Each fresh context faults immediately, drops, gets reacquired on the next consumer event, faults again. The terminal strobes between WebGL and DOM renderers forever. The "recovery" never converges because the underlying fault never clears.

## Root cause

A reacquire-on-loss loop has no termination condition when the fault is steady-state rather than transient. The fix is a sliding-window circuit breaker in `recordContextLoss()`: 3 losses (`LOSS_THRESHOLD`) within 60s (`LOSS_WINDOW_MS`) calls `setHardwareAvailable(false)`, a one-way trip that forces DOM mode for the rest of the session.

The non-obvious second half: two _different_ failure modes produce context-loss events, and a naive counter conflates them.

- **Per-context faults (must count individually):** M-series fractional-scaling losses are distinct GPU events spaced over seconds — each one should advance the breaker.
- **Bulk GPU eviction (must count as one):** Chromium 146 D3D11on12 memory pressure / `GL_OUT_OF_MEMORY` drops _every_ active context via a single IPC, dispatching `webglcontextlost` synchronously to all N pool entries in the same animation frame. Counting each of those N as a breaker tick would trip the threshold from a single, possibly-recoverable GPU event.

Resolution: loss events route through `scheduleContextLossFlush()`, which increments `pendingLossCount` and coalesces on a `requestAnimationFrame` so one GPU event = one breaker tick regardless of how many pool entries fired. Only `flushContextLoss` calls `recordContextLoss`. The loss handlers still drop their own pool entry synchronously (identity-gated on `pool.get(id)?.addon === ownAddon`); only the _breaker counting_ is coalesced.

## Lesson

- Any auto-reacquire-on-failure loop for a hardware resource (WebGL context, GPU buffer, device handle) needs a circuit breaker with a sliding window — otherwise a steady-state fault turns recovery into an infinite strobe. A bare "retry on loss" is fine only when losses are provably transient.
- The breaker is a one-way session trip via `setHardwareAvailable(false)`; do not auto-rearm it on a timer (that just restarts the strobe). Existing healthy pool entries are left intact — only future `ensureContext` calls are gated.
- When counting failure events to trip a breaker, distinguish "many independent faults" from "one fault that fans out to many handlers." A single bulk GPU eviction fires N synchronous `webglcontextlost` events in one frame; coalesce them on a `requestAnimationFrame` before counting, or a single recoverable event will false-trip the breaker. Coalesce the _counting_, not the _cleanup_ — each handler must still drop its own entry immediately.
- Keep breaker-trip and software-skip logs gated to one line each (`hasLoggedBreakerTrip`, `hasLoggedSoftwareSkip`) and suppress the redundant software-GPU warning once the breaker has fired.

## Applies when

- Touching `recordContextLoss` / `scheduleContextLossFlush` / `flushContextLoss` / the `LOSS_THRESHOLD`/`LOSS_WINDOW_MS` constants in `src/services/terminal/TerminalWebGLManager.ts`.
- Any `onContextLoss` / `webglcontextlost` capture handler, or changing what happens after a WebGL context drops (auto-requeue vs. wait-for-consumer-event).
- Reports of terminals visibly flickering/strobing between renderers, especially on M-series Macs on external displays at fractional scaling, or under GPU memory pressure (Chromium 146 D3D11on12 `GL_OUT_OF_MEMORY`).
- Adding any retry/reacquire loop for a hardware-backed resource where the underlying fault could be persistent rather than transient — add a sliding-window breaker and decide whether failures fan out within one frame.
- Tuning the `webgl`↔`dom` mode hysteresis or `setHardwareAvailable`; the breaker rides on the hardware-unavailable one-way path.
