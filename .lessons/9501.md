## Context

`PluginViewHost` (`src/components/Plugin/PluginViewHost.tsx`, factory `makePluginViewHost`) is the renderer-side inline host that `React.lazy(() => import(componentPath))`-loads a plugin's React component over the `plugin://` protocol and mounts it under `ErrorBoundary variant="component"` + `Suspense`. Each plugin view receives `PanelViewProps` (`shared/types/plugin.ts`): `panelId`, `pluginId`, and a `disposeSignal: AbortSignal` so authors get teardown via `fetch({ signal })` / `addEventListener({ signal })` even when they skip a `useEffect` cleanup return.

## Problem

Two failure modes that look fine until exercised: (1) after a plugin module fails to load and the user hits "Try again", the retry silently does nothing — the same failed module appears again. (2) After a retry, when the plugin's panel kind is later removed, the wrong (already-stale) `AbortController` is aborted, so the live plugin view's cleanup never fires and its fetches/subscriptions leak past unload.

## Root cause

- `React.lazy` memoizes the import promise by **factory-function identity**. The same `lazy()` reference caches its first resolution forever — including a rejected promise. Re-rendering after an `ErrorBoundary` reset re-runs the same `lazy()` ref, which re-throws the cached rejection. A retry must produce a _genuinely new_ `lazy()` reference. The host holds it in state (`useState(() => createLazyView())`) and on reset calls `setLazyView(() => createLazyView())` — not `useMemo` keyed on a counter, because the factory closure identity is what `lazy()` keys on.
- The teardown effect is intentionally `deps: []` (subscribe to `plugin:panel-kinds-changed` exactly once). But the `disposeSignal` controller lives in state and is swapped on retry (`setController(new AbortController())`). A `[]` effect that closed over `controller` directly would forever abort the _original_ controller. The fix mirrors the current controller into a ref (`controllerRef`, updated in a `[controller]` effect) and the removal handler reads `controllerRef.current?.abort()` — so the post-retry controller is the one aborted.
- Renderer-first teardown ordering: `PluginService.unloadPlugin` (`electron/services/PluginService.ts:2300`) runs `unregisterPluginPanelKinds` while the in-memory plugin entry (`this.plugins.delete`, line 2407) still exists; the unregister listener (line 610) calls `schedulePanelKindsBroadcast`, pushing `plugin:panel-kinds-changed` so the renderer can abort `disposeSignal` from the broadcast — the host aborts synchronously when its kind disappears from the payload, before React unmounts the subtree.

## Lesson

- To make a `React.lazy` view retryable after a load failure, store the `LazyExoticComponent` in `useState` and replace it with a brand-new `lazy(factory)` on reset. Never reuse the same factory reference or a `useMemo` that can return the cached one — `lazy()` keys its promise cache on factory identity, so the rejected promise comes back.
- When a long-lived `deps: []` effect must act on a value that other handlers swap during the component's life (an `AbortController`, a client, a subscription target), mirror the current value into a ref and read `ref.current` inside the effect. Closing over the state value directly pins the effect to the initial instance.
- Thread an `AbortSignal` (`disposeSignal`) as the teardown channel for third-party/plugin code so cleanup happens even when the author forgets a `useEffect` return. Drive `.abort()` from both unmount and the cross-process removal broadcast.
- The PR body mentioned discriminating chunk-load vs render errors in the fallback copy; the shipped host does **not** do this — it uses the generic component-variant fallback. Don't assume that discrimination exists.

## Applies when

- Adding or modifying any `React.lazy` / dynamic-`import()` surface that needs a user-triggered "retry" after a failed load (plugin views, lazily-loaded panels, `plugin://`-served modules).
- Working on `PluginViewHost`, `makePluginViewHost`, `PanelViewProps`, or anything threading `disposeSignal` to plugin-contributed React components.
- Wiring `ErrorBoundary` `onReset` / `resetKeys` for a Suspense-loaded subtree and finding the retry appears to do nothing.
- A `useEffect(..., [])` that must abort/dispose a state value (AbortController, MessagePort, client) that gets swapped during the component lifetime — and the wrong (stale) instance is being torn down.
- Cross-process teardown ordering between `electron/services/PluginService.ts` unload and renderer cleanup via `plugin:panel-kinds-changed`, where plugin host APIs must still be live when renderer cleanups run.
