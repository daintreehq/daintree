## Context

`electron/services/mcp-server/` is Daintree's inbound MCP control surface — every external agent and the in-app help assistant dispatch through the `CallTool` handler in `sessionServer.ts` (tier check → grant → dedup → confirm → dispatch → audit). PR #8517 added a per-`(sessionId, toolId)` token-bucket rate limiter to that pipeline as a "runaway-loop guard" (issue #8468): `highFreqRead` tools like `terminal.getOutput` got 60 tokens/min, `standard` 30/min, `mutation` tools (commit, push, worktree delete) 10/min.

## Problem

The in-app assistant fires several concurrent `terminal.getOutput` reads when inspecting more than one pane — normal behavior, not abuse. That drained the `highFreqRead` bucket, and every read after it got rejected with a hard `MCP_RATE_LIMITED` tool-error carrying `retryAfter`. The assistant's model client never honored `retryAfter` — it surfaced the rejection as a hard `TERMINAL_OUTPUT` error to the model, which then flailed for several turns trying to recover from an error it had no protocol for. The guard built to protect the server from a misbehaving agent broke a well-behaved one instead.

## Root cause

A token-bucket rate limiter is correct design for human- or API-key-driven clients that can read `retryAfter` and back off. It's the wrong shape for a model-driven client: the thing reading the rejection is an LLM mid-turn, not code with a retry loop, so a hard reject is unrecoverable, not a transient hiccup. #8517's ordering was careful — charged after tier/grant so denied calls don't burn tokens, before dedup so a replayed dedup key still gets bounded — but that care didn't matter, because the guard's basic shape (reject now, retry later) assumed a consumer capable of "later."

#10766 (resolving #10764) removed the limiter wholesale rather than tuning bucket sizes: `RATE_LIMIT_TIERS`, `RATE_LIMIT_TOOL_MAP`, `consumeToken`, `SessionStore.consumeRateLimitToken`/`rateLimitBuckets`/`clearRateLimitState`, and the `CallTool` enforcement block are all gone (-602/+45 lines). It kept the `rate_limited` audit vocabulary alive as dead-but-parseable legacy — `McpAuditResult`'s `rate_limited` variant and `MCP_RATE_LIMITED_CODE` (now module-local to `auditLog.ts`) exist only so historical on-disk audit records still validate — and left `PLUGIN_MCP_RATE_LIMITED` (Daintree calling third-party plugin MCP servers, a different trust boundary), the IPC leaky-bucket (`checkRateLimit`/`waitForRateLimitSlot`), and the GitHub `RateLimitBucket` type untouched: those gate non-model consumers that can back off. `MCP_DEDUP_ALLOWLIST` also stayed — it bounds loops on a different axis (same-args collapse) and was never what broke the assistant. Verified in the current tree: `docs/architecture/mcp-server.md` (touched 2026-07-08, two weeks after #10766 merged) still documents a 7-step gate order with rate-limit as step 2 and a "Rate limits and dedup" section citing `RATE_LIMIT_TIERS`/`RATE_LIMIT_TOOL_MAP` — none of it exists in code anymore (`grep -rn RateLimit electron/services/mcp-server/` outside `auditLog.ts`'s legacy comment returns nothing).

## Lesson

- **Don't put hard-rejecting rate limits on a surface an LLM drives directly, unless the consumer implements retry/backoff.** A model client hitting a tool error mid-turn can't "wait 1s and retry" the way application code can — it burns turns flailing instead. An MCP surface needing backpressure should queue/serialize the call or widen the tier so legitimate concurrency never trips it — not return a terminal error the model has no recovery path for.
- **When removing enforcement that produced a persisted audit vocabulary, keep the vocabulary read-only rather than deleting it.** `auditLog.ts` kept `MCP_RATE_LIMITED_CODE` and the `rate_limited` `AuditOutcome` variant so `classifyMcpDispatchResult` can still parse historical on-disk records; deleting the enum member would break loading old audit logs.
- **A guard built for a hypothetical failure mode (runaway loop) can be net-negative against the real usage pattern that shows up later.** #8517 was reasonable given #8468's threat model at the time; it only became the wrong call once the assistant started driving MCP with real concurrency. Don't assume a guardrail merged for good reasons is still earning its keep once the consumer's usage pattern changes.
- **`docs/architecture/mcp-server.md` is stale on rate limiting as of this writing — don't trust its gate-order diagram or "Rate limits and dedup" section.** The current `CallTool` order is tier → grant → dedup → confirm → dispatch → audit, no rate-limit step. Verify against `shared.ts`/`sessionServer.ts` before relying on that doc, and strip the dead section if you're editing it anyway.
- **A distinct subsystem sharing a name/vocabulary is not automatically in scope.** #10766 left `PLUGIN_MCP_RATE_LIMITED`, the IPC leaky-bucket, and the GitHub `RateLimitBucket` type alone — same words, different trust boundary and a non-model consumer, so the same reasoning doesn't transfer.

## Applies when

- Adding any throttle, rate limit, or hard-rejection guard to `electron/services/mcp-server/` or any surface the in-app assistant or an external agent drives via MCP.
- Reading `docs/architecture/mcp-server.md`'s CallTool pipeline diagram or "Rate limits and dedup" section — cross-check against `shared.ts`/`sessionServer.ts`/`sessionStore.ts` first.
- Diagnosing the assistant surfacing a hard tool error and flailing for several turns instead of recovering — check whether a CallTool gate is rejecting instead of degrading gracefully.
- Removing enforcement code that produced a persisted audit/log value — keep the value's type/schema as read-only legacy so old records still parse.
- Reviewing a "protect against runaway agent" guard — confirm its rejection is recoverable by the actual calling agent (human, API client, or LLM), not just theoretically correct.
