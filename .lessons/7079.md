## Context

`parseGitHubError` (now `plugins/builtin/github/main/GitHubErrors.ts`) maps a raw thrown error from the GitHub client into one canonical user-facing string. The renderer then routes that string: `isTokenRelatedError`/`isTransientNetworkError` in `src/lib/forgeErrors.ts` (renamed from `src/lib/githubErrors.ts` during forge neutralization, so the same classifiers now serve any forge provider, not just GitHub) decide whether to flip the GitHub dropdown into "reconnect / bad token" mode or treat the failure as a transient blip. Octokit already throws structured `RequestError` (`@octokit/request-error`) and `GraphqlResponseError` (`@octokit/graphql`) objects that carry `.status`, `.response`, and `.response.headers`.

## Problem

Transient GitHub incidents — 5xx, network/DNS blips, brief auth-service 401s that return an HTML error page, and per-org `X-GitHub-SSO: partial-results` responses — were misclassified as token-invalid or SSO-required. Users saw reconnect banners blaming their token during outages that had nothing to do with it.

## Root cause

The old classifier flattened the typed error to `error.message` and substring-matched it: `message.includes("401")`, `message.includes("403")`, `message.includes("SSO")`. That throws away the exact signals Octokit already preserves:

- A 401 from a transient auth-service blip and a 401 from a revoked token have the same `401` substring but different bodies — only `"Bad credentials"` is GitHub's definitive revoked-token signal.
- `X-GitHub-SSO: required` (token must re-authorize against an org) vs `X-GitHub-SSO: partial-results` (token is globally fine; one org refused per-org SSO, response still carries data) both contain `"SSO"` but mean opposite things — partial-results is NOT a token problem.
- A pre-HTTP failure (DNS/abort/unreachable) is re-wrapped by Octokit as a `RequestError` with `status = 500` and **`response === undefined`**, indistinguishable from a real server 500 if you only look at status.
- `GraphqlResponseError` is thrown even on HTTP 200 (when the body's `errors` array is populated), so the SSO header lives on `error.headers`, not on a non-2xx response.

## Lesson

Dispatch GitHub error classification on the typed object, not the message string:

- `instanceof RequestError` → read `error.status` and `error.response`. Treat `!error.response` as a network/connectivity error (distinguishes pre-HTTP wrap from a genuine 5xx). For 401, only `message.includes("Bad credentials")` is invalid-token; everything else at 401 is transient. For 403, read `X-GitHub-SSO` header (via `parseSsoKind`) before defaulting to scope-missing.
- `instanceof GraphqlResponseError` → headers are on `error.headers` (present even on 200-OK throws); SSO classification must read them there.
- Keep `required` vs `partial-results` discrimination in a dedicated `parseSsoKind` separate from URL extraction (`parseSsoHeader`) so security/URL validation stays in one place.
- When in doubt at an ambiguous auth status, prefer the transient message over flipping the user into reconnect mode — a separate health probe (`GitHubTokenHealthService`) confirms a truly unhealthy token over time. Misclassifying transient→token-invalid is a worse UX than the reverse.
- `5xx` → transient, not a token/permission failure. Mirror the same rule in `GitHubAuth.validate()` (the Settings "Test token" flow) so it reads the 401 body for `"Bad credentials"` and treats 5xx as transient.
- A legacy substring fallback is acceptable ONLY for non-Octokit synthetic errors, and the bare `"401"`/`"403"` matches must be dropped — keep only `"Bad credentials"` as the invalid-token signal so a status-bearing typed error never reaches it.

## Applies when

- Touching `parseGitHubError`, `GitHubAuth.validate`, or any classification of GitHub/Octokit errors into user-facing strings.
- Adding handling for a new GitHub failure mode (rate limit, SSO, scope, 404, network) or a new `X-GitHub-SSO` form.
- Editing `isTokenRelatedError` / `isTransientNetworkError` / `isRateLimitError` in `src/lib/forgeErrors.ts`, or the dropdown reconnect-mode routing that consumes them.
- Any error-classification code that has access to a typed error from a library (Octokit, a fetch wrapper, a gRPC client) but is tempted to `String(error).includes(...)` — reach for `instanceof` + structured fields (`.status`, `.response`, `.headers`) instead.
- Investigating user reports of spurious "invalid token"/"reconnect" banners during what was actually a GitHub incident or a transient network drop.
- Distinguishing a pre-HTTP network failure from a server 5xx where the client re-wraps connectivity errors with a synthetic status (Octokit uses `status=500`, `response=undefined`).
