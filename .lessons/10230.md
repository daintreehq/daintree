## Context

`notify()` (`src/lib/notify.ts`) writes a history entry stamped `seenAsToast` and may render a transient toast (`src/components/ui/toaster.tsx`). `seenAsToast` is the read-marker: the unread badge counts `!seenAsToast`, and `useReEntrySummary` surfaces missed signals by filtering `(e) => !e.seenAsToast && !e.summarized && e.timestamp >= blurTime` (line 109). The OS-native channel is narrow (`shouldNative = priority === "watch"` only), so for everything else the in-app toast IS the delivery and `seenAsToast` must mean the user could actually have seen it.

## Problem

Toasts fired while the window was blurred rendered into a window nobody was looking at, auto-dismissed after ~8s while still blurred, and were written `seenAsToast: true` — so no unread badge and, because `useReEntrySummary` filters on `!seenAsToast`, no re-entry summary on refocus either. An escalated error got strictly WORSE delivery than a routine blurred notification (which kept `seenAsToast: false` and got a badge) — a delivery inversion. The bug pointed the wrong way because the toast code looked correct in isolation; the hole was that three independent dispatch paths each separately assumed focus.

## Root cause

`seenAsToast` was set from `effectiveShouldToast || originVisible` (now line 1028) without every producer of a toast honoring focus. Three paths could fire a toast into a blurred window: (1) thread re-promotion — `shouldToastThread` consulted `shouldReToast` (severity-escalation) but did NOT re-check focus the way `shouldToast` does, so an escalation toasted while `document.hasFocus()` was false; (2) the suppression-grace blur handler called `promote()` immediately on blur, with a comment about surfacing "when they come back" — but "come back" was the blur, not a refocus; (3) the toaster's auto-dismiss timer paused on hover / focus-inside / dropdown-open but not on window blur, so a toast racing its ~8s timer dismissed unseen. Fixing one path left the other two leaking.

A second, subtler mechanism: `document.hasFocus()` is STALE inside a `blur`/`focus` event handler in Chromium 148 — re-reading it synchronously in the handler returns the pre-event value. So the fix cannot re-read focus in the handler; the event arrival itself is the signal. The mount-time read (outside any handler) is fine and initializes `isWindowBlurred`, but the blur/focus listeners are pure state flips.

## Lesson

- **`seenAsToast: true` is a claim the user could have seen it — never set it for a toast rendered into a blurred window.** Every path that can produce a toast must gate on `document.hasFocus()` the same way the primary `shouldToast` does, or keep `seenAsToast: false` so the unread badge and `useReEntrySummary` still surface it. This is a cross-cutting invariant, not a single call site: PR #10230 had to fix `shouldToastThread` (added `isFocused &&`), the suppression-grace blur handler, AND the toaster dismiss timer independently.
- **`urgent` bypasses quiet hours and rate limiting but NOT the focus gate.** An urgent escalation arriving blurred stays inbox-only (`seenAsToast: false`) until refocus. If you add a new priority or bypass, decide explicitly whether it pierces focus — the default answer is no.
- **In Chromium 148, `document.hasFocus()` is stale inside a `blur`/`focus` handler — do not re-read it there.** Treat the event arrival as the signal (pure `setIsWindowBlurred(true/false)` flips). Reading `hasFocus()` synchronously at mount/dispatch time (outside a handler) is correct and is how a toast born into an already-blurred window starts paused.
- **On window blur, eagerly clear the in-flight dismiss timer inside the handler — don't wait for the React effect-cleanup re-render.** A timer expiring in the gap between blur and re-render dismisses the toast unseen, so the blur handler both flips state and calls `clearTimeout(dismissTimerRef.current)`.
- **The visible-duration cap (`MAX_VISIBLE_DURATION_MS = 15000`) must consume VISIBLE time, not wall-clock.** Credit accumulated blurred time (`blurredAccumRef`) into the deadline (`firstShownAt + cap + blurredAccumRef.current`, line 313); without it a blur outlasting the cap computes a 0ms delay on refocus and instant-dismisses the toast the user came back for.
- **Deferred surfacing means arm a one-shot refocus listener, not `promote()` on blur.** The suppression-grace path pauses its 500ms drop timer and arms an idempotent one-shot `focus` listener that either restarts the countdown (if `isOriginSurfaceVisible`) or promotes; repeated blurs must not stack listeners.

## Applies when

- Adding any new toast dispatch path, priority, or `urgent`-style bypass in `src/lib/notify.ts` — confirm it gates on `document.hasFocus()` before writing `seenAsToast: true`.
- Diagnosing "a notification never showed up / no unread badge / no re-entry summary after alt-tabbing away" — check whether it was toasted while blurred and marked read.
- Writing or reviewing any `blur`/`focus` window handler in the renderer that re-reads `document.hasFocus()` synchronously — in Chromium 148 that read is stale; use the event as the signal.
- Testing toasts/notifications under jsdom: `document.hasFocus()` defaults to `false`, so every toast mounts blur-paused and never auto-dismisses (tests pass for the wrong reason or hang). Pin `vi.spyOn(document, "hasFocus").mockReturnValue(true)` file-wide and override per-test for blur cases (`src/components/ui/__tests__/toaster.test.tsx`).
- Touching auto-dismiss timing, the `MAX_VISIBLE_DURATION_MS` cap, or `useReEntrySummary`'s `!seenAsToast` filter.
