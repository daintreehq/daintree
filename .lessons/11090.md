## Context

The toolbar Issues dropdown reads from a renderer-side list cache (`src/lib/forgeResourceCache.ts`, 45s TTL) that mutation call sites can optimistically patch via `mutateCacheEntries`/`patchIssueAssigneeCache` so the UI updates before the next poll; `NewWorktreeDialog` and `BulkCreateWorktreeDialog` already patched the cache after a self-assign, but the Quick Create Palette's `worktree.createWithRecipe` and `workflow.startWorkOnIssue` (`src/services/actions/definitions/workflowCreationActions.ts`) didn't, so issue #11087 reported the dropdown staying stale after the most common assign flow.

## Problem

Adding the missing patch call was the obvious fix, but it wasn't sufficient on its own: even with the optimistic write in place, the dropdown could still flash back to "unassigned" moments later, the stale state resurfacing from directions that had nothing to do with the missing patch call, each one a separate read path re-seeding the same cache slot with pre-assignment data.

## Root cause

An assignment never changes the open-issue count, so every count-based staleness signal in the system is blind to it, and four independent paths use exactly that blind signal to justify overwriting the cache: (1) `planWarmRevalidate` in `useGitHubResourceListSWR.ts` downgrades the next open-time revalidate to `"cached"` whenever `countAtWrite` still matches the live count, letting the backend's own 60s list cache hand back the pre-assignment page over the patch; (2) a stats-page broadcast stamps its `fetchedAt` when the push is _built_, not when its pages left the forge, so `existingIssues.timestamp < payload.fetchedAt` is true even for a broadcast built before the assign, and it would wholesale-replace the patched entry; (3) `ForgeStatsToolbarButton`'s hover prefetch is cache-first (`bypassCache: false`) and joins whatever list query is already in flight on the main-process singleflight — which only skips the join when bypassing — so a hover right after an assign can be handed a page fetched _before_ it; (4) `assignIssueImpl`/`unassignIssueImpl` in `mutations.ts` invalidated nothing, so a later stats poll could broadcast the stale main-process page straight back through path (2).

The fix threads a `stale: boolean` flag through the entry (`patchIssueAssigneeCache` sets it and restamps `timestamp`) and makes all four paths respect it: `planWarmRevalidate` returns `"bypass"` unconditionally when `cached.stale`, checked before the `countAtWrite` shortcut; the broadcast handler in `useRepositoryStats.ts` requires `!existingIssues.stale` alongside the timestamp check; the hover prefetch sets `bypassCache: cached?.stale === true` instead of the fixed `false`; and the new `invalidateRepoIssueCachesForAssignment` in `GitHubCaches.ts` drops the main process's repo issue-page cache, the combined stats-and-page snapshot, and the mutated issue's tooltip on every assign/unassign. Adding the forward patch also created a new inverse bug — the palette's Undo action would strip the forge assignment but leave the optimistic row in the cache — so `forge.unassignIssue` needed the same patch call, not as scope creep but because the forward fix made it newly necessary.

## Lesson

- **Enumerate every reader of a cache before trusting a patch, not just the one that surfaced the bug report.** A single `mutateCacheEntries` call at the write site only helps if no other path re-derives "is this fresh?" from a signal blind to your specific mutation — here, an assignment doesn't move the open-issue count, so every count-keyed freshness check treats the entry as still valid.
- **A `fetchedAt`/timestamp on a push or broadcast records when the payload was _assembled_, not when its data left the source of truth** — don't let a broadcast's own timestamp win a staleness race against a patch that landed after the fetch; gate broadcast writes on an explicit `stale` flag instead of trusting timestamp ordering alone.
- **A cache-first read (hover prefetch, speculative fetch) that joins an in-flight singleflight request inherits that request's snapshot-in-time, which may predate your own recent write** — when an entry is marked `stale`, force that read path to bypass rather than join, or it silently commits pre-mutation data over your patch.
- **Adding an optimistic patch for the forward mutation (assign) can make the inverse mutation's (unassign) missing patch a live bug for the first time** — audit the paired operation whenever you add one side.
- **Prefer one `stale` boolean threaded through every consumer over teaching each consumer its own bespoke "is this write trustworthy" heuristic** — four call sites here (`planWarmRevalidate`, the broadcast handler, the hover-prefetch gate, the main-process invalidator) key off the same flag instead of reimplementing the assignment-vs-count-mismatch logic four times.

## Applies when

- Adding or reviewing an optimistic cache patch anywhere a renderer-side TTL cache sits in front of a backend that has its own independent cache/TTL (forge list caches, any `mutateCacheEntries`-style patch).
- Diagnosing "the UI updates then flashes back to the old value a moment later" — that shape is a re-seed race, not a missing patch; find every writer of the same cache slot (broadcasts, background polls, prefetch, revalidate planners).
- Touching `src/lib/forgeResourceCache.ts`, `useGitHubResourceListSWR.ts`'s `planWarmRevalidate`, `ForgeStatsToolbarButton`'s hover-prefetch gate, or `GitHubCaches.ts` invalidation helpers.
- Adding a mutation whose effect a count-based or fingerprint-based staleness check cannot detect (e.g. changes metadata but not counts, order, or membership that the fingerprint tracks).
- Implementing one side of a paired mutation (assign/unassign, add/remove, lock/unlock) — check whether the other side now needs the same cache treatment.
