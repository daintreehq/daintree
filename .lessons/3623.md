## Context

`WorktreeMonitor` polled `git status` on a fixed 2s/10s schedule regardless of file activity. With 5+ worktrees, this spawned many git processes unconditionally, even when nothing had changed.

The existing `GitFileWatcher` already watched `.git/index` and `.git/refs/heads/` but missed the most common case: edits to working directory files. `.git/index` only updates on staged operations, not plain file saves.

## Problem

Most git spawns during a quiet session were redundant. The watcher infrastructure existed but watched the wrong paths.

## Root cause

Working directory files were not watched — only git internals. The primary refresh driver remained the fixed timer for the majority of real-world changes (editing, saving, new files).

## Lesson

For accurate git status freshness, the file watcher must cover the working directory (excluding `.git/`) in addition to git internals. Without this, the "event-driven" watcher only handles staged operations and the timer remains the primary mechanism.

Working-tree watching uses `@parcel/watcher` (`electron/utils/gitFileWatcher.ts`) — a single cross-platform recursive stream (native FSEvents on macOS, inotify on Linux, ReadDirectoryChangesW on Windows), not raw `fs.watch`. Three implementation considerations:

1. **Max-wait debounce ceiling**: rapid file changes (build tool, linter) flood the debouncer. The flush has a worktree max-wait ceiling (`worktreeMaxWaitMs`, set to `WATCHER_WORKTREE_MAX_WAIT_MS = 1500` ms in `electron/workspace-host/WatcherController.ts`) so sustained rapid changes still produce periodic status updates rather than being indefinitely deferred. The debounce is adaptive — a per-event ramp inside a `worktreeMinDebounceMs..worktreeMaxWaitMs` range, not a flat interval.
2. **Watcher failure recovery lives in the controller, not the watcher**: `gitFileWatcher.ts` only surfaces failures via the `onWatcherFailed` / `onInotifyLimitReached` (Linux ENOSPC) / `onEmfileLimitReached` (macOS FSEvents fd ceiling) callbacks. Retry-with-backoff is owned by `WatcherController`: `handleWatcherFailed()` reconstructs the watcher in `git-only` mode (a graceful fallback that still tracks git internals), then `scheduleRetry()` retries up to `WATCHER_MAX_RETRIES` (5) before staying dark — never silently lose status freshness.
3. **Timer as fallback is mandatory**: `@parcel/watcher` silently drops overflow events on all platforms (no equivalent to `fs.watch`'s `IN_Q_OVERFLOW` / `kFSEventStreamEventFlagMustScanSubDirs` signal), so a polling fallback must stay to catch missed events. Do not remove the fixed-interval timer.

## Applies when

- Adding file-system-event-driven git status refresh
- Diagnosing stale status in the worktree panel
- Linux inotify limit (ENOSPC) or macOS FSEvents fd ceiling (EMFILE) with many watched worktrees
