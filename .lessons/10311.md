## Context

Before hibernation was removed, background terminals were suspended and later woken via `TerminalWakeManager.wakeAndRestore` (since deleted): on activation the renderer asked the pty-host for a snapshot to replay. The yellow `⚠ Output dropped` marker was meant to fire only when the host had actually discarded a pane's buffered output under backpressure. Every agent CLI runs as a full-screen alternate-buffer TUI, so all went through this wake path.

## Problem

Every newly-created agent terminal showed `⚠ Output dropped (output)` at startup, even though nothing was dropped — it had never been suspended. The `(output)` label (rather than `~N bytes`) was the tell: it means `droppedBytes === 0`, which only a marker injected without a measured byte count produces — pointing straight at a path drawing the marker with no real drop behind it.

## Root cause

A fresh terminal's `serialize()` returns `""`; `PtyEventRouter` coerces that (and any absent snapshot) to `null`, so the renderer sees `state === null`. A genuine backpressure discard — host threw away the pane's only buffered copy, nothing to serialize — ALSO yields `null`. One sentinel, two opposite meanings: "never had content to lose" vs. "had content and lost it." #9894 (`bdf7d6f01`) had just turned the silent `if (!state) return false` into `if (!state) { noteDecline(id, true); return false }` (marker + retries) AND removed an `if (managed.isAltBuffer) return false` guard that let alt-buffer TUIs decline silently — so every agent terminal now hit the marker branch on its clean first wake.

The shipped fix (`8a2ab5db7`) added a lifetime `everWoken?` flag on `ManagedTerminal`, set true only on the first successful snapshot replay (inside the identity guard, so a mid-wake LRU evict+respawn under the same id can't stamp a stale ref). The null-state branch then no-ops silently for a never-restored terminal and retries-without-a-marker for a previously-restored one that lost its snapshot. Critically, the wake path stopped drawing the marker at all — genuine drops were left to the pre-existing OSC 57301 signal (#8375). The issue's own Codex-assisted guide had proposed a heavier host-side latch plumbed through five layers; the renderer-only flag sufficed once "loss" was seen to already own that dedicated channel.

This fix was short-lived: hibernation removal (#10811, `eb9cd64a7`, 2026-06-27, ~20 days later) deleted `TerminalWakeManager` wholesale, so `everWoken`, `wakeAndRestore`, and `noteDecline` no longer exist. What SURVIVED is the durable half — `injectDataLossMarker`/`drawDataLossMarker` in `TerminalInstanceService.ts`, now driven ONLY by the window-scoped `data-loss` pulse at `src/store/listeners/panel/lifecycle.ts:391` (a real host discard carrying `droppedBytes`). No absence-inference path can inject a zero-byte marker now.

## Lesson

- **A single falsy sentinel cannot carry two opposite meanings.** `!state` conflated "fresh, nothing to lose" with "had a buffer, host discarded it" because `serialize()` → `""` → `null` collides with a genuine-drop `null`. Any wake/restore/hydrate/resume path that infers a bad outcome from an empty/null payload must first prove the absence is anomalous (a lifetime flag, a prior-content marker) — never treat "no data" and "lost data" as one branch.
- **Prefer a dedicated positive signal over overloading an ambiguous absence.** The enduring fix routes real loss through OSC 57301 (`\x18\x1b]57301;<bytes>;backpressure\x07`), carrying a measured byte count, and stripped the wake path of any marker. When two paths can emit the same signal, make the authoritative source the ONLY source; a path re-deriving it from missing data emits false positives.
- **`⚠ Output dropped (output)` is a live diagnostic tell.** `drawDataLossMarker` labels `droppedBytes === 0` as `(output)` and `> 0` as `~N bytes`. A `(output)` marker means a zero-byte injection — almost always a false positive from a path that drew it without a measured drop. Grep `injectDataLossMarker` callers (today just the `lifecycle.ts` `data-loss` pulse) when one appears without backpressure.
- **When disambiguating an absence with a "succeeded once" flag, key it on the landed outcome, not the IPC return.** `everWoken` flipped only after a snapshot actually replayed, inside the identity guard — a wake that returned a snapshot but failed to apply it must not set it, or a later null wake gets misread as loss. The marker is also window-scoped (#9891); never widen it to a terminal-global latch that could mark sibling windows.

## Applies when

- Diagnosing a spurious `⚠ Output dropped` marker, especially one labeled `(output)` (zero bytes) — trace `injectDataLossMarker` / `drawDataLossMarker` in `TerminalInstanceService.ts` and confirm a real host discard drove it.
- Adding any terminal wake/restore/resume/hydration path where an empty `serialize()` (`""`) or absent host snapshot coerces to `null` and could be mistaken for lost content.
- Deciding how to surface a "we lost something" event: reach for a dedicated positive signal carrying evidence (OSC 57301 with a byte count), and check whether that concept already owns a channel the ambiguous path should stop competing with.
- Working the terminal wake area historically: `TerminalWakeManager`, `everWoken`, `wakeAndRestore`, `noteDecline` were removed with hibernation (#10811); the surviving marker path is the `lifecycle.ts` `data-loss` pulse.
