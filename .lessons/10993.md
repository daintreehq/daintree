## Context

The Daintree Assistant (`launchAgentId: "daintree-assistant"`) runs as a real agent terminal with its own auto-launch and hibernate-resume machinery in `HelpSessionController`, but before #10993 there was no real way to stop it — `HelpPanel`'s `handleClose` only called `setOpen(false)`, hiding the panel while the agent kept running, and `terminal.killAll` deliberately skips it (`excludeFromPersistence === true`). #10989 filed this gap; #10993 added `endSession()` plus a header `CircleStop` button.

## Problem

A naive `terminal.kill()`-equivalent would not have stuck. The assistant is a supervised, self-reviving process: an auto-relaunch path (`_maybeAutoLaunch`) can respawn it on the same open cycle, a launch already in flight can still resolve and bind a fresh terminal after the "stop" fires, and a persisted hibernate slot can restore the just-ended conversation the next time the panel opens. Killing only the PTY leaves all three revival paths intact — the assistant (or its conversation) comes back almost immediately, and it looks like the stop button silently failed.

## Root cause

`endSession()` (later refactored into a shared `_stopBoundSession`/`_applyStopSuppression` pair by the same-day assistant-lifecycle redesign, mechanism unchanged) has to close every path that could resurrect the session, in order, before it can call itself done. First, bump `_launchGen` and clear `_isLaunching`/the watchdog, mirroring `cancelLaunch` — every async checkpoint in `launch()` compares its captured `gen` against the live `_launchGen` and bails if superseded, so a provision mid-flight when Stop was clicked can't land a terminal afterward. Second, revoke the bearer token via `revokeHelpSession(previousSessionId)` _before_ removing the panel (which fires the PTY-kill IPC) — this ordering exists because of #7522's `HelpSessionService` single-backend invariant: `removePanel()` triggers an async kill, and if revoke ran after it, an MCP call already in flight could still authenticate against the dying PTY before the kill lands. This step was extracted into `_teardownBoundSession()`, shared with `launch({ replaceExisting })` — which #10993 _also_ reordered from remove-then-revoke to revoke-then-remove, closing the same race in the pre-existing "new session" flow, not just the new Stop button. Third, clear the persisted hibernate slot (`clearHibernateSession` / now `HibernationManager.clearAndSuppress`) and disarm any pending hibernate timer — Stop is destructive, not a pause, so skipping this resumes the just-ended conversation on next open. Fourth, set `_hasAutoLaunched = true` so `_maybeAutoLaunch` treats this open cycle's budget as spent; `_syncInputs` resets the flag on the next panel open, so suppression is cycle-scoped, not permanent.

Separately, `ProjectStatsService` counted the assistant's PTY into both the switcher's agent counts and its `processCount`, because it only checked `terminal.projectId` + PTY liveness, not agent identity. The fix added `AgentAvailabilityStore.isHelpTerminal(terminalId)` as an exclusion check (skip it for `active`/`waiting`) and a per-project `helpProcessCounts` map to net it out of `processCount`, clamped with `Math.max(0, ...)` because stats can momentarily lag the async help-terminal mark by one poll cycle — an accepted, documented non-goal, not a bug.

## Lesson

- **For any self-relaunching/supervised process, enumerate every revival path before writing the stop, and close each one explicitly** — a monotonic generation counter for in-flight work (`_launchGen`), persisted resume state (hibernate slot), and any auto-retry budget (`_hasAutoLaunched`) are three independent mechanisms and a stop that only handles one of them will appear to work and then silently undo itself.
- **When teardown involves both an auth/session token and a kill IPC, revoke before kill, never the reverse** — `removePanel()`/PTY kill is async, so revoking the bearer first ensures anything still in flight 401s instead of racing the teardown (#7522). This PR fixed the same ordering bug in the pre-existing `launch({ replaceExisting })` path while adding the new Stop feature, which is a sign this ordering is easy to get backwards even when you already know the rule.
- **A "stop" and a "replace" that share teardown logic should share the actual function, not just the concept** — `_teardownBoundSession()` (later folded into `_stopBoundSession`) is used by both `endSession()` and `launch({ replaceExisting })`; if they'd stayed separate, only one of the two would have gotten the ordering fix.
- **Auto-relaunch suppression is cycle-scoped, not permanent, by design** — `_hasAutoLaunched = true` only holds until `_syncInputs` resets it on the next panel open. Don't "fix" this into a permanent suppression flag; the intent is that closing and reopening the panel is a fresh decision to relaunch.
- **A tooling-internal PTY that's excluded from user-facing counts needs an identity check, not a heuristic** — `ProjectStatsService` had to add `AgentAvailabilityStore.isHelpTerminal(id)` rather than inferring from launch args, and had to net it out of `processCount` with a clamp rather than assume the async mark always beats the poll.

## Applies when

- Adding a stop/kill/cancel affordance to any agent or process that has its own auto-relaunch, hibernate/resume, or retry logic (`HelpSessionController`, or any future `*SessionController` built the same way).
- Touching `HelpSessionController`'s launch/teardown paths (`launch`, `endSession`, `_stopBoundSession`, `_teardownBoundSession`, `handleAgentExited`) or the hibernate/auto-launch fields (`_hasAutoLaunched`, `_launchGen`, `HibernationManager`).
- Diagnosing "I stopped/killed X but it came back" for any supervised process — check for an auto-relaunch budget, an in-flight async operation not gated by a generation counter, and a persisted resume/hibernate entry.
- Reordering revoke-vs-kill or auth-vs-teardown steps anywhere a bearer token and an IPC-triggered process kill coexist — default to revoke first.
- Extending `ProjectStatsService` agent/process counts — check `AgentAvailabilityStore.isHelpTerminal` (or the equivalent identity check) before assuming a live PTY with a `projectId` belongs in user-facing counts.
