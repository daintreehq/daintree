## Context

`AppLayout`'s sidebar boots at `DEFAULT_SIDEBAR_WIDTH` (350px) and only picks up its persisted width ~50-100ms later when the async `appClient.getState()` restore resolves. An earlier fix (issue #10321) suppressed the sidebar's own CSS width transition during that window via `isSidebarWidthHydrating`, so the sidebar itself doesn't visibly animate from 350px to the restored width. But `useContentGridContext`, `TwoPaneSplitLayout`, and `TerminalReconciliationWatchdog` all measure the `<main>` container's width on mount via `ResizeObserver`, independent of the sidebar's own transition — none of them were gated by the #10321 fix.

## Problem

On first app load (issue #10827), the empty-state content grid rendered slightly too narrow with a gap on the left, then visibly snapped flush to the sidebar a moment later. It reproduced on a MacBook Air but not a Mac Studio — a classic tell for a measure-before-async-value-lands race that a fast machine's restore beats before first paint, and a slow machine doesn't. The #10321 fix looked directly relevant (same 350px-then-restored value, same startup window) yet didn't touch this bug at all, because it silenced the sidebar's transition, not the grid's independent measurement.

## Root cause

Two distinct problems stacked. First, the obvious one: three separate consumers each ran their own mount-time `ResizeObserver` measurement against the container while the sidebar was still at its default width, and #10321's fix was scoped to the sidebar's own CSS transition — it never reached these other measurers because they don't consume `isSidebarWidthHydrating` at all. The fix adds a second, independent, one-shot lock (`hydrationLocked` in `layoutTransitionLock.ts`) alongside the existing transition lock, combined behind a single `isSidebarMeasurementLocked()` query that all three consumers now gate on and remeasure from via `subscribeSidebarHydrationUnlock`.

Second, and less obvious: `App.tsx` mounts a pre-hydration skeleton `<AppLayout isHydrated={false}>` (no `ContentGrid`) before the real `<AppLayout isHydrated={isStateLoaded}>` takes over. Both instances run the identical `restoreState()` effect body, and the skeleton's `appClient.getState()` call typically resolves _before_ the real `AppLayout` (and its grid) even mounts. If the unlock effect released `hydrationLocked` purely because `isSidebarWidthHydrating` went false — with no regard for which `AppLayout` instance observed it — the skeleton's restore would fire `unlockSidebarHydration()` first, and the real grid would then mount straight into the already-unlocked fast path at the stale default width, reproducing the exact bug the lock exists to prevent. The fix guards the unlock effect with `if (!isHydrated) return;` so only the real, grid-owning instance can ever release the lock — a plain value check was not sufficient; the release had to be gated on _which component instance_ observed it.

## Lesson

- **A module-level singleton lock released by "value X became false" is unsafe if more than one mounted component instance can observe that value change** — gate the release on instance identity/role (`isHydrated`), not just the tracked value, whenever a skeleton/placeholder version of a component can mount the same effect ahead of the real one.
- **A partial fix for an async-hydration race only covers the consumer you noticed breaking** — #10321 fixed the sidebar's own transition but left three other `<main>`-width measurers (`useContentGridContext`, `TwoPaneSplitLayout`, `TerminalReconciliationWatchdog`) ungated; when you fix one symptom of "value arrives async at startup," grep for every other `ResizeObserver`/measure-on-mount site reading the same container before declaring the race closed.
- **Combine multiple locks behind one query function, never let callers check either lock individually** — `isSidebarMeasurementLocked()` is the single OR of `locked` (transition) and `hydrationLocked` (startup); `useContentGridContext.hydration.test.ts` and `twoPaneSplitLayout.sidebar.test.ts` source-scan their consumer file and assert `expect(content).not.toContain("isSidebarLayoutTransitionLocked")` so a future edit can't reintroduce a bare check that silently skips the hydration half (`TerminalReconciliationWatchdog.test.ts` has no equivalent guard yet — a gap, not a pattern to copy).
- **A one-shot unlock needs a synchronous already-unlocked fast path for late subscribers** — `subscribeSidebarHydrationUnlock` fires the listener immediately (and returns a no-op cleanup) if `hydrationLocked` is already false, so a measurement effect that mounts after hydration completed still gets its deferred remeasure instead of silently missing it.
- **Any lock gated on an external async call needs a give-up timeout** — `SIDEBAR_HYDRATION_UNLOCK_FALLBACK_MS = 5000` releases the lock even if `appClient.getState()` neither resolves nor rejects, degrading to the pre-fix visible-snap behavior rather than leaving the grid permanently unmeasured.

## Applies when

- Touching `src/lib/layoutTransitionLock.ts`, `AppLayout.tsx`'s hydration effects, or any consumer of `isSidebarMeasurementLocked()`/`subscribeSidebarHydrationUnlock`.
- Adding a new `ResizeObserver`-based measurement of the panel grid or `<main>` container — check whether it needs to gate on the combined measurement lock, not just the transition lock.
- Diagnosing a first-load-only visual snap/flicker that reproduces on slower hardware but not fast machines — that asymmetry is the signature of a measure-before-async-restore race, not a rendering bug.
- Designing a module-level lock/flag pattern where a skeleton or placeholder component might mount the same effect as the real component it precedes — check whether the release condition depends on which instance fired it.
- Extending a previous fix for "value arrives late on startup" (e.g. #10321) — audit every other consumer of that same async value for the identical race before assuming the class of bug is closed.
