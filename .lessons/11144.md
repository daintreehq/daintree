## Context

`ActionService.dispatch(actionId, args, opts)` is the typed dispatch layer for menus, keybindings, context menus, and agent automation (`src/services/ActionService.ts`), returning `Promise<ActionDispatchResult<Result>>`. By design it never rejects — every failure path (`NOT_FOUND`, `DISABLED`, `RESTRICTED`, schema validation, handler execution) resolves `{ok:false, error}` instead of throwing, so callers decide for themselves whether and how to surface a failure (the `DISABLED` no-toast comment at `ActionService.ts:404-406` references issue #8814 for that specific case, but the never-reject shape applies to every path).

## Problem

Issue #11114 found three UI call sites written as if `dispatch()` could throw or its result didn't matter: `FilePane`'s "open in editor" used `.dispatch(...).catch(logError)` — dead code, since the promise never rejects; `useDevPreviewNavigation`'s promote-to-portal used `void dispatch(...).finally(() => { isPromotingRef.current = false })` without ever reading the result; and `BrowserPane`'s blocked-navigation "open externally" button fired `void dispatch(...)` then synchronously cleared the blocked-nav banner — the user's only recovery route — regardless of whether the open actually succeeded. All three read as ordinary, careful error handling and had passed prior review; the bug is invisible unless you already know dispatch's contract.

## Root cause

Two mechanisms compound. First, a never-rejecting dispatch makes idiomatic promise error-handling into a silent no-op: `.catch()` never fires, `.finally()` alone never inspects the outcome, and bare `void dispatch(...)` discards it outright. The code visually looks like error handling but structurally can't be. The PR body flags this as app-wide — "dozens of other `void dispatch(...)` call sites" and even `BrowserPane`'s own toolbar "Open in browser" button were left unfixed as out of scope, so this is a standing trap, not a closed one.

Second, fixing the call site alone is not sufficient. Review found `devPreviewActions.ts`'s `promoteToPortal` handler had its own `catch` block that rolled back the half-created portal tab (`usePortalStore.getState().closeTab(tabId)`), logged, and returned normally after a failed `portal.create` IPC call — so `dispatch()` resolved `{ok:true}` on an actual failure. Any caller-side `result.ok` branch built on top of that would have been decorative. Fixed by rethrowing after the rollback (`devPreviewActions.ts`, `throw error;` right after `closeTab(tabId)`).

A third, narrower trap in `BrowserPane`: the 10s auto-dismiss timer for the blocked-nav notice cleared `blockedNav` unconditionally. `clearTimeout()` in an effect's cleanup cannot cancel a callback the event loop already scheduled, so a click and the timer firing could race — the timer could null the notice mid-attempt, leaving the failure with nothing to attach to. Fixed by having the callback re-check `noticeId` and `phase === "blocked"` before clearing.

## Lesson

- Before wrapping `actionService.dispatch(...)` in `.catch()`/`.finally()`/try-catch, read the return type: it resolves `ActionDispatchResult` (`{ok:false, error}` on every failure) and **never rejects**. A `.catch()` on it is dead code, a `.finally()` alone drops the failure, and bare `void dispatch(...)` is fire-and-forget. Always `await` and branch on `result.ok`.
- When fixing a swallowed-dispatch-failure bug, trace into the action handler itself, not just the call site — a handler that catches its own async/IPC error for cleanup and returns normally makes `dispatch()` report success on a real failure. `devPreviewActions.ts`'s `promoteToPortal` did exactly this; a caller-side `result.ok` fix would have been decorative without also making the handler rethrow after its rollback.
- Guard an awaited dispatch result against being stale relative to the component's identity. `FilePane` (`openAttemptRef`/`openInFlightRef`, keyed on `[id, filePath]`), `useDevPreviewNavigation` (`promoteAttemptRef`, keyed on `[id, currentProjectId]`), and `BrowserPane` (`blockedNav.noticeId`, bumped per new block) each added an attempt/generation counter, checked before applying the awaited result — reuse this idiom whenever `await dispatch(...)` sits inside a component keyed on volatile props (file path, panel id, project id).
- A timer that clears user-facing recovery UI unconditionally races the user: `clearTimeout()` in cleanup can't cancel a callback already queued by the event loop, so the callback itself must re-check the state's identity/phase before clearing — see `BrowserPane`'s blocked-nav auto-dismiss, gated on `noticeId` + `phase === "blocked"`.
- Failure UI for a dispatch belongs on the pane that owns the action, not a global toast — this is Tier 3 (`docs/architecture/notification-system.md`: "inline error banner, pane-local failure + recovery"). All three fixes render `InlineStatusBanner`/inline error state in-pane and assert `notify()` was never called.
- Treat this as a standing app-wide pattern, not a closed bug: grep for `.dispatch(` followed by `.catch(` or bare `void` before assuming any given call site handles failure — the PR fixed exactly 3 of a much larger set on purpose.

## Applies when

- Writing or reviewing any `actionService.dispatch(...)` call site — check for `await` + `result.ok` branching, not `.catch()`/`.finally()`/bare `void`.
- Diagnosing "clicking X does nothing when the underlying operation fails" anywhere dispatch is involved — suspect the never-rejects contract before suspecting a broken action.
- Touching an action handler in `src/services/actions/definitions/*.ts` that catches its own IPC/async error for cleanup — confirm it rethrows or otherwise reports failure rather than swallowing and returning normally.
- Adding async, dispatch-driven state to a component keyed on props that can change mid-flight (file path, panel/terminal id, project id) — needs an attempt/generation guard against stale results, or a race can overwrite the current context with a superseded one.
- Reviewing a timer-based auto-dismiss of user-facing recovery UI — confirm the callback re-checks ownership of the state it clears rather than relying on `clearTimeout` to have cancelled it in time.
