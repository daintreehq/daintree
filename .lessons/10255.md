## Context

The dev-only demo/screencast engine (`window.electron.demo`, driven by the `demo-video-creator` skill) draws animated captions over a recorded 4K master. `resolveAnnotationPlacement` in `src/components/Demo/DemoOverlay.tsx` clamps each caption box inside a 5% SMPTE title-safe margin (`SAFE_MARGIN = 0.05`). The clamp runs at placement time, before the caption is in the DOM, so it can only reason about an _estimated_ box size — the caption animates in/out, so there is no stable post-layout moment to measure the real element. Issue #10146 reported captions still bleeding past the title-safe area in the recorded output.

## Problem

Captions crossed the title-safe margin in the 4K master even though the clamp existed to prevent exactly that. Three failure modes: long captions wrapped to 3+ lines while the estimator hard-capped height at 2 lines (`lines = estW >= maxBoxW ? 2 : 1`) so top/bottom-anchored boxes grew past the far margin; wide glyphs / all-caps / CJK / emoji under-shifted horizontally because width was a flat `text.length * fontPx * 0.55` char-advance guess; and a single unbreakable token (a file path or branch name) overflowed the box with no `overflow-wrap`. The root defect: the clamp reasoned about a coarse estimate, not the box's real wrapped dimensions, and every error skewed toward _under_-estimating — the one direction that lets a box escape the margin.

## Root cause

Two mechanisms compound. (1) **Canvas `measureText` disagrees with the layout engine's own rendering.** In Chromium 148 (our pinned target — `target: "chrome148"` in `vite.config.ts`, Electron 42) the same `system-ui` string resolves to different SF Pro optical variants in a 2D canvas context vs LayoutNG, and canvas under-reports width by roughly 15% on macOS. A measure-then-render pipeline that trusts canvas width builds a box narrower than what LayoutNG paints, so the clamp under-shifts and the real box crosses the margin. The fix biases every canvas measurement by `MEASURE_FUDGE = 1.15` so the estimate errs toward MORE lines and a WIDER box — over-estimating is harmless (box centers inside), under-estimating is the failure. (2) **Char-count wrapping is wrong for real text.** `split(/\s+/)`/`length * advance` can't find break opportunities in CJK (no spaces) and splits ZWJ emoji into fake break points. The fix uses a module-level `Intl.Segmenter(undefined, { granularity: "word" })` greedy wrap in `estimateWrappedLines`, which also models CSS `overflow-wrap: break-word` by splitting an unbreakable token wider than the box across `ceil(w/limit)` lines (`estimateCaptionBox` falls back to a coarse `length * 0.55 * MEASURE_FUDGE` only when no canvas context exists).

## Lesson

- **In Chromium 148, canvas `measureText` is NOT a faithful proxy for what LayoutNG renders for `system-ui` — it under-reports ~15% on macOS (SF Pro optical-variant mismatch).** Any pipeline that measures text off-DOM to clamp, truncate, or lay out on-DOM must apply a deliberate over-estimation bias (`MEASURE_FUDGE = 1.15`) in the safe direction. Decide which measurement error is harmful (here: too-small box escapes the margin) and bias so every error lands on the harmless side.
- **Count wrapped lines with `Intl.Segmenter(granularity: "word")`, never `split(/\s+/)` or `text.length * advance`.** Char-count height caps (the old `lines = estW >= maxBoxW ? 2 : 1`) and space-splitting silently mis-wrap CJK and ZWJ emoji. Create the segmenter once at module scope — it is reusable and construction is not free.
- **When you can't measure the real post-layout box, improve the estimator; don't fake a measurement.** #10146 suggested measuring the rendered box, but the caption animates and the clamp runs pre-render, so there's no stable box to read. The fix instead made the estimate faithful and kept estimator and renderer in agreement via `white-space: pre-wrap` (explicit `\n` counts as a line in both) plus `overflow-wrap: break-word` (long tokens wrap in-box, matching `estimateWrappedLines`).
- **A clamp with mutually-exclusive `else-if` edge checks flings an oversized box off the far edge.** The fix made the per-edge shifts _independent_ (`if` not `else if`) per axis: a box larger than the safe area violates both edges, and applying both shifts centers it symmetrically instead of slamming it against one margin. Boxes that fit only ever trip one edge, so it's a no-op for the common case.
- **Untyped IPC payloads poison downstream math with NaN.** `SIZE_FRACTION[payload.size]` on a malformed `size` returned `undefined`, propagating `NaN` through every coordinate and silently disabling the clamp; `normalizeSize` coerces unknown values to `"md"`. Guard any object-index lookup whose key arrives over `window.electron.*`.

## Applies when

- Measuring text via canvas `measureText` (or `OffscreenCanvas`) to drive on-DOM layout, clamping, truncation, or ellipsis anywhere in the renderer — the canvas-vs-LayoutNG width gap and the `MEASURE_FUDGE` bias apply beyond the demo engine.
- Touching `estimateCaptionBox` / `estimateWrappedLines` / `resolveAnnotationPlacement` in `src/components/Demo/DemoOverlay.tsx`, or captions crossing the title-safe margin in a recorded demo/screencast master.
- Counting wrapped lines or word-break opportunities for text that may contain CJK, emoji, or long unbreakable tokens (paths, URLs, branch names) — use `Intl.Segmenter`, not char-count or `split(/\s+/)`.
- Writing any measure-then-render pipeline where estimate and rendered element could diverge, or indexing a config map by a value from an untyped IPC payload (coerce unknown keys before the lookup so a bad payload can't emit `NaN`).
