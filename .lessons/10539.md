## Context

Plugins contribute custom React panels via `contributes.panels` + `contributes.views`; the kind registers in `PANEL_KIND_DEFINITION_REGISTRY`, `usePluginPanelKinds` wires each to a `PluginViewHost`/`PluginViewContent` that lazy-imports the component over `plugin://`, and `GridPanel` already mounts plugin kinds via `getPanelKindDefinition`. Grid membership is computed in `useContentGridContext`: `gridTerminals` is the render list, and `isEmpty = gridTerminals.length === 0` drives whether `ContentGridDefault` shows the empty state instead.

## Problem

Custom-React plugin panels — the main reason to build a Daintree plugin — never rendered end to end, and nothing errored. `panel.openPluginPanel` returned `{ok:true}`, the kind registered, the panel landed in the store, yet the Content region kept showing the empty state and neither the view nor its error fallback appeared (#10512). Every layer reported success, so the failure was invisible: `GridPanel`, which could mount the panel, was never called.

## Root cause

Every grid list-builder resolved carrier ids through `getNarrowPanel` (`selectors.ts`), which narrows a store entry to the built-in `PanelInstance` discriminated union — returning `undefined` for `browser`/`dev-preview`/`review`/PTY misses AND for any plugin/extension kind, by design. Reused as a membership filter, `gridTerminals` mapped ids through it and dropped the `undefined`s, so plugin panels vanished from the render set: `isEmpty` stayed `true`, `ContentGridDefault` rendered the empty state, and the panel never reached a mounted `GridPanel`. The same narrow-as-filter pattern sat in `getTabGroupPanelsMapped` (the real render path), maximized/two-pane paths, and `GridTabGroup`. The fix splits two conflated reads: `isPanelRenderEligible(panel)` / `getRenderablePanel(panelsById, id)` answer "should this render in the grid?" — true for built-in kinds, `isRegisteredPanelKind(kind)` plugin kinds, and the disabled-plugin escape hatch (a `pluginId` or a dotted `kind` string, so a disabled plugin still renders a `PluginMissingPanel` placeholder). `getNarrowPanel` stays built-in-only for the union-typed callers (fleet, terminal queries) and the dock (`ContentDock` is PTY-only: `getNarrowPanel` + `isPtyPanel`). The pre-existing `selectors.test.ts` _enshrined_ the drop — asserting `getNarrowPanel` returns `undefined` for plugin kinds as correct, encoding the bug as spec while green.

## Lesson

- **A discriminated-union narrowing helper is not a membership filter — separate "renderable membership" reads from strict union-narrowing reads.** `getNarrowPanel` returns `undefined` for anything outside the built-in `PanelInstance` union, so reusing it to build `gridTerminals` silently drops every extensible kind. For any extensible-kind registry, "does this belong in the render set?" needs its own predicate (`isPanelRenderEligible`/`getRenderablePanel`) that admits registered plugin kinds, not the narrowing adapter that exists to satisfy the compiler.
- **Do not blanket-swap the two reads — pick the path per surface's semantics.** The fix routed grid/tab-group builders through `getRenderablePanel` but KEPT `getNarrowPanel` for fleet (needs PTY union) and `ContentDock` (PTY-only chrome). Swapping every call would leak plugin panels into surfaces whose affordances assume a terminal.
- **When a capability "registers without error but renders nothing," look upstream at the membership/emptiness gate, not the renderer.** `GridPanel` could already mount plugin kinds; an upstream list-builder excluded them. `isEmpty = gridTerminals.length === 0` is a silent chokepoint — anything filtered out of `gridTerminals` flips the whole grid to its empty state.
- **A unit test that pins a narrowing helper's plugin-kind drop as "correct" locks in the very bug at the call site.** `selectors.test.ts` asserted the drop — right about the helper, wrong about the feature. When repurposing a helper, re-audit tests that enshrine its old contract.
- **Registration-only E2E hides dead extensible features — assert the component actually mounts.** The plugin-panels spec only checked that the _kind registered_; it passed while the panel never rendered. The fix ships a hand-authored `plugin://` ESM view in `rich-daintree` and asserts `[data-testid="rich-panel-view"]` becomes visible. Sample `view/` assets are copied verbatim by `build-main.mjs` (never esbuild-processed) so bare `react` resolves through the host import map to the single React instance.
- **A `plugin://` `import()` behind Suspense with no timeout strands the user on an infinite skeleton** — the ErrorBoundary only catches rejections, never a pending promise. Race it against a 10s timeout (`PLUGIN_VIEW_IMPORT_TIMEOUT_MS`) so a wedged load rejects into "Try again". This now lives in `PluginViewContent.tsx` (moved out of `PluginViewHost.tsx` by the later #11240/#11228 split).

## Applies when

- Building or debugging any read feeding grid membership / `gridTerminals` / `isEmpty` in `useContentGridContext`, or any tab-group / maximized / two-pane render path — use `getRenderablePanel` for the render set.
- Adding a panel surface and choosing between `getNarrowPanel` (built-in union callers: fleet, dock, terminal queries) and `getRenderablePanel`/`isPanelRenderEligible` (must render plugin kinds).
- Diagnosing "a plugin registers and `openPluginPanel` returns ok but nothing renders" — trace the membership/emptiness gate upstream of `GridPanel`.
- Reusing a discriminated-union narrowing helper as a general filter over an OPEN/extensible kind set — it drops unknown kinds silently; add a render-eligibility predicate.
