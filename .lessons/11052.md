## Context

`restartTerminal` (`src/store/slices/panelRegistry/restart.ts`, the shared code path for the restart button, `#8787`'s resume-latest fallback, and `#9164`'s parallel-kill optimization) rebuilds an agent's launch command on restart, choosing between an exact session resume (`buildResumeCommand`), a "resume the most recent session" fallback (`buildResumeLatestCommand`, e.g. `claude --continue` / `codex resume --last` / `gemini -r latest`, driven by each agent's `resumeLatestArgs` in `shared/config/agents/*.ts`), or a fresh launch. Main already captures a live session id during the graceful-shutdown quit it runs on every agent kill (`electron/ipc/handlers/terminal/lifecycle.ts`, `handleTerminalGracefulKill` / `ptyClient.gracefulKill`), but until this PR that captured id was only used for journaling on close, never fed back into a same-pane restart.

## Problem

Restarting an agent terminal could load a different terminal's conversation into the pane — not a crash, just silently wrong history appearing after a routine restart. It only showed up with several panes running the same agent (a very normal Daintree scenario: fleet broadcasting means many parallel same-agent terminals), so single-terminal manual testing never caught it, and the wrong-conversation symptom looked like a data/persistence bug rather than a command-construction one.

## Root cause

`restartTerminal` never had the pane's own session id at the point it built the restart command, so lacking `currentTerminal.agentSessionId` it fell through to `buildResumeLatestCommand`. That function resolves to "the most recently active session in scope" for the agent CLI, not "this pane's session" — with N panes of the same agent, whichever pane's session the CLI considers most recent wins, regardless of which pane's restart button was pressed. The fix was one hop away the whole time: `gracefulKill` already captures the live session id on every agent kill (`electron/ipc/handlers/terminal/lifecycle.ts`), but restart called the bare `terminalClient.kill(id)`, which discards it.

The non-obvious part is ordering, not plumbing. Command selection used to run before the kill, computed from already-loaded settings in one pass. To use the captured id, the resume/fresh decision has to move to AFTER the kill resolves — the live session id doesn't exist until the graceful shutdown that produces it has actually run. The diff carries three precomputed variables (`resumeFlags`, `freshCommand`, `freshLaunchFlags`) across the teardown, but doesn't resolve them into `commandToRun` until after `Promise.all([gracefulKill(id), buildRestartEnv(...)])` settles — the kill and env-fetch still parallelize per #9164, only the final command choice moves later.

Two failure modes needed guarding once the capture was live. Identity mismatch: the graceful shutdown quits whatever agent is actually detected running (`currentTerminal.detectedAgentId`), so a Claude-launched pane hosting a hand-started Codex session would otherwise build `claude --resume <codex-session-id>` — gated on `detectedAgentId === undefined || detectedAgentId === effectiveAgentId`. Degrade path: an exact id whose `buildResumeCommand` returns null must fall to a fresh launch, not resume-latest — degrading there reopens the exact nondeterminism being fixed.

## Lesson

- **Treat any "most recent / latest" fallback as inherently wrong wherever multiple live instances of the entity exist.** `buildResumeLatestCommand` is correct only with one session in scope; Daintree's whole model (parallel same-agent panes) violates that constantly. Before reaching for "resume/attach the latest X", check whether X's own identity can be captured instead.
- **A value already captured elsewhere in the lifecycle is often reusable before you build new capture machinery** — the fix routed restart's kill through the existing `gracefulKill` channel instead of the bare `kill` channel; no new capture mechanism was needed.
- **When a value only becomes available as a side effect of an async step you're already awaiting, move the consuming decision to after that step resolves** — don't compute it early just because the inputs are convenient there. `commandToRun` finalizes only after `capturedSessionId` comes out of the `Promise.all`.
- **Never let an exact-identity fallback chain degrade to a "most recent" fallback mid-chain** — if `buildResumeCommand(effectiveAgentId, sessionId, resumeFlags)` returns null for a real captured id, fall to a fresh launch, not `buildResumeLatestCommand`.
- **A resume command is transient; never persist it as the pane's durable `command`** — `durableCommand` stays `currentTerminal.command` whenever `consumedSessionId || usedResumeLatest`, or the next restart replays an already-consumed id.
- **Gate identity capture on the caller's actual intent, not just availability** — `RestartTerminalOptions.allowResumeLatest: false` (used by `moveToNewWorktreeAndTransfer`, #4773) discards the capture because that flow re-seeds context via injected scrollback and an exact resume would double the history; a pre-existing stored `agentSessionId` still resumes there (an intentional exception).

## Applies when

- Touching `restartTerminal` / `src/store/slices/panelRegistry/restart.ts`, or anything rebuilding an agent launch command on kill-and-relaunch.
- Diagnosing "restarted terminal shows a different/wrong conversation" with multiple panes running the same agent — check whether it's falling through to `buildResumeLatestCommand` instead of an exact captured id.
- Adding or reviewing a "resume most recent / attach latest" fallback where the product allows multiple concurrent instances of the underlying resource.
- Wiring a captured async value (session id, PID, handle) into a decision that currently runs before the operation producing the capture — verify the decision point actually moves, not just the capture call.
- Reviewing `gracefulKill` vs bare `kill` call sites (`electron/ipc/handlers/terminal/lifecycle.ts`, `PtyManager`) — confirm which is needed when downstream logic wants the quit-time session id versus plain process teardown.
