## Context

Agent terminals show a synthetic `directing` state (pencil indicator) while the user composes a prompt. Pressing plain Enter is supposed to immediately advance `directing → working` so the indicator closes at submit time rather than after the 1.5s/10s composition debounce. That transition is wired in `TerminalListenerInstaller.ts` via the xterm `terminal.onKey` listener, which calls `deps.onEnterPressed(id)` → `TerminalAgentStateController.onEnterPressed`. Separately, `XtermAdapter.tsx` installs a custom key handler via `attachCustomKeyEventHandler` that intercepts plain Enter to write `\r` (and route Fleet broadcasts).

## Problem

After pressing Enter, single-terminal agents sat in `directing` for the full debounce window instead of closing the indicator immediately. Fleet raw-broadcast Enter had the same problem across every armed target. The write itself succeeded — the prompt was submitted — so the bug was easy to miss.

## Root cause

xterm 6.0's `attachCustomKeyEventHandler` callback returning `false` _consumes_ the event: xterm short-circuits its internal key flow and never emits `onKey` or `onData`. The custom Enter branch in `XtermAdapter.tsx` (around line 418) writes `\r` directly via `writeTerminalInputOrFleet` and returns `false` — so the `onKey` listener in `TerminalListenerInstaller.ts:366` (which is the _only_ thing that calls `onEnterPressed`) never fires for that keystroke. The documented "Enter detection lives in the onKey listener" path (lesson #3545) is dead whenever the custom handler claims the event. The directing timer therefore expired on its own schedule instead of clearing on submit. The same applies to `fleetRawInputBroadcast.ts`: when broadcast intercepts the origin's raw input, the origin's own onKey path is bypassed too, so `notifyEnterPressed` must be called explicitly for every target including origin.

## Lesson

- When a custom key handler (`attachCustomKeyEventHandler`) returns `false` to consume an Enter/keystroke, it has also silently disabled every `onKey`/`onData` listener for that event. Any side effect those listeners perform must be **duplicated in the custom handler** — they will not run otherwise.
- For plain Enter in `XtermAdapter.tsx`, call `terminalInstanceService.notifyEnterPressed(terminalId)` right after the write (it's a no-op when not in `directing`, guarded in `TerminalAgentStateController.onEnterPressed`).
- For Fleet raw broadcast, fire `notifyEnterPressed` for every target including origin, gated on an exact `data === "\r"` match — `\n` is Codex soft-newline and `\x1b\r` is legacy ESC+CR, neither is a submit.
- Treat the return value of `attachCustomKeyEventHandler` as an event-ownership claim, not just "did I handle it": returning `false` means "xterm, do nothing else with this," which includes its listener emission.

## Applies when

- Adding/modifying the `attachCustomKeyEventHandler` callback in `src/components/Terminal/XtermAdapter.tsx`, especially any branch that returns `false` after writing input.
- A terminal side-effect that you wired via `terminal.onKey` / `terminal.onData` (in `TerminalListenerInstaller.ts`) stops firing for keystrokes the custom handler intercepts (Enter, Shift+Enter soft-newline, Tab, chord prefixes).
- The `directing` indicator stays lit past submit, or agent state doesn't advance to `working` on Enter, even though the prompt was clearly submitted.
- Working on Fleet broadcast input (`fleetRawInputBroadcast.ts`) where the origin's normal onKey/onData path is bypassed because broadcast intercepts raw input.
