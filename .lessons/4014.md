## Context

Daintree configures xterm.js with a base scrollback limit (`SCROLLBACK_DEFAULT = 1000` in `shared/config/scrollback.ts`), then applies a per-type policy multiplier in `src/utils/scrollbackConfig.ts`: `getScrollbackForType(isAgent, baseScrollback)` runs plain terminals through `PLAIN_POLICY = { multiplier: 0.3, maxLines: 2000, minLines: 200 }`, so a base of 5000 yields `floor(5000 * 0.3) = 1500` effective lines (clamped to `[200, 2000]`). When output exceeds this limit, xterm.js's ring buffer evicts the oldest lines. This E2E spec (`e2e/full/terminal/core-terminal-scrollback.spec.ts`) validates the buffer behaves correctly after a flood of 5000+ lines.

## Problem

There was no end-to-end coverage that scrollback eviction actually bounds the buffer under sustained high-volume output, nor that xterm.js stays usable afterward. Two failure modes were unguarded: (1) the buffer growing past the configured limit (eviction not firing, or firing at the wrong threshold) and dropping or duplicating lines, and (2) xterm.js entering a degraded state after processing a large volume of lines so the terminal is no longer interactive. A naive test of either is brittle — hardcoding the limit duplicates the constant, and asserting an exact oldest-line number ignores shell and viewport overhead.

## Root cause

The effective scrollback is derived, not a single literal: it is `baseScrollback * policy.multiplier` clamped to the policy's `[minLines, maxLines]` band. A test that hardcodes "1500" couples itself to both the base value and the 0.3 multiplier, and silently goes stale if either changes. The exact retained-line boundary is also non-deterministic in row terms: viewport rows plus shell overhead (prompt lines, the echoed loop command) shift the oldest visible line number off any round figure. Reading the buffer back as rendered text (via `getTerminalText`) rather than the raw model means a tolerance band, not exact equality, is the only correct assertion shape.

## Lesson

Drive the scrollback value the test asserts against, instead of trusting an implicit default. The spec sets the base up front through the `terminalConfig.setScrollback` action dispatched via the `__daintreeDispatchAction` debug API (not the IPC bridge directly), because the action updates both the renderer Zustand store and persists via IPC — so the assertions follow from the value the test itself set. It then reads buffer contents back with the `getTerminalText` helper.

Bound the assertions with a tolerance band, not exact equality, to absorb viewport rows and shell overhead:

- newest retained line is exactly 5000 (the last line written is never evicted);
- oldest retained line is approximately `5000 - 1500 = 3500` (asserted `> 3400` and `< 3550`);
- total retained count is approximately 1500 (asserted `> 1400` and `< 1650`, upper bound generous for viewport rows);
- the retained line numbers form a contiguous ascending sequence (no gaps, no duplicates) — this is the real integrity check, proving eviction trimmed a clean window rather than corrupting the buffer.

Use ANSI-colored output lines (e.g. `\x1b[31m...\x1b[0m`) so the test also exercises escape-sequence handling alongside line counting.

The "is the terminal still interactive after the flood" assertion (`echo INTERACTIVE_CHECK` followed by `waitForTerminalText`) is as important as the buffer bounds check — it catches xterm.js degrading after a large volume of writes, a failure the bounds check alone would miss.

Don't hardcode the scrollback limit in the test; let it flow from the configured base and the `getScrollbackForType` policy so the test tracks the real configuration. If the limit or multiplier changes, the band-derived expectations move with it.

## Applies when

- Changes to xterm.js scrollback configuration or the `scrollbackConfig.ts` policy multipliers/clamps
- Changes to how PTY data is chunked and sent to the renderer
- Testing buffer memory behavior under sustained high-volume output
