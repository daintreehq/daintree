## Context

Daintree configures xterm.js with a scrollback limit (`SCROLLBACK_DEFAULT = 1000` in `shared/config/scrollback.ts`; terminal panels apply a multiplier so a 5000 base yields ~1500 effective lines). When output exceeds this limit, the oldest lines should be evicted. The test validates the buffer behaves correctly after outputting 5000+ lines.

## What the test verifies

- Output 5000 numbered lines via a shell loop
- Assert buffer holds approximately the effective scrollback (~1500 lines, ±tolerance)
- Assert oldest retained line number is approximately `5000 - effectiveScrollback` (~3500, ±100, tolerating viewport rows)
- Assert terminal is still interactive after the flood

## Design details that matter

**±100 tolerance**: Viewport rows plus shell overhead (prompt lines, echo of the loop command itself) mean the exact oldest line number is not a round figure. The test uses a tolerance band rather than exact equality.

**Configured scrollback via the action dispatcher**: Rather than relying on an implicit default, the test sets the base scrollback up front through the `terminalConfig.setScrollback` action (dispatched via the `__daintreeDispatchAction` debug API) so the action updates both the renderer Zustand store and persists via IPC. Buffer contents are read back through the `__daintreeReadTerminalBuffer` debug API (in `TerminalInstanceService`). If the configured limit changes, the test's assertions follow from the value it set.

**ANSI-colored output**: The test deliberately uses ANSI color codes in the output lines to verify the buffer handles escape sequences correctly alongside line counting.

## Lesson

Terminal scrollback tests must use the configured scrollback limit constant (not a hardcoded number) and must include a tolerance band for shell overhead. The "is the terminal still interactive" assertion after a flood is as important as the buffer bounds check — it detects cases where xterm.js enters a degraded state after processing a large volume of lines.

Export `scrollbackLimit` from the service (or via the debug API) for tests to reference. Don't hardcode it in two places.

## Applies when

- Changes to xterm.js scrollback configuration
- Changes to how PTY data is chunked and sent to the renderer
- Testing buffer memory behavior under sustained high-volume output
