## Context

Main-process error telemetry goes through `@sentry/electron`. `electron/setup/globalErrorHandlers.ts` registers an app-owned `uncaughtException` handler (before `initializeTelemetry()` runs), and `electron/services/TelemetryService.ts` defines `sanitizeEvent` — wired as Sentry's `beforeSend` — to strip PII (home paths, tokens) from every outbound event.

## Problem

Two latent gaps, both invisible in dev:

- **Lost crash reports.** The fatal handler ended with a synchronous `app.exit(1)`. Sentry's transport is async HTTP; the process died before any in-flight crash envelope could be sent. Only manifests in production where the transport is real, so it never shows in local testing.
- **PII leak in stack frames.** `sanitizeEvent`'s frame loop only walked `frame.filename` and `frame.abs_path`. It shipped `context_line`, `pre_context`, `post_context`, and `vars` raw.

## Root cause

- **Ordering / async-vs-sync.** The app-owned handler fires _before_ Sentry's own `onUncaughtExceptionIntegration`, and `app.exit(1)` terminates synchronously — there is no microtask turn for the queued HTTP flush. The fix replaces it with `closeTelemetry().catch(() => {}).finally(() => app.exit(1))`. `closeTelemetry` internally calls Sentry's `close(SENTRY_CLOSE_TIMEOUT_MS)` (2000ms cap) so it drains the transport but can't hang exit. The re-entrant fatal path deliberately stays synchronous (a second crash mid-flush shouldn't wait another 2s).
- **Hidden PII fields.** `contextLinesIntegration` and `localVariablesIntegration` are _default_ integrations in `@sentry/electron`. They populate frames with raw source lines (`context_line`/`pre_context`/`post_context`) and local-variable values (`vars`) _before_ `beforeSend` fires. Those fields routinely contain string literals with user paths, tokens in locals, or transcripts. A sanitizer that only touches `filename`/`abs_path` misses the largest leak surface. Fix walks all four via `sanitizeStringsDeep` (recurses arrays/objects, only mutates strings so numeric/structured locals survive).

## Lesson

- **Never `app.exit`/`process.exit` synchronously from a fatal handler when an async reporter (Sentry, analytics, log shipper) is registered.** Drain it first: `closeTelemetry().catch().finally(exit)`, with a bounded internal timeout so exit can't hang. The reporter's own integration may run _after_ your handler, so you can't rely on it to flush itself.
- **When scrubbing Sentry events in `beforeSend`, scrub the whole frame, not just paths.** Cover `context_line`, `pre_context`, `post_context`, and `vars` — these come from `contextLinesIntegration`/`localVariablesIntegration` (enabled by default) and carry raw source + locals. Use a recursive deep-string scrubber that leaves non-string values intact.
- Pin `fingerprint` on synthetic/analytics events (`["analytics", eventName]`) — Sentry's default fingerprint hash is unstable across SDK upgrades, so grouping silently drifts otherwise; and buffered/replayed events must carry the _same_ fingerprint as direct sends.

## Applies when

- Touching `electron/services/TelemetryService.ts`, `sanitizeEvent`, `closeTelemetry`, or `beforeSend` PII scrubbing.
- Modifying `electron/setup/globalErrorHandlers.ts` or any `uncaughtException`/`unhandledRejection`/fatal-exit path that calls `app.exit`/`process.exit`.
- Adding or upgrading `@sentry/electron` integrations — especially `contextLinesIntegration` / `localVariablesIntegration`, which add new PII-bearing event fields.
- Any work where a crash/exit path must flush an async transport (telemetry, analytics, remote logging) before terminating the process or a utility-process host.
- Investigating "crash reports never arrive in production but tests pass," or secrets/home-paths leaking into Sentry despite a sanitizer being present.
- Designing event grouping/fingerprints for synthetic events to keep issue tracking stable across SDK version bumps.
