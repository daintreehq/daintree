## Context

D2 destructive actions (push, pull-rebase, force-push, cache clears) must show the ACTUAL content being touched, not a count. Three git confirm dialogs each hand-rolled the same async commit-preview box (bordered list, spinner, error+Retry, `max-h-[180px]` scroll): `GitPushConfirmDialog`, `GitPullRebaseConfirmDialog`, and `ForcePushConfirmDialog`; `DevPreviewDestructiveConfirmDialog` followed the same fetch-then-render shape. Issue #9570 documents the triplication and the safety gap it produced.

## Problem

Two of the three copies let the user confirm a push or pull-rebase while the commit preview was still loading or had errored — `onConfirm={() => resolveConfirmation(true)}` unconditionally. The preview was _rendered_, so the dialog visually satisfied the D2 "show actual content" rule, but the confirm button never consulted the preview's state: a blind approve of a shared-state git mutation. Only `ForcePushConfirmDialog` blocked correctly (`if (isLoading) return; if (loadError) return;`). Separately, `AppDialog` hardcoded `role="alertdialog"` for every destructive variant, including these preview dialogs.

## Root cause

Rendering the preview and gating the confirm are two independent wirings, and duplication let them diverge. The preview lives in the dialog's `children`; the confirm gate lives in `confirmDisabled` / the `onConfirm` handler — nothing in the primitive connects them. Each copy-paste of the preview box carried the rendering but only one carried the gate. Note the fix is NOT what the PR body describes: #9575's body (and #9570's desired end state) call for a "preview slot that auto-manages confirm-disabled", but the shipped diff is a `hasPreview?: boolean` passthrough (`ConfirmDialog` → `AppDialog`) plus manual per-dialog `confirmDisabled={commits === null || !!loadError}` — verified still true in the current code. The gate remains a per-consumer responsibility, so a new async-preview dialog can silently recreate the bug. The `check:confirm-wiring` guard (`scripts/codegen/confirm-wiring.mjs`) only verifies a ConfirmDialog-family component coexists with the action ID in some file — it cannot see whether confirm is gated on preview load.

The ARIA half: WAI-ARIA APG scopes `role="alertdialog"` to brief text-only messages. Screen readers flatten everything reachable via `aria-describedby` into a single utterance, so a scrollable commit list inside an alertdialog reads as an uninterruptible wall of text. `AppDialog` now computes `role={variant === "destructive" && !hasPreview ? "alertdialog" : "dialog"}` (`AppDialog.tsx:393`); terse no-preview destructive confirms (kill terminal, delete recipe) keep `alertdialog` so the speech queue still interrupts.

## Lesson

- **Wiring a destructive dialog with an async preview means wiring TWO things: the preview render AND `confirmDisabled` on its load state.** The primitive does not derive one from the other — despite the PR body claiming an auto-managing slot, none exists. Pattern to copy: `confirmDisabled={commits === null || !!loadError}` (`GitPushConfirmDialog.tsx:114`). `ConfirmDialog` also guards inside the handler (`if (confirmDisabled) return;`, `ConfirmDialog.tsx:196`), so the gate holds even against programmatic clicks.
- **Use a null sentinel to distinguish not-loaded from loaded-and-empty.** `commits === null` blocks confirm; `commits.length === 0` is a valid loaded state that renders the empty message and confirms normally. `!commits?.length` would conflate the two and wrongly block an empty-but-loaded preview.
- **Gate only on load-bearing preview data, not ornamental metrics.** `DevPreviewDestructiveConfirmDialog` blocks on `!meta` (WHAT gets deleted) but deliberately does not block when only the sizes fetch fails (byte counts are decoration) — the test "does not disable confirm when only sizes fail" pins this. Blocking on ornamental data would let a slow `du` deny a legitimate action.
- **Any destructive dialog whose body scrolls must set `hasPreview={true}`** to switch from `alertdialog` to `dialog`. Later adopters: `PluginArchiveInstallConfirmDialog` (#11283), `ArtifactOverlay`, and `TerminalDestructiveActionConfirmDialog` which sets it conditionally per content shape (`hasPreview={pending.kind === "deletedWorktreeGroupDismiss"}`).
- **The safeguards doc understates this**: `docs/architecture/destructive-action-safeguards.md` (primitive conventions, bullet 5) still says destructive variants get `role="alertdialog"` unconditionally — the `hasPreview` exception lives only in the code's doc comments. Don't "fix" a preview dialog back to alertdialog to match the doc.
- **`check:confirm-wiring` proves presence, not quality.** Passing the guard means a dialog exists near the action ID; it says nothing about preview gating, so review must check the gate manually on any new D2 dialog.

## Applies when

- Adding or modifying a destructive `ConfirmDialog` that fetches its preview asynchronously (commit lists, file tables, cache manifests) — anything following the `GitPushConfirmDialog` / `DevPreviewDestructiveConfirmDialog` shape.
- Tempted to assume `ConfirmDialog`'s preview handling is automatic because the #9575 PR body says "preview slot ... auto-manages the confirm-disabled state" — it does not; the gate is manual per dialog.
- Reviewing a D2 confirm where `onConfirm` resolves unconditionally, or where the disabled expression uses `!items?.length` instead of `items === null`.
- Deciding the ARIA role for a dialog: destructive + scrollable body → `hasPreview={true}` → `role="dialog"`; destructive + brief text → default `alertdialog`.
- Consolidating the still-triplicated commit-preview box (#9570's shared-slot end state was never built) — the slot must own loading/error/empty AND drive `confirmDisabled`, or it re-opens this gap.
