## Context

`PtyClient` (`electron/services/PtyClient.ts`) is the MAIN-process front-end to the `pty-host` utility process. It keeps `pendingSpawns: Map<string, PtyHostSpawnOptions>` of every live terminal so it can recreate them on the new host after a crash via `respawnPending()` (line ~408), which iterates the whole map and re-sends a `spawn` per entry. `onBeforeRestart` sets `needsRespawn`; the next `ready` event triggers the replay. A sibling map `pendingKillCount` tracks in-flight kills, decremented by host `exit` events.

## Problem

`pendingSpawns` was unbounded. Because it is the source the restart path replays from, every host crash re-sends the entire accumulated map as one synchronous burst. If the host crashes _during_ that replay burst (a fork bomb of terminals can crash the host again), the map is never trimmed, so the next restart replays an even larger burst — restart-storm amplification. The map also never shed entries for terminals whose spawn failed silently, so it grew monotonically across a session.

## Root cause

The map served two roles that look identical but have opposite sizing pressure: a _local tracking set_ (bounded by real live terminals) and a _replay buffer_ fed back into IPC on every restart (whose size sets the fan-out cost of the next crash). Nothing bounded admission, so a pathological or malicious spawn loop turned a single host crash into a self-amplifying restart loop.

## Lesson

Cap admission at the top of `spawn()`: `if (!this.pendingSpawns.has(id) && this.pendingSpawns.size >= MAX_PENDING_SPAWNS)` reject with a `spawn-result` failure carrying `SpawnErrorCode "PENDING_SPAWNS_CAPPED"` (added to the union in `shared/types/pty-host.ts`) so `DevPreviewSessionService` and the renderer's existing failure paths fire — don't throw or silently drop. The `!has(id)` carve-out is load-bearing: a respawn/option-update for an _already-tracked_ id must pass even at capacity, or you'd reject the very replay you're trying to enable. `kill()` deletes from `pendingSpawns`, so kills naturally reclaim slots — the cap is on live fan-out, not lifetime count. The sibling `pendingKillCount` cap (`MAX_PENDING_KILLS = 500`, follow-up #5319) is deliberately **soft** (log-only, still track) because its real defense is `pendingKillCount.clear()` inside `respawnPending()` — kills targeting the dead host will never get an `exit` decrement, so they're flushed on restart rather than admission-gated. `pendingSpawns` gets the **hard** cap because it is replayed, not cleared. Same map shape, opposite bounding strategy, dictated by whether the entries survive a restart.

## Applies when

- Adding/auditing any MAIN-process map that a crash-recovery path replays back into a utility process (`pendingSpawns`, `ipcDataMirrorIds`, future replay buffers in `PtyClient`).
- A spawn/admission queue can grow under a crash loop, fork-bomb, or runaway recipe and you're deciding between a hard admission cap vs. a soft clear-on-restart cap — pick based on whether the entries are replayed or discarded on restart.
- Wiring a new `SpawnErrorCode`: emit it via `spawn-result` so existing renderer/DevPreview failure handling stays correct; never throw from `spawn()`.
- Touching `respawnPending()` / the `ready`-event replay (lines ~379–433) — the cap and the carve-out for already-tracked ids are coupled to that loop.
