## Context

`createHardenedGit` (`electron/utils/hardenedGit.ts`) wraps every git spawn with a sanitized, security-hardened env (`buildHardenedGitEnv`: strips `EDITOR`/`GIT_EDITOR`/`PAGER`/SSH-askpass-family keys, sets `GIT_TERMINAL_PROMPT=0`, locale pins, etc.) and a `UNSAFE_FLAGS` allowlist for simple-git's own risky-flag scanner. The `--continue` path for rebase/merge/cherry-pick/revert (`handleContinueRepositoryOperation` in `electron/ipc/handlers/git-write.ts`) needs one more thing on top: suppress the editor so `--continue` doesn't try to open one in the Electron main process, since `git rebase --continue` has no `--no-edit` flag.

## Problem

Clicking "Continue rebase" (and continue on any in-progress merge/cherry-pick/revert) failed with a toast: `Use of "EDITOR" is not permitted without enabling allowUnsafeEditor` (#10786). `Abort rebase` still worked, which pointed suspicion away from the hardening wrapper and toward something rebase-specific. The toast named `EDITOR` even for users who never set it, which read as a false positive.

## Root cause

Two independent simple-git behaviors compounded. First, simple-git 3.36.0 (a `^3.33.0` semver-range float) added an env scanner in `@simple-git/argv-parser` that rejects any spawn-env key normalizing to `EDITOR`, `GIT_EDITOR`, or `GIT_SEQUENCE_EDITOR` unless the instance was built with `unsafe.allowUnsafeEditor: true`. The pre-existing continue-path helper, `withNonInteractiveEnv`, set `GIT_EDITOR: "true"` specifically to suppress the editor — the exact value the scanner now blocked, regardless of the fact that the value itself was safe. The scanner fires on key presence, not value origin or intent.

Second, `withNonInteractiveEnv` spread raw `process.env` (leaking the user's actual shell `EDITOR` into the child, the first thing the scanner saw and named in the error) and then called `.env()` a second time on a git instance `createHardenedGit` had already configured. `simple-git`'s `.env()` is last-write-wins on the whole object, not a merge — so this second call silently discarded every hardening var from the first call (`GIT_TERMINAL_PROMPT`, `GIT_OPTIONAL_LOCKS`, `GCM_INTERACTIVE`, `GIT_ASKPASS`, locale pins) on the continue path only. This is the same trap issue #7058 previously documented for a different call site. The fix replaced the two-call pattern with one `buildContinueEnv()` that spreads `buildHardenedGitEnv()` and layers `GIT_EDITOR`/`GIT_MERGE_AUTOEDIT` on top, called via a single `.env()`, plus `allowUnsafeEditor: true` added to `UNSAFE_FLAGS`. A third, unrelated trap surfaced verifying against real git 2.54.0: `git merge --continue --no-edit` fails with exit 129 (`--continue expects no arguments`) — merge's `--continue` takes zero flags, unlike cherry-pick/revert's `--continue --no-edit`. `GIT_MERGE_AUTOEDIT=no` does the suppression work `--no-edit` can't.

## Lesson

- **`simple-git`'s `.env()` is last-write-wins on the whole object, not a merge.** Never call `.env()` twice on the same instance expecting the second call to layer on the first — audit any path that does (`grep -n "\.env(" electron/`) and consolidate into one env-building function whose output is complete, spread from the hardened base then overlaid with path-specific keys.
- **A `^` semver range on a dependency whose parser enforces security policy (like `simple-git`) can silently add new spawn-env restrictions on a routine `npm install`.** Pinned exact to `3.36.0` (no caret) so a future minor can't re-float unnoticed; if bumping it, re-diff `@simple-git/argv-parser`'s unsafe-flag list against `UNSAFE_FLAGS` in `hardenedGit.ts`.
- **simple-git's env scanner rejects a key by its name, not by whether the value is safe.** Setting `GIT_EDITOR: "true"` to suppress an editor is exactly as blocked as leaking a real editor command — the only way past it is the matching `allowUnsafeEditor` flag in the `unsafe` config passed to `createHardenedGit`/`createAuthenticatedGit`/`createWslHardenedGit`.
- **`git merge --continue` takes zero arguments; `cherry-pick --continue`/`revert --continue` accept `--no-edit`; `rebase --continue` accepts neither.** Don't assume the shapes are interchangeable across continue-style operations — verify against the real git binary, not just simple-git's typings, before adding a flag.
- **Never spread raw `process.env` into a hardened git spawn.** Always route through `buildHardenedGitEnv` (or a wrapper that spreads it first) so `BLOCKED_INHERITED_GIT_ENV_KEYS` stripping applies — spreading `process.env` directly reintroduces every key hardening was built to remove.

## Applies when

- Touching `electron/utils/hardenedGit.ts` (`UNSAFE_FLAGS`, `BLOCKED_INHERITED_GIT_ENV_KEYS`, `buildHardenedGitEnv`, `buildContinueEnv`) or any `createHardenedGit`/`createAuthenticatedGit` call site in `electron/ipc/handlers/git-write.ts`.
- Adding a new git operation that needs non-interactive/editor-suppressed behavior (any future `--continue`-like flow, or a new `.env()` overlay on an existing hardened instance).
- Bumping `simple-git` in `package.json` — it is pinned exact (`3.36.0`, not `^3.36.0`) on purpose; check the new version's `@simple-git/argv-parser` unsafe-flag list before widening the pin.
- Diagnosing a git operation that fails with a `simple-git`/`argv-parser` error naming an env var the user never set (leaked-inheritance smell) or a hardening feature (locale, terminal prompt, askpass) that stopped applying on one specific code path but not others.
- Adding a new `--continue`/no-flags git subcommand — confirm its actual accepted-argument shape against the real git binary rather than mirroring a sibling operation's flags.
