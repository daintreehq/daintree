## Context

Daintree restarts crashed utility-process hosts (pty-host, workspace-host) and the main-process watchdog automatically with backoff. Each restart manager (`PtyHostLifecycle`, `WorkspaceHostProcess`, `MainProcessWatchdogClient`) needs a crash-loop guard that gives up after repeated failures so it stops respawning a process that can never come up cleanly.

## Problem

`PtyHostLifecycle` used a per-cycle integer `restartAttempts` counter that was reset to 0 on every `markReady()`. That counter has two opposite failure shapes baked into one number: three instant crashes (host dies before `markReady()` ever fires) trip the cap in milliseconds, while three crashes spread across hours each get individually "forgiven" by the intervening successful ready and never accumulate — so a slow-but-persistent crash loop is never caught.

## Root cause

An integer counter cannot distinguish "3 crashes in 50ms" from "3 crashes over 6 hours" — it only knows count-since-last-ready. The correct primitive is a sliding window of crash _timestamps_ (`crashTimestamps: number[]`), trimmed to entries within `CRASH_WINDOW_MS` at crash-record time, tripping when `length >= CRASH_THRESHOLD`. But porting that window introduced two non-obvious ordering invariants that an integer counter never needed:

- **Do NOT clear the window on `markReady()`.** Clearing on ready re-creates the integer counter's blind spot for a crash-ready-crash-ready oscillation: each fresh ready would wipe the history right before the next crash, so the loop never accumulates. The window must only be cleared by a _stability timer_ that fires after a full `STABILITY_TIMEOUT_MS` of clean running.
- **The stability timer MUST be cancelled on crash.** `markReady()` arms a `setTimeout` to clear the window. If the host crashes ~100ms before that timer fires, an un-cancelled timer fires _after_ the crash and wipes `crashTimestamps` even though the host never ran cleanly for the full interval — silently defeating the three-strike guard for any crash-near-ready pattern. `handleExit()` must `clearTimeout(stabilityTimer)`.

`manualRestart()` (user-initiated) deliberately clears the window for a fresh budget; the stability/decay clear is the only _automatic_ clear path.

## Lesson

For any auto-restart crash-loop guard on a process host:

- Use a sliding window of crash timestamps trimmed to `CRASH_WINDOW_MS`, not an integer counter that resets on success. An integer counter conflates fast-loop and slow-loop failure shapes and one of them always slips through.
- Decay the window only via a stability timer that requires a full clean interval — never clear it on the per-cycle "ready"/"fork OK" success signal, or a crash-ready-crash-ready oscillation evades the guard.
- Cancel the stability timer in the crash/exit handler so it can't fire post-crash and wipe a window the host never actually earned.
- Unref both the restart timer and the stability timer (`timer.unref?.()`) so they don't pin the Electron event loop alive past `app.quit`.
- This is now a three-way replicated policy (`PtyHostLifecycle`, `WorkspaceHostProcess`, `MainProcessWatchdogClient`) with constants intentionally duplicated (not imported — different layers) and kept in lockstep by `electron/services/__tests__/crashGuardAlignment.test.ts`. If you tune `CRASH_THRESHOLD`/`CRASH_WINDOW_MS` in one, update all three or the alignment test fails.

## Applies when

- Adding or modifying crash/restart logic in `PtyHostLifecycle.ts`, `WorkspaceHostProcess.ts`, `MainProcessWatchdogClient.ts`, or `GpuCrashMonitorService.ts`.
- Writing any "give up after N failures" guard for a utility process, child process, or reconnecting client, where successes and failures interleave over time.
- You see a `restartAttempts`-style integer reset on a success callback (`markReady`, `onForkSuccess`, `onConnect`) — that is the trap; it should be a timestamp window with a stability-timer decay.
- Tuning `CRASH_THRESHOLD` / `CRASH_WINDOW_MS` / `STABILITY_TIMEOUT_MS` constants (alignment enforced by `crashGuardAlignment.test.ts`).
- Debugging "host respawns forever and never gives up" (slow loop) or "host gives up far too eagerly" (fast loop) symptoms.
- Reviewing a sliding-window guard for the subtle clear-on-ready / cancel-timer-on-crash invariants — testing these requires faking `Date` alongside the timer functions (`vi.useFakeTimers({ toFake: ["setTimeout","clearTimeout","setImmediate","Date"] })`) so `Date.now()` advances with the timers.
