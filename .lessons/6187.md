## Context

The shadcn-style Radix wrappers in `src/components/ui/` (popover, dropdown-menu, context-menu, select, tooltip) drive their open/close motion entirely through Tailwind utility classes keyed off Radix's `data-[state=open|closed]` and `data-[side=*]` attributes — e.g. `data-[state=open]:animate-in`, `fade-in-0`, `zoom-in-95`, `slide-in-from-top-2`. These utilities historically came from the `tailwindcss-animate` plugin bundled with shadcn setups.

## Problem

After the Tailwind v3→v4 migration, every overlay (popover, dropdown, context menu, select, tooltip) opened and closed instantly with no transition. There was no build error, no console warning, no lint failure — the class names were still on the elements, they just resolved to nothing. Easy to ship and only catch on visual review.

## Root cause

Tailwind v4 does not ship the `animate-in`/`animate-out`/`fade-in-*`/`zoom-in-*`/`slide-in-from-*` utilities — the old `tailwindcss-animate` plugin is not v4-compatible and was not auto-replaced by the migration. Unknown Tailwind utility classes are emitted as-is into the DOM (Tailwind never errors on a class it doesn't recognize), so the wrappers kept rendering `animate-in` etc. as dead class names with no matching CSS rule. The animations silently became no-ops. The v4 successor is the standalone `tw-animate-css` package, imported as plain CSS (`@import "tw-animate-css";` in `src/index.css`, after `@import "tailwindcss";`) — not a `@plugin`.

## Lesson

- On any Tailwind v3→v4 upgrade, audit for `tailwindcss-animate` usage: grep for `animate-in`, `animate-out`, `fade-in`, `zoom-in`, `slide-in-from`. These do NOT exist in v4 core. Add `tw-animate-css` and `@import` it in `src/index.css`.
- Dead Tailwind utilities fail silently — there is no compile/lint signal. A green build with intact class strings does NOT prove the utilities resolve. Verify animation-bearing classes by checking the built CSS emits `@keyframes enter`/`@keyframes exit`, or with a render test asserting the class set (see `src/components/ui/__tests__/radix-animation-classes.test.tsx`).
- Reduced-motion is handled via `tw-animate-css`'s CSS custom properties, not by killing the whole animation. Under `prefers-reduced-motion` and `body[data-reduce-animations="true"]`, zero only the spatial vars (`--tw-enter-scale`, `--tw-exit-scale`, `--tw-enter-translate-x/y`, `--tw-exit-translate-x/y`) on `[data-state][data-side]` so the fade survives — preserves WCAG 2.3.3 (`src/index.css`, both blocks must stay in sync).
- Per-state durations are applied as separate `data-[state=open]:duration-200` / `data-[state=closed]:duration-[120ms]` classes aligned to the `animationUtils.ts` Tier-2 tokens (palette tier 150/100ms for tooltip). When adding a new overlay wrapper, copy the full class set onto BOTH the Content and SubContent variants — SubContent is the one most often forgotten.

## Applies when

- Migrating Tailwind v3→v4, or adding/auditing any `src/components/ui/` Radix wrapper (popover, dropdown-menu, context-menu, select, tooltip, or a new overlay primitive).
- An overlay/menu/tooltip opens or closes with no transition despite the `animate-in`/`fade-in-0`/`zoom-in-95`/`slide-in-from-*` classes still being present on the element.
- Touching `src/index.css` import order, `prefers-reduced-motion` / `data-reduce-animations` motion-suppression blocks, or the `tw-animate-css` dependency.
- Investigating why a Tailwind utility class appears in the DOM but produces no styling (silent unknown-utility passthrough).
- Adding a new shadcn-derived component copied from upstream docs that assumes `tailwindcss-animate` is installed.
