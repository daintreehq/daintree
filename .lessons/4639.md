## Context

PR #4598 added ack-based backpressure to the PTY host → renderer MessagePort path using transferable `ArrayBuffer`s. It was fully reverted because it caused all agent terminals to render blank until clicked.

## Problem

Two bugs, both caused by binary `ArrayBuffer` transfer over MessagePort:

1. **Node.js Buffer pool corruption**: `Buffer.from(data)` for small strings uses a shared 8KB slab pool — multiple buffers share the same underlying `ArrayBuffer`. Transferring `bytes.buffer` as a transferable detaches the _entire_ slab, corrupting every other `Buffer` in the PTY host that shared that pool.

   ```js
   const b1 = Buffer.from("hello");
   const b2 = Buffer.from("world");
   console.log(b1.buffer === b2.buffer); // true — same 8192-byte slab
   ```

Fix requires copying into a dedicated `new ArrayBuffer(n)` — never transfer `Buffer.buffer` directly.

2. **Blank terminals after Buffer fix**: Even after patching the slab issue, blank terminals persisted. The full PR revert was needed. Root cause traced to backpressure gating (`portQueueManager.isAtCapacity()`) interacting badly with React StrictMode's mount/unmount/remount double-cycle — the renderer's `onData` callback registration was arriving after the host had already queued and stalled.

## Root cause

Using transferable `ArrayBuffer` with Node `Buffer.from()` corrupts the shared slab pool. Additionally, backpressure capacity checks that gate terminal output interact with the renderer's async callback registration lifecycle in ways that cause blank terminals.

## Lesson

- **Never transfer a slab-aliased `Buffer.buffer` directly** over MessagePort. node-pty Buffers under ~4KB share an 8KB pool slab; transferring a slab-backed buffer detaches the slab and corrupts every other Buffer that aliases it. This invariant is still load-bearing today and is documented inline in `electron/pty-host/portBatcher.ts` (`mergeChunks`, citing PR #4639).
- **Binary transport IS used today — but only over buffers proven not to alias the slab.** The transport later moved from string output back to transferable `Uint8Array` (see `electron/pty-host/handlers/connection.ts`, which posts `{ type: "data", id, data, bytes }` with `[data.buffer]` in the transfer list). The slab invariant is preserved via an `owned` ownership flag in `PortBatcher`: a chunk is only transferred without copying when it fully owns its ArrayBuffer (`byteOffset === 0`, occupies the whole buffer — escaped the slab via `new Uint8Array(...)` at ingestion); otherwise `mergeChunks` copies into a fresh allocation. A `batchDataToString` fallback path remains for postMessage transfer errors. (Strings were the original #4639 reimplementation; the owned-transfer optimization landed in #8367.)
- **React StrictMode doubles mount/unmount**: any capacity-based backpressure that stalls before `onData` registers will silently black out a terminal. The `earlyDataBuffer` map in `src/clients/terminalClient.ts` was added to handle this race — it buffers data that arrives before a live callback is registered, deferring the ACK until the callback fires.
- The original #4639 reimplementation used string `"ack"` messages in a capacity queue — simple, correct, and avoiding shared-memory/transferable semantics. String `"ack"` messages are still the backpressure ack mechanism (`port.postMessage({ type: "ack", id, bytes })` in `terminalClient.ts`); only the data direction later regained binary transfer under the ownership guard above.

## Applies when

Implementing binary MessagePort transport in Electron's PTY host, or any backpressure mechanism gating output to renderer callbacks that may not be registered yet (especially under React StrictMode).
