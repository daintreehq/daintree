## Context

The file-viewer dialog (`FilePane` rendered inside `PanelDialogHost`) hosts a markdown source/rendered toggle. `PanelDialogHost` passes `AppDialog` only a `max-h-[85vh]` clamp and no definite height, so the dialog sizes itself to content every single frame. `MarkdownViewer` loads its rendered path through `lazy()` + `Suspense`, whose fallback is a 10-line `SkeletonText` with no height floor (the source path has `min-h-[300px]`, the rendered path had nothing equivalent).

## Problem

Switching a markdown file from source to rendered made the whole dialog visibly shrink to the skeleton's height, then jump back up once the lazy chunk resolved and the real document committed (issue #11255). It reproduced every time the chunk wasn't already warm, i.e. on the first toggle in a session — easy to write off as "just Suspense being Suspense" rather than a fixable layout bug.

## Root cause

`FilePane` swaps element types between source and rendered mode, so React remounts the subtree on every toggle — there's no persistent box for a `ResizeObserver` or a `useLayoutEffect` in the _new_ subtree to defend, because by the time either fires, the old content is already gone and the Suspense fallback has already painted at its own (smaller) height. The pin has to be taken **synchronously inside the click handler that triggers the mode change**, before the Zustand `setFileViewMode` action even runs — `FilePane.handleViewModeChange` calls `heightHold.hold()` (which reads `getBoundingClientRect()` off the still-live source subtree) and only then dispatches the store update. A `useLayoutEffect` in the new (rendered) subtree is one commit too late: it only runs after React has already committed the Suspense fallback, i.e. after the box has already shrunk.

Release is symmetric and non-obvious in its own way. `useHeightHold.handleRendered` is wired to `MarkdownDocument`'s own `useEffect(() => onRendered?.(), [onRendered])` — the _first-commit_ signal of the real content, not a timer — and then waits two more `requestAnimationFrame`s before clearing `minHeight` (one frame for layout, one for paint; releasing in the commit's own frame hands the dialog a pre-layout height and reintroduces the jump). An earlier revision had a 4-second deadline that force-released the pin if `onRendered` never fired; review deleted it because firing while the chunk is still loading collapses the dialog to the skeleton and re-expands it later — the _original bug, merely delayed_, not fixed. Because `min-height` is a floor and not a cap, there is no shrink-then-grow sequence to defend once the pin is armed: taller content just grows past the floor (release is a no-op), shorter content is held until release settles it in one animated move (120ms panel-minimize tier, `.file-pane-body-releasing`) — which is why no `ResizeObserver` is needed.

## Lesson

- **When a content-sized container (only `max-height`, no `min-height`/fixed `height`) swaps in a `lazy()`/`Suspense` subtree that remounts rather than updates, a layout effect in the new subtree is always one commit late** — it runs after the fallback has already painted. Take the measurement **synchronously in the event handler that triggers the swap**, on the still-mounted old subtree, before the state update that causes the remount.
- **A "wait for X, but fall back after Nms" timeout on a pin/hold can silently reintroduce the exact bug it's protecting against** — firing mid-load drops the pin before the real content is ready, reproducing the original collapse-then-expand on a delay. If the awaited signal never arrives, holding forever at the old height beats guessing a deadline; review deleted this PR's 4s cap for exactly that reason (follow-up commit `15a2746a6`, same PR).
- **`min-height` as a pin needs no `ResizeObserver`** when the invariant is "content only replaces content that used to be visible" — a floor can only be grown past (no-op) or held-then-released (one settle), never shrunk-then-regrown, so there's nothing an observer would ever catch that the hold/release lifecycle doesn't already handle.
- **Release the pin on the content's first commit signal (`onRendered` forwarded up through `MarkdownViewer` → `MarkdownDocument`'s `useEffect`), then wait two more animation frames**, not one — the first frame is layout-only, releasing there hands the host a pre-layout height and reproduces the jump; the second is what confirms paint.
- **Cancel the pin on every real exit path, not just the happy path**: reverting the toggle before the chunk lands, the file path changing under an active pin, and the pane being promoted out of the dialog into a layout-sized grid/dock host (a content-sized `min-height` floor is meaningless — and potentially harmful — once the host itself sizes the box).

## Applies when

- Building or reviewing any dialog/panel that has only a `max-height` clamp and swaps in a `lazy()`/`Suspense` chunk, an async-loaded viewer, or any remounting subtree — check whether the fallback has a height floor before assuming a `useLayoutEffect` fix will work.
- Diagnosing a UI element that "flickers smaller then bigger" or "jumps" right after a mode/tab toggle, especially the first time that mode is used in a session (cold lazy chunk).
- Tempted to add a timeout/deadline to a hold-until-signal pattern (loading guards, pending-state pins, debounced releases) — check whether firing that timeout while the awaited condition is still false reproduces the original symptom instead of preventing it.
- Touching `src/panels/file/useHeightHold.ts`, `FilePane.tsx`'s view-mode toggle, or `MarkdownViewer`/`MarkdownDocument`'s `onRendered` forwarding chain — the pin/release/cancel lifecycle and its epoch-based staleness guard are load-bearing, not incidental.
- Adding a new content-sized dialog host on top of `PanelDialogHost`/`AppDialog` and wiring any async-loaded content into it.
