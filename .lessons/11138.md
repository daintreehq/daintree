## Context

Every panel kind (`terminal`, `browser`, `dev-preview`, `diff`, `file`, `review`) is handed a shared `onClose` prop from `registry.tsx` (`onClose: (force?: boolean) => void`, line 54), backed by `usePanelHandlers.handleClose`. The optional `force` flag is load-bearing: `PanelHeader.tsx:1222` calls `onClose(e.altKey)` so Alt+Click deliberately routes to permanent deletion, while a plain click leaves `force` undefined and goes through the recoverable path. `ReviewPane` renders `ReviewHubContent`, which owns its own internal Close button and declares its own prop as a plain zero-arg `onClose: () => void` (`ReviewHubContent.tsx:86`).

## Problem

#11116: the Review panel's own Close button and its Escape fallthrough did nothing — the panel stayed closable only via the surrounding grid chrome. Root cause was mundane (`ReviewPane` never declared or destructured `onClose` at all, so `ReviewHubContent` got a literal `noop`), but fixing it by declaring the prop and forwarding it bare — the obvious one-line change — would have "fixed" the dead buttons while silently making every Review-panel close permanent and unrecoverable.

## Root cause

`usePanelHandlers.ts`'s `handleClose` branches on its argument: `if (force) { removePanel(terminalId); ... }` (permanent, no `Reopen Last Closed`) versus the default path, `trashPanelGroup` via `requestPanelClose` (optimistic, recoverable). `ReviewHubContent` wires its internal Close button bare — `onClick={onClose}` at line 1514, and calls `onClose()` bare again on its Escape path at line 1284 — against its own declared `onClose: () => void`. Forwarding `ReviewPane`'s real `onClose: (force?: boolean) => void` straight into that slot (`<ReviewHubContent onClose={onClose} />`) type-checks cleanly under `tsc --strict` — verified directly: a function accepting an optional trailing parameter is assignable anywhere a zero-arg function is expected, because TS considers dropping an unused optional/trailing parameter always safe. That rule is correct for ordinary callers, but `ReviewHubContent`'s own `onClick={onClose}` line then hands that "zero-arg" value a live `MouseEvent` at runtime — also type-checked clean, since a bare `() => void` is likewise assignable into a `MouseEventHandler` slot (JS silently drops unread arguments). Neither assignment is wrong in isolation; chained, the compile-time fiction of "zero args" evaporates and the actual underlying function is still `handleClose`, so the click's `MouseEvent` — a truthy object — lands in `force` and takes the destroy-without-recovery branch. No `tsc` error anywhere in the chain flags this; it was caught only because the PR author reasoned about the runtime call graph instead of trusting the types, and wrote a test (`ReviewPane.test.tsx`) whose stub reproduces the real child's exact bare `onClick={props.onClose}` wiring rather than a clean mock.

## Lesson

- **A prop typed `(x?: T) => void` can be forwarded into any narrower callback slot (`() => void`, a bare `onClick`) with zero TypeScript errors at every hop** — dropping an optional/trailing parameter is always assignability-safe by design, so the type system will never flag the chain that leads to a live event landing in that parameter at runtime. Verified with an isolated `tsc --strict` compile of the exact shape: `ReviewHubContent`-style bare forward → zero diagnostics.
- **Before forwarding any `onClose`/`onDismiss`-shaped prop into a child that has its OWN internal close control, read how the child actually invokes its own prop** (`grep onClick=\{onClose\}` / `onClose()` in the child), not just its declared prop type — the declared type is often narrower than the value actually flowing through it.
- **Wrap with a zero-arg adapter whenever forwarding across this boundary**: `const handleContentClose = useCallback(() => onClose(), [onClose])`, exactly as `ReviewPane.tsx` now does — this is the only form immune to the parameter falling through.
- **Test the child's real wiring shape, not a clean mock.** `ReviewPane.test.tsx`'s stub deliberately reproduces `ReviewHubContent`'s bare `onClick={props.onClose}`, and asserts both call-count (catches the no-op regression) and argument falsiness (catches the force-close hazard) — a mock that calls `onClose()` cleanly, or one that only checks call count, would pass on the dangerous bare-forward version.
- **Any panel kind that adds its own internal close affordance inherits this risk** — `registry.tsx`'s shared `onClose: (force?: boolean) => void` contract flows into every panel body (`src/panels/*/`), so `browser`, `dev-preview`, `diff`, `file`, and `terminal` panels all carry the same hazard the moment one of them wires its own Close button instead of relying solely on `PanelHeader`'s.

## Applies when

- Touching `src/panels/registry.tsx`'s `onClose` contract, `usePanelHandlers.ts`'s `handleClose`, or any panel body under `src/panels/*/` that renders its own internal close/dismiss control alongside the grid's `PanelHeader`.
- Forwarding any handler shaped `(flag?: boolean) => void` (or similar optional-param-as-semantic-flag) across a component boundary into a JSX event prop (`onClick`, `onKeyDown`) — check arity at the actual call site, not the declared type.
- Reviewing a "just forward the prop" one-line fix for a dropped/no-op callback — trace what the receiving component's own JSX actually calls it with before approving.
- Diagnosing "close works from the panel header but not from the panel's own button" (or the reverse), or "Reopen Last Closed doesn't restore something that visually closed."
- Adding a new panel kind whose content needs its own Close affordance — also note `ReviewPane`'s worktree-unavailable `EmptyState` branch has no close control at all (pre-existing gap, out of scope of #11138, not yet filed).
