## Context

`ProjectStore` (`electron/services/ProjectStore.ts`) has always minted a project's id via `generateProjectId(path) = sha256(path)`, and that id is the primary key for everything project-scoped: the per-project state directory, settings, secure env, panel/terminal ids, terminal `.restore` scrollback, Daintree Assistant hibernation, and the session journal. Issue #11282 asked for a "Move or rename project" workflow that keeps all of that continuous across a folder move or rename; #11285 is phase 1, the identity layer the rest of #11282 builds on.

## Problem

Before this PR, `relocateProject` had to delete the old DB row, insert a new one under a freshly hashed id, `fs.cp` the entire state directory across, call `migrateEnvForProject`, invalidate both the old and new state-cache entries, and roll all of it back by hand on any failure. The renderer's `locateProject` then treated the old id as dead and called `useHelpPanelStore.getState().clearHibernateSession(projectId)` — garbage-collecting the Assistant's hibernated conversation for what was, from the user's perspective, the same project. It looked like a hibernation-cleanup bug or a migration-robustness bug; it was actually neither, both were correct implementations of an identity model that was wrong.

## Root cause

`generateProjectId` derived a supposedly-durable identity from the one project attribute guaranteed to change: its filesystem path. Every symptom (the copy/delete dance, the two-sided cache invalidation, the orphaned hibernation session) was a correct consequence of that choice — patching `relocateProject` in place could never remove the cascade, only removing the cause could. The fix makes a registered id immutable for the life of the project: reattaching a moved folder becomes `updateProject(id, { path })`, an ordinary column update, and everything keyed by the id stays reachable with zero copying or re-keying. Moves are detected via a git-tracked anchor — `.daintree/project.json` gains an optional `id` field (written by `ProjectIdentityFiles.writeInRepoProjectIdentity`) holding the project's real 64-hex id — and disambiguated from a clone, which inherits that same tracked anchor, by `tryAdoptMovedProject` checking whether the anchored project's _original_ registered path still exists: present means copy, gone means move. A subtler consequence is that an id can now outlive the path it was hashed from, so `mintProjectId` needed its own collision guard against a stale hash being reused by an unrelated later project created at the same path.

## Lesson

- **Never derive a registered/durable identity from an attribute that can change.** `id = hash(path)` looked stable but wasn't; the fix is immutable-once-registered plus `ProjectStore.resolveProjectIdForPath(path)` as the one correct lookup — it resolves through the DB by path and only falls back to `generateProjectId` for a path that was never registered. Never call `generateProjectId(path)` to _look up_ an existing entity, only to mint a brand-new one.
- **An id that outlives the value it was hashed from needs a collision guard at mint time, not just at lookup time.** `mintProjectId` retries with `randomBytes(32)` if the preferred hash is already taken by a live row _or_ an orphaned state directory (`isProjectIdTaken` checks both) — cleanup after a removed project is best-effort, so a leftover directory can outlive its row and must still block reuse.
- **Copy-vs-move is undecidable from the new location alone when the anchor is git-tracked (clones inherit it too).** Check the _old_ location instead: anchored project's original path still there means copy, gone means relocated. Every uncertain case (EACCES/EIO on the stat, anchor pointing at the currently-open project, invalid/unknown anchor id) falls through to "register fresh" — wrong-but-safe, since a declined move just costs a manual re-link while a wrongly-accepted one hands one project's settings/secure-env/panels to an unrelated repo.
- **A partial-patch writer that rebuilds the whole record silently erases fields the caller didn't pass.** `writeInRepoProjectIdentity` used to build `{version, name, emoji, color}` from scratch on every settings edit; adding the `id` anchor required explicitly reading the existing on-disk id and carrying it forward when the caller's patch omits it, or an unrelated emoji/color edit would silently disarm move detection.
- **Fixing the hashing convention at one call site does not fix the other callers — grep for all of them.** This PR repointed `WorkspaceHostPool` to `resolveProjectIdForPath` and explicitly deferred `WorkspaceHostEventRouter` and workspace-host `WorkspaceService` (both still call `generateProjectId(path)` directly, per the PR body). It missed a third, uncalled-out one: `electron/services/PullRequestService.ts:379` (`this.projectId = generateProjectId(cwd)`) still hashes the path — verified still present. Before treating project-move support as complete, `grep -rn generateProjectId electron src shared` and check every hit.
- **An `async`-gapped check/mint/insert sequence is a TOCTOU race, not just a design nicety.** `addProject` awaits `readInRepoProjectIdentity` and `tryAdoptMovedProject` before reaching `mintProjectId`, so two concurrent `addProject` calls for the same brand-new folder can both pass the initial `getProjectByPath` miss, each mint a distinct id (the `path` column has no unique index), and both insert — two rows for one directory. The fix is a second `getProjectByPath` re-check immediately before the insert, in the same tick as minting; add that re-check whenever a mint-then-insert sequence has awaits ahead of it.

## Applies when

- Touching `electron/services/ProjectStore.ts` identity/relocation logic (`addProject`, `relocateProject`, `tryAdoptMovedProject`, `mintProjectId`, `isProjectIdTaken`) or anything keyed by `projectId`.
- Adding a new consumer that needs a project's id from a path — use `projectStore.resolveProjectIdForPath`, never `generateProjectId(path)`, unless you are intentionally minting a new project's id.
- Designing any "was this entity moved or copied" detection (worktrees, plugins, recipes) — the git-tracked-anchor-plus-check-the-old-location pattern generalizes beyond projects.
- Diagnosing "Assistant/session/hibernation state disappeared after I moved or renamed a project folder" — confirm `locateProject`/relocation did not regenerate the id; post-#11285 it shouldn't, and if it does the immutable-id invariant has regressed.
- Reviewing any partial-patch persistence writer that reconstructs a record from scratch (`ProjectIdentityFiles`-style) — verify fields the caller didn't specify are read back and carried forward, not dropped.
