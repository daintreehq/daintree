## Context

The forge-provider abstraction (mid-May 2026, commits `9828a3caa` / `d6ceee393`, direct to develop) made the provider-agnostic `forge:*` IPC handlers the primary dispatch path; the `github.*` actions became deprecated aliases delegating to `forge.*`. Main-process anti-flood protection in this codebase is `checkRateLimit(channel, maxCalls, windowMs)` (`electron/ipc/utils.ts`) called as the first statement of each handler — an established convention across 13+ handler files, with dedicated wiring suites (`github.rateLimit.test.ts`, `worktree.rateLimit.test.ts` at the time). Issue #9956 found the new surface never inherited it.

## Problem

The `github.*` handler file carried 29 `checkRateLimit` calls; `forge.ts` and `forgeData.ts` had **zero** — 14 entry points fully uncapped. `forge:open-issues` / `open-prs` / `open-commits` / `open-issue` call `openExternalUrl` (which has no internal throttle), so a buggy or compromised renderer could browser-tab-bomb the user with no cap. Two things made the gap easy to miss: the `forgeData.ts` header comment claimed the file split "keeps rate-limit/error handling for reads from tangling with the action surface" — describing a guard that did not exist in the file — and the 150ms single-flight coalescer in `forgeData.ts` looked like throttling. The same migration also dropped the `path.isAbsolute(cwd)` check the `github.*` handlers enforced: `resolveForCwd` only checked non-empty.

## Root cause

Nothing structural carries cross-cutting guards across a surface rewrite. `typedHandle` / `defineIpcNamespace` inject no rate limiting or path validation; every guard is a manually placed first statement inside the handler body. The forge surface was written fresh from the normalized `ForgeProviderImpl` contract rather than by porting `github.ts` handler-by-handler, so everything orthogonal to the contract — anti-flood budgets, cwd validation — silently stayed behind in the old file. The two look-alikes then masked the hole: a stale-guarantee comment (written about the surface being replaced, pasted onto the replacement) and a coalescer that only collapses **concurrent identical** reads (same `cwd` + args key) — sequential calls and distinct-arg floods pass straight through, so it is not a rate limiter at all.

#10104 restored the guards with budgets mirroring the replaced channels (`open-*` 20/10s, `assign`/`unassign`/`validate-token`/`set-credential` 5/10s, `list-*` 10/10s, `get-issue`/`get-pr` 25/10s, misc 10/10s), restored `path.isAbsolute` at the shared choke point `resolveForCwd` (one fix covers every forge handler), and corrected the false comment. Placement detail: `forge:classify-push-error` validates-then-returns-`null` on bad input, so the guard sits **before** that swallowing logic — floods reject loudly with `RATE_LIMITED` instead of degrading to silent `null`s.

## Lesson

- **When a new handler namespace replaces an old one, diff the old file's guard set channel-by-channel before deleting or deprecating it.** Grep the outgoing surface for `checkRateLimit`, `path.isAbsolute`, and payload validation, and carry each budget to its successor channel explicitly — guards are per-handler statements, and as of today there is still no lint rule or check script enforcing `checkRateLimit` presence, so this trap is live for every future surface migration (new forge providers, MCP tool surface, plugin host channels).
- **A single-flight coalescer is not a rate limiter.** The `forgeData.ts` `createSingleFlight` (still there, ~line 181) dedupes only concurrent identical reads; sequential or distinct-arg call floods are uncapped. Never accept "there's a coalescer" as flood protection when auditing a read surface.
- **Verify claimed guards by grep, never by comment.** The `forgeData.ts` header asserted rate-limit handling that never existed in the file — a guarantee-describing comment can be inherited from the surface it replaced. If a comment names a protection, confirm the symbol appears in the same file.
- **Put `checkRateLimit` before any error-swallowing validation.** Handlers that return `null`/default on bad payloads (e.g. `forge:classify-push-error`) would otherwise convert a flood into silent no-ops; guard-first makes abuse visible as `RATE_LIMITED` rejections.
- **Bucket semantics: `checkRateLimit` keys by `channelToCategory[channel] ?? channel`** (`electron/ipc/utils.ts`). Forge channels deliberately have no category entries, so each gets an independent per-channel bucket — decide per-channel vs shared-category explicitly when adding a handler; a shared category means one chatty channel starves its siblings.
- **The only structural backstop is an exhaustive wiring test.** `forge.rateLimit.test.ts` `it.each`-covers every channel of the surface against a fake non-GitHub provider (proving the guards sit on the normalized contract), and behavioral specs reset state via `_resetRateLimitQueuesForTest`. It worked: `github.ts` and its test are now fully deleted (GitHub ships as a builtin forge plugin) and the forge surface has since grown to ~30 guarded handlers in `forge.ts` alone with the convention intact.

## Applies when

- Replacing, splitting, or rewriting any IPC handler surface where a new namespace supersedes an old one — the successor must inherit the predecessor's `checkRateLimit` budgets and validation gates explicitly.
- Adding a handler to `electron/ipc/handlers/forge*.ts` — first statement is `checkRateLimit` with a budget matched to the operation class (open 20, mutation/token 5, list 10, get 25 per 10s).
- Reviewing or asserting that a surface "has rate limiting" — grep for `checkRateLimit` in that exact file; header comments and coalescers do not count.
- Evaluating renderer-compromise blast radius of channels that reach `openExternalUrl` or other unthrottled OS-touching sinks.
- Touching `resolveForCwd` in `electron/ipc/handlers/forgeResolution.ts` — the `path.isAbsolute` gate there is the single shared validation point for every forge handler's `cwd`; do not bypass it with a new resolution path.
