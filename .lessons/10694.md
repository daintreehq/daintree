## Context

The Daintree Assistant pane (`HelpPanel`) show/hide used the same pattern as the worktree sidebar: a flex-sibling wrapper animating `transition-[width]` between `0` and `layout.helpPanelWidth` over 250ms, with the panel grid pushed by that same width change. `AppLayout.tsx` wires this; the hosted terminal inside the pane runs a CLI (the Daintree Assistant, often Ink-rendered) whose PTY is resized by `TerminalResizeController`/`XtermAdapter` off a `ResizeObserver` on that same wrapper.

## Problem

Issue #10693: every time the assistant pane was hidden and shown again, one extra orphaned "Standing by" status line was left behind in the terminal's scrollback, and it compounded — each toggle cycle stacked another stale copy. Nothing in the app's own resize/dispose code looked wrong; the geometry math, `xterm.resize()` calls, and PTY plumbing were all individually correct, which made this look like an Ink/CLI bug rather than a Daintree layout bug.

## Root cause

A `ResizeObserver` on an animating box does not fire once at the end of a CSS transition — it fires on essentially every animation frame, because the observed box's content rect is genuinely changing every frame. A single 250ms width animation produced a _storm_ of `xterm.resize()` → `pty.resize()` → SIGWINCH calls sweeping the terminal narrow and back, instead of one clean resize once the animation settled. The hosted CLI repaints synchronously per SIGWINCH, but its own width-state bookkeeping lags the true terminal width by a tick, so mid-storm it briefly rendered wider than the just-shrunk terminal, autowrapped its bottom status line, and left a row orphaned in scrollback. The CLI only auto-clears that artifact on shrink, not on grow-back, so exactly one orphan survived per hide→show cycle.

The fix is structural, not a debounce: stop animating `width` on any box that contains (or is measured for) the PTY at all. The assistant wrapper is now fixed-width (`layout.helpPanelWidth`, constant) and slides via `transform: translateX(0 | helpPanelWidth)` — compositor-only, so it never triggers layout or `ResizeObserver` and terminal geometry cannot change mid-slide. The `<main>` push is now driven by a separate `aria-hidden`, terminal-free sibling _spacer_ that animates `width` 0↔`helpPanelWidth` — no terminal inside it, so its resize churn is inert. The one remaining real reflow (the spacer's width transition reflowing `<main>`) is still coalesced: `handleAssistantSpacerTransitionStart` arms `suppressSidebarResizes()` on the spacer's `transitionstart`, and `handleAssistantTransitionEnd` fires one corrective repaint on the wrapper's `transitionend`, filtered to `event.propertyName === "transform"` and `event.target === event.currentTarget` (ignore bubbled child transitions). Every path that suppresses the transition entirely — `reduceAnimations`, `data-performance-mode`, a live-subscribed OS `prefers-reduced-motion` match, or an in-flight drag-resize — settles `inert`/repaint itself synchronously in a `useEffect`, since no `transitionend` ever arrives on those paths. `TerminalInstanceService`'s dead-man safety TTL was bumped from `durationMs + 100` to `durationMs + 150` to outlive `XtermAdapter`'s ~50ms `ResizeObserver` debounce tail, which can fire a stray resize after the transition visually settles.

## Lesson

- **Never animate `width`/`height` (even Tailwind `transition-[width]`) on any box that a `ResizeObserver`-driven PTY terminal lives inside or is measured against** — the observer fires on nearly every frame of a continuous CSS transition, not just at the end, turning a quarter-second animation into a SIGWINCH storm. Animate `transform` on a fixed-size wrapper instead; it's compositor-only and structurally cannot trigger a resize observation.
- **When a layout push must still visually animate, split it onto a second, terminal-free element** — a `aria-hidden` spacer that owns the `width` transition (and therefore the `<main>` reflow), while the terminal-bearing wrapper slides via `transform` in lockstep. Do not try to make one element serve both the geometry-push role and the PTY-safe role.
- **A resize-suppression lock still needs arming on whatever element still animates `width`**, and any settle-repaint handler must filter on both `event.propertyName` and `event.target === event.currentTarget` — an unfiltered `onTransitionEnd` fires on every transitioned child property and every bubbled child transition, not just the one you mean.
- **Every code path that can suppress an animation needs its own synchronous settle logic** (reduced-motion preference, performance mode, OS `prefers-reduced-motion` — live-subscribed, not just read once at mount — and in-flight drag-resize) — `transitionend` simply never fires on those paths, so any state a handler is responsible for (here, `inert`) will desync permanently without a fallback effect.
- **A "repaint once on settle" callback races cold provisioning.** The PR's own `repaintAssistantAfterTransition` (a guarded one-shot) later dropped the very-first-open repaint entirely because the terminal didn't exist yet at settle time (#11070), and was replaced by `createAssistantRevealCoordinator`, a durable retry obligation discharged once the terminal attaches. Treat "fire once on settle" as advisory, not a guarantee, when the repaint target can be created asynchronously.

## Applies when

- Animating any panel, sidebar, or dock region that sits adjacent to or wraps a live PTY terminal (grid panels, the worktree sidebar, the Daintree Assistant/help panel, any future dockable panel) — check whether the animated CSS property is `width`/`height` (unsafe) vs `transform` (safe).
- Touching `src/components/Layout/AppLayout.tsx`'s transition handlers (`handleAssistantSpacerTransitionStart`, `handleAssistantTransitionEnd`, `handleSidebarTransitionEnd`) or `src/lib/sidebarToggle.ts`.
- Diagnosing orphaned, duplicated, or autowrapped status-line/output rows that appear specifically around a show/hide or resize animation of a hosted CLI — Ink-based agents are especially prone since they don't clear stray rows on regrow.
- Adding or changing a post-transition repaint/reveal callback — verify it survives the repaint target not existing yet (cold provisioning) and every path that can skip the CSS transition outright.
- Reviewing a resize-suppression dead-man TTL after changing a transition's duration — the TTL must outlive the real animation duration plus the `ResizeObserver` debounce tail (~50ms), not just match the nominal duration.
