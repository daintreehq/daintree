## Context

The renderer imports from large barrel packages: `lucide-react` (1,583 icon modules, imported in ~204 source files) and eight `@radix-ui/*` packages (`react-select`, `react-checkbox`, `react-context-menu`, `react-dropdown-menu`, `react-popover`, `react-slot`, `react-switch`, `react-tooltip`). Vite 8 bundles Rolldown (not Rollup/esbuild) as its engine — see lesson #3490.

## Problem

The barrel re-export modules force the bundler to construct the full module graph across all 1,583 lucide modules before tree-shaking can prune them. This inflated the transformed-module count to 3,820 and added measurable cold-start/build parse cost. The obvious fix — Vite's documented `optimizeDeps.optimizePackageImports`, which rewrites barrel imports to direct subpath imports — was tried first and was completely inert: it is an esbuild-pre-bundle feature with no effect under the Rolldown build path.

## Root cause

Two non-obvious facts compound:

1. **Tree-shaking happens too late to help parse cost.** Barrel parse/graph-construction is paid _before_ tree-shaking can prune unused exports. So "Rolldown tree-shakes anyway" does not eliminate the barrel cost — the 1,583 modules are parsed regardless of which icons are actually used.

2. **`optimizePackageImports` is a no-op under Rolldown.** It lives under `optimizeDeps` (the esbuild dependency pre-bundler), not the production bundler. Vite 8's production build runs through Rolldown, which has its own equivalent: `build.rolldownOptions.experimental.lazyBarrel`. Enabling that single flag rewrites barrel imports to direct subpath imports _at build time_ with zero source churn, dropping transformed modules from 3,820 to 2,129 (44%).

## Lesson

- Under Vite 8 / Rolldown, the barrel-import lever is `build.rolldownOptions.experimental.lazyBarrel: true` (see `vite.config.ts` ~line 600), **not** `optimizeDeps.optimizePackageImports`. The latter is an esbuild pre-bundle option and silently does nothing on the Rolldown production path — verify any "optimization" actually moved a metric, don't trust that a documented Vite option applies under Rolldown.
- Don't assume tree-shaking absolves barrel cost. Graph construction / parse of the barrel's re-exports is paid before pruning, so the fix has to operate at import-rewrite time, not prune time.
- This change touches three perf baselines: `eager-import-baseline.json`, `renderer-bundle-size-baseline.json`, and `compiler-bailout-baseline.json` all shifted because module identity/count changed. Any flag that alters the module graph requires regenerating them in the same PR or the budget-gate scripts fail. (The compiler baseline no longer moves with the module graph — it scans files on disk now, precisely so it stops drifting for bundling reasons.)
- More broadly: when a Vite option is gated behind `optimizeDeps`, check whether your code path is the Rolldown production build (where it doesn't apply) versus the dep pre-bundler.

## Applies when

- Tuning Vite 8 / Rolldown build performance in `vite.config.ts`, especially `rolldownOptions`.
- Cold-start or build-time parse cost from large barrel packages (`lucide-react`, `@radix-ui/*`, or any package with a giant index re-export).
- You reach for `optimizeDeps.optimizePackageImports` (or any `optimizeDeps.*` option) and it appears to have no effect on the production bundle.
- A change shifts the renderer module graph and you see `eager-import-baseline.json`, `renderer-bundle-size-baseline.json`, or `compiler-bailout-baseline.json` budget checks failing.
- Reasoning that "tree-shaking will handle it" to justify ignoring barrel-import bloat.
