## Context

Each project gets its own cached `WebContentsView` via `ProjectViewManager` (LRU-evicted, multi-window). Switching to a cached ("warm") project detaches the outgoing view and reattaches the cached one behind an anti-flash bridge, gated by a "warm paint gate" that only releases the swap once the renderer confirms its terminals have re-woken and repainted (`notifyWarmViewPainted`, armed with a 500ms soft / 1500ms hard timeout — `DEFAULT_WARM_PAINT_GATE_TIMEOUT_MS` / `DEFAULT_WARM_PAINT_GATE_HARD_TIMEOUT_MS` in `ProjectViewManager.ts`). The renderer's terminal wake fan-out (`scheduleWake()` in `WorktreeStoreContext.tsx`) was written to trigger off the standard web-platform `visibilitychange` and Chromium `resume` events.

## Problem

Every warm project switch measured ~1502-1506ms round trip regardless of machine or project size — suspiciously exactly the gate's hard-timeout value, not the time terminals actually took to repaint. The e2e perf harness (`e2e/full/resilience/project-switch-perf.spec.ts`, `RUN_PERF_SWITCH=1`) logged 14 hard-timeout hits on develop. It looked like a slow wake fan-out or a slow git/worktree load, both red herrings — the fan-out ran in tens of ms once triggered, it just was never triggered on most switches.

## Root cause

A cached view is hidden via `setVisible(false)` and detached from the window, not frozen or navigated. Electron 42's `WebContentsView` does not fire `visibilitychange` or `resume` for that specific detach/reattach lifecycle — `document.visibilityState` reads `"visible"` the entire time the view sits in the cache, so no event ever landed in the renderer to run `scheduleWake()`. `resume` only fires when the OS/Chromium Efficiency profile actually froze the page, a minority of switches. So on the common path the gate had no signal to release on and always ran out the clock to its 1500ms hard timeout — the warm-switch latency floor was the timeout value, not real work. This is a category of bug: assuming a standard DOM/Chromium lifecycle event fires for every view-visibility transition, when Electron's multi-`WebContentsView` model has transitions (bare detach + `setVisible(false)`) that map to no web-platform signal. Only main actually knows when it re-attaches a cached view, so `ProjectViewManager.switchTo` sends an explicit `CHANNELS.APP_VIEW_WARM_ACTIVATED` IPC event right after arming the gate (both the bridged and unbridged reveal paths), and the renderer's `onViewWarmActivated` handler routes it into the existing `scheduleWake()` coalescer — the visibility/resume listeners stay wired as fallbacks, not replaced. After the fix: warm reveal p50 dropped from 1502ms to 66-200ms, hard timeouts went from 14 to 0.

## Lesson

- **Never trust `visibilitychange`/`resume`/`focus` to fire for every `WebContentsView` attach-state transition in Electron 42.** A `setVisible(false)` detach-then-reattach is a case with no corresponding web-platform event; `document.visibilityState` stays `"visible"` the whole time. If a renderer needs to react to a main-driven view lifecycle change, have main send an explicit IPC signal (`webContents.send(...)`) at the exact moment it acts — don't infer it from a DOM event that may not exist for that transition.
- **Keep the DOM-event listener as a fallback, not a replacement, when adding the explicit signal.** `WorktreeStoreContext.tsx` deliberately left the `visibilitychange`/`resume` listeners in place alongside `onViewWarmActivated` — the Efficiency-profile freeze path still legitimately fires `resume`, and coalescing both through the same `scheduleWake()` avoids double-work without losing either signal.
- **A gate/timeout hitting its exact configured value on every run means the trigger never fired, not that the work is slow.** 1502ms round-trip against a 1500ms hard timeout was the tell — if measured latency clusters suspiciously close to a configured timeout constant, go find what's supposed to release the gate before assuming the underlying work regressed.
- **When you make two previously-serial async operations concurrent (here: the view swap and the workspace-host git load in `activateProjectView`, `electron/ipc/handlers/projectCrud/switch.ts`), audit every consumer of state either one can mutate for a stale-write race.** Three guards were needed: `WorkspaceHostPool.loadProject` gained a per-window monotonic `windowLoadSeq` so a superseded slow load can't flip `windowToProject` back after a newer switch already claimed the window ("last requested wins," not "last completion wins"); the swap-failure path is guarded by a per-window `windowSwitchEpochs` counter so a late failure-restore can't clobber a newer switch; `releaseWindow` clears the sequence so a stale in-flight load can't resurrect a mapping post-release.

## Applies when

- Diagnosing a project-switch, panel-reveal, or any cached-view reactivation that stalls at a suspiciously round number matching a known timeout/gate constant.
- Writing renderer code that must react to a `WebContentsView` becoming visible/active again after `ProjectViewManager` detaches and caches it — check whether `visibilitychange`/`resume` actually fire for that specific transition before relying on them, especially anything gated behind `setVisible(false)`.
- Touching `ProjectViewManager.ts`'s warm/cold swap paths, the paint gate (`notifyWarmViewPainted`, `onViewWarmActivated`, `onViewRevealed`), or `WorktreeStoreContext.tsx`'s `scheduleWake`/`scheduleRepaint`.
- Making any two previously-sequential operations in a project-switch or window-lifecycle path run concurrently — check for a per-window/per-project "last write wins" ordering bug the same way `WorkspaceHostPool.windowLoadSeq` and `windowSwitchEpochs` were added here.
- Reviewing new Electron multi-`WebContentsView` code that assumes a Chromium/DOM lifecycle event will always accompany a main-driven attach/detach/visibility change.
