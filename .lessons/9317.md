## Context

`DevPreviewReadinessProbe.waitForServerReady` (`electron/services/DevPreviewReadinessProbe.ts`) polls a dev-server URL after it's detected on stdout and only flips the panel to `running` once the server is actually serving the app. PR #2265 established this poll and recommended accepting any `200–499` via HEAD ("accept 4xx — some servers 405 to HEAD"). This PR overturns that guidance.

## Problem

Two false-ready paths slipped through. (1) A `404`/`401`/`405` from `historyApiFallback`, a still-warming auth proxy, or an uncompiled route was treated as ready, loading a non-app response. (2) Docker / dev-container port-forwards answer `502/503/504` while the inner server boots, then cleanly transition to `200`; the probe took the first non-5xx as ready and pointed the `WebContentsView` at the gateway error page. Even a clean `200` can be premature — the bundler can serve a 200 HTML shell while still inside its blocking compile, so the first paint is a stale/empty doc.

## Root cause

HTTP status alone cannot distinguish "TCP-reachable / proxy-up" from "app compiled and serving." HEAD made it worse (servers 405 to HEAD, which the old gate accepted). The compile state is only observable over the same-port HMR WebSocket: Vite 8 uses subprotocol `vite-hmr` on `/`, Next.js 16 uses `/_next/webpack-hmr` (a WebSocket, not SSE since v12), webpack-dev-server 5 uses `/ws`. A successful WS handshake proves the bundler is past its blocking compile. But as of 2026 all three frameworks enforce Origin validation (Vite CVE-2026-39363, Next.js CVE-2026-27977, webpack-dev-server CVE-2025-30360), so a main-process probe with no/mismatched Origin gets 403/400 — the probe must spoof `Origin: <scheme>//<host>` matching the server. Node's global `WebSocket` can't set custom headers; the `ws` package can (same constraint that drove `VoiceTranscriptionService`).

## Lesson

- Narrow the HTTP ready gate to **2xx/3xx only** (`status >= 200 && status < 400`), and switch HEAD→**GET**. Classify `5xx` as a distinct third state, not failure.
- Add a **conditional warmup-race guard**: once any `5xx` is seen, the next `2xx/3xx` is not ready by itself — require a _follow-up_ `2xx/3xx` to confirm (`hasSeen5xx` + `awaitingConfirmation` latch; a new 5xx resets `awaitingConfirmation`). The common `ECONNREFUSED → 200` path (no 5xx ever) must still resolve on the first 200, so the second-confirmation requirement is gated on having observed a 5xx.
- Layer an **opportunistic HMR WebSocket handshake** before resolving: race candidates `{path:"/", subprotocols:["vite-hmr"]}`, `/_next/webpack-hmr`, `/ws`. Spoof `Origin` on every candidate to pass the CVE-patched validators. Use the `ws` package (custom headers); the global `WebSocket` won't work. The probe is opportunistic — `waitForServerReady` does not gate `return true` on the WS result; the handshake is a settle delay, not a hard requirement, so non-HMR static servers still pass.
- `ws` emits **both `error` and `close`** on a failed socket. When N candidates race to a `pending` counter, guard each socket with a per-socket `counted` flag so one failed socket decrements `pending` exactly once — otherwise two failures (4 events) settle the probe to false before a slower third socket fires `open`.

## Applies when

- Touching `DevPreviewReadinessProbe.ts` / `DevPreviewSessionService.ts`, or any readiness/health probe that maps HTTP status to "ready."
- Debugging dev-preview loading the gateway error page or a blank/stale shell behind Docker / dev-container port-forwards (502/503/504-then-200 warmup).
- Adding probes against Vite / Next.js / webpack-dev-server HMR endpoints, or any framework WebSocket — remember Origin-header validation (CVE-patched) and the `ws`-vs-global-`WebSocket` header constraint.
- Racing multiple `ws` sockets to a shared counter/promise (the error+close double-fire trap).
- Reconsidering the older "accept 4xx as ready / use HEAD" advice from PR #2265 — that guidance is superseded here.
- The stdout-marker fast-path and the abort-in-flight-poll-on-error race for this same readiness probe are #8294 — this lesson covers the HTTP-gate narrowing and the HMR WebSocket handshake.
