## Context

With WebContentsView-per-project (#4672), each project runs in its own V8 context with its own Zustand `projectStore` holding a snapshot of the full project list. The MRU project switcher (`Cmd+Alt+=`, `getProjectMruSwitchTarget` in `src/lib/projectMruSwitch.ts`) sorts that local list by `lastOpened` to pick the next/previous project. `ProjectStore.setCurrentProject` (main process) bumps `lastOpened` on the incoming project and the departing one inside a single SQLite transaction.

## Problem

`Cmd+Alt+=` jumped to the wrong project and the switcher palette highlighted the wrong default. After switching A→B in one view, switching again from another (cached) view used stale `lastOpened` timestamps, so the MRU sort ranked projects incorrectly.

## Root cause

`setCurrentProject` writes both the departing and incoming project rows but emits **no IPC** — it is a silent persistence mutation. The view that triggered the switch may learn the new timestamps via the switch payload, but every _other_ cached WebContentsView's `projectStore` keeps its old snapshot. Because each view is an isolated V8 heap (the whole point of #4672), nothing implicitly propagates the row changes. Three separate switch entry points all hit this: `activateProjectView` (`electron/ipc/handlers/projectCrud/switch.ts`), `ProjectSwitchService.performSwitch`, and the `handleDirectoryOpen` menu path (`electron/menu.ts`). `PROJECT_ON_SWITCH` only carries the _active_ project, never the departing row, so even the switching view missed the demoted project's bump. The fix added `broadcastProjectSwitchUpdates(previousProjectId, activeProjectId)` (`electron/ipc/projectSwitchBroadcast.ts`), wired at all three sites, which re-reads both rows via `getProjectById` and fans `CHANNELS.PROJECT_UPDATED` to all views via `broadcastToRenderer` (loops `getAllAppWebContents()`). It re-reads (rather than trusting the input) because under write-suppression `lastOpened` may be unchanged while `status` still flipped.

## Lesson

- A main-process store mutation that persists state is **not** the same as notifying renderers. `setCurrentProject` commits rows but emits no IPC; any renderer-side state derived from those rows (MRU sort, switcher default) goes stale in every view that didn't trigger the change.
- WebContentsView-per-project isolation cuts both ways: it removes cross-project contamination (#4672), but it also means any push-derived shared snapshot (the project list) must be **explicitly fanned out** to all views via `broadcastToRenderer` — there is no shared heap to keep them in sync.
- Audit _all_ switch entry points, not one. There were three (`switch.ts`, `ProjectSwitchService`, `menu.ts`); wiring one leaves the bug live on the others. Extract a shared helper so the fan-out can't drift between paths.
- A targeted payload (`PROJECT_ON_SWITCH` carries only the active project) is insufficient when a single operation mutates multiple rows — broadcast both the departing and incoming rows.
- Re-read rows from the store before broadcasting rather than echoing the caller's intent: write-suppression can leave `lastOpened` unchanged while `status` flips, and the broadcast must reflect actual persisted state.
- This is the inverse of #4641 (which narrowed an over-broad broadcast to a targeted send): request-response replies target `event.sender`; cross-view shared-state invalidations must broadcast to all.

## Applies when

- Adding or modifying any project-switch entry point in `electron/` (`projectCrud/switch.ts`, `ProjectSwitchService`, `menu.ts handleDirectoryOpen`, or a new one).
- Touching `ProjectStore.setCurrentProject` or any main-process store write that bumps `lastOpened` / `status` / other fields a renderer reads.
- Working on MRU project ordering, the project switcher palette, `Cmd+Alt+=`, or `ProjectHistoryService`.
- Any symptom where one cached WebContentsView has correct project metadata but another shows stale ordering/timestamps after a switch.
- Designing a fan-out for shared snapshot state across isolated WebContentsView V8 contexts — deciding between a targeted `event.sender` reply and a `broadcastToRenderer` invalidation.
