## Context

The terminal context menu (`src/components/Terminal/TerminalContextMenu.tsx`) gates its Copy/copy-as items on whether the xterm instance has a live selection — it reads `managed.terminal.getSelection()` at menu-open time (around line 143) and sets `hasSelection`. Copy-on-select and agent context injection paths in `TerminalPane.tsx` similarly branch on `terminal.hasSelection()`.

## Problem

After selecting terminal text (`selectAll` or drag-select), a single Escape keypress silently wiped the selection. The context menu then opened with Copy disabled even though the user believed text was still selected. The same wipe surfaced as a flaky e2e failure: a test helper pressed `Escape` to dismiss palettes before right-clicking, destroying the `selectAll()` the test had just performed.

## Root cause

xterm 6.x's `Terminal._keyDown` calls `clearSelection()` synchronously for any key event it does **not** treat as browser-handled. A key counts as browser-handled only when xterm itself consumes it (copy/paste shortcuts, scrollback navigation, etc.). Escape is **forwarded to the PTY** as input, so xterm classifies it as non-browser-handled and clears the selection on the way. The clear happens in the same synchronous keydown tick — before any `contextmenu` handler or `getSelection()` read can observe the prior selection. Nothing in the app code calls `clearSelection`; it is an internal xterm side effect of the key being PTY-bound rather than browser-consumed.

## Lesson

- In xterm 6, treat **any non-shortcut keypress as a selection-destroying event**, not just clicks. Plain keys (Escape, arrows, Enter, typed chars) are forwarded to the PTY and trigger xterm's internal `clearSelection()` in `_keyDown`.
- Never assume a selection survives across a keypress when wiring features that read `terminal.getSelection()` / `terminal.hasSelection()` (context menus, copy-on-select, "send selection to agent"). Read the selection on the gesture that opens the surface (right-click, button), and do not interleave synthetic key events between the selection and the read.
- In e2e helpers and any automation, do not press Escape (or other PTY-forwarded keys) while xterm has focus if you need the selection intact. PR #7649 added a `preserveSelection` option to `openTerminalContextMenu` (`e2e/helpers/terminal.ts`) that skips the Escape for exactly this reason; dismiss blocking overlays by other means (click elsewhere, target the overlay).
- Secondary note from the same PR: in `electron/workspace-host/ResourceActionExecutor.ts`, an early `return` on a no-op provision skipped `emitUpdate`, leaving the renderer's Zustand worktree store holding a stale `resourceConnectCommand`. When an early-return short-circuits a handler that has already mutated monitor state, still broadcast — but re-fetch the monitor first (`this.ctx.getMonitor(id)`), because emitting a snapshot for a worktree removed mid-await can resurrect a deleted row through the version-counter/tombstone path (`src/store/createWorktreeStore.ts`).

## Applies when

- Wiring or debugging the terminal context menu, copy-on-select, "copy selection", or "send selection to agent / context injection" — anything that reads `terminal.getSelection()` or `terminal.hasSelection()`.
- A terminal selection mysteriously disappears or Copy is unexpectedly disabled after pressing Escape, arrows, Enter, or typing.
- Writing or fixing flaky e2e terminal tests that combine `selectAllTerminalText` / drag-select with `keyboard.press(...)` (especially Escape to dismiss palettes) before asserting on the selection or context menu.
- Upgrading or auditing xterm 6.x keyboard / selection behavior, or porting selection-dependent UI across an xterm major version.
- Adding an early-return to a workspace-host action handler (`ResourceActionExecutor`, resource lifecycle) that has already mutated `WorktreeMonitor` state — ensure `emitUpdate` still fires and guards against resurrecting a removed monitor.
