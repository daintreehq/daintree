## Context

Recipe launches fan out terminal spawns through `runRecipeWithResults` (`src/store/recipeStore.ts`), which builds `RecipeSpawnResults = { spawned[], failed[] }` recording every terminal that didn't start: out-of-bounds indices, the `MAX_AGENT_RECIPE_TERMINALS` (3) agent-cap drop, the panel-limit partial remainder, and per-terminal `Promise.allSettled` rejections. #7220 surfaced those failures only in the RecipeRunner panel's inline `SpawnErrorBanner`. Every other entry point — dock launch menu, `recipe.run` (palette, keybindings, MCP), `workflow.createWithRecipe` / `workflow.startWorkOnIssue`, NewWorktreeDialog, WorktreeCard — called the void `runRecipe` wrapper and discarded the payload (issue #9946).

## Problem

Launch a recipe from any non-panel surface and when terminals fail to spawn they simply don't appear — no toast, banner, or inbox entry. Worse: `workflowCreationActions.ts` set `recipeLaunched = true` purely because the awaited call resolved, so MCP agent callers were told the recipe launched when zero terminals spawned. Every call site _looked_ correct — `await runRecipe(...)` inside a try/catch is the idiomatic shape; the catch just never fires, because spawn failures don't reject.

## Root cause

Two deliberate store-layer contracts compose into whole-path silence when a caller discards the result. First, `runRecipeWithResults` only **throws** for a missing recipe id; all spawn-level failures **resolve** into `results.failed` — a try/catch around the await catches nothing that matters. Second, `preflightSpawnBatchLimit` (`src/store/panelLimitStore.ts`) only notifies when the batch is _fully_ blocked (`available === 0`); a partial drop (2 slots free, recipe wants 5 → `allowed = 2`) returns silently by design, on the assumption the caller surfaces the per-terminal `failed[]` entries. The store never calls `notify()` for spawn failures (only `logError`), so surfacing is 100% caller-owned — and three of four launch paths voided the payload away (the dock menu a bare `void runRecipe(...)` with a latent unhandled rejection on top).

The fix (#10110) centralized surfacing in `notifyRecipeSpawnFailures` (`src/utils/recipeNotify.ts`): error toast "Recipe launch failed" on zero-spawn, warning "Recipe partially launched" on partial, relaying the reason only when all failures share one (mixed reasons → counts only). It carries its own notify subtlety: the context passes `projectId` but **deliberately omits `worktreeId`**, because `isOriginSurfaceVisible` (`src/lib/notify.ts`) suppresses toasts whose `context.worktreeId` matches the active worktree — and the failing worktree _is_ the active one in the common case for these paths, none of which render an inline fallback. `projectId` alone is never a surface, so it can't trigger suppression. For MCP, `recipe.run` now notifies _first_ and then throws on zero-spawn — the notify reaches palette/keybinding users (their dispatch rejection is only logged), the throw is the structured error for MCP callers — and both `recipe.run` and the workflow actions grew `spawnedCount`/`failedCount`/`failedTerminals` result-schema fields (`mcpOutputSchema: true`) with `recipeLaunched = results.spawned.length > 0`.

## Lesson

- **Never call the void `runRecipe` wrapper** — it still exists in `recipeStore.ts` (drops the result) with zero production callers left; reaching for the shorter name from a new launch surface silently reintroduces this bug class. Use `runRecipeWithResults` + `notifyRecipeSpawnFailures`.
- **A resolved recipe spawn is not a successful one.** Spawn failures populate `results.failed` without rejecting, and the panel-limit preflight is silent on partial drops. Gate any "launched"/success flag on `results.spawned.length > 0`, never on the promise resolving.
- **More notify() context can mean less visibility.** A `context.worktreeId` matching the active worktree suppresses the toast to inbox-only (modulo the 500ms navigate-away grace). For a failure originating on the surface the user is looking at _with no inline fallback_, omit `worktreeId`/`panelId` — pass `projectId` for inbox scoping only. Adding worktreeId "for completeness" kills exactly the toasts that matter most.
- **Exactly one surface per failure.** The RecipeRunner panel owns `SpawnErrorBanner` inline and must not also call `notifyRecipeSpawnFailures` (the helper's header comment says so); every bannerless path must call it. Don't add a notify inside the store — surfacing stays caller-owned so the panel keeps its inline treatment.
- **MCP callers need the throw, UI users need the toast — do both, notify first.** An action that resolves reports success to MCP regardless of toasts; an action that only throws leaves palette users blind because UI dispatch rejections are just logged. Zero-spawn → notify, then throw; partial → notify + structured counts in the result.
- **Forward `ctx.dispatchSource` on every path reaching `runRecipeWithResults`** — the workflow actions were missing it, so MCP-driven worktree+recipe combos bypassed the `MAX_AGENT_RECIPE_TERMINALS` cap that `recipe.run` enforced.

## Applies when

- Adding any new recipe launch entry point (action, menu item, plugin surface, panel) or touching `useRecipeStore` spawn calls — the void-wrapper trap and caller-owned surfacing both still stand.
- Wiring a `notify()` for an error originating on the currently active worktree/panel — check `isOriginSurfaceVisible` suppression before including `worktreeId`/`panelId` in the context.
- Reviewing any API shaped `{ ok[], failed[] }` where call sites `await` it void or set success booleans from mere resolution.
- Diagnosing "launched a recipe, some/all terminals never appeared, no error shown" — the detail is in `results.failed`; find which path dropped it.
- Defining action `resultSchema`s consumed by MCP (`mcpOutputSchema: true`) — success booleans must encode actual outcome, and zero-success must reject, or agent callers plan on top of phantom terminals.
