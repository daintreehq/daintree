## Context

`TerminalResizeController` computes cols/rows from cached cell metrics instead of calling xterm's `FitAddon.proposeDimensions()` directly, because `proposeDimensions()` reads the live DOM which may not yet reflect the `ResizeObserver` box that triggered the resize, so the controller has to reimplement FitAddon's arithmetic by hand, and `TerminalReconciliationWatchdog` (`WATCHDOG_INTERVAL_MS = 3000`) treats a real `FitAddon` computation as ground truth, comparing it against the controller's grid every 3s and "correcting" any mismatch.

## Problem

Cursor-relative inline TUIs (the Daintree Assistant sidebar) would paint correctly, then visibly re-wrap and drop rows about 3 seconds later with no user action in between (#11095): Daintree computed 67 columns, `FitAddon` computed 65, and the watchdog silently reflowed the live grid from under an app that had already rendered assuming 67 — the wrong number won the sprint, then lost the race.

## Root cause

Three independent divergences between the manual math and `FitAddon`, all masquerading as one symptom:

1. **Scrollbar gutter never reserved.** `37ff040e4` introduced raw `Math.floor(width / cellWidth)`; `9cd995a9d` later set `scrollbar: { width: 15 }` for the overview ruler but never touched the column-math call sites, so xterm/FitAddon started reserving 15px that the manual conversions still divided into the grid.
2. **Fractional vs. whole-pixel division.** `FitAddon` measures via `parseInt(getComputedStyle(el).width, 10)`, i.e. whole CSS pixels, but `ResizeObserver`'s `contentRect` and `getBoundingClientRect()` report fractional values, and CSS grid/flex tracks are fractional far more often than not — dividing the raw fractional width lands a column (or row) past what FitAddon itself would fit.
3. **The `<1px` dedup swallowed real changes.** `resize()` skipped applying a new box when `Math.abs(delta) < 1`, but a change like 671.9px → 672.1px is only 0.2px and can still cross the pixel boundary that FitAddon's truncated view treats as significant — exactly the changes that mattered were the ones being thrown away.

All three push in the same direction: the manual estimate runs wide, and the only thing that ever notices is the watchdog, 3 seconds later, after the pane has already painted.

## Lesson

- **When two implementations must agree, only one can own the arithmetic — express the other as a helper wrapping the same constant.** `TERMINAL_SCROLLBAR_WIDTH` in `src/config/xtermConfig.ts` now feeds both `getXtermOptions()` (what xterm reserves) and `getEffectiveScrollbarWidth()` (what every pixel-to-column site subtracts); before this, the two only agreed by accident and drifted the moment one side changed.
- **Mirror the library's gating, not just its formula.** `getEffectiveScrollbarWidth()` returns 0 when `scrollback === 0` or `showScrollbar === false`, because `FitAddon.proposeDimensions()` has that same gate — copying only the `width - 15` arithmetic without the gate would still diverge on gutterless terminals.
- **If the oracle truncates to whole pixels, truncate before you divide, not after.** `toFitPx()` (`Math.trunc`, clamped at 0) normalizes a `ResizeObserver`/`getBoundingClientRect` value to FitAddon's `parseInt`-truncated view before either the cols/rows division or the redundant-resize dedup use it — applying it in only one of those two places would have left the other divergence in place.
- **A `<Npx` dedup threshold is a claim about the oracle's precision, not an arbitrary tolerance — verify it against the truncation boundary.** `isRedundantResize()` now compares `toFitPx(lastWidth) === toFitPx(width)` instead of `Math.abs(delta) < 1`, because a sub-pixel change that crosses a truncation boundary is not "no-op" to FitAddon even though it is under 1px.
- **A geometry reconciler that treats another component as ground truth turns any silent divergence into a delayed, user-visible correction.** `TerminalReconciliationWatchdog` fires every `WATCHDOG_INTERVAL_MS` (3000ms) and re-wraps whatever it disagrees with — for cursor-relative inline UIs that already painted assuming the wrong grid, that "fix" is the corruption. Treat any repeat offender against such a watchdog as a math-parity bug in the producer, not a timing bug in the watchdog.
- **Test parity against the real oracle, not a hardcoded expected value.** `TerminalResizeController.fitParity.test.ts` drives an actual `FitAddon` off the actual production `getXtermOptions()` and asserts equality with the controller's output — a fixed "should be 65 cols" assertion would not catch divergence #2 or #3, which only show up at specific fractional/boundary pixel values.

## Applies when

- Touching `calculateTerminalDimensions`/`getXtermOptions`/`getEffectiveScrollbarWidth` in `xtermConfig.ts`, or any of the four pixel-to-column sites in `TerminalResizeController` (`resize()`, `resizePtyFromCachedCellMetrics()`, `reconcileGeometryFresh()`'s cell-metric fallback, prewarm).
- Diagnosing a terminal grid that looks correct on spawn/paint but silently re-wraps a few seconds later — check `TerminalReconciliationWatchdog` logs for a repair before assuming a layout/CSS bug.
- Adding or changing a `<Npx` / `Math.abs(delta) < N` resize-dedup guard — confirm the threshold matches the consumer's own rounding/truncation behavior, not an arbitrary "small enough" number.
- Bumping `@xterm/addon-fit` or changing `scrollbar.width`/`showScrollbar` — re-verify `getEffectiveScrollbarWidth()`'s gating still matches `FitAddon.proposeDimensions()`'s current gating.
- Extending resize coordination further: #11098 (same arc) adds a strategy-aware coordinator so xterm and PTY geometry change together, because per-terminal locks and a `fit()`-before-PTY-strategy split were letting the watchdog repair through in-flight, unsettled geometry.
