## Context

PR #5534 added per-module log-level overrides that must reach the `pty-host` and `workspace-host` utility processes so their loggers filter consistently with main. The host-side clients (`PtyClient`, `WorkspaceHostProcess`) own a forked utility process and a `send()` channel; overrides arrive at runtime via an IPC handler (`electron/ipc/handlers/logs.ts`) and must also survive host restarts.

## Problem

The obvious wiring — push the override map to the child immediately after `forkUtilityProcess`/spawn — silently drops the message. The child's own `port.on("message", ...)` listener (the pty-host case at `electron/pty-host.ts` ~L1507, `case "set-log-level-overrides"`) is not attached until the child has finished its own bootstrap and emitted `"ready"`. A message posted to the port before that listener exists is delivered to a port with no consumer and lost — no error, no retry. A second, independent trap in the same PR: `registerLogsHandlers(deps)` originally captured a _destructured snapshot_ of `deps`, so `deps.worktreeService` assigned later (after pty-client became ready) was invisible to the fan-out — overrides only reached pty-host, never workspace-host.

## Root cause

Utility-process message delivery is fire-and-forget over a port whose receive side is wired during the child's async startup, so the producer and the consumer race; "spawned" is not "listening." The fix makes the host clients hold a `logLevelOverridesCache` and replay it from inside the `"ready"` handler on every ready (initial spawn AND every restart) — see `PtyClient.ts` (`this.send({ type: "set-log-level-overrides", ... })` in the ready branch) and `WorkspaceHostProcess.ts` (`setLogLevelOverrides` + replay at L445). The cache is seeded synchronously from the persisted store (`readPersistedOverrides`) so hosts spawned during early boot — before any renderer IPC handler registers (e.g. `prewarmProject`) — still inherit saved config. The deps trap is fixed by passing `deps` _by reference_ and reading `deps.ptyClient`/`deps.worktreeService` at fan-out time, never destructuring at registration time.

## Lesson

To push runtime config into a forked utility-process host: cache it on the host-client, send it from the `"ready"` handler (not the spawn path), and re-send on every subsequent `"ready"` so restarts re-inherit it automatically — callers must not track restarts themselves. Seed the cache from durable storage at construction so boot-time host spawns are correct before any renderer round-trip. When a handler fans out to services that are assigned _after_ registration, keep the `deps` object live — read fields lazily at call time; never destructure into a snapshot at registration.

## Applies when

Wiring any new runtime setting (resource profile, feature flag, token, log level) from main into `PtyClient`/`WorkspaceHostProcess` or a new utility-process host, or whenever an IPC handler fans a value out to services that may not exist yet at registration time.
