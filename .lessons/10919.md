## Context

Fast wheel-scrolling a full-screen mouse-reporting TUI (e.g. `grok build`) while several other agent terminals streamed output locked up ALL terminals at once, including the one being scrolled. Two prior PRs had already tried to fix "multi-agent terminal slowness": #10884 made `TerminalOutputIngestService` yield background drains so a focused terminal's queued scroll/keystroke dispatches first, and #10886 made the pty-host's `PortQueueManager`/`PortBatcher` exempt the focused terminal from the aggregate backpressure watermark and service it first. Both are legitimate priority fixes, and both left the lockup fully reproducible — that survival is the tell #10919 chases down.

## Problem

The `paused-backpressure` pill never appeared during the lockup — nothing crossed a queue watermark, so the obvious backpressure/prioritization framing (what #10884/#10886 had just extended) was a dead end. The real signature was CPU saturation on two single-threaded chokepoints doing unpreemptible parse work, invisible to any watermark-based diagnostic.

## Root cause

`@xterm/headless`'s (and `@xterm/xterm`'s) `WriteBuffer` self-slices parse work to a 12ms budget, but that budget is checked only BETWEEN `write()` entries, never within one. Two places defeated this: (1) the renderer's `TerminalOutputIngestService` coalesced up to 256KB into a single `terminal.write()` call, so one entry became one atomic 10-50ms main-thread task Blink could not interrupt to dispatch the user's own wheel events — the scrolled TUI was starving its own scroll. (2) the pty-host feeds one `@xterm/headless` mirror per terminal, and the 12ms slicing is per-instance: with M terminals streaming, one event-loop iteration could run up to M×12ms of back-to-back parse slices in the timers phase, starving the `setImmediate` transport flushes that deliver frames to the renderer. Priority-ordering reorders which QUEUED item runs next; it cannot preempt a task already mid-parse, so a big enough entry or enough concurrent mirrors saturates the loop regardless of ordering.

The fix is slicing plus a process-wide pacer, not reordering. `TerminalWriteController.WRITE_SLICE_BYTES` caps every write-buffer entry at 32KB (`src/services/terminal/TerminalWriteController.ts:30`) so xterm's between-entry yield fires often enough for Blink to service input. `TerminalOutputIngestService` adds a wheel-burst hold: while an active wheel gesture is detected (`getActiveWheelId`), background terminals' drains recheck on a 24ms timer with a 250ms per-queue cap and ~1s decay, exempting the wheeled and focused terminals. The new pty-host `HeadlessMirrorScheduler` (`electron/services/pty/HeadlessMirrorScheduler.ts`) routes every mirror feed through a shared FIFO-per-terminal pacer with a 64K/terminal/tick fairness budget and a strict 128K aggregate-unparsed-chars cap enforced via parse-callback bookkeeping — bounding total parse work per iteration to a few ms regardless of terminal count, without dropping or reordering bytes (VT frames are non-idempotent deltas). A companion `eventLoopMonitor.ts` (`monitorEventLoopDelay` + ELU) surfaces a "PTY host lag p99" tile in the Why-Slow panel (`src/components/Diagnostics/WhySlowContent.tsx`) so high loop lag with zero paused terminals now reads as the CPU-saturation signature, distinct from backpressure.

## Lesson

- **When a queue-priority fix doesn't resolve "slow under multi-agent load," stop looking for a bigger watermark and look for an atomic unpreemptible task** — reordering queued work cannot help if the CPU is saturated by one task that can't yield mid-execution, which is exactly why #10884/#10886 didn't fix this.
- **xterm's WriteBuffer parse budget (12ms) is enforced only between `write()` entries, never within one** — coalescing output into fewer bigger writes (as `TerminalOutputIngestService` did, up to 256KB) trades yield frequency for throughput and can starve input dispatch; keep entries small (`WRITE_SLICE_BYTES = 32 * 1024`) when responsiveness matters more than call overhead.
- **A per-instance self-slicing budget does not compose across instances** — each `@xterm/headless` mirror caps itself at 12ms, but M concurrent mirrors still cost up to M×12ms in the same timers phase; a per-terminal self-limiting mechanism in the pty-host needs a process-wide aggregate cap on top (`HeadlessMirrorScheduler`'s 128K cap), or it doesn't actually bound total work.
- **Add an event-loop-lag tile before chasing a CPU-saturation bug by feel** — `eventLoopMonitor.ts`'s p99 lag with zero paused terminals is the signature that separates "CPU-bound, unpreemptible" from "backpressure, watermark-bound"; without it this bug class looks identical to the backpressure bugs #10884/#10886 already fixed.
- **Pacing must never drop or reorder bytes for a stateful terminal parser** — `HeadlessMirrorScheduler` only ever delays feeding, preserving strict per-terminal FIFO order and firing callbacks only after actual parse completion (`pendingHeadlessWrites` gating unchanged); reordering or truncating here would silently corrupt terminal state instead of just being slow.

## Applies when

- Diagnosing "scrolling a terminal locks up other terminals" or "the app stalls under several concurrent streaming agents" and the `paused-backpressure` pill never shows — check pty-host loop lag (`eventLoopMonitor`) before assuming it's a watermark/queue issue.
- Touching `TerminalOutputIngestService`, `TerminalWriteController`, or code that batches/coalesces PTY output before a `terminal.write()` call — bigger batches mean fewer xterm yield points.
- Feeding `@xterm/headless` (or any xterm `WriteBuffer` consumer) from multiple concurrent sources in one process — a per-instance budget needs a process-wide aggregate cap, not just per-instance trust.
- Reviewing a fix that reorders/prioritizes queued work for a performance symptom — verify the bottleneck is queue-ordering, not an atomic task reordering can't preempt.
- Extending the Why-Slow panel (`WhySlowContent.tsx`, `shared/types/whySlow.ts`) — event-loop lag with zero pauses is the established CPU-saturation signature, distinct from backpressure.
