## Context

Every terminal-feel benchmark before this PR (PERF-034) ran headless xterm instances inside a Node process — a simulated slice, not the path a user actually feels: keydown → IPC → pty-host → PTY echo → MessagePort → parse → paint. #11023 adds `e2e/full/terminal/interactivity-perf.spec.ts` (PERF-120..122), driving the real built app with CDP keyboard input and stamping every pipeline segment on the renderer clock, paired with new pty-host marks `terminal_port_input_written` / `terminal_interactive_echo_dispatched`. Same symptom class as the #10948 pty-host regression ("focused terminal stops responding under load"), but here it's the output pipeline, not the memory budget.

## Problem

Under saturation (a focused composer-sim terminal plus 6 unthrottled background streams), keystroke-to-paint p95 was 84ms and typing FPS dropped to 33, with 7 long animation frames (up to 394ms). The instinctive read is "some stage of the pipeline is slow." Segment attribution showed the echo byte itself was never slow in isolation — `cat-solo` and `sim-fleet` (12 background terminals throttled to ~32KB/s) were unchanged from baseline. It only regressed once background terminals were unthrottled: the tell that this is a queueing problem, not a compute problem.

## Root cause

Three places let a focused keystroke's echo queue behind background "freight" instead of skipping ahead of it. First, `TerminalOutputIngestService` fed every terminal the same 128KB in-flight / 256KB coalesce-cap watermarks regardless of focus; bytes already handed to `xterm.write()` are un-holdable main-thread parse backlog (xterm chews them in ~12ms slices), so a background terminal fed 128KB+256KB windows keeps the main thread busy parsing sibling output long after the focused echo wants to render. Second, the pty-host `PortBatcher.write()` only escalated an interactive (echo) chunk to "swap the pending throughput timer for a `setImmediate`" — under a saturated host loop even a `setImmediate` sits behind milliseconds of already-queued poll work; it is not actually immediate once the event loop has backlog. Third, nothing told the renderer "a keystroke is in flight, protect this slot" — `TerminalBurstController` already held background drains during wheel-scroll (`getActiveWheelHoldId`) but had no echo equivalent.

The fix is three coordinated queue-priority changes, not a speed-up of any stage: (a) `shouldDeferDrain(id)` drops non-focused terminals to 32KB/16KB/32KB watermarks (`BACKGROUND_HIGH_WATERMARK_BYTES` etc.), shrinking un-holdable backlog to roughly one parse slice; (b) `PortBatcher.write()` flushes synchronously the instant an interactive chunk arrives (`if (interactive) { this.flush(); return true; }`), never via `setImmediate`; (c) `onEchoPendingInput`/`onEchoData`/`getEchoPendingHoldId` arm a bounded 150ms (`ECHO_PENDING_HOLD_MAX_MS`) hold on background drains the moment a keystroke leaves for the PTY, released one frame after the echo lands, composed via `getActiveWheelHoldId() ?? getEchoPendingHoldId()`. Result: p95 84ms → 52ms, FPS 33 → 60, long animation frames 7 → 0; `sim-solo`/`sim-fleet` were untouched since nothing there needed protecting — confirming the diagnosis, not just the fix.

## Lesson

- **When a "slow path" regression only reproduces under background load, suspect queueing/scheduling ahead of compute.** Segment-attribute first (paired host/renderer marks bracketing each stage) before optimizing any stage — the marks here proved pty-host turnaround was sub-millisecond even under full load, so speeding up the host would have wasted effort.
- **`setImmediate` is not a synchronous-flush primitive under a busy event loop.** For a genuinely latency-critical chunk, flush synchronously rather than scheduling — `PortBatcher.write()`'s `if (interactive) { this.flush(); return true; }` is the pattern; a scheduled callback queues behind whatever poll/IO work is pending.
- **"Focused feel beats background throughput" is an established contract — extend the existing hold machinery rather than inventing a parallel one.** The echo-pending hold (`getEchoPendingHoldId`) is deliberately shaped like the pre-existing wheel-scroll hold (`getActiveWheelHoldId`), composed with `??`.
- **A per-terminal hold needs a bounded escape hatch tied to real feedback, not a timer alone.** `getEchoPendingHoldId()` bounds at `ECHO_PENDING_HOLD_MAX_MS = 150` so a wedged PTY can't starve siblings, and a generation counter (`echoPendingGen`) stops a stale release from clearing a hold re-armed by a later keystroke.
- **Bytes already inside `xterm.write()` cannot be paused — the leverage point is the window size before the call, not a hold after.** Background terminals get smaller in-flight/coalesce caps (32KB vs 128KB) because feed batches already committed to xterm block the main thread regardless of any later hold.
- **A benchmark that only exercises simulated/headless slices (PERF-034-style) cannot catch scheduling-under-real-load regressions.** `interactivity-perf.spec.ts` drives the built app via CDP with real background terminals; the `sim-saturation` cell (6 unthrottled streams) reproduces the failure — throttled `sim-fleet` does not.

## Applies when

- Diagnosing "typing feels laggy" or "a focused terminal stalls" only when other terminals stream output — check `shouldDeferDrain`, `PortBatcher`'s `interactive` fast path, and `TerminalBurstController`'s hold state before assuming a stage is slow.
- Touching `TerminalOutputIngestService` watermarks, `PortBatcher.write()`, or `TerminalBurstController` — these three form one coordinated "protect the focused terminal" system; changing one without the others reopens the queueing gap.
- Adding a new sustained-interaction hold beyond wheel-scroll and keystroke-echo — extend `TerminalBurstController`'s hold-id pattern (arm/data/getHoldId, bounded max, generation guard) rather than a parallel mechanism.
- Writing or extending a terminal perf benchmark — headless simulation (PERF-034-style) cannot reproduce scheduling-under-load bugs; use the CDP-driven `interactivity-perf.spec.ts` pattern (`RUN_PERF_INTERACTIVITY=1`, never gates CI).
- Reasoning about `setImmediate`/`setTimeout(…, 0)` as "fast enough" for a user-visible interactive path — verify against a saturated event loop, not an idle one.
