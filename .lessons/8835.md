## Context

`ProjectViewManager.performSwitch` runs an anti-flash "paint gate" on cold project switches: the incoming `WebContentsView` is attached _behind_ the still-visible outgoing view (`addChildView(view, 0)`), and the outgoing view is only detached once the incoming renderer confirms it has committed its first structural paint. The confirmation signal (`APP_VIEW_PAINTED`) is fired from the renderer in `src/App.tsx` via a **double-`requestAnimationFrame`** in `notifyViewPainted` (`src/utils/removeStartupSkeleton.ts`). The main process blocks on it in `waitForPaint`, with soft/hard timeouts.

## Problem

Cold switches routinely hit the paint-gate soft/hard timeout instead of resolving via the signal path. The fallback timeouts had to be set very high (3s soft / 8s hard) to mask it, and switches felt sluggish.

## Root cause

Because the incoming view is stacked at index 0 _behind_ the still-visible outgoing view, Chromium 146's compositor marks the incoming renderer as occluded and **throttles its `requestAnimationFrame` callbacks**. That throttle stalls the renderer's double-rAF — the exact mechanism that produces the `APP_VIEW_PAINTED` signal the gate is waiting on. So the gate waits on a signal that Chromium has suspended, and almost always falls through to the timeout.

The two obvious knobs are both wrong:

- `backgroundThrottling` is **window-wide since Electron 28** (lesson #4683 / #8599): toggling it on the `BrowserWindow` un-throttles _every_ cached sibling, not just the incoming view.
- `paintWhenInitiallyHidden` is a **`BrowserWindow`-only** constructor flag; it does not apply to `WebContentsView` cold starts.

The correct lever is per-target: `Page.setWebLifecycleState("active")` via CDP (`unfreezeWebContents` in `electron/utils/webContentsLifecycle.ts`), which pushes Blink back to the foreground lifecycle so rAF keeps firing during the swap window. It is fire-and-forget (the helper owns the CDP-error swallow-list and `console.warn`s the rest). Critically it **must run after `did-finish-load`** — calling it earlier hangs the CDP session on an uninitialised frame host on Chromium 146.

## Lesson

- A `WebContentsView` attached behind a visible sibling is **occluded**, and Chromium 146 throttles its rAF. Any cross-process readiness handshake that relies on the occluded renderer's rAF (paint gates, first-frame signals, double-rAF flushes) will stall until you force the renderer's lifecycle to `active`.
- Use `unfreezeWebContents` (CDP `Page.setWebLifecycleState("active")`) — the per-target lever. Do **not** reach for `backgroundThrottling` (window-wide since Electron 28, un-throttles every cached sibling) or `paintWhenInitiallyHidden` (`BrowserWindow`-only, irrelevant to `WebContentsView`).
- Order matters: call it **after** `did-finish-load`. Earlier and the CDP attach hangs on an uninitialised frame host.
- Once the rAF stall is removed, the paint-gate timeouts can be tightened (here: 3s/8s → 1.5s/4s perf, 5s/12s → 2.5s/6s efficiency). Keep the `ProjectViewManager` `DEFAULT_PAINT_GATE_*` fallbacks in lockstep with the Balanced profile in `shared/types/resourceProfile.ts`.

## Applies when

- Touching the cold-switch / project-view paint gate in `ProjectViewManager.ts` (`performSwitch`, `waitForPaint`, `notifyViewPainted`, `APP_VIEW_PAINTED`, `loadToPaintMs`, `projectview.coldstart`, `paintgate.softtimeout`/`hardtimeout`).
- Adding any main↔renderer handshake that waits on a `requestAnimationFrame`/double-rAF or first-paint signal from a `WebContentsView` that is mounted behind another visible view.
- Tempted to disable `backgroundThrottling` or set `paintWhenInitiallyHidden` to "wake up" a hidden/occluded view — reach for `unfreezeWebContents` (CDP per-target lifecycle) instead.
- Debugging why a cached/incoming project view's timers, animations, or paint confirmations seem frozen while the view is not the frontmost child.
- Adjusting `paintGateTimeoutMs` / `paintGateHardTimeoutMs` in `shared/types/resourceProfile.ts` — must stay in lockstep with `DEFAULT_PAINT_GATE_TIMEOUT_MS` / `DEFAULT_PAINT_GATE_HARD_TIMEOUT_MS`.
