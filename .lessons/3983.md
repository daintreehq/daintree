## Context

Agent terminals must stay pinned to the bottom of their output as the agent streams, while still honoring a deliberate user scroll-back. A regression caused the viewport to intermittently snap to line 0 mid-stream, forcing users to manually scroll down again.

## Problem

xterm 6's `onScroll` fires for both user-initiated scrolls and programmatic buffer operations (every `scrollToBottom()`, and `baseY` increments as `write()` advances the buffer). The early implementation tried to drive "user scrolled back" state directly off `onScroll`, so streaming writes looked like user scrolls and flipped `isUserScrolledBack = true`, which then disabled the auto-pin.

## Root cause

`onScroll` carries no provenance — there is no flag on the event saying who caused it. You cannot distinguish a user drag/wheel from a programmatic `scrollToBottom()` or a write-driven `baseY` bump inside the handler itself. Any scroll-state tracking that runs unguarded in `onScroll` mislabels programmatic scrolls as user intent. Note the lesson's earlier `_isWriting`-guard framing was wrong: that flag never shipped — the merged design uses a different two-signal approach.

## Lesson

Track scroll provenance with explicit out-of-band signals, never by interpreting `onScroll` alone. The live mechanism (`TerminalListenerInstaller.ts`, `TerminalInstanceService.ts`) has three parts:

1. Pin on parsed output, not raw write — `terminal.onWriteParsed` calls `scrollToBottomSafe(managed)` when `!isUserScrolledBack && !isAltBuffer` (and the user has no active selection; a live selection latches `isUserScrolledBack = true` so writes don't yank the selection out of view).
2. Suppress self-induced scroll — `scrollToBottomSafe` wraps `terminal.scrollToBottom()` in `managed._suppressScrollTracking = true` (try/finally), and the `onScroll` handler early-returns while that flag is set, so the programmatic scroll it just issued can't re-trigger state updates.
3. Detect real user scroll from DOM input — `wheel`/`keydown` (PageUp/PageDown/Home/End/Arrows) listeners on the host element set `managed._userScrollIntent = true`; `onScroll` clears it each fire. Final review (commit `30ce0f7c6`) removed the `_userScrollIntent` gate from the `onScroll` else-branch (it blocked scrollbar drag, which emits no wheel/key event) and relied solely on `_suppressScrollTracking` to reject programmatic scrolls — so `_userScrollIntent` survives as a wheel/scroll-indicator hint, not the gate.

Resize follows the same discipline: `TerminalResizeController.applyResize` re-pins via `latestWasAtBottom && !isUserScrolledBack` after resizing, instead of mutating scroll intent during the resize.

## Applies when

- Implementing auto-scroll / bottom-pinning in xterm.js terminals (`TerminalInstanceService`, `TerminalListenerInstaller`)
- Any code that writes `isUserScrolledBack` from an `onScroll` handler
- Calling `terminal.scrollToBottom()` / `scrollToLine()` programmatically while also listening on `onScroll`
- Distinguishing user scroll from programmatic scroll in any virtualized/buffered viewport that lacks event provenance
- High-frequency output streams (agent terminals, build output) where writes advance `baseY`
- Resize handlers that capture/restore scroll position
