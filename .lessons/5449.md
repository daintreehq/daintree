## Context

PR #5449 flipped `noUncheckedIndexedAccess: true` in `tsconfig.json:23` (still set today) and fixed the resulting type errors across 212 files. The issue estimated ~75 errors; the compiler surfaced 1,286, because the flag widens _every_ array index (`arr[i]`) and _every_ object/record index (`record[key]`) to `T | undefined`, and this codebase leans heavily on dynamic record lookups (normalized Zustand maps like `panelsById`) and array-to-object projections.

## Problem

The flag does not narrow on the checks you'd expect. A length guard (`if (arr.length > 0) arr[0]`), an `in`/`.has()` membership test, or a prior `if (record[id])` does NOT teach the compiler that a _later_ index access is defined — TypeScript re-widens on each separate index expression. So the naive fixes are wrong in two distinct ways: (1) blanket non-null assertion `match[1]!` on regex capture groups, where an optional group can legitimately be `undefined` at runtime; (2) spreading an indexed value twice — `{ ...state.panelsById, [id]: { ...state.panelsById[id], ... } }` — which both fails to type and reads the map index twice.

## Root cause

`noUncheckedIndexedAccess` models the runtime truth that indexing is partial, but TS flow analysis keys narrowing to a specific _expression_, not to the underlying slot. `record[id]` checked on line N is a fresh, un-narrowed `T | undefined` on line N+1. The only sound fix is to bind the indexed value to a local once and guard _that_ local: `const existing = state.panelsById[id]; if (!existing) return state;` then use `existing`. This is simultaneously the type fix and the correct way to write a normalized-map Zustand reducer — it collapses the double lookup and gives the no-op/early-return path an explicit branch.

## Lesson

Three audited patterns from this migration are the canonical fixes; reuse them, don't invent a fourth:

1. **Length/bounds-guarded array access** (`focusNext`-style wrap-around in `terminalFocusSlice.ts`, `sortedWorktrees[0]` in `stateHydration/index.ts:946`): non-null assert `arr[i]!` ONLY when a length/modulo guard makes it provably in-bounds.
2. **`.map(id => record[id])` projection chains**: filter with a typed predicate (`.filter((x): x is T => x !== undefined)`) rather than asserting per element.
3. **Zustand spread into `Record<string, T>`** (`trashActions.ts:78-79`, `:406-407`): capture `const existing = state.panelsById[id]; if (!existing) return state;` (or return a no-op partial), then spread `existing`. Annotate the new map `Record<string, T>` explicitly so the spread types. Never blanket-`!` a regex capture group (`match[1]!`) without confirming the group is non-optional in the pattern — that one _can_ be `undefined` and the `!` hides a real bug.

## Applies when

- Indexing a normalized Zustand map (`panelsById`, `trashedTerminals`, any `Record<string, T>`) inside a `set((state) => ...)` reducer — bind to a local and guard before spreading.
- Writing wrap-around navigation over an array (`(i + 1) % list.length`) and the compiler now flags `list[nextIndex]` — assert `!` only because the modulo guarantees bounds.
- Reading regex `match[N]` for an optional capture group, or any `arr[i]` where a prior `if`/`in`/`.has()` check on a _different_ expression made you assume narrowing.
- Adding a new strictness flag and triaging the blast radius: run the compiler, don't trust the manual estimate — index-access flags fan out far past the predicted file count.
