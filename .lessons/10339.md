## Context

#10339 ("Interface responsiveness") added a shared, gated `withViewTransition` helper (`src/lib/viewTransition.ts`), made a few store actions optimistic, and improved scheduling. Its "feel instant" ideas split along one fault line: a safe subset shipped and stuck; the rest self-defeated.

## Problem

Every idea looked like a pure win at the call site; three failed only in a _downstream_ interaction. Two were dropped in review (a palette crossfade, optimistic git staging); one shipped and was reverted hours later, same day (grid-maximize). The shared misleading trait: the call succeeds, and breakage surfaces on the _next_ action — a later tab-close, a dialog handoff, or where focus lands after a row moves.

## Root cause

Three distinct mechanisms, one theme — a responsiveness trick that mutates layout/focus defers a cost rather than removing it:

1. **Grid-maximize wrapped `toggleMaximize` in a document-level View Transition** (commit `7fde8627c`). A document-level VT snapshots the whole page and holds it across the animation; the maximize mutation landed, but a _subsequent_ tab close never committed — the panel stayed in its group, so the tab bar never collapsed. Reproduced deterministically in `core-panel-tab-groups` e2e and reverted in `f9045f693`. `GridPanel.handleToggleMaximize` is a plain direct `toggleMaximize` again.
2. **The palette prefix-route crossfade gave the outgoing and incoming dialog the same constant `view-transition-name`.** In a keep-mounted handoff both are in the DOM at snapshot time; the name must be unique per snapshot, so the duplicate collided and the morph misfired. Dropped in review.
3. **Optimistic git staging in the Review Hub moved file rows synchronously on click.** The Review-hub file list carries a keyboard-navigation/focus contract (issue #9215, guarded by `ReviewHub.lifecycleAndReadiness.test.tsx`). Reordering focusable rows under the user's cursor jumps focus and violates it. Dropped in review.

## Lesson

- **Route every View Transition through `withViewTransition` (`src/lib/viewTransition.ts`), never bare `document.startViewTransition`.** It falls back to a plain mutation (returning `null`) under reduced-motion / `reduceAnimations` / performance-mode / hidden document, and calls `activeViewTransition.skipTransition()` to end an in-flight transition before starting a new one so rapid re-clicks can't stack snapshots. Pass a `scope` element (Chromium 147+ element-scoped API) to confine the snapshot and avoid capturing unrelated xterm canvases.
- **Do NOT wrap a panel-layout mutation in a document-level View Transition** — grid maximize/restore that moves a panel between groups is exactly the case #10339 got wrong: a later tab-close silently never committed (`f9045f693` reverted it). A document-level VT holds a whole-page snapshot across the mutation and can leave a follow-up state change uncommitted. The proven-safe VT sites still wired: dock→grid restore (`DockedPanel`) and crash-recovery resolve.
- **`view-transition-name` must be unique among every element present during a snapshot — the caller owns naming.** A constant literal breaks in any keep-mounted handoff (palette prefix routes, dialog swaps) where old and new coexist in the DOM: both carry the name, the morph misfires. Derive a per-instance name; the reverted GridPanel path did this right (injected a scoped `<style>` with `panel-maximize-${safeId}`, cleaned up on the transition's `finished` promise so rapid clicks couldn't pile up `<style>` nodes) — the uniqueness pattern was correct even though that call site was still reverted for reason #1.
- **Optimistic UI is safe for property-only changes with snapshot+rollback, but NOT for structural reordering that moves focusable elements under the user.** `projectStore.updateProject` (rename/emoji) and `fleet.deleteNamedFleet` apply immediately and roll back to a captured snapshot on IPC failure — they mutate values, not positions. Optimistic git staging reordered Review-hub rows and broke #9215. If the optimistic mutation moves the element the user is navigating, it's the wrong tool.
- **Prefer the "feels instant" wins that touch neither layout nor focus** — those shipped and stuck: `captureBufferText` tail-scans the xterm buffer bottom-up in doubling rounds keyed on _stripped_ (visible) length (`TerminalInstanceService.ts`), avoiding a full-scrollback scan freeze when the send-to-agent palette opens; `useDeferredValue` on the project-switcher query; and `yieldToScheduler()` (`scheduler.yield()`, Chromium 129+) instead of `setTimeout(0)` between fleet-broadcast batches.

## Applies when

- Adding a View Transition anywhere — reach for `withViewTransition` with a `scope`, never bare `document.startViewTransition`, and never on grid-panel maximize / group moves.
- Assigning a `view-transition-name` for a crossfade/morph between two elements, especially in a keep-mounted dialog or palette handoff where both coexist in the DOM — names must be unique per snapshot; derive them per-instance.
- Making any action optimistic — check first whether the mutation reorders or moves a focusable element under the user (Review-hub list, any keyboard-navigable grid).
- Diagnosing "a panel maximize left a later tab-close stuck" or "a dialog crossfade won't morph" — suspect a document-level VT holding a page snapshot, or a colliding `view-transition-name`.
- Touching `src/lib/viewTransition.ts`, `GridPanel`/`DockedPanel` transitions, `projectStore` optimistic updates, or `captureBufferText`.
