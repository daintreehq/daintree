## Context

`electron/store.ts` builds the persistent electron-store singleton, used app-wide via `import { store }`. In dev, `electron/setup/environment.ts` calls `app.setPath("userData", "<appData>/daintree-dev")` so the dev instance doesn't collide with the production app's settings.

## Problem

The singleton was exported as a module-load side effect: `export const store = initializeStore()`. ESM evaluates that the moment ANY module imports `store` — including preflight, quarantine helpers, and test files that pull in services transitively. If any of those evaluated before `setup/environment.js` ran, `new Store()` resolved `userData` to the production directory (or worse, an unset path), reading/writing the wrong on-disk config. Order of first-import, not intent, decided where settings lived.

## Root cause

A top-level `const x = sideEffectfulInit()` couples object creation to import order. `electron-store`'s constructor immediately reads `app.getPath("userData")` and touches disk, so the side effect is path-sensitive. `app.setPath("userData", ...)` is itself a side effect that must win the race — and import graphs don't guarantee that `environment.ts` is evaluated first just because `bootstrap.ts` imports it before `store.ts`. The fix makes init explicit (`initializeStore()` is now idempotent via a module-scoped `storeInstance`) and calls it from `bootstrap.ts` AFTER `import "./setup/environment.js"` and boot migrations. The `store` export became a `Proxy` (`electron/store.ts:820`) that delegates via `Reflect` and lazy-inits on first access (`getOrLazyInitInstance`, line 811) — so every existing `store.get/set` call-site keeps working without edits, and tests that never bootstrap still get the in-memory fallback the old eager export gave them implicitly. The Proxy must `.bind(instance)` returned functions so detached methods (`const get = store.get`) keep `this`.

## Lesson

Never initialize a path/disk/IPC-sensitive singleton as a top-level `export const x = init()`. Module-load side effects fire at the mercy of import order, which silently loses the race against lifecycle setup like `app.setPath("userData")`. Make init an explicit, idempotent function invoked at a known lifecycle point (`bootstrap.ts`), and if you need to keep the eager `import { store }` ergonomics, expose a `Proxy` that lazy-resolves the instance and binds methods. Surface the unrecoverable case loudly: bootstrap checks `_peekStoreInstance()?.path === ""` (the in-memory fallback signature) and shows a native `dialog.showErrorBox` + `app.exit(1)` rather than letting the app run on a volatile store that loses changes on restart.

## Applies when

Adding or refactoring any main-process singleton whose constructor reads `app.getPath(...)` or touches disk/IPC at construction (electron-store, SQLite, caches, loggers); deciding between `export const x = init()` vs. an explicit `initializeStore()`-style call; or debugging dev settings that land in the production userData dir or appear unset because a module imported the store before `setup/environment.js` ran.
