## Context

Plugin panel views render inside the host renderer, loaded via the `plugin://` privileged protocol as raw, un-transpiled browser ESM (`PluginViewHost` does `React.lazy(() => import("plugin://…"))`). Bare specifiers in that module resolve through the host `<script type="importmap">` `index.html` injects at build, which maps ONLY the five React specifiers (`react`, `react/jsx-runtime`, `react/jsx-dev-runtime`, `react-dom`, `react-dom/client`) to the single `vendor-react` chunk (the React-identity contract of lesson #9493). The data-flow hooks `useHostChannel` / `usePluginEvent` / `usePluginPanelEvent` are thin wrappers over the `window.electron.plugin.invoke` / `.on` / `.onPanel` bridge.

## Problem

The docs told authors to bare-import `usePluginEvent` / `useHostChannel` from `@daintreehq/plugin-sdk/react` inside a panel view and marked them **shipped**. Four test plugins that needed a live view hit a runtime dead end: the import never resolves. The failure is runtime-only — an unresolved-specifier error at first render — so nothing catches it at author or build time (a raw view has no build step). Every author independently fell back to the _undocumented_ `window.electron.plugin.on(pluginId, channel, cb)` bridge: the "shipped" path was a dead end and the working path was invisible. (#10583 filed it; #10512 earlier fixed views _rendering_ — this is the separate problem of a rendered view getting _data_.)

## Root cause

The import map serves ONLY React. `@daintreehq/plugin-sdk/react` has no entry, so a raw un-bundled view's bare import fails at runtime. The hooks resolve _only_ when the view is bundled by `@daintreehq/plugin-vite`: that preset **inlines the SDK** while **externalizing React** (regex `/^react($|\/)/`, `packages/plugin-vite/src/index.ts` — never `external: ["react"]`, which bundles `react/jsx-runtime` as a second React) so React still resolves to the host's single instance. A raw view has no bundler to inline the SDK, so the only transport is the bridge the hooks wrap: `.on(pluginId, channel, cb)` (broadcast, receives `host.postToPanel`/`broadcastToRenderer`), `.onPanel(pluginId, channel, panelId, cb)` (per-instance targeting, #10618), `.invoke(pluginId, channel, ...args)` (request/response → the plugin's `registerHandler`) — all in `electron/preload.cts` (~2959–2986).

The obvious fix — add `@daintreehq/plugin-sdk/react` to the host import map — was considered and **rejected**. That means serving a host SDK chunk; unless it externalizes React exactly like `vendor-react`, it drags in a second React → `Invalid hook call` (the failure #9493 exists to prevent). It also pre-empts deferred F15/F36 SDK-extraction: `@daintreehq/plugin-sdk` is currently a **types-only barrel** (empty `dist/*.js`, all-`.d.ts`) with runtime hooks in `packages/plugin-sdk/src/react/` reachable only via plugin-vite bundling — no publishable SDK runtime to import-map yet. So the fix was docs-only: bundle-or-bridge, not map-the-subpath.

## Lesson

- **A raw `plugin://` view is un-transpiled browser ESM — every bare specifier resolves through the host import map, which serves ONLY the five React specifiers.** Any other bare import (the SDK, lodash, anything) fails at _runtime_ with an unresolved specifier and produces **no build error**, because nothing compiles the file. "Docs say shipped" ≠ "resolves at runtime".
- **The SDK hooks (`useHostChannel`/`usePluginEvent`/`usePluginPanelEvent`) resolve ONLY in a view bundled by `@daintreehq/plugin-vite`** (inlines SDK, externalizes React). For a hand-authored raw view, use `window.electron.plugin.on` / `.onPanel` / `.invoke` directly — the _exact_ transport the hooks wrap, so zero behavioral gap, only missing ergonomics.
- **Do NOT "fix" an unresolved SDK import by adding `@daintreehq/plugin-sdk/react` to the host import map.** That serves a host SDK chunk that, unless it externalizes React the same way `vendor-react` is shared, bundles a second React → `Invalid hook call` (#9493). It also front-runs the deferred F15/F36 SDK extraction. The import-map entry is a deliverable of that work, not a quick bolt-on.
- **`@daintreehq/plugin-sdk` is a types-only barrel** (empty `dist/*.js`, surface in `.d.ts`); the runtime hooks live in `packages/plugin-sdk/src/react/` re-exported through thin `src/hooks/` shims. A `.d.ts` typing `useHostChannel` says nothing about whether the module _resolves at runtime_.
- **When a doc claims a subpath import "works," pin it to the concrete resolver** — the import map for raw views, bundler externals for built views — not the type surface. This PR was a docs correction because the two had silently diverged.

## Applies when

- Authoring or reviewing a `plugin://` panel view, or its docs — choosing between the SDK hooks and the `window.electron.plugin` bridge, or explaining why a hook import fails.
- Diagnosing a raw plugin view throwing an unresolved bare-specifier error at first render (the SDK, or any non-React import).
- Tempted to add a new specifier (the SDK, a shared lib, `scheduler`) to the host import map — check the #9493 React-identity contract and whether the served chunk externalizes React the same way.
- Touching the host import map (`HOST_IMPORTMAP_SPECIFIERS`, `vite.config.ts` `hostImportMapPlugin`, `docs/plugins/architecture.md`), the plugin-vite externals preset, or the `electron/preload.cts` plugin bridge (`on`/`onPanel`/`invoke`).
- Working on F15/F36 SDK extraction/publish — the import-map entry and bare-import ergonomics are that work's job, deferred here.
