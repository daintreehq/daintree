## Context

`useContentGridContext` runs a focus-enforcement effect while a grid tab group is maximized: if `focusedId` sits outside the group it calls `setFocused` to snap focus back to the group's active tab, via `getMaximizedGroupFocusTarget` (`contentGridFocus.ts`). The effect exists to rescue stale persisted focus — a `focusedId` pointing at a panel that no longer exists. `activeDockTerminalId` in `usePanelStore` tracks which dock popover is open, set atomically alongside `focusedId` by both `addPanel.ts` (`activateDockOnCreate`) and `terminalFocusSlice.ts`'s `openDockTerminal`.

## Problem

While a grid tab group was maximized, the dock was effectively unusable (#11065): launching a panel into the dock, or clicking an existing dock chip, opened the popover and the enforcement effect closed it again almost instantly, because it saw `focusedId` sitting outside the maximized group and snapped focus back. `setFocused` clears `activeDockTerminalId` for any grid target, so the popover either flashed and vanished or never appeared to open at all. Only group maximize was affected — a maximized single panel has no such enforcement — which is why the bug hid behind a specific interaction shape.

## Root cause

The tempting fix is "exempt focus enforcement whenever `activeDockTerminalId` is set" — trust the pointer as proof a popover is open. That is wrong and would have been a worse bug: `DockPanelOffscreenContainer`'s watchdog deliberately keeps a dock panel mounted, and therefore keeps `activeDockTerminalId` pointing at it, for as long as the panel still exists in `panelsById` (#7278) — specifically so the popover survives a worktree switch that filters it out of the currently-rendered dock, and reopens correctly when the user switches back. So `activeDockTerminalId` can be non-null for a panel the dock is NOT currently rendering (wrong worktree, trashed, moved to grid, or the help panel, which owns its own surface). Treating that stale pointer as "popover is live" would stand enforcement down permanently and strand focus outside the maximized group — a closes-too-eagerly bug traded for a never-recovers one.

The fix separates the pointer from liveness: a new predicate `isDockPanelRendered` (`dockPanelVisibility.ts`) checks registration in `panelIds`, dockable kind, `location === "dock"`, untrashed, not the help panel, and worktree scope (global or matches `activeWorktreeId`) — mirroring filters `ContentDock` and `DockPanelOffscreenContainer` already inline separately. `useContentGridContext` derives `openDockPopoverId` by running `activeDockTerminalId` through this predicate inside a Zustand selector, not a `useMemo`, because layout undo can rewrite a panel's worktree in place while the pointer itself holds still — a memo keyed on the pointer id would miss that. `getMaximizedGroupFocusTarget` then returns `null` (no enforcement) only when `focusedId !== null && focusedId === openDockPopoverId`, letting the popover's live, deliberate focus stand instead of being read as the stale focus the effect exists to rescue.

## Lesson

- **A persisted pointer to "the currently open X" is not proof X is currently rendered** — keep-alive/watchdog machinery (here, #7278's offscreen-container watchdog) can deliberately keep the pointer valid long after the referent stopped being visible, for good reasons unrelated to your enforcement effect.
- **Before exempting an enforcement/reconciliation effect on a stored pointer, ask what keeps that pointer valid after it should have gone stale** — if the answer is "a different subsystem, on purpose," the naive check is a trap; intersect the pointer with an actual-rendered-state predicate (`isDockPanelRendered`) instead of trusting it alone.
- **Compare against `null` explicitly, not truthiness, when "nothing focused" and "no popover open" collapse to the same falsy value** — `contentGridFocus.ts` uses `focusedId !== null && focusedId === openDockPopoverId` so the no-focus/no-popover case still falls through to the stale-focus rescue instead of short-circuiting on a coincidental match.
- **Derive cross-cutting visibility predicates as selectors returning primitives, not memoized objects** — `openDockPopoverId` is selected as a string-or-null so the selector's equality check short-circuits on unchanged output even though it re-runs on every store write; per-panel-object memoization was the churn source #8593 already fixed once, don't reintroduce it.
- **A new shared predicate doesn't have to immediately replace every inline duplicate** — `ContentDock` and `DockPanelOffscreenContainer` keep their own inlined versions of these filters because those are pinned by literal-source-text assertions in `ContentDock.test.tsx`; `isDockPanelRendered` is documented as the shared definition for them to adopt later, not silently drifting from them today.

## Applies when

- Touching `useContentGridContext.tsx`'s maximized-group focus enforcement, `getMaximizedGroupFocusTarget`, or any effect that snaps focus back based on `focusedId`.
- Adding a check that trusts a store pointer (`activeDockTerminalId`, or any "currently active/open X" id) as proof that X is presently visible, without checking against what's actually rendered.
- Debugging a popover, panel, or overlay that closes itself almost immediately after opening, especially only under one specific parent state (here: only while the grid group is maximized).
- Working near `DockPanelOffscreenContainer`'s keep-alive watchdog (#7278) or any other "keep mounted while still registered" pattern — its side effect is that pointers into it outlive the thing they name.
- Reviewing a fix that exempts an enforcement/reconciliation effect based on a persisted id — confirm the exemption is intersected with live-render state, not the raw pointer.
