## Context

`DndProvider.tsx` drives all panel drag-and-drop (dock↔grid, grid reorder, worktree accordion) on dnd-kit, configured with `MeasuringStrategy.Always` (continuous remeasurement of every droppable's rect, not just a snapshot at drag start). Before #10996, `resolveTargetIndex` in `dropResolution.ts` resolved an exact-terminal hover match to a hardcoded `idx` — landing always immediately before the hovered panel — and the grid only exposes one droppable per existing panel plus the whole-grid container, no dedicated between-slots targets. Issue #10995: with a single panel in the grid, dragging a docked terminal in could only ever land in the first slot; reaching the second slot took two separate drags.

## Problem

#10996 added `resolveGridInsertionIndexFromRects`, comparing the dragged rect to the hovered panel's rect (above/left of midpoint → before, below/right → after) so a drop could target either side of a panel in one drag. That alone reproduced a new symptom during manual testing: hovering the pointer perfectly still over a panel near its midpoint made the placeholder flicker rapidly between the before and after slot instead of settling. It looked like an input/event problem (mouse jitter, dnd-kit event ordering) rather than a self-inflicted measurement loop, because the pointer genuinely wasn't moving.

## Root cause

`MeasuringStrategy.Always` means dnd-kit re-reads every droppable's rect on essentially every frame, so a placeholder-insertion decision that reads those rects is coupled to its own side effect: inserting the placeholder at "after" reflows the DOM, which shifts the hovered panel's measured rect, which can flip the raw geometry verdict back to "before" on the very next measurement — remove the placeholder from "after", reflow again, flip back to "after", repeat. This is the same class of bug as #10872's `isScrollMode`/`ResizeObserver` loop (a layout decision changing the input it's derived from) but the feedback channel here is dnd-kit's continuous drag-rect measurement, not a `ResizeObserver` on a CSS-toggled element. The fix is a hysteresis dead-zone: `resolveGridInsertionIndexFromRects` takes a `previousIndex` and, when the drag center sits within `GRID_INSERTION_HYSTERESIS_PX` (8px) of the hovered panel's horizontal midpoint, returns the previous verdict instead of recomputing from the (now-shifted) rects. The harder part was _where_ to store "previous verdict". `handleDragOver` computes a `groupIndex` against `tabGroups` (group-space — `ContentGrid`'s `SortableContext` is keyed on tab groups, so a multi-panel group collapses to one slot) to drive the live placeholder preview, while `handleDragEnd`'s `resolveTargetIndex` computes against the flat `terminalsById`/`panelIds` arrays (terminal-space) to commit the actual reorder. An absolute index memoized in one space reconstructs wrong in the other whenever the two diverge (any earlier multi-panel tab group shifts terminal-space indices relative to group-space ones). #10996 memoizes `gridInsertMemoRef.current = { overId, after: boolean }` — a target-relative boolean, not an index — and each read site reconstructs its own index locally (`after ? baseIndex + 1 : baseIndex`) against that site's own `baseIndex`.

## Lesson

- **Any drop-position decision computed from live dnd-kit rects under `MeasuringStrategy.Always` is a latent feedback loop**: the placeholder's own DOM position feeds the reflow that the next measurement tick reads back. Suspect this whenever a geometry-derived UI decision flickers while the pointer is stationary — the PR's own description generalizes it to "any live-measured drop preview".
- **Hysteresis memory must be keyed to the hovered target's identity, not just a bare threshold.** `gridInsertMemoRef` is invalidated (`= null`) on every hover-target change, group-drag, placeholder-hover fallback, and drag end/cancel — a stale verdict surviving a target switch would stick the wrong panel's decision onto a new one.
- **When a decision is read back across two different index spaces, memoize the decision itself (a relative boolean), never an absolute index.** Group-space (`tabGroups`, used for the live preview) and terminal-space (`terminalsById`/`panelIds`, used for the commit) diverge whenever a multi-panel tab group exists; storing `after: boolean` relative to `overId` and reconstructing `baseIndex + (after ? 1 : 0)` locally in each space is what makes preview and commit agree.
- **Bias missing/degenerate geometry toward the product-specified default, don't default to "insert before".** `resolveGridInsertionIndexFromRects` returns `after` when rects are unusable or the midpoint is an exact tie, because #10995 explicitly asked for "no clear target → land last", not index 0.
- **Multi-panel group drags are deliberately excluded from the geometry branch** (`isGroupDrag` gate in `handleDragOver`) because they already commit through a separate before-biased path in `handleDragEnd`; extending geometry-based before/after to group drags requires updating both the preview path and the commit path together, or the placeholder will show one slot and the drop will land in another.

## Applies when

- Touching `handleDragOver`/`handleDragEnd` in `DndProvider.tsx` or `resolveTargetIndex`/`resolveGridInsertionIndexFromRects` in `dropResolution.ts`, or adding any new geometry-based drop-position rule.
- Diagnosing a drag-and-drop placeholder, insertion caret, or reorder indicator that oscillates between two positions while the pointer holds still over a target.
- Adding a `MeasuringStrategy.Always` (or any continuous-remeasurement) dnd-kit config alongside logic that reads rects to make a placement decision.
- Adding hysteresis/memoized state for a value that gets computed in more than one coordinate or index space (e.g. a grouped/collapsed view vs. a flat underlying list) — store the relative decision, not the absolute index.
- Extending grid drop targeting to multi-panel tab groups — verify the `handleDragOver` preview and `handleDragEnd` commit stay on the same resolution path so they can't disagree.
