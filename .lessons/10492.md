## Context

Plugin-contributed actions dispatch through the same `ActionService` as built-ins: `usePluginActions` builds a synthetic action `definition` whose `run()` calls `window.electron.plugin.invoke(pluginId, id, args)`. Separately, the #10476 observability arc gave plugin dispatch an audit trail: `PluginActionAuditService.initialize` (main) subscribes to the `action:dispatched` bus event and appends a record with a hardcoded `result: "success"`, while the plugin invoke boundary (#10463, `electron/ipc/handlers/plugin.ts` + `dispatchHandler`) already writes an `error` audit record when a handler throws. #10492 closed the last two remainders of #10476.

## Problem

A plugin action whose handler threw showed the user a correct failure toast, but the machine-readable audit log recorded that same dispatch as a `success` — two rows for one failed invoke, the human-facing signal and the compliance record flatly contradicting each other. Because the two rows were written by different processes on different code paths, nothing at either boundary looked wrong in isolation; the corruption only existed in the merged log a future reviewer or the Settings viewer would read.

## Root cause

`ActionService.dispatch` treats a resolved `run()` as success: it emits `action:dispatched` (which the audit service turns into a `success` row) and returns `{ok:true}`; only a _thrown_ `run()` is caught into `{ok:false, error:{code:"EXECUTION_ERROR"}}` with **no** `action:dispatched` emission. `usePluginActions`' catch — a contain-the-rejection pattern inherited from the #9276 "boundary 2" work — showed its toast and then `return undefined`. That swallow was benign until the #10476 dispatch-success audit subscription existed; once it did, the swallowed rejection made `run()` resolve, so ActionService emitted `action:dispatched` and the audit service appended a `success` row on top of the genuine main-side `error` row. The renderer's local error-handling decision silently poisoned an observability surface two layers away, in another process.

The fix is one line of intent: **`throw err` after the gated toast** instead of `return undefined`. ActionService then returns `{ok:false}` and never emits `action:dispatched`, so no false success row is written and the main-side `error` record (#10463) is the sole audit row. Rethrowing re-exposes the failure to `useActionPalette`, which owns a generic `{ok:false}` toast — that would now double-notify, since the plugin already self-notified. So the palette suppresses its toast for exactly one case: `item.pluginId !== undefined && result.error.code === "EXECUTION_ERROR"` (it threads `pluginId` onto `ActionPaletteItem` for this). A plugin `NOT_FOUND` (stale palette row) never self-notified and a built-in `EXECUTION_ERROR` never self-notifies, so both still toast.

## Lesson

- **In a dispatch pipeline where the success branch fires an observability/audit event, swallowing a rejection is a false-positive at the record layer, not just a lost error.** `ActionService` writes a `success` audit row purely from `run()` resolving; returning `undefined` from a caught rejection manufactures that success. Rethrow after any user-facing handling so the `{ok:false}` result contract stays truthful all the way up.
- **Make the process that owns the failure the sole author of the failure record.** The main-side invoke boundary already writes the authoritative `error` row (#10463); the renderer's job is only to _not_ contradict it. Two independent audit-writers for one event is the trap — the renderer must yield the record, not add a competing one.
- **When you rethrow a rejection that a lower layer already toasted, you re-arm a higher layer's generic toast — suppress it by the narrowest possible key.** The palette gate is `pluginId !== undefined && code === "EXECUTION_ERROR"`, the exact shape `usePluginActions` self-notifies. Do not suppress by `pluginId` alone (would eat `NOT_FOUND`) or by code alone (would eat built-in `EXECUTION_ERROR`).
- **A benign swallow turns malignant when a later PR adds a consumer downstream of the swallowed path.** The #9276 boundary-2 `return undefined` was correct until #10476 subscribed the audit service to `action:dispatched`. When adding a listener to a success event, audit every path that resolves it to confirm none is a swallowed failure.
- **The deliberate exception: user cancellation still `return undefined`s.** A cancelled confirm never invoked the handler, so nothing failed and no main-side error row exists. The distinction is "did the handler run and throw" (rethrow) vs "did the user decline" (return), not "was the outcome not-success".

## Applies when

- Touching `usePluginActions` / the synthetic plugin-action `definition.run()`, or any renderer catch that currently `return`s instead of rethrowing at an IPC-invoke boundary.
- Adding or reviewing a subscriber to `action:dispatched` (or any success-only dispatch event) — verify no upstream path resolves it by swallowing a failure.
- Diagnosing an audit/observability record that disagrees with the toast the user saw, or a `success` row for an action that visibly failed (`PluginActionAuditService`, the Settings `PluginActionAuditLogViewer`).
- Reviewing any pipeline where a lower layer surfaces its own error toast AND a higher layer has a generic failure toast — check for double-notify and the narrowest suppression key.
- Assuming a toast is sufficient error handling — if a machine-readable contract (`{ok}`) or audit event rides on the same return value, swallowing corrupts it silently.
