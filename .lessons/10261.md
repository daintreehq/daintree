## Context

Browser/dev-preview panels host untrusted pages in `<webview>` guests. Main intercepts guest `js-dialog` events (Electron 40+; the event is omitted from the TS overload union, so it's attached via an `as {on}` cast in `setupWebviewCSP`, `electron/setup/protocols.ts`), stores the native `callback` in `WebviewDialogService.pendingDialogs`, and sends `webview:dialog-request` to the renderer through the parent window's app webContents. The renderer hook `useWebviewDialog` (`src/hooks/useWebviewDialog.ts`) queues the request and shows an overlay; `WebviewDialogService` originally only cancelled callbacks from the guest's `destroyed` listener.

## Problem

The overlay covers only the page area — the panel toolbar stays live — so a user can reload, go back, or type a new URL while an `alert`/`confirm`/`prompt` is pending. Afterwards the stale overlay from the old page sits over the freshly loaded page until manually answered, and the answer lands in a page context that no longer exists. Real browsers auto-dismiss JS dialogs on cross-document navigation and renderer crash; Daintree did neither. The renderer queue only dequeued on explicit user response, and the main-side callback leaked.

## Root cause

A JS dialog is bound to a **document**, not to the guest `webContents`. Chromium silently discards the native dialog state on three distinct events — cross-document main-frame navigation, renderer crash, and webContents teardown — but the cleanup was keyed on only the last (`destroyed`). So a navigation or crash left both a leaked main-side callback and a stale renderer overlay. The fix wires one `dismissPendingDialogs` handler to all three (`contents.on("did-navigate")`, `contents.on("render-process-gone")`, `contents.once("destroyed")`); it cancels the main callback via `WebviewDialogService.cancelPendingForGuest(contents.id)` (resolving each pending callback with `false`) **and** broadcasts a new `WEBVIEW_DIALOG_DISMISS` IPC event so `useWebviewDialog` drains its queue (`setDialogQueue([])`). Clearing only one side is insufficient: cancel-only leaves the overlay; drain-only leaks the callback and never satisfies Chromium's native dialog callback.

The subtle, review-surfaced half (second commit `21945e270` inside this PR) is the `destroyed` path: by then the guest's `hostWebContents` is already unreachable, so `getWindowForWebContents(contents.hostWebContents ?? contents)` returns null and there's no parent window to send the dismiss IPC to. The fix caches the parent window during the guest's lifetime via a shared `resolveParentWindow()` helper — it re-resolves and stores `cachedParentWindow` on every call while `!contents.isDestroyed()`, and returns the cached reference (if still alive) once the guest is gone. The `js-dialog` handler routes through the same helper, so the cache is warm before any dialog can be pending.

## Lesson

- **Native UI state tied to a webview's document must be invalidated on document lifecycle, not teardown.** Handle `did-navigate` (cross-document nav) and `render-process-gone` (crash) in addition to `destroyed` — Chromium drops the dialog on all three, and keying cleanup only on `destroyed` leaves stale overlays over the new page.
- **On the `destroyed` path a guest's `hostWebContents` is already unreachable — cache the parent BrowserWindow while the guest is alive** if you need to notify the renderer after teardown. `getWindowForWebContents(contents.hostWebContents ?? contents)` returns null at that point; the PR's `resolveParentWindow()` re-caches on every live call and falls back to `cachedParentWindow` (guarded by `!isDestroyed()`) when the guest is gone.
- **Use `did-navigate`, not a broad navigation event, to distinguish cross-document from same-document.** Same-document changes (hash / `pushState`) emit `did-navigate-in-page` and must be ignored — the dialog's document survives, so dismissing it would be wrong. This distinction is load-bearing, not incidental.
- **The main-side callback and the renderer queue are separate state that must be cleared together.** `cancelPendingForGuest` resolves each pending callback with `false` (swallowing throws from an already-gone guest); the renderer separately drains via `WEBVIEW_DIALOG_DISMISS` filtered on `panelId`. Fixing one without the other reproduces half the bug.
- **Don't over-apply the caching pattern:** `notifyUnresponsive`/`notifyResponsive` in the same file keep the direct live `getWindowForWebContents` lookup because they early-return on `contents.isDestroyed()` and never run post-teardown. The dialog-dismiss path needs caching _precisely because_ it must run on `destroyed`.

## Applies when

- Adding or auditing main-side state keyed on a webview guest `webContents` (dialogs, unresponsive banners, OAuth capture) that must clean up across guest navigation, crash, or remount in `electron/setup/protocols.ts`.
- A `<webview>`/browser-panel overlay, banner, or modal survives navigating the page, crashing its renderer, or a partition-change remount — check that cleanup is wired to `did-navigate` + `render-process-gone` + `destroyed`, not just one.
- Sending a main→renderer IPC from a guest `destroyed`/teardown handler and finding the parent window null — you likely need a reference cached during the guest's lifetime, since `hostWebContents` is unreachable by then.
- Deciding whether to react to a webview navigation event — confirm `did-navigate` (cross-document) vs `did-navigate-in-page` (same-document) before invalidating document-scoped state, and know that `cancelPendingForGuest`/`pendingDialogs` and `useWebviewDialog`'s queue must stay in sync via `WEBVIEW_DIALOG_DISMISS`.
