## Context

ProcessMemoryMonitor (`electron/services/ProcessMemoryMonitor.ts`) polls app-wide metrics every 30s (`POLL_INTERVAL_MS`) and wants per-renderer event-loop saturation telemetry to sit alongside its Blink-memory tier. Each project renders in its own `WebContentsView` with an independent V8 context; the preload (`electron/preload.cts`) runs `sandbox: true`. This PR adds renderer-side event-loop-utilization (ELU) sampling reported back to main, keyed by `webContents.id`, with a per-view streak counter that warns once at 6 consecutive saturated samples (3 min sustained).

## Problem

The obvious implementation — `performance.eventLoopUtilization()` in the preload, sampled on a renderer-owned `setInterval` — fails on two independent axes: the Node ELU API isn't exposed under `sandbox: true`, and a renderer `setInterval` is silently throttled (or suspended) in cached/backgrounded views, so the cadence drifts and produces bursty samples that don't reflect real user-visible lag.

## Root cause

Two stacked Electron/Chromium constraints:

- **`performance.eventLoopUtilization` is unavailable in a sandboxed preload.** The sandboxed preload doesn't get the Node `perf_hooks` ELU surface. The web-platform substitute is a `PerformanceObserver` for `long-animation-frame` (LoAF, Chromium 123+): accumulate each entry's `blockingDuration` between samples. Because the preload shares the renderer main thread with the page, LoAF `blockingDuration` directly measures user-visible JS-thread saturation. By spec `blockingDuration` is 0 for frames < 50ms — that 50ms floor IS the "long task" noise gate, intentionally relied upon.
- **Renderer timers can't drive the sampling cadence.** Chromium throttles/suspends JS timers in backgrounded and cached views (the same throttling exploited by `ProjectViewManager` / lessons #3508, #4683). A renderer-owned `setInterval` would skew or stall exactly when you most need the signal. So **main drives the cadence**: `startAppMetricsMonitor` calls `actions.sampleRendererElu()` each poll, which (defined in `globalServicesInit.ts`) fans a `window:sample-renderer-elu` push event out to every renderer, and each preload replies with its accumulated `blockingDuration` + the wall-clock window width it measured. Crucially the fan-out **filters to `state === "active"` views only** — sampling a throttled cached view would report misleadingly low blocking against a real wall-clock window.

## Lesson

- In a sandboxed preload you do NOT have `performance.eventLoopUtilization`. To measure main-thread saturation, observe `long-animation-frame` via `PerformanceObserver` and sum `blockingDuration`. Wrap `observer.observe({ type: "long-animation-frame", buffered: true })` in try/catch — older runtimes throw; the fallback is "report 0 blocking", not a crash.
- Never sample a per-renderer signal on a renderer-owned `setInterval` if cached/background views matter — Chromium timer throttling makes the cadence unreliable. Drive the cadence from main (here, piggybacked on `ProcessMemoryMonitor`'s 30s poll) and have the renderer reply with both the measured value AND the wall-clock window it measured, so main can derive the ratio without trusting a renderer clock.
- Skip non-active views in the fan-out (`pvm.getAllViews().filter(v => v.state === "active")`). A throttled view's accumulated blocking divided by a real wall-clock window understates saturation and pollutes the streak counter.
- Sampling state keyed by `webContents.id` must be cleared on view eviction — `recordEluSample`/`forgetEluSample` are paired, and `ProjectViewManager.evict` calls `forgetEluSample(wcId)` next to `forgetBlinkSample(wcId)`. The streak map is NOT gap-aware across an active→cached→active transition (documented limitation); a count alone can overstate the contiguous observation window if the signal is ever promoted from telemetry to a proactive trigger.

## Applies when

- Adding any renderer-side performance/health telemetry (event-loop lag, frame timing, jank) that must work from a sandboxed (`sandbox: true`) preload.
- Reaching for `performance.eventLoopUtilization` / `perf_hooks` in a preload and finding it undefined.
- Designing a main→renderer sampling protocol across `WebContentsView` instances where some views are cached/throttled (`ProjectViewManager`, multi-window, `setBackgroundThrottling`/CDP CPU throttling).
- Considering a renderer `setInterval` for periodic measurement and wondering why backgrounded/cached views produce bursty or missing samples.
- Touching `ProcessMemoryMonitor` fan-out, `globalServicesInit.ts` `sampleRendererElu`/`sampleBlinkMemory`, or adding per-`webContents.id` state that needs eviction cleanup.
