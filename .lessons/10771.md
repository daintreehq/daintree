## Context

Daintree runs a WebGL circuit breaker (`TerminalWebGLManager`) that drops panes to xterm's DOM renderer on GPU trouble (M-series Mac + external display at fractional scaling per #6163, software GPU, repeated context loss) or above a per-profile pane-count threshold (Efficiency 8 / Balanced 12 / Performance 14), plus a focus pin (`pinnedId`) keeping the focused pane on WebGL through a fleet DOM-mode flip. #10768 reported a stable horizontal "zebra" (alternating near-black/dark-gray rows) filling full-screen alt-buffer TUI panes (OpenCode, vim, Gemini CLI) on HiDPI/fractional-scaled displays.

## Problem

The pane looked corrupted — full-width horizontal stripes, stable not flickering, covering OpenCode's own prompt box and border bars. It only reproduced on fractional-DPR displays on panes that had fallen to the DOM renderer, which made it easy to misdiagnose as an OpenCode/Ink bug or confuse with the unrelated `RenderService._isPaused` freeze in #10660 (same pane class, different mechanism).

## Root cause

xterm's DOM renderer (`DomRenderer._updateDimensions` in `@xterm/xterm@6.1.0-beta.221`) computes `device.cell.height = Math.floor(device.char.height * lineHeight)` (integer device px), then `css.canvas.height = Math.round(device.canvas.height / dpr)`, then `css.cell.height = css.canvas.height / rows` — that last division is fractional whenever `dpr` is non-integer, and gets stamped onto every row div's `style.height`/`style.lineHeight`. Chromium then pixel-snaps each row's fractional height to the device grid independently, so adjacent rows disagree by ~1 device px and the near-black background bleeds through the seam; repeated down the pane, that's the zebra. `lineHeight: 1.0` in `src/config/xtermConfig.ts` already exists for this failure family but only forces the earlier `Math.floor`, not the later fractional division — the mitigation was incomplete, not wrong. `@xterm/addon-canvas`, the historical third renderer that would have sidestepped this, is gone entirely in xterm 6.x (absent from `package.json` and `node_modules`) — only WebGL (no seam) and DOM (seam) remain. The fix is two-pronged: (1) `TerminalWebGLManager` gained an `altBufferPinnedIds` set, unified with the existing focus pin behind a shared `isPinned(id)` helper across all 8 DOM-mode exemption sites, so alt-buffer panes stay on WebGL through a fleet flip to DOM instead of ever hitting the seam; the pin is visibility-independent (survives hide/reveal, unlike the focus pin) since nothing re-fires a buffer-mode transition on reveal. (2) For panes that must run DOM anyway (breaker tripped, no GPU), `TerminalListenerInstaller` added an `onRender` hook that reads the first row's stamped height and, if non-integer, redistributes `count` rows into `base`/`base+1` px via a midpoint-start Bresenham walk summing exactly to the recovered canvas height (`Math.round(cellHeight * count)`) — an exact sum matters since rows stack in normal flow and drift would push the stack past the fixed-height screen element.

## Lesson

- **A stable (non-flickering) full-width horizontal banding pattern in a terminal pane on a HiDPI/fractional-scaled display is a DOM-renderer cell-height seam, not app or agent-CLI corruption** — check `document.querySelector(".xterm-screen canvas")` (null/inactive means DOM renderer) and `parseFloat(getComputedStyle(rowEl).height) % 1` (non-zero means fractional seam) before chasing the TUI's own rendering.
- **`@xterm/addon-canvas` is gone as of xterm 6.x** — never propose "fall back to canvas" for an xterm rendering gap; only WebGL and DOM remain, so the fix space is always "keep it on WebGL" or "make DOM tile correctly."
- **Per-row/per-cell pixel snapping in a stacked-flow layout must sum exactly to the original container size, and prefer `onRender` over `onResize` to drive it.** `snapDomRowHeightsToIntegerPixels`'s Bresenham walk exists because naive per-row rounding would drift the row stack past the fixed-height `.xterm-screen` element; `onRender` (not `onResize`) is the trigger because renderer swaps and DPR changes re-stamp heights without a cols/rows resize.
- **A pin driven by a stateful transition (buffer-mode change) needs different lifecycle rules than one driven by a repeating event (focus).** `altBufferPinnedIds` is deliberately NOT cleared on hide, unlike `pinnedId` which safely drops on blur since the next focus event re-arms it — nothing re-fires a buffer-mode transition on reveal, so copying focus-pin's clear-on-hide would have broken hidden-then-revealed panes.
- **Every DOM-mode exemption/attach-gate site that checks `id === this.pinnedId` needs the same treatment for any new pin category.** This PR found and updated all 8 such sites (`ensureContext`, `queuePinnedAttach` gating, `evaluateMode`/`flipToDom`, the release-drain loop, in-flight-drain flip check, `releaseNext`, `attachWithLoadedAddon`'s post-drain re-check) behind one `isPinned()` helper — a partial update would silently drop the new category's context mid-lifecycle.

## Applies when

- Diagnosing terminal-pane visual corruption (banding, seams, misaligned glyphs) that only reproduces on HiDPI/Retina or fractional-scaled displays.
- Touching `TerminalWebGLManager`'s pin/exemption logic (`pinnedId`, `altBufferPinnedIds`, `isPinned`, the circuit breaker, fleet DOM-mode flips) or adding a new DOM-mode exemption category.
- Adding or modifying an xterm listener that must react to renderer swaps or DPR changes — deciding between `onRender` and `onResize`.
- Investigating whether an xterm rendering gap can be patched via `addon-canvas` — it is not installed and does not exist in the xterm 6.x line used here.
- Reviewing a fix that redistributes rounded/snapped pixel dimensions across a stacked-flow list — confirm the redistribution sums exactly to the original total.
