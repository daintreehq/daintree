## Context

The local MCP server exposes the `ActionService` manifest as the tool surface for external agents and the in-app assistant. Each session's `ListToolsRequestSchema` handler in `sessionServer.ts` live-fetches the manifest with `requestManifest()` (`rendererBridge.ts`), an IPC round-trip to the active project view. `getCachedManifest()` holds the last-known manifest — the shared `cachedManifest` for unpinned external/api-key sessions, a per-WebContents cache for pinned help-sessions (so window A's tools never leak to a session pinned to window B, #7003/#9887).

## Problem

A transient renderer hiccup — the 5s `requestManifest` timeout, no active project view ("MCP renderer bridge unavailable"), or a renderer mid-teardown/project-switch — made `requestManifest()` reject. The `ListTools` handler had no `try/catch`, so the rejection propagated as a JSON-RPC `InternalError` and wiped the agent's _entire_ tool surface, even though the server held a good last-known manifest and `CallTool` already served from that cache. A cold start or a project switch was enough to leave an agent thinking it had zero tools.

## Root cause

Two parts. First, `ListTools` was the lone handler that ignored the cache: `CallTool`'s `lookupManifestEntry` already consulted `getCachedManifest()` before any live fetch, so only the listing path could hard-fail on a bridge hiccup. The fix falls back to the cached manifest on rejection (fail-open) — a slightly stale list is far less harmful than a failed `tools/list`, since dispatch still re-resolves against the renderer via `dispatchAction`.

Second, the subtle part is _where_ you read the fallback. `getCachedManifest()` reads shared mutable state: `rendererBridge`'s `cachedManifest` is reassigned on every `requestManifest()` success (`cachedManifest = manifest`) and nulled by `clearCache()` on server stop/restart. Reading it in the `catch` **after** the failed await would capture whatever a _concurrent_ operation left it as during the in-flight fetch — a `clearCache()` mid-await nulls it and needlessly fail-closes an unpinned session that had a good cache when the call started; and at the time of this PR `getCachedManifest` for pinned sessions read the live `session→WebContents` map, so a pinned session torn down mid-await (map entry deleted) would flip to the shared cache and serve _another window's_ tools. The fix snapshots `const cachedFallback = getCachedManifest()` **synchronously before the await**, pinning the value while the request is still in flight. The fail-closed split rides on that snapshot: pinned help-sessions return `null` by design, so `cachedFallback === null` → `throw new McpError(ErrorCode.InternalError, "Action manifest unavailable")`. The guard is `=== null`, **not** `!manifest`, so an empty manifest (a legitimate zero-tool surface) is not misread as "unavailable."

The ordering guard survived a later hardening: #9887 (`80a93f002`, same day, _after_ this PR) reworked the pinned `getCachedManifest` to capture `pinnedWebContentsId` at build time and read a per-WebContents cache, independently closing the "flip to shared cache on teardown" race — the `sessionServer.ts` comment still describes the old live-map version, but the snapshot-before-await ordering is still correct defense against the `clearCache`/refresh window.

## Lesson

- **A fallback that reads shared mutable state must snapshot it BEFORE the await it guards, not in the `catch`.** Between the failed `requestManifest()` starting and its rejection landing, a concurrent success (`cachedManifest = manifest`), a `clearCache()` (nulls it), or a session teardown can change what `getCachedManifest()` returns. Snapshot up front so the fallback is the value that was valid when the request began — reading it post-await captures a racing writer's result.
- **Encode fail-open vs fail-closed in the fallback _value_, not the handler branch.** `getCachedManifest()` returns a manifest for unpinned sessions (fail-open to stale) and `null` for pinned help-sessions (fail-closed); the handler stays policy-free (`cachedFallback === null → McpError`, else serve). Route any new MCP fallback's cross-window decision through the same `null`-means-fail-closed convention rather than re-deciding isolation at the call site.
- **Guard the fallback sentinel exactly: `=== null`, never `!value`.** An empty manifest `[]` is a valid zero-tool surface (all tools filtered out by tier); `!` would misclassify it as "cache unavailable" and hard-fail a session that legitimately exposes no tools.
- **Never hard-fail an entire capability listing on a transient bridge error.** A wiped `tools/list` is unrecoverable in the moment; a stale list self-heals on the next fetch and dispatch re-resolves anyway. Mirror the sibling handler that already degrades gracefully (`CallTool`/`lookupManifestEntry`).
- **The tier/visibility filter (`shouldExposeTool`) runs after the manifest resolves, so it applies identically on the live and cached paths** — the fallback can't widen the tool surface past the session's tier. When adding a cache path, keep the security filter downstream of the fetch/fallback merge, never inside the live branch only.

## Applies when

- Touching `sessionServer.ts`'s `ListTools`/`CallTool` handlers or any MCP handler that live-fetches via `requestManifest()` / reads `getCachedManifest()`.
- Adding a cache/last-known fallback around any `await` that reads shared mutable state (`rendererBridge` `cachedManifest`, `perWebContentsCache`) — snapshot before the await, not in the `catch`.
- Diagnosing an agent whose tool surface goes empty or whose `tools/list` fails on project switch, cold start, or renderer teardown.
- Reasoning about cross-window MCP manifest isolation (#7003/#9887) — verify a torn-down pinned session cannot flip to the shared `cachedManifest`.
- Reviewing any fail-open/fail-closed fallback whose open-vs-closed policy is per-session — confirm it rides the fallback value (a `null` sentinel), not a handler branch.
