## Context

The theme pipeline computes every token once at theme-build time: `getAppThemeCssVariables` (backed by `shared/theme/themes.ts`) derives fallback values like `"diff-insert-background": tokens["diff-insert-background"] ?? withAlpha(tokens["status-success"], dark ? 0.18 : 0.1)`, and `applyAppThemeToRoot` writes the whole resolved map as inline styles on the root element. Color-vision-deficiency modes layer on top via `applyColorVisionMode`, which writes `RED_GREEN_OVERRIDES` / `BLUE_YELLOW_OVERRIDES` (`shared/theme/colorVisionOverrides.ts`) as more inline styles; `withStatusSurfaces` already re-derived the `--theme-status-*-surface` washes from the overridden status hex so banners stayed on-hue.

## Problem

With red-green CVD mode active on a light theme, the diff viewer still rendered the original red and green fills — additions vs deletions indistinguishable for exactly the users the mode exists for, on the IDE's primary review surface (#10028). The misleading part: dark-mode diffs, status banners, and header churn text all remapped correctly, so the CVD system looked healthy; only the light-mode diff body bypassed it.

## Root cause

Two independent mechanisms, both generic to the token pipeline.

**1. Baked derivation is invisible to runtime overrides.** No built-in theme sets explicit diff tokens, so every theme's `--theme-diff-*` values are derived from `status-success` / `status-danger` — but at theme-build time, baked into concrete rgba strings. Swapping `--theme-status-success` inline at runtime never re-computes them. The bug only surfaced in light mode because token consumption is split across two CSS tiers: the dark/default diff rules read `--color-status-*` directly (so they track CVD overrides live for free), while the `.light .diff-viewer` rules read the baked `--color-diff-*` tokens (rules now in `src/components/Worktree/DiffViewer.css` ~L224-241; the issue's evidence predates the move out of `src/index.css`, where only the `--color-diff-*: var(--theme-diff-*)` bridge remains). Fix: `withDiffSurfaces` mirrors `withStatusSurfaces` — re-derives the six `--theme-diff-*` tokens (background alpha 0.1, edit-background 0.2, gutter = raw hex; light-polarity alphas only, since dark CSS never reads the baked tokens) from whatever status hex the override map contains, composed as `withDiffSurfaces(withStatusSurfaces({...}))`. The helper is input-gated (`if (!hex) continue`), so applying it to BLUE_YELLOW too is harmless — blue-yellow overrides neither status color and gains no diff tokens.

**2. Base theme and overrides share one physical layer.** `--theme-*` tokens exist ONLY as the inline styles `applyAppThemeToRoot` writes — there is no stylesheet declaration underneath. The old clear path did `root.style.removeProperty(token)` for every token in `ALL_CVD_TOKENS`, which doesn't "reveal" the base value, it destroys it: switching red-green → blue-yellow stripped `--theme-status-success` / `-danger` (which blue-yellow doesn't set) to undefined. Fix: `applyColorVisionMode(root, mode, scheme?)` now restores each token from `getAppThemeCssVariables(scheme)` and falls back to `removeProperty` only when no scheme is supplied; `appThemeStore` threads the scheme at both call sites — critically the EFFECTIVE scheme after `applyAccentOverrideToScheme(resolveAppTheme(...), accentColorOverride)`, not the raw theme, or clearing CVD would also silently revert the accent override.

## Lesson

- **Any token themes.ts derives via `?? withAlpha(...)`-style fallback is frozen at build time — every runtime layer that can override its input must re-derive it.** Adding a new derived token family means auditing the CVD maps (and any future override layer) for a matching `with*Surfaces` helper; the helpers compose, and input-gating makes them safe to apply to every map unconditionally.
- **In an inline-style token system, "clear the override" is not `removeProperty`.** Base and override occupy the same `element.style` slot; without a stylesheet fallback, removal blanks the token. Clearing = re-writing base values from the resolved scheme — and the base must be the effective scheme including accent overrides, or clearing one layer reverts another.
- **Consumption-tier asymmetry hides these bugs.** CSS that reads `--color-status-*` (or `color-mix` over it) tracks overrides live; CSS that reads a baked derived token silently freezes. When a mode "works in dark but not light" (or vice versa), diff the two CSS tiers' token sources before suspecting the override maps.
- **The override maps must stay 3/6-digit hex.** `hexToRgba` produces `rgba(NaN, …)` for oklch/rgb()/8-digit input, which CSS silently drops — no error, just a missing fill.
- **Test derived values against their own inputs, not literals.** The new tests compute expected rgba from the override map's own status hex (catches swapped insert/delete polarity or a wrong alpha without locking hand-tuned hexes) and gate CVD-simulated gutter distance above a 0.05 floor; the `ALL_CVD_TOKENS.size` literal (43 → 49) is an intentional canary, and `-background` washes are excluded from the culori signal filter because rgba() strings are unparseable there.

## Applies when

- Adding a derived token family to `shared/theme/themes.ts` or new tokens to `RED_GREEN_OVERRIDES` / `BLUE_YELLOW_OVERRIDES` in `shared/theme/colorVisionOverrides.ts`.
- Touching `applyColorVisionMode` / `applyAppThemeToRoot` / `appThemeStore` scheme application, or building any new runtime token-override layer (high-contrast variants, per-project theming, accent-style overrides).
- Diagnosing an accessibility/override mode that works in one color scheme but not the other — check which CSS tier consumes live `--color-status-*` vs baked derived tokens.
- Reviewing any code that "resets" state by stripping inline style properties — confirm a stylesheet fallback exists, else it must restore explicit base values.
- Writing CSS that consumes `--color-diff-*` or any other status-derived token (e.g. in `DiffViewer.css`) and expecting it to follow CVD or accent overrides.
