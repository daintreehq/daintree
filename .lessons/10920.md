## Context

`experiment/multi-threading` (#10920) moved CPU-heavy work off single-threaded event loops — worst offender the pty-host — onto persistent `worker_threads` pools in four places: per-terminal output analysis (`AnalysisWorkerPool` behind an `AnalysisBackend` seam, so `TerminalProcess` can run in-thread or worker-backed), main-process SQLite maintenance (`DbWorkerClient` + a second WAL connection), workspace-host copytree generation (`CopytreeWorkerClient`), and renderer diff-syntax tokenization (a module Web Worker). Every path keeps the old single-threaded implementation and falls back to it automatically.

## Problem

Two failure classes, one caught before merge and one after. Review found roughly a dozen concurrency bugs — ordering barriers, respawn state seeding, single-flight races, stale-write clobbers — all variants of "a message from a worker that no longer represents the current state arrived anyway." Four days after merge, follow-up #10953 found a subtler one in production: `ResourceGovernor`'s memory signal silently read near-0% for worker-backed terminals — a 24-terminal fleet with ~440MB of real buffer memory in worker isolates raised no warning and triggered no pre-pause trim — until a worker hit its own heap cap and died with `ERR_WORKER_OUT_OF_MEMORY`.

## Root cause

Electron 37+ has a known bug where repeated worker spawn/terminate cycling crashes the process with `Assertion failed: !flush_tasks_` (documented inline in `AnalysisWorkerPool.ts` and `dbWorkerClient.ts`). That constraint forces every pool into the same shape: spawn once, `unref()`, never `.terminate()` in normal operation, cap respawns hard (`MAX_RESPAWNS_PER_SLOT = 1` for the analysis pool, `MAX_SPAWN_ATTEMPTS = 3` for the DB worker), then degrade permanently to the fallback past the cap.

But persistent doesn't mean stable — a worker backing a terminal's analysis session can still die and be silently replaced mid-session, so every callback or write crossing the worker boundary needs a generation stamp or a late message corrupts the new session. `TerminalProcess`/`WorkerAnalysisDelegate` stamp `onActivityState`/`onWaitingTimeout` with `spawnedAt` and reject a mismatch; `WorkerAnalysisBackend` stamps flow-control acks with a monotonic `feedEpoch`, bumped on every fresh-slot rebuild, and sets `persistSuppressed` so a fresh post-respawn buffer can't clobber previously-persisted scrollback; `DbWorkerClient.advanceFence()` bumps `PRAGMA user_version` on the main connection so a ring write still queued on a dying worker, stamped with the old epoch, no-ops on execution. The review-caught bugs were all missing or incomplete versions of this one guard.

The second trap: `process.memoryUsage()` is scoped to the calling V8 isolate, so moving the headless-mirror buffers into worker isolates made them invisible to `ResourceGovernor`, which only sampled the host's own isolate. Since the persistent-pool design exists specifically to avoid termination, an unguarded worker hitting its own `--max-old-space-size` and dying with `ERR_WORKER_OUT_OF_MEMORY` recreates, one level up, the exact failure the architecture was built to prevent. #10953 fixed it by having `AnalysisWorkerRuntime` self-sample isolate memory every 2s (unref'd timer) and folding that into `ResourceGovernor`'s signal.

## Lesson

- **Never call `.terminate()` on a worker_thread in normal operation on this Electron version** (37+, matches this repo's Electron 42) — spawn/terminate cycling crashes with `!flush_tasks_`. Spawn once, `unref()`, replace a slot only on unexpected `exit`, cap respawns hard, then degrade permanently to the fallback.
- **State that must survive a worker respawn needs a generation stamp, not a null check.** Copy `spawnedAt` (session identity), `feedEpoch` (per-backend in-flight ack counter), or a `PRAGMA user_version` fence (cross-process write ordering) — whichever matches what's racing. Skipping this was the single largest bug class the review caught.
- **`process.memoryUsage()` cannot see another isolate's heap.** A resource governor that only samples the host process goes blind the moment buffers move into a worker — see `AnalysisWorkerRuntime`'s 2s self-sample into `ResourceGovernor` — or it looks free right up until `ERR_WORKER_OUT_OF_MEMORY`.
- **Every worker pool needs a kill switch and a synchronous fallback.** `DAINTREE_DISABLE_ANALYSIS_WORKERS` / `DAINTREE_DISABLE_DB_WORKER` / `DAINTREE_DISABLE_COPYTREE_WORKER` all force the pre-worker path; copy `DbWorkerClient.run(op, fallback)` — try the worker, on _any_ failure run `fallback()` synchronously on main — for new worker-backed operations.
- **Size pools conservatively; worker isolates aren't free.** `defaultAnalysisPoolSize()` caps at 2 workers under 8GB total RAM, 4 under 16GB — a full CPU-derived pool would compete with the heap budget `ResourceGovernor` protects.

## Applies when

- Adding or touching a worker_thread pool (`AnalysisWorkerPool`, `DbWorkerClient`, `CopytreeWorkerClient`) or writing a new one for CPU-heavy work anywhere in `electron/`.
- Diagnosing a stale-data or double-apply race after a worker crash or respawn — grep for `spawnedAt` / `feedEpoch` / `user_version` guards and check whether the new code path has an equivalent.
- Adding a memory-pressure signal or touching `ResourceGovernor` — confirm it actually sees worker-isolate memory and not just `process.memoryUsage()` on the host process.
- Reviewing any PR that spawns a `Worker` and calls `.terminate()` outside of process shutdown — flag it, it crashes current Electron with `!flush_tasks_`.
- Seeing `ERR_WORKER_OUT_OF_MEMORY`, or agent-state detection glitching specifically on worker-backed terminals under a large terminal fleet.
