## Context

During state hydration, orphaned backend terminals no longer carry a `worktreeId`. `panelRestorePhase.ts` recovers the association by calling `inferWorktreeIdFromCwd(terminal.cwd, worktrees)` (`src/utils/stateHydration/statePatcher.ts`), which longest-prefix-matches the terminal's `cwd` against the loaded worktree paths. The `cwd` originates from `node-pty`; the worktree `path` list originates from `simple-git`.

## Problem

On Windows the inference silently failed for any terminal not in the active worktree. The match only worked when both strings happened to use the same separator style, so the panel fell back to `activeWorktreeId` (`panelRestorePhase.ts:495-500`) and attached to the wrong worktree on restore. There is no error — just a quietly incorrect grid-filter association.

## Root cause

The two path sources use **opposite separators for the same logical path**: `node-pty` returns Windows `cwd` with backslashes (`C:\repo\wt-a\src`), while `simple-git` returns worktree paths with forward slashes (`C:/repo/wt-a`). The old comparison checked both separator variants on the _cwd side only_ (`cwd === wt.path || cwd.startsWith(wt.path + "/") || cwd.startsWith(wt.path + "\\")`) but never normalized `wt.path`, so a backslash cwd against a forward-slash worktree path matched neither branch. Testing "both separators" on one operand does not cover the mixed-source case where the _two operands disagree_. The fix normalizes both sides (`replace(/\\/g, "/").replace(/\/+$/, "")`) before the equality/prefix check, and — critically — the longest-prefix tiebreaker now compares **normalized** lengths (`normalizedWtPath.length`), not raw `wt.path.length`, since backslash-vs-slash counts can differ in degenerate cases and the tiebreaker must rank on the same string it matched.

## Lesson

- When two path strings come from **different sources** (node-pty cwd vs simple-git/`git worktree list` paths, OSC sequences, persisted state), assume they may use opposite separators and **normalize both operands** before any `===`, `startsWith`, or length comparison. Accepting "either separator" on one side is not enough.
- Make the failure mode loud in your head: a path comparison that silently returns `undefined`/no-match here produces a **wrong-worktree fallback**, not an exception. Silent-fallback path matches are a Windows-bug class — add a mixed-separator fixture and a sibling-prefix negative case (`C:/repo/wt-a` must not match `C:\repo\wt-a-long`).
- Any longest-prefix / tiebreaker logic must rank on the **normalized** value, not the raw input, so the comparison key and the match key are the same string.
- Note there is no single shared path-normalizer in this repo — `normalizeForComparison` (statePatcher), `normalizePath` (cloudSyncDetection.ts, PluginArchive.ts) are independent locals. If you add a new comparison, write/reuse a normalizer rather than assuming one exists.

## Applies when

- Touching `inferWorktreeIdFromCwd` or any code in `src/utils/stateHydration/` that maps a terminal `cwd` to a worktree.
- Comparing, prefix-matching, or deduping paths where one operand comes from `node-pty` (`cwd`) and another from `simple-git` / `git worktree list` / persisted hydration state.
- Implementing longest-prefix or "is X under directory Y" checks that must survive Windows backslash vs forward-slash inputs.
- Debugging Windows reports where a restored terminal/panel lands in the wrong worktree, loses its worktree filter, or falls back to the active worktree with no error.
- Reviewing any `path.startsWith(other)` / `a === b` path comparison that only handles separators on one side.
