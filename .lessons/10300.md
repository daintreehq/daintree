## Context

Agent activity detection lives in `ActivityMonitor` (`electron/services/ActivityMonitor.ts`), driving the FSM in `AgentStateService` / `shared/utils/agentFsm.ts` over layered pattern / `AgentActivityTemperature` / prompt / completion / boot detectors. In May the commit `f1fdafaba` ("simplify output-driven status detection") added a "simple-output" mode: `buildActivityMonitorOptions` sets `simpleOutputState: effectiveAgentId !== undefined`, and since every production agent monitor has an agent id, they ALL take the simple-mode early returns in `onData()` and `runPollingCycle()`. Four PRs merged 2026-06-07 — #10300 (lead), #10297, #10298, #10299 — repaired the fallout.

## Problem

A cluster of unrelated-looking status bugs: `completed` never fired for any live agent (killing cost/token extraction, blocking #4996); `waitingReason` was always `undefined`; slow-booting agents showed "waiting"; panes stranded on "working" at an idle prompt; a false "Agent waiting for input" notification ~200ms AFTER an agent exited; 1Hz output (retry countdowns, timers) never recovering to working. Misleading part: the docs — rewritten a _month after_ the refactor — still described all four layers as live, so nothing pointed at the mode fork.

## Root cause

Two facts compound. First, the mode fork orphaned everything behind it: the simple-mode early returns sit _ahead_ of the pattern/prompt/completion/boot layers, so for agents `transitionToCompleted`/`detectCompletion`, both `classifyWaitingReason` sites, the compiled `completionPatterns`/`promptPatterns`, and the boot guard never ran — though all still constructed per-spawn, invisible to typecheck and review.

Second, agent state is two coupled machines: the FSM (`agentFsm.ts`) _and_ `ActivityMonitor`'s private `state: "busy"|"idle"`. Every `working→waiting` idle path gates on the private `state === "busy"`, and the FSM watchdog only fires from `waiting` — so promoting the FSM externally without arming the monitor has no route back. #9875/#10297: `TerminalProcess.noteAgentOutputActivity` promotes straight to `working` via `handleActivityState("busy")`, bypassing the monitor whose state stayed `"idle"`. And there are TWO `AgentActivityTemperature` instances (`agentOutputTemperature` per PTY chunk vs `simpleOutputTemperature` poll-to-poll at 50/500ms), so a redraw aliasing the 500ms poll heats the chunk copy (promote) while the poll copy stays cold: stranded forever.

## Lesson

- **When a mode branch becomes the production default, re-wire (or explicitly delete) every layer downstream of the early-return — a still-constructed-but-never-consulted layer passes typecheck and review.** #10300 wired all four into simple mode: `detectPatternsFromData` feeds the rolling buffer; `trySimpleCompletion` gates on dual quiet clocks (`SIMPLE_COMPLETION_MIN_QUIET_MS=1500` on both the activity and data timestamps, so raw bytes past a static viewport still block); `transitionSimpleToIdle` funnels all idle paths through `classifyWaitingReason`; the boot guard holds `busy` with a 3s prompt-history early exit.
- **Any path that promotes the FSM externally must ALSO arm `ActivityMonitor`'s private bookkeeping.** #10297 added `notifyExternalPromotion()`, mirroring `becomeBusy`'s clocks/timers (working hold, debounce, watchdog, recovery debouncers, completion timer) but WITHOUT `onStateChange` — the FSM already transitioned, so re-emitting `"busy"` double-fires. The idle path gates on private `state === "busy"`; skip the monitor and there's no way back. It also `reset()`s `simpleOutputTemperature` so a stale quiet clock can't bounce the FSM back at the next poll (like `notifyFocus`, #8865).
- **Synthetic teardown observations look byte-identical to real transitions — suppress at the source and purge downstream buffers on terminal death.** #10298: `handleActivityState` had no `"dispose"` trigger branch, so the teardown observation fell to the else and published a real `working→waiting` at confidence 1.0 → false post-exit notification. Fix drops it there (log only) and splices the per-terminal `waitingBurstBuffer` on `completed`/`exited` so the 200ms `flushWaitingBurst` can't fire on a dead terminal; the real `completed`/`exited` event still guards the never-stuck net.
- **Sample-count thresholds tuned for bursty content mathematically exclude steady low-frequency output — add a signal dimension, don't loosen the constant.** #10299: `computeStateHint`'s 4-sample minimum with a 900ms `workingMaxChangeGapMs` can NEVER be met by 1Hz output (each late tick resets `changedSampleCount` to 0–1). Observations now carry `signalKind`; indicator-class (`isStatusLineRewrite` — spinners, counters) uses 2000ms / 2-sample, generic content keeps 900ms / 4-sample (still the guard against scroll/resize bursts that `699d9a050` added).

## Applies when

- Touching `ActivityMonitor` simple-output mode (`simpleOutputState`, the `onData`/`runPollingCycle` early returns) or adding any detector layer — verify it runs in simple mode (the production default), not only the non-simple branch.
- Transitioning the agent FSM from outside `ActivityMonitor` (direct `handleActivityState`, `TerminalProcess.noteAgentOutputActivity`) — arm the monitor via `notifyExternalPromotion` or the agent strands in `working`.
- Diagnosing agents stuck on `working` at a prompt, `completed`/`waitingReason` never appearing, or 1Hz retry/timer agents never recovering from `waiting`.
- Debugging a false "Agent waiting for input" notification just after an agent exits/is killed — suspect synthetic teardown observations and the `waitingBurstBuffer` flush.
- Tuning `AgentActivityTemperature` thresholds (`workingMaxChangeGapMs`, `changedSampleCount`, `signalKind`) — prove both directions: 1Hz indicators recover, scroll/resize bursts still don't.
