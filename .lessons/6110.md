## Context

Recipes live in two backing stores: `.daintree/recipes/{name}.json` (git-tracked, team-shared, sanitized — see #4593) and `userData/.../recipes.json` via `ProjectFileStore` (machine-local, holds runtime fields like env secret values, `lastUsedAt`, `usageHistory`, `projectId`, `worktreeId`). The same recipe is represented in both, keyed differently: in-repo recipes carry an `inrepo-` scoped id (`stableInRepoId()`), legacy/local ones carry an arbitrary `recipe-...` id.

## Problem

The two stores drifted into split-brain. Deleting a recipe from only one store let the other resurrect it on the next project load. A corrupted/stale `recipes.json` entry would shadow or duplicate the correct in-repo copy. There was no single authority that aligned the two on load.

## Root cause

No reconciliation step ran on load, and the delete handlers only cleaned one store. `ProjectStore.reconcileProjectRecipes()` (called from `PROJECT_GET_RECIPES` in `electron/ipc/handlers/projectRecipes.ts`) now treats `.daintree/recipes/` as canonical and realigns `ProjectFileStore` every load, handling four distinct cases keyed by id scope:

1. In both → in-repo wins, overwrite the fileStore copy.
2. In-repo only → backfill to fileStore.
3. FileStore only, non-`inrepo-` id → promote legacy recipe to `.daintree/`, then backfill.
4. FileStore only, `inrepo-` id (`isInRepoRecipeId`) → stale (deleted from `.daintree/` but lingered) → prune.

The subtle part is the write-back merge: in-repo is canonical for _content_, but the on-disk in-repo file is deliberately sanitized (env values blanked, `projectId`/`worktreeId` dropped — #4593). So reconciliation must re-merge the runtime-only fields from the existing fileStore copy (env values per matching terminal index, `projectId`, `worktreeId`, `lastUsedAt`, `usageHistory`) onto the canonical record, or every load would wipe secrets and usage metadata. The idempotency guard also has to exclude `projectId`/`worktreeId` from its content-equality check, since the canonical file never carries them.

## Lesson

- When the same entity is persisted in two stores, pick ONE canonical source and run a reconciliation pass on load that realigns the other — don't trust either store in isolation, and don't rely on every write path touching both.
- Enumerate reconciliation by membership × id-scope: in-both, A-only, B-only-promotable, B-only-stale. Decide each case explicitly; a vague "merge" hides the resurrection bugs.
- Delete handlers must clean BOTH stores. A delete from the non-canonical store alone is undone by reconciliation; a delete from canonical alone leaves a stale shadow. In `projectRecipes.ts`, both delete paths now look up the recipe in the other store by id/name and remove it there too (best-effort, with reconciliation as the backstop).
- The canonical store may intentionally hold a _reduced_ projection (sanitized, machine-local fields stripped). Reconciliation must re-merge those non-canonical-only fields back, and the no-op/idempotency check must ignore them — otherwise every load destroys data that only the non-canonical store has.
- Never silently drop an un-reconcilable record. Filename collisions on promotion (two names that slugify to the same file) keep the loser as a project-local recipe and surface a `RecipeNameCollision` upward (the #9195 fix), rather than dropping it.

## Applies when

- Touching recipe storage, reconciliation, or delete handlers in `electron/services/ProjectStore.ts` / `ProjectFileStore` / `ProjectIdentityFiles.ts` / `electron/ipc/handlers/projectRecipes.ts`.
- Any feature with dual persistence: a git-tracked `.daintree/` projection plus a machine-local `userData` store (settings, templates, presets) where one holds secrets/runtime metadata.
- Symptoms: deleted item reappears after restart/project-switch; stale or duplicate config entry shadows the correct one; env secrets or usage metadata wiped on load.
- Designing any "load X, then align Y" pass, especially where the canonical copy is a sanitized/reduced projection and the other holds the only copy of some fields.
