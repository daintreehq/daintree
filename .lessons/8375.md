## Context

When the pty-host drops bytes from the IPC fallback queue during a heavy-output burst (drop-don't-block policy, see #1510/#1572), the renderer surfaces a discontinuity marker in the terminal. `injectDataLossMarker` in `TerminalInstanceService` is the renderer-side entry point; `TerminalParserHandler` registers OSC handlers on the xterm parser (alongside the OSC 52 clipboard block from #3722).

## Problem

The original marker wrote a styled ANSI line (`\x18\r\n\x1b[33m⚠ Output dropped...\x1b[0m\r\n`) directly into the xterm buffer. This coupled the wire format to presentation: the byte count and reason lived inside a human-readable string, so the gap could not be asserted in WebGL-disabled E2E (no rendered pixel to read) and any change to the warning's appearance was a change to the transport.

## Root cause

Two distinct traps:

- **Wire/presentation coupling.** Writing the formatted line straight to xterm means the only record of "data was dropped, here is how much and why" is the human-facing string. There is no structured payload a test or another consumer can read.
- **Write-during-parse reentrancy.** The fix routes the signal through `terminal.parser.registerOscHandler(57301, ...)`. That handler fires _synchronously from inside xterm's parse loop_. Calling `terminal.write()` from inside an OSC handler re-enters the parser while it is still mid-parse — undefined/corrupting behavior in xterm 6.0. The presentation write must therefore be deferred out of the parse callback.

## Lesson

- For renderer-side terminal signals that originate in the pty-host but carry **metadata** (counts, reason codes, state), encode them as a **private-use OSC sequence** rather than a raw ANSI write. Wire format here: `ESC ] 57301 ; <droppedBytes> ; <reasonCode> BEL`. The parser handler consumes it (`return true`) so it never reaches the buffer as text, and fires a typed callback (`onDataLoss(bytes)`). Presentation stays in the renderer, off the wire — and the signal becomes assertable without a rendered pixel.
- Pick the OSC number from the **high private range (57300+)** to avoid clashing with emulator conventions (iTerm2 1337, rxvt 777, WezTerm 1000-range) and your own OSC 11/52 handlers.
- **Never call `terminal.write()` from inside an OSC/CSI parser handler.** It re-enters the parse loop. Defer the write with `queueMicrotask` (see `drawDataLossMarker`), and **re-check instance state inside the microtask** — hibernation/disposal can happen between the OSC write and the deferred draw.
- **Always consume** the private OSC (`return true`) even on malformed payloads, so a crafted/garbled stream targeting your private-use number can never leak into the buffer. Validate the numeric field with a strict `^\d+$` + `Number.isSafeInteger` check — plain `Number()` would coerce `""`, `"0x10"`, `"1e3"`, `"+1"`, `" "`.
- Prepend `\x18` (CAN) to the injected sequence so it cancels any partial in-progress escape sequence mid-stream and the OSC parses cleanly.
- A transient pulse like this is not a runtime state: it is excluded from persistence at the type level (`PersistableFlowStatus = Exclude<TerminalFlowStatus, "data-loss">` in `shared/types/panel.ts`). Don't freeze the terminal on it; fire the marker and resume the prior status. There is no replay — the marker is a gap indicator only.

## Applies when

- Adding any new renderer-consumed signal that the pty-host or another producer needs to inject in-band into a terminal stream (data loss, flow-control transitions, resource-governor events, agent-state markers).
- Writing or modifying an OSC/CSI handler in `TerminalParserHandler.ts`, or registering anything via `terminal.parser.registerOscHandler` / `registerCsiHandler`.
- Symptoms: corrupted/garbled terminal output after a handler runs, intermittent xterm crashes traceable to a `terminal.write` call reached from inside a parser callback.
- Choosing a wire format for terminal metadata and tempted to embed a human-readable line — or needing to assert a terminal signal in WebGL-disabled E2E where no pixel renders.
- Touching `injectDataLossMarker` / `drawDataLossMarker` in `TerminalInstanceService`, the `data-loss` flow status, or `PersistableFlowStatus` in `shared/types/panel.ts`.
