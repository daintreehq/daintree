## Context

`electron/window/deferredInitQueue.ts` is the canonical primitive for pushing non-critical main-process startup work (telemetry, GitHub auth, auto-updater, crash-recovery timer, monitors, MCP server, hibernation/idle/sleep, project bulk-stats) off the first-paint critical path. Producers call `registerDeferredTask({ name, run })`; the queue drains sequentially once the renderer reports it has painted an interactive frame via the `app:first-interactive` IPC (`signalFirstInteractive`), with `setImmediate` interleaved between tasks so renderer IPC stays serviceable during the drain. The renderer side lives in `src/utils/removeStartupSkeleton.ts::notifyFirstInteractive`. Critical services (crash reporter, crash-loop guard, DB migrations, project store, PtyClient construction) stay eager and must NOT use the queue.

## Problem

A deferred-init queue keyed off a single renderer "I'm ready" IPC has three independent ways to silently hang or fire too early, each of which a competent senior eng would miss:

1. Registration happens inside `setupWindowServices`, which `await`s slow/hangable work (PTY host fork, workspace `loadProject`, plugin init) AFTER some tasks are registered. If the drain trigger isn't armed until registration "finishes", any of those awaits hanging means the queue never becomes drainable — deferred services never start, even though the renderer painted fine.
2. The happy-path `app:first-interactive` signal can simply never arrive: renderer crash, shutdown before first paint, or a view that errors during hydration. With no fallback the queue stalls forever.
3. The last window closing and a later macOS `activate` reopening must get a fresh queue (`resetDeferredQueue`), but in-flight `setImmediate` drain callbacks from the prior cycle can wake up after the reset and mutate the fresh cycle's state — marking an empty new queue "drained" before any task runs.

## Root cause

"Drainable" is a separate lifecycle phase from "all tasks registered," and the renderer signal is best-effort, not guaranteed. The design splits the lifecycle explicitly: `finalizeDeferredRegistration()` is called SYNCHRONOUSLY at `perWindowInit.ts:117` — right after the last `registerDeferredTask` and BEFORE any further `await` in window setup. It arms a 10s `unref`'d fallback timer and, if the signal already arrived, drains immediately. So the queue's drainability never depends on a slow await completing. `signalFirstInteractive(webContentsId)` dedups per-`webContents` (via `drainedSenderIds`) and tolerates a `null` id; arriving before `finalizeDeferredRegistration` just sets a latch (`firstInteractiveReceived`) that the finalize step honors. The renderer wraps the signal in TWO nested `requestAnimationFrame` calls (`removeStartupSkeleton.ts:73-75`): a single rAF runs before the paint it scheduled is composited, so one frame guarantees nothing; the second rAF runs after the first frame ships, so "interactive" actually means a frame reached the screen. A `generation` counter (incremented on every `resetDeferredQueue`) is captured at drain start; every `drainNext` callback bails if `drainGen !== generation`, neutralizing stale `setImmediate` chains across a reset.

## Lesson

For any main-process deferred-init queue gated on a renderer-side signal: arm the drain trigger (and a timeout fallback) synchronously before any await that could hang, treat the renderer signal as best-effort with a mandatory `unref`'d fallback timer, and guard `setImmediate`-chained drain callbacks with a generation counter so a queue reset can't be corrupted by a prior cycle's in-flight callbacks. On the renderer, "first interactive" requires a double-`requestAnimationFrame` — one rAF fires before the frame composites and proves nothing. Classify each startup task deliberately: critical-path services (migrations, crash guards, store, PtyClient object) stay eager; only ignorable-until-painted work goes in the queue. Late `registerDeferredTask` calls after drain has begun run immediately (with their own try/catch), so registration order is not a correctness dependency — but the eager/deferred split is.

## Applies when

- Adding a new main-process startup service and deciding whether to `registerDeferredTask` it or keep it eager.
- Deferred services mysteriously never start in some sessions (renderer crashed/hung during hydration, or a new `await` was added to `setupWindowServices` before `finalizeDeferredRegistration`).
- Touching the macOS reopen / multi-window lifecycle where `resetDeferredQueue` runs and a stale drain could race the fresh cycle.
- Wiring any renderer→main "ready/painted" handshake that must survive a lost or never-sent signal.
