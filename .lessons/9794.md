## Context

#9794 (issue #9265) bumped Electron 41 → 42, which is really three bumps at once: Chromium 146 → 148 (lockstep `build.target` change in `vite.config.ts`), Node 22 → 24.15, and V8 → 14.8 with a new NODE_MODULE_VERSION (146). `scripts/postinstall.cjs` rebuilds the native modules (`node-pty`, `win-job-object`, `posix-pty-reaper`) against the Electron ABI on every install; `better-sqlite3` previously sat outside that loop behind a `dlopen` ABI probe that decided whether the prebuilt binary needed rebuilding.

## Problem

`better-sqlite3@12.10.0` would not compile against V8 14.8 — `npm install` died in an opaque C++ error deep in `@electron/rebuild` output, with nothing connecting it to the Electron bump. Separately, after the upgrade, native notifications on macOS dev builds simply stopped appearing: no throw, no rejection, no visible error — `notification.show()` succeeds and nothing is displayed.

## Root cause

V8 14.8 changed the `v8::External` API: `v8::External::New(isolate, value)` and `->Value()` gained a required tag argument (`New(isolate, value, 0)` / `Value(0)`), and `SetNativeDataProperty` stopped accepting `0` for a pointer parameter. The upstream fix existed (WiseLibs/better-sqlite3#1475) but was unreleased, so #9794 backported it as `patches/better-sqlite3+12.10.0.patch` via patch-package, with the External changes gated on `#if NODE_MODULE_VERSION >= 146` — the same node_modules tree still compiled cleanly for the Node ABI (vitest runs under Node), and only the Electron build got the new-signature calls.

Two traps sat in the wiring, both about failure visibility. (1) Ordering: the patch MUST apply before `@electron/rebuild` compiles better-sqlite3 from source, or you get the V8 compile error with no hint the patch was the missing piece — so patch application became the literal first step of `runPostinstall()`, and it ran with `--error-on-fail` because patch-package's default only exits non-zero under CI; without that flag a broken patch on a local dev machine "succeeds" and the developer debugs a C++ error instead. (2) Failure isolation: when the patch failed, better-sqlite3 was excluded from the rebuild list (the other three natives still rebuilt, node-pty's ConPTY post-install still ran) — otherwise its guaranteed compile failure would mask the real cause in the failure report. The PR also deleted the old `dlopen` ABI probe entirely: always rebuilding from source costs ~30s but removes a heuristic that depended on which binary prebuild-install fetched and on CI env vars (`npm_config_runtime`/`npm_config_target`).

The notification half: Electron 42 routes macOS notifications through `UNUserNotificationCenter`, which requires the app to be code-signed. On unsigned dev builds the notification is dropped and the `Notification` emits a `"failed"` event — the only signal that anything went wrong. #9794 replaced the bare `notification.once("failed", cleanup)` with a handler that logs a `console.warn` diagnostic AND still runs `cleanup()` (skipping cleanup on failure leaks the notification in `activeNotifications` until dispose).

**Current state:** the patch machinery is gone. Twelve days later (`4f85a1236`, 2026-06-17) better-sqlite3 `^12.11.1` shipped #1475 natively, so the `patches/` dir, patch-package dep, and its postinstall invocation were all removed — do not go looking for them. What survives on develop: better-sqlite3 rebuilt unconditionally from source in `scripts/postinstall.cjs` (`rebuildModules = [...NATIVE_MODULES, "better-sqlite3"]`), and the `failed` diagnostic in `electron/services/NotificationService.ts` (~line 254).

## Lesson

- **Treat a native-module compile failure after an Electron bump as a V8 ABI break, not a local build problem.** First move: search the module's upstream issues for the new V8/NODE_MODULE_VERSION. The bridge pattern when the fix is unreleased: backport it via patch-package, gated on `#if NODE_MODULE_VERSION >= <new Electron ABI>` so the Node-ABI build (unit tests run under Node) is untouched by the same patch.
- **patch-package only hard-fails under CI by default — always pass `--error-on-fail`.** Without it, a patch that no longer applies "succeeds" on local dev and the developer debugs the downstream compile error instead of the patch.
- **Patches before rebuilds, and isolate the dependent failure.** Apply patches as step zero of postinstall; if a patch fails, skip rebuilding exactly the module it targets (keep rebuilding the independent natives) so the failure report names the patch, not the masked compile error.
- **Prefer unconditional source rebuild over ABI probes.** The old `dlopen` probe's answer depended on which prebuilt binary was fetched, which depended on CI env vars — a fragile three-way coupling traded away for ~30s of build time.
- **A backport patch is a bridge with an expiry.** Watch the upstream release and remove the patch the moment it ships (`4f85a1236` did so after 12 days). A stale patch against a bumped package version silently stops applying — which is exactly what `--error-on-fail` exists to catch.
- **Electron 42 macOS notifications are signing-gated and fail silently.** On unsigned dev builds `show()` displays nothing and the only signal is the `"failed"` event — any `new Notification()` call site needs a `failed` handler that both logs and runs the same cleanup as the success path. Signed release builds are unaffected, so "notifications broken in dev, fine in release" is expected, not a bug.

## Applies when

- Bumping Electron a major version — expect at least one native module (`better-sqlite3`, `node-pty`, `win-job-object`, `posix-pty-reaper`) to break at the V8 ABI layer, and re-check `build.target` in `vite.config.ts` (chrome148 lockstep rule).
- Diagnosing an opaque C++ compile error from `@electron/rebuild` during `npm install` / `npm run rebuild`.
- Reintroducing patch-package or editing the step order in `scripts/postinstall.cjs` — patch application must precede every rebuild, with `--error-on-fail` and per-module failure isolation.
- Diagnosing macOS notifications that never appear in dev builds while release builds work — check for `[NotificationService] native notification failed` warns before touching notify() plumbing.
- Reviewing any `new Notification()` call site or Electron API whose failure mode is an event rather than a throw — the upgrade checklist item is "is the failure event handled with cleanup?".
