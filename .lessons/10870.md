## Context

`ActionService` (`src/services/ActionService.ts`) is the typed dispatch layer behind menus, keybindings, and — via `electron/services/mcp-server/` — every tool the Daintree assistant and external MCP clients can call. #10864 added `agentSessionHistory.list`, a read-only action exposing the closed-session resume journal to the assistant, and declared a `resultSchema` (`AgentSessionRecordSchema` in `src/services/actions/definitions/schemas.ts`) deliberately narrower than the underlying on-disk record. #10870 then added a sibling `agentSessionHistory.getSnapshot` action so the assistant could preview one closed session's captured scrollback on demand.

## Problem

While building `getSnapshot`, review found that `agentSessionHistory.list` was already returning each record's captured `snapshot` (an opt-in scrollback tail, up to ~32KB per session, from the then-new exit-snapshot feature) verbatim in its bulk MCP response — despite `list`'s declared `resultSchema` explicitly omitting a `snapshot` field. The narrower schema looked like it should have been protective; it did nothing.

## Root cause

`resultSchema` + `mcpOutputSchema: true` only feeds `computeSchemas()` (`zodSchemaToJsonSchema(definition.resultSchema, "output")`), which builds the advertised `outputSchema` on `tools/list` — pure documentation. `dispatch()` returns `await definition.run(validatedArgs, runContext)` completely unvalidated (`ActionService.ts:460`), and `sessionServer.ts`'s `CallToolRequestSchema` handler feeds that raw result into `buildStructuredContent(entry, outcome.value.result)`, which (`tierAuth.ts:154-169`) only checks `result` is a non-null, non-array, non-Error object before casting it straight to `structuredContent` — never calling `.parse()`/`.strip()` against `entry.outputSchema`. Nothing between `run()` and the wire enforces the schema. `list`'s `run()` did `const sessions = await window.electron.agentSessionHistory.list(worktreeId); return { sessions };` — forwarding bridge records as-is, `snapshot` and all, regardless of what `AgentSessionRecordSchema` claimed. #10870's fix reconstructed each record by hand (`const lean = sessions.map(({ snapshot: _snapshot, ...rest }) => rest); return { sessions: lean };`) and made `getSnapshot` the sole deliberate, one-at-a-time accessor, scoped to the workbench/assistant tier only, not the external API-key tier (`MCP_TOOL_ALLOWLIST_ENTRIES` in `electron/services/mcp-server/shared.ts`). Caveat for anyone chasing this exact incident: the exit-snapshot feature itself (`getAgentSessionSnapshot`, `AGENT_SESSION_GET_SNAPSHOT`, `agentSessionHistory.getSnapshot`) was removed whole the same day (commit `1325501175af`, "remove exit-snapshot capture feature") — zero references remain in the tree. The action is gone; the schema-is-decorative trap it exposed is permanent and applies to every other action — re-documented today in `agentSessionHistory.ts`'s `normalizeRecords()` comment, which strips a legacy on-disk `snapshot` key because "the MCP `list` action's raw result is serialized without `resultSchema` parsing."

## Lesson

- **A Zod `resultSchema` on an action definition is not runtime validation.** It only becomes JSON Schema for the MCP tool manifest (`mcpOutputSchema: true` → `computeSchemas()`); nothing calls `.parse()` or `.strip()` on it before the value ships. Declaring a schema narrower than what `run()` actually returns does not remove the extra fields.
- **Trace the literal path when auditing an MCP action's exposure:** `definition.run()` → `ActionService.dispatch()`'s unvalidated return → `sessionServer.ts`'s `buildStructuredContent(entry, result)` → `tierAuth.ts`'s shallow "is this a plain object" check → `structuredContent`. Any object shape survives that path unchanged.
- **If the underlying data can carry a sensitive/heavy field, build the lean object by hand inside `run()`** — destructure it away (`const { snapshot: _snapshot, ...rest } = record`) — don't rely on a schema mirror to do it for you. Mirroring an on-disk record type into a "result schema" without checking every field the bridge actually returns is the exact anti-pattern that leaked here.
- **Prefer a scoped, one-at-a-time accessor over exposing sensitive per-item data in a bulk `list`/`search` action**, and gate the accessor to the narrowest MCP tier that needs it (workbench/assistant vs. the external API-key tier) rather than trusting bulk-list callers to behave.
- **The feature can vanish while the trap survives** — `agentSessionHistory.getSnapshot` was removed the same day, but the `resultSchema`/`mcpOutputSchema` mechanism is unchanged in `ActionService.ts` and will bite the next action author who assumes a schema filters output.

## Applies when

- Adding or reviewing any `ActionDefinition` with `mcpOutputSchema: true` and a `resultSchema` — check the literal object `run()` returns matches the schema field-for-field, not just its declared TypeScript type.
- An action's `run()` forwards an IPC/bridge result directly or via a thin wrapper (`{ sessions }`, `{ items }`, `{ records }`) without reconstructing each item — that shape passes leaked fields through unchanged.
- Touching `ActionService.ts`'s `computeSchemas`/`dispatch`, or `sessionServer.ts`/`tierAuth.ts`'s `buildStructuredContent` — confirm any change there still doesn't (or now does) validate results against `outputSchema`.
- Designing an MCP action over data that may carry sensitive fields (tokens, scrollback, file contents, credentials, paths) — default to a scoped single-item accessor gated to the narrowest tier, not a bulk listing.
- Diagnosing an MCP client receiving fields absent from a tool's advertised `outputSchema`, or "I narrowed the schema but the field is still there."
