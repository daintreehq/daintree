## Context

Each project lives in its own `WebContentsView` with an independent V8 context, managed by `ProjectViewManager` (PVM). PVM maps a WebContents to its bound project via `webContentsToProject` (`electron/window/ProjectViewManager.ts`), populated only by `registerInitialView` (the boot window) and the open-project flow. The `project:get-current` IPC handler answers per-sender so each window resolves its own project.

## Problem

Opening File > New Window rendered the previous window's project chrome (toolbar, project name) over an empty worktree grid instead of the WelcomeScreen (#6015).

## Root cause

A user-triggered new window gets a PVM created in `createWindow()` but `registerInitialView` is never called for it, so its WebContents has no entry in `webContentsToProject` and `getProjectIdForWebContents(id)` returns null. The old handler treated "PVM exists but no binding" as a miss and fell through to the process-global `projectStore.getCurrentProject()`, leaking the last-active project into every unbound window. The global singleton is the wrong source of truth for a per-WebContents question: absence of a binding means "no project here," not "use whatever was active last."

## Lesson

For any per-WebContents IPC handler, an unbound sender must resolve to null, not to a global fallback — the renderer renders the correct empty state (`<WelcomeScreen />` on null in `App.tsx`) from that null. This is now generalized in `resolveScopedProjectForIpcContext` (`electron/ipc/projectContext.ts`), shared by `crud.ts` and `app/state.ts`: when a PVM is present, exhaust per-view sources (`getProjectIdForWebContents`, then the `?projectId=` URL param) and return `{ project: null }` if all miss; only fall back to the global current project when no PVM exists at all. Also gate side-effects on the binding: skip `worktreeService.loadProject` for an unbound view, because no MessagePort has been brokered for it and the worktree snapshot would be orphaned.

## Applies when

Adding or editing a main-process IPC handler that answers a per-window/per-WebContents question (current project, scoped worktree state, active session) and is tempted to fall back to a process-global singleton when the sender has no PVM binding.
