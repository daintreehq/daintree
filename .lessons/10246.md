## Context

`panelIdsByWorktreeId` (`src/store/slices/panelRegistry/worktreeIndex.ts`) is a derived per-worktree index over the flat `panelIds` array, introduced by issue #7451 so per-row selectors — `useWorktreeTerminals(wid)` and `AgentButton` — can scope work to a single worktree's panels via an O(1) bucket lookup instead of scanning all of `panelIds` on every per-terminal field tick. It carries a documented reference-stability invariant: the bucket array for any worktree whose membership did NOT change in a mutation must keep the SAME array reference across `set()`, so `useShallow` selectors strict-equality-skip when an unrelated worktree ticks. To honor that, the index has a two-tier maintenance contract: membership changes use the targeted helpers (`addToWorktreeIndex` / `removeFromWorktreeIndex` / `transferBetweenWorktreeIndex`, which only rebuild touched buckets), while pure ORDER changes call the full `buildWorktreeIndex(newIds, panelsById)` (new refs for every bucket, acceptable because reorder is user-gesture rate).

## Problem

After drag-reordering tab groups in the grid or dock, the sidebar worktree terminal lists (`WorktreeTerminalSection`'s `SortableContext`) and the `AgentButton` kept the PRE-drag order — but only until some unrelated mutation happened to rebuild the index, which silently "healed" it. A classic ghost bug: the order looks wrong, then fixes itself on the next unrelated store write. The misleading part: the main grid and two-pane split were UNAFFECTED, so it looked like an isolated sidebar/agent-button glitch rather than an index bug.

## Root cause

`reorderTabGroups` in `tabGroups.ts` rebuilt `panelIds` into the new order and then returned only `{ panelIds: newIds }` — it never rebuilt `panelIdsByWorktreeId`. Its three sibling ordering actions in `ordering.ts` (`reorderTerminals`, `moveTerminalToPosition`, `restoreTerminalOrder`) all end with `panelIdsByWorktreeId: buildWorktreeIndex(newIds, ...)`, each carrying the same comment `// Rebuild bucket order so per-worktree selectors observe the new order (issue #7451)`. `reorderTabGroups` was the one order-mutating action that missed it. Because the consumers read bucket order DIRECTLY (`useWorktreeTerminals` iterates `panelIdsByWorktreeId[worktreeId]` and renders rows straight from it; `AgentButton` picks the first matching active session in bucket order), the stale bucket surfaced as stale UI. The grid/split escaped because they derive order from `getTabGroups`, which sorts by `panelIds` — a different, freshly-updated source. The fix (#10246, resolving #9939) adds `panelIdsByWorktreeId: buildWorktreeIndex(newIds, state.panelsById)` to the final return, plus a regression test in `worktreeIndexInvariant.test.ts`.

## Lesson

- **Every panel-registry mutation that changes the ORDER of `panelIds` must rebuild `panelIdsByWorktreeId` in the SAME `set()` return** — targeted add/remove/transfer helpers cannot express a within-bucket reorder, so ordering paths need the full `buildWorktreeIndex(newIds, state.panelsById)`. Returning bare `{ panelIds: newIds }` from a reorder is the bug shape; grep the `ordering.ts` siblings for the canonical pattern before writing a new one.
- **Know which tier applies: membership vs order.** Membership changes (add/remove/transfer a panel) use the targeted helpers to PRESERVE bucket reference stability (#7451) so unrelated per-row selectors skip; only pure order changes may full-rebuild. Do NOT "fix" a membership path by swapping in `buildWorktreeIndex` — that would hand every bucket a new array ref and re-fire every `useWorktreeTerminals` selector on every per-terminal tick.
- **A stale-derived-index bug can be partial and self-healing, which misdirects triage.** Only consumers reading the index DIRECTLY (`useWorktreeTerminals`, `AgentButton`) showed stale order; consumers deriving from `getTabGroups` (grid, split) looked fine, and any later unrelated mutation rebuilt the index and erased the evidence. "Some views update, some don't, and it fixes itself" points at a missed derived-index rebuild, not at the views.
- **`getTabGroups` sorts by `panelIds`; the sidebar/agent-button read `panelIdsByWorktreeId` buckets** — these are two order sources kept in sync by the mutation, not one. When they disagree after a reorder, the write that touched `panelIds` forgot the index.

## Applies when

- Adding or editing any action in `src/store/slices/panelRegistry/` that reorders `panelIds` (reorder/move/restore/tab-group drag) — mirror the `ordering.ts` sibling pattern and rebuild the worktree index in the same return.
- Diagnosing "the sidebar worktree terminal list / agent button shows stale order after a drag, then fixes itself on the next action" — suspect a `panelIdsByWorktreeId` rebuild missing from the reorder path, not the rendering component.
- Touching `worktreeIndex.ts` helpers (`buildWorktreeIndex`, `addToWorktreeIndex`, `removeFromWorktreeIndex`, `transferBetweenWorktreeIndex`) — respect the reference-stability invariant: full rebuild only on order changes, targeted helpers on membership changes.
- Reviewing any Zustand slice with a derived index over a flat array where some consumers read the index and others re-derive from the source — verify every source mutation updates BOTH, and add a `worktreeIndexInvariant.test.ts`-style assertion that the index reflects the new state immediately.
