## Context

`electron/bootstrap.ts` enables Node's V8 compile cache at boot (`enableCompileCache(userData/compile-cache)`) so the multi-MB packaged main bundle skips re-parsing on later launches. Issue #9772 flagged that nothing had ever verified it does anything: `module.flushCompileCache()` appeared nowhere in the repo, `enableCompileCache()`'s return value was discarded, and the cold-start perf harness (`scripts/perf/lib/packagedLaunch.ts`) minted a fresh temp `userDataDir` per run — so every cold-start sample ever collected was cache-cold and a warm boot had never been measured.

## Problem

Three invisible failure modes, none producing any signal: (1) Node persists compile-cache writes to disk only on graceful process exit, and Daintree has crash-loop-guard machinery precisely because exits aren't always clean — a crashy first session could leave the cache empty forever, every launch re-parsing the bundle; (2) a `FAILED` status from `enableCompileCache()` (unusable directory) is indistinguishable at runtime from a working cache — the app just silently runs uncached; (3) even if the cache worked, the perf pipeline could never show the win, so a regression here would never be caught.

## Root cause

Two platform facts compound. First, Node's compile cache is write-on-graceful-exit: entries accumulate in memory and only hit disk when the process tears down normally; `flushCompileCache()` (Node 22.10+) is the only explicit commit. Daintree's shutdown coordinator terminates every quit — even a clean one — via `app.exit(outcome === "clean" ? 0 : 1)` in `electron/lifecycle/shutdown.ts`, and Electron's `app.exit()` skips `will-quit` and the normal teardown sequence, so relying on Node's own exit-time flush (or on a `will-quit` hook) is structurally unsafe here. Second, `enableCompileCache()` returns `{ status, directory }` exactly once — Node exposes no later getter and no programmatic hit/miss API — so a failed enable is undetectable unless the status is captured at the call site. The only hit/miss observability at all is `NODE_DEBUG_NATIVE=COMPILE_CACHE` on a manual run.

The fix (#9791) flushes at two chosen points: in `bootstrap.ts` immediately after `await import("./main.js")` resolves (first-run writes survive any later crash/SIGKILL, and the synchronous fs write stays off the boot-critical path), and at the top of `runShutdownChain` before its first `await` (so the flush can't race the cleanup hard-timeout that ends in `app.exit()` — same doctrine as the eager `takeBackup()` beside it). The status is stashed via `setCompileCacheEnableStatus()` and attached to the `APP_BOOT_START` NDJSON mark by `getCompileCacheMeta()` (`electron/utils/hostPerformance.ts`), with a `console.warn` on `FAILED`. The harness gained `--warm` (one persisted profile dir + an unmeasured warmup boot, results bucketed cold-vs-warm in `coldStartAggregate.ts`).

## Lesson

- **Exit-time persistence must live inside the shutdown chain, never on `will-quit`.** Daintree's terminal action for every quit path is `app.exit()`, which never emits `will-quit`. Put the work in `runShutdownChain`, synchronous and before the first `await`, so the cleanup timeout can't preempt it.
- **Any write-on-clean-exit facility needs an explicit post-boot flush.** With crash recovery machinery in the app, "persists on graceful exit" means "may never persist". `flushCompileCache()` after the boot-critical import is one cheap synchronous fs write; without it a crashy first session yields permanently cold boots.
- **Capture one-shot status returns at the call site and put them in telemetry.** `enableCompileCache()`'s status has no getter afterwards; `setCompileCacheEnableStatus()` → `getCompileCacheMeta()` → `APP_BOOT_START` mark is what makes "cache silently disabled" detectable from NDJSON instead of a debug session. When reading that mark: `ENABLED` (1) and `ALREADY_ENABLED` (2) are both healthy — the tests document 2 as the normal production path — only `FAILED` (0) / `DISABLED` (3) are broken.
- **Strip `NODE_COMPILE_CACHE` (and `NODE_DISABLE_COMPILE_CACHE`) from perf-harness child envs.** If the agent shell or dev machine sets it, Node enables the cache against that shared directory before the app's own `enableCompileCache()` runs — "cold" baselines silently hit a warm cache and the numbers are bogus. `launchPackagedAndMeasure` deletes both keys.
- **Warm-harness gotchas:** Node nests cache files one level down in a versioned subdir (`compile-cache/v22.x-arch-<hash>/`), so counting the base dir always yields 0 or 1 — `countCompileCacheFiles` sums the subdirs. And the perf NDJSON is append-only with a first-wins `parseBootDuration`, so a reused warm `userDataDir` must have its marks file removed before each launch or every warm run reports the warmup boot's timings.
- The PR-era `npm run perf:cold-start` was later consolidated into the dispatcher: it's now `npm run perf cold-start -- --warm` via the `REGISTRY` in `scripts/perf/index.ts`.

## Applies when

- Touching `electron/bootstrap.ts`, `electron/lifecycle/shutdown.ts`, or adding anything that must persist at quit (settings, journals, caches) — the `app.exit()`/no-`will-quit` constraint applies to all of it.
- Diagnosing why packaged boots don't get faster on second launch, or verifying the compile cache at all — run the packaged app twice against the same `--user-data-dir` with `NODE_DEBUG_NATIVE=COMPILE_CACHE` and look for hit lines; check `compileCacheStatusName` in the `APP_BOOT_START` NDJSON mark first.
- Writing or modifying any perf harness that launches Electron/Node children and claims "cold" baselines — audit the inherited env for `NODE_COMPILE_CACHE` and mind the append-only NDJSON when reusing profile dirs.
- Assuming `enableCompileCache()` "just works" once called, or that Node flushes the cache on Daintree's clean quit — neither holds here.
- Reviewing changes to `scripts/perf/cold-start.ts` / `coldStartAggregate.ts` bucketing — degraded (wall-clock-fallback) runs are excluded from cache-kind buckets by design; don't pool them back in.
