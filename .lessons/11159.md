## Context

`XtermAdapter.tsx` owns the single `attachCustomKeyEventHandler` callback deciding, per keydown, whether a key reaches xterm/the PTY as-is, gets rewritten, or is intercepted for a Daintree keybinding/action (chords, `terminal.focus*` pane navigation, etc). Issue #11154 asked for Option+Left/Right to jump the shell cursor by word on macOS, matching Ghostty and iTerm2's "Natural Text Editing" preset. `macOptionIsMeta: true` was already set in `src/config/xtermConfig.ts`, so Option+B/F already worked.

## Problem

Option+Left/Right did nothing in the terminal — no cursor movement, no error, key just absorbed. The natural assumption was that `macOptionIsMeta` should already cover this since Option+B/F worked fine; it doesn't, and chasing that config value further would have been a dead end.

## Root cause

`macOptionIsMeta` only rewrites **character** keys to their Meta-prefixed byte; xterm has no equivalent option for arrow keys. For Option+Left/Right it always emits the CSI modifier sequence (`\x1b[1;3D` / `\x1b[1;3C`) regardless of that setting. Neither zsh's ZLE nor bash's readline binds those CSI sequences to word motion by default — only the meta sequences `\x1bb` / `\x1bf` (`ESC b` / `ESC f`, i.e. `backward-word` / `forward-word`) are bound out of the box. So the fix isn't a config flag, it's an app-level rewrite: intercept the raw KeyboardEvent in `XtermAdapter` and write `\x1bb`/`\x1bf` directly via `getOptionWordJumpSequence` (new pure function in `terminalWordNavigation.ts`), bypassing xterm's own CSI-arrow encoding entirely (`return false` from the handler suppresses it).

That rewrite has to be scoped or it breaks other things. Three traps, all resolved in the same handler: (1) a full-screen TUI (vim, less — the alternate screen buffer) decodes the CSI modifier arrows itself as its own Alt+Arrow binding; rewriting there hands it a Meta+B/F it never asked for, so the gate is `!terminalInstanceService.getAltBufferState(terminalId)`, read **live on every keypress** (not cached at handler-install time, since `attachCustomKeyEventHandler` installs once per mount and a TUI can flip the buffer mode any time after). (2) The pre-existing `if (event.repeat) return true` early-return exists to skip repeats for the chord/keybinding system further down — but word jump must keep firing on a held key, so the repeat branch became `return wordJumpSequence ? writeWordJump(event, wordJumpSequence) : true`, resolving word jump **before** the repeat check reaches (and could complete or invalidate) a pending chord. (3) The behavior being copied is iTerm2's opt-in "Natural Text Editing" preset, not either terminal's shipped default — both iTerm2 and Ghostty emit the CSI arrows out of the box, so this is a deliberate product choice, not "restoring standard terminal behavior."

## Lesson

- **`macOptionIsMeta` (or any per-app "Option is Meta" toggle) does not cover arrow keys** — it's character-keys-only in xterm.js. A missing Option+Arrow/Alt+Arrow binding needs its own CSI-sequence rewrite, not a config tweak; check `\x1b[1;3D`/`\x1b[1;3C` (CSI modifier arrows) vs `\x1bb`/`\x1bf` (meta sequences) before assuming a flag exists.
- **Any rewrite meaningful only in the shell line editor must gate on alt-buffer state read live per keystroke**, via `terminalInstanceService.getAltBufferState(terminalId)` — not a value captured when `attachCustomKeyEventHandler` was installed. The buffer can flip (shell → vim → shell) any time after mount without a remount.
- **`event.repeat` early-returns in `XtermAdapter` are a chokepoint, not a blanket skip.** A rewrite that must keep firing on a held key (word jump, and anything like it) has to resolve _inside_ the repeat branch, before the chord/keybinding resolution below — otherwise an auto-repeat either silently stalls after one firing or leaks into `keybindingService.getPendingChord()`/`resolveKeybinding` and completes a chord the user never re-pressed.
- **When a key rewrite bypasses xterm's own `onData` path (`return false`), manually replicate what `onData` would have done**: call `terminalInstanceService.notifyUserInput(terminalId)` and the captured `stableOnInput` callback, or input-tracking/agent-composition accounting silently drops that keystroke (`writeWordJump`'s comment references #8255). Keep the synthetic payload empty for pure-motion keys — a cursor jump isn't composed text and shouldn't count toward composition totals.
- **Verify a platform-parity claim before citing it as precedent.** iTerm2 and Ghostty ship the CSI modifier arrows by default; word-jump matches iTerm2's _opt-in_ "Natural Text Editing" preset, not either app's default. Don't describe a deliberate UX choice as "matching standard terminal behavior" in comments/PR text — it invites someone to "fix" it back to the CSI passthrough later.

## Applies when

- Adding or modifying key rewrites inside `XtermAdapter`'s `attachCustomKeyEventHandler` (word navigation, macro keys, any Option/Alt/Cmd combination that should behave differently than xterm's default encoding).
- Diagnosing "a key combo does nothing in the terminal but works in iTerm2/Ghostty/VS Code" — check whether the shell's readline/ZLE actually binds the sequence xterm emits, not just whether xterm emits _something_.
- Touching the `event.repeat` branch, the alt-buffer gate, or the chord/`keybindingService.getPendingChord()` resolution order in `XtermAdapter` — these three are coupled in one code path and an edit to one changes the others' correctness.
- Writing a new synthetic-input path that returns `false` from the custom key handler — check whether `notifyUserInput`/`stableOnInput`/composition-tracking need manual replication.
- Comparing Daintree's terminal-key behavior to another terminal app's default — confirm it's actually the shipped default and not an opt-in preset before writing that comparison into a comment, issue, or PR body.
