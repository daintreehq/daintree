## Context

`handleProjectGetBulkStats` in `electron/ipc/handlers/projectCrud/stats.ts` retrieves stats for all projects at once for the project switcher, which polls it every ~10 seconds while open. Internally it built per-project agent counts (active/waiting) and ran per-project stats lookups against the pty utility process. The pty-host's `get-all-terminals` and `get-terminals-by-state` query handlers serialize each terminal through `mapTerminalInfo` in `electron/pty-host/handlers/terminalInfo.ts`.

## Problem

Two distinct defects in the same bulk-stats path:

1. **N+1 IPC pattern.** The old aggregation called `getTerminalAsync` once per terminal to build agent counts. With 10 projects × 8 terminals each, a single `getBulkStats` run triggered ~180 IPC round-trips across the renderer-host ↔ pty utility-process boundary — repeated on every 10s poll. Each individual call looked innocuous, which is why the quadratic cost was easy to miss.
2. **Silent `isTrashed` bug.** `mapTerminalInfo` read `isTrashed` off the raw `TerminalInfo` record, but that field is not maintained on the in-memory terminal object — trashed-ness lives in the pty-host registry. The field was therefore always `undefined`, so trashed terminals silently counted as live in the agent tallies.

## Root cause

1. The aggregation iterated a collection by issuing one cross-process async fetch per element instead of fetching the collection once and grouping in memory — the classic N+1 shape, where the boundary crossing is the dominant cost.
2. The serialized `TerminalInfo` shape and the pty-host registry are two different sources for the same logical state. `isTrashed` is registry-derived (via `ptyManager.isInTrash(id)`), not a stored field on `TerminalInfo`. Reading it directly off the deserialized object compiled cleanly because the optional field exists in the type, but it was never populated — TypeScript can't catch an optional field that the producer never sets.

## Lesson

- When aggregating data that requires iterating a collection, batch the underlying fetch first, then aggregate in memory. `handleProjectGetBulkStats` now issues a single `deps.ptyClient!.getAllTerminalsAsync()` and runs the per-project `getProjectStats` lookups in parallel via `Promise.all` / `Promise.allSettled`, then groups agent counts by `projectId` from the one bulk terminal list. A loop of async calls that each cross a process boundary (IPC, network) is an N+1 pattern even when each call looks cheap.
- When reading fields off deserialized IPC objects, verify the producer actually sets the field — don't trust that an optional field is populated just because it typechecks. The fix reads trashed-ness from the authoritative source: `isTrashed: ctx.ptyManager.isInTrash(t.id)` in `mapTerminalInfo`. The registry and the serialized `TerminalInfo` both exist for valid reasons but have different shapes; always trace which shape you're reading from.

## Applies when

- Any bulk-stats handler that loops over terminals/windows/processes and fetches per-element across a process boundary.
- Reading derived state (trashed, active, paused) from IPC objects — always trace which object shape supplies the field and confirm the producer populates it.
