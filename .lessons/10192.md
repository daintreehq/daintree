## Context

Daintree's forge layer is host-neutral: providers register as plugins (`getRegisteredForgeProviders()`), GitHub ships as a builtin, GitLab is in flight. Most forge IPC calls resolve the provider from the project's git remote via `resolveForCwd(cwd)` — legitimate context. But `FORGE_VALIDATE_TOKEN` (the pre-save Test button in Preferences → Code Forge) validates a raw token with no repo context, so the old handler had nothing to resolve from and fell back to ambient global state.

## Problem

The GitHub Test button reported valid GitHub PATs as invalid. The action dispatched `forge.validateToken` with `{ token }` only; the handler read global `forgeDefaultProviderId`, and when that didn't match — or was unset — fell back to `providers[0]`, whichever forge registered first, validating a GitHub token against GitLab (issue #9985). The misleading part: this is exactly the flow a user reaches for when a token misbehaves, so a false "Invalid token" points them away from the real problem. The save path (`GITHUB_SET_TOKEN` → `validateGitHubToken`) was never affected — only the pre-save Test flow, which made it easy to overlook.

## Root cause

The payload carried no provider identity, so selection was inferred from process-global state (`store.get("forgeDefaultProviderId")`, else `providers[0]`). That default was **latent-correct only while GitHub was the sole registered forge** — with one provider, "first registered" is always right. The forge abstraction was built for multiple providers, so the fallback became wrong the instant a second could register, and it was fail-_open_: on failure to resolve it routed to a _different, arbitrary_ provider instead of refusing. The peer channel `FORGE_SET_CREDENTIAL` (`forgeSettings.ts`) already did it right — explicit `providerId`, strict `getForgeProviderImpl(providerId)`, no fallback — and that inconsistency was the tell. The fix: payload is now `{ providerId, token }`; the handler normalizes via `normalizeProviderId`, resolves strictly by canonical `makeForgeProviderId(pluginId, contributionId)` (`{pluginId}.{contributionId}`), and returns a resolved `{ valid: false, error: "Unknown forge provider …" }` for unknown/inactive providers. The pre-fix handler even had a bare `contribution.id === providerId` fallback alongside the canonical match; the fix dropped it to make matching strict.

Relocated since merge (all verified present): the action moved `githubActions.ts` → `src/services/actions/definitions/forgeActions.ts` (`forge.validateToken`); the settings tab moved into the builtin plugin (`plugins/builtin/github/renderer/components/GitHubSettingsTab.tsx`); the deprecated `github.validateToken` alias was later dropped with the other `github.*` aliases (`bd95e2c84`). The handler (`electron/ipc/handlers/forge.ts`) and id helpers (`shared/utils/forgeProviderIds.ts`) are unchanged.

## Lesson

- **A provider-neutral IPC surface with no natural resolution context (no cwd/remote to key on) MUST carry the target `providerId` explicitly — never infer it from global default or first-registered.** `resolveForCwd`-based calls are fine because the git remote _is_ the context; `validateToken` had none, so ambient global state silently picked the wrong backend.
- **On failure to resolve a provider, fail closed: return a resolved `{ valid: false, error }`, never fall back to a different provider.** Falling back to `providers[0]` doesn't degrade gracefully — it produces a confidently-wrong result (valid token → "invalid") against a backend the user never chose. Match strictly by canonical `makeForgeProviderId` id; don't add a loose `contribution.id` fallback.
- **"Pick the default / first X" is invisibly correct while there's exactly one X, and becomes a bug the moment a second registers.** Any provider/plugin-neutral surface built in the single-provider era can reproduce this; audit for implicit-default selection wherever the abstraction is designed to hold more than one implementation (forge, agent, plugin registries).
- **A provider-specific UI must pin its own provider id, not read the global default,** and require it at the schema boundary: the GitHub tab passes `BUILTIN_GITHUB_PROVIDER_ID`, and the action `argsSchema` requires `providerId: z.string().min(1)` so a legacy `{ token }` caller hits a loud `VALIDATION_ERROR` instead of silently routing to a non-GitHub default.
- **Copy the strictest sibling channel, not the loosest.** `FORGE_SET_CREDENTIAL` already modeled explicit-id + strict-impl-lookup + no-fallback; `validateToken`'s divergence from it was the diagnosable signal it was fail-open.

## Applies when

- Adding or reviewing any forge IPC channel or `forge.*` action that operates without a `cwd`/remote to resolve the provider from (`electron/ipc/handlers/forge.ts`, `src/services/actions/definitions/forgeActions.ts`) — require an explicit `providerId` and resolve it via `normalizeProviderId` + `makeForgeProviderId`.
- Diagnosing a "valid token reported invalid" (or credential/API call hitting the wrong backend) once more than one forge provider is registered or a non-default global forge is set.
- Building any provider-, agent-, or plugin-neutral surface where selection falls back to a global default or `list()[0]`, or wiring a provider-specific settings tab/button — pin the caller's own canonical id (e.g. `BUILTIN_GITHUB_PROVIDER_ID`), never lean on the stored global default.
- Reviewing any registry lookup whose "not found" branch falls through to an arbitrary entry instead of returning a resolved failure.
