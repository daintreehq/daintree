## Context

`daintree-plugin dev` (this PR) implements the CLI's dev command: build once, symlink the plugin into `~/.daintree/plugins/<name>`, write `.dev-marker`, load/activate it over the CLI control socket, then rerun on every `vite build --watch` rebuild. Plugins in dev mode already ran inside a `utilityProcess.fork` worker (`PluginDevWorkerHost`, #9304), with the real host bridged over a `MessagePort` (`PluginDevWorkerMainBridge` on the main side, `pluginDevWorkerHostProxy` in the worker). Before this PR, `registerFileDecorationProvider` was an unconditional dev-mode stub, same as `registerForgeProvider` — both just warned "not supported in dev mode" and returned a no-op disposer.

## Problem

`FileDecorationProvider` looked exactly like `registerForgeProvider` on the surface: a plugin registers an implementation object, the host later calls into it. Both were stubbed identically, so it read like both had the same structural blocker. But decoration providers actually needed to work in dev — plugin authors iterating on a file-decoration extension had no way to test it without packaging and installing, which defeats the entire purpose of `daintree-plugin dev`.

## Root cause

The two provider interfaces differ in exactly one dimension that matters for a `MessagePort` boundary: how the host _consumes_ the implementation's return value. `FileDecorationProviderImpl.provideDecorations(scope, paths)` is called by the host as part of an already-async decoration-refresh pass — the host is happy to `await` it. `ForgeProviderImpl.parseRemote(url)` (plus the URL builders and `classifyPushError`) is called synchronously at the point the host needs an immediate routing decision — there is no `await` at that call site, and adding one is an API-shape change the host side doesn't make just to accommodate the worker. Because every worker host-call is inherently async over the port, `provideDecorations` proxies as a one-line wrapper (`this.invoke({ kind: "file-decoration-method", providerId, method: "provideDecorations", args: [scope, paths] })`), while `parseRemote` cannot: proxying it would make it return a `Promise<RepoRef | null>` where the host's routing logic reads a value synchronously, so the provider would register but never actually route — a silent no-op worse than the honest stub. The fix was recognizing the two interfaces aren't the same shape of problem: implement the one that composes (`provideDecorations`), leave the one that doesn't (`parseRemote`) permanently stubbed (same gap reconfirmed in #10550 for the production worker). The decoration proxy also guards reload races: `PluginDevWorkerMainBridge` captures `this.reloadGeneration` before `await this.host.registerFileDecorationProvider(...)` settles, and disposes the just-bound provider if `this.disposed || generation !== this.reloadGeneration` by resolve time — else a worker respawn mid-registration leaks a provider bound to a dead generation. Unregister uses an identity-guarded delete (`fileDecorationProviders.get(providerId) === impl` before removing) so a stale disposer from a since-overwritten `providerId` can't evict the currently-active implementation.

## Lesson

- **When two host APIs look structurally identical (both "plugin registers impl, host calls into it"), check the call site's sync/async expectation before assuming they share a blocker.** `provideDecorations` and `parseRemote` were stubbed with the same warning text pre-#10494; only reading where the host actually consumes the return value (awaited pass vs. synchronous routing decision) revealed one is fixable and one is structural.
- **An interface is boundary-proxyable over MessagePort iff the host already awaits its result.** If the real, non-worker call site is `await impl.method(...)`, a worker proxy is a one-line `this.invoke(...)` wrapper. If the call site reads the return value synchronously (no `await`), a `MessagePort` proxy would silently change its type to `Promise<T>` and break the caller without a build error — don't attempt it; stub it honestly instead (see #10550's `registerForgeProvider` stub for the wording pattern).
- **Guard provider registration against reload races with a captured generation number, not just a `disposed` flag.** `PluginDevWorkerMainBridge` snapshots `reloadGeneration` before the `await`, then disposes the result if the generation moved — a plain `disposed` check alone misses the case where the worker reloaded (new generation) without the bridge itself being disposed.
- **Guard provider unregistration by identity, not just by key.** Deleting `providerId` from the map unconditionally would let a stale disposer captured by an earlier `register()` call evict a different implementation that a later `register()` on the same id installed; compare `map.get(id) === thisImpl` before deleting, on both the worker-side proxy and the main-side bridge.

## Applies when

- Adding a new plugin-contributed provider interface (anything shaped like `register<X>Provider(descriptor, impl)`) and deciding whether it can run inside the dev/prod worker — read the host's actual consumption call site first, don't assume from the registration shape.
- Touching `pluginDevWorkerHostProxy.ts` or `PluginDevWorkerMainBridge.ts` provider-registration cases (`registerFileDecorationProvider`, `registerForgeProvider`) or extending the `file-decoration-method` / equivalent invoke-relay pattern to a new provider kind.
- Debugging a plugin provider that "registers fine but never gets called" across a worker boundary — check whether the host's consumption of it is sync (permanently blocked) vs async (should proxy cleanly, so the bug is elsewhere).
- Adding disposer/unregister logic for any worker-relayed registry (`providerDisposers`, `fileDecorationProviders`) — apply the identity-guarded delete and reload-generation-guard patterns rather than an unconditional map delete.
