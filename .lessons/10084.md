## Context

Main-process IPC handlers validate renderer payloads with Zod. The canonical contract (`electron/ipc/validationError.ts`) is: log the full Zod detail main-side via `z.prettifyError`, then throw `ValidationError(channel)` whose message is only `"IPC validation failed: <channel>"` — schema shape, field paths, and user-supplied values never travel back to the renderer. `parseIpcPayload` (`electron/ipc/utils.ts`) and schema-bearing ops in `defineIpcNamespace` (`electron/ipc/define.ts`) implement it. Issue #9883 found six handler sites doing manual `safeParse` and embedding the raw error instead; #10084 fixed them. Sibling PR #10101 hardened the analogous telemetry boundary (see `.lessons/10101.md`).

## Problem

`copyTree.ts` (five sites) and `appAgent.ts` (`handleSetConfig`) built renderer-bound error strings as `` `Invalid payload: ${parseResult.error.message}` ``. It reads like ordinary error hygiene — include what went wrong — but in Zod v4 (pinned `^4.3.6`) `ZodError.message` is not a sentence: it is `JSON.stringify` of the full issues array — field paths, issue codes, expected/received types, and the raw user-supplied values. copyTree made it worse than a developer-only leak: `error` is a field of `CopyTreeResult` that renders as user-facing error text, so the JSON blob could hit the UI verbatim.

## Root cause

Two mechanisms, both invisible at the call site. First, the Zod v4 API trap: `error.message` looks like the idiomatic human-readable summary (on most error classes it is), but Zod v4 made it the serialized machine-readable issue list; `z.prettifyError(error)` is the human formatter, and even that carries field paths and received values — fine for a main-process log, never for the boundary. Second, the enforcement gap: the sanitizer lives in the throw path (`ValidationError`), but four of the six sites don't throw — copyTree reports failure through returned result objects (`{ content, fileCount, error }`) because its callers consume results, not rejections. A contract enforced by a throwing helper is structurally bypassed by every result-object error channel, and the sites looked compliant because they already logged `z.prettifyError` locally. The fix: throw sites (`copytree:get-file-tree`, `appAgent` set-config) route through `ValidationError(channel)`; result-object sites return the static string `"Invalid payload"` (current copyTree.ts lines ~277/344/502/710).

## Lesson

- **Never embed `ZodError.message` (or `prettifyError` output) in anything renderer-bound or user-facing.** In Zod v4 `message` is the JSON issues array with raw user input inline. Log detail main-side with `z.prettifyError`; cross the boundary with `ValidationError(channel)` or a static string.
- **A sanitizer that lives in the throw path does not cover result-object error channels.** Handlers returning `{ error: string }` (copyTree's `CopyTreeResult`) bypass `ValidationError` structurally. When auditing a sanitization contract, enumerate every route an error takes to the renderer — thrown IPC rejections AND returned fields — not just callers of the helper.
- **Prefer schema-bearing `defineIpcNamespace` ops over manual `safeParse` inside handlers** — the define-layer parse throws the sanitized `ValidationError` for you; manual validation is where all six divergent sites came from. Result-object handlers that can't throw must sanitize by hand.
- **Substring assertions can't catch leak-by-append.** The pre-fix tests asserted `stringContaining("Invalid payload")` — which passed against the leaking `"Invalid payload: {json}"` too. #10084 tightened them to exact `stringMatching(/^Invalid payload$/)` plus negative contains (no `expected`/`received`/raw value) on the thrown message. Sanitization tests must pin the exact message.
- Test gotcha: copyTree channels share the `"fileOps"` rate-limit bucket (`checkRateLimit`, 10s window), so a validation-path test running after other handler calls in the suite gets preempted by the rate limiter — advance fake timers past the window (11s) before invoking.

## Applies when

- Writing or reviewing any IPC handler in `electron/ipc/handlers/` that validates with Zod and reports failure to the renderer — especially manual `safeParse` blocks.
- Tempted to interpolate `error.message` from a `ZodError` (or any structured error type) into a renderer-bound string, toast, or result field.
- Adding a result-object error field (like `CopyTreeResult.error`) — the throwing sanitizer will not cover it; return a static sanitized string inline.
- Writing tests that assert a sanitized boundary message — use exact match, never `stringContaining`.
- Auditing what crosses the `window.electron` trust boundary after a Zod major bump — v4 changed what `.message` contains.
