## Context

`PtyClient` (now via `electron/services/pty/PtyHostLifecycle.ts`) supervises the `daintree-pty-host` UtilityProcess: on death it must classify the crash (`CrashType`), emit `host-crash-details` to the renderer, and decide whether to auto-restart. The only signal `UtilityProcess`'s own `exit` event gives is an exit code — no signal, no reason. `classifyCrash(code, signal)` is a pure heuristic over that code (137→OOM, 134→ASSERTION, 128+N→signal). Electron exposes a far better signal on the app object: `app.on("child-process-gone", (_e, details))` carries an authoritative `details.reason` (`"oom"`, `"killed"`, `"crashed"`, `"launch-failed"`, `"integrity-failure"`, etc.) plus a reliable `details.exitCode`.

## Problem

The intuitive wiring — classify inside the `exit` handler, optionally enrich from `child-process-gone` — silently loses the authoritative reason every time. On Electron 37–41 the two events fire in the WRONG order: `exit` usually fires BEFORE `child-process-gone` for utility-process crashes (electron/electron#42283). So an `exit`-handler classification has nothing to enrich from and always falls back to the exit-code guess. Separately, the exit-code itself is unreliable: Windows pre-41.0.4 mangled the signed/unsigned exit code on the `exit` event (fixed in electron/electron#50386, Electron 41.0.4), and on Windows the POSIX `128+signum` heuristic turns NTSTATUS codes like `0xC0000005` into garbage signal strings (lesson #7028).

## Root cause

`exit` and `child-process-gone` are emitted on different objects (the `UtilityProcess` vs `app`) with no ordering guarantee, and the more-informative one arrives second. A synchronous `exit` handler executes before the gone event is queued, so it can never see the reason — the classification is locked in too early.

## Lesson

Split capture from classification and bridge the gap with `setImmediate`:

1. Register ONE `app.on("child-process-gone")` listener, filtered to your host by `details.type === "Utility"` AND (`details.name === "daintree-pty-host" || details.serviceName === "daintree-pty-host"` — both are typed optional and Electron 41 populates `name` from `serviceName` at runtime). The handler does nothing but stash `{ reason, exitCode }` into a `pendingChildProcessGoneReason` field.
2. The `exit` handler does NOT classify inline. It computes a `fallbackCrashType` and schedules a `setImmediate` continuation. That one-tick defer lets the later-arriving gone event populate the pending field first.
3. In the continuation: if a reason was captured, `mapGoneReasonToCrashType(reason)` wins and `details.exitCode` overrides the exit event's code (defense against the Windows mangling bug); otherwise fall back to the heuristic. Then clear the pending field so it can't leak into the next host cycle. Two more invariants the defer window opens: (a) clear `pendingChildProcessGoneReason` on dispose, on restart, AND in the deferred continuation — three sites, because a missed `exit` would otherwise carry a stale reason forward; (b) guard the auto-restart with `if (this.child !== null) return`, since a renderer-driven `manualRestart()` can spawn a new host during the defer window and an unguarded restart would orphan it. This pattern is now the canonical host-supervision shape, duplicated in `WorkspaceHostProcess.ts` for the workspace host — each instance keys its filter on its own service name so concurrent per-project hosts don't cross-capture.

## Applies when

Supervising any Electron `UtilityProcess` (pty-host, workspace-host, future hosts) and you need to classify WHY it died or react differently per crash reason. Any time you wire `child-process-gone` enrichment onto an `exit` handler — assume `exit` fires first and never classify synchronously inside it. Reach for this whenever a crash-classification or restart-decision path reads only the UtilityProcess exit code; the `reason` string is more reliable and the exit code is platform-unreliable.
