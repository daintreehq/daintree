## Context

The worktree sidebar renders through react-virtuoso, and `useScrollIndicator` (`src/components/Sidebar/useScrollIndicator.ts`) drives the "N more above" / "N more below" offscreen-count pills. The list is heterogeneous: worktree rows vary ~120–260px and section headers are interleaved, all flattened into one `sidebarItems` array of `{ kind: "row" | "header" }` entries. Virtuoso runs with `SIDEBAR_VIRTUOSO_OVERSCAN_PX = 600` — that overscan is load-bearing, not a tuning knob: it keeps `useSortable` hooks mounted just past the viewport so dnd-kit drop targets survive a drag past the edge.

## Problem

The pills reported counts that didn't match what was actually scrolled out of view (#9666). The trap is that the two obvious data sources both produce plausible-looking numbers: the shipped code used a scroll-height fraction estimate (`round(itemCount * clientHeight/scrollHeight)` apportioned by `scrollTop/scrollableHeight`), and the tempting fix — read virtuoso's rendered range and treat first/last rendered as first/last visible — is wrong in a different way. Neither fails loudly; both are just consistently off.

## Root cause

The fraction estimate assumes uniform row heights. With 30px headers mixed among 120–260px rows the item-per-pixel density varies along the list, so mapping scroll fractions to item counts is systematically biased — and it counts headers as hidden "items" on top of that. The rendered-range approach fails because virtuoso's rendered set is the _mounted_ set: inflated by 600px of overscan on each side (~2–5 rows here), so first-rendered ≠ first-visible. Shrinking the overscan to make them converge isn't available — it exists for dnd-kit drop-target liveness.

The fix (#9677) computes visibility from ground truth: virtuoso's `itemsRendered` callback supplies per-item `{ index, offset, size, data }`; each rendered `kind: "row"` item is classified against the live viewport `[scrollTop, scrollTop + clientHeight]` with a 1px `VISIBILITY_EPSILON_PX` (a row flush against an edge must not flicker between states), and a partially-visible row counts as visible. Items outside the rendered window are unmounted and carry no geometry at all — they're counted straight off the backing `items` array by index (`i < firstRenderedIndex` / `i > lastRenderedIndex`), filtering to `kind === "row"`. Two subtleties make the naive wiring wrong: (1) `itemsRendered` only fires when the mounted set _changes_ — scrolling within the overscan window fires nothing — so the geometry is cached in `renderedItemsRef` and the `onScroll` path (rAF-coalesced per #9580) recomputes from cache against fresh `scrollTop`; (2) cached geometry describes one specific layout, so it's tagged with the identity of the `items` array it was measured against (`geometryItemsRef`), and on mismatch (filter/sort/group changed the list) the hook returns a conservative 0/0 until virtuoso re-fires with fresh geometry — an identity check chosen precisely because it's ordering-independent, with no reliance on effect-vs-callback timing (hardened in-PR by `06fdae89a`). The hook call in `SidebarContent.tsx` also had to move below the `sidebarItems` memo, since the indicator now consumes the full flat list rather than a count. Post-merge commit `a00cc677b` moved the `itemsRef.current = items` latest-value mirror from the render body into an effect: writing a ref during render violates React's concurrent/strict-mode purity, and the effect write is sufficient because every reader (virtuoso callbacks, scroll/resize handlers) runs post-commit.

## Lesson

- **Never derive per-item visibility counts from `scrollTop`/`scrollHeight` fractions on a heterogeneous list.** Variable row heights and interleaved non-item rows make item-per-pixel density non-uniform; the estimate is plausible and systematically wrong, which is worse than obviously broken.
- **Virtuoso's rendered range is the mounted range, not the visible range** — inflated by overscan on both sides. If the overscan is load-bearing (here: dnd-kit drop-target liveness), you can't tune it away; derive visibility by comparing each item's `offset`/`size` from `itemsRendered` against the live scroll position instead.
- **`itemsRendered` does not fire for intra-overscan scrolls.** Any consumer of its geometry must cache it (in a ref, not state — no re-render needed) and recompute from cache on `onScroll`; keep the rAF coalescing so a scroll burst costs one layout read.
- **Tag cached layout geometry with the identity of the input array it measured; on mismatch return a conservative zero-state, never measure stale offsets against a new layout.** Identity comparison is ordering-independent — it beats any choreography of "clear the cache in an effect before the callback lands".
- **Unmounted items have no geometry by definition** — count them from the backing list by index range outside `[firstRenderedIndex, lastRenderedIndex]`, applying the same kind filter as the rendered path so headers never inflate counts.
- **Latest-value refs must be written in an effect, not during render** (`a00cc677b`) — render-phase ref writes break concurrent/strict-mode purity; the effect write is safe whenever all readers run post-commit.

## Applies when

- Adding any visible-range-derived affordance to a react-virtuoso surface — offscreen pills, "new items below" jumpers, unread markers, scroll-position indicators. `LogsContent`, `EventTimeline`, and `ConsolePanel` also render via virtuoso and have none yet; this hook is the template.
- Touching `useScrollIndicator.ts`, the virtuoso wiring in `SidebarContent.tsx`, or `SIDEBAR_VIRTUOSO_OVERSCAN_PX` — the overscan value is coupled to dnd-kit drop-target liveness, not just render-ahead smoothness.
- Tempted to treat `itemsRendered`/`rangeChanged` indices as "what the user currently sees", or to estimate counts from scroll geometry on any list with mixed row kinds or variable heights.
- Diagnosing offscreen counts that are wrong after a filter/sort/group change, oscillate at viewport edges (epsilon), or freeze during slow scrolls (the non-firing intra-overscan window).
