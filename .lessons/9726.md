## Context

Fleet broadcast has two entry doors with identical blast radius (N armed PTYs): the structured path (`tryFleetBroadcastFromEditor` — Enter in a fleet primary's hybrid input fans the draft out via `executeFleetBroadcast`) and the raw path (`broadcastFleetRawInput` — typing directly into an armed terminal mirrors every keystroke chunk to all armed peers). Issue #8689 / PR #8725 (2026-05-20) built an elaborate D2 confirm on the structured path only: `fleetBroadcastConfirmStore` (deferred-promise store), two confirm shapes in `FleetArmingRibbon` (inline warning strip + divergence `ConfirmDialog` with per-target resolved-payload preview and opt-out), destructive/byte/multiline detection (`FLEET_DESTRUCTIVE_RE`, `FLEET_CONFIRM_BYTE_THRESHOLD` = 512B, `needsFleetBroadcastConfirmation`, `getFleetBroadcastWarnings`, `getFleetBroadcastDestructiveMatch`), and escape-stack/chord integration.

## Problem

Fifteen days later, #9722 / PR #9726 (2026-06-04) deleted the entire apparatus — store, both dialogs, all detection helpers, their test corpus, and the `useFleetEscapeChords` `pendingBroadcast` parameter. To a future auditor the current code looks alarming: destructive commands, large pastes, and multiline payloads all fan out to N terminals with zero confirmation, from a codebase whose CLAUDE.md destructive-tier rules normally demand `ConfirmDialog` at D1 and confirm+preview at D2. The obvious "fix" — re-adding the gate — would reverse a documented deliberate decision.

## Root cause

The confirm only ever guarded one of two equivalent doors, and the other door cannot be gated by construction. `broadcastFleetRawInput` mirrors each PTY data chunk as typed — by the time `data === "\r"` arrives (the submit), every byte of `rm -rf` has already reached every armed pane character-by-character. There is no submit-time interception point on the raw path that isn't after the fact. So the choice was never "confirm both paths vs one"; it was "confirm one door and leave the identical other door open (theater), or accept that consent lives elsewhere." The team ruled that arming a 2+ fleet IS the explicit opt-in — once armed, submit just submits — and moved broadcast awareness to ambient UI: `useFleetArmingStore.getState().noteBroadcastCommit()` bumps a counter (`broadcastSignal`) that the ribbon diffs to fire a one-shot commit flash. #9726 added the same call to the structured path on non-cancelled fully-successful fan-out, so both doors now signal identically. The audit row in `docs/architecture/destructive-action-safeguards.md` (line ~128) was reclassified D2 → D1 with wired = "safe (deliberate, #9722)" — an explicit, documented exception to the D1-gets-a-ConfirmDialog norm.

What stayed is as instructive as what left. The Enter-time snapshot of `useFleetTargetOverridesStore` (`initialOverrides` / `initialSkipped`) was originally justified by a dialog-specific cascade: the divergence ConfirmDialog's focus trap closed the Radix popover, whose on-close effect called `clear()`, so a live re-read at resolve time would silently submit un-reviewed defaults — the #7880 silent-fallback class. The dialog is gone, but the snapshot survives with a rewritten comment: any async gap between capture and dispatch is enough for a popover-close effect to clear the store mid-send. The dispatch-time safety also survives: `doSend` re-filters against live `resolveFleetBroadcastTargetIds()` and re-runs `filterEligibleIds` so panes that disarmed or lost their PTY between Enter and dispatch receive nothing.

## Lesson

- **Do not re-add a confirm to `fleet.broadcast` — the removal is a ruling, not a gap.** The audit row says "safe (deliberate, #9722)" at tier D1 with no dialog; treating that row as a violation and "fixing" it reopens a settled decision. Anyone proposing a gate must engage #9722's rationale, not just wire a ConfirmDialog.
- **A safeguard on one of several equivalent-blast-radius paths is theater; check every door before building the gate.** #8725 spent a full store + two dialog shapes + a regex corpus protecting the structured path while the raw path fanned out the same bytes unconfirmed. Before adding any destructive-action confirm, enumerate all routes to the same effect and confirm each is gateable.
- **When paths can't converge on "gated" (the raw keystroke mirror dispatches before submit), place consent at mode entry instead of per-submission.** Arming the fleet is the consent boundary; per-send awareness demoted to the ambient ribbon flash (`noteBroadcastCommit` counter-bump, subscribers diff their last observed value). This is the fleet precedent for "arming-as-consent" arguments elsewhere.
- **When deleting a blocking step, re-derive which of its defenses guarded the dialog vs the async gap — keep the latter.** The overrides snapshot and the dispatch-time eligibility re-checks (`filterEligibleIds`, live armed-set re-filter) outlived the confirm because they protect any capture→dispatch gap, not the dialog. Never swap the snapshot for a live re-read inside `doSend`.
- **The detection machinery is gone on purpose — don't resurrect it from git history casually.** `FLEET_DESTRUCTIVE_RE`, the 512-byte `FLEET_CONFIRM_BYTE_THRESHOLD`, and friends were deleted with their tests; only `FLEET_LARGE_PASTE_BYTE_THRESHOLD` (100KB) and `FLEET_LARGE_PASTE_BATCH_SIZE` survive in `fleetBroadcast.ts`/`fleetExecution.ts` because they serve batching/perf, not consent.
- **Safeguard changes must land with the audit doc in the same PR.** #9726 updated both the D2 table row and the known-bypasses row; `check:confirm-wiring` (`scripts/codegen/confirm-wiring.mjs`, gates `npm run check`) plus `actionDefinitions.quality.test.ts` make the safeguards doc load-bearing, not commentary.

## Applies when

- Auditing `docs/architecture/destructive-action-safeguards.md` or running a destructive-tier sweep and finding `fleet.broadcast` fanning out destructive commands with no confirm — it is classified "safe (deliberate, #9722)".
- Touching `tryFleetBroadcastFromEditor`, `broadcastFleetRawInput`, `FleetArmingRibbon`, or proposing any confirmation/warning step in the fleet submit path.
- Designing a confirm for an action reachable via multiple paths (structured submit vs raw/keystroke/IPC side door) — verify every path is actually gateable before building the gate.
- Tempted to re-read a live Zustand store inside an async send/dispatch closure that captured a snapshot — popover-close effects can clear the store mid-flight (#7880 silent-fallback class).
- Citing #8689/#8725's resolved-payload confirm as precedent — that design shipped and was then deliberately reversed by #9722/#9726.
