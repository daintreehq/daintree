## Context

Daintree ships auto-updates via electron-updater reading `latest-mac.yml` / `latest-linux.yml` / `latest.yml` (Windows) from `https://updates.daintree.org/releases/`. `AutoUpdaterService.ts` sets `autoUpdater.allowDowngrade = channel === "nightly"` (`electron/services/AutoUpdaterService.ts:395`) — so the **stable** channel runs with `allowDowngrade = false`. Releases publish through the `publish-daintree` composite action (`.github/actions/publish-daintree/action.yml`) shared by `release-{macos,linux,windows}.yml`, which uploads the freshly built YAML feeds to R2.

## Problem

If a publish overwrites the live stable feed with a version that is equal-or-lower than what's already advertised, every installed client sees the remote as not-newer-than-installed and, because `allowDowngrade = false`, stops offering updates entirely. The breakage is silent (no error surfaced client-side) and irreversible from the client: those installs stay stuck until a version strictly greater than every previously shipped one lands. Triggers are mundane — a back-merge resurfacing an old `package.json` version, a tag rewind, a republish of the same tag, or a split-brain matrix build where platforms disagree on the version.

## Root cause

electron-updater's `allowDowngrade = false` is correct safety behavior for a single monotonic channel, but it makes the published feed's version an **invariant that can only ever go up**. Nothing in the build chain enforced that invariant — the release pipeline would happily upload whatever version the artifacts carried, and a regression doesn't fail loudly anywhere; clients just go quiet. The only safe place to catch it is _before_ the bytes hit the CDN, because once the feed is regressed there is no client-side recovery.

## Lesson

- Treat the live stable update feed as a monotonic ledger: every publish must be **strictly greater** than what's currently advertised. Equal is also a regression (republishing the same version is the same footgun) — `checkVersionMonotonic` rejects `!semver.gt(new, live)`.
- Gate this at publish time, between artifact download and R2 upload (`scripts/ci/check-version-monotonic.mjs` in the `publish-daintree` composite action), not at build time — the build doesn't know what's live.
- **Fail closed.** A 404 on the live feed is the only "pass" exception (first release in a channel). Every other outcome — network error, CDN stall, YAML parse failure, missing/non-string `version` field, platforms disagreeing — must fail the publish. A CDN outage must never be allowed to wave a regression through.
- Validate the channel prefix (`UPDATE_METADATA_PREFIX` / `RELEASE_PLATFORMS`) against an allowlist (`latest`/`rc`/`beta`) before fetching. A typo like `latset` would 404 every feed, which the gate would otherwise read as "first release in channel" and silently pass — re-introducing exactly the hole it guards.
- Arm the `AbortController` across the body read, not just the headers fetch — a 200-then-stall response otherwise hangs to the job timeout instead of failing closed at the 15s budget.

## Applies when

- Touching `AutoUpdaterService.ts`, `allowDowngrade`, channel/feed-URL logic, or `setFeedURL`.
- Editing the release pipeline: `.github/workflows/release-{macos,linux,windows}.yml`, the `publish-daintree` composite action, R2 upload of `latest-*.yml`, or `scripts/ci/check-version-monotonic.mjs` / `generate-update-metadata.mjs` / `validate-update-metadata.mjs`.
- Adding a new release channel or platform (Windows `latest.yml`, a new arch) — the new feed needs the same monotonic gate and an allowlist entry.
- Reasoning about gitflow back-merges, tag rewinds, or version bumps that could resurface an older `package.json` version into a release build.
- Any decision about whether a CI guard for a publish/upload step should fail-open vs fail-closed when the remote it compares against is unreachable.
