## Context

Daintree persists main-process config (log level overrides, agent settings, pins, window state) via electron-store. The idiomatic Conf-style way to clear a stored key — `store.set(key, undefined)` — worked silently on electron-store v10 and earlier, and is scattered through handlers and migrations.

## Problem

After bumping to electron-store v11 (`^11.0.2`), any code path that cleared a key via `store.set(key, undefined)` crashed at the call site instead of clearing the value. There is no deprecation warning — the upgrade turns a previously-silent no-op-equivalent into a hard thrown error wherever the old pattern survives.

## Root cause

electron-store v11 introduced a breaking change: `store.set(key, undefined)` now throws instead of silently clearing the key. The documented replacement is `store.delete(key)`. Because the old pattern is idiomatic in Conf-style stores and produces no compile-time or deprecation signal, it's easy to leave dormant call sites in place during the bump that only blow up when their reset path is exercised.

## Lesson

On electron-store v11+ never call `store.set(key, undefined)`. Two safe patterns, both live in the tree: clear with `store.delete(key)`, or — when callers expect a concrete shape — write an explicit default. `handleClearLevelOverrides` (electron/ipc/handlers/logs.ts:204) writes `store.set("logLevelOverrides", {})` rather than `undefined`; migration `013-cleanup-phantom-pins.ts:67` rebuilds and writes back the whole `agentSettings` object in one call instead of deleting a sub-key (mirroring migration 012). The mock store in electron/services/**tests**/StoreMigrations.test.ts:90 enforces this by throwing on `set(key, undefined)`, so regressions are caught in unit tests. When upgrading electron-store, grep for `\.set\([^)]*,\s*undefined\)` before merging, and re-read the v11 changelog — several APIs changed subtly, not just this one.

## Applies when

Writing or reviewing main-process persistence code that clears or resets stored values. Upgrading electron-store across a major version. Investigating crashes in code paths that nullify config entries. Any new handler or migration that needs to "reset" a nested store key.
