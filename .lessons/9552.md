## Context

`PullRequestService` (main process) polls the forge for PRs per worktree and emits `sys:pr:detected`. CI status is not fetched inline: detection emits synchronously without it, then `enrichPRWithCIStatus` fires-and-forgets a batched `getCIStatuses` lookup (all `load()` calls enqueue in the same tick to coalesce into one batch — the inline comment warns never to `await` before `load()`) and re-emits `sys:pr:detected` when the batch resolves. The event flows `PRIntegrationService` → `WorkspaceService.onPRDetected` → worktree-update snapshot + `pr-detected` overlay → renderer `WorktreeStoreContext` → the `PRBadge` CI dot (`getCIStatusVisual` in `src/lib/worktreeCIStatus.ts` returns `null` for a falsy status, so `undefined` = no dot).

## Problem

On every PR status refresh the CI dot in the worktree sidebar blinked out, then reappeared a moment later (#9551) — an amber "running" dot visibly strobing on each poll. The misleading part: the issue diagnosis pointed at the renderer's full-replace handlers in `WorktreeStoreContext.tsx`, but patching preservation into the renderer would have been the wrong layer — the fix landed entirely in the workspace host, and the renderer deliberately stayed full-replace.

## Root cause

`sys:pr:detected` is a two-phase emission: phase-1 synchronous with no CI fields (enrichment hasn't run yet), phase-2 async once the coalesced batch resolves. `WorkspaceService.onPRDetected` full-replaced `prCiStatus` from the event payload, so the phase-1 `undefined` was written straight into the worktree snapshot and overlay, and the dot went dark until phase-2 landed. The deeper flaw: `undefined` was overloaded to mean both "no CI checks" (authoritative, dot should clear) and "not fetched yet" (transient, dot should hold) — consumers had no way to distinguish them.

The fix decomposes this into three explicit payload states. Phase-1 sets `isCiStatusLoading: true` (declared on `sys:pr:detected` in `electron/services/events.ts`, forwarded by `PRIntegrationService`). `WorkspaceService.onPRDetected` preserves the prior `prCiStatus` / `linked.pr.ciStatus` only when the flag is set AND `prevSnapshot.prNumber === data.prNumber` — the same-PR guard stops a stale dot riding across a PR reassignment. Critically, the pre-fix `enrichPRWithCIStatus` had `if (!ciStatus) return;` — once a hold exists, that early-return would convert "checks genuinely vanished" into a permanently stale dot, so phase-2 now re-emits even when the batch answers `null` (the batch contract surfaces a transient miss as a rejection → `.catch`, so a resolved `null` is a confirmed "no checks") and the flag-absent emit full-replaces the held value away. Follow-up `bf5ac9ba9` (2026-06-07, unattended-instance perf) exposed the flag's contract: when `ciEnrichmentEnabled` is false there is no phase-2 coming, so phase-1 emits `isCiStatusLoading: this.ciEnrichmentEnabled || undefined` — absent, not `false` — or downstream would hold "loading" forever; it also added a mid-flight guard discarding a batch that resolves after enrichment was disabled, and the pending-sweep re-emit omits all CI fields entirely (absent = "unknown", never "passing" or "loading").

## Lesson

- **A staged-enrichment emitter must mark its intermediate emit explicitly — never make consumers infer "loading" from a missing field.** A phase-1 `undefined` is byte-identical to an authoritative "no data"; downstream full-replace writers will blank real state on every refresh. Put an `is<X>Loading` flag in the event payload itself.
- **Hold prior values entity-scoped, never blanket.** `preserveCiStatus` requires both the loading flag and `prevSnapshot.prNumber === data.prNumber`; without the identity guard, a hold designed to stop flicker carries PR #41's dot onto PR #42.
- **Once a hold exists, the authoritative phase must re-emit the empty case.** The old `if (!ciStatus) return;` was harmless under full-replace but becomes a permanent-staleness bug under a hold. Every "preserve while loading" needs a paired explicit clear path, and the empty result must be distinguishable from a transient failure (here: resolved `null` = confirmed no-checks, rejection = miss).
- **A loading flag is a promise of a resolution emit — omit it when the phase-2 is not guaranteed.** `bf5ac9ba9` gates the flag on `ciEnrichmentEnabled` (`|| undefined` so it's absent, not `false`) because unattended instances skip enrichment entirely; also guard mid-flight (`if (!this.ciEnrichmentEnabled) return;` inside the `.then`) so a batch resolving after disable doesn't write back.
- **Put the hold at exactly ONE layer and keep everything downstream full-replace.** The hold lives in `WorkspaceService` (workspace host); the renderer `WorktreeStoreContext` stays full-replace by design. Independent holds at two layers would make authoritative clears undeliverable and split the semantics across processes.

## Applies when

- Diagnosing any badge/dot/count that blinks out and returns on a refresh cycle — look for a two-phase emitter upstream (sync detect + async enrich) before patching preservation into the renderer store; the renderer is usually the wrong layer.
- Adding an enriched field to `sys:pr:detected` or any detect-then-enrich event — the phase-1 emit will blank it in every full-replace consumer unless flagged as loading.
- Touching `PullRequestService.enrichPRWithCIStatus`, `WorkspaceService.onPRDetected`, or the `isCiStatusLoading` plumbing through `PRIntegrationService` — the flag, the same-PR guard, and the clear-on-null re-emit are one interlocked contract; removing any leg reintroduces either the blink or permanent staleness.
- Gating or disabling an async enrichment path (unattended role, window blur, rate-limit park) whose phase-1 emit carries a loading flag — the flag must be omitted or downstream spins on "loading" forever.
- Reviewing any "preserve prior value while loading" logic — verify the entity-identity guard, the explicit empty-case clear, and that only one layer owns the hold.
