## Context

`FileLinksAddon` linkifies file paths in terminal output via the xterm `ILinkProvider`: `FILE_PATH_REGEX` finds path tokens on a line, and a resolver peels the optional `:line[:col]` suffix into the absolute path + line/col that a click dispatches to `file.view` / `file.openInEditor`. #10211 (issue #9919) added WSL UNC support and fixed a latent suffix bug. The regex + resolver were later extracted (`54320836a`) out of `FileLinksAddon.ts` into `src/services/terminal/filePathDetection.ts` — now shared by terminal file links AND composer/context-menu "View file" (`resolveSelectedFilePath`, consumed by `HybridInputBar`/`TerminalContextMenu`); a regex regression now hits both surfaces, and the tests moved to `filePathDetection.test.ts`.

## Problem

Two silent partial failures that looked correct on inspection. (1) Every file link dropped its `:line:col` — clicking a compiler/stack-trace path opened the wrong location or nothing, and worse, a path that carried a suffix resolved to a non-existent `…App.tsx:45:12` path (colon included). Bare paths (the common `git status` / `ls` case, no suffix) worked fine, so the bug stayed latent across POSIX, Windows, and UNC. (2) On the primary Windows+WSL setup, `\\wsl$\<distro>\…` / `\\wsl.localhost\…` paths in terminal output either weren't linkified at all or produced a clickable-but-broken relative fragment (`Ubuntu\home\user\file.tsx:42`) that failed IPC containment on click with no user feedback.

## Root cause

Two independent regex mechanisms.

1. **Greedy swallow.** The old resolver was `/^(.*)(?::(\d+)(?::(\d+))?)?$/`. `.*` is greedy AND the suffix group is optional, so `.*` consumes the ENTIRE string including `:45:12`, the optional group then matches zero-width, and `$` matches — the overall regex succeeds with `.*` maximal, so the engine never backtracks to hand the suffix to the group. A greedy quantifier gives back characters only when the rest of the pattern would otherwise FAIL; an optional group can always succeed empty, so nothing forces backtracking. Result: `pathPart` retained `:45:12`, and `line`/`col` were always `undefined` (verified empirically). The fix anchors the greedy prefix to a terminator — `/^(.*\.[^\s:]+?)(?::(\d+)(?::(\d+))?)?$/` — where `\.[^\s:]+?` (an extension that cannot contain a colon) forces the path/suffix boundary back onto the `:`.

2. **Missing + mis-ordered alternation.** `FILE_PATH_REGEX` had no WSL alternative, and its bare-relative fallback `[\w-]+[\\/][\w./\\-]+` excludes `\` and `$`, so a `\\wsl$` prefix couldn't anchor any branch — the scanner skipped forward and started matching mid-path, yielding the broken relative fragment. The fix prepends `\\\\wsl(?:\$|\.localhost)\\[^\\]+(?:\\[\w.-]+)+` as the FIRST alternative, ordered ahead of the bare-relative fallback so the general branch can't capture the distro segment shorn of its leading `\\`.

## Lesson

- **A greedy `.*`/`.+` immediately before an OPTIONAL trailing group swallows exactly what the group was meant to capture — and never gives it back.** The engine backtracks a greedy quantifier only when the remainder would otherwise fail to match; an optional group always matches zero-width, so the whole match succeeds with the prefix maximal and the suffix empty. Do not assume greedy will "release" characters so an optional group can match.
- **Anchor a greedy capture to a concrete terminator, not to an optional lookahead.** The fix keys the path/suffix boundary on the extension (`\.[^\s:]+?`, colon-free) so `:line:col` can't be absorbed. Any tokenizer peeling an optional suffix off a greedy prefix needs the prefix bounded by a character class the suffix cannot contain.
- **Order regex alternations most-specific-prefix first.** `\\wsl$\…` must precede the bare-relative `[\w-]+[\\/]…` branch; otherwise — and because that fallback's char class excludes `\`/`$` — an unmatched specific prefix makes the scanner skip ahead and linkify a broken mid-path fragment, a clickable link that silently fails containment on click.
- **Silent partial regex failures hide behind the common case.** No-suffix paths masked the swallow bug; non-WSL machines masked the UNC gap. Exercise the token variants that DON'T dominate output — with-suffix, UNC, dotted distro (`Ubuntu-22.04`), hidden dir (`.config`) — and assert the parsed `line`/`col`/`absolutePath`, not merely that a link was produced.
- **This regex is no longer addon-local.** Since `54320836a` it lives in `filePathDetection.ts` and feeds both terminal file links AND composer/context-menu selected-path viewing; a change here touches both surfaces — run `filePathDetection.test.ts`.

## Applies when

- Editing `FILE_PATH_REGEX`, `resolveFilePathCandidate`, or `resolveSelectedFilePath` in `src/services/terminal/filePathDetection.ts`, or any terminal/composer file-link detection.
- Writing any regex that peels an optional suffix (`:line:col`, `?query`, `#frag`, `@version`) off a greedy prefix — verify the greedy part is anchored to a terminator the suffix can't contain, or the suffix gets swallowed.
- Ordering alternations where a specific prefix (`\\wsl$`, `\\?\`, a URL scheme, a drive letter) could be captured by a broader fallback branch.
- Diagnosing "the link opens the file but ignores the line number", "clicking a stack-trace path opens nothing", or WSL/UNC paths not linkifying (or linkifying a truncated fragment).
- Reviewing a link/path change that only adds positive tests — demand negative, with-suffix, and platform-variant cases asserting parsed fields, not tautological constants.
