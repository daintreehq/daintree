## Context

The GitHub Issues/PRs toolbar pills (`ForgeStatsToolbarButton`) stopped background-polling their dropdown lists to save GraphQL quota, which made opening a dropdown feel slow. A hover-to-prefetch was added to hide that delay: `onPointerEnter` scheduled `prefetchResourceList(type)` behind a `HOVER_PREFETCH_DELAY_MS = 150` trailing-edge `setTimeout` (`issuesHoverTimerRef`/`prsHoverTimerRef`), with an `onPointerLeave` handler and an unmount effect that `clearTimeout`'d the pending fire. The prefetch forced `bypassCache: true` and stamped `freshBypassAt` so a subsequent open would skip SWR revalidation.

## Problem

The prefetch rarely warmed anything: opening a dropdown still mounted cold, so the feature did nothing on the common path. Worse, every sustained hover spent a full GraphQL query even though a warm 60s main-process list cache could have served it for free — a UX feature quietly acting as a quota drain. The misleading part: the debounce/cancel machinery looked correct and defensive, so the failure read as "prefetch is racy" rather than "prefetch is structurally cancelled by its own success path."

## Root cause

Two independent design errors, each self-defeating against the exact interaction timeline the prefetch claimed to serve.

1. The debounce cancelled the very flow it targeted. The dominant interaction is hover-then-immediately-click, and with a 150ms trailing-edge timer that click lands _inside_ the debounce window before the timer fires. The click flips the dropdown open, and the open-state re-check (`isOpenRef.current` → return) plus the `onPointerLeave`/unmount `clearTimeout` cancel the pending prefetch outright. So the fast path — the one worth accelerating — got zero warm-up; only a slow deliberate hover (which doesn't need help) ever completed. A debounce longer than the human hover→click gap accelerates nothing.

2. `bypassCache: true` on every hover converted warm hits into spend. The main process holds a 60s list cache; forcing bypass made each hover a guaranteed GraphQL query. A prefetch is only quota-safe if it is cache-first: a warm slot costs zero queries, a cold slot spends exactly the one query the click would have made anyway — strictly ≤ the no-prefetch baseline.

The fix fires `prefetchResourceList` synchronously on `pointerenter` (mouse only) with no timer, sets `bypassCache: false`, and deletes the timer refs, `onPointerLeave` handler, and unmount cleanup. Fly-by cost is now bounded by the in-flight guard (`issuesPrefetchInFlightRef`/`prsPrefetchInFlightRef`), the `PREFETCH_FRESHNESS_MS = 10_000` skip, and cache-first cheapness — not a debounce. A companion change caps the lazy list-chunk preload in `GitHubStatsDropdown.tsx` at `requestIdleCallback(preload, { timeout: 2000 })` so a first click under launch load can't land on a cold Suspense skeleton.

## Lesson

- **Debounce is the wrong tool when the event you want to accelerate is itself the cancel trigger.** A trailing-edge timer on hover treats hovers as noise to filter, but a hover about to be clicked is signal, and a click-time cancel guarantees the prefetch never lands for the fast path. Fire prefetch instantly on `pointerenter` and bound cost with in-flight + freshness guards, not a delay. Reserve debounce for events with no downstream cancel racing the fire.
- **A cache-bypassing prefetch is a quota leak, not a latency win.** Prefetch must be cache-first (`bypassCache: false`): a warm slot costs zero, a cold slot costs the same query the click would issue. Forcing bypass "to be fresh" inverts it into strictly-more network than doing nothing. Bypass is reserved for explicit user intent (dropdown open, manual refresh).
- **Don't arm a skip-revalidate marker on speculative reads.** The cache-first prefetch omits `freshBypassAt` (consumed by `useGitHubResourceListSWR.ts` `FRESH_REVALIDATE_SKIP_MS` to skip one revalidation) because it may have been served from cache — a possibly-stale page must still run its cheap open-time revalidate. Keep `countAtWrite` (the count cache-buster); drop the freshness marker. Only a real `bypassCache: true` fetch earns `freshBypassAt`.
- **Cap `requestIdleCallback` with a timeout when the deferred work gates a first interaction.** An untimed `requestIdleCallback` can be starved for seconds during launch hydration / Electron IPC bursts; a lazy chunk preload behind it will still miss the first click. Pass `{ timeout: 2000 }` (or `setTimeout` fallback) so idle-preload has a hard ceiling.
- **One exception (#11087):** a `stale`-flagged entry (optimistic assignee patch, count-poll divergence) prefetches with `bypassCache: true` for _correctness_, not freshness — a cache-first read joins an in-flight singleflight query that may predate the local write and clobber the optimistic patch. Cache-first stays the default; only a proven-diverged entry bypasses (and it's not extra spend — the write already invalidated the backend page).

## Applies when

- Adding or tuning any hover/focus prefetch (`onPointerEnter`, dropdown/menu warm-up) — verify any debounce is shorter than the hover→click gap and isn't cancelled by the click's own open/leave handlers; touching `ForgeStatsToolbarButton.tsx` `prefetchResourceList` / `handlePrefetchPointerEnter` / `PREFETCH_FRESHNESS_MS`.
- Deciding `bypassCache` on a speculative or background fetch against a forge/GraphQL cache — cache-first unless there's a correctness reason (a `stale`-flagged entry), never "to be fresh."
- Writing to `forgeResourceCache` — whether to stamp `freshBypassAt` (SWR skip-revalidate, real bypass only) vs `countAtWrite` (count cache-buster, always).
- Preloading a lazy React chunk a first click depends on via `requestIdleCallback` — pass a `timeout` so launch-time main-thread pressure can't strand it behind a Suspense skeleton.
