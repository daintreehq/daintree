## Context

`WindowRegistry` (`electron/window/WindowRegistry.ts`) tracks all open windows in a `Map<number, WindowContext>` and exposes `getPrimary()`. `getPrimary()` is the canonical "which window is the user looking at" resolver consumed all over the main process: notification-click routing (`NotificationService.ts:182`), plugin renderer dispatch fallback (`PluginRendererDispatcher`), shutdown/lifecycle dialogs (`shutdown.ts`, `appLifecycle.ts`), theme/recovery/diagnostics IPC handlers (`?? deps.mainWindow`).

## Problem

With multiple windows open, anything routed to the "primary" window (notification clicks, recovery prompts, theme application) landed on the **first-opened** window, not the one the user was actively focused on. The bug is invisible in single-window sessions and only manifests the moment a second window opens.

## Root cause

`primaryWindowId` was only ever set on first registration (`if (this.primaryWindowId === null)`), and `unregister()` reassigned it by iterating the `Map` in insertion order. Map insertion order is a stable-looking but wrong proxy for "primary" — it tracks _when a window was opened_, never _which window has focus_. Nothing subscribed to focus changes, so primary froze on the oldest live window.

The fix wires `app.on("browser-window-focus")` via `wireFocusTracking(app)` (called once in `main.ts` after registry construction) and maintains a `focusHistory: number[]` (oldest→newest, with `recordFocus` moving a re-focused id to the tail). Three non-obvious edges had to be handled:

- **Sync show/focus race:** a window can be focused _before_ the async `browser-window-focus` event fires. `register()` calls `win.isFocused()` and promotes immediately if true, otherwise `getPrimary()` returns the wrong window for the gap between register and the first focus event.
- **Unregister fallback:** when the primary closes, walk `focusHistory` newest→oldest for the first live window so the user lands on the window they were _last_ looking at; only fall back to Map insertion order when focus history is exhausted (no focus events ever fired).
- **Stale focus events:** a `browser-window-focus` can arrive for a window whose `BrowserWindow.isDestroyed()` is already true but whose registry entry hasn't been cleaned up — guard with `isDestroyed()` so a dead window isn't revived as primary. Also guard `windows.has(win.id)` to ignore detached DevTools / Electron-internal windows.

## Lesson

In a multi-window Electron app, "primary window" is a _focus_ concept, never a _registration/insertion-order_ concept. If a registry exposes `getPrimary()`:

- Subscribe to `app.on("browser-window-focus")` and update primary on every focus change. Make the wiring idempotent (`focusTrackingWired` guard) so repeated setup attaches one listener.
- Maintain an explicit focus-history list and, when the primary unregisters, prefer the most-recently-focused **live** window; fall back to Map order only when history is empty.
- Promote at registration time if `win.isFocused()` is already true — the sync show/focus can beat the async focus event.
- Guard the focus listener against destroyed-but-not-yet-unregistered windows (`isDestroyed()`) and against windows not in your registry (`windows.has(id)` / `windows.get(id)`).
- Keep the registry decoupled from the real `electron` module for testability: accept a narrow structural `FocusTrackingApp` interface, not the full `app`.

## Applies when

- Adding or reviewing any main-process code that resolves a target window via `WindowRegistry.getPrimary()` or `?? deps.mainWindow` (notification routing, recovery/theme/diagnostics IPC handlers, plugin/agent/MCP renderer dispatch that carries no source window).
- Implementing "send to the active/focused window" for any feature in a multi-window session.
- Any registry that picks a "default/active/primary" element by Map/array insertion order when the real intent is "most recently used/focused" — the insertion-order proxy silently breaks the moment a second element exists.
- Debugging "notification click opens the wrong window" or "dialog appears on the background window" in multi-window sessions.
- Touching `electron/window/WindowRegistry.ts` or its focus/unregister logic.
