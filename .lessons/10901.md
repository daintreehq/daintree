## Context

The plugin manifest's `contributes.*` schemas (`electron/schemas/plugin.ts`, built by `getPluginManifestSchema`) are strict zod objects, and contributions register through the `PluginService` load path. Issue #10888 flagged this ahead of the plugin API freeze: zod validating a field proves the shape is well-formed, it proves nothing about whether any runtime code ever reads that field. Once the manifest schema is frozen at 1.0, an accepted-but-unread field becomes a permanent public-contract lie that can never be cleanly removed.

## Problem

`ViewContributionSchema` accepted `name` and `description` on every `contributes.views` entry, and both validated cleanly. Neither was read anywhere — the matching `contributes.panels` entry is the single source of truth for a panel's display name and icon, so a plugin author who set a view's `name`/`description` got silent no-op behavior with no warning at manifest-validate time or runtime.

## Root cause

`electron/schemas/__tests__/manifestContributionConsumers.test.ts` closes the gap with a two-layer contract, not a single check. Layer one is compile-time: `MANIFEST_CONTRIBUTION_FIELD_CONSUMERS` is asserted `satisfies FieldConsumerCoverage`, a type built from `Record<keyof z.infer<typeof Schema>, ConsumerDescriptor>` per contribution kind — a schema field with no matching map key breaks the build, and a stale map key for a removed field also breaks it (`satisfies` checks both directions). Layer two is runtime: `shapeKeys()` unwraps each swept schema (`z.ZodObject`, or optional-wrapped via `.unwrap()`) to its actual `.shape` keys, and `it.each` asserts the map's field set equals the schema's real field set — the backstop against `z.infer` edge cases the type check can't see. A third `it.each` asserts `existsSync(consumer.file)` for every named consumer, so a map entry can't point at a file that doesn't exist. Running the sweep once against the pre-existing schema surfaced `views.name` and `views.description` as having zero real consumers, and PR #10901 deleted them end-to-end: the zod schema, the SDK scaffold templates (`packages/daintree-plugin/src/scaffold/templates.ts`), the sample fixture (`plugins/sample/rich-daintree/plugin.json`), and every test constructing a view with those fields. `views.iconId` was kept despite having no runtime reader either, because the SDK's `validate` command still reads it advisorily — the map's `mode` field (`verbatim` / `derived-input` / `cross-reference` / `intentional-metadata`) is what lets the test distinguish "no consumer, dead" from "consumed by first-party tooling, fine."

The "no unknown contribution kind" guard (`Object.keys(parsed.data.contributes).sort()` against `TOP_LEVEL_GROUPS`) only works because every top-level array kind is declared `.default([])`, so an empty manifest still materializes every kind's key for the sweep. This has held: the codebase later added a `skills` contribution kind, and it shows up in `SWEPT_SCHEMAS`, `TOP_LEVEL_GROUPS`, and a full `MANIFEST_CONTRIBUTION_FIELD_CONSUMERS.skills` entry — the contract is actively maintained, not a one-time sweep left to rot. A future kind declared `.optional()` without a default would silently skip this guard.

## Lesson

- **Adding any field to a `contributes.*` schema (or a swept nested schema — `AgentDetectionConfigSchema`, `CredentialFieldSchema`, `ForgeProviderContributionSchema.shape.slots`, `SettingDefinitionObjectSchema`) requires a matching entry in `MANIFEST_CONTRIBUTION_FIELD_CONSUMERS`** naming a real file/symbol, or both the `satisfies` compile check and the runtime `.shape` sweep in `manifestContributionConsumers.test.ts` fail — this is deliberate, not a flake to work around.
- **A field that only reaches zod validation, never runtime, is exactly the class of bug this test exists to catch** — before wiring a new manifest field, trace it to an actual read site (registry, `PluginService.loadPlugin`, a supervisor) the same way `commands.danger`'s `derived-input` mode documents that it only feeds the host-authoritative `effectiveDanger` (#8331), never trusted verbatim.
- **New top-level contribution kinds must stay `.default([])`, not `.optional()`**, or the empty-manifest sweep that detects "unknown kind added without a swept schema" silently stops seeing it — verified this convention still held when a later `skills` kind was added.
- **The contract proves a consumer is declared and locatable, not that it still executes** — the test file's own header calls this a curated map + `existsSync` check, not static usage analysis; a reviewer still confirms the cited symbol actually reads the field.
- **When the sweep surfaces an orphan field, cut it everywhere in one PR** — schema, SDK scaffold templates, sample plugin fixtures, and every test fixture constructing that field — or downstream tests break on strict-schema rejection instead of validating cleanly.

## Applies when

- Adding or modifying a field on any plugin manifest contribution schema in `electron/schemas/plugin.ts`.
- Adding a new `contributes.*` contribution kind, top-level or nested (e.g. `agents.detection`, `forgeProviders.credentialFields`, `forgeProviders.slots`).
- `manifestContributionConsumers.test.ts` fails after a schema change — the fix is a map entry with a real consumer, never a test skip or a loosened assertion.
- Investigating a plugin-manifest field an author set that appears to do nothing at runtime.
- Reviewing plugin-manifest schema changes ahead of the 1.0 plugin API freeze, where an unconsumed field becomes permanent public-contract debt.
