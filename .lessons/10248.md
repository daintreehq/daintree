## Context

The plugin authoring toolchain ships two CLI packages to npm from `packages/*`: `daintree-plugin` (the CLI, which also re-exports a library surface — `runNew`, `scaffoldPlugin`, `runValidate`, `runPackage`, `TEMPLATE_KINDS` from `src/index.ts`) and `create-daintree-plugin` (a thin `npm create daintree-plugin` shim whose `src/create.ts` does `import { runNew } from "daintree-plugin"`). Both build with tsup and publish only `dist/` via `files: ["dist"]`. The docs tell authors to `npx create-daintree-plugin`, so both are real published artifacts. #10248 (issue #9884) repaired their npm-publish metadata.

## Problem

The metadata was wrong for the published tarball but correct-looking inside the monorepo, so nothing failed in local CI (typecheck/lint/build all green). Two latent breakages that only manifest for an external consumer after `npm install`: (1) a TypeScript consumer importing `daintree-plugin` resolves to a missing types file and gets zero declarations; (2) `npm create daintree-plugin` pulls whatever the newest published `daintree-plugin` major is at install time, not the version the shim was built against.

## Root cause

Two workspace-symlink illusions. `daintree-plugin`'s `types` and `exports["."].types` pointed at `./src/index.ts` while `files: ["dist"]` excludes `src/`, and tsup ran with `dts: false` so no `.d.ts` was emitted. Inside the monorepo the workspace symlink exposes `src/`, so `create-daintree-plugin` resolves the types fine — the in-source comment even justified `dts: false` on exactly that basis. In the published tarball `src/index.ts` does not exist: the package advertises a library entry with no declarations behind it. Fix: emit a bundled declaration into `dist/` (`dts: { resolve: true }`, `resolve: true` follows the `src/index.ts` re-export chain and inlines internal types into one `dist/index.d.ts`) and repoint both type fields at `./dist/index.d.ts` — the SDK packages (`@daintreehq/plugin-sdk` etc.) already did this correctly; only the CLI pair was broken.

The second: `create-daintree-plugin` declared `"daintree-plugin": "*"`. A bare `*` is NOT the `workspace:` protocol — npm only rewrites `workspace:`-prefixed ranges to a concrete version at publish; a literal `*` ships verbatim and resolves to the newest published major at install time. Because the shim externalizes `daintree-plugin` (`external: ["daintree-plugin", "electron"]`) and imports `runNew` at runtime, a future breaking `daintree-plugin` major with a drifted `runNew` signature would silently break `npm create daintree-plugin`. Fix: bound it to `^0.1.0` (on a 0.x version caret locks the minor — `>=0.1.0 <0.2.0` — the intended tight coupling pre-1.0). A `prepare: "tsup"` script was added to both so `npm publish`/pack rebuilds `dist/` first.

## Lesson

- **The `types`/`exports.types` pointer must resolve to a path inside the `files` allowlist — verify it, don't trust local resolution.** With `files: ["dist"]` any pointer into `src/` yields a declaration-less published package; the workspace symlink resolves it locally so typecheck stays green. The reusable check for any `packages/*` addition: does the type entry live under a shipped directory, and is a `.d.ts` actually emitted there?
- **A bare `"*"` (or any plain semver) on a sibling workspace dependency is not the `workspace:` protocol and is never rewritten at publish.** Only `workspace:`-prefixed ranges get pinned to a concrete version by npm at publish; everything else ships literally. If a shim resolves a sibling at runtime (externalized + imported), bound it — `^0.1.0`, not `*` — or a future breaking major of the sibling silently poisons the installed consumer.
- **Enabling tsup `dts` on these packages needs `compilerOptions: { ignoreDeprecations: "6.0" }` scoped to the dts pipeline.** tsup's dts bundler (rollup-plugin-dts) injects a deprecated `baseUrl` that trips TS5101 under TypeScript 6; the override lives only in `tsup.config.ts`'s `dts` block so the package `tsconfig.json` used by `typecheck` stays clean. Removable once TS 7 lands and tsup catches up.
- **`src/index.ts` is the published public-surface gate — anything re-exported there ships to consumers** because `dts: { resolve: true }` inlines the whole re-export chain. Treat additions to that barrel as intentional API, not internal wiring.
- **Local CI cannot catch published-shape bugs; there is no publint/arethetypeswrong guard here.** typecheck/lint/build all pass on the symlinked workspace. Reason about the tarball (`npm pack --dry-run`, or mentally strip everything outside `files`) when touching metadata for a shipped `packages/*` package.

## Applies when

- Adding, publishing, or editing `package.json` metadata (`types`, `exports`, `main`, `files`, `bin`) for any package in `packages/*` — confirm the type/entry pointers land inside the `files` allowlist and that the build emits them.
- Declaring a dependency between two workspace packages that both publish to npm — never leave it `"*"`; use `workspace:` (rewritten at publish) or a bounded caret matching the sibling's real coupling.
- Turning on `dts` emit in a tsup config here and hitting a TS5101 / deprecated-`baseUrl` build failure — scope `ignoreDeprecations: "6.0"` to the `dts.compilerOptions`, not the package tsconfig.
- Diagnosing "the published npm package has no TypeScript types" or "`npm create daintree-plugin` pulled an unexpected version" where everything works inside the monorepo.
- Reviewing changes to `daintree-plugin` / `create-daintree-plugin` / SDK packaging, or the `src/index.ts` barrel that defines their published surface.
