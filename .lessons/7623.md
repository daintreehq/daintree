## Context

`PtyPool` (`electron/services/PtyPool.ts`) pre-warms shells so the next launch is an instant spawn. The pool was built to make agent terminal launches feel instant — agents are the high-frequency, latency-sensitive case. Acquisition flows through `acquirePtyProcess` in `electron/services/pty/terminalSpawn.ts`.

## Problem

The pool was dead weight for the exact case it existed for. The old gate read `canUsePool = ... && !options.env && ...` — it refused to serve any spawn carrying `options.env`. Every agent launch carries an `options.env` (preset metadata, base URLs, etc.), so agents always missed and fell through to a cold `pty.spawn`. The optimization built for agents rejected agents 100% of the time.

## Root cause

A single pre-warmed shell can't carry per-caller env, so the naive fix (just stop checking `options.env`) is wrong two ways: (1) baking a caller's secrets into an idle pooled shell leaks them to whoever acquires it next, and (2) keying the pool on the full raw env fragments the pool into one slot per distinct secret, so it never warms.

The fix keys entries on `(cwd, envHash)` where `envHash = computePoolEnvHash(options.env)` — and critically the hash runs over the **post-filter view** of the env (`filterSensitiveOnly`), the same view `PtyPool.buildSpawnEnv` actually writes into the spawned shell. Consequences that fall out of "hash what the child actually gets":

- Secrets (API keys, tokens, passwords) are stripped before hashing, so callers differing only in stripped secrets share a slot — correct, because those secrets never reach the pre-warmed shell anyway. No secret persists in an idle pool process.
- Volatile shell-state keys (`SHLVL`, `PWD`, `OLDPWD`, `_`) are excluded so they don't fragment the pool.
- Auto-injected metadata that `injectDaintreeMetadata` always overwrites on the fresh-spawn path (`DAINTREE_PANE_ID`, `DAINTREE_CWD`, `DAINTREE_PROJECT_ID`, `DAINTREE_WORKTREE_ID`) is excluded — but _caller-supplied_ `DAINTREE_*` vars that reach the child intact are kept in the hash, or a slot warmed for caller A would be served to caller B with different metadata.

Supporting machinery: `warmForKey` (fire-and-forget refill with a `warmsInFlight` stampede guard), a global `maxEntries` LRU cap that evicts from a _different_ key than the incoming one, and an `onExit` that skips refill when the entry was already removed by drain/evict/acquire.

## Lesson

When pooling pre-warmed processes keyed by environment:

- Key on a hash of the **exact env the child will receive**, not the raw request env. If the spawn path filters/transforms env before handing it to the process, the pool key must hash that same transformed view, or the key won't predict what's in the slot.
- That single rule subsumes secret hygiene: hash the filtered view → secrets are absent from both the key and the idle shell. Never let a raw secret influence the pool key (fragments the pool) or get baked into an idle warmed process (leaks across acquires).
- Normalize out keys that don't change the effective execution environment (volatile shell state) and keys the spawn path always overwrites (auto-injected metadata) so semantically-identical launches share a slot. But keep any key that actually reaches the child distinct in the hash.
- Make the hash order-independent (sort entries) so object key order doesn't fragment the pool.
- When relaxing a "don't pool if X is present" guard, confirm whether X is present in the _common_ case — here `options.env` was present on literally every agent launch, so the guard disabled the feature for its primary user.

## Applies when

- Touching `PtyPool`, `computePoolEnvHash`, `buildSpawnEnv`, or the `canUsePool`/`acquireByKey`/`warmForKey` path in `terminalSpawn.ts`.
- Adding a new field to `options.env` or agent preset env, or changing `filterSensitiveOnly`/`filterEnvironment` — any such change shifts which launches share a pool slot and must keep hash and `buildSpawnEnv` filtering in lockstep.
- Adding any new pre-warm/object-pool keyed by config or environment elsewhere in the codebase.
- Debugging "the PTY pool never hits / always cold-spawns for agents," "a terminal came up with another launch's env," or a suspected secret leaking into a pooled/reused shell.
- Reviewing changes that loosen a pooling eligibility predicate (`!options.env`, `!options.args`, cwd match) — check the predicate isn't excluding the feature's main use case.
