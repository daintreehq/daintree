## Context

The renderer is served over the privileged `app://` scheme with `codeCache: true` (`electron/main.ts:111`), and the renderer's V8 context has bytecode caching on (#3621). That cache is keyed per script file by content. All project `WebContentsView`s share one `persist:daintree` session (#4686), so the bytecode cache is shared across sessions and project switches. The build splits `node_modules` into named vendor chunks via Rolldown `codeSplitting.groups` in `vite.config.ts` (`build.rollupOptions.output.codeSplitting`).

## Problem

A single catch-all `vendor` chunk concatenated React, Radix, and dozens of other third-party packages into one file. Any version bump to any dependency in that bucket changed the chunk's contents and hash, invalidating the V8 bytecode cache for the _entire_ vendor bundle — even though React and Radix themselves almost never change between releases. Every app update paid full re-parse/recompile cost on the next cold start for code that was byte-identical to the previous build.

## Root cause

The V8 code cache is per-script-file: cache validity is tied to the exact bytes of each emitted chunk, not to individual modules within it. Bundling a low-churn dependency (React, Radix primitives) together with high-churn ones in one chunk couples their cache lifetimes — the stable code's cache dies whenever any volatile neighbor changes. Chunk _topology_, not just whether caching is enabled, decides how much bytecode survives a release. This is invisible at build time (total gzip is unchanged — same bytes, redistributed) and is not a cold-start speedup on a fresh install; it is cross-session cache-stability hygiene that only pays off across upgrades.

## Lesson

Group vendor chunks by churn profile, not just by size or alphabet. Isolate low-churn, load-bearing deps into their own named groups so their bytecode caches stay warm across dependency upgrades:

- `vendor-react` (react/react-dom/scheduler/use-sync-external-store) and `vendor-radix` (@radix-ui/\*) are their own `codeSplitting.groups` with explicit Rolldown `priority` ordering (higher priority wins; the catch-all `vendor` group sits at `priority: 10` and matches everything else).
- The catch-all `vendor` is the volatile bucket — accept that it churns; the point is to keep the stable buckets _out_ of it.
- Don't reverse this for a cold-start metric: total bytes are unchanged, so a one-shot startup benchmark won't show the win. The payoff is cache survival across the next N releases.
- Stable chunks reinforce a second mechanism: the `vendor-react` chunk's hashed filename is wired into a host import-map (`hostImportMapPlugin` in `vite.config.ts`) so externalized plugin bundles resolve to one React instance, and the document URL is kept static for bytecode-cache reuse (#9162). Keeping React in its own stable chunk is load-bearing for both.

## Applies when

- Editing `build.rollupOptions.output.codeSplitting.groups` / `manualChunks` in `vite.config.ts` — adding, merging, or reordering vendor groups.
- Tempted to merge small vendor chunks back into one bucket "to reduce file count" — that re-couples cache lifetimes.
- Investigating slow cold starts _after an app update_ (vs. fresh install), or evaluating V8 bytecode / `codeCache` effectiveness across sessions.
- Adding a new heavy, low-churn dependency (a UI primitive lib, a framework runtime) — give it its own group rather than letting it fall into the catch-all `vendor`.
- Touching `codeCache: true` on the `app://`/`plugin://` schemes or the `vendor-react` host-import-map, which depend on chunk-naming stability.
