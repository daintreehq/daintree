## Context

IPC handler and listener accumulation was a suspected source of memory leaks and "ghost" event processing. There was no automated test to catch regressions.

## Problem

Without a way to count active IPC handlers and listeners from tests, listener leaks would only surface as memory issues or mysterious duplicate event handling after many terminal/panel cycles.

## Root cause

No observability into IPC handler counts from the test layer.

## Lesson

Read IPC handler/listener counts directly from the main process via `app.evaluate()` against the Electron `ipcMain` internals — the helpers `getHandlerCount()`, `getListenerCount()`, and `getTotalHandlerCount()` in `e2e/helpers/ipcFaults.ts` (they probe `ipcMain._invokeHandlers` and `ipcMain.listenerCount()`). E2E tests can then assert that counts remain stable after N open/close cycles. The pattern:

1. Record baseline counts after app launch
2. Perform N cycles of the operation under test
3. Assert counts are within a small delta of baseline

This catches both renderer-side listener leaks and main-process handler leaks. Reading the main-process `ipcMain` state directly via `app.evaluate()` is the correct mechanism — don't rely on renderer `window` introspection for main process state. Note: most migrated events (`worktree:update`, `agent:state-changed`, `terminal:exit`, …) now travel over the multiplexed `events:push` channel, so observe listener counts there rather than per-event channels.

## Applies when

- Any new IPC channel added without corresponding cleanup verification
- Debugging IPC handler accumulation or "handler already registered" warnings
- Adding E2E coverage for operations that register/deregister IPC listeners
