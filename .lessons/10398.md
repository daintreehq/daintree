## Context

Daintree ships three macOS artifacts per release (x64, arm64, universal) as `.dmg` + `-mac.zip`, with `scripts/ci/generate-update-metadata.mjs` writing `latest-mac.yml` for electron-updater and the website linking downloads by filename. electron-builder's default macOS arch is x64, and its `getArchSuffix` returns `""` for the default arch (the unpacked dir is bare `release/mac/`, arm64 is `release/mac-arm64/`). PR #10398 fixed the artifact naming; companion #10399 added a runtime Rosetta warning banner (issue #10378).

## Problem

macOS x64 artifacts were published with no arch suffix — `Daintree-X.Y.Z.dmg` / `Daintree-X.Y.Z-mac.zip` — while arm64 carried `-arm64`. So the Intel build looked like _the_ Mac download. Apple Silicon users grabbed it and ran the whole Electron app under Rosetta: multi-second interactions, ~1-minute startup, renderer pinned at ~100% CPU (Rosetta re-translates V8's JIT output at runtime). The auto-updater never rescues them: `MacUpdater` filters Mac artifacts by the `arm64` substring, so an x64 install on Apple Silicon stays x64 forever. Diagnosed only because a diagnostics export showed `runtime.arch: x64` on an M4 (issues #10341, #10378).

## Root cause

electron-builder's `${arch}` macro renders to `""` for the build's default arch, not because of a config value but because `getArchSuffix` strips it unless the suffix is user-forced. The default artifactName template therefore produced an unsuffixed x64 file. The fix is a **user-specified `artifactName` on the `mac` and `dmg` blocks that explicitly includes `${arch}`**, which forces the token to render `x64` and bypasses the default-arch stripping — yielding `Daintree-X.Y.Z-x64.dmg` and `Daintree-X.Y.Z-x64-mac.zip`. Four non-obvious constraints hem this in: (1) the `dmg` pattern drops `${os}` (`${productName}-${version}-${arch}.${ext}`) but the zip pattern must KEEP `-${os}` (`...-${arch}-${os}.${ext}`) because `macZipPriority()` matches `*-mac.zip`; (2) a root-level `zip` block is rejected by electron-builder's schema (`additionalProperties: false`), so the zip's name has to ride on the `mac` block, not its own; (3) do NOT set `mac.defaultArch` to force the suffix — that changes `computeAppOutDir`, renames `release/mac/` → `release/mac-x64/`, and breaks the hardcoded app-bundle paths in `release-macos.yml`; the suffix belongs on `artifactName` only; (4) `macZipPriority()` had to re-rank: `-x64-mac.zip` = 0, legacy bare `-mac.zip` = 1, `-arm64-mac.zip` = 2, `universal-mac.zip` = 3, so a stale bare artifact in a dirty release dir can't outrank the current x64 build, while old published bare builds still resolve.

The #10399 companion trap: `app.runningUnderARM64Translation` is **also `true` for x64 under WOW64 on Windows ARM**, where a "Download Apple Silicon build" CTA is nonsense. `isRunningUnderRosetta()` therefore gates on `process.platform === "darwin" && app.runningUnderARM64Translation === true`.

## Lesson

- **electron-builder emits the default arch (x64 on macOS) with NO arch suffix.** Per-arch naming needs an explicit `artifactName` with `${arch}` on the `mac`/`dmg` blocks; the token renders empty otherwise and one arch masquerades as the generic download. Verify shipped filenames, not config intent — the stripping is silent.
- **Don't force the suffix via `mac.defaultArch`.** That renames the _unpacked_ output dir (`release/mac/` → `release/mac-x64/`) and breaks the hardcoded `release/mac/Daintree.app` paths in `.github/workflows/release-macos.yml`. Unpacked dir naming (getArchSuffix) and compressed artifact naming (artifactName) are controlled separately — change only the latter.
- **The macOS zip artifactName must keep its `-${os}` (`-mac`) suffix**, because `macZipPriority()` in `generate-update-metadata.mjs` selects and ranks by matching `*-mac.zip`; the `dmg` pattern drops `${os}` but the zip must not. A root-level `zip` block is schema-rejected — put the zip name on `mac`.
- **electron-updater routes macOS updates by the `arm64` substring only** (`MacUpdater` keeps files containing `arm64` on Apple Silicon, excludes them on Intel). `-x64-mac.zip` contains neither `arm64` nor `universal`, so renaming is safe on the update side — but that same filter means the updater never migrates an x64 install to arm64.
- **When ranking release artifacts, rank the current explicit name above the legacy bare name**, not equal — a leftover bare `-mac.zip` in a dirty release dir must never outrank the fresh `-x64-mac.zip`. Keep the legacy branch for back-compat with already-published builds.
- **`app.runningUnderARM64Translation` is not macOS-exclusive** — it also reports `true` for x64 under Windows ARM's WOW64. Any "you're under Rosetta, download the Apple Silicon build" logic must be Darwin-gated (`isRunningUnderRosetta()`).

## Applies when

- Editing `electron-builder.config.cjs` artifact naming, adding a new arch/target, or debugging why a shipped macOS file has no `-x64` / arch suffix.
- Touching `scripts/ci/generate-update-metadata.mjs` `macZipPriority()` / artifact selection, or `latest-mac.yml` ranking — any change to how per-arch macOS zips are chosen for auto-update.
- Diagnosing an Electron app that's catastrophically slow on Apple Silicon (~100% renderer CPU, minute-long startup) — check `runtime.arch` in a diagnostics export for `x64` under Rosetta before chasing app-level perf.
- Writing or reviewing any use of `app.runningUnderARM64Translation`, or modifying `release-macos.yml` hardcoded `release/mac*/Daintree.app` paths — confirm the Darwin gate, and that unpacked-dir vs compressed-artifact naming (which diverge) both stay correct.
