## Context

MCP sessions (SSE and Streamable-HTTP) self-expire after `MCP_SSE_IDLE_TIMEOUT_MS` of inactivity. Expiry was a bare `setTimeout(..., MCP_SSE_IDLE_TIMEOUT_MS)` in `SessionStore.createIdleTimer` / `createHttpIdleTimer` (`electron/services/mcp-server/sessionStore.ts`) that revokes grants, closes the transport, and unpins the WebContents.

## Problem

On a laptop suspend/resume, a `setTimeout` does not count down "real elapsed time." Depending on platform and how long the machine slept, the timer either fires immediately on wake (treating the entire sleep as elapsed) or fires only after the full delay measured in awake time — so an MCP session would either get revoked too early (killing an active agent's grant) or linger well past its intended idle window.

## Root cause

`setTimeout` is driven by the event-loop clock, not the wall clock, and Chromium/Node behavior across OS suspend is inconsistent: the timer's remaining delay is frozen during suspend on some platforms and the queued fire is delivered late or coalesced on others. So neither "wall-clock elapsed" (`Date.now() - start`) nor "raw setTimeout" correctly models an idle timeout that should count only _awake_ time. The codebase already has `SystemSleepService` (`electron/services/SystemSleepService.ts`) which listens to `powerMonitor` `suspend`/`resume`, records sleep periods, and exposes `getAwakeTimeSince(startTimestamp)` — elapsed wall time minus any sleep that overlapped the window. That is the correct clock for an idle timer, but a plain `setTimeout` never consults it.

## Lesson

For any timeout that should measure _awake_ time (idle expiry, session TTL, grant revocation, "stale after N minutes"), don't trust a bare `setTimeout` to survive suspend/resume. Use the three-layer pattern from this fix:

- **Anchor to a timestamp, not a duration.** Record `idleStartedAt = Date.now()` when arming; compute remaining as `MCP_SSE_IDLE_TIMEOUT_MS - getSystemSleepService().getAwakeTimeSince(startedAt)`. `getAwakeTimeSince` excludes sleep, so accumulated awake idle time is preserved across multiple suspend/wake cycles (it does not reset each wake).
- **Recompute on wake.** Subscribe to `SystemSleepService.onWake` and call a `recomputeIdleTimers()` that, per session, either expires immediately (`awakeElapsed >= timeout`) or `clearTimeout` + re-arms with the recomputed remaining. Wrap the `getSystemSleepService()` call in try/catch — it may not be initialized at early startup (the `McpServerService` constructor guards the `onWake` subscription the same way).
- **Defense-in-depth in the callback.** The fired callback must independently re-check `getAwakeTimeSince` before acting: if still under threshold (wake-recompute raced, missed this session, or never ran), re-arm for the remaining time and `return` instead of expiring. Only expire when awake-elapsed actually exceeds the timeout (or the timestamp is missing / the service throws — fall through to expiry).

Also: snapshot the map entries (`Array.from(map.entries())`) before iterating in `recomputeIdleTimers`, since expiry mutates the maps mid-loop; clear the timestamp maps in `drain()` and in the per-session expiry path so no stale entries survive; and `unref()` the re-armed timers.

## Applies when

- Adding or reviewing any `setTimeout`/`setInterval` that encodes an idle timeout, TTL, session/grant expiry, "auto-close after N minutes," or watchdog deadline in the Electron main process.
- Working in `electron/services/mcp-server/` (session lifecycle, idle eviction) or anywhere that revokes/cleans up a resource on a timer.
- Touching `SystemSleepService`, `powerMonitor` `suspend`/`resume` handlers, or `getAwakeTimeSince` / `onWake`.
- Bug reports of the shape "session/connection/timer expired right after waking the laptop" or "stayed alive far too long after sleep," or flaky timing that only reproduces across machine suspend.
- Any new long-lived timer where the correct clock is "time the app was actually awake," not raw wall-clock and not raw event-loop delay.
