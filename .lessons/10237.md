## Context

Daintree's terminal scrollback restore layer (`TerminalRestoreController.restoreFromSerialized` / `restoreFromSerializedIncremental`) rehydrates a serialized xterm snapshot into a live `Terminal`. By design (hardened in #8535) these methods **never throw**: they catch write timeouts, xterm parse errors, and poisoned `writeChain` links internally, stash a classified `TerminalScrollbackRestoreError` on `managed.lastScrollbackRestoreError`, and return `false`. Two callers consumed that outcome — startup hydration (`scrollbackRestoreScheduler`) and, at the time, the wake-on-focus path `TerminalWakeManager.wakeAndRestore`.

## Problem

Issue #9896: a terminal woken from hibernation whose snapshot replay failed reported a **successful** wake. The user got a blank or partial pane with no banner, no retry, `needsWake` cleared. Every downstream consumer proceeded as if restore worked: `TerminalRendererPolicy` cleared `needsWake` (nothing retries), `triggerWake` recorded `lastWakeTime` (rate-limiting follow-up wakes), `onPostWake` ran, and held bytes flushed onto the blank buffer via `onResumeFlush`. The misleading part: the wake code _looked_ correct — it awaited the restore and returned — and try/catch would have caught nothing, because the restore swallows its own errors.

## Root cause

`wakeAndRestore` called the restore method and then `return true` unconditionally — it read **neither** failure signal. The restore contract is dual-channel: a `boolean` return _and_ a stashed `managed.lastScrollbackRestoreError`. A caller must read both; the try/catch instinct is a trap because nothing is thrown. The sibling hydration path did it right: `scrollbackRestoreScheduler` reads `managed.lastScrollbackRestoreError` after a `false` return and surfaces an inline retry banner via `usePanelStore.setScrollbackRestoreError`. The wake path set the same classified error (through the shared controller) and read it nowhere. The fix mirrored hydration: read the boolean, on failure surface the stashed error via `setScrollbackRestoreError` and `return false`; on success `clearScrollbackRestoreError` — re-reading via `getInstance(id)` because a mid-wake LRU eviction + respawn under the same id makes the captured `managed` reference stale.

Caveat: the fix site `TerminalWakeManager.ts` was **deleted three weeks later** by hibernation-removal PR #10811 (commit `eb9cd64a7`) — the wake path is gone. The _contract_ survives untouched: `TerminalRestoreController` still returns a boolean and stashes `lastScrollbackRestoreError`, `scrollbackRestoreScheduler` still consumes both, current callers are `TerminalInstanceService` and `paintFabric/PaintFabricCompositor`. The trap stays live for any new caller.

## Lesson

- **In the terminal restore layer, failure travels on two channels — a `false` return AND `managed.lastScrollbackRestoreError` — and neither is an exception.** Any caller of `restoreFromSerialized` / `restoreFromSerializedIncremental` that returns success without reading both reports a failed replay as good. try/catch catches nothing: the methods swallow write-timeout, xterm-parse, and poisoned-`writeChain` errors internally (#8535).
- **A failed restore is worse than a no-op because `terminal.reset()` runs first.** The buffer is wiped before the failing write, so a false success flushes held bytes / runs post-restore hooks on top of a blank buffer. Treat "restore returned" as unverified until you've checked the failure signal.
- **Copy the canonical consumer, don't reinvent the surfacing.** `scrollbackRestoreScheduler` is the reference: on `false`, read the stashed error and route it through `setScrollbackRestoreError` (inline banner + retry); on success call `clearScrollbackRestoreError` to drop a stale banner.
- **The synchronous `restoreFromSerialized` fire-and-forgets its large-state branch** (`void this.restoreFromSerializedIncremental(id, state); return true`), so its boolean cannot reflect an async incremental failure — a large-state caller trusting the sync boolean re-creates #9896. Consume the async result or the stashed error for big snapshots.
- **Fixing "caller ignores a fallible op" means grepping EVERY caller.** #9896's point: the classification machinery and one correct consumer already existed — that proves nothing about the other callers. Existence of the signal ≠ every caller reads it.

## Applies when

- Adding or reviewing any caller of `restoreFromSerialized` / `restoreFromSerializedIncremental` (`TerminalRestoreController`, `TerminalInstanceService`, `paintFabric/PaintFabricCompositor`) — verify it reads both the boolean and `lastScrollbackRestoreError`.
- Diagnosing a blank or partial terminal after hydration or project switch-back with no error banner and no retry — the restore likely failed silently and a caller reported success.
- Wrapping a terminal restore in try/catch expecting to catch write-timeout / parse errors — they are swallowed and stashed, not thrown; you catch nothing.
- Touching scrollback-restore error surfacing (`scrollbackRestoreScheduler`, `usePanelStore.setScrollbackRestoreError` / `clearScrollbackRestoreError`, `TerminalScrollbackRestoreError`).
- Reviewing any Daintree op that reports failure via a stashed classified error + boolean instead of throwing — confirm the failure channel is read by every caller downstream.
