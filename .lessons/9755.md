## Context

`VoiceCorrectionService` post-processes STT transcripts through the OpenAI Responses API (user-configurable model) after every dictation stop — a user-visible wait, so the prize is time-to-first-token (cached prefixes skip prefill), not cost. `buildCorrectionSystemPrompt` in `shared/config/voiceCorrection.ts` was deliberately ordered fixed-first with a `prompt_cache_key` (`buildPromptCacheKey`: prefix + model + project + dictionary) specifically so the OpenAI prompt cache would hit.

## Problem

Issue #9746 diagnosed that the fixed-first design was plausibly delivering nothing: correction calls never hit the cache. The misleading part is total silence — the request looks correct (stable prefix, `prompt_cache_key` set, docs even explained the caching rationale), there is no error, no warning, no response-quality change. The only observable signal is `usage.input_tokens_details.cached_tokens` staying 0, which nothing surfaces unless you go read the `cachedTokens` debug log in `callApi()`.

## Root cause

Two independent cache-eligibility failures stacked. First, the floor: OpenAI only caches when the stable prefix independently exceeds **1,024 tokens** (the first 1,024 must be byte-identical; extension happens in 128-token increments beyond that). `CORE_CORRECTION_PROMPT` measured ~706 tokens — under the floor, so every call was full-price prefill with zero errors. Second, the call shape: the system prompt rode in the top-level `instructions` field with a plain-string `input`, which the arc's diagnosis (#9746) treated as keeping the stable prefix outside the cacheable message array entirely. #9755 fixed both: expanded `CORE_CORRECTION_PROMPT` to ~1,110 tokens with genuinely useful content (35+ domain-grouped phonetic STT mappings, 4 few-shot examples — not filler), and migrated `callApi()` to `input: [{role:"developer", content:systemPrompt}, {role:"user", ...}]` with `instructions` gone.

The third finding is a deliberate **omission**: `prompt_cache_retention: "24h"` would keep the cache warm across dictation sessions (default in-memory retention evaporates after ~5–10 idle minutes), but the correction model is user-configurable and unsupported models 400 on the param. `callApi()` throws on non-OK, and `correct()` swallows every non-abort error into a raw-text fallback with only a `logWarn` — so one unsupported optional param would silently disable correction entirely for affected models, every call, indistinguishable from "correction just isn't very good". Marginal win, silent-degradation risk: omitted, and a regression test asserts `prompt_cache_retention` stays absent.

## Lesson

- **Prompt-cache failure is perfectly silent — verify with usage data, never by inspecting the request.** Below the 1,024-token floor there are no errors and no cache hits; the only truth is `usage.input_tokens_details.cached_tokens` (logged as `cachedTokens` in `callApi()`). One dictation session with two consecutive corrections answers it empirically.
- **Cache eligibility needs BOTH the floor and the shape.** ≥1,024 identical prefix tokens AND the prefix leading the `input` message array (first `developer` message), not the `instructions` field with a string input. Fixing only one buys nothing — e.g. the file-link detection call (`instructions: FILE_LINK_DETECTION_PROMPT`, ~230 tokens) still uses the old shape, and migrating it alone is pointless until that prompt clears the floor.
- **Guard token floors with a char-proxy regression test.** Unit tests can't count tokens; `shared/config/__tests__/voiceCorrection.test.ts` asserts `CORE_CORRECTION_PROMPT.length > 4800` — ~1,090 tokens at a conservative ~4.4 chars/token for dense technical English, leaving headroom over 1,024 if a future edit compacts the prose. Without it, a well-meaning prompt trim silently kills caching again.
- **When you must grow a prompt past a floor, add capability, not padding.** The expansion was domain phonetic mappings and few-shot examples that improve correction quality anyway. Few-shot examples in a JSON-schema-constrained call must explicitly restate the output contract ("always return the JSON object") or examples showing plain corrected text teach the model to break schema.
- **Optional API params on a user-configurable-model call are a silent-degradation trap when the error path falls back.** Unsupported params 400; `correct()` degrades any `callApi` failure to raw text with just a warn log. Before adding a param like `prompt_cache_retention`, trace what a persistent 400 does end-to-end — an optimization that can zero out the feature for some models is a bad trade.
- **Every prompt-content change requires a `PROMPT_CACHE_PREFIX` bump, exactly one per landed change.** #9755 bumped v5→v6; the same-day #9754 (keyterm biasing + prompt softening) checked first and bumped v6→v7 rather than double-bumping. Current prefix is `voice-correction-v7`.

## Applies when

- Adding or modifying any OpenAI Responses API call that sets `prompt_cache_key` — in `VoiceCorrectionService`, the file-link detection path, or any new LLM feature expecting cache hits.
- Editing `CORE_CORRECTION_PROMPT`, `SHARED_TERMS_BLOCK`, or `buildCorrectionSystemPrompt` in `shared/config/voiceCorrection.ts` — keep the 4,800-char floor test green and bump `PROMPT_CACHE_PREFIX`.
- Diagnosing voice-correction latency (the visible wait after recording stops) — check `cachedTokens` in the `[VoiceCorrection]` debug logs before blaming network or model speed.
- Tempted to add an optional OpenAI request param (`prompt_cache_retention`, service tiers, new sampling knobs) to a call whose model users choose and whose errors degrade silently.
- Assuming a "cache-optimized, fixed-first" prompt design is working because the code and docs say so — the design delivered zero hits for its whole life until #9746 measured it.
