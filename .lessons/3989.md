## Context

E2E coverage for panel reordering in the content grid, which is built on @dnd-kit. The original PR shipped a mouse-based `dragElementTo()` helper that called `page.mouse.down()` then nudged the pointer past the `MouseSensor` 8px activation distance, waited, and moved to the target element's bounding-box center with `{ steps }` to feed dnd-kit enough `pointermove` events for collision detection.

## Problem

The simulated-pointer drag was flaky in headless Linux/Xvfb CI. Reordering depends on dnd-kit's collision detection resolving the pointer's screen coordinates against rendered element geometry, and bounding-box centers in Xvfb don't line up with headed-mode layout the way the helper assumed — the drop frequently landed on the wrong target (or no target), so the reorder assertion was nondeterministic. Adding more intermediate `mouse.move` steps and longer settle waits papered over it but never made it reliable.

## Root cause

Pointer-coordinate collision in @dnd-kit is geometry-sensitive: it needs the dragged pointer position to actually overlap the destination's measured rect. Under Xvfb, frame timing and sub-pixel layout differ enough that a center-to-center mouse path is not a stable input. Simulating the mouse was the wrong abstraction for a reorder assertion — the test cared that `DndContext` `handleDragEnd` produced a new order, not that a pointer traversed specific pixels.

## Lesson

For @dnd-kit reorder E2E, drive the **keyboard sensor**, not simulated mouse drags. The current helper `keyboardReorderElement()` (`e2e/helpers/dragDrop.ts`) focuses the drag handle, presses `Space` to pick up, presses arrow keys to move, and `Space` to drop. The app's `DndProvider` (`src/components/DragDrop/DndProvider.tsx`) already registers `KeyboardSensor` with `sortableKeyboardCoordinates` alongside its `NoDndMouseSensor`, so keyboard reorder exercises the exact same `DndContext`/`handleDragEnd` path while using dnd-kit's deterministic coordinate resolver instead of headless pointer geometry. `core-drag-drop.spec.ts` (now `e2e/full/panels/`) presses `ArrowRight` sequences and asserts the panel-id order changed. This is also more honest coverage: it validates the accessible reorder path real keyboard users rely on. The reverted `dragElementTo()` helper is gone — do not reintroduce mouse-path drag simulation for dnd-kit reorder. (Cross-grid moves like grid↔dock now use the explicit minimize button and the dock chip's double-click handler, not a simulated drag across containers.)

## Applies when

- Writing or fixing a Playwright E2E test for any @dnd-kit sortable (panel grid, dock, toolbar `ToolbarSettingsTab`, `PortalToolbar`)
- A reorder test is flaky in headless Linux/Xvfb CI and the helper uses `page.mouse.move`/`mouse.down`/`dragTo` with bounding-box coordinates
- You only need to assert the resulting order changed (not that a specific pixel path was traversed)
- Tempted to "fix" drag flakiness by adding more `{ steps }` or longer settle timeouts — switch to the keyboard sensor instead
