## Context

The local MCP server (`electron/services/mcp-server/`) exposes the ActionService manifest as tools; `buildAnnotations` in `tierAuth.ts` serializes each `ActionManifestEntry` into the four MCP `ToolAnnotations` hints (`readOnlyHint` / `idempotentHint` / `destructiveHint` / `openWorldHint`) that clients like Claude Code and Claude Desktop use to decide when to prompt the user. Every action carries two independent classifications: a `kind` (`query` vs `command`) and a `danger` rating (`ActionDanger = "safe" | "confirm" | "restricted"`, `shared/types/actions.ts`) — the same danger axis that drives ConfirmDialog wiring and the destructive-tier framework (#7880).

## Problem

Every non-query action serialized `destructiveHint: true` — including reversible `danger: "safe"` commands like `git.stageFile` and `terminal.new` — so MCP clients were nudged toward confirmation prompts on actions Daintree itself classifies as safe. The misleading part: the code looked deliberate and spec-faithful. The MCP spec's default posture for an unspecified `destructiveHint` IS conservative (`true`), and a test comment even blessed the values as "spec-conservative true defaults" — reading it as intent, not defect.

## Root cause

`buildAnnotations` derived three hints from a single axis: `readOnlyHint ?? isQuery`, `idempotentHint ?? isQuery`, `destructiveHint ?? !isQuery`. Kind answers "does it mutate?" — but destructiveness is "is the mutation hard to reverse?", which is exactly what the `danger` field already encodes and what the destructive-tier audit maintains per action. Deriving destructiveHint from kind collapses the two axes, marking every mutation destructive. The fix (#9574, resolving #9568) is one line: `destructiveHint: overrides?.destructiveHint ?? entry.danger === "confirm"`. `restricted` needs no serialization branch because `shouldExposeTool` (tierAuth.ts:91) filters `danger === "restricted"` entries out of the tools list upstream — a restricted entry that somehow bypassed that gate serializes `destructiveHint: false`, and a regression test pins that as the intended shape.

The instructive half is the fix that was deliberately NOT made. #9568 flagged `idempotentHint` as having the same defect shape (`?? isQuery` marks naturally-idempotent commands like `git.stageAll` or `worktree.setActive` non-idempotent), but idempotence is orthogonal to danger: `terminal.new` is `danger: "safe"` yet not idempotent (each call spawns a new terminal), while `git.stageAll` is safe AND idempotent. Mapping idempotentHint from danger would emit wrong hints in both directions. A correct fix needs a new per-action `idempotent` metadata field plumbed through the action definition, manifest entry, and `buildAnnotations`, plus a per-action audit to populate it — so it was scoped out, left on the conservative `isQuery` default with `mcpAnnotations.idempotentHint` as the per-action escape hatch. That is still the state of the code today (verified 2026-07: tierAuth.ts:139).

## Lesson

- **Each MCP hint derives from its own semantic axis** — readOnly ↔ kind, destructive ↔ danger, idempotent ↔ per-action idempotence metadata (which does not exist yet), openWorld ↔ its own spec default. Never derive two hints from one classification just because the ternaries line up in a column.
- **Identically-shaped sibling lines can demand opposite treatment.** The tempting "complete the fix" edit — `idempotentHint ?? entry.danger === "confirm"` — is wrong: safe ≠ idempotent (`terminal.new` proves safe-but-not-idempotent; `git.stageAll` proves safe-and-idempotent). If picking up the open idempotentHint half of #9568, add a per-action `idempotent` field + audit; do not map from danger.
- **Spec-conservative defaults are not app-faithful defaults.** The MCP spec defaults an unspecified `destructiveHint` to `true`, but mirroring that in code that HAS a danger classification contradicts your own metadata and degrades client UX (confirm prompts on every safe command). When richer local metadata exists, the hint must report it, not the spec's worst-case fallback.
- **Annotations are untrusted client hints, never authorization gates.** Real enforcement is `shouldExposeTool` + `isTierPermitted` tier allowlists and the grant cache (`sessionServer.ts:426`). Changing a hint is UX-fidelity work with zero security implications — and conversely, no gating logic may ever rely on a hint value.
- **Override precedence needs `??`, never `||`.** An explicit `mcpAnnotations.destructiveHint: false` must beat the danger-derived `true`; swapping `??` for `||` silently discards explicit-false overrides. `tierAuth.test.ts` pins this ("??-guard regression" test) — keep those tests when refactoring `buildAnnotations`.

## Applies when

- Touching `buildAnnotations` in `electron/services/mcp-server/tierAuth.ts`, or adding a new hint field to `ActionMcpAnnotations` (`shared/types/actions.ts`) — decide the hint's own derivation axis before writing the `??` default.
- Picking up the still-unfixed `idempotentHint` scope of #9568 — the correct shape is a new per-action `idempotent` metadata field with a per-action audit, NOT a danger mapping.
- Diagnosing why MCP clients (Claude Code / Claude Desktop) prompt for confirmation on safe Daintree actions like `git.stageFile` or `terminal.new`.
- Reviewing any change that derives a second boolean flag from an existing classification because the source lines look parallel — check that the axes actually coincide.
- Assuming `danger: "restricted"` needs a branch at annotation/serialization time — it is filtered upstream by `shouldExposeTool` and intentionally serializes as non-destructive if that gate is bypassed.
