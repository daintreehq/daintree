## Context

Backgrounded project views are detached and frozen (`Page.setWebLifecycleState("frozen")` + CDP CPU throttling). Reactivating a cached view used to reattach it immediately as "already painted". Agent terminals run xterm's WebGL addon, whose glyph texture atlas is **module-global** — shared by every terminal with a matching font/theme config (hazard block at `TerminalWebGLManager.ts` ~line 254, #8080).

## Problem

Switching back to a backgrounded project flashed every agent terminal as solid glyph blocks for a frame (#9679) — geometry right, glyphs wrong, self-correcting in under a second. Separately (#9701, fixed in #9703), Redraw on ONE Claude Code pane blanked the OTHER visible pane until clicked. Both symptoms mislead: the flash looks like slow rendering (it's a stale GPU surface), and the Redraw corruption lands in the pane you _didn't_ touch.

## Root cause

Freezing is not a WebGL context loss: no `webglcontextlost` fires, so the pooled addon stays marked healthy while its atlas goes stale, and the reveal path's WebGL restore sat behind a 100ms debounce that skipped still-pooled addons. Worse, on reattach the compositor can push the view's cached pre-freeze GPU surface for a frame **before any renderer JS runs**, and `setBackgroundColor` can't mask it — it only shows through transparent content, never over an opaque stale surface. The fix is main-process z-order: `activateView(host, cached, /* insertBehind */ true)` stacks the incoming view at z-index 0 behind the still-attached outgoing view (occluded but unfrozen, so its rAF + wake fan-out run), and only after the renderer signals a clean post-repair frame (`APP_VIEW_WARM_PAINTED`, double-rAF in `warmReactivationGate.ts`) — or the 500ms soft / 1500ms hard timeout — is the outgoing view detached. Cold-start `APP_VIEW_PAINTED` is one-shot per V8 context and never re-fires from a cached view, hence the separate re-fireable channel plus the `releaseChannel` discriminator on `PaintGate` so cold/warm signals can't cross-release each other's gates.

The Redraw bug is the shared-atlas footgun: `resetRenderer` called xterm's public `clearTextureAtlas()`, which clears the _shared_ atlas — co-owner panes start sampling wrong glyph images and stay corrupted until their own resize/click. The safe per-pane reset is the resize-like local path `resetLocalWebGLRenderer` (`_renderer.handleResize`, falling back to `_clearModel(true)`, then `terminal.refresh`) — packaged as `TerminalWebGLManager.repairAtlasForReactivation(id)`, used by both the wake seam and Redraw, with a plain `refresh` fallback for DOM-renderer terminals when it returns false.

## Lesson

- **A frozen `WebContentsView`'s first composited frame after reattach can be pre-freeze GPU state — only main-process z-order can mask it.** Renderer-side repair alone always loses the race. Reattach behind the outgoing view (`addChildView(view, 0)`), wake occluded, reveal on the renderer's clean-frame signal with a hard-timeout escape; don't focus the behind-bridged view until reveal (`insertBehind` skips `webContents.focus()`).
- **One-shot vs re-fireable renderer signals must be discriminated at the gate.** `notifyViewPainted` fires once per V8 context; warm reactivation needs its own channel, and `releaseChannel` keeps a stray signal of the wrong kind from releasing the bridge early. The discriminator later grew a third variant (`"skeleton-painted"`) — extend it, never overload an existing signal.
- **A gate is only as reliable as the trigger that runs its releasing code.** As shipped, the warm wake keyed off `visibilitychange`/`resume`, which a detached + `setVisible(false)` view mostly never receives — warm switches silently sat until the 1.5s hard timeout. #10965 added `APP_VIEW_WARM_ACTIVATED`: main tells the renderer to wake, sent _after_ the gate is armed so the completion signal can't slip past. If main gates on a renderer signal, main must guarantee the renderer runs the code that emits it.
- **Never fix one xterm pane by clearing shared state: `clearTextureAtlas()` is module-global.** Per-pane recovery = `repairAtlasForReactivation` (local model reset + refresh only). #9703's sibling-isolation test (`TerminalInstanceService.reflow.test.ts`) is the template: assert the co-owner terminal receives zero calls.
- **Release the gate in a `finally`.** `wakeActiveWorktreeTerminals` fires `notifyWarmReactivationComplete()` unconditionally — a zero-terminal grid or a thrown fan-out must not leave main holding the bridge until timeout. The signal is a safe no-op when no gate is pending.
- `ProjectViewManager` unit tests not exercising the bridge must pass `warmPaintGateTimeoutMs: 0, warmPaintGateHardTimeoutMs: 0`, or warm reactivations block on a signal that never comes. The GPU flash itself is compositor-timing-dependent and was never runtime-reproduced — test the invariants instead (repair-before-wake ordering, z-order, gate release/mismatch/cancel).

## Applies when

- Touching warm/cold project-view switching, freeze/unfreeze, or paint gates — post-split homes: `ProjectViewSwitchController.ts`, `ProjectViewPaintGateController.ts`, `ProjectViewLifecycleController.ts`. Note `warmReactivationGate.ts`'s docstring still describes an older "opaque background-color cover" framing; the real mechanism is the insert-behind bridge.
- Diagnosing a one-frame flash of stale/garbled terminal content on project switch-back, or corruption in a pane _other than_ the one an action targeted (shared-atlas signature: ~12 tiled agents, 1Hz status-line rewrites, unfocused panes corrupted until resize — #8080).
- Reviewing any call to xterm's `clearTextureAtlas()` or any per-terminal recovery path — route through `repairAtlasForReactivation` / `resetLocalWebGLRenderer` instead.
- Adding a main-process gate that waits on a renderer IPC signal — verify it's re-fireable for your path, discriminated from other gates, armed before the trigger is sent, and released in a `finally`.
- Assuming a frozen renderer will notice reactivation via `visibilitychange` — it won't when detached; send an explicit activation IPC.
