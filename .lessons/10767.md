## Context

`usePollingLifecycle` (`src/hooks/usePollingLifecycle.ts`) is the shared polling primitive behind renderer hooks like `useRepositoryStats` (the forge toolbar's issue/PR/commit counts) and `useProjectHealth` — it fires a fetch on mount, on a scheduled interval, on tab-visibility changes, on project switch, and on manual refresh. Each project runs in its own `WebContentsView` (`ProjectViewManager`), backgrounded and later reactivated on switch-back; the forge stats fetch (`FORGE_GET_REPO_STATS`) goes through a main-process `checkRateLimit(CHANNELS.FORGE_GET_REPO_STATS, 10, 10_000)` throttle in `electron/ipc/handlers/forgeData.ts`.

## Problem

Switching rapidly between two GitHub-backed projects (5-10 times in 10s) painted the forge toolbar into a persistent red error line (`forge-status-error`) that stuck until the user clicked something to force a refresh. It looked like a GitHub-side rate-limit problem — misleading, since the actual trigger was Daintree's own IPC throttle, tripped by local reactivation traffic before any request reached GitHub. A prior fix, #10762 (a switch-back cache + `fetchGenerationRef`), had "resolved" the earlier report #10761 and its unit tests passed, but the bug reappeared under this exact repro as #10765.

## Root cause

Two things compound. First, a single reactivation (switching back to a project) fires **two independent triggers** through `usePollingLifecycle`'s subscriber interface: `onVisibilityVisible` (from the renderer's `visibilitychange` listener) and `onProjectSwitch` (from the per-view `PROJECT_ON_SWITCH` IPC event) — each independently calls `callFetchFn(false, …)`, so one switch means two `getRepoStats` calls. Rapid A→B→A→B switching bursts past the 10-calls/10s limiter, `checkRateLimit` throws `AppError(RATE_LIMITED)`, the renderer catch sets `statsError`, and `getForgeIndicatorStatus()` paints the red line, which then persists since nothing re-fetches to clear it.

Second, #10762's switch-back cache (`switchBackStatsCache`, `fetchGenerationRef`) only suppressed the loading skeleton — `fetchFn` still called `forgeClient.getRepoStats()` on every reactivation regardless of a cache hit, so the redundant IPC traffic that actually trips the limiter was never touched. Its unit tests passed anyway because they modeled a single shared renderer instance whose current-project value mutates A→B→A — a model that predates `ProjectViewManager` giving each project its own `WebContentsView`. Production runs one `useRepositoryStats` instance per view, so `switchBackStatsCache` never sees a second project in that instance, and the "cache restore" path the tests exercised doesn't correspond to what switch-back actually does in the app.

## Lesson

- When a hook subscribes to multiple lifecycle signals that can legitimately co-fire on the same user action (`visibilitychange` + a switch/focus IPC event), **assume they WILL co-fire and design for N calls per action, not 1** — `onVisibilityVisible` and `onProjectSwitch` are independent subscriber callbacks in `usePollingLifecycle` with no dedupe between them.
- Threading a `reason` (`PollingLifecycleFetchReason`: `"initial" | "reactivate" | "scheduled" | "manual"`) through the fetch context lets a consumer set different network policy per trigger without touching the trigger sites — `useRepositoryStats` skips the network when `reason === "reactivate"` and data is still fresh (`freshLastUpdatedRef`, `FRESH_THRESHOLD_MS = 90_000`), while scheduled/manual/initial always hit it. `callFetchFn`'s `REASON_RANK` strongest-wins coalescing (`manual > scheduled > reactivate > initial`) ensures a queued manual/scheduled fetch is never silently downgraded by a reactivation arriving mid-flight. Reuse this for any future `usePollingLifecycle` consumer that needs to special-case reactivation.
- **A local rate limiter is a first-class suspect for any "persistent error state" bug**, before assuming an upstream/remote cause — the IPC-level `checkRateLimit(channel, maxCalls, windowMs)` throttle (used by dozens of handlers in `electron/ipc/handlers/*.ts`, not just forge) throws before a request ever reaches a provider, so a burst of legitimate-looking local traffic can produce an error UI that looks like a remote API problem but isn't.
- **A test suite that passes against a stale mental model of the process architecture proves nothing.** #10762's tests modeled "one renderer, project prop changes over time" — accurate before `ProjectViewManager` gave each project its own `WebContentsView`, false after. When Daintree's process/view topology changes (multi-window, per-project views), re-verify that existing hook tests still model how many instances of the hook actually run in production, not just what the mocks return.
- A cache/short-circuit that only hides a loading indicator, without preventing the network call it's meant to make unnecessary, doesn't fix a rate-limit or bandwidth problem — check what a "fix" actually prevents, not just what visibly changes in the UI. #10767's short-circuit runs after the switch-back cache restore (which repopulates the freshness ref) and returns before `setIsValidating(true)`, so a skipped reactivation never even flashes a validating affordance.

## Applies when

- Adding a new `usePollingLifecycle` consumer, or modifying `useRepositoryStats`/`useProjectHealth`, that reacts to tab focus or project-switch reactivation.
- Diagnosing a forge/toolbar error state that "only happens when switching projects quickly" — check `checkRateLimit` call sites and count triggers per reactivation before suspecting the remote API.
- Writing or reviewing unit tests for a hook whose behavior depends on Daintree's per-project-view architecture — confirm the test fixture models one hook instance per `WebContentsView`, not one shared instance mutating across projects.
- Reviewing a "switch-back cache" or similar reactivation-suppression fix — verify it prevents the actual network/IPC call, not just a loading-state flash.
