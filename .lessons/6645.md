## Context

`AppLayout` lays out the toolbar, `<main>` content grid, and the right-edge panels (Daintree Assistant, Portal/web-chat dock, ThemeBrowser overlay). PR #6620 converted the Assistant from an overlay into a **flex sibling** of `<main>` (a "push sidebar"). The Portal dock (`PortalDock`) was still rendered inside `<main>` as `position: absolute; right-0`.

## Problem

After #6620, opening the Portal while the Assistant was open made the Portal stop at the Assistant's left edge instead of covering the full viewport width — it anchored to `<main>`'s right edge, not the window. Separately, the shared `--portal-right-offset` CSS var (read by toasts, popovers, dropdowns, `ReEntrySummary`, `GettingStartedChecklist`, and the ThemeBrowser overlay to dodge right-edge panels) over-displaced those elements when both panels were open: it summed `portalWidth + assistantWidth`, displacing by the combined width even though the Portal **overlays** the Assistant rather than sitting beside it.

## Root cause

Two coupled traps from the same refactor:

1. **Containing-block re-anchor.** Once `<main>` became one of several flex siblings (rather than the full-width row), an `absolute right-0` child of `<main>` resolves "right" against `<main>`'s shrunken box, not the viewport. Promoting a node to a flex sibling silently shrinks the containing block of any absolutely-positioned descendant — no error, no devtools warning. (This is the flex-layout analog of #2574's `backdrop-filter` containing-block trap, but the trigger is a layout-tree change, not a paint property.)
2. **Sum vs. overlap.** The offset var encoded "total occupied right-edge space." When two right-edge panels can both be open but one **overlays** the other (Portal z-50 sits on top of Assistant), the rightmost obstruction is `max(portalWidth, assistantWidth)`, not their sum. The sum only happens to be correct when the panels tile side-by-side.

The fix hoists `PortalDock` into a `createPortal(..., document.body)` with `position: fixed`, and changes the offset to `Math.max(...)`. A second-order consequence: body-portaling moved `PortalDock` out of the `inert` main-content wrapper, so the `inert` attribute had to be re-applied directly to the new fixed wrapper (gated on `isThemeBrowserOpen`) to keep the Portal's React chrome non-interactive under the ThemeBrowser overlay.

## Lesson

- When promoting any element to a flex/grid sibling, audit every `position: absolute` descendant that anchored to that element — its containing block just changed. If it needs viewport coverage, body-portal it with `position: fixed` (mirror `ThemeBrowser`'s pattern in this file).
- Body-portaling re-parents the node out of any ancestor that applied behavior to the subtree (`inert`, `aria-hidden`, scroll-locking, focus traps). Re-apply those attributes to the new portal wrapper.
- A shared right-edge (or any-edge) offset var that multiple panels feed must reflect the panels' **stacking relationship**: use `max()` when one overlays another, `sum` only when they tile. State which it is in a comment, since the wrong one is silently correct in the single-panel case.
- Prefer one CSS custom property as the single source of truth for "how far in from the edge must floating UI sit" rather than re-deriving the ternary per consumer. #6800 later split this into two vars — `--portal-right-offset` (Portal-only, for toolbar dropdowns above the main row) and `--right-obstruction-offset` (max of Portal+Assistant, for fixed body-portaled overlays) — because the two consumer classes have different layout truths; keep them distinct.

## Applies when

- Refactoring `AppLayout.tsx` right-edge panels (Assistant / Portal / ThemeBrowser) or their widths/offsets.
- Converting an overlay panel into a push sidebar (flex/grid sibling) and a previously-`absolute` child now stops at the wrong edge.
- Debugging a `position: absolute`/`fixed` element that respects a container's bounds instead of the viewport, where the cause is the flex/grid layout tree (not `backdrop-filter` — see #2574 for that variant).
- Touching `--portal-right-offset` / `--right-obstruction-offset` or any shared CSS var consumed by toasts, popovers, dropdowns, `ReEntrySummary`, `GettingStartedChecklist`, or the ThemeBrowser overlay.
- Two simultaneously-open panels on the same viewport edge where displacement math (sum vs. max) depends on whether they tile or overlap.
- Moving any subtree into `createPortal(document.body)` and needing to preserve `inert` / `aria-hidden` / focus-trap behavior the old ancestor provided.
