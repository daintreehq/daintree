## Context

The GitHub forge plugin went through a provider-abstraction migration (the "CodeForge migration") that moved PR listing off the legacy `GitHubPRs.listPullRequests` service class and onto `readOps.listPRsImpl`, part of the forge-provider abstraction described in `docs/architecture/forge-provider-abstraction.md`. Two surfaces render PR CI status: the toolbar PR dropdown (fed by `listPRsImpl` via `LIST_PRS_QUERY` -> `toForgePR` -> `mapListCIStatus`) and the worktree sidebar badge (fed by `PullRequestService` -> `getCIStatusesImpl` -> `buildBatchRequiredChecksQuery` + `deriveRequiredCIStatus` in `prRequiredCIStatus.ts`).

## Problem

The dropdown and the sidebar showed conflicting CI status for the same PR (#11251, reproduced on PR #11250: dropdown said "Checks pending", sidebar showed failed). It looked like a cache-timing bug — the two surfaces poll and revalidate on different schedules — but reverting to fresh fetches on both sides did not converge them, because they were not computing the same value in the first place.

## Root cause

`listPRsImpl` only has `statusCheckRollup.state`, the coarse repo-wide rollup, because `LIST_PRS_QUERY` returns rows in a `pullRequests(first:N)` connection and GraphQL cannot bind `isRequired(pullRequestNumber:)` to a sibling node's own number inside that connection shape. The sidebar's `getCIStatusesImpl` uses a separate batched-alias query (`buildBatchRequiredChecksQuery`) built for exactly this, then derives via `deriveRequiredCIStatus`. A green rollup masking one failing required check reads as passing on the coarse path and failing on the required-check-aware path — two pipelines computing two different facts, not one fact read at two staleness points, so reverting to fresh fetches on both sides would not have converged them.

The legacy pre-migration `GitHubPRs.listPullRequests` enriched rows with required-check status inline; that behavior was simply never carried over when the forge-provider migration re-homed listing into `readOps.listPRsImpl`. The migration preserved the method's return type and primary happy path but dropped a secondary behavior nobody had pinned with a test. This is the same shape as #9061, where the same migration wave moved `runQuery` in `forgeProvider.ts` onto direct GraphQL calls and dropped the legacy service layer's per-entity 60s `Cache<>` instances and in-flight dedup entirely. Both times, re-homing a concrete method behind an abstraction kept the contract on paper (the return type, the happy path) but lost a behavior that was never written into that contract, because nothing forced the migration author to enumerate everything the old method did before deleting it.

A doomed one-way patch was already in place before this PR: the `pr-detected` MessagePort handler in `WorktreeStoreContext.tsx` used `mutateCacheEntries` to patch the dropdown's renderer-side `forgeResourceCache` whenever the sidebar detected fresh CI status. It only wrote the renderer cache, never the main-process `forgePRListCache` the dropdown actually reads from, so the next revalidate overwrote it with the stale coarse value again — a one-way sync patch between two independently-refreshing caches is a race the read path always wins.

## Lesson

- **Before re-homing a concrete method behind an abstraction, enumerate everything the old method did, not just its return type.** `GitHubPRs.listPullRequests` did required-check enrichment that was never in `listPRsImpl`'s signature or tests, so it fell out silently; the analogous #9061 gap was caching. List the old method's side effects (caching, enrichment, dedup, retry) alongside its return value, and carry each forward explicitly or document why it's dropped.
- **Two surfaces rendering "the same fact" from two different query/derivation pipelines diverge even with zero caching involved.** When two surfaces disagree, check whether they compute the same value before assuming staleness; the fix routed `listPRsImpl` through the existing `getCIStatusesImpl` (one derivation, one `prRequiredStatusCache` entry) instead of adding a second required-check query.
- **A one-way cache patch that doesn't write the read path's actual cache is dead code that will re-break on the next revalidate.** The removed `mutateCacheEntries` patch only touched `forgeResourceCache`, never `forgePRListCache` — delete rather than extend a patch like this once you find the real shared source.
- **Enrichment added to a list's critical path needs a time budget.** `enrichPRPageWithRequiredStatus` caps the added GraphQL call at `REQUIRED_STATUS_ENRICHMENT_BUDGET_MS = 4_000` via `Promise.race`, because unbounded could hold the dropdown for the full 15s API timeout across sequential chunks — and still lets the in-flight request finish to warm the cache, so only that page degrades to coarse.
- **When flagging a migration-loss bug, name the confirmed prior instance.** The PR body cites #9061 as "the same shape" — recognizing the pattern turns a one-off bug into a named class worth grepping for on every future forge-provider re-homing (issue ops, review-thread ops still to migrate).

## Applies when

- Migrating any concrete service method (GitHub, or any future forge/plugin provider) behind an abstraction layer — audit the method's full behavior (caching, enrichment, dedup, rate-limit handling), not just its signature, before deleting the original.
- Two UI surfaces render the same conceptual value (CI status, PR state, review status) from different query paths — check whether they derive the value identically before chasing it as a cache-timing bug.
- Touching `plugins/builtin/github/main/readOps.ts` (`listPRsImpl`, `enrichPRPageWithRequiredStatus`, `getCIStatusesImpl`) or `GitHubCaches.ts` (`forgePRListCache`, `prRequiredStatusCache`) — both must stay in sync on what "required-check enrichment" means.
- Reviewing a one-way cache-sync patch (a handler that mutates one cache to match another) — verify it writes the cache the actual read path consults, or it's cosmetic and will regress on the next revalidate.
- Adding a network call to an existing list/read critical path — it needs an explicit time budget and a defined degrade-to-coarse behavior, not an unbounded await.
