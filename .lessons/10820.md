## Context

#10818 added auto-reopen + auto-resume for the Daintree Assistant help panel on cold switch-back: when a project's `WebContentsView` is LRU-evicted or crashes with the panel open, main stamps a `panelWasOpen` hibernation entry and pushes `help:cold-resume` from `onViewReady`, and the renderer's `HelpSessionController._executeLaunch` auto-launches with `resumeOnly: true`. The single-backend-per-project invariant (#7509) is enforced by `provisionHelpSession` calling `HelpSessionService.displacePriorSessions(projectId)`, which revokes/kills any existing backend for that project before minting a new one. The atomic winner-take-all claim on the captured hibernation entry is `window.electron.help.takePendingHibernation(projectId)` — first caller gets the entry, everyone else gets `null`.

## Problem

Opening the same project in two windows and letting both cold-restore near-simultaneously (both evicted, both switched back to around the same time) left neither window with a live assistant, and the hibernation token was already consumed — so there was nothing left to retry. No crash, no error banner: the feature just silently failed for the one scenario it was explicitly built to handle less gracefully.

## Root cause

`_executeLaunch`'s original `resumeOnly` path called `provisionHelpSession(launchProject, ...)` first and only checked `takePendingHibernation` afterward, deep in the resume-lookup block, to decide whether to resume or abort. Filed as #10819 (found via Codex review during the #10818 merge): the atomic guard was real, but it ran downstream of a side effect. Both windows entered `provisionHelpSession` before either had checked who won the take, and it unconditionally calls `displacePriorSessions` — so window B's provisioning killed window A's just-resumed backend (or vice versa) before window B ever reached the code that would tell it "you lost." The eventual abort only cleaned up the loser's own newly-minted session; it had no way to undo the backend it had already caused main to revoke.

A secondary bug rode along: the resume decision was ultimately driven off the local `helpPanelStore.hibernateSessions[projectId]` entry, not strictly off a successful `takePendingHibernation` result — a stale local entry from before the race could still push a window toward provisioning without having won the take.

The fix hoists the take: `if (options.resumeOnly && !reservedId && !options.seedPrompt)` now calls `takePendingHibernation` and aborts via `_abandonInFlightLaunch` on `gen !== this._launchGen`, `!earlyPending`, or `earlyPending.agentId !== launchAgentId` — _before_ `provisionHelpSession` runs. A winner seeds `useHelpPanelStore.getState().setHibernateSession(...)` directly from the take result, so the resume block reads authoritative data instead of the local store's possibly-stale copy. The subsequent unconditional re-seed (originally `_seedHibernateFromMain`, since refactored into `this._hibernationManager.seedFromMain` in `src/controllers/HibernationManager.ts`) is now skipped when `resumeOnly` is true, since a second take on an already-consumed entry would just return `null`.

## Lesson

- **In a claim-then-act protocol, the atomic claim must be the FIRST side effect on that path, not just present before the terminal state.** An abort check that exists but runs after a mutating call (`provisionHelpSession` → `displacePriorSessions`) doesn't delay the mutation, it delays _discovering_ the mutation was a mistake — the damage is already done by the time the check fires.
- **Gate continuation decisions on the authoritative result of the atomic operation, not a locally cached mirror of it.** `helpPanelStore.hibernateSessions[projectId]` can be stale; the fix makes the resume block consume the `takePendingHibernation` return value directly instead of re-reading the Zustand store as truth.
- **Audit every call path into a globally-destructive function for pre-checks that arrive too late, whenever the function is reachable concurrently from independent windows.** `displacePriorSessions` revokes another window's live backend — any caller of `provisionHelpSession` needs to prove it already won its claim before calling it, not merely intend to check afterward.
- **Test the interleaving, not just each branch's outcome.** #10820 added an explicit `takeOrder < provisionOrder` assertion via `mock.invocationCallOrder`, plus separate cases for null-take, `agentId` mismatch, generation-superseded-mid-await, and take-IPC-throws — call-order is the one assertion that actually encodes "the fix is the fix" rather than restating a literal.
- **Before skipping a downstream step because "the work already happened," confirm the skip is provably safe, not just plausible.** The re-seed on `resumeOnly` is skipped specifically because a second `takePendingHibernation` call is known to return `null` on an already-consumed entry — that invariant is what makes the skip correct.

## Applies when

- Touching `HelpSessionController._executeLaunch`, the `resumeOnly` launch path, or `HibernationManager.seedFromMain` (renamed from `_seedHibernateFromMain`) — verify any atomic take still runs before `provisionHelpSession`.
- Adding or reviewing any claim-then-act / winner-take-all guard (atomic IPC take, DB row lock, CAS-style flag) upstream of a call that mutates shared state other processes depend on.
- Diagnosing "opened the same project in two windows and lost the assistant/session in both," or any cold-resume, crash-recovery, or eviction-revival flow racing across `WebContentsView`s or windows.
- Reviewing code where a function enforcing a single-instance-per-key invariant (`displacePriorSessions`, any revoke/kill-prior-owner call) is reachable from more than one concurrent launch/provision path.
- Assuming a Zustand-persisted store entry (`useHelpPanelStore.getState().hibernateSessions[...]`) is authoritative for a cross-process decision — check whether a main-process source of truth exists and gate on that instead.
