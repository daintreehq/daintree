## Context

PtyPool pre-warms shell PTYs to make terminal spawn feel instant. Originally pool entries were spawned at `os.homedir()`, and `acquirePtyProcess` relocated them on handoff by writing a shell-level `cd "<projectCwd>"` command into the pooled PTY before clearing the screen.

## Problem

A `cd` write is not a safe way to move a shell that has already started. `cd` is a shell builtin the user can redefine: zoxide, direnv, and oh-my-zsh `chpwd` hooks all wrap or intercept `cd`, and any of them can land the shell in a different directory (zoxide's frecency jump, a `chpwd` that re-roots, a hook that errors and aborts). The pooled shell then hands off to the user already in the wrong cwd, with no signal that anything went wrong. The fixup also had to be platform-forked (`cd /d` for cmd, `Set-Location` for PowerShell, `cd` for POSIX), multiplying the surface for the same class of failure.

## Root cause

The bug was the _mechanism of relocation_, not just the choice of warm cwd. A pre-spawned shell can only be moved by issuing input through its stdin, and stdin goes through the user's fully-customized shell — there is no privileged channel to chdir a running shell from outside. The only relocation that bypasses user shell logic is the one done _before_ the shell starts: node-pty's `cwd` spawn option, which does a kernel-level `chdir()` before `exec`, so the shell comes up already rooted correctly and no `cd` ever runs. The fix therefore warms the pool at the active project's cwd from the start (`drainAndRefill(projectPath)` on project switch) and removes the `cd` write entirely — the only write left to a pooled PTY is a screen/scrollback clear.

Two non-obvious supporting pieces: (1) `acquirePtyProcess` must verify the pool's cwd matches the request and skip the pool on mismatch (multi-window: another window may have drained the global-singleton pool to a different cwd) rather than hand back a misconfigured shell — `canUsePool` gates on the key match, today via `acquireByKey(options.cwd, envHash)`. (2) Draining-and-refilling a live pool is a race: in-flight `createPoolEntry` spawns and `onExit→refill` cascades from a _previous_ cwd would otherwise register or re-warm at the stale cwd. `PtyPool` guards this with a `drainEpoch` counter captured into each spawn closure; `drainAndRefill` bumps the epoch before killing, so stale spawns reject and the old entries' exit handlers skip refilling.

## Lesson

To position a pooled/pre-warmed PTY at a directory, set node-pty's `cwd` at spawn time (kernel chdir before exec) — never write a `cd` into an already-running shell, because `cd` is user-redefinable and shell hooks (zoxide/direnv/chpwd) will silently send it elsewhere. When a pre-warmed resource can be repointed at runtime, treat the repoint as a race: tag in-flight creations with a generation/epoch captured at spawn time and reject stragglers from the prior generation, and suppress the auto-refill cascade triggered by killing the drained entries. And because the pool is a global singleton shared across windows, the acquire path must validate the entry actually matches the requested cwd (and env) and fall back to a fresh spawn on mismatch rather than trusting the warm to be correct.

## Applies when

Pre-warming or pooling PTYs/processes that must start in a specific directory. Reviewing any code that writes `cd`/`Set-Location`/`cd /d` into a terminal to relocate it. Debugging "pooled/instant terminal opened in the wrong directory" reports, especially for users with zoxide, direnv, or oh-my-zsh. Adding `drainAndRefill`-style runtime repointing to any warm-pool, or wiring a per-window project switch to pool state.
