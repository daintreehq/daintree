## Context

The MCP server (`electron/services/mcp-server/`) gates each HTTP request through two functions in `tierAuth.ts`: `isAuthorized` decides accept/reject, and `resolveTokenTier` decides the privilege tier (`external` > `system` > `action` > `workbench`) that scopes which actions the session may dispatch. Both parse the same `Authorization: Bearer <token>` header to extract the token, then look it up against pane tokens (`mcpPaneConfigService`) and help-session tokens (`helpTokenValidator`).

## Problem

A token that authenticated successfully could still be silently demoted to the lowest `workbench` tier. Reported as #7129: a help/pane token presented with a TAB between the scheme and token (`Bearer\thelp-tok`) authorized fine but resolved to `workbench`, stripping its real privileges — a silent privilege drop with no error surfaced.

## Root cause

The two functions had been written with independent, inconsistent header parsers:

- `isAuthorized` extracted the token via `authHeader.startsWith("Bearer ")` + `slice` for the pane path, but `/^Bearer\s+(.+)$/` (which `\s` matches tabs) for the help path.
- `resolveTokenTier` used only `startsWith("Bearer ")` + `slice`, which requires a literal single space.

So `Bearer\thelp-tok` passed `isAuthorized` (the help branch's `\s+` matched the tab) but failed `resolveTokenTier`'s strict-space check, falling through to the `return "workbench"` default. Accept and tier-resolve disagreed about what counts as a valid Bearer header. Whenever two code paths parse the same security-relevant input with separately-authored logic, they drift, and the drift manifests as an authorization/tier mismatch rather than a clean rejection.

## Lesson

- One header, one parser. The fix introduces a single `extractBearerToken(authHeader)` (regex `/^Bearer[ \t]+(.+)$/i`, trims surrounding tab/space, rejects no-whitespace and CR/LF variants) that BOTH `isAuthorized` and `resolveTokenTier` (and `resolvePinnedWebContentsId` in `httpLifecycle.ts`) call. Never let a security decision and the privilege-scoping decision derived from the same input use different extractors.
- Deliberately keep the api-key path OUT of the normalizing parser. The api-key check hashes the RAW header and `timingSafeEqual`s it against a precomputed digest of `"Bearer " + apiKey` — so `Bearer\tsecret` is rejected (exact match, constant-time), while pane/help tokens go through the lenient `extractBearerToken`. This asymmetry is intentional: the shared secret must match byte-for-byte; capability tokens tolerate whitespace variants. Don't "unify" the api-key path into the lenient parser.
- Guard `timingSafeEqual` against length mismatch first (`apiKeyBearerHash.length === actualHash.length && timingSafeEqual(...)`) — it throws on unequal-length buffers, which would otherwise crash the auth path on a malformed cached hash.
- Precompute the expected hash once at `setApiKey` time (`precomputeApiKeyBearerHash`), not on every request.

## Applies when

- Touching MCP server auth, tier resolution, or `Authorization`/Bearer parsing in `electron/services/mcp-server/tierAuth.ts` or `httpLifecycle.ts`.
- Adding a new token type (pane, help-session, api-key, or future) to the MCP tier system — route it through `extractBearerToken`, and decide explicitly whether it needs exact-match (like api-key) or normalized parsing.
- Any place where one function decides accept/reject and a separate function derives a privilege level/scope from the same request input — verify both use identical extraction; a silent demotion (not a 401) is the symptom.
- Debugging reports of an MCP/agent token that "works" but lacks expected permissions, or sessions unexpectedly landing in `workbench` tier.
- Reviewing `timingSafeEqual` usage — confirm a length check precedes the comparison.
