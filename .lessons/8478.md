## Context

The worktree sidebar (`SidebarContent.tsx`) was rewritten to render its rows inside a flat react-virtuoso list (overscan ~600px) so 50–200+ worktrees stop paying full mount cost. Rows are dnd-kit sortable via `SortableWorktreeCard` / `useSortable`, and the whole grid drives a `DndProvider` (`src/components/DragDrop/DndProvider.tsx`) that also handles terminal-accordion drags.

## Problem

Once the list is virtualized, dragging a worktree far enough to autoscroll the source row out of Virtuoso's overscan window silently converted the drop into a cancel — the reorder was lost with no error. Reordering worked only when the source row happened to stay mounted for the whole drag.

## Root cause

dnd-kit reads drag payload from `active.data.current`, which is populated by the live `useSortable` hook on the dragged element. Virtuoso unmounts off-window rows; when autoscroll pushes the source row outside overscan, its `useSortable` hook unmounts and `active.data.current` becomes `undefined` _before_ `handleDragEnd` fires. Two code paths then misfire:

1. `handleDragEnd` reads `active.data.current`, sees `undefined`, and the worktree-sort branch (`isWorktreeSortDragData(...)`) no longer matches, so the reorder never runs.
2. dnd-kit's `cancelDrop` callback runs _before_ `handleDragEnd`; its worktree-sort short-circuit (`return false` = allow drop) also keyed off `active.data.current`, so an unmounted source row made it fall through and convert the drop to a cancel.

This is the inverse pressure of lesson #4438: there, `content-visibility: auto` had to be disabled during drag to protect dnd-kit transforms. Here Virtuoso owns windowing, so `content-visibility` is dropped from `SortableWorktreeCard` entirely (`SortableWorktreeCard.tsx` style no longer sets it) — it bought no extra paint savings and only risked breaking transforms on the active row.

## Lesson

When a dnd-kit sortable list is virtualized (Virtuoso, react-window, react-virtual), the dragged element can unmount mid-drag. Snapshot its payload at pickup instead of trusting `active.data.current` to persist:

- In `handleDragStart`, pin `activeWorktreeSortDataRef.current = active.data.current` (a `useRef`, not state) the moment the drag is identified as the virtualized kind.
- In `handleDragEnd`, treat the ref as canonical: `activeWorktreeSortDataRef.current ?? (isWorktreeSortDragData(live) ? live : undefined)`, then clear the ref.
- In `cancelDrop`, also gate on the ref: `activeWorktreeSortDataRef.current !== null || isWorktreeSortDragData(active.data.current)`. cancelDrop fires first; skipping the ref here loses the drop before handleDragEnd ever runs.
- In `handleDragCancel`, clear the ref so it never leaks into the next drag.
- Drop `content-visibility: auto` from rows once a virtualizer owns windowing — it adds no paint savings over Virtuoso and reintroduces the #4438 transform breakage on the active row.
- Prefer flat `Virtuoso` over `GroupedVirtuoso` when the list is also a dnd-kit sortable surface: keep sticky group headers as sentinel items (`item.kind === "header"`) in the same flat array so collision detection sees one contiguous coordinate space. GroupedVirtuoso's DOM-split sticky model fragments it.

## Applies when

- Adding or debugging drag-reorder on any virtualized list (Virtuoso/react-window/react-virtual + `@dnd-kit/sortable`).
- A reorder "works for short drags but loses the move on long drags" or only fails when autoscroll kicks in.
- Touching `DndProvider.tsx` worktree-sort branches, `handleDragStart` / `handleDragEnd` / `cancelDrop` / `handleDragCancel`, or `SortableWorktreeCard`.
- Deciding between flat Virtuoso vs GroupedVirtuoso for a list that is also a sortable / collision-detection surface.
- Migrating a list off `content-visibility: auto` onto a windowing virtualizer (revisit lesson #4438's drag guard).
- Wiring `aria-activedescendant` keyboard navigation over rows that virtualization may unmount (stable DOM ids must survive the unmount, e.g. `getWorktreeSidebarRowId`).
