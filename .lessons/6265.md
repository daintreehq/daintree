## Context

Errors thrown inside `ipcMain.handle`/`handleOnce` listeners are caught by the global wrapper in `electron/setup/security.ts` (`enforceIpcSenderValidation`), serialized via `serializeError` (`shared/utils/ipcErrorSerialization.ts`), and sent to the renderer as an `IpcErrorEnvelope`. `serializeError` copies many whitelisted error fields onto the wire — not just `message`, but also `userMessage`, `stack`, `code`, `gitReason`, `context`, `cause`, and arbitrary `properties`. The packaged-build branch strips/sanitizes these before they leave the main process; the secret scrubber (`scrubSecrets`) pattern-matches GitHub PATs, Anthropic keys, Bearer tokens, etc.

## Problem

The IPC error sanitizer scrubbed `serialized.message` but left `serialized.userMessage` untouched. `AppError` (`electron/utils/errorTypes.ts:122`) carries a parallel, user-facing `userMessage` field that `serializeError` promotes onto the wire (`ipcErrorSerialization.ts`, `if (typeof err.userMessage === "string")`). A secret embedded in `userMessage` (e.g. `please rotate sk-ant-…`) reached the renderer unredacted in packaged builds even though the same secret in `message` was caught.

## Root cause

Two compounding traps:

1. **Parallel message field.** The error's user-facing text is NOT only in `.message`. `AppError.userMessage` is a Daintree-custom field (not an Electron platform field) that the codebase's own `serializeError` whitelists and forwards. A scrubber written against `.message` alone silently misses it. Any future field `serializeError` decides to promote (e.g. `gitReason`, `properties`) has the same exposure.
2. **Dev-invisible leak path.** The scrub/strip logic is gated entirely behind `app.isPackaged`. In dev, the catch block calls `wrapError(error)`, which is a raw `serializeError` with NO scrubbing and NO path-stripping. So a developer testing IPC errors in dev sees neither the scrubbing nor the leak — the gap only manifests in packaged builds, exactly where it can't be caught by casual local testing.

## Lesson

- When scrubbing an IPC error before it crosses the trust boundary, scrub **every string field `serializeError` promotes onto the wire**, not just `message`. Today that means `message` AND `userMessage`; audit `KNOWN_ERROR_KEYS` / the `serialized.*` assignments in `shared/utils/ipcErrorSerialization.ts` whenever a new promoted field is added, and scrub or null it in `enforceIpcSenderValidation`.
- Treat any `app.isPackaged`-gated security path as **dev-untestable by inspection** — write unit tests that flip the gate (`appMock.isPackaged = true`) and assert the scrubbed envelope directly, because the dev run will never exercise it.
- Run path-normalization (`sanitizePaths`) before token scrubbing (`scrubSecrets`) — `sanitizeErrorForRenderer` does `scrubSecrets(sanitizePaths(msg))` so a token embedded inside a collapsed `<path>` is still caught.
- In-memory diagnostic paths (`logBuffer`, diagnostics dock) are intentionally left UNscrubbed — scrub only at outbound sinks that escape to disk or the renderer (logger file-write + console mirror, both `emergencyLog.ts` files, the IPC envelope). Over-redacting in-memory destroys debuggability for no security gain.

## Applies when

- Adding or modifying the IPC error envelope path in `electron/setup/security.ts` (`enforceIpcSenderValidation`, `sanitizeErrorForRenderer`, `makeErrorSafe`).
- Adding a new field to `serializeError` / `KNOWN_ERROR_KEYS` in `shared/utils/ipcErrorSerialization.ts`, or adding a new property to `AppError`/`DaintreeError` (`electron/utils/errorTypes.ts`) — ask "does this carry user/secret-bearing text to the renderer, and is it scrubbed?"
- Writing or reviewing any redaction/secret-scrubbing change (`shared/utils/secretScrubber.ts` call sites) — verify it covers all outbound sinks, not the one you happened to test.
- Reviewing any security or sanitization logic gated behind `app.isPackaged` (or any dev-vs-prod branch) — flag that local dev testing does not exercise it; demand a test that forces the packaged branch.
- Touching the crash/emergency log writers (`electron/utils/emergencyLog.ts`, `electron/pty-host/emergencyLog.ts`) or `electron/utils/logger.ts` file/console sinks.
