## Context

The main-process SQLite store (`electron/services/persistence/db.ts`, `daintree.db`) runs in WAL mode (`journal_mode = WAL`, `busy_timeout = 3000`). It is written through a single shared connection from `getSharedDb()`, but it is NOT the only open handle: `electron/services/persistence/readLastProjectId.ts` opens its own read-only `better-sqlite3` connection before `app.whenReady()` to pick the initial session partition, and any future worker/utility-process connection widens the surface further. Three write-only transactions — `ProjectStore.setCurrentProject`, `ScratchStore.setCurrentScratch`, `TaskPersistence.saveSync` — mutate the DB via `db.transaction(fn)`.

## Problem

Under concurrency, a write-only transaction could fail with `SQLITE_BUSY_SNAPSHOT` even though `busy_timeout = 3000` is set. `busy_timeout` does NOT retry that error — it is a hard "your snapshot is stale, abort" signal, not a transient lock contention — so the write surfaces as an immediate exception rather than blocking-then-succeeding. Invisible in single-writer unit tests; only manifests when a second connection holds a snapshot.

## Root cause

`db.transaction(fn)` in drizzle-orm (0.45.2, `SQLiteTransactionConfig.behavior?: 'deferred' | 'immediate' | 'exclusive'`) defaults to **DEFERRED**. A DEFERRED transaction acquires a _read_ lock and pins a WAL snapshot when the first statement runs, then tries to _upgrade_ to a write lock on the first mutating statement. In WAL mode, if another connection committed a write after this transaction's read snapshot was established, the upgrade fails with `SQLITE_BUSY_SNAPSHOT`. `busy_timeout` only retries plain `SQLITE_BUSY` (lock held by someone else), not `SQLITE_BUSY_SNAPSHOT` (your snapshot is now too old to write against) — there is nothing to wait for, the snapshot is permanently stale, so the only fix is to retry the whole transaction. Declaring `behavior: "immediate"` makes SQLite take the write lock up front (`BEGIN IMMEDIATE`), before any snapshot is pinned, eliminating the read→write upgrade entirely.

## Lesson

- For any transaction that is **write-only** (no read-then-decide logic that needs the read at DEFERRED's snapshot isolation), pass the behavior explicitly: `db.transaction(fn, { behavior: "immediate" })`. The drizzle option is the second positional arg.
- Do NOT rely on `busy_timeout` to paper over this — it does not retry `SQLITE_BUSY_SNAPSHOT`. The pragma only helps with `SQLITE_BUSY`.
- The trap is dormant in single-writer tests and single-connection code. It activates the moment a second connection exists — and this codebase already has one (`readLastProjectId.ts`), with more likely as features add worker/utility-process DB access. Treat "another connection may write between my read lock and my first write" as the default assumption in WAL mode, not an edge case.
- Reserve DEFERRED for transactions that genuinely read first and must see a consistent snapshot across the read and write. EXCLUSIVE is rarely needed in WAL mode (it blocks other readers too).
- When auditing, grep for `db.transaction(` / `.transaction(` call sites that lack a second arg; each write-only one is a candidate.

## Applies when

- Adding or reviewing a `db.transaction(...)` / `tx.*` call against the shared SQLite store in `electron/services/` (ProjectStore, ScratchStore, TaskPersistence, or any new persistence service).
- Diagnosing intermittent `SQLITE_BUSY_SNAPSHOT` (or unexplained `SQLITE_BUSY`) errors on writes, especially ones that appear only with multiple windows open, on app launch (where `readLastProjectId.ts` reads early), or once a new worker/utility-process opens its own connection.
- Opening a new `better-sqlite3` / drizzle connection to `daintree.db` from any process or host (workspace-host, pty-host, a probe, a backup/checkpoint path) — this adds a parallel writer/reader and can trigger the snapshot upgrade failure on the shared connection.
- Writing tests for persistence: a passing single-connection test does NOT prove transaction-mode correctness; assert the `{ behavior: "immediate" }` arg is plumbed through (`vi.spyOn(db, "transaction")`) as the PR's tests do.
- Any work touching WAL pragmas (`journal_mode`, `busy_timeout`, `wal_checkpoint`) in `electron/services/persistence/db.ts`.
