## Context

The embedded MCP server exposes the Actions registry (~300 `ActionDefinition`s) to help-assistant model sessions. `tools/list` (handled in `electron/services/mcp-server/sessionServer.ts`) maps each tier-permitted manifest entry to an MCP tool, emitting `name` + `description` + full `inputSchema`/`outputSchema` per entry.

## Problem

Emitting all ~300 actions with full `inputSchema` produced roughly 200KB of schema text. Tool definitions are not a one-time discovery cost: the MCP/model protocol re-sends the active tool manifest as context on every turn, so the model re-pays the full ~200KB each call — directly inflating per-turn token spend and crowding the context window.

## Root cause

The naive assumption is that a tool list is paid once at session start. It isn't — the tool manifest is part of the per-turn request context, so an eager "expose everything" manifest multiplies its cost by the number of turns. With a large action registry this dominates context. The fix inverts the default from eager to lazy via a three-value `mcpVisibility` classification on `ActionDefinition`/`ActionManifestEntry` (`shared/types/actions.ts`):

- `core` — always on `tools/list`.
- `discoverable` — omitted from `tools/list`, reachable only via meta-tools.
- `hidden` — never surfaces in discovery at all. `shouldExposeTool` (`electron/services/mcp-server/tierAuth.ts`) early-returns `false` for `discoverable` and `hidden`, so the manifest ships only the ~8 `core` entries plus two meta-tools — `actions.search` (ranked keyword search returning lightweight entries WITHOUT inputSchema) and `actions.getSchema` (pulls one full schema by id on demand), both defined in `src/services/actions/definitions/introspectionActions.ts`. Result: ~6KB default manifest (97% cut) with no loss of reachable capability — the model discovers and pulls schemas lazily. Note `actions.search` strips `inputSchema`/`outputSchema` from results and skips `hidden` entries, and `actions.getSchema` returns a `{ ok: false, error: NOT_FOUND }` data object (not a thrown error) for unknown or hidden ids.

## Lesson

When exposing a large registry over MCP (or any protocol where the tool manifest rides along on every model turn), do NOT emit the full surface eagerly. Costs that look one-time (a tool list) are actually per-turn. Instead:

- Classify entries with an explicit visibility tier; default the manifest to a small curated `core` set.
- Provide search + get-schema meta-tools so anything outside core is reachable lazily, and make the meta-tool descriptions actively steer the model away from the heavy "list everything" tool (the `actions.list` description explicitly says "Do NOT use this for discovery — it returns every schema and is expensive").
- Search results must omit `inputSchema`/`outputSchema` (the bulk weight); only `getSchema` pays for the full schema, and only for the one action chosen.
- Keep visibility orthogonal to existing auth tiers — `mcpVisibility` gates the discovery surface; `shouldExposeTool`'s tier/`danger` checks still gate authorization. New actions default (undefined `mcpVisibility`) to the legacy eager behavior, so classify deliberately rather than relying on the default.

## Applies when

- Adding or changing any MCP-exposed action and deciding whether it should appear on `tools/list` (touching `mcpVisibility`, `introspectionActions.ts`, `tierAuth.ts`, or `sessionServer.ts`).
- Investigating high token/context cost in help-assistant or Codex/Claude MCP sessions, or context-window pressure that scales with conversation length rather than a single spike.
- Adding meta-tools (search/getSchema-style indirection) to expose a large or growing registry to a model without dumping every schema.
- Any feature where a manifest/capability list is re-sent to a model on each turn and someone assumes it's a one-time discovery cost.
- Auditing whether a new action leaks onto the default MCP surface because its `mcpVisibility` was left undefined.
