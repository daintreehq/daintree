## Context

#11028 turned the single-file diff modal into a multi-file review workspace and added image compare (Two-up/Swipe/Onion skin), which needed a new `diffMedia:readFileVersions` IPC channel (`electron/ipc/handlers/diffMedia.ts`) to serve working-tree image bytes to the renderer. Daintree already has a documented containment convention for renderer-supplied paths from #6263 (`electron/ipc/handlers/files.ts`, lesson `.lessons/6263.md`): realpath both root and target, prefix-contain, then `open()` with `O_NOFOLLOW` so a symlink swapped into the final path component after the check loses with `ELOOP`. `diffMedia.ts`'s `readWorkingSide` explicitly says in its own comment "Same containment discipline as files:read."

## Problem

Despite claiming parity with the established pattern, `readWorkingSide` does two things `files.ts`'s `handleRead` does not: it opens with `O_NONBLOCK` in addition to `O_NOFOLLOW`, and after the open succeeds it re-stats the **file descriptor** (`fileHandle.stat()`) and rejects anything that is no longer `isFile()`. Neither addition is explained by the symlink threat #6263 already closes — `O_NOFOLLOW` already handles a symlink swap. They exist for a different substitution: a regular file swapped for a **FIFO** in the window between the pre-open `fs.stat(realFile)` check and the `fs.open()` call. A FIFO isn't a symlink, so `O_NOFOLLOW` does nothing to stop the open from succeeding on it.

## Root cause

Opening a FIFO for read in blocking mode (no `O_NONBLOCK`) stalls the `open()` call itself until some process opens the other end for writing — POSIX open-on-FIFO semantics, not a read-time hang. If nothing ever writes to that FIFO, the `open()` promise never resolves, and the whole IPC handler call hangs forever with no error surfaced to the renderer. `readWorkingSide` closes this in two moves: `O_NONBLOCK` (a no-op on Windows, real on POSIX) makes a read-only open of a FIFO return immediately instead of blocking, and the subsequent `fileHandle.stat()` re-checks the **fd**, which is authoritative for what was actually opened — the earlier `fs.stat(realFile)` was a path-level check that is stale the instant a substitution happens after it runs. `files.ts`'s `handleRead` has none of this: it stats `realFile`, then opens `filePath` with only `O_RDONLY | O_NOFOLLOW`, then calls `fileHandle.readFile()` directly with no post-open type re-check — so the exact same FIFO-swap window is still open in `files:read` today, verified by reading the current source (no `O_NONBLOCK`, no fd-level stat in `electron/ipc/handlers/files.ts`). `diffMedia.ts` is the more hardened of the two siblings, not an equal restatement of #6263.

## Lesson

- **`O_NOFOLLOW` blocks symlink swaps, not type swaps.** A regular file replaced by a FIFO (or other special file) between your pre-open `stat()` and your `open()` isn't a symlink, so `O_NOFOLLOW` is silent on it — and without `O_NONBLOCK`, opening a FIFO for read blocks the `open()` call itself until a writer attaches, hanging that handler's promise indefinitely with no error.
- **Re-verify on the fd you actually got, not the path you asked for.** A path-level `fs.stat()` before `open()` is stale the moment something changes after it runs; only a post-open `fileHandle.stat()` tells you what you're really holding. Add `O_NONBLOCK` so a FIFO returns immediately instead of hanging, then reject anything the fd-stat says isn't `isFile()`.
- **"Same containment discipline as X" is a claim to verify, not a fact to inherit.** `diffMedia.ts`'s own comment asserts parity with `files:read`, but it actually added two hardening steps `files.ts` lacks. When you see that comment pattern, diff the two handlers side by side before trusting it — the two have already drifted once.
- **`electron/ipc/handlers/files.ts`'s `handleRead` still has this exact gap** (confirmed in the current source: `fs.open(filePath, O_RDONLY | O_NOFOLLOW)` with no `O_NONBLOCK` and no fd-level stat before `readFile()`). Next time you touch it, backport `O_NONBLOCK` + post-open `fdStat` from `diffMedia.ts` rather than assuming the older, more-referenced handler is the more complete one.
- **A two-stage check-then-open flow always has a TOCTOU gap between the two syscalls**; adding a flag like `O_NOFOLLOW` narrows _which_ substitution class is blocked, it does not narrow the _time window_. Close the window with a post-open re-check on the fd, for whatever invariant you actually care about (regular-file-ness, size, owner).

## Applies when

- Adding or auditing any IPC handler that opens a renderer- or agent-supplied filesystem path after a containment check (`files:read`, `diffMedia:readFileVersions`, or any future diff/media/preview channel).
- Touching `electron/ipc/handlers/files.ts`'s `handleRead` — it is the sibling missing this hardening; treat `diffMedia.ts`'s `readWorkingSide` as the reference implementation to backport from, not the other way round.
- Reviewing a path-security fix whose comment claims parity with an existing pattern (`files:read`, `electron/setup/protocols.ts` containment from #6442/#9492) — verify the two implementations line up rather than trusting the comment.
- Diagnosing an IPC file-read call that hangs indefinitely instead of erroring or timing out, especially over a working tree where build tooling or another process could plausibly emit a FIFO or socket at a path Daintree expects to be a regular file.
- Writing any stat-then-open flow anywhere in the codebase (not just file-serving IPC) that assumes `O_NOFOLLOW` alone closes the TOCTOU window between the check and the open.
