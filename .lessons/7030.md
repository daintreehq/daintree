## Context

`IpcQueueManager` and `PortQueueManager` (`electron/pty-host/`) each track per-terminal byte accounting (`queuedBytes`) and a `pausedTerminals` map of safety-timeout handles. When the queue crosses the high watermark they pause the PTY by taking a named hold on the shared `PtyPauseCoordinator` (`"ipc-queue"` / `"port-queue"` or a per-window `pauseToken` like `"port-queue-7"`). Resume happens three ways: ack-driven `tryResume`, the safety-timeout force-resume, and `clearQueue` (called by `disconnectWindow`, terminal exit, and the `force-resume` IPC handler).

## Problem

Two latent wedges in the same family. (1) The IPC-path safety-timeout closure deleted the pause maps but left `queuedBytes` intact, so after a force-resume the very next `addBytes` re-painted the queue above the high watermark and `applyBackpressure` immediately re-paused — the pause loop could span an entire renderer reload. (2) `clearQueue` cleared its own internal maps but never called `coordinator.resume(token)`; it only worked because every existing caller happened to release the coordinator separately (`resumeAll()` / `forceReleaseAll()`). Separately, the `force-resume` handler cleared only `ipcQueueManager` state and never iterated `rendererConnections`, leaking stale `pausedTerminals` entries in per-window port managers whose safety timeouts later fired and emitted spurious `pause-end` reliability metrics.

## Root cause

A force-resume that drops the pause maps but keeps the byte accounting is **self-undoing**: the coordinator hold is released, but the stale `queuedBytes` total re-triggers `applyBackpressure` on the next byte arrival. Byte accounting and pause state are two halves of the same invariant and must be cleared together. The `clearQueue` token leak is a fragility trap: a method that owns a coordinator hold worked "by accident" because the only two callers released the token through a different path — any new caller (here, the force-resume cleanup) inherits a wedged coordinator with no recovery. The multi-window leak comes from `force-resume` bypassing the `disconnectWindow` lifecycle that normally drains each per-window `portQueueManager`.

## Lesson

- Treat `queuedBytes` (byte accounting) and `pausedTerminals` (pause state) as one invariant. Any path that force-resumes or clears must drop **both** — and also fix the aggregate (`totalQueuedBytes -= removed`). Capture utilization for the reliability metric BEFORE clearing bytes, or the metric reports 0%.
- A manager method that owns a `PtyPauseCoordinator` hold must **self-release its own token** when it tears down internal state — never rely on callers to release it separately. `PtyPauseCoordinator.resume(token)` is a no-op for an unheld token, so self-release is always safe; guard on `wasPaused` only to skip a useless coordinator lookup. Release the token BEFORE clearing the internal maps so any re-entrant `applyBackpressure` sees clean state.
- Use the manager's stored `this.pauseToken` for release, never a hardcoded literal — per-window managers hold distinct tokens (`"port-queue-7"`).
- When adding a force-resume / reset path that bypasses the normal `disconnectWindow` lifecycle, fan out over `ctx.rendererConnections.values()` and call `clearQueue` on every per-window `portQueueManager` (no-op when the terminal isn't tracked), not just the single IPC manager.

## Applies when

- Editing `clearQueue`, `tryResume`, `dispose`, or the safety-timeout closure in `electron/pty-host/ipcQueue.ts` or `electron/pty-host/portQueue.ts`.
- Adding any new path that force-resumes a PTY or resets backpressure state (renderer reload, view eviction, the `force-resume` handler in `electron/pty-host/handlers/backpressure.ts`).
- Symptoms: a terminal re-pauses immediately after a force-resume; a PTY stays wedged/paused after window disconnect or reload; spurious `pause-end` reliability metrics firing seconds after a terminal resumed normally.
- Any code that takes a named `PtyPauseCoordinator` hold (`"ipc-queue"`, `"port-queue"`, per-window `pauseToken`) and later tears down its own state — verify it self-releases the token rather than depending on a sibling caller.
- Multi-window pty-host work where per-window state lives in `rendererConnections` and a cleanup path must touch every window.
