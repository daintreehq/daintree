## Context

The multi-window project-view swap (`projectview.warm-swap`) tears down and re-attaches `TerminalPane` instances. Each pane writes visibility to two places in parallel from its `IntersectionObserver` callback: the Zustand `panelStore` via `updateVisibility(id, isVisible)`, and `terminalInstanceService.setVisible(id, isVisible, gen)`. `getTerminalRefreshTier` (`panelStore.ts`) derives a render-throttle tier (`FOCUSED`/`VISIBLE`/`BACKGROUND`) from `panelStore.isVisible` + `agentState`; `TerminalReconciliationWatchdog` sweeps every ~6s to repair any terminal whose applied renderer tier diverges from its computed tier.

## Problem

After switching back to a project, on-screen agent terminals rendered stale until each was clicked. The watchdog log showed it "repairing" the same terminal every ~6s — 296 times over 35 minutes (#10416) — while never converging: `computedTier: BACKGROUND (1000)`, `appliedTier: VISIBLE (200)`, and the repair just re-applied `VISIBLE`. The build already had the wake-fanout fix (#10362), so timing was a red herring — the real fault: the repair couldn't converge because the divergence lived somewhere the watchdog never wrote.

## Root cause

Two defects compounded.

1. Write-path asymmetry. `setVisible(id, isVisible, gen)` was attach-generation guarded; the parallel `updateVisibility(id, ...)` was not — and the unmount cleanup `useEffect(() => () => updateVisibility(id, false), ...)` fired from the PREVIOUS mount site after the replacement pane re-attached during the warm swap (generation advanced). The service dropped the stale write via its guard; the store accepted it, pinning `panelStore.isVisible = false` while DOM and service both said visible. `getTerminalRefreshTier` returns `BACKGROUND` whenever `isVisible === false` (`panelStore.ts:160`), so the computed tier stuck at `BACKGROUND` for an on-screen terminal.

2. Non-converging reconciler. The repair only called `applyRendererPolicy(id, tier)` — it re-applied the renderer tier but never wrote the store where the divergence lived. Its own comment conceded "a misclassified computed tier can't be corrected here (it lives in the panel store)." So it floored to `VISIBLE`, stamped the cooldown, and re-detected the identical divergence next tick, forever. It also fought policy: completed/exited and PTY-less panels compute `BACKGROUND` by design, which the watchdog treated as divergence too.

## Lesson

- **When two writes must stay consistent, they need the SAME guard.** The service write carried the attach-generation check; the store write didn't — that asymmetry let a stale warm-swap callback poison one side into a permanent split. The fix guards both: the IO callback early-returns `if (getAttachGeneration(id) !== gen) return;` before EITHER write, and the unmount cleanup moved into `useUnmountVisibilityCleanup`, which captures `gen` at mount and skips if it advanced. Adding a generation/epoch guard to one of a pair of parallel writes? Audit the other.
- **A reconciler that repairs the symptom instead of the divergent source loops forever.** The watchdog re-applied the renderer tier while the poison sat in `panelStore.isVisible`, so it re-repaired every tick (296×/35min). The fix gave it `repairStoreVisibility(id)` (`usePanelStore.getState().updateVisibility(id, true)`) to correct the store at the source, then re-derives via `getRefreshTier`. A repair path must be able to write every state it reads as divergent, or it can't converge.
- **A reconciler must model intentional states or it fights policy.** Completed/exited/PTY-less panels compute `BACKGROUND` by design. The discriminator is DOM vs store: `isStoreHidden(id)` (`panelsById[id]?.isVisible === false`) separates a stale-write bug (store hidden while DOM+service say visible → repair) from policy (store intact → `if (computedTier === BACKGROUND && !storeHidden) return 0`, skip). Before repairing "divergence," prove it isn't a state set on purpose.
- **Re-capture the generation on restart, not just at mount.** `useUnmountVisibilityCleanup(id, restartKey, updateVisibility)` lists `restartKey` in deps: a restart re-attaches under a new generation, and without re-capturing, the final REAL unmount looks like a stale cleanup and is skipped — leaving the panel wrongly marked visible. An epoch-keyed guard must refresh the epoch whenever the thing it protects legitimately re-attaches. Failed repairs still stamp `lastWatchdogRepairAt` and honor the cooldown, so an unconverged store retries slowly, not per-tick.

## Applies when

- Touching `TerminalPane.tsx` visibility writes, `useUnmountVisibilityCleanup`, or any pane teardown across `projectview.warm-swap` / restart — a prior mount's cleanup can fire after the replacement re-attached, so guard it on the attach generation.
- Adding or auditing an attach-generation / epoch guard on one of a pair of parallel writes, where a stale write poisoning one side alone produces a permanent divergence.
- Working on `TerminalReconciliationWatchdog` or any interval-driven reconciler that "repairs" divergence — verify the repair writes the actual divergent source, and that policy states (`BACKGROUND` for completed agents) are modeled and skipped, not fought every tick.
- Diagnosing an on-screen terminal stuck rendering stale until clicked, or watchdog logs repeating "on-screen terminal at BACKGROUND tier — repairing" for the same id every ~6s — the computed tier is pinned by `panelStore.isVisible === false` (`panelStore.ts:160`).
