## Context

`WorktreeMonitor` (utility-process workspace-host) drives the worktree git-status pipeline. Since the recursive `gitFileWatcher` (WatcherController) catches every working-tree/HEAD/refs/index change, the polling timers were demoted to a belt-and-braces heartbeat for OS suspend/wake recovery and watcher-ghost detection. PR #6785 relaxed three base intervals: `WATCHER_FALLBACK_POLL_INTERVAL_MS` 30s→300s, `WATCHER_GIT_ONLY_ACTIVE_POLL_INTERVAL_MS` 10s→60s, `RESOURCE_POLL_DEFAULT_BACKGROUND_MS` 120s→300s.

## Problem

Two pieces of code silently depended on the _magnitude_ and the _specific value_ of those base constants. Raising the constants would have (1) blown out stale-detection latency from ~90s to ~15min, and (2) silently reverted an explicitly-configured `statusInterval: 300` recipe back to the 30s active default on every focus change.

## Root cause

- **Uncapped multiplicative derived threshold.** The heartbeat-gap stale check computed `threshold = Math.max(delayMs * HEARTBEAT_GAP_MULTIPLIER, HEARTBEAT_GAP_FLOOR_MS)` (multiplier = 3). The threshold was _derived_ from the base interval with no ceiling, so bumping the base to 300s ballooned the raw threshold to 900s — suspend/wake detection silently degrades from ~90s to ~15min. Fix: clamp with `Math.min(Math.max(delayMs * MULTIPLIER, FLOOR), HEARTBEAT_GAP_CEILING_MS)` where `HEARTBEAT_GAP_CEILING_MS = 360_000` (`WorktreeMonitor.ts:45,1306-1311`). The ceiling sits just above the largest base (300s) so a normal quiet-repo heartbeat fire doesn't false-positive stale, but bounds detection latency to ~60s of drift past the expected fire.
- **Value-equality default sentinel.** The `isCurrent` focus-flip setter only auto-adapted the resource poll cadence "if using defaults", detecting that via `resourcePollIntervalMs === RESOURCE_POLL_DEFAULT_ACTIVE_MS || === RESOURCE_POLL_DEFAULT_BACKGROUND_MS`. Once the background default became 300s, an explicit `statusInterval: 300` from a recipe was _indistinguishable from a default_ and got silently overwritten to 30s on focus change. Fix: a dedicated `resourcePollIntervalExplicit` boolean set by `setResourcePollInterval()`, gating the auto-adapt with `if (!this.resourcePollIntervalExplicit)` (`WorktreeMonitor.ts:240,540,817`).

## Lesson

- A derived threshold computed as `base * k` is an implicit dependency on the base's magnitude. When the base is a tunable interval, **clamp the derived value with an explicit floor AND ceiling** — otherwise a routine perf bump silently degrades the behavior the threshold protects (here, suspend/wake stale detection).
- **Never use value-equality against a default constant as an "is-this-a-default?" sentinel.** The moment a user/config value can legally equal a default (and raising a default makes more values collide), the comparison misfires. Track provenance explicitly with a boolean flag (`*Explicit`) set at the configuration entry point, not by comparing the value to the default.
- When raising any base interval/threshold constant, grep for every site that multiplies it or compares against it; both classes of dependent are invisible at the constant's definition.

## Applies when

- Tuning poll/heartbeat/fetch cadence constants in `electron/workspace-host/` (`WorktreeMonitor.ts`, `WatcherController.ts`): `WATCHER_FALLBACK_POLL_INTERVAL_MS`, `WATCHER_GIT_ONLY_ACTIVE_POLL_INTERVAL_MS`, `RESOURCE_POLL_DEFAULT_*_MS`, or any `HEARTBEAT_GAP_*`.
- Touching the stale-mood / suspend-wake heartbeat path or the `isCurrent` focus-flip auto-adapt logic in `WorktreeMonitor`.
- Anywhere a threshold is computed as `interval * multiplier` (debounce, retry backoff, timeout, staleness) and the interval is configurable — add a ceiling clamp.
- Anywhere code distinguishes "user-supplied value" from "default" by comparing to the default constant — replace with an explicit-set flag, especially before changing the default's value.
- Recipe/config `statusInterval` handling and any flow where a config value can coincidentally equal a runtime default constant.
