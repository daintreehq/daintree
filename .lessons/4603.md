## Context

Next.js 15 dev servers started in webpack mode (the default in v15) produce blank or completely unstyled pages when loaded inside Daintree's Electron webview. The pages appear to load but render without CSS — or are entirely blank due to Next.js's FOUC prevention (`body{display:none}`) never being cleared.

## Problem

Next.js webpack mode uses `style-loader` to inject CSS via JavaScript at runtime. `style-loader` works by creating `<style>` tags via DOM manipulation. This mechanism fails silently inside Electron webviews — the CSS injection call returns without error but the styles are never applied, leaving the page visually broken.

## Root cause

webpack's `style-loader` uses `document.head.appendChild` to inject styles, which appears to succeed inside the webview but the styles don't take effect. This is a known incompatibility between webpack's runtime CSS injection and Electron's webview security model.

The fix: `--turbopack` switches Next.js to Turbopack, which uses a different (compatible) CSS delivery mechanism that works correctly inside Electron webviews.

## Lesson

When a Next.js dev server shows blank/unstyled pages in Daintree's webview but works fine in a regular browser, the cause is almost certainly webpack's `style-loader` CSS injection failure, and the fix is to run `next dev --turbopack` instead of `next dev`.

The injection is NOT unconditional — an early "always inject" version backfired on Next.js 14, where `next dev --turbopack` was not stable and the appended flag broke the dev server. Two gates now guard it (both in `normalizeNextjsDevCommand`, `electron/services/DevPreviewCommandNormalizer.ts`):

1. **Next major version >= 15** via `resolveNextMajorVersion(cwd)` (`electron/utils/resolveNextVersion.ts`, which reads `node_modules/next/package.json` then falls back to the `package.json` dep spec). Versions below 15 (or unresolvable) get `stripTurbopackFlag` instead of injection.
2. **User `turbopackEnabled` toggle** (default `true`; persisted on the session in `DevPreviewSessionService`, type in `shared/types/project.ts`). When off, the flag is stripped rather than added.

The normalizer lives in `DevPreviewCommandNormalizer.ts`; `DevPreviewSessionService.ts` only re-exports `normalizeNextjsDevCommand` and calls it at runtime with `session.turbopackEnabled`. The upfront, UI-display enhancement lives separately in `findDevServerCandidate` / `findAllDevServerCandidates` (`src/utils/devServerDetection.ts`, renderer side via `applyNextjsTurbopack`) — note this renderer path gates only on `turbopackEnabled`, not the version, since it has no `cwd`/`node_modules` access.

Injection is idempotent (`TURBOPACK_FLAG_RE` checks for an existing `--turbo`/`--turbopack` flag before adding) and skips compound/piped/commented commands (`SHELL_CONTROL_RE`). Package-manager separator matters: npm/pnpm/yarn forward the flag through `run <script>` via `-- --turbopack`, while bun forwards extra args with a plain space (`bun ... --turbopack`); direct `next dev` invocations take the flag inline.

## Applies when

- Any Next.js project with blank/unstyled integrated browser rendering
- Adding support for other frameworks that use webpack runtime CSS injection — may need similar treatment
- Writing dev server detection logic: normalize commands at both detection time (`devServerDetection.ts`) and runtime (`DevPreviewCommandNormalizer.ts`), and gate framework-specific flag injection on the framework version when a flag is only stable past a certain release
