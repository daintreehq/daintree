## Context

`ActionBreadcrumbService` (`electron/services/ActionBreadcrumbService.ts`) keeps a fixed `MAX_RING = 50` ring of recent action dispatches in the main process. It feeds Sentry breadcrumbs and the `recentActions` field on crash log entries, and lives in main precisely so the ring survives a renderer crash — the moment its data is most needed. Each entry now carries a `danger: ActionDanger` tier (`"safe" | "confirm" | "restricted"`) that flows end-to-end from `ActionService.dispatch` through the `action:dispatched` event and `events.ts` normalization into the ring.

## Problem

The ring was single-tier FIFO (`this.ring.shift()` on overflow). Chatty low-signal actions — e.g. `terminal.list` repeating during a heavy MCP session at intervals wider than the 250ms `DEDUP_WINDOW_MS` — would fill the ring and push out the exact high-value forensic entries (a `danger:"confirm"` outcome like `worktree.delete`, an error) before a crash log captured them. The buffer looked perfectly correct under normal steady load; the defect only manifests during the burst of activity that _precedes_ a crash, which is precisely when the displaced entries are the ones you need.

## Root cause

A FIFO ring treats all entries as interchangeable by recency. For a forensic buffer that assumption is inverted: the value of an entry is its signal (tier), not its age. Dedup did not save it either — Sentry's own SDK only dedupes the _immediately preceding_ breadcrumb, and Daintree's dedup window is 250ms, so a chatty action firing slightly slower than that defeats dedup entirely and each repeat consumes a fresh slot. The fix (`evictOne(incomingDanger)`) makes eviction priority-aware without touching ring size or dedup: scan from newest for a strictly-lower-priority entry and evict that; if every existing entry outranks the incoming one, _drop the incoming entry_ rather than admit it; in a mixed ring evict the newest _same-tier_ entry so a higher tier is never displaced; only fall back to plain FIFO when all entries share the incoming tier. Evicting the _newest_ low-priority entry (not oldest) deliberately preserves older forensic context.

## Lesson

- A bounded buffer whose purpose is post-mortem diagnosis must rank-evict by signal value, not FIFO by age. FIFO is correct only when every entry is equally valuable.
- The failure mode of such a buffer is invisible under steady load and only appears in the burst before the event you're trying to diagnose — do not trust "looks fine in normal operation" for forensic data structures.
- When the incoming entry is lower priority than everything already retained, _refuse admission_ — admitting it and evicting something else would lose signal. Don't assume the newest write always belongs in the buffer.
- Propagate the priority/tier all the way to the eviction site. Here `danger` had to be threaded through `ActionService` → `action:dispatched` event (`electron/services/events.ts`) → `normalizeActionDispatchedPayload` in `electron/ipc/handlers/events.ts` (which defaults unknown/invalid `danger` to `"safe"`) → the ring. A priority policy is useless if the priority isn't carried with the data.
- Don't reach for ring resizing or smarter dedup first; the eviction _policy_ is the lever. Size and dedup stayed unchanged here.

## Applies when

- Touching `ActionBreadcrumbService`, `TelemetryService.addActionBreadcrumb`, crash-log `recentActions`, or Sentry breadcrumb wiring.
- Adding or changing any bounded/ring/LRU buffer that retains diagnostic, audit, telemetry, or forensic data destined for a crash log, error report, or post-incident review.
- Threading a new field (priority, tier, severity) from `ActionService` dispatch through the `action:dispatched` event and `normalizeActionDispatchedPayload` into main-process consumers.
- Reasoning about whether the _newest_ write should always be admitted to a fixed-capacity buffer, or about eviction order in any capacity-limited cache holding non-fungible entries.
- Investigating why a crash report is missing the high-signal action (a `danger:"confirm"` outcome, an error) that immediately preceded the failure while showing many repeated low-signal entries.
