## Context

`PullRequestService` (workspace-host) polls the forge for PRs per worktree branch: `checkForPRs` → `resolvePRsForBranches` → `prByBranchLoader` (a `BatchLoader` coalescing into `findPRsByBranches`, with per-branch `findPRByBranch` fallback for keys the batch map omits). Results drive `sys:pr:detected` / `sys:pr:cleared`, which `WorkspaceService` applies to `WorktreeMonitor` and the renderer renders as dashboard PR rows. The service carries a full error apparatus: `consecutiveErrors`, a 3-error circuit breaker, `computeBackoff` exponential backoff, `sys:pr:detection-state` → `PRDetectionPausedIndicator`, and a rate-limit gate (`checkRateLimitGate`). The forge-bridge migration #8879 moved all provider calls behind `ForgeBridge` RPC.

## Problem

After #8879, a single 30s bridge timeout, network blip, or mid-cycle 429 silently wiped valid PR rows from the worktree dashboard, and during a total outage the service kept polling at full cadence with zero user-visible signal — the breaker never tripped, backoff never engaged, `sys:pr:detection-state` never fired (#9994). The misleading part: the code _looked_ defended — breaker, backoff, detection-state indicator, rate-limit gate all existed and reviewed as healthy. They were all dead code from the polling path.

## Root cause

One error-swallow at the wrong layer produced a compound failure. The per-branch fallback in `createLoaders` was `bridge.findPRByBranch(...).catch(() => null)`, and `resolvePRsForBranches` additionally mapped loader rejections to `{ branch, pr: null }`. But `checkForPRs` treats `pr === null` as _authoritative_ "no PR" — required, because without an explicit clear, `WorktreeMonitor._linked` stays `undefined` and the renderer's preservation rule (#8870) holds stale rows forever. So a transient rejection became a confirmed absence: `sys:pr:cleared` → `clearPRInfo()` + `clearLinked()` → row gone. A mid-cycle rate-limit block was the mass-wipe case: `findPRsByBranchesImpl` returns an empty map while blocked, so _every_ branch fell to the per-branch fallback, every fallback rejected under `rateLimitAwareFetch`, and every rejection became a clear — the pre-cycle `checkRateLimitGate` only covers blocks that existed at cycle start.

The second half is the disarming: because every failure source was absorbed _inside_ the loader, no error could escape to `checkForPRs`'s catch, so `handleError` was unreachable from polling — `consecutiveErrors` never incremented, and the entire breaker/backoff/detection-state apparatus downstream of it could never engage. The machinery wasn't broken; it was unreferenced. Note also that typed errors don't survive the bridge (`forgeBridge.ts` rejects with `new Error(result.error)` — a flattened string), so rate-limit attribution can't come from inspecting the error; it must come from re-consulting `getRateLimit`. The fix (#10173, all in `PullRequestService.ts`): the fallback surfaces rejections as per-key `Error`s using `BatchLoader`'s slot contract (`BatchLoadFn` must always resolve; an `Error` in a slot rejects just that key — `electron/workspace-host/batchLoader.ts`); `resolvePRsForBranches` returns `{ branch, pr, error }` tuples, absorbing only the `"BatchLoader disposed"` rejection (a mid-cycle provider swap, not a lookup failure — the stale-provider guard discards that whole cycle anyway); `checkForPRs` skips errored branches (rows survive; the loader evicts settled keys so next cycle retries fresh) and routes failures to `handleError` once per cycle — per cycle, not per branch, so a 20-branch repo doesn't trip the 3-error breaker in one sweep — after re-consulting `checkRateLimitGate` so a mid-cycle 429 pauses via the rate-limit path (which clears the streak) instead of counting toward the breaker.

## Lesson

- **A `.catch(() => null)` upstream of a consumer that takes destructive action on "absent" is a destructive false-negative generator.** Preserve the transient-vs-not-found distinction per key: resolved `null` = confirmed absence (may clear state), `Error` = unknown (skip, keep existing state, retry next cycle). `prByNumberLoader` already had this contract; the branch path was the outlier.
- **Error-swallowing at the innermost layer disarms every outer layer.** If a service has breaker/backoff/indicator machinery, prove a live path exists from each actual failure source to it — after #8879 moved I/O behind the bridge, all failure sources were absorbed pre-`handleError` and the whole apparatus reviewed as present but was unreachable. Grep for who _calls_ `handleError`, not whether it exists.
- **`BatchLoader`'s per-key rejection contract is the tool for this:** the batch function must always resolve; return an `Error` object in a slot to reject only that key. Distinguish infrastructural rejections (`"BatchLoader disposed"` from `invalidateProvider()`) from lookup failures — the former must not count toward any breaker.
- **Aggregate failures per cycle before routing to the breaker** so breaker cadence isn't topology-dependent (`branchErrorCount` + `firstBranchError`, one `handleError` call after the loop), and **re-check the rate-limit gate at failure-attribution time** — typed errors flatten to strings crossing the forge bridge, so the 429 signal must come from `getRateLimit`, and blind retry through GitHub secondary limits risks escalation to a ban.
- **Scope the success-reset to cycles that did the guarded work:** only `prResults.length > 0` clears `consecutiveErrors` — an issue-title-only cycle must not erase a real PR-lookup error streak. Symmetrically, confirmed clears must delete the `detectedPRs` entry, else a stale pending-CI entry keeps the 30s revalidation boost armed indefinitely.

## Applies when

- Touching `PullRequestService` loaders (`prByBranchLoader`, `resolvePRsForBranches`, `checkForPRs`, `checkRateLimitGate`) or writing any `BatchLoader` batch function with a per-key fallback.
- Writing `.catch(() => null)` / `.catch(() => {})` anywhere the null/empty result feeds a consumer that emits clears, deletes rows, or evicts cache entries — especially forge/polling paths where `null` means authoritative absence.
- Diagnosing PR rows vanishing from the worktree dashboard, or a forge outage producing no breaker trip / no backoff / no `PRDetectionPausedIndicator` despite the machinery existing.
- Reviewing any refactor that moves I/O behind a bridge or RPC layer (errors flatten to `Error(string)` crossing `forgeBridge`) — verify the error apparatus is still _reachable_ and that typed-error attribution (rate limits) has a side channel.
- Adding a forge provider whose batch API omits keys while blocked (empty map under rate limit) and relies on per-key fallbacks to fill gaps.
