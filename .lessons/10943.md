## Context

`useFileAutocomplete` backs the `@file` provider in the hybrid input bar's autocomplete menu (`AutocompleteMenu.tsx`, wired through `HybridInputBar.tsx` and `useEditorKeymap.ts`). File search runs against a per-pane `cwd` (each terminal pane can point at a different git worktree) and is debounced, so the visible `files` array can lag behind what the user has actually typed by a full debounce window plus IPC round-trip.

## Problem

Typing fast and hitting Enter or Tab immediately could accept a match from the previous query — the menu still showed the old top result because the new search hadn't resolved yet. Separately, an in-flight search could resolve after the user had already switched panes (a different `cwd`/worktree) and silently repopulate the menu with results that happened to share the same query text but belonged to the wrong directory.

## Root cause

The hook already had a `requestIdRef` counter to reject out-of-order network responses — that guard is necessary but not sufficient. It only protects against a _slower_ older request clobbering a _newer_ one; it does nothing about the window where the newest request hasn't even fired yet because it's still sitting in the debounce timer. During that window the displayed `files` are unambiguously stale relative to the live input, yet no race has occurred, so `requestIdRef` sees nothing wrong. Staleness-vs-live-input and ordering-of-network-responses are two different invariants and need two different mechanisms.

The fix stamps every result set with the `{ cwd, query }` that produced it (`resultsFor` state in `useFileAutocomplete`) and derives `resultsQuery` by additionally checking `resultsFor.cwd === cwd` — results from a different cwd are `null` (never current), independent of whether the query text matches. This is the non-obvious part: the same literal text searched in two different worktrees is not the same query, because it answers a different question. A dedup keyed on query text alone would let a pane that just switched worktrees briefly show the old worktree's file list under the new worktree's identical-looking query. `HybridInputBar.tsx` derives `isFileStale = isFileMode && fileResultsQuery !== fileQuery` and builds a `staleItemKeys` set consumed by `useEditorKeymap.ts`: Enter falls through to sending the literal typed text (never silently accepts a stale top match), Tab is swallowed as a no-op, and `AutocompleteMenu.tsx` dims stale rows via `isRowStale` / `aria-disabled`.

The staleness plumbing was later generalized in #11043 from a single boolean `isResultsStale` to the per-item `staleItemKeys: ReadonlySet<string>` in the current `useEditorKeymap.ts`, because only the debounced async `@file` provider can go stale — a synchronous `@diff` list or the `$` picker never can, so a global flag would have wrongly dimmed non-file modes once more providers arrived. The `resultsQuery`/cwd-stamp mechanism from #10943 is unchanged and is what this lesson documents.

## Lesson

- **A request-id/monotonic-counter guard prevents out-of-order writes but does not prevent stale-but-in-order reads.** If a value is debounced before it's ever raced, you need a second check: stamp the result with the input that produced it, and compare that stamp against the _current_ input at the point of consumption (Enter/Tab), not just at the point of write.
- **Scope identity, not just query text, when the same async hook can be reused across contexts.** Here the context is `cwd` (a terminal pane's worktree); tag results with the full identity tuple (`{ cwd, query }`) and invalidate on any component changing, not just the query. The same pattern applies to any per-pane/per-project debounced fetch (git status, forge counts, branch lists) where switching the pane's target mid-flight is possible.
- **Disabling/closing must also bump the race guard.** `useFileAutocomplete`'s effect increments `requestIdRef.current` and clears `resultsFor` when `!enabled || !cwd`, so a search that was in flight when the menu closed can't repopulate it later — this is the same mechanism as the cwd check, applied to the "closed" case.
- **Give Enter and Tab different stale-fallback behavior, not a shared disable.** Enter has a safe fallback (send the literal typed text) so it should fall through; Tab has no literal-send equivalent, so on stale it must be swallowed entirely (`return true` with no action) rather than left to do its default (which would move focus out of the editor).
- **A single boolean staleness flag doesn't survive adding a second async provider.** #10943 shipped `isResultsStale: boolean`; #11043 had to widen it to `staleItemKeys: ReadonlySet<string>` once the `$` picker was added, because staleness is a property of the specific provider's result set, not of the input bar as a whole. If you're adding a new autocomplete mode, check whether it needs its own staleness key before reusing a boolean.

## Applies when

- Adding or modifying any debounced-then-async data source feeding a UI list where the user can act (Enter/Tab/click) on the currently-rendered items — autocomplete, search-as-you-type, live filters.
- Touching `useFileAutocomplete.ts`, `useEditorKeymap.ts`, `AutocompleteMenu.tsx`, or `HybridInputBar.tsx` completion providers, or adding a new completion source (`AgentConfig.completionSources`).
- A per-pane or per-worktree async hook that can be reused across different `cwd`/project contexts within the same component instance — check whether results are tagged with full context identity or just the query.
- Diagnosing "autocomplete accepted the wrong file" or "menu briefly showed the old worktree's results after switching panes" — the mechanism to check is whether the consuming hook compares a result stamp against live input, not just whether it has a request-id guard.
- Reviewing any accept-on-Enter / apply-on-Tab flow driven by async data — verify staleness is checked at the moment of acceptance, not only inside the fetch effect.
