## Context

The theme engine (`createDaintreeTokens` in `shared/theme/themes.ts`) derives semantic tokens from a small palette; before #9720 only `status-danger-surface` existed as a pre-derived wash, and components needing tinted success/info/warning backgrounds rolled their own with Tailwind arbitrary values like `bg-[color-mix(in_oklab,var(--color-status-success)_14%,transparent)]`. Issue #9708 ("light mode looks undesigned") named `GridNotificationBar` as concretely the wrong color on light themes. #9720 completed the `status-{success,warning,info}-surface` family, added the `borderInkOverride` / `statusSurfaceOpacity` `ThemeStrategy` knobs, and rewired `GridNotificationBar` onto the pre-baked tokens.

## Problem

`GridNotificationBar`'s status banners rendered dark and muddy on light themes — a gray-green smear instead of a light green tint — while looking fine on every dark theme. Daintree is developed dark-first, and `color-mix(..., transparent)` reads as the idiomatic alpha wash, so the pattern had shipped unnoticed. Nothing about the CSS looks wrong; the failure is entirely in how Chromium resolves it.

## Root cause

The `transparent` keyword is transparent **black** (`rgba(0,0,0,0)`). Spec-correct premultiplied interpolation would make `color-mix(in oklab, C 14%, transparent)` a pure alpha fade of C, but Chromium's oklab pipeline (observed on Chromium 146, our Electron at the time; guard still enforced on 148) drags lightness toward black — you get a darkened C at low alpha. Over a dark surface a black-shifted wash is indistinguishable from the correct one, so the bug is invisible in dark-first development; over a light surface the darkening dominates the tint and the wash reads gray. The fix derives the wash arithmetically: `withAlpha(hex, alpha)` emits `rgba(r, g, b, a)` from the hex status color, baked into `status-*-surface` at token-compile time (`dark ? 0.1 : 0.08`, scaled by `statusSurfaceOpacity`), and components consume `bg-status-*-surface`.

Pre-baking has a systemic cost the PR paid in two other places: a usage-site `color-mix(var(--theme-status-danger)…)` retints automatically when anything patches the base variable, but a pre-baked `rgba()` literal does not. So CVD mode (`colorVisionOverrides.ts`) wraps its maps in `withStatusSurfaces()` to re-derive an on-hue surface (`CVD_STATUS_SURFACE_ALPHA = 0.1`) for every patched status base, and `normalizeAppColorScheme`'s raw-token plugin path re-derives surfaces when a plugin overrides a base color without a matching surface. That second site had its own trap: `normalizedTokens` is seeded from the fallback scheme, so guarding on `typeof normalizedTokens[surfaceKey] !== "string"` never fires — the guard must check `tokenOverrides[surfaceKey]`, else the fallback scheme's differently-hued surface leaks through under a custom status color.

## Lesson

- **Never mix a chromatic color toward `transparent` for a wash that composites over light surfaces.** Chromium's oklab pipeline black-shifts it. Derive the alpha form from the hex instead — `withAlpha` in `shared/theme/themes.ts` — or consume the pre-baked `bg-status-*-surface` token. `builtInThemes.test.ts` enforces the invariant: every built-in `status-*-surface` must match `/^rgba\(/`.
- **`withAlpha` is only safe for hex input.** Its non-hex branch falls back to exactly the `color-mix(in oklab, … , transparent)` form that black-shifts. Built-in palettes must keep hex status colors — that is what the rgba-wash test is really pinning.
- **For a faded border over a known backdrop, mix toward the actual opaque backdrop, not transparent.** `GridNotificationBar` borders became `color-mix(in_oklab, var(--color-status-*)_35%, var(--color-surface-grid))` — same visual softening, no alpha, no black-shift.
- **Pre-baking a derived token severs the live var() dependency chain.** Every path that patches the base color must now also patch the derivative: CVD overrides (`withStatusSurfaces`), the plugin normalize path, and any future runtime recolor. When you add a derived token to `createDaintreeTokens`, grep for who else rewrites its base.
- **In `normalizeAppColorScheme`, gate derived re-derivation on `tokenOverrides`, not `normalizedTokens`** — the latter is pre-seeded from the fallback scheme so "is it missing?" checks are dead code there.
- **A new `ThemeStrategy` knob must be threaded through four places** or it silently no-ops for some theme source: `palette.ts` (type), `semantic.ts` + `compilePaletteToTokens` (plumbing), and the Zod schema in `electron/schemas/customSchemes.ts` — Zod strips unknown keys, so a forgotten field drops the knob for custom themes with no error.

## Applies when

- Adding any translucent tint/wash/highlight — CSS or a Tailwind arbitrary `color-mix(...,transparent)` — that can render over a light theme; the surviving instances in `src/index.css` / `src/utils/terminalTheme.ts` are dark-composited, near-achromatic, or shadow colors where darkening is harmless.
- Diagnosing "this banner/pill/highlight is the wrong color, but only on light themes" — check for a mix toward `transparent` before suspecting the palette.
- Touching `colorVisionOverrides.ts` or `normalizeAppColorScheme`: patching a base status/accent color requires re-deriving its pre-baked `-surface` twin, and the plugin-path guard must read `tokenOverrides`.
- Adding a derived token to `createDaintreeTokens` or a knob to `ThemeStrategy` — walk the full chain (types → semantic → themes → customSchemes Zod → `src/index.css` `--color-*` mapping → CVD canary count in `applyAppTheme.test.ts`).
- Reviewing a component that consumes `bg-status-*-surface` vs doing its own mix — the pre-baked token is the sanctioned form.
