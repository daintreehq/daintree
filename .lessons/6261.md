## Context

`createDaintreeFileProtocolHandler` (and the parallel plugin-protocol handler) in `electron/setup/protocols.ts` serve files to the renderer over the privileged `daintree-file://` / `canopy-file://` schemes. They take an attacker-influenceable `path` and a `root` query param and must confine the served file to within `root` before handing it to `net.fetch`.

## Problem

The guard normalized both paths with `path.normalize` and confined with `normalizedFile.startsWith(normalizedRoot + path.sep)`. A symlink committed inside the workspace (paths in a tracked repo are attacker-controlled) whose target points outside `root` passed the check: its _lexical_ path is genuinely inside `root`, so the string-prefix test succeeded, and `net.fetch(file://...)` then followed the symlink to `/etc/passwd` or any host file. Same bug class as CVE-2025-53109 / CVE-2025-54794. A secondary bug: bare `startsWith("..")` as the traversal guard wrongly rejected legitimate in-root files whose name begins with two dots (e.g. `..hidden/file.txt`).

## Root cause

`path.normalize` is purely lexical — it collapses `.`/`..`/separators as string operations and **never touches the filesystem**, so it cannot detect that a path component is a symlink to elsewhere. Containment built on lexical paths only constrains the _name_, not the _resolved location_. Resolving symlinks requires `fs.realpath`, which hits the filesystem. Separately, `startsWith("..")` matches both the escape segment `..` and any filename merely _starting_ with `..`, conflating a path-traversal token with a valid leading-dot filename.

## Lesson

For any privileged file-serving protocol or IPC handler that confines reads to a root:

- Resolve **both** the root and the target with `fs.realpath` (`fs/promises`) _before_ the containment test, and serve/fetch the realpath-resolved path — never the lexical one.
- Test containment with `path.relative(realRoot, realFile)` and reject on `rel === ".." || rel.startsWith(".." + path.sep) || path.isAbsolute(rel)`. The exact-match + `".." + path.sep` form avoids the `..hidden` false positive; `path.isAbsolute(rel)` catches Windows cross-drive escapes (`path.relative('D:\\proj','C:\\win') === 'C:\\win'`).
- Treat every `realpath` failure (`ENOENT`, `ELOOP`, `EACCES`) as `404`, not `403` or `500` — a distinct status leaks whether the path exists.
- A realpath check still leaves a TOCTOU window: a symlink swapped into the final component between `realpath` and the read survives. Close it by opening the _user-supplied_ path (not realFile) with `O_RDONLY | O_NOFOLLOW` and rejecting `ELOOP` (no-op on Windows where `O_NOFOLLOW === 0`, but realpath containment still applies). This is the canonical pattern now shared by `daintree-file://` and the plugin handler.

Note `..`-segment guards (lesson #4702) and symlink-resolution containment are **different defenses** — segment checks block `../` traversal in the name; realpath blocks in-root symlinks with no `..` at all. You need both.

## Applies when

- Adding or auditing any custom Electron `protocol.handle` scheme that serves filesystem content (`daintree-file`, `canopy-file`, plugin protocols, or new ones in `electron/setup/protocols.ts`).
- Writing IPC file-read handlers that confine reads to a project/worktree/plugin root.
- Reviewing any "is this path inside that directory" check built on `path.normalize` + `startsWith` — that pattern is symlink-blind.
- Choosing the `..`-traversal guard string and hitting false positives on dotfiles, or needing Windows cross-drive escape coverage.
- Hardening file serving against attacker-controlled paths from a tracked repo (symlinks in git are attacker input).
