## Context

The demo engine (`DemoCursor.tsx`) exposes `waitForIdle(settleMs?, timeoutMs?)` as an authoring primitive in the `demo-video-creator` skill — the call an author reaches for to sync a beat against a terminal finishing its output before a screenshot or the next cursor move. The original `demo:exec-wait-for-idle` handler declared the page idle when `document.getAnimations()` reported no running animations, a `MutationObserver` on `document.documentElement` had been quiet for `settleMs`, and a double-`requestAnimationFrame` confirmed a paint. Daintree renders every terminal through `@xterm/addon-webgl` (`TerminalWebGLManager`), painting to a WebGL canvas.

## Problem

`waitForIdle` resolved "idle" while an xterm terminal was still visibly streaming output, or while a `<video>` was mid-playback (issue #10144). The heuristic looked complete — animations quiet, DOM quiet, paint confirmed — so it was easy to trust. A demo script that placed `waitForIdle` after `typeInTerminal` to wait for a command's output to drain would fire the next beat while the frame was still moving.

## Root cause

The three signals cover one pipeline and miss two others. `document.getAnimations()` returns only Web Animations API / CSS animations / transitions — never rAF-driven canvas, WebGL, or video repaints. A `MutationObserver` watching `attributes`/`childList`/`characterData`/`subtree` never fires for pixel updates, because WebGL and 2D `<canvas>` draw calls (and `<video>` frame advances) do not mutate the DOM. So a terminal repainting via the WebGL renderer, or a playing video, produces zero animations and zero mutations — the heuristic settles and resolves while the pixels are still changing. This is structural, not a tuning bug: no `settleMs` value fixes a channel the observer cannot see.

The fix (#10254) adds two explicit activity channels. **Terminal:** subscribe to `terminal.onWriteParsed` on each live terminal (snapshotted from `usePanelStore.getState().panelIds` via `terminalInstanceService.get`), each firing `resetTimer()`. `onRender` was explicitly rejected — the cursor blink cycle fires `onRender` continuously, so subscribing to it would keep `waitForIdle` from ever settling; `onWriteParsed` fires at most once per frame _after_ an async parse of `terminal.write()` completes and never on blink/scroll/focus (it is the same write-completion signal `TerminalListenerInstaller` uses for scroll-to-bottom and reflow). **Video:** media events don't bubble, so capture-phase `playing`/`pause`/`ended`/`waiting` listeners on `document` maintain an `activeVideos` set; idle requires it empty. A cancellable double-rAF (`rafCancelled`, flipped by `resetTimer()`) closes the race where activity lands in the gap between `check()` scheduling the confirmation and the second rAF firing — without it, late activity would falsely resolve.

## Lesson

- **Any "is the page idle/settled" check in Daintree is blind to terminals and video unless it adds an explicit per-medium channel.** `getAnimations()` sees only WAAPI/CSS; `MutationObserver` sees only DOM mutations; a double-rAF only confirms _a_ paint happened, not that painting stopped. Terminals paint via WebGL canvas and `<video>` advances frames — both bypass those signals. Applies to any screenshot-sync, perf-settle, or "wait for output to drain" logic, not just the demo engine.
- **For xterm activity/idle detection subscribe `onWriteParsed`, never `onRender`.** The cursor blink cycle fires `onRender` continuously, so an `onRender`-based idle check never settles. `onWriteParsed` fires ~once per frame only after a `terminal.write()` parse completes — it is the correct settle signal and the one the rest of the terminal stack already treats as "output landed."
- **Media events don't bubble — listen in the capture phase on `document`, and treat `waiting` (buffering) as inactive** so a stalled video can't permanently block idle (`playing` re-arms the timer if playback resumes). Also prune DOM-disconnected videos each `check()` (`!v.isConnected`): a React conditional unmount can drop a playing `<video>` without firing `pause`/`ended`, otherwise blocking idle until `timeoutMs`.
- **A settle confirmation spanning a double-rAF needs a cancel flag.** Activity in the rAF gap must abort the in-flight resolve; `resetTimer()` sets `rafCancelled = true` and the inner rAF bails. Multi-channel settle timers also need one idempotent, exception-safe `cleanup()` (guarded by a `cleaned` flag) tearing down observer, terminal disposables, and video listeners on both resolve and timeout paths — a throwing `dispose()` must not strand the rest.
- **Code drift:** the PR guarded the snapshot with `if (!managed || managed.isHibernated) continue`, but hibernation was later torn out (`7d417ab2a`) — the current guard is just `if (!managed) continue`; no `isHibernated` flag remains.

## Applies when

- Touching `waitForIdle` / `demo:exec-wait-for-idle` in `src/components/Demo/DemoCursor.tsx`, or adding any new "wait until the page settles" primitive to the demo engine or elsewhere.
- Diagnosing `waitForIdle` (or any settle/screenshot-sync check) resolving early while a terminal is still streaming output or a video is still playing.
- Building screenshot, perf-measurement, or capture logic that assumes a `MutationObserver` or `document.getAnimations()` observes terminal or canvas/WebGL activity — it does not.
- Choosing which xterm event to subscribe for activity/idle detection (`onRender` vs `onWriteParsed`) — cursor blink makes `onRender` fire forever.
- Adding `<video>` playback into demo scripts and needing beats to wait for it, or handling media elements that unmount mid-playback without firing `pause`/`ended`.
