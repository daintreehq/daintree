## Context

Daintree gives each project its own `WebContentsView` (independent V8 context) managed by `ProjectViewManager` (`electron/window/ProjectViewManager.ts`), with LRU eviction keeping non-active views cached. The window itself owns one `appWebContents` (the chrome/shell) while the visible project view is swapped in/out via `activate`. Code written before this per-project-view architecture (#4672) assumed one long-lived renderer per window.

## Problem

Three latent bugs surfaced only in cached/non-active views or during shutdown:

- The "Window Not Responding" dialog's "Restart view" button captured `appWebContents` at dialog-creation time and called `forcefullyCrashRenderer()` on it — but the _active project view_ (a different webContents) is what's actually wedged, so the restart hit the wrong process.
- `handleRenderProcessGone` unconditionally fired a `notifyError` toast ("A project view crashed and was automatically reloaded") even when a **cached, non-active** view crashed — the user is looking at a different project and the reload is invisible, so the toast is noise.
- `WorktreePortBroker` relied on `webContents.once("destroyed")` / `did-start-navigation` for port cleanup, but those don't fire when the **host side** closes the port (utility-process crash, port-transfer failure), leaking the `port1` entry.

## Root cause

The per-project-view swap invalidates two single-renderer assumptions that are easy to miss:

1. **"The window has one webContents" is false.** `win.webContents` / a captured `appWebContents` is the shell, not the active project view. Any handler created once (a dialog `.then`, a registered listener) that closes over a webContents reference goes stale the moment the active view swaps. The fix late-resolves at action time: `getProjectViewManager()?.getActiveView()?.webContents` (`electron/window/windowRef.ts:33`, `ProjectViewManager.getActiveView()` at `ProjectViewManager.ts:661`), with an `appWebContents` fallback for the shutdown window when PVM is null, and an `isDestroyed()` guard before use.
2. **"Every renderer event is user-observable" is false.** With cached views, `render-process-gone` can fire for a project the user isn't looking at. The recovery _action_ (reload) must still run, but the _notification_ must gate on `projectId === this.activeProjectId` (`ProjectViewManager.ts:1281`) — mirroring the same active-only gate already used for `onViewCrashed` port teardown at line 1210. Non-active crashes demote to `console.warn`.
3. **renderer-side lifecycle events don't cover host-side port death.** `port1.on("close")` is the authoritative signal when the workspace-host end closes the port; without it the broker's map entry leaks. `closePortsForView` is idempotent (map-deletion guard), so the extra listener is safe, and `cleanupListeners` must `removeListener` it on re-broker to avoid accumulation across host restarts.

## Lesson

- In multi-window / per-project-view Electron code, **never capture a `webContents` reference for later use in a callback that outlives a possible view swap.** Resolve `getProjectViewManager()?.getActiveView()?.webContents` at the moment of action, guard with `isDestroyed()`, and fall back to `appWebContents` only for the shutdown/no-PVM case.
- **Gate user-facing crash/error notifications on `projectId === activeProjectId`.** A cached-view event is not observable to the user; per the notify() policy, demote it to `console.warn` while still running the silent recovery. The active-only gate already exists for port teardown — reuse the same predicate.
- **Don't trust renderer-side lifecycle events (`destroyed`, `did-start-navigation`) alone for MessagePort cleanup.** They don't fire when the _peer_ (utility-process host) closes the port. Subscribe to `port1.on("close")` as a fallback, rely on idempotent cleanup, and remove the listener in your stored `cleanupListeners` so re-brokering doesn't accumulate handlers.
- When auditing old code for this class of bug, search for `win.webContents`, captured `appWebContents`, and unconditional `notifyError(... renderer-crash ...)` — these are the single-renderer fingerprints.

## Applies when

- Adding or editing handlers in `electron/window/ProjectViewManager.ts`, `createWindow.ts`, or anything touching `unresponsive` dialogs, `render-process-gone`, `forcefullyCrashRenderer`, or `getActiveView()`.
- Writing code that captures a `webContents` / `appWebContents` reference inside a `dialog.showMessageBox().then()`, a `setTimeout`, or any long-lived listener in a window that hosts multiple project `WebContentsView`s.
- Deciding whether a main-process crash/error event should `notifyError` (toast) vs `console.warn` — gate on active-project match for anything that can fire for a cached view.
- Working on `WorktreePortBroker` or any `MessageChannelMain` port lifecycle where one end lives in a utility-process host (pty-host, workspace-host) and the other in a renderer — port-transfer failure and host crash won't trigger renderer-side webContents events.
- Auditing pre-multi-window (pre-#4672/#4715) code for stale single-renderer assumptions after a project-view swap or LRU eviction.
