## Context

The MCP server (`electron/services/mcp-server/`) exposes Daintree actions as tools an LLM can call. Side-effecting/creation tools — `terminal.new`, `worktree.createWithRecipe`, `agent.launch`, `recipe.run`, and several destructive mutations (`git.commit`, `git.push`, `worktree.delete`, `forge.openIssue`...) — each dispatch through one `CallToolRequestSchema` handler in `sessionServer.ts`. Models retry tool calls freely (timeouts, transport hiccups, hallucinated re-sends), so a naive handler double-creates.

## Problem

A single retry-protection mechanism is insufficient. Two distinct duplicate windows exist and require different handling: (a) a _concurrent_ duplicate arrives while the first dispatch is still pending, and (b) a _sequential_ duplicate arrives after the first call already completed. A bare result cache misses (a); a bare in-flight Promise map misses (b). Caching every result (including failures) makes a transient error stick for the whole TTL. And a slow dispatch resolving after the session is torn down can resurrect a dead session's cache.

## Root cause

Idempotency for agent-retried creation tools is a two-window problem, not one. `sessionDedup.ts` + `sessionServer.ts` cover both: an `inFlight` Map gives concurrent identical calls the _same_ Promise via singleflight (`dispatchAction` runs exactly once); a separate `resultCache` Map with `MCP_DEDUP_TTL_MS = 120_000` returns the prior result for post-completion retries. The dedup key is `buildDedupKey()` — `actionId:rk:<requestKey>` if the caller supplied one, else `actionId:auto:<sha256(actionId + canonicalStringify(args))>`. `canonicalStringify` recursively sorts object keys (arrays keep order) so key-insertion-order variance hashes identically. Three subtleties make it correct:

- **Success-only caching** — the `.then()` hook caches only when `outcome.kind === "result" && outcome.value.ok`; failures fall through so the next retry actually re-dispatches.
- **Drain-clears-before-resolve liveness guard** — `SessionStore.drain()` clears `dedupInFlight`/`dedupResultCache` _up front_, and the resolve hook re-reads `dedupInFlight.get(sessionId)` and bails if it isn't the same Map identity it registered against. Without this, a dispatch resolving after teardown writes into a resurrected session's cache (same resurrection class as #2243's invalidated-cache resurrection, here in the MCP session lifecycle).
- **Collision detection** — a stored entry also carries `argsHash`; if a caller-supplied `requestKey` is reused with _different_ args, the handler returns `MCP_DEDUP_KEY_COLLISION` instead of silently returning the stale result.

## Lesson

For any new MCP tool (or similar agent-callable RPC) that has an observable side effect and could be retried:

- Add it to `MCP_DEDUP_ALLOWLIST` (`shared.ts`) — but **only** side-effecting/creation tools. The allowlist is deliberately bounded; blanket-deduping all mutations would mask legitimate "do it again" calls (re-running the same git command on purpose). Reads never need it.
- Rely on the existing two-window machinery; do not hand-roll a one-sided cache. Singleflight handles concurrent dupes, TTL cache handles sequential retries — you need both.
- Cache only successful results. Caching a failure pins a transient error for the whole TTL and blocks the retry that would have succeeded.
- Any async hook that writes back into per-session state after an await MUST re-fetch the session/Map and verify identity before writing — `drain()` may have torn it down (resurrection guard). Clear teardown state up front so the late resolver finds nothing to write into.
- When supporting a caller-supplied idempotency key, store the canonical args hash alongside it and reject reuse-with-different-args as a collision rather than returning a stale result.

## Applies when

- Adding a new MCP creation/mutation tool, or adding any action to `MCP_DEDUP_ALLOWLIST` / `RATE_LIMIT_TOOL_MAP`.
- Touching `electron/services/mcp-server/sessionServer.ts` (the `CallToolRequestSchema` handler), `sessionDedup.ts`, or `sessionStore.ts` dedup maps (`dedupInFlight`, `dedupResultCache`).
- Symptoms: an agent retrying a tool call double-creates a terminal/worktree/agent/PR; a transient tool failure keeps returning the same error for ~2 minutes; a cached result reappears after a session was revoked/drained.
- Designing any singleflight + TTL-cache idempotency layer for retried RPC where both concurrent and sequential duplicates are possible.
- Building canonical request hashing where key-insertion order or nested-object order must not change the dedup identity (`canonicalArgsHash` / `canonicalStringify`).
- Any per-session async cache where teardown can race a pending resolver (resurrection guard — see also #2243).
