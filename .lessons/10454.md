## Context

The renderer preload (`electron/preload.cts`) reads several launch-time flags synchronously so the renderer knows its identity before first paint: initial color scheme (#9169), initial project id (#9162), instance role (#10123), surface-host id, `--demo-mode`, and the E2E flags (`DAINTREE_E2E_MODE` / `_SKIP_FIRST_RUN_DIALOGS` / `_FAULT_MODE`). Because the preload runs under `sandbox: true`, the (unsandboxed) main process reads the launch env and threads stable argv switches (`--daintree-e2e-mode`, etc.) into every view's `webPreferences.additionalArguments` via `resolveE2EPreloadArgs()` (`electron/window/skeletonCss.ts`), wired in `createWindow.ts`, `ProjectViewFactory.ts`, and `SurfaceViewManager.ts`; the preload then reads them from `process.argv`.

## Problem

Release dry-run E2E across the per-OS release workflows failed: the app would not enter E2E mode on some platforms even though the launcher exported `DAINTREE_E2E_MODE=1`. #10454's PR body pinned it on "sandboxed preload could miss environment-derived E2E flags on some platforms." The misleading part: that reads like a pure env-propagation bug, so the "obvious" fix — drop env, read the argv switch only — was itself later found to fail on **local Playwright runs**, where the argv switch was the thing missing.

## Root cause

Two facts about Electron 42 sandboxed preloads combine into a two-sided trap. (1) `process.env` IS polyfilled under `sandbox: true`, but it does NOT reliably carry every launch-env variable across platforms/builds — a specific var can silently fail to arrive. So the original AND gate (commit `6a97e62d4`: `hasE2EModeEnv && process.argv.includes(E2E_MODE_ARG)`) failed wherever env didn't reach the preload. (2) `process.argv` IS reliably readable in a sandboxed preload — that is why the color-scheme, project-id, instance-role, and surface-host reads all use it — BUT the `additionalArguments` argv switches themselves don't always arrive either: per the current in-code comment, "Electron 42 local sandboxed WebContentsView preloads can omit those extra argv switches." So #10454's argv-only fix (`ab220970b`) then broke the local Playwright process where the argv switch was empty.

The robust resolution (commit `ed9479323`) ORs both channels, gated by `!isPackagedBuild`: `process.argv.includes(E2E_MODE_ARG) || process.env.DAINTREE_E2E_MODE === "1"` (`preload.cts:245-254`; mirrored in `runtimeFlags.ts`). The main-side `resolveE2EPreloadArgs()` also ORs both, so the argv switch is emitted whether the launcher set env OR passed argv. Env matching is EXACT `=== "1"` (a test rejects `"true"`/`"yes"`/`"on"`), and the `!isPackagedBuild` gate — `process.argv.some(a => a.includes("app.asar"))` — keeps production from ever flipping into E2E mode via a stray env or argv token.

## Lesson

- **Detecting a launch flag in a sandboxed Electron preload: OR both channels — `process.argv.includes(SWITCH)` (threaded via `additionalArguments`) AND an exact `process.env` check — never rely on one.** Neither reaches an Electron 42 sandboxed `WebContentsView` preload reliably: env drops individual vars per-platform, and `additionalArguments` argv switches can be omitted on local WebContentsView preloads. The correct pattern is belt-and-suspenders, not "argv instead of env."
- **`process.env` being present under `sandbox: true` is not the same as being populated.** It's polyfilled, but a specific variable may be missing on some OS/build; treat any single env read in a preload as best-effort, and follow the `instanceRole` pattern already in `preload.cts` (argv first, env fallback for "contexts the main process did not seed").
- **The sanctioned way to get a main-process value into a sandboxed preload is `webPreferences.additionalArguments` read via `process.argv` — but wire it into EVERY view factory**, or LRU-evicted / project-switch / surface-host views silently miss the flag. `resolveE2EPreloadArgs()` is spread into `createWindow.ts` (app view), `ProjectViewFactory.ts` (project views), AND `SurfaceViewManager.ts`; adding a channel in only one is a latent per-view bug.
- **Gate every E2E/dev preload flag on `!isPackagedBuild` (`app.asar` in argv) and match env values EXACTLY (`=== "1"`)**, so a stray env var or a truthy-but-not-exact string can never enable test hooks in a shipped build — there's a regression test asserting `"true"`/`"yes"`/`"on"` don't count.
- **Don't trust a PR body's one-line root cause.** #10454 concluded "read argv, not env," but the real invariant is "neither alone" — the argv-only change regressed local runs and was corrected within days (`ed9479323`). The naive takeaway sends a future agent straight into the second half of the trap.

## Applies when

- Adding or reading any launch-time flag in `electron/preload.cts` or `electron/setup/runtimeFlags.ts` (demo-mode, instance-role, surface-host, initial-project-id, a new E2E hook) and deciding how the value reaches the sandboxed renderer.
- Diagnosing "E2E mode / a preload flag works in dev but not packaged or in CI, or on one OS only" — check BOTH the `additionalArguments` threading and the env fallback, and whether the reading view factory was even wired.
- Threading a new value through `webPreferences.additionalArguments` — confirm it's spread into `createWindow.ts`, `ProjectViewFactory.ts`, AND `SurfaceViewManager.ts`, not just one path.
- Reviewing any preload code that reads `process.env` directly with no argv fallback, or that enables a test/dev hook without a `!isPackagedBuild` gate and an exact env-value match.
