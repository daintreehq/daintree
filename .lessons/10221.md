## Context

The e2e.yml retry path scopes GitHub's "Re-run failed jobs" to a subset: on `run_attempt > 1` it passes `--test-list failed-specs.txt` (built from the prior attempt's Playwright JSON report at `test-results/report.json`) instead of re-running the whole suite — every suite except `nightly` and `online`. The release-gating `core` and `online` suites additionally run with `failOnFlakyTests` (`playwright.config.ts:63`, gated by the `FAIL_ON_FLAKY_TESTS` env — `full-*` buckets keep retries WITHOUT a flake gate for PR velocity), so a spec that fails its first attempt but passes an in-run retry ("flaky") makes the whole job exit non-zero. #10221 (resolves #10039) fixed how that retry list is built.

## Problem

On `core`, a mixed hard-failure + flaky-failure run could be re-run to green without ever re-exercising the flaky spec that tripped the gate. `failed-specs.txt` was built with `jq -r '.suites[] | .. | objects | select(.file != null and .ok == false) | .file'`. The retry passed, the release proceeded, and the flaky test — the exact thing `failOnFlakyTests` exists to catch — was never validated. A false green on the release gate, invisible because the primary attempt's red looked "handled."

## Root cause

In the Playwright JSON reporter `spec.ok` is `test.ok()`, which returns `true` for outcome `expected`, `flaky`, OR `skipped`. A flaky spec (failed then passed on retry) therefore has `spec.ok === true`, so a `.ok == false` filter omits it from the retry list — even though under `failOnFlakyTests` that flaky spec IS why the job went red. The retry-list predicate disagreed with the suite's own failure semantics. Two branches diverge: **pure flaky** → list empty → the downstream `[ -s failed-specs.txt ]` non-empty gate fails → the workflow falls back to a full rerun (safe); **mixed hard+flaky** → list contains only the hard-failure file → `--test-list` reruns just that file, never touches the flaky spec, and if the hard failure now passes the job goes green. There is no full-suite fallback in that branch, so only the mixed case was broken — which is why it was easy to miss. The fix extracted `scripts/ci/extract-failed-specs.mjs` (`extractFailedSpecPaths` / `specFailed`) whose predicate includes a spec when any test `status === "flaky"` OR its last-result status is not `passed`/`skipped`, plus a 12-case vitest file, and replaced the `jq` one-liner in `e2e.yml`.

## Lesson

- **Playwright's `spec.ok` is not "did this spec pass" — it is `test.ok()`, true for `expected`, `flaky`, AND `skipped`.** Never build a CI retry or failure list by filtering on `.ok == false`; it silently drops flaky specs (and skipped ones). The correct predicate walks each test: include the spec when any test `status === "flaky"` OR its last-result (`test.results.at(-1).status`) is not `passed`/`skipped` — see `scripts/ci/extract-failed-specs.mjs`.
- **A scoped rerun list must be a superset of everything that tripped the gate.** `core`/`online` run `failOnFlakyTests` (`playwright.config.ts:63`), so flaky counts as job failure; a retry list that excludes flaky validates a different subset than what failed. Whenever a rerun narrows to a subset, prove the subset covers every failure cause, or a mixed-cause red re-runs to a false green.
- **Same JSON report, two extractors, deliberately OPPOSITE flaky semantics — do not unify them.** `extract-failed-specs.mjs` (retry list) INCLUDES flaky; the sibling `scripts/ci/extract-failures.mjs` (stabilize-triage failure signatures) EXCLUDES flaky on purpose (`test.status === "unexpected"` only) because a recovered flake shouldn't be surfaced as a failure to triage. There is no single "is this a failure" predicate — the right flaky treatment depends on the consumer.
- **The empty-list fallback hides the bug for the pure-flaky case.** `[ -s failed-specs.txt ]` gates the `--test-list` branch, so a pure-flaky failure (empty list) safely falls back to a full rerun. Test the MIXED hard+flaky case explicitly — testing each cause alone passes and misses the real defect.
- **When replacing a shell filter with a script, preserve its output-shape contract.** The extractor emits `specs.join("\n") + "\n"` only when non-empty, matching `jq -r | sort -u` so downstream `wc -l` and `[ -s failed-specs.txt ]` stay accurate; a trailing newline on empty output would defeat the `[ -s ]` gate and re-trigger a scoped (empty) retry instead of the full-rerun fallback.

## Applies when

- Touching the e2e retry / `--test-list` path in `.github/workflows/e2e.yml`, `scripts/ci/extract-failed-specs.mjs`, or its `.test.mjs`.
- Writing ANY CI tooling that parses a Playwright JSON report to decide what failed or what to re-run — reach for test-level `status`/`results`, never `spec.ok`.
- Changing `failOnFlakyTests` / `FAIL_ON_FLAKY_TESTS` gating, or which suites are release-gating (`core`/`online`) vs velocity (`full-*`).
- Diagnosing a `core`/`online` release job that went green on "Re-run failed jobs" but had a flaky failure in the original attempt.
- Editing either `extract-failed-specs.mjs` or `extract-failures.mjs` — apply the flaky semantics that match THAT consumer, don't copy the other's predicate.
