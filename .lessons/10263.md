## Context

The deferred init queue (`electron/window/deferredInitQueue.ts`) postpones non-critical global-service startup — `mcp-server`, `plugin-cli-server`, `resource-profile-service`, `disk-space-monitor`, and the other `registerDeferredTask` entries in `globalServicesInit.ts` — until after first-interactive so the window paints fast. It drains via a self-rescheduling `setImmediate` chain (`doDrain` → `drainNext`), plus a 10s fallback timer (`finalizeDeferredRegistration`) for boots where first-interactive never arrives.

## Problem

On a fast quit-after-launch (Cmd+Q landing in the few-hundred-ms drain window near first-interactive), or a boot where first-interactive never fires and the 10s fallback drain runs mid-shutdown, the app exited leaving live sockets/servers/timers and a stale `~/.daintree/cli.sock` behind. The misleading part: every init-side guard was present and correct — `if (getResourceProfileService()) return`, `if (singleton) return` — yet passed, because they read state teardown had _just_ nulled.

## Root cause

The `setImmediate` drain chain only bailed when the `generation` counter changed, and the sole non-test caller of `resetDeferredQueue()` (which bumps `generation`) is `windowServices.ts` `win.on("closed")` — last-window-close only. The `before-quit` handler calls `event.preventDefault()` then runs a long async cleanup chain (dynamic `import()`s, PTY kill up to 4s) with **no shutdown flag visible to the drain**. The event loop keeps servicing immediates and import continuations during those awaits, so the drain ran _concurrently_ with teardown: teardown nulls a service ref, the still-pending task's init guard reads that null → passes → re-creates the service. Worst case is `PluginCliServer`: `startPluginCliServer()` assigns `singleton` only _after_ `await server.listen()`, so if shutdown's `stopPluginCliServer()` runs while the task still awaits `listen()`, stop reads `singleton === null` and no-ops, then the task binds a fresh unix socket never closed before `app.exit()`.

The fix is a process-lifetime `halted` latch and exported `haltDeferredQueue()`, guarded at all five entry points (`registerDeferredTask`, `signalFirstInteractive`, `finalizeDeferredRegistration`, `doDrain`, and `drainNext`'s `drainGen !== generation || halted` bail). It is the first statement of `runShutdownChain` in `shutdown.ts`, before the first `await` (the two sync steps after it don't yield). `runShutdownChain` is shared by `before-quit` and AutoUpdaterService install and is entered via `startShutdown` only once quit is committed.

## Lesson

- **The halt must be set synchronously, before the shutdown chain's first `await`.** A `setImmediate` step already scheduled but not yet run still executes after your first yield — setting the latch at the top of `runShutdownChain` (before any `import()`) is what makes those pending callbacks observe `halted` and bail. Put it after an await and the drain step you're racing has already fired.
- **Reach the halt only after quit commits, and make it permanent/unresumable.** `haltDeferredQueue()` sits in `runShutdownChain`, entered via `startShutdown` only after the quit dialog resolves _confirmed_. A cancelled quit must never halt — an abandoned drain chain cannot be resumed, so the queue would be dead for the session. Don't hoist the halt earlier in `before-quit` "to be safe."
- **`resetDeferredQueue()` must deliberately NOT clear the latch — this is a macOS ordering constraint.** On quit, `last-window-close` fires _before_ `before-quit`, and `win.on("closed")` calls `resetDeferredQueue()`. If reset cleared `halted`, that close-then-quit sequence would un-halt the queue right before teardown. So reset leaves `halted` set; only the test-only `__resetDeferredQueueForTests()` clears it. The regression guard is the macOS re-open path (reset _without_ a prior halt still drains a fresh cycle normally).
- **An init guard that reads a ref teardown nulls is not safe against a concurrent drain — it reads the race backwards.** `if (getX()) return` passes _because_ teardown already set `X` to null, so it skips nothing at the exact moment it should skip. When start and stop race, the stop's "already null → no-op" and the start's "still null → create" both fire and you get an orphan. Halt the whole queue; per-service null-guards can't close this.
- **A generation/epoch counter only covers the reset path it was built for.** `generation` bailed the drain on last-window-close but was blind to quit — a self-rescheduling `setImmediate` chain needs an _explicit_ shutdown-aware bail, not the reuse of a counter only one path increments.

## Applies when

- Adding a deferred/lazy global-service init via `registerDeferredTask` in `globalServicesInit.ts` — confirm its teardown races safely against a mid-drain quit (start/stop must be latch-guarded, not just null-guarded).
- Touching `deferredInitQueue.ts` drain/reset internals (`doDrain`, `drainNext`, `resetDeferredQueue`, `generation`) or the `halted` latch / `haltDeferredQueue()`.
- Diagnosing orphaned sockets/servers/timers or a stale `~/.daintree/cli.sock` after quit, especially on quit-immediately-after-launch or a slow-first-interactive boot.
- Adding any synchronous halt/latch to an Electron `before-quit` chain — set it before the first `await`, reach it only after quit commits, and decide _explicitly_ whether reset clears it (macOS `last-window-close` fires before `before-quit`). Same trap for a start/stop pair where stop no-ops on a null singleton and start assigns it only after an `await`.
