## Context

The MCP server's `GrantCache` (`electron/services/mcp-server/grantCache.ts`) holds per-(session, tool) "Approve once" grants that let an agent call an elevated tool without re-prompting the user. To avoid nagging on every back-to-back call, the grant uses a _sliding_ TTL: `refresh()` resets `expiresAt = now + ttlMs` (`MCP_GRANT_TTL_MS = 15 min`) on every successful dispatch. `check()` and a periodic `sweep()` lazily evict aged-out entries.

## Problem

A single user "Approve once" decision could be held indefinitely. Because every dispatch slid the window forward, any agent calling the granted tool more often than once per 15 minutes never let the grant expire — turning a one-shot approval into a permanent capability that outlived the SSE session it was scoped to.

## Root cause

A sliding-TTL refresh has **no upper bound by construction**: as long as use is frequent enough to keep beating the TTL, `expiresAt` is perpetually pushed into the future. The TTL only measures _time since last use_, never _total lifetime_. There was no constraint relative to the grant's immutable `issuedAt`, so "expires after 15 minutes of inactivity" silently meant "never expires under steady load."

## Lesson

Any sliding/refresh-extended lifetime on a _security or capability_ token must carry a hard wall-clock ceiling measured from an immutable issue time, not just an idle TTL:

- Store an immutable `issuedAt` and enforce `now > issuedAt + maxLifetimeMs` in **every** read path — here `check()`, `refresh()`, and `sweep()`. The ceiling is a _stricter_ predicate than the TTL: a just-refreshed entry has a future `expiresAt` but can still be past the ceiling, so the TTL skip (`now <= expiresAt`) will miss it. Evict on `pastCeiling || pastTtl`.
- Size the ceiling so the grant can never outlive its containing scope. `MCP_GRANT_MAX_LIFETIME_MS = 30 min` is deliberately equal to `MCP_SSE_IDLE_TIMEOUT_MS` and `MCP_TIER_ELEVATION_TTL_MS` (`shared.ts`) so a grant can never survive its SSE session.
- Keep the audit trail truthful by distinguishing eviction _causes_: a ceiling hit on a still-fresh grant emits `grant.revoked` with `revokedReason: "grant-ceiling"`, while an idle-out emits `grant.expired`. The deciding test is `pastCeiling && !pastTtl` — if the TTL already lapsed it's a passive idle timeout regardless of the ceiling, so don't relabel it. Don't collapse active revocation and passive timeout into one reason.
- Re-approval mints a fresh `issuedAt`, resetting the clock; combine this with the existing `issuedAt`-token race guard (#2243) so a stale in-flight `refresh()` carrying the old `issuedAt` no-ops against the new grant.

## Applies when

- Touching `GrantCache`, MCP per-tool grants, `MCP_GRANT_TTL_MS`, `MCP_GRANT_MAX_LIFETIME_MS`, or tier-elevation TTLs in `electron/services/mcp-server/`.
- Adding or modifying any "remember this approval" / "approve once" / session-scoped capability cache, OAuth-like refresh window, or cooldown that _extends on use_.
- Reviewing security-relevant lifetimes: ask "can frequent use keep this alive forever?" — if the expiry is sliding/refresh-based, require a ceiling from issue time.
- Auditing `revokedReason` / grant-lifecycle telemetry, or any code that emits distinct `revoked` vs `expired` audit events and must keep them honest.
- Writing eviction logic across multiple paths (lazy-on-read + periodic sweep): verify the sweep's TTL fast-skip doesn't let a stricter ceiling condition slip through.
