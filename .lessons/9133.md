## Context

Dev-preview sessions spawn a dev server (Vite/Next/webpack) in a PTY on a port assigned by `allocatePort` (`electron/services/DevPreviewPortAllocator.ts`) and tracked in `portRegistry` keyed by session. On `stop`/`restart`/`restartAndClearCache`, `DevPreviewSessionService` kills the PTY and — for restart — respawns on the **same** port, because `allocatePort` returns the already-registered port immediately without re-probing (lines 10-11: `const existing = portRegistry.get(sessionKey); if (existing !== undefined) return existing;`).

## Problem

On Windows, restarting a dev preview intermittently failed with `EADDRINUSE` on the same port the session had just been using — even though the previous dev-server process was confirmed dead. The session would either crash on respawn or show a misleading "stopped" state while the port was actually still held.

## Root cause

Process death is not the same as socket release. When the dev server's PTY is force-killed (SIGKILL escalation after `DEV_PREVIEW_STOP_ESCALATION_MS`), the OS can hold its listening socket in `TIME_WAIT` after the process exits — on Windows up to ~240s. The restart logic assumed "process dead ⇒ port free" and respawned immediately. Because `allocatePort` short-circuits on the registry entry and never re-probes a reused port, the next `srv.listen()` (now the dev server's own bind) hit the kernel-held socket and threw `EADDRINUSE`. On macOS/Linux listening sockets release on process exit so the bug effectively never reproduced there — making it a Windows-only, hard-to-see failure.

## Lesson

- After killing a process that held a TCP port, **poll for actual bindability before reusing the port** — never assume the port is free just because the process is gone. The kernel-held `TIME_WAIT` window is platform-dependent and worst on Windows.
- Probe with the **same** bind call the allocator uses (`net.createServer().listen(port, "0.0.0.0", ...)` then `close()`), so a "free" answer here implies the real spawn will also succeed (the TOCTOU gap aside). This is what `waitForPortFree` does (200ms poll, 15s timeout, `AbortSignal`-aware).
- On poll timeout, **evict the port from the registry** (`releasePort`) so the next `ensure()`/`allocatePort` picks a _fresh_ candidate instead of retrying the still-held one. Surface a distinct `error: { type: "port-conflict" }` state rather than a misleading `stopped` — the socket is still occupied, so the UI must not pretend the session is cleanly stopped.
- Wire the wait in _every_ path that respawns or transitions to stopped after a kill (`stop`, `restart`, `restartAndClearCache`), not just one.

## Applies when

- Touching `DevPreviewPortAllocator.ts` / `DevPreviewSessionService.ts`, dev-server restart/stop logic, or anything that reuses a `portRegistry` entry.
- Writing any code that kills a child/PTY process and then re-binds the same TCP port (dev servers, OAuth loopback listeners, local proxies, test fixtures spawning servers).
- Diagnosing intermittent `EADDRINUSE` that reproduces on Windows but not macOS/Linux, or "port still in use after I killed the process" symptoms.
- Designing restart flows where the allocator short-circuits on an existing registration without re-probing — confirm the port is actually bindable before reuse.
- Any cross-platform process-lifecycle work involving socket cleanup, force-kill / SIGKILL escalation, or `TIME_WAIT` lingering.
