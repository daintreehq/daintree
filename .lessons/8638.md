## Context

`ProjectViewManager` keeps multiple `WebContentsView` project views in one `BrowserWindow` — exactly one active, the rest cached/hidden; the activate/deactivate lifecycle itself lives in `ProjectViewLifecycleController.ts`. To reclaim CPU it threw `setBackgroundThrottling(true)` at deactivated views in `deactivateEntry` and `setBackgroundThrottling(false)` at the activating view in `activateView`.

## Problem

Cached sibling views kept burning CPU as if active. The per-view `setBackgroundThrottling(true)` calls were silent no-ops — deactivated renderers never actually throttled (#8599).

## Root cause

The `setBackgroundThrottling` name implies per-`WebContents` scope, but since Electron 28 the flag is applied at the `BrowserWindow` level: calling `setBackgroundThrottling(false)` on ANY WebContents in a window disables timer throttling for ALL sibling WebContents in that window. Because every window has one always-active view calling `(false)`, that one call un-throttled every cached sibling — making the cached-view `(true)` calls ineffective by construction. This is a different mechanism than the global-Chromium-flag override in lesson #4683 (no `disable-renderer-backgrounding` switch was set here); the window-wide scope is intrinsic to the API. The fix is per-target CDP: `Emulation.setCPUThrottlingRate` (`rate: 4` cached, `rate: 1` active) via `wc.debugger`, wrapped as `throttleCpuWebContents` / `unthrottleCpuWebContents` in `webContentsLifecycle.ts`. CPU throttling slows the V8/Blink clock for one renderer only while leaving the event loop, IPC, and MessagePort dispatch running — so cached views still receive live worktree/workspace messages. The `Emulation` domain (unlike `Page`) needs no `enable` call before `setCPUThrottlingRate`.

## Lesson

- Do NOT use `WebContents.setBackgroundThrottling` to throttle individual views in a multi-view single-window layout. It is window-wide; a single `(false)` on the active view defeats every `(true)` on siblings.
- For genuine per-renderer throttling use CDP `Emulation.setCPUThrottlingRate` through the per-target `wc.debugger` session. `rate > 1` slows that renderer's CPU clock without freezing its event loop — safe for cached views that still need MessagePort/IPC delivery.
- This is orthogonal to but supersedes the assumption in lesson #4683: even with NO global `disable-renderer-backgrounding` / `disable-background-timer-throttling` flags, `setBackgroundThrottling` still can't be scoped per-view inside one window.
- Keep the freeze path (`Page.setWebLifecycleState`, Efficiency profile) separate from the throttle path — they are independent CDP mechanisms; this PR only changed throttle.
- When sampling renderer-health metrics (LoAF/ELU in `globalServicesInit.ts`), only sample the active view — CPU-throttled or frozen cached views produce burst lag signal that doesn't reflect user-visible jank.

## Applies when

- Adding or debugging per-view CPU/timer throttling for `WebContentsView` instances in `ProjectViewManager`/`ProjectViewLifecycleController` or any multi-view single-`BrowserWindow` Electron layout.
- A `setBackgroundThrottling(true/false)` call appears to have no effect, or background views consume unexpected CPU.
- Working in `electron/utils/webContentsLifecycle.ts`, `electron/window/ProjectViewLifecycleController.ts` (`deactivateEntry` / `activateView`), or `electron/window/globalServicesInit.ts` metric sampling.
- Choosing between freeze (`Page.setWebLifecycleState`) vs throttle (`Emulation.setCPUThrottlingRate`) for a cached renderer that must still receive live MessagePort/IPC traffic.
- Reviewing lessons #4683 / #3508 about backgroundThrottling — this is the per-window-scope gotcha they don't cover.
