## Context

The project switcher (`⌘⌥P` modal, `useProjectSwitcherPalette.ts` + `ProjectSwitcherPalette.tsx`) lists projects and lets arrow keys/Enter walk them. Modal browse shows only switchable projects (active, background, or holding processes) — closed/idle ones are dropped. The hook produced one `results` array for ranking/paging, but the component applied a second, narrower filter (`displayResults`) just for modal-mode rendering, then mapped selection back onto the original array via a `resultIndexMap` id→index lookup.

## Problem

Arrowing down through the modal list made the highlight vanish for one keypress, then reappear on the next project down (issue #11071). Pressing Enter during that blank step switched to a project not on screen at all. It looked like a rendering glitch, but the defect was in the selection model, not the row markup — `aria-activedescendant` named an id with no matching DOM node, a WAI-ARIA violation (screen readers drop or repeat stale announcements), not just a cosmetic flash.

## Root cause

`selectedIndex` and `selectNext`/`selectPrevious` were bounds-checked and stepped against the full, unfiltered `results` array, but `ProjectListContent` rendered `displayResults`, a component-local `.filter()` of that same array for modal mode. The two arrays diverge the moment any row is filtered out. When the roving index landed on a project present in `results` but absent from `displayResults`, `resultIndexMap.get(project.id)` resolved for every rendered row except the filtered ones, so nothing matched `index === selectedIndex` — the highlight (and `aria-activedescendant`) pointed at an unrendered row. Enter still fired against `results[selectedIndex]`, committing that invisible project.

A second bug shared the same root: `selectedIndex` was itself a raw number, not derived from an id. Because `results` can shrink while open (an agent-count push demotes a project, a background project exits), a tracked index can silently start addressing a different project than the one picked, even with the two-array bug fixed. The fix treats the _project_ as selection state and derives the index by `findIndex` against whatever `results` currently is: `useProjectSwitcherPalette.ts` now holds `selectedProjectId` and computes `selectedIndex = results.findIndex(p => p.id === selectedProjectId)` in a `useMemo`, falling back to 0 only when nothing matches. The component was simplified to match — `displayResults`/`resultIndexMap` are gone, rows get `isSelected` by `project.id === results[selectedIndex]?.id`. `buildResults()` now does rank → scope → cap in that order (`useProjectSwitcherPalette.ts:215-224`) so the cap applies to the eligible set — a background project past the first 15 unscoped rows still surfaces. Scope also lifts on the live query (`isSearching`) while ranking follows the deferred one, so clearing search doesn't flash "No projects match" against a stale scoped list for one frame.

## Lesson

- **A list with roving keyboard selection may have exactly one array**: the thing rendered, the thing indexed, and the thing arrow keys walk must be the same reference. Apply any scoped/filtered view where `results` is _built_ (inside the hook), never as a second `.filter()` at the render site — a second array is what let `aria-activedescendant` point at an unrendered id.
- **Track selection by identity (id), derive the index, never store the index as state.** An index survives a list mutation by pointing at whatever now occupies that slot; an id-derived index (`results.findIndex(p => p.id === selectedId)`) degrades gracefully, falling back only when the row is truly gone. Any list whose backing array can change while open (async stats, live filtering) needs this pattern.
- **Resolve the "current" row inside the state updater when stepping selection**, not by closing over a value from the render that scheduled the step: `setSelectedProjectId(prev => { const from = results.findIndex(p => p.id === prev); ...})`. Two `selectNext()` calls batched into one tick then compose instead of the second overwriting the first.
- **When ranking (deferred, expensive) and scoping (cheap membership check) both gate a list, drive scope off the live value and ranking off the deferred one** if the two can visibly disagree mid-transition — deriving both from the deferred query flashed "No projects match" over a scoped-empty list on the first keystroke.
- **A blinking or vanishing selection highlight in any listbox/combobox is an `aria-activedescendant` resolution bug before a CSS bug** — check the highlighted id resolves to a DOM node with `role="option"`; the test pattern (`document.getElementById(activeDescendantId)` non-null for every index) generalizes to any custom listbox here.
- **A counter/badge reflecting state outside the visible/filtered list needs its own source, not the scoped array** — the toolbar's background-agent badge read `projectSwitcher.results` (scoped for modal display) and blinked off whenever a project's agent count landed before its process count did; #11077 added `nonActiveAgentCounts` from the unscoped `searchableProjects`.

## Applies when

- Building or reviewing any palette/listbox/combobox with roving keyboard selection where the rendered list can be filtered, capped, or reordered while open.
- Diagnosing a highlight that disappears for one step, jumps unexpectedly, or an Enter/click that activates something not visibly highlighted — suspect two arrays before CSS or the row component.
- Touching `useProjectSwitcherPalette.ts`'s `results`/`buildResults`/`selectedIndex`/`step`, or `ProjectSwitcherPalette.tsx`'s render loop — the single-array/derived-index invariant must hold after your change.
- Adding a badge/counter that reads a palette's scoped `results` array — check whether it needs the unscoped equivalent so presentation filtering can't hide real state.
- Reviewing `aria-activedescendant` usage anywhere in the app — it must resolve to a currently-rendered `role="option"` node, never an id from a superset list.
