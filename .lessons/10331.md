## Context

`app.whenReady()` in `electron/main.ts` was `await import("./services/PluginService.js")` before `createWindow()`, purely to hand `registerPluginProtocol` a `getPluginDir` resolver for the `plugin://` scheme. That pulled a ~2900-line module and its whole static graph (`semver`, `zod`, `PluginMcpSupervisor`, ~6 `plugin/*` submodules) onto the first-paint critical path — evaluated before the `WebContentsView` even exists — for a single function reference. #10331 (issue #10322) moved the import off that path.

## Problem

Window reveal was gated behind evaluating the entire PluginService graph, yet `plugin://` requests don't arrive until after the renderer mounts and plugins activate — well after first paint. The naive fix (defer the import, populate the resolver later) is a trap: the deferred `plugin-service` task in `globalServicesInit.ts` already re-imports the same module (`import()` is module-cached, so it's a cache hit — the eager import saved nothing, it just pulled evaluation earlier), but you cannot simply reach back and update the resolver of a protocol handler that was already registered.

## Root cause

This is a design-forces lesson, not a bug. Two Electron facts box in the fix. (1) `createPluginProtocolHandler(getPluginDir)` closes over its resolver argument, and `protocol.handle(scheme, handler)` freezes that closure — there is no API to reach an already-registered handler and swap what it calls. A bare setter reassigning a variable the handler captured by value would never be seen. (2) `plugin://` is session-scoped: `registerProtocolsForSession` (per-project `WebContentsView` sessions) only wires the handler `if (cachedGetPluginDir)`, so the resolver must be cached synchronously before `createWindow`, and the `protocol.handle` call itself must stay synchronous-before-window — deferring registration (not just the import) lets an early request hit an unregistered scheme and fail with `ERR_UNKNOWN_URL_SCHEME`. `protocol.unhandle` then re-`handle` on swap reopens exactly that micro-tick gap.

The fix threads both: register early with a placeholder resolver `registerPluginProtocol(() => undefined)` (every request 404s) but wire the handler to a module-scoped `resolvePluginDir` indirection — `createPluginProtocolHandler(resolvePluginDir)`, NOT `createPluginProtocolHandler(getPluginDir)`. `resolvePluginDir` reads `cachedGetPluginDir` live at request time. The deferred task then calls `setPluginDirResolver((id) => pluginService.getPluginDir(id))`, which only reassigns `cachedGetPluginDir`. The frozen closure is the stable indirection, so the swap is picked up by every handler already registered — default session plus any per-session handlers wired during `createWindow` — with no re-registration.

## Lesson

- **To make an Electron `protocol.handle` resolver swappable after registration, freeze a stable indirection function in the handler closure and have it read a mutable module variable per request — never freeze the real resolver.** Here the handler always closes over `resolvePluginDir`; `setPluginDirResolver` just mutates `cachedGetPluginDir`, and both default-session and per-session handlers see it live. A setter that reassigned a value the handler captured directly would silently keep serving the stale (placeholder) resolver.
- **Never `protocol.unhandle`/re-`handle` to swap a scheme's implementation.** It opens a micro-tick window where a request to that scheme fails with `ERR_UNKNOWN_URL_SCHEME`. Keep the registration call synchronous-before-window; only defer the module _evaluation_, and mutate behind the indirection.
- **Defer heavy module evaluation off first paint with a placeholder-then-swap, not by deferring registration.** Register `plugin://` before `createWindow` with `() => undefined` (404s), import PluginService in the post-first-interactive `plugin-service` deferred task, then swap the resolver. `import()` is module-cached so nothing loads twice — you only move the ~2900-line evaluation off the window-reveal path.
- **Session-scoped protocols gate on the cached resolver being truthy at `createWindow` time.** `registerProtocolsForSession` wires `plugin://` only `if (cachedGetPluginDir)`; the early placeholder registration flips that gate true so per-project `WebContentsView` sessions get the handler. Defer the whole registration and per-session views silently never get the scheme.
- **Keep the swap unconditional on init failure (partial-failure posture).** The deferred task swaps the resolver and drains the open-file installer _even when_ `pluginService.initialize()` rejects — so plugins that did load can still serve assets. Tests in `globalServicesInit.order.test.ts` lock this.
- **Known residual, accepted:** `initialize()` broadcasts `plugin:panel-kinds-changed` a microtask before `setPluginDirResolver` runs, so a plugin panel restored from persisted state can 404 its first asset — self-heals via `PluginViewHost`'s `ErrorBoundary` "Try again", not worth a synchronous barrier.

## Applies when

- Touching `electron/setup/protocols.ts` (`registerPluginProtocol`, `setPluginDirResolver`, `resolvePluginDir`, `registerProtocolsForSession`, `createPluginProtocolHandler`) or any custom-scheme registration whose resolver/backing service isn't ready at registration time.
- Deferring a heavy module (`PluginService` or similar) off the `app.whenReady()` → `createWindow` first-paint path while needing something it provides registered synchronously before the window.
- Reaching for `protocol.unhandle`/re-`handle` to change a scheme's behavior at runtime — stop; use a module-scoped indirection the frozen handler reads live.
- Diagnosing a custom-scheme request that 404s or throws `ERR_UNKNOWN_URL_SCHEME` shortly after launch, or a restored plugin panel that fails its first asset fetch then recovers on retry.
- Adding a new per-session (per-project `WebContentsView`) protocol and wondering why project views don't get a scheme the default session has.
