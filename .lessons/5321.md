## Context

`electron-store` schema migrations live as ~19 modules under `electron/services/migrations/`, re-exported from a barrel `migrations/index.ts` and run once on startup by `MigrationRunner` in `electron/window/globalServicesInit.ts` (originally `windowServices.ts`). The migrations barrel transitively imports heavy modules (e.g. `ProjectStore` in `003-migrate-recipes-to-project.ts`), so eagerly parsing it costs startup time for the overwhelmingly common case: a user whose store is already at the latest version and has zero pending migrations.

## Problem

The startup path statically imported `{ migrations }` from the barrel, paying full parse cost on every launch even when no migration would run. The fix wants the barrel split into its own chunk that is only fetched when work exists — but a bundler will only emit a separate chunk for `await import("../services/migrations/index.js")` if there is **no surviving static import** of that same module graph anywhere in the bundle. One leftover `import { migrations }` collapses the dynamic import back into the main chunk and the lazy-load silently does nothing.

## Root cause

Two non-obvious coupling points:

1. **Bundler chunk-splitting is all-or-nothing per module.** esbuild/Rolldown only hoist a module into a separate `chunks/migrations-*.js` if every reference is dynamic. The win required deleting the static `import { migrations }` from the startup file, not just adding the `await import`.
2. **You cannot ask the runner "is anything pending?" without loading the barrel** — that would re-import the thing you are trying to avoid. So the gate is a hand-maintained constant `LATEST_SCHEMA_VERSION` in `StoreMigrations.ts`, compared against `migrationRunner.getCurrentVersion()` (which reads only the persisted `_schemaVersion`, no migration modules). The dynamic import fires only when `currentVersion !== LATEST_SCHEMA_VERSION`. A hand-maintained constant drifts: bump a migration without bumping the constant and up-to-date stores skip a real migration, or worse, never run. The guard is a unit test asserting `LATEST_SCHEMA_VERSION === Math.max(...migrations.map(m => m.version))`. That test must `vi.mock("electron")` before importing the barrel, because the barrel touches `electron.app.getPath` at module-load time (via `ProjectStore`) — importing it in a non-Electron vitest context throws otherwise.

## Lesson

To lazy-load a module behind a "do we even need it?" gate: (1) the gate predicate must be answerable WITHOUT importing the gated module — derive it from cheap already-loaded state (here, the persisted `_schemaVersion`); (2) delete every static import of the gated module or the bundler merges the chunk and the `await import()` becomes a no-op — verify with `npm run build:main` that a separate `chunks/*.js` exists; (3) if the gate is a hand-maintained constant mirroring data, add a drift-guard test asserting they match; (4) that test will likely need `vi.mock("electron")` before the barrel import, because migration/store modules touch `electron.app` at load time.

## Applies when

Adding lazy `await import()` to skip startup parse cost for a barrel or heavy module; gating any dynamic import on a hand-maintained version/feature constant; adding a new store migration (must bump `LATEST_SCHEMA_VERSION`); writing a vitest that imports anything transitively reaching `electron.app` at module load.
