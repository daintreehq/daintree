## Context

The GitHub toolbar pill shows issue/PR/commit counts. On cold launch the count comes from a network poll (`getRepoStats`), but disk caches (`GitHubStatsCache`, `GitHubFirstPageCache`) usually already hold valid numbers. `useRepositoryStats` runs a one-shot hydration effect that reads the disk cache via IPC and seeds the pill before the first poll lands.

## Problem

The pill flashed an em-dash placeholder on every cold start even when real cached counts were on disk. A naive fix that reused the strict cache read would silently fail: `GitHubStatsCache.get()` rejects anything older than its 10-minute `MAX_CACHE_AGE_MS`, so on most launches the cache returned `null` and the pill stayed blank. Two follow-on hazards: a fast network poll could be clobbered by a slow disk hydration landing afterward, and switching projects mid-hydration could apply the previous project's counts.

## Root cause

One TTL cannot serve both consumers. The polling path needs freshness (10 min strict — see #2025: a poller's cache TTL must be shorter than its cadence). The cold-start path wants the _opposite_ policy: "old number marked stale" beats an em-dash, so it should accept much older data. Reusing `get()`'s strict TTL for hydration defeats the whole feature.

The race had two parts. (1) The disk read is async IPC; a network result (success _or_ error) can land first, and `setCache`/`setStats` had no "already applied" interlock, so a late hydration would overwrite fresher data. (2) The original effect captured `project` before the `getFirstPageCache` await and only checked `cached.projectPath !== project.path` once — but a project switch firing during the await means `project` itself is the stale identity, so the comparison passes against the wrong project.

## Lesson

- Give a shared cache **two read methods with different TTLs** when it has two consumers with opposite freshness needs. `GitHubStatsCache.getForBootstrap(repoKey, maxAgeMs = 60*60*1000)` shares the disk path and validation of `get()` but accepts entries up to 60 min old; `get()` stays at 10 min for polling. Do not "fix" the bootstrap TTL to match the polling TTL — that reintroduces the em-dash flash.
- Add a **one-shot fresher-wins interlock** for slow async hydration that races a faster path: `hasAppliedResultRef` is set true on the first `applyStatsResult` (network success, error, or stale push) and reset to false on project switch. Hydration only seeds counts when `!hasAppliedResultRef.current`, so a late disk read can never clobber an already-applied network result or error.
- **Re-verify the current identity after _every_ await**, not just once with the pre-await value. After `getFirstPageCache` resolves, re-read `projectClient.getCurrent()` and bail if `currentProject.path !== project.path` (the captured identity) — this is what detects a switch that happened during the await. This is the renderer-hook analog of #2773's main-side scope-id tagging and #1377's monotonic checkId.
- Keep a **stats-only payload distinct from an items payload**: when the first-page items cache expired but stats are still inside the bootstrap window, the IPC returns empty `issues`/`prs` arrays with valid `stats`. Guard `if (cached.issues.items.length > 0)` before seeding the renderer items cache so empty arrays never overwrite real items.

## Applies when

- Building or reviewing cold-start / first-paint hydration that reads a disk or IPC cache before a network refresh lands (toolbar pills, sidebar counts, dashboard summaries).
- A single cache (`GitHubStatsCache`, `githubResourceCache`, git-status cache) is read by both a strict freshness-sensitive poller and a "stale-but-real beats blank" bootstrap path — design two TTLs, not one.
- Debugging "placeholder/em-dash flashes on launch even though data is cached", "fast network result gets overwritten by a stale value a moment later", or "previous project's counts briefly show after switching".
- Any async effect in a React hook that captures an identity (project path, repo key, worktree id) before an `await` and then mutates shared state — re-read and compare the live identity after the await before applying.
