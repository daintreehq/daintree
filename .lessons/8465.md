## Context

`agent.focusNextWaitingGlobal` (`Cmd+Shift+Alt+/`) jumps to the next project that has a waiting agent, switches `WebContentsView`, then focuses the waiting terminal. Daintree gives each project its own `WebContentsView` with an independent V8 context (`ProjectViewManager`, `#4672`). A project switch swaps which view is attached, destroying / detaching the initiating view's renderer context.

## Problem

A naive "switch, then focus" action would dispatch `switchProject(...)` and then call the focus logic in the same renderer. But the moment the view swaps, the initiating V8 context is torn down — any continuation in that renderer never runs. Even if the focus were re-issued from the _incoming_ view on paint, dispatching `agent.focusNextWaiting` at that moment silently no-ops: the paint signal fires before `panelStore` hydrates, so `panelStore.panelIds` is still empty and there's no terminal to focus.

## Root cause

Two distinct ordering constraints stack on top of each other, and getting either wrong yields a silent no-op (no error, focus just never happens):

1. **The initiator is gone.** Cross-context post-switch work cannot live as a callback in the initiating renderer. It must be parked as main-process state and re-delivered to whichever view becomes active. The fix stores a one-shot `pendingFocusIntent` _on the `ProjectViewManager` instance_ (not a module global — multi-window must not cross-leak), set in the switch handler **before** `activateProjectView`. PVM owns the lifecycle: consumed exactly once, and discarded on paint-gate timeout / load failure / project-id mismatch so a later unrelated switch can't pick up a stale focus jump.

2. **Paint ≠ hydration.** Main delivers the intent only after the paint gate resolves with `"signal"` (`signalViewPainted` → `consumePendingFocusIntent` → targeted `webContents.send(PROJECT_FOCUS_ON_ACTIVATE)`; never broadcast, per `#4641`/`#5010`). But the paint signal arrives after the first React commit and _before_ `useAppHydration` finishes. So the renderer receiver (`useFocusOnActivateIntent`) must subscribe unconditionally on mount (to beat the paint signal) yet **buffer** the intent in state and only fire the local `agent.focusNextWaiting` dispatch when `isStateLoaded` transitions true.

Cached-view reactivation skips the paint gate entirely, so that path delivers the intent synchronously inside `switchTo`'s cache-hit branch instead.

## Lesson

When an action needs to do work in the renderer _after_ a project/view switch:

- Do not chain the post-switch work in the initiating renderer — its V8 context dies on the swap. Thread an intent through the switch IPC payload (`options.focusIntent`), store it as a one-shot on the per-window `ProjectViewManager` instance, and have the incoming view consume it.
- The intent must be consumed exactly once and cleared on every terminal outcome (delivered, paint-gate timeout, load failure, project-id mismatch). Otherwise a later unrelated switch re-triggers it.
- Deliver only on a positive paint signal (`gateResult === "signal"`); a timeout means there's no proof the receiver is mounted — drop, don't fire blind.
- In the renderer receiver: subscribe on mount (unconditionally, to register before paint fires), but gate the actual dispatch on `isStateLoaded`, not on receipt. `isStateLoaded`/paint comes _before_ `panelStore` hydration; dispatching against an empty store silently no-ops.
- Send targeted to the specific incoming `webContents`, never broadcast across windows.

## Applies when

- Adding any action that switches projects/views and then must act on the newly-activated renderer (focus a panel, scroll, open something, run a command) — `agent.*`, `navigation.*`, project-switch-triggered follow-ups.
- Wiring a new `project:*` push-event channel that the _incoming_ view must receive after `ProjectViewManager.switchTo`.
- Debugging a "switch happens but the follow-up action silently doesn't" symptom across a project switch, especially when it works on a cached view but not on cold start (or vice-versa).
- Any new per-switch state on `ProjectViewManager` — confirm it's instance-scoped (multi-window) and cleared on the cold-start timeout/error/cache-hit paths, mirroring `pendingFocusIntent` / `consumePendingFocusIntent`.
- Distinguishing the paint signal (`signalViewPainted`, `isStateLoaded` first-paint) from `panelStore`/`useAppHydration` completion when timing renderer-side reactions to a view becoming active.
