## Context

`EVENT_POLICY` in `src/lib/notify.ts` is a typed `Record<NotificationEventKind, EventPolicy>` that `notify()` consults at dispatch to fill routing defaults the caller omitted (`baseInterruption` → priority/urgent, `preferredSurface`, `defaultDurationMs`, `userOverrideKey`). It replaced a per-call-site four-question checklist and is documented as the "single typed source of truth" for routing across the ten notification kinds. The manifest PR (#9008) also shipped `shouldReToast` in `src/lib/notificationSeverity.ts` — the thread re-promotion predicate — and left an `EventPolicy` field `reToastOnSeverityEscalation` behind, JSDoc'd "Reserved for future escalation wiring — not behavioral yet."

## Problem

The reserved field looked like live routing config but had **zero readers** anywhere in `src/`, `shared/`, or `electron/` — only its interface definition and the ten manifest literals. Worse, it actively misstated reality: the manifest set it `true` for `host`/`recovery` and `false` for the other eight kinds, so anyone reading the manifest concluded host/recovery escalations re-toast and git/agent escalations don't. In fact **all** kinds re-toast on severity escalation, because `shouldReToast` never consults the manifest. #10061 flagged it: a field that contradicts shipped behavior in a manifest sold as the source of truth is a trap for the next maintainer.

## Root cause

`shouldReToast(payloadType, threadEntries, urgent)` is **deliberately kind-agnostic**. It re-toasts a `correlationId`-bearing notification (that the normal gate would route inbox-only) when the payload is `urgent`, when incoming severity strictly exceeds the thread's worst _active_ (non-archived) severity, or when the whole thread was archived (un-snooze). It takes the notification `type` (error/warning/info/success) and the thread's history — never the `eventKind`, never `EVENT_POLICY`. It is called unconditionally on both dispatch paths in `notify.ts`: the grid-bar auto-resurface path (`wouldRePromote`, ~L918) and the main path (`wouldRePromoteThread`, ~L972). So severity-escalation re-toast is one dimension of notification behavior that lives **outside** the routing manifest on purpose — a global cross-cutting rule that layers on top of routing, not a per-kind opt-in.

That is why the field was a live trap, not harmless clutter. The obvious "make the dead field do something" move — gate `shouldReToast` on `EVENT_POLICY[kind].reToastOnSeverityEscalation` — would have **silently disabled already-shipped escalation re-toast for the eight `false` kinds** (an `info` git thread that turned `error` would stop re-surfacing). #9008's own body anticipated the split: the manifest "naturally carries `reToastOnSeverityEscalation` per kind, but `shouldReToast` can ship as a global rule independent of it." The global rule shipped; the per-kind flag stayed behind as a speculative placeholder and rotted into a contradiction. #10241 deleted the field from `EventPolicy` and all ten `EVENT_POLICY` entries, and JSDoc'd `shouldReToast` as kind-agnostic/global so it isn't reintroduced.

## Lesson

- **`EVENT_POLICY` is total for routing, not for all notification behavior.** Severity-escalation re-toast is intentionally global (`shouldReToast`) and does not read the manifest — do not assume the manifest describes everything a kind does, and do not "complete" it by adding a per-kind escalation field. If you want per-kind escalation control you must wire `shouldReToast` to read it _and_ accept the behavior change; otherwise leave escalation global.
- **A zero-reader manifest field whose values contradict shipped behavior is a trap — delete it, don't honor it.** Honoring `reToastOnSeverityEscalation` (host/recovery `true`, eight kinds `false`) would have silently regressed re-toast for those eight. When a "reserved for future wiring" field's implied behavior disagrees with what already ships, the safe resolution is removal plus a JSDoc note documenting the real rule next to the code that implements it (`shouldReToast`), not making the field load-bearing.
- **Verify a "reserved / not behavioral yet" field before acting on it.** Grep `src/`, `shared/`, `electron/` for readers first. If the only references are the definition and its manifest literals, and the behavior it "reserves" already ships elsewhere, it is dead config — the placeholder was superseded, not pending.
- **Document cross-cutting global rules at the function that enforces them, not in the routing manifest.** The fix put the kind-agnostic note on `shouldReToast` in `notificationSeverity.ts` precisely because the manifest is the wrong place to teach "this dimension is global" — a maintainer reading `EVENT_POLICY` should not have to infer it.

## Applies when

- Touching `EVENT_POLICY` / `EventPolicy` in `src/lib/notify.ts` — adding a per-kind field, or assuming the manifest fully describes a notification kind's behavior (escalation re-toast is not in it).
- Working on notification thread re-promotion, severity escalation, un-snooze, or `shouldReToast` in `src/lib/notificationSeverity.ts` — it is kind-agnostic by design; gating it per-kind is a behavior change that would drop re-toast for the majority of kinds.
- Encountering any field JSDoc'd "reserved for future wiring / not behavioral yet" whose manifest values seem to disagree with observed behavior — grep for readers before honoring it.
- Reviewing a change that "wires up" a dormant config flag to make it functional — confirm the behavior it would introduce isn't the opposite of what already ships.
