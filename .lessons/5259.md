## Context

`electron/services/TelemetryService.ts` initializes `@sentry/electron` via `Sentry.init({...})` to capture main-process crash reports, scrubbed through a `beforeSend` (`sanitizeEvent`) sanitizer.

## Problem

The init options carried `sampleRate: 0.1`, which silently discarded 9 of every 10 error events before they ever left the process. The result was a 90% blind spot in crash reporting that no test, log, or runtime signal surfaced — crashes simply never arrived in Sentry.

## Root cause

In the Sentry SDK, `sampleRate` is the _error/message_ capture sample rate: it applies to `captureException` / `captureMessage` (i.e. crash reports), NOT to performance tracing. Performance trace sampling is a separate knob, `tracesSampleRate`. The two are easy to conflate because tracing-heavy example configs prominently set a fractional `tracesSampleRate`, so `sampleRate: 0.1` reads at a glance like "sample 10% of perf traces" when it actually means "throw away 90% of crashes". The SDK applies it silently with no warning, and a fractional value looks intentional in review.

## Lesson

Leave `sampleRate` unset so it defaults to `1.0` (100% error capture) — for a crash reporter you almost never want to sample errors away. Reserve fractional sampling for `tracesSampleRate` (performance) only. The fix removed the field entirely and added a _fail-closed_ regression test (`electron/services/__tests__/TelemetryService.test.ts`) asserting `options` passed to `Sentry.init` does `not.toHaveProperty("sampleRate")`, so any reintroduction at any value is caught — testing for absence, not a specific value, is the right shape because any value < 1 is the bug.

## Applies when

Editing `Sentry.init` options anywhere (`TelemetryService.ts`), or any crash/error reporter that exposes separate error-sampling vs trace-sampling rates; reviewing a fractional `sampleRate` in telemetry config; or adding performance tracing (use `tracesSampleRate`, never repurpose `sampleRate`).
