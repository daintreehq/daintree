## Context

Each project lives in its own `WebContentsView` with an independent V8 context, managed by `ProjectViewManager` (`electron/window/ProjectViewManager.ts`). A _cold_ switch (no cached view) spawns a brand-new renderer process: Chromium loads the bundle, React mounts, then Zustand stores hydrate from disk. A _cached_ reactivation reuses an already-painted renderer.

## Problem

On a cold switch the old `WebContentsView` was detached the instant the switch began, then the new view was attached and `loadView()` awaited. Between attach and the first React commit the user saw a blank-canvas flash — the new renderer's compositor surface was attached but had no painted content yet. `did-finish-load` does not help: it fires when the document finishes loading, well before React commits its first frame, so swapping on it still flashes.

## Root cause

A `WebContentsView`'s compositor surface goes live (and blank) the moment `addChildView` runs, but useful pixels only exist after the renderer's first React commit _and_ Chromium submitting that frame — two events `loadView()`/`did-finish-load` cannot observe from the main process. The only authority on "first useful paint" is the renderer itself, and the cross-V8-context boundary means the main process must wait for an explicit IPC signal. Naive waits drop the signal: the renderer fires `APP_VIEW_PAINTED` exactly once per V8 context (one-shot, never retried), and on a fast cold disk that signal can land on the same tick as `did-finish-load` — if the gate isn't armed before `loadView()`, every fast switch falls through to the timeout.

## Lesson

For seamless cold cross-context view swaps under the per-project `WebContentsView` architecture:

- **Keep the outgoing view visually on top.** Insert the incoming view BEHIND it via `addChildView(view, 0)` — Chromium's child stack is z-ordered last-on-top, so index 0 keeps the booting view hidden until you detach the outgoing one in a single frame. Resize the outgoing view too while the gate is open (the `resizeHandler` syncs `pendingPaintGate.outgoingView` bounds) so a mid-switch window resize doesn't desync.
- **Gate on a renderer paint signal, not a load event.** The renderer fires `notifyViewPainted()` (`src/App.tsx`) from a `useEffect` placed in the Suspense _parent_ (so it commits even while `AppInner` is suspended on `app:boot`), via double-rAF: first rAF lands after React's commit, second waits for Chromium to submit the frame. It is idempotent (module-level one-shot guard) so Strict Mode's double-mount is safe.
- **Arm the gate BEFORE `loadView()`.** The one-shot signal can arrive same-tick as load; pre-arming captures it instead of dropping it.
- **Stale-check every signal by `webContentsId`.** `signalViewPainted(id)` ignores a paint from a superseded switch (`gate.webContentsId !== id`).
- **Two-tier timeout, not one.** Soft (~1.5s) only logs `projectview.paintgate.softtimeout` and keeps waiting (legitimately slow cold starts stay flash-free); hard (~4s) forcibly detaches as a last resort against a stuck/crashed renderer. A single 3s timeout (the original PR) was later split into this soft/hard pair.
- **Rollback must re-`registerAppView` the outgoing view.** On load failure the failed incoming view had already overwritten the app-view registration; restore `registerAppView(this.win, previousEntry.view)` so `getAppWebContents()` keeps resolving for portal/voice/accessibility IPC instead of falling through to the bare `BrowserWindow` webContents.
- **Cached reactivations skip the gate** — the destination is already painted; detach immediately.

## Applies when

- Touching `ProjectViewManager` cold-start / swap / eviction / rollback paths, or `waitForPaint` / `signalViewPainted` / `pendingPaintGate`.
- Adding any new `WebContentsView`-per-X surface (portal tabs, multi-window) that must swap without a blank flash.
- Debugging a blank-canvas flash, a stuck/never-detaching outgoing view, or `projectview.paintgate.softtimeout` / `.hardtimeout` warnings.
- Wiring a main-process gate that depends on a one-shot renderer IPC signal (the arm-before-load + webContentsId stale-check + timeout-fallback triad).
- Moving the `notifyViewPainted` double-rAF effect in `src/App.tsx`, or adding work that could delay React's first commit relative to hydration.
- Distinguishing this main-process compositing flash from the renderer-side Zustand atomic-swap flash (#4451) — they are different layers and both must be handled.
