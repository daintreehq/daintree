## Context

`assertPathAllowed` in `electron/ipc/handlers/systemShell.ts` guards every renderer-supplied path before it reaches a system sink (`shell.openPath`, `EditorService.openFile`, `shell.showItemInFolder`) behind an allow-list of project roots, worktree roots, and the app's `userData` dir, via `resolveContainedPath` from `pathGuard.ts`. Before #11278, worktree roots weren't tracked directly — `collectWorktreeParentDirs` reconstructed a predicted _parent_ directory by resolving the worktree path pattern (`shared/utils/pathPattern.ts`) against each project root, reading only the global `worktreeConfig.pathPattern` (plus `DEFAULT_WORKTREE_PATH_PATTERN`).

## Problem

Issue #11277: opening a file from inside a worktree via "Open in Editor" or "Reveal in Finder" failed with `[OUTSIDE_ROOT] Path is outside all allowed roots`, while the file viewer panel displayed the exact same file without complaint. That asymmetry was the misleading part — it pointed at "the file viewer must know something the shell handler doesn't" rather than at the shell handler's containment logic, because `files.ts` trusts a caller-supplied `rootPath` (the panel already knows the worktree root) while `systemShell.ts` reconstructs its own root set from scratch.

## Root cause

Predicting the worktree parent from a pattern was simultaneously too broad (admitting the predicted parent wholesale admits _every_ child under it, worktree or not) and too narrow: the reconstruction only read the _global_ `worktreeConfig.pathPattern`, never the per-project `worktreePathPattern` override that `resolveWorktreePattern` (`electron/utils/worktreePattern.ts`) treats as authoritative — so a project with a custom pattern had every one of its worktrees fall outside all allowed roots, and a worktree created by hand via `git worktree add` was never predictable at all.

The fix stops predicting and asks git: `collectTrackedWorktreeRoots` calls `gitServiceCache.getGitService(root).listWorktrees()` per project root and admits each _returned path itself_ as a root, never a derived parent — strictly narrower and strictly more complete.

Trusting `listWorktrees()`'s raw output blindly would have reopened the same hole, though — three vetting steps were layered in across three same-day commits as review caught each gap. (1) `isAdmissibleRecord` excludes `bare: true` entries: a linked worktree's record can describe its _bare backing repository_ (e.g. `/srv/repo.git`), and admitting it hands out the object store, refs, config, and hooks. (2) It drops any record whose path equals the filesystem root, since `resolveContainedPath` special-cases `realRoot === nodePath.sep` to mean "contains every absolute path." (3) `isLiveWorkingTree` probes `fs.access(join(candidate, ".git"))`, because git keeps listing a worktree directory as tracked ("prunable") after it's deleted from disk until `git worktree prune` runs, and `GitService.listWorktrees()`'s porcelain parser doesn't filter these out. If that stale path is later reused by anything unrelated, `fs.realpath` alone succeeds — the `.git` check is the _only_ thing left standing between a reused directory and a granted root. The probe stays narrow: only `ENOENT`/`ENOTDIR` disqualifies, since an `EACCES` or transient I/O error says nothing and would lock users out of a real worktree over a permission hiccup.

## Lesson

- **Never build a security-relevant allow-list by predicting where resources "should" live from a config pattern — enumerate the actual tracked state.** Prediction over-admits (every child of a guessed parent) and under-admits (per-entity overrides, manual out-of-pattern creation) at once; `collectWorktreeParentDirs` missed `worktreePathPattern` entirely because it only read the global config key.
- **An enumerated list from an authoritative source still needs per-record vetting before it becomes a containment root.** `bare` worktree records describe the backing bare repo, not a working tree — granting one exposes the object store/hooks. A record equal to the filesystem root is a universal grant, since `resolveContainedPath` treats `realRoot === path.sep` as "contains everything."
- **Enumerated does not mean present on disk.** Git keeps listing a deleted worktree as tracked until `git worktree prune` runs. If that stale path is later reused by anything unrelated, `fs.realpath` succeeds fine; only confirming the marker that makes it a worktree (an on-disk `.git` entry) still catches it. Treat liveness-confirmation as mandatory whenever enumerated git/filesystem state feeds an authorization decision, not a display list.
- **A liveness probe backstopping an authoritative source should only disqualify on a definitive not-found.** `isLiveWorkingTree` rejects only on `ENOENT`/`ENOTDIR`; an `EACCES` or transient I/O error says nothing about existence and must not lock a user out of a worktree git already confirmed is real.
- **Defer expensive per-entity verification until the cheap check actually needs it.** `assertPathAllowed` only calls into git after the base-roots check throws `OUTSIDE_ROOT` — a union-containment check is identical to checking against whichever root actually contains the path, so the common in-project-root case stays subprocess-free.

## Applies when

- Touching `systemShell.ts` (`assertPathAllowed`, `collectTrackedWorktreeRoots`, `isAdmissibleRecord`, `isLiveWorkingTree`) or any allow-list gating `shell.openPath` / `EditorService.openFile` / `shell.showItemInFolder`.
- Building or reviewing a path/resource containment check that derives its allow-list from a config pattern (`worktreePathPattern`, `shared/utils/pathPattern.ts`) instead of actually-tracked state (`GitService.listWorktrees()`, workspace-host).
- Diagnosing "the file viewer can open this file but Reveal in Finder / Open in Editor rejects it with `OUTSIDE_ROOT`" — check whether the rejecting handler reconstructs its own roots instead of trusting a caller-supplied `rootPath` the way `files.ts` does.
- Adding a new consumer of `GitService.listWorktrees()` for anything security- or authorization-adjacent — its porcelain parser does not filter bare or stale/prunable entries, so the caller must.
- Reviewing enumeration code that treats an external system's list as already-trustworthy — check whether entries need excluding (bare, root-pointing) or liveness-confirming (stale-on-disk) before being used as a grant.
