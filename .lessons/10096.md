## Context

Forge providers are plugin-contributed (`registerForgeProvider` binds a `ForgeProviderImpl`; GitHub ships as a builtin plugin, keeping the host forge-neutral). #8454 added a generic `credentialFields` form in Preferences → Code Forge so a second provider (GitLab, Gitea) could collect a token: `FORGE_SET_CREDENTIAL` validated via `impl.validateToken(primaryValue)`, persisted the record under the `forgeCredentials` electron-store key, and pushed to the workspace host. The `ForgeProviderImpl` contract (`shared/types/forge.ts`) already declared `setCredentials?`/`getCredentials` for exactly this handoff.

## Problem

For any non-GitHub provider, a saved token never reached the impl: every `listIssues`/`listPRs`/`getCIStatus` call ran unauthenticated, both immediately after save and after restart (#9983). Every observable signal was green — `validateToken` succeeded (it is called with the raw form value directly, not through the impl's stored auth), the store was populated, and `GenericCredentialForm` showed "{provider} connected" off the store flag alone. The builtin GitHub plugin masked the hole for months: it declares no `credentialFields` and reads its token through its own legacy path (`GitHubTokenOrchestrator`), so the only shipped provider never exercised the generic path at all.

## Root cause

`impl.setCredentials` had zero callers anywhere in the codebase, and nothing ever read `forgeCredentials` back except the `hasCredential` status check — the save flow was write-only. The workspace-host push could not compensate: post-#8870, `PRIntegrationService.updateForgeCredentials` deliberately relays only presence/absence (forge calls from that process RPC back to main, where the impl reads its own auth), so the main-process impl is the SOLE authoritative credential holder — and it was the one place the credential never went. The violated invariant: a bridge from persisted config to a live object must deliver at every point where a live object can exist without having observed a save event. There are three — (1) save, (2) clear, (3) bind/rebind (`registerForgeProvider` fires on cold start, plugin reload, and dev-mode rescan, all long after any save event). #10096 wired all three: `impl.setCredentials?.({ kind: "bearer", value: primaryValue })` after validation in `FORGE_SET_CREDENTIAL`; `setCredentials(null)` in `FORGE_CLEAR_CREDENTIAL` (impl may be unbound — a user can clear while the plugin is inactive, so the lookup is guarded); and a replay at bind via the new `buildStoredCredentials` in `electron/services/forge/forgeCredentialUtils.ts`. The PR put the replay in `PluginService.registerForgeProvider`; it now lives in `electron/services/plugin/PluginHostFactory.ts` (~line 686) after the PluginService file split — same code, same comments.

## Lesson

- **A store write plus a passing validation is not delivery.** Validation ran on the raw form value, so green validation + populated store + "connected" UI all coexisted with a permanently unauthenticated impl. When wiring a settings save for a long-lived service object, grep for who reads the persisted key back — if the only consumers are a status flag and the clear handler, the path is write-only.
- **Deliver at three points: save, clear, and replay-on-bind.** Fixing only the save leaves the provider broken after every restart/reload, because `registerForgeProvider` binds a fresh impl that never saw the save event. The bind-time replay (`buildStoredCredentials` → `impl.setCredentials`) is what covers cold start, plugin reload, and dev rescan.
- **The error-handling asymmetry is deliberate — don't uniform it away.** At save time a synchronous `setCredentials` throw is intentionally uncaught (a plugin bug should surface in the settings flow, mirroring `validateToken`); at bind time the replay is try/catch'd with a `console.warn` because a plugin throw must not abort activation. Both choices are commented inline at the call sites.
- **The builtin GitHub plugin does not exercise the generic credential path** — it declares no `credentialFields` and owns its token flow. Any change to the generic path needs a fake second provider in tests (the suites register an `acme.gitea` with `credentialFields`); "works with GitHub" proves nothing here.
- **Multi-field credential forms pass exactly ONE primary value to the impl**: `pickPrimaryValue` picks the first `password`-typed declared field, else the first declared field — and it is shared between the save path (`forgeSettings.ts`) and the replay so both agree. Tests deliberately declare the password field second to catch `fields[0]`-always bugs; keep that shape when adding providers.

## Applies when

- Building or reviewing a forge provider plugin with `credentialFields` (GitLab #11062, Gitea) — verify the impl actually receives credentials at save, clear, and bind, not just that validation passes.
- Wiring any bridge from a persisted store key to a live object (plugin impl, service instance, worker) — enumerate every point a live instance can (re)appear without a save event and deliver there too.
- Diagnosing "provider shows connected but every forge call runs unauthenticated / returns empty" for a non-GitHub provider, especially when it also breaks after restart.
- Touching `FORGE_SET_CREDENTIAL`/`FORGE_CLEAR_CREDENTIAL` in `electron/ipc/handlers/forgeSettings.ts` or the `registerForgeProvider` binding in `electron/services/plugin/PluginHostFactory.ts`.
- Assuming the workspace-host credential push carries auth — `PRIntegrationService.updateForgeCredentials` relays presence/absence only (#8870); the main-process impl is the sole credential holder.
