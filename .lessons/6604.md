## Context

The Daintree Assistant launches a real Claude/Codex/Gemini/Copilot CLI against the in-app MCP server. `HelpSessionService` provisions a per-project session dir under `userData/help-sessions/<projectPathHash>/` containing a generated `.mcp.json` (or `.gemini/settings.json` / Codex `-c` args) that points the agent at `http://127.0.0.1:<port>/sse` (Claude) or `/mcp` (everyone else), authenticated with a per-launch session bearer. The bearer must reach the wire as an `Authorization: Bearer <token>` header.

## Problem

The assistant authenticated against the MCP server with `Authorization: Bearer ${DAINTREE_MCP_TOKEN}` — the placeholder went out literally and every request 401'd. The config looked correct (it mirrors how `${VAR}` substitution works for every other field), so it appeared wired but never authenticated. A second, separate failure: launching with `--strict-mcp-config` silently disabled the cwd discovery the session dir depends on.

## Root cause

Two coupled Claude-Code-specific launcher traps:

1. **`${VAR}` substitution in `.mcp.json` `headers` is broken in Claude Code** (placeholder not forwarded to the wire — `anthropics/claude-code#6204`; still broken v2.1.83–v2.1.133 as of May 2026). Worse, `claude mcp add`/`claude mcp remove` _rewrite_ `${VAR}` to its literal env value whenever they touch `.mcp.json` (`#18692`, `#57131`), so even if substitution worked it would leak the live bearer to disk. (Separately `#28293` drops headers on SSE-transport POSTs regardless — a limitation neither path fixes.) So Daintree bakes the literal token directly: `headers: { Authorization: \`Bearer ${token}\` }` (`HelpSessionService.writeMcpConfig`, `McpPaneConfigService`).
2. **`--strict-mcp-config` strips Claude's normal cwd discovery** of the session-dir `.mcp.json`. The flag was removed; action-tier help launches now spawn bare `claude` and rely on cwd discovery. The session dir also writes `.claude/settings.json` with `enableAllProjectMcpServers: true` — without it Claude interactively prompts to trust each project-scoped server on first launch, blocking the assistant.

The non-obvious part is that this is **agent-specific**, not universal. Gemini (`${DAINTREE_MCP_TOKEN}` in `.gemini/settings.json`), Copilot (`$DAINTREE_MCP_TOKEN`), and Codex (`bearer_token_env_var`) all support env-var substitution and read the bearer from `DAINTREE_MCP_TOKEN` in PTY spawn env, so **no literal token lands on disk** for them. Only Claude requires the literal-on-disk workaround, which is why the session dir is `0o700` and the file `0o600`, the token rotates every provision, and the in-memory `sessionsByToken` map (not the disk file) is the auth boundary.

## Lesson

- For Claude Code MCP configs, **never** put `${VAR}` / `$VAR` in `.mcp.json` `headers` — it won't substitute, and `claude mcp add/remove` would rewrite it to a disk-resident literal anyway. Write the literal bearer and protect it with file mode + in-memory revocation instead.
- The bearer-delivery strategy is **per agent**: literal-on-disk for Claude; env-var substitution from PTY env for Codex/Gemini/Copilot. Don't unify these into one code path — match the spawn config writer to the agent's documented substitution behavior.
- Don't pass `--strict-mcp-config` when you depend on the agent's cwd `.mcp.json` discovery; it silently strips that discovery.
- When writing project-scoped MCP servers Claude must use without prompting, set `enableAllProjectMcpServers: true` in the session's `.claude/settings.json`, or first launch blocks on an interactive trust prompt.
- Treat any literal secret written to disk as needing a separate auth boundary (here: `sessionsByToken` in memory + `0o600` file + per-provision rotation), since the disk value can't be the gate.

## Applies when

- Wiring any agent CLI (Claude/Codex/Gemini/Copilot) to the in-app MCP server, or touching `HelpSessionService` / `McpPaneConfigService` / `McpServerService`.
- Generating `.mcp.json`, `.gemini/settings.json`, or Codex `-c mcp_servers.*` config for a spawned agent and deciding how to deliver the `Authorization: Bearer` header.
- Symptoms: assistant/agent MCP requests 401 despite a config that looks correct; `Authorization: Bearer ${DAINTREE_MCP_TOKEN}` reaching the server literally; first-launch hang on a Claude "trust this MCP server?" prompt.
- Adding or removing CLI flags on help/assistant terminal spawns in `electron/ipc/handlers/terminal/lifecycle.ts` (especially `--strict-mcp-config`, `--mcp-config`, `--dangerously-skip-permissions`).
- Reviewing whether a session bearer baked into a file on disk is adequately gated (file mode, rotation, in-memory revocation).
