## Context

Daintree's anti-flicker loading strategy uses two independent gates. CSS `animate-pulse-delayed` (`src/index.css:1107`) carries `animation-delay: var(--anti-flicker-delay)` = 400ms (`src/index.css:669`) so a skeleton stays invisible for 400ms before pulsing in — the Doherty-threshold onset gate. The JS counterparts `useSkeletonGate`/`useDohertyGate` (`src/hooks/useDeferredLoading.ts`) suppress _early_ display the same way. PR #9040 added `useSkeletonDisplayFloor`/`useSkeletonFloor` to complement them with a _minimum-dwell_ floor, plus a preventive comment about a Suspense-fallback trap.

## Problem

Two failure modes around skeletons, both producing a glitch rather than a smooth load:

1. A skeleton wired as a React `Suspense` fallback would show a ~700ms blank dead-zone before the pulse even becomes visible, then a layout-shifting pop.
2. Even with the onset gate alone, when underlying work resolves _just after_ the onset gate clears, the skeleton appears and is torn down in the same frame — a same-frame flash that reads as a glitch.

## Root cause

The two anti-flicker gates compound **additively**, not by overlapping. React 19.2.6 hardcodes `FALLBACK_THROTTLE_MS = 300` (verified in `node_modules/react-dom/cjs/react-dom-client.development.js:27346` and `react-reconciler`): once a Suspense fallback commits, React throttles further fallback commits for 300ms. Stack that 300ms onset throttle on top of the skeleton's own 400ms CSS `animation-delay` and you get ~700ms of blank space before anything is visible. Nobody designed a 700ms gate; it emerged from two independently reasonable 300/400ms decisions colliding.

The same-frame flash is separate: an onset gate only governs _when display starts_, never _minimum display duration_. If `isShowing` goes true then false within one tick after the gate clears, the placeholder mounts and unmounts instantly. The fix anchors the floor to a first-reveal timestamp (`shownAtRef`, seeded at mount) so re-renders and `true→false→true` flaps cannot reset or escape it; the hide timer is scheduled for only the _remaining_ floor time. Performance mode collapses the floor to 0 via `getPerformanceModeFloor` (`src/lib/animationUtils.ts:43`); reduced-motion is deliberately NOT read in JS because CSS owns that presentation.

## Lesson

- Never wire an `animate-pulse-delayed` skeleton (or any CSS-delayed placeholder) as a React `Suspense` `fallback` — the 300ms `FALLBACK_THROTTLE_MS` and the 400ms CSS `animation-delay` add up to a ~700ms blank dead-zone. All `Suspense` in `App.tsx` correctly use `fallback={null}`. If a real fallback is ever needed, defer with `useTransition` (it bypasses the throttle and keeps `isPending` true) and render the skeleton from that pending state, not from Suspense.
- An onset gate (`useSkeletonGate`/`useDohertyGate`) and a dwell floor (`useSkeletonFloor`/`useSkeletonDisplayFloor`) are orthogonal and must be _paired_ for anything whose resolve time is unpredictable around the gate boundary — onset suppresses early display, the floor guarantees minimum display. Canonical pairing: `PortalDock.tsx:91-92` (`useSkeletonGate(isTabRestoring)` → `useSkeletonFloor(...)`).
- Anchor a minimum-dwell floor to a first-reveal timestamp, not to the last render; schedule the hide timer for the _remaining_ time, and seed the ref at mount so the floor still applies if input flips false before the first effect commits.
- Honor performance mode by collapsing JS timers to 0 (`getPerformanceModeFloor`), but leave reduced-motion to CSS — don't read `prefers-reduced-motion` in a JS timing hook.

## Applies when

- Adding or wiring a `Suspense` boundary in the renderer and considering a non-null `fallback` (especially a skeleton/`animate-pulse-delayed` placeholder).
- Building or touching loading/skeleton UI under `src/hooks/useDeferredLoading.ts`, `src/lib/animationUtils.ts`, or any `animate-pulse-delayed` / `--anti-flicker-delay` consumer in `src/index.css`.
- Symptoms: a skeleton flashes for a single frame on fast resolves; a long blank window before a placeholder appears; layout-shift "pop" after a Suspense fallback.
- Choosing between an onset gate vs a minimum-dwell floor — or deciding you need both — for lazy-loaded panels, portal/webview restores, tab restores, or any async UI whose resolve time straddles the ~200–400ms gate boundary.
- Upgrading React major versions: re-verify `FALLBACK_THROTTLE_MS` (still 300 in 19.2.6) and the Chromium target, since the dead-zone math depends on both the throttle and the CSS delay constant.
