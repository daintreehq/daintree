## Context

Agent launch configuration has a dual representation. `generateAgentCommand` (`shared/types/agentSettings.ts`) builds the one-shot command string for the initial spawn — it may include runtime-dynamic values (clipboard directory, initial prompt) that must NOT be replayed. `buildAgentLaunchFlags` builds the durable process-level flag array (registry default args, inline-mode flag, `--model`, dangerous args, custom flags) persisted on the panel as `agentLaunchFlags`; its doc comment states the invariant: "These flags must be re-supplied on every CLI invocation (they are not embedded in the session)." The restart slice (`src/store/slices/panelRegistry/restart.ts`) seeds `nextAgentLaunchFlags` from `currentTerminal.agentLaunchFlags` and rebuilds every subsequent command from it — `buildResumeCommand(agentId, sessionId, flags)`, `buildResumeLatestCommand`, `buildLaunchCommandFromFlags`. It never parses the stored command string.

## Problem

Issue #9650: an agent launched from a recipe with dangerous mode enabled lost `--dangerously-skip-permissions` the moment it was restarted, continued, or resumed — plus its recipe `args`, and (in `runRecipeWithResults`) even the initial command missed the recipe's `agentModelId`. First launch was flawless, which is the trap: the recipe paths baked everything into the command string, so nothing looked wrong until a restart, and the drop itself was completely silent — resume produced a clean `claude --resume <id>` with no error, just an agent that suddenly started prompting for permissions mid-task.

## Root cause

Two duplicated spawn sites — `runRecipeWithResults` (`src/store/recipeStore.ts`) and `spawnPanelsFromRecipe` (`src/components/Worktree/panelSpawning.ts`) — called `generateAgentCommand` for the live command but called `addPanel` without computing `agentLaunchFlags`. `spawnPanelsFromRecipe` forwarded `t.agentLaunchFlags`, which looked correct but is `undefined` for every disk recipe: `sanitizeRecipeTerminal` / `stripSessionOverridesFromRecipe` deliberately strip `agentModelId`/`agentLaunchFlags`/`location` as session-only state on persist and load, so the field is only populated on the in-memory clone-layout path (`terminalToRecipeTerminal`). The canonical launcher path (`useAgentLauncher`) had always done it right — `buildAgentLaunchFlags` then persist — but the fix never propagated to the recipe copies of the spawn logic.

The restart slice made the omission unrecoverable in exactly the branches that mattered. A settings-derived fallback (`buildAgentLaunchFlagsForRuntimeSettings`) existed, but at the time it only ran on the fresh-launch branch (`commandToRun === currentTerminal.command`); the resume and continue branches chose `commandToRun` before that check, so undefined flags flowed straight into `buildResumeCommand(agentId, sessionId, undefined)`. And even today's broader fallback can only reconstruct settings-derived flags (dangerous mode, inline mode, global switches) — per-panel recipe `args` and `agentModelId` exist nowhere in settings, so if they are not in the persisted flags they are simply gone. The fix (#9654) mirrors `useAgentLauncher` at both sites: `buildAgentLaunchFlags(entry, agentId, { modelId })` plus the recipe args as raw whitespace-split tokens, passed through `addPanel` with `agentModelId`; both sites still cite #9650 today, and #10432/#10876 later layered preset-args/global-switch reconciliation onto restart.

## Lesson

- **`agentLaunchFlags` is the source of truth; the command string is derived, one-shot state.** Any spawn path that builds a command with `generateAgentCommand` and calls `addPanel` with `launchAgentId` MUST also persist `buildAgentLaunchFlags(...)` (plus per-panel extras) — restart/resume/continue regenerate the command purely from persisted flags and never parse the command string.
- **First-launch success masks the omission entirely.** The baked command carries the flags, so manual testing of the spawn path proves nothing. When touching a spawn site, test the restart round-trip: spawn → restart/resume → assert the regenerated command still carries the dangerous flag, model, and args (#9650 tests: `recipeStore.test.ts`, `panelSpawning.test.ts`).
- **Settings-derived fallbacks cannot recover per-panel data.** `buildAgentLaunchFlagsForRuntimeSettings` rebuilds what current settings imply, but recipe `args` and per-panel `modelId` have no other home than the persisted flags — do not assume "the restart path will regenerate it from settings" covers panel-specific launch options.
- **Forwarding a field is not persisting it.** `spawnPanelsFromRecipe` passed `t.agentLaunchFlags` through — always `undefined` for disk recipes because recipe sanitization strips session-scoped fields. Use the preserve-then-compute pattern both sites use now: `t.agentLaunchFlags ?? [...buildAgentLaunchFlags(...), ...args]` (clone-layout keeps live flags; disk recipes compute fresh).
- **Append recipe args as raw whitespace-split tokens** (`args.trim().split(/\s+/).filter(Boolean)`) — the restart command builders apply their own escaping, so pre-escaped tokens would double-escape.
- **Spawn logic is duplicated; a fix to one copy does not propagate.** `generateAgentCommand` has ~6 non-test call sites (`useAgentLauncher`, `recipeStore`, `panelSpawning`, `panelDuplicationService`, `restart.ts`, `statePatcher`). Adding a new per-panel launch option means threading it through BOTH `generateAgentCommand` and the persisted-flags computation at every site.

## Applies when

- Adding or modifying any agent spawn site — a new `addPanel({ kind: "terminal", launchAgentId, command, ... })` caller, MCP/plugin-driven agent spawning, or any new consumer of `generateAgentCommand`.
- Diagnosing an agent that loses `--dangerously-skip-permissions`, its model, or extra CLI args after restart, "Continue", or resume — check whether the panel's `agentLaunchFlags` is undefined/incomplete before suspecting the restart slice.
- Touching `restart.ts` flag seeding (`nextAgentLaunchFlags`, `resumeFlags`, `freshLaunchFlags`) or the resume command builders in `shared/types/agentSettings.ts`.
- Adding a new per-panel launch option (model, preset args, custom flag) — it must land in both the initial command AND `agentLaunchFlags`, at every spawn site.
- Reviewing recipe persistence: `agentModelId`/`agentLaunchFlags`/`location` are intentionally stripped from disk recipes, so any code reading them from a `RecipeTerminal` must handle undefined by computing from live settings.
