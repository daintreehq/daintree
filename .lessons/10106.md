## Context

`XtermAdapter` is the React adapter around `terminalInstanceService`'s pooled xterm instances: one big attach `useLayoutEffect` runs `getOrCreate` → `attach` → key-handler install, and its cleanup runs `flushResize` + `detach()`. The memoized `terminalOptions` object (built by `getXtermOptions` from theme, font size/family, scrollback, screen-reader mode) sat in that effect's dependency array, so React treated any new options identity as "re-run the whole attach lifecycle".

## Problem

Every appearance change — font size, scrollback, screen-reader toggle, and worst of all a theme-picker _hover_ — tore down and re-attached every mounted terminal (#9929). Hovering a theme sets `previewSchemeId`, and `selectEffectiveTheme`'s cache key includes the preview id, so each hover mints a fresh `ITheme` object and thrashes the full hide/reveal/refit cycle across the grid. Separately and less visibly: `detach()` unconditionally calls `managed.terminal.blur()` with no compensating refocus path, so a focused terminal silently lost keyboard focus after any appearance change — including the `terminal.setFontSize` action dispatched via keybinding or agent MCP.

## Root cause

The direct cause is the classic imperative-adapter trap: an options object in the attach effect's deps conflates "which instance am I bound to" with "what should that instance look like", so a value tweak pays the full structural teardown — pointless here because `getOrCreate` already applies option changes in place for existing instances (via `refreshManagedFromCreateArgs` → `updateOptions`).

But the naive fix (drop `terminalOptions` from deps, add a second effect that calls `updateOptions(terminalId, terminalOptions)`) breaks on two layered contracts in `terminalInstanceService.updateOptions`. First, **it keys on key presence, not value change**: `textMetricKeys.some((key) => key in options)` zeroes `lastWidth`/`lastHeight` and refits, and `"theme" in options` forces a full-row `terminal.refresh` — so forwarding unchanged `fontSize`/`fontFamily` alongside a changed theme would refit every mounted terminal on each hover. Second, **a mount-time full-options call breaks the saved-dims reattach contract**: `attach` skips the resize when saved `targetCols`/`targetRows` still match after a project-switch detach, but a text-metric-presence `updateOptions` firing on the same commit would zero the dimension cache and force the refit anyway. #10106 therefore ships three pieces: the attach effect reads options through `terminalOptionsRef` (identity out of deps), a separate options `useLayoutEffect` diffs applied-vs-current and forwards only changed keys, and an applied-options handshake (`appliedOptionsRef` is stamped right after `getOrCreate`, which already applied those options itself) makes the options effect a no-op on attach commits.

## Lesson

- **Never put a derived options/config object in the dep array of an effect that owns an imperative widget's attach/detach lifecycle.** Split into an attach effect keyed on identity (terminal ID + stable callbacks) that reads options via a ref, and a separate effect that applies option changes in place. Any memo upstream that mints fresh objects (here: theme-preview hover through `selectEffectiveTheme`) multiplies the teardown across every mounted instance.
- **Before forwarding an options object to an imperative API, check whether it keys on presence or on change.** `terminalInstanceService.updateOptions` triggers refit on _presence_ of any text-metric key and full-row refresh on _presence_ of `theme` — so the caller must diff and send only changed keys. Assume other imperative `setOptions`-style APIs behave the same until proven otherwise.
- **When both the attach path and the options path can apply options, add an applied-options handshake.** `getOrCreate` applies options itself; the attach effect records `appliedOptionsRef.current` so the options effect skips the commit where attach already did the work — otherwise every mount fires a redundant full-options call that violates the saved-dims skip in `attach`.
- **The delta diff in `XtermAdapter` enumerates exactly five keys** (`theme`, `fontSize`, `fontFamily`, `screenReaderMode`, `scrollback`) because those are the only runtime-variable outputs of `getXtermOptions` — the rest is the static `BASE_TERMINAL_OPTIONS` constant. Making any other xterm option user-configurable without extending this diff means it silently never applies in place (only on the next full attach).
- **`detach()` blurs unconditionally and nothing restores focus** — any code path that detaches a focused terminal outside a real unmount is a focus-steal bug, not just a perf cost. Treat an unexpected `terminal.blur()` in a repro trace as evidence the attach lifecycle ran when it shouldn't have.

## Applies when

- Touching `XtermAdapter`'s effects or their dependency arrays — especially adding anything derived from appearance/theme state to the attach effect.
- Making a new xterm option user-configurable (via `getXtermOptions` / settings / theme system) — the `XtermAdapter` options-effect diff must be extended or the option won't apply live.
- Writing any React adapter around a stateful imperative widget (xterm, editors, canvas/WebGL surfaces) where "reconfigure" is cheap but "recreate/reattach" is expensive or side-effectful.
- Diagnosing "keyboard focus vanishes after changing a setting/theme" or "theme-picker hover is heavyweight / flickers all terminals" — check whether the attach lifecycle re-ran by watching `detach`/`attach` call counts (the regression suite in `XtermAdapter.lifecycle.test.tsx` asserts exactly this).
- Reviewing calls to `terminalInstanceService.updateOptions` / `applyGlobalOptions` — passing a full options object instead of a delta forces refits/refreshes for every unchanged-but-present key.
