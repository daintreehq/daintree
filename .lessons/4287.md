## Context

Electron's shutdown sequence runs a chain of async cleanup operations (flush buffers, close PTY processes, save state, close DB). If any cleanup step hangs (e.g., a PTY process that never exits, a network call that never resolves), the app freezes indefinitely and never quits.

## Problem

No hard timeout existed on the shutdown cleanup chain. A hang in any cleanup phase would prevent the process from exiting, requiring a force-kill from the OS or the user.

## Root cause

The cleanup chain `await`ed each disposal step sequentially with no upper bound on total time. A single unresolved promise (a PTY that never emits exit, a network I/O with no per-op timeout) blocks the `await`, so `before-quit` never completes and the process stays alive. There was no `Promise.race` backstop to force the process down when an individual step stalled, and no record of which step was in flight, so a hang was undiagnosable.

## Lesson

**Every async cleanup chain must have a hard timeout.** The pattern is `Promise.race([cleanupPromise, timeoutPromise])` (`electron/lifecycle/shutdown.ts:453`). The timeout promise rejects after `CLEANUP_TIMEOUT_MS`; whichever settles first wins.

**On timeout/error, call `app.exit(1)`; on clean completion, `app.exit(0)`** (`shutdown.ts:488,505`) — use `app.exit`, not `app.quit`, because `quit` re-triggers lifecycle events while `exit` is immediate. Guard with an `exitCalled` flag so the race winner and the safety-belt can't both call `exit` and clobber the code.

**Track the current phase** to log which step was running when the timeout fired. A `currentPhase` variable is updated as each cleanup step begins (`shutdown.ts:171,390`) and interpolated into the rejection message (`Hard shutdown timeout after ${CLEANUP_TIMEOUT_MS}ms — stuck at phase: ${currentPhase}`, `shutdown.ts:447`).

**10 seconds is a reasonable hard limit** (`CLEANUP_TIMEOUT_MS = 10_000` in `electron/lifecycle/shutdownConfig.ts`). Users notice hangs after 2-3 seconds; 10 seconds is long enough for real cleanup (flushing DB, closing PTY) but short enough to not feel frozen. The constant lives in a side-effect-free module so the signal handler (`appLifecycle.ts`) and tests can import it without pulling in the full shutdown service graph.

**Clear the timeout** on normal completion (`clearTimeout(hardTimer)`, `shutdown.ts:457,493`) so the process doesn't receive a spurious `exit(1)` after a successful shutdown.

The timeout is a backstop, not a replacement for per-operation timeouts. Individual operations (e.g., waiting for a subprocess to exit) should still have their own shorter timeouts. A separate signal-handler safety belt (`SAFETY_BELT_TIMEOUT_MS = CLEANUP_TIMEOUT_MS + 3_000 + 2_500`) outlasts the full chain and is defused via `clearSafetyBeltTimer()` before the final telemetry flush so it can't fire mid-`await closeTelemetry()` and override the intended exit code.

## Applies when

- Electron `before-quit` / `will-quit` handlers with multi-step async cleanup
- Any cleanup chain where a single hung step would deadlock the entire shutdown
- Service `stop()` methods that rely on external processes or network I/O
