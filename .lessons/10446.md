## Context

Docked terminals (a tab group popped over the dock rail, or a single dock item) do NOT get their refresh tier from the grid's `IntersectionObserver`-driven `setVisible` path — their stable xterm wrapper is relocated into the popover container by `useDockPanelPortal().moveToDestination()` WITHOUT a React remount, so no observer governs it. Instead `DockedTabGroup.tsx` and `DockedTerminalItem.tsx` imperatively call `terminalInstanceService.applyRendererPolicy(id, VISIBLE|BACKGROUND)` themselves: VISIBLE while the popover is open (RAF-gated, after `fit()`), BACKGROUND when it closes. Docked tab groups shipped in #8160.

## Problem

Switching the active tab inside an already-open docked tab group left the tab you switched AWAY from pinned at the `VISIBLE` refresh tier even though its wrapper had been parked offscreen behind the popover. It kept painting at full active cadence and kept feeding the backend at the fast poll rate — invisible waste that accumulates one stale panel per tab switch, the refresh-tier-starvation class of #5878.

## Root cause

The renderer-policy effect keys on `activePanelId` and re-runs on every tab switch, but its only downgrade branch was `if (!isOpen) applyRendererPolicy(activePanelId, BACKGROUND)` — it fired ONLY when the whole group closed. On a tab switch the group stays open, so the effect re-ran for the NEW `activePanelId`, upgraded it to `VISIBLE`, and never touched the outgoing panel. The companion move-effect parked the old wrapper offscreen (`moveToDestination(id, null)`) but a portal relocation does not change a terminal's applied tier — nothing downgraded it. There is no arbiter in the policy layer that enforces "only one VISIBLE panel": `applyRendererPolicy` transitions the single id you name and nothing else, so imperative VISIBLE grants ACCUMULATE. A stale VISIBLE tier is expensive on three coupled axes — the renderer keeps repainting at active cadence, `backendPollingIntervalForTier(VISIBLE)` holds the PTY host's ActivityMonitor at 200ms (vs 500ms for BACKGROUND), and `onTierApplied` runs `webGLPolicy.wantsWebGLAtTier(managed, VISIBLE)` → true, so the panel stays in the WebGL want set (`getWantsSize()`); once the fleet want-count crosses the 12-context per-surface threshold the whole surface flips to the DOM renderer, taking the genuinely-visible terminals off the GPU path with it.

## Lesson

- **Any component that imperatively upgrades a terminal's refresh tier owns the paired downgrade of whatever it displaced — the policy layer has no single-VISIBLE arbiter and the `IntersectionObserver` won't cover you.** The dock deliberately bypasses `setVisible` (portal relocation, no remount), so #5878's automatic visibility-follows-want machinery never runs for docked panels; you drive both directions by hand. The fix tracks the prior id in `prevActivePanelIdRef` and calls `applyRendererPolicy(prevId, BACKGROUND)` before upgrading the new panel.
- **Update the prev-active ref on EVERY path through the effect, including the early returns.** `prevActivePanelIdRef.current = activePanelId` is written before the `if (!isOpen)` return and before `if (!portalContainer) return`, so it never goes stale across a close/reopen and a reopen doesn't spuriously downgrade a panel that was never the previous tab.
- **The downgrade is synchronous; the upgrade is RAF-gated — and the effect cleanup must `cancelAnimationFrame` the pending upgrade.** On a switch faster than a frame the outgoing panel's own VISIBLE RAF is still queued; the cleanup cancels it so it never reaches VISIBLE, while the new synchronous BACKGROUND still lands. Both regression tests in `DockedTabGroup.mountGuard.test.tsx` assert exactly this ordering.
- **Lean on the policy's downgrade hysteresis for rapid flips instead of debouncing yourself.** `applyRendererPolicy` applies upgrades immediately but debounces downgrades by `TIER_DOWNGRADE_HYSTERESIS_MS = 500`; a t1→t2→t1 flip schedules t1's BACKGROUND on a 500ms timer that the immediate re-upgrade cancels, so flipping the same tab back never actually backgrounds it. Do NOT add a second guard on top.
- **A refresh tier is not just paint cadence — it is also backend poll rate AND WebGL want-membership.** Leaving one panel a tier too high silently inflates `getWantsSize()` toward the DOM-fallback threshold and holds the PTY host at the faster ActivityMonitor interval. When auditing tier bugs, check all three consequences, not just whether the pixels look right.

## Applies when

- Building any surface that reveals or relocates a terminal panel imperatively (dock, popover, floating window, split reveal, pop-out) and calling `applyRendererPolicy(id, VISIBLE)` — you must also downgrade whatever it replaced.
- Touching `DockedTabGroup.tsx` / `DockedTerminalItem.tsx` renderer-policy or move effects, or adding a new tab/active-panel transition to a group that hosts live terminals.
- Diagnosing "terminals feel like they're painting too much" / the whole fleet unexpectedly on the DOM renderer / elevated PTY-host poll rate with panels that should be idle — suspect a stale VISIBLE tier inflating `getWantsSize()` past 12.
- Reviewing any refresh-tier or resource-lease transition that upgrades an incoming entity — confirm there is a paired path that downgrades the outgoing one, and that a portal-relocated wrapper (moved without remount) isn't silently assumed to be governed by the `IntersectionObserver` (the #5878 / #10446 starvation class).
