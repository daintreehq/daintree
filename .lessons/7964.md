## Context

`KeybindingService` stores combos as strings like `"Cmd+Shift+E"` or chord sequences like `"Cmd+K Cmd+W"`. It does conflict detection (`findConflicts`), registration guards (`registerBinding`), and runtime matching (`matchesEvent`). The settings rebind UI (`SettingsShortcutCapture.tsx`) does its own unbind comparison against stored overrides and defaults. On Windows/Linux there is no physical Cmd key — Cmd-prefixed bindings fire on the Ctrl key (`hasCmd = mac ? event.metaKey : event.ctrlKey`).

## Problem

Two distinct off-Mac bugs:

1. `Cmd+Shift+E` and `Ctrl+Shift+E` were treated as different combos by the equality check (case-folded string compare), so `findConflicts` and `registerBinding` silently missed the collision — one binding overrode the other with no warning. A live instance shipped in defaults (`panel.diagnosticsEvents` on `Ctrl+Shift+E` shadowing `terminal.sendToAgent` on `Cmd+Shift+E`).
2. On international layouts (German/French/Nordic), AltGr produces `event.ctrlKey && event.altKey`. Any `Ctrl+Alt+<key>` binding matched and swallowed the AltGr keystroke, so users couldn't type `€ @ { }` etc.

## Root cause

A combo equality function that string-compares `"cmd+..."` vs `"ctrl+..."` is wrong off-Mac because both prefixes map to the same physical key. Conflict detection needs Cmd folded into Ctrl, but display must keep them distinct (Mac shows ⌘, Win shows Ctrl) — so you cannot just normalize the stored string. The fold has to live in the _comparison_, gated by platform: off-Mac, treat `cmd` as `cmd || ctrl` and force `ctrl` false so the two forms collapse; on Mac keep both fields separate. AltGr is a separate trap: it arrives as ctrlKey+altKey, so it is indistinguishable from a deliberate Ctrl+Alt chord at the modifier-bit level — only `event.getModifierState("AltGraph")` disambiguates, and that check must run _before_ any binding is tested.

## Lesson

- Compare combos with one platform-aware function (`combosFieldsEqual` in `keybindingUtils.ts`), not ad-hoc `combo.trim().toLowerCase() ===`. It splits on whitespace to handle chord sequences segment-by-segment and folds Cmd↔Ctrl off-Mac via `singleComboFieldsEqual` (`aCmd = mac ? pa.cmd : pa.cmd || pa.ctrl`, `aCtrl = mac ? pa.ctrl : false`).
- Every code path that decides "are these the same binding?" must use that one function: `findConflicts`, `registerBinding`, the chord-prefix check, AND the renderer's unbind path in `SettingsShortcutCapture.tsx`. If any path keeps its own string compare, the collision survives a manual rebind. This is why the function was lifted out of `KeybindingService.ts` into the shared `keybindingUtils.ts`.
- In `matchesEvent`, add an early `if (!mac && event.getModifierState?.("AltGraph")) return false;` before any modifier check, so Ctrl+Alt bindings never swallow AltGr international input. Gate to non-Mac (macOS has no AltGr).
- Keep a regression fence: a unit test iterates `DEFAULT_KEYBINDINGS` and runs `findConflicts` on each to catch any future built-in that collides cross-form on Windows/Linux — the constructor pushes defaults without going through `registerBinding`'s guard, so that audit is the only thing catching built-in collisions.

## Applies when

- Adding or changing default keybindings, especially anything Cmd/Ctrl + a letter that could collide cross-platform (e.g. a new `Ctrl+Shift+*` default).
- Touching `findConflicts`, `registerBinding`, `matchesEvent`, or the rebind/unbind capture logic in `SettingsShortcutCapture.tsx`.
- Comparing two combo strings for equality anywhere — reach for `combosFieldsEqual`, never raw `.toLowerCase()` string compare.
- Debugging a report that a shortcut "silently does nothing" on Windows/Linux, or that international characters (`€ @ { } [ ]`) can't be typed because a Ctrl+Alt binding eats them.
- Any work where a binding behaves correctly on macOS but collides or misfires on Windows/Linux (or vice versa).
