## Context

Daintree runs one `WebContentsView` per project (`ProjectViewManager`), tracked by `electron/window/webContentsRegistry.ts`: `registerAppView` maps `win.id → view` in `windowToAppView` and installs a `view.webContents.once("destroyed")` listener that prunes the entry when the view dies. Separately, `electron/ipc/handlers/webview.ts` attaches a CDP debugger to browser-pane webContents; its `message`/`detach` listeners forward console output to the renderer, reading webContents through the registry. Cleanup was purely event-driven: the `destroyed` listener was trusted to remove stale entries before anyone could read them.

## Problem

Recurring production crash (#9647): `TypeError: Cannot read properties of undefined (reading 'isDestroyed')` from a `Debugger.emit` frame in the main process — uncaught, so the whole main process died. The minified stack pointed at the CDP listeners but not at _why_ a webContents would be `undefined`; the listeners already guarded `session.ownerWindow && !session.ownerWindow.isDestroyed()`, so the obvious targets looked covered.

## Root cause

Electron 41 shipped an undocumented breaking change (upstream electron/electron#50249, still open, filed only to request release-note documentation): the `WebContentsView.webContents` getter returns `undefined` once the view's webContents is destroyed — including _inside_ the `destroyed` handler itself. On Electron 40 it stayed defined throughout teardown. Daintree picked this up with the v40→v41 bump (#4660, 2026-03-31); the crash surfaced in production weeks later and was fixed by #9652 (2026-06-02). The behavior persists on the current Electron 42 pin — upstream considers the new shape correct.

The race window: destruction nulls the getter synchronously, but the `once("destroyed")` listener that prunes `windowToAppView` runs as an event afterwards. Buffered CDP `Debugger` messages can emit inside exactly that window, so `getAppWebContents(win)` found the stale view in the map and ran `!view.webContents.isDestroyed()` on `undefined`. TypeScript actively hides this: `WebContentsView.webContents` is declared non-optional, so the unguarded read typechecks cleanly. And because the throw happened inside a main-process `EventEmitter` emit, it escaped uncaught — one dying browser pane took down the entire app.

The fix is two independent layers. (1) **Guard + prune-on-read** at all three registry read paths (`getAppWebContents`, `getAllAppWebContents`, `unregisterAppView`): test `view.webContents && !view.webContents.isDestroyed()`, and on failure delete the stale map entry immediately (plus `invalidateAllAppWebContentsCache()`) so the `win.webContents` fallback is reached — don't wait for a `destroyed` event that may not have fired yet. (2) **try/catch around the entire CDP `message` and `detach` listener bodies** in `webview.ts` (`logWarn` "CDP … listener failed mid-teardown"), because any future teardown-race variant in those listeners is otherwise a process kill.

## Lesson

- **On Electron 41+, never read `view.webContents` without a presence guard.** `view.webContents && !view.webContents.isDestroyed()` is the canonical form; the plain `!view.webContents.isDestroyed()` typechecks (the type is non-optional) and crashes at runtime. The getter is `undefined` even inside the view's own `destroyed` handler (electron#50249).
- **`once("destroyed")` cleanup is necessary but not sufficient for registries holding views.** There is always a window between the getter nulling and your listener firing; anything that can execute in that window (CDP emits, IPC, timers) sees the stale entry. Registries must also prune on read: detect the dead view at the read site, delete the entry, fall back — `getAppWebContents` in `webContentsRegistry.ts` is the pattern.
- **Uncaught throws in main-process event listeners are full app crashes, so wrap listener bodies in try/catch as a class defense.** The specific unguarded read was fixed, but #9652 also wrapped both CDP listener bodies wholesale — the cost is a `logWarn` on a path that was going to crash anyway.
- **This is a bug class, not a bug.** #9652 flagged ~10 more unguarded `view.webContents` reads in `ProjectViewManager.ts`; #10931 later confirmed one for real — `cleanupEntry` read `entry.view.webContents.id` unguarded, and a teardown race would strand the entry in `views`, breaking eviction loops and `dispose()` mid-iteration. Raw reads still exist today (e.g. the `resizeHandler` paint-gate branch, ~line 255) that lean on `switchChain` serialization — new code must not copy them.
- **Test the race by nulling the getter directly:** `(view as unknown as { webContents: unknown }).webContents = undefined` without firing `destroyed` — `webContentsRegistry.test.ts` covers both halves (undefined getter, and present-but-destroyed webContents) this way. A test that fires `destroyed` first never exercises the window.
- **Recognize the signature:** a production `TypeError: … (reading 'isDestroyed')` under `Debugger.emit` or any `EventEmitter.emit` in main.js means an event landed mid-teardown; hunt the unguarded liveness check, not a missing listener removal.

## Applies when

- Reading `view.webContents` (or any `WebContentsView` property) in main-process code — `ProjectViewManager.ts`, `webContentsRegistry.ts`, `PortalManager`, window teardown paths.
- Building or auditing any registry/map keyed on views or webContents whose cleanup relies on a `destroyed`/`close` event listener.
- Writing main-process listeners for CDP debugger events, `render-process-gone`, or anything that can emit during teardown of its own target.
- Diagnosing a main-process crash with `Cannot read properties of undefined (reading 'isDestroyed')` or similar liveness-check TypeErrors in an emit stack.
- Bumping Electron majors: electron#50249 was an intentional, release-note-absent behavior change that surfaced weeks later in production — sweep lifecycle-getter assumptions (`grep -rn 'view\.webContents' electron/`) during the upgrade, not after the crash reports.
