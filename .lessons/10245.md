## Context

`extractPatches` in `shared/utils/artifactParser.ts` classifies streamed terminal output into patch artifacts. The output flows straight from the semantic worker (`extractArtifacts` → `ARTIFACT_DETECTED`) into `useArtifacts`, is stored and rendered verbatim with an "Apply patch" affordance, and `applyAllPatches()` hands the text to `git apply`. There is no revalidation anywhere between the extractor and that button — the extractor's classification IS the gate.

## Problem

Any line starting with `---` opened a patch block, and any following `-`/`+`/` `/`@@`/`+++` line was appended; once the block passed 3 lines it was emitted as a patch. Markdown horizontal rules, YAML front-matter delimiters, and the bullet lists that usually follow them all satisfied that loose heuristic (`---` then `- item one` / `- item two` …). The user got a fake patch artifact with an "Apply patch" button that then failed loudly against `git apply` (#9998).

## Root cause

The heuristic promoted on a single ambiguous token (`---`) with zero corroboration, and because nothing downstream revalidates, one false positive in the worker surfaces directly as a broken user action. The fix is a three-tier classifier, all tiers required to emit: **Tier 1 trigger** — `diff ` prefix (unambiguous, `isDiffStart`) OR a `--- a/<file>` source header via `UNIFIED_OPENER_REGEX = /^---\s+\S/`; bare `---` and `--- ` (whitespace only) never match, which is what kills the Markdown-HR / YAML false positives. **Tier 2 corroborate** — required only for the ambiguous `--- ` opener (not for `diff --git`): a `+++`-target header (`TARGET_HEADER_REGEX = /^\+\+\+\s+\S/`) within `TARGET_HEADER_LOOKAHEAD = 4` lines, skipping blanks and extra `---` headers so combined/octopus diffs still pass. **Tier 3 commit** — at finalize, the block must be >3 lines AND contain a real hunk header, `HUNK_HEADER_REGEX = /^@@@*\s+-\d+/`. The anchored `-\d+` after the run of `@`s is deliberate: it rejects prose like `@@user` and `@@@handle` that a bare `@@` check would accept.

The subtle tie to #10224: the SAME pipeline deliberately runs a LOOSE patch detector and a STRICT one. `WorkerBufferService.findOpenPatchStart` (added by #10224) still opens a patch on ANY bare `---` — on purpose, because it only decides the buffer TRIM ANCHOR, where a false positive merely over-retains bounded memory. `extractPatches` (this PR) is strict, because its false positive ships a broken affordance to the user. Same signal, opposite strictness, chosen by the cost of being wrong.

## Lesson

- **When a heuristic classifier is the only gate before a user-facing action that will fail loudly (here: worker → `ARTIFACT_DETECTED` → `useArtifacts` "Apply patch" → `git apply`, no revalidation), one ambiguous opener is not enough to promote.** Require a corroborating structural marker. If you can't add a revalidation step downstream, the tightening has to happen in the extractor.
- **Concrete gate for diff detection: trigger + corroborate + commit.** `diff ` OR `/^---\s+\S/` (never bare `---`) to trigger; a `+++` target within 4 lines to corroborate the ambiguous opener; at least one `/^@@@*\s+-\d+/` hunk to commit. All three, or drop the block.
- **Anchor a discriminating regex on the token that actually distinguishes signal from prose, not on the prefix.** `@@` alone matches `@@user`; requiring `-\d+` immediately after the `@`-run is what separates a hunk header from an @-mention. `---\s+\S` (non-space after whitespace) is what separates a diff source header from a Markdown rule.
- **The same signal can warrant opposite strictness in two places — do NOT unify the detectors.** `findOpenPatchStart` (anchoring, #10224) stays loose because a false positive costs bounded memory; `extractPatches` is strict because a false positive costs a broken user action. Refactoring them into one shared detector would break one of the two.
- **Don't over-tighten the accepting side.** The `+++`/`---` path prefix is intentionally NOT enforced (`git diff --no-prefix` drops `b/`; `/dev/null` marks new/deleted files), and `\ No newline at end of file` must count as a body line or `git apply` rejects the very patch you extracted.

## Applies when

- Touching `shared/utils/artifactParser.ts` `extractPatches` / `extractCodeBlocks`, or anything that turns streamed agent text into an artifact rendered with an actionable affordance.
- Adding or loosening any heuristic that promotes streamed/parsed text into a user action (apply, run, open) where nothing downstream revalidates — the extractor is the gate.
- Diagnosing "a Markdown rule / YAML block / bullet list showed up as a fake patch" or "Apply patch fails against `git apply`".
- Writing a regex that classifies terminal/agent output — anchor on the discriminating token (`-\d+` after `@@`, `\S` after `--- `), not the shared prefix.
- Considering sharing a detector between a lossy-but-bounded path (buffer trim anchor) and a user-facing path (artifact emit) — keep them separate; their acceptable false-positive rates differ.
