## Context

The demo recording engine (driven by the `demo-video-creator` skill via `window.electron.demo`) hand-rolled two semi-implicit Euler springs inside `requestAnimationFrame` loops: the scroll glide in `DemoCursor.tsx` (the `demo:exec-scroll` handler) and the spotlight-cutout glide in `DemoOverlay.tsx` (`animateSpotlightRect`, springing `x`/`y`/`width`/`height` of an SVG mask). The engine is dev-only, but its output is a user-facing 4K screencast captured by `DemoCaptureBridge.tsx` via `getDisplayMedia` + `MediaRecorder` at 3840×2160, so the glide must read identically every run regardless of the recording machine.

## Problem

The recorded glide played in slow motion, and the motion's duration was implicitly tied to the recording frame rate. The misleading part: it looked perfectly fine when driving the app normally (~60fps), so the bug only surfaced in the finished video under capture load — never in an interactive dev session, which is where you'd naturally test it.

## Root cause

Both loops did `dt = Math.min(dt, 0.032)` and then integrated `velocity += force * dt; current += velocity * dt`. Clamping the integration step discards real elapsed time: the spring can only advance at most 32ms of simulated time per frame, no matter how much wall-clock time actually passed. When 4K `getDisplayMedia`/`MediaRecorder` capture drives the renderer's rAF cadence below ~31fps, _every_ frame exceeds the clamp, so simulated time falls behind wall-clock proportionally and a 1-second glide stretches out. The clamp looks like a defensive guard against post-stall teleport, but it only ever bites when frames are _persistently_ slow — and sustained-slow-frames is precisely the capture condition, so the guard silently converts capture load into systematic slowdown.

The fix (`src/lib/demoSpring.ts`) is a fixed-timestep accumulator: accumulate real elapsed `rawDt`, consume it in fixed `DEMO_SPRING_FIXED_DT = 1/120` sub-steps (`accumulateSpring`), and clamp only the per-frame _addition_ (`DEMO_SPRING_MAX_FRAME_DT = 0.064`, ~7-8 sub-steps) as the actual spiral-of-death guard — never the step itself. Simulated time then tracks wall-clock exactly at any rAF rate. `1/120` divides both 60Hz and 120Hz cleanly and sits ~34× inside the semi-implicit Euler stability bound (`dt < c/k ≈ 0.285s`). Shared constants `DEMO_SPRING_STIFFNESS = 70` / `DEMO_SPRING_DAMPING = 20` (overdamped: c=20 > critical 2√70 ≈ 16.73, so no overshoot) were extracted so both springs tune together instead of drifting apart as duplicated literals.

## Lesson

- **Never clamp the integration `dt` in a duration-accurate rAF animation.** `Math.min(dt, X)` on the step makes total simulated time a function of frame delivery — slow frames drop wall-clock time silently. Accumulate elapsed time and consume it in fixed sub-steps; clamp only the per-frame _time added_ (spiral-of-death guard), never each step. The clamp that looks like a spike guard becomes a systematic slowdown the instant the loop runs persistently below the clamp rate.
- **The same clamp is fine on a real-time smoothing filter, harmful on a captured animation** — know which you have. `VoiceInputButton.tsx` / `VoiceRecordingToolbarButton.tsx` legitimately use `Math.min((now-lastTime)/1000, 0.1)` on an audio-level low-pass filter: it only needs to look right live at ~60fps, is never recorded, and has no target duration. The demo springs must be wall-clock-true because their output is a _video_ decoupled from the machine that rendered it.
- **Keep the integrator pure and rAF-free so frame-rate independence is directly testable.** `stepSpring`/`accumulateSpring`/`isSpringSettled` return fresh state and never touch `requestAnimationFrame`; `runSpringLoop` is a thin rAF shell over them. The regression guard in `demoSpring.test.ts` asserts equal wall-clock time yields equal spring state at 120/60/20fps and irregular pacing — impossible to write cleanly if the math is entangled with rAF.
- **An orphaned demo rAF loop hangs the 30s main-side command timeout.** These loops resolve a Promise that gates `sendDone(requestId)`; unmount mid-glide and the loop never settles, so the demo command times out at 30s. `runSpringLoop` returns a `{ cancel }` handle — `DemoCursor` stores `scrollAnimRef`, `DemoOverlay` stores `spotlightAnimRef` + the exit timer, both cancelled in effect cleanup. Any re-triggerable rAF animation must store and cancel its previous handle. `onUpdate` returning `false` also aborts for a torn-down target, and `onSettled(targets)` snaps to exact final values, not the integrator's sub-pixel approximation.

## Applies when

- Writing or touching any rAF-driven physics/spring/tween whose total duration must be wall-clock-accurate — especially anything in the demo capture pipeline (`src/components/Demo/`, `demoSpring.ts`, `DemoCaptureBridge.tsx`) whose output is a recorded video.
- Diagnosing "the recorded demo plays in slow motion" or "animation duration changes with frame rate / under capture load" — look for a `Math.min(dt, …)` clamp on the integration step, not for a bug in the capture bridge.
- Reviewing any `Math.min(dt, X)` (or `dt = min(...)`) inside an integration loop: confirm it clamps the accumulated per-frame addition (spiral guard), not the sub-step that advances the simulation.
- Assuming an animation that "looks fine in the dev session" is correct — interactive runs stay near 60fps and never trip the clamp; the failure only appears under sustained-slow-frame conditions like 4K capture.
