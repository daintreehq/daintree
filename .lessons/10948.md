## Context

After hibernation removal (#10811) every background terminal stays fully live, so the pty-host's real memory cost is the per-terminal analysis buffers (headless mirror, semantic buffer, forensics ring, agent-output mirror, preserved snapshots). #10948 put those on a policy budget: a `TerminalRetentionCoordinator` sweeps every 5s and stamps each terminal a retention tier (`foreground` / `working` / `settled` / `archived`) from focus, agent state, and activity, and the pty-host `ResourceGovernor`'s pre-pause reclaim was made tier-aware so a chatty agent's history could be reclaimed without flattening every quiet terminal.

## Problem

The app got slower under exactly the workload it should handle best: a few agent terminals running at once. Not a crash, not a leak, just intermittent multi-second stalls where active terminals stopped painting output, and it only showed up "under pressure." It reproduced on a 64GB machine, which threw off the initial read (plenty of free RAM, so memory pressure looked implausible).

## Root cause

Two facts combine into a self-defeating reclaim path.

1. The pty-host runs on a **fixed 512MB V8 heap budget** (`HEAP_BUDGET_MB = 512`, plus 256MB external headroom for ArrayBuffer backing stores). This is a hard `--max-old-space-size` cap and is **not scaled to system RAM** — a 64GB box hits it identically to an 8GB one. The `ResourceGovernor` measures `max(combined / 768MB, heapUsed / 512MB)` and pauses PTY reads at 85% (70% under the efficiency profile), with a 10s force-resume.

2. #10948 changed `performPrePauseTrim` from `.filter(s => s.scrollbackLines > SCROLLBACK_MIN)` (trim **every** terminal over 100 lines down to 100, heaviest first) to `.filter(s => s.tier !== "foreground")` (exempt **all** foreground terminals, trim only the rest to their tier floor). A focused/visible working agent is `foreground`.

So when a few visible active agents filled the 512MB budget, the pre-pause reclaim skipped exactly the buffers causing the pressure and freed almost nothing (only background terminals and preserved snapshots, of which there were none). Utilization kept climbing to the pause threshold, and the governor escalated to the **global PTY pause** — suspending output on up to N terminals for up to 10s. That pause is the felt slowdown; foreground terminals were only trimmed at 95% critical (`performCriticalTrim`), which runs _after_ the pause. The old flatten-to-100 path had reclaimed those same buffers pre-pause and avoided the pause entirely.

Confirmed empirically: reverting #10948 and rebuilding made the stalls disappear. Reverted whole (develop `9adfb0b5`) rather than patched, because the flaw is the PR's central premise, not a peripheral bug.

## Lesson

- **On a fixed process memory budget (not RAM-scaled), never exempt the dominant consumer from the reclaim path.** Exempting foreground terminals sounds protective, but the visible active terminals _are_ what fill the pty-host's 512MB heap. A reclaim path that can't touch the biggest consumer doesn't prevent the hard stop, it just defers to a worse one (the 10s PTY pause). If you rank-and-filter terminals for trimming, verify the exempted category isn't the one dominating the budget.
- **The pty-host's 512MB heap is not scaled to system RAM.** "This machine has 64GB free" does not mean the pty-host has headroom. A slowdown that looks impossible on a big machine can still be a per-process-budget pause. Check `HEAP_BUDGET_MB` / `ResourceGovernor` thresholds before ruling out memory pressure on high-RAM hardware.
- **Know which buffer you are protecting.** The trim targets the _headless analysis mirror_ (state detection, session snapshots, forensics), NOT the renderer's visible xterm scrollback. Flattening it to 100 lines is invisible to the user and cheap; pausing PTY output for 10s is visible and expensive. #10948 traded the cheap invisible cost for the expensive visible one to preserve history the user never actually sees.
- **A floor you can never reach is dead config.** `terminalRetention.ts` defined `foreground.pressureMirrorFloorLines = 5000` for a graceful pre-pause trim, but the governor filtered foreground out entirely, so that floor was unreachable until 95% critical. If a config value exists to soften a path, prove the path actually executes.
- **When a regression is the PR's core design premise, prefer a full revert over a patch.** Patching here meant reversing "exempt foreground" while keeping ~1900 lines of coordinator, tier, epoch, and staleness-guard machinery built on top of it. The pre-existing simple flatten-under-pressure path already bounded memory, so the whole subsystem was speculative complexity that earned a net-negative.

## Applies when

- Touching `electron/pty-host/ResourceGovernor.ts` reclaim (`performPrePauseTrim`, `performCriticalTrim`, `trimBuffersTargeted`) or any memory-pressure path that ranks, filters, or exempts terminals from trimming.
- Adding state-aware / tier-based buffer trimming or retention policy to the pty-host (`TerminalRetentionCoordinator`, `shared/config/terminalRetention.ts`).
- Diagnosing "the app slows down under load / with several agents running" where terminal output stalls intermittently — grep the pty-host logs for `[ResourceGovernor] Paused N/M terminals` and compare frequency across builds; the pause is the mechanism.
- Assuming a high-RAM machine has memory headroom for a subprocess — the pty-host is capped at a fixed `HEAP_BUDGET_MB` regardless of `os.totalmem()`.
- Reviewing any optimization that exempts a category of resource from an eviction/reclaim/GC path — confirm the exempted category is not the dominant consumer, or the exemption inverts the intent.
