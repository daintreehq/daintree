## Context

Worktree cards in the sidebar are dnd-kit sortables, wired through `DndProvider` (`src/components/DragDrop/DndProvider.tsx`). The card itself is the drag activator, but it also contains many inline interactive elements — popover triggers, dropdown menus, issue/PR badges, a sign-in CTA, a plan-file button, toolbar buttons. The `MouseSensor` is configured with an `activationConstraint: { distance: 8 }` (`DRAG_ACTIVATION_DISTANCE`) so a stationary click works and only pointer travel starts a drag.

## Problem

Clicking an inline button on a card was unreliable: a "sloppy" click where the pointer drifted >8px between `mousedown` and `mouseup` registered as a drag start instead of activating the button. The card would begin sorting instead of opening the popover/dropdown/badge target.

## Root cause

dnd-kit's `activationConstraint` is a single threshold on the whole sortable subtree — it distinguishes _drag intent_ (moved far enough) from _click intent_ (didn't move) purely by distance, with no notion of which DOM element was the target. Every descendant of the card, including its buttons, lives on the same activation surface. So a button click that happens to drift past the distance threshold is indistinguishable from a drag start. Raising the distance would only widen the dead zone, never fix the ambiguity, and would also make legitimate drags feel sluggish.

## Lesson

Use the dnd-kit community `data-no-dnd` subtree pattern (clauderic/dnd-kit#477), not a tuned distance:

- Subclass the sensor and short-circuit activation when the `mousedown` target sits inside an opt-out subtree. `NoDndMouseSensor extends MouseSensor` and overrides the static `activators` array; its `onMouseDown` handler returns `false` (and skips `onActivation`) when `event.target.closest("[data-no-dnd]")` matches or when `event.button === 2` (right-click). The override must mirror the upstream `activators` shape exactly so options like `activationConstraint` still flow through.
- Annotate every inline interactive element with `data-no-dnd`; leave ONLY the legitimate drag activator (the grip handle / card body) un-annotated. The opt-out is inverted from intuition — you mark the things that should NOT drag, and the un-marked remainder is the drag surface. Missing one annotation silently re-breaks that one control.
- This only gates pointer sensors. The `KeyboardSensor` is unaffected and needs no opt-out because keyboard activation is explicit (Space/Enter on a focused node), not bubbling pointer input — don't add `data-no-dnd` handling there.
- Factor the predicate out (`isNoDndTarget`) and unit-test it plus the activator handler directly; mounting `DndProvider` requires mocking 10+ modules, so test the integration seam in isolation.

## Applies when

- Adding any clickable control (button, popover/dropdown trigger, badge, link) inside a dnd-kit sortable or draggable, especially `src/components/Worktree/WorktreeCard/*` and anything rendered under `DndProvider`.
- A click inside a draggable element intermittently starts a drag instead of firing the click, or the click only works when the pointer stays perfectly still.
- Touching `DndProvider.tsx` sensor config — reach for `NoDndMouseSensor` / `data-no-dnd` rather than bumping `DRAG_ACTIVATION_DISTANCE`.
- Adding interactive UI to other draggable surfaces (e.g. `GridScrollbar.tsx` already adopts `data-no-dnd`); the same opt-out convention applies project-wide.
