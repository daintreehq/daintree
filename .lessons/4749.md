## Context

The project switcher list (`ProjectSwitcherPalette.tsx`) renders one `ProjectListItem` per result during keyboard navigation, so every arrow-key press can re-render the visible list. An early version passed `selectedIndex: number` down to each item and called `items.indexOf(item)` inside each item to decide whether it was selected.

## Problem

`selectedIndex` changes on every keypress, so passing it as a per-item prop makes React's reference-equality check fire a re-render for every item — even items whose selection state didn't actually change. Computing selection via `items.indexOf(item)` inside each item's render is an O(n) scan per item, making a full list render O(n²).

## Root cause

A numeric `selectedIndex` is a single value that differs on every keystroke, so feeding it to all n items couples all of them to a value that's only relevant to two of them (the item gaining selection and the item losing it). Derived selection (`indexOf`) computed inside each item compounds this into an O(n²) scan.

## Lesson

For lists with keyboard-driven selection:

1. Pass `isSelected: boolean` per item instead of `selectedIndex: number`. The boolean flips for only two items per keypress (the one gaining and the one losing selection), not all n. The parent computes `isSelected={index === selectedIndex}` once at the map site (`ProjectSwitcherPalette.tsx:434`) and each item consumes a stable boolean (`isSelected` prop at `ProjectSwitcherPalette.tsx:111`). This narrows re-render fan-out at the source regardless of any memoization strategy.
2. Don't compute selection with a per-item `items.indexOf(item)` scan — the index is already known at the map site, so pass the comparison result down. This kills the O(n²) render.
3. Do NOT hand-add `React.memo` (with or without a comparator) to fix this. The renderer build runs `babel-plugin-react-compiler` v1.0 in `compilationMode: "infer"` (`vite.config.ts:551-563`), which auto-memoizes every component — a manual `memo` wrapper is dead weight (see lesson #3709; `compiler-bailout-baseline.json` confirms zero bailouts). The boolean-prop change still matters under the compiler because it reduces the input churn that drives re-renders, which memoization alone can't fix.
4. Pre-compute derived display values (`displayPath`, status booleans) in the data model or hook, not inside each item's render.
5. Hoist context providers (`TooltipProvider`, theme providers, etc.) to the list container rather than mounting one per item — provider instantiation per row is expensive at scale.

## Applies when

- Any list with keyboard-driven selection (palette, command menu, autocomplete)
- Any component tree where a frequently-changing parent prop (an index, a cursor) flows into many leaf components that each only care about a single derived boolean
- Reaching for `React.memo` to fix list re-renders — check the React Compiler is already handling memoization before adding manual wrappers
