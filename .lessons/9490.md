## Context

Plugin contributions (actions, panel kinds, toolbar buttons) live in the main process and are mirrored into each per-project renderer. The renderer hooks (`src/hooks/usePluginActions.ts`, `usePluginPanelKinds.ts`, `usePluginToolbarButtons.ts`) get their state two ways: a one-shot IPC **pull on mount** (`plugin:actions-get` etc.) plus a **persistent push listener** on `EVENTS_PUSH` that receives `plugin:*-changed` broadcasts whenever the registry mutates. Each project is its own `WebContentsView` with an independent V8 context; `ProjectViewManager` LRU-evicts cached views (default cache=2) to bound memory.

## Problem

Two distinct, intermittent failures, both invisible without exercising real startup ordering and view eviction together:

1. **Init race** — if the mount-time pull lands before `PluginService.activateStartupFinishedPlugins()` runs, every handler returns `[]`. The renderer registers nothing and stays empty until the next unrelated mutation happens to broadcast.
2. **LRU broadcast gap** — when a view is cold-restored after eviction, its fresh V8 context remounts the hooks and pulls again, but it missed every `plugin:*-changed` broadcast emitted while its _previous_ context was alive. Pull-on-mount alone can race; push-on-mutate never replays. No error, just silently stale plugin UI in the restored view.

## Root cause

A push-hydrated cache (persistent broadcast listener) assumes the listener was alive for every mutation. A cold-restored `WebContentsView` violates that: the new context's listener registers _after_ the broadcasts it needed. The pull path that's supposed to backfill the cold context races main-process startup activation, so it can read an empty registry. Crucially, `ProjectViewManager.onViewReady` (wired to `did-finish-load`) **only fires for the active view** (`electron/window/ProjectViewManager.ts:1168-1177` — guarded so a background reload can't steal the PTY MessagePort), and **never fires on warm reactivation** (re-showing a cached view triggers no `did-finish-load`). So the natural "view became ready" hook doesn't cover every case the pull was supposed to.

## Lesson

For any per-view V8 context that hydrates from main-process **push broadcasts** plus a **pull-on-mount**, both paths need hardening or the cache silently goes stale:

- **Gate the pull on an init promise.** `PluginService.waitForInit()` resolves only after `activateStartupFinishedPlugins()` settles; the three pull handlers `await` it before reading the registry. Resolve the gate in a `finally` (and in `dispose()`) so a crashed plugin activation — or the zero-plugins short-circuit — can never deadlock renderer IPC forever.
- **Add a targeted snapshot replay on view-ready, not just a global broadcast.** `pushSnapshotTo(webContents)` re-sends actions/panel-kinds/toolbar-buttons to a single restored view on the _same_ `EVENTS_PUSH` channel the persistent listeners already consume — so no renderer changes are needed. Wire it into the existing `onViewReady` (`electron/main.ts:339-355`), which covers cold start / LRU restore / crash reload / DevTools refresh.
- **Mind which cases `did-finish-load` does NOT cover.** It only fires for the active view and never on warm reactivation — so it's the right hook for cold-restore but you must verify warm reactivation already converges (here it does: the cached view's listener was alive the whole time).
- **Replay snapshots are "load ticks," not authoritative sweeps.** Send toolbar buttons with `complete: false` so the renderer doesn't run its stale-prune pass against a partial single-view replay.
- **Guard each send independently (TOCTOU).** A wc can be destroyed between the `isDestroyed()` check and an individual `send()`; one throw must not drop the remaining channels. Mirror `broadcastToRenderer`'s per-send try/catch.

## Applies when

- Adding or debugging any main→renderer state that hydrates via `EVENTS_PUSH`/`*-changed` broadcasts plus a pull-on-mount IPC handler (plugins, toolbar buttons, panel kinds, file decorations, action registries).
- A per-project `WebContentsView` shows correct state on first load but goes stale/empty after switching away and back (LRU eviction → cold restore), with no error in logs.
- Renderer mount-time IPC pulls return `[]` intermittently on app startup because they race a main-process `activate*`/`initialize` step — fix with a `waitForInit()`-style gate resolved in `finally`.
- Wiring anything into `ProjectViewManager.onViewReady` / `did-finish-load` — remember it fires active-view-only and never on warm reactivation, so it covers cold-restore but not cache re-show.
- Designing snapshot-replay vs broadcast semantics: distinguish a single-view "load" replay (`complete: false`, no prune) from an authoritative multi-view sweep.
