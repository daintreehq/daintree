## Context

`TerminalInstanceService.onUserInput()` promotes a terminal's `TerminalRefreshTier` on every keystroke (`applyRendererPolicy(id, BURST)`), which `TerminalRendererPolicy` turns into a backend cadence hint (`setBackendTier` → `terminalClient.setActivityTier`). Separately, `electron/pty-host/ipcQueue.ts` and `portQueue.ts` emit a `paused-backpressure` `flowStatus` when a terminal's IPC/port queue floods, shown in the UI as a "Paused" pill. #10669 reported typing into a paused terminal never cleared the pill, though clicking away and back did.

## Problem

A terminal stuck at `paused-backpressure` stayed visibly "Paused" while the user typed — input was accepted but the pause indicator never cleared. The misleading part: clicking away and back DID recover it, pointing at "the wake path is broken" rather than "typing never calls the wake path at all."

## Root cause

Two dedup layers stack. `TerminalRendererPolicy.applyRendererPolicy()` early-returns when the requested tier equals `managed.lastAppliedTier` (already `BURST` from rapid typing). Even when the tier genuinely changes (`FOCUSED` → `BURST`, e.g. first keystroke after just focusing), `setBackendTier()` dedupes a layer deeper: both `FOCUSED` and `BURST` map to the same backend params (`"active"`, 50ms polling), so `tierChanged`/`pollingChanged` are both false and it returns before ever calling `terminalClient.setActivityTier` — no host-facing signal fires at all. Typing's only channel to the backend was this tier-promotion path, and both of its dedup gates could independently swallow it.

The only path that bypassed the tier system was focus: `setFocused()` in `terminalFocusSlice.ts` calls `terminalInstanceService.wake(id)` directly, which is why click-away/click-back always worked and typing never did — two different mechanisms reaching the same visible "un-pause the pill" outcome, only one of which skipped the dedup. #10717's fix was to give `onUserInput()` its own explicit `wake(id)` call, gated on `flowStatus === "paused-backpressure"` and `!backgroundedTerminals.has(id)` (the #9906 guard), both read from a single `usePanelStore.getState()` snapshot so the two fields can't diverge across a re-render. `paused-resource-governor` was deliberately excluded from the same gate.

The exclusion's _justification_ has since been rewritten from under the fix, which is itself the sharper lesson. At merge (2026-06-22) `wake(id)` routed through `TerminalWakeManager` and a host-side `wakeExecutor.ts`; the exclusion held because "wakeExecutor only releases the backpressure coordinator token, not the resource governor." Five days later the hibernation-removal rewrite (`eb9cd64a72`, 2026-06-27) deleted `TerminalWakeManager` and `wakeExecutor.ts` outright — grepping either today returns nothing. `wake(id)` now calls `TerminalRevealController.wake(id)`, documented there as "now a plain repaint." Backpressure release moved entirely to flow control: the host's `acknowledge-data` handling drains the queue and calls `ipcQueueManager.tryResume` / the port-queue equivalent below the low watermark (`ipcQueue.ts`, `portQueue.ts`) — no wake IPC involved. The same rewrite deleted `lifecycle.ts`'s own auto-wake on `paused-backpressure` too, since the only available auto-resume primitive (`forceResume` → `PtyPauseCoordinator.forceReleaseAll()`) drops every pause token, too broad to fire automatically. So `onUserInput`'s wake is now effectively the _only_ surviving trigger on this transition — same exclusion, same conclusion, different mechanism than the PR's comments describe.

## Lesson

- **A state-diffing dedup silently swallows a distinct intent when two different source states map to the same target value.** `setBackendTier` compares the _applied_ backend value, not the _renderer_ tier — `FOCUSED`→`BURST` is a real promotion that still no-ops downstream because both flatten to `"active"/50ms`. When a caller needs a guaranteed side effect (release a pause, force a resume), fire an explicit, separately-named call (`wake(id)`) instead of trying to express it as a tier/state promotion through a dedup layer.
- **"Clicking away and back fixes it, typing doesn't" is a diagnostic tell.** It means a second code path (`setFocused()`'s direct `wake(id)`) reaches the same visible outcome by bypassing the dedup. Find that shadow path before assuming the primary system needs a redesign — the fix is usually "call what the shadow path calls."
- **Read every field a guard needs from one store snapshot.** `onUserInput` takes a single `usePanelStore.getState()` and reads both `flowStatus` and `backgroundedTerminals` off it so the two can't diverge — this is what let the fix preserve the pre-existing #9906 background-wake guard without a second race.
- **`wake(id)` is not one fixed mechanism — verify what it does today before trusting an older description of it.** Between this PR (2026-06-22) and the hibernation-removal rewrite (2026-06-27) `wake()` went from an IPC-coalesced `TerminalWakeManager`/`wakeExecutor.ts` round-trip to a plain local repaint in `TerminalRevealController`. An exclusion can also stay correct while its justification changes underneath it: `paused-resource-governor` is still excluded today, but now because of `forceReleaseAll()`'s blast radius, not per-token scoping — re-derive old exclusions against the current mechanism, don't trust the inline comment's history.

## Applies when

- Touching `TerminalRendererPolicy.applyRendererPolicy()` / `setBackendTier()`, or any tier-promotion path in `TerminalInstanceService.ts` — check whether two distinct source values can collapse to the same applied/backend value and swallow a caller's intent.
- Diagnosing a terminal stuck showing the "Paused" (`paused-backpressure`) pill where clicking away and back recovers it but typing doesn't, or any similar "one interaction path works, an equivalent one doesn't" symptom.
- Adding or auditing a `wake`/`resume`/force-refresh side effect layered on top of a state-diffing policy object anywhere in the terminal stack.
- Reasoning about `wake(id)`, `TerminalWakeManager`, or `wakeExecutor.ts` from an older PR description or comment — that machinery was removed by the hibernation-removal rewrite; verify current behavior in `TerminalRevealController.ts` and `electron/pty-host/{ipcQueue,portQueue}.ts` instead.
- Reviewing a `paused-resource-governor` vs `paused-backpressure` exclusion in any pause/resume path — confirm it against `PtyPauseCoordinator.forceReleaseAll()`'s current blast radius, not the old per-token model.
