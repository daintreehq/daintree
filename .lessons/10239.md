## Context

`src/hooks/useArtifacts.ts` keeps a module-level `const artifactStore = new Map<string, Artifact[]>()` keyed by terminal id. Main detects code/patch artifacts in agent output and pushes them over IPC; the hook's `artifactClient.onDetected` handler appends each `ARTIFACT_DETECTED` payload's artifacts (each holding a full content string) into that Map, and `useArtifacts(terminalId)` consumers subscribe via a module-level `listeners` Set. The Map lives at module scope, so it persists for the whole renderer lifetime, independent of which panels are mounted.

## Problem

Across a session of opening and closing terminals — worktree teardown, panel churn, user-closed panels — every terminal that ever produced an artifact kept its content strings resident. The only code that deleted a Map entry was the user-initiated `clearArtifacts()` ("Clear all" button); nothing pruned on teardown, so the renderer heap grew monotonically. The misleading part: the semantic-analysis _worker_ already forgot each terminal (`rendererStoreOrchestrator.ts` calls `semanticAnalysisService.unregisterTerminal()` → worker `UNREGISTER_TERMINAL`), so the terminal looked fully cleaned up while the renderer-side Map silently retained it.

## Root cause

Two independent gaps compound. (1) A module-level strong `Map` is a GC root; app code must explicitly `delete` the entry or it is retained until the module unloads (i.e. never, in a running renderer). #10239 added `removeArtifactsForTerminal(terminalId)` and wired it into `rendererStoreOrchestrator.ts`'s per-terminal teardown — the single convergence point that already prunes input controllers, console capture, resource metrics, and voice buffers.

(2) Wiring it into the obvious `panelIds`-shrink subscriber is NOT sufficient, because the most common close path never shrinks `panelIds`. `trashPanel` (`src/store/slices/panelRegistry/trashActions.ts`) flips `panelsById[id].location` to `"trash"` and pushes the id into the `trashedTerminals` Map, but calls `saveNormalized(newById, state.panelIds)` with `panelIds` unchanged — the panel stays in `panelIds` for the TTL undo window. So a `panelIds`-only subscriber bails on every user-close. The fix adds a **second** subscriber watching `trashedTerminals`, firing removal for each newly-trashed id. (This same trashPanel-doesn't-shrink-panelIds constraint later pulled #11183's worktree-maximize cleanup into the very same subscriber.)

There is also a millisecond-scale IPC race: main can have an `ARTIFACT_DETECTED` packet in flight _before_ teardown that lands in `onDetected` _after_ removal and re-creates the Map entry, re-leaking. The guard is a `removedTerminals` Set tombstone that removal adds to and the append path checks. The non-obvious second half: the tombstone MUST be cleared on remount — the per-terminal `useEffect(..., [terminalId])` calls `removedTerminals.delete(terminalId)` — or a fast re-spawn reusing the same id (common in one worktree) is permanently blackholed and never records another artifact.

## Lesson

- **Any module-level `Map<terminalId, X>` (or `Set`) in the renderer leaks for the renderer's entire lifetime unless something explicitly deletes the entry — wire removal into `rendererStoreOrchestrator.ts`, not a component effect.** The orchestrator is the single per-terminal teardown convergence point; mirror `unregisterInputController` / `useResourceMonitoringStore.removePanel`. A component's own `useEffect` cleanup owns only its listener registration, never the shared module-level store.
- **The `panelIds`-shrink subscriber does NOT catch the user-close path.** `trashPanel` flips `location = "trash"` and pushes to `trashedTerminals` while leaving `panelIds` intact for the TTL undo window (`saveNormalized(newById, state.panelIds)`). Per-terminal cleanup that must run on user-close needs a **separate `trashedTerminals` subscriber** diffing new keys against `prevTrashed`; relying on `panelIds` alone silently misses the most common teardown.
- **An IPC handler that lazily re-creates store entries needs a teardown tombstone.** Without a `removedTerminals` guard, an in-flight `onDetected` re-inserts after removal and re-leaks. Check the tombstone in the single shared append path (`appendArtifacts`) so the production handler and any test/simulate path cannot drift.
- **A teardown tombstone is a trap unless you also clear it on remount.** Clear it in the per-terminal `useEffect(..., [terminalId])`, NOT on unmount — a re-spawn reusing the same id is otherwise permanently blackholed. The tombstone stays bounded by the working set precisely because every fresh mount re-clears its own id.
- **Distinguish teardown-removal from user "Clear all": only teardown tombstones.** `clearArtifacts()` runs on a _live_ terminal that must keep detecting; it does the same `artifactStore.delete` + notify but must NOT add to `removedTerminals` — a button click doesn't change `[terminalId]`, so the mount effect never re-clears it and the rest of the session would be blackholed.
- Defense-in-depth added later: `MAX_ARTIFACTS_PER_TERMINAL = 50` FIFO-caps one long-lived terminal's entry (`slice(-MAX)` in `appendArtifacts`), but explicit teardown remains the primary reclaim path.

## Applies when

- Adding any renderer-side module-level `Map`/`Set` keyed by terminal or panel id (artifact/console/metrics/voice/input caches) — verify pruning in `rendererStoreOrchestrator.ts`, covering BOTH the `panelIds` and `trashedTerminals` paths.
- Diagnosing renderer-heap growth across open/close terminal cycles where the worker/main side looks correctly unregistered but the renderer keeps climbing.
- Wiring cleanup that must fire on user-close (trash) — assuming `panelIds` shrinks on close is wrong; it stays put through the TTL undo window (`trashPanel`).
- Removing an entry that a still-queued IPC packet could immediately re-create — you need a tombstone, and you need to clear it on remount for id reuse.
- Reviewing any tombstone/blacklist Set for the missing clear-on-reuse half, or any store-clear helper for whether it should tombstone (teardown) or must not (live user clear).
