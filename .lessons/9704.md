## Context

Each project runs in its own `WebContentsView`, frozen while cached via CDP `Page.setWebLifecycleState("frozen")` and unfrozen fire-and-forget on switch-back (`void unfreezeWebContents(wc)` in `electron/window/ProjectViewManager.ts` — still unawaited today). Per-terminal visibility rides an `IntersectionObserver` scoped to the page's own viewport, so hiding/showing the whole view at the Electron level never trips it — every pane keeps "intersecting" its grid the entire time. The whole switch-back repaint therefore rode on ONE trigger: document `visibilitychange → visible` fanning out `fullWakeForVisibilityRestore` (deferred resize, reflow, `repairAtlasForReactivation`, buffer restore, refresh, flush resume) to every visible pane (#9702).

## Problem

Switching back to a project left terminals showing stale or completely blank content until each one was clicked. The blank case is WebGL: on warm reactivation the compositor can push the stale pre-freeze GPU surface, and only `repairAtlasForReactivation` inside the fan-out clears it. The misleading part: clicking always fixed it, which suggested the click path did more — but click (`wake()`) is actually the WEAKER path (buffer restore + `xterm.refresh()` only); it "worked" purely because it is unconditional and synchronous. The docstring at the time claimed the exact inverse (that the focus path additionally ran the resize/reflow/flush steps) — it was backwards, and #9704 corrected it. Never trust a lifecycle docstring's strong/weak-path claims without reading both paths.

## Root cause

Three independent fail-silent holes, each of which left panes permanently unwoken.

1. **Frozen-renderer delivery.** Because unfreeze is fire-and-forget, the queued `visibilitychange` could be processed while the renderer was still frozen — a lifecycle state where the fan-out queues but cannot execute. `document.visibilityState === "visible"` is NOT proof the renderer can run work. The Page Lifecycle `resume` event is the authoritative "renderer thawed, now executable" signal; Chromium fires `resume` immediately before `visibilitychange` in the same turn on thaw, so both listeners must coalesce through a shared de-dupe (`scheduleWake` in `WorktreeStoreContext.tsx` — a microtask in #9704, since widened to a double-rAF for #10362's post-paint layout settling) or the fan-out double-runs.

2. **Terminal skip on mid-attach.** `fullWakeForVisibilityRestore` early-returned when `isAttaching`, with a comment claiming attach's post-rAF reconciliation would cover it — but that reconciliation does NOT run the full visibility-restore sequence, and there was no retry, so a pane attaching when the fan-out fired stayed stale forever. Fix: a one-shot `pendingVisibilityWake` flag on `ManagedTerminal` (`src/services/terminal/types.ts`), consumed read-and-clear by `notifyAttachSettledWaiters` (now `TerminalSettleWaiterRegistry.ts`) so a re-entrant call can't double-fire.

3. **Asymmetric lock release.** The resize-lock bypass gated on `isResizeSuppressed === true`, but the unlock additionally required `resizeSuppressionEndTime` to be truthy. The suppression timer can clear the end time between switch-back and the deferred wake while `isResizeSuppressed` stays true — so `applyDeferredResize` no-oped under the still-held lock and geometry stayed stale. Fix: unlock whenever suppressed; missing end time just means relock TTL 0.

The mechanism survives today but re-homed: `fullWakeForVisibilityRestore` moved from `TerminalInstanceService.ts` to `src/services/terminal/TerminalRevealController.ts` in the file-split, and it has since been layered — the flag is now set BEFORE the geometry sync (`pendingVisibilityWake = isAttaching === true`) so a throw can't strand it, geometry sync runs even mid-attach (#10070), streaming panes defer grid changes (#10863), and a separate post-reveal repaint pass on `app:view-revealed` exists because the wake can run while the view is still occluded behind the warm anti-flash bridge (#9679), where Chromium culls the paint (#10362).

## Lesson

- **`visibilitychange → visible` does not mean the renderer is executable.** During CDP-driven unfreeze the event can be processed while still frozen. Any renderer-side work triggered by visibility restore must also listen for the Page Lifecycle `resume` event, and the two must coalesce through one de-dupe gate because Chromium fires them back-to-back in the same turn.
- **`IntersectionObserver` visibility is scoped to the page's own viewport — a whole-`WebContentsView` hide/show at the Electron level never fires it.** Whole-view transitions must ride document-level events (`visibilitychange`/`resume`) or main-process signals (`app:view-revealed`); never assume per-element observers cover project switches.
- **A fan-out that skips a member in a transient state has silently skipped it forever unless it records a pending obligation consumed when the state settles.** The `pendingVisibilityWake` flag + `notifyAttachSettledWaiters` consumption is the canonical shape; read-and-clear the flag before dispatching so re-entrancy can't double-fire, and set it before any step that can throw.
- **Paired guard conditions drift.** If a bypass keys on `isResizeSuppressed`, the release must not additionally require `resizeSuppressionEndTime` — a timer can clear one half of the pair. Derive the decision from ONE condition and treat the missing companion as a default (TTL 0), keeping lock/unlock symmetric.
- **"Clicking fixes it" does not mean the click path is the complete one.** Here the focus path was the weak one and only won by being unconditional; the fix is making the strong path's delivery reliable, not adding work to the click path.

## Applies when

- Touching the visibility/resume wiring in `src/contexts/WorktreeStoreContext.tsx` (`scheduleWake`, `handleResume`), `TerminalRevealController.fullWakeForVisibilityRestore`, `TerminalSettleWaiterRegistry.notifyAttachSettledWaiters`, or `src/store/wakeActiveWorktreeTerminals.ts`.
- Diagnosing terminals that are stale, blank, or WebGL-garbled after a project switch-back and recover on click — the fan-out delivery holes are the first suspects, and the prior-history class is #8562/#9679/#10362.
- Adding any renderer-side listener that must run on project-view reactivation — the view may still be frozen when `visibilitychange` lands, and may still be occluded (paint culled) when the wake runs.
- Writing any broadcast/sweep that early-returns on a transient per-member state (`isAttaching`, mid-reveal, mid-resize) — verify the skipped member gets a deferred re-run, not a comment claiming another path covers it.
- Reviewing lock bypass/restore code where the bypass condition and the TTL come from two separate fields.
