## Context

`useIdleTerminalNotifications`, `useHibernationNotifications`, and `useDiskSpaceWarnings` each subscribe to a main→renderer broadcast IPC channel (via `idleTerminalClient.onNotify` etc., resolving to the preload's `_typedOn(channel, cb)` → `ipcRenderer.on(channel, handler)`) and call `notify()` on each event. The listener is meant to be one app-lifetime singleton, so each hook guarded with a module-scope `let ipcListenerAttached = false` latch, returning early when already `true`. All three mount inside `PostHydrationListeners`, which `AppInner` renders behind `{isStateLoaded && …}` (late-mount gating, #9769) — so the subtree mounts after hydration and can unmount/remount when that condition toggles.

## Problem

The same idle-terminal / hibernation / disk-space toast fired twice for a single event. The `notify()` calls already carried a coalesce window (`key: "idle-terminal-notify:projects"`, `windowMs: 30_000`), so the duplication was slipping past coalescing entirely — pointing at a second live subscriber rather than a coalesce miss. It only showed up after a `PostHydrationListeners` remount, so it looked intermittent and unrelated to the notification code itself.

## Root cause

The latch was intended to make the subscription a once-per-app singleton, but the `useEffect` cleanup did `unsubscribe(); ipcListenerAttached = false;` — resetting the very gate that was supposed to be permanent. Resetting re-arms re-subscription: a remount sees `ipcListenerAttached === false` and subscribes again. Each `_typedOn` call registers a _distinct_ `ipcRenderer.on` handler closure (returning a `removeListener` bound to that closure), so a second subscribe = a second live listener = two `notify()` calls per broadcast. A per-instance `didAttachListener` ref gated whether cleanup actually ran, which made teardown conditional and order-sensitive; under React 19 concurrent remount of a conditionally-rendered subtree the old listener's teardown and the new subscribe can overlap, leaving two handlers live at once — exactly the duplicate-toast symptom.

A second, opposite failure was baked into the ordering: `ipcListenerAttached = true` was set _before_ the `onNotify(...)` call, so a throwing subscribe (e.g. a partially-initialized preload) would wedge the latch `true` forever and silently skip every future subscription — total notification suppression, no error surfaced. #10456 removed the cleanup entirely (the listener is app-lifetime, never torn down), deleted the vestigial `didAttachListener` ref, and moved `ipcListenerAttached = true` to _after_ the subscribe returns. The remount-dedup tests assert `onNotify` is called exactly once across `render → unmount → render → render`; `useIdleBackgroundCloseNotifications` (added later) mirrors the one-way pattern.

## Lesson

- **A module-scope "do this once" latch that a cleanup resets is not once-only — it's once-per-mount.** If the guarded resource is genuinely app-lifetime (a broadcast IPC listener that should outlive any component), the latch must be truly one-way: no cleanup, no reset. Cleanup/subscribe _symmetry_ is the correct default for component-scoped effects and exactly wrong here — matching them re-opens the gate.
- **Set the latch only AFTER the guarded operation succeeds, never before.** Setting `ipcListenerAttached = true` ahead of the subscribe means a throwing subscribe wedges the latch and permanently blocks all future attempts (silent, total suppression). Set-after-success keeps the gate open for a retry — this ordering guards the opposite failure mode from the duplicate one.
- **Duplicate notifications that slip past a coalesce window are a second-subscriber symptom, not a coalescing bug.** Each `_typedOn`/`ipcRenderer.on` subscribe is an independent handler; N live listeners = N deliveries. Count subscriptions across a mount→unmount→remount cycle before touching coalesce keys — the bug is invisible in a single mount and only surfaces on the second.
- **`useErrors.ts` still carries the old, unfixed pattern** (`ipcListenerAttached = false` reset in its cleanup, deps `[addError, updateRetryProgress]`). It is currently latent only because it is mounted once directly in `AppInner` (`App.tsx`), not inside the remounting `PostHydrationListeners` subtree — moving it there, or letting its deps change identity, would resurrect the duplicate-listener bug. Do not copy that hook as a template.

## Applies when

- Adding or editing any renderer hook that subscribes to a main→renderer broadcast channel via `*.onNotify` / `_typedOn` / `ipcRenderer.on` and guards with a module-scope boolean latch — especially anything mounted in `src/components/PostHydrationListeners.tsx`.
- Diagnosing duplicate toasts / notifications where a coalesce window (`notify({ coalesce })`) is set but two identical entries still appear — suspect a second live IPC listener from a remount, not the coalesce logic.
- Reviewing a `useEffect` whose cleanup resets a module-scope singleton flag: ask whether the guarded thing is app-lifetime; if so the reset is the bug. The regression test must unmount then remount and assert subscription/`notify` count, not just re-render.
- Touching `useErrors.ts`, or moving any singleton-listener hook into a conditionally-rendered (hydration-gated) subtree — re-check the one-way-latch invariant first.
