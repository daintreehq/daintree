## Context

Daintree styles the renderer entirely through a Tailwind v4 `@theme inline { … }` block in `src/index.css` that defines a bespoke token system (`--color-daintree-*`, `--color-status-*`, `--radius-*`) instead of Tailwind's stock scales. PR #10374 was a 67-item design-consistency sweep that, among other things, cleaned up two categories of drift left behind by the earlier v3→v4 Tailwind upgrade. Both categories are worth a lesson because they fail _silently_ — no build error, no runtime error, no type error — so they accumulated invisibly across dozens of components.

## Problem

Two visible-but-unexplained symptoms. (1) Several checkboxes rendered as fully-rounded pills — a `w-3.5 h-3.5` checkbox with `rounded` looked like a radio button, and keyboard chips / settings badges / small inputs read visibly rounder than deliberately-sized siblings. (2) Warning and error accents were just _missing_: `text-amber-500` on a "Tool description changed" label, `bg-emerald-500/15 text-emerald-400` count pills, `text-red-400` failure lists all rendered with no color at all. Neither symptom threw anything — the checkbox "looked designed" and the missing accent looked like an oversight, so both pointed away from the real cause.

## Root cause

Two independent mechanisms, both rooted in the `@theme` block.

1. **Bare `rounded` now resolves to `var(--radius)` = 10px, not 4px.** `src/index.css:176` sets `--radius: calc(0.625rem * var(--theme-radius-scale, 1))` = 10px at the default scale. Tailwind v4's bare `rounded` utility reads that `--radius` variable; in v3 it was a hard-coded `0.25rem` (4px) unaffected by any variable. So every component authored expecting `rounded` ≈ 4px silently drifted to 10px the moment the app moved to v4. Because `--radius-lg: var(--radius)` too (`src/index.css:392`), `rounded` and `rounded-lg` are now the _same_ 10px. On a 14px checkbox box, a 10px radius is nearly a full circle — hence the radio-button look. The fix is to pin small controls explicitly: `rounded-sm` (6px) for the checkbox, `rounded-[var(--radius-xs)]` (4px) for chips. The full scale is `--radius-xs:4 / -sm:6 / -md:8 / -lg:10 / -xl:14` at `src/index.css:389-393`.

2. **`--color-*: initial` deletes the entire stock Tailwind palette.** `src/index.css:34-35` opens the block with `@theme inline { --color-*: initial; … }`, which removes every default color variable. So `--color-amber-500`, `--color-emerald-500`, `--color-red-400`, `--color-blue-400`, `--color-green-400` simply don't exist — and a Tailwind v4 color utility with no backing `--color-*` variable generates _no rule at all_. `text-amber-500` isn't an error, it's a no-op class. Only the explicitly-defined families survive: `status-{error,warning,success,info}` (+ `-surface`), `daintree-*`, `overlay-*`, `tint`, `text-placeholder`, `text-link`. The fix replaces every stock reference with a token: `text-amber-500`→`text-status-warning`, `bg-emerald-500/15 text-emerald-400`→`bg-status-success/15 text-status-success`, `text-red-400`→`text-status-error`, `text-blue-400`→`text-status-info`.

There is **no lint/stylelint guard** for either trap — the PR added none and none exists today; both are caught only by eye.

## Lesson

- **In this repo bare `rounded` means 10px, not 4px** — it reads `--radius` (`src/index.css:176`) under Tailwind v4, and equals `rounded-lg`. When you round a _small_ control (checkbox, chip, badge, ≤~16px input), never lean on bare `rounded`; pick explicitly from the `--radius-*` scale (`rounded-sm`=6px, `rounded-[var(--radius-xs)]`=4px). A checkbox at `rounded` reads as a radio button.
- **Bare `rounded` is fine where 10px is actually wanted** (overlays, menus, dialogs — the sweep even made those explicit as `rounded-[var(--radius-lg)]`). The trap is _only_ small controls authored pre-v4 expecting the old 4px; audit those specifically rather than blanket-replacing `rounded`.
- **Never use a stock Tailwind palette class** (`text-amber-500`, `bg-emerald-500/15`, `text-red-400`, `-blue-400`, `-green-400`, etc.) — `--color-*: initial` at `src/index.css:34` wiped them, so they silently render nothing. Reach for `status-error` / `status-warning` / `status-success` / `status-info` (each with a `-surface` variant); these are the only status colors that exist.
- **Both failures are invisible at build and runtime** — no type error, no console warning, no guard. Treat a missing accent color or an over-round control as a _token_ bug, not a spacing/design oversight, and grep the file for stock color names and bare `rounded`.
- **Treat a Tailwind bump like an xterm bump** (cf. `9546.md`): the utility _semantics_ change even when class names don't. After any Tailwind upgrade or `@theme` edit, re-verify that `rounded`, the `--radius-*` scale, and every color utility still resolve to what the authoring component assumed.

## Applies when

- Authoring or reviewing a new renderer component that rounds a small control — checkbox, radio, chip, badge, pill, or a compact input — and reaching for `rounded`.
- Adding a warning/error/success/info accent and about to type `text-amber-*`, `bg-emerald-*`, `text-red-*`, `text-blue-*`, or `text-green-*` — use `status-*` tokens instead.
- Bumping the Tailwind version or editing the `@theme inline` block / `--radius` / `--color-*` definitions in `src/index.css`.
- Diagnosing "this checkbox looks like a radio button," "everything is too rounded," or "the warning/error color isn't showing up" with no error in the console.
- Reviewing a design-consistency PR that touches border radius or status colors — check for silent drift, since neither trap surfaces in CI.
