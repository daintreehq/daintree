## Context

PR #4603 made Canopy auto-inject `--turbopack` into Next.js dev commands (webpack's `style-loader` CSS injection silently fails inside the Electron webview). It did so at two layers: `findDevServerCandidate` / `applyNextjsTurbopack` in the renderer (`src/utils/devServerDetection.ts`, for the displayed command) and `normalizeNextjsDevCommand` in the main process (`electron/services/DevPreviewCommandNormalizer.ts`, as the runtime safety net). Turbopack only became the supported/stable dev flag in Next.js 15; on Next 14 and below `next dev --turbopack` breaks the project. #5168 gates injection on the installed major version and adds a per-project toggle.

## Problem

The renderer injection layer has no version awareness — it cannot read `node_modules`, so `applyNextjsTurbopack` appends `--turbopack` to ANY detected Next.js command. That pre-injected command is then sent over IPC (`DevPreviewEnsureRequest`) and reaches the main-process normalizer. The obvious gate — "if Next major < 15, return the command unchanged" — is wrong: the command it receives already carries the renderer's `--turbopack`, so skipping injection still leaks the flag onto a Next 14 project.

## Root cause

Asymmetric context across the IPC boundary: the layer that injects (renderer) lacks the information needed to decide whether injection is valid (the filesystem version), and the layer that has the information (main, via `resolveNextMajorVersion` reading `node_modules/next/package.json` then `package.json` deps) is downstream of the injection. A gate written as "skip adding the flag" assumes the input is clean; here the input is already dirty.

## Lesson

When a flag is injected by one layer and validated by another, and the injecting layer lacks the validation context, the validating layer must actively NEUTRALIZE the bad input, not merely decline to add to it. In `normalizeNextjsDevCommand` the no-go branches return `stripTurbopackFlag(command)` (removes both `next dev --turbopack` direct form and `npm run dev -- --turbopack` package-manager form) rather than returning `command`. Three branches strip: `turbopackEnabled === false`, version `null`, and major `< 15`. Treat `null` (version unresolvable — dist-tag like `latest`/`canary`, missing dep, malformed JSON) as "unknown = strip", the safe default. The renderer toggle (`turbopackEnabled` threaded through `useDevServer` → `DevPreviewEnsureRequest` → `session.turbopackEnabled`) gates BOTH layers, but the version check stays main-only because only main can read the filesystem. Note the `package.json` fallback parser strips the leading semver-range prefix (`^~>=<v` and whitespace) before `parseInt` — a caret range `^15.0.0` must resolve to `15`, not `NaN`.

## Applies when

- Editing `normalizeNextjsDevCommand` / `stripTurbopackFlag` / `applyNextjsTurbopack`, or adding gating for any other dev-command flag (e.g. a new framework's CSS-mode flag).
- Any two-layer command/argument rewrite where an upstream layer (renderer, UI display) injects without the context the downstream layer (main, filesystem) uses to validate — the downstream branch must strip, and a unit test must assert the strip on a pre-injected input, not just absence-of-injection.
- Parsing an installed package version: prefer `node_modules/<pkg>/package.json` `version`, fall back to `package.json` dep range with the range-prefix stripped, and return `null` (not a guessed major) for dist-tags so callers can choose the safe default.
