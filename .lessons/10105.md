## Context

The RecipeRunner is the one-click agent launcher: grid mode is the default layout (the common first-run case), list mode (`RecipeRunnerList.tsx`) appears with search above the threshold. List mode already implemented the combobox pattern correctly — focus pinned in the search input, `aria-activedescendant={focusedItemId}`, a container `handleKeyDown` in `useRecipeRunner.ts` owning arrows/Enter. The grid was the inconsistent sibling: each recipe was a native, Tab-reachable `<button onClick={() => onRun(recipe.id)}>` inside a wrapper `<div onKeyDown={...}>`, with a separate `focusedIndex` state (initialized to 0, moved only by Arrow keys) driving an `aria-selected` ring and deciding what Enter activates (#9962).

## Problem

Tab to the third recipe, press Enter — the **first** recipe launches its terminals. On an automation launcher that spawns agent processes, that's an action misfire, not a cosmetic glitch. Arrow keys compounded it: they moved the `aria-selected` ring while real DOM focus stayed put, so two different items could appear highlighted simultaneously. The misleading part: every individual piece looked fine in isolation — the buttons had correct onClick handlers, the keydown handler had correct index math. The bug only exists in the interaction between the two.

## Root cause

Two live focus models with no synchronization. Native buttons own Tab (browser moves real DOM focus); `focusedIndex` owns Enter (container keydown dispatches `handleRun(flat[focusedIndex].id)`); nothing — no `onFocus` handler — ever wrote the Tabbed-to button back into `focusedIndex`. The killer line was `e.preventDefault()` in the Enter branch: it cancelled the focused button's **native** activation (which would have run the right recipe) and substituted the handler's stale-index dispatch. The hand-rolled handler simultaneously suppressed the correct behavior and executed the wrong one — without that preventDefault the bug would have been invisible.

The fix (#10105) unified the grid on a roving-tabindex model where all three signals — visual selection, DOM focus, and what Enter runs — are one item by construction: `tabIndex={focusedIndex === i ? 0 : -1}` on each option, a per-button `handleOptionKeyDown` whose pure `moveFocus()` maps arrows/Home/End to the next index and calls `buttonRefs.current[next]?.focus()` (real focus moves), `onFocus={() => setFocusedIndex(i)}` so ANY focus entry (Tab, Shift+Tab, click, programmatic) resyncs the index, and — critically — **no Enter/Space branch at all**: activation is the native button click, and a test explicitly asserts Enter is not preventDefault'ed. List mode legitimately kept the other model (`useRecipeRunner.ts` `handleKeyDown`, ~L492, still live on develop) because focus must stay pinned in the search input for typing. Both models now coexist in one component tree, each internally consistent — the rule was never "always use activedescendant", it's "one model per widget".

## Lesson

- **One focus model per composite widget.** If children are Tab-reachable (all `tabIndex={0}`) AND a separate index state decides activation, Tab desyncs them by construction. Commit to roving tabindex (real focus moves, index follows) or `aria-activedescendant` (focus pinned, handler owns everything) — never both halves of each.
- **`e.preventDefault()` on Enter in a container keydown over native buttons is the review tell.** It cancels the visibly focused button's native activation and substitutes handler state — upgrading a cosmetic highlight desync into executing the wrong action. If the children are buttons, the Enter branch shouldn't exist.
- **Choose the model by whether a typing surface must hold focus.** RecipeRunnerList keeps focus in the search input → activedescendant is correct there; RecipeRunnerGrid has no input → roving tabindex + native activation. The repo has 10+ activedescendant widgets (`PanelPalette`, `SearchablePalette`, sidebar, dropdowns) — don't blindly copy one into a widget with no pinned input.
- **Roving-tabindex checklist (all four or it's broken):** `tabIndex` 0 only on the focused item, −1 on the rest; a refs array so arrow handlers call `.focus()` on the target; `onFocus` syncs the index (this is what catches Tab entering mid-list — arrows-only sync is the original bug); a modifier bailout (`if (e.altKey || e.ctrlKey || e.metaKey) return`) so app shortcuts pass through the widget.
- **A `focusedIndex` with no `onFocus` writer is stale by design** — arrows are just one of four ways focus enters an item. The same hand-rolled-roving class recurred later in the dock rail (#11156, arrows in a docked terminal stolen by an unguarded chip keydown): treat every bespoke composite widget in this codebase as a candidate for this audit.
- Detail worth copying: the trailing create option stays reachable when items are disabled (`tabIndex={disabled || focusedIndex === createIndex ? 0 : -1}`), so keyboard users can always reach "Create new recipe" with zero recipes. A later launcher polish (`34704b2f8`) gated the `aria-selected` ring behind `group-focus-within/recipes:` so the ring only paints while the grid actually contains focus — killing the ghost-highlight-while-focus-is-elsewhere artifact.

## Applies when

- Building or reviewing any hand-rolled listbox / grid / menu / toolbar with arrow-key navigation — especially one mixing native `<button role="option">` children with an index state.
- Diagnosing "Enter/Space activates the wrong item", "the first item runs no matter what's focused", or "two items look highlighted at once".
- Adding a container-level `onKeyDown` that calls `preventDefault()` above focusable children — verify no child's native activation is being cancelled.
- Touching `RecipeRunnerGrid.tsx`, `RecipeRunnerItem.tsx`, or the still-live list-mode `handleKeyDown` in `useRecipeRunner.ts`.
- Assuming a keydown-driven index and real DOM focus "stay in sync on their own" — without an `onFocus` writer they cannot.
