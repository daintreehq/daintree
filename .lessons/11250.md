## Context

Plugin custom UI reaches non-panel locations (bulk-create worktree dialog, issue selector, settings tab, stats dropdown, icon) through `builtinRendererRegistry.ts` — a second, bespoke registry alongside the standard `contributes.views` / `PluginViewContent` panel path. Issue #11244 (part of a panel-as-dialog consolidation wave, after #11239/#11240) proposed folding this seam into `contributes.panels` + `contributes.views` so plugins get dialog presentation through the same mechanism they already use for panels, retiring the second registry. #11250 investigated that fold.

## Problem

The investigation didn't find a fold, it found a wall: the standard path is architecturally incompatible with how built-in renderers ship today. Along the way it also found the seam was silently unguarded in both directions — a dropped or typo'd `forgeProviders.slots` ref reached production as missing UI with only a dev-console warning nobody watches, and a `registerBuiltinView` call registered under the wrong `pluginId` would leave a disabled plugin's UI on screen (it slips the enable-aware gate in `resolveSlot`).

## Root cause

`contributes.views` resolves a view's `componentPath` to a `plugin://{id}/{path}` URL and lazy-imports it (`PluginViewContent.tsx`, `PluginViewHost.tsx` — see the `import('plugin://...')` race-against-timeout in `PluginViewContent.tsx`). That requires the plugin to ship its renderer as a separately built, `plugin://`-loadable bundle. Built-in renderer entries do not: `builtinPluginRenderers.ts` uses `import.meta.glob("../../plugins/builtin/*/renderer/index.{ts,tsx}", { eager: true })` to pull every built-in's renderer straight into the **host** bundle for its registration side effects, and those components import host modules directly (`BulkCreateWorktreeDialog.tsx` alone pulls in ~20 `@/` modules). The glob's eagerness is load-bearing (a deferred import races first render and `getBuiltinView` returns null), and `package.json`'s `sideEffects` array pins `./src/registry/builtinPluginRenderers.ts` plus `./plugins/builtin/*/renderer/index.ts(x)` explicitly so rolldown doesn't tree-shake the chain. There is no `plugin://` module for the standard loader to reach, so folding needs a real architectural change — either give built-ins a standalone build boundary (sever the host imports through the SDK/import map) or teach view-resolution to resolve host-bundled components in-process — not a manifest tweak.

An earlier draft tried a middle path anyway: a new `contributes.builtinViews` contribution kind cross-validated against `slots`. Reverted for three reasons: it made `builtinViews` required on the public `PluginManifest`, breaking `npm run typecheck` across 7 existing fixtures; it broke external (non-built-in) forge plugins that use `slots`, since they could satisfy neither the ref check nor a builtin-only gate; and it was circular — `slots` already names the ids, so declaring them a second time only checks two strings against each other, leaving the relationship that actually matters (declared id → registered component) unproven. The merged fix checks that instead: `builtinViewRegistrations.test.ts` source-scans each built-in's `plugin.json` for `forgeProviders.slots` refs and its `renderer/index.ts(x)` for matching `registerBuiltinView("<id>", ..., { pluginId })` calls, asserting every ref has a registration and every registration's `pluginId` matches the declaring plugin's manifest name. It's a regex-based text scan, not an execution trace — a call that's commented out, tree-shaken, or built with a non-literal id is invisible to it — a deliberate tradeoff to avoid pulling the whole host renderer graph into a dependency-free node test.

## Lesson

- **Before proposing to unify `builtinRendererRegistry` with `contributes.views`, know the build-boundary blocker is unresolved** — built-in renderers are eagerly globbed into the host bundle (`sideEffects`-pinned), not shipped as `plugin://`-loadable assets; #11244 stays open pending one of the two architectural changes named above, and neither was attempted here.
- **Don't re-attempt the `contributes.builtinViews` middle path** — tried and reverted for three concrete reasons (breaks manifest typecheck, breaks external `slots`-using plugins, circular against `slots`). If you find yourself designing "a new contribution field that mirrors `slots`," re-read this first.
- **When a seam splits validation across two processes that can't see each other, add a drift test, not a runtime check.** Main validates `forgeProviders.slots` for shape only (no access to the renderer bundle); the renderer only warns in dev mode. `builtinViewRegistrations.test.ts` closes that gap statically, at the source-text level, in CI.
- **A "no view registered for slot" dev warning is not a safety net** — fires only in dev mode, only after render, and nobody watches the console; treat any similarly-shaped cross-process registration seam (declared-here, implemented-there) as needing a CI source-scan guard, not a runtime warn.
- **`pluginId` ownership checks matter as much as existence checks** — a `registerBuiltinView` call present but registered under the wrong plugin's id passes a naive "is it registered" check while still slipping the enable-aware gate in `resolveSlot`, leaving a disabled plugin's UI rendering.

## Applies when

- Picking up issue #11244 or any follow-on to fold `builtinRendererRegistry` slots into the panel/view contribution path.
- Adding a new built-in plugin renderer entry, or a new `forgeProviders.slots` ref, and wondering whether it's validated end-to-end (it isn't, outside this test).
- Designing a plugin manifest contribution field that duplicates an id already declared elsewhere in the manifest "for cross-checking" — check whether the duplication proves anything or is circular like the reverted `contributes.builtinViews` draft.
- Touching `src/registry/builtinPluginRenderers.ts`, its `import.meta.glob(..., { eager: true })`, or the `package.json` `sideEffects` array — these must move together or the built-in view chain gets tree-shaken or race-loses to first render.
- Reviewing any two-sided registration seam (declared in config, implemented in code, validated by neither side) — check whether a source-scan drift test is missing before adding a third such seam.
