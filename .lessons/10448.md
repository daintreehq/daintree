## Context

On app restart, `restorePanelsPhase` respawns each saved panel by reconnecting to its live backend session. If a PTY panel's reconnect times out (~2000ms), `statePatcher.buildArgsForRespawn` passes `requestedId: undefined` so the store mints a **fresh generated id** instead of the saved one (`statePatcher.ts:619` — `requestedId: reconnectTimedOut ? undefined : saved.id`). Tab groups (panel groupings) are persisted separately and hydrated afterward by `hydrateTabGroups` (`tabGroups.ts:644`), which validates each group's `panelIds` against the live id set.

## Problem

After a restart where a saved PTY panel failed to reconnect in time, its tab group silently collapsed: a two-tab group became a solo panel, and it never came back. No error surfaced. Misleading because the panel restore looked correct — the panel reappeared fine; only its membership vanished, so the bug read as "grouping is flaky" rather than "restore regenerated the id."

## Root cause

The timed-out panel respawns under a NEW id, but the persisted tab group still references the OLD saved id, un-remapped. `hydrateTabGroups` filters `panelIds` against the live id set, drops the now-dead saved id, then discards any group left with `finalPanelIds.length <= 1` (`tabGroups.ts:680`) — and crucially **persists the shrunk result** via `saveTabGroups` on the happy path (`tabGroups.ts:768-769`, gated only by `!options?.skipPersist`). So the collapse isn't a transient view — it's written back to storage, permanently. The catch path passes `skipPersist: true`; the success path has no such guard.

Fix (#10448): `restorePanelsPhase` already tracks `restoredIdsByIndex`, so it now builds a **sparse** `savedIdToRestoredId` map (only divergent ids get an entry; identity mappings excluded) and returns it. `hydrateAppState` remaps each group's `panelIds` and `activeTabId` through it _before_ `hydrateTabGroups` (`index.ts:550`).

Companion #10450 (issue #10441): the same membership integrity broke at runtime add-tab. `addPanelToGroup` returned `void` and only `console.warn`'d when its `set()` updater rejected an add (missing group, worktree mismatch, deleted mid-await — `tabGroups.ts:147`). Every caller created a panel, called `addPanelToGroup`, then unconditionally `setActiveTab`/`setFocused` — orphaning the new panel and stealing focus onto it on rejection. The fix returns a `boolean` read from the **canonical store** (`get().tabGroups.get(groupId)?.panelIds.includes(panelId)` — `tabGroups.ts:214`), not a closure flag, because a zustand `set()` updater that returns unchanged state cannot signal failure to its caller. Callers gate activation behind it and `trashPanel` the orphan (plus any group the call created).

## Lesson

- **When restore can regenerate a persisted id, every persisted structure keyed to the old id is silently orphaned unless you thread a saved→restored remap through hydration.** The reconnect-timeout path (`statePatcher.ts:619`) mints a fresh id; tab-group membership, `activeTabId` pointers, focus targets — any cross-reference to a saved id — must remap BEFORE the consumer validates against the live id set. `restorePanelsPhase` returns `savedIdToRestoredId`; new id-referencing persisted state must consume it too.
- **A sanitizer that persists its own output turns a transient filter into permanent data loss.** `hydrateTabGroups` drops ≤1-member groups then `saveTabGroups` the shrunk map (`skipPersist` guards only the error path). Any hydrate step that both filters AND writes back must be certain the filter is correct — an over-eager filter erases the source of truth. When unsure, hydrate view-only and defer the persist.
- **Keep the remap sparse and fail-safe.** Exclude identity mappings so consumers fast-path on `savedIdToRestoredId.size > 0`; declare it outside the restore `try` so a restore throw leaves it empty and groups hydrate unremapped (pre-fix behavior), not against a half-built map. Skip malformed entries (`Array.isArray(group.panelIds)`) — mapping over a non-array throws into the catch, which clears ALL groups for the session.
- **A zustand `set()`-based mutation with a silent reject path needs a success signal read from `get()`, not a closure flag — the updater returns unchanged state on rejection and can't signal failure (#10450).** Create-then-mutate-then-focus callers must gate `setActiveTab`/`setFocused` behind a post-`set()` membership check and `trashPanel` the orphan (plus any group the call created), in both the reject branch and the catch.

## Applies when

- Touching `src/utils/stateHydration/` (`panelRestorePhase`, `index`, `statePatcher`) or any restore path where a panel/session can respawn under a new id after a reconnect timeout.
- Adding any persisted structure that references panel ids (tab groups, active-tab/focus pointers, saved layouts) — remap it through `savedIdToRestoredId` during hydration or lose members silently and permanently.
- Diagnosing "a tab group silently collapsed after restart," or any post-restart membership loss that does NOT recur next launch (the sanitized loss was persisted).
- Reviewing any zustand `set()` mutation with a reject branch whose callers create-then-add-then-focus — confirm it returns a `get()`-derived success signal and callers trash the orphan.
- Writing a hydration sanitizer that both filters AND persists — verify the filter can't erase valid state before it writes back, and that error paths use `skipPersist`.
