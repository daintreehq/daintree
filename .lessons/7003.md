## Context

The MCP server lets the Daintree Assistant (and external clients) dispatch Actions and read the action manifest in the renderer. Each project window is its own `WebContentsView` with an independent V8 context. The renderer bridge (`rendererBridge.ts`) routed every MCP tool call through `getActiveProjectWebContents()` — the most-recently-focused live view.

## Problem

With two or more windows open, focused-window routing crossed the trust boundary. A help-session bearer minted by window A (project A) would dispatch its tool calls into whichever window happened to have focus — so assistant A could silently read project B's worktrees, terminals, and git state, and act on them. The session's bearer authority is scoped to project A, but the dispatch target was decoupled from that authority entirely.

## Root cause

The security boundary for a help-session bearer is the **WebContents that minted it at handshake**, not whoever has focus at call time. "Active window" is a UI affordance; it has nothing to do with which session is authorized for which renderer. As long as routing keyed off focus, the bearer's scope and the dispatch target could diverge the moment the user clicked another window. A single shared bridge with one "active view" resolver cannot express per-session authority.

Two non-obvious follow-on traps once you pin per session:

- **Fail-open fallback re-opens the hole.** Resolving the pinned `webContents.fromId(id)` at call time and falling back to the active view when it's destroyed silently re-routes to a different project. The pinned helpers (`getPinnedWebContents`) must throw `MCP pinned view <id> no longer available` and fail closed.
- **The shared manifest cache re-leaks across the boundary.** `cachedManifest` is global across all callers. If a pinned session writes window A's manifest into it (or reads it), window B's session can be served A's manifest. Pinned helpers must bypass the cache entirely — `requestManifestForWebContents` does not write `cachedManifest`, and `buildSessionServerDeps` returns a `getCachedManifest` that yields `null` for any session in `sessionWebContentsMap`. This forced a fix in `lookupManifestEntry` (`sessionServer.ts`), which used to re-read `getCachedManifest()` _after_ `await requestManifest()` — always null for pinned sessions, silently dropping confirm-elicitation and structuredContent. It now uses the direct return value of `requestManifest()`.

## Lesson

- For any session-scoped capability in a multi-WebContents app, **pin the target WebContents id at handshake/provision time and store it per session** (here `sessionWebContentsMap`, resolved from the bearer via `HelpSessionService.getWebContentsIdForToken`). Never resolve the target from focus/active-window state at call time.
- **Fail closed.** When the pinned view is gone (`fromId` returns undefined or `isDestroyed()`), throw an explicit error — never fall back to a default/active view. Falling back is the same bug wearing a different hat.
- **Audit shared caches for cross-boundary leakage.** A process-wide cache (`cachedManifest`) keyed by nothing is safe only when all callers share one trust scope. The moment you introduce per-session scoping, the cache must be bypassed for scoped sessions, and any "request-then-re-read-cache" pattern breaks — use the request's direct return value instead.
- **Lifecycle parity is mandatory.** The per-session pin map must be cleaned up in _every_ path that removes a session (idle timer, `onclose`, catch block, `drain()`), in lockstep with `sessionTierMap`, or it leaks WebContents ids and can stomp a reused session id.
- External (api-key / pane-token) sessions deliberately keep the focused-window fallback — pinning applies only to bearers whose authority is window-scoped. The resolver returns `null` for non-help bearers.

## Applies when

- Adding any MCP transport, IPC channel, or background service that dispatches into a renderer on behalf of a credential/session, in a multi-window / `WebContentsView`-per-project app.
- Reviewing code that resolves a dispatch target via `getActiveProjectWebContents()`, `getFocusedWebContents()`, or "the active window" when the operation carries session/bearer authority.
- Introducing per-session scoping over an existing shared cache, or seeing a "call X, then re-read shared state" pattern where X may not populate that state.
