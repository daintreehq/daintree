## Context

On cold start the renderer paints a default theme before the async `appThemeClient.get()` (via `useAppThemeConfig`) resolves the persisted scheme. The main process tries to pre-paint the right colors two ways: a `WebContentsView` background color at construction time, and `injectSkeletonCss(wc)` which calls `wc.insertCSS(..., { cssOrigin: "user" })` to set `:root` theme CSS variables on the startup skeleton. The renderer's `applyDefaultAppTheme(root)` (`src/theme/applyAppTheme.ts`) sets `--theme-*` custom properties as inline styles on `documentElement`.

## Problem

The wrong theme flashed on every cold start (initial load, project switch, LRU-evicted view re-creation) until the async config resolved — even though the main process had already pushed the correct theme variables via `insertCSS`. Default fell back to `prefers-color-scheme`, so a user with a saved light theme saw a dark flash (and vice-versa). #9169.

## Root cause

CSS cascade _origin precedence_. `WebContents.insertCSS` injects at **user-origin**. The renderer's `applyDefaultAppTheme` writes the same `--theme-*` variables as **inline styles on the element** — which are **author-origin** and (for non-`!important` declarations) always outrank user-origin in the cascade. So the main process's `insertCSS` theme variables were correct but were silently overridden by the renderer's author-origin inline defaults the moment React mounted. The precedence is invisible at either call site — you'd assume `insertCSS` "wins" because it runs first in main, but origin order, not timing, decides.

## Lesson

- `insertCSS({ cssOrigin: "user" })` cannot override renderer **inline** styles. Inline styles are author-origin and beat user-origin in the cascade regardless of injection timing. Don't rely on `insertCSS` to seed values the renderer will later set inline — fix it at the inline-style layer instead.
- To get a value from the main process into the renderer **before first paint** (before any IPC/async config resolves), pass it through `webPreferences.additionalArguments` (e.g. `["--daintree-initial-color-scheme-id=daintree"]`). `preload.cts` reads it synchronously from `process.argv` — which works even under `sandbox: true` — and exposes it via `contextBridge.exposeInMainWorld` (here `window.__DAINTREE_INITIAL_THEME__`). This is the canonical pre-paint seed channel; IPC/`appThemeClient.get()` is too late.
- preload can't import the main-process constant across the esbuild bundle boundary, so `INITIAL_COLOR_SCHEME_ARG` is hardcoded in `preload.cts` and a unit test (`resolveInitialColorSchemeId.test.ts`) asserts the literal matches — a rename otherwise silently reintroduces the flash.
- Only resolve **synchronously-knowable** values this way. The seed path applies only built-in scheme ids (`getAppThemeById`); custom/unknown ids deliberately fall through to the `prefers-color-scheme` default and let the async `useAppThemeConfig` phase finish, rather than painting a wrong built-in.
- The seed must cover every cold-start origin: both `createWindow.setupBrowserWindow` and `ProjectViewManager.createView()` must pass `additionalArguments`, or project-switch / LRU-evicted views regress.

## Applies when

- Diagnosing a theme / color / dark-mode flash or FOUC on Daintree startup, project switch, or after an LRU view eviction.
- Touching `injectSkeletonCss` / `skeletonCss.ts`, `wc.insertCSS`, or any `cssOrigin: "user"` injection and expecting it to override renderer styles.
- Editing `applyDefaultAppTheme` / `src/theme/applyAppTheme.ts`, `applyAppThemeToRoot`, or anything that sets `--theme-*` inline on `documentElement`.
- Needing a main-process value available in the renderer _before first paint_ — reach for `webPreferences.additionalArguments` + `process.argv` in preload, not IPC.
- Adding a new `WebContentsView` / `BrowserWindow` creation path (e.g. in `ProjectViewManager`) — replicate the `additionalArguments` seed or reintroduce the flash on that path.
- Any "main says X but the renderer shows Y" CSS bug where both sides set the same custom property — check cascade origin (author inline vs user `insertCSS`), not injection timing.
