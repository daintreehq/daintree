## Context

The help-assistant flow spins up an in-process MCP server (`McpServerService` → `httpLifecycle.ts`) before writing the agent's `.mcp.json` and launching the assistant terminal. `HelpSessionService.ensureMcpServerReady()` gates that launch on the server being "ready" so the assistant doesn't connect to a dead endpoint.

## Problem

Subtle MCP init failures (handler not wired, auth misconfigured, transport half-initialized) passed the readiness gate silently. `.mcp.json` got written and the assistant terminal launched against a server that then hung or 500'd on the assistant's very first request — a failure that only surfaced after the user was already in the session (#6898).

## Root cause

The readiness check was passive: `isRunning` is defined (httpLifecycle.ts:172) as `httpServer !== null && httpServer.listening && port !== null`. `server.listen()` flips `listening` true the instant the OS socket binds — that happens _before_ the HTTP request pipeline, the bearer-auth path, host validation, and the Streamable-HTTP/SSE transport handlers have ever serviced a real request. So the readiness signal fired far earlier than actual end-to-end readiness; the gap between socket-bound and request-serviceable was invisible to a check that only reads `listening`.

## Lesson

For any spawned server you hand to another process, do not gate downstream wiring on the OS-level "socket bound" signal (`server.listening`, `httpServer.listening`, a resolved `listen()` callback). That only proves the kernel accepted the bind. Gate on an **active self-probe** that exercises the real request path end-to-end:

- `probeMcpServer(port, apiKey)` POSTs a genuine `initialize` JSON-RPC to `/mcp` with the bearer token and only succeeds on HTTP 200 + a real `mcp-session-id` response header — proving handler dispatch + auth + transport all work.
- Bound the probe: bounded attempts (`PROBE_MAX_ATTEMPTS=3`), exponential backoff (`PROBE_BASE_DELAY_MS` × 2^n), a per-request timeout, and a separate hard timeout (`PROBE_HARD_TIMEOUT_MS`) capping the whole loop — so a hung server fails fast instead of blocking launch forever.
- A successful probe creates real server state (an MCP session); tear it down fire-and-forget (DELETE with the `mcp-session-id`) so the probe doesn't leave a zombie session. Make cleanup non-fatal — log on failure, never bubble.
- One transport can stand in for another only when they share the wiring being validated: the probe hits `/mcp` (Streamable HTTP) even though the assistant config uses `/sse`, because auth + host validation + handler dispatch are shared. Note explicitly when a probe is a proxy for a different path (only a transport-specific fault would slip through). A later change added `probeMcpSseServer` for the SSE path specifically.

## Applies when

- Adding or changing readiness/health gates for any locally-spawned server (MCP server, dev-preview server, portal, any `http.createServer` in `electron/services/`).
- Touching `httpLifecycle.ts` `isRunning`, `McpServerService`, or `HelpSessionService.ensureMcpServerReady()` / session provisioning.
- A bug report where an agent/assistant connects to a server that hangs or 500s on its first request despite the server reporting "running"/"ready".
- Any code that treats `server.listening`, a resolved `listen()` callback, or a "process started" signal as proof the service can serve requests.
- Writing `.mcp.json` (or any agent config pointing at a live endpoint) and launching a terminal/agent against it — verify the endpoint actually answers before writing config.
