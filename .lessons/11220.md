## Context

Each project gets its own `WebContentsView` via `ProjectViewManager`; switching away caches the previous view for a fast switch-back rather than destroying it — `ProjectViewLifecycleController.deactivateEntry` does this via `contentView.removeChildView(view)` plus `view.setVisible(false)`, and also applies `Emulation.setCPUThrottlingRate` to the guest. The terminal subsystem's periodic work — `TerminalReconciliationWatchdog.tick()`, `TerminalReflowController`'s reflow heartbeat, `TerminalWriteController`'s `requestAnimationFrame` activity markers — was gated on `document.visibilityState !== "visible"` to skip work on panes nobody can see.

## Problem

Diagnostics for #11212 found a cached (backgrounded, not visible to the user) project view still burning 4.5% CPU at 3300 idle wakeups/second — as if it were the active foreground project. It wasn't just wasted timers: because a cached view's hosts still carried real, viewport-passing rect geometry, the watchdog classified panes in the hidden project as on-screen and issued real repairs against them — `forceReflow`, `ensureWebGL` (contending for the fleet-wide WebGL context cap, #10671) — work with a real cost, spent on a project the user had switched away from.

## Root cause

Chromium tracks page occlusion/visibility at the `BrowserWindow` level, not per child `WebContentsView`. `removeChildView` and `setVisible(false)` are exactly the operations `deactivateEntry` uses to cache a view, and neither one changes `document.visibilityState` for that view's page — a cached view reports `"visible"` forever and its `requestAnimationFrame` loop keeps firing at full rate. Every gate written as `document.visibilityState !== "visible"` was therefore dead code for the cached-view path, while still working correctly for genuine OS-level occlusion (minimizing the window) — the same line is correct in one hidden-state and silently inert in another, which is why it hid. The CPU throttle already applied alongside caching (`Emulation.setCPUThrottlingRate`) slows each callback's execution but not how often it fires. Only a `Page.setWebLifecycleState` freeze cuts firing rate, and that's deliberately skipped whenever the cached project still has a live agent running — exactly the case costing the most. So no existing DOM/Chromium signal told the renderer "I am a cached child view"; it had to come from main over IPC.

## Lesson

- **`document.visibilityState` is a `BrowserWindow`-level signal in a multi-`WebContentsView` app; it does not reflect `removeChildView`/`setVisible(false)` on a child view.** Combine (AND) a timer/rAF gate with an explicit main-lifecycle signal — don't replace the visibility check with it, since the visibility check still correctly catches real OS occlusion (window minimize); see `src/lib/viewCacheState.ts`'s doc comment.
- **CPU throttling is not a firing-rate gate.** `Emulation.setCPUThrottlingRate` slows what a callback does per tick, but a `requestAnimationFrame` loop still fires at full cadence and burns wakeups; only a `Page.setWebLifecycleState` freeze stops the firing, off the table whenever the cached view still hosts a live process (agent TUI) that can't be suspended. When that's true the renderer must demote its own periodic work — there's no free platform lever.
- **Gate every entry point to the work, not just its timer.** `TerminalReflowController`'s per-write path (`onWriteParsedReflow`) calls `maybeReflow()` directly, bypassing the heartbeat interval — gating only the interval would have missed most invocations. Enumerate every call site before declaring a gate complete.
- **New reusable pattern:** `src/lib/viewCacheState.ts` is a lazily-armed renderer singleton seeded from `window.electron.app.isViewCached()`, updated via `onViewCached`/`onViewWarmActivated`/`onViewRevealed`. The seed is latched in `electron/preload.cts` (`_viewCached`, before any page script runs) because the `app:view-*` signals are non-replaying `ipcRenderer.on` edges and a cold switch is released at the pre-React skeleton — a switch storm can cache a view before its module graph subscribes, permanently losing the edge. Reuse preload-latching for any main→renderer lifecycle signal a late subscriber must not miss.
- **The un-gate signal is `warm-activated`, not `revealed`.** Main only sends `revealed` when a switch lands on that view; a superseded switch delivers `warm-activated` alone, so keying the clear on `revealed` strands a reactivated view demoted forever. Any rollback path that force-restores visibility (`ProjectViewSwitchController`'s cold-switch failure branch) must itself resend `warm-activated`, or it leaves a _visible_ view with a permanently-paused xterm.
- **Don't let a hidden-view fix touch the byte stream.** The gate covers only render/analysis timers (markers, reflow, watchdog) — ingest, `terminal.write`, and ledgers stay fully live while cached. Gating ingest would reintroduce the reveal-time backlog detonation #4853's flush budget fixed, and pausing/resyncing a live agent TUI is exactly what #10811 removed hibernation to stop doing.

## Applies when

- Touching `TerminalReconciliationWatchdog`, `TerminalReflowController`, `TerminalWriteController`, or any per-terminal periodic/`requestAnimationFrame` work and reasoning about whether it stops when a project is backgrounded.
- Diagnosing unexplained idle CPU or high wakeup counts attributed to a project view that isn't the focused/active one.
- Writing or reviewing any Electron code that gates work on `document.visibilityState` inside a child `WebContentsView`/`BrowserView` — confirm whether "hidden" means real OS occlusion (the check works) or app-level detach/cache via `removeChildView`/`setVisible(false)` (the check is dead).
- Adding a new gate for cached/backgrounded views — use `isProjectViewCached()` from `src/lib/viewCacheState.ts` and AND it with the existing visibility check rather than replacing it.
- Adding any new main-to-renderer lifecycle IPC signal that a cold-start or fast-switch renderer could miss due to subscription-timing races — consider latching it in `electron/preload.cts`.
