## Context

`shell.openExternal(url)` hands a URL to the OS to launch in the default handler for its scheme. The app has a central wrapper `openExternalUrl` (`electron/utils/openExternal.ts`) that validates the URL against an `ALLOWED_PROTOCOLS` set before calling `shell.openExternal`. Several call sites — `OAuthLoopbackService` (renderer-supplied `authUrl`), `forge.ts`, `github.ts`, `voiceInput.ts`, `menu.ts` — were calling `shell.openExternal` directly, skipping the wrapper.

## Problem

The OAuth loopback flow passed a renderer-supplied `authUrl` (from a dev-preview webview) straight to `shell.openExternal` after only a `typeof === "string"` check. A scheme like `file:///etc/passwd`, `javascript:…`, or a custom app scheme would reach the OS launcher unvalidated — the renderer could make the main process launch arbitrary external handlers. Each ad-hoc call site was its own bypass with no single chokepoint to audit.

## Root cause

Two distinct gaps:

1. **No single sink.** Direct `shell.openExternal` calls scattered across handlers meant the allowlist was advisory, not enforced. There was no structural guarantee that a new call site would inherit validation.
2. **`ALLOWED_PROTOCOLS` was a flat constant set including platform-specific schemes everywhere.** `ms-settings:`/`ms-windows-store:` only resolve on Windows and `x-apple.systempreferences:` only on macOS, but allowlisting them on all platforms widens the attack surface: on a platform that doesn't own a scheme, a third-party app can register it as its handler, so allowing the scheme there lets a renderer-supplied URL hijack into that foreign app. The fix replaces the constant with `buildAllowedProtocols(platform)` that gates each platform scheme to its owning platform; `http:`/`https:`/`mailto:` stay universal.

## Lesson

- **One chokepoint.** Route every external-launch through `openExternalUrl`. Never call `shell.openExternal` directly outside `openExternal.ts`. The standing regression invariant is `grep -rn "shell\.openExternal" electron/` returns only `openExternal.ts` itself — wired into the audit table in `docs/architecture/destructive-action-safeguards.md` ("External launch surfaces").
- **A `typeof === "string"` check is not validation.** Any renderer-supplied URL reaching a system sink must pass a protocol allowlist; treat string-type as untrusted input.
- **Make scheme allowlists platform-conditional.** A platform-specific scheme should only be allowed on the platform that owns the handler — otherwise an attacker-registered handler on a foreign platform becomes a hijack vector. Use `buildAllowedProtocols(platform)`, not a flat set.
- **Validate before side effects in a typed-result contract.** `startOAuthLoopback` parses `new URL(authUrl)` and returns `{ success: false, cause: "server-error" }` on failure _before_ `cancelOAuthLoopback(panelId)` runs — a malformed URL must not synchronously throw out of the result contract, nor cancel an in-flight session for the same panel. A disallowed scheme settles as `open-external-failed` via the `.catch`.
- `shell.openPath` takes a filesystem path, not a URL, so the protocol allowlist does not apply — gate those on app-derived or validated-absolute paths instead.

## Applies when

- Adding any new call that opens a URL externally (PR links, settings deep-links, help/docs links, mic/privacy settings) — route through `openExternalUrl`, never `shell.openExternal` directly.
- Touching `OAuthLoopbackService`, `forge.ts`, `github.ts`, `voiceInput.ts`, or `menu.ts` external-open paths.
- Any renderer-supplied or webview-supplied value (`authUrl`, `prUrl`) flowing toward a main-process OS sink — audit for a protocol allowlist, not just a type check.
- Adding a platform-specific URL scheme (`ms-settings:`, `x-apple.systempreferences:`, store deep-links) to an allowlist — gate it to its owning platform in `buildAllowedProtocols`.
- Reviewing destructive/external-launch surfaces against `docs/architecture/destructive-action-safeguards.md`; verifying the `grep` invariant during security review.
