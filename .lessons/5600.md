## Context

Plugins register `ActionDefinition` entries at runtime through the host API. This is the foundational PR for that path: `PluginService` holds a `pluginActions` Map of `PluginActionDescriptor`, `usePluginActions` mirrors them into the renderer `ActionService`, and a startup validator (`handleValidateActionIds` in `electron/ipc/handlers/plugin.ts`) checks that every toolbar-button/menu-item `actionId` resolves to a real action.

## Problem

Three non-obvious traps sit under "let a plugin register an action," each of which a competent engineer hits by treating a plugin action like a built-in:

- A plugin's action handler is a closure over main-process state — it physically cannot be serialized across the IPC boundary into the renderer's `ActionService`, where `dispatch()` and the command palette expect to call `run()` directly.
- The startup unknown-action validator snapshots `BUILT_IN_ACTION_IDS` and would flag every plugin-contributed `actionId` as unknown, because plugins register dynamically _after_ that snapshot is taken.
- A plugin whose main module calls `host.registerAction` / `host.registerHandler` synchronously at import time would throw "Unknown plugin", because the plugin wasn't in `this.plugins` yet when its own module evaluated.

## Root cause

The plugin-action registry is split across the process boundary by _capability_, not just by data: the executable handler is main-only, the metadata is what the renderer needs. So the renderer never receives a real action — it receives a `PluginActionDescriptor` (metadata + ids only) and reconstitutes a **synthetic `ActionDefinition`** whose `run()` IPC-bounces back to main via `window.electron.plugin.invoke(pluginId, id, args)` (`toSyntheticDefinition` in `src/hooks/usePluginActions.ts`). `ActionService` dispatch, palette, and confirm flow all work on this synthetic shell; the actual work happens one IPC hop away in the plugin's main module.

The validator trap is the same split viewed from the other side: `knownIds` is a startup snapshot, but the plugin-action set is _live_. `handleValidateActionIds` must merge `pluginService.listPluginActions()` into `knownIds` at call time (`for (const { id } of pluginService.listPluginActions()) knownIds.add(id)`) — never validate plugin contributions against a static action-id list.

The import-ordering trap is a registration race: `PluginService.loadPlugin` does `this.plugins.set(manifest.name, plugin)` **before** `await import(mainModule)`, so any host-API call during module evaluation sees `hasPlugin(pluginId) === true`. Insert-then-import, not import-then-insert.

Two consequences ride along: plugin action ids are namespaced `{pluginId}.{actionId}` (built-ins use colons, so the formats can't collide) and ownership is enforced (`id.startsWith(pluginId + ".")`); and the renderer mirror uses pull-on-mount as a safety net with push-on-change authoritative (`pushReceived` guard drops a late-resolving mount pull) — the same propagation discipline as the panel-kind registry in #6324.

## Lesson

- When an extension-contributed unit of behavior carries a non-serializable executable (a handler closure over host state), do NOT try to ship the executable. Ship metadata + ids, reconstitute a **synthetic definition on the consuming side whose `run()` IPC-bounces back** to where the real handler lives. The consumer's dispatch/palette/registry machinery then works unchanged.
- Any "is this id known?" validator over a set that extensions mutate at runtime must read the **live registry at call time**, never a startup snapshot. Merge `listPluginActions()` (or the equivalent live source) into the known-set inside the handler.
- Register the plugin into the loaded-plugins map **before** importing its main module, so synchronous `host.*` calls during module evaluation see the plugin as loaded. Insert-then-import.
- Namespace plugin-contributed ids as `{pluginId}.{id}` so they can't collide with built-in ids (built-ins use colons here), and reject any id a plugin tries to register outside its own namespace.

## Applies when

- Adding any plugin/extension contribution type whose behavior is an executable that lives in main but is consumed in the renderer (actions, commands, handlers) — decide metadata-only + IPC-bounce vs. trying to cross the boundary.
- Touching `toSyntheticDefinition` / `usePluginActions` (`src/hooks/usePluginActions.ts`), `registerPluginAction` / `listPluginActions` in `electron/services/PluginService.ts`, or the `plugin:actions-*` / `plugin:invoke` channels.
- Writing or reviewing any startup-time validator (`handleValidateActionIds`, toolbar-button/menu-item id checks) that asserts ids resolve — confirm it consults the live plugin registry, not `BUILT_IN_ACTION_IDS`.
- Adding host-API methods plugins may call synchronously during module import — verify `PluginService.loadPlugin` inserts into `this.plugins` before `await import`.
