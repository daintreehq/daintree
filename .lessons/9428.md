## Context

`PluginService` (in the main process, `electron/services/PluginService.ts`) loads curated plugins: validates the manifest, registers contribution points (panels, menus, forge providers, file-decoration providers, IPC handlers), then runs the plugin's exported `activate()`. Activation requires a dynamic `import()` of the plugin's `main` module.

## Problem

Loading fused two phases inside `loadPlugin`: it `import()`-ed and `activate()`-ed every plugin with a `main` entry at startup, even plugins never used that session. Cold-start cost scaled linearly with the curated plugin set for no benefit — contribution-point registration (cheap, needed for routing) paid the full module-import + activate cost it didn't need.

## Root cause

The two phases have different cost profiles and timing requirements but were collapsed: contribution registration is needed eagerly so menus/panels/actions can route, but `import()`+`activate()` only needs to run the first time a plugin is actually exercised. Splitting them surfaced three non-obvious traps:

- **Idempotency contract.** `activatePlugin(id)` is hit by racing triggers (panel open + action dispatch in the same tick). It must run `_doActivate` exactly once: synchronous fast-path `activatedPlugins: Set` check, then an in-flight `activationPromises: Map<id, Promise>` so concurrent callers share one promise. On success the entry caches for the plugin lifetime; on failure it is _deleted_ so Settings "Retry activation" can re-run. Critically, `activatePlugin` **never rejects** — contribution-point triggers require a failed activation to leave routing entries intact, so errors go only to the persisted `loadError` provenance record.
- **Unload race, both directions.** Unload clears `plugins`/`activatedPlugins`/`activationPromises` synchronously, but a late-resolving activation would (a) re-insert a tombstoned id into `activatedPlugins`, and (b) write a `cleanup` fn into `cleanupMap` _after_ unload already cleared it — leaking e.g. a `setInterval` the plugin set in `activate()`. Both writes are gated on `this.plugins.has(pluginId)` re-checked after the await.
- **import() timeout is coupled to Promise.allSettled fan-out.** Startup activation and file-decoration-scope activation use `Promise.allSettled([...].map(activatePlugin))`, which waits for _every_ promise to settle. A plugin with a hanging top-level await (`await new Promise(() => {})`) would pin its activation promise forever and stall the whole fan-out. So `runImport` races `import()` against a 5s `IMPORT_TIMEOUT_MS` (separate from `ACTIVATE_TIMEOUT_MS`, which guards the exported `activate()`). ESM's URL-keyed module cache means a successful import resolves instantly on retry.
- **pluginId-contains-dot attribution.** Plugin ids are `publisher.name` (already a dot), and contributions are namespaced `pluginId.contributionId`. Resolving the owner of `acme.foo.bar` by string-splitting on `.` mis-attributes. `activatePluginForForgeProvider` resolves the owner by iterating the manifest registry and reconstructing `` `${pluginId}.${contribution.id}` `` for equality instead.

## Lesson

When a load step bundles cheap eager work (registration) with expensive lazy work (import/activate), split it on the cost/timing boundary. For deferred activation in `PluginService`:

- Keep manifest validation + contribution-point registration at scan time; defer `import()`+`activate()` to `activatePlugin(id)`, triggered implicitly by the first real use (action dispatch in `dispatchHandler`, file-decoration pull, forge-provider lookup) plus an `onStartupFinished` opt-in.
- An idempotent activation entry point needs all three: a synchronous done-Set fast path, an in-flight promise Map for concurrent dedup, and a never-rejecting contract that surfaces errors via a side record (`loadError`) — not by rejecting the promise that triggers route through.
- Re-check `this.plugins.has(id)` after every `await` inside activation before writing back any state (activated-set, cleanup fn), because unload can run concurrently.
- Any `import()` reachable from a `Promise.allSettled` fan-out must be timeout-bounded — `allSettled` is only as fast as the slowest unsettled promise, and a plugin's hanging top-level await is unbounded otherwise.
- Resolve a namespaced contribution's owning plugin via the registry, never by splitting on `.` — plugin ids already contain a dot.
- New `activationEvents` values must be validated loudly at parse time (`z.literal("onStartupFinished")` in `electron/schemas/plugin.ts`) so authors writing `onCommand:foo` (not yet implemented) fail at scan, not silently never-activate.

## Applies when

- Adding a new plugin contribution-point type and wiring its lookup path — you must add an implicit-activation hook (like `activatePluginsForFileDecorationScope` / `activatePluginForForgeProvider`) so providers bound during `activate()` are queryable on the first pull.
- Touching `loadPlugin`, `_doActivate`, `activatePlugin`, `activateStartupFinishedPlugins`, `unloadPlugin`, or `runImport` in `electron/services/PluginService.ts`.
- Adding new `activationEvents` (e.g. `onCommand:*`, `onView:*`) — update both `electron/schemas/plugin.ts` and `shouldActivateOnStartup`.
- Debugging a plugin that "loaded but its handler/provider isn't there yet" on first call, a `loadError` that won't clear, a hung startup behind a slow/hanging plugin, or a leaked timer/interval after plugin unload.
- Any main-process service that defers expensive per-item work behind an idempotent async entry point hit by concurrent callers, or fans out per-item async work via `Promise.allSettled` where one item could hang.
