## Context

`WorkspaceService` (workspace-host utility process) delegates `.git/worktrees/` watching to a dedicated `TopologyWatcher` (`electron/workspace-host/TopologyWatcher.ts`), which uses `@parcel/watcher` so external `git worktree add/remove` reconcile into the cache. `WorkspaceService`'s own `createWorktree`/`deleteWorktree` run `git worktree add/remove`, which themselves fire watcher events on the same metadata subdir. To avoid a redundant `discoverAndSyncWorktrees` pass for app-owned ops, the watcher suppressed matching events around those ops.

## Problem

Suppression was a blanket `topologyWatchSuppressUntil = Date.now() + 60000` timestamp: `scheduleTopologyReconcile()` early-returned for the whole window. Any _external_ `git worktree remove` that landed during those 60s was silently dropped — the deleted worktree stayed in the cache until the next adaptive poll (up to ~30s later). The window could not tell an app-initiated change from a concurrent external one (#8412).

## Root cause

A time-window suppressor discards events by _when_ they arrive, but self-induced and external changes are interleaved in time and indistinguishable by timestamp. The only thing that actually distinguishes "my event" from "someone else's" is _identity_ — which path changed and in which direction. The blanket window threw that information away, so it had to choose between dropping real external events (the bug) or letting redundant app-owned reconciles through.

## Lesson

When you must suppress the watcher/event-stream noise _your own_ operation produces, filter by exact identity match, not by a time gate:

- Register the affected key before your op (here `TopologyWatcher.metadataKey()` — `basename(pathResolve(worktreePath))`, the exact leaf `@parcel/watcher` reports for `.git/worktrees/<name>`), into direction-specific sets — `pendingCreate` vs `pendingDelete` (`electron/workspace-host/TopologyWatcher.ts:74-75`), via `markPendingCreate`/`markPendingDelete`. Gate the match on event `type` so a pending _create_ can't swallow an external _delete_ of a same-named entry.
- Drop a pending entry the first time a matching event drains it (`clearPending`), so a _subsequent_ external change to the same name is no longer treated as yours.
- Buffer events across the existing debounce and filter at drain time so burst coalescing is preserved; anything unmatched (or an unclassifiable empty payload) still reconciles.
- Add a clear-only safety valve (5s `setTimeout`, `.unref()`, `markPending`'s `pendingSafetyTimers`) so a missed/never-arriving watcher event can't leave an entry suppressing real external changes forever. Clear-only — never trigger a reconcile from the valve; the cooldown/dirty path already reschedules genuinely-needed reconciles.
- Clear all pending sets + their timers on stop/dispose (`TopologyWatcher.stop()`): a stale entry surviving a pause/resume would suppress a real external change after restart.
- In the op's `catch`, clear the pending key too (hoist the key above the `try` so the catch can reach it) — a failed op must not mask a later external change to that name.

## Applies when

- Touching `TopologyWatcher` (`electron/workspace-host/TopologyWatcher.ts`) — `pendingCreate`/`pendingDelete`, `markPendingCreate`/`markPendingDelete`/`clearPending`, `scheduleReconcile`, `startSafetyTimer` — or `WorkspaceService`'s `discoverAndSyncWorktrees`/`scheduleTopologyReconcile` (the thin wrapper that delegates to `topologyWatcher.scheduleReconcile`), or anything keyed off `.git/worktrees/` events.
- Adding any "suppress the watcher during my own write" logic against `@parcel/watcher`, `chokidar`, `fs.watch`, or git file watching where the app both writes and watches the same path.
- Symptoms: external `git worktree remove`/`add` not reflected until the next poll; cache showing stale or missing worktrees only when an app-owned create/delete recently ran; "works in isolation, lost under concurrency" topology bugs.
- Reviewing any `Date.now() + N` / `suppressUntil` time-window guard intended to filter self-induced events — flag it and ask whether identity-keyed filtering is needed instead.
