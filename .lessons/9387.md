## Context

Daintree announces async status (form errors, save confirmations, inline status) to screen readers through a single `AccessibilityAnnouncer` live region (`aria-live="polite"/"assertive"`) mounted once at the App root (`src/App.tsx:772`), driven by `useAnnouncerStore.announce()` (`src/store/accessibilityAnnouncerStore.ts`). Modals (`AppDialog`, `AppPaletteDialog`, `ProjectSwitcherPalette`, `ReviewHub`, `WorktreeOverviewModal`, fullscreen `ErrorFallback`) render with `aria-modal="true"`.

## Problem

Any `announce()` fired while a modal is open is silently dropped on macOS VoiceOver. The DOM mutates and the live region updates correctly, but VoiceOver never speaks it — so a save confirmation or form error after a modal interaction is invisible to AT users with no error and no failing test.

## Root cause

This is a platform AT filter, not a code bug. When an `aria-modal="true"` dialog has focus, VoiceOver (via Chromium) suppresses `aria-live` region updates that live **outside** that modal's DOM subtree (Chromium issue 354736464). The app-root announcer is outside every modal's subtree, so its updates are filtered out the moment any modal is focused. No JS error fires; the live region's `textContent` changes exactly as written — the AT just refuses to narrate it.

## Lesson

- The real fix is the native `document.ariaNotify(msg, { priority })` API, which queues announcements directly with the platform AT and **bypasses the aria-modal subtree filter entirely**. It is only newly available in Chrome 141+ / Chromium 146 / Electron 41 — do not assume older docs mention it. Feature-detect at call time (`typeof document.ariaNotify === "function"`) inside a `try/catch`, since it's optional and can throw. Map `polite → { priority: "normal" }`, `assertive → { priority: "high" }` (`tryAriaNotify` in `accessibilityAnnouncerStore.ts:40`). Declare it as optional on `Document` (`src/types/aria-notify.d.ts`) so every call site is forced to feature-detect.
- Keep a DOM-mutation fallback for when `ariaNotify` is unavailable or throws: co-locate an `<AccessibilityAnnouncer />` **inside** each `aria-modal` wrapper so the live region lives in the focused subtree. Any new modal/palette that renders its own `aria-modal` (especially ones that portal to `document.body` and bypass `AppDialog`/`AppPaletteDialog`, like `ProjectSwitcherPalette`) needs its own co-located announcer.
- The fallback creates a stale-replay hazard: multiple announcer instances subscribe to the same store entry, so a modal mounting _after_ an announcement was already spoken would re-narrate the stale message into its newly focused subtree. Guard with a module-scoped `deliveredIds` per channel (`isDelivered`/`markDelivered`) — a later-mounting announcer skips any entry id already delivered.

## Applies when

- Adding or debugging screen-reader announcements (`useAnnouncerStore.announce()`, `aria-live`, `AccessibilityAnnouncer`) — especially announcements that fire while a dialog/palette is open.
- Building a new modal, dialog, palette, or overlay that sets `aria-modal="true"` (anything via `AppDialog`, `AppPaletteDialog`, or a hand-rolled `createPortal(..., document.body)` modal) — it needs a co-located live region for the DOM fallback path.
- Reports of "VoiceOver doesn't speak X" where the DOM clearly updates and tests pass — suspect the aria-modal subtree filter, not your code.
- Reaching for a newly-shipped Chromium DOM API: confirm it's actually present in the bundled Chromium version (Chromium 146 / Electron 41) and feature-detect; `document.ariaNotify` is one such API.
- Coordinating multiple instances of the same announcer/live-region component so they don't double-narrate — use module-scoped delivered-id tracking rather than store state.
