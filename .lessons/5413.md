## Context

Batch worktree/terminal creation stalled in hard pauses every 10 terminals. The first 10 spawned instantly, then the flow froze for the rest of the window before the next 10 went, repeating as a visible step-function.

## Problem

`waitForRateLimitSlot` in `electron/ipc/utils.ts` is a single name fronting TWO completely different rate-limiting algorithms, dispatched purely by arity: the 2-arg form `waitForRateLimitSlot(key, intervalMs)` is a strict-interval leaky bucket (one caller released every `intervalMs`, smooth cadence), and the 3-arg form `waitForRateLimitSlot(key, maxCalls, windowMs)` is a sliding window (up to `maxCalls` run freely, then everyone queues until the window rolls). The terminal spawn handler in `electron/ipc/handlers/terminal/lifecycle.ts` called the 3-arg form `("terminalSpawn", 10, 30_000)`. That call site reads as a perfectly reasonable "10 per 30s" cap, but a sliding window with a small `maxCalls` is a step-function under sustained batch load: it releases a burst of `maxCalls`, then blocks the whole batch until the oldest timestamp ages out.

## Root cause

The overload makes the algorithm choice invisible at the call site — arity, not a named parameter, selects between leaky-bucket and sliding-window. Worktree creation had already moved to the 2-arg leaky form for exactly this reason (#4519), but terminal spawn silently kept the 3-arg sliding form. The fix was a one-line swap to `waitForRateLimitSlot("terminalSpawn", 1_000)`, choosing the leaky bucket so N concurrent `Promise.all` spawners claim sequential slots synchronously (`state.nextAvailableMs` advances before any `await`, see `waitForLeakyBucketSlot`) and drain at a steady 1/sec instead of in batches. The spawn call site has since moved again: `electron/ipc/handlers/terminal/lifecycle.ts:91-95` now calls `waitForBurstRateLimitSlot("terminalSpawn", TERMINAL_SPAWN_INTERVAL_MS, TERMINAL_SPAWN_BURST)` — a token-bucket sibling that banks a small idle burst (`TERMINAL_SPAWN_BURST = 6`) before settling to the same steady `TERMINAL_SPAWN_INTERVAL_MS = 1_000` cadence, plus a separate recipe-batch admission gate (`claimRecipeSpawnBatchAdmission`) so a scripted multi-terminal recipe launch shares one slot instead of contending per-terminal. `waitForBurstRateLimitSlot` is always a 3-arg call and is still leaky-bucket underneath — it is a second, differently-named helper, not the sliding-window overload of `waitForRateLimitSlot`.

## Lesson

For any rate limit fronting a batch-tolerant operation (spawn, bulk create), the sliding-window form produces step-function stalls and is almost never what you want — reach for the strict-interval leaky bucket (`waitForRateLimitSlot`'s 2-arg form) or its burst-capable sibling `waitForBurstRateLimitSlot(key, intervalMs, burst)` so a burst drains at smooth cadence. Because `waitForRateLimitSlot` selects the algorithm by arity, the wrong choice is invisible at the call site and reads as a sensible cap; the spawn test (`electron/ipc/handlers/terminal/__tests__/lifecycle.spawn.test.ts`, `"terminal spawn rate limiting (#5352)"`) guards this by asserting `waitForRateLimitSlot` is never called at all (`expect(waitForRateLimitSlotMock).not.toHaveBeenCalled()`) alongside the exact args passed to `waitForBurstRateLimitSlot`, precisely because a stray call to the arity-dispatched helper would silently reintroduce the stalling behavior. When auditing a rate-limited handler, count the arguments on `waitForRateLimitSlot` calls specifically, and check which of the two named helpers is actually in play — `waitForBurstRateLimitSlot` is 3-arg by design and is still leaky-bucket, so arity alone stops disambiguating once both helpers are in scope.

## Applies when

- Calling `waitForRateLimitSlot` or `waitForBurstRateLimitSlot` in `electron/ipc/utils.ts` for any handler invoked in bulk (terminal spawn, worktree create, recipe batch admission, batch IPC)
- Diagnosing batch flows that pause every N operations in a repeating step-function rather than throttling smoothly
- Reviewing a rate-limit change and seeing a 3-arg `waitForRateLimitSlot(key, maxCalls, windowMs)` call on a batch path — prefer the 2-arg leaky-bucket `(key, intervalMs)` form, or `waitForBurstRateLimitSlot(key, intervalMs, burst)` if a bounded idle burst is genuinely wanted; a 3-arg call to `waitForBurstRateLimitSlot` itself is not the sliding window and needs no fix
