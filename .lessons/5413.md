## Context

Batch worktree/terminal creation stalled in hard pauses every 10 terminals. The first 10 spawned instantly, then the flow froze for the rest of the window before the next 10 went, repeating as a visible step-function.

## Problem

`waitForRateLimitSlot` in `electron/ipc/utils.ts` is a single name fronting TWO completely different rate-limiting algorithms, dispatched purely by arity: the 2-arg form `waitForRateLimitSlot(key, intervalMs)` is a strict-interval leaky bucket (one caller released every `intervalMs`, smooth cadence), and the 3-arg form `waitForRateLimitSlot(key, maxCalls, windowMs)` is a sliding window (up to `maxCalls` run freely, then everyone queues until the window rolls). The terminal spawn handler in `electron/ipc/handlers/terminal/lifecycle.ts` called the 3-arg form `("terminalSpawn", 10, 30_000)`. That call site reads as a perfectly reasonable "10 per 30s" cap, but a sliding window with a small `maxCalls` is a step-function under sustained batch load: it releases a burst of `maxCalls`, then blocks the whole batch until the oldest timestamp ages out.

## Root cause

The overload makes the algorithm choice invisible at the call site — arity, not a named parameter, selects between leaky-bucket and sliding-window. Worktree creation had already moved to the 2-arg leaky form for exactly this reason (#4519), but terminal spawn silently kept the 3-arg sliding form. The fix is a one-line swap to `waitForRateLimitSlot("terminalSpawn", 1_000)`, choosing the leaky bucket so N concurrent `Promise.all` spawners claim sequential slots synchronously (`state.nextAvailableMs` advances before any `await`, see `waitForLeakyBucketSlot`) and drain at a steady 1/sec instead of in batches.

## Lesson

For any rate limit fronting a batch-tolerant operation (spawn, bulk create), the sliding-window form produces step-function stalls and is almost never what you want — reach for the strict-interval leaky bucket (2-arg form) so a burst drains at smooth cadence. Because `waitForRateLimitSlot` selects the algorithm by arity, the wrong choice is invisible at the call site and reads as a sensible cap; the spawn test guards this with `expect(mock.calls[0]).toHaveLength(2)` precisely because a stray third argument silently reverts to the stalling behavior. When auditing a rate-limited handler, count the arguments, not just the numbers.

## Applies when

- Calling `waitForRateLimitSlot` in `electron/ipc/utils.ts` for any handler invoked in bulk (terminal spawn, worktree create, batch IPC)
- Diagnosing batch flows that pause every N operations in a repeating step-function rather than throttling smoothly
- Reviewing a rate-limit change and seeing a 3-arg `(key, maxCalls, windowMs)` call on a batch path — prefer the 2-arg leaky-bucket `(key, intervalMs)` form
