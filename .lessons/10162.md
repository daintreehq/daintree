## Context

`notify()` (`src/lib/notify.ts`) routes every notification across surfaces by three flags: `priority` (`"low"` = inbox-only, no toast), `transient` (skip the inbox entirely), and `placement`. #9050 centralized routing in the `EVENT_POLICY` manifest — each `NotificationEventKind` maps to a `baseInterruption`, and `resolveEventPolicyDefaults()` fills any omitted `priority`/`urgent`/`placement` from it (`INTERRUPTION_TO_PRIORITY` maps `passive → "low"`). The same PR added the `notify-event-kind` lint rule requiring `context.eventKind` on every `notify()` call, kicking off a long-tail migration.

## Problem

User-visible confirmations silently vanished with no error anywhere: "Error details copied" on the crash screen (`ErrorBoundary.tsx`), bulk-remove success (`useWorktreeBulkRemove.ts`), "Issue assigned" with its Undo action (`NewWorktreeDialog.tsx`), "Diagnostics saved" with its CTA (`diagnosticsReviewStore.ts`), and the `safeStorage` permanent-fallback warning. Every call site looked correct in isolation and in review — each had a semantically accurate `eventKind` and a sensible `transient: true` for ephemeral feedback.

## Root cause

Two individually-correct defaults compose into a no-op. The passive eventKinds (`uiFeedback`, `settings`, `workingPulse`) resolve an omitted `priority` to `"low"`, which routes inbox-only; `transient: true` skips the inbox. Their intersection routes to no surface at all — `notify()` returns normally and nothing renders. Ten call sites had adopted passive eventKinds specifically to satisfy the #9050 lint rule, treating `eventKind` as a classification label when it is actually a routing directive; the lint rule itself herded callers into the trap.

Every existing guard was blind to the composed shape. The #6885 lint ban matches only a literal `priority: "low"` property in source — the policy layer reconstructs the banned shape at runtime where lint cannot see it. The DEV `console.warn` for `transient` + low fired, but its message ("transient with priority: 'low' is a no-op") was incomprehensible to a caller who never wrote `"low"`. The `EVENT_POLICY` test suite asserted passive demotion only with `type: "info"`, non-transient, action-free payloads. A secondary trap compounded the Undo case: the history-actions filter in `notify()` keeps only actions with an `actionId`, so an onClick-only Undo on an inbox-routed notification is unreachable even in the inbox. The fix (#10162): explicit `priority: "high"` at the ten sites (eventKind stays; explicit fields always win over policy), a DEV warn that distinguishes caller-written from policy-resolved low via `hadExplicitPriority` captured before `resolveEventPolicyDefaults()`, and a `no-restricted-syntax` rule flagging exactly `transient: true` + passive eventKind + no explicit `priority`.

## Lesson

- **`context.eventKind` changes routing, not just classification.** Tagging `uiFeedback`/`settings`/`workingPulse` resolves an omitted `priority` to `"low"` (inbox-only). Any user-visible feedback — copy confirmations, undo toasts, failure warnings — must pin `priority: "high"` explicitly alongside the semantically-correct kind (the `panelLimitStore.ts` / `projectActions.ts` pattern).
- **Audit the intersections of surface-suppressing flags, not each flag alone.** `priority: "low"` (skip toast) and `transient: true` (skip inbox) are each sensible; together they deliver nowhere. When touching any default-filling layer, enumerate the pairwise combinations with every flag that suppresses a surface and prove each combo still lands somewhere.
- **A lint rule that mandates metadata will drive a regression if the metadata has behavioral side effects.** Callers added eventKinds to satisfy `notify-event-kind`, unaware each kind carries routing defaults. When introducing a required-metadata rule, check whether the metadata alters runtime behavior — and if it does, say so in the lint message.
- **Static lint bans on literal payload shapes are blind to policy-resolved equivalents.** #6885 bans a written `priority: "low"` on error toasts, yet `resolveEventPolicyDefaults()` rebuilds that exact shape at runtime. Guard composed no-ops twice: at the resolver (a DEV warn that distinguishes caller-written from policy-resolved values — a warn naming a value the caller never wrote gets ignored) and at the composition trigger in lint.
- **onClick-only actions die outside the live toast.** The history-actions filter keeps only `actionId`-backed actions, so any notification demoted to inbox-only silently loses its onClick actions. Action-bearing `notify()` calls must guarantee toast delivery (explicit high priority) or use `actionId` actions.
- **esquery `:has()` trap in `eslint.config.js`:** a child combinator followed by a descendant chain inside `:has()` (`:has(> A > B > C)`) silently matches nothing in our esquery version — the selector passes review and CI while enforcing nothing. Both notify rules deliberately omit the leading `>` before the `context` property; copy that shape for any new nested-payload selector, and test a new selector against a known-violating fixture before trusting it.

## Applies when

- Writing or reviewing any `notify()`/`addNotification()` call that sets `context.eventKind` to `uiFeedback`, `settings`, or `workingPulse` — especially with `transient: true` or an `action`.
- Diagnosing "a toast/confirmation stopped appearing" with no error or log — check whether policy demotion routed it inbox-only, or the `transient` + passive-kind intersection dropped it entirely (DEV builds now warn; production is silent).
- Adding kinds to `EVENT_POLICY`, changing a `baseInterruption`, or touching `resolveEventPolicyDefaults()` / `INTERRUPTION_TO_PRIORITY` in `src/lib/notify.ts`.
- Introducing any policy/default-resolution layer that fills omitted fields, or a lint rule that mandates metadata feeding one — the #9050 → #10162 arc is the canonical failure sequence.
- Writing a `no-restricted-syntax` selector in `eslint.config.js` that needs `:has()` over a nested object payload.
