## Context

React 19.2 introduced the Activity API for preserving component tree state across visibility transitions (e.g., tab switching). This PR evaluated whether Activity could be used for instant project UI switching in Daintree.

## Problem

Vestigial `key={activeProjectId}` props on `<ProjectScopeProvider>` and `<AppShell>` in `App.tsx` forced a full component tree remount on every project switch, adding unnecessary teardown/remount cost.

## Root cause

The Activity API preserves state across visibility transitions _within a single React tree_. Daintree's per-project `WebContentsView` architecture gives each project its own renderer process — across the project boundary there is no shared tree to preserve, so Activity cannot make project switching "instant" the way it would in a single-renderer app. (Activity is still useful _within_ a renderer for hide-without-unmount cases — Daintree now uses `<Activity>` in `src/components/ui/fixed-dropdown.tsx` to keep an open dropdown mounted while hidden; that intra-tree use is unrelated to the cross-project case this PR evaluated.)

The `key={activeProjectId}` props were a leftover pattern from before per-project renderers existed, when project switching genuinely needed to reset all component state. They now cause unnecessary full remounts with no benefit.

## Lesson

`key` props on top-level component trees force complete React subtree remounts. In Electron apps where project isolation is achieved via separate `WebContentsView` renderer processes, `key`-based remounting at the app root is redundant and should be removed.

Before adopting a React feature for state preservation across tab/view switches, confirm whether the boundary you're crossing is within one React tree or spans separate renderer processes. The React 19 Activity API only preserves state within a single tree — it cannot bridge Daintree's per-project `WebContentsView` renderer boundary.

## Applies when

- Evaluating React 19 Activity / `<Activity>` component for Electron apps
- Auditing `key` props on top-level components after architectural changes
- Migrating from single-renderer to multi-renderer project isolation
