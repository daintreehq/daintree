## Context

GitHub shipped as the builtin `daintree.github` forge plugin, but the app still carried native GitHub surfaces: `github:*` IPC handlers, a `window.electron.github` preload bridge, renderer view slots (toolbar pills, settings tab, issue selector), and a startup token probe in `globalServicesInit`. Preferences exposed a per-plugin enable toggle. #10343 made it authoritative; #10347 then deleted all host GitHub knowledge, leaving the `ForgeProviderImpl` contract as the only seam.

## Problem

Disabling `daintree.github` in Preferences removed nothing — issues, PRs, repo stats, and the settings panel all stayed live, even across a restart. The toggle was cosmetic: it flipped persisted `disabled` state and nothing consulted it. Worse, a disabled plugin still leaked a background `/user` fetch on startup, because token-health probing lived outside any plugin lifecycle.

## Root cause

Wiring is static; enable-state is dynamic — and both surfaces resolved feature contributions at wiring time, so a runtime flag could never reach them. The `github:*` IPC handlers registered unconditionally at boot (a one-time side effect — you cannot un-register a handler by flipping a store), so they answered regardless of plugin state. The renderer's slot registry registered plugin views unconditionally too, and consumers imported the component directly, so nothing checked `disabled` at render. A toggle that only writes persisted state is inert unless each surface re-reads it at the point of use.

The fix splits registration from resolution on both sides. Renderer: `registerBuiltinView(slotId, component, { pluginId })` still registers unconditionally, but `resolveSlot` returns `null` when `pluginId` is in `pluginRuntimeStore.disabledPluginIds` — and the React entry point is `useBuiltinView`, which subscribes to that set so a live toggle drops the UI without a restart (`getBuiltinView` is the non-reactive read and won't re-render). `pluginRuntimeStore` mirrors the disabled set from `plugin.list()`, refreshed on every `plugin:provenance-changed`. Main: handlers still register at boot (`registerForgeDataHandlers`), but each calls `resolveForCwd(cwd)` at dispatch, which throws `Forge provider "…" not activated` when the active provider is absent — callers catch and fall back (e.g. commit-only repo stats). #10347 finished the job: `github:*` channels, the preload bridge, `shared/types/github.ts`, and the hardcoded `github.com` regex (`isGitHubRemote` boolean → `matchedForgeProviderId`) were all deleted behind `providerId`-keyed `forge:*` channels and capability probing, so "disabled" and "not installed" collapse to one path: no active provider → resolution throws → surfaces fall back.

## Lesson

- **A disable flag that only writes persisted state removes nothing — gate at the point of USE, not at wiring time, which is also what makes a LIVE (no-restart) toggle possible.** Registration side effects (`registerBuiltinView`, `registerForgeDataHandlers`) run once at boot and cannot be undone by a flag; resolution (`resolveSlot`, `resolveForCwd`) runs per-render / per-dispatch and can. Keep registration unconditional and put the enable check in the resolver.
- **The renderer mirror and the main-process gate have opposite, deliberate failure modes.** `pluginRuntimeStore.disabledPluginIds` is empty until the first `plugin.list()` snapshot lands, so the renderer is fail-OPEN (unknown ⇒ enabled) — safe only because the main process independently gates plugin-backed IPC fail-CLOSED, so a brief optimistic render still can't reach a disabled plugin's data. Don't "harden" the renderer to fail-closed; that inverts the design and flashes empty UI on launch.
- **A disabled plugin must issue zero background network — move probing into `activate()`/`dispose()`, never `globalServicesInit`.** The startup `/user` token validation leaked because it initialized eagerly outside the plugin. Token _storage_ stays eager (a stored token survives a disable/enable cycle); token _probing_ is lifecycle-owned — `GitHubAuth.initializeStorage()` now runs at the top of `activate()`.
- **Never auto-enable a persisted-disabled plugin** — opening a matching repo surfaces a dismissible recommendation (`useForgeEnableRecommendation`); a persisted disable is the user's call. With the plugin off, the settings subtab falls back to General rather than render a panel for a gone provider.
- **Host symbols went forge-neutral in #10347** — `GitHubStatsToolbarButton` → `ForgeStatsToolbarButton`, `useGitHubEnableRecommendation` → `useForgeEnableRecommendation`; `FORGE_PROVIDER_UNAVAILABLE` is now only a comment marker (the live gate is `resolveForCwd` throwing).

## Applies when

- Adding a plugin/feature enable toggle and expecting "disabled" to actually remove the feature live — audit that IPC dispatch, renderer slots, background probing, and settings each re-read the flag.
- Touching `src/registry/builtinRendererRegistry.ts`, `useBuiltinView`/`getBuiltinView`, or `src/store/pluginRuntimeStore.ts` — the renderer slot-gating seam and its optimistic disabled-set mirror.
- Gating a main-process IPC handler on plugin/provider state — put the check at dispatch (`resolveForCwd`/`getImplForNamespace`), not at registration.
- Diagnosing "I disabled the plugin but its UI/data/network is still there" or "the toggle does nothing without a restart"; or adding a new `ForgeProviderImpl` builtin.
