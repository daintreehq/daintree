## Context

User plugins run isolated in `utilityProcess.fork` workers via `PluginDevWorkerHost` / `plugin-dev-worker.ts`, driven by `PluginService.activateViaWorker`. The only audited enforcement boundary for a plugin's declared `scopes.fs.allowedPaths` is `pluginFsContainment.ts`, which realpath-contains calls made through the sanctioned `host.fs`/`host.git` API — it does nothing for a plugin that bypasses the host API and calls raw `require("fs")` or spawns a child process directly. Issue #10890 spiked whether Node's experimental permission model (`--permission`, `--allow-fs-read`, `--allow-fs-write`, `--allow-child-process`, `--allow-addons`) could close that gap by mapping `allowedPaths` onto worker `execArgv` flags, since the fork already passes `execArgv` (`--max-old-space-size=256`) and Electron 42 ships Node 22, which has this permission model.

## Problem

The design looks free: forks already accept `execArgv`, Node already defines these exact flags for this use case, and mapping `allowedPaths`/capabilities onto them is a small, pure, unit-testable function. #10900 built the mapper (`pluginPermissionFlags.ts`), wired it behind an opt-in env var (`DAINTREE_PLUGIN_PERMISSION_MODEL_SPIKE`), and added a worker boot self-check to measure the result. The measurement came back negative: on the repo's own Electron 42.4.0 binary, `process.permission` is `undefined` inside the worker even with `--permission --allow-fs-read=...` passed, and an out-of-scope `fs`/`child_process` call from the worker is not blocked. The flags parse without error and produce no diagnostic — nothing tells a reviewer the enforcement isn't happening.

## Root cause

Electron's `utilityProcess.fork()` bootstraps a Node environment but never runs Node's own `--permission` CLI-flag parsing/install step, so passing `--permission`/`--allow-fs-*`/`--allow-child-process`/`--allow-addons` in `execArgv` is inert — the permission subsystem is simply never activated in that process, regardless of which flags were requested. This is an Electron bootstrap gap, not a Node-version or plugin-specific issue, and it is a classic fail-open trap: `execArgv: ["--permission", "--allow-fs-read=/plugins/acme"]` reads as enforcement to anyone scanning the fork call, and nothing in the code path throws or logs to say otherwise.

A second, independent limitation applies even if a future Electron version starts honoring the flags: `execArgv` is fixed at `fork()` time, but `scopes.fs.allowedPaths` supports a `${worktree}` token that resolves per-call against whichever worktree is currently active. A flag set computed once at fork time reflects only the fork-time worktree and would go silently stale on a worktree switch, since nothing restarts the worker when the active worktree changes; `${project}` (the stable main worktree root) doesn't have this problem, `${worktree}` does.

## Lesson

- **`utilityProcess.fork()` does not honor Node's `--permission`/`--allow-*` execArgv flags** — verified empirically against Electron 42.4.0 via a worker boot self-check (`process.permission` presence). Passing Node CLI flags through `execArgv` does not guarantee Node's own CLI-flag behavior inside an Electron utility process; Electron's bootstrap runs its own subset of Node's startup path.
- **This is an Electron-bootstrap gap, not a plugin-specific one** — every Daintree host forked via `utilityProcess.fork` (`plugin-dev-worker.ts`, `PtyHostLifecycle.ts`, `WorkspaceHostProcess.ts`, `watchdog-host.ts`, `AssistantHostProcess.ts`) is equally unaffected. Don't scope this finding to plugins only when evaluating hardening for the other hosts.
- **The real, audited plugin containment boundary stays `pluginFsContainment.ts`** realpath containment on the sanctioned `host.fs`/`host.git` surface — a plugin calling raw `fs`/`child_process` instead of the host API bypasses it entirely, and no execArgv flag closes that today.
- **Never trust flag presence as proof of enforcement.** If you add Node CLI-flag-based hardening to any `utilityProcess.fork` worker, instrument a runtime self-check first (worker reports over the port whether the guard is actually active; host logs the honored verdict) — a clean `execArgv` array proves nothing by itself.
- **Static `execArgv` can't express per-call dynamic scope** — a token like `${worktree}` that resolves differently per call cannot be safely baked into a flag set fixed at fork time; enforcement built on frozen argv needs either a worker restart on worktree switch or a non-argv mechanism.
- **Gate speculative security hardening behind an explicit env flag with a fail-open path** — `DAINTREE_PLUGIN_PERMISSION_MODEL_SPIKE` defaults off, and `PluginService.activateViaWorker` catches computation errors and forks without flags rather than blocking activation. Exploratory security code should never become a silent default just because it compiles and its unit tests pass.

## Applies when

- Touching plugin worker isolation (`PluginService.activateViaWorker`, `PluginDevWorkerHost.ts`, `plugin-dev-worker.ts`) or any other `utilityProcess.fork` host and considering `execArgv`-based enforcement.
- Evaluating Node's experimental permission model (`--permission`, `--allow-fs-read`, `--allow-fs-write`, `--allow-child-process`, `--allow-addons`) for sandboxing anything inside Electron 42 (Chromium 148 / Node 22).
- Reviewing a PR that adds security-relevant `execArgv` flags to any `fork()` call — demand a runtime-verified honored/not-honored signal, not just that the flag string was constructed correctly.
- Revisiting the plugin sandbox "freeze plan" decision (#10890 references decision D3) or deciding whether `DAINTREE_PLUGIN_PERMISSION_MODEL_SPIKE` should graduate past opt-in.
- Diagnosing why a plugin's declared `scopes.fs.allowedPaths`/capabilities don't stop a raw Node call — check `pluginFsContainment.ts` coverage (host-API-only) before assuming any worker-process-level enforcement exists.
