## Context

Recipe launches and bulk worktree creation spawn N panels at once via `spawnPanelsFromRecipe` (`src/components/Worktree/panelSpawning.ts`) and `recipeStore.runRecipeWithResults`. Each `addPanel` appends an id to `panelStore.panelIds` — the high-fanout subscription that the worktree dashboard, dock, and CSS grid all read. The PTY-host startup queue already serializes the actual `node-pty` forks, so the cost being optimized here is purely renderer-side commits/reflows.

## Problem

A 5-panel recipe burst triggered 5 separate React commits and 5 CSS grid reflows. The original serial `for-await` loop awaited each `addPanel` in turn; the obvious "fix" of switching to `Promise.all` does **not** collapse the renders.

## Root cause

Zustand wires React via `useSyncExternalStore`. Every `set()` synchronously notifies subscribers, and `useSyncExternalStore`'s store-change path forces a **synchronous re-render outside React's event/microtask batching**. React 19 auto-batching only coalesces updates that flow through React's own dispatch (event handlers, `await` continuations of React-scheduled work). An external store flushing per `set()` sidesteps that entirely — so N `addPanel` calls produce N `panelIds` commits no matter whether you await them serially or fire them concurrently with `Promise.all`. Promise-level concurrency changes ordering, not the number of store flushes.

The real fix is store-level batching that defers the high-fanout field. The batch (`beginSpawnBatch`/`flushSpawnBatch`, reusing the hydration batch machinery in `hydrationBatch.ts`) lets each `addPanel` commit its `panelsById[id]` entry immediately — so IPC listeners can still resolve panels by id — but **defers the `panelIds` append**, collecting ids in `pendingIds`. `flushSpawnBatch` does a single `set()` that reveals all ids at once: one commit, one reflow. Three things make it safe:

- **Begin-if-free:** `beginSpawnBatch()` returns `null` rather than superseding an active batch, so overlapping recipe runs don't orphan each other's panels; the active batch's dedup-on-flush sweeps them.
- **Limit gating:** per-call `panelLimitStore` checks would all read the same stale count while `panelIds` is deferred, so the loop calls `preflightSpawnBatchLimit` once up front and passes `bypassLimits: true` on every `addPanel`.
- **Focus suppression:** the per-panel focus mutation (which would focus the last grid panel) is suppressed during the batch and replayed once after flush.

## Lesson

- To collapse N store-driven renders into one, **batch at the Zustand store level**, not with `Promise.all`. Concurrency at the promise layer does nothing for render count because `useSyncExternalStore` flushes synchronously per `set()` and bypasses React 19 auto-batching.
- The pattern: commit per-item state needed by listeners immediately, but defer the single high-fanout array/field that drives layout, then apply it in one `set()` at flush. `panelIds` is that field for panels; `panelsById` is not.
- Reuse the existing batch primitive (`hydrationBatch.ts`) rather than inventing a parallel one — but distinguish `kind: "hydration"` vs `"spawn"`, because their staleness contracts differ: a stale hydration is discarded (panels from a project being left), a stale spawn is inherited (real user-initiated panels must not be orphaned in `panelsById`).
- When you defer a field that other code reads to enforce limits, the per-call checks go stale — gate the whole burst once and bypass per-call limits.
- Make burst-batches begin-if-free (decline to nest), and put the flush in a `finally` so a throw mid-burst can't leave `isHydrationBatchActive()` stuck true and starve the next batch.

## Applies when

- Spawning, importing, or bulk-creating multiple panels/worktrees/items that each push to a high-fanout Zustand field in a loop.
- You reach for `Promise.all` expecting fewer renders and don't see them collapse.
- Any new Zustand-backed bulk mutation where you want one commit/reflow instead of N — defer the subscribed collection field and flush once.
