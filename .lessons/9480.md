## Context

Help-session crash-safe PTY reaping relies on two vendored native modules: `win-job-object` (Windows, N-API `.node` addon attaching the PTY tree to a Job Object, #7526) and `posix-pty-reaper` (macOS/Linux, a compiled C executable `daintree_pty_supervisor`, #8769). Both are validated at packaging time in `scripts/afterPack.cjs` alongside `better-sqlite3` and `node-pty`. Neither is required for app start, so a broken binary degrades silently rather than crashing.

## Problem

Two ways a binary could compile, pack, sign, and ship while the reaper was dead:

1. An **existence / executable-bit check passed on a present-but-broken binary** — `fs.existsSync` or `fs.accessSync(X_OK)` succeed even when a transitive dependency (e.g. `VCRUNTIME140.dll` on Windows) doesn't resolve or the binary is the wrong arch. The supervisor would then fail only at first runtime use.
2. `posix-pty-reaper` was **bundled instead of externalized** by esbuild. Its `getSupervisorPath()` (`node_modules/posix-pty-reaper/index.cjs:19`) is `path.join(__dirname, "build", "Release", "daintree_pty_supervisor")`. Bundling rewrites `__dirname` to the main-bundle output dir, so the path resolved to a nonexistent location and `isAvailable()` silently returned false — crash-safe reaping disabled with no error.

## Root cause

- **#8769 added `posix-pty-reaper`** (the module, the `rebuild` script entry, the dependency in `package.json`) but **did not add it to the esbuild `external` list in `scripts/build-main.mjs`** (and `scripts/build-import-budget.mjs`). `win-job-object` had been externalized in 81850e293; this one was missed. A `__dirname`-relative native module MUST be external or its path breaks at runtime.
- **N-API dlopen polarity is the OPPOSITE of NAN/V8-raw.** `better-sqlite3` uses the raw V8/NAN API, so its binary is ABI-specific: a successful `process.dlopen` under Node (which runs afterPack) proves it was _wrongly_ built for the Node ABI, not Electron. `win-job-object` is an N-API addon — N-API is ABI-stable (the binary embeds `NODE_MODULE_VERSION -1`, which Node skips), so a correct addon loads under _both_ Node and Electron. A successful dlopen there proves every transitive dependency resolved; a failure means a missing DLL or wrong arch. Reusing the `better-sqlite3` "dlopen-must-fail" assertion for an N-API module would be exactly backwards.
- The C supervisor has no `--version` flag and `main()` blocks reading stdin until EOF. `validatePosixReaperExec` execs it with `spawnSync(binary, [], { input: "", ... })`: empty stdin → immediate EOF → no-op reap over zero registered pids → exit 0 in well under a millisecond. A spawn error or non-zero exit catches a missing shared library / bad interpreter / wrong arch that the executable-bit check misses.

## Lesson

- For every vendored native module, **prove loadability, not presence**: dlopen `.node` addons and actually exec standalone binaries. `existsSync` and `accessSync(X_OK)` do not catch unresolved transitive deps or arch mismatch.
- **Classify the addon's ABI model before writing the probe.** NAN/V8-raw (`better-sqlite3`): a successful Node-side dlopen means the binary is WRONG (expect a `NODE_MODULE_VERSION` / `invalid ELF header` / `not a valid Win32 application` throw to mean it's right). N-API (`win-job-object`): a successful Node-side dlopen means the binary is RIGHT. The polarity is inverted — do not copy one probe onto the other module type.
- To exec a binary that blocks on stdin and has no version flag, hand it empty stdin (`input: ""`) so it hits immediate EOF and exits cleanly; assert `result.error == null && result.status === 0`.
- **Any `__dirname`-relative native module must be in the esbuild `external` list** in `scripts/build-main.mjs` AND `scripts/build-import-budget.mjs`. Bundling silently relocates `__dirname` and breaks runtime path resolution; the failure is invisible because `isAvailable()`-style guards swallow it. When adding a native module, externalizing it is part of the same change as adding the dependency — not a follow-up.
- afterPack probes run on the matching target OS; the Windows dlopen probe only validates loadability when target arch === host arch (cross-arch packs fall back to the existence check), so don't assume the dlopen ran on every build.

## Applies when

- Adding, upgrading, or validating any vendored/native module in `scripts/afterPack.cjs` (`win-job-object`, `posix-pty-reaper`, `better-sqlite3`, `node-pty`, or new ones).
- Adding a native dependency that resolves a path via `__dirname` (compiled binaries, sidecar executables) — check it is in the esbuild `external` lists.
- Writing an ABI/loadability probe and deciding whether a successful `process.dlopen` under Node means pass or fail — distinguish N-API (ABI-stable) from NAN/V8-raw modules.
- Debugging "help-session crash-safe reaping disabled" / supervisor-not-found / `isAvailable()` returns false in a packaged build but works in dev.
- Windows `ERR_DLOPEN_FAILED` or "specified module could not be found" / "%1 is not a valid Win32 application" at native-module load — suspect a missing transitive DLL (VCRUNTIME140) or arch mismatch, not just a bad source build.
- Editing the esbuild `external` array or import-budget baseline when introducing a CJS native module that must keep named exports at runtime.
