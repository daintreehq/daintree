## Context

The toolbar issue/PR count badge (GitHub builtin forge plugin, `plugins/builtin/github/main/`) is fed by two sources: a background stats poll and the dropdown's list-derived `totalCount`. The poll is gated by the cheap `/events` activity probe — on "unchanged", `getRepoStatsAndPageForContext` (`GitHubStats.ts`) skips the real count fetch and re-serves cached counts from `repoStatsAndPageSnapshotCache` (10 min TTL) or `restCountsCache` (1 h TTL), each re-stamped `lastUpdated: Date.now()`. The renderer badge picks the fresher source by timestamp via `resolveForgeDisplayCount` (`src/components/Layout/forgeStatsCountDisplay.ts` — the PR body's `resolveGitHubDisplayCount`; GitHub was later generalized behind the forge abstraction, the main caches stayed put).

## Problem

The badge oscillated: opening the dropdown showed the real count (2), then seconds later it rolled back to a stale 1, repeating on every background poll. The dropdown was clearly right, yet a passive probe that fetched nothing kept overwriting it.

## Root cause

A single `lastUpdated` field conflated two facts: "we believe this count is still current" and "we actually asked GitHub for it". The probe re-serve re-stamped `lastUpdated = Date.now()` with no network read, so a stale cached count always looked fresher than the dropdown's newer observation, and `resolveForgeDisplayCount` (arbitrating purely on recency) picked the stale one every poll. The correction had no staying power: the dropdown's real `totalCount` was written only to `repoStatsCache` (60s TTL), dying within a minute while the 10-min snapshot and 1-h REST caches resurrected the old value. The same permanently-fresh `lastUpdated` defeated the cure too — the dropdown-open force-refresh gate keyed off it, saw "just updated", and skipped the fetch that would have healed the caches. Self-reinforcing: the stale value won the display AND suppressed its own correction.

The fix adds honest per-count stamps `issueCountRefreshedAt` / `prCountRefreshedAt` (`RepoStats` in `types.ts`, threaded through `ForgeRepoCounts` in `shared/types/forge.ts`) that advance ONLY on a real count read (GraphQL `totalCount`, the REST pair, a list write-back, or a 304 — a 304 is GitHub confirming the content, so it re-verifies). A probe re-serve keeps `lastUpdated` re-stamped but preserves the refreshed-at stamps; arbitration and the open-refresh gate read the honest stamps, treating absence/`stale:true` as null-recency. `updateRepoStatsCount` (`GitHubPRs.ts`) also reconciles: a list total disagreeing with a stored snapshot/REST baseline drops that entry (its page items are stale by the same evidence) and bumps `bumpETagCacheVersion()` so an in-flight `fetchRestCounts` can't 304-recommit the pre-drop value.

## Lesson

- **Never re-stamp a "last read from source of truth" timestamp on a cheap unchanged-check that fetched nothing.** Split the concepts: `lastUpdated` = "believed current" (fine to re-stamp on an unchanged probe) vs per-count `*RefreshedAt` = "actually asked the endpoint" (advances only on a real read/304). Collapsing them lets a re-served entry impersonate a fresh read, so recency arbitration prefers stale-but-re-stamped over genuinely-fresher.
- **A staleness gate must key off the honest stamp, not the re-stamped one** — else the very fetch that would heal a busted cache is suppressed because the entry looks freshly updated. The dropdown-open force-refresh in `ForgeStatsToolbarButton.tsx` (`OPEN_REFRESH_STALENESS_MS`) reads `*RefreshedAt` and treats `null` as "unknown → refresh", never "fresh".
- **When a correction is written only to the shortest-TTL cache while longer-TTL caches hold the stale value, the longer caches win by resurrection.** Reconcile on write: in `updateRepoStatsCount`, a fresh observation disagreeing with a stored snapshot/REST baseline drops that entry (forcing a re-read) instead of letting it out-live the correction.
- **Dropping a REST baseline must also invalidate any conditional fetch already in flight.** The drop bumps `etagCacheVersion` (`bumpETagCacheVersion()`); a `fetchRestCounts` that read its ETag before the drop compares versions at commit and discards its own 304. Kept deliberately separate from the list-cache `repoListCacheEpochs`.
- **Recency stamps a write-back touches must be per-kind** — a PR write-back stamping a field shared with issues makes the untouched issue count read as freshly verified. Stamp only the kind observed.

## Applies when

- The toolbar count badge oscillates, rolls back to a stale value after the dropdown showed the right one, or a manual refresh "doesn't stick" — trace whether a passive `/events`-gated re-serve is re-stamping recency without fetching.
- Touching `getRepoStatsAndPageForContext`, `updateRepoStatsCount`, `fetchRestCounts`, or `resolveForgeDisplayCount`, or adding any consumer of `RepoStats`/`ForgeRepoCounts` recency (`*CountRefreshedAt` vs `lastUpdated`).
- Designing any multi-TTL cache where a cheap "unchanged" check re-serves data — decide explicitly whether it may advance a freshness timestamp; split "believed current" from "actually re-fetched" before wiring arbitration or a staleness gate to it. Same for any "most recent of N sources" arbitration: a source that can re-stamp without a real observation always beats slower honest sources.
- Companion PR #10344 makes the count poll a cache-buster (`invalidateRepoListCachesForCountChange` + a per-repo/type `getRepoListEpoch` guard so an in-flight list query can't write a pre-change page back over the busted cache) — read both together for forge count/list freshness.
