## Context

Renderer terminal scrollback depth is sized by `getScrollbackForType(isAgent, base)` in `src/utils/scrollbackConfig.ts`, which multiplies the user's base setting by a per-kind policy (`AGENT_POLICY` for agents, `PLAIN_POLICY` for shells). Two earlier tightenings — `ada4bb8e3` (agent multiplier 2.5→1.5) plus `0627b0a2c` (base default 2500→1000) — had collapsed agent terminals from ~5000 visible lines to ~1500. Since reviewing agent work is a core use of the app, #10352 asked to restore usable depth, floating two options: (1) lazy-load older lines from the main-process buffer into the live xterm on scroll-to-top, or (2) raise the cap.

## Problem

Option 1 is the tempting one: the main-process PTY buffer already retains more history than the renderer shows (`DEFAULT_SCROLLBACK` in `electron/services/pty/types.ts`), so "the data is already there — page it in on demand" looks like the memory-free win. An agent handed "make agent scrollback deeper without the memory cost" will reach for this design and go hunting for an xterm API to inject older lines at the top of the buffer.

## Root cause

There is no such API. xterm's public surface (verified against pinned `@xterm/xterm@6.1.0-beta.290` — grep `node_modules/@xterm/xterm/typings/xterm.d.ts` for `prepend|inject|writeAt|insertLines|unshift` → zero hits) only offers `write()` (appends at cursor/end), `clear()`, and `reset()` (both wipe), with a **read-only** `buffer` namespace. You cannot prepend lines to the top of an existing scrollback. The only way to surface older history in a live instance is `terminal.reset()` then re-write the entire buffer from the start — functionally identical to just holding a larger scrollback, but with a full re-parse/re-render flash on every scroll-to-top. Lazy-loading is therefore a dead end on xterm 6.x. PR #10356 documented this and took option 2: raise `AGENT_POLICY.multiplier` 1.5→5 (restoring the 5000-line default); follow-up #11223 (`434a9c05a`) pushed it to the current `{ multiplier: 10, maxLines: 10000, minLines: 500 }`.

A subtlety that surfaced later: at PR-time the justification was "the main buffer holds 10k, the renderer only 5k, so widening the renderer is free." That relationship has since **inverted** — the live renderer now holds 10000 lines while `DEFAULT_SCROLLBACK` was reduced to 5000. The pty-host mirror feeds _analysis_ (`terminal.getOutput` caps at 1000) and serialize/restore, NOT the visible viewport, so a session restored after project-view eviction recovers only ~5000 lines even though a live pane holds 10000. Renderer window and mirror buffer are separate numbers with separate purposes — don't assume one bounds the other.

## Lesson

- **Lazy-loading older scrollback into a live xterm instance is impossible on xterm 6.x** — no prepend/inject API; `write()` only appends, and `reset()`+full re-replay equals a bigger buffer with a re-render flash. If asked to "page in history on scroll-to-top" or "deepen scrollback without memory cost," don't investigate the xterm API — widen the window (`AGENT_POLICY.multiplier`/`maxLines`) instead, bounded by memory.
- **Scrollback depth is a single lever: `getScrollbackForType` in `src/utils/scrollbackConfig.ts`.** Every renderer sizing path routes through it (`XtermAdapter`, `TerminalRegistryController`, `TerminalScrollbackController`, `addPanel`, `TerminalSettingsTab`). Change the policy there, not per-callsite.
- **The renderer window and the pty-host mirror are different buffers with different sizes.** `AGENT_POLICY.maxLines` (renderer, currently 10000) is what the user scrolls; `DEFAULT_SCROLLBACK` (mirror, currently 5000) feeds analysis + restore. Raising `DEFAULT_SCROLLBACK` to match the renderer needs a pty-host memory review (comment in `types.ts` says so) — they are deliberately unequal, so a restored-after-eviction session recovers less than a live one.
- **Widening focused scrollback is affordable because unfocused terminals are trimmed independently.** At ~1200 bytes/line (`BYTES_PER_LINE`), 8 focused agents at 5000 lines is ~48MB worst case, but the background-tier reduction (`ptyClient.trimState(SCROLLBACK_BACKGROUND)`, =500, in `perWindowInit.ts`/`globalServicesInit.ts`) holds unfocused terminals to 500 lines, so steady-state is ~9MB. The ceiling is also resource-profile-aware — `useResourceProfile` pushes `setAgentScrollbackMaxLines` (efficiency lowers it to ~4k).
- **Pin scrollback tests to computed invariants, not the literal policy value.** #10356 added agent≥plain-at-all-bases, proportional-below-cap, and clamped-above-cap checks — so a multiplier regression fails loudly without re-asserting the multiplier itself, which legitimately changed 5→10 afterward while the invariants held.

## Applies when

- Asked to "lazy-load scrollback," "page in older history on scroll-to-top," or "give agents deeper scrollback without the memory cost" — the xterm-prepend approach is a verified dead end; reach for the multiplier/maxLines lever.
- Touching `src/utils/scrollbackConfig.ts` (`AGENT_POLICY`, `PLAIN_POLICY`, `getScrollbackForType`, `setAgentScrollbackMaxLines`) or reasoning about how deep a terminal scrolls back.
- Assuming the renderer scrollback window and the main-process/pty-host mirror (`DEFAULT_SCROLLBACK`) are the same size — they are not, and restored-after-eviction sessions recover only the mirror's depth.
- Estimating terminal memory: use `BYTES_PER_LINE` (~1200) but remember unfocused terminals are trimmed to `SCROLLBACK_BACKGROUND` (500), so focused-ceiling math overstates steady-state.
- Bumping `@xterm/*` — re-check whether a scrollback prepend/inject/buffer-write API has appeared before re-opening the lazy-load design.
