## Context

`deriveRequiredCIStatus` (`plugins/builtin/github/main/prRequiredCIStatus.ts`) condenses a PR's `statusCheckRollup` contexts into a single CI indicator for the GitHub PR dropdown. To avoid letting flaky non-required checks turn the indicator red, #5566 added a filter that only counts contexts where `isRequired === true`, then derives FAILURE / PENDING / SUCCESS from those required checks alone. The renderer (`prCIStatus.ts`) maps the derived `ciStatus` + `ciSummary` to a green check, amber dot, or red X with tooltip copy.

## Problem

Every repo _without_ branch-protection rules — the common case for personal repos, forks, and most projects — has zero contexts flagged `isRequired`. Those PRs always showed a green check with the tooltip "No required checks", even when CI was actively failing or still in flight. Real red/amber CI was silently rendered green.

## Root cause

The `requiredTotal === 0` branch hardcoded a success result:

```ts
return {
  ciStatus: "SUCCESS",
  ciSummary: { requiredTotal: 0, requiredFailing: 0, requiredPending: 0 },
};
```

"No required checks were found" was conflated with "all required checks passed." Two compounding effects: (1) `ciStatus: "SUCCESS"` drove the green-check visual unconditionally; (2) the zeroed `ciSummary` forced the renderer's tooltip down the `summary.requiredTotal === 0 ? "No required checks"` path (`prCIStatus.ts:47`), so even the tooltip never revealed the true state. The actual rollup state (`rawCiStatus`, already computed via `normalizeRawState`) was discarded. The original intent — "non-required failures shouldn't turn the indicator red" — was a real concern for repos _with_ required checks, but the zero-required branch overcorrected it into a blanket false-green for repos with no required-vs-non-required distinction at all.

The fix returns `{ ciStatus: rawCiStatus, ciSummary: undefined }`. A `undefined` summary makes the renderer fall through to the raw-state tooltip copy ("All checks passed" / "Checks pending" / "Checks failing"), so the indicator now reflects actual rollup health.

## Lesson

- A sentinel/empty count (`requiredTotal === 0`) almost never means "everything is fine" — it usually means "this dimension doesn't apply here." Don't collapse "no data in the filtered view" into the success terminal state. Fall back to the broader unfiltered signal you already have (here, the raw rollup) instead of inventing a green default.
- When a derived status drives a UI color, the _most common_ input (repos with no branch protection) is the one most likely to hit a hardcoded default — verify the default against that case, not just the configured/protected case the feature was built for.
- A "filter out the noise" fix (ignore non-required checks) has two regimes: (a) required checks exist → filter is correct; (b) zero required checks → the filter ate everything and the fallback must be the unfiltered state, not a constant. Test both regimes.
- `ciSummary: undefined` is load-bearing here, not just "no extra info": the renderer uses summary presence to decide tooltip phrasing. Returning a zeroed summary actively routes copy down the wrong branch. When a field's _presence_ gates downstream rendering, prefer `undefined` over a zeroed object.

## Applies when

- Touching `deriveRequiredCIStatus` / `deriveGlobalCIStatus` in `plugins/builtin/github/main/prRequiredCIStatus.ts`, or the PR CI indicator/tooltip in `plugins/builtin/github/renderer/utils/prCIStatus.ts`.
- Any code that filters GitHub `statusCheckRollup` contexts by `isRequired`, branch-protection state, or required-check configuration and then derives a single status.
- Reviewing any "ignore noisy/non-required signals" change to a health/status indicator — check what happens when the filter removes _all_ inputs (empty filtered set).
- Adding a `requiredTotal === 0`, `count === 0`, or empty-list short-circuit that returns a success/green/passing terminal state.
- Debugging reports of "CI shows green but checks are failing" on repos without branch protection, forks, or personal repos in the PR dropdown.
- Deciding between returning a zeroed summary object vs `undefined` when a field's presence controls downstream tooltip/label branching.
