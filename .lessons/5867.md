## Context

`startLongTaskMonitor()` (`src/utils/longTaskMonitor.ts`, wired always-on via `usePerformanceMonitors.ts`) is the renderer's only runtime-jank probe — it warns on slow frames and, under `DAINTREE_PERF_CAPTURE`, emits a perf mark. It originally observed the `longtask` PerformanceEntry type.

## Problem

The `longtask` entry type produces near-useless diagnostics: every entry's `name` is `"self"` (or a coarse container name) with `duration`/`startTime` and nothing else — no script URL, no function name, no blocking breakdown. A warning told you a frame was slow but never _which_ code blocked it, so the signal couldn't drive any fix.

## Root cause

`longtask` predates script attribution. The successor `long-animation-frame` (LoAF, Chromium 123+ / Electron 41 ships Chromium 146) attaches `PerformanceScriptTiming[]` with `sourceURL`, `sourceFunctionName`, `sourceCharPosition`, `invoker`, `invokerType`, plus frame-level `blockingDuration`, `renderStart`, `styleAndLayoutStart`, `paintTime` — the data needed to pin the culprit. Two non-obvious traps when switching:

1. **Incompatible observe shape.** `long-animation-frame` requires `observer.observe({ type, durationThreshold })` — the single-`type` form. It does NOT work with `entryTypes: [...]` (that array form silently ignores unknown/threshold-only types), and `durationThreshold` filters in the browser so the manual `if (entry.duration < thresholdMs) continue` gate is gone.
2. **lib.dom drift.** TypeScript's bundled `lib.dom.d.ts` doesn't yet declare `PerformanceLongAnimationFrameTiming`, `PerformanceScriptTiming`, or `durationThreshold` on `PerformanceObserverInit`. You must `declare global` local stubs or the code won't typecheck.

## Lesson

For renderer jank attribution prefer `long-animation-frame` with `observe({ type: "long-animation-frame", durationThreshold })` and read `entry.scripts`; sort scripts by `duration` descending and surface the top offender (`summarizeScripts()` keeps the top 3) — the highest-duration script is the actionable one, not `scripts[0]` (array order is invocation order, not blame order). `longtask` gives you a yes/no jank bit with no attribution; only reach for it on engines without LoAF. When using a Chromium-ahead-of-lib.dom API, ship local `declare global` interface stubs rather than waiting for the TS lib to catch up.

## Applies when

- Adding or revising any renderer PerformanceObserver probe (jank, INP, layout) and you want to know _which script_ blocked the frame
- Seeing perf warnings that say a frame was slow but give no `sourceURL`/`sourceFunctionName`
- A PerformanceObserver silently never fires after adding a new entry type (check `entryTypes` array vs single-`type`+`durationThreshold` shape)
- Typecheck fails on `PerformanceLongAnimationFrameTiming` / `PerformanceScriptTiming` / `durationThreshold`
