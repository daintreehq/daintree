## Context

`routeHostEvent` in `electron/services/pty/PtyEventRouter.ts` is the single switch that translates host-to-main events (emitted by the pty-host utility process via `sendEvent`) into `EventEmitter` events the main process re-broadcasts to renderers. Event payloads are typed by the `PtyHostEvent` discriminated union in `shared/types/pty-host.ts`. The pty-host's `ResourceGovernor` (`electron/pty-host/ResourceGovernor.ts:288`) emits an `fd-leak-warning` event when open file descriptors outpace active terminals.

## Problem

The `fd-leak-warning` event type was already a member of the `PtyHostEvent` union and the producer emitted it correctly, but `routeHostEvent` had no `case "fd-leak-warning"`. Every warning fell through to the router's `default` branch, which logged `[PtyClient] Unknown event type: fd-leak-warning` (every ~2s under the governor's check cadence) and returned `false` — silently dropping a real safety signal. On macOS the ptmx pool caps at 511; an unchecked fd leak eventually blocks all new terminal spawns, and the only trace was noise that read like benign logging.

## Root cause

The switch is terminated by a `default` branch that casts `const unknownType = (event as { type: string }).type`. That cast widens `event` away from the discriminated union, so TypeScript never narrows the `default` to `never` and never flags an unhandled variant. There is no `assertNever(event)` in the default. Result: adding a new member to the `PtyHostEvent` union produces **zero compile errors** even when no consumer handles it — the new event is correctly typed, correctly emitted, and silently swallowed at runtime. The type system gives a false sense of coverage because the union member exists; only the router _case_ is missing, and nothing enforces case-to-variant parity.

## Lesson

- A new host→renderer PTY event requires wiring **four** layers, none of which the compiler will force on you: (1) a `case` in `routeHostEvent` (`PtyEventRouter.ts`) that `emit`s on the EventEmitter; (2) an IPC channel constant in `electron/ipc/channels.ts` plus a forwarder in `electron/ipc/handlers/terminal/events.ts` that calls `broadcastToRenderer`; (3) preload exposure in `electron/preload.cts` and the matching method on `ElectronAPI` in `shared/types/ipc/api.ts` + the `IpcEventMap` entry in `shared/types/ipc/maps.ts`; (4) a renderer-side listener (e.g. a store listener under `src/store/listeners/`) registered in `panelStoreListeners.ts`.
- A `default`/fallthrough branch that casts `event as { type: string }` defeats discriminated-union exhaustiveness. When a switch over a union must remain total, end it with `default: { const _: never = event; ... }` (or an `assertNever(event)` helper) so a newly added union member fails the build until handled. Use a tolerant `default` only when the union is genuinely open (e.g. forward-compatible host events) — and treat that tolerance as a deliberate, documented choice, not the norm.
- "Unknown event type" warnings on a hot path are not noise to be filtered — they signal a dropped, fully-typed event whose handler is missing downstream.

## Applies when

- Adding any new variant to `PtyHostEvent` (`shared/types/pty-host.ts`) or any new host→main→renderer signal that flows through `routeHostEvent` / `PtyEventRouter.ts`.
- Debugging why a pty-host event (resource metrics, fd-leak, backpressure, reliability, governor state) is emitted by the host but never reaches the renderer or diagnostics dock.
- Seeing repeated `[PtyClient] Unknown event type: <x>` in main-process logs.
- Reviewing or extending switch statements over discriminated unions in `electron/` that terminate in a casting `default` branch — verify whether exhaustiveness is intended and whether `assertNever` should guard it.
- Wiring any cross-process event across the channels.ts → events.ts → preload.cts → api.ts/maps.ts → store-listener chain, where missing one layer fails silently rather than at compile time.
