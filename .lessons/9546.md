## Context

Terminal panes pool and dispose xterm.js instances aggressively for the tier/hibernation system (`TerminalWebGLManager`, `terminalInstanceService`, and the background-tier dispose path from #4213). When a pane is torn down or hibernated, app code calls `Terminal.dispose()` / `WebglRenderer.dispose()` expecting the instance and its WebGL context to be fully reclaimable.

## Problem

Renderer heap grew across close/hibernate cycles even though every app-side `dispose()` call was present and ordered correctly. The leak only materialized when the WebGL addon was actually attached (issue #9540) — detached/DOM-renderer panes looked clean, so it was easy to misattribute to our own pooling code.

## Root cause

The leaked objects lived _inside_ xterm 6.0's own internals, not in our code. `WebglRenderer._cursorBlinkStateManager`, `RenderService._pausedResizeTask`, and the `RenderService` `IntersectionObserver` were never registered with xterm's internal disposable registry, so `dispose()` never tore them down — they stayed as GC roots holding the renderer (and its WebGL context) alive. No amount of correct app-side disposal can reclaim an object the library forgot to register as a disposable. The fix was purely an upstream patch (xterm.js #5818), shipped only in the 6.1 line — so the resolution was a dependency bump (pinned to `6.1.0-beta.221` / addons `*-beta.220`), not a code change in our terminal lifecycle. The same 6.1 bump silently reshaped the typed options surface: `customGlyphs` was removed (now always-on) and the overview-ruler width moved from `overviewRuler: { width }` to `scrollbar: { width }` (the scrollbar is VS Code's viewport implementation as of v6). These are the _search-match markers_ in the scrollbar track — drop the option and the markers silently disappear, with no type error loud enough to catch at build time.

## Lesson

- When a memory leak survives a correct, complete app-side `dispose()` sequence, suspect the library's own undisposed internals before re-auditing your teardown order — especially for xterm renderers/observers/blink managers. Confirm by heap-snapshotting retainers: if the GC root is an xterm-internal field (`_cursorBlinkStateManager`, `_pausedResizeTask`, an `IntersectionObserver`), the fix is an upstream bump, not local code.
- A leak that only appears with WebGL attached needs a test that actually attaches WebGL — default CI runs with `--disable-gpu` + `DAINTREE_DISABLE_WEBGL=1`, so the leak is inert there. PR added a GPU-gated nightly suite (`e2e/nightly/nightly-memory-leaks.spec.ts`, opt-in via `DAINTREE_E2E_ENABLE_WEBGL=1`) precisely because the regular suite can never reproduce it.
- Treat every xterm minor/major bump as a breaking change to the _options object_, not just the API. The option types are loose enough that removed/renamed fields (`customGlyphs`, `overviewRuler.width` → `scrollbar.width`) don't reliably fail the build — they just silently stop doing anything. After a bump, re-verify each option in `src/config/xtermConfig.ts` against the new release notes; `scrollbar.width` is what now enables the scrollbar-track search-match markers.
- Note `overviewRulerBorder` in `src/utils/terminalTheme.ts` is a _theme_ property and stayed put — the migration was partial, which is exactly why a blind find-replace would have been wrong.
- Core must lead the addons by one build: `addon-webgl@0.20.0-beta.220` peers on `^6.1.0-beta.221`, so the nine `@xterm/*` packages can't be bumped uniformly. This is a beta pin (#9547 tracks the swap to 6.1.0 stable); the maintainer requirement is to drop beta suffixes the moment stable ships.

## Applies when

- Investigating renderer-heap growth or WebGL-context leaks across terminal close, project switch, or hibernation/tier-down cycles, and app-side `dispose()` looks correct.
- Bumping any `@xterm/*` package (core, headless, or any addon) — checking option migrations, peer-dependency lockstep, or whether scrollbar/overview-ruler/search-match-marker behavior changed.
- Search match markers (the colored ticks in the terminal scrollbar track) stop appearing after an xterm upgrade.
- Touching `src/config/xtermConfig.ts`, `TerminalWebGLManager`, `terminalInstanceService`, or the WebGL pooling/eviction code (#3243, #3358, #4970, #4213) and seeing memory not return to baseline.
- Writing or triaging a memory-leak regression where the symptom only reproduces with a real GPU / WebGL attached and the default `--disable-gpu` CI path shows nothing.
