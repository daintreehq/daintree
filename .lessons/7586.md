## Context

The error subsystem persists a `pendingErrors` array into the electron-store JSON config (`electron/store.ts`) so errors survive a crash and surface on next launch. Two independent paths write it: the renderer-driven retry path (`ErrorService.persistError` in `electron/ipc/errorHandlers.ts`) and the main-process fatal path (`persistPendingError` in `electron/setup/globalErrorHandlers.ts`, handling `uncaughtException` / `unhandledRejection`). A third producer (`openFileInstall.ts`) was added later.

## Problem

The renderer path enforced a 50-entry cap (`[...existing, error].slice(-MAX_PENDING_ERRORS)`); the main-process path appended with no cap (`[...pending, appError]`). Fatal errors — exactly the ones most likely to recur in a crash loop — could grow the array unbounded. Each unbounded append also made every subsequent `store.set` progressively more expensive and more dangerous to interrupt.

## Root cause

electron-store v11 wraps `conf`, whose `_write` (`node_modules/conf/dist/source/index.js:396`) calls `_serialize(value)` on the **entire** config object on every `set()` — not just the changed key. So `store.set("pendingErrors", bigArray)` re-stringifies the whole store (terminal config, worktree config, every audit array, etc.) synchronously on the main thread, an O(total-config-size) block that grows with the unbounded array. Worse, the write is only atomic on the default path (`atomicWriteFileSync` = temp file + rename). Two real fallback paths drop to non-atomic `fs.writeFileSync` directly onto the live config file: `process.env.SNAP` (Linux Snap, line 412) and the Windows `EXDEV` rename-failure catch (line 423). A larger payload widens the partial-write window on those paths, so a crash mid-write can corrupt the config. The cost is invisible at the call site — `store.set` looks like a cheap key assignment.

## Lesson

- Any array persisted into electron-store MUST be capped, and the cap MUST be enforced at a single shared writer — not duplicated inline at each call site, where one path inevitably diverges. PR #7586 extracted `appendPendingError` / `MAX_PENDING_ERRORS` (`electron/ipc/pendingErrorsStore.ts`) so all producers delegate to one capped writer.
- Trim **before** append (`existing.slice(-(MAX-1))` then `push`), not after, so a store already bloated by a pre-fix path doesn't allocate a giant intermediate array on the first corrected write.
- Treat `store.set` as a whole-config re-serialize + fsync, not a cheap field update. Don't write growing collections to it on hot or crash paths. The store already has several capped siblings (`MCP_AUDIT_DEFAULT_MAX_RECORDS`, `PLUGIN_AUDIT_DEFAULT_MAX_RECORDS`, `FORGE_AUDIT_DEFAULT_MAX_RECORDS`) — match that pattern for any new log/history/audit array.
- When the same persisted key has more than one writer, that is the bug shape: divergent caps, divergent transforms (note `globalErrorHandlers` also tags `fromPreviousSession: true`). Centralize.

## Applies when

- Adding or modifying any array stored in `electron/store.ts` via electron-store — error queues, audit logs, history lists, frecency, recent-items.
- Writing to `pendingErrors` or touching `appendPendingError` / `MAX_PENDING_ERRORS` / `ErrorService.persistError` / `persistPendingError`.
- Reviewing code that calls `store.set` on a path that can fire repeatedly (crash loops, per-event handlers, polling) — check whether the payload is bounded.
- Investigating slow/janky main-thread blocks during config writes, or corrupted/truncated electron-store JSON config on Windows or Linux Snap installs.
- Any time the same persisted store key is written from more than one code path — verify caps and transforms match by routing through a single writer.
