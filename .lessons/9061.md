## Context

The CodeForge migration re-routed all GitHub data access through a clean provider abstraction: `forgeProvider.runQuery` (main process) is now the sole GraphQL entry point, and `ForgeBridge` (workspace-host UtilityProcess, which has no plugin loader) dispatches every provider call to main over a `forge:rpc` MessagePort. The legacy concrete GitHub service layer that this replaced had per-entity 60s `Cache<>` instances and in-flight coalescing baked in.

## Problem

Every forge call became a full GraphQL round-trip. The new provider interface looked functionally complete — same return shapes, same call sites — but the cache and singleflight that lived in the old concrete layer were never carried over. A poller + a watcher + a user action hitting the same repo each fired an independent network request, burning the GitHub rate limit and multiplying IPC round-trips across the process boundary.

## Root cause

Migrations that re-route through a new abstraction lose **cross-cutting, non-functional concerns** (cache, singleflight, retry, throttle) that were implemented in the old concrete classes, not in the interface. The abstraction's contract only captures functional behavior, so a "complete" port silently regresses the NFRs. Here, the cache/dedup had been an implementation detail of the legacy service methods, so re-implementing those methods on top of `runQuery` reproduced the API while dropping the throttling.

## Lesson

- When migrating behind a new provider/abstraction layer, **explicitly enumerate the non-functional behaviors of the old layer** (caching, in-flight dedup, retry, backoff, throttle) and re-home each one. A green test suite proves functional parity, not NFR parity.
- Dedup may need **two layers across a process boundary**, and they are complementary, not redundant:
  - **IPC-boundary singleflight** (`ForgeBridge.invoke`, keyed `method\0namespacedId\0stringify(args)`, **evicted on settlement**) collapses synchronous concurrent identical RPCs so they cross the boundary once.
  - **Provider-level TTL cache + in-flight map** (`runQuery`, keyed `query\0safe-stable-stringify(variables)`) absorbs _staggered_ bursts that arrive in main after the IPC-side dedup already settled — the 60s response cache catches the second caller that the evict-on-settle bridge map would have missed.
- **Co-locate the new cache with the existing caches' invalidation, not with the code that uses it.** `forgeQueryCache`/`forgeQueryInflight` live in `GitHubCaches.ts` (not `forgeProvider.ts`) precisely so `clearGitHubCaches()` (token/settings change) and `clearPRCaches()` (manual PR refresh) drop them **atomically** with every sibling cache. A query cache that a manual refresh forgets to clear serves stale CI/PR state for the full TTL.
- **Never cache errors** (cf. #4832): cache only inside `.then`, evict the in-flight entry in `.finally` (guarding `if (map.get(key) === request)` against a newer entry). A cached rejection would block retries for the entire TTL.
- Use a deterministic serializer (`safe-stable-stringify`'s `configure`) for cache keys so equivalent variable objects coalesce regardless of property order, and delimit key parts with `\0` (impossible inside a GraphQL document, so the query segment can't forge the variables segment).

## Applies when

Migrating data access behind any new provider/forge/repository abstraction; reviewing a PR that re-routes calls through a new "clean" interface (check for lost cache/dedup/retry); adding a new GraphQL/forge query path that must respect the GitHub rate limit; wiring a new cache that user-triggered refreshes must be able to invalidate; designing dedup for an operation that crosses the main↔utility-process boundary.
