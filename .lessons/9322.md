## Context

`PluginService.unloadPlugin` (`electron/services/PluginService.ts:2300`) tears down everything a plugin registered: IPC handlers, actions, menu/keybinding/context-menu/toolbar contributions, panel kinds, forge providers + impls, file-decoration providers + impls, settings state, MCP servers. Plugins can be unloaded at runtime (dev-mode re-scan, reload with a fixed manifest), and each registry the plugin touched is a separate global keyed by plugin id.

## Problem

A single throw partway through the cascade (e.g. a forge descriptor unregister blowing up) would skip every later step. The skipped steps leak registry entries — most damagingly the matching `*Impls` entries — which resurface as duplicate-id errors the next time the same plugin loads. The renderer side had a parallel hole: `plugin.invoke` rejections fell through silently, so a throwing plugin action produced no user-visible signal.

## Root cause

The unload teardown was a flat sequence of imperative registry calls. Wrapping the whole thing in one try/catch (or leaving it bare) means error containment is all-or-nothing: a throw at step N aborts N+1..M, leaving partial state. Critically, a descriptor unregister and its impl unregister were a single step, so a descriptor failure stranded the impl — the exact pair that produces duplicate-registration errors on reload. This is a cleanup cascade, not normal control flow: failing fast is wrong because every remaining disposer still needs to run.

## Lesson

- Wrap **each** disposer in a multi-step cleanup/unload cascade in its own try/catch so a throw at one step can't strand the rest. Canonical helper: `runUnloadStep(pluginId, step, fn)` (`PluginService.ts:308`) logs a `console.warn` (best-effort cleanup is not user-actionable) and continues.
- Split descriptor-unregister and impl-unregister into **separate** steps (forge: `unregisterForgeProviders` vs `unregisterForgeProviderImpls`; file-decoration: the parallel pair). A failure in one must not prevent the other, since stranded impls are what re-surface as duplicate-id errors.
- Bulk `*Impls` clears must be idempotent — already-cleared keys are silent no-ops — so the belt-and-suspenders bulk call after per-provider disposers can't throw on a double-clear.
- At the renderer dispatch boundary, wrap `window.electron.plugin.invoke` in try/catch (`usePluginActions.ts:179`): surface a "Plugin action failed" toast gated on `!isDisposed()` (so a late-resolving invoke after HMR/window-close can't toast a stale failure), `logWarn`, then return `undefined` — do **not** rethrow, or `ActionService.dispatch` double-routes the same failure.
- Normalize anything thrown out of a plugin (`activate()` etc.) to a serializable `{ message, stack?, at }` record via a helper like `toPluginLoadErrorRecord`; guard `JSON.stringify(undefined) === undefined` by coalescing to `String(err)` so bare `throw undefined`/`throw null` still yield a usable label.

## Applies when

- Editing `PluginService.unloadPlugin` or any step in its cascade, or adding a new plugin contribution type (you must add both a registration AND a `runUnloadStep`-wrapped unregister, splitting descriptor vs impl into separate steps).
- Writing any multi-step teardown/dispose/cleanup sequence in the main process where each step touches a different global registry (menu, keybinding, action, panel-kind, forge, decoration, MCP registries) and a single failure must not strand later steps.
- Debugging duplicate-id / "already registered" errors that appear only after a plugin reload or runtime re-scan — suspect a partial unload from an earlier throwing disposer.
- Adding error handling at a plugin/extension boundary (activation, action dispatch in main `dispatchHandler` or renderer `usePluginActions`, view render) where untrusted third-party code can throw arbitrary (including non-`Error`) values.
- Surfacing a plugin failure as a toast from a hook with an async IPC call that may resolve after unmount — gate the notify on an `isDisposed()` check and return `undefined` rather than rethrowing into `ActionService`.
