## Context

`restorePanelsPhase` in `src/utils/stateHydration/panelRestorePhase.ts` restores saved terminal panels on app boot. PR #11233 (`2a7374d6c`, for #11232 "keep agent terminals alive when their worktree is deleted") added re-homing: a saved panel whose `worktreeId` isn't in the current worktree list gets rewritten to `activeWorktreeId` rather than restored onto a dead worktree. `getKnownWorktreeIds()` builds the membership Set from `worktreesPromise`, which resolves via `worktree.getAll()` → `WorkspaceClient._doGetAllStates(windowId)`, prefetched at the top of hydration to overlap with terminal restoration.

## Problem

On a cold restart, every agent terminal in every worktree but one collapsed into a single worktree, and which one was inconsistent across restarts of the same project. It didn't look like a race — just panels appearing to have moved — and since the corrupted assignment gets persisted by the normal panel-save loop, a second restart could move everything again, to a different worktree. Filed as #11234.

## Root cause

`getKnownWorktreeIds()` originally did `list ? new Set(...) : null`. In JavaScript an empty array is truthy, so a resolved-but-empty `worktree.getAll()` response produced an empty (non-null) Set — the exact same shape as "loaded, confirmed zero worktrees exist." `resolveRestoredWorktreeId()` treats a non-null Set as authoritative: every saved `worktreeId` fails the `known.has(worktreeId)` check against an empty Set, so every panel gets re-homed to `activeWorktreeId`, regardless of whether its worktree is alive and well.

The empty response is not an error, it's a real race baked into the boot sequence by design (#8827: hydration overlaps with backend init for speed). `worktree.getAll()` resolves `[]` two ways depending on timing: `WorkspaceClient._doGetAllStates` returns `[]` outright if the per-window host isn't registered in `WorkspaceHostPool` yet, and even once the host exists, its `get-all-states` handler iterates `this.monitors`, a map that stays empty until `load-project` finishes `git worktree prune`, `listService.list()`, `mapToWorktrees()`, and `syncMonitors()` — several real git subprocess calls the renderer's hydration prefetch can easily outrace. Over the wire, "host not ready" and "loaded, zero worktrees" are bit-for-bit identical: both are `[]`. The disambiguating domain fact: the second case can never actually happen — `git worktree list` always reports at least the main worktree, so a _successful_ enumeration is never empty. `[]` therefore only ever means "not ready yet."

The fix (`c7b362959`) changes the check to `list && list.length > 0 ? new Set(...) : null`, collapsing empty into the same "unknown, keep the saved id" branch as `null`. The active-worktree restore path in `index.ts` needed the identical `worktreesAreKnown = worktrees !== null && worktrees.length > 0` guard — same truthy-`[]` bug independently, silently restoring no active worktree on the same race. Fixing the sentinel exposed a second-order problem: `cleanupOrphanedTerminals()` calls `removePanel`, which kills the PTY, and used to run unconditionally after restore. With panels no longer wrongly re-homed, a panel whose worktree really _was_ deleted keeps its dead `worktreeId` — exactly what cleanup should catch — but if the _active_ worktree selection is itself stale (same race), cleanup could kill a live terminal before `selectFallbackWorktree` got a chance to repair the selection. So orphan cleanup (`968f9114a`, `298090e9b`) is now gated on `worktreesAreKnown && activeWorktreeIsLive`, skipping the destructive pass for one boot rather than risk killing a live agent PTY — precisely the failure mode #11232 was written to eliminate.

## Lesson

- **A resolved-but-empty collection is not automatically a real answer — check whether "zero" is even reachable for the domain.** `[]` from `worktree.getAll()` is indistinguishable over IPC from "not ready," but the domain invariant `git worktree list` always includes the main worktree proves zero is impossible, so empty can only mean "unknown." Before trusting an empty array/list/Set as authoritative, ask if the source can ever legitimately produce zero.
- **`list ? ... : null` is a truthy-empty-array trap** — an empty array is truthy in JS, so this pattern conflates "resolved with nothing" with "resolved with real data" instead of with `null`/`undefined`. Use an explicit length check (`list && list.length > 0 ? ... : null`) whenever "empty" and "unknown" must stay distinguishable.
- **Persisted-state corruption from a boot race compounds silently across restarts** — restore results feed the normal panel-save loop, so a wrong answer on one boot isn't self-correcting, it's the new saved truth for the next boot, and can get re-homed again to a _different_ wrong target as the active worktree shifts. Any hydration logic that both reads and writes persisted state needs the trustworthiness check before any derived value gets saved.
- **Fixing an ambiguous-sentinel bug can unmask a second bug the ambiguity was accidentally hiding** — here, the incorrect re-homing had been quietly absorbing the case where `cleanupOrphanedTerminals` would otherwise kill a live PTY over a stale active-worktree selection. When you fix a sentinel/race bug, check whether anything downstream was relying on the old (wrong) behavior as an accidental safety net, and re-gate that consumer on the same "is this data trustworthy" signal you just introduced.
- **Known residual gap:** `resolveRestoredWorktreeId` still re-homes onto `activeWorktreeId` without validating it's live — the cleanup gate prevents that from killing a PTY, but doesn't fix the re-home target. Proper fix needs `selectFallbackWorktree` extracted out of `src/utils/stateHydration/index.ts` to avoid a circular import; noted as a follow-up, not yet its own issue as of this writing.

## Applies when

- Touching `restorePanelsPhase`, `getKnownWorktreeIds`, `resolveRestoredWorktreeId`, or the active-worktree restore branch in `src/utils/stateHydration/index.ts`.
- Diagnosing panels/terminals/tabs "collapsing" into one item on cold restart, especially if the target is inconsistent across restarts — check for a persisted-state save loop compounding a one-time race.
- Writing hydration/restore code that awaits an IPC-fetched list (`worktree.getAll`, any `WorkspaceClient`/`WorkspaceService` snapshot) before the host has necessarily finished `load-project` — the #8827 prefetch-for-speed pattern means early callers can see a transiently empty result.
- Reviewing any `list ? f(list) : fallback` pattern feeding a decision that then gets persisted — verify empty-truthy isn't conflated with "confirmed empty."
- Touching orphan/cleanup logic gated on worktree existence (`cleanupOrphanedTerminals`) — confirm it can't run destructively (PTY kill) on a stale or not-yet-authoritative list.
