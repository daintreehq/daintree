## Context

Each project gets its own `WebContentsView` via `ProjectViewManager` (multi-window/project-view architecture), with a paint gate: on a cold-start switch the outgoing view stays attached until the incoming renderer signals readiness (double `requestAnimationFrame`), bounded by soft/hard timeouts. `createWindow.ts` already guarded the initial `appView` with `setBackgroundColor(windowBg)` and an explicit comment ("WebContentsView defaults to white otherwise"), and #9207 had fixed the identical white flash on Portal browser tabs (`PortalManager.ts`) four days before this PR. #9573 then reported the same flash a third time — on the views `ProjectViewManager.createView` builds during a project switch.

## Problem

Cold-start project switches briefly flashed white before the incoming project painted. The misleading part: the paint gate exists precisely to prevent this — the swap waits for renderer readiness before detaching the outgoing view — so the tempting diagnosis was a broken or too-loose gate. The gate was working exactly as designed; no timeout tuning could have fixed it.

## Root cause

Two facts compose. (1) Electron instantiates every `WebContentsView` with an opaque white compositor background (upstream electron/electron#37201); any frame where the view's renderer has not yet presented pixels shows that clear color. (2) The renderer readiness signal — double rAF — only confirms the main thread finished its render steps (style, layout, paint, commit to the compositor). Commit is not presentation: GPU rasterization and present can land one or two frames later. So the outgoing view detaches a frame or two before the incoming view's pixels are actually on screen, and in that gap the compositor draws the bare view's background — white. There is no "pixels presented" event to gate on, so the compositor clear color is the only possible backstop for the present gap.

The deeper trap is that the invariant cannot be centralized: Electron offers no global default-background hook, so the guard must be re-asserted at each `new WebContentsView(...)` site — and history shows each new factory misses it. The fix added `resolveInitialCanvasBackgroundColor()` to `electron/window/skeletonCss.ts` (synchronously reads persisted `appTheme` from electron-store, runs `migrateCustomSchemes`, resolves the scheme via `resolveAppTheme`, returns `tokens["surface-canvas"]`) and calls it in `createView` immediately after construction — before `addChildView` and before `loadURL`. Accent override is intentionally omitted because `applyAccentOverrideToScheme` never touches `surface-canvas`. Note the code moved: #9576 patched `ProjectViewManager.createView`, but the #11004 file split (`e0f194191`) extracted it to `electron/window/ProjectViewFactory.ts` `createView()` (called from `ProjectViewSwitchController.ts`); the guard now lives at line ~78 there.

## Lesson

- **Every `new WebContentsView(...)` must call `setBackgroundColor(...)` between construction and `loadURL`/`addChildView` — there is no central enforcement.** The miss recurred independently in three factories (`createWindow.ts` appView had the guard; `PortalManager.createTab` missed it → #9207; `ProjectViewManager.createView` missed it → #9573). Current guarded sites: `createWindow.ts` ~312, `ProjectViewFactory.ts` ~78, `SurfaceViewManager.ts` ~170, `PortalManager.ts` ~162. Adding a fifth view factory without the guard WILL reintroduce the white flash.
- **Never try to fix a swap/reveal flash by tightening the paint gate.** Double-rAF proves compositor commit, not GPU presentation; a 1-2 frame present gap is structural. The themed clear color is the backstop that makes the gap invisible — the gate only bounds how long the old view stays up.
- **Use `resolveInitialCanvasBackgroundColor()` (skeletonCss.ts), not a hand-rolled color.** It resolves the persisted theme's `surface-canvas` token including custom-scheme migration, synchronously (safe pre-loadURL). Hardcoding a hex or reading `nativeTheme` alone breaks for users on custom/light schemes — the flash just changes color.
- **Test the call ORDER, not just the call.** The #9576 tests assert via `mock.invocationCallOrder` that `setBackgroundColor` precedes both `loadURL` and `addChildView`, and separately cover the LRU-evicted replacement path — replacement views after a destroyed webContents go through the same factory and are an easy second miss.
- **Mocked views need the method stubbed everywhere.** Adding the call broke seven `ProjectViewManager.*.test.ts` mock factories that modeled views as `{ webContents, setBounds }` — when extending a view factory, sweep every test mock of that view shape in one pass.

## Applies when

- Adding any new `WebContentsView` creation site — a new panel host, portal, surface, preview, or plugin-owned view (`grep -rn "new WebContentsView" electron/` and compare against the four guarded sites).
- Diagnosing a white or wrong-color flash on project switch, overlay open/close, window show, view LRU-eviction/replacement, or dock/portal reveal.
- Tempted to fix a swap flash by adjusting `paintGateTimeoutMs`/`paintGateHardTimeoutMs` or the renderer readiness signaling in `ProjectViewManager`/`ProjectViewSwitchController`.
- Touching `electron/window/skeletonCss.ts` cold-start theme resolution (`resolveInitialColorSchemeId`, `resolveInitialCanvasBackgroundColor`, skeleton CSS) or changing what `surface-canvas` resolves to.
- Reviewing tests that mock `WebContentsView` shapes for `ProjectViewManager`/`SurfaceViewManager` — the mock must include `setBackgroundColor` or the suite fails on unrelated changes.
