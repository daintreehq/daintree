## Context

`initializeStore` in `electron/store.ts` maintains a `.bak` sibling of `config.json` so a corrupt main config can be recovered. Two defenses run on startup: `preflightValidateConfig` quarantines and restores from `.bak` when the file is unparseable JSON, and after the `Store` is constructed `refreshBackup` copies the current good config over `.bak`. The store is created with `clearInvalidConfig: true`.

## Problem

A config that is _valid JSON but schema-invalid_ (e.g. `{"_schemaVersion": "not-a-number"}`) sails past `preflightValidateConfig` — it parses fine. Then the `new Store()` constructor, seeing the schema violation, silently overwrites the file with defaults. The unconditional `refreshBackup` that ran next immediately copied the now-defaulted file over `.bak`, destroying the user's last recoverable state with no error, no event, and no log.

## Root cause

`electron-store`'s `clearInvalidConfig: true` performs the wipe _inside the constructor_ — there is no throw and no event, so nothing downstream can tell a defaulted file from a genuine user file. Compounding this, byte-inequality cannot distinguish a destructive wipe from a benign default-merge: a normal app upgrade also rewrites `config.json` to add new default keys while preserving every user value, and that rewrite legitimately _should_ refresh `.bak`. Preflight only guards the unparseable-corruption path; the schema-violation path is a distinct, invisible failure mode.

## Lesson

- When a library mutates a file _during construction_ with no error or event (here `electron-store` + `clearInvalidConfig`), snapshot the raw on-disk bytes **before** construction and re-read **after**, then diff to decide what actually happened. Don't trust the absence of an exception.
- Distinguish a _wipe_ (user data lost) from a _merge_ (defaults added, user values preserved) by **key survival**, not byte-equality: `detectStoreWipe` parses pre/post and treats it as a wipe if any pre-existing key is missing post or any value changed (via per-key `JSON.stringify` compare). A merge keeps every original key/value, so `.bak` should still refresh; a wipe drops/changes them, so `.bak` must be left frozen.
- Gate the destructive `refreshBackup` behind that check — only refresh the backup when the post-construction file is provably still the user's own data.
- When a more specific recovery state is already set upstream (preflight's `restored-from-backup`), do not clobber it; only set `reset-to-defaults` when `pendingSettingsRecovery` is still `null`.

## Applies when

- Touching `electron/store.ts` initialization, `refreshBackup`, `detectStoreWipe`, `readRawSnapshot`, or `pendingSettingsRecovery` ordering.
- Adding or changing the schema/defaults of any electron-store-backed config, or adding new persisted stores that use `clearInvalidConfig`.
- Any backup-on-startup pattern where a library rewrites the source file at load time — verify the refresh can't overwrite the last-good copy with freshly-defaulted content.
