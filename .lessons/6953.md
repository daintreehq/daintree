## Context

The assistant HelpPanel spawns its own terminal in the content dock, then _hides_ it from the dock's tab-group list because it's surfaced inside the panel instead. `ContentDock.tsx` (around line 101) filters that terminal out by excluding `helpPanelStore.terminalId`: `groups.filter((g) => !(g.panelIds.length === 1 && g.panelIds[0] === helpTerminalId))`. The `+ New session` and `Run anyway` flows tear down the old help terminal and spawn a fresh one via `usePanelStore.getState().addPanel(...)`.

## Problem

After `+ New session`, a stray help terminal occasionally appeared as a real tile in the dock (#6951). It was the freshly-spawned help terminal that should have been filtered out — but for one render it wasn't.

## Root cause

`addPanel` is async. The old order was: `await addPanel()` → then `setTerminal(newId, ...)` to teach the dock filter the new id. Between `addPanel` resolving (which synchronously commits the panel into `panelsById`, so the dock re-renders) and the subsequent `setTerminal` microtask, `helpPanelStore.terminalId` was still the old/null value, so the filter predicate `panelIds[0] === helpTerminalId` was false and the new panel rendered unfiltered. A second hazard compounds it: the panel-missing cleanup effect treats `terminalId set && panel absent` as "process died, revoke session" — which would fire (and wipe the reservation) during the in-flight window where the id is reserved but `addPanel` hasn't committed the panel yet.

## Lesson

When a filter/exclusion predicate keys off an id that is normally set _after_ an async create resolves, invert the order: pre-generate the id (`` `terminal-${crypto.randomUUID()}` ``), write it into the keyed store synchronously _before_ the first `await`, and pass it into the create call as `requestedId` so the panel commits under the already-known id. Then:

- Guard any "id set but entity absent → clean up" effect with a pending-id ref (`_pendingNewTerminalId`); skip cleanup while `id === pendingId` so the in-flight window doesn't self-destruct the reservation (`HelpSessionController.handleTerminalPanelMissing` returns early when `terminalId === this._pendingNewTerminalId`).
- Clear the reservation (`clearTerminal()` + null the pending ref) on EVERY failure path — provision non-ok, `addPanel` returning falsy, and the catch — or a failed launch leaves a phantom filtered id forever.
- The store write must happen before any `await`; one microtask of gap is enough to render the unfiltered panel.

## Applies when

- Adding or editing dock/list visibility filters that exclude a panel/terminal by an id pulled from a Zustand store (`ContentDock.tsx` `helpTerminalId` exclusion, any `groups.filter(... === someStoreId)`).
- Spawning a panel via `usePanelStore.addPanel` where the renderer must immediately treat it as special (hidden, bound, owned) — use the `requestedId` + `activateDockOnCreate` options so the id is known before the await resolves.
- Working in `HelpSessionController` `+ New session` / `Run anyway` / launch flows, or any controller that tears down then re-creates a panel and re-binds it in `helpPanelStore`.
- Any "entity id is set but the entity isn't in the store yet → assume it died and clean up" effect during an async create; you need a pending-id guard to distinguish "not created yet" from "was created then removed".
