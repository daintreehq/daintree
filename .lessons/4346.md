## Context

When the Electron renderer process crashed, the app hung silently with a blank window. Users had no path to recovery except force-quitting the entire application. In a multi-worktree IDE where each project has its own `WebContentsView`, renderer crashes are a meaningful risk.

## Problem

No crash handling was implemented for the per-project `WebContentsView`. Electron fires `render-process-gone` on `WebContents` but nothing listened to it. The renderer becoming unresponsive also had no production handler.

## Root cause

Renderer crash recovery requires distinguishing between a one-off crash (recoverable via `webContents.reload()`) and a crash loop (repeated crashes within a short window indicating a persistent corruption). A simple auto-reload without loop detection would infinitely reload a broken state, consuming CPU and never presenting the user with a recovery option.

## Lesson

Implement crash recovery on the per-view `render-process-gone` handler (in `electron/window/ProjectViewHandlers.ts`, extracted from `ProjectViewManager.ts` in #11004) with reason-aware, tiered logic. The same pattern is duplicated at two other layers: the window-level main renderer in `createWindow.ts`, and each `SurfaceViewManager.ts` paint surface — keep all three in sync when the recovery contract changes.

1. **Single non-loop crash:** reload the view (and for `reason === "oom"`, destroy and recreate the window via `onRecreateWindow`) — covers most OOM/transient crashes.
2. **Crash loop (`CRASH_LOOP_THRESHOLD` = 3 crashes within `CRASH_LOOP_WINDOW_MS` = 60s):** Load a static recovery HTML page (served at `app://daintree/recovery.html` in production, `${devServerUrl}/recovery.html` in dev; source lives in `public/recovery.html`) with no React dependencies — React itself may be broken. The recovery page offers reload, workspace reset, and diagnostics via a minimal IPC channel (`CHANNELS.RECOVERY_RESET_AND_RELOAD`, exposed as `recovery.resetAndReload` in `preload.cts`).

The recovery page must be static HTML/JS with zero dependencies on the main app bundle. Wire `unresponsive`/`responsive` events in production only (not dev) to avoid false positives during HMR (the window-level unresponsive dialog lives in `createWindow.ts`). Always track crash timestamps (`crashTimestamps` per view) to detect loops. `getMainWindow()` is defined in `electron/window/windowRef.ts` (re-exported from `windowServices.ts`) for the recovery IPC handler to reach it.

## Applies when

- Any `WebContentsView` or `BrowserWindow` that runs the main renderer
- Electron 37+ where utility process crashes are also fatal
- Implementing "reset workspace" recovery that clears persisted state before reload
