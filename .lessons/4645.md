## Context

`createWindow()` had an early-exit guard: if a window already existed, it focused the existing window instead of creating a new one. This was the explicit single-window assumption baked into the core lifecycle.

## Problem

Three collisions when the guard was removed without additional scoping:

1. **Terminal ID collisions**: two windows creating terminals with the same ID prefix would corrupt PTY routing.
2. **Global service re-initialization**: the second window triggered re-initialization of global services (WorkspaceClient, PtyClient) that should only be set up once.
3. **`second-instance` CLI paths**: when the app was already running and the user ran `daintree /path/to/repo`, the handler focused the existing window instead of opening a new one.

## Root cause

The app was designed with implicit single-window assumptions embedded in several places: the `second-instance` handler, `createWindow()`, the window-service setup, and terminal ID generation. The OS-level lifecycle handlers (`second-instance`, `activate`, `window-all-closed`) now live in `electron/lifecycle/appLifecycle.ts`.

## Lesson

- **Don't try to dodge PTY-routing collisions with window-prefixed terminal IDs** — that approach was superseded. We initially reached for per-window ID prefixes, but the collision is now solved _structurally_, not by namespacing IDs: each window opens its own MessagePort to the PTY host with per-window project filtering (`PtyClient.connectMessagePort(windowId, port)` / `disconnectMessagePort` and `windowProjectContexts` in `electron/services/PtyClient.ts`; #4646), and each project runs in an isolated `WebContentsView` with its own V8 context (`ProjectViewManager`; #4672). Panel/terminal IDs are now opaque `crypto.randomUUID()` values (`${kind}-${crypto.randomUUID()}` in `src/store/slices/panelRegistry/addPanel.ts`), never window-prefixed — global uniqueness comes from the UUID, routing isolation comes from the port topology.
- **Distinguish global vs. per-window service initialization** by routing each through the right module: `setupWindowServices()` (`electron/window/windowServices.ts`) calls `initGlobalServices()` (`electron/window/globalServicesInit.ts`) exactly once (gated on `getGlobalServicesInitialized()`) and `initPerWindowServices()` (`electron/window/perWindowInit.ts`) per window. Singleton clients are skipped on the second window via ref guards: PtyClient with `if (!getPtyClient())` in `perWindowInit.ts`, WorkspaceClient with `if (!getWorkspaceClientRef())` (gated behind the global-init block) in `windowServices.ts`.
- **`second-instance` must open a new window for the CLI path** (`opts.onCreateWindowForPath(cliPath)` in `appLifecycle.ts`), not `win.focus()`. Focus-existing was correct for single-window but breaks the multi-window contract; plain re-launches and `.dntr` installs still bring the primary window to the front.
- **The `createWindow()` guard was load-bearing for single-window testing**: all unit tests assumed one window. After removing the guard, tests need explicit scoping of window references.
- **`activate` on macOS (dock click) should still create a window only when none are open** (`appLifecycle.ts` checks `windowRegistry.size > 0`) — this is distinct from `second-instance`, which always honors the CLI path.

## Applies when

Removing single-window guards from any Electron app being upgraded to multi-window. Audit terminal/session ID generation, service initialization ordering, and OS-level single-instance handlers.
