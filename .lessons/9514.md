## Context

Each project remembers which worktree was active so switching away and back lands on it. The renderer's `useWorktreeSelectionStore` (`src/store/worktreeStore.ts`) holds the selection; `buildOutgoingState` (`src/store/projectStore.ts`) snapshots it into the project-switch IPC payload, and hydration (`src/utils/stateHydration/index.ts`) restores it. A worktree can become "active" two ways: the user deliberately selects it (clicks a card, palette), or a terminal in some other worktree gains focus and the orchestrator promotes that worktree (`rendererStoreOrchestrator.ts`).

## Problem

After a batch PR-merge run (which spins up and tears down many temporary worktrees), switching away from a project and back restored a leftover temporary PR worktree instead of the root worktree the user was actually working in.

## Root cause

Three independent bugs compounded — each harmless alone:

1. **Incidental focus promotion was persisted as the restore point.** A single `activeWorktreeId` field served both "what's on screen now" and "what to restore later." When a terminal in a temp worktree gained focus, the orchestrator called `selectWorktree(id)`, which persisted that incidental promotion as the project's durable selection.
2. **A lagging main-process read clobbered the renderer's value.** `ProjectSwitchService.saveOutgoingProjectWorktreeState` re-derived the selection from `store.get("appState").activeWorktreeId`. That electron-store value trails the renderer by the async `app:set-state` write, so it could resurrect a stale/incidental worktree and overwrite the correct value the renderer had just persisted via `persistOutgoingProjectState`.
3. **An unreliable `isMainWorktree` fallback.** When the saved worktree no longer existed, the fallback sorted by `isMainWorktree` first, but that flag isn't always populated — so an alphabetically-first temp worktree could win over the real root.

## Lesson

- **Separate durable restore intent from in-session active state.** Add `restoreWorktreeId` alongside `activeWorktreeId`. Only `restoreWorktreeId` round-trips across project switches; `activeWorktreeId` is session-only. Persist the durable field, never the active one.
- **Tag selection calls with provenance.** `selectWorktree(id, { source: "user" | "focus" })`: `"user"` (default) updates the durable target, persists to the main store, and records MRU; `"focus"` updates only the session-active id. Incidental promotion must never write the restore point, persist, or pollute MRU. A deliberate re-selection of an already-focus-promoted worktree _upgrades_ it to durable.
- **Never re-derive a value in the main process from a store snapshot that lags the renderer.** If the renderer is the source of truth and writes via async IPC, the main-process electron-store copy is stale by definition during a switch. Preserve the renderer-authored per-project value verbatim; do not "helpfully" recompute it from `store.get("appState")`.
- **Validate the restore target against the live worktree set before persisting** (`getWorktreeIdSet()` in `buildOutgoingState`): drop it to `undefined` if removed so hydration falls through cleanly. Skip validation only when no view store is mounted (`null`).
- **In fallback selection, identify the main worktree by canonical `path`/explicit flag, treating an absent `isMainWorktree` as non-main — never let an alphabetical sort pick the fallback** (`selectFallbackWorktree`). Same family as #2251 / #3979.

## Applies when

- Adding any "remember the last X and restore it" feature where X can also change incidentally (focus, auto-selection, transient spin-ups).
- Any main-process code tempted to read `store.get("appState")` to reconstruct a value the renderer owns during a switch/teardown flow.
- Writing fallback/default selection over a worktree (or similar) list, especially when temporary entities with arbitrary names can coexist with the canonical one.
