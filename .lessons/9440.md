## Context

`PullRequestService` (main process) revalidates every tracked open PR on a steady-state poll, fanning out one GraphQL `findPRsByNumbers` re-fetch per PR through the forge bridge into the workspace-host. GraphQL queries cost ~3 points each against GitHub's 5000/hr GraphQL budget; REST conditional GETs cost zero on a `304 Not Modified`. The forge provider exposes optional `BatchLookupCapability` methods (`shared/types/forge.ts`).

## Problem

At 25 open PRs polling every 30s, the per-PR GraphQL revalidation tick burned ~9000 GraphQL points/hour per instance — nearly 2x over the 5000/hr budget — even on a completely idle repo where nothing had changed.

## Root cause

A steady-state "is anything different?" check was paying full GraphQL fetch cost on every tick instead of asking the cheap question first. GitHub's REST `GET /repos/{owner}/{repo}/pulls?state=open&per_page=100` supports `If-None-Match`; an authenticated `304` costs no quota at all and proves no open PR on page 1 changed. The fix (`probeOpenPRList` in `GitHubPRDiscovery.ts`, gated through `bridge.probeOpenPRList` in `PullRequestService.revalidateResolvedPRs`) runs that probe first and short-circuits the GraphQL fan-out entirely on `unchanged`, dropping steady-state cost ~25x. Two non-obvious traps sit inside the short-circuit:

- **ETag commit discipline.** You must NOT advance the cached ETag on every `200`. The caller passes `PRSnapshot[]` (its current `head.sha`/`updated_at` view); the probe commits the new ETag ONLY when the diff is clean (no tracked PR differs), i.e. the caller has already consumed the change. If you committed the ETag while a change was still unconsumed, the next tick returns `304` against the advanced baseline and the unconsumed change is masked forever. Leaving the old ETag in place forces a re-fetch (`200`) and re-diff until the caller catches up — gating the commit on caller-sync without a second round-trip. This mirrors `fetchActivityProbe` in `GitHubStats.ts` / `repoEventsETagCache`.
- **A 304 does not mean CI status is unchanged.** A CI re-run does NOT bump the PR's `updated_at`, so the probe reports those PRs `unchanged` and the metadata re-fetch is skipped — but green/red transitions would then never surface. `revalidateResolvedPRs` therefore still calls `enrichPRWithCIStatus` for any `ciStatus === "PENDING" || "EXPECTED"` PR not already enriched, even on an otherwise-unchanged tick.

## Lesson

- When a steady-state poll re-fetches via an expensive API (GraphQL, paid quota), front it with a cheap REST conditional GET keyed by ETag; treat `304` as "skip the whole fan-out," not as a single resource.
- The ETag baseline is single-owner: a main-process singleton cache keyed `owner/repo`, gated behind the per-project poll lease (`acquirePollLease`) so sibling windows don't race the baseline forward. Commit the ETag ONLY after confirming the caller's snapshots match the probe — never on raw `200`. A failed/partial fetch must never advance the ETag (it would mask the unconsumed change). On a `200` with no ETag header, `invalidate` the entry rather than leaving a stale one.
- Enumerate every signal the conditional GET's change-key does NOT capture and keep polling those independently. Here `updated_at` misses CI re-runs, so PENDING/EXPECTED CI keeps polling through the short-circuit.
- Return a three-way result (`unchanged` | `changed` | `fallback`), and make any inconclusive outcome (rate-limit block, network/parse error, mid-flight cache-version change, missing capability) fall back to the full re-fetch — fail open, never silently claim `unchanged`.
- Page-1-only ETag (`per_page=100`) over-reports (a tracked PR on page 2 reads as absent → flagged changed every tick) but never under-reports — acceptable when few entities are tracked.

## Applies when

- Adding or modifying any GitHub/forge polling path: `PullRequestService`, `GitHubPRDiscovery.ts`, `GitHubStats.ts`, `forgeProvider.ts`, `BatchLookupCapability`, or anything that fans out `findPRsByNumbers` / `getCIStatuses` GraphQL calls per entity.
- Touching ETag conditional-GET caches (`openPRListETagCache`, `repoPRListETagCache`, `repoEventsETagCache`, `prETagCache`) or writing a new `probe*` function with `If-None-Match` / `304` handling — review the "commit only when in sync" discipline.
- Investigating GraphQL/REST rate-limit exhaustion, 5000/hr budget overruns, or quota cost from background PR/issue/CI polling.
- A bug report where CI status (or some other field the ETag's change-key doesn't track) stops updating after an optimization that added conditional-GET short-circuiting.
- Designing a poll that must be single-owner across multiple windows/views (per-project poll lease) to keep a shared ETag baseline from racing forward.
