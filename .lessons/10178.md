## Context

The dev-preview pane loads a `<webview>` pointed at a stable reverse-proxy origin (`dp-<x>.localhost:43000`) fronted by `DevPreviewProxyService`, which self-generates a bare `text/plain` HTTP 502 (`send502`) when the upstream dev server is down, mid-restart, or unregistered. The pane already had a styled error overlay (`webviewLoadError`) with a "Restart dev server" recovery branch — but it was driven exclusively by `did-fail-load`, i.e. Chromium _net_ error codes (`ERR_CONNECTION_REFUSED` and friends). Nothing in the renderer ever inspected an HTTP response status.

## Problem

When the proxy returned a 502, the pane rendered the raw plaintext body ("The dev server isn't responding.") as page content and never recovered — even after the dev server came back (#9948). The misleading part: the styled overlay code was all present and looked correct; it was silently defeated at runtime because the events it depended on classified the 502 as a _success_.

## Root cause

Two Electron `<webview>` semantics combine into a dead zone. First, **an upstream HTTP error status is a successful network load**: TCP connected, a response committed, so `did-fail-load` never fires and `did-finish-load` does — and `handleDidFinishLoad` unconditionally cleared `webviewLoadError`, actively erasing any error state something else might have set. Second, no commonly-used load event carries the status: `did-navigate` exposes only `url`. The **only renderer-side `<webview>` event carrying `httpResponseCode` (plus `isMainFrame`) is `did-frame-navigate`** — which nothing listened to.

The fix (#10178) hangs on event ordering within one navigation: `did-start-loading` → `did-frame-navigate` → `did-navigate` → `did-finish-load`, all firing sequentially within one microtask pump. `handleDidFrameNavigate` detects a main-frame 502, sets the `proxy_error` overlay, and latches `pendingHttpErrorRef = true`; `handleDidNavigate` skips its error-clear when the latch is set; `handleDidFinishLoad` consumes the latch and returns early (skipping both the error-clear and the device-emulation re-apply). `handleDidStartLoading` clears any _stale_ latch so a fresh navigation starts clean — `did-frame-navigate` re-sets it if the new load also 502s. A plain ref (not React state) is mandatory: the three trailing events read the latch in the same tick it was written, before any re-render could deliver state.

Detection is scoped **strictly to 502** because that is the only status the proxy self-generates; every other response — including a dev app's own 500/503/504 error page or a bootstrap 403/405 — is forwarded upstream untouched and must render so developers see their own error pages. A compounding gap made auto-retry load-bearing rather than cosmetic: the proxy origin is stable across dev-server restarts, so `computeDevServerUrl` (`src/components/DevPreview/urlSync.ts`) returns `false` once the pane is on the origin and the URL-adoption effect never re-navigates — without an active reload loop the raw 502 was terminal. The retry (1s→2s→4s→8s→16s, `PROXY_MAX_RETRIES = 5`) has split lifetimes: `did-start-loading` cancels the pending _timer_ (the new load supersedes it) but preserves `proxyRetryCountRef` so a still-dead upstream keeps walking up the backoff; the count resets only on a genuine successful load.

## Lesson

- **Never key webview error UI solely on `did-fail-load` — it fires only for Chromium net errors, never for HTTP 4xx/5xx.** An HTTP error page is a successful load: `did-finish-load` fires, and any handler that unconditionally clears error state on it will erase HTTP-error detection added elsewhere. Anything clearing `webviewLoadError` must respect `pendingHttpErrorRef` first.
- **HTTP status detection in a renderer `<webview>` must live on `did-frame-navigate`** — it is the only renderer-side event exposing `httpResponseCode` + `isMainFrame`; `did-navigate` carries only `url`. Guard with `isMainFrame` or subframe fetches will trip it.
- **Latch the error in a plain ref, ordered around the navigation event sequence**: `did-start-loading` clears stale latch → `did-frame-navigate` sets it → `did-navigate`/`did-finish-load` check-and-skip their clears, with `did-finish-load` consuming it. React state cannot work here — all four events fire within one microtask pump, before any re-render.
- **Only intercept statuses your own infrastructure self-generates.** The proxy emits exactly one status (502 via `DevPreviewProxyService.send502`); upstream 4xx/5xx pass through so an app's own error pages render. Widening the match to "any 5xx" would hide developers' error pages behind Daintree chrome — the tests assert 500/503/504/403 pass-through precisely to block that.
- **A stable proxy origin has no natural recovery signal**: `computeDevServerUrl` returns `false` once on the origin, so a dev-server restart triggers no re-navigation — recovery requires an active reload loop. Split timer vs count lifetimes: cancel the timer on any new load, preserve the count across reloads for backoff progression, reset only on genuine success.
- The overlay markup later moved from `DevPreviewPane.tsx` to `DevPreviewWebviewOverlays.tsx` (the `proxy_error`/`connection_refused` shared recovery branch); the lifecycle mechanism above is intact in `useDevPreviewLoadLifecycle.ts`.

## Applies when

- Adding error, status, or health detection to any Electron `<webview>`/WebContentsView surface (dev-preview pane, browser panel, plugin panels) — especially anything reacting to HTTP responses rather than net errors.
- Diagnosing "the error overlay never shows" or "a raw text/plain error body renders as page content" in the dev-preview pane.
- Touching `handleDidFinishLoad`, `handleDidNavigate`, or `handleDidStartLoading` in `useDevPreviewLoadLifecycle.ts` — any new clear of `webviewLoadError` or early return must account for the `pendingHttpErrorRef` latch and the retry timer/count split.
- Changing `DevPreviewProxyService` response behavior — a new self-generated status code needs a matching (and equally narrow) renderer-side interception, or it will render as raw text.
- Assuming `did-fail-load` covers "the page failed to load", or that a successful `did-finish-load` means the content is healthy.
