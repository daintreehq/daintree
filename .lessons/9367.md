## Context

Daintree ships 14 hand-tuned built-in themes in `shared/theme/builtInThemes/*.ts`. Each has a 5-tier surface elevation ramp (`grid → sidebar → canvas → panel → elevated`) plus `accent` / `accentSecondary`. #9336 added a hard test gate (`getSurfaceRampMetrics` + monotonic / min-ΔL-step / max:min step-ratio ≤ 2.0 assertions) and #9319 added hard cross-theme accent-distinctness gates (0.065 OKLab floor, no-duplicate-hex), then retuned 12 themes to satisfy them.

## Problem

The retunes degraded several themes' identity: the default Daintree sidebar picked up a visible green tint, Bondi went purple-leaning, Redwoods canvas shifted olive, Hokkaido turned pink-warm, Highlands lost its purple character. #9367 reverted both PRs wholesale — restored all 14 palettes, deleted `shared/theme/oklch.ts`, and dropped the gates.

## Root cause

The gate measured and constrained only OKLab **L** (lightness). To satisfy a min-ΔL-step or step-ratio bound, palette hexes were nudged — but a hex edit that moves L also moves **a/b (chroma/hue)** unless they're explicitly held. Nothing in the gate bounded chroma or hue drift, so each nudged rung absorbed a hue cast. Concretely, daintree sidebar went `#131312` (warm-neutral, R≈G≈B) → `#121510`, where the G channel (`15`) now sits above both R (`12`) and B (`10`) — a green tint. A "monotonic L-step" gate looks mathematically complete but is one-dimensional: it polices the depth ordering while silently permitting the hue regressions it was supposed to prevent. Hard-failing CI on hand-tuned values forces the human to mutate carefully-balanced colors to appease a partial metric.

## Lesson

- A perceptual color gate that constrains a single axis (L) must **also bound the orthogonal axes** (chroma, hue) before it can hard-fail, or it will trade the policed defect for an unpoliced one.
- Treat hand-tuned design tokens as authoritative: audit them **warn-first**, not fail-first. The resolution lives in current `shared/theme/oklch.ts` — `auditSurfaceRamp`, `auditAccentProminence`, `auditCrossThemeAccents` all return `failures: []` and push every finding to `warnings`, and the tests `console.warn` them while only asserting `failures` is empty. The advisory surfaces drift to a reviewer without rewriting the artist's palette.
- Only an objective, identity-neutral violation (an unparseable hex, an exact-duplicate accent) belongs in `failures`. Perceptual-threshold opinions (JND step floor, runaway ratio, cross-theme ΔE) belong in `warnings`.
- The OKLCH conversion itself is fine (canonical CSS Color 4 / Ottosson sRGB→LMS chain, no new deps) — the failure was the enforcement posture, not the math.

## Applies when

- Adding or tightening any automated gate over `shared/theme/builtInThemes/*.ts` palettes, surface ramps, or accent colors.
- Working in `shared/theme/oklch.ts` (`hexToOklch`, `deltaOklch`, `auditSurfaceRamp`, `auditAccentProminence`, `auditCrossThemeAccents`) or `shared/theme/__tests__/builtInThemes.test.ts`.
- Writing any CI assertion that constrains one channel of a perceptual color space (lightness-only, contrast-only) and would force edits to hand-curated design tokens — verify the unconstrained axes can't regress, and default to warn-first.
- Symptoms: a theme picking up an unexpected hue cast (green/purple/olive/pink) in sidebar/canvas/panel after a "ramp evening" or "accent diversification" change; reviewers reporting a theme "lost its character."
