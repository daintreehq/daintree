## Context

#9633 (from #9617) swapped the panel drag-overlay pickup in `DragOverlayWithCursorTracking` (`src/components/DragDrop/DndProvider.tsx`) from a flat 150ms tween to a Framer Motion 12 perceptual spring (`visualDuration: 0.15`, `bounce: 0.05`, constants `DRAG_OVERLAY_SPRING_*` in `src/lib/animationUtils.ts`). The interesting part is not the spring — it's that the PR had to add an explicit `prefersReducedMotion ? { type: "tween", duration: 0 } : spring` branch at the call site, despite the app already having three global reduced-motion guards.

## Problem

Daintree looks blanket-covered for reduced motion: `App.tsx` wraps everything in `MotionConfig reducedMotion={reduceAnimations ? "always" : "user"}`, `index.css` defines the `@custom-variant reduce-motion` (OS media query + `body[data-reduce-animations]`) that neutralizes CSS animations, and `getUiAnimationDuration()` collapses JS timers. So a new FM transition looks safe by default. It isn't: each guard covers a disjoint slice, and none of them fully stops a Framer Motion animation on `opacity` — the pickup would still visibly animate under Reduce Motion without the call-site branch.

## Root cause

Verified in the installed framer-motion 12.40.0 (`^12.37.0` pinned): `motion-dom/dist/es/animation/interfaces/visual-element-target.mjs` substitutes `{ type: false }` (instant) only when `shouldReduceMotion && positionalKeys.has(key)`, where `positionalKeys` = `width/height/top/left/right/bottom` + `transformPropOrder` (`x`, `y`, `scale`, `rotate`, …). `opacity`, colors, and every other value keep their full configured transition — spring physics and tween durations alike. So `MotionConfig reducedMotion` auto-kills the pickup's `scale` animation but lets the `opacity` spring run at full duration. The CSS `@variant reduce-motion` never touches any of it: FM drives inline styles/WAAPI, invisible to CSS `animation: none` rules. And `getUiAnimationDuration()` deliberately no longer collapses under reduced motion — its comment says CSS owns reduced-motion presentation; only performance mode zeroes JS timers.

Second trap, also verified in source: `useReducedMotion()` reads only the OS `prefers-reduced-motion` media-query global — it never consults `MotionConfigContext`. So the explicit branch added in #9633 fires for the OS setting but NOT for Daintree's in-app "Reduce animations" toggle (which reaches FM only as `MotionConfig "always"`, i.e. transform-keys-only). The composed signal (OS pref + `body[data-reduce-animations]` + `body[data-performance-mode]`) is `useShouldSkipMotion()` (`src/hooks/useShouldSkipMotion.ts`) — added later (2026-07-14), which is why `DndProvider` and `FleetArmingRibbon` still use the raw hook.

## Lesson

- **Never assume a global guard covers a new Framer Motion transition.** The FM guard instant-completes only positional/transform keys; the CSS `reduce-motion` variant only touches CSS-driven animation; `getUiAnimationDuration()` only reacts to performance mode. Any FM animation that must fully collapse under reduced motion needs an explicit call-site branch — this is now the house pattern at all three spring sites (`DndProvider`, `FleetArmingRibbon`, `CelebrationConfetti`).
- **Opacity's exemption is policy, not oversight** — the `index.css` reduce-motion block documents "remove spatial motion while leaving opacity changes intact" (WCAG 2.2 SC 2.3.3). Decide per call site whether a fade should survive: `FleetArmingRibbon` degrades its spring to an opacity-only fade; the drag overlay collapses to fully instant because a trailing ghost during an active drag is itself spatial.
- **Prefer `useShouldSkipMotion()` over FM's `useReducedMotion()`** for new branches — the FM hook sees only the OS media query (and is `null` until it resolves), so a branch on it silently ignores the in-app toggle and performance mode. Existing raw-hook sites are upgrade candidates when touched.
- **FM transition durations are in seconds; every repo motion token is in ms.** `visualDuration: 0.15` ≈ the old 150ms tween; passing `DURATION_150` would ask for a 150-second spring. The `animationUtils.test.ts` guard (`toBeLessThan(1)`) exists precisely to catch a ms figure — keep that shape when adding spring constants.
- **For mount-only entries, gate `initial` too** (`initial={reduced ? false : entryValues}`): `initial: false` mounts directly at the target so nothing animates regardless of transition; the transition branch additionally covers later `animate`-value changes. #9633 kept both. Spring tuning values live as named constants in `animationUtils.ts` — never inline literals.

## Applies when

- Adding or modifying any `framer-motion` transition in `src/` — especially one animating `opacity` (or color), spring or tween, where "reduced motion is handled globally" is the tempting assumption.
- Debugging "an animation still plays with Reduce Motion on" or "the in-app Reduce animations toggle doesn't affect X" — check whether the animated key is positional and which of the four guard layers actually reaches it.
- Touching the spring call sites: `DragOverlayWithCursorTracking` in `DndProvider.tsx`, `FleetArmingRibbon.tsx` ribbonMotionProps, `CelebrationConfetti.tsx`.
- Choosing between `useReducedMotion` (OS-only, `null`-initial) and `useShouldSkipMotion` (composed), or wiring a new motion-skip signal.
- Writing any FM `visualDuration`/`duration`/`delay` value near the repo's ms-based `DURATION_*` tokens — the units differ by 1000x and nothing type-checks it.
