## Context

`#10980` shipped Daintree's read-only markdown viewer (dialog + panel), rendering `react-markdown` output through `@tailwindcss/typography`'s `.prose` class via `<div className="markdown-document prose prose-daintree max-w-none">`. `.prose-daintree` already existed in `src/index.css` (reused from an earlier chat-interface markdown surface) remapping the plugin's `--tw-prose-*` variables to Daintree's theme tokens (`--color-daintree-text`, `--color-text-primary`, etc.), and it lived inside that file's single shared `@layer base { ... }` block alongside every other base rule.

## Problem

Rendered markdown in dark mode showed unreadable colors — the plugin's light-theme text/heading colors on dark surfaces. The natural read was "the token values are wrong" or "the class isn't matching": `.prose-daintree`'s remaps were present, correctly scoped to `.markdown-document`, and visibly shipped in the built CSS, so nothing about the rule itself looked broken. It only reproduced in dark mode, which pointed investigation at the token values rather than the actual cause.

## Root cause

Tailwind v4's `@tailwindcss/typography` plugin registers `.prose` inside `@layer utilities`. CSS cascade layers make every rule in a later-declared layer beat every rule in an earlier layer, unconditionally — specificity and source order inside a layer only matter for breaking ties within that same layer, they never let an earlier layer win. Tailwind's project-wide layer order declares `base` before `utilities`, so nothing placed in `@layer base` can out-rank `.prose`'s own defaults from `@layer utilities`, no matter how the selector is written. `.prose-daintree` sat inside `src/index.css`'s single `@layer base { ... }` block, so its `--tw-prose-*` custom-property assignments were structurally incapable of beating the plugin — this wasn't a specificity or ordering bug, it was a layer-membership bug, and specificity tweaks could never have fixed it. The fix in `#10982` proves this: it deletes `.prose-daintree` from `src/index.css` and moves the identical variable remaps into a new file, `src/components/Markdown/MarkdownDocument.css`, imported directly by `MarkdownDocument.tsx` with no `@layer` wrapper at all. Same selectors, same token values, zero specificity change — the only thing that changed is layer membership, and unlayered author styles beat every named layer including `utilities`, so the override started winning.

## Lesson

- **Layer origin beats specificity and source order, full stop.** If a rule needs to override a Tailwind plugin's own output (`.prose`, or any future plugin-emitted class), check which `@layer` the plugin registers into before writing the override — an override inside an earlier-declared layer can never win regardless of selector strength.
- **"CSS looks right but doesn't apply" in one theme polarity only is a layer-membership smell, not a token-value smell.** Before re-checking variable values or selector specificity, check computed layer membership (DevTools' Layers/`@layer` panel) whenever a Tailwind plugin is in the mix.
- **The sanctioned fix pattern here is an unlayered, component-scoped stylesheet** — `src/components/Markdown/MarkdownDocument.css` is intentionally unlayered (its header comment states the invariant explicitly) and is imported straight by the component rather than folded into `src/index.css`'s shared `@layer base` block. Copy this pattern for any future third-party-plugin surface (a new prose-like plugin, a component library's own utility layer) that needs theme-token remapping.
- **A source-order or snapshot test cannot catch a future re-layer regression — only a resolved-color assertion can.** `e2e/full/panels/core-file-panel.spec.ts` (~line 121, "Rendered mode renders the document with theme-token colors") reads the heading's actual `getComputedStyle(...).color`, computes what the theme token should resolve to via a throwaway probe element, and asserts equality — that's what makes it impossible for someone to silently re-wrap the override in `@layer` again without a test failing.
- **State the layer invariant inline in the file, not just in a PR description.** `MarkdownDocument.css`'s header comment spells out "wrapping these rules in any `@layer` block would silently hand the colors back to the plugin's light-theme defaults" so a future edit that adds `@layer` for tidiness doesn't look like a harmless refactor.

## Applies when

- Touching `src/components/Markdown/MarkdownDocument.css`, `.prose`/`.prose-daintree` usage, or any override of a Tailwind-plugin-emitted class, and colors fail to apply in only one theme polarity.
- Adding a new plugin-driven surface (another `@tailwindcss/typography`-style plugin, a component library shipping its own utility classes) that needs theme-token remapping — put the remap in an unlayered file scoped to the component, not in `src/index.css`'s shared `@layer base` block.
- Diagnosing any "the CSS is definitely there but doesn't win" bug — check `@layer` membership before specificity or source order, especially when a Tailwind plugin is involved.
- Reviewing a new `@layer` block or CSS import touching `src/index.css` — verify it isn't quietly fighting a plugin-emitted class that lives in `@layer utilities`.
- Writing an E2E guard for theme-dependent CSS — assert the resolved computed color/property value against the theme token, not just the presence of a class or rule in the stylesheet.
