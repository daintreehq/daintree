## Context

`TerminalRestoreController` has two restore paths: a small path (single `terminal.write()`) and an incremental path (multiple chunks). The incremental path guards against stale callbacks using a `restoreGeneration` counter — if the managed xterm instance is replaced (restore/reconnect/instance swap) between scheduling the write and the callback running, the generation mismatch causes the callback to bail out.

## Problem

The small restore path only checked object identity (`terminal === managed.terminal`), not `restoreGeneration`. Identity alone catches a full `ManagedTerminal` replacement (a different object returned for the same id, e.g. after the instance is torn down and `getOrCreate` rebuilds it), but it does not catch a newer restore/reconnect starting on the SAME still-alive object — same identity, bumped generation. That gap let a stale callback pass the identity check and apply a scroll offset calculated from the old terminal buffer against the new state, corrupting the display.

## Root cause

The two restore paths were written at different times. The incremental path added `restoreGeneration` protection as a later safety measure, but the fix was not backported to the small path. The small path looked safe (object identity check) but the check was insufficient: identity only guards against the `ManagedTerminal` object itself being swapped out, not against a second restore/reconnect being scheduled on the same object while an earlier callback is still pending — that case needs the generation counter, not identity, to detect.

## Lesson

When a safety mechanism (generation counter, epoch check) is added to one code path, audit all sibling paths for the same vulnerability. The incremental and small restore paths share the same race window; generation checks should be consistent across both.

Pattern: capture `const gen = ++managed.restoreGeneration` before the async operation, then check `managed.restoreGeneration === gen` in the callback. This is safe even if the counter wraps (extremely unlikely at write frequency).

## Applies when

- Adding new async write operations to `TerminalRestoreController.ts` — always capture and validate `restoreGeneration`.
- Any pattern where a callback is scheduled on an object that can be replaced before the callback fires — generation counters are the correct solution.
