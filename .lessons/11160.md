## Context

`ContentDock.tsx` implements the dock rail as a roving-tabindex toolbar: `handleDockKeyDown` wires ArrowLeft/ArrowRight/Home/End to move focus between `[data-dock-item]` chips, explicitly modeled on the same pattern already working in `Toolbar.tsx` (`handleToolbarKeyDown`). Docked terminal panels render inside a Radix Popover, and `DockedTerminalItem.tsx` portals the actual terminal body via `createPortal` into that Popover's content, which Radix mounts under `document.body`.

## Problem

Typing ArrowLeft/ArrowRight into a docked terminal — grid terminals were unaffected — kicked keyboard focus out of the terminal mid-type onto an adjacent dock chip (issue #11156). It read like a terminal-focus bug, but the terminal was never the faulty component: the keydown was reaching the dock rail's own roving-tabindex handler, a container the terminal is not even a DOM descendant of.

## Root cause

React synthetic events propagate along the component (fiber) tree that produced them, not the rendered DOM tree. `createPortal` relocates an element's DOM node elsewhere (here, into a Radix `PopoverContent` under `document.body`) but keeps it a React child of whatever rendered the portal, so its events still bubble up through `ContentDock`'s `onKeyDown` exactly as if it were an in-place child. `handleDockKeyDown` had no target check at all, so any arrow keydown that reached it — regardless of DOM origin — advanced `activeDockIndexRef` and moved focus. Two independent input surfaces failed to stop the event from arriving: xterm intentionally does not call `stopPropagation` when `screenReaderMode` is on, an OS-accessibility-driven runtime toggle rather than a fixed dev-time setting, and the CodeMirror input bar calls `preventDefault` without `stopPropagation`. Either path let the arrow keep bubbling until it hit the rail. `Toolbar.tsx` already guards against exactly this — `if (!toolbarRef.current?.contains(e.target as Node)) return;` at `Toolbar.tsx:798` — and `ContentDock`'s own header comment says the rail mirrors Toolbar's roving-tabindex pattern, but the copy dropped the one line that makes the pattern safe under portals. The fix is the mirror-image guard: `if (!(e.target instanceof Node) || !scrollContainerRef.current?.contains(e.target)) return;` at the top of `handleDockKeyDown`.

## Lesson

- **Any keydown/focus/click handler on a container with portaled descendants must gate on real DOM containment, not fiber-tree membership.** `container.contains(e.target as Node)` (after an `instanceof Node` check, since synthetic `e.target` is typed as `EventTarget`) is the only reliable test — "this handler only sees my own children" is false the moment a Radix Popover/Dialog/DropdownMenu or a raw `createPortal` sits anywhere in that fiber subtree.
- **"Modeled on X" is not "audited against X."** `ContentDock`'s comment claimed parity with `Toolbar.tsx` since inception, but the one guard line that made `Toolbar.tsx` portal-safe was never copied over. When a component's docs claim it mirrors another, diff the two implementations line-by-line for the specific guards, not just the general shape.
- **Don't rely on a descendant's `stopPropagation` as your safety net — cancellation is state-dependent and can silently flip.** xterm's `screenReaderMode` (driven by live OS accessibility state, not a static flag) changes whether it stops propagation on a given keystroke; CodeMirror already never stops propagation at all. A handler that implicitly depends on children canceling events for it is fragile to states it doesn't control and can't observe.
- **Fix key-ownership bugs at the listening ancestor, not by making the leaf defensive.** This PR deliberately did not add `stopPropagation` near xterm or touch `XtermAdapter` — the project has a history of repeated reverts from over-broad key interception there. The correct owner of "is this keydown mine?" is the rail/toolbar container, not the terminal.
- **Before declaring a sibling handler safe, verify it structurally, not by inspection alone.** `DockedTabGroup`'s tab-strip handler was checked and left untouched because its tablist is a DOM _and_ React sibling of the terminal body — terminal keydowns cannot structurally reach it — which is a different, stronger guarantee than "it happens not to have this bug today."

## Applies when

- Touching `ContentDock.tsx`'s `handleDockKeyDown`, `Toolbar.tsx`'s `handleToolbarKeyDown`, or any other roving-tabindex / arrow-key navigation handler under `src/components/Layout/`.
- Adding or reviewing a Radix Popover/Dialog/DropdownMenu (or any `createPortal` use) whose content hosts an interactive child — terminal, editor, input — inside a component that also owns its own keyboard navigation.
- Diagnosing a "focus jumps away mid-interaction" bug where the surface that visibly loses focus and the surface actually causing it are different DOM subtrees — check `composedPath()` and `e.target.closest(...)` against the suspected handler's real container, not just where the bug is _seen_.
- Reviewing any handler documented as "mirrors `<OtherComponent>`'s pattern" — confirm the specific guard lines were actually copied, not just the general structure.
- Working near `screenReaderMode`-sensitive xterm behavior or CodeMirror's input bar — both are documented non-`stopPropagation` paths that leak keydowns to ancestors.
