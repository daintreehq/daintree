## Context

Daintree's terminal lifecycle spans three processes (renderer, main, pty-host) linked by async IPC, and a "restarted" terminal (kill + respawn, host-crash respawn, shard migration) keeps the SAME `terminalId` for its new incarnation. Before #10950, a run of one-off PRs (#10811 hibernation removal, #10905 resume/journal, #10927 persisted-field pipeline, #10940) each patched an individual symptom of this. #10950 built `AgentTerminalLifecycleLedger` (`shared/utils/agentLifecycleLedger.ts`), one instance per process (renderer's own, main's via `electron/services/pty/lifecycleLedger.ts`, pty-host's own field on `PtyManager`), to close the whole class off with one mechanism.

## Problem

Async completions from a killed terminal incarnation could land on its live successor because every cross-process message is keyed only by `terminalId`, and that id is not unique to one incarnation. Concretely: a late `spawn-result` from a killed predecessor could delete the replacement's `pendingSpawns` entry (losing it from host-crash replay); a resize buffered before a kill could become the successor's boot size; a persisted-session hydration snapshot resolving after a fresh relaunch could overwrite the fresh launch's `launchAgentId`/model/preset/env; a kill's own journal write could race a fast same-id restart and be dropped or attributed to the wrong session. Each surfaced independently and looked like its own bug — the shared cause was easy to miss because "does the terminal still exist" is a natural but insufficient staleness check: the id still exists, it's just owned by a different incarnation now.

## Root cause

Existence is not ownership. Checking `if (get().panelsById[id])` or `if (this.pendingSpawns.has(id))` confirms the id is still tracked but says nothing about whether the async result in hand belongs to the incarnation currently holding it. The fix is a monotonic `launchGeneration` per terminal id: main mints it once per spawn (`recordLaunch` in `PtyClient.ts`, at the respawn-after-crash and shard-migration call sites), stamps it onto the spawn options sent to the pty-host, and the pty-host's own ledger ADOPTS that number (`options?.generation`) instead of minting its own — both processes key the same incarnation identically without an extra sync round trip. Every completion crossing a process boundary (`exit`, `spawn-result`, `agent-session-captured`) echoes the generation back, and mutators validate against it before applying anything.

Two validation regimes are required, because "stale" means different things per operation. Live-state ops (resize, restore, attach, detected-agent, worktree-attribution) go through `withCurrent()`: only the CURRENT generation may apply, older or newer is rejected — a buffered resize or restore merge from any other incarnation is simply wrong for the live one. Terminal-final ops (close, journal) go through `withGenerationMark()`, keyed by `${terminalId}#${generation}`: exactly-once PER generation, but past generations are still accepted, because a kill's journal write can legitimately arrive after the same id respawned and must attribute to the generation that produced it, neither dropped nor pinned on the successor. Swap the regimes and the bug returns: "current-only" for journal drops legitimate history from a fast restart; "any generation" for resize lets a dead incarnation's buffered dims boot the new one.

Sharp edge: `recordJournal` marks a RESERVATION before the durable write lands, not a receipt — `journalAgentSession` must call `rescindJournal` on write failure or every other close path for that generation is permanently locked out by the exactly-once gate (a crash mid-write would otherwise irreversibly drop that session's history).

## Lesson

- **Never use "does this id still exist" as your only staleness guard when the id can be reused across an async gap.** Existence isn't ownership; add a generation/epoch counter that increments on every re-spawn and validate cross-process completions against it.
- **Match the validation regime to what the operation means, not one blanket rule.** Live-state ops (resize/restore/attach) reject any non-current generation (`withCurrent`); terminal-final ops (close/journal) are exactly-once-per-generation while still tolerating past generations (`withGenerationMark`) — collapsing these into one rule either drops legitimate late history or leaks a dead incarnation's state into the new one.
- **Mint the generation in exactly one authoritative place and adopt it everywhere else.** Main mints on spawn; the pty-host and renderer echo/adopt that same number, so cross-process agreement is structural (an integer riding the existing message), not a new synchronization RPC.
- **A "mark before durable write" idempotency reservation needs an explicit rescind path on the failure branch**, or a crash mid-write permanently blocks every future retry for that key — `recordJournal`/`rescindJournal` is the pattern; look for the same reserve-then-write-then-maybe-rollback shape anywhere else exactly-once semantics are attempted.
- **When a run of one-off fixes keeps landing on the same class of symptom, check whether they share one root invariant violation before adding another targeted patch.** Here it was id reuse across an async boundary; a systemic mechanism (the ledger) closed off variants the individual fixes hadn't even hit yet.

## Applies when

- Touching terminal restart/respawn flows where the SAME `terminalId` is reused for a new incarnation: `PtyClient.ts` (`respawnPending`, `migrateShardTerminalsToDefault`), `PtyManager.ts`'s `pendingResizes`, or `addPanel.ts`/`restart.ts` in `panelRegistry`.
- Diagnosing "a killed terminal's stale state landed on its replacement" — wrong boot dimensions, wrong resumed session/env/model, a vanished `pendingSpawns` entry, a duplicated or missing session-journal record.
- Adding a new cross-process completion keyed by `terminalId` — decide up front whether it is live-state (current-generation-only) or terminal-final (exactly-once-tolerate-past) before wiring its guard.
- Reviewing a staleness guard that checks only "is this still tracked" — sufficient for a never-reused id, not sufficient here.
- Extending `shared/utils/agentLifecycleLedger.ts`, `electron/services/pty/lifecycleLedger.ts`, `electron/services/pty/agentSessionJournal.ts`, or `src/services/terminal/lifecycleLedger.ts`, or wiring a fourth per-process ledger instance for a new boundary.
