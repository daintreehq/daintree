## Context

Daintree detects an unclean previous exit by leaving a marker on disk (`CrashRecoveryService` / `CrashLoopGuard.markCleanExit()`, the `running.lock` signal). On the next launch, a still-present marker means "we crashed last time"; a cleared marker means "we quit cleanly". The `before-quit` handler in `electron/lifecycle/shutdown.ts` runs a graceful cleanup chain (PTY teardown, WorkspaceClient dispose, MCP stop, audit flushes, DB checkpoint) guarded by a 10s hard timer that fires `app.exit(1)` if the chain hangs (#4287).

## Problem

Two distinct misclassifications of exit cleanliness:

1. A hung shutdown that hit the 10s hard timeout and exited via `app.exit(1)` was nonetheless recorded as a _clean_ exit — so the next launch never knew the previous session died dirty (no recovery/backup prompt).
2. A transient `unhandledRejection` (the app keeps running — no `app.exit` follows) called `recordCrash()`, writing the crash marker. The very next normal Cmd-Q then booted as a phantom crash on next launch, since the marker was already poisoned.

## Root cause

1. `cleanupOnExit()` and `markCleanExit()` were called at the _entry_ of `before-quit`, before the cleanup chain even started. So the marker was cleared unconditionally — the timeout/error branch (`app.exit(1)`) had already lost the dirty-exit signal by the time it ran. The clean-exit marker is a statement about _how the process actually exited_, which is only known after the chain resolves or times out.
2. `unhandledRejection` is non-fatal in this process — it logs, persists a pending error, notifies the renderer, but does NOT terminate. Recording a crash there conflates "an error happened" with "the process died uncleanly". `uncaughtException` (which does call `app.exit(1)`) is the only handler that legitimately marks a crash. The rejection handler was misaligned with it.

## Lesson

- Write the clean-exit marker (`cleanupOnExit()` / `markCleanExit()`) **only in the success branch, after the cleanup chain resolves** — never at `before-quit` entry. The timeout/error branch must deliberately leave the marker on disk so the next launch reads it as a dirty exit. The marker encodes the _outcome_ of shutdown, not the _intent_ to shut down.
- Mark clean **before** best-effort teardown like telemetry, and wrap each marker write in its own `try/catch` so a `closeTelemetry()` failure (or one marker write throwing) can't skip the other. Telemetry must never gate marker cleanup.
- Only record a crash in a handler that actually terminates the process. A non-fatal `unhandledRejection` handler must NOT call `recordCrash()` — that poisons every subsequent clean quit. Keep it aligned with the fatal `uncaughtException` path, which is the sole legitimate crash recorder.
- Note the asymmetry: an eager `takeBackup()` _is_ still taken at quit-intent (so any exit branch has a recent backup), but the clean-_marker_ is not — backups are additive and harmless to take early; the clean marker is a claim that must be earned.

## Applies when

- Editing `before-quit` / shutdown ordering in `electron/lifecycle/shutdown.ts`, or moving where `cleanupOnExit()` / `markCleanExit()` / `recordCrash()` / `takeBackup()` are called.
- Adding or modifying the hard-timeout / `app.exit(1)` branch of the graceful cleanup chain.
- Touching `electron/setup/globalErrorHandlers.ts` — especially the `unhandledRejection` vs `uncaughtException` handlers or anything that writes the crash marker.
- Debugging "app reports a crash on launch even though I quit normally last time" or "a hung quit didn't trigger crash recovery / backup restore".
- Any work on `CrashRecoveryService`, `CrashLoopGuard`, the `running.lock` marker, or safe-mode boot where exit cleanliness is read on the next launch.
- Reviewing code that clears a persisted "we exited cleanly" flag — verify it's set on the actual exit outcome, not the exit intent, and that best-effort steps (telemetry, flushes) can't gate or skip it.
