## Context

The panel tab strip is sortable via dnd-kit and FLIP-animated via framer-motion. `SortableTabButton` (`src/components/Panel/SortableTabButton.tsx`) calls `useSortable`, which produces a CSS `transform` applied via `CSS.Transform.toString(transform)` to a `<div ref={setNodeRef}>` (the isolation div). Both `PanelTabList` and `DockedTabGroup` render the buttons inside `<AnimatePresence mode="popLayout">` with a per-tab `<m.div layout="position">` so close/reorder gets a width-collapse + FLIP slide.

## Problem

Dragging a tab and releasing it produced visible stutter on drag-end. `SortableTabButton` had its own inner `<m.div layout="position">` wrapping the `TabButton`, in addition to the outer `m.div` that `PanelTabList` already provides.

## Root cause

Two independent transform sources were fighting over the same animated element. dnd-kit writes a CSS `transform` to the isolation div during drag; framer-motion's `layout="position"` on the inner `m.div` measures geometry and writes its own `transform` to reconcile layout on drag-end. The two counter-measured each other — dnd-kit's drag transform and motion's FLIP transform resolved on different nodes/frames, so the tab snapped and re-corrected instead of settling. The fix relies on the **double-wrapper isolation pattern**: the dnd-kit transform sits on the `setNodeRef` div _between_ the framer-motion layout wrapper (outside) and the `TabButton` (inside), so the two transform writers never share a node. The inner `m.div` collapsed that isolation. Removing it was correct for `PanelTabList` (which supplies the outer wrapper), but `DockedTabGroup` rendered `SortableTabButton` directly with **no** outer `m.div`, so removal silently killed its close/reorder FLIP — the layout-animation contract was being inherited, not owned. The fix had to re-add the `AnimatePresence` + `m.div layout="position"` wrapper to `DockedTabGroup` to restore parity.

## Lesson

- When a node is both dnd-kit sortable and framer-motion layout-animated, keep exactly one transform source per DOM node. Put the dnd-kit `transform` on the `setNodeRef` div and the `m.div layout="position"` _outside_ it (the caller owns the layout wrapper). Never nest a second `layout` motion node inside the sortable subtree.
- A motion wrapper that looks "redundant and harmless" inside a leaf component may be the only thing supplying the layout-animation contract for a _different_ consumer. Before deleting it, grep every render site (`PanelTabList`, `DockedTabGroup`) — a component rendered in two places can rely on the wrapper in one and inherit it in the other.
- Mirror the `AnimatePresence initial={false} mode="popLayout"` + `m.div layout="position"` (with `UI_ANIMATION_DURATION`/`EASE_OUT_EXPO_FM` from `src/lib/animationUtils.ts`) pattern at every site, and gate both branches on `document.body.dataset.performanceMode === "true"` to drop all motion in performance mode.

## Applies when

- Editing `SortableTabButton`, `PanelTabList`, `DockedTabGroup`, or any component that combines `useSortable`/`CSS.Transform.toString` with `m.div layout` / `AnimatePresence`.
- Investigating stutter, snap, or double-correction on drag-end of a draggable+animated element.
- Removing or refactoring a framer-motion `layout` wrapper that looks redundant — check whether a second render site depends on it.
- Adding FLIP / close / reorder animation to a new dnd-kit sortable list (tabs, cards, worktree lists) and deciding which node carries the transform.
- Adding a `performanceMode` bypass to a motion-wrapped list and needing both branches to stay structurally consistent.
