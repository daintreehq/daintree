## Context

`ProcessMemoryMonitor` polls process/system memory every 30s (`POLL_INTERVAL_MS`) and escalates through two tiers on pressure: tier 1 (light reclaim), then tier 2 if it persists (`destroyHiddenWebviews(2)`, evict cached project views, `hibernateUnderMemoryPressure()`). `ResourceProfileService.computeTargetProfile()` runs a separate, parallel pressure score (`efficiency`/`balanced`/`performance`) off the same system-memory signal (`process.getSystemMemoryInfo()`: free + purgeable on macOS).

## Problem

On a 64GB Mac, the machine got progressively less responsive under exactly the workload it should handle well — a handful of agent terminals — no crash, no leak, just recurring stalls that only showed up "under pressure." The instinct was to suspect the PTY data plane, but the pty-host stayed healthy throughout; the interruption was the app's own periodic housekeeping, not the terminals.

## Root cause

Two design choices compounded into a self-inflicted incident, plus one masking bug that hid the loop from its own escalation logic.

1. **Unbounded RAM-fraction thresholds.** The system-available-memory floor was `totalRamMb * SYSTEM_LOW_MEMORY_FRACTION` (`0.1`, no cap) — on a 64GB machine that's a 6.4GB "critical" floor (`ResourceProfileService`'s `SYS_AVAILABLE_LOW_FRACTION`/`HIGH_FRACTION` had the same shape). macOS routinely leaves several GB "free" occupied by harmless file-cache on high-RAM boxes, so a threshold scaling linearly with `os.totalmem()` with no ceiling manufactures permanent "critical" pressure on exactly the machines with the most memory to spare.
2. **No tier 1 cooldown, and tier 1 was destructive to the foreground.** Every 30s poll that saw pressure re-ran tier 1 unconditionally, and its `clearCaches` action called `session.defaultSession.clearCache()` + `clearStorageData({storages:["shadercache","cachestorage"]})` and broadcast `window:reclaim-memory` to **every** window — including the currently visible, foreground renderer. With the threshold effectively always tripped, real cache clears and forced GC repeatedly interrupted the active renderer: that's the stall the user felt, not a PTY problem.
3. **The resample gating escalation ignored the signal that caused the pressure.** After tier 1, `pressureRemains` was recomputed only from per-process/aggregate RSS, never re-checking system-wide available memory. So even with the OS-level 1.1GB-available condition unchanged, the resample could report "resolved" and tier 2 (evict cached project views, hibernate idle projects — the thing that would actually help) never fired.

The fix spans four files: the new `electron/utils/systemMemory.ts`'s `getSystemMemoryThresholds()` caps critical at `min(0.1 × totalMb, 1024)` and warning at `min(0.2 × totalMb, 2048)`; `globalServicesInit.ts`'s `clearCaches` action (the `session.defaultSession.clearCache()` + `clearStorageData` + all-windows `window:reclaim-memory` broadcast) was deleted outright and removed from the tier 1 call site in `ProcessMemoryMonitor.ts` (tier 1 now only trims pty-host state and destroys already-hidden webviews); the resample in `ProcessMemoryMonitor.ts` re-reads `readAvailableSystemMemoryMb()` (`systemPressureRemains`) so persistent system-wide pressure reliably reaches tier 2 (now backed by `ProjectViewEvictionController.ts`'s `evictStaleViews` via the new `evictCachedProjectViews` action); and a 5-minute `TIER1_MITIGATION_COOLDOWN_MS` makes tier 1 fire once per episode, not once per poll.

## Lesson

- **Cap RAM-relative thresholds, don't just scale them.** A `fraction × os.totalmem()` floor with no ceiling becomes multiple GB on 64–128GB machines, where ordinary file-cache occupancy then reads as permanent critical pressure. Give any "the OS is starved" threshold an absolute cap (`CRITICAL_MAX_MB = 1024`, `WARNING_MAX_MB = 2048` here) alongside the fraction.
- **A mitigation that touches the foreground renderer needs its own cooldown, independent of the detection poll.** Re-running `clearCache()` + forced GC every 30s while pressure persists turns "help under pressure" into a recurring self-DoS on the renderer the user is looking at. Gate anything destructive-to-foreground on a cooldown longer than the poll interval (`TIER1_MITIGATION_COOLDOWN_MS`), separate from tier-2's own cooldown.
- **Never clear Chromium caches or force GC in the currently visible renderer as an automated mitigation, at any frequency.** #11092 didn't cooldown `clearCaches` into safety, it deleted it from tier 1 — the cost (stall, repaint, jank) lands immediately on an active user. Reclaim hidden/background state instead (`destroyHiddenWebviews`, `evictCachedProjectViews`, pty-host trim).
- **A tiered response's "did it work" resample must recheck every signal that could have triggered escalation, not just the easiest one to re-measure.** Here the resample checked app RSS but not system-wide available memory, so `pressureRemains` could go false while the real condition was unchanged — a state machine that thinks it recovered because it stopped looking at the right variable.
- **"64GB free" is not evidence against memory pressure — check the threshold math, not the gut feeling.** Unbounded-fraction thresholds get worse, not better, as RAM grows. Inverse of #10948's fixed 512MB pty-host heap budget (which doesn't scale with RAM when intuition expects it to): here the threshold scales with RAM when it needed a cap.

## Applies when

- Diagnosing intermittent renderer stalls on high-RAM (64GB+) macOS machines that "shouldn't" be under pressure — check `ProcessMemoryMonitor`'s `memory-pressure-tier1-mitigation`/`-reclaim` logs for 30s-cadence repetition before suspecting the PTY/terminal data plane.
- Adding or tuning any threshold expressed as `fraction × os.totalmem()` — verify an absolute cap exists (`electron/utils/systemMemory.ts`'s `getSystemMemoryThresholds`), or high-RAM machines will manufacture false criticality.
- Adding a periodic mitigation/reclaim action that can touch the foreground/visible renderer (cache clear, forced GC, reload) — it needs a cooldown independent of the polling interval and should default to background-only targets.
- Building or reviewing any tiered pressure/escalation system (`ProcessMemoryMonitor.ts` tier logic: `TIER1_MITIGATION_COOLDOWN_MS`, `MITIGATION_COOLDOWN_MS`, `PRESSURE_COUNT_TIER2`) — confirm the resample rechecks every escalation signal, not a subset.
- Touching `ResourceProfileService.ts`'s system-memory score or `ProjectViewEvictionController.ts`'s pressure-forced eviction path.
