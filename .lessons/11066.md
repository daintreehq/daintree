## Context

The `DragDrop` system (`src/components/DragDrop/`) uses `@dnd-kit/sortable`'s `useSortable()` for reorder mechanics and a separate `m.div` (framer-motion) wrapper around every sortable item for the visual reflow animation. #6862 ("apply framer-motion layout pattern to all sortable wrappers", May 2026) established that split identically across `SortableDockItem`, `SortableDockPlaceholder`, `SortableWorktreeCard`, `SortableWorktreeTerminal`, and `GridPlaceholder`: each got an outer `m.div layout="position"` plus `useSortable({ animateLayoutChanges: () => false })` on the same node. #11066 revisits two of those five — the dock chip and the dock's empty-slot placeholder.

## Problem

Issue #11063: dropping a panel into the footer terminal dock made every other dock chip visibly slide from its old slot to its new one. That doesn't match the dock's own metaphor — the macOS dock just snaps a dropped item into place, no shuffle. The misleading part: `useSortable()` on the dock chip already had `animateLayoutChanges: () => false` set, which reads like "reflow animation is off" — so checking the dnd-kit config first (the obvious move) found nothing wrong and pointed away from the real animator.

## Root cause

Two independent systems wrap the same dock chip and either one can animate its reflow. dnd-kit's own sort-transition machinery is gated by `animateLayoutChanges`; a separate outer `m.div` from framer-motion owns FLIP via the `layout="position"` prop, measuring the node's position before/after a re-render and interpolating a CSS transform to make it "fly" there — entirely independent of dnd-kit. #6862 turned dnd-kit's animation off specifically so framer would be the sole animator (`SortableTerminal.tsx:76-79`: "Disable dnd-kit's own layout animation. Framer-motion's `layout=\"position\"` owns FLIP...without this the two systems fight over `style.transform`"). That trade is correct for the grid and worktree lists, where a smooth FLIP slide on resort is the desired feel. But #6862 rolled the identical wrapper onto the dock too, without asking whether the dock's own affordance (mimicking the macOS dock) wants a slide at all. "Disable the other library's animator" and "disable animation" are not the same operation — #6862 only ever tuned one knob per consumer. #11066's fix is flipping the second knob (`layout="position"` → `layout={false}`) that #6862 never separated by context.

## Lesson

- **Two animation systems wrapping the same reorderable node are independent, not coupled.** dnd-kit's `useSortable`/`animateLayoutChanges` and framer-motion's `m.div layout` prop each animate reflow on their own; disabling one leaves the other fully armed. If a "turn off reflow animation" fix only touches `animateLayoutChanges`, it hasn't touched framer at all — check the wrapping `m.div`'s `layout`/`layoutId` too.
- **Don't roll one animation pattern uniformly across UI paradigms that imitate different real things.** #6862 applied `layout="position"` to all five sortable wrappers for consistency; the dock specifically imitates the macOS dock (snap, no shuffle) while the grid/worktree lists don't — that mismatch is exactly what #11066 had to carve back out. A shared component pattern is not a shared design intent.
- **A wrapper that looks inert once `layout={false}` can still be load-bearing.** The outer `m.div` forwards dnd-kit's ARIA `attributes` (via `remainingAttributes`) onto a node deliberately kept separate from the one carrying dnd-kit's drag transform (`setNodeRef`). Collapsing the two into one element puts both libraries' transforms on the same node — the exact stutter #9029 already fixed for tab buttons (`SortableTabButton`/`DockedTabGroup`). `DockReflow.test.tsx` asserts the split directly (`ariaWrapper !== transformNode`, `ariaWrapper.contains(transformNode)`), not just the absence of animation.
- **Assert the opt-in predicate, not the literal prop value.** `DockReflow.test.tsx` checks `Boolean(record.layout) || Boolean(record.layoutId)` is false on every motion node the dock renders, across idle and dragging states, so dropping `layout` entirely (behaviorally identical to `false`) still passes while a regression on either wrapper or state fails. Mutation-checked: temporarily restoring `layout="position"` fails exactly the 3 no-FLIP cases and nothing else.
- **The same trap is still live elsewhere, on purpose.** `GridPlaceholder.tsx` and `SortableWorktreeTerminal.tsx` still carry `layout="position"` from #6862 unchanged — #11063 scoped the bug to the dock only. Don't assume the dual-animator issue is fixed everywhere just because the dock's chip and placeholder were addressed; the same two-knob check applies if grid/worktree reflow ever changes.

## Applies when

- Debugging "I disabled the reflow/reorder animation but it's still sliding" on any dnd-kit + framer-motion sortable wrapper (`SortableDockItem`, `SortableTerminal`, `GridPlaceholder`, `SortableWorktreeCard`, `SortableWorktreeTerminal`) — check `layout`/`layoutId` on the `m.div`, not just `animateLayoutChanges`.
- Adding a new sortable/reorderable element that wraps children in both a dnd-kit `useSortable()` node and a framer-motion `m.div` — decide the reflow feel per container instead of copy-pasting the existing wrapper pattern wholesale.
- Touching `SortableDockItem.tsx`, `DockPlaceholder.tsx`, `SortableTerminal.tsx`, `GridPlaceholder.tsx`, or `SortableWorktreeTerminal.tsx` and tempted to delete the outer `m.div` because `layout={false}` makes it look inert — it still forwards dnd-kit's ARIA attributes and keeps framer's node separate from dnd-kit's transform node (#9029's contract).
- Reviewing or extending drag-and-drop animation where the UI is meant to mimic an external real-world affordance (macOS dock, a native list) — verify the animation actually matches that affordance instead of inheriting whatever the rest of the drag system does.
