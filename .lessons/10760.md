## Context

Every open project keeps a dormant `WorkspaceHostPool` entry (a utility-process host doing git status/fetch/PR polling) and, when its `WebContentsView` is LRU-evicted from the small warm cache, a fully-cold renderer reload on switch-back. This PR arc (#10737 busy overlay, #10746 background-pause wiring, #10748 freeze-vs-destroy, #10751 skeleton paint gate, #10757 idle warm-up, #10760 wrapping it up) started from a report that switching "didn't feel fast" even after the skeleton-reveal work had merged — a real `daintree.log` session confirmed the fast path worked but exposed reliability problems under realistic multi-project use: 1-1.75s main-process event-loop stalls and 326 workspace-host spawns in one session.

## Problem

A brand-new A/B harness (`e2e/full/resilience/project-switch-stress.spec.ts`, opt-in via `RUN_PERF_STRESS=1`) rotated 5 projects x 8 rounds on a 64GB machine. Baseline never completed the storm — it wedged, with a worst main-loop freeze of 7,044ms and 43 workspace-host respawns. This PR's build finished clean in 12.7s with zero freezes and zero in-storm respawns. A pathological 20-project cycle (working set far bigger than any cache) only improved ~13% — a reminder that the fix's payoff is entirely about whether the cache size matches the real workload, not a universal speedup.

## Root cause

Three mis-scaled caps combined into one class of bug: warm resources sized without regard to the real working set or actual free RAM. (1) `WorkspaceHostPool`'s dormant pool was a flat `MAX_WARM_ENTRIES = 3`, and `computeDefaultCachedViews` capped the `WebContentsView` cache at 4 even on a 64GB machine. Cycling a normal 5-project workflow evicted the least-recently-used dormant host/view and respawned one cold every switch — a utility-process fork plus a full git rescan for the host, a full renderer boot for the view — exactly the 1-1.75s stall and 326-spawn pattern. Fixed by RAM-scaling both to shared tiers (2/3/4/5 across <16/16/32/64GiB) via `computeDefaultCachedViews(os.totalmem())`.

(2) `ResourceProfileService`'s "efficiency" profile — entered on battery, thermal, CPU, or worktree-count pressure, not necessarily memory — called `pvm.setCachedViewLimit(1)` gated by a `lastMemoryScore > 0` check meant to skip non-memory triggers. The real trap was one level up: `globalServicesInit.ts`'s `getUserCachedViewLimit()` fell back to a hardcoded `?? 1` for any user with no stored `cachedProjectViews` preference, so restoring the cap on efficiency-exit reclamped fresh installs to 1 regardless of actual RAM, guaranteeing a cold-start storm on the next switch. #10748 removed the clamp entirely: efficiency now only frees CPU (`setEfficiencyFreeze(true)` plus `view.setVisible(false)` to release GPU tile textures), and destruction is owned exclusively by `ProjectViewEvictionController`'s `evictStaleViews()`, gated on its own `lowMemoryFreeThresholdMb` floor which fires only when free RAM is genuinely low, decoupled from profile. The hardcoded fallback became `effectiveCachedProjectViews()` (RAM-tiered, E2E-aware).

(3) A third "who forgot to pause" gap: `WorkspaceHostPool.releaseOldProject` never told the outgoing host it was backgrounded, so a project you switched AWAY from kept polling git/fetch/PRs at full rate until you closed it, not until you switched away. #10746 fixed this by sending `{type:"background"}`/`{type:"foreground"}` on ref-count transitions in `loadProject`/`releaseOldProject`, with a multi-window guard (don't background a host another window still holds), and a mirror in the legacy non-pool `switch.ts` IPC path, which bypasses the pool entirely.

## Lesson

- **Size warm caches/pools to the realistic working set, not an arbitrary constant.** `MAX_WARM_ENTRIES = 3` and a view-cache ceiling of 4 both meant an ordinary 5-project workflow evicted+cold-respawned on nearly every switch; RAM-scale the tiers instead (`computeDefaultCachedViews`, `electron/utils/cachedProjectViews.ts`) so the cap reflects what the machine can actually hold.
- **Decouple "free CPU" from "free RAM" in any pressure-response policy.** `setEfficiencyFreeze(true)` (CPU/timer suppression) must never be bundled with a destructive action (`setCachedViewLimit`) unless the trigger that fired is actually memory pressure — a battery/thermal/CPU-only trigger destroying a cache buys zero RAM benefit and creates a guaranteed cold-start storm on the next switch.
- **A hardcoded fallback buried in a restore path silently reintroduces the bug the primary fix just removed.** `getUserCachedViewLimit()`'s `?? 1` re-clamped every user without a saved preference on efficiency-exit, regardless of RAM. Grep every consumer of a tunable config value for a stale hardcoded default before declaring a sizing/policy fix complete.
- **A lifecycle "pause on X" hook wired to only one exit path silently leaves every other exit path unpaused.** `WorkspaceHostPool` only demoted hosts on project close; #10746 added the switch-away transition (refCount drops to 0) because a project you switched away from is functionally background from that window, even if another window still has it open — audit close AND switch-away AND any legacy/non-pool fallback path.
- **Validate perf fixes against a workload that matches real usage, not just a stress ceiling.** The pathological 20-project cycle (nothing fits any cache) improved only ~13%, while the realistic 5-project rotation went from wedged/7044ms/43-respawns to 12.7s/0-freezes/0-respawns — a fix that only shows up in the realistic case is still the correct fix.

## Applies when

- Touching `WorkspaceHostPool` (`maxWarmEntries`, `releaseOldProject`, the `background`/`foreground` `send`) or `ProjectViewEvictionController`/`ProjectViewManager` cache-limit logic (`setCachedViewLimit`, `evictStaleViews`, `lowMemoryFreeThresholdMb`).
- Sizing any LRU/warm-pool cap in Daintree's multi-project architecture — check `computeDefaultCachedViews` for the RAM-tier pattern before inventing a new fixed constant.
- Adding or reviewing a `ResourceProfileService` efficiency-profile action — confirm whether it frees CPU (cheap, always safe) or destroys state (must gate on genuine memory pressure only, via `evictStaleViews`, never a profile-level clamp).
- Diagnosing "switching between several open projects feels slow / stalls" — check workspace-host spawn counts and eviction logs; a 5-8 project realistic rotation is the meaningful stress workload, not a 20-project pathological cycle.
- Wiring any resource-lifecycle hook (pause/resume/background/foreground/freeze) — audit every exit and entry path, not just the first one you find, including legacy/non-pool fallback code paths.
