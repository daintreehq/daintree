## Context

The `plugin://` custom scheme (mirroring `daintree-file://`) serves plugin static assets from disk. The handler in `electron/setup/protocols.ts` (`createPluginProtocolHandler`) maps `plugin://{pluginId}/{path}` to a plugin's installed root via `PluginService.getPluginDir`, then must serve only files that genuinely live under that root — defending against path traversal AND symlink escape from a renderer-controlled URL.

## Problem

A naive containment check — resolve `path.resolve(root, userPath)`, then `path.relative(root, candidate)` and reject `..` — looks correct but is unsound against symlinks. The candidate path is a _lexical_ construct; if any component (or the final file) is a symlink pointing outside the root, the lexical `path.relative` check passes while the actual read escapes (CVE-2025-53109 / -54794 class). A second, separate failure mode: a privileged scheme that is not declared in `protocol.registerSchemesAsPrivileged` before `app.whenReady()` is _silently_ downgraded — the `protocol.handle` call still succeeds, but the scheme loses `standard`/`secure`/`codeCache`/`corsEnabled` semantics with no error.

## Root cause

Containment is a two-stage TOCTOU problem:

1. **Lexical resolution is not real resolution.** `path.relative` operates on strings; it cannot see symlinks. You must call `fs.realpath` on BOTH the root and the candidate, then run the `path.relative(realRoot, realFile)` containment check on the resolved real paths (reject `rel === ".."`, `rel.startsWith(".." + path.sep)`, or `path.isAbsolute(rel)` — the `isAbsolute` branch catches Windows cross-drive `relative('D:\\','C:\\') === 'C:\\'`).
2. **realpath has its own TOCTOU window.** Between `fs.realpath(candidate)` and the actual `fs.open`, an attacker can swap the final component for a symlink. So the open must use `fs.open(candidatePath, O_RDONLY | O_NOFOLLOW)` on the _user-derived candidate path_ — NOT the realpath-resolved path — so a final-component symlink injected after realpath fails with `ELOOP` (mapped to 404). On Windows `O_NOFOLLOW` is `0` (no-op); realpath containment is the only line of defense there.

The `registerSchemesAsPrivileged` requirement is an Electron lifecycle constraint: the privileged-scheme table is frozen at `app.whenReady()`. Registration is split — the scheme privileges go in `main.ts` synchronously at module top-level, while the actual `protocol.handle` wiring happens inside `whenReady()`.

## Lesson

When writing a custom Electron protocol handler that serves files from disk:

- Declare the scheme in `protocol.registerSchemesAsPrivileged([...])` at module top-level (synchronously, before `whenReady`). Late registration fails silently, not loudly.
- Do NOT trust `path.relative`-based containment alone. Resolve symlinks with `fs.realpath(root)` and `fs.realpath(candidate)` first, run containment on the real paths, THEN `fs.open` the _candidate_ (not the realpath result) with `O_RDONLY | O_NOFOLLOW` to close the realpath→open swap window. Map `ELOOP`/`ENOENT`/`EISDIR` to 404, other errors to 500.
- Segment-scan for `..` (never `includes('..')` — see #4702), reject backslashes and null bytes, and decode `%2e%2e` before the scan. These are belt-and-suspenders; realpath+O_NOFOLLOW is the actual traversal defense.
- Set `Cross-Origin-Resource-Policy: cross-origin` (not `same-origin`) so COEP-isolated embedders can load the assets; leave `bypassCSP` off (#3757).
- Return identical 404s for unknown plugin id, disabled plugin, and missing file — don't leak path existence via distinct status codes.

## Applies when

- Adding or auditing a custom Electron scheme that serves files from disk (`protocol.handle`, `registerSchemesAsPrivileged`) in `electron/setup/protocols.ts` or `electron/main.ts`.
- Writing path-containment logic for renderer-controlled URLs or IPC file paths, especially where symlinks could escape a sandbox root (plugin roots, worktree dirs, daintree-file://).
- Diagnosing a custom scheme that loads but lacks `secure`/`standard`/CORS/codeCache behavior — check it's in `registerSchemesAsPrivileged` and registered before `app.whenReady()`.
- Reviewing any `path.relative(root, x).startsWith('..')` containment check — verify it runs on `fs.realpath` output and is backed by `O_NOFOLLOW`.
- Plugin asset loading, COEP/CORP header issues where plugin sub-resources are blocked with `ERR_BLOCKED_BY_RESPONSE`.
