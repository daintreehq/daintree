## Context

The empty-canvas launcher (`ContentGridEmptyState.tsx`) has a staggered fade+slide entry: each section carries the `launcher-section-enter` marker plus `motion-safe:animate-in`/`fade-in`/`slide-in-from-bottom-1`, with a `--tw-animation-delay` ladder (30-150ms) and `fill-mode-backwards` so a delayed section doesn't flash visible before its turn. It's DOM-entry motion: static classes that play once when a section mounts. A worktree switch remounts this component (free replay); a project switch does not — each project keeps its own persistent `WebContentsView` and React tree via `ProjectViewManager`, so switching just reveals an already-mounted subtree and nothing re-enters the DOM. Issue #11209 filed this gap: great on worktree switch, dead on project switch.

## Problem

The fix needed to replay a CSS animation on an already-mounted element from JS, triggered by the existing `app:view-revealed` signal (documented in `useClearSwitchBusyStateOnReveal.ts`, fired by main once the anti-flash bridge detaches). The obvious tool is the Web Animations API — `element.getAnimations()` then `.cancel()`/`.play()` on each. Written that way, the replay silently does nothing: `getAnimations()` returns an empty array for exactly the sections the replay targets, no error, no warning, launcher still doesn't animate on project switch.

## Root cause

Per the Web Animations spec, `getAnimations()` only returns animations that are "relevant" — current or in effect. An animation's effect is "in effect" after it finishes only if its fill mode extends forward (`forwards`/`both`) past the active interval's end; a `backwards`-only fill (used here to avoid the pre-delay flash) only extends _before_ the interval starts, never after. Once the entry animation finishes it drops out of "current" (no longer running) and out of "in effect" (fill doesn't cover the finished state) at the same moment — `getAnimations()` omits it entirely. `cancel()`/`play()` iterating that empty list is a silent no-op: nothing throws, nothing warns, and the animation most likely to have already finished by the time a user switches back (a 200ms fade with a 150ms max stagger) is precisely the one the API refuses to hand back.

The shipped fix is imperative CSS, not WAAPI: `replaySectionEntries()` walks `.launcher-section-enter` elements and does `element.style.animationName = "none"`, reads `element.offsetWidth` (forces a reflow so the teardown lands instead of collapsing with the next write into one style resolution), then `element.style.animationName = ""` to hand the animation back to the class, which re-reads `--tw-animation-delay` fresh. The PR also corrected a wrong hypothesis in the issue: #11209 speculated a cold-started (evicted) view's animation plays behind the anti-flash bridge and is spent before the user sees it. Investigation showed cold switches release the paint gate on a `skeleton-painted` event firing before the module even evaluates — the bridge detaches before hydration mounts the canvas, and cold views never receive `app:view-revealed` at all (only warm/cached reveals do). A cold entry does overlap that view's own startup-skeleton exit, but that's true of every cold boot — startup choreography, not the persistent-tree gap this PR closes, correctly left unfixed.

## Lesson

- **Never reach for `element.getAnimations()` + `cancel()`/`play()` to replay a finished CSS animation without checking its fill mode first.** A `fill-mode: backwards`-only animation (or `none`) drops out of the "relevant" set the instant it finishes; only `forwards`/`both` keeps it visible to `getAnimations()` after completion. Verify against the spec's "current or in effect" definition before trusting the API — the failure mode is a silent empty array, not an exception.
- **The imperative CSS restart recipe: clear `animationName` to `"none"`, force a reflow by reading a layout property (`offsetWidth`), then clear the override back to `""`.** Skipping the reflow read lets both style writes collapse into one resolution and the animation never restarts. Reuse this when WAAPI is unusable rather than re-deriving it.
- **CSS-only motion suppressors (`motion-safe:`, a `data-*` attribute read only by a media/attribute selector) don't protect a JS-driven replay.** `isMotionSuppressed()` restates the same triple check (`prefers-reduced-motion`, `data-reduce-animations`, `data-performance-mode`) `triggerPanelTransition` already makes, in JS, before calling `replaySectionEntries` — the CSS rules that normally flatten these animations to nothing can't intercept an imperative restart.
- **On a per-project persistent `WebContentsView` architecture, "switch" is not "remount."** Any entry/mount animation that looks right in manual testing (typically fresh mounts or worktree switches, which do remount) needs a second check against a project switch specifically — the component tree survives, nothing re-enters the DOM, and the animation is dead on that path until driven from a reveal signal like `app:view-revealed`.
- **When an issue's root-cause guess turns out wrong, say so explicitly in the fix rather than silently fixing something adjacent.** The issue guessed cold-view timing; the actual gap was warm-view remount-vs-reveal. Stating the wrong hypothesis (cold views never even receive `app:view-revealed`) stops a future agent from re-chasing the same dead end.

## Applies when

- Writing any "replay this CSS animation on an already-mounted element" logic — before reaching for `getAnimations()`, check whether the target animation uses `fill-mode: backwards` (or no forward-extending fill) and will therefore be invisible to WAAPI once finished.
- Touching `ContentGridEmptyState.tsx`, its `SECTION_ENTRY`/`SECTION_ENTRY_MARKER` constants, or `replaySectionEntries` — the marker class name is shared with a reduce-motion block in `index.css`, so renaming one means renaming both.
- Building entry/mount animations for content inside a per-project `WebContentsView` (`ProjectViewManager`) — test the project-switch (reveal-without-remount) path separately from any worktree-switch or fresh-mount path.
- Diagnosing "this animation plays once and never again" bugs where the element is being reused rather than recreated — suspect a `getAnimations()`-based restart silently matching nothing before suspecting the animation logic itself.
- Wiring new behavior off `app:view-revealed` (`window.electron.app.onViewRevealed`) — remember it only fires for warm/cached view reveals, never for cold-started views, which mount fresh instead.
