## Context

A warm project switch reactivates a cached `WebContentsView` behind the anti-flash bridge view, then wakes its terminals. On deactivation, `detachForProjectSwitch` parks each terminal offscreen and the view's PTY `MessagePort` is revoked; on reactivation, `activateProjectView` (`electron/ipc/handlers/projectCrud/switch.ts`) rebrokers a fresh port (`ptyClient.onProjectSwitch` + `distributePortsToView`) and the renderer runs `fullWakeForVisibilityRestore` per terminal. Same-day fixes #10159 and #10160 repaired three independent staleness mechanisms in this path.

## Problem

Two warm-switch symptoms (#10075, #10070): active-agent terminals looked frozen for several hundred ms after the swap — stuck on the wake-restored buffer snapshot — and terminals rendered at the default 80×24 grid, then snapped to full size (glaring in Codex TUIs). Both misled: the freeze looked like slow terminals (it was IPC handler ordering in Main), and the snap looked like one race (it was two separate geometry-bookkeeping holes).

## Root cause

Three mechanisms. (1) **Ordering** (#10159): `pvm.switchTo()` commits the visible swap first, but the handler then `await`ed `worktreeService.loadProject` — git prune, worktree list, status sync, LFS probe; hundreds of ms warm — _before_ the PTY block. Cached views need a fresh port (theirs was revoked at deactivation), so the already-visible view had no live terminal stream; new output queued in the headless mirror for the whole git load. The PTY work has zero data dependency on `loadProject` (PtyClient tracks its own per-window project context), and the legacy `ProjectSwitchService` had the correct order — the PVM rewrite silently inverted it. (2) **Coarse attach guard** (#10160): `fullWakeForVisibilityRestore` early-returned whole when `isAttaching`, deferring the _safe_ geometry sync (`applyDeferredResize` → only `terminal.resize()` + PTY IPC) together with the genuinely unsafe async wake (buffer restore races attach's post-rAF reconciliation, which calls `terminal.reset()`). The deferred re-run (`pendingVisibilityWake` → `notifyAttachSettledWaiters`) fires only after the bridge view has dropped — so the user watches the exact snap the bridge existed to hide. (3) **Dual geometry bookkeeping** (#10160): the background-tier resize path (ResizeObserver firing against a `content-visibility:hidden` container; cols/rows computed from cached cell metrics, `terminal.resize()` deliberately skipped) writes only `latestCols`/`latestRows`, never `targetCols`/`targetRows` — but the warm-attach resize consumes `targetCols`/`targetRows`. A terminal resized _only while backgrounded_ therefore reattaches targetless and paints 80×24. Fix: `detachForProjectSwitch` backfills targets from latest — only when targets are unset (never clobber an explicit `setTargetSize`) and `latestCols > 0` (a zero backfill would poison the cold-seed resize before `open()`).

## Lesson

- **Perceived warm-switch staleness is the gap between visible-swap commit and data-path restoration, not total switch time.** Anything the now-visible view needs to be live (ports, streams) must run before any slow await; #10965 later pushed further and starts `loadProject` concurrently with the swap itself. When a rewrite replaces a legacy path (`ProjectSwitchService` → PVM), diff the _operation order_, not just the operations — legacy ordering encodes past fixes.
- **Hoisting best-effort work above a critical await demands a try/catch.** The rebroker moved before `loadProject`; an uncaught throw there would now skip the load and leave `windowToProject` stale (cross-project IPC contamination). Reordering changed the PTY block's blast radius, so the PR wrapped it.
- **Split composite wake/restore operations by mid-attach safety instead of guarding them whole.** `terminal.resize()` is attach-safe; anything touching `terminal.reset()`/buffer restore is not. Deferring the safe half alongside the unsafe half converts a race guard into a visible glitch whenever the deferral outlives the occlusion window. Caveat: "resize is always safe" was later qualified — #10863 added `deferGridChangeForStream` because a grid-_changing_ resize re-wraps committed scrollback under a still-streaming Ink-style CLI.
- **Set the deferred-re-run flag before fallible work.** `pendingVisibilityWake = current.isAttaching === true` is assigned _before_ the geometry-sync block so a throw (terminal disposed mid-wake) can't strand the re-run; the proceed path clears it after the guard.
- **Any resize path that updates `latestCols/Rows` without `targetCols/Rows` (or vice versa) creates the reattach-at-80×24 bug class.** Seed the missing half at the lifecycle boundary that knows a warm reattach is coming (`detachForProjectSwitch`), guarded unset-only and non-zero. Audit this pair whenever adding a resize tier or deferral.
- Code moved since: `fullWakeForVisibilityRestore` now lives in `src/services/terminal/TerminalRevealController.ts` (TIS delegates); the target-backfill is still in `TerminalInstanceService.detachForProjectSwitch` (~line 1631); the #10159 comment block survives in `switch.ts` (~line 459) above the now-concurrent load settle.

## Applies when

- Touching `activateProjectView` / `electron/ipc/handlers/projectCrud/switch.ts` — adding steps to the switch sequence, or reordering anything around the `loadWorktrees` await or the PTY rebroker block.
- Diagnosing "terminals frozen/stale for a moment after switching projects" or any render-small-then-snap / 80×24 flash on warm reactivation, dock restore, or panel reattach.
- Modifying `fullWakeForVisibilityRestore`, `notifyAttachSettledWaiters`, `applyDeferredResize`, or any `isAttaching`-guarded path in `TerminalRevealController` / `TerminalInstanceService`.
- Adding or changing a resize path in `TerminalResizeController` — check which of `latestCols/Rows` vs `targetCols/Rows` it writes and which consumer reads the other.
- Assuming an early-return guard that defers "the whole wake" is free because a deferred re-run exists — the re-run may land after the occlusion window that hid the glitch.
