## Context

A panel's on-disk identity travels through a long pipeline before it can affect a restored terminal: renderer state -> `panelToSnapshot` (base fields) or a per-kind `serialize()` (`src/panels/terminal/serializer.ts`) -> `PanelSnapshot` JSON on disk -> `statePatcher.ts`'s `buildArgsFor*` family on load -> an IPC spawn/reconnect call -> the pty-host's own `TerminalProcess`/`terminalInfo.ts` records, which get mapped back out through snapshot/reconnect handlers on the next save. #10927 (launch `env`, issue #10922) and #10929 (`titleMode`, issue #10738) each added a new field that had to survive that entire round trip.

## Problem

Two independent symptoms from the same shape of bug. #10922: a terminal launched via a Z.AI/GLM preset resumed on default Anthropic and silently fell back to `opus` after an app restart — the saved session file still said `glm-5.2`, but Claude Code couldn't honor it. #10738: a preset-branded title like `Claude [Z.ai]` reverted to bare `Claude` after restart. Both looked like restore/hydration bugs in isolation; both were actually "a field never made it across one of five hops."

## Root cause

For `env`: the launch environment was resolved once at spawn time (preset + recipe + caller layers merged) and only ever used, never stored — `serializer.ts` persisted `command`, `agentSessionId`, `agentPresetId`, but not `env`. On restore, `buildArgsForRespawn` tried to _re-derive_ the env from `saved.agentPresetId` via `getMergedPreset`, which can't reproduce a recipe's inline env and comes up empty for a stale/deleted/not-yet-loaded preset — re-deriving from an id is not the same as persisting the resolved value.

For `titleMode`, the drop was four separate points, each independently plausible: `panelToSnapshot` never included it in `BASE_PANEL_FIELDS`; `statePatcher.ts`'s `SavedTerminalData`/`buildArgsForRespawn` never read it back; `TerminalProcess.ts` seeded it with `options.title ? "default" : "default"` — a ternary whose both branches are the same value, so it was silently always `"default"` regardless of intent; and the backend's own snapshot/reconnect handlers (`electron/ipc/handlers/terminal/snapshots.ts`, `electron/pty-host/handlers/terminalInfo.ts`'s `mapTerminalInfo`) never forwarded it across the pty-host/renderer process boundary. Any one alone would not have fixed the bug.

The two fixes land at different guard strengths. #10927 added `env` to `PTY_FIELD_CLASSIFICATION` in `src/panels/__tests__/registry.fieldcoverage.test.ts`, typed `as const satisfies Record<keyof PtySerializeInput, boolean>` — a compile-time exhaustiveness check: add a field to `PtyPanelData` and the build fails until you classify it persisted or runtime-only. `BASE_PANEL_FIELDS` in `panelPersistence.ts` (where `titleMode` lives) has no equivalent: it's `as const satisfies readonly (keyof PanelSnapshot)[]`, which only catches _deletions_ — the code's own comment admits it ("does NOT catch new keys added to PanelSnapshot; a reviewer must ensure new base fields... are listed here"). That gap is exactly how `titleMode` was dropped, and it is still open today for the next base field.

## Lesson

- **Persist a spawn-time-resolved value (merged env, a computed default) as the resolved value itself, not the id that produced it** — a preset/recipe id can go stale, be deleted, or not yet be loaded, and re-derivation silently comes up empty in exactly those cases. Prefer the saved value over live re-resolution (`sanitizeAgentEnv(saved.env) ?? presetEnv`), falling back to live resolution only for legacy snapshots predating the field.
- **Trace a new panel field through all five hops before calling it wired: per-kind serializer, `statePatcher.ts`'s `SavedTerminalData` + every `buildArgsFor*` (`buildArgsForBackendTerminal`, `buildArgsForReconnectedFallback`, `buildArgsForRespawn`, `buildArgsForNonPtyRecreation`), the spawn options type, the pty-host's own record, and the backend mapping (`mapTerminalInfo`) that reports it back out.** A field present in 4 of 5 layers still silently vanishes.
- **A ternary with identical branches (`x ? "default" : "default"`) is a silent bug, not dead code** — it means the field was never actually threaded through, and nothing catches it because both paths type-check. Grep for this shape when hunting a "field X is never anything but its default" symptom.
- **When a value that used to be transient-only becomes persisted, re-check whether it can now leak a secret onto disk** — #10927 also had to carry `excludeFromPersistence`/`removeOnExit` through the "Run anyway" relaunch path in `TerminalPane.tsx` specifically because env now persists. Sanitize with the same function on both write (`serializer.ts`) and read (`statePatcher.ts`), since the on-disk snapshot is untrusted input on the way back in too.
- **A field on `PtyPanelData` forces classification in `PTY_FIELD_CLASSIFICATION` at compile time (trust that gate); a field on `BasePanelData`/`PanelSnapshot` does not** — `BASE_PANEL_FIELDS` in `panelPersistence.ts` only catches deletions, so a new base field silently never persists unless a reviewer manually adds it, exactly as `titleMode` did.

## Applies when

- Adding a field to `PtyPanelData`, `BasePanelData`, or `PanelSnapshot` that must survive an app restart or project-view reconnect.
- Diagnosing "a setting/preset/env reverts to default after restart" — check every hop before assuming the restore logic itself is wrong.
- Touching `panelPersistence.ts`, `src/panels/terminal/serializer.ts`, or `statePatcher.ts` — these plus the pty-host's `terminalInfo.ts`/snapshot handlers are one coupled pipeline, not independent layers.
- Reviewing a new persisted field added to a per-kind serializer only, or to `statePatcher.ts` only — write, read, and backend mapping are all required.
