## Context

`src/App.tsx` always-mounts ~10 lazy dialog hosts (`GitPushConfirmDialog`, `GitPullRebaseConfirmDialog`, `PanelLimitConfirmDialog`, `RecipeConflictDialog`, `McpConfirmDialog`, `PluginConfirmDialog`, `PluginMcpConfirmDialog`, `DiagnosticsReviewDialogHost`, `TerminalInfoDialogHost`, and formerly `FileViewerModalHost`). Each was wrapped in `ErrorBoundary variant="component"` with `resetKeys={[Number(isStateLoaded)]}` — the boundaries were added under issue #7906 (unguarded overlay crashes escalating to the fullscreen boundary), which flagged that reset keys are load-bearing. Open/close-cycled overlays got `[Number(isOpen)]`; the always-mounted hosts got a constant. Several of these hosts are deferred-promise dialogs: their store's `requestConfirmation` parks a `resolve` and returns a Promise that only settles through the dialog's own buttons — no timeout (`gitPushConfirmStore.ts`).

## Problem

A single render error inside any of these hosts left it dead for the rest of the session, and the failure was invisible. After such a crash, every subsequent `git.push` / pull-rebase / panel-limit / MCP-confirm parked a Promise in its store that no UI would ever resolve — the action just silently never completed. No error, no toast, no thrown exception: the push simply doesn't happen. The user's only "recovery" (the boundary's "Try again" button) was itself unreachable.

## Root cause

Two mechanisms compound. First, `react-error-boundary`-style reset: `ErrorBoundary.componentDidUpdate` (`src/components/ErrorBoundary/ErrorBoundary.tsx`) only calls `resetError()` when `resetKeys` **change** (length-or-index shallow compare). `isStateLoaded` flips `false→true` once at hydration and stays true forever, so `[Number(isStateLoaded)]` is `[1]` for the entire session and can never trigger a reset. The same trap bites any boolean-derived key: `[Number(isOpen)]` on `TerminalInfoDialogHost` stays `[1]` across repeated opens while the dialog is already open, and `[Number(fileView != null)]` likewise — so a crash during one open never clears on the next.

Second, the recovery UI is off-screen: the `component`-variant fallback renders below `AppLayout`'s `h-screen` container under `html,body,#root { overflow: hidden }`, so its "Try again" button sits outside the viewport. Auto-reset via `resetKeys` was the _only_ viable recovery path, and it was wired to a constant. The deferred-promise stores made the blast radius silent rather than cosmetic — a dialog host is the _only_ code that resolves those parked promises, so a dead host converts every later action into a leaked promise.

## Lesson

- **Never derive an ErrorBoundary reset key from a one-way or steady-state boolean.** `Number(isStateLoaded)`, `Number(isOpen)`, `Number(x != null)` all collapse to a constant once the boolean settles, and `componentDidUpdate` resets _only on change_ — so a crashed boundary is permanently dead. The key must track the _pending-request_ signal, not a lifecycle flag.
- **For deferred-promise dialog stores, expose a monotonic `requestSeq` and bump it atomically with the pending payload in the same functional `set` updater** — e.g. `set((state) => ({ pendingConfirm: {...}, requestSeq: state.requestSeq + 1 }))` (`gitPushConfirmStore`, `gitPullRebaseConfirmStore`, `panelLimitStore`, `recipeConflictStore`, `diagnosticsReviewStore`). A counter (not a derived key like `` `${panelCount}-${memoryMB}` ``) is required because back-to-back supersede replaces `pendingConfirm` without returning to `null`, and the batch-preflight path passes identical params (`memoryMB: null`) every time — a value-derived key wouldn't change, so the boundary would stay stuck.
- **`requestSeq` is transient runtime state — exclude it (and `pendingConfirm`) from the store's `partialize`.** `panelLimitStore.ts` deliberately keeps it out of the persisted slice; a persisted reset counter is meaningless and would rehydrate stale.
- **Match the key shape to the store shape:** FIFO-queue dialog stores (`mcp`, `plugin`, `pluginMcp`) key off the live `current?.requestId` UUID (`pluginArchiveInstall` off `current?.intentId`); event-driven hosts holding no store state (`terminal-info`) increment a local `useState` counter per open event. Inner boundaries inside the dialog components need the same signal, not just the outer host in `App.tsx`.
- **A silent-failure boundary needs a reachable recovery path OR guaranteed auto-reset — verify at least one exists.** The `component`-variant fallback here renders below the `h-screen` `overflow:hidden` layout and is invisible, so auto-reset was the sole recovery. When a boundary wraps a promise-resolving host, a crash isn't cosmetic — it silently strands every future action; treat the reset key as a correctness invariant, not polish.

## Applies when

- Adding a new always-mounted dialog host in `src/App.tsx` — wire its reset key into `src/hooks/app/useModalResetKeys.ts`, the canonical home the PR's inline logic was later extracted into (extended since to `pluginCapabilityConfirm`/`pluginArchiveInstall`; the retired `fileViewer` host became the `FilePane` panel kind).
- Writing `resetKeys` for any `ErrorBoundary` — audit that the key actually _changes_ on the recovery trigger; a boolean/steady-state derived key is a silent no-op reset.
- Building a deferred-promise confirm store (`requestConfirmation` returns a Promise resolved only by dialog buttons, no timeout) — a render crash in its host strands every subsequent call; give the store a monotonic `requestSeq`.
- Diagnosing "git push / a confirm action silently does nothing, no error, no toast" — suspect a crashed dialog host whose boundary can't reset, not the action pipeline.
- Reviewing any `ErrorBoundary variant="component"` fallback in the app frame — confirm the fallback is actually on-screen given `h-screen` + `overflow:hidden`, or that `resetKeys` guarantee auto-recovery.
