## Context

Terminal output flows host→renderer over a MessagePort under flow control. The renderer keeps a per-terminal FIFO of the ORIGINAL pty-host byte counts for each queued chunk (`pendingPortAckBytes` in `src/clients/terminalClient.ts`); `acknowledgePortData` acks those exact counts back after xterm consumes each chunk. The pty-host mirrors this as `queuedBytes` per terminal (`electron/pty-host/ipcQueue.ts`, `portQueue.ts`); a terminal pauses when its queue crosses a watermark and resumes as acks call `removeBytes` to drain `queuedBytes` below the low watermark. #10305 (with siblings #10268/#10286) hardened this ledger for the then-live hibernate/wake path.

## Problem

Across teardown cycles the backpressure pause stopped resuming promptly: a torn-down/backgrounded terminal sat paused until its 10-second safety timeout instead of resuming the instant acks arrived, and the deficit grew each cycle (#9910). The symptom read as a pause/resume bug, not a phantom accounting entry teardown had left stranded — the pause machinery was fine; the ledger it read was permanently wrong.

## Root cause

The ledger is STRICT two-sided accounting: every byte the host adds to `queuedBytes` must eventually be removed by a matching renderer ack (`removeBytes`). When the renderer drops queued port chunks WITHOUT acking them — a renderer-side destroy that never went through `kill` (project close, LRU eviction of an exited terminal) — the host counts those bytes as in flight, forever. The per-terminal deficit never clears, so that terminal's `queuedBytes` stays above the low watermark and every future pause can only be released by the `BACKPRESSURE_SAFETY_TIMEOUT_MS = 10000` (10s) force-resume, never by a normal ack-driven resume. The fix is `terminalClient.discardPortAcks(id)`: drain the whole FIFO as ONE batched ack on the destroy path (`TerminalInstanceService.ts` destroy); the FIFO entry is always deleted even when the port is gone or `postMessage` throws, or stale counts re-sum into a phantom ack on the next discard. The asymmetry is the point: `kill`/`gracefulKill`/`trash` just `delete` the FIFO with NO ack, because the host terminal (and its `queuedBytes`) dies too — no surviving ledger to reconcile.

The sibling PRs patched the same then-live hibernate/wake subsystem, now DEAD CODE: #10811 (`eb9cd64a7`) removed all per-terminal hibernation (`TerminalHibernationManager`, `TerminalWakeManager`, the wake-serialize handler) — suspend-then-resync was the root cause of the agent-TUI corruption class (#10805/#10807). #10305's "skip the flush after a replayed snapshot" half (and #10286's `pendingWrites`-guard) died with it; only the ledger-ack half survived, repurposed from wake to destroy/eviction — it endured because it is a general renderer↔host invariant, not a hibernation feature.

## Lesson

- **Any renderer-side teardown where the pty-host terminal OUTLIVES the renderer instance must settle its held byte ledger before wiping local queues.** Discriminator is host survival: host dies too (`kill`/`gracefulKill`/`trash`) → just `delete` the FIFO; host survives (`destroy` on project close / LRU evict of an exited pane) → `discardPortAcks` to batch-ack, or `queuedBytes` deficits permanently.
- **A stranded per-terminal `queuedBytes` deficit is silent and cumulative — it never errors, it just degrades every future pause on that terminal to the 10s `BACKPRESSURE_SAFETY_TIMEOUT_MS` force-resume.** Diagnosing "pauses take ~10s to clear" / "resume feels laggy after backgrounding" → suspect an unacked drop on a teardown path before touching watermark/resume logic.
- **Ack the host's original byte counts, never the renderer's string length.** `pendingPortAckBytes` stores host byte counts per chunk; `discardPortAcks`/`acknowledgePortData` sum those, because UTF-8 host bytes ≠ UTF-16 renderer chars and `removeBytes` accounts in host bytes. A length-based ack silently mis-counts and re-strands the ledger.
- **xterm 6 has NO disposed-instance guard in `_innerWrite`** — a `Terminal.dispose()` while writes are queued in its `WriteBuffer` silently drops the pending write callbacks with no error (the #10286 finding, still true of the pinned xterm). Any counter tracking in-flight writes across a dispose (`pendingWrites`, still in `TerminalWriteController`) gets stranded; reset it on teardown/restart, don't assume dispose settles it.
- **In any pause→serialize→resume block, put the resume in a `finally`** (the #10268 pattern) so the unblock fires even if serialization throws; a resume-before-serialize leaks live bytes into both the snapshot and the port queue, double-painting.

## Applies when

- Adding or reviewing a terminal teardown path (`TerminalInstanceService` destroy, project close, LRU eviction, `kill`/`gracefulKill`/`trash`), or touching the flow-control ledger (`pendingPortAckBytes` / `discardPortAcks` / `acknowledgePortData` in `terminalClient.ts`; `queuedBytes` / `removeBytes` in `ipcQueue.ts` / `portQueue.ts`) — decide ack-vs-delete by whether the pty-host terminal survives the renderer instance.
- Diagnosing terminals that stay paused ~10s (`BACKPRESSURE_SAFETY_TIMEOUT_MS`) instead of resuming on ack, or a per-terminal deficit growing across background/teardown cycles.
- Disposing an xterm `Terminal` while writes may be queued, or maintaining an in-flight-write counter (`pendingWrites`) across dispose/restart.
- Reading dead references to `TerminalHibernationManager` / `TerminalWakeManager` / a `backpressure.ts` wake-serialize handler — removed by #10811; only this arc's byte-ledger still lives.
