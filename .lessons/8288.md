## Context

The GitHub services (`GitHubAuth`, `gitHubRateLimitService`, `gitHubTokenHealthService`, etc.) were rehomed from `electron/services/github/` into a built-in plugin at `plugins/builtin/github/main/`, exposed through the `ForgeProviderImpl` forge-provider contract. `PluginService.loadPlugin` loads the plugin's compiled entry (`dist-electron/plugins/builtin/github/main/index.js`) at runtime. At the time, compat shims at the old `electron/services/github/*` paths re-exported from the plugin to keep `window.electron.github.*` IPC handlers working during the staged cutover — that shim (`electron/services/github/index.ts`) and the `window.electron.github.*` namespace it backed have since been removed once the forge-neutral cutover completed (#8063 lineage); GitHub is now reached purely through the forge-provider abstraction, with no main-process re-export of the plugin's singletons.

## Problem

Two failure modes appear the moment a runtime-loaded plugin and the main bundle both reference the same module-level singletons:

1. If the plugin entry is bundled in a _separate_ esbuild run from the main process, each bundle inlines its own copy of `GitHubAuth`/rate-limit/token-health singletons. The IPC shim mutates one instance; the forge provider reads another. State silently diverges.
2. If the plugin is loaded from a directory that is _not_ where its shared chunks live, the bundled output's relative `import` paths (`../chunks/...`) strand. The plugin descriptor registers but the implementation never binds — a silent registration gap, not a crash.

## Root cause

esbuild only dedupes a shared module into a single chunk when all consumers are entry points of the **same build with `splitting: true`**. PR #8288 added `plugins/builtin/github/main/index.ts` to the existing ESM `entryPoints` array and switched `outdir` to `dist-electron` with `outbase: "."` and `chunkNames: "electron/chunks/[name]-[hash]"`, so the plugin entry and the main/host entries emit into one chunk graph — the singletons become one shared chunk both sides reference. At the time, identity held only because the compat shim's target (`plugins/builtin/github/main/index.ts`) participated in the same build; the shim itself (`electron/services/github/index.ts`, `export * from "../../../plugins/builtin/github/main/index.js"`) is gone now that the cutover is done, but the shared-build requirement it depended on is still enforced today for every built-in plugin: `scripts/build-main.mjs`'s `discoverBuiltInPluginMainEntries()` walks `plugins/builtin/*/main/index.ts` and splices all of them into the same `entryPoints` array PR #8288 hand-edited, so any future plugin needing singleton identity with the host (or with another builtin) gets it for free, with no build-config edit.

The load-path half: `PluginService.getBuiltinDir()` returns `path.join(app.getAppPath(), "dist-electron", "plugins", "builtin")` for **both** dev and packaged modes. Inside a packaged app this resolves to `app.asar/dist-electron/plugins/builtin`, which sits next to `dist-electron/electron/chunks/` — so the plugin's chunk-relative imports resolve. Copying the plugin into `Resources/plugins/builtin/` (the intuitive packaging move) would strand those relative chunk references. The manifest (`plugin.json`) is _not_ emitted by esbuild, so `copyBuiltInPluginManifests()` mirrors it next to the compiled entry, and the prod-clean step now wipes `dist-electron/plugins` too so a renamed/removed contribution can't survive between builds.

## Lesson

- When a runtime-loaded built-in plugin shares module-level singletons with the main process (directly or via a compat shim re-export), the plugin entry MUST be an entry point in the **same esbuild build** with `splitting: true`. A second build run produces duplicate singleton instances with silently diverging state — no error, no type failure.
- The plugin must load from the directory that holds its emitted shared chunks. Use one path for dev and packaged (`app.getAppPath()/dist-electron/plugins/builtin`) so chunk-relative imports stay honest inside `app.asar`. Do NOT copy built-in plugins into `Resources/` — it strands the relative chunk refs and yields a registered-descriptor / unbound-impl gap that no test catches unless you assert the impl is actually invoked.
- esbuild emits JS but not static assets: any `plugin.json`/manifest must be copied alongside the compiled entry separately, and the production clean step must wipe the plugin output dir, not just the electron dir.
- A compat shim (`export * from "<plugin>/index.js"`) is a legitimate non-breaking cutover tool, but it only preserves singleton identity because of the shared-build invariant above — treat the build wiring as load-bearing, not incidental.

## Applies when

- Adding a new built-in plugin under `plugins/builtin/*` that exposes services consumed by the electron main process or other hosts.
- Touching `scripts/build-main.mjs` esbuild config — changing `entryPoints`, `outdir`, `outbase`, `splitting`, or `chunkNames` for the ESM bundle.
- Modifying `PluginService.getBuiltinDir()` or any plugin load-path / packaging logic; debugging why a built-in plugin descriptor registers but its forge provider / service is never bound.
- Investigating divergent state between two consumers that both appear to hold "the same" module-level singleton but don't — the `window.electron.github.*` / forge-provider split this lesson originated from is gone now that the compat shim and its IPC namespace were removed post-cutover, but the same silent-divergence failure mode recurs any time a host process and a plugin entry both reference a singleton without sharing a build.
- Adding compat shims that re-export from a rehomed module path, or removing them after the consumer migration lands — the shim this lesson describes (`electron/services/github/index.ts`) has already been removed (#8063 lineage complete), so treat that as the worked example of the removal step, not an open TODO.
- Any packaging change that moves plugin output between `dist-electron/` and `Resources/` inside `app.asar`.
