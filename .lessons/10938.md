## Context

`toolbarPreferencesStore.ts` persists the toolbar's button layout (`layout.leftButtons` / `rightButtons`, an ordered array of button ids) through Zustand's `persist` middleware, with a per-version `migrate()` chain and a `merge()` that runs `mergeButtonList` on every hydration to reconcile the persisted list against the current default set. `Toolbar.tsx` renders one pill per array entry with no dedup at the render layer.

## Problem

In dev mode the forge status pills (issues/PRs/commits) rendered two or three times, stacked as separate sibling pill groups a few px apart — easy to misread as a rendering or view-compositing bug. Issue #10806 had in fact previously diagnosed an earlier instance of this exact symptom (two side-by-side forge toolbars) as an orphaned `ProjectViewManager` `WebContentsView` from rapid project-switching; #10938's root-cause work makes it plausible that was the same bug at 2x, not the view-layer theory that shipped.

## Root cause

Two independent mechanisms compound instead of canceling out. First, the v10 `renameForgeStats` migration — added by #10347's forge-neutral rename (`github-stats` → `forge-stats`) — renamed the id with a plain `.map()` and no dedup — unlike the v3 `renameAgentSetup` migration directly above it in the same file, which sets the precedent by deduping with `Array.from(new Set(...))` specifically to avoid duplicate React keys. Second, `mergeButtonList` re-inserts any id that is "missing" from the persisted list but present in the current defaults — so whenever a stale/older dev build (an old worktree, a bisect checkout, a pre-rename branch) hydrates the shared `daintree-dev` profile (set once in `bootstrap.ts` via `app.setPath("userData", "daintree-dev")`), its old-schema defaults still contain `github-stats`, which the old build's `merge()` sees as missing and re-inserts next to the already-renamed `forge-stats`. Switch back to a `develop` build and the v10 migration renames that reinserted `github-stats` into a second `forge-stats`. Every old-build/new-build round-trip on the shared profile mints another copy, and since the render layer maps one pill per array entry, N copies means N stacked pill groups. Production never hits this: it uses a separate profile only touched by builds `>=v0.19`, so the old-schema writer that drives the reinsertion never runs — which is also why the bug was invisible outside dev-mode multi-branch testing.

## Lesson

- **Every rename/collapse migration on a persisted array must dedup, not just remap.** A bare `.map()` that renames `id-a` to `id-b` silently produces a duplicate the instant the array already contains `id-b` from a previous migration or write. Check the file for a precedent (here, v3's `Array.from(new Set(renamed))`) before assuming a plain map is safe.
- **A "reinsert missing defaults" merge path is a duplicate-minting engine when the input can regress to an older schema.** `mergeButtonList` re-adds ids present in defaults but absent from the persisted list — correct for genuinely new buttons, but it cannot tell "new button never seen" apart from "old id not yet renamed by this build," so a downgrade-then-upgrade cycle re-triggers the rename against a list that already has the target id.
- **Dev builds sharing one profile (`daintree-dev`) across branches/worktrees is a real hydration-mixing vector, not a hypothetical.** Any store with versioned migrations should assume its dev-mode persisted blob can be written by both older and newer schema versions in the same session; production's per-release profile does not have this exposure, so a dev-only symptom does not mean a low-priority bug.
- **Put the durable guard in the version-independent path, not just the migration.** #10938 layered three defenses in order of durability: `sanitizeButtonList` deduping on every `merge()` (runs on every load, catches blobs already stamped with the current version), a one-time v11 migration as an explicit repair matching the file's per-version convention, and a final dedup at the render boundary (`effectiveLeftButtons`/`effectiveRightButtons` in `Toolbar.tsx`) as belt-and-suspenders. The migration alone would miss a blob already stamped with the current version but still carrying duplicates from before the fix shipped.
- **A render layer that maps one visual element per array entry with no dedup will faithfully display any upstream data bug as a visible artifact.** The toolbar wasn't wrong — it rendered exactly what was in the array. Don't assume a duplicated visual means a duplicated mount/view; check the backing collection for the duplicate first.
- **Revisit old bug diagnoses when a new mechanism explains the same symptom more directly.** #10806's orphaned-`WebContentsView` theory required no `ProjectViewManager` change to fix #10938's occurrence of the same visual bug — evidence the view-layer theory was likely a misdiagnosis of this migration bug, not a separate confirmed root cause.

## Applies when

- Writing or reviewing any `migrate()` step in a Zustand `persist` store that renames, merges, or collapses ids in a persisted array — grep the file for prior rename migrations and match their dedup convention.
- Touching `mergeButtonList` / `sanitizeButtonList` in `src/store/toolbarPreferencesStore.ts`, or any similar "merge persisted list with current defaults" helper elsewhere in the ~100-store Zustand layer.
- Diagnosing a UI element (pill, badge, button, tab) that renders duplicated or stacked in dev mode but not production — check the persisted store state (`localStorage.getItem(...)`) for repeated ids before suspecting the view/mount layer.
- Debugging with multiple worktrees/branches/bisect checkouts that all run in dev mode and share the `daintree-dev` userData profile — expect old-schema writes to resurface and interact with newer migrations.
- Reopening a closed issue whose fix theory didn't require touching the code its diagnosis pointed at — that's a signal (as with #10806's orphaned-view theory here) the original root cause may have been wrong.
