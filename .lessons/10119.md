## Context

Exit cleanliness is read on the next boot from three persisted markers, written in `electron/lifecycle/shutdown.ts` after the graceful cleanup chain settles: `getCrashRecoveryService().cleanupOnExit()` (removes `running.lock`), `getCrashLoopGuard().markCleanExit()` (`crash-loop-state.json`), and `getPanelSuspectLedger().markCleanLaunch()` (suspect decay counters). `GpuCrashMonitorService` mitigates GPU-process crash loops by escalating through ANGLE fallback → nuclear GPU disable, each tier ending in either `app.relaunch() + app.exit(0)` or a crash-loop hard-stop `app.exit(0)` — four exit sites total.

## Problem

After a GPU-mitigation relaunch — a deliberate, controlled restart — the next boot showed a stale crash-recovery dialog, classified the session as `native-crash`, and added a crash-loop guard strike. Enough GPU escalations in a row could walk an otherwise healthy install toward safe mode. The exit code was 0 and the restart was intentional, which is exactly why it looked correct in review: nothing about the call site suggests a crash.

## Root cause

Electron's `app.exit()` terminates immediately without emitting `before-quit`/`will-quit`, so the shutdown chain that writes the marker trio never runs. Crash detection has no concept of intent — it only reads state on disk. A leftover `running.lock` means "crashed", `cleanExit: false` in `crash-loop-state.json` means "strike", and the suspect ledger never advances its decay. Any exit path that bypasses the graceful chain must therefore make the disk lie of a crash impossible by writing the trio itself. This is a recurring cross-cutting invariant, not a one-off: the AutoUpdater had the identical bug (#9638, "Auto-update relaunch is treated as a crash") before this PR hit the GPU monitor.

The fix is a file-local `writeCleanGpuMitigationMarkers()` wired into all four exit sites, replicating the `shutdown.ts` order (`cleanupOnExit` → `markCleanExit` → `markCleanLaunch`), each call in its own try/catch so one failure can't skip the next, and every write synchronous (`writeFileSync`) so it commits before `app.relaunch()`/`app.exit(0)`. Markers go BEFORE the awaited `closeTelemetry()` — a telemetry rejection or hang must never gate marker cleanup (lesson #7158) — and `closeTelemetry()` itself got try/catch on the hard-stop branches since a rejection there would skip `app.exit(0)` and hang the process. Tests lock the ordering with `mock.invocationCallOrder` assertions so a refactor can't silently invert markers-before-exit.

## Lesson

- **Every `app.relaunch()`/`app.exit()` call site in Main is a crash-classification hazard.** `app.exit()` skips `before-quit`, so either route the exit through the coordinated shutdown (`electron/lifecycle/shutdownCoordinator.ts` — how the AutoUpdater does it today) or write the trio at the site (`cleanupOnExit` → `markCleanExit` → `markCleanLaunch`, in `shutdown.ts` order). When adding any new self-restart path, grep existing `app.exit(` callers and copy `writeCleanGpuMitigationMarkers` or the shutdown-coordinator route.
- **"Intentional" lives only in the code's head — crash detection reads disk.** A restart with exit code 0 still books as a crash if the markers are missing. Symptom signature: stale recovery dialog + `native-crash` classification + a crash-loop strike immediately after a deliberate restart.
- **Marker writes must be mutually isolated and synchronous.** Independent try/catch per marker (one throw can't skip the rest), `writeFileSync` so nothing races the process teardown, and the exit still proceeds if every write fails — never let cleanliness bookkeeping block the restart itself.
- **Markers before best-effort teardown.** Awaiting `closeTelemetry()` before the markers puts an async rejection between intent and disk state; the shutdown.ts invariant is markers first, telemetry after, telemetry failure logged and swallowed.
- **Assert ordering in tests with `invocationCallOrder`,** not just call counts — the bug class here is sequencing (markers vs `relaunch()` vs `exit(0)`), which `toHaveBeenCalled` can't see.

## Applies when

- Adding or reviewing any `app.relaunch()`, `app.exit()`, or self-restart path in the Main process — GPU mitigation, updater, safe-mode toggles, migration restarts.
- Debugging "crash dialog appears after an update / GPU fallback / deliberate restart" or unexplained crash-loop strikes with exit code 0.
- Touching `GpuCrashMonitorService` escalation tiers, `shutdown.ts` marker order, or `shutdownCoordinator.ts` routing.
- Tempted to treat a clean exit code as sufficient — cleanliness is the marker trio on disk, not the exit code.
- Writing tests for exit paths — sequencing assertions (`invocationCallOrder`) are the load-bearing part, not call presence.
