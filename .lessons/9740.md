## Context

`RepoFetchCoordinator` (workspace-host) serializes background `git fetch` per repo commondir so sibling worktrees don't race on `packed-refs.lock`. When a fetch failed with an auth-classified error it suspended fetching for the whole repo with `AUTH_FAILURE_TTL_MS = Number.POSITIVE_INFINITY` — a fail-closed policy justified by fear of storming GitHub's secondary rate limits with repeated bad-token attempts (the quota-protection posture from #9440/#9077). The suspension state is per-commondir, and `WorkspaceService` mirrors it onto every sibling monitor, so `UpstreamSyncBadge` painted a "GitHub authentication failed" stripe on every worktree card of the project at once.

## Problem

One transient background-fetch failure left the stripe stuck on every card indefinitely — even when credentials were fine and `git fetch` worked from a terminal — with "last fetched 2 days ago" counts (#9736). Clicking the stripe only opened the GitHub settings tab; nothing cleared the suspension short of re-saving the token, an OS sleep/wake, or an app restart. #9740 wired the click to a new `worktree:retry-auth-fetch` IPC path (`WorkspaceService.retryAuthFetch`: `clearAuthFailures()` then `triggerFetchNow()` on running monitors only) but deliberately kept the TTL infinite, shipping only half of what #9736 asked for. Two weeks later #10670 was refiled against the identical symptom: users never click the badge, so the manual escape hatch unstuck nobody.

## Root cause

The infinite suspension conflated three failure classes because `classifyGitError` (`shared/utils/gitOperationErrors.ts`) bucketed them all as `auth-failed`: (1) a genuinely broken/revoked token; (2) GitHub secondary rate limiting, which returns HTTP 403 on the exact same `unable to access ...: The requested URL returned error: 403` line; (3) transient credential-helper hiccups — background fetches run with `GIT_ASKPASS=true` / `GIT_TERMINAL_PROMPT=0`, so a momentary keychain stall surfaces as `could not read Username for`. The "never auto-retry auth" safety rationale applies to none of the transient cases, and even a real broken token tolerates slow retries — hourly polling is nowhere near secondary-rate-limit territory. The permanent policy was compensating for a too-broad trigger bucket.

#10675 reversed the policy by fixing the bucket first: a new `rate-limited` `GitOperationReason` matched BEFORE `auth-failed` (same 403 line plus a `secondary rate limit` sideband; a code comment + a "prefers rate-limited over auth-failed" test guard the ordering) with its own long-but-finite window (`RATE_LIMIT_FAILURE_TTL_MS` 45min + 15min jitter); `could not read Username` deliberately left unmatched so it falls through to `unknown` (short transient retry). Auth failures then got `AUTH_FAILURE_BACKOFF_SCHEDULE_MS = [5, 15, 30, 60min]` clamped at the last entry, and the per-card stripe is gated behind `AUTH_FAILURE_CONFIRM_RETRIES = 3` (~20min of persistence) — pre-confirmation failures show the softer transient tooltip, and confirmation fires `onAuthFailureConfirmed` once per repo for a single escalation toast instead of N stripes. Concurrent sibling force-retries inside one backoff window coalesce into one retry round so a multi-worktree cold start can't insta-confirm. The #9740 manual path survives as the skip-the-backoff fast lane (it also clears `authFailureConfirmedNotified` so a still-broken token can re-toast).

## Lesson

- **When a policy is permanent/infinite "for safety", audit the trigger bucket for conflated causes before accepting the policy.** The infinite TTL existed because `auth-failed` swallowed rate limits and credential-helper blips; splitting the classification made a finite policy safe. Fix the bucket, then give each class a proportionate finite window.
- **A manual recovery affordance is not a fix for a stuck state users can't see they're in.** #9740 shipped click-to-retry and skipped #9736's finite-window half; #10670 refiled the same symptom ~2 weeks later because nobody clicks. If you ship half an issue, the unshipped half's symptom recurs — say so on the issue or expect the refile.
- **Classifier ordering in `GIT_ERROR_PATTERNS` is load-bearing: `rate-limited` must run before `auth-failed`.** GitHub secondary rate limiting rides the same `403` line and differs only by sideband text. Bucketing it as auth used to suspend the repo on a throttle that clears on its own. A dedicated test guards the order — don't reorder without it.
- **Per-commondir failure state fans out to every sibling worktree card — gate alarming UI on confirmed persistence, escalate once.** One transient failure decorating N cards over-signals; the stripe now requires 3 consecutive failures and the escalation is a single toast (`onAuthFailureConfirmed`), mirroring the toolbar's persistent-severity stripe rule. Coalesce concurrent sibling retries per backoff window or cold starts confirm instantly.
- **The rate-limit-safe finite retry shape is known — reuse it, don't re-derive it.** Hourly-ceiling exponential backoff for auth (5/15/30/60min clamped), 45min+jitter for rate limits, 60s+jitter for network/transient. Neither infinite suspension nor aggressive fast retry is acceptable; recovery affordances (`retryAuthFetch`, credential rotation) bypass the window on explicit user action.

## Applies when

- Touching `RepoFetchCoordinator` retry constants, failure kinds, or suspension logic — or tempted to add any permanent/infinite failure state "to be safe".
- Adding or matching a new `GitOperationReason` in `shared/utils/gitOperationErrors.ts` — check pattern ordering and whether the new bucket conflates transient with durable causes.
- Diagnosing a stuck "authentication failed" / "Sign in to refresh" stripe or stale "last fetched" counts on worktree cards when credentials work elsewhere.
- Reviewing a fix that adds only a manual recovery affordance (click/badge/button) for a state the app enters automatically — ask what clears the state when nobody clicks.
- Designing retry policy for anything that polls GitHub — secondary rate limits are 403s that look like auth failures, and retrying into them extends the throttle window.
