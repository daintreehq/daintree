## Context

Several toolbar/sidebar controls (Copy Context button, AgentButton primary + chevron, sidebar arm-matching button) are wrapped in a Radix `Tooltip` whose copy explains _why_ the control is unavailable (e.g. `Open a worktree first`, `Claude needs setup`). The control needs to be disabled when its precondition isn't met, but the tooltip must still be readable so the user understands the block.

## Problem

With native HTML `disabled`, a disabled-but-tooltip-wrapped button is a control that visibly does nothing with no explanation: the user hovers, no tooltip appears, and they can't discover the precondition. The AgentButton chevron also needs to block its dropdown from opening while disabled.

## Root cause

Three interacting facts, none individually surprising but easy to get wrong together:

- **Chromium 146 strips pointer events from natively `disabled` elements.** No `pointerenter`/`mouseenter` fires, so the Radix `Tooltip` (which opens on hover of `TooltipTrigger`) never triggers on a `disabled` button.
- **Radix `DropdownMenuTrigger` opens on `pointerDown` and `keyDown`, not `click`.** Gating only `onClick` leaks the menu open: a `pointerDown` (mouse) or `Enter`/`Space`/`ArrowDown` (keyboard) opens the dropdown before any click handler runs. See `AgentButton.tsx:493-507` — all three handlers (`onPointerDown`, `onKeyDown`, `onClick`) must `e.preventDefault()` when disabled.
- **`:not(:disabled)` CSS/selector matching does NOT match `aria-disabled`.** The toolbar roving-focus query in `Toolbar.tsx:387` had to change from `[data-toolbar-item]:not(:disabled)` to `[data-toolbar-item]:not([disabled])` — otherwise `aria-disabled` items (which have no native `disabled` attribute and so were never excluded by `:not(:disabled)`) would still need a way to be considered, and the attribute selector keeps them in the focus ring intentionally.

## Lesson

When a disabled control is wrapped in a tooltip that explains the precondition, do NOT use native `disabled`. Instead:

- Set `aria-disabled={cond || undefined}` (use `|| undefined` so the attribute is absent, not `aria-disabled="false"`, when enabled).
- Gate every action handler on the same `cond` (early-`return` in `onClick`, or `e.preventDefault()` for Radix triggers).
- For a **Radix `DropdownMenuTrigger`** (or any Radix trigger), gating `onClick` alone is insufficient — Radix opens on `pointerDown`/`keyDown`. Add `onPointerDown`, `onKeyDown` (Enter/Space/ArrowDown), and `onClick` guards, each calling `e.preventDefault()` when disabled.
- Style the disabled look via `aria-disabled:opacity-* aria-disabled:cursor-not-allowed` Tailwind variants, not a manual `cond && "opacity-50"`.
- If any selector elsewhere excludes disabled controls via `:not(:disabled)` (roving focus, query-all, focus traps), switch it to `:not([disabled])` or add explicit `aria-disabled` handling — `:disabled` pseudo-class never matches `aria-disabled`.
- Tooltip copy should name the precondition (`Open a worktree first`), not promise an action the now-blocked control can't perform.

## Applies when

- Adding/modifying a toolbar, sidebar, or chevron button that is conditionally unavailable AND wrapped in a `Tooltip`/`TooltipTrigger`.
- A user reports "the button does nothing and there's no tooltip / no explanation" on a greyed-out control.
- Wiring or gating a Radix `DropdownMenuTrigger`, `PopoverTrigger`, or similar — anything where the open fires on `pointerDown`/`keyDown` rather than `click`.
- Touching the toolbar roving-focus query (`[data-toolbar-item]` in `Toolbar.tsx`) or any focus-management code that filters on `:disabled` / `:not(:disabled)`.
- Working in `AgentButton.tsx`, `Toolbar.tsx`, or `SidebarContent.tsx`, or adding new conditionally-disabled controls anywhere in the renderer.
