## Context

#10642 (follow-up to #10634, resolving #10638) exposed process `exitCode`/`exitSignal` on every MCP-facing read path — `terminal.getStatus`, `agent.getState`, the `daintree://agent/{id}/state` resource, `terminal.waitUntilIdle`, and the `agent:state-changed` push notification — so the Daintree Assistant's conductor can tell a clean agent finish from a failure instead of scraping scrollback.

## Problem

The issue that spawned this PR (#10638) noted the exit code was "already captured internally, it just never leaves the main process" — `TerminalProcess.ts` stored it, but no MCP read path returned it. The PR fixed that plumbing, then review caught a second, independent gap in the same arc: even after the capture fix, `exitCode` still never reached MCP, because the `pty-host`→main IPC wire itself was silently stripping the field. Two unrelated-looking bugs, same root cause.

## Root cause

`TerminalProcess` and `AgentStateService` run inside the **pty-host utility process**, not main. Getting a value from there to an MCP tool response crosses five explicit-shape hops, and every field has to be listed by hand at each one: (1) `TerminalProcess.ts` exit handler stores `terminal.exitCode`/`exitSignal` on the in-process terminal object; (2) `AgentStateService.updateAgentState` constructs the `agent:state-changed` payload object literal and must spread `exitCode`/`exitSignal` onto it itself (only when `event.type === "exit"` — pattern/timeout completions have no exit code); (3) that payload is serialized as a `PtyHostEvent` (`shared/types/pty-host.ts`) sent over the actual pty-host↔main IPC channel, so the **type union** must declare the fields or nothing downstream can even see them on the wire; (4) `PtyEventsBridge.bridgePtyEvent` in main receives the `PtyHostEvent` and re-constructs a **second** object literal to re-emit on main's internal `events` bus — this is the exact hop the review-found bug lived in, the field existed correctly in steps 1-3 and still got dropped here; (5) `AgentAvailabilityStore` subscribes to that re-emitted event and caches into `Map<agentId, ...>` fields, again by explicit field name, for later reads (`already-idle`, the `state` resource) after the live event has passed. Only after all five hops forward the field can `sessionServer.ts` / `waitUntilIdle.ts` put it in a tool response. None of these hops use a generic passthrough (`...rest` or structural typing) — all are named-field object literals — so adding a field is invisible-by-default: TypeScript never errors when a hop's literal simply omits a field the type allows to be optional, it just silently stops forwarding it. The PR also codified two prior lessons: use `!== undefined` presence checks rather than truthiness (`exitCode: 0` and `exitCode: null` are both meaningful and both falsy), and never POSIX-decode the raw signal number (`128 + signum` is wrong on Windows — lesson #7028).

## Lesson

- **Treat any field added to a pty-host-originated payload as needing verification at every hop, not just the source.** Grep the field name across `TerminalProcess.ts` → `AgentStateService.ts` (event construction) → `shared/types/pty-host.ts` (the `PtyHostEvent` union) → `PtyEventsBridge.ts` (bridge reconstruction) → any store that caches the bridged event (`AgentAvailabilityStore`) → the MCP surface (`sessionServer.ts`, `waitUntilIdle.ts`) → renderer schemas (`src/services/actions/definitions/schemas.ts`). A field present in the type but missing from one hop's object literal compiles clean and just silently disappears.
- **`PtyEventsBridge.bridgePtyEvent` is the single highest-risk hop** — it is the literal pty-host-process-to-main-process IPC boundary, and #10642's review-found bug lived exactly there: the field was captured correctly on both sides of it and still didn't cross.
- **Use presence checks (`!== undefined`), never truthiness, when forwarding optional fields that can legitimately be `0`, `null`, or `false`.** `exitCode: 0` and `exitCode: null` are both meaningful values a truthy/falsy spread (`value && {...}`) would silently drop.
- **Don't gate a new field's capture on an unrelated existing condition.** Pre-#10642, `exitCode` was stored only inside `TerminalProcess`'s `shouldPreserveOnExit` branch, so any non-preserved terminal reported no exit code at all — capture unconditionally on every natural exit (user kills still excluded, they emit `agent:killed` not a completion) and let downstream decide what to do with it.
- **When an agentId can be reused by a respawn, clear cached metadata on the new spawn.** `AgentAvailabilityStore` deletes `exitCodes`/`exitSignals` on `agent:spawned` so a stale exit code from a prior session can't be read as the new session's outcome.

## Applies when

- Adding any new field to an agent/terminal state payload that originates in `TerminalProcess.ts` or `AgentStateService.ts` and needs to reach an MCP tool, resource, or notification.
- Touching `PtyEventsBridge.ts`, the `PtyHostEvent` union in `shared/types/pty-host.ts`, or `AgentAvailabilityStore.ts` — these are the silent-drop points in this chain.
- Debugging "the data is definitely captured (I can see it in the pty-host logs / TerminalProcess state) but the MCP tool/resource never returns it" — check every hop's object literal for the missing field name before assuming a logic bug.
- Reviewing a PR that adds a field to an event bus payload or IPC message type in this codebase — confirm every named-object-literal hop between source and consumer was actually updated, not just the type definition.
- Forwarding a value that can be `0`, `null`, or `false` across any of these hops — verify the spread uses `!== undefined`, not truthiness.
