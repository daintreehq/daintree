## Context

Panel kinds live in two parallel registries: `PANEL_KIND_REGISTRY` (config/metadata, `shared/config/panelKindRegistry.ts`) and `PANEL_KIND_DEFINITION_REGISTRY` (config + React component, `src/panels/registry.tsx`). Built-in kinds (`terminal`, `browser`, `dev-preview`, `review`) are wired at module load with **no** `extensionId`; plugins register their own kinds with an `extensionId` set. Both registries are mutated by `registerPanelKind*` and read through a snapshot that backs `useSyncExternalStore`.

## Problem

A plugin could replace a built-in panel kind just by registering the same `id` string — `register*` warned and overwrote silently, so a malicious or buggy plugin could hijack the `terminal`/`browser` component or metadata. Separately, `unregisterPanelKindDefinition` originally compared the id against a hardcoded list of built-in kind strings; that allowlist silently rots — a newly added built-in kind would be unprotected until someone remembered to extend the list (and a fourth built-in, `review`, was in fact added afterward).

## Root cause

The real invariant is a **cross-category trust boundary**, not a fixed set of names: built-ins are exactly the entries with `extensionId === undefined`, and a plugin entry always carries an `extensionId`. A kind-string allowlist re-encodes that boundary as a literal list that drifts out of sync with `BUILT_IN_PANEL_KINDS`. The collision to refuse is specifically "existing has no extensionId AND incoming has one" — that single predicate is self-maintaining: any future built-in (no extensionId) is automatically protected, and plugin-to-own-plugin re-registration (reconciliation) and built-in re-patching (init hooks) still pass. A second trap: when an overwrite is **refused**, the function must early-return _without_ bumping the snapshot reference, because `getPanelKindDefinitionsSnapshot()` feeds `useSyncExternalStore`; invalidating it on a no-op mutation re-renders every subscriber for zero actual change.

## Lesson

- Protect built-in registry entries with the `existing.extensionId === undefined && incoming.extensionId !== undefined` guard, not a hardcoded id allowlist. Mirror the same predicate everywhere the boundary matters (`registerPanelKind`, `registerPanelKindDefinition`, `unregisterPanelKind`).
- `unregisterPluginPanelKinds`/`unregisterPanelKind` must reject empty/non-string ids first, so a JS-side `undefined` cast can't match a built-in whose `extensionId` is also `undefined`.
- A rejected/no-op registration must early-return before any snapshot recompute or listener notification — a changed snapshot identity under `useSyncExternalStore` forces spurious re-renders. Adversarial tests should assert `getSnapshot() === snapshotBefore` after a refused write.
- Log listener throws via `logError`, not `console.warn`: these listeners drive `useSyncExternalStore`, so a thrown listener can leave the UI stale (a real error, not a diagnostic warning).
- Fallbacks for unknown kinds must not impersonate a built-in — `getPanelKindColor` returns `var(--theme-text-secondary)`, never the terminal brand color, so an unrecognized extension kind doesn't masquerade as a terminal.

## Applies when

- Adding/modifying any registry that mixes built-in (app-owned) and plugin/extension-contributed entries keyed by a shared string id — panel kinds, action definitions, panel-kind definitions, agent/theme registries.
- Writing overwrite/collision or unregister guards and tempted to enumerate the protected ids in a literal allowlist.
- Touching `shared/config/panelKindRegistry.ts` or `src/panels/registry.tsx` (`registerPanelKind`, `registerPanelKindDefinition`, `unregisterPanelKind*`, `getPanelKindColor`, snapshot/listener plumbing).
- Any registry whose snapshot backs `useSyncExternalStore` — verify no-op/refused mutations leave the snapshot reference unchanged to avoid render storms.
- Adding a new built-in panel kind (e.g. extending `BUILT_IN_PANEL_KINDS`) and needing to confirm it's automatically protected from plugin overwrite.
