## Context

Full-screen mouse-reporting TUIs (grok, lazygit, btop, some agent CLIs) own their own scrolling: every wheel line is a full round trip — a synthetic mouse report down the PTY, an app redraw, the frame back through `TerminalProcess`. `ResourceProfileService` downgrades a global `performance`/`balanced`/`efficiency` profile under sustained event-loop lag, and that profile drives both the pty-host's `portBatcher` throughput delay and `TerminalWebGLManager`'s WebGL-vs-DOM flip thresholds. #10848 fixed the "smooth at first, then slow and stays slow" symptom behind issue #10858; #10860 extended the fix to ordinary scrollback scrolling; #10895 cut further latency from the same wheel-to-frame path. All three merged within three days as one investigation arc.

## Problem

Scrolling a full-screen TUI felt fine at first, then degraded and stayed degraded under load — not a crash, a felt latency regression that only showed up "under pressure," which initially pointed at the wheel-normalization code (a red herring: the classifier and pacing were fine).

## Root cause

Scrolling a mouse-reporting TUI is itself CPU/event-loop work (parse the report, redraw, ship the frame). `ResourceProfileService` samples event-loop lag via `monitorEventLoopDelay` and, once sustained, latches the profile to `efficiency`. Two knobs move with that latch: `portBatchThroughputDelayMs` goes from the `performance`/`balanced` value `PORT_BATCH_THROUGHPUT_DELAY_MS = 16` (`electron/pty-host/portBatcher.ts`) to `40`, and the WebGL upper flip threshold drops (balanced 12 → efficiency 8 concurrent WebGL-wanting terminals against the flat 16-context cap at merge time, per #10858), pushing panes onto the slower DOM renderer — #11192 later made these RAM-tiered ratios (`electron/utils/webglContextBudget.ts`, `WEBGL_THRESHOLD_RATIOS`), so 12/8 no longer appear as literal constants but the mechanism is unchanged. Both changes fire exactly while the user is mid-scroll, because scrolling is the load that triggered the downgrade — the governor throttles the very interaction causing the pressure it's reacting to, a closed loop that worsens the longer you scroll.

The fix is not a smarter or slower-triggering signal — a GPU/VRAM pressure API was considered and rejected, Electron 42/Chromium 148 exposes none — it's a renderer-driven, time-boxed override. `ResourceProfileService.requestInteractiveOverride(durationMs)` clamps the profile to ≥ `balanced` for up to `MAX_INTERACTIVE_OVERRIDE_MS = 5_000`, called from `TerminalBurstController.onActiveWheel`/`onUserScrollIntent` (moved out of `TerminalInstanceService.ts` by an unrelated later refactor — symbols still resolve, just relocated) with a 1500ms hold re-requested every throttled 500ms so continuous scrolling never lets the hold lapse. It lifts an already-latched efficiency profile back to balanced and blocks re-entry (`isInteractiveOverrideActive()` gates both `sampleLag` and the single `applyProfile` choke point), can never pin the profile above the 5s cap, and short-circuits a no-op transition so a redirected request doesn't churn a broadcast while already balanced. #10895 separately found the renderer's own `requestAnimationFrame` gate before dispatching wheel reports added a full extra frame, since Chromium already frame-aligns wheel delivery — fixed by dispatching synchronously when no drain is in flight (`WHEEL_MIN_DISPATCH_GAP_MS = 6`).

## Lesson

- **A resource governor that degrades throughput under load must check whether the degraded resource is the one the triggering interaction depends on.** Efficiency mode here stretched the exact PTY round-trip delay and WebGL threshold that scrolling needs, so the "protective" downgrade made the felt symptom worse. Before adding a profile/tier downgrade, ask what interactive paths route through the resource being throttled.
- **Prefer a narrow, time-boxed interactive override over decoupling or replacing the trigger signal.** A GPU/memory-pressure signal was considered for the WebGL threshold and rejected — no such API exists on this Electron/Chromium pin. `requestInteractiveOverride` is the general pattern: hold the degraded setting off its worst value for a short, renewable, hard-capped window driven by "user is interacting right now," rather than making the global signal smarter.
- **A single choke point for all transitions beats guards scattered at each call site.** The override clamp lives once, inside `applyProfile`, catching both the lag-latch path (`sampleLag`) and any future memory/fleet-driven downgrade path without each needing its own check — grep for `applyProfile` before adding a new transition source.
- **Chromium already frame-aligns wheel events — don't add your own rAF gate in front of that.** A wheel handler debouncing through `requestAnimationFrame` before dispatch may be adding a full redundant frame of latency; check the browser's own event coalescing before assuming you need one.
- **Do not delete a hand-rolled override of a library's built-in handling just because the library later shipped "the same fix."** `TerminalListenerInstaller.ts` keeps a block comment noting xterm's own scroll fixes are all present upstream, but the app still overrides `MouseService._consumeWheelEvent` on purpose (it zero-floors small trackpad gestures) — the override and the upstream fix solve different problems.

## Applies when

- Touching `ResourceProfileService.ts` transition logic (`applyProfile`, `sampleLag`, `computeTargetProfile`) or any code reading `currentProfile` to scale a throughput/threshold knob (`portBatcher.ts`, `TerminalWebGLManager.ts`).
- Diagnosing "smooth at first then gets slow and stays slow" under a resource-tier system — check whether the downgraded tier also throttles the interaction generating the pressure.
- Adding a new resource-pressure-driven degradation (profile knob, tier, eviction/throttle path) — verify the degraded resource isn't on the hot path of the interaction most likely to trigger the pressure.
- Working on wheel/scroll input dispatch (`TerminalListenerInstaller.ts`, `TerminalBurstController.ts`, `mouseWheelClassifier.ts`) — check for an existing rAF/debounce gate before adding another.
- Bumping xterm and seeing a "deliberate override, don't delete" comment — verify against the current changelog before removing it; upstream fix and local override can coexist.
