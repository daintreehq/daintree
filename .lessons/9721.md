## Context

The first-paint splash is a `#startup-skeleton` div in `index.html` (removed by `src/main.tsx` once React mounts). Before `win.show()`, the main process seeds it with the persisted theme's real token values via `wc.insertCSS(..., { cssOrigin: "user" })` in `electron/window/skeletonCss.ts` — called from both `createWindow.ts` and `ProjectViewFactory.ts` (per-project `WebContentsView`s get it too). At PR time this was one `injectSkeletonCss` function; since split into `buildSkeletonCss` + `insertSkeletonCss` with `injectSkeletonCss` kept as a wrapper. #4672 had scoped the seeded block to `:root`. The live app themes differently: `applyAppThemeToRoot` (`src/theme/applyAppTheme.ts`) writes tokens as inline styles on `documentElement` and diffs `root.dataset.themeVariableKeys` to `removeProperty` tokens the new theme doesn't define.

## Problem

Issue #9716: start on a light theme, switch to a dark theme — the panel grid background keeps the light color until app restart, while everything else (Settings dialog etc.) updates live. The symptom looks like the renderer's live-switch path "skipping" some tokens or a hardcoded color (the separate #9707), pointing nowhere near a main-process startup-CSS file that ran once, minutes earlier.

## Root cause

Three individually harmless facts compound. (1) **`insertCSS` stylesheets are never removed** — they persist for the whole page lifetime unless you keep the returned key and call `removeInsertedCSS`, which Daintree never does. (2) **For normal declarations, author-origin inline styles outrank user-origin rules** — so the ~always-present `--theme-*` tokens were safe: `applyAppThemeToRoot` re-sets them inline on every switch and the inline value wins (#9333 relies on exactly this ordering). (3) **The theme system has OPTIONAL extension tokens** (`shared/theme/extensionRegistry.ts`) that only some themes define — `--panel-grid-bg` exists in light themes like bondi and table-mountain but in no dark theme. On a light→dark switch, `applyAppThemeToRoot` removes it by absence: the `themeVariableKeys` diff calls `removeProperty`. But that only deletes its _own inline_ declaration — with no inline value left, the persistent user-origin `:root { --panel-grid-bg: … }` seeded at startup becomes the only declaration in the cascade and wins. The consumer chain `--color-grid-bg: var(--panel-grid-bg, var(--terminal-grid-bg, var(--theme-surface-grid)))` (`src/index.css`) needs the token to be **undeclared** for its fallback to fire; a stale declared value short-circuits it, so the grid stayed light.

The fix scopes the entire seeded block to `#startup-skeleton`: `#root` is a _sibling_, so the live app can never inherit anything from the injected stylesheet, while the splash's own descendants still inherit every var they need. It was also a delayed-fuse bug: #4672's `:root` scope (2026-03-31) was correct when merged — the collision only materialized when the extension-registry work (~2026-05-28) made themes legitimately diverge on optional tokens. The PR also added a `.catch` on `insertCSS` (a destroyed/navigated WebContents during rapid project switching rejects; `index.html` carries hardcoded fallbacks so the splash still paints).

## Lesson

- **Never seed CSS custom properties at `:root`/`html` via `insertCSS`** — the stylesheet outlives the startup phase by the whole session. Scope injected first-paint CSS to an element that exits the live cascade (`#startup-skeleton`, removed by `src/main.tsx` after mount); descendants inherit, siblings like `#root` don't.
- **Remove-by-absence theming can only remove its own declarations.** `applyAppThemeToRoot`'s `themeVariableKeys` diff deletes inline properties it previously set; it cannot neutralize the same custom property declared by any other stylesheet on an ancestor of the consumer. If a `var()` fallback chain is the mechanism for "this theme doesn't have that token", any persistent declaration anywhere defeats it silently.
- **The `cssOrigin: "user"` inline-outranks ordering protects only tokens re-declared on every switch.** Required `--theme-*` tokens are safe under it; OPTIONAL extension tokens whose new value is _absence_ get zero protection. When reasoning about injected-CSS persistence, enumerate the optional set in `shared/theme/extensionRegistry.ts` — those are the leak candidates.
- **"One surface stale until restart, everything else live" fingerprints a startup-time seed winning the cascade**, not a broken switch path. Check whether the stale token is OPTIONAL and present in the FROM theme but absent in the TO theme; restart-fixes-it means a session-lifetime stylesheet — in Daintree, `skeletonCss.ts`.
- **Always `.catch` main-process `insertCSS`/`executeJavaScript` on WebContents that can be torn down mid-flight** — rapid project switching destroys views while the seed promise is in flight, surfacing as an unhandled rejection.

## Applies when

- Touching `electron/window/skeletonCss.ts` (`buildSkeletonCss`, `insertSkeletonCss`, `injectSkeletonCss`) or adding any new main-process `insertCSS` / pre-React first-paint seeding path.
- Adding an OPTIONAL extension token to `shared/theme/extensionRegistry.ts` or defining one in some `shared/theme/builtInThemes/*` but not others — the divergence is what arms this bug class.
- Diagnosing a live theme switch that leaves one surface on the old theme until restart while other surfaces update correctly.
- Modifying `applyAppThemeToRoot` / `applyDefaultAppTheme` token application, the `themeVariableKeys` diff, or any `var(--optional, fallback)` chain that relies on a token being undeclared.
- Reviewing any change that assumes `removeProperty` (or a theme "not defining" a token) is sufficient to reset styling — verify no other origin/stylesheet ever declares that property on an ancestor.
