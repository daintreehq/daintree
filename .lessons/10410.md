## Context

Memory-housekeeping batch across the host processes (`#10410`; sibling window-layer batch `#10412`). `ProcessTreeCache` polls `ps` on Unix, parses each line with a regex in `parseUnixLine`, and caches `ProcessInfo` (`comm`/`command` strings) for memory attribution and `ProcessTreeKiller`. Alongside it: `WorktreeMonitor`/`GitStatusPass` diff-hash git status across polls, `WorkspaceService` dedups acknowledged delete mutations, `GitServiceCache` pools one `GitService` per worktree, and `getWorktreeChangesWithStats` line-counts untracked files — all long-lived across a project session. The PR also added `--max-old-space-size` caps to workspace-host (256MB), watchdog (128MB), and plugin-dev-worker (256MB), matching `PtyHostLifecycle` — the renderer had been the only capped process.

## Problem

Host RSS crept up quietly over a session with no classic leak: the retained heap was orders of magnitude larger than the logical content of the caches. A `ProcessTreeCache` entry is a 10-character `comm` plus a short command line, yet each poll's cache pinned megabytes; `WorktreeMonitor` held a change-count-proportional string forever; a dedup `Set` and a per-worktree cache both grew without bound. Individually tiny values, wildly oversized retention — which is exactly why heap-snapshot retainer chains, not object counts, are the tool that finds it.

## Root cause

V8 represents a `String.prototype.match` capture (and `.slice()`/`.substring()`) as a **SlicedString**: a view holding an offset+length into the parent buffer, not a fresh allocation. Caching `match[5]` (the `comm`) keeps the _entire_ multi-MB `ps` stdout string alive as the parent slab for as long as the entry lives. `String(x)`, `x + ""`, and template literals do not sever the tie — they produce `ConsString`s that still reference the parent. Only `Buffer.from(str).toString()` allocates a fresh flat copy that drops it. The same batch fixed four more quiet-accumulation variants: (a) `calculateStateHash` retained a `path:status:ins:del` string proportional to change count as `previousStateHash` for the monitor's lifetime → now a 32-bit FNV-1a digest seeded with `0x811c9dc5` (the digest of an empty change list, preserving the legacy `""`-sentinel "initial load == clean tree" semantics; the code has since moved to `electron/workspace-host/GitStatusPass.ts` in a file-split); (b) `WorkspaceService.acknowledgedMutations` grew unbounded → FIFO-capped at `MAX_ACKNOWLEDGED_MUTATIONS = 500`; (c) `GitServiceCache` never evicted a worktree's `GitService` on removal → new `delete(path)`; (d) `countFileLines` decoded up to 10MB to UTF-8 just to count newlines; (e) the untracked line-count cache key baked in `headOid`, so every commit thrashed content-pure entries.

## Lesson

- **When you store a regex capture, `.slice()`, or `.substring()` from a large source string in any long-lived structure, force a flat copy with `Buffer.from(str).toString()`.** V8 keeps those substrings as SlicedString views onto the parent slab, so caching a 10-char `comm` pins all of multi-MB `ps` stdout. `String()`, concatenation, and template literals produce `ConsString`s that still reference the parent — they do NOT sever it. The `Buffer.from().toString()` round-trip in `ProcessTreeCache.parseUnixLine` is the only idiom that reliably forces the copy.
- **To count newlines or scan bytes in a file, iterate the `Buffer` for `0x0a` — never `buffer.toString("utf-8")` first.** Decoding a 10MB file doubles the allocation for zero benefit; `0x0A` is unambiguous in UTF-8. See `countFileLines` in `electron/utils/git.ts`.
- **A cache key must include ONLY the inputs the value depends on.** Untracked-file line counts are pure content, so `makeUntrackedLineCountCacheKey` excludes `headOid` (an `untracked:` prefix keeps it disjoint from tracked-diff keys); the old shared key carried `headOid`, so every commit invalidated unchanged content. Tracked numstat keys DO keep `headOid` — they genuinely depend on HEAD content.
- **Replace any retained "concatenate everything then compare" state signature with a fixed-width digest.** `calculateStateHash` (now `GitStatusPass.ts`) folds the sorted change list into a 32-bit FNV-1a number instead of holding a change-count-proportional string alive as `previousStateHash`. Accept the ~1-in-2^32 collision — it suppresses one change event until the next non-colliding state, cheap next to the retained allocation.
- **Any unbounded Set/Map keyed by an arbitrary id (UUID, not path-scoped, so nothing else evicts it) needs an explicit cap.** `acknowledgedMutations` is FIFO-capped via `recordAcknowledgedMutation` — add, then if over `MAX_ACKNOWLEDGED_MUTATIONS` delete `values().next().value` (insertion-order oldest). A session sees well under 100 deletes, so 500 never drops a live id.
- **Evict a per-resource cache on the resource's teardown event, not just by TTL.** `GitServiceCache.delete(path)` now fires on the `worktree-removed` event (`WorkspaceHostEventRouter`) AND the legacy worktree-delete IPC path (`worktree/lifecycle.ts`) — a deleted worktree's `GitService` otherwise lingered until process exit.

## Applies when

- Storing any regex-capture / `slice` / `substring` from large subprocess or file output (`ps`, `git`, log parsing) into a cache or long-lived field — force-copy with `Buffer.from().toString()`.
- Diagnosing quiet RSS growth in a host process where a cache retains far more than its logical content and there is no classic leak — snapshot retainer chains, not object counts.
- Adding or reviewing a cache key — verify it carries only true dependencies (content vs HEAD OID) and that entries are evicted on the resource's removal event, not only by TTL.
- Adding any Set/Map dedup keyed by an arbitrary/UUID id in a long-lived service — confirm it is size-capped.
- Building change-detection over large derived strings across polls — prefer a fixed-width digest over retaining the concatenation.
