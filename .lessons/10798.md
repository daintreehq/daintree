## Context

`TerminalWebGLManager` pools WebGL renderer contexts for agent terminal panes and runs an atlas-resync path (`scheduleAtlasResync` / `runAtlasResync`) built earlier (tracked in #8080, commit `7965d6244`) to fix real glyph corruption: xterm shares one module-global `TextureAtlas` across every terminal with a matching font/theme config, and a page-merge (`TextureAtlas._mergePages`) rewrites glyph texture-page indices while each `WebglRenderer` keeps its own local model/vertex buffers, so a merge leaves renderers sampling stale atlas coordinates until something resets their local state. `scheduleAtlasResync` listens for `onChangeTextureAtlas` / `onRemoveTextureAtlasCanvas`, coalesces a burst into a single rAF-batched call to `runAtlasResync`, which calls `resetLocalWebGLRenderer` per pending id — a local resize-like reset chosen over the public `clearTextureAtlas()` specifically to avoid perturbing co-owner renderers under tiled-agent load.

## Problem

Heavy-output alt-screen-buffer apps (OpenCode, vim) pinned a CPU core once an atlas page-merge fired. The visible symptom was misleading: glyphs sheared/garbled under load, appeared to heal on a real window resize, then came back the moment the pane refocused — which reads like a resize-timing or OpenCode-specific bug, not a global renderer loop that affects any alt-buffer TUI.

## Root cause

`resetLocalWebGLRenderer` calls xterm's own `WebglRenderer.handleResize`, which internally re-runs `_refreshCharAtlas`. That method SYNCHRONOUSLY re-fires the very `onChangeTextureAtlas` / `onRemoveTextureAtlasCanvas` events that `scheduleAtlasResync` subscribes to as its trigger (confirmed by reading the `@xterm/addon-webgl` source, not inferred — `handleResize` → `_refreshCharAtlas` → an inline `Emitter.fire`, and `TextureAtlas._mergePages` fires synchronously too). `scheduleAtlasResync` had no re-entrancy guard, so every resync scheduled the next one on the following animation frame: atlas event → resync → `handleResize` → atlas event → resync → ... roughly every 16ms, forever, once a single page-merge kicked it off. The rAF coalescing already in place (`atlasResyncPending` / `atlasResyncRafId`) only batches multiple _external_ trigger events into one resync per frame — it does nothing to stop the resync from re-triggering _itself_, because the self-induced event arrives synchronously inside the very call the coalescing was meant to debounce. The loop's re-entrant driver lives entirely inside xterm's internals, invisible from Daintree's own call graph, which is why it read as an OpenCode/resize quirk rather than a structural loop in the atlas-recovery code that #8080 had introduced.

## Lesson

- **When a recovery path calls a library API that can internally re-emit the very event class that triggered the recovery, assume re-entrancy and guard it** — even when the call looks like an innocuous `handleResize`. Verify by reading the library source for inline event fires, not by assuming a resize is side-effect-free.
- **rAF/debounce coalescing of the trigger is not a re-entrancy guard.** Coalescing collapses multiple _external_ firings into one call per frame; it does not stop a _self-induced_ firing produced by the call itself. Both are independently needed here (`atlasResyncPending`/`atlasResyncRafId` for the former, `suppressAtlasResync` for the latter).
- **The fix pattern is a synchronous boolean flag set before the reset loop and cleared in a `finally`, checked at the first line of the listener** (`scheduleAtlasResync` returns immediately if `suppressAtlasResync`). A flag suffices, with no debounce/timestamp math, only because the re-fire was proven synchronous in the addon source — if a future xterm version made `_refreshCharAtlas` async, this exact guard shape would stop working and the loop could reappear one rAF later.
- **Test both directions of a re-entrancy guard, not just "no loop."** The regression test forces `handleResize` to re-fire the atlas event mid-reset and asserts exactly one reset happened (loop suppressed), then fires the event again afterward and asserts a second, genuine reset occurs (guard isn't permanently stuck on) — a guard that never clears is as broken as no guard.
- **A symptom that "heals on resize, returns on refocus" in an alt-buffer TUI is a renderer-state clue, not proof of app-specific behavior** — it means some reset path is running (resize forces one), so look for what re-arms the corruption afterward rather than assuming the specific app (OpenCode) is special.

## Applies when

- Touching the atlas-resync path in `TerminalWebGLManager.ts` (`scheduleAtlasResync`, `runAtlasResync`, `resetLocalWebGLRenderer`, `suppressAtlasResync`) or any other WebGL/xterm renderer recovery code.
- Diagnosing a pinned CPU core, constant redraw, or glyph shearing/corruption in alt-buffer TUIs (OpenCode, vim, htop) — especially when it "heals" on resize and recurs on refocus.
- Writing or reviewing any event-driven recovery/retry path whose recovery step calls a lower-level library method that might re-emit the higher-level event the path listens for.
- Bumping `@xterm/*` past the beta line pinned here (`6.1.0-beta.287`+) — re-verify `WebglRenderer.handleResize` / `_refreshCharAtlas` still fire atlas-change events synchronously; an async change would silently defeat the synchronous-flag guard.
- Reviewing new subscribers to `onChangeTextureAtlas` / `onRemoveTextureAtlasCanvas` (or any xterm-internal atlas event) for the same self-triggering trap.
