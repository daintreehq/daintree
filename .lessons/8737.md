## Context

Structured fleet broadcast (`src/components/Fleet/fleetExecution.ts`) fans `terminalClient.submit` out to every armed pane and classifies each rejection so dead PTYs auto-disarm. Classification needs the errno (`EPIPE`/`EBADF`) to tell a permanently-gone pipe apart from a transient failure. The renderer relies on `classifyFleetRejectionReason` (`src/components/Fleet/fleetBroadcast.ts`) matching against `PERMANENT_FAILURE_CODES`.

## Problem

A dead PTY's `submit` rejection arrived in the renderer as a generic `Error` with `.code` missing, so `classifyFleetRejectionReason` couldn't see the errno. (Separately, the pre-fix bug was that `submit` was fire-and-forget and never rejected at all — #8706.) The natural fix — `throw new AppError({ code: "EPIPE", ... })` and read `err.code` in the renderer — would silently fail because `.code` vanishes across IPC on this path.

## Root cause

The codebase has TWO error-serialization regimes and they behave differently:

- The **transparent envelope** (`wrapError`/`serializeError`/`deserializeError` in `shared/utils/ipcErrorSerialization.ts`, lesson #3769) explicitly re-serializes `.code`, `errno`, `syscall`, etc. into `{ ok: false, error: SerializedError }` and the preload's `_unwrappingInvoke` rebuilds a full Error. On this path `.code` survives.
- The **plain `defineIpcNamespace` + `op` + `typedHandle` path** (`electron/ipc/define.ts`, `electron/ipc/utils.ts`) registers a bare `ipcMain.handle` and just re-`throw`s on error — it never calls `wrapError`. There is no envelope on the wire, so Electron's native `ipcRenderer.invoke` error serialization runs, which carries only `message`/`name`/`stack` and strips every custom property including `NodeJS.ErrnoException.code`.

`terminal.submit` is registered via `op(CHANNELS.TERMINAL_SUBMIT, handleTerminalSubmit)` (the plain path), so even though the preload binding goes through `_unwrappingInvoke`, no envelope exists on error and `.code` is lost. Knowing about lesson #3769 actively misleads here: the envelope is opt-in, not applied to every handler.

## Lesson

- Do not assume `err.code` (or any custom Error field) survives IPC. It only survives on handlers that go through `wrapError`/`serializeError`. The `defineIpcNamespace`/`op`/`typedHandle` plain path does NOT wrap errors, so native Electron serialization strips everything but `message`.
- When a renderer must classify a rejection from a plain `typedHandle` op, encode the discriminator in the **message text** (`handleTerminalSubmit` throws `EBADF: terminal X not found` / `EPIPE: terminal X has no live PTY`) and match it by substring renderer-side. Document the constraint at the throw site so nobody "cleans it up" into a `.code` field.
- Re-throw `AppError` unchanged in the handler's catch (`if (error instanceof AppError) throw error`) — wrapping it in a new `Error("Failed to ...: " + msg)` would clobber the leading errno token.
- If you genuinely need structured fields across IPC, migrate that op onto the envelope path rather than smuggling fields through the message string.

## Applies when

- Adding or debugging any IPC op registered via `op()` / `defineIpcNamespace` / `typedHandle` where the renderer needs to branch on error type, errno, or any custom Error property (not just the message).
- A renderer classifies `terminalClient.submit` / fleet-broadcast rejections, or works in `src/components/Fleet/` (`classifyFleetRejectionReason`, `PERMANENT_FAILURE_CODES`).
- You see `err.code === undefined` / a generic `Error` in the renderer despite the main process throwing a typed error with a `code` field.
- You're tempted to set `danger`/discriminator fields on a thrown error and read them post-IPC — first confirm the channel goes through `wrapError`, not the plain `typedHandle` path.
- Reviewing main-process error throws on terminal/PTY IPC handlers and deciding whether the errno needs to reach the renderer.
