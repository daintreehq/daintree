## Context

`setupWebviewCSP` in `electron/setup/protocols.ts` installs an `onHeadersReceived` listener per webview partition that rewrites the `Content-Security-Policy` header via `mergeCspHeaders`. Partitions are classified by `classifyPartition` (`electron/utils/webviewCsp.ts`) into `project` (strict app CSP), `dev-preview` (localhost-only `getLocalhostDevCSP`), `browser`, `portal`, and `unknown`. The `persist:browser` session backs the integrated browser panel, where users navigate to arbitrary remote sites (GitHub, Slack, docs, AI tools).

## Problem

`applyCSP("persist:browser")` was applying the localhost-only `getLocalhostDevCSP()` policy to the browser session. That policy whitelists only `'self'` + `localhost`/`127.0.0.1`/`[::1]` in `script-src`, `connect-src`, and `form-action`. On a remote site `'self'` is the site's own origin, so first-party scripts loaded but every third-party CDN (`cdn.jsdelivr.net`, `googletagmanager.com`, `fonts.gstatic.com`), every cross-origin `fetch`/`XHR`/`WebSocket`, and every cross-origin form post was silently blocked — breaking most of the web with no app-side error.

## Root cause

Two compounding effects, both invisible to the app:

- `mergeCspHeaders` first _strips_ the remote site's own `Content-Security-Policy` header and replaces it with ours, removing the site's intended defenses.
- The replacement (or, where a UA merges multiple CSPs, the intersection) is enforced most-restrictive-wins by Chromium. A localhost-scoped policy on an arbitrary remote origin is maximally restrictive against everything the site actually needs.

The deeper mistake was treating a CSP overlay as a security _add_ for a browser-as-component. For a partition rendering untrusted remote content, the meaningful boundary is already provided by `sandbox:true`, `contextIsolation:true`, no preload, the deny-all `lockdownUntrustedPermissions` handler (`electron/setup/security.ts`), and the `will-navigate`/`will-redirect` guards. Layering an app CSP on top adds no protection and only sabotages legitimate sites.

## Lesson

- Do NOT apply any app-controlled CSP overlay to a partition that loads arbitrary remote origins. The fix adds `browser` to the early-return guard in `applyCSP` (alongside `unknown` and `portal`), so the remote site's own CSP is left intact.
- Reserve `getLocalhostDevCSP()` for `dev-preview` partitions only — its name says "localhost dev", and applying it anywhere a non-localhost origin can load is a bug.
- Remember `mergeCspHeaders` _replaces_ the upstream CSP, it doesn't append. Installing it on a partition silently discards whatever defenses the loaded site shipped — only do that for origins you control (the trusted `project` shell, localhost dev servers).
- For untrusted remote content, the security boundary is sandbox + contextIsolation + deny-all permissions + navigation guards, not a header overlay. Lock the contract with partition-type applicability tests (`webviewCsp.test.ts`) so a future refactor can't quietly re-add the browser overlay.

## Applies when

- Touching `setupWebviewCSP` / `applyCSP` / `classifyPartition` in `electron/setup/protocols.ts` or `electron/utils/webviewCsp.ts`, or adding a new webview partition type.
- Debugging why third-party scripts, CDNs, cross-origin `fetch`/`WebSocket`, or form submits silently fail in the integrated browser panel (`persist:browser`) but work in dev-preview.
- Wiring any `onHeadersReceived` / `mergeCspHeaders` CSP header rewrite onto a session that can load origins you don't control.
- Reviewing security-hardening PRs that propose "add a CSP" to a browser/embedded-webview surface — verify the partition only ever loads first-party or localhost origins before overlaying.
