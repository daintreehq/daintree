## Context

The main process boots off `electron/main.ts`; its eager static-import closure parses and evaluates before first paint. A prior effort (#9285) tried to defer the ~3,200-line `PluginService` (pulls `semver`/`ajv`/`yauzl`) by removing its `app.whenReady()` import site — every call site elsewhere already used `await import()`. A parallel arc (#10403) did the same for the ~637KB MCP server stack (SDK server, transports, `iconv-lite`, zod-v4 schemas), which defaults to off. #10406 is the lead; #10413 is a third sibling.

## Problem

The deferrals had silently rotted. `PluginService`, `PluginMcpSupervisor`, `semver`, `ajv`, and `yauzl` were all still evaluating during main-bundle module-eval, pre-first-paint — every careful `await import()` elsewhere was just a cache hit on an already-evaluated module (#10385). The MCP SDK was parsed pre-first-paint too (#10384). Nothing looked wrong in the deferral commit; the re-anchoring lived in unrelated import edges, and the only signal was the eager-module count.

## Root cause

Three distinct import-graph mechanisms each re-anchored a "deferred" module, and none of them fails the typecheck. (1) **The eager handler barrel.** `electron/ipc/handlers.ts` statically imports `./handlers/plugin.js` and `./handlers/pluginMcp.js`, which _value_-imported the `pluginService` singleton — the barrel dragged all 3,200 lines back onto boot. The fix is NOT to delazify the barrel (it still eagerly imports the handlers) but to make the handlers stop value-importing the singleton: `import type * as PluginServiceModule` + a cached `await import()` accessor (`getPluginService`, mirroring `helpAssistant.ts`). (2) **A lone constant drags its whole module.** `plugin.ts`'s import of `MAX_DNTR_BYTES` from `PluginArchive.js` pulled `yauzl` onto boot — one bare constant re-anchoring the whole zip library; the fix moved it to a zero-dep `electron/utils/pluginArchiveConstants.ts`. (3) **`import type` vs value import of a "types" file.** The MCP SDK's `types.js` constructs the full zod protocol schemas at module init, so any _value_ import edge reaching it runs that at boot. `readinessProbe.ts` (eager via `HelpSessionService`) and `pluginMcpHash.ts` reached the SDK-touching `mcp-server/shared.ts` only for `ACTIONS_LIST_TOOL` / `safeSerializeToolResult`. #10403 lifted those SDK-free pieces to `shared/config/helpAssistantTierAllowlists.ts` and `electron/utils/safeSerializeToolResult.ts` and imported them _directly_, leaving `shared.ts` re-exporting for back-compat.

## Lesson

- **A deferral is an invariant, not a one-time fix.** An eager barrel that statically imports a handler re-negates that handler's deferral the moment the handler value-imports the heavy singleton. Don't trust the deferral commit — verify against the eager-module count. Keep the barrel eager; make the leaf import `import type` + cached `await import()`.
- **A single bare-constant import can drag a heavy transitive dep onto boot.** `MAX_DNTR_BYTES` from `PluginArchive.js` pulled `yauzl`. Put boot-reachable constants in zero-dep files and update _all_ importers — one stray importer keeps the dep eager and defeats the whole extraction.
- **`import type` erases; a value import runs module-init side effects even for a file named `types.js`.** The MCP SDK's `types.js` builds zod schemas at import. To sever, extract the SDK-free symbols to their own homes and import them directly, not through the SDK-touching barrel.
- **Lazifying a service with a synchronous subscription contract needs a buffering proxy.** #10403's `LazyMcpServerProxy` (`electron/services/connectivity/index.ts`) buffers `onStatusChange` subscriptions in a `Map` and replays them via `setReal()` when the real service wires, preserving the connectivity registry's sync ordering. `wireMcpServerToConnectivityRegistry` runs at `McpServerService.ts` module scope so every load path wires exactly once, idempotently.
- **The count-based `eager-import-baseline.json` guard is the only durable defense — and it is NOT in CI pre-1.0.** `scripts/check-import-budget.mjs` fails on eager-module-count growth or a new sync FS/store/SQLite call on the eager path, but runs locally on demand only. Run `npm run import-budget` after any main-process import change; the baseline keeps catching regressions (1227 → 935 at #10406 → 817 now).
- **Lazy-importing a dep only helps if no eager consumer keeps its chunk alive.** #10413 lazified `simple-git` and moved host schemas to `zod/mini`, but esbuild unions shared chunks, so `pty-host` shed only 18KB — main's classic-zod consumers keep the ~295KB `zod/core` chunk alive that both hosts import. Verify the dep is gone from _every_ eager closure, not just the one you edited.

## Applies when

- Adding or "completing" a lazy-import deferral of a heavy main-process service (`PluginService`, `McpServerService`, `PluginMcpSupervisor`) — check eager barrel edges (`electron/ipc/handlers.ts`), bare-constant imports, and `types.js`-style value imports that re-anchor it.
- Extracting a constant/helper to sever a dep from boot, or choosing `import type` vs a value import from a schema/SDK module — grep _all_ importers; value imports run zod/ajv schema construction at module init.
- Lazifying any service with a synchronous `onX`/subscribe contract — you need a buffering proxy (`LazyMcpServerProxy`) or you break subscription ordering.
- Touching the eager main-process import path or the `check-import-budget` guard — it is local-only pre-1.0; run `npm run import-budget` yourself, CI won't.
