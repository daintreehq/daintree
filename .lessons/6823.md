## Context

Trashed terminals get a soft-delete TTL: `scheduleTrashExpiry` (`src/store/slices/panelRegistry/trash.ts`) sets a `setTimeout(removePanel, expiresAt - now)` so an entry in `trashedTerminals` disappears ~20s after being trashed. The timer is the only thing that fires the removal; the Zustand panel store has no other poll driving expiry.

## Problem

When the Daintree window (a `WebContentsView` per project) is hidden — backgrounded, minimized, or the user switches to another project view — trashed terminals that should have aged out stay visible. The user comes back after a minute and sees trash that was supposed to be gone, because the expiry callback never fired on schedule.

## Root cause

Chromium 146's `IntensiveWakeUpThrottling` coalesces `setTimeout`/`setInterval` wake-ups in a hidden document to at most one per minute after the page has been hidden for ~5 minutes (and aggressively throttles before that). A 20s TTL timer therefore fires 30–60s late — or not at all until the document is shown again. The other PRs in this codebase (#3508, #4683, #4838) treat this throttling as a _feature_ to lean into for power saving; the trap here is the _inverse_: any correctness logic riding on `setTimeout` fire-time silently degrades in the background. The fix does not fight the throttling — it adds a `visibilitychange` listener that, on `document.visibilityState === "visible"`, sweeps `trashedTerminals` and removes every entry whose stored **wall-clock `expiresAt` is already in the past** (`trashedInfo.expiresAt <= Date.now()`). Correctness comes from comparing against the absolute deadline, not from when the timer happened to run.

## Lesson

- A `setTimeout`-based TTL/expiry is not reliable in a hidden renderer. If the expiry must be correct when the user returns, add a `visibilitychange` sweep that re-evaluates against a stored absolute deadline (`expiresAt` wall-clock), never against elapsed-timer assumptions.
- Store the absolute `expiresAt` in state (not just a relative delay) precisely so a late sweep can decide correctly regardless of how delayed the timer was.
- This codebase already has the sibling pattern: `TerminalAgentStateController.handleVisibilityChange` (`src/services/terminal/TerminalAgentStateController.ts:222`) sweeps stale agent-state entries on restore for the same reason. Match that structure: guard `typeof document === "undefined"` and `addEventListener` existence (the store slice runs under non-DOM vitest environments), bail unless `visibilityState === "visible"`, and provide a `cleanup*Listeners()` teardown to remove the listener.
- Make the sweep idempotent and tolerant of the timer firing too: both `scheduleTrashExpiry`'s timer callback and `sweepExpiredTrash` re-check current state (`panelsById[id]?.location === "trash"`) and clean stale/orphaned metadata, so a double-fire is a safe no-op. Wrap per-entry work in `try/catch` so one broken entry doesn't abort the whole sweep.

## Applies when

- Adding any TTL, debounce-to-removal, auto-dismiss, or scheduled cleanup in the renderer via `setTimeout`/`setInterval` (trash expiry, toast auto-dismiss, transient banners, cache invalidation, "completed" state decay).
- Working in `src/store/slices/panelRegistry/trash.ts` / `trashActions.ts`, or any Zustand slice whose only expiry driver is a timer.
- Symptom: state that "should have cleared by now" lingers, but only when the window was backgrounded / another project view was active / the laptop was idle — and clears the instant the user refocuses.
- Adding visibility-restore reconciliation; mirror `TerminalAgentStateController.handleVisibilityChange` and remember the `typeof document` / `addEventListener` guards because the slice is constructed in non-jsdom unit tests.
