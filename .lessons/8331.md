## Context

Plugins contribute actions via `PluginActionContribution`, each carrying a self-declared `danger: "safe" | "confirm"`. That classification has two real behavioral effects in the renderer: it gates the confirm dialog before dispatch, AND it excludes the action from `ActionService.repeatLast` eligibility and the `useActionPalette` MRU rail (per the Destructive Action Tiers rules). The renderer originally read the plugin's declared `danger` verbatim when building the synthetic `ActionDefinition`.

## Problem

A plugin could declare `danger: "safe"` on a genuinely destructive action (one backed by `shell:exec`, `git:write`, filesystem writes, or `agent:invoke`), and the renderer would honor it — slipping past the confirm gate, the MRU exclusion, and `repeatLast` ineligibility. The action's classification is a privilege boundary, so trusting the plugin's value is privilege escalation, not a cosmetic mislabel.

## Root cause

The trust boundary was inverted: the host (main process) is the only party that knows the plugin's actual granted capabilities (`manifest.capabilities`), yet classification authority sat with the untrusted plugin. The fix moves derivation to `PluginService.registerPluginAction`, which computes a host-authoritative `effectiveDanger` from a fixed set `CONFIRM_TRIGGERING_CAPABILITIES` (`shell:exec`, `git:write`, `fs:project-write`, `fs:user-data-write`, `agent:invoke`). Two non-obvious constraints make it correct:

- **Raise-only semantics:** `effectiveDanger = (danger === "confirm" || hasHighRiskCapability || hasCompoundElevation) ? "confirm" : "safe"`. The host can promote `safe`→`confirm` but never lower a plugin's own stricter `confirm` declaration. The plugin's `danger` becomes purely advisory.
- **Renderer fail-safe to `confirm`:** `usePluginActions` reads `descriptor.effectiveDanger ?? "confirm"` (not `danger`). A missing field — e.g. a stale descriptor from a pre-migration cached WebContentsView arriving over IPC — must default to the safe side, never silently downgrade.
- Read-only/reversible capabilities (`*-read`, `network:fetch`, `clipboard:*`) are deliberately excluded from the flat set; promoting on those alone would over-confirm and train users to dismiss the dialog.
- The host also raises danger via a compound-capability lattice (`manifestTriggersCompoundElevation`, #9247): it catches exfiltration pairs (a sensitive `*-read` + an unconstrained `network:fetch`/`shell:exec` sink) and remote-mutation pairs (`network:fetch` + a local write/shell sink) that no single flat-set capability covers — reinforcing that classification authority lives entirely in the host. A tight `scopes.network.allowedUrls` attenuates the network-driven classes.

Note the confirm dialog itself is a UI consent gate, not a hard runtime enforcement boundary (enforcement is trust-based per #5651). The durable security value is that the _classification_ — which drives MRU/repeatLast exclusion and the prompt — can no longer be forged by the plugin.

## Lesson

- For any plugin/extension-contributed metadata that drives a privilege or safety decision (danger level, capability, scope), compute the authoritative value in the host from data the host controls (granted manifest capabilities), and treat the contributor's self-declared value as advisory only.
- Use **raise-only** merge semantics so the host can tighten but never loosen a contributor's own stricter declaration.
- On the consuming side, read the host-derived field and **fail safe** (default to the most-restrictive value) when it is absent — descriptors crossing IPC or coming from a cache may predate the migration.
- When a `danger:"confirm"` classification feeds both a confirm gate and palette/MRU/`repeatLast` exclusion, remember both consequences ride on the same value — forging it is escalation on two axes, not one.

## Applies when

- Adding or changing plugin action contributions (`PluginActionContribution`, `PluginActionDescriptor` in `shared/types/plugin.ts`) or their registration in `electron/services/PluginService.ts`.
- Touching `src/hooks/usePluginActions.ts` synthetic-definition construction, `pluginConfirmStore`, or `PluginConfirmDialog`.
- Introducing any new plugin-declared field that influences a security/safety/privilege decision (capabilities, scopes, danger, trust level) — verify the host derives it rather than trusting the plugin.
- Wiring confirm gates or MRU/`repeatLast` eligibility for actions whose `danger` originates outside the trusted app code.
- Reviewing IPC-transported descriptors for "missing field silently downgrades the safe path" bugs; fail-safe defaults belong on the consuming side.
