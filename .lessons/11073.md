## Context

`WorkspaceHostProcess` (Main) wraps the workspace-host utility subprocess (`electron/workspace-host.ts`) that each project's git/file work runs in; `project:free-memory` (#10829, `electron/ipc/handlers/projectFreeMemory.ts`) evicts a background project's renderer, PTYs, and workspace-host to reclaim memory without closing the project. `dispose()` posts `{type:"dispose"}` to the child and arms a 1s backstop that used to call Electron's `UtilityProcess.kill()` if the child didn't exit in time.

## Problem

Right-clicking a background project and choosing "Free memory" froze the entire app for about a second — mouse clicks landed late or were dropped, worst in the project switcher dropdown. Issue #11069 guessed the culprit was the synchronous-looking renderer eviction (`evictProjectRenderer`) or workspace-host teardown in the IPC handler. That guess was wrong: `cleanupEntry` is `removeChildView` plus an async `wc.close()`, and `dispose()` itself just posts a message and arms a timer — nothing there blocks.

## Root cause

Two independent facts combined into a main-thread stall. First, the workspace-host's `dispose` message handler cleaned up services but never called `process.exit()` — and Electron's `ParentPort` has no `close()` method, so nothing else drains the event loop either. Second, a separate SIGTERM handler was installed on the child (`process.on("SIGTERM", ...)`) that also didn't exit; merely installing that listener suppresses Node's default terminate-on-SIGTERM behavior, so the process became un-killable by signal. When the 1s backstop in `WorkspaceHostProcess` fired `this.child.kill()`, that call runs Chromium's `Process::Terminate` (SIGTERM) followed by `base::EnsureProcessTerminated` — and per `base/process/kill.h`, "on OS X this method may block for up to 2 seconds" (a kqueue `WaitForChildToDie`, then SIGKILL, then a blocking `waitpid` reap). Main was calling this synchronously, so it blocked main itself for up to 2s waiting on a child that had no way to die. Window input routing and IPC both flow through Main, so that block reads app-wide as dropped clicks, worst in whatever surface polls or repaints most (the project switcher). A second-order bug rode along: since the child never exited, "Free memory" leaked the very process it existed to reclaim.

## Lesson

- **Never call Electron's `UtilityProcess.kill()` (or `ChildProcess.kill()`) synchronously on Main expecting it to be fire-and-forget.** On macOS it can block the calling thread up to 2s via `base::EnsureProcessTerminated`. Use a raw `process.kill(pid, "SIGKILL")` instead — non-blocking, cannot be trapped by the child — and treat the subsequent `exit` event, not the call itself, as proof of death.
- **Installing a signal handler is not the same as handling the signal.** `process.on("SIGTERM", fn)` disables Node's default terminate-on-SIGTERM; if `fn` doesn't itself call `process.exit()`, the process becomes immune to SIGTERM entirely. Any child process (utility-process, worker) that installs a SIGTERM/dispose handler must end that handler with an explicit, idempotent exit path.
- **A child needing a "just in case" exit deadline must set it with `unref()`.** `electron/workspace-host.ts`'s `shutdown()` arms `setTimeout(() => process.exit(0), 500)` unref'd — a safety net for the case where the loop doesn't drain on its own (it won't here, since `ParentPort` has no `close()`), without itself holding the process open if something else already drained it.
- **Give a cooperative shutdown a real but short window before force-killing, and clear the backstop on success.** `WorkspaceHostProcess`'s `disposeTimer` is cleared from the `exit` handler so a host that cooperates never gets signalled at all, and its own value is bounded (1s) well above the child's ~500ms exit budget so a normal write tail (the `.daintree` copy) can still finish.
- **Log the cooperative-exit path at info, not warn.** After making `dispose` reliably cause an exit, every eviction now ends in the same `exit` event a crash would use — gate on `this.isDisposed` (or equivalent) to avoid every routine "Free memory" click reading as a crash in the logs.
- **This exact pattern — blocking `child.kill()` armed as a backstop — is still present** in `electron/services/pty/PtyHostLifecycle.ts` (lines ~404, ~433), `electron/services/plugin/PluginDevWorkerHost.ts` (lines ~209/273/315), and `electron/services/assistant-host/AssistantHostProcess.ts` (line ~137); PR #11073 fixed only `WorkspaceHostProcess` and flagged the rest as known, deliberately out-of-scope follow-ups.

## Applies when

- Touching any utility-process/child-process teardown path in `electron/services/` (`WorkspaceHostProcess`, `PtyHostLifecycle`, `PluginDevWorkerHost`, `AssistantHostProcess`) or their subprocess entry points.
- Diagnosing "the UI freezes for ~1s and drops clicks" after any action that tears down a subprocess (project close, free-memory, worker recycle) — suspect a blocking `kill()` on Main before suspecting the async eviction/cleanup calls around it.
- Adding or reviewing a SIGTERM/dispose handler in any Node child/utility process — verify the handler path ends in an actual `process.exit()`, not just cleanup.
- Adding a force-kill backstop timer around any subprocess dispose — confirm it's cleared on cooperative exit and uses a raw signal, not the Electron/Node `kill()` wrapper, if it must be non-blocking on Main.
- Reasoning about Electron `UtilityProcess`/`ChildProcess` lifecycle on macOS specifically — `base::EnsureProcessTerminated`'s up-to-2s block is a Chromium-level behavior, not something Daintree code can configure away.
