## Context

#11210 tracked project-view renderer memory climbing 50-135MB/hour while agent terminals streamed truecolor syntax-highlighted output, never recovering even after terminal close/dispose (part of the same investigation as #11211 reclaim-pass and #11212 hidden-view work, both closed alongside this fix) — scrollback was capped, renderer stores were bounded, and terminal teardown was verified thorough (xterm instance, WebGL context, addons, listeners, ingest queues all disposed ~20s after close via the trash TTL), yet none of it moved the number, and #11221 traced the growth into `@xterm/addon-webgl` 0.20.0-beta.289 itself, adding `src/services/terminal/TerminalWebGLAtlasCap.ts` wired from `TerminalWebGLManager.ts`.

## Problem

A project view renderer never plateaus: a fresh view at ~450MB climbed to 1.1GB over 4 hours with 4 agent terminals running, and closing terminals didn't return the memory — the misleading part is that app-side disposal was complete and correctly ordered (this echoes #9546's xterm-6.0 core leak), so the instinct is to re-audit the teardown path, but the retained objects here aren't reachable from any per-terminal disposable at all: they live in a cache shared across terminals.

## Root cause

Two upstream facts compound.

1. `CharAtlasCache.charAtlasCache` (in `@xterm/addon-webgl`'s `CharAtlasCache.ts`) is a module-level array, not a per-terminal field: `acquireTextureAtlas()` matches entries by `configEquals` and pushes the requesting terminal into that entry's `ownedBy: Terminal[]`, and `removeTerminalFromCache()` only disposes the atlas when the terminal being disposed was the _last_ owner. Every Daintree terminal shares font/theme, so they all share one atlas entry and any surviving sibling pane keeps the whole thing alive — upstream's own comment on the interface warns "this implementation potentially holds onto copies of the terminal forever, so this may cause memory leaks." That's why growth never reverses on terminal close: the atlas isn't owned by the terminal you disposed.

2. The glyph cache inside that atlas (`TextureAtlas`'s `FourKeyMap`, keyed on code/chars + bg + fg + ext) has no per-entry eviction — the only thing that frees anything is `_evictAllPages` clearing the whole map. Pages start at 512px and only grow by merging four same-size pages into one double-size page, gated on `page.width * 2 <= TextureAtlas.maxTextureSize`. That static is process-global and Daintree never set it, so `GlyphRenderer`'s hardware probe left it at `gl.MAX_TEXTURE_SIZE` (often 16384). Merges then always succeed as pages ratchet 512→1024→...→16384, so `_evictAllPages` is never reached — truecolor plus per-token syntax highlighting maximizes distinct keys, exactly the agent-streaming workload behind #11210.

The fix (`applyAtlasPageSizeCap`) reaches the class through a live atlas instance's constructor (`addon._renderer._charAtlas.constructor`) since the class itself isn't exported by the package or its typings — a deep import would get a different class than the one the shipped bundle closed over. It must run _after_ `loadAddon`: `GlyphRenderer`'s probe assigns `maxTextureSize`/`maxAtlasPages` together, gated on `maxAtlasPages === undefined`, so writing the cap earlier gets silently clobbered. `loadAddon → activate → new WebglRenderer → _initializeWebGLState` is synchronous, so the atlas is reachable the instant `loadAddon` returns. `maxAtlasPages` is deliberately left alone — it's baked into the fragment shader and texture-unit binding at `GlyphRenderer` construction, so changing it post-hoc would desync the renderer from the shader.

## Lesson

- **A leak that survives correct per-instance disposal may live in a shared module-level cache, not a missed `dispose()` call.** If close/dispose is thorough and memory still doesn't return, check whether the library pools resources across instances (`ownedBy`-style reference counting) before re-auditing your own teardown order — same shape as #9546's undisposed-internals trap, different location (shared cache vs. unregistered disposable).
- **When a library exposes a cache-sizing knob but never set it, check what "unset" defaults to before assuming it's inert.** `maxTextureSize` unset meant "hardware maximum," the worst case for an eviction path gated on hitting that ceiling — the option wasn't neutral, it was actively disabling the only cleanup path (`_evictAllPages`).
- **Reading a private/unexported upstream class requires going through a live instance, not a deep import.** `TextureAtlas` isn't in the addon's exports or typings; `addon._renderer._charAtlas.constructor` gets the actual class the shipped bundle closed over, while deep-importing the source file gets a different, disconnected class. Guard every property read and degrade to `false` on failure, since this runs inside the WebGL attach path where a thrown error would drop the terminal to DOM rendering.
- **Ordering against upstream construction matters when a static is probed-and-cached.** `GlyphRenderer` assigns the atlas statics together gated on one being `undefined`; capping before that probe runs gets clobbered, capping after is permanent for that renderer's lifetime — any "set a library static before its own lazy hardware probe" fix needs this same after-construction check.
- **Don't touch a coupled sibling static just because it looks like the same knob.** `maxAtlasPages` sits next to `maxTextureSize` on the same class but is baked into the fragment shader at construction — capping it post-hoc would desync the shader from the JS-side page accounting.
- **This class of leak is invisible to the default test suite by construction.** CI forces `--disable-gpu` / `DAINTREE_DISABLE_WEBGL=1`, so WebGL never attaches and the atlas never allocates — same structural blind spot documented in #9546. Nightly WebGL-gated plateau validation under sustained truecolor streaming is the natural follow-up to catch a regression here.

## Applies when

- Investigating project-view (renderer process) memory growth that climbs steadily while agent terminals stream truecolor/syntax-highlighted output and doesn't recover after terminal close.
- Bumping `@xterm/addon-webgl` or `@xterm/xterm` and needing to check whether glyph-atlas behavior, `maxTextureSize`, or `_evictAllPages` reachability changed upstream.
- Touching `TerminalWebGLManager.ts`'s `loadWebglAddon`/`ensureContext` attach path or `TerminalWebGLAtlasCap.ts`'s `applyAtlasPageSizeCap`.
- Diagnosing any leak where per-instance `dispose()` is verified complete but the retained memory persists — check for a module-level/shared cache with reference counting before re-auditing teardown code.
- Reviewing a fix that writes to a third-party class's static property — confirm it runs after the library's own construction/probe path, not before.
