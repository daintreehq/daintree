## Context

#11031 added the first interactive-latency benchmarks for surfaces with zero perf coverage: fleet broadcast, diff tokenization for the review workspace (PERF-160/161/162), and command-palette fuzzy filtering (PERF-170/171). It flagged the 800-line diff tokenize (~76ms p95) and the oversized-fallback case (~447ms) as the obvious follow-up. #11037 is that follow-up: it profiled `runDiffTokenize` (`src/components/Worktree/diffTokenizer.ts`) and `rankActionMatches` (`src/lib/actionPaletteSearch.ts`) and optimized both. #11039 landed the same day with further hot-path work and re-confirmed both numbers on a wider rerun.

## Problem

The instinctive suspects for slow diff tokenization were syntax highlighting (refractor) and the word-level diff (diff-match-patch) — both third-party, both plausible, both wrong. On the oversized-fallback fixture, highlighting cost ~7ms and diff-match-patch ~22ms of a 414ms tokenize: the two things everyone would optimize first accounted for under 8% of the time. The other 92% (~377ms) was inside `react-diff-view`'s own `tokenize()`, a dependency nobody suspected because its job — walk a token tree and reshape it — looks like it should be linear.

## Root cause

`react-diff-view`'s internal `normalizeToLines` rebuilds its whole accumulator array with spreads on every token path (quadratic in path count); its `backToTree` runs a lodash deep-equal per attached node while reassembling the tree. Neither cost is visible from outside — the public contract is just `tokenize(hunks, options)` returning `HunkTokens` — so profiling by call stack, not by "which npm package is this," was the only way to find it. The fix reimplements both as `tokenizeFast` in a new `diffTokenizePipeline.ts`: single-pass path collection instead of per-path spreads, and a merge rule (`backToTreeChildren`) that only coalesces adjacent same-type text leaves instead of a general deep-equal. Everything else — refractor highlighting, and critically the library's own `markEdits`/`pickRanges` enhancers — stayed untouched, so ranking/marking semantics couldn't drift from react-diff-view's real output. Correctness was proven, not assumed, with a ten-case parity suite (`src/components/Worktree/__tests__/diffTokenizePipeline.test.ts`) running both `tokenizeFast` and the library's real `tokenize` on the same hunks and asserting `toEqual` — multi-hunk gaps, uneven delete/insert blocks, nested grammars, no highlighting, extra picked ranges, deep hunk offsets, unicode/CR content, no trailing newline, empty hunks. Result: PERF-161 (oversized fallback) 410ms → 64ms (85% faster), PERF-160 (800-line) 66ms → 35ms (48% faster); the five baselines were reseeded to the new p95s with the same ~2x CI headroom, so a regression toward the old numbers now trips `scripts/perf/config/budgets.json`. The palette hotspot was parallel: `rankActionMatches` re-sorts the ~380-action catalog every keystroke, and the real cost was `Intl.Collator.compare` inside the sort comparator's tiebreak (orders of magnitude pricier than a numeric compare), not the per-character regex tests that also got replaced. Fixed by computing one stable-collator-sorted rank array per catalog and comparing integers in the hot comparator, cached in a `WeakMap` keyed by the items array and invalidated by an identity-snapshot check (element-by-element `===`) so in-place mutation can't serve stale ranks.

## Lesson

- **Profile by call stack, not by intuition about which layer "should" be slow.** Highlighting and diff-match-patch were the obvious suspects and were both innocent (~7ms + ~22ms of 414ms); the real cost was two internal functions inside a dependency (`normalizeToLines`, `backToTree`) with no name in the public API. If a wrapped library call is slow, profile through it before assuming the cost is in your adapter or the "expensive-sounding" step.
- **When reimplementing third-party internals for speed, keep the library's own public behavior-defining calls (`markEdits`, `pickRanges`) as the seam** — only replace the plumbing around them, so ranking/marking semantics ride on code you didn't touch and can't silently diverge.
- **Prove behavioral parity with a deep-equal suite that runs both implementations on the same inputs**, not before/after eyeballing. Ten fixture shapes (`src/components/Worktree/__tests__/diffTokenizePipeline.test.ts`) is the right granularity: normal cases plus the edge shapes a naive port gets wrong (unicode/CR, no trailing newline, deep hunk offsets, empty hunks). Any future change to `diffTokenizePipeline.ts` must keep passing this suite or it has drifted from react-diff-view's contract.
- **In a hot per-keystroke comparator, suspect the tiebreak, not the primary sort key.** `rankActionMatches` looked fine at a glance (numeric score compare first); the buried `Intl.Collator` tiebreak was the actual cost. Cache the collator-derived rank (a `WeakMap` keyed on the items array) rather than avoiding the collator, so ordering stays exact — but guard the cache with an explicit staleness check (length + element-by-element `===` against a stored snapshot), since reference identity alone misses in-place mutation like `items.reverse()`.
- **When a perf fix changes a metric's real cost, reseed the baseline and tighten the budget together** (`scripts/perf/config/{baseline.*.json,budgets.json}`) — an unmoved budget after an 85% speedup leaves no gate against regressing back toward the old number.

## Applies when

- Diagnosing slow diff rendering/tokenization in the review workspace, or any "why is this npm-library call slow" investigation — profile inside the library before optimizing your own call site.
- Touching `diffTokenizePipeline.ts`, `diffTokenizer.ts`, or `diffRefractor.ts` in `src/components/Worktree/` — changes must keep passing the parity suite in `src/components/Worktree/__tests__/diffTokenizePipeline.test.ts`.
- Touching `rankActionMatches`/`scoreAction` in `src/lib/actionPaletteSearch.ts`, or any hot per-keystroke comparator sorting with `Intl.Collator` or another expensive tiebreak.
- Adding a `WeakMap`/`Map` cache keyed on an array or object the caller might mutate in place — verify there's a staleness check, not just a reference-identity hit.
- Writing or updating `scripts/perf` benchmarks/baselines after a hot-path optimization — reseed baseline and budget together so the win is actually gated.
