## Context

Dev-preview panels never load the dev server directly: `DevPreviewProxyService` (httpxy) gives each panel a stable `dp-<token>.localhost:43000` origin (#9100) and reverse-proxies HTTP + WebSocket to the allocated upstream port. Separately, `DevPreviewSessionService` gates the panel's RUNNING state on a readiness probe (`DevPreviewReadinessProbe`) against the predicted `localhost` URL. #9752 was the next failure in the chain after the pnpm port-injection fix (`a8d8c8380`, follow-up to #9134): ports finally injected correctly, Vite bound the right port — and the proxy still couldn't reach it.

## Problem

Against a healthy Vite 8.0.14 / SvelteKit project on macOS, the panel header showed RUNNING but every proxied request returned 502 "The dev server isn't responding." The misleading part was the passing probe: the session pipeline said the server was up (it was), so the 502 looked like a proxy bug, a port mismatch, or a wedged server — not an address-family split. The curl matrix from #9747 told the real story: `localhost:5762` → 200, `[::1]:5762` → 200, `127.0.0.1:5762` → connection refused; `lsof -nP -iTCP:5762 -sTCP:LISTEN` showed a single IPv6 `[::1]` row.

## Root cause

One constant, `PROXY_HOST = "127.0.0.1"`, served two roles with opposite requirements: the proxy's own `server.listen()` bind address AND the upstream connect target passed to `proxy.web()` / `proxy.ws()`. Vite 8 resolves its default `localhost` host through the OS resolver; on macOS that returns `::1` first, so Vite binds IPv6-only — nothing listens on IPv4 loopback at all. The readiness probe built its URL from `predictedUrl` with hostname `localhost`, and Node's Happy Eyeballs (`autoSelectFamily`, default since Node 20) happily connected over `[::1]` → probe passes → RUNNING. The proxy dialed the literal `127.0.0.1` → `ECONNREFUSED` on every request → httpxy surfaces 502. Health signal and gated data path resolved the upstream differently, producing a split-brain that no amount of staring at the proxy logic alone would explain.

The fix (merged 2026-06-04, still live at `DevPreviewProxyService.ts:21/26`) splits the constant by role: `PROXY_LISTEN_HOST = "127.0.0.1"` — the bind stays a literal because narrow reachability is deliberate — and `UPSTREAM_HOST = "localhost"` — a hostname, so Happy Eyeballs tries whichever family the dev server actually bound, IPv6-first with IPv4 fallback. A knock-on: httpxy rewrites the Host header to the target, so upstreams now see `localhost:<port>` instead of the `dp-*` subdomain — the test pinning `seenHost` to `127.0.0.1` had to change. Later hardening kept both constants but generalized around them: the upstream target gained `${scheme}://` for https dev TLS, and `DevPreviewReadinessProbe.buildReadinessUrls` now explicitly fans `localhost` out to `127.0.0.1` and `[::1]` candidates, so today the probe side is family-exhaustive too.

## Lesson

- **A readiness probe must exercise the same dial string as the traffic it gates.** When "probe says healthy but the gated path fails," diff the two connect targets (hostname AND resolution behavior) before debugging either endpoint — `localhost` vs `127.0.0.1` are different network paths on a single-family bind.
- **Never share one HOST constant between "where I listen" and "whom I connect to."** They want opposite things: a listen address should be a literal (narrow, deliberate bind — `PROXY_LISTEN_HOST`), a connect target should be a hostname (`UPSTREAM_HOST = "localhost"`) so Node's `autoSelectFamily` finds the bound family. Any constant appearing in both a `server.listen()` and a proxy/connect target is this bug waiting.
- **Do not assume local dev servers dual-stack.** Vite 8 on macOS binds `[::1]`-only by default because `localhost` resolves IPv6-first. The fix is a hostname target, not `family: 6` — pinning IPv6 just mirrors the bug for IPv4-only binds (Docker port-forwards, older tools).
- **The 30-second diagnostic for this class:** curl the triple `localhost` / `127.0.0.1` / `[::1]` on the upstream port, then `lsof -nP -iTCP:<port> -sTCP:LISTEN` — an IPv6-only bind shows as a single IPv6 row while the hostname curl succeeds.
- **Tests for single-family behavior must prove the fixture is single-family.** The PR binds upstreams with `{ host: "::1", port: 0, ipv6Only: true }` and sanity-asserts `expectIpv4Refused(port)` before the real assertion — a dual-stack fixture would pass even with the old broken target. Environments that can't bind `[::1]` are probed once at module load and skipped via `it.skipIf(!canBindIpv6Only)` instead of reporting a misleading pass.
- **Rewriting a proxy's target host rewrites the upstream Host header** (httpxy derives Host from the target). Upstream dev servers with host allow-lists now see `localhost:<port>`; any assertion or allow-list keyed on the old literal breaks.

## Applies when

- Touching `DevPreviewProxyService`, `DevPreviewReadinessProbe`, or any main-process service that both listens on loopback and dials a loopback upstream (port-forwards, MCP endpoints, plugin dev workers).
- Diagnosing "panel says RUNNING but the webview 502s," or any `ECONNREFUSED` against a server that curl-via-`localhost` says is up.
- Adding a health/readiness probe that gates a proxy, webview load, or forwarded port — verify the probe and the gated path share hostname and resolution behavior.
- Hardcoding `127.0.0.1` (or `::1`) as a connect target anywhere — on macOS with modern tooling the upstream may only exist on the other loopback family.
- Writing tests around address-family behavior — bind `ipv6Only: true`, assert the other family refuses, and skip (not pass) where `[::1]` can't bind.
