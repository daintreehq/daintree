## Context

`HelpSessionController` drives the Daintree Assistant's launch FSM (`idle` → `version-checking` → `provisioning` → `live`, etc.) behind `HelpPanel`; each project runs in its own `WebContentsView` (`ProjectViewManager`), and switching away parks the outgoing view in an LRU cache (`ProjectViewSwitchController`). A 90s dead-man watchdog, `_armLaunchWatchdog` (`LAUNCH_WATCHDOG_MS = 90_000`), exists specifically to reap a launch that hangs mid-flight: reset the phase and surface a retryable error via `_surfaceLaunchError`.

## Problem

Issue #10739: switching to another project mid-launch and back sometimes left the Assistant panel stuck on its loading skeleton (`HelpLaunchingState`) forever — not a crash, not visual corruption, just permanently unresponsive, well past the 90s watchdog window. A working watchdog with a sane timeout made this look like a rare one-off rather than a structural gap in front of the reporter; two independent mechanisms had to both fail before the hang became permanent, and the panel gave zero visible signal that anything had gone wrong.

## Root cause

Two structural facts compound. First, Chromium freezes a parked `WebContentsView`'s renderer timers, so a `setTimeout`-based watchdog armed before the switch away never fires — not delayed, dead. Only a main-process-driven signal delivered as IPC after the view wakes is reliable; the repo already has one, `CHANNELS.APP_VIEW_REVEALED` (`app:view-revealed`), sent by `ProjectViewSwitchController` once it reveals the cached view and re-confirms `activeProjectId === projectId`, and it already backs the identical stuck-flag-across-park pattern in `useClearSwitchBusyStateOnReveal`. Second, even once revealed, `_maybeAutoLaunch` short-circuits on `document.hidden`, so the normal auto-launch entry path never retries a launch interrupted by the switch away — the reap direction and the retry direction were both closed.

Wiring a new listener to `app:view-revealed` was not automatically sufficient, either. `HelpPanel` already had a reveal-driven repaint effect subscribed to `onViewRevealed`, but its `useEffect` dependency array was `[controller, terminalId, terminal]` — gated on `terminalId`. A stuck auto-launch by definition has no terminal bound yet, so `terminalId` is null and that effect's registration path is exactly the one case it needed to fire for. PR #10741 added a second, separate effect gated only on `isOpen` so it stays subscribed through the terminal-less stuck state. Recovery is also intentionally silent: `handleViewRevealed` reaps and re-drives via `_maybeAutoLaunch` without calling `_surfaceLaunchError`, and only fires when `_hasAutoLaunched` is true and `terminalId` is null; a manual `selectAgent()` pick and the `hibernating` phase (a live terminal mid graceful-shutdown) are both excluded.

## Lesson

- **A renderer `setTimeout` armed on a per-project `WebContentsView` cannot be trusted as a dead-man switch across a project-switch park.** Reuse `app:view-revealed` — a main-process signal fired only after the cached view is confirmed foreground again — for anything that must recover after a background park, never a renderer timer or bare `visibilitychange`.
- **Before wiring a new reveal-recovery listener, audit existing effects gated on the same signal for a dependency that's null exactly during the failure you're chasing.** The pre-existing repaint effect subscribed to `onViewRevealed` too, but its `terminalId` dependency meant it silently never mounted for the terminal-less stuck-launch case — the fix needed a second listener, not a broadened one.
- **A reap path that resets FSM state must unwind every side effect the original path minted, not just the visible phase.** #10707 found the watchdog reset the phase but left the just-minted MCP bearer token unrevoked, plus unconditional `_pendingSessionId = null` assignments that could clobber a newer launch's guard; the fix ties nulling to a session-id ownership check and adds `HelpSessionService.sweepOrphanSessions` as a 30-min-ceiling/5-min-sweep backstop for whatever a renderer crash still misses.
- **Scope a stall-recovery reap to exactly the stuck condition, not to "any non-idle phase."** `handleViewRevealed` only reaps when `_hasAutoLaunched` is true and no `terminalId` is bound, and explicitly excludes `hibernating` — reaping a manual launch or a graceful-shutdown-in-progress terminal would discard state the user didn't ask to lose.
- **Don't let a stateful FSM fork into near-duplicate methods for "the auto path" vs "the manual path."** #10714 found `_executeAutoLaunch` and `_executeLaunch` (~230 lines each) had already drifted — the auto path was missing the gen-ownership release in its `finally` block — purely from being maintained as two copies; unify into one parameterized method instead.

## Applies when

- Touching `HelpSessionController`'s launch FSM (`_armLaunchWatchdog`, `_maybeAutoLaunch`, `handleViewRevealed`, `_executeLaunch`) or `HelpPanel`'s `onViewRevealed`-gated effects.
- Adding any renderer-side dead-man timer/watchdog whose owning component lives inside a per-project `WebContentsView` — `ProjectViewManager`'s LRU parking freezes it the same way.
- Diagnosing a UI state that "should have timed out by now" but never did after a project switch away and back — check whether the timer was armed on a view that got parked mid-wait, and whether an `app:view-revealed` listener exists but is gated on a field that's absent in the stuck state.
- Reviewing any watchdog/error-recovery path that resets a phase or status field — verify it also releases every resource (tokens, ids, re-entrancy guards) the original path minted, not just the field a spinner reads.
- Considering two "auto" vs "manual" (or similarly forked) copies of the same stateful flow — prefer one parameterized function; #10714 is the concrete drift example.
