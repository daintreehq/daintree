## Context

`AnimatedLabel` (`src/components/ui/AnimatedLabel.tsx`, introduced by the micro-animations batch #5733) is the crossfade primitive for short labels and ticking counts: outgoing and incoming spans share one CSS grid cell, and the `label-swap-in`/`label-swap-out` keyframes in `src/index.css` animate the swap. It backs always-visible count surfaces — `PanelHeader` Zen-mode active/working counts, `FleetCountChip`, `GettingStartedChecklist`, `EmptyState`, and the `Waiting`/`Status`/`BackgroundContainer` layout chips. As shipped in #5733, the keyframes animated `filter: blur(2px)` → `blur(0)` alongside opacity/translateY, and both `.animate-label-swap-*` classes declared `will-change: opacity, transform, filter`.

## Problem

Count-chip text read thin and soft — not just mid-animation, but at rest, after the crossfade had visibly settled (#9615). The symptom pointed everywhere except the cause: soft glyphs on a chip look like a font-rendering, theme, zoom/DPR, or WebGL problem, and nothing about a settled label suggests "animation bug." Frame rate was fine throughout, so no perf tooling flagged it either — this was a pure text-fidelity defect with an invisible mechanism.

## Root cause

Chromium renders text with subpixel (LCD) antialiasing only on the normal paint path where it can blend glyphs against a known-opaque background. Any CSS `filter` — including the identity endpoint `blur(0)` — forces the element through a composited filter pass where that guarantee is gone, so glyphs rasterize with grayscale AA and read visibly thinner/softer. Two details made the degradation outlive the 150ms swap. First, `will-change: filter` in the `.animate-label-swap-*` classes promotes the span for as long as the class is applied, independent of whether the keyframe is mid-flight, and `animation-fill-mode: both` holds the 100% frame (`filter: blur(0)` — still an active filter chain, not `filter: none`) after the motion completes. Second, `AnimatedLabel` remounts its spans and restarts the animation on every value change (the `generation` counter), so a chip whose count ticks frequently spends most of its life with the class applied — on an always-on chip the softness is effectively permanent.

The fix (#9632) is subtractive: delete the `filter` lines from both keyframes and drop `filter` from both `will-change` declarations. `opacity` + `translateY` carry the same crossfade; they also composite, but only transiently during the swap, and their settled endpoints (`opacity: 1`, `translateY(0)`) impose no filter pass — the resting frame renders on the normal path with full subpixel AA. A 150ms AA wobble during motion is imperceptible; a filter held at rest is not. The now-dead `filter: none !important` in the reduced-motion override was removed in the same pass.

## Lesson

- **Never put `filter` (or `will-change: filter`) in keyframes or animation classes applied to text-bearing elements.** `blur(0)` is not "no filter" — any filter value routes the glyphs through a composited filter pass that drops subpixel AA. Blur-in/blur-out is a common "juicy" crossfade recipe; in this codebase it is banned for text, and opacity+transform carry the motion instead.
- **Animation endpoints matter as much as the motion.** `animation-fill-mode: both` holds the 100% keyframe after the animation ends, so whatever property state the keyframe settles on IS the resting render state while the class remains. Audit what the final frame leaves applied, not just what moves.
- **Soft/thin glyphs at rest → check for compositing triggers before blaming fonts or themes.** Inspect computed `filter`, `will-change`, and DevTools layer borders on the affected element. The cause can live in an animation the element isn't visibly running — especially on frequently-restarting primitives like `AnimatedLabel`, where the animating class is applied most of the time on busy counters.
- **Enforce CSS policy with source-level contract tests — JSDOM never applies stylesheets.** The regression guard in `AnimatedLabel.test.tsx` ("AnimatedLabel CSS contract") reads `src/index.css` directly, extracts each keyframe/class block with a brace-depth scanner keyed on headers like `@keyframes label-swap-in`, and asserts no `filter:`/`blur(` inside. Asserting rendered styles in JSDOM would silently pass forever; asserting the source actually bites.
- **When deleting a CSS property from an animation, sweep its overrides.** The `prefers-reduced-motion` block carried `filter: none !important` solely to neutralize the blur; leaving it would be dead config implying the filter still exists. #9632 removed it in the same diff.

## Applies when

- Adding or polishing motion on labels, counts, chips, badges, or any text — especially crossfades tempted to use blur, glow, drop-shadow, or other `filter` effects for "smoothness".
- Diagnosing blurry, thin, or soft text that persists when nothing appears to be animating — particularly on `AnimatedLabel` consumers (`PanelHeader`, `FleetCountChip`, layout containers) or other frequently-restarting animated elements.
- Touching the `label-swap-*` keyframes, `.animate-label-swap-*` classes, or the reduced-motion block in `src/index.css` — the CSS-contract test in `AnimatedLabel.test.tsx` fails on any reintroduced `filter`.
- Writing a test to lock in a stylesheet-level rule — JSDOM can't see CSS, so assert against the CSS source text, following the `extractBlock` pattern in `AnimatedLabel.test.tsx`.
- Reviewing any keyframe or `will-change` declaration that names `filter` on an element containing text, or any `animation-fill-mode: both`/`forwards` whose final frame leaves a compositing trigger applied.
