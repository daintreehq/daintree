## Context

Project switches had a visible overlay that was blocked by terminal scrollback deserialization. The `getSerializedStates` IPC fetch was on the critical path inside `stateHydration`, meaning the switch overlay stayed visible until all scrollback data had been fetched and deserialized — even for terminals in non-visible worktrees.

## Problem

`stateHydration/index.ts` issued a batch IPC call for all terminal scrollback states upfront before the UI rendered. This added significant latency to every project switch because scrollback deserialization is expensive and was done synchronously in the critical path before the overlay could dismiss.

## Root cause

The hydration logic conflated two distinct concerns: restoring layout/panel state (needed immediately) and restoring scrollback history (only needed when the user actually looks at a terminal). Both were bundled into one synchronous blocking operation.

## Lesson

Separate critical-path UI restoration from deferred background work. The pattern used here:

1. Restore screen state and layout immediately (critical path — allows overlay to dismiss)
2. Once panels are restored, every terminal's scrollback task — active worktree or not, there is no critical/deferred split anymore — is handed to `scheduleScrollbackRestore` (src/utils/stateHydration/scrollbackRestoreScheduler.ts:28), called from src/utils/stateHydration/index.ts:507
3. Each task is dispatched via `scheduleBackgroundFetchAndRestore` (src/utils/stateHydration/batchScheduler.ts:63), which uses `scheduler.postTask({ priority: "background" })` (src/utils/stateHydration/batchScheduler.ts:71) — NOT `requestIdleCallback`, whose deadline-based callbacks are unreliable in Chromium for restore work
4. There is no lazy on-interaction mode: a task that fails is left in `"none"` state, surfaced as an inline error via `setScrollbackRestoreError`, and re-queued only on explicit user action — the `BatchScrollbackRestoreBar` retry button calls `retryFailedScrollbackRestoreBatch` (src/utils/stateHydration/scrollbackRestoreScheduler.ts:131), which re-submits the original tasks (captured at schedule time, keyed by terminal id) through the same background-priority path

Each terminal instance tracks restore lifecycle in `managed.scrollbackRestoreState: "none" | "pending" | "in-progress" | "done"` (src/services/terminal/types.ts:212) so callers — including the scheduler's own re-submit gate (`scrollbackRestoreState !== "none"`) and the retry path — know whether restore is pending, in-progress, or complete. The actual fetch+replay lives in `TerminalRestoreController` (src/services/terminal/TerminalRestoreController.ts).

## Applies when

- Any IPC operation that blocks UI rendering during a transition or switch
- Multi-worktree scenarios where non-active worktrees' data is fetched eagerly
- Terminal or panel hydration that mixes layout reconstruction with expensive data loading
