## Context

Project switches had a visible overlay that was blocked by terminal scrollback deserialization. The `getSerializedStates` IPC fetch was on the critical path inside `stateHydration`, meaning the switch overlay stayed visible until all scrollback data had been fetched and deserialized — even for terminals in non-visible worktrees.

## Problem

`stateHydration/index.ts` issued a batch IPC call for all terminal scrollback states upfront before the UI rendered. This added significant latency to every project switch because scrollback deserialization is expensive and was done synchronously in the critical path before the overlay could dismiss.

## Root cause

The hydration logic conflated two distinct concerns: restoring layout/panel state (needed immediately) and restoring scrollback history (only needed when the user actually looks at a terminal). Both were bundled into one synchronous blocking operation.

## Lesson

Separate critical-path UI restoration from deferred background work. The pattern used here:

1. Restore screen state and layout immediately (critical path — allows overlay to dismiss)
2. `splitSnapshotRestoreTasks` (src/utils/stateHydration/batchScheduler.ts:16) partitions restore work into `criticalTasks` (active worktree's terminals) and `deferredTasks` (everything else), and `scheduleScrollbackRestore` (src/utils/stateHydration/scrollbackRestoreScheduler.ts:19) dispatches each batch by mode from src/utils/stateHydration/index.ts:416-440
3. Critical tasks run in `"background"` mode via `scheduleBackgroundFetchAndRestore`, which uses `scheduler.postTask({ priority: "background" })` (src/utils/stateHydration/batchScheduler.ts:69-77) — NOT `requestIdleCallback`, whose deadline-based callbacks are unreliable in Chromium for restore work
4. Deferred (non-active-worktree) terminals run in `"lazy"` mode via `registerLazyScrollRestore` (src/utils/stateHydration/batchScheduler.ts:84), which restores on first DOM interaction — a one-shot `wheel` or a `PageUp`/`PageDown` keydown on `managed.hostElement` — instead of fetching eagerly

Each terminal instance tracks restore lifecycle in `managed.scrollbackRestoreState: "none" | "pending" | "in-progress" | "done"` (src/services/terminal/types.ts:140) so callers (and the lazy trigger's `!== "pending"` guard) know whether restore is pending, in-progress, or complete. The actual fetch+replay lives in `TerminalRestoreController` (src/services/terminal/TerminalRestoreController.ts).

## Applies when

- Any IPC operation that blocks UI rendering during a transition or switch
- Multi-worktree scenarios where non-active worktrees' data is fetched eagerly
- Terminal or panel hydration that mixes layout reconstruction with expensive data loading
