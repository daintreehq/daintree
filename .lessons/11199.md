## Context

`PtyPool` (`electron/services/PtyPool.ts`) keeps a small warm pool of already-spawned PTY processes keyed by cwd+env hash so new terminals feel instant; `acquireByKey` hands a pooled entry off to become a real, long-lived user terminal, while `dispose()`, `evictIfAtCapacity()`, and `drainAndRefill()` tear pool entries down. Separately, `electron/pty-host/handlers/connection.ts` and `electron/pty-host.ts` manage `MessagePort` connections between the pty-host utility process and each renderer window/terminal-worker. PR #11199 added a long-session benchmark (`e2e/full/resilience/memory-growth-perf.spec.ts`, `npm run perf memory-growth`) simulating hours of real usage — project switching, terminal churn, scrollback saturation — in one process tree.

## Problem

The pty-host's open file descriptor count grew by ~60 every benchmark cycle, unbounded, with no crash — just a slow climb visible only in an FD count, not in any user-facing symptom. Every existing teardown path in `PtyPool` looked correct: `dispose()`, `evictIfAtCapacity()`, and `drainAndRefill()` all faithfully disposed `entry.dataDisposable`. Nothing in code review pointed at PtyPool because the paths people check for leaks — the explicit cleanup paths — were clean. Renderer heap also grew slightly across cycles, which looked like a second leak but wasn't.

## Root cause

Two independent, additive causes combined into the descriptor growth. First, an upstream bug: node-pty before `1.2.0-beta.14` leaks file descriptors via kqueue on macOS on process spawn/exit, so every `PtyPool` refill cycle bled descriptors regardless of Daintree's own code — fixed only by bumping `node-pty` from `1.2.0-beta.12` to `1.2.0-beta.14` (no app-code fix exists, same shape as the xterm 6.1 upstream-bump trap in #9546).

Second, and more instructive: `PooledPty` tracked a `dataDisposable` for the `onData` listener and disposed it everywhere — but `ptyProcess.onExit()`'s returned disposable was simply discarded, never stored, never disposed, on _any_ path, including `acquireByKey` where a pooled PTY graduates into a real terminal that can live for hours. That closure captures `entry`, `id`, `epoch`, and `this` (the whole `PtyPool` instance, its `pool` Map, `refillPool()`, `recordFastExit()`) and stayed registered on the real `ptyProcess` for the terminal's entire lifetime — on the _success_ path, not a failure path. The fix adds `exitDisposable` alongside `dataDisposable`, disposes it at the top of `acquireByKey` (right after `this.pool.delete(id)`), and routes every teardown path through a new shared `disposePooledListeners(entry)` helper so both halves of the pair are always disposed together.

The same asymmetry existed in `connection.ts`: the paired `"message"` listener was stored as `handler` and correctly removed via `conn.port.removeListener("message", conn.handler)` in `disconnectWindow`/`disconnectTerminalWorkerPort` (`electron/pty-host.ts`), but `"close"` was registered as an anonymous inline arrow passed straight to `receivedPort.on("close", () => {...})` — with no captured reference, `removeListener` could never target it, so every disconnect+reconnect (project switch, window reload) permanently added one more listener. Fixed by naming it `closeHandler`, storing it on `RendererConnection`/`TerminalWorkerConnection` (`electron/pty-host/handlers/types.ts`), and removing it alongside `handler` in both functions.

A third, smaller fix: `FdMonitor` took its baseline FD count once at construction, before Electron's startup FD churn settled, causing false-positive leak warnings early in a session; `calibrationChecksRemaining` (default 5) now lets the baseline float upward for the first N checks before treating growth as signal.

## Lesson

- **One half of a listener pair disposed everywhere gives false confidence, not real cleanup.** `dataDisposable` was disposed on every path, so `PtyPool` looked leak-free; `onExit`'s disposable wasn't tracked at all. Seeing one half of a pair (`onData`/`onExit`, `"message"`/`"close"`) carefully disposed is not evidence the other half is — grep the other registration call and confirm it stores and disposes its own disposable.
- **Audit the success/handoff path, not just teardown.** The leak was in `acquireByKey` — where a pooled PTY graduates to a live terminal, code that reads as "it worked," not as cleanup. `dispose()`/`evictIfAtCapacity()`/`drainAndRefill()` all got reviewed because they look like cleanup; the acquire path didn't, and that's where the leak lived.
- **An anonymous inline listener passed straight to `.on(...)` is a leak-in-waiting** — with no captured reference, `removeListener` can never target it later. Grep for `.on("close"`/`.on("message"` with no assigned variable in pty-host/IPC connection code; every removable listener needs a named, stored handler.
- **Check the installed `node-pty` version against upstream release notes before blaming app code for a PTY fd leak** — same shape as xterm in #9546: no app-side disposal fixes a leak inside the native layer. Here it was a macOS kqueue bug fixed only in `1.2.0-beta.14`.
- **A leak detector's baseline must be taken after the system reaches steady state, not at cold start.** `FdMonitor`'s one-shot construction-time baseline caused false leak warnings during startup churn; `calibrationChecksRemaining` (float the baseline up for the first N checks) is the reusable pattern for any "measure once, compare forever" monitor.
- **Don't chase a rising number without object-level evidence.** ~90% of this benchmark's residual renderer heap growth was V8 JIT code/feedback metadata from repeatedly exercising cold paths, confirmed by heap snapshots showing no growing population of closed xterm/WebGL instances — call it a leak only once a snapshot shows retained objects.

## Applies when

- Touching `electron/services/PtyPool.ts` (`acquireByKey`, `evictIfAtCapacity`, `drainAndRefill`, `disposePooledListeners`) or any pool that hands a live resource from an internal registry to a longer-lived external owner.
- Touching MessagePort lifecycle in `electron/pty-host/handlers/connection.ts` or the disconnect functions in `electron/pty-host.ts` (`rendererConnections`, `terminalWorkerConnections`).
- Diagnosing pty-host (or any Electron utility-process) fd growth across repeated project-switch/terminal-churn cycles — use `npm run perf memory-growth` / `memory-growth-compare` instead of eyeballing RSS.
- Bumping `node-pty` — check its changelog for platform-specific (macOS kqueue) descriptor fixes before assuming any fd growth is app-owned.
- Reviewing any `addEventListener`/`.on()` pair added together — verify both halves have a stored, removable reference and both are disposed on every path that disposes either, especially the success/handoff path.
