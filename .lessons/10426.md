## Context

The full-codebase performance audit (#10426, 79 of 97 findings, 50 commits; boot/preload siblings #10402/#10405/#10409/#10411) turned React Compiler memoization back on across the renderer's hot paths. Compiler coverage is tracked per-file in `scripts/baselines/compiler-bailout-baseline.json`, gated by `scripts/check-compiler-budget.mjs` (`npm run compiler-budget:check` after a `vite build`) — a build-gated check, NOT part of `npm run check` or CI's `ci-ok`.

## Problem

Hot components silently weren't memoizing despite stable inputs. The headline case: the 1,158-line `useContentGridContext` hook assembles a 40-field context object consumed by every grid panel, and that object got a fresh identity on every grid render — churning all consumers — because the compiler had bailed the entire hook. The bailout is invisible at runtime (correct output, just no memoization), so it reads as ordinary code.

## Root cause

Three innocuous syntax patterns each disable React Compiler memoization for the ENTIRE enclosing function, not just the offending expression: a statement-level `try`/`catch`/`finally` block, a raw dynamic `import()` expression, and a `++`/`--` increment. `useContentGridContext` had a statement-level try/catch (the `handleAddTabForPanel` body); `AppInner` had `void import(...)` inside effects; sampling paths used `++echoProbeCounter`. The fix in every case is to HOIST the offender to module scope: the try/catch became a module-level `export async function addTabForPanel(panel)` with `handleAddTabForPanel` now a one-line `useCallback((panel) => addTabForPanel(panel), [])`; loaders became module consts (`const load = () => import(...)`), keeping specifiers static for chunking while the component compiles; counters moved to module-scope `let` (`src/clients/terminalClient.ts`).

The subtler half: compiling is NOT always the goal. `useContentGridContext` still ships `"use no memo"` on purpose. It uses the #8593 pattern — subscribe to narrow STRUCTURAL fields, then read the full panel map NON-reactively via `panelStoreApi.getState()` at evaluation time. The compiler can't see those untracked reads, so a compiled build cached derivations against stale state and freshly-spawned panels never appeared in the grid (caught only by core E2E). Same class: `useColdNumberGap` (#8079) reads `prev.current` at render as its whole mechanism; compiling it errors or breaks the lag. Both must keep `"use no memo"`.

## Lesson

- **A statement-level `try`/`catch`/`finally`, a raw `import()` expression, or a `++`/`--` increment anywhere in a component/hook body bails React Compiler for the WHOLE function** — not just the expression. Hoist the offender to module scope: try/catch → a module-level async fn the component calls; `import()` → `const load = () => import(...)`; counter → a module-scope `let`. Living examples carry a `// … bails React Compiler memoization for the whole …` comment (`Toolbar.tsx`, `TerminalSearchBar.tsx`, `useTerminalLogic.ts`, `useWorktreeActions.ts`, `NotificationCenterEntry.tsx`, `WslGitBanner.tsx`).
- **Do NOT "fix a bailout" by forcing compilation when the component deliberately reads UNtracked reactivity.** Hooks on the #8593 narrow-subscribe / wide-`getState()` pattern (`useContentGridContext`) or render-time `ref.current` reads (`useColdNumberGap`, #8079) MUST keep `"use no memo"` — the compiler caches derivations against state it can't see, producing stale UI. The deliberate opt-out is correct, and registers as a `skip` (not `error`) in the baseline.
- **Clear the syntax obstacle even on an intentionally-opted-out hook** — it keeps `"use no memo"` the SOLE remaining reason, so a future migration to tracked selectors is a one-directive change. `useContentGridContext` deliberately keeps BOTH the module-hoisted try/catch AND `"use no memo"` (the trailing `"use memo"` line is documentary, overridden by the `"use no memo"` above it).
- **Compiler coverage is a tracked budget.** `scripts/check-compiler-budget.mjs` diffs `scripts/baselines/compiler-bailout-baseline.json` and fails on any per-file regression. It needs a `vite build` and is NOT in `npm run check`/CI — rebank with `npm run compiler-budget:update` after intentional changes; never let a stray `++`/try/`import()` move a file from `success` to `error`.
- **Bundling twin (#10405, mirrors #8852):** Vite's catch-all vendor `codeSplitting` group sweeps lazy-ONLY packages into the EAGER vendor chunk unless it sets `entriesAware: true` + `entriesAwareMergeThreshold: 0`. `React.lazy`-ing a component saves nothing if its deps still land eager — verify absence from the eager closure in the build manifest.

## Applies when

- Adding a `try`/`catch`/`finally`, a dynamic `import()`, or a `++`/`--` counter to any hot renderer component/hook — confirm `compiler-bailout-baseline.json` didn't flip the file from `success` to `error`.
- Diagnosing a component that churns a context/object identity every frame despite unchanged inputs — suspect a whole-function compiler bailout before re-auditing selectors and dependency arrays.
- Tempted to delete a `"use no memo"` to "improve coverage" — first confirm the hook doesn't read `store.getState()` untracked (#8593) or `ref.current` at render (#8079); those opt-outs are load-bearing and removing them ships stale UI.
- Touching `useContentGridContext.tsx`, `useColdNumberGap.ts`, or any hook mixing narrow Zustand subscriptions with `panelStoreApi.getState()` reads; or adding `React.lazy`/dynamic imports for first-paint savings (verify deps land in a deferred `entriesAware` chunk).
