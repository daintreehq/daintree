## Context

`electron/store.ts` exposes a single `electron-store` config file (`config.json`) holding everything: themes, keybindings, notification settings, app state, and `windowStates` (per-project window bounds keyed by project path). `electron/windowState.ts` wires `resize`/`move`/`close` BrowserWindow events to a save handler that does a read-modify-write of the whole `windowStates` map.

## Problem

electron-store rewrites the entire JSON file on every `store.set`. Window `resize`/`move` fire continuously — dragging a window across displays produces 10+ full-file rewrites in seconds. Each rewrite is a corruption window: a crash, an antivirus lock, or a cloud-sync tool (Dropbox/iCloud) racing the write can leave a truncated or 0-byte `config.json`. Because window bounds shared that file, a single window drag could destroy the user's themes, keybindings, and settings — data that has nothing to do with window geometry. (This is the same failure mode as Obsidian's June 2025 0KB `workspace.json` bug.)

## Root cause

The risk wasn't losing window bounds (cheap, regenerable) — it was that co-locating the highest-write-frequency, lowest-importance data with the lowest-write-frequency, highest-importance data made every window event a corruption opportunity for irreplaceable settings. Corruption blast radius scales with what shares the file, multiplied by how often that file is rewritten. A secondary contributor: the old close handler wrote `windowState` AND `windowStates` and could race a still-pending debounced save at quit (double write at the most fragile moment — app teardown).

The fix (verified live):

- A dedicated `windowStatesStore` (`window-states.json`, `name: "window-states"`) in `electron/store.ts:838-867`, separate electron-store instance with `clearInvalidConfig: true` and an **in-memory `Map` fallback** if init throws — window placement degrades to non-persistent rather than crashing the app.
- Migration 020 (`electron/services/migrations/020-window-states-store.ts`) moves `windowStates` + legacy `windowState` out of the main store, seeds `__legacy__` only when migration 009 never ran, then `store.delete()`s the old keys (uses `delete`, not `set(undefined)` — electron-store v11 throws on undefined, per lesson #2727).
- Close handler (`electron/windowState.ts:249-252`) calls `debouncedSaveState.cancel()` then a single synchronous `saveState()` — exactly one write at quit, no debounce-vs-close race.

## Lesson

- **Split persisted state into separate store files by write frequency, not by domain.** Before adding a key to the shared `electron-store` config, ask: how often is this written, and would its writes risk corrupting the file's other contents? High-churn data (window bounds, scroll positions, UI ephemera driven by mouse/resize events) belongs in its own store instance so its write cadence can't amplify corruption blast radius onto themes/keybindings/settings.
- electron-store rewrites the **whole file** per `set`. There is no partial write. Anything sharing the file shares every corruption window of the noisiest writer.
- A dedicated store for regenerable data should degrade to an **in-memory fallback** on init failure (catch the constructor throw, return a `Map`-backed shim) — never block app startup on placement data.
- When debounced saves are wired to lifecycle events, the teardown/close handler must `cancel()` the pending debounce and flush exactly once — never let a debounced timer race a synchronous close write (cf. #3177 for the PTY-kill version of this).
- Migrating a key OUT of a store still uses `store.delete(key)`, not `set(key, undefined)` (electron-store v11 throws — #2727).

## Applies when

- Adding a new key to `electron/store.ts` / the shared `electron-store` config, especially one written on a frequent event (mouse, resize, scroll, polling).
- Wiring BrowserWindow `resize`/`move`/`close` (or any high-frequency renderer event) to a persisted save handler.
- Investigating reports of lost/reset themes, keybindings, or settings, or 0-byte / truncated `config.json` (suspect cloud-sync or AV racing a high-frequency rewrite).
- Designing crash/corruption recovery (`CrashRecoveryService`) or a new electron-store migration — remember per-frequency store partitioning and `delete` vs `set(undefined)`.
- Adding any debounced persistence tied to a lifecycle/teardown event where a quit-time write could race the pending timer.
