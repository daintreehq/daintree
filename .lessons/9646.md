## Context

When LRU view eviction (or window close / idle auto-close) tears down a project's Daintree Assistant, `HelpSessionService.revokeSession({ captureHibernation: true })` awaits `ptyClient.gracefulKill(terminalId)` — the agent flushes its transcript, exits, and resolves with a resume ID — then writes that ID into `PendingHelpHibernationStore` keyed by project. On the next open, the renderer calls `takePendingHibernation(projectId)` and resumes the conversation. Critically, the eviction chain (`ProjectViewEvictionController` → `revokeByWebContentsId`) is fire-and-forget: nothing blocks the project view reload on the capture completing.

## Problem

Switching away from a project and quickly back made the assistant visibly restart with a fresh session while every other agent terminal resumed normally (#9639). Sibling bug #9637 (fixed in #9644): after a switch-back the assistant froze — new output never rendered until a manual resize. Both symptoms were assistant-only, which made them look like assistant-process bugs; #9637's writeup even chased an `IntersectionObserver` visibility race that turned out to be irrelevant.

## Root cause

Two instances of the same structural fact: the assistant terminal is special-cased outside every generic terminal path. (1) The restart: `revokeSession` wrote the pending-hibernation entry only after `gracefulKill` resolved — a multi-second window while the agent flushes and exits. A fast switch-back loaded the new renderer view inside that window, called `takePendingHibernation`, got `null`, and dispatched a fresh `agent.launch`. (2) The freeze: `wakeActiveWorktreeTerminals` fans `fullWakeForVisibilityRestore` out to grid terminals of the active worktree and deliberately excludes dock/trash locations — but the assistant is a dock-located (today overlay-located) panel rendered persistently in `HelpPanel`, so no generic path ever woke it; its xterm buffer accumulated output that was never painted.

The #9646 fix is three load-bearing parts. First, before the `gracefulKill` await, synchronously write a placeholder entry with the empty-string sentinel `agentSessionId: ""` — the renderer treats the sentinel as "resume latest" (`buildResumeLatestCommand`, claude `--continue`), which beats a fresh launch even without the exact ID. Second, ownership: `pendingCapturesByProject: Map<projectId, sessionId>` records who wrote the placeholder; the post-`gracefulKill` overwrite only fires if `get(projectId) === sessionId` still holds, and every superseding path — `displacePriorSessions` on a same-project re-provision mid-kill, and `takePendingHibernation` itself — deletes the ownership entry (displacement also clears the placeholder), so a stale resume ID can never shadow the session that took the slot. Third, validators: `PendingHelpHibernationStore.isValid` required `agentSessionId !== ""` and would have silently dropped the sentinel on the next load — reintroducing the race across an app restart mid-capture — so the non-empty check was removed; the same pass added `capturedAt <= Date.now()` because staleness is only checked as `capturedAt < now − 14d`, so a corrupt far-future stamp would pin a dead resume entry forever.

## Lesson

- **When a fire-and-forget teardown produces a recovery token, persist a synchronous sentinel BEFORE the async step, then overwrite with the real value.** Any observer racing the teardown must see "capture in flight → resume latest", never an empty store. If the async step fails or returns null, leaving the sentinel in place is correct — resume-latest still beats a fresh launch.
- **A deferred overwrite after an await needs an ownership guard.** Record writer identity (`pendingCapturesByProject`, project → sessionId) at placeholder time and compare before finalizing; every path that supersedes the capture (displacement, take, re-provision) must release ownership, or the late write shadows a newer session with a stale token.
- **Introducing a sentinel value means auditing every validator/deserializer on its round-trip.** `isValid`'s innocuous `!== ""` check would have silently discarded the placeholder on restart — the in-memory fix only works because persistence accepts it too.
- **A timestamp validated only by `< now − TTL` needs an upper bound.** `capturedAt <= Date.now()` — otherwise corruption/clock-skew produces an entry that never ages out.
- **The Daintree Assistant terminal is outside every generic panel fan-out** — non-grid location, rendered persistently in `HelpPanel`, id only in `useHelpPanelStore.terminalId`. Any new "for all worktree terminals" iteration must explicitly decide assistant inclusion; use `collectActiveWorktreeTerminalTargets()` in `src/store/wakeActiveWorktreeTerminals.ts` (post-#9644 it folds the assistant in, with existence and dedupe guards) rather than filtering `panelsById` by location yourself.
- **To test a mid-flight race, back the mock store with real state and hand-resolve the kill.** The #9646 test uses a `Map`-backed store mock plus a manually-resolvable `gracefulKill` promise so `takePendingHibernation` is asserted to see the sentinel while the kill is genuinely outstanding — a resolved-by-default mock can't prove the window exists.

## Applies when

- Touching `HelpSessionService.revokeSession` / `revokeByWebContentsId` / `displacePriorSessions`, `PendingHelpHibernationStore`, or any capture-then-resume flow around `gracefulKill`.
- Designing any teardown that computes a resume/recovery token asynchronously while callers are fire-and-forget — the reader can always arrive before the token lands.
- Diagnosing "assistant restarts / loses its session / freezes on project switch-back while other terminals behave" — check whether a generic fan-out or store write excludes the help-panel terminal before suspecting assistant process logic.
- Adding a fan-out over "all terminals of the active worktree" (wake, repaint, broadcast, trim) — the assistant id lives in `useHelpPanelStore`, not in the grid-location panel set.
- Adding a sentinel/placeholder value to any persisted store — validators, staleness cutoffs, and the restart round-trip must all accept it, or it silently vanishes exactly when needed.
