## Context

Window/project-view memory-housekeeping batch (`#10412`, resolving `#10391`; sibling host-layer batch `#10410`). Each project gets its own `WebContentsView` + V8 context via `ProjectViewManager`; on LRU deactivation (`deactivateView`) the view is CPU-throttled (CDP rate 4) and can be frozen by Chromium after ~5min hidden or under memory pressure. Main and utility processes broadcast to all app `webContents` via `broadcastToRenderer`, and the logger transport pushes high-frequency log batches to every renderer. Each `ProjectViewManager` also runs a 30s cached-view memory sampler (`app.getAppMetrics()`), previously via `setAlignedInterval`.

## Problem

Two costs that only surface with several windows open. Pushed broadcasts to a cached/throttled/frozen view queue **unbounded** in its renderer task queue — there is no consumer and no backpressure once throttled — so log batches to evicted views grew memory. Separately, every window's 30s sampler fired on the same wall-clock instant, stacking `app.getAppMetrics()` (5–50ms of synchronous main-thread work each) into a periodic main-thread hitch that scaled with window count.

## Root cause

Two mechanisms. **(1) Broadcast fan-out has no notion of "cached".** `broadcastToRenderer` sends to every app `webContents`; a deactivated view keeps receiving pushes it cannot drain. The tempting fix — blanket-skip cached views — is wrong, because `#9490` established that a cached view has **no replay path on warm reactivation**: a cold-restored V8 context misses every `*-changed`/state broadcast emitted while it was evicted, and silently registers stale state. So skipping is only safe for events the renderer can _re-pull on mount_. Log batches qualify (Logs panel pulls `LOGS_GET_ALL` on mount); project added/updated/removed and every other state broadcast do NOT. The PR adds `broadcastToVisibleRenderers` (skips `isCachedViewWebContents`) and wires it to the **logger transport only**; `broadcastToRenderer` is unchanged for state. The mark is stamped by `registerCachedViewWebContents` in `deactivateView` and cleared by `unregisterCachedViewWebContents` on activation, `webContents` destroy, `unregisterProjectView`, and both stale-prune paths. **(2) `setAlignedInterval` fires on wall-clock-aligned ticks** — identical across windows, so all samplers collapse onto one instant. Replaced with a recursive `setTimeout` seeded from `Math.random() * CACHED_VIEW_MEMORY_SAMPLE_INTERVAL_MS` (30s), fixed cadence afterward, `unref`'d and dispose-safe; `setAlignedInterval` stays for its other four consumers.

## Lesson

- **Before adding any main→renderer broadcast in this multi-window build, classify it replayable vs state.** Replayable/high-frequency events the renderer re-pulls on mount (log batches → `LOGS_GET_ALL`) may use `broadcastToVisibleRenderers` to skip cached views. STATE broadcasts — project added/updated/removed, plugin `*-changed`, anything with no pull-on-mount path — MUST use `broadcastToRenderer` and reach cached views. Defaulting a state event to the visible-only helper is a silent-desync bug: the cold-restored V8 context has no replay path (`#9490`) and never learns what it missed.
- **A cached/throttled/frozen renderer provides NO backpressure** — pushed messages queue unbounded in its task queue. That is why high-frequency streams to cached views are a _memory_ problem, not just a CPU one; the fix is to stop pushing (skip the send), not to push differently.
- **A per-window periodic task that does real synchronous main-thread work must NOT use `setAlignedInterval`.** Wall-clock alignment collapses every window onto the same tick and stacks the cost (`app.getAppMetrics()` = 5–50ms) into a hitch that scales with window count. Jitter with a random initial offset (`Math.random() * intervalMs`), then fixed cadence; `unref` it and make disposal clear the pending timer. `setAlignedInterval` is fine for cheap or singleton consumers where cross-window coincidence is harmless.
- **To keep a backgrounded `webContents`' live SSE/WS streams alive while cutting CPU, CPU-throttle — do NOT freeze.** `throttleCpuWebContents` (CDP rate 4) drops V8/Blink CPU while the event loop and sockets keep running; `Page.setWebLifecycleState` freeze suspends the loop and drops the streams. Never `setBackgroundThrottling` — it is window-wide since Electron 28 (`#8599`). `PortalManager` throttles parked tabs on `showTab`/`hideAll` and unthrottles before show.
- **Clear the cached mark on EVERY exit from cached state, not only activation.** `unregisterCachedViewWebContents` runs on activate, `webContents` destroy, `unregisterProjectView`, and both stale-prune paths — miss one and a recycled `webContents` id stays flagged cached and silently loses visible-only broadcasts.

## Applies when

- Adding a new main→renderer broadcast — choosing `broadcastToRenderer` vs `broadcastToVisibleRenderers`; the tie-breaker is whether the renderer can re-pull the data on mount.
- Diagnosing renderer memory growth OR stale UI in a cached/evicted project view — check whether it is queueing pushed high-frequency events, or missing state broadcasts it can't replay (`#9490`).
- Adding any per-window periodic timer that does non-trivial synchronous main-thread work — jitter the phase instead of aligning it.
- Backgrounding a `WebContentsView` or portal tab that holds live SSE/WS connections — throttle, never freeze, never `setBackgroundThrottling`.
- Touching `webContentsRegistry` cached-set registration or `ProjectViewManager` deactivate/activate ordering.
