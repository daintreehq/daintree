## Context

`setupWindowServices()` (`electron/window/windowServices.ts`) wires global main-process singletons (PtyClient, WorkspaceClient, WorktreePortBroker, ResourceProfileService, CCR watcher, connectivity/notification services, watchdog) once behind a `globalServicesInitialized` boolean guard. The previous `win.on("closed")` handler treated "last window closed" (`windowRegistry.size === 0`) as "app shutting down" and disposed every global, resetting `globalServicesInitialized` to `false` so the next window would re-init from scratch.

## Problem

On macOS, closing all windows does NOT quit the app. Reactivating from the dock (or the OOM window-recreation path) re-enters `setupWindowServices()` while the async last-window-close teardown is still in flight. The new window read `globalServicesInitialized` as still `true`, skipped re-init, and ran against singletons being torn down underneath it. The defensive `await ccrConfigService.stopWatching()` in the closed handler was a band-aid for exactly this race. Two disposal paths existed for the same services (last-window-close AND `before-quit`).

## Root cause

Window-close lifecycle is decoupled from app-quit on macOS — `window-all-closed` does not auto-`app.quit()` there (unlike Windows/Linux). So "last window closed" is not "process exiting"; a reactivation can interleave with the async dispose chain over shared singleton module refs. The dispose-then-reinitialize transition is what creates the race; a boolean init guard cannot protect against it because disposal is asynchronous and the guard is still `true` mid-teardown.

## Lesson

App-lifetime global singletons must be initialized once and disposed once, at `before-quit` (`electron/lifecycle/shutdown.ts`) — never on last-window-close. Keeping globals alive makes the macOS dock-reactivation path a pure no-op past `initGlobalServices()` and removes the race by construction (no dispose→reinit transition exists, so the `globalServicesInitialized` guard is correct as written).

- The `win.on("closed")` handler should now do only per-window-scoped cleanup (here: `resetDeferredQueue()`); leave globals untouched.
- This directly reverses the earlier guidance (lesson #4624) to "dispose globals when the last window closes (`WindowRegistry.size === 0`)" — that rule is a Windows/Linux assumption that breaks on macOS.
- Windows/Linux are unaffected: `window-all-closed` → `app.quit()` → `before-quit` still fires once, so disposals run exactly once. Verify no double-disposal regression there.
- When relocating disposals into `before-quit`, wrap each in its own `try/catch` so one throw can't strand the rest of the chain, and serialize order-sensitive teardown ahead of the bulk `Promise.all`: stop file watchers / unwire client refs (`ccr.stopWatching()`, `pluginService.setWorkspaceClient(null)`) BEFORE disposing the `WorkspaceClient` they call into, so a late file-change callback can't fire into a half-disposed client. Null the singleton refs after dispose so any straggler callback no-ops.

## Applies when

- Adding or moving disposal/teardown for any main-process global singleton (PtyClient, WorkspaceClient, monitors, watchers, connectivity/notification services, watchdog, port brokers).
- Writing or reviewing `win.on("closed")` / `window-all-closed` handlers, or any code gated on `windowRegistry.size === 0`.
- Touching `electron/window/windowServices.ts`, `electron/lifecycle/shutdown.ts`, or `electron/window/serviceRefs.js`.
- Debugging macOS-only symptoms after closing all windows then reactivating from the dock (services "already disposed", null refs, skipped re-init, watcher restarted then nulled).
- Reasoning about init guards (`globalServicesInitialized`) and whether a boolean is sufficient against an async dispose-then-reinit transition.
- Sequencing order-dependent teardown where a watcher/callback could fire into a client being disposed.
