## Context

`OutputVolumeDetector` (`electron/services/pty/OutputVolumeDetector.ts`) classifies whether a PTY is producing "real" output (agent working) vs protocol noise, feeding `ActivityMonitor`'s idle→busy escalation. `ActivityMonitor` polls at two cadences: 50ms when the window is active, 500ms when backgrounded (`applyTier`, `setPollingInterval`).

## Problem

The detector used a fixed-window AND-gate: `framesInWindow >= minFrames && bytesInWindow >= minBytes` over a `windowMs` window (defaults 3 frames / 2048 bytes / 500ms). Tuned at the 50ms foreground cadence, it became meaningless at the 500ms background cadence — consecutive frames straddled the window boundary and pinned `framesInWindow` at 1, so backgrounded agents could never escape "waiting" when output resumed. This produced a class of recurring regressions (#6641, #1135, #4972). Each tier change re-exposed the same brittleness.

## Root cause

The frame-count threshold (`minFrames`) is fundamentally a function of how often `update()` is called, not of the underlying byte stream. At 50ms polling you get ~10 frames/500ms; at 500ms polling you get ~1. The same byte stream classifies differently purely because of observation frequency — the algorithm was coupled to sampling cadence. The earlier fix (#6641) added tier-aware override knobs (`backgroundOutputWindowMs`, `activeOutputWindowMs`, `reconfigureWindow()`) that re-scaled the window per tier. Those knobs _masked_ the coupling rather than removing it — every new cadence needed a new hand-tuned window.

## Lesson

- A detector whose state is a frame **count** or byte sum **over a wall-clock window** is only valid at one polling rate. Do not "fix" it by adding per-tier window overrides — that is a band-aid that re-breaks on the next cadence.
- Replace it with a continuous-state **leaky bucket** (GCRA-style): bytes accumulate into `level`; on each `update()`, drain `elapsedMs * leakRatePerMs` first, then add the (capped) contribution; fire when `level >= activationThreshold`. Because the drain is computed from elapsed time, the result depends only on the byte stream, not on how often you sample — provably evaluation-rate invariant.
- Keep a per-frame contribution cap (`maxBytesPerFrame`) as the noise gate replacing `minFrames`: a single oversized chunk (status-line write, unrecognized OSC) contributes at most the cap, so it can't fire on its own.
- Derive any "recent activity" window the consumer needs from the bucket parameters (`recencyWindowMs = activationThreshold / leakRatePerMs`) rather than carrying a separate `windowMs`.
- When merging partial config, filter explicit-`undefined` keys before spread (`Object.entries(...).filter(([, v]) => v !== undefined)`) so `{ leakRatePerMs: undefined }` doesn't clobber defaults and trip the positivity clamps.

## Applies when

- Touching `OutputVolumeDetector`, `ActivityMonitor`, `IdleSequenceFilter`, or `terminalActivityPatterns` agent-state detection in `electron/services/`.
- Adding or changing a polling cadence / tier (active vs background, battery throttle in #4838) and a downstream classifier reads accumulated counts.
- Writing any heuristic that thresholds on "N events within window W" where the producer is sampled or polled at a variable rate (git status polling, CPU sampling, output-volume/backpressure gates).
- Seeing a regression where agent state behaves correctly foreground but gets stuck (waiting/idle) when the window is backgrounded, or vice versa.
- Tempted to add a per-tier override knob (`backgroundXMs` / `activeXMs`, `reconfigureWindow`) to make a windowed detector work at a second cadence — that signals the underlying algorithm is cadence-coupled and should be made invariant instead.
