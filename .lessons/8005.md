## Context

`FixedDropdown` (`src/components/ui/fixed-dropdown.tsx`) supports a `keepMounted` mode that keeps the dropdown body in the DOM and hides it with a React 19.2 `<Activity mode="hidden">` instead of unmounting, so reopening is instant and state is preserved. The GitHub list dropdowns use this, and their rows render Radix tooltips through the shared `Tooltip` wrapper (`src/components/ui/tooltip.tsx`), which portals content (Floating-UI positioned) to `document.body`.

## Problem

Hovering a row to show a tooltip, then closing the dropdown, left a ghost tooltip stranded in the top-left corner (0,0) of the viewport until reload (issue #8001). It stayed fully painted but disconnected from any anchor.

## Root cause

Two interacting library behaviors that neither library documents together:

- React 19 `<Activity mode="hidden">` applies `display:none` to the subtree **synchronously** but **defers effect cleanups**. The trigger DOM is hidden instantly, so the browser never fires the `pointerleave`/`blur` events the tooltip's dismiss path depends on — the tooltip never learns it should close.
- Radix Tooltip **portals its content to `document.body`**, which lives _outside_ the Activity subtree. So `display:none` on the dropdown never reaches the portaled content; it stays mounted and visible, and because its anchor is now hidden, Floating-UI falls back to coordinates `(0,0)`.

A second, subtler trap surfaced in review: forcing the Radix `Root` to `open={false}` is not enough for uncontrolled tooltips. Radix's `useControllableState` only updates its internal `uncontrolledProp` via uncontrolled `setValue` calls; the controlled-close path (`open: undefined → false`) fires `onOpenChange` but never resets the uncontrolled state. On reopen, releasing back to `open={undefined}` re-reads the stale `true` and re-opens the tooltip with no user hover.

## Lesson

- Inside a `keepMounted` / `<Activity mode="hidden">` subtree, treat any **portaled overlay** (Radix Tooltip/Popover/HoverCard/DropdownMenu content, Framer `AnimatePresence` exit children) as a hazard: it escapes the Activity tree and won't be hidden or dismissed by the synchronous `display:none`.
- Propagate visibility into the subtree via context. `FixedDropdown` exports `FixedDropdownVisibleContext` (default `true`) and provides `shouldRender` inside the `keepMounted` Activity branch. The shared `Tooltip` wrapper consumes it and forces `open={false}` when the dropdown is hidden — explicitly closing the overlay before its portaled node can strand.
- When you flip a Radix primitive from uncontrolled to controlled-closed, also **remount it** (`key` on visibility) so its internal `useControllableState` doesn't retain the stale uncontrolled value and re-open on reveal. The hidden tree has no user-visible state worth preserving.
- Route overlays through the shared wrapper, not raw Radix primitives — direct primitive usage bypasses this guard. The default `true` context keeps standalone tooltips and non-`keepMounted` dropdowns unaffected.

## Applies when

- Adding or auditing tooltips, popovers, hovercards, or dropdown menus inside a `keepMounted` `FixedDropdown` or any `<Activity mode="hidden">` subtree.
- Seeing a ghost overlay/tooltip stranded at the top-left (0,0) corner that persists after its parent closed.
- Working in `src/components/ui/fixed-dropdown.tsx` or `src/components/ui/tooltip.tsx`, or wiring overlays for the GitHub issue/PR list dropdowns.
- Switching a Radix primitive between controlled and uncontrolled `open` state and finding it re-opens without user interaction.
- Considering using `<Activity>` to hide rather than unmount any tree that contains Floating-UI / portal-positioned content.
