## Context

The pty-host and workspace-host run as Electron `utilityProcess` children. The parent supervises them via `app.on("child-process-gone")` + the host's `exit` event, driving crash classification and restart (`PtyHostLifecycle.ts`, `WorkspaceHostProcess.ts`). For that supervision to fire, a fatally-broken host must actually _terminate_.

## Problem

A workspace-host that hit an `uncaughtException` or `unhandledRejection` would log the error, post an `error` event, and then **keep running as a zombie**. The parent never observed `child-process-gone`, so the watchdog/restart path never triggered — the host stayed alive in a broken state instead of being recycled.

## Root cause

A version-behavior change that silently inverted the assumption. In Electron 36 and earlier, an unhandled rejection in a utility process crashed it (so the supervision path triggered for free). **From Electron 37 onward, utility processes only WARN on unhandled rejections — they do not auto-exit.** The `workspace-host.ts` handlers logged and emitted but never called `process.exit`, so post-37 the process simply continued. (Note: several older lessons describe Electron 37+ as "crashing" on unhandled rejections — that is the pre-37 behavior; 37+ only warns. This PR is built on the corrected understanding.)

The fix mirrors the pty-host pattern: after logging + emitting, call `setImmediate(() => process.exit(1))`. The `setImmediate` deferral is load-bearing for two independent reasons:

1. It lets the Mojo IPC channel flush the `error` event before the process dies (otherwise the parent loses the diagnostic message).
2. It bridges the `exit`/`child-process-gone` ordering race (`electron/electron#42283`) so the authoritative crash reason/exitCode from `child-process-gone` can arrive and be preferred over the (sometimes wrong) `exit` code. The Windows signed/unsigned exit-code mangling bug (`electron/electron#50386`) was fixed in Electron 41.0.4; the `gone ? gone.exitCode : code` preference is retained as defense-in-depth for pre-41.0.4 builds and future regressions.

## Lesson

- In any Electron `utilityProcess` entry point (`*-host.ts`), `uncaughtException` and `unhandledRejection` handlers MUST end with `setImmediate(() => process.exit(1))`. Do not assume the runtime will kill the process for you — on Electron 37+ it won't; it just warns.
- Wrap the pre-exit `sendEvent(...)` in `try/catch` — the IPC channel may already be dead during a fatal handler, and a throw there would mask the exit.
- Use `setImmediate` (not synchronous `process.exit`) so the error event flushes over Mojo IPC and the parent's `child-process-gone` reason wins the race against `exit`.
- When preferring an exit code, keep `gone ? gone.exitCode : code` as defense-in-depth even though `#50386` is fixed in 41.0.4.
- The crash-loop constants (`CRASH_THRESHOLD`, `CRASH_WINDOW_MS`) are deliberately duplicated (not imported) across the three guards — `electron/services/pty/PtyHostLifecycle.ts`, `electron/services/WorkspaceHostProcess.ts`, `electron/services/CrashLoopGuardService.ts` — because they operate at independent layers (disk-persisted app-level vs in-memory per-host) and must not be coupled at the module level; `scripts/ci/check-crash-loop-constants.mjs` (wired into `npm run check`) keeps the values aligned in CI, and the runtime test `electron/services/__tests__/crashGuardAlignment.test.ts` exercises the same invariant from vitest. (`MainProcessWatchdogClient.ts` has its own separate `RAPID_CRASH_WINDOW_MS` / `STABILITY_TIMEOUT_MS` and is not part of this aligned set.)

## Applies when

- Adding or auditing fatal error handlers (`uncaughtException`, `unhandledRejection`) in any utility-process entry point: `electron/pty-host.ts`, `electron/workspace-host.ts`, their bootstrap files, or a new `*-host.ts`.
- A utility-process host is observed staying alive / not restarting after an error, or the parent never logs `child-process-gone`.
- Touching parent-side supervision (`PtyHostLifecycle.ts`, `WorkspaceHostProcess.ts`): crash classification, restart/backoff, `exit` vs `child-process-gone` handling, exit-code interpretation.
- Reasoning about Electron version-behavior deltas around unhandled rejections in utility processes (anything citing "Electron 37+ crashes on unhandled rejection" should be re-checked — 37+ only warns).
- Working with Windows exit-code values from utility processes, or relying on `electron/electron#42283` / `#50386` behavior.
