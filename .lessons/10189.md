## Context

The Daintree Assistant help panel attributes each MCP tool call to an assistant "turn" in two surfaces: `McpActivityStrip` renders live started/settled IPC events, and `RecentCallsPopover` renders persisted audit records grouped by `groupCallsByTurn`. The turn register lives in `turnOutcomeLog.ts`: a fresh turnId is minted on every FSM active transition, stored in `turnIdBySession` keyed by HELP session id (not the MCP transport id — the #9759 gap), and deliberately deleted on the matching active→passive transition so post-turn dispatches aren't stamped with the stale turn.

## Problem

One tool call rendered under two different turn groupings at once: the strip's row keyed on turn T1 while the same call's audit record landed in the popover's unlabeled `turnId: null` bucket (issue #10067). Intermittent — it only happened when a call straddled the turn boundary, i.e. the agent emitted its completion (active→passive) while a tool call was still in flight. The unlabeled null bucket made it look like data corruption rather than a legitimate category, so users had to guess what "unassociated" meant.

## Root cause

`httpLifecycle.ts` had three independent closures — `notifyToolCallStarted`, `notifyToolCallSettled`, and `appendAuditRecord` — each calling `getCurrentTurnIdForSession(helpSessionId)` live, at its own execution time. A tool-call lifecycle spans multiple awaits (tier/grant guards, the `danger:"confirm"` modal, the dispatch itself), and the FSM's active→passive transition runs `turnIdBySession.delete(sessionId)` whenever it fires. Each individual read was "correct at its moment" — the started event honestly read T1, the audit write honestly read null — but the violated invariant is that all reads belonging to ONE call must agree. Crucially the register clear is load-bearing and cannot be removed: without it, dispatches issued after the turn ends would inherit the prior turn's ID (the exact inverse bug).

The fix moves attribution to the call's origin: `sessionServer.ts`'s CallTool handler snapshots `const capturedTurnId = getCurrentTurnId?.() ?? null` at the top of dispatch (sessionServer.ts:404), before any guard or await can yield to an FSM transition. The new optional `getCurrentTurnId` dep, implemented in `httpLifecycle.buildSessionServerDeps` closing over the build-time `helpSessionId`, is the single place the live register is consulted. That one snapshot threads through every consumer — both notify events and all ~8 `appendAuditRecord` sites including error/rejection paths. In `appendAuditRecord`, `capturedTurnId` is a transport-only carrier: destructured off (`const { capturedTurnId, ...recordInput } = input`) and re-stamped as the public `turnId` field so the plumbing name never persists. `RecentCallsPopover` also gained a "Not tied to a turn" label on the null group, because legitimately-null calls exist (between-turn dispatches, external/api-key sessions with no help binding).

## Lesson

- **Snapshot mutable correlation context once at the dispatch boundary — before any guard or await — and thread the captured value through every consumer.** N closures each live-reading a shared register produce N independently-correct values that disagree whenever the register mutates mid-call. If two surfaces must agree on an attribution, they must consume one capture, not two reads.
- **Attribution follows the call's origin, not whichever state was current when a write happened to flush.** The audit record is written seconds after dispatch; stamping it with write-time state means late-settling calls silently migrate buckets. Decide which moment owns the attribution and capture there.
- **Don't fix a mid-call attribution race by removing or delaying the register clear.** `turnIdBySession.delete` on active→passive exists so post-turn dispatches aren't stamped with the stale turn — it is correct. The register can be both promptly cleared and correctly attributed if consumers hold a snapshot instead of re-reading.
- **Peel transport-only carrier fields off before persistence.** `appendAuditRecord` spreads its input into the stored record; without the `const { capturedTurnId, ...recordInput }` destructure the plumbing field leaks into every persisted record forever — the test asserts `persisted.capturedTurnId === undefined`.
- **Enforce the snapshot structurally in tests** and simulate the race: `sessionServer.test.ts` asserts `getCurrentTurnId` is called exactly once per dispatch, `httpLifecycle.test.ts` asserts the write path never calls `getCurrentTurnIdForSession`, and `mockReturnValueOnce("turn-T1").mockReturnValue(null)` proves started and settled still agree across the clear.
- **A legitimately-null correlation bucket needs a UI label.** Null-turn calls are a real category, not an error; "Not tied to a turn" turns apparent corruption into explained behavior.

## Applies when

- Adding any new consumer to the MCP tool-call lifecycle (`sessionServer.ts` CallTool handler, `httpLifecycle.buildSessionServerDeps`) — a new notify event, audit path, or telemetry hook must receive `capturedTurnId`, never re-read `getCurrentTurnIdForSession` itself.
- Diagnosing a call that appears under one turn in `McpActivityStrip` but lands in "Not tied to a turn" (or a different turn) in `RecentCallsPopover` — check for a fresh register read on the divergent path before suspecting the FSM.
- Designing correlation/attribution stamping where the ID source is cleared by a lifecycle transition (agent FSM turns, session teardown, view eviction) and the stamped operation spans awaits — snapshot at origin rather than keeping the register populated longer.
- Reviewing code where the same logical operation reads a live getter (`getCurrentTurnIdForSession`, session maps, focus state) in more than one closure — flag it even if no race has been observed yet.
