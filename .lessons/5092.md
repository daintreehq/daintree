## Context

Standard terminals (non-agent) use xterm.js's DOM renderer. Agent terminals normally use WebGL, but they aren't permanently exempt: `TerminalWebGLManager` (`src/services/terminal/TerminalWebGLManager.ts`) flips the whole pool to the DOM renderer once the live WebGL-context count crosses a threshold (`getWebglUpperThreshold`/`getWebglLowerThreshold`), so the DOM-renderer failure mode below can reach agent panes too once that cap trips. Per-terminal hibernation (the system that used to serialise scrollback and replace a live `Terminal` with a fresh one on unhibernate) was removed entirely in PR #10811 — terminals now stay live until closed or the process exits. Fresh `Terminal` instances still get created and (re)opened against an existing host element on the surviving paths: cold restore after app restart/LRU-rehydrate (`TerminalRestoreController`), panel remount, and split-pane rearrangement, all funneling through `TerminalInstanceService.getOrCreate`/`ensureOpened`.

## Problem

Two distinct failures surfaced together:

1. Standard terminals went blank/frozen silently. No error, no user action — the terminal was just visually stuck despite the process still running.
2. When a fresh `Terminal` instance was opened against a reused host element, it could end up in a zombie state: buffer restored, but nothing rendered because the DOM was never bound.

## Root cause

**Blank/frozen:** xterm.js's DOM renderer (6.0 at the time, now 6.1 beta) installs an `IntersectionObserver` internally. Any layout change, CSS transform, or `clip-path` that briefly drops `isIntersecting` below the threshold sets `_isPaused = true` on the renderer. The renderer never self-recovers — it waits for the next intersection event that may never come if the element stays technically visible but the observer misfired.

**Zombie on reopen:** creating a fresh `Terminal` instance and restoring its buffer without calling `terminal.open(hostElement)` leaves the DOM never bound, so xterm never paints. The needed guard: defer `open()` when `clientWidth`/`clientHeight === 0` (element not yet in layout). This is exactly what `TerminalInstanceService.hostHasRenderableDims()` checks before `ensureOpened()` calls `terminal.open(managed.hostElement)` — `TerminalRevealController`'s reveal/wake path calls `ensureOpened` through that same guard rather than opening unconditionally.

## Lesson

When using xterm.js's DOM renderer, never assume a visible terminal is a rendering terminal. The `IntersectionObserver`-based pause mechanism can trigger on layout side-effects and will not recover on its own. Build layered recovery — still true today in `TerminalReflowController.ts`: (1) a per-write reflow via `maybeReflow()`/`forceXtermReflow` (called from `onWriteParsedReflow`), (2) a periodic heartbeat (`REFLOW_HEARTBEAT_MS`, 3s) that recovers a paused renderer with no writes, (3) `window.focus`/`document.visibilitychange` listeners for the moments a user is most likely to notice a blank terminal. Also: `terminal.open(host)` is mandatory before any rendering — always call it when creating a fresh instance for an existing host element (cold restore, panel remount, split-pane rearrangement — no longer hibernation, which no longer exists), guarded by a dimension check (`clientWidth`/`clientHeight > 0`, i.e. `hostHasRenderableDims`) to avoid binding to an element not yet in layout.

## Applies when

- Creating or restoring Terminal instances (cold restore/reconnect via `TerminalRestoreController`, LRU project-view rehydrate, panel remount, split-pane rearrangement)
- Configuring the DOM renderer for standard terminals, or hitting the WebGL→DOM fallback once `TerminalWebGLManager`'s context-count cap trips
- Adding any CSS transform/clip-path/layout animation that touches a terminal's ancestor chain
- Implementing any terminal lifecycle that serialises/deserialises xterm state
