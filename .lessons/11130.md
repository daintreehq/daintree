## Context

`DatabaseMaintenanceService` runs a 5-minute idle-tick timer that backs up the app's sqlite database (`sqlite.backup(tmpPath)` then `fs.renameSync(tmpPath, backupPath)`) and, on boot, calls `probeDb()` + `attemptRecovery()` to detect and recover from corruption; `probeDb()` predates this PR and is deliberately fail-open (on a non-corruption error, e.g. a transient `EACCES` at boot, it returns `true` so a healthy database is never wrongly quarantined), and #11130 (resolving #11105) found that same fail-open `probeDb()` being reused to gate the backup-promotion rename — a context where fail-open is exactly backwards.

## Problem

Latent SQLite corruption could destroy the app's only backup with no error surfaced anywhere. The failure mode wasn't a crash or a loud exception — a truncated or partially-written temp copy would probe as "fine" (because the probe was designed to say "fine" when uncertain) and `fs.renameSync` would happily promote it over the last known-good backup. Compounding it, the deferred `quick_check` that was supposed to catch a corrupt _live_ database cleared its own pending flag before its async result landed, so a slow or unavailable check could look "done" while never having actually run, and the very first backup after a clean-exit boot raced that same check.

## Root cause

One predicate, two irreconcilable correctness requirements. At boot, `probeDb(dbPath, fullCheck)` guards against _false quarantine_: a healthy database must survive a transient read error, so ambiguous outcomes map to "ok" (fail-open). At backup-promotion time the correct guard is the opposite: a candidate copy must prove itself before overwriting the one existing safety net, so ambiguous outcomes must map to "not ok" (fail-closed). `sqlite.backup()` copies pages verbatim with zero validation — an interrupted or partially-flushed copy can look byte-plausible enough that a fail-open check doesn't reject it, and `fs.renameSync` is unconditional once called, so there's no second chance. The fix wasn't tightening `probeDb()` (that would break its boot-time job) — it was adding `probeDbFile()`, a strict tri-state (`"ok" | "corrupt" | "unknown"`) where only a proven `"ok"` promotes a candidate and only a proven `"corrupt"` suspends future backups; `"unknown"` retries later rather than either promoting or condemning. The same split applies inside `attemptRecovery()`: restoring _from_ a backup over the live DB is itself a destructive promotion, so it moved from `probeDb(backupPath)` to `probeDbFile(backupPath)` too. A second, independent bug in the same PR: `runDeferredQuickCheck()` used to clear `deferredQuickCheckPending` synchronously, before the awaited worker result came back, so a slow check raced the tick's own backup call and a corruption verdict could land after the flag already said "done." The fix tracks an in-flight `Promise<boolean>` (`deferredQuickCheckInFlight`) and clears the pending flag only on an exact `"ok"` — any other outcome (including "worker unavailable") leaves it pending for retry, and the tick's backup chains onto the check's resolution instead of firing concurrently.

## Lesson

- **A validation function's fail-open/fail-closed polarity is a property of its call site, not the function.** `probeDb()` is correctly fail-open for "should I quarantine a database I'm about to open" and catastrophically wrong for "should I let this candidate overwrite the only backup." Before reusing an existing health check at a new call site, ask which direction an ambiguous result should resolve.
- **A copy operation with zero built-in validation (`sqlite.backup()`, `fs.copyFileSync`, checksum-less `rsync`) needs an explicit post-copy probe before anything irreversible (rename-over, delete-original) runs on the result.** The bug wasn't a missing check, it was a check that existed but answered the wrong question.
- **When a destructive operation has exactly one fallback copy (`backupPath`, singular, no rotation), every promotion into that slot must be fail-closed by construction** — a tri-state result (`"ok" | "corrupt" | "unknown"`) forces the "did I actually verify this" question, whereas a boolean invites treating "unknown" as `false`≈"safe to proceed."
- **A pending/in-flight flag must clear only on confirmed success, never optimistically before the async result lands** — `deferredQuickCheckPending` cleared synchronously let a check that hadn't returned, or returned "worker unavailable," permanently masquerade as done; the fix tracks the in-flight `Promise` itself (`deferredQuickCheckInFlight`) and chains downstream work on it instead of racing it.
- **A single verification failure on a copy is evidence the copy is bad, not proof the source is.** `onBackupVerifyFailed()` re-checks the _live_ database rather than immediately condemning it, and only latches `backupsSuspended` after `MAX_BACKUP_VERIFY_FAILURES` (3) consecutive failures — conflating "the copy looks wrong" with "the source is corrupt" would stop backups on one transient write glitch.
- **Recovery must not repeat the class of bug it's fixing** — after a reset-to-fresh, the next idle tick would back the new empty database up over any surviving-but-unusable backup; `attemptRecovery()` calls `preserveStaleBackup()` to rename it aside first, and boot-time outcomes are threaded to the user via a `DatabaseRecovery` result instead of `console.log` only.

## Applies when

- Reusing any existing validation/health-check function (`probeDb`, an `isValid`/`healthCheck`/`ping` helper) at a new call site — check whether that site needs the opposite fail-open/fail-closed default.
- Writing or reviewing a backup/promotion/rename-over-the-last-good-copy path (`DatabaseMaintenanceService.ts`, `db.ts`'s `attemptRecovery`/`probeDbFile`) — confirm the promotion gate is fail-closed even though the source's own health probe may legitimately be fail-open.
- Diagnosing "the backup is corrupt too" or silent data loss after a restart — check whether a copy op (`sqlite.backup`, `fs.copyFileSync`) ran with no post-copy integrity probe, or used the fail-open probe.
- Touching a pending/in-flight boolean guarding a deferred async check — verify it clears strictly on a confirmed-good result, not synchronously before the awaited call resolves.
- Adding boot-time or session recovery notifications — verify the reported outcome (`restored-from-backup` vs `reset-to-fresh`) matches what the filesystem calls actually returned.
