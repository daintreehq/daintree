## Context

Voice input's mic-permission preflight lives in `electron/ipc/handlers/voiceInput.ts` (`requestMicPermission`, `checkMicPermission`, `openMicSettings`), called by `VoiceRecordingService.start()` in the renderer before it opens `getUserMedia`. The handler also has an "open OS sound settings" escape hatch that shells out to a platform-specific utility. Both paths were written against macOS's API surface and never re-verified against Electron 42's actual Windows/Linux behavior.

## Problem

Voice input was completely dead on arrival for fresh Windows users — the mic permission prompt never appeared, with no error surfaced. Separately, clicking "open sound settings" on any non-GNOME Linux desktop (anything without `gnome-control-center` installed) crashed the entire app, not just the settings link. Issue #11108 traced both to the same handler file.

## Root cause

Two independent platform traps, both from assuming an API's behavior generalizes past the platform it was designed for.

1. `systemPreferences.askForMediaAccess` is a **macOS-only** Electron API — Windows and Linux have no main-process mic-request API at all; `getUserMedia` itself is the real permission gate on those platforms. `requestMicPermission()` hardcoded `return false` for non-macOS ("permission requested via getUserMedia in the renderer" — but nothing downstream knew that). `VoiceRecordingService.start()` read `not-determined` status plus that `false` as `mic_permission_denied` and set a **fatal** error before ever calling `getUserMedia`. The boolean's contract was ambiguous — "OS confirmed access" vs. "clear to attempt access" — and the non-macOS branch picked the value that reads as the former but was written to mean the latter.
2. `openMicSettings()`'s Linux branch did `spawn("gnome-control-center", ["sound"], {...}).unref()` inside a synchronous try/catch. `spawn()` returns a `ChildProcess` immediately even when the executable doesn't exist — the OS-level ENOENT only surfaces later as an **async `"error"` event** on that `ChildProcess`. A try/catch around the `spawn()` call itself cannot catch an event emitted after the call already returned. With no listener attached, that error event became an unhandled `EventEmitter` error, which Node re-throws as an `uncaughtException` on the next tick — caught by `electron/setup/globalErrorHandlers.ts`'s global handler, which treats every uncaught exception as fatal (crash recording, renderer notify, and `app.exit(1)` on re-entry). A dead settings link took down the whole app.

Point 2 is not a new class of bug for this repo: `.lessons/5648.md` documents the same terminal failure mode (unhandled async error on a child process reaching the global `uncaughtException` handler), via a different path — inherited stdio fds returning `EIO`/`EBADF` on piped streams. Here it's the `ChildProcess` object's own `"error"` event from a missing binary, not its stdout/stderr streams, but the rule is identical: spawn-adjacent async errors need an explicit listener, a try/catch is not enough, and any unhandled one is fatal to the whole app, not just the feature that spawned it.

## Lesson

- **Never assume a `systemPreferences` (or any Electron) method is cross-platform — check per-platform behavior in the Electron 42 docs before writing the non-primary-platform branch.** `askForMediaAccess` only exists on macOS; the fallback branch needs its own correct behavior, not a value that merely compiles.
- **A boolean IPC return whose meaning shifts by platform needs its contract documented at the type, not just in a code comment** — `shared/types/ipc/api.ts` now spells out that `requestMicPermission()` means "clear to attempt `getUserMedia`," not "the OS granted access," precisely so a future edit can't silently revert the non-macOS branch back to `false` for looking more "correct."
- **`child_process.spawn()` for a possibly-missing binary always needs a `child.on("error", ...)` listener before anything else runs (including `.unref()`)** — ENOENT for a missing executable is asynchronous, and a try/catch around the `spawn()` call only guards the synchronous call itself. Grep any new `spawn(` call site in `electron/` for this before merging.
- **Any unhandled async error in the main process is an app-wide crash here, not a local failure** — `globalErrorHandlers.ts`'s `uncaughtException` handler doesn't distinguish "opening OS settings failed" from a genuine fatal fault; both get fatal recovery + restart. Low-stakes best-effort spawns (settings openers, sound playback) need the same rigor as PTY spawns for exactly this reason.
- **Test platform-specific IPC handlers by stubbing `process.platform` per branch, not by running on one OS** — `voiceInput.permissions.test.ts` uses `Object.defineProperty(process, "platform", { value, configurable: true })` to exercise darwin/win32/linux in one suite; this caught what manual testing on a macOS dev machine never would.

## Applies when

- Touching `electron/ipc/handlers/voiceInput.ts`, `VoiceRecordingService.ts`, or any `systemPreferences.*` call — verify the non-macOS branch is actually correct, not just non-throwing.
- Wiring any new `child_process.spawn()` in `electron/` for an OS utility that may not be installed (settings openers, `xdg-open`-style fallbacks, optional CLI tools) — attach `child.on("error", ...)` before `.unref()`, and cite `.lessons/5648.md` in review as the established pattern.
- Diagnosing "the app crashed" (not "the feature failed") triggered by a small, low-stakes action like opening a settings panel or link — check for an unlistened child-process `"error"` reaching `globalErrorHandlers.ts`.
- Reviewing a PR that adds a fallback branch for a platform-restricted Electron API — confirm the fallback's return value has a well-defined meaning on the platforms that lack the primary API, not just a value that avoids a crash.
- A permission-preflight boolean and an OS-reported status disagree or lag each other (`not-determined` vs. `unknown` vs. a native `true`/`false`) — check which platform can answer authoritatively before trusting either signal over the actual capture attempt.
