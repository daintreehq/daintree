## Context

Fleet broadcast fans a single editor draft out to N armed worktree panes, substituting recipe variables (`{{worktreePath}}`, `{{branchName}}`, `{{issueNumber}}`) per target so each pane receives different resolved bytes. Destructive or oversized broadcasts route through a `ConfirmDialog` gated by `needsFleetBroadcastConfirmation` (`src/components/Fleet/fleetBroadcast.ts`) before `executeFleetBroadcast` writes to the PTYs. This is a Tier-D2 shared-state mutation per `docs/architecture/destructive-action-safeguards.md` — already-dispatched IPC writes cannot be revoked.

## Problem

The confirm gate evaluated the _source draft_ only — its byte threshold and destructive-substring check ran against the typed text, and the dialog showed a category label ("destructive command detected") plus a target count. A safe-looking draft (`cleanup {{worktree_path}}`) could expand per-target past the 512-byte threshold or surface `rm -rf` that wasn't in the source — and skip the gate entirely. Even when the gate fired, the user approved a _description_, not the bytes each pane would receive. This is the same silent-fallback class as #7880: the user confirms an abstraction, not the payload.

## Root cause

Two layered defects. (1) **Wrong input to the gate:** the danger signal lives in the resolved fan-out, not the draft — variable substitution makes each target's payload different and individually capable of crossing the threshold or introducing a destructive substring. (2) **TOCTOU between confirm-request and confirm-submit:** the dialog reads live worktree state, which rebuilds on every keystroke and mutates while the modal is open (a pane disarms, trashes, or loses its PTY; an override changes the resolved payload). Without a frozen snapshot, the user confirms one set of bytes and a different set dispatches.

## Lesson

For any destructive confirm over a derived/expanded payload:

- **Gate on the resolved output, not the input.** `needsFleetBroadcastConfirmation(text, resolvedPayloads)` checks _each_ non-excluded resolved payload — any single one over `FLEET_CONFIRM_BYTE_THRESHOLD` or matching `FLEET_DESTRUCTIVE_RE` trips the gate. The aggregate is not the signal; one dangerous target is.
- **Show the actual bytes.** Render the resolved per-target payload and point at the real match (`getFleetBroadcastDestructiveMatch` returns `{substring, index}`) — a count + label is insufficient (the #7880 root cause; a count wouldn't have caught the silent-fallback commit message either).
- **Snapshot the preview at request time.** `PendingFleetBroadcast.divergence.targets` is a frozen request-time snapshot; the confirm UI reads only this snapshot, never the live `fleetResolutionPreviewStore`. The dispatch uses the snapshotted payloads as `perTargetOverrides`, so late mutations can't change confirmed bytes.
- **Re-filter eligibility at dispatch, not just request.** `filterEligibleIds` re-runs _after_ confirmation (`src/components/Fleet/fleetExecution.ts`) so a pane that went ineligible while the dialog was open is dropped — snapshot eligibility is stale by submit time.
- **Regex gotcha:** `FLEET_DESTRUCTIVE_RE` is deliberately flagless (no `/g`/`/y`) so module-level `.exec()` / `.test()` are stateless and re-callable; if you add `/g` you must reset `lastIndex` or repeated calls drift.

## Applies when

- Adding or reviewing any destructive-confirm gate (`ConfirmDialog`) over a payload that is _derived, templated, or expanded_ before dispatch — recipe-variable substitution, fleet broadcast, bulk operations, context injection.
- Working in `src/components/Fleet/` (broadcast, divergence preview, arming ribbon) or touching `fleetBroadcastConfirmStore` / `fleetResolutionPreviewStore`.
- A confirm dialog reads from a live Zustand store that rebuilds on keystroke/state-change while the modal is open (TOCTOU between request and submit).
- Classifying an action in `docs/architecture/destructive-action-safeguards.md` as D2+ — the preview must show actual content (diff, message, resolved command, file list), never just a count or label.
- A threshold/danger check appears to run against user-typed input but the thing actually sent to N targets differs per target.
- Adding `/g` or `/y` to a shared module-level regex used for repeated matching.
