## Context

Fleet broadcast fans a single editor draft out to N armed worktree panes, substituting recipe variables (`{{worktreePath}}`, `{{branchName}}`, `{{issueNumber}}`) per target so each pane receives different resolved bytes. At the time of this PR, destructive or oversized broadcasts routed through a `ConfirmDialog` gated by `needsFleetBroadcastConfirmation` before `executeFleetBroadcast` wrote to the PTYs — a Tier-D2 shared-state mutation per `docs/architecture/destructive-action-safeguards.md` (already-dispatched IPC writes cannot be revoked).

**That gate no longer exists.** #9722 removed it entirely: arming a 2+ fleet is now the sole consent boundary, and `tryFleetBroadcastFromEditor` (`src/components/Fleet/fleetEnterBroadcast.ts`) submits immediately on Enter, matching the raw-input broadcast path (`broadcastFleetRawInput`), which has always fanned out without a confirm. The block comment at `fleetEnterBroadcast.ts:149` spells this out: "Submit just submits: once a fleet is armed there is no confirmation step." `needsFleetBroadcastConfirmation`, `fleetBroadcastConfirmStore`, `PendingFleetBroadcast`, and `FLEET_DESTRUCTIVE_RE` are all gone — do not resurrect a fleet confirm dialog off the back of this lesson. What survives is the underlying principle, which now shows up in other D2 confirms (`GitPushConfirmDialog`, the Artifact "Apply All Patches" flow) and in the snapshot/re-filter mechanics that stayed in `fleetEnterBroadcast.ts` even after the modal was cut.

## Problem

The confirm gate evaluated the _source draft_ only — its byte threshold and destructive-substring check ran against the typed text, and the dialog showed a category label ("destructive command detected") plus a target count. A safe-looking draft (`cleanup {{worktree_path}}`) could expand per-target past the 512-byte threshold or surface `rm -rf` that wasn't in the source — and skip the gate entirely. Even when the gate fired, the user approved a _description_, not the bytes each pane would receive. This is the same silent-fallback class as #7880: the user confirms an abstraction, not the payload.

## Root cause

Two layered defects. (1) **Wrong input to the gate:** the danger signal lives in the resolved fan-out, not the draft — variable substitution makes each target's payload different and individually capable of crossing the threshold or introducing a destructive substring. (2) **TOCTOU between confirm-request and confirm-submit:** the dialog reads live worktree state, which rebuilds on every keystroke and mutates while the modal is open (a pane disarms, trashes, or loses its PTY; an override changes the resolved payload). Without a frozen snapshot, the user confirms one set of bytes and a different set dispatches.

## Lesson

For any destructive confirm over a derived/expanded payload:

- **Gate on the resolved output, not the input.** The fleet version of this check (`needsFleetBroadcastConfirmation`) is gone along with the whole confirm step, but the principle is exactly what backs the confirms that remain D2: `WorktreeDeleteDialog.isHighTier` escalates to the typed-name D3 gate based on the worktree's actual current `hasTrackedChanges` state, not on the `force` flag the user clicked, and the Artifact "Apply All Patches" flow gates on the actual snapshotted patch list, not a description of the bulk action. The aggregate or the pre-expansion input is never the signal; the resolved per-instance state is.
- **Show the actual bytes.** Render the resolved content and point at what will actually happen — a count + label is insufficient (the #7880 root cause; a count wouldn't have caught the silent-fallback commit message either). Live examples: `GitPushConfirmDialog` previews the target branch and recent local commits (not just "push?"); the Artifact apply-all dialog previews the snapshotted patch list with per-patch `+N −N` stats; `WorktreeDeleteDialog` splits the file count into tracked vs untracked so the user sees what's actually at risk.
- **Snapshot the preview at request time.** This half of the pattern outlived the fleet confirm dialog: `tryFleetBroadcastFromEditor` still snapshots `payloadOverrides`/`skippedIds` into `initialOverrides`/`initialSkipped` at Enter-press and never re-reads the live `fleetTargetOverridesStore` inside `doSend` — the TOCTOU window just shrank from "however long the modal stays open" to "however long the async dispatch takes," it didn't disappear. The current canonical example with a real confirm dialog in front of it is `ArtifactOverlay.tsx`: `pendingBulkPatches` is snapshotted at request time and threaded through to `applyAllPatches(snapshot)` on confirm, so patches detected while the dialog was open are never applied unseen.
- **Re-filter eligibility at dispatch, not just request.** `filterEligibleIds` (`src/components/Fleet/fleetExecution.ts`) still runs immediately before dispatch in `fleetEnterBroadcast.ts` — right after the snapshot is filtered against the live armed set — even with no confirm dialog in between now. A pane that disarmed, trashed, or lost its PTY between snapshot and send is still dropped. The lesson generalizes past "after confirmation": re-check eligibility at the last possible moment before the irrevocable write, whether or not there's a confirmation UI in the middle.
- **Regex gotcha:** `FLEET_DESTRUCTIVE_RE` no longer exists (removed with the rest of the gate in #9722), but the underlying gotcha is general: a module-level regex reused across calls via `.exec()`/`.test()` must stay flagless (no `/g`/`/y`) to remain stateless and re-callable; if you add `/g` you must reset `.lastIndex` on every call or repeated calls drift.

## Applies when

- Adding or reviewing any destructive-confirm gate (`ConfirmDialog`) over a payload that is _derived, templated, or expanded_ before dispatch — recipe-variable substitution, bulk operations, context injection. Fleet broadcast itself is no longer gated this way (see Context) — the live examples to model against are `GitPushConfirmDialog`, the Artifact "Apply All Patches" flow, and `WorktreeDeleteDialog`.
- Working in `src/components/Fleet/` (broadcast, arming ribbon, execution) — the snapshot-then-re-filter mechanics (`initialOverrides`/`initialSkipped` in `fleetEnterBroadcast.ts`, `filterEligibleIds` in `fleetExecution.ts`) still apply even without a confirm dialog in the middle.
- A confirm dialog, or any deferred-dispatch flow, reads from a live Zustand store that rebuilds on keystroke/state-change while the user hasn't yet committed (TOCTOU between request and submit).
- Classifying an action in `docs/architecture/destructive-action-safeguards.md` as D2+ — the preview must show actual content (diff, message, resolved command, file list), never just a count or label.
- A threshold/danger check appears to run against user-typed input but the thing actually sent or applied differs per target after expansion.
- Adding `/g` or `/y` to a shared module-level regex used for repeated matching.
