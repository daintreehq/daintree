## Context

`GitInitDialog` drives the guided git-init flow with two IPC surfaces at once: it `await`s `projectClient.initGitGuided(...)` (an `ipcMain.handle` request/reply) and subscribes to `project:init-git-progress` push events (`CHANNELS.PROJECT_INIT_GIT_PROGRESS`, sent via `sendToRenderer` from `electron/ipc/handlers/projectCrud/gitInit.ts`) to render a live step log. Before #10372 the dialog derived success from `sawTerminalEventRef` — "did any progress event arrive by the time the invoke resolved?" — instead of from the invoke's own return value.

## Problem

Immediately after creating a project, a fully successful init showed a red "Initialization failed / finished without a status update" banner even though every step in the log was green (`.gitignore file created`, `Files staged`, `Committed: initial commit`, `Git initialization complete`) and the footer already showed the success-state `Continue` button. The repo was fine; only the banner was wrong (issue #10361). A green log directly above a failure banner is the misleading part — it reads as a rendering bug, not an ordering race.

## Root cause

Two transport paths, no ordering guarantee between them. Progress events push on their own channel via `sendToRenderer` (`webContents.send`); the invoke result returns through the `ipcMain.handle` reply. The handler emits every event _synchronously before it returns_, so main-side ordering is correct — but at the renderer the invoke Promise can resolve before those pushes reach the `onInitGitProgress` listener. The resolve-time check `if (!sawTerminalEventRef.current) setError("…finished without a status update…")` then fired: the reply won the race, no event had landed, the ref was still `false`. Worse, the fallback was sticky — the banner only cleared on an _error_-status event, so the `complete/success` event that arrived a moment later never cleared it (it only flipped `isComplete`, hence `Continue` showing while the banner stayed red).

The fix makes the invoke result authoritative. `GitInitResult` gained `outcome: "success" | "error"`, populated on _both_ resolve paths — the clean `emitProgress("complete","success")` return, and the identity-not-configured "commit skipped" branch that resolves-with-error instead of throwing. The dialog now trusts it: `result.outcome === "success"` completes and clears any stale error; the no-status fallback fires only on a non-success outcome with no event. The discriminant is named `outcome`, not `ok`/`success`, _deliberately_ — see lesson 3 on `ForbidIpcEnvelopeKeys` (#6020). Late `complete/success` events may now _clear_ a stale error, but guarded by `sawErrorEventRef` so a stray/foreign broadcast can't overwrite a real failure (a success never legitimately follows an error within one run).

## Lesson

- **Never infer an IPC invoke's success/failure from the arrival timing of side-channel push events.** The `ipcMain.handle` reply and `sendToRenderer`/`broadcastToRenderer` pushes are independent transports; even though main emits every event before it returns, the renderer can resolve the invoke Promise before those pushes reach their listener. Carry the outcome _in the invoke result_; treat progress broadcasts as log/UI decoration, not the source of truth for completion.
- **Put an explicit outcome discriminant in the invoke return type, set on EVERY resolve path.** #10372 added `outcome:"success"|"error"` on both the happy return and the "commit skipped / identity not configured" branch that resolves-with-error rather than throws. A discriminant set only on the happy path leaves the ambiguous cases as ambiguous as before.
- **That discriminant cannot be named `ok` or `success`.** `ForbidIpcEnvelopeKeys<T>` (#6020) rejects those keys on any typed handler return at the registration site with a branded compile error, because the security envelope owns `ok` and `_unwrappingInvoke` swallows inner `{ok:false}`. Use a neutral name (`outcome`, `result`, `status`).
- **A sticky error banner needs a symmetric clear path — with a directional guard.** The bug lingered because only an error event cleared the banner while a late success never did. If late events can _set_ an error, they must also be able to _clear_ it — but gate the clear (`sawErrorEventRef`) so a stray success can't mask a real terminal error. Model which polarity is terminal within one run (here error is terminal; success never legitimately follows it).
- **A "did any event arrive?" flag gating a fallback is a race smell.** `sawTerminalEventRef` conflated "the operation produced no result" with "the result beat the decorative events" — never let an absence-of-events check drive user-visible error state.

## Applies when

- Touching `src/components/Project/GitInitDialog.tsx`, `electron/ipc/handlers/projectCrud/gitInit.ts`, or `shared/types/ipc/gitInit.ts`.
- Wiring any renderer flow that pairs an `invoke` request/reply with push/broadcast progress events (`sendToRenderer`, `broadcastToRenderer`, `on…Progress` listeners) and derives completion or error state from them.
- Adding a success/failure discriminant to any IPC handler return type — check `ForbidIpcEnvelopeKeys` / #6020 before naming it `ok` or `success`.
- Diagnosing a spurious error banner that shows while every progress step reports success, or any UI state that "sticks" because only one polarity of event clears it, or code that infers an operation's outcome from event-arrival timing rather than its own return value.
