## Context

`WebviewDialog` renders the app-native dialog Daintree shows in place of a guest page's `window.confirm`/`window.alert`/`window.prompt`; the overlay wraps an OK button, a Cancel button, and (for prompts) a text input.

## Problem

Issue #11106: pressing Enter while the dialog's Cancel button was focused confirmed the guest's dialog instead of cancelling it — a user deliberately tabbed to Cancel, hit Enter, and got OK's behavior.

## Root cause

The overlay's wrapping `<div>` had an `onKeyDown` handler that ran unconditionally on every bubbled `Enter`: `e.preventDefault(); handleOk();`. A native `keydown` fires at the actually-focused element first and bubbles upward; the browser's built-in "Enter activates the focused button" behavior is evaluated as part of that same bubble phase, keyed off whether the event's default was prevented before it finishes bubbling. So the ancestor handler's `preventDefault()` reached the Enter before the browser could turn it into "click the focused button," cancelling the focused Cancel button's native activation — and then the handler's own unconditional `handleOk()` ran anyway, so the guest's dialog was always confirmed regardless of which button had focus. The same bug class existed in more dangerous form in `FleetArmingRibbon.tsx`: a capture-phase `window` keydown listener installed while a fleet confirmation was pending consumed Enter and dispatched `fleet.kill`/`fleet.trash` with `{confirmed: true}` — capture phase runs before the target's own listeners, so it beat a focused Cancel button to the key and could execute a destructive action the user thought they were declining.

## Lesson

- **Never intercept a key on an ancestor when a native element already owns that key's default action.** A focused `<button>` owns Enter (click activation); a focused `<input>` outside a `<form>` does NOT (there is no native Enter action to preserve). Test which is true before deciding whether the ancestor handler needs to touch the key at all — `WebviewDialog`'s fix left Enter alone entirely for buttons and gave only the prompt `<input>` its own `onKeyDown` submit handler.
- **`preventDefault()` on a bubbled `keydown` retroactively cancels the focused element's pending native action**, not just future default behavior — this is easy to get backwards because the code looks like it's only about "my dialog's Enter behavior," not "every focused descendant's Enter behavior."
- **Capture-phase `window`/`document` listeners are the sharper version of this trap**: they run before ANY target-phase handler, so they can override a focused Cancel button even if that button's own click-activation logic is completely correct. `FleetArmingRibbon`'s destructive-action listener needed an explicit modal-open guard (`document.querySelector('[role="dialog"][aria-modal="true"]') !== null`) to back off — the same guard pattern already used in `src/hooks/useGlobalKeybindings.ts`, so check that file before inventing a new one.
- **Guard by existence, not ancestry, when the interfering surface can portal.** Radix menus/selects render their content under `<body>`, outside the dialog's own DOM subtree, so `closest('[aria-modal])')` from the event target would miss them; a global `querySelector` for an open modal catches them regardless of where they're mounted.
- **A queue of sequential modals is one focus session, not N.** `useWebviewDialog.ts` captures `document.activeElement` only on the queue's empty→non-empty edge and restores only on non-empty→empty, specifically to avoid a naive per-dialog recapture recording the _previous_ dialog's own OK button as "what to restore to." Capture runs in a `useLayoutEffect` (before the overlay's `requestAnimationFrame`-deferred autofocus can move focus first).
- **`.focus()` is a silent no-op on a disconnected, disabled, or inert candidate** — it neither throws nor moves `document.activeElement`, so a restore chain must verify each candidate actually took focus (`document.activeElement === candidate`) before accepting it, or focus silently drops to `<body>`. `restoreFocusTo()` in `src/lib/accessibility.ts` is the shared primitive for this chain (previously-focused element → the webview → the app shell's first tabbable) — reuse it for future modal/overlay focus-restore rather than hand-rolling another one.

## Applies when

- Adding or reviewing any ancestor `onKeyDown`/`keydown` handler over a region containing native interactive elements (`button`, `input`, `select`) — check whether the key you're intercepting already has a native action on the focused descendant.
- Adding a capture-phase global keydown listener for a destructive or confirming action (kill/trash/delete/confirm shortcuts) — it must back off while any `[role="dialog"][aria-modal="true"]` is open, checked by existence not ancestry.
- Building or touching a dialog/overlay that can queue (multiple pending confirms/prompts) — verify capture/restore treats the whole queue as one session, not per-item.
- Implementing focus restore-on-close for any modal/popover — reuse `restoreFocusTo()` rather than a bare `.focus()` call, and verify the candidate actually took focus.
- Diagnosing "the wrong button's action ran on Enter/keyboard-only interaction" in any dialog, ribbon, or confirmation surface.
