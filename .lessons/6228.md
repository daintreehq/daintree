## Context

PTY output is mirrored into a `@xterm/headless` `Terminal` instance per process (`TerminalProcess.terminalInfo.headlessTerminal`). `trimScrollback(targetLines)` is the buffer-reclaim primitive: it lowers `headlessTerminal.options.scrollback`. The `ResourceGovernor` (utility-process pty-host) wires this as `trimBuffers` and calls it as a one-shot "pre-pause reclaim" under memory pressure before escalating to throttling/pausing terminals.

## Problem

A global scrollback governor that reclaims memory under pressure only works if shrinking `options.scrollback` retroactively trims the live buffer. If lowering scrollback merely capped future appends (leaving already-buffered lines resident), the governor's `trimBuffers()` call would free nothing and the escalation logic ("trim first, wait one tick, then pause") would be built on a false premise. The behavior is not documented per-version and is easy to assume wrong.

## Root cause

In `@xterm/headless` 6.0, assigning a smaller value to `terminal.options.scrollback` triggers an immediate, synchronous buffer resize: existing lines beyond the new limit are evicted in the same tick (`buffer.active.length` drops right after assignment). Eviction drops the _oldest_ lines and retains the _newest_ (verified: `line 0` gone, `line ${N-1}` retained in `electron/__tests__/headless-scrollback-trim.test.ts`). The evicted lines' JS references are released synchronously, but `heapUsed` does not fall until GC runs — so the governor must wait a tick after trimming before deciding whether to escalate (see the comment block in `ResourceGovernor.ts` around the `trimBuffers()` call: "drops JS references synchronously so the next GC can collect old-gen scrollback strings. heapUsed won't drop in this tick").

## Lesson

- Treat `headlessTerminal.options.scrollback = n` as **active eviction**: it immediately shrinks the live buffer, oldest-first, not just a forward cap. This makes it a legitimate memory-reclaim lever.
- Reclaim is two-phase: the assignment frees references synchronously, but heap only drops after the next GC. Any governor logic that gates on `heapUsed` must wait at least one tick after trimming before measuring or escalating.
- The complement (`growScrollback`) only raises the cap and does not retroactively recover already-evicted lines — trimming is lossy; don't rely on growing scrollback to restore trimmed history.
- If you bump the xterm major version, re-verify this eviction semantics (it underpins `ResourceGovernor`'s pre-pause reclaim); `electron/__tests__/headless-scrollback-trim.test.ts` is the canonical guard.

## Applies when

- Designing or modifying memory-reclaim logic in `electron/pty-host/ResourceGovernor.ts` (the `trimBuffers` / pre-pause path) or `TerminalProcess.trimScrollback` / `growScrollback`.
- Upgrading `@xterm/xterm` or `@xterm/headless` to a new major and validating buffer/scrollback behavior.
- Investigating why memory does (or does not) drop after a scrollback trim, or why `heapUsed` lags a synchronous trim by a tick.
- Reasoning about whether shrinking any xterm `scrollback` setting affects already-buffered output vs only future writes.
- Touching `shared/config/scrollback.ts` (`SCROLLBACK_MIN`, `normalizeScrollbackLines`) where trim targets are defined.
