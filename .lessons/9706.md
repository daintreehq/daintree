## Context

Daintree's icon policy is Lucide-only with a short list of sanctioned bespoke exceptions (`src/components/icons/README.md`), and `AgentStateCircles.tsx` is one of them: `SpinnerCircle`, `HollowCircle`, `InteractingCircle`, and `ExitedCircle` are hand-drawn agent-state glyphs on a **16×16 viewBox**. They render at `w-3 h-3` (12px) directly beside Lucide icons in `QuickStateFilterBar.tsx`, `HelpPanelHeader.tsx`, `DockedTerminalItem.tsx`, `DockedTabGroup.tsx`, and `terminalStateConfig.tsx`. The icons were born (commit `17dfa4c70`) with `strokeWidth="2"` — copied from Lucide's convention.

## Problem

Issue #9705: in the worktree quick-state filter chips, the working and waiting circles looked visibly heavier than the finished chip (Lucide's `CheckCircle2`) at the same 12px render size. The misleading part is that every icon involved declared the **identical** `strokeWidth="2"` attribute — a source-level diff of the SVGs suggests they should match, so the weight difference reads like a rendering bug or a font-smoothing artifact rather than what it is.

## Root cause

SVG `stroke-width` is measured in **user units — the viewBox coordinate system — not device pixels**. The rendered line weight is `strokeWidth × (renderSize / viewBoxSize)`. At 12px: the custom 16-viewBox circles drew `2 × 12/16 = 1.5px` strokes while Lucide's 24-viewBox `CheckCircle2` drew `2 × 12/24 = 1.0px` — exactly 1.5× heavier, and the ratio is render-size-independent, so no `w-*` sizing tweak can fix it. The fix (#9706) normalized the custom icons to Lucide's grid by setting the ring `strokeWidth` to `1.333` (= `2 × 16/24`) and scaling the inner detail strokes by the same 2/3 factor (`InteractingCircle` cross `1.5 → 1.0`, `ExitedCircle` dash `1.8 → 1.2`), preserving the hand-tuned inner-to-ring proportions (0.75× and 0.9×). Geometry (`r=6`, the circumference-derived `DASH`/`GAP` arc constants) was untouched — only stroke weights changed. All four circles were fixed even though only two appear in the filter bar, because the same components render in the help-panel header and terminal state config; fixing only the reported pair would have traded one inconsistency for another.

## Lesson

- **Never copy Lucide's `strokeWidth=2` into an SVG with a non-24 viewBox.** Rendered weight = `strokeWidth × renderSize / viewBoxSize`, so a bespoke icon matches Lucide's line weight only when `strokeWidth = 2 × viewBox/24` (1.333 for a 16 grid). Alternatively draw new bespoke icons on the 24×24 grid so Lucide's nominal values are honest — `McpServerIcon` does this (24 viewBox; its 1.6 stroke is a deliberate weight choice, not a scaling error).
- **Rescale every stroke in the icon by the same factor, including inner detail strokes.** The inner/ring thickness proportion is the design; scaling only the ring silently fattens the inner details relative to it. #9706's factor-of-2/3 applied uniformly kept `InteractingCircle` at 0.75× and `ExitedCircle` at 0.9× of the ring.
- **The trap only bites stroke-based icons.** Fill-based glyphs (`brands/` — viewBoxes range from 21 to 1200) are immune because fills have no line weight; a wildly nonstandard viewBox on a fill icon is fine.
- **Fix all consumers of a shared icon component, not the surface where the mismatch was reported.** `AgentStateCircles` renders in five sites; a filter-bar-only fix would have introduced a new cross-surface inconsistency.
- **Guard weight parity with a cross-icon ratio test, not a literal.** The regression test in `icons-a11y.test.tsx` renders each custom circle AND a real `CheckCircle2`, computes `strokeWidth / viewBoxWidth` for both from the DOM, and asserts equality (`toBeCloseTo(…, 3)`), plus a second test pinning the inner/ring stroke ratio. Reading a relationship between two rendered icons keeps it out of the repo's banned tautological-literal pattern (`expect(x).toHaveClass(...)`) — it fails if either side drifts. Attribute-host gotcha: Lucide puts `stroke-width` on the `<svg>`, the custom icons put it on the `<circle>`/`<line>`.

## Applies when

- Adding or modifying any bespoke stroke-based icon in `src/components/icons/` that renders beside Lucide icons — the README's sanctioned-exception list (`DaintreeIcon`, `AgentStateCircles`, `McpServerIcon`, `brands/`) is exactly where this recurs.
- Diagnosing "this icon looks heavier/bolder/thicker than its neighbors" when the SVG sources declare the same `strokeWidth` — check the viewBoxes first, not the render size or antialiasing.
- Changing an existing bespoke icon's viewBox (re-gridding, adding padding) — `strokeWidth` must be re-derived by the new ratio or the weight shifts.
- Reviewing a PR that pastes Lucide-path or Lucide-styled SVG markup into a component with a non-24 viewBox.
- Writing icon consistency tests — assert DOM-read ratios between two rendered components, never literal `stroke-width` values copied from the source (CI no-tautology rule).
