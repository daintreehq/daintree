## Context

Plugins contribute launchable agents via `contributes.agents` (#10560, part of #10511). `AgentContributionSchema.command` originally accepted only bare PATH binary names (`SAFE_ID_PATTERN = /^[a-zA-Z0-9._-]+$/`), so a plugin could not ship a self-contained agent backed by its own bundled code — the realistic case. #10574 widened the schema to accept `./`-prefixed plugin-relative paths and wired them end-to-end through `registerPluginAgents` → `contributionToAgentConfig` → the node-pty spawn.

## Problem

A plugin-relative command like `./bin/agent.mjs` looks like it should "just work" because the terminal spawns with `cwd` set to the worktree/plugin dir. It doesn't: the binary resolves against the wrong directory and ENOENTs at spawn; and once made absolute, a space in the install path (macOS `~/Library/Application Support/...`) silently splits the command string into `command` + stray args, so the agent launches wrong or not at all.

## Root cause

node-pty resolves the command binary BEFORE it applies the `cwd` option — a relative command is resolved against the process's own cwd, not the spawn cwd, so a plugin-relative path never points where the manifest author expects. The fix is to resolve `./`-commands to an absolute path at REGISTRATION time, never at spawn: `resolvePluginAgentCommand` in `shared/config/pluginAgentRegistry.ts` joins the command against the plugin's install `pluginDir`, threaded through `registerPluginAgents(id, contributions, pluginDir)`. It uses a separator-aware pure string join (not `node:path`) so the module stays safe to bundle in the renderer, relying on the schema to guarantee POSIX `./seg/seg` form. Two secondary traps ride along. (1) The resolved absolute path has separators, which `CliAvailabilityService.VALID_COMMAND_RE` (`/^[a-zA-Z0-9._-]+$/`) rejects — so an `isAbsolute(command)` branch probes the file directly via `probeNativePaths` (existence + X_OK) instead of rejecting it. (2) The absolute path contains spaces on macOS — so `resolveAgentLaunchBaseCommand` (`src/utils/agentLaunchCommand.ts`) shell-escapes any path-like base command (`escapeShellArgOptional` on POSIX, `& '...'` quoting on Windows) before it reaches the spawn string. The schema also REQUIRES the `./` prefix for relative paths and rejects bare `bin/agent.mjs`, absolute paths, `\` separators, NUL, and any `..` traversal segment: a bare relative path is ambiguous with a PATH name, and `..` could escape the plugin dir, so `isSafePluginAgentCommand` (`electron/schemas/plugin.ts`) turns those into loud manifest errors rather than a spawn-time ENOENT or an escape from the plugin directory.

## Lesson

- **node-pty resolves the command binary before applying `cwd`** — never pass a relative command expecting the spawn `cwd` to anchor it. Resolve to an absolute path at the point you know the base dir (registration), not at spawn. `resolvePluginAgentCommand` deliberately uses a pure separator-aware string join, not `node:path`, so the registry stays renderer-bundle-safe; the schema already guarantees the input is POSIX `./seg/seg`.
- **Widening a "command" field from PATH-name to path breaks every consumer that regex-validates it.** `CliAvailabilityService.VALID_COMMAND_RE` rejects separators, so a resolved plugin path needs a dedicated `isAbsolute()` → filesystem-probe branch. When you loosen such a field, audit each consumer for a bare-PATH-name assumption.
- **A resolved path with spaces silently splits the spawn string.** macOS plugin dirs live under `~/Library/Application Support` — path-like base commands MUST go through `resolveAgentLaunchBaseCommand` / `escapeShellArgOptional`, never be concatenated raw. The arg-count regression is invisible until a user installs under a spaced path, so a happy-path test on `/tmp/plugins` won't catch it.
- **Require an explicit `./` for plugin-relative paths and reject `..`/absolute/backslash at the schema, not at spawn.** `isSafePluginAgentCommand` makes ambiguity (`bin/agent` vs a PATH name) and traversal loud manifest errors. This intentionally mirrors the MCP-server `command` contract documented on the same plugins docs page — keep the two rules in sync.

## Applies when

- Adding or widening any plugin manifest field that becomes a spawned command/binary path (agents, MCP servers, forge providers) — check node-pty resolution order and every PATH-name assumption downstream.
- Diagnosing a plugin/agent that ENOENTs at spawn even though the file exists and cwd looks correct — the command was resolved relative to the wrong directory before cwd applied.
- A command that works from `/Users/x/plugins` but fails once installed under `Application Support` — suspect an unescaped space in a path-like command.
- Touching `resolvePluginAgentCommand`, `registerPluginAgents`, `isSafePluginAgentCommand`, `CliAvailabilityService.VALID_COMMAND_RE`/`probeNativePaths`, or `resolveAgentLaunchBaseCommand`.
