## Context

`useConsoleCaptureStore` retained per-pane message entries forever because its only cleanup path was the React component unmount in the DevPreview console components. The store-orchestration layer knew how to react to panel teardown but never called into the capture store.

## Problem

Programmatic panel removal (project reset, close-all, drag-out) never unmounted the component, so captured messages leaked indefinitely in memory across sessions.

## Root cause

Relying on component unmount as the cleanup trigger only works for user-driven close actions. Any path that destroys state without rendering (reset, migration, restore) bypasses the cleanup entirely. The store orchestration layer is the single source of truth for "this terminal/panel is going away" — every peer store that holds entity-keyed data needs to be notified from there. In this codebase that choke point is the `panelStore` subscription in `rendererStoreOrchestrator.ts`, which diffs `panelIds`, computes `removedIds`, and fans out a removal call to each peer store; `panelStore`'s `onTerminalRemoved` middleware handles the terminal-slice teardown.

## Lesson

Entity teardown must be coordinated from the layer that owns the lifecycle (the `panelStore` `panelIds` subscription in `rendererStoreOrchestrator.ts`, fed by `panelStore`'s `onTerminalRemoved` middleware), not from React component unmounts. Every peer store with entity-keyed data needs a removal call (e.g. `useConsoleCaptureStore.getState().removePane(id)`, `useResourceMonitoringStore.getState().removePanel(id)`) from that single choke point. Component unmount cleanup is fine as belt-and-suspenders, but never the primary path. Run the cleanup synchronously on the removal diff — do not defer it, the cleanup must complete in the same tick as the removal.

## Applies when

Adding a new Zustand store that holds per-terminal/per-panel/per-worktree state. Audit the panel-removal fan-out in `rendererStoreOrchestrator.ts` (and `panelStore`'s `onTerminalRemoved` middleware / similar `onXxxRemoved` orchestrators) and add your cleanup call there. Also applies when investigating memory leaks during rapid open/close cycles.
