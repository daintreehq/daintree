## Context

`TerminalProcess` starts a `ProcessDetector` (`electron/services/ProcessDetector/ProcessDetector.ts`) keyed on the spawned PTY's OS pid, to build process-tree evidence for agent-state detection and descendant-process counting (`getPtyDescendantCount`, `TerminalRegistry.getProjectStats`). The pty-host also emits a `terminal-pid` event over the host/main IPC boundary (`electron/pty-host/handlers/lifecycle.ts` → `PtyEventRouter.ts`) so the renderer/main side learns the pid for killing and resource tracking (`ResourceGovernor.trackKilledPid`).

## Problem

On Windows, every terminal logged a repeating `[WARN] [PtyHost] Invalid PTY PID for terminal <id>: 0` on every refresh tick (filed as #10787, reported from local Windows E2E). Not a crash — steady-state noise — but it meant `ProcessDetector` was starting on an unusable pid and could never produce process-tree evidence for that terminal, silently degrading agent-state detection on every Windows terminal.

## Root cause

`node-pty`'s Windows ConPTY backend reports `pid: 0` for a real, non-zero window of time between spawn and the async `connect()` completing (`_innerPid` starts at `0` and only gets the true value once the conout socket attaches) — and critically, **no event ever fires when the real pid lands**. Every producer/consumer site in the codebase gated on `pid !== undefined`, and `0 !== undefined` is `true`, so the sentinel sailed through every check that looked type-safe: the `ProcessDetector` constructor guard in `TerminalProcess.ts`, `startProcessDetector()`, `getPtyDescendantCount()`, `createProcessStateValidator()` in `terminalActivityPatterns.ts`, the `terminal-pid` emit and four `trackKilledPid` call sites in `lifecycle.ts`, and `TerminalRegistry.getProjectStats()`'s pid filter — eight-plus sites total, none of which independently looked wrong.

The one-line fix (`pid !== undefined` → `pid > 0`, generalized to a shared `isValidPid` helper requiring `Number.isInteger(pid) && pid > 0`) is necessary but not sufficient. `TerminalProcess`'s constructor captures `ptyPid` once and hands it to `new ProcessDetector(...)`; just tightening that check to `> 0` means a terminal spawned during the pid-0 window never gets a detector for its lifetime, since nothing re-reads the pid later — trading warning-spam for silently-permanent loss of process monitoring. The fix instead adds a bounded `setImmediate` poll, `schedulePidRetry` in `lifecycle.ts` (capped at `PID_RETRY_MAX_ATTEMPTS = 20`), re-reading `ptyManager.getTerminal(id)?.ptyProcess?.pid` across event-loop turns until positive, then emitting `terminal-pid` and calling the new `PtyManager.startProcessDetectorForTerminal(id)` (idempotent — `startProcessDetector()` no-ops if a detector exists). The retry abandons cleanly if the terminal is killed/trashed before the pid resolves (`getTerminal` returns `undefined`).

## Lesson

- **A "not undefined" check on a numeric OS handle (pid, fd, socket) is not the same as "valid".** `0` is a real sentinel for "not yet assigned" on at least one platform backend (Windows ConPTY here) and passes every `!== undefined` / `!= null` guard a reviewer would call type-safe. Gate pid/fd/handle values on `Number.isInteger(x) && x > 0`, not just definedness.
- **A tightened validity gate that only rejects, with no retry, converts a noisy bug into a silent one.** If the value can transition from invalid to valid later (ConPTY resolving) and nothing re-checks it, gating harder just makes the feature quietly stop working instead of complaining loudly. Before shipping a stricter guard, check whether anything re-reads the value after it first fires false — if not, add the retry/poll in the same change.
- **When a library hands you a transient invalid value with no completion event, poll the live object, don't trust a one-time read.** `node-pty` never emits anything when ConPTY's real pid lands; the fix polls `ptyManager.getTerminal(id)?.ptyProcess?.pid` via bounded `setImmediate` recursion (20 attempts) instead of waiting on an event that doesn't exist.
- **One bad sentinel entering at the producer propagates to every consumer that trusts it** — this touched 8+ sites across `lifecycle.ts`, `TerminalProcess.ts`, `PtyEventRouter.ts`, `TerminalRegistry.ts`, `terminalActivityPatterns.ts`. `PtyEventRouter.ts`'s `terminal-pid` handler re-validates as defense-in-depth even though the pty-host already gates it — don't assume an upstream gate makes downstream validation redundant across a process/IPC boundary.
- **Grep every pid/handle comparison for the same sentinel before calling a fix complete** — the same loose `!== undefined` idiom was copy-pasted across producer and consumer sites, so a single-site patch would have left the warning (or the silent-loss variant) alive elsewhere.

## Applies when

- Touching anything that reads `ptyProcess.pid` — `TerminalProcess.ts`, `lifecycle.ts`, `PtyEventRouter.ts`, `TerminalRegistry.ts`, `terminalActivityPatterns.ts`, or `PtyManager.ts` — especially `startProcessDetector`, `getPtyDescendantCount`, `createProcessStateValidator`.
- Diagnosing repeated `Invalid PTY PID for terminal <id>: 0` warnings or agent-state/process-tree detection that never activates, specifically on Windows.
- Adding or reviewing any gate of the form `value !== undefined` / `value != null` on a numeric OS handle (pid, fd, socket, handle) — check whether `0` or another sentinel int can pass it.
- Writing a stricter validity check for a value that can transition from invalid to valid asynchronously — verify a retry/poll/re-trigger path exists, or the stricter check just hides the feature failing silently.
- Working with `node-pty` on Windows/ConPTY generally — the pid-during-connect() window is a real platform quirk, not a Daintree bug, and no upstream event marks its resolution.
