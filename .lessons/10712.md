## Context

#10696 promoted the fleet-broadcast primitives `terminal.arm`, `terminal.disarm`, `terminal.disarmAll` from renderer-only to MCP-callable, adding them to `MCP_TOOL_ALLOWLIST_ENTRIES` in `electron/services/mcp-server/shared.ts` (the `external`/api-key tier's curated surface) with `danger: "safe"` and mutation-tier rate limiting. #10712 is the immediate follow-up, filed because the Daintree Assistant's own drift check flagged the same three tools as "documented but missing from the live server."

## Problem

Three tools that #10696 had just spent a whole PR wiring through MCP — confirm-classified, rate-limited, action-tested — were invisible to the Daintree Assistant one PR later. The assistant connects at help-tier `system` (`HelpSessionService.ts`, `isDaintreeAssistant` check against `ASSISTANT_ONLY_AGENT_IDS`), not `external`, and `tierAuth.ts`'s `shouldExposeTool` gate (called from `sessionServer.ts`'s tool-listing path) only consults `TIER_ALLOWLISTS[tier]`. Since the arming tools were absent from `WORKBENCH_TIER_TOOLS` / `ACTION_TIER_ADDONS` / `SYSTEM_TIER_ADDONS` in `shared/config/helpAssistantTierAllowlists.ts`, they were dispatchable by an api-key client but never advertised to the in-app assistant — despite both paths ultimately gating the same `ActionService` action.

## Root cause

`electron/services/mcp-server/shared.ts` builds `TIER_ALLOWLISTS` as `{ workbench, action, system: unionSet(WORKBENCH_TOOLS, ACTION_TIER_ADDONS, SYSTEM_TIER_ADDONS), external: MCP_TOOL_ALLOWLIST }` — four tiers, but `external` draws from a separate source list (`MCP_TOOL_ALLOWLIST_ENTRIES`, curated in `shared.ts` itself) than `system`/`action`/`workbench` (drawn from `shared/config/helpAssistantTierAllowlists.ts`). Neither list is derived from or validated against the other. `docs/architecture/mcp-server.md` already calls this out for forge actions ("keep these three lists in lockstep... the tier snapshots guard against drift"), but that guidance is comment-only — it did not stop the exact same drift recurring for a different tool family one PR later. The #10712 body says it plainly: "There's no build-time guard diffing `MCP_TOOL_ALLOWLIST` against the help-tier sets, which is why this drift went unnoticed" — and as of this writing (verified via `grep -rn "MCP_TOOL_ALLOWLIST\|helpAssistantTierAllowlists" scripts/`) that guard was never built; the trap is still live. The fix itself is a deliberate placement, not a mechanical sync: `terminal.arm`/`disarm`/`disarmAll` went into `SYSTEM_TIER_ADDONS` only (not `WORKBENCH_TIER_TOOLS`/`ACTION_TIER_ADDONS`) because the Daintree Assistant (`ASSISTANT_ONLY_AGENT_IDS`) is deliberately granted `system` while third-party Claude/Codex help overlays sit at the `action` floor and should NOT get fleet-arming power — mirroring the boundary already used for `worktree.delete` and the git mutations.

## Lesson

- **Adding a tool to `MCP_TOOL_ALLOWLIST_ENTRIES` (external/api-key tier) does not expose it to the help-assistant tiers, and vice versa** — these are two hand-curated lists in different files (`electron/services/mcp-server/shared.ts` vs `shared/config/helpAssistantTierAllowlists.ts`) with no shared source of truth or cross-check.
- **Every new MCP-exposed action needs a deliberate placement decision in BOTH curations**, not a copy-paste: which help tier (`workbench`/`action`/`system`) it belongs in is a separate judgment call from whether `external` clients should reach it at all — `danger` classification affects neither decision (`terminal.arm` is `danger:"safe"` yet still gated to `system`, purely on tier policy).
- **`system` tier is the "this is our own conductor" boundary, not just "more powerful."** The Daintree Assistant (`ASSISTANT_ONLY_AGENT_IDS`, checked in `HelpSessionService.ts`) is force-elevated to `system`; third-party help overlays (Claude/Codex) stay at the user-configured `action` floor. Adding a tool to `SYSTEM_TIER_ADDONS` means "the first-party assistant gets this by default, third-party overlays never do without an explicit grant" — confirm that's the intended blast radius before placing a tool there.
- **A "documented but missing from the live server" drift report from the assistant's own tooling is a real signal of exactly this class of bug** — check both allowlist files before assuming a wiring bug in the dispatch path.
- **The comment-only "keep in lockstep" convention is not enforced anywhere** — a build-time guard (in the style of `scripts/ci/check-channel-drift.mjs`) diffing tool ids across `MCP_TOOL_ALLOWLIST_ENTRIES` and the three `helpAssistantTierAllowlists.ts` exports would close this permanently; nothing currently stops the next tool from repeating #10696/#10712.

## Applies when

- Adding any new MCP-exposed action (`scope` other than pure-renderer, or explicitly wired for MCP) — check placement in BOTH `MCP_TOOL_ALLOWLIST_ENTRIES` (`electron/services/mcp-server/shared.ts`) and the relevant `helpAssistantTierAllowlists.ts` tier array.
- Diagnosing "the Daintree Assistant can't see tool X" or any drift-check output claiming a tool is documented but not live — check `shouldExposeTool`/`TIER_ALLOWLISTS` against both source lists before assuming a dispatch bug.
- Deciding which help tier a new action belongs in — distinguish "should the first-party assistant (`system`) get this" from "should third-party overlays (`action` floor) get this" from "should external api-key clients (`external`) get this"; these are three independent yes/no calls.
- Touching `electron/services/mcp-server/shared.ts`, `shared/config/helpAssistantTierAllowlists.ts`, or `HelpSessionService.ts`'s `isDaintreeAssistant`/tier-resolution logic.
- Reviewing a PR that adds a tool to only one of these lists — treat it as incomplete unless the PR explicitly reasons about the other curation, per #10696 → #10712.
