## Context

The portal (in-app browser dock) caps live `WebContentsView`s at `PORTAL_MAX_LIVE_TABS = 3` (`electron/services/PortalManager.ts`); `evictIfNeeded()` walks `lruOrder` and destroys the oldest view, skipping only `this.activeTabId`. The renderer restores an evicted/persisted tab in `PortalVisibilityController.ensureTabAndRestore`: IPC `portal.create` → poll `getPortalPlaceholderBounds()` up to ~1s (20 × 50ms waiting for the DOM placeholder to lay out) → IPC `portal.show`. Crucially, `activeTabId` is assigned only at the very end of `showTab()`.

## Problem

A tab could vanish while it was being restored, stranding the dock on its restore skeleton forever — `isTabRestoring = !createdTabs.has(activeTabId)` never cleared because the follow-up `showTab` found no view in `viewMap` and silently returned early (#9971). The trigger is concurrent background creates during the ~1s bounds-polling window: `portal.openUrl({ background: true })` calls `create` without `show`, so three background opens push the restoring tab to LRU-oldest and the fourth `createTab`'s `evictIfNeeded()` destroys it mid-restore.

## Root cause

Two facts about the guard make the whole restore window unprotected. First, the protection key (`activeTabId`) is written at the END of the flow it is supposed to protect — for the entire create → bounds-poll → show interval it is still null or pointing at the previous tab, so main-process state lags the renderer's intent by up to a second. Second, `createTab` ending with `touchLru(tabId)` looks protective but isn't: recency in an LRU only shields a tab during its own `evictIfNeeded()` call; any subsequent create demotes it. The fix (#10166) is an explicit in-flight set: `PortalCreatePayload.isRestore?: boolean` travels on the first IPC call, the `portal.create` handler calls `markRestoring(tabId)` BEFORE `createTab` (order asserted in `portal.create.test.ts` — marking after would reopen a sub-window and orphan the guard if create throws), and `evictIfNeeded()` skips `restoringTabIds` members. The guard is cleared on every terminal path: `showTab()` success (where the `activeTabId` guard takes over), `destroyView()`, the `webContents` `"destroyed"` handler, `createTab`'s invalid-URL early return AND its catch block, and `destroy()`. Miss one and a reused tab id inherits a permanent eviction shield — the test suite enumerates each path individually. When every candidate is protected (all live tabs active-or-restoring), eviction deliberately does nothing and the live count temporarily exceeds the cap; the next `showTab()` runs `touchLru` + `evictIfNeeded()` and reclaims. `destroyHiddenTabs()` (the memory-pressure sweep) was intentionally left keying on `activeTabId ?? lastShownTabId` only — a pressure sweep during a cold restore can still kill the mid-restore tab, and the renderer recovers via `onTabsEvicted → markTabsUncreated` re-triggering restore. That gap is a scope decision, not an oversight — don't "fix" it without reading #10166's rationale.

## Lesson

- **A protection check keyed on a "current/active" pointer written at the end of a multi-step async flow protects nothing during the flow.** `activeTabId` is set in the last line of `showTab()`, but restore is create → ~1s polling → show; the whole window was evictable. Audit any eviction/cleanup guard for WHEN its key is written relative to the operation it guards.
- **Carry intent as an explicit flag on the FIRST call of the flow, not inferred later.** The renderer knows it's restoring; main cannot deduce it. `isRestore: true` on `PortalCreatePayload` lets the IPC handler mark protection before any eviction can run. Mark BEFORE the operation that can trigger eviction (`markRestoring` precedes `createTab`, order-asserted).
- **An in-flight protection Set needs a clear on every terminal path, proven by tests per path.** #10166 clears in five places (showTab, destroyView, destroyed handler, both createTab failure paths, destroy()); a single leak makes a reused id permanently unevictable. When adding such a set, enumerate success/failure/teardown exits and write one test per exit — the "reused tab id must not inherit protection" assertions are the template.
- **When all eviction candidates are protected, temporarily exceed the cap rather than violate a protection.** `PORTAL_MAX_LIVE_TABS` is a soft cap: overflow is tolerated until a `showTab` releases a guard and the deferred `evictIfNeeded()` reclaims. Never weaken protection to satisfy a resource cap synchronously.
- **`touchLru` recency is not protection.** It only wins the eviction that runs in the same call; the next create demotes it. If a lifecycle stage must survive concurrent creates, it needs a membership guard, not a fresher LRU slot.

## Applies when

- Touching `PortalManager` eviction/lifecycle (`evictIfNeeded`, `destroyView`, `destroyHiddenTabs`, `markRestoring`) or the `PortalVisibilityController` restore flow — especially tempted to "simplify away" `restoringTabIds` or extend the pressure sweep to respect it.
- Adding LRU eviction, caps, or pressure-reclaim to any subsystem whose setup spans multiple async steps or IPC round-trips — `ProjectViewManager` view eviction, plugin subprocess pools, panel restore — ask what protects an item between creation and the moment the "active" pointer lands on it.
- Diagnosing a portal tab stuck on its restore skeleton (`isTabRestoring` never clears) or any "restored thing silently disappeared" symptom — check whether a concurrent create evicted it inside the create→show window.
- Reviewing any guard of the form `if (id === this.activeX) continue;` in an eviction loop — verify when `activeX` is assigned relative to the multi-step flows that create the items it protects.
- Writing a protection/ownership Set keyed by reusable ids — verify every failure and teardown path deletes the entry, or a recycled id inherits stale protection.
