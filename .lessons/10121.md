## Context

Cold-start session restore runs through `hydrateAppState` (`src/utils/stateHydration/index.ts`), whose FIRST await is `ensureHydrationBootstrap()` (`src/utils/stateHydration/bootstrapGuard.ts`): a `Promise.all` of `keybindingService.loadOverrides()` and `useUserAgentRegistryStore.initialize()`, ahead of `appClient.hydrate()` and every restore phase (panels, active worktree, MRU, tab groups, recipes). The whole chain is invoked from `useAppHydration` (`src/hooks/app/useAppHydration.ts`), whose `restoreState` wraps it in one try/catch.

## Problem

Issue #9931: if `window.electron.keybinding.getOverrides()` rejected, the rejection propagated out of the bootstrap `Promise.all` and aborted the entire session restore — no panels, no worktree selection, no MRU, no tab groups, no recipes. The misleading part: nothing crashed and no error surfaced. `useAppHydration`'s catch logs `"Failed to restore app state"` and its `finally` sets `isStateLoaded(true)` anyway, so the user just got an empty workspace with no explanation — a cosmetic subsystem (keyboard shortcut overrides) silently took down restore.

## Root cause

Two contracts collided inside one `Promise.all`. The sibling task `useUserAgentRegistryStore.initialize()` self-catches: on failure it sets `{ error: formatErrorMessage(e, ...), isInitialized: false }` in its store and resolves — non-fatal by construction. `loadOverrides()` awaited the IPC bare, so its rejection was the only path out of the bootstrap that could rethrow. And the outer boundary is fail-open by design: `useAppHydration` catches, logs, and marks the app loaded regardless, which means the outer catch is a symptom mask, not a handler — any per-task rejection anywhere on the hydrate path becomes "app loads fine, workspace is empty", one of the hardest symptom shapes to trace back to its cause. The per-phase restore code already followed the degrade convention (`logWarn("Failed to restore panels during hydration")`, draft inputs, tab groups each self-catch); the bootstrap task was the asymmetric hole.

The fix (#10121) brings `loadOverrides()` into the self-catch contract with three deliberate mechanics beyond the bare try/catch: (1) last-known-good ordering — the pre-fix body called `this.overrides.clear()` and rebuilt after the await, so the restructure ensures the clear only happens after the IPC resolves (today `clear()` lives inside `applyOverrides()`, called only on success), meaning a failed reload can never clobber previously loaded customizations and a fresh boot falls back to constructor-seeded `DEFAULT_KEYBINDINGS`; (2) no `notifyListeners()` on the degraded path — the constructor seed is already the stable observed state, so notifying would churn subscribers for a no-op; (3) the warn formats via `formatErrorMessage(error, fallback)` from `@shared/utils/errorMessage` because interpolating a hostile rejection value (an object whose `toString`/`Symbol.toPrimitive` throws) into a template literal throws INSIDE the catch and re-introduces the exact failure being handled — there is a regression test for this in `KeybindingService.test.ts`.

Post-fix evolution (verified current as of 2026-07): #10390 added the batched `app:boot` payload, so `bootstrapGuard.ts` now seeds via `keybindingService.applyOverrides(boot.keybindingOverrides)` when the ride-along field is present and only falls back to the `loadOverrides()` IPC pull on older mains or the safe-boot `{ ok: false }` path — the self-catch still guards that fallback. The guard's singleton (`hydrationBootstrapPromise`) still nulls itself on rejection so a genuinely fatal bootstrap error retries on the next call; that path remains reachable only through `initialize()`-style tasks rejecting, which production code prevents by the same self-catch contract.

## Lesson

- **Every task awaited on the `hydrateAppState` path must self-catch and degrade** — the outer `useAppHydration` catch logs and sets `isStateLoaded` anyway, so an uncaught rejection doesn't crash or surface, it silently aborts every restore phase after it and ships an empty workspace. Adding a new bootstrap task or restore phase without internal degradation re-opens #9931 for whatever subsystem you touched.
- **Siblings in one `Promise.all` must share one error contract.** The tell in #9931 was asymmetry: `initialize()` degraded into store error state while `loadOverrides()` rethrew. When adding a member to an existing `Promise.all`, read how the current members handle failure and match it — a single rethrowing member defines the failure mode for the whole batch.
- **Reload-style loaders must not clear current state until the replacement payload has resolved.** Order the body as await-then-clear-then-apply (today: `applyOverrides()` runs only on IPC success), so a transient failure keeps last-known-good overrides instead of wiping user customizations to defaults.
- **Inside a catch block, never `String(error)`-interpolate — use `formatErrorMessage(error, fallback)`.** Hostile rejection values with throwing coercion re-throw inside the handler, silently converting your non-fatal path back into a fatal one.
- **Weigh the subsystem against the blast radius.** Keyboard-shortcut overrides are cosmetic; session restore is the product. Loading defaults and continuing is strictly better than aborting — if a boot dependency's failure would cost more than living without its data, it must be non-fatal.

## Applies when

- Adding any task to `ensureHydrationBootstrap`'s `Promise.all`, a new restore phase to `hydrateAppState`, or any await ahead of the restore phases in `src/utils/stateHydration/index.ts`.
- Diagnosing "app starts to an empty workspace — no panels, no worktree, no recipes — but nothing crashed": grep the renderer log for `Failed to restore app state`; the real cause is whichever hydrate-path await rejected before the phases ran.
- Touching `KeybindingService.loadOverrides()` / `applyOverrides()` or the `app:boot` ride-along seeding in `bootstrapGuard.ts` (#10390) — the self-catch on the IPC fallback and the clear-after-resolve ordering are load-bearing.
- Reviewing any `Promise.all` of boot/init tasks where members have visibly different error handling — the rethrowing member is the whole batch's failure mode.
- Writing a catch block that logs the caught value — interpolate via `formatErrorMessage`, never raw `String(error)`/template-literal coercion.
