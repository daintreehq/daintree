## Context

A "paint-first" startup order created the window and loaded the renderer URL before all IPC handlers were registered. Some services initialized late (e.g., workspace host over IPC), so a subset of handlers landed after the renderer's first frame.

## Problem

Cold start produced ~25 "No handler registered for 'channel'" errors as the renderer fired IPC calls before their handlers existed. Some were benign retries; others silently failed and left the UI in a partial state.

## Root cause

The renderer attaches listeners and dispatches IPC eagerly on mount. Any handler not yet registered via `ipcMain.handle()` at that moment produces an error. "Paint-first" optimistically assumed the renderer would lazily probe — but React 19 / Zustand initialization is aggressive and fires dozens of calls in the first tick.

## Lesson

Register every IPC handler synchronously (via `registerIpcHandlers` in `electron/ipc/handlers.ts`) before the renderer load fires (`opts.loadRenderer` in `electron/window/windowServices.ts`). If a handler depends on an async-initialized service, use a shared mutable `HandlerDependencies` object (`electron/ipc/types.ts` — `ptyClient`/`worktreeService` are optional and bound lazily) and have handlers read from it at call time — don't defer registration. Make any "already active" handler (e.g., `project:reopen` in `electron/ipc/handlers/projectCrud/switch.ts`) idempotent rather than throwing, since the renderer can legitimately re-invoke on hot reload.

The pattern:

1. Create sync-only services.
2. Register all handlers once (late-bound via the `HandlerDependencies` deps object).
3. Start the renderer load.
4. Fork/await the async hosts (pty host, workspace host) in parallel — handlers read the now-populated deps lazily once each host is ready.

Note: as of the early-renderer boot path (#8827/#8828), step 3 deliberately precedes step 4 — the renderer loads in parallel with PTY/workspace host init so first paint is no longer blocked on the host handshake. This inverts the original "await services, then load" ordering and is only safe because handlers are already registered (step 2) and read async services lazily through the deps object. The serial after-services-ready trigger survives only as a fallback for smoke tests and the `DAINTREE_E2E_DEFER_RENDERER_LOAD` opt-in.

## Applies when

Adding a new IPC handler whose backing service initializes asynchronously. Seeing "No handler registered" in the console during cold start or hot reload. Reordering main-process bootstrap for any reason.
