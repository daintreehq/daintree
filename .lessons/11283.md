## Context

Issue #11280 reported that double-clicking a `.dntr` plugin archive installed it immediately, with a post-install success toast as the user's first feedback — plugins run with full unsandboxed Node privileges, so this is a D2 destructive action per `docs/architecture/destructive-action-safeguards.md` and needed a pre-install confirm with a real content preview, not a filename and a count.

## Problem

The issue's own diagnosis pointed at one file, `electron/setup/openFileInstall.ts`, which handles the macOS `open-file` event and called `installPlugin` with no gate.

Patching only that file would have left Windows and Linux unguarded: their double-click path went through a fully separate implementation in `electron/lifecycle/appLifecycle.ts` — `installDntrPath`, its own `pendingDntrPaths` queue, and its own zip-magic pre-screen (`isValidDntrArchive`) — that shared no call site, no file, and no import with `openFileInstall.ts`. Only reading the diff (not just the issue text) surfaced this: the two implementations existed because macOS delivers file associations via the app's native `open-file` event, while Windows/Linux have no such event for an already-running instance, so Daintree's single-instance lock forwards the second launch's argv and `extractDntrPaths` scans it instead — two different Electron mechanisms solving the same OS-integration need, wired up independently at different times.

## Root cause

The two ingress paths diverged because nothing forced them to share code: `open-file` fires as an Electron app-level event handled in `electron/setup/`, while the second-instance argv path is handled inside `electron/lifecycle/appLifecycle.ts`'s `registerAppLifecycleHandlers`. A developer fixing "the file-open handler" a bug report names has no structural cue that a second, platform-specific consumer of the same OS action exists elsewhere in the tree — it isn't a shared function, a shared queue, or a shared test file.

A second, independent defect surfaced building the fix: `electron/preload.cts`'s cross-context event bus buffers replayable events for renderers that haven't subscribed yet (`_eventBusReplayable`, `_eventBusBuffered`), using a `Map<name, payload>` that always overwrites. That's correct for a signal like `plugin:deep-link` where only the newest value matters, but wrong for a per-file decision queue — several `.dntr` archives arriving cold before the renderer's hook subscribes would silently collapse to the last archive, with no error and nothing to notice short of a multi-file cold-launch test.

## Lesson

- **Don't trust a bug report's file pointer as the fix's scope.** Grep for every consumer of the underlying action (`installPlugin`, the OS event name, the file extension) across the whole tree before considering a security gate complete — here the fix required touching `electron/lifecycle/appLifecycle.ts` as much as the file the issue named.
- **Know Daintree's two OS-file-ingress mechanisms and check both.** macOS: app `open-file` event (`electron/setup/openFileInstall.ts`, gated on `deepLinkInstall.ts`'s painted-primary tracking). Windows/Linux: second-instance argv scan (`extractDntrPaths`, `electron/lifecycle/appLifecycle.ts`). They are not the same code path and can silently diverge in behavior (one gated, one not) until someone audits both.
- **A replay/buffer mechanism built for one ambient signal breaks silently when reused for a decision queue.** `preload.cts`'s `_eventBusBuffered` defaults to latest-wins; this PR added a separate `_eventBusFifoReplay` set so `plugin:archive-install-intent` accumulates instead of overwriting. Before marking a new event replayable, ask whether a second event of the same kind before the first is consumed should be lost (ambient state) or preserved (a discrete decision) — get this wrong and events vanish with no crash, no log, and no CI signal.
- **Consolidate duplicate per-platform implementations instead of patching both in parallel.** The fix replaced `installDntrPath` + `pendingDntrPaths` (in `appLifecycle.ts`) and the old gate in `openFileInstall.ts` with one shared module, `electron/setup/archiveInstallIntent.ts`, that both ingress paths call into — removing ~300 duplicated lines and making a future third platform-specific path structurally have to plug into the same queue.
- **Manifest/archive preview text is attacker-controlled and needs Unicode sanitizing, not just escaping.** `archiveInstallIntent.ts`'s `UNSAFE_DISPLAY_CHARS` strips bidi overrides and zero-widths (e.g. U+202E) before display — React's text-node escaping blocks markup injection but not a manifest visually reordering the dialog's own trusted copy.

## Applies when

- Touching any Electron OS-integration ingress (file associations, protocol/deep-link handlers, second-instance argv forwarding) — check both the native app-event path and the second-instance/argv-scan path; they are different mechanisms for different platforms and are not guaranteed to be kept in sync.
- Fixing a bug report that names one specific file for an OS-level trigger (file open, protocol handler, drag-drop) — assume a duplicate platform-specific implementation exists until a repo-wide grep proves otherwise.
- Wiring a new event onto `preload.cts`'s `_eventBusReplayable` / `_eventBusBuffered` mechanism — decide whether it's a single ambient signal (latest-wins, current default) or a queue of discrete per-item decisions (needs `_eventBusFifoReplay`, like `plugin:archive-install-intent`).
- Building a pre-install/pre-execute confirmation dialog that renders attacker-supplied strings (plugin manifest, MCP tool args, forge webhook payload) — check whether Unicode bidi/format-control stripping is needed before display.
- Auditing D1/D2 coverage against `docs/architecture/destructive-action-safeguards.md` — verify against the current dispatch code, since the doc update is commonly deferred as a separate follow-up.
