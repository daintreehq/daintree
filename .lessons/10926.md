## Context

PR #10716 (resolving issue #10715) added an inline `BlockingOpRow` (Continue/Abort buttons) to the worktree card for a real but rare case: Daintree itself starts a rebase/merge/revert/cherry-pick and leaves it stuck, with `.git/REVERT_HEAD` (or equivalent sentinel) on disk and no in-app way to resolve it. The row rendered off `worktree.repoState`, gated Continue on `worktreeChanges` showing no `conflicted` entries, and wired straight to the existing `window.electron.git.abortRepositoryOperation` / `continueRepositoryOperation` IPC.

## Problem

The buttons looked clickable and authoritative but mostly didn't work. #10921 reported that in the common case — a coding agent running the rebase/merge itself, in its own PTY — Continue either did nothing useful or collided with the agent's still-running git process, and the conflict/status data it gated on was stale.

## Root cause

In Daintree almost every rebase/merge/revert is driven by an agent inside its own terminal, not by the user. Two independent facts made the card-level buttons unsound for that majority case, not just unhelpful: (1) firing `git rebase --continue` / `--abort` from the main process via IPC starts a second git process against the same working tree while the agent's own git process may still be running in its PTY — a straight collision on the repo, not a UX nicety issue; (2) `WorktreeMonitor.updateGitStatus()` deliberately skips the git-status check while any blocking op is in progress (to avoid contending for `.git/index.lock`), so the `worktreeChanges`/conflict data the Continue-disabled-state depended on was frozen at the pre-op snapshot — the button's own gating logic could be looking at stale reality. Either the button fires into a live collision, or it evaluates a decision (has conflicts cleared?) against data that was never refreshed while the op it's judging is happening. The fix removed `BlockingOpRow` entirely from `WorktreeHeader.tsx`/`WorktreeCard.tsx`, keeping only the passive `gitStateIndicator` badge (still built in `useWorktreeStatus.ts`) so the state stays visible without being actionable. The IPC handlers (`abortRepositoryOperation`, `continueRepositoryOperation`) were left intact because `ConflictPanel.tsx` (`src/components/Worktree/ReviewHub/`) is a separate, coherent manual-resolution surface — the Review Hub is where the user deliberately steps in, as opposed to the worktree card which is a passive-glance surface the user is not necessarily about to take over from an agent.

## Lesson

- **Before adding an interactive control that fires a git/process mutation from a passive-glance surface (a dashboard card, a status row), ask who else might already be running that same operation.** If the answer is "a coding agent, in its own PTY, most of the time," a second process from the UI is a race, not a convenience — verify by checking whether status polling for that state is itself suppressed during the operation (grep the monitor for an early-return keyed on the same `repoState`/sentinel the button reads).
- **A surface that intentionally freezes polling during an operation (here, to protect `.git/index.lock`) cannot also host a control whose enabled/disabled state depends on that same polled data.** The frozen data and the interactive gate on it are in direct tension — if a button's `disabled` prop reads a field the monitor stops updating during the exact state the button targets, the button is judging the past, not the present.
- **When two surfaces both wire the same IPC action, check whether they actually share a component before assuming a fix or removal must touch both.** #10921 assumed the worktree card and the Review Hub's `ConflictPanel` shared `BlockingOpRow`; they didn't — `ConflictPanel` is deliberately separate and was correctly left untouched. Read the actual import graph, not just "same underlying git-write.ts handler."
- **Solve the rare-and-real case (#10715's stuck-sentinel-with-no-recovery-path) at the surface built for deliberate takeover, not at every surface that happens to render the state.** The Review Hub's `ConflictPanel` already existed as that surface; adding a second, weaker recovery affordance on the dashboard card duplicated intent without duplicating the safety of the frozen-status problem.
- **A passive indicator (badge/label) is a legitimate final state for an in-progress-but-not-actionable-from-here status** — don't treat "the user should be able to see this" as automatically implying "the user should be able to act on this from here."

## Applies when

- Adding any button/action to `WorktreeCard.tsx` or `WorktreeHeader.tsx` that fires a git mutation (`window.electron.git.*`) based on worktree/repo state.
- Touching `WorktreeMonitor.updateGitStatus()` or any status-polling path that skips/freezes updates during a blocking git operation — check what UI reads the frozen field before assuming a `forceRefresh` will unstick it.
- Designing a recovery affordance for a stuck git state (rebase/merge/revert/cherry-pick sentinel left on disk) — default to the Review Hub / `ConflictPanel`-style deliberate-takeover surface, not a dashboard card.
- Reviewing any UI element on a surface agents also drive (worktree card, terminal chrome) that would fire a second process into state an agent might already own.
- Assuming "the same IPC handler is used elsewhere" means "the same component is shared elsewhere" — verify the actual render tree before scoping a fix to touch both.
