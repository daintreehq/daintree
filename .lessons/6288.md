## Context

The GitHub Issues/PRs toolbar dropdowns (host chrome is now forge-neutral, `ForgeStatsToolbarButton`; the dropdown body is supplied by the GitHub plugin, `GitHubStatsDropdown.tsx`) were code-split via `React.lazy` and only rendered their first page on click. A 30s poll already fetched `totalCount` for the badge. Making click-to-data feel instant from cold start, on every click, and on every reopen required four layered changes, not a cache TTL bump.

## Problem

Even when data and the JS chunk were already available, opening a dropdown flashed a skeleton for one render. Cold start showed a skeleton until the first poll landed. And once the body was kept mounted across open/close to preserve scroll/filter state, every reopen risked clearing the visible rows and re-flashing a skeleton.

## Root cause

Four distinct mechanisms, each non-obvious:

- **`React.lazy` suspends on the first render of its boundary regardless of whether the import promise has already resolved.** A preloaded/cached chunk still triggers the Suspense fallback for one render. Fix: eagerly resolve the concrete component reference into state on mount (`importResourceList().then(m => setResourceList(() => m.GitHubResourceList))`) and render `<ResourceList>` directly, keeping the `lazy()`+`Suspense` only as the cold-click fallback (`GitHubStatsDropdown.tsx:61-77,116-121`). The toolbar button itself was later split forge-neutral (`ForgeStatsToolbarButton.tsx` now just hosts the pills/badge/shell); this eager-resolve technique moved one layer down into the GitHub plugin's dropdown body and was generalized to cover both the issue/PR list and the commit list.
- **Click-time latency was never the network fetch — it was an empty renderer cache on first mount.** The 30s stats GraphQL query (`REPO_STATS_AND_PAGE_QUERY`) was extended to also fetch the first page of open issues/PRs in one round-trip, broadcast over the (now forge-neutral) `forge:repo-stats-and-page-updated` IPC channel, and the renderer primes `forgeResourceCache` (renamed from `githubResourceCache`, `src/lib/forgeResourceCache.ts`) under the default `(open, created)` cache key. The dropdown then opens against hot cache.
- **Cold start has no broadcast yet,** so the first page is persisted to `userData/github-first-page-cache.json` (`GitHubFirstPageCache`, 10-min freshness, MAX 10 LRU — `GitHubFirstPageCache.ts:72-73`) and `useRepositoryStats` hydrates the renderer cache on mount via `forgeClient.getFirstPageCache`. Because the async disk read can resolve _after_ the live broadcast push, hydration carries a **stale-overwrite guard**: `setCache` only writes if `!existing || existing.timestamp < cached.lastUpdated` (`useRepositoryStats.ts:830,841`).
- **Under React 19.2 `<Activity>` (the `keepMounted` path in `fixed-dropdown.tsx`), effects unmount+remount on each hide/reveal but component state and refs are preserved.** That means the load effect cannot use `mountedRef` to tell an Activity reveal apart from a filter/sort/search change — both look like "effect re-fired while state survives." The fix is `lastLoadedEffectKeyRef` holding `` `${cacheKey}|${debouncedSearch}` `` (search is NOT part of `cacheKey`): a reveal with an unchanged key takes the silent SWR revalidate path (no clear, no skeleton); a changed key takes the real-remount path that clears rows and shows the skeleton (`useGitHubResourceListSWR.ts:186,512-517`).

## Lesson

- Preloading a `React.lazy` chunk does NOT prevent the Suspense fallback flash. If you need a zero-flash render of a cached lazy component, resolve the module to a concrete component reference in state and render it directly; keep `lazy`+`Suspense` only as the not-yet-loaded fallback.
- When you wrap a body in `<Activity>` to preserve state across hide/reveal (`keepMounted`), do not rely on a `mountedRef`/first-mount flag to detect input changes — effects re-fire on every reveal while state survives. Track the actual input tuple in a ref and compare it; include inputs (like a debounced search string) that aren't part of your cache key, or a reveal of a different search will be misread as a same-key reveal.
- The latency a user calls "slow" on first click is usually the empty cache, not the fetch. Fold the first page into an existing background poll and persist it to disk for cold start, rather than bumping a TTL.
- Any disk-hydration-on-mount that races a live push must carry a timestamp-based stale-overwrite guard, since the async disk read can land after the fresher broadcast.
- Don't broadcast cache-extended data: only push when the backend actually hit the network (`source === "network"`), or the renderer's `TtlCache.set()` resets expiry from write time and masks staleness.

## Applies when

- Adding/optimizing any code-split panel, dropdown, popover, or palette body that uses `React.lazy` + `Suspense` and flashes a skeleton even when the chunk is cached.
- Using React 19.2 `<Activity>` / `keepMounted` to preserve state across hide/reveal anywhere (FixedDropdown, tooltip, tabbed panels) and seeing rows clear, skeletons flash, or revalidates not fire on reopen.
- Working in `ForgeStatsToolbarButton`, `GitHubStatsDropdown`, `fixed-dropdown.tsx`, `useGitHubResourceListSWR`, `useRepositoryStats`, `GitHubFirstPageCache`, `getRepoStatsAndPage` (`GitHubStats.ts`), or `forgeResourceCache`.
- Making a "make X instant on click" performance change where the real cost is an empty/cold cache, and you're tempted to just raise a cache TTL.
- Designing disk-persistence-plus-live-push hydration where an async read can race a synchronous broadcast and downgrade fresher data.
