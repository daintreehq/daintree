## Context

The toolbar open-issue/PR count badge has two independent sources per count: the background stats poll (`useRepositoryStats` → `getRepoStatsAndPage` in `plugins/builtin/github/main/GitHubStats.ts`, gated behind a `/events` ETag activity probe) and the dropdown's own list fetch (`onCountUpdate` from `useGitHubResourceListSWR`). These counts are how a merge run gets watched, so they must stay fresh without user interaction. Everything was later renamed forge-neutral for the GitLab plugin — `GitHubStatsToolbarButton.tsx` → `ForgeStatsToolbarButton.tsx`, `resolveGitHubDisplayCount` → `resolveForgeDisplayCount` in `forgeStatsCountDisplay.ts`, stats types in `shared/types/forge.ts` — mechanisms unchanged.

## Problem

A four-stage chain, each fix self-defeating in turn. Originally the badge read the server-total stats query while the dropdown loaded 20 items — badge higher than the visible list (#9693). #9694 bound the badge to the list, capping it at `20+` forever (#9717). #9718 plumbed the GraphQL `totalCount` through, after which the list count won unconditionally — the badge froze until the dropdown was reopened, even as fresher polls landed (#9741, fixed here). Then #9742's own arbitration produced the worst symptom (#10348): open the dropdown, see the real count, and seconds later the badge rolls back to a stale one — oscillating on every background poll.

## Root cause

Two layered mechanisms. First, ownership: with two writers for one number, both "last writer wins" (the original mismatch) and "source X always wins" (#9694/#9718's freeze) are unstable; the stable design is recency arbitration — `resolveForgeDisplayCount` shows whichever source has the newer epoch-ms timestamp, `>=` (not `>`) so the higher-fidelity list count survives a same-millisecond tie, and `statsLastUpdated == null` (no baseline yet) letting a present list count through.

Second, and deeper (#10348): the arbitration initially compared against `RepositoryStats.lastUpdated` — a serve timestamp, not an observation timestamp. When the `/events` probe reports no change, `getRepoStatsAndPage` re-serves cached counts from `repoStatsAndPageSnapshotCache` (10 min TTL) or `restCountsCache` (1 h TTL) re-stamped `lastUpdated: Date.now()` — so a stale cached count looked fresher than the dropdown's genuine observation on every poll and won. Meanwhile the dropdown's correction was only written to the 60s-TTL `repoStatsCache`, so the longer-lived caches kept resurrecting the stale value, and the permanently-fresh `lastUpdated` also suppressed the dropdown-open force refresh (`OPEN_REFRESH_STALENESS_MS`) that would have healed it. The fix added honest per-count stamps `issueCountRefreshedAt` / `prCountRefreshedAt` that only advance when GitHub is actually asked about that count (probe re-serves preserve them; per-count because a PR write-back says nothing about issue recency), made `updateRepoStatsCount` drop disagreeing snapshot/REST baselines and bump the ETag cache version so an in-flight conditional fetch can't 304-recommit the stale value, and mapped stale disk fallbacks to null recency so a direct observation always outranks them.

## Lesson

- **When one displayed number has two data sources, arbitrate by per-source recency timestamps — every fixed-priority rule fails in turn.** The visible chain: stats-always (mismatch #9693) → list-always (`20+` cap #9717, then freeze #9741) → `resolveForgeDisplayCount` recency arbitration, which is the design that stuck.
- **A recency stamp must record when the value was observed at the source of truth, never when it was last served.** `lastUpdated` is re-stamped on every activity-probe cache re-serve, so arbitrating on it inverted the intent — stale beat fresh on every poll (#10348's oscillation). If a timestamp participates in a freshness comparison, trace every path that writes it and confirm none re-stamp without re-reading.
- **A correction observed out-of-band must be written into, or invalidate, every cache tier that can resurrect the stale value — including in-flight requests.** The dropdown's real total died in the 60s `repoStatsCache` while the 10-min snapshot and 1-h REST caches kept re-serving the old count; `updateRepoStatsCount` now drops disagreeing entries AND bumps the ETag cache version because an already-in-flight conditional fetch would otherwise 304-recommit the value just invalidated.
- **Reset arbitration state on scope switch with a dedicated scope-keyed effect, never by piggybacking on a guarded loading-state effect.** The `[currentProject?.path]` effect in `ForgeStatsToolbarButton.tsx` clears list counts and timestamp refs because the `lastUpdated == null` reset path sits behind a `statsLoading` guard a fast project switch trips in the same batch — leaving project A's timestamp suppressing project B's first poll.
- **Derive visible-poll cadence from the existing ETag activity probe rather than a second heuristic.** `nextPollIntervalMs` surfaces `eventsProbeDelayMs` (60s floor, growing to a 5-min ceiling on consecutive 304s, snapping back on change), renderer-clamped to [30s, 5min]. Later design work (#11151) layers git-signal-driven refresh on top; it does not replace this.

## Applies when

- Touching `ForgeStatsToolbarButton.tsx`, `forgeStatsCountDisplay.ts`, the `GitHubStats.ts` poll/cache paths, or building the stats surface of a new forge provider (the GitLab plugin mirrors this contract).
- Displaying any value fed by both a background poll and an on-demand fetch — counts, CI status, review states — and deciding which source "owns" the display.
- Diagnosing an indicator that freezes until user interaction, or oscillates back to a stale value after each background refresh — freeze means fixed priority, oscillation means a re-stamped timestamp is winning arbitration.
- Adding a cache or ETag/304 short-circuit in front of a value used in recency comparisons — on `RepositoryStats`, `lastUpdated` means "last served"; `issueCountRefreshedAt`/`prCountRefreshedAt` mean "last actually read from the forge".
- Writing a client-side correction into a multi-TTL cache hierarchy and assuming the shortest-lived tier is enough — the longer tiers resurrect the old value once it expires.
