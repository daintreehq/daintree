## Context

The diff panel (`DiffPane` + `DiffViewer.tsx`) renders four kinds of diff via `DiffPanelData["diffSource"]`: `working-tree`, `unstaged`, `staged`, `base-branch`. Issue #11263 asked for a "Full file" scope that expands every hunk gap using `DiffViewer`'s dormant `source` prop, documented as "Full new-side file content for single-file working-tree diffs" but never wired up because `DiffPane` never passed it — the expand-hidden-lines control existed and was inert. PR #11268 wires it up by reading the new-side file over `filesClient.read` (`useDiffFileSource.ts`) and gating availability per file in `fullFileAvailability.ts`.

## Problem

The issue's own "Constraints" section asserted "Working-tree, staged and unstaged diffs have their new side on disk" and told the implementer `filesClient.read` already reaches it for all three. If built as specified, selecting "Full file" on a staged diff would read the working-tree file from disk and silently render it as the diff's context — including whenever the file had been edited again after `git add`, which is a completely ordinary workflow (stage, keep typing).

## Root cause

A staged diff's new side is the index blob (`git cat-file blob :<path>`), a distinct git object frozen at stage time — not the working-tree file. The moment the file is edited again after staging, disk and index diverge, and nothing in the app invalidates the staged diff to reflect that. `files:read` only ever reaches disk, and Daintree has no ref/blob-read IPC capability anywhere in the codebase, so implementing the issue literally meant either threading git blob OIDs through IPC (real scope, not attempted here) or silently showing the wrong revision as if it were verified context — exactly what the issue text elsewhere explicitly forbids for base-branch diffs. The PR resolves this with two layered defenses rather than one: `fullFileAvailability.ts`'s `DISK_BACKED_SOURCES` set includes only `working-tree` and `unstaged`, disabling the toolbar control for `staged`/`base-branch` with a stated reason string. But a caller correctly marking a source as disk-backed still isn't sufficient — the file can drift between the diff snapshot and the read even for working-tree diffs (a live watched worktree), so `DiffViewer.tsx`'s `sourceMatchesHunks` re-derives trust at render time: every hunk already carries its own new-side lines, so it checks that those exact lines appear verbatim at `newStart` in the fetched source before treating any of it as safe context. A mismatch reports `source-mismatch` and falls back to changed-lines-only rendering — never a believable-looking wrong-revision render.

## Lesson

- **Don't infer "this diff's new side is on disk" from the diff kind alone** — staged = index blob, base-branch = another ref's blob, only working-tree/unstaged actually mirror the file on disk. Reason from git's object model (`git cat-file`), not from a plausible-sounding constraint someone wrote down.
- **When pairing a live content read with a previously-computed diff/snapshot, verify the fetched content against the snapshot's own data before trusting it** — don't rely on a caller's or type's "this is safe" guarantee alone, because the guarantee can be true when written and false by the time the read resolves. Concrete mechanism to copy: `sourceMatchesHunks` requires each hunk's new-side lines to appear verbatim at `newStart`; on mismatch, degrade to a narrower but definitely-correct view (changed-lines-only) rather than rendering.
- **Scope a feature to the mechanically sound cases now rather than faking the unsound ones** — staged and base-branch full-file view were left as an explicit follow-up needing a real ref/blob read, instead of shipping a disk read gated by a "trust me" flag that would misrender on a common workflow.
- **Issue write-ups are not ground truth on git semantics** — this issue's own Constraints section stated the wrong thing about staged content, and the fix required correcting it in the PR's design-decisions section, not just implementing it as written. Re-verify any issue's git-internals claims (staged vs. working tree, ref reachability) against actual git behavior before building on them.
- **Check for dormant machinery before adding new logic** — `DiffViewer`'s `source` prop and "expand hidden lines" control already existed with the right contract; the fix was wiring `DiffPane` to pass it, not inventing new expansion code.

## Applies when

- Adding a feature that reads live file or blob content to pair with a git diff (`DiffPane`, `CrossWorktreeDiff.tsx` — which per the PR also omits the `source` prop and is a known follow-up, or any new diff surface) — check `diffSource`/ref before assuming `filesClient.read` reaches the right content.
- Touching `src/panels/diff/fullFileAvailability.ts` (`DISK_BACKED_SOURCES`, `EXPANDABLE_STATUSES`), `useDiffFileSource.ts`, or `DiffViewer.tsx`'s `sourceMatchesHunks`/`buildSyntheticOldSource` path.
- Reviewing any feature that fetches "the current version" of something to overlay or expand around a diff, snapshot, or historical view — check whether the fetched source could have drifted from what was actually diffed.
- An issue or spec asserts a git-semantics claim ("X is reachable via Y read") — verify it against git's actual object model before implementing, especially staged/index vs. working-tree distinctions.
- Extending full-file view to staged or base-branch diffs — the correct fix is a ref/blob read (`git cat-file blob <ref>:<path>`), not a disk read with an availability gate removed.
