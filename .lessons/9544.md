## Context

`TerminalProcess` (`electron/services/pty/TerminalProcess.ts`) owns a live, non-pooled node-pty process. Its private `teardown(reason)` is the single chokepoint reached by all three end-of-life paths: explicit `kill()`, natural `onExit`, and `dispose()`. Separately, `PtyPool` manages prewarmed pooled shells and tears them down via a shared `destroyPty()` helper (`electron/services/PtyPool.ts:99`).

## Problem

Every live terminal close — user kill, agent exit, or panel dispose — leaked one master `/dev/ptmx` file descriptor. Under churn (e.g. a crash-loop, #7892) the leak multiplied by ~60 fds/iter until the system-wide `ptmx_max` (≈511 on macOS) was exhausted, at which point no new terminal could spawn. The pooled paths were leak-free; only the live path leaked.

## Root cause

node-pty's `kill()` only sends a signal to the child process — on Unix the master `/dev/ptmx` fd stays open until `destroy()` is explicitly called (the native binding retains a reference until GC, which is non-deterministic). `teardown()` aborted the process-tree killer and disposed the data listener but never called `destroy()`, so the master fd was orphaned. Two things make this easy to miss: (1) `destroy()` is **not on the exported `IPty` TypeScript type** — it exists only on the concrete `UnixTerminal`/`WindowsTerminal`, so it must be accessed structurally; code reading the typed surface sees no destroy method and assumes `kill()` is sufficient. (2) `PtyPool` already had the discipline via `destroyPty()`, creating a live-vs-pool asymmetry where the obviously-correct-looking live teardown silently leaked.

## Lesson

- node-pty `kill()` is NOT cleanup. To release the master fd you must call `destroy()` (via the shared `destroyPty()` in `PtyPool.ts`, which calls `destroy()` then `kill()`, both in try/catch). Treat any PTY teardown that calls only `kill()` as an fd leak.
- `destroy()` is absent from the `IPty` type — cast structurally (`p as IPty & { destroy?: () => void }`) and fall back to `kill()` when missing (test mocks). Don't trust the typed surface to tell you cleanup exists.
- Funnel all PTY end-of-life paths (kill / natural exit / dispose) through one teardown method and put `destroyPty()` there, guarded by the lifecycle state machine (`lifecycle.transition` returns false on re-entry) so it fires exactly once regardless of signal order. Per-path cleanup invites exactly this kind of one-path-missed-it asymmetry.
- When one class (pool) has resource-release discipline a sibling class (live) lacks, that asymmetry is a leak smell — audit both.

## Applies when

- Adding or refactoring any PTY teardown, kill, exit, or dispose path in `electron/services/pty/` or `electron/services/PtyPool.ts`.
- Investigating fd / `/dev/ptmx` exhaustion, "too many open files", `ptmx_max` errors, or FdMonitor warnings (the detector side is #3710) on macOS/Linux.
- Writing new node-pty lifecycle code and reaching for `kill()` as the cleanup call.
- Reviewing code that operates on the `IPty` type and assumes the typed surface lists every available method.
- Spawning PTYs through a second pathway (background, headless, plugin, recipe) that bypasses the existing `TerminalProcess.teardown()` chokepoint — that new path needs its own `destroyPty()`.
