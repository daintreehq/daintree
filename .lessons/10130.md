## Context

The unit suite in `.github/workflows/ci.yml` is sharded across parallel runners via vitest's native `--shard=i/N` (introduced `76928a69e`, 2026-05-31). The shard count lived as independent literals: the matrix list `shard: [1, 2, 3, 4]` plus a bare `/4` in both the step name and the `--shard` run argument, with only an inline comment telling maintainers to update both by hand. `ci-ok` is the sole required branch-protection check, so nothing downstream validates that every partition actually ran. #10130 (from #10006) centralized the denominator into a job-level `SHARD_TOTAL: 4` env var referenced by both literals.

## Problem

The failure mode is asymmetric, and the dangerous direction is silent. Shrink the matrix to `[1, 2, 3]` while `/4` stays: vitest partition `4/4` is simply never scheduled, roughly a quarter of test files never execute, every scheduled shard passes, `ci-ok` goes green, and any regression living in the missing partition ships unobserved. Grow the list to `[1..5]` against `/4` instead and shard `5/4` fails loudly — so only the coverage-losing direction gives no signal. There is no error, no warning, no count mismatch surfaced anywhere; the only evidence is test files that no runner ever mentions.

## Root cause

GitHub Actions has no native way to bind a matrix dimension's length to a step argument, and both "obvious" single-sourcing mechanisms are wrong in non-obvious ways. (1) You cannot parameterize `strategy.matrix` from `env` — the `env` context is not available at `strategy.matrix` evaluation time (it is job-scoped, defined in the very job being expanded), while `inputs`/`github`/`needs` contexts ARE available there (the same job's `os` dimension was already computed via `fromJSON(inputs.os ...)`). So the matrix list must stay a literal, and the env var can only flow the other way, into step-level strings. (2) `strategy.job-total` was rejected as the denominator because it is the Cartesian product across ALL matrix dimensions, not one dimension's length — with the then-present `os` dimension, `os=both` dispatch made it 8, which would mis-shard every runner. #10130's fix: `SHARD_TOTAL: 4` as job-level env, both `/4` literals replaced with `/${{ env.SHARD_TOTAL }}`, matrix list kept literal with a comment binding it (`[1, 2, ..., SHARD_TOTAL]`). This also flips the residual failure mode loud: a missing/mistyped env yields `--shard=2/`, a vitest parse error, instead of a valid-but-wrong partition.

The afterlife is the second half of the lesson. The fix survived 45 minutes: same-day direct commit `34d18a74e` merged the sharded `test` job into `check` (unsharded), deleting `SHARD_TOTAL` with it. When PR #10758 re-sharded the suite on 2026-06-24 (4 shards, threads pool, Vite transform cache), it reintroduced the hardcoded `/4` in both places with no env var and no maintenance warning in the comment. As of 2026-07-22, develop's `ci.yml` carries the exact trap #10130 removed: `shard: [1, 2, 3, 4]` (~line 85) against literal `/4` in the step name and `npx vitest run --shard=${{ matrix.shard }}/4` (~lines 119-120). `strategy.job-total` would coincidentally work today (shard is now the only matrix dimension) but silently corrupts the moment anyone re-adds an `os` or node-version dimension.

## Lesson

- **Vitest `--shard=i/N` mis-sharding is silent only in the coverage-losing direction.** Denominator larger than the scheduled index list = unscheduled partitions that never run and never fail; denominator smaller = loud invalid-shard error. Any edit to a shard count must verify list length == denominator in both places, because CI gives zero signal for the dangerous case.
- **`env` context is unavailable at `strategy.matrix` evaluation; `inputs`/`github`/`needs` are.** You cannot drive the matrix list from a job-level env var — single-source the count either as job-level env referenced by all step-level literals (list stays literal, #10130's shape), or compute it in a prior job and emit the whole matrix as JSON via outputs + `needs` + `fromJSON` — `e2e.yml`'s `matrix-setup` job is the in-repo canonical, deriving per-entry `shard` and `shardTotal` fields from one shell variable so index and denominator cannot diverge.
- **Never use `strategy.job-total` as a shard denominator.** It is the Cartesian product across all matrix dimensions (8 for os×shard on `os=both`), equal to the shard count only while shard is the sole dimension — adding any dimension silently rewrites every runner's denominator.
- **Prefer the wiring whose residual failure parses wrong loudly.** `/${{ env.SHARD_TOTAL }}` with a missing env produces `--shard=2/` → vitest parse error; a stale literal produces a valid-but-wrong partition → silent skip. When choosing between two single-sourcing mechanisms, pick the one whose breakage is a crash, not a quiet subset.
- **This fix no longer exists in the codebase — re-apply it when touching the shard count.** `34d18a74e` deleted the sharded job (and `SHARD_TOTAL`) 45 minutes after #10130 merged; #10758 re-sharded with hardcoded `/4`. Guard mechanisms living inside a workflow job die with the job on rewrites: when restructuring or re-adding a CI job, diff the deleted version for env single-sourcing and maintenance comments that must survive.

## Applies when

- Changing the unit-test shard count or matrix in `.github/workflows/ci.yml` — the trap is currently live (literal `/4` in the step name and `npx vitest run --shard=` line, decoupled from `shard: [1, 2, 3, 4]`).
- Adding a matrix dimension (`os`, node version) to any sharded job, or tempted to use `strategy.job-total` as a shard denominator.
- Tempted to parameterize `strategy.matrix` from `env` — it never evaluates there; use `inputs` in `fromJSON`, or the `e2e.yml` `matrix-setup` outputs + `fromJSON` pattern for computed counts.
- Reviewing any CI change that shrinks or grows a shard list — confirm every partition `1..N` is actually scheduled; a green `ci-ok` proves nothing about missing partitions.
- Restructuring, merging, or re-adding CI jobs — check the deleted job's diff for guard mechanisms (env single-sourcing, coupling comments) that the rewrite silently drops, as happened to this very fix.
