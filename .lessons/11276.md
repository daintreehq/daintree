## Context

#11276 added a third "Diff" option to the file viewer panel (`FilePane.tsx`) alongside the existing Source/Rendered toggle, so a file an agent just changed can be diffed without leaving the viewer (issue #11274). To know whether a file has a Diff option, `FilePane` has to answer two questions that sound trivial but aren't: does this file have local changes, and which worktree's changes should it be checked against.

## Problem

Both questions have an obvious-looking wrong answer. The obvious way to check "does this file have local changes" is to look up `filePath` in the worktree's `WorktreeChanges.changes` list keyed by `FileChangeDetail.path`, which the type declares as "Relative path to the file from worktree root". The obvious way to know "which worktree is this file in" is the panel's own `panel.worktreeId` field, already carried by every panel for exactly this purpose. Both are wrong, and neither failure is loud — a lookup that silently never matches, or a diff fetched against the wrong worktree, looks like "no changes" or "wrong file", not a crash.

## Root cause

`electron/utils/git.ts`'s `addChange` (around line 846-870) builds `changesMap` keyed by `absolutePath` and writes `path: absolutePath` into every `FileChangeDetail` it emits — the JSDoc on the type (`shared/types/git.ts:34`) says relative, the runtime value is always absolute. There is no code path that ever produces a relative `path` today; the type has simply never matched the producer. Any consumer that trusts the type and does a plain string-equality or naive relative-join against `change.path` silently fails for every file, because absolute strings never equal the relative paths it expects.

Separately, `file.openPanel` (`src/services/actions/definitions/fileActions.ts`) resolves an explicit `rootPath` argument to compute `absolutePath` via `resolveFilePanelPath`, but then unconditionally stamps the new panel with `worktreeId: callbacks.getActiveWorktreeId()` — the currently _focused_ worktree, not the worktree the resolved path actually sits in. An agent or MCP caller can pass a `path`/`rootPath` pointing at a different worktree (or a nested one) than whatever the user currently has focused, and the panel ends up carrying a `worktreeId` that names the wrong worktree, or none at all when the file isn't under the active worktree. `panel.worktreeId` is a stamp from panel-creation time, not a live fact about the file's location.

The fix for both is to never trust the denormalized/typed value and instead derive ground truth at read time: `toWorktreeRelative` (new export in `shared/utils/path.ts`, built on `isPathInside`) folds both an absolute and a relative `change.path` to the same relative form before comparing. `FilePane` resolves "which worktree is this file in" itself, scanning `useWorktreeStore`'s worktrees for `isPathInside(filePath, worktree.path)` and keeping the longest (deepest) matching root, ignoring `panel.worktreeId` entirely. `isPathInside`, not a raw `startsWith`, is what makes that safe: a naive prefix check would treat `/repo-other/x.ts` as inside `/repo`, mangling it into a bogus relative path `-other/x.ts`.

## Lesson

- **A field's doc comment is a claim, not a guarantee — check the producer, not the type.** `FileChangeDetail.path` says "relative"; the only producer (`electron/utils/git.ts`) has always written absolute. Before writing a lookup/comparison against any cross-process shared type, grep the field back to where it's actually constructed.
- **A denormalized ID stamped at creation time (`panel.worktreeId`) is a cache, not a source of truth — re-derive it from a live fact when correctness matters.** `file.openPanel` stamps the _active_ worktree even when the resolved path belongs to a different one; anything that needs a file's real worktree must resolve by path containment (`isPathInside`) against the live worktree set, not read the stamped field.
- **When two consumers of the same fact disagree on shape (relative vs. absolute path), normalize at the comparison site with a shape-tolerant helper, don't pick one shape and hope.** `toWorktreeRelative` folds both shapes before comparing; it already existed as a private helper in `fileActions.ts` and was promoted to shared `shared/utils/path.ts` for this second caller — check for an existing near-identical helper before writing a new one.
- **Prefer `isPathInside` over `startsWith` for any path-containment check.** A sibling directory whose name merely extends the root as a string (`/repo-other` vs `/repo`) is not contained in it; `startsWith` says yes, `isPathInside` says no — covered by dedicated tests in `shared/utils/__tests__/path.test.ts`.
- **When multiple roots could contain a path (nested worktrees), the deepest (longest) match wins.** A file under `/repo/nested/src/index.ts` resolves against `/repo/nested`, not `/repo`, because the parent's change list won't list the file at all.
- **A runtime sanitizer filtering a union by literal equality (`sanitizeFileViewMode` in `src/config/panelKindSerialisers.ts`) must gain the new literal whenever the type gains one** — widening the type alone silently drops every persisted value of the new mode on deserialization, with no type error to catch it.

## Applies when

- Reading or comparing any field from `WorktreeChanges.changes` (`FileChangeDetail.path`) — confirm whether you need the absolute or relative form and normalize explicitly, don't trust the JSDoc.
- Touching `panel.worktreeId` on any panel type, or a code path (`file.openPanel`, similar `*.openPanel` actions) that stamps a panel's worktree at creation time — check whether the value can go stale relative to the panel's actual content.
- Writing a path-containment check anywhere in the renderer or Main process — use `isPathInside` / `toWorktreeRelative` from `shared/utils/path.ts`, never a raw `startsWith`.
- Adding a new literal to a persisted union type deserialized via `src/config/panelKindSerialisers.ts` — grep for the matching `sanitize*` function and add the literal there too.
- Diagnosing "this lookup never matches" or "the diff/action operates on the wrong worktree" — suspect an absolute/relative shape mismatch or a stale `worktreeId` stamp before assuming the data is simply missing.
