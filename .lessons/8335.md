## Context

`KeybindingService` registers `DEFAULT_KEYBINDINGS` (139 code-authored entries) and merges them with user overrides persisted via `window.electron.keybinding.getOverrides()`. Action IDs use the open-union pattern from #4489: `BuiltInActionId` (closed) widened to `ActionId = BuiltInActionId | (string & {})` so plugins can register arbitrary IDs.

## Problem

The open union (`ActionId`) was applied uniformly, so `KeybindingConfig.actionId` was just `string`. Two failures resulted: (1) typos in the code-authored defaults compiled silently and only surfaced at runtime; (2) `loadOverrides()` stored every persisted entry blindly, so users carrying overrides for actions since renamed or removed (e.g. `app.toggleSidebar` → `nav.toggleSidebar`, `terminal.newPanel` → `terminal.new`) accumulated dead bindings that pointed at nothing. The loose typing also forced an unsafe `as Parameters<typeof actionService.dispatch>[0]` cast at the dispatch site in `useGlobalKeybindings`.

## Root cause

Open-union (`BuiltIn... | (string & {})`) typing is correct for the _registration/plugin_ path but wrong for two other surfaces that get conflated with it:

- **Code-authored defaults** want the _narrow_ `BuiltInActionId` so a renamed action breaks the build. Using the open union there discards the only compile-time check that matters for in-repo data.
- **Persisted user data** is an untyped runtime boundary regardless of TS types — the open union accepts any string, so a stale ID from a previous app version type-checks and silently stores. Compile-time typing cannot police this; it needs a runtime filter against what is actually live.

The fix splits the type in two (`src/services/keybindingUtils.ts`): `KeybindingConfig.actionId: BuiltInActionId` for `DEFAULT_KEYBINDINGS`, and `RegisteredKeybindingConfig = Omit<KeybindingConfig,"actionId"> & { actionId: ActionId; when?; pluginId? }` for internal storage, `registerBinding`, return types, and the plugin path. `loadOverrides()` then warn-and-drops any persisted actionId that is neither in `builtInActionIdSet` (`BUILT_IN_ACTION_IDS ∪ KEY_ACTION_VALUES`) nor already in `this.bindings` (catches plugin bindings registered before override load). The narrow default type made the unsafe dispatch cast unnecessary.

## Lesson

- A single open-union action-ID type is not enough. Split by surface: **narrow `BuiltInActionId` for code-authored data** (defaults, in-repo tables) so renames/typos fail the build; **open `ActionId` for the registration path and any runtime store** so plugins still work.
- The open union makes persisted user data type-check unconditionally — that is _not_ validation. At every load boundary that reads persisted IDs, warn-and-drop entries not in the live set (built-ins ∪ key actions ∪ already-registered bindings). Check `this.bindings.has(id)` too, so plugin bindings registered before hydration survive.
- Reconciles with #4489: that lesson said "relax runtime validation to accept any string" — that applies to the _plugin registration_ guard, not to _persisted-data hydration_, which must still filter against live IDs.
- When you tighten an in-repo type from the open union to `BuiltInActionId`, audit downstream casts: loose typing that forced an `as Parameters<...>` cast (e.g. `useGlobalKeybindings` dispatch) usually becomes unnecessary and the cast should be deleted.
- Add a quality test asserting every code-authored default ID resolves in the registry (or is an allowlisted key-only action) — `actionDefinitions.quality.test.ts` does this for `DEFAULT_KEYBINDINGS`.

## Applies when

- Editing `KeybindingService`, `keybindingUtils.ts`, `defaultKeybindings.ts`, or anything reading `window.electron.keybinding.getOverrides()`.
- Renaming or removing a `BuiltInActionId` / `BuiltInKeyAction` and worrying about users' persisted overrides going stale.
- Designing any persisted/hydrated store keyed by an open-union ID type (`ActionId`, `PanelKind`, agent registry keys) — the type permits stale keys, so the load path needs an explicit live-set filter.
- Seeing `actionId as Parameters<typeof actionService.dispatch>[0]` or similar casts at a dispatch site — likely a symptom of loose `string` typing upstream that should be a narrow built-in union.
- Adding a new code-authored keybinding-like table and deciding whether to type it with the narrow or open union (use narrow for in-repo data).
