## Context

`AuditRingStore` (`electron/services/persistence/auditRingStore.ts`) is a single shared SQLite-backed ring buffer (`audit_rings` table) behind six different logs: `mcpAuditLog`, `mcpTurnOutcomeLog`, `pluginAuditLog`, `forgeAuditLog`, `runHistoryRecords`, `pluginMcpAuditLog`. Settings → Daintree Assistant → Privacy exposed an "Audit log retention" dropdown (7 days / 30 / Off) that persisted `helpAssistant.auditRetention` via the `helpAssistant.setSettings` IPC handler.

## Problem

Issue #10776: the retention dropdown did nothing. `auditRetention` was written and validated (`isValidAuditRetention`) on every settings save, and roundtrip tests for that write/validate path were all green — but grep across the repo showed the value was never read anywhere. The `mcpAuditLog` / `mcpTurnOutcomeLog` rings were trimmed by record count only (500 cap), never by age, so a user who picked "7 days" kept the full cross-session backlog forever. This is also why assistant diagnostics "felt massive" — the viewer showed count-capped history with a control that implied but never performed age-based trimming.

## Root cause

Two independent traps stacked. First, the settings field was added with a full validate/persist/roundtrip path but no consumer was ever wired at the same time — the passing tests only prove the round trip, not that anything acts on the value, so this class of bug is invisible to normal test coverage. Second, once pruning was implemented, the obvious column to filter on — `created_at` on `audit_rings` — turns out to be structurally useless for age. `AuditRingStore.writeAll` is a full-snapshot rewrite: its transaction does `clear.run(ring)` then re-`insert.run(ring, record, now)`s every surviving record with `now = Date.now()` at flush time (`writeAllSerialized`, `auditRingStore.ts:108-131`). Every record in a ring gets the same `created_at` timestamp — the time of the last flush — regardless of when it actually happened. Filtering on `created_at` would compute the same age for every row and re-zero it on every subsequent flush, silently defeating any retention window. The only timestamp that survives serialization untouched is the record's own embedded `.timestamp` field, stamped once at `Date.now()` when the record was originally appended in-memory.

## Lesson

- **Never use `audit_rings.created_at` for record age** — it is re-stamped to the flush time on every `writeAll()`, not the insert time of that specific record. `AuditService.pruneByAge` / `TurnOutcomeService.pruneByAge` both filter on the record's own embedded `timestamp` field instead (`auditLog.ts:659-680`, `turnOutcomeLog.ts:547-558`) — copy that pattern, not the column.
- **This trap is still live for the other four `AuditRingStore` consumers.** `PluginActionAuditService`, `forgeAuditService`, `runHistoryService`, and `plugin-mcp/instances.ts` all still trim by count only (verified: no `pruneByAge`/`created_at` age logic in any of them as of this PR). The fix was applied per-consumer, not at the store level, so adding age-based retention to any of those four will re-encounter the exact same `created_at`-is-flush-time footgun unless the embedded-timestamp pattern is copied deliberately.
- **A settings field with a full write/validate/persist path and passing roundtrip tests can still be completely inert.** `store.get("helpAssistant")?.auditRetention` had a real consumer nowhere in the repo before this PR. When wiring a new persisted setting, grep for actual _read_ sites beyond the settings-tab component and the IPC handler's own get/set, not just that the value round-trips.
- **Guard threshold checks on stored config against type corruption, not just value.** `PeriodicCleanupService` checks `typeof retentionDays === "number" && Number.isFinite(retentionDays) && retentionDays > 0` before pruning — a stringly-typed `"7"` from a corrupted electron-store write coerces `"7" > 0` to `true` in a naive comparison, silently pruning on garbage instead of skipping it.
- **Apply a changed retention/config value both immediately and on the next periodic pass.** The setting-change handler fires `pruneAuditByRetention` right away (`helpAssistant.ts:205-215`) _and_ `PeriodicCleanupService`'s 4-hour tick re-reads the setting fresh — a shortened window takes effect without a restart.

## Applies when

- Adding age/retention-based pruning to any `AuditRingStore` consumer — check `pluginAuditLog`, `forgeAuditLog`, `runHistoryRecords`, `pluginMcpAuditLog` still trim by count only, and each will need its own embedded-timestamp `pruneByAge`.
- Touching `electron/services/persistence/auditRingStore.ts` (`writeAll`, `writeAllSerialized`, the `audit_rings` schema in `electron/services/persistence/schema.ts`) — any age-based logic layered on top must not trust `created_at`.
- Diagnosing "this Settings control doesn't seem to do anything" for any tab under `src/components/Settings/` — grep the field name repo-wide for read sites, not just the write/validate path in the IPC handler.
- Adding a new field to `HelpAssistantSettings` (or any persisted settings shape) — wire a consumer in the same PR, or file the gap explicitly rather than shipping an inert control.
- Writing a numeric threshold comparison against a value read from `electron-store` — assume it can be corrupted to a non-number and guard with `typeof`/`Number.isFinite`, not just a bare comparison.
