## Context

Dev preview panels (`DevPreviewPane.tsx`) and browser panels (`BrowserPane.tsx`) render an Electron `<webview>` tag, which runs its own isolated guest `webContents`, not a DOM node inside the app renderer. `electron/setup/protocols.ts`'s `setupWebviewCSP()` already installs a `before-input-event` listener on every webview guest to intercept Cmd/Ctrl+F (find), Cmd/Ctrl+G (next/prev match), Escape (close find), and Cmd/Ctrl+R (dev-preview reload only) — keys that never reach the app because the guest owns keyboard focus.

## Problem

Pressing Cmd+W (Ctrl+W elsewhere) while a webview held focus closed the ENTIRE Daintree window, not the panel. It only reproduced when the webview-backed panel was the only panel open — add any terminal panel to the grid and Cmd+W worked correctly, closing just the focused panel. That narrowness pointed straight at the webview: terminal panels are normal renderer DOM whose keydown reaches the app; webview panels' keystrokes do not.

## Root cause

Both `createWindow.ts` (initial app view) and `ProjectViewHandlers.ts` (per-project `WebContentsView`, the successor to the old `ProjectViewManager.ts` guard the linked issue #10859 pointed at) install a `before-input-event` handler that computes `isCloseShortcut` and calls `wc.setIgnoreMenuShortcuts(isCloseShortcut)` — this is what stops Electron's native `role: "close"` menu accelerator (`electron/menu.ts:263`) from firing and instead lets the app's own `terminal.close` action (bound to Cmd+W) handle it. That guard runs on the HOST webContents. A `<webview>` element's content process is a separate guest `webContents` (`contents.hostWebContents` points back to the host) with its own OS keyboard focus and its own `before-input-event` stream — the host's `setIgnoreMenuShortcuts` call is scoped to the host `webContents` object and has zero effect on the guest. So when the guest has focus, Chromium delivers Cmd+W to the guest, the host's `setIgnoreMenuShortcuts(true)` never runs (the host never sees the keydown), and Electron's native accelerator fires against the whole `BrowserWindow` unblocked. Every "we already guard against this" audit that only enumerates known top-level `webContents` (main window, each project view) will miss this, because a guest webContents doesn't show up in that enumeration at all — it's attached dynamically per `<webview>` instance via `will-attach-webview`.

The fix mirrors the existing find/reload interception: extend the SAME `before-input-event` listener in `setupWebviewCSP()` to also match the close chord (platform-correct modifier, explicitly rejecting the opposite modifier so Ctrl+Cmd+W isn't treated as close — matching the host-level check byte-for-byte), `event.preventDefault()` the guest event, and forward `WEBVIEW_CLOSE_SHORTCUT` with the panel id (`getWebviewDialogService().getPanelId(contents.id)`) to the host, which dispatches `actionService.dispatch("terminal.close", { terminalId: id }, { source: "keybinding" })`. Unlike Cmd/Ctrl+R (gated to `getPanelKind(contents.id) === "dev-preview"` only — browser panels have no reload handler), the close shortcut has NO panel-kind gate: every webview-hosting panel kind has the identical bug.

## Lesson

- **A host-level `setIgnoreMenuShortcuts` / `before-input-event` guard does not protect any `<webview>` inside that host.** The guest is a separate `webContents` with independent OS keyboard focus; treat "we guard the main window and every `WebContentsView`" as an incomplete audit until you've also checked each webview guest's own `before-input-event` stream.
- **The interception point for guest-swallowed shortcuts already exists** — `setupWebviewCSP()`'s `contents.on("before-input-event", ...)` in `electron/setup/protocols.ts` — so a new guest-swallowed-key bug is very likely an extension of that one listener (match its chord-detection style: explicit modifier, explicit rejection of the opposite modifier, `!input.alt`/`!input.shift` guards) rather than a new mechanism.
- **When a native `role:*` accelerator (close, reload, quit) needs to be suppressed for a webview guest, `event.preventDefault()` inside the guest's own listener plus an IPC round-trip to the host is required** — you cannot call `setIgnoreMenuShortcuts` on the guest's `webContents` to achieve the same effect from inside the guest handler; the working fix forwards a message and lets the host act.
- **Do not gate a webview-guest shortcut fix by panel kind unless the underlying capability genuinely differs.** Cmd/Ctrl+R is dev-preview-only because browser panels have no reload target; Cmd/Ctrl+W applies to every webview kind uniformly (dev-preview AND browser) because both close the same way — check whether your new shortcut is capability-specific or panel-agnostic before copying the reload gate.
- **A bug that "only reproduces when panel X is the only panel open" and disappears once a plain terminal panel is added is a strong signal the culprit is `<webview>` focus-stealing**, not app-level keybinding logic — terminal panels are ordinary renderer DOM and always route keydown through the app handler.

## Applies when

- Adding a new webview-backed panel kind, or adding any new keyboard shortcut that must work while a `<webview>` (dev-preview, browser, or future webview panel) has focus.
- Diagnosing "shortcut X works everywhere except panel Y" where panel Y renders a `<webview>` — check `contents.on("before-input-event")` in `setupWebviewCSP()` before suspecting `ActionService` or keybinding registration.
- Reviewing or extending `electron/setup/protocols.ts`'s webview `before-input-event` handler, or the host-level guards in `electron/window/createWindow.ts` / `electron/window/ProjectViewHandlers.ts`.
- Auditing "we already guard Cmd+W / native accelerators everywhere" claims — verify the audit covers webview guest `webContents`, not just top-level window/view `webContents`.
- Wiring a new `WEBVIEW_*` IPC channel that forwards a guest-swallowed event to the host renderer — `WEBVIEW_CLOSE_SHORTCUT` is the template (channel in `electron/ipc/channels.ts`, event map in `shared/types/ipc/maps.ts`, typed API in `shared/types/ipc/api.ts`, preload in `electron/preload.cts`).
