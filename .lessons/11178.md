## Context

Deliberate theme picks already got a 400ms directional wipe (`runThemeReveal` in `src/lib/appThemeViewTransition.ts`, via the View Transitions API): the old snapshot is clipped away via WAAPI `clip-path` to reveal the new one, encoding the click's origin/direction. Issue #11170 asked for programmatic changes (OS dark-mode switch at sunset, the first-run wizard's silent auto-select, both routed through `setSelectedSchemeIdSilent` in `src/store/appThemeStore.ts`) to get a gentler cue instead of swapping every CSS custom property in one frame. PR #11178 added `runThemeCrossfade`, a 200ms opacity fade at `UI_ENTER_DURATION`, deliberately not reusing the wipe since programmatic changes have no gesture origin to encode a direction from.

## Problem

The naive fix — a standard `document.startViewTransition()` at the document root — would have animated nothing and hard-cut, exactly the bug being fixed. Once a manual WAAPI crossfade replaced it, a subtler problem surfaced only under rapid theme churn: a stale crossfade callback landing after a newer theme write wouldn't just paint the wrong colors, it would silently overwrite them again and cancel the newer write's own pending frame, leaving the DOM out of sync with the store with no error to point at.

## Root cause

`src/index.css` sets `animation: none` on `::view-transition-old(root)` and `::view-transition-new(root)` so the wipe's `clip-path` animation can run uncontested — but that same rule also disables the user agent's _default_ crossfade animation on those pseudo-elements, since both are driven by the same CSS `animation` property. A bare `startViewTransition(mutate)` on the root therefore has nothing left to animate; the crossfade has to be a second manual WAAPI animation (`document.documentElement.animate({opacity:[1,0]}, {pseudoElement: "::view-transition-old(root)"})`), added only after `transition.ready` resolves (the pseudo-element tree doesn't exist before that). Fading only the _old_ snapshot is sufficient — it sits at a higher z-index over an opaque new snapshot, so animating both would double-composite and dip midpoint brightness.

The concurrency trap: a View Transition's `mutate` callback (the theme write itself) is deferred by the browser to run a frame after the call site. If a newer theme change (a direct pick, a hover preview, another OS flip) starts and finishes before that stale callback fires, the stale callback still runs `injectSchemeToDOM(scheme, { immediate: true })` — and `immediate` mode's whole job is to `cancelAnimationFrame` any pending write and apply synchronously. So the stale callback doesn't just paint an old scheme, it **destroys the newer scheme's in-flight write**, stranding the DOM on the old scheme while the store's `selectedSchemeId` says something else. Comparing `selectedSchemeId` wasn't a viable guard either: hover-preview paths (`injectTheme`) call `injectSchemeToDOM` directly without ever touching `selectedSchemeId`, so a preview could supplant a crossfade unnoticed. The fix is a module-level monotonic `themeIntentSeq`: `claimThemeIntent()` runs at the top of _every_ `injectSchemeToDOM` call (every direct write is itself the newest intent) and again right before `runThemeCrossfade` starts, capturing the claimed value in the deferred closure; the closure checks `intent !== themeIntentSeq` and bails instead of writing.

## Lesson

- **A CSS rule that disables an animation so a manual one can "run uncontested" can silently disable an unrelated built-in animation on the same selector.** `animation: none` on `::view-transition-old/new(root)` kills both the wipe's competing default AND the UA's default crossfade, since both ride the same `animation` property. Before assuming `startViewTransition()` "just works" on a pseudo-element, check what prior CSS already targets it.
- **When a DOM write is deferred across an async boundary (rAF, a transition callback, a `.then()`), a "stale" callback isn't just wasted work — check what it can destroy.** Here the stale write's `immediate: true` mode actively cancelled the newer write's pending frame. Trace what the stale path's side effects clobber, not just whether it repaints something outdated.
- **Guard staleness with a counter bumped by every write path, not by comparing a state field a fast path can bypass.** `selectedSchemeId` identity misses hover previews (`injectTheme`) that write the DOM without touching it; the fix claims a monotonic `themeIntentSeq` inside `injectSchemeToDOM` itself so no direct-write call site can be forgotten.
- **Claim the intent token before starting the async operation, not inside its callback.** `claimThemeIntent()` runs synchronously before `runThemeCrossfade` starts, so a second crossfade queued right after always outranks the first regardless of which eventual callback the browser runs first.
- **Guard on "did the bucket actually change", not "did this fire".** `nativeTheme` can re-fire without crossing the light/dark boundary; crossfading unconditionally would `skipTransition()` an in-flight wipe to fade between two identical snapshots. `setSelectedSchemeIdSilent` only crossfades when `previousSchemeId !== scheme.id`.

## Applies when

- Adding a second View Transitions consumer on the document root, or touching the `::view-transition-old/new(root)` rules in `src/index.css` — check what animation those rules already suppress before assuming the UA default still applies.
- Deferring a DOM write into `requestAnimationFrame`, `transition.ready.then()`, or any callback that can race a newer synchronous write to the same target — check what the stale callback's write mode does to the newer write's pending state.
- Reviewing a "cancel if stale" guard keyed on persisted state (an id, a selection) instead of a counter bumped by every code path performing the effect — look for a preview/hover/ephemeral path that performs the effect without updating that state.
- Touching `appThemeViewTransition.ts`, `appThemeStore.ts`'s `injectSchemeToDOM`/`themeIntentSeq`, or `setSelectedSchemeIdSilent` — the crossfade and wipe share one guard stack and intent counter; changes to one must keep the other's staleness check valid.
- Diagnosing a theme flicker or "DOM shows an old theme but the store says a new one" under rapid switching (fast OS toggling, hover-then-click in the picker, programmatic + deliberate changes overlapping).
