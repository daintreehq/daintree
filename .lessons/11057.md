## Context

`ContentDock.tsx`'s scroll row is sized with `min-h-[var(--dock-item-height)]` (a `flex-1` row, not a fixed-height box), and every real docked chip (`DockedTerminalItem`, `DockedNonPtyPanelItem`, `DockedTabGroup`) clamps itself with an explicit `h-[var(--dock-item-height)]`, matching the same token rather than inheriting from the row.

## Problem

Dragging a browser or dev-preview panel over an empty dock made the whole dock bar visibly grow during the drag and snap back on drop (#11055); terminal and agent drags never did this, which pointed investigation at drag-specific state rather than the ghost's own CSS, since "only some panel kinds" looks like a data/kind bug, not a layout one.

## Root cause

`DockPlaceholder`'s ghost box used `h-full` while every real sibling chip uses `h-[var(--dock-item-height)]`. Percentage/`full` heights only resolve against a definite height on the ancestor chain; the dock row sets `min-height`, not `height`, so `h-full` computed to `auto` and the ghost's own content dictated its height instead of being clamped by it — exactly the CSS spec behavior (percentage heights need a definite ancestor height) that `min-height`-only ancestors never satisfy. That alone would have been harmless if the ghost's content were short, but `BrowserPlaceholder` and `DevPreviewPlaceholder` also rendered their full padded content body (address-bar art plus a ~30px content box) even when called with `compact` — the exact same `compact` prop that `TerminalPlaceholder`/`AgentPlaceholder` already used to omit that body. The `compact` boolean shrank paddings and gaps in these two components but never gated the body's presence, so passing `compact` didn't guarantee the component fit `--dock-item-height`; it only guaranteed it looked visually smaller than its full-mode self, which is a different and weaker property. Two independent gaps had to both exist for the bug to appear: the auto-height ancestor removed the clamp, and the two heaviest-content placeholders were the ones whose content actually exceeded the budget.

## Lesson

- **`h-full`/percentage heights require a definite ancestor height — `min-height` doesn't count.** If the parent's height comes from `min-h-*`, flex growth, or content, a `h-full` child computes `auto` and the causality inverts: the child's content now sets the parent's height instead of the parent clamping the child. Fix at the child by pinning it to the same explicit token/pixel value real siblings use (`h-[var(--dock-item-height)]`), not by trying to force a definite height onto the ancestor.
- **When several sibling components share a size budget, check that ALL of them clamp to it explicitly — don't assume the newest one inherited the pattern.** `TerminalPlaceholder`/`AgentPlaceholder`/`DockedTerminalItem` etc. all matched `--dock-item-height`; `BrowserPlaceholder`/`DevPreviewPlaceholder` were the odd ones out, which is exactly why the bug was kind-specific and read as a drag/state bug instead of a CSS one.
- **A `compact` (or similar mode) prop that shrinks paddings/gaps is not the same as a prop that bounds total height.** Verify the compact path actually drops enough content to fit the target box (here: omit the whole padded body, gated by `data-placeholder-body` in tests) rather than just scaling down its dimensions — scaled-down content can still overflow a small fixed budget.
- **A symptom that's specific to only SOME variants of a shared component is a strong signal to diff those variants' markup/CSS against each other**, not to look for logic specific to those kinds elsewhere (drag state, z-index, kind-dependent branching) — here the fix was purely in the two odd-one-out placeholders plus the one shared ghost wrapper.
- **Structural regression tests for pure-CSS layout bugs need a DOM marker, not a pixel measurement** — jsdom has no layout engine, so this PR asserts `[data-placeholder-body]` presence/absence and the absence of the `h-full` class rather than measured heights; add the same marker-based pattern for any future height-containment fix.

## Applies when

- Building any drag-ghost, overlay, or placeholder that must fit inside a fixed-budget row/token (dock, tab strip, toolbar) — check whether the ancestor sets `height` or only `min-height`/`flex` before reaching for `h-full`.
- Adding a new panel kind to `PlaceholderContent.tsx` or any similar per-kind-variant component family — confirm the new variant's `compact` path is bounded the same way the existing variants are, not just visually smaller.
- Diagnosing "only these one or two kinds/variants misbehave" bugs in shared multi-branch components — diff the odd variants against the well-behaved ones before suspecting the surrounding state/logic.
- Touching `--dock-item-height` or the `ContentDock.tsx` row sizing, or any Tailwind flex row that mixes `min-h-[var(...)]` ancestors with `h-full` children.
