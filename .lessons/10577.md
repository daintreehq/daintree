## Context

Plugins run sandboxed and are gated by declared capabilities, but they also get a generic `host.dispatch(actionId, args)` that funnels into the same `ActionService.dispatch` the UI, keybindings, and the MCP agent surface use. The read-only `agent:read` capability was designed to withhold `terminalId` so a plugin "can't drive, pause, resume, or inject into an agent session." Injecting text is normally `terminal.sendCommand` — classified `danger: "safe"` in `terminalQueryActions.ts`.

## Problem

A zero-capability plugin could type-and-Enter arbitrary text into any agent terminal via `host.dispatch("terminal.sendCommand", { terminalId, command })` (#10558). The `agent:read` boundary was real but moot: `host.dispatch` will invoke ANY `safe` built-in, and `sendCommand` auto-submits. The model looked airtight surface-by-surface while a second dispatch route walked straight past it. Two follow-ons found the SAME class again: `worktree.createWithRecipe`/`workflow.startWorkOnIssue` are `danger:"safe"` but spawn recipe terminals — the exact effect `recipe.run` (`danger:"confirm"`) gates (#10582/#10589); and a manifest could statically wire a button to a denied action, or ship a typo'd own-namespace `actionId` as a dead button (#10580/#10596).

## Root cause

The safety boundary lived on the wrong axis. Capabilities gate _named host APIs_, but `host.dispatch` is a second, capability-blind route to the _same effects_, so any effect reachable through an ungated `safe` action bypasses the whole model. Worse, `danger` is a _static per-action-id_ classification, but real blast radius can be _argument-conditional_: `worktree.createWithRecipe` with no `recipeId` just makes a worktree; with a `recipeId` it calls `runRecipeWithResults` and spawns N terminals unprompted — the effect the `confirm`-gated `recipe.run` blocks, yet `canDispatch` greenlit it as `"ok"`. The fix closes one class at three layers: (1) `denyPluginDispatch?: boolean` on `ActionDefinition` (`shared/types/actions.ts`), enforced in `ActionService.dispatch` — `if (definition.denyPluginDispatch && source === "plugin")` returns `RESTRICTED`, leaving `danger:"safe"` intact so agent (MCP) and user dispatch carry NO confirm/elicitation collateral; set on `terminal.sendCommand`, `terminal.paste`, and the four `fleet.*` relays; paired with a new `agent:input` capability + `host.sendToActiveAgent(text, { submit? })` (JIT consent, bracketed-paste staging, default stage-only). (2) An args-conditional source guard in `workflowCreationActions.ts` — `if (recipeId && ctx.dispatchSource === "plugin") throw` BEFORE any IPC fires. (3) Parse-time enforcement in `electron/schemas/plugin.ts`: contributions wired to `DENY_PLUGIN_DISPATCH_ACTION_IDS` are rejected during manifest validation, and own-namespace `actionId`s are cross-checked against declared `contributes.commands[]`.

## Lesson

- **A capability model is only as strong as its least-gated dispatch route.** Before trusting a capability gate, enumerate EVERY path that reaches the gated effect — `host.dispatch` into `safe` built-ins was a capability-blind side-door that made the entire `agent:read` design moot. Adding a capability without closing the generic-dispatch route protects nothing.
- **Gate by dispatch source, not by raising `danger`.** `denyPluginDispatch` returns `RESTRICTED` only for `source === "plugin"`; agent (MCP) and user are the sanctioned surfaces and stay unaffected. Bumping `danger` to `"confirm"` instead would have inflicted CONFIRMATION_REQUIRED / MCP elicitation on every legitimate agent and user caller — the source-scoped flag is the surgical tool.
- **Static per-action `danger` cannot see argument-conditional effects.** When an action's blast radius depends on its args (a `recipeId` that turns a worktree-create into a terminal-spawn), the id-level classification lies and `canDispatch` reports the more dangerous path as `"ok"`. Guard the effect with an early `ctx.dispatchSource === "plugin"` check that runs before any IPC; reason about the _effect_ an arg unlocks, not the action name.
- **Push a runtime deny-list to parse time so a bad wiring can't ship at all.** `DENY_PLUGIN_DISPATCH_ACTION_IDS` (`shared/config/actionIds.ts`, typed `as const satisfies readonly BuiltInRuntimeActionId[]` for compile-time drift detection) is checked in the manifest `superRefine`, so a contribution wired to a denied action fails validation instead of painting a dead button. Defense in depth: runtime + parse-time + a completeness test asserting the list matches every `denyPluginDispatch: true` flag.
- **Own-namespace `actionId` validation must cross-check declared commands — but only when commands exist.** The bare `actionId.startsWith(ownNamespacePrefix)` check passed any typo'd id in the namespace, shipping dead buttons; the fix cross-checks against `contributes.commands[]` **gated on `commands.length > 0`**, because imperative `host.registerAction` is invisible at parse time and must stay a valid fully-imperative escape hatch.

## Applies when

- Adding a capability to the plugin model, or reviewing whether an existing one is actually enforced — audit `host.dispatch` and every other route into the gated effect, not just the named host API.
- Touching `ActionService.dispatch` gate ordering, `denyPluginDispatch`, or `ActionContext.dispatchSource` — the plugin/agent/user distinction is load-bearing; do not collapse plugin denial into a `danger` bump.
- Classifying a new action's `danger`, or adding an arg that changes its blast radius (spawns terminals, writes shared state) — static id-level danger misses args-conditional effects; add a source guard before IPC.
- Wiring or validating plugin manifest contributions that reference an `actionId` — deny-listed built-ins and undeclared own-namespace ids must fail at parse time.
- Finding text injected into an agent terminal from a plugin — the sanctioned path is the `agent:input`-gated `host.sendToActiveAgent` (now resolved in `electron/services/plugin/PluginHostFactory.ts`, moved there from `PluginService.ts` after this PR).
