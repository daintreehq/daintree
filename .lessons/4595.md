## Context

The project resource badge shows memory health status. PR 4595 evolved it into a full diagnostics panel with real-time process metrics (PID, type, memory, CPU%), V8 heap progress bar, and trend indicators.

## Problem

Displaying meaningful memory trend data requires more than just a current snapshot. A single reading can't tell you if memory is growing, stable, or declining, and a delta between the last two samples is dominated by GC noise — momentary heap fluctuations produce false "growing" arrows. Showing a raw MB number also gives users no actionable context. Continuously fetching the full process list and heap stats over IPC to drive a panel most users never open is wasteful overhead.

## Root cause

The needed signals have fundamentally different cost and freshness profiles, so a single naive polling loop is wrong on every axis. The total-memory number that colors the badge is cheap and must update even when the panel is closed, so it polls always at `BADGE_POLL_MS`. The full diagnostics payload (`systemClient.getProcessMetrics()`, `getHeapStats()`, `getDiagnosticsInfo()`, plus per-project bulk stats) is expensive and only meaningful while the popover is visible, so it is gated on the `open` state and torn down on close. A trend direction can't be read off two samples because the underlying memory series is noisy; it needs a regression over a window to extract the real slope from the jitter.

## Lesson

- Poll expensive diagnostics (process list, heap stats, per-project bulk stats) only when the UI displaying them is open — `src/components/Project/ProjectResourceBadge.tsx` wires the popover fetch loop to the `open` state (`useState`/`onOpenChange`), runs it at `POPOVER_POLL_MS` (4s), and clears the interval plus nulls `popoverData` on close. The cheap badge-coloring memory total polls independently and always, at `BADGE_POLL_MS` (10s).
- Use a sliding window with least-squares linear regression rather than delta-between-last-two for trend indicators. `computeSlope` runs over a `MAX_SAMPLES` (12) window; at the 10s `BADGE_POLL_MS` cadence that is a 2-minute trend resistant to momentary GC spikes. `getTrendDirection` converts slope-per-sample to slope-per-minute via `SAMPLES_PER_MIN` and applies a `TREND_DEADBAND_MB_PER_MIN` (3 MB/min) deadband before showing an up/down arrow.
- Separate the IPC channels for different data freshness needs: `diagnostics:get-process-metrics` (changes per second) vs `diagnostics:get-heap-stats` (changes per few seconds). Both are defined in `electron/ipc/channels.ts` (`DIAGNOSTICS_GET_PROCESS_METRICS` / `DIAGNOSTICS_GET_HEAP_STATS`) and typed in `shared/types/ipc/maps.ts`.
- Express memory thresholds in absolute MB, not percentages — available system RAM varies wildly between machines. `getMemoryState` uses `MEMORY_THRESHOLD_ELEVATED` (500 MB) and `MEMORY_THRESHOLD_CRITICAL` (800 MB); the V8 heap bar flags separately at `> 85%`. (Note: state coloring is purely threshold-on-total; the growth-rate signal lives in the trend arrow, not folded into the badge state.)

## Applies when

- Building any live diagnostics or monitoring UI in Electron
- Implementing trend/sparkline indicators from sampled data
- Deciding polling frequency and when to pause polling
