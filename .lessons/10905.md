## Context

The 30-day resume journal (`agent-session-history.json`, `electron/services/pty/agentSessionHistory.ts`) lets closed agent terminals be resumed from the panel palette, the resume palette, and the empty-grid card. Originally only the pty-host's 20s trash-expiry timer wrote it. #10849/#10856 routed `terminal.kill`, `gracefulKill`, and app-quit shutdown through `persistAgentSession` too, adding an in-module `writeQueue` promise chain so the newly-concurrent close paths wouldn't lost-update each other. #10865 then built a worktree-grouped, searchable browse list on the now-denser journal.

## Problem

Records still silently disappeared or got clobbered after #10856's serialization, especially around app quit. Separately, #10865's grouped browse view showed a spurious "No worktree" group sitting right next to the real worktree's group for sessions that plainly ran inside it. Both looked fixed by the just-shipped work in isolation, which pointed investigation the wrong way.

## Root cause

`persistAgentSession`'s `writeQueue` is `let writeQueue: Promise<unknown> = Promise.resolve()` — module-scope state. `electron/pty-host.ts` and main are **separate OS processes**, each with its own loaded copy of `agentSessionHistory.ts`, so each has its own independent `writeQueue`. The chain correctly serializes close paths _within_ one process (what #10856 needed) but has zero visibility into the other process's chain. Both sides still do read-file → modify-array → write-file; when the pty-host's trash-expiry capture and main's app-quit shutdown snapshot land close together (the common case at quit), the second write simply overwrites the first process's freshly-appended record at the OS level. A correct-looking mutex was scoped to the wrong boundary — per-process, not per-resource — so it could never have prevented this.

The fix isn't more locking, it's architectural: make main the journal's **sole writer**. The pty-host no longer calls `persistAgentSession` directly; on trash expiry it emits a `PtyHostEvent` of type `agent-session-captured` (`shared/types/pty-host.ts`, record minus `savedAt`). `PtyEventsBridge.bridgePtyEvent` re-emits it onto main's bus as `agent-session:captured`, and `electron/ipc/handlers/terminal/events.ts` is the only place left that calls `persistAgentSession` for pty-host-originated records, now applying the real `getAgentSessionRetentionDays()` (the pty-host previously had no settings-store access and hardcoded retention to `0`/keep-forever as a workaround). Only after that write resolves does main emit `agent-session:recorded`, telling resume surfaces to refetch — signalling before the write lands just moves the race to the read side.

A second, unrelated defect rode the same arc: #10865 grouped rows by `session.worktreeId`, stamped once at capture time. Terminals spawned before worktree selection settles are journaled with `worktreeId: null`, so those rows landed in a synthetic "No worktree" bucket despite genuinely running inside a worktree. #10905 dropped grouping entirely and fixed the data underneath: `buildResumeSessionItems` (`src/services/resumeSessionItems.ts`) now re-derives a missing `worktreeId` via `inferWorktreeIdFromCwd` (longest-prefix match against live worktree paths, moved to `src/utils/worktreePaths.ts`) before deciding staleness or the location label.

## Lesson

- **A module-scope promise-chain/mutex only serializes writers inside the process that declared it.** Two Electron processes (main, pty-host, workspace-host) each `import`-ing the same module and each writing the same file get two independent queues — no cross-process ordering, however correct the in-process chaining is. #10856's `writeQueue` was necessary for intra-process safety but could never close the main↔pty-host race.
- **When N processes must mutate one persisted resource, designate exactly one process the writer and have every other process ship data over the existing event bus instead of writing.** Here: `agent-session-captured` `PtyHostEvent` → `PtyEventsBridge` → `agent-session:captured` on main's bus → `persistAgentSession`. This also retired a workaround: the pty-host no longer needs `0`/keep-forever retention as a stand-in for a setting it couldn't read.
- **Order the "it's ready" signal strictly after the write resolves.** `agent-session:recorded` fires only once `persistAgentSession` succeeds so a listener's refetch is guaranteed to see the new record — signalling eagerly just relocates the race to the read path.
- **Don't bucket UI rows on a field that can be legitimately null or stale at capture time when a live-derivable fallback exists.** Grouping by the recorded `worktreeId` (null pre-worktree-selection) fabricated a bogus "No worktree" group; re-deriving from `cwd` fixes the data, and dropping grouping for a flat list sidesteps the bug class here.
- **Two individually-correct fixes can still compose into a race.** #10856's serialization and #10865's grouping both looked fine standalone; the bug only showed in the cross-process interaction, needing a third PR (#10905) to resolve.

## Applies when

- Touching `agent-session-history.json`, `agentSessionHistory.ts`, `PtyManager.trash()`/`gracefulKill`, or any close path that journals a resumable session.
- Adding a new writer to a file the pty-host (or workspace-host, or any other utility subprocess) also writes — check for a cross-process writer before trusting an in-process queue, debounce, or mutex to make it safe.
- Diagnosing intermittently missing or clobbered records in a JSON-file-backed store when multiple Electron processes can each independently trigger a write around the same event, especially app quit.
- Reviewing any `let queue: Promise<...>` / lock / debounce pattern spanning an Electron main↔utility-process boundary — module state is never shared across processes, only within one.
- Designing a "group by X" browse UI fed by a value stamped once at write time (worktree, project, owner) — check whether X can be null or stale at capture and whether a live-derived value can re-home it.
