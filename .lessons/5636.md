## Context

Persisted panels are restored on project load by `panelRestorePhase.ts`. When a panel's `kind` is not in the live `panelKindRegistry`, hydration has a deliberate policy: skip it (`Skipping persisted panel with unregistered kind`). That policy was correct for removed _built-in_ kinds — restoring the "notes" kind deleted in #5616 produced "Unknown Panel Type" ghost panels, so dropping it on load was the fix.

## Problem

Plugin-contributed panels produce the _same_ unregistered-kind signal as removed built-ins, but for the opposite reason: the kind is absent only because the plugin is temporarily disabled/uninstalled, and it can come back. The unconditional drop meant disabling a plugin silently deleted its panels from the layout permanently — re-enabling the plugin would not bring them back, because the persisted entry was already gone. The two cases collide on one indistinguishable predicate (`!getPanelKindConfig(kind)`).

## Root cause

Two structural facts. First, "kind not registered right now" conflates two states with opposite correct handling — a permanently-removed built-in (drop) vs a recoverable disabled-plugin panel (preserve) — so the skip predicate must carry a discriminator beyond registry presence. Second, plugin provenance cannot be recovered at hydration or render time, because the plugin may already be gone from the registry by then. It must be captured _while the registry still has the entry_ — at panel creation. `createCorePanelActions` (`src/store/slices/panelRegistry/core.ts`) stamps `pluginId = kindConfig?.extensionId ?? options.pluginId`: live registry lookup wins, falling back to the hydration-supplied value when the registry has no entry.

## Lesson

When restore logic drops state on a "not registered / not recognized" check, that check is a _policy_, not a fact — split it for any subtype that is recoverable rather than gone. Here the escape hatch is `if (!getPanelKindConfig(kind) && !saved.pluginId && !kind.includes("."))` (`panelRestorePhase.ts:363`): a `pluginId` field (current format) or a dotted kind string `${manifest.name}.${panel.id}` (legacy pre-#5580 panels saved without a `pluginId`) both mark the panel as plugin-owned and recoverable, so it is restored and the renderer (`GridPanel`/`DockedPanel`, `isPluginOwned = Boolean(terminal.pluginId) || kind.includes(".")`) surfaces a `PluginMissingPanel` placeholder instead of a ghost. Threading a new provenance field end-to-end means every snapshot/restore builder must forward it: the Zod schemas (`electron/schemas/ipc.ts`), all `buildArgsFor*` patchers (`statePatcher.ts`), `panelToSnapshot`'s `BASE_PANEL_FIELDS` allowlist, and the React.memo equality (`gridPanelPropsAreEqual`) — miss any one and the field is silently stripped at that hop.

## Applies when

- Adding or removing a panel/registry kind and reasoning about what happens to already-persisted instances on the next load.
- Disabling/uninstalling a plugin should _hide_ its panels (recoverable) rather than _delete_ them — verify the hydration skip predicate has the plugin escape hatch.
- Any restore path that drops unrecognized state: confirm the drop is correct for permanently-removed entries but does not also nuke recoverable ones sharing the same "unknown" signal.
- Adding a new field to `TerminalInstance`/`PanelSnapshot` that must survive save/restore — audit the full chain (Zod schema, `BASE_PANEL_FIELDS`, `buildArgsFor*`, memo equality) or it dies at one hop.
