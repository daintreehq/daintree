## Context

`registerAppLifecycleHandlers` in `electron/lifecycle/appLifecycle.ts` installs the main-process OS-signal handler (SIGTERM/SIGINT/SIGUSR2, plus SIGHUP in dev). The handler calls `setSignalShutdown()`, schedules a safety-belt timer, then `app.quit()` so `before-quit` runs the full graceful cleanup chain in `shutdown.ts` — which includes `CrashLoopGuard.markCleanExit()` and `closeTelemetry()`. The cleanup chain itself has its own hard timeout `CLEANUP_TIMEOUT_MS` (10s, added in #4287).

## Problem

Three independent shutdown-correctness defects coexisted in the signal handler:

1. The safety-belt `setTimeout(() => process.exit(0), 5000)` fired at 5s — shorter than the 10s `CLEANUP_TIMEOUT_MS` cleanup budget. Signal-driven shutdowns killed the process mid-cleanup, so `markCleanExit()` and telemetry flush often never completed.
2. SIGHUP was unregistered. Closing the dev terminal sends SIGHUP, which bypassed `before-quit` entirely; `markCleanExit()` never ran, so on the next launch CrashLoopGuard counted a phantom crash — three dev-terminal closes in a minute booted the app into safe mode for no reason (same failure mode SIGUSR2/nodemon had).
3. The handler was guarded by a one-shot `signalHandled` boolean. Once set, every later signal was silently swallowed with no force-exit — if cleanup stalled, the user's Ctrl-C escape hatch did nothing.

## Root cause

The safety belt and the cleanup chain are two independent timers that must be ordered: the belt is the last-resort kill, so it MUST be strictly greater than the worst-case cleanup wall time, or it pre-empts the very cleanup it's protecting. The original 5s belt was authored without reconciling against `CLEANUP_TIMEOUT_MS`. Worst-case cleanup is not just `CLEANUP_TIMEOUT_MS` — `closeTelemetry()` runs after the cleanup race and can add ~2.5s (Sentry `SENTRY_INIT_WAIT_CAP_MS` 500ms + `SENTRY_CLOSE_TIMEOUT_MS` 2000ms in `TelemetryService.ts`). For the dev-signal trap, any signal that terminates the process without routing through `app.quit()`/`before-quit` skips `markCleanExit()`, which CrashLoopGuard reads as an unclean exit. For the escape-hatch trap, a permanent one-shot flag conflates "already shutting down" with "ignore the user forever."

## Lesson

- A safety-belt / last-resort exit timer must be strictly longer than every cleanup budget it backstops, including post-race work. Express the dependency in code, not a magic number: the constant now lives in `electron/lifecycle/shutdownConfig.ts` as `SAFETY_BELT_TIMEOUT_MS = CLEANUP_TIMEOUT_MS + 3000 + 2500` (cleanup race + historical buffer + worst-case telemetry close), with a comment tying each term to its source.
- Put shared shutdown-timing constants in a side-effect-free module (`shutdownConfig.ts`), not in `shutdown.ts` — so the signal handler and tests can import them without dragging in the full service graph (ProjectStore, TelemetryService).
- Every signal that should shut the app down cleanly must route through `app.quit()` so `before-quit` fires `markCleanExit()`. Any signal you don't register, or that terminates outside `before-quit`, becomes a phantom crash in CrashLoopGuard. Register dev-only signals (SIGHUP) gated on `!app.isPackaged` — packaged builds are TTY-detached and SIGHUP conventionally means "reload config" to launchd/systemd, so do NOT intercept it in production.
- Replace a one-shot boolean guard with a temporal-window pattern when the user needs an escape hatch: record `firstSignalTime`, and on a second signal within ~2000ms call a dirty force-exit; ignore signals after the window (cleanup is genuinely in progress). The belt itself should fire `app.exit(1)` (dirty, lets Electron's native teardown run and reports the right code to process supervisors), never `process.exit(0)`.
- The belt handle must be cleared by the cleanup chain (`clearSafetyBeltTimer()` in `shutdown.ts`, handle stored in `signalShutdownState.ts`) before its own `app.exit()`, or a slow `closeTelemetry()` lets the stale belt fire after a normal exit and clobber the exit code.

## Applies when

- Touching `electron/lifecycle/appLifecycle.ts`, `shutdown.ts`, `shutdownConfig.ts`, or `signalShutdownState.ts`.
- Adding or changing any OS-signal registration (SIGTERM/SIGINT/SIGHUP/SIGUSR2) or `before-quit`/`will-quit` handlers in the main process.
- Adjusting any shutdown/cleanup timeout (`CLEANUP_TIMEOUT_MS`, `SAFETY_BELT_TIMEOUT_MS`, `closeTelemetry()` / Sentry close timeouts) — re-check the belt still strictly exceeds the cleanup chain.
- Debugging the app spuriously booting into safe mode, or `CrashLoopGuard.markCleanExit()` not running, after dev restarts (nodemon) or closing the dev terminal.
- Designing any "last-resort kill" timer that backstops an async cleanup chain, or any one-shot handler where the user might need to re-trigger to force-exit a stalled operation.
- Reports that Ctrl-C / repeated kill signals do nothing while the app hangs on shutdown.
