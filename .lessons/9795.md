## Context

At cold launch `AppInner` mounted ~60 hooks in its first commit, all their mount effects flushing in one post-paint long task right in the first-input window — early keystrokes paid for listener registration the app didn't need yet. #9795 (issue #9769) moved nine hooks that only matter after state restoration into a new `PostHydrationListeners` null component rendered behind `{isStateLoaded && ...}`. Since the App.tsx split the mount site is `src/ModalHostLayer.tsx` (~line 869), and the roster has grown to eleven (`useIdleBackgroundCloseNotifications`, `usePluginUpdateCheckListener` joined; the GitHub hooks became `useForgeTokenHealth`/`useForgeRateLimit`).

## Problem

Moving a hook's mount later looks like a pure perf refactor — the hooks already gated their behavior on `isStateLoaded` internally, so deferring the mount seems equivalent. It is not: one of the nine, `useDiskSpaceWarnings`, subscribes to `window:disk-space-status`, and main pushes the current non-normal status exactly once at `did-finish-load` (`electron/window/windowServices.ts`, `getCurrentDiskSpaceStatus()` → `EVENTS_PUSH`). With the subscriber now mounting after the hydration round-trip, a slow startup delivers that one-shot to zero subscribers and the preload event bus drops it. The user with a nearly-full disk sees nothing — until the next status _change_, which the 5-minute Schmitt-trigger poll in `DiskSpaceMonitor.ts` may never produce if the disk stays uniformly low. Silent, intermittent, cold-launch-only.

## Root cause

The preload event-bus multiplexer (`_ensureEventBusWired` in `electron/preload.cts`, from #5734) discards envelopes that arrive with no subscriber unless the event name is in `_eventBusReplayable`, which buffers the payload and replays it to the first subscriber. Deferral therefore changes the delivery contract for push-only events: before #9795 the disk-status subscriber attached during the first commit flush, before main's `did-finish-load` push landed; after, there is a real window between the push and the hydration-gated mount. The fix was one line — add `window:disk-space-status` to `_eventBusReplayable` (latest-wins is correct: single-shot, low-frequency, current-state, so the buffered payload always reflects reality). The event-bus side — replay semantics (latest-wins vs the FIFO `_eventBusFifoReplay` set from #11280), eager wiring, the three cold-launch timing gaps — is lesson 9564's territory; this lesson is the consumer-side rule: the audit you owe every hook you stage later.

## Lesson

- **Deferring a subscriber is a semantic change, not a layout change.** A hook that "gates on `isStateLoaded` internally" still registered its listener in the first flush; moving the mount moves the subscription. Before staging any hook later, enumerate every push event it subscribes to and ask: can main fire this before the new mount point? For one-shots fired at `did-finish-load`, the answer is yes on every slow startup, and the failure is silent.
- **The late-mount audit has four passing categories** (from the `PostHydrationListeners` doc comment): (1) module-scope re-attach latch — `useDiskSpaceWarnings`' `ipcListenerAttached` one-way latch (never reset; resetting caused duplicate-toast #10455); (2) pulls current state on mount (the forge/store hooks); (3) poll-backed; (4) subscribes to events that cannot fire before the window is interactive. A hook fitting none of these must either stay pre-paint or get its event added to `_eventBusReplayable` — that dual outcome is the whole audit.
- **The keep-set is load-bearing — don't "finish the job" by deferring it.** Global keybindings, the action registry, MCP/plugin bridges, `useFocusOnActivateIntent`, OS DND, and `usePluginDeepLink` (now in `src/hooks/app/useAppBootstrap.ts`) must subscribe before first paint or they miss real events. A future "reduce the first effect flush further" task must treat these as fixed.
- **`setStartupQuietPeriod` suppresses, it does not replay.** It only quiets toasts during the restore window; it is not a delivery mechanism and covers nothing about dropped events. Don't let its existence pass the audit for you.
- **Staged mounts need their own perf mark.** `POST_HYDRATION_LISTENERS_MOUNT` (`shared/perf/marks.ts`) anchors the deferred flush so LoAF attribution stays readable — otherwise work moved out of `RENDERER_FIRST_INTERACTIVE` reappears as unattributable long tasks. Any new staging tier ships with its own mark.

## Applies when

- Adding a new app-level listener hook and choosing between `PostHydrationListeners` and the pre-paint set in `useAppBootstrap`/`ModalHostLayer` — run the four-category audit; the roster has grown twice since #9795 and each addition owes it.
- Doing startup-perf work that moves effect registration later (staging, lazy mounting, Suspense-gating any subscriber) — every moved subscription needs the one-shot audit, not just the ones that look event-driven.
- Diagnosing a warning/notification that appears on warm reload but not cold launch, or shows up minutes late — check whether its event is a `did-finish-load` one-shot missing from `_eventBusReplayable` before calling it flaky.
- Touching main-side pushes at `did-finish-load` in `electron/window/windowServices.ts`, or adding any main→renderer one-shot whose subscriber mounts behind `isStateLoaded` — pair it with a replayable-set entry (semantics choice: lesson 9564).
- Reviewing a perf PR that claims a hook move is behavior-neutral because "the hook already gates internally" — internal gating governs what the hook does with events, not whether it receives them.
