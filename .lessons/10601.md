## Context

After #10574 made plugin agents launchable, #10587/#10601 let a contributed agent drive the working/waiting/completed UI via declared output `detection` patterns — a bounded-regex block added to `AgentContributionSchema` / `PluginAgentContribution` and threaded onto the resolved `AgentConfig` by `contributionToAgentConfig`. The activity monitor that matches those patterns and resolves `getEffectiveAgentConfig` runs inside the pty-host utility subprocess, not in main or the renderer.

## Problem

A plugin agent's declared patterns did nothing: deterministic output like `Thinking… / Waiting for approval… / Completed.` left the terminal as a generic "running" pane, never reaching working/waiting/completed. The symptom pointed straight at the matcher or the schema — as if the regexes weren't compiling or weren't being scanned — when in fact the pty-host had never even been told the agent existed.

## Root cause

`shared/config/pluginAgentRegistry.ts` is module state — a SEPARATE singleton instance in every process that imports it. `registerPluginAgents` / `setPluginAgentRegistry` ran only in main (and the renderer via broadcast); the pty-host process, which owns the activity monitor and calls `getEffectiveAgentConfig`, held its own empty instance main never synced. So `getEffectiveAgentConfig(pluginId)` returned undefined there and the patterns were structurally inert no matter how correct the regex. The fix is an explicit cross-process mirror: a `set-plugin-agent-registry` IPC message (`shared/types/pty-host.ts`) carrying main's flattened, command-resolved snapshot (`Record<string, AgentConfig>`); the pty-host handler in `resourceConfig.ts` applies it via `setPluginAgentRegistry`, guarding the shape at the boundary (reject array/null so a spread can't corrupt the snapshot). Two ordering constraints make it correct under crash recovery: `PluginService` pushes on every plugin load/unload (`getPtyClient()?.syncPluginAgentRegistry()`), AND `PtyClient` replays the authoritative main snapshot on EVERY host-ready BEFORE spawn replay, so a restarted host — or a project shard forked mid-session — resolves patterns from tick 1 rather than only for terminals spawned after the next unrelated plugin event. One red herring the PR explicitly ruled out: `agentState` was never gated on `detectedAgentId`; the `isBuiltInAgentId` guard at `TerminalAgentDetection.ts:79` gates process-detector IDENTITY promotion only, not the activity-monitor state path — so the ONLY blockers were the missing `detection` schema field and the missing registry sync.

## Lesson

- **Any `shared/config` registry is a per-process singleton, not shared state.** A utility subprocess (pty-host, workspace-host, plugin workers) that reads `getEffectiveAgentConfig` or any registry gets its OWN copy — main writing to the module does nothing there. When a feature depends on a registry inside a utility process, you MUST mirror it explicitly over IPC; relying on the module import to carry config across the process boundary is a silent no-op.
- **Mirror state must be REPLAYED on host-ready before spawn replay, not just pushed on change.** `PtyClient.handleShardReady` re-sends the snapshot on every ready so a crashed/restarted host (or a freshly forked project shard) re-syncs BEFORE it replays pending spawns — otherwise respawned terminals run pattern-blind until the next unrelated plugin load/unload. Push-on-change alone leaves the whole post-restart window broken.
- **Keep the mirror one-way: main is authoritative, the utility process only ever applies.** The pty-host never calls `registerPluginAgents` itself — it applies whatever snapshot arrives and validates the shape. One-way avoids divergent copies drifting between processes.
- **The pty-host fabric multiplied this invariant per-shard.** With `DAINTREE_PTY_FABRIC` sharding the host per project, `syncPluginAgentRegistry` now fans out to EVERY ready shard and each `handleShardReady` replays independently. Adding a consumer process inherits the mirror+replay contract automatically — when you add a process that reads the registry, wire its sync.
- **Before concluding "the matcher is broken," confirm the matcher's process even has the config.** The inert-patterns symptom pointed at regex/schema; the cause was an empty registry in another process. `getEffectiveAgentConfig` returning undefined inside the pty-host is the tell — check the cross-process state before re-auditing the matcher.

## Applies when

- Adding config/registry state that a utility subprocess (`pty-host/`, `workspace-host/`, plugin workers) must read — wire an explicit IPC mirror plus a host-ready replay; don't rely on the shared module import to cross the boundary.
- Diagnosing plugin/agent detection (working/waiting/completed) that does nothing despite valid declared patterns — check whether `getEffectiveAgentConfig` resolves the agent INSIDE the pty-host, not just in main/renderer.
- Touching `set-plugin-agent-registry`, `syncPluginAgentRegistry`, `PtyClient.handleShardReady`, `resourceConfig.ts`, or any `setPluginAgentRegistry` caller.
- Reasoning about crash-recovery ordering for any host-process-wide setter — it must replay on ready before spawn replay, and independently per shard under the pty-host fabric.
- Suspecting agent state is gated on `detectedAgentId` — it isn't; `isBuiltInAgentId` at `TerminalAgentDetection.ts:79` only gates identity promotion, not the state path.
