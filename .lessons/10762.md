## Context

`useRepositoryStats` (src/hooks/useRepositoryStats.ts) drives the issue/PR counts in the toolbar's `ForgeStatusIndicator`, and is built on the shared `usePollingLifecycle` primitive (src/hooks/usePollingLifecycle.ts, extracted May 2026) which owns the timer, in-flight guard, and a fetchId-based `isInvalidated()` that a consumer's `fetchFn` is expected to call after each `await`. On top of that primitive contract, `useRepositoryStats` also kept its own ad hoc cross-project guard: a ref holding the last-seen project's path, compared against the just-resolved project on every fetch completion.

## Problem

Switching away from a project before its forge-stats fetch resolved, then switching back, left the toolbar stuck on a persistent red error line (`forge-status-error` in `ForgeStatusIndicator.tsx`, issue #10761) that only cleared once a manual click forced a fresh fetch. The guard looked correct on inspection — `if (lastKnownCountsRef.current.projectPath !== null && ...!== project.path) return;` reads like a textbook cross-project check — so the bug was easy to misdiagnose as "the comparison is wrong" when the real defect was a few lines away, in what reset the ref.

## Root cause

`onProjectSwitch` fired on every switch, before the next fetch, and reset `lastKnownCountsRef.current = { issueCount: null, prCount: null, projectPath: null }`. The guard's own condition requires `projectPath !== null` to engage at all — so resetting it to `null` on every switch disarmed the exact check that switch was supposed to arm. A fetch already in flight for the old project would resolve (success or error) after that reset, call `projectClient.getCurrent()` (now returning the new project), sail past the permanently-disabled guard, and get applied via `applyStatsResult` onto the new project — including the old project's error, which is the red line that persisted until a manual click overwrote it with fresh data.

`usePollingLifecycle`'s own `isInvalidated()` (fetchId-based) does not automatically save you here: it only fires when a _new_ `callFetchFn` invocation supersedes one that's in-flight, it must be called explicitly at each bail point, and it says nothing about "which project" — it's a generic supersession signal, not an identity guard. A later comment in the same hook (added for issue #11078's seeding logic) makes this explicit: the seed logic deliberately lives inside the epoch-guarded `fetchFn` rather than a render-time effect, because ordering between the IPC-driven `onProjectSwitch` callback and the renderer's own `useProjectStore` update is not guaranteed — a render-time effect could seed the outgoing project's counts into the incoming project, "exactly the class of bug #10761 exists to prevent."

## Lesson

- **Never use a nullable/sentinel ref as an async-supersession guard when the same event that should arm it also resets it to the sentinel** — that's the `!== null` bypass. `lastKnownCountsRef.current.projectPath` went `null` on every switch, which is precisely when the guard needed to be armed.
- **Use a monotonically-incrementing generation counter compared with strict `!==`, not a nullable equality check** — there is no valid counter value that reads as "don't check," so it can't be silently disarmed. #10762 replaced the path ref with `fetchGenerationRef`, captured as `const myGeneration = fetchGenerationRef.current` before the first `await` and rechecked after every subsequent `await`, including inside the `catch` block (an old project's _error_ landing on the new project is just as wrong as its success).
- **Increment the generation counter unconditionally in the switch handler, before any mounted-guard early return** — `useRepositoryStats` bumps `fetchGenerationRef.current += 1` even when `!mountedRef.current`, so a straggling promise's later comparison is still correct regardless of unmount timing.
- **`usePollingLifecycle`'s `isInvalidated()` is a related but narrower guard, not a substitute.** It's opt-in (call it yourself after every `await`) and scoped to "a newer trigger arrived while this fetch was in flight" inside the primitive's own queue — it doesn't protect state changes made outside `fetchFn` (broadcast pushes via `onRepoStatsAndPageUpdated`, render-time seeding effects). A hook doing cross-identity work beyond the primitive's fetch cycle needs its own generation ref alongside `isInvalidated()`, as this hook now does at every bail point.
- **This is an established Daintree idiom, not a one-off invention** — `focusGenerationRef` in `src/components/Terminal/HybridInputBar.tsx` (predates this PR, landed 2026-05-19) guards a RAF-scheduled focus-steal against a superseding focus change with the identical capture/increment/recheck shape. Reach for "capture generation, recheck after every await" whenever an async continuation must not apply against a since-changed identity — project, focus target, panel, terminal.

## Applies when

- Touching `useRepositoryStats.ts`, `usePollingLifecycle.ts`, or `useProjectHealth.ts` fetch/switch logic, or building a new hook on `usePollingLifecycle`.
- Writing or reviewing any hook-owned async fetch that reads mutable "current X" state (current project, current focus target, current panel/terminal) across an `await` and must discard stale results when X changes mid-flight.
- Diagnosing a toolbar/indicator stuck on a stale error or stale data until a manual refresh "fixes" it — a classic symptom of an async guard that fails to stay armed across the very event it should catch.
- Reviewing a "cross-X contamination guard" shaped like `ref.current !== null && ref.current !== newValue` — check whether anything resets that ref to `null` on the same code path that should trip the guard.
- Deciding whether `usePollingLifecycle`'s `isInvalidated()` alone suffices for a new consumer, versus needing a dedicated generation ref for state touched outside `fetchFn`.
