## Context

The error-retry path (`ErrorService.handleRetry` → `executeAction` in `electron/ipc/errorHandlers.ts`) re-attempts a failed terminal spawn by calling `PtyClient.spawn(id, options)`. `PtyClient.spawn()` (`electron/services/PtyClient.ts:630`) returns `void`: it normally posts a `{type:"spawn"}` message to the pty-host utility process and the real outcome arrives later as a `"spawn-result"` EventEmitter event once the host round-trips.

## Problem

The terminal branch was fire-and-forget: it called `spawn()` and let the surrounding `await executeAction(...)` resolve immediately. Any spawn failure — including a synchronous `PENDING_SPAWNS_CAPPED` rejection — was reported to the user as a successful recovery, and the retry backoff in `handleRetry` never saw the error code to classify it.

## Root cause

`spawn()` has two outcome channels through the _same_ `"spawn-result"` event, with different timing. The cap guard (`PtyClient.spawn`, lines 631-644) emits `spawn-result` **synchronously**, inline, before `spawn()` returns — there is no host round-trip when `pendingSpawns.size >= MAX_PENDING_SPAWNS`. Every other failure (and success) arrives asynchronously from the host message. A `void`-returning method that signals via an EventEmitter gives the caller no value to await, and because one path emits synchronously, you cannot "call then subscribe" — the event has already fired and been lost by the time you attach the listener.

## Lesson

When a method returns `void` but reports its result via an EventEmitter event, and any branch can emit that event synchronously, the caller MUST attach the listener BEFORE invoking the method, then await a promise that the listener settles. See `spawnTerminalAndAwaitResult` (`errorHandlers.ts:358`): `ptyClient.on("spawn-result", onSpawnResult)` is wired first (comment at line 411 marks why), `spawn()` is called inside `try/catch` afterward, and the listener filters on `eventId === id` so concurrent spawns don't cross-settle. Carry `result.error.code` onto the thrown `Error` (`error.code = result.error.code`) so the retry classifier (`isTransientError`) sees `PENDING_SPAWNS_CAPPED` as non-transient and skips the backoff loop instead of retry-storming a wedged host. Always pair the listener with a timeout (`TERMINAL_RETRY_SPAWN_TIMEOUT_MS`, 30s) and `AbortSignal` wiring so a host that never answers can't leak the listener forever — a `settled` guard + `cleanup()` removes the listener, clears the timer, and detaches the abort handler on every exit path.

## Applies when

You are awaiting the result of a `void` IPC/host method that emits its outcome on an EventEmitter (`PtyClient` spawn/kill, any utility-process round-trip with a synchronous cap/guard rejection), or you see a retry/recovery path treat a fire-and-forget `spawn()`/`send()` as success without observing the result event.
