## Context

`ProcessMemoryMonitor` and `ResourceProfileService` both poll `app.getAppMetrics()` (main-process aggregate API, returns `Electron.ProcessMetric[]`) to size per-process memory pressure and pick a resource profile. Both read memory via `(proc.memory.privateBytes ?? proc.memory.workingSetSize) / 1024`. They also used fixed-MB ceilings (Browser 300 / Tab 768 / Utility 500) that don't track device RAM.

## Problem

On macOS and Linux — two of the three platforms — the monitor was effectively reading a memory footprint of **zero** for every process. No per-process threshold could ever trip, and `ResourceProfileService` never escalated to the efficiency profile on memory pressure. The fallback `?? workingSetSize` looked correct in review and passed tests that supplied a populated `privateBytes`.

## Root cause

`Electron.ProcessMetric.memory.privateBytes` (the shape returned by `app.getAppMetrics()`) is **Windows-only**. On macOS/Linux the field is present but reported as `0`, not `undefined`. `0` is a valid number, so the nullish-coalescing `privateBytes ?? workingSetSize` resolves to `0` and the `workingSetSize` branch is never reached — the fallback silently no-ops on 2 of 3 platforms.

This is distinct from (and the inverse of) lesson #3360, which says "use privateBytes not workingSetSize on macOS." That lesson is about a **different API**: `process.getProcessMemoryInfo()`, called from within each process, where `privateBytes` IS populated cross-platform and is the more honest signal (uncompressed resident). The two lessons are not contradictory — **which Electron memory API you call determines whether `privateBytes` is real.** The aggregate `app.getAppMetrics()` shape only fills `privateBytes` on Windows; the per-process `getProcessMemoryInfo()` shape fills it everywhere.

Fix: read `proc.memory.workingSetSize` unconditionally in both services (the only field `app.getAppMetrics()` guarantees on all three platforms). Thresholds were also reworked from fixed MB to fractions of `os.totalmem()` (e.g. `300/8192`, calibrated to reproduce the legacy value on an 8 GB baseline), plus an aggregate working-set check at 25% of RAM and a system-wide floor via `process.getSystemMemoryInfo()` (free + purgeable on macOS) at 10%.

## Lesson

- When consuming `app.getAppMetrics()`, treat `proc.memory.privateBytes` as Windows-only and use `workingSetSize` for any cross-platform comparison. Do not write `privateBytes ?? workingSetSize` against this API — the `??` never fires off Windows because the field is `0`, not `undefined`.
- Nullish-coalescing is the wrong guard for a field that reports `0` to mean "unavailable." `??` only catches `null`/`undefined`; a hard zero passes straight through. When an API uses `0` as an absent-sentinel, branch explicitly or pick the universally-populated field.
- Don't conflate Electron's two memory surfaces: `getProcessMemoryInfo()` (per-process, `privateBytes` populated everywhere — lesson #3360) vs `app.getAppMetrics()` (aggregate `ProcessMetric`, `privateBytes` Windows-only). The right field depends on the API, not just the platform.
- Memory thresholds that gate behavior should scale with `os.totalmem()` (fractions), not fixed MB — fixed ceilings are too tight on small machines and too loose on large ones. `os.totalmem()` is stable for the process lifetime; read it once at monitor start (mirrors `ResourceProfileService`'s constructor pattern, keeps `vi.spyOn(os, "totalmem")` tests deterministic).
- A test that supplies a populated `privateBytes` will not catch this — add a regression case using the real macOS/Linux shape (`privateBytes: 0`, populated `workingSetSize`) to lock the metric.

## Applies when

- Reading or comparing memory from `app.getAppMetrics()` / `Electron.ProcessMetric.memory` in main-process services (`ProcessMemoryMonitor`, `ResourceProfileService`, `ProjectViewManager` memory floors).
- Adding any `privateBytes` / `workingSetSize` threshold, leak-trend, or resource-profile-escalation logic in `electron/services/`.
- Writing `x ?? y` (or `x || y`) against a numeric API field where the "unavailable" sentinel is `0` rather than `null`/`undefined` — Electron memory metrics, CPU metrics, and similar OS-bridged numbers.
- Cross-platform memory bugs where pressure mitigation, hibernation, or efficiency-profile selection never fires on macOS/Linux but works on Windows (or vice versa).
- Deciding between `process.getProcessMemoryInfo()` and `app.getAppMetrics()` — recall that field population (especially `privateBytes`) differs between the two.
- Writing tests for `app.getAppMetrics()` consumers: mock the platform-accurate `privateBytes: 0` shape, and `vi.spyOn(os, "totalmem")` to pin RAM so RAM-scaled thresholds are deterministic across CI hosts.
