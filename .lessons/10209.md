## Context

Each project view is its own `WebContentsView` + V8 context under `ProjectViewManager`. Renderer persistence is debounced: panel/tab-group layout writes sit behind a 500ms trailing debounce in `src/store/persistence/panelPersistence.ts`, and the terminal MRU list behind a `debouncedPersistMruList` in `src/store/rendererStoreOrchestrator.ts` (150ms at the time of this PR, later lengthened to 1s by `5bc494969`). To avoid stranding the last write on teardown, `src/store/listeners/panel/resource.ts` registered a `beforeunload` handler that called `flushPanelPersistence()`. This PR (resolves #9914) swapped that handler — and added a missing MRU flush — over to `visibilitychange`.

## Problem

A user changes the panel layout (close a panel, move a tab) and then switches projects, closes the window, or quits — and on next launch the layout is wrong: the last action vanished. The symptom is intermittent (only lands if you quit inside the 150ms/500ms debounce window) and pointed the wrong way: the `beforeunload` flush _looked_ present and correct, and the code works fine in a plain browser window, so it was easy to assume the persistence layer was at fault rather than the teardown hook.

## Root cause

`beforeunload` **does not fire when a `WebContentsView` is detached** in Electron 41/42 (Chromium 148). Only LRU eviction routes a view through the graceful `webContents.close()` path; a project switch or a window close tears the view down without ever dispatching `beforeunload`, and the main process sends no pre-teardown flush request to views. So the handler that was supposed to save-on-exit simply never ran on the three paths that matter (switch, close, quit). The MRU debounce was worse — it had _no_ teardown flush on any signal at all.

The reliable signal is `visibilitychange`: when the view detaches, `document.hidden` flips to `true` **while the renderer is still alive and its IPC channels are still open**, so an async flush initiated there completes before the view is destroyed. The fix registers a `visibilitychange` listener that flushes when `document.hidden` becomes true, in _both_ `resource.ts` (sync `flushPanelPersistence()`) and `rendererStoreOrchestrator.ts` (async `void debouncedPersistMruList.flush()`), and each also **flushes immediately if `document.hidden` is already true at registration** — a fast switch can hide the doc between render and the effect, so without that guard the event is missed. This is the shape already codified in `src/hooks/useFlushOnHide.ts` and consumed by `SettingsDialog`; #10209 brought the odd-one-out panel path in line, and `beforeunload` now survives in the renderer only in comments explaining why it isn't used.

## Lesson

- **In the renderer, `beforeunload` is never a reliable teardown/flush hook — `WebContentsView` detach (project switch, window close, app quit) does not fire it in Electron 41/42 (Chromium 148).** Any save-on-exit wired to `beforeunload` is silently dead on exactly the paths users hit; use `document.addEventListener("visibilitychange", …)` gated on `document.hidden === true` instead. Grep for `beforeunload` in `src/` — a live one is a bug.
- **Always pair the `visibilitychange` listener with a flush-if-already-hidden check at registration.** A fast switch can hide the document between render and effect, so `if (document.hidden) flush()` right after `addEventListener` is load-bearing, not defensive padding — both `useFlushOnHide` and the two paths in #10209 include it.
- **Pick the teardown hook by whether the flush is sync or async.** `visibilitychange` fires early (view alive, IPC open) so async IPC flushes like `persistMruList` complete; `pagehide` fires in the late teardown window and only survives _synchronous_ work — that's why `src/services/terminal/optimisticPanelClose.ts` rides `pagehide` for its sync close-intent flush but the MRU debounce could not. Don't hang an async IPC flush off `pagehide`.
- **A debounced renderer write needs an explicit teardown flush hook, and its absence is invisible until someone quits mid-window.** `debouncedPersistMruList` (150ms at the time of this PR, now 1s) and `panelPersistence` (500ms) both persist last-write-wins state; audit every trailing-debounce persistence path for a `visibilitychange` flush, because the loss window is short enough to pass all manual testing.
- **The main process does not flush renderer views before closing them.** Don't assume window-close or quit gives views a chance to save via a main-side request — the renderer must self-flush on `visibilitychange`; only LRU eviction uses the graceful `webContents.close()` path.

## Applies when

- Wiring any save-on-exit / flush-on-teardown in the renderer, or reviewing one that uses `beforeunload` — in this multi-`WebContentsView` architecture it will not fire on detach.
- Diagnosing "my last layout/setting/MRU change was lost after switching projects, closing the window, or quitting" — suspect a debounced write with no `visibilitychange` flush.
- Adding a trailing-debounce persistence path (panel layout, MRU, settings) and deciding how to guarantee the final write survives teardown.
- Choosing between `visibilitychange` and `pagehide` for a flush — async IPC must use `visibilitychange`; only synchronous work is safe on `pagehide`.
- Touching `src/store/listeners/panel/resource.ts`, `src/store/rendererStoreOrchestrator.ts`, `useFlushOnHide`, or `optimisticPanelClose.ts`, or any `ProjectViewManager` view-swap teardown path.
