## Context

MCP help-sessions run agent tool calls gated by a tier model (`workbench`/`action`/`system`) checked in `sessionServer.ts` via `isTierPermitted`. When an agent calls a tool above the session's static tier, the renderer shows an approval banner. The "Approve once" flow used to call `setSessionTier`, permanently elevating the entire session.

## Problem

A single "Approve once" elevated the whole session for its remaining lifetime — one approval, unlimited blast radius across every other tool at or below that tier, until the session ended. This is the Azure-PIM standing-elevation / request-fatigue anti-pattern: users click approve once and silently grant far more than they intended.

## Root cause

Per-tool intent ("let this one tool run now") was being expressed through a session-wide, durable mechanism (`sessionTierMap` mutation). Approval scope (one tool) and approval persistence (session lifetime) were conflated into a single coarse lever. The fix introduces `GrantCache` (`electron/services/mcp-server/grantCache.ts`): a `Map` keyed by `${sessionId}:${toolId}` holding `{issuedAt, expiresAt, ttlMs}` entries with a 15-min sliding TTL (`MCP_GRANT_TTL_MS`) and a hard 30-min wall-clock ceiling (`MCP_GRANT_MAX_LIFETIME_MS`, added in #9161 so a busy grant can't slide forever). Three subtle constraints make it safe:

1. **Additive layer, not a replacement.** `sessionServer.ts` only consults the grant cache _after_ `isTierPermitted` denies — the static `TIER_ALLOWLISTS` floor is never bypassed. A session whose static tier already permits the action never reads the cache.
2. **Race-guard token on refresh.** `check()` returns the entry's `issuedAt`; the post-dispatch `refresh(sessionId, toolId, issuedAt)` no-ops if the stored `issuedAt` no longer matches. Without this, a grant revoked-and-reissued between `check()` and dispatch completion would have its TTL wrongly extended — a winning revoke silently undone by an in-flight authorized dispatch (the security-relevant cousin of the cache-resurrection race in #2243).
3. **Idle-reaper truncation.** A successful grant dispatch must call `sessionStore.resetIdleTimer(sessionId)` alongside `refresh()`. Otherwise a 30-min idle reaper that armed before the 15-min grant could kill the session mid-grant.

The "Always allow" path still calls `setSessionTier` intentionally — that is a deliberate standing permission paired with a project-level `daintreeMcpTier` write, not the per-tool flow.

## Lesson

- Separate approval _scope_ from approval _persistence_. A "do this once" affordance must mint a narrowly-keyed, time-bounded grant — never flip a session/global capability bit. Only an explicit "always" path may write standing permission.
- Make grants an **additive fallback** behind the static authorization floor, checked only on denial, so the floor can never be widened by a grant bug.
- Any check-then-act authorization where the grant can be revoked concurrently needs a race-guard: stash an identity token (`issuedAt`) at check time and verify it before the act/refresh writes back. A stale token must no-op, so a winning revoke is never resurrected by an in-flight dispatch that started before it.
- A sliding TTL needs a hard wall-clock ceiling measured from immutable `issuedAt`, or a frequently-used grant lives forever.
- When a grant's lifetime overlaps an idle/GC reaper on the same entity, the use-path must reset the reaper, or the reaper truncates the grant.

## Applies when

- Adding or reviewing any "Approve once" / "Allow this time" / elevation affordance in the MCP server (`electron/services/mcp-server/`), the help-session flow, or `HelpSessionController.approveTierOnce`.
- Touching `GrantCache`, `sessionServer.ts` tier checks, `setSessionTier`, `isTierPermitted`, `TIER_ALLOWLISTS`, or grant lifecycle IPC (`MCP_SERVER_ISSUE_GRANT`, `MCP_SERVER_REVOKE_SESSION_GRANTS`, `MCP_GRANT_LIFECYCLE`).
- Designing any capability grant with a TTL, sliding refresh, or revoke path — symptoms like "one approval granted access to everything", "TTL extended after a revoke", or a grant outliving/being truncated by an idle reaper.
- Any check-then-act security path where the authorizing entry can be invalidated between the check and the action completing.
