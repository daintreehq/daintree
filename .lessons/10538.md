## Context

`@daintreehq/plugin-vite` (`packages/plugin-vite/src/index.ts`) is the Vite preset plugin authors build `.dntr` plugins with; it externalizes React so the host import map (injected by `vite.config.ts`) resolves every plugin's `react` import to Daintree's single `vendor-react` instance. `PluginArchive.ts` packs/verifies the `.dntr` zip. #10538 (fixing #10514) repaired four failures found by building a working stdio MCP server and a React panel through the documented path.

## Problem

All four failures were invisible at plugin BUILD time and only surfaced when the plugin ran inside the app or was distributed: a plugin importing `react-dom/server` built clean then threw an unresolved-bare-specifier error at load; a scaffolded stdio MCP server built with exit 0 (only a missable externalization warning) then crashed on first connect with `process.stdin === undefined`; a sideloaded panel mounted in production but failed under `npm run dev`; and a packaged `.dntr` silently shipped the author's `package.json`/`package-lock.json` (leaking their absolute home path in a `file:` layout), with a crafted `./package.json` entry able to slip past the exclusion filter.

## Root cause

All four are coupling points between the plugin bundler and the host that only bind at plugin runtime or distribution, so nothing in the plugin's own build catches them. (1) `reactExternals` (`/^react($|\/)/`, `/^react-dom($|\/)/`) is deliberately broader than the host import map, which serves exactly five specifiers (`react`, `react/jsx-runtime`, `react/jsx-dev-runtime`, `react-dom`, `react-dom/client`); a subpath in the gap (`react-dom/server`) externalizes fine but has no map entry, dying at load as an unresolved bare specifier — and the two lists, hand-synced across two files, drifted. (2) `vite build` runs one config per pass, and the scaffold routed the node `server.ts` entry through the browser config where `node:process` is browser-shimmed to an empty module. (3) The production import map points each specifier at the hashed `vendor-react` chunk, which doesn't exist under `npm run dev`. (4) `normalizePath` stripped a leading `/` but not `./`, and `isExcludedRootDevFile` only matches root-level names (no `/`), so `./package.json` dodged the dev-file guard and shipped.

## Lesson

- **A regex external set broader than the import map is only safe with a build-time guard closing the gap.** `HOST_IMPORTMAP_SPECIFIERS` is now one exported constant in `packages/plugin-vite/src/index.ts` that `vite.config.ts` imports from source to build the `<script type="importmap">`, plus a `resolveId` hook that `throw`s on any `isReactSpecifier(id) && !isHostMappedSpecifier(id)`. Keep the broad regex (it stops `react/jsx-runtime` bundling a second React → `Invalid hook call`); the guard makes the breadth safe. Never re-hand-sync the two lists — a test asserts every specifier is matched by `reactExternals` and that `react-dom/server` externalizes but is absent from the list.
- **A `node` plugin target must externalize Node built-ins (bare AND `node:`-prefixed) and drop the `browser` resolve condition — a browser build shims them to empty modules and stdio servers crash.** `daintreePlugin({ target: "node" })` externalizes `[...builtinModules, ...builtinModules.map(m => "node:"+m)]`, sets `conditions: ["node","module","import","default"]` / `target: "node18"`, and does NOT externalize React or attach the guard. Since one `vite build` runs one config, the scaffold ships a separate `vite.config.server.ts` (`emptyOutDir: false` so it keeps the browser pass) chained as `vite build && vite build --config vite.config.server.ts`.
- **A dev import map can't reuse the production one — the prod `vendor-react` chunk doesn't exist under `npm run dev`.** `hostImportMapDevPlugin` (serve-only) maps each specifier to a stable `virtual:daintree-host-react/<spec>` module at `/@id/...` re-exporting host React (`export *` + a computed `export default m.default ?? m` so subpaths like jsx-runtime with no own default don't throw); Vite resolves the virtual import server-side, landing on the one host React instance. Don't point it at the optimized-dep URL — that hash isn't static.
- **Any archive exclusion/traversal filter must normalize the path FIRST (strip both `/` and `./`) or a cosmetic prefix bypasses it.** Stripping leading `./` makes `./package.json` collapse to `package.json` and hit `isExcludedRootDevFile`; exclusions scope to root only (`name.includes("/") → false`) so a legit `dist/app.config.json` survives; packer and CLI `verify`/`isExcludedArchiveEntry` share one predicate so packed and rejected sets can't diverge. `package.json`/lockfiles are excluded because they leak the author's home path, not merely for bloat.

## Applies when

- Changing which React (or host-provided) subpaths plugins may import — edit `HOST_IMPORTMAP_SPECIFIERS` in `packages/plugin-vite/src/index.ts` only; `vite.config.ts` and the guard follow it.
- Diagnosing a shipped plugin that builds clean but fails at load with an unresolved bare specifier or `Invalid hook call`, or a panel that mounts in prod but not under `npm run dev`.
- Building/scaffolding a plugin with a stdio MCP server or any Node entry, or debugging `process.stdin === undefined` / `Cannot read properties of undefined (reading 'on')` from a plugin server.
- Touching `.dntr` packing, `normalizePath`, `isExcludedRootDevFile`, `isExcludedArchiveEntry`, or `REQUIRED_EXCLUSIONS` in `electron/services/PluginArchive.ts` — verify `./`-prefixed/crafted paths normalize before the exclusion/traversal check and that packer and verifier share the predicate.
- Reviewing any two-file "keep these in lockstep" contract — demand one shared constant plus a subset/equality test, not a hand-synced pair of lists.
