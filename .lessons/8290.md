## Context

`ProjectSettings` (run commands, env vars, resource environments, MCP tier, etc.) persists to a per-project `settings.json`. PR #8290 centralized all shape, version, and migration logic into `electron/services/projectSettingsCodec.ts` as the single authority; `ProjectSettingsManager` reads/writes through it, and `project:save-settings` IPC writes flow through `ProjectSettingsSaveSchema`. Before this, parsing/migration was scattered across `projectSettingsParsers.ts`, `ProjectSettingsManager`, `useProjectSettingsForm`, and `WorktreeLifecycleService`.

## Problem

Two latent data-integrity hazards in the old shape:

- The natural failure mode for a persisted-config reader is `try { JSON.parse(...) } catch { return defaults }`. A transient corruption (partial write, manual edit, disk glitch) silently replaces the user's real settings with empty defaults — and the next save overwrites the original on disk, destroying it permanently with zero user signal.
- An older build reading a file written by a newer build (downgrade / mixed-version cohort) would partially parse the unknown shape, drop fields it doesn't understand, and re-save a lossy version. There was also no defense against a renderer injecting a fake version key.

## Root cause

A parse-error → silent-default path conflates "I couldn't read this" with "the user has no settings." Recovery requires distinguishing the two and refusing to overwrite. The codec encodes this:

- `decode(raw): ProjectSettingsDecodeResult` is **total — it never throws** (`projectSettingsCodec.ts:304`). Corruption surfaces as a return value (`{ ok: false, reason: "future-version", onDiskVersion }`), so the caller can react rather than crash into a catch block. `JSON.parse` failure is caught separately in `ProjectSettingsManager` and treated as corruption.
- A `_schemaVersion: 1` envelope (`encodeEnvelope`, line 429) is stamped on every write. On read, `rawVersion > PROJECT_SETTINGS_SCHEMA_VERSION` returns `ok:false` so the file is quarantined, never re-saved lossily (`decode` line 315-320). Absent `_schemaVersion` is treated as legacy v0 and migrated.
- On `ok:false` or `SyntaxError`, `ProjectSettingsManager` renames the file to `.corrupted.<ts>` / `.future-v<n>` (best-effort, never clobbers a prior artifact via `existsSync` timestamp tail) and broadcasts `NOTIFICATION_SHOW_TOAST` so the user knows defaults are temporary, not authoritative.
- Renderer-supplied `_schemaVersion` is a spoof vector — a renderer could set `_schemaVersion: 999` to make the file self-quarantine on next load. Closed defense-in-depth: `ProjectSettingsSaveSchema` uses `.passthrough()` (forward-compat) but `.refine()`-rejects any payload carrying `_schemaVersion` (line 505), and `encodeEnvelope` also `delete`s it before write (line 443) so the codec's version always wins.

## Lesson

When reading any persisted user data that can be corrupt, future-versioned, or hand-edited:

- Make the decoder a **total function returning a result type**, not one that throws — `try/parse/catch→defaults` silently destroys data on the next save. Distinguish "unreadable" from "empty."
- On unreadable/future-version input: **quarantine the original file (rename, don't delete) and notify the user**; only then fall back to defaults at runtime. Never let the recovery path re-save over the original.
- Stamp a **`_schemaVersion` envelope** on write and reject future versions on read so an older build can't lossily rewrite a newer file. Treat a missing version as the earliest legacy version and migrate forward.
- Keep schema + envelope + migrations in **one codec module** that is pure (no I/O) so it's property-testable (`fc.anything()` never-throws, round-trip stability, migration idempotence); push SVG sanitization / secure-env resolution into the I/O layer.
- Treat the persisted version key as **reserved**: reject it at the IPC gate (`.refine()`) AND strip it at the encoder. A renderer-supplied version is untrusted and can trigger self-quarantine.

## Applies when

- Adding or changing the schema/migrations for `ProjectSettings`, `settings.json`, recipes, or any per-project/per-app persisted config under `electron/services/`.
- Writing a reader for any JSON/SQLite/config file that users can hand-edit or that survives across app versions (downgrade, mixed-version sync, in-repo settings).
- You see a `try { JSON.parse } catch { return defaults }` (or equivalent) pattern guarding persisted user data — flag it as silent data-loss risk.
- Gating an IPC write handler with a Zod schema (`typedHandleValidated`) where the payload could contain reserved/server-owned fields (version stamps, ids, timestamps) the renderer must not control.
- Adding a new `ProjectSettings` field: it must be wired through `projectSettingsCodec.ts` `decode`/`encodeEnvelope` and `ProjectSettingsSaveSchema`, not parsed ad hoc in a component or service.
- Implementing forward/backward compatibility for any versioned on-disk format, or deciding what to do when a file is "too new."
