## Context

The destructive-action safeguards (#7880 tiers) split enforcement across two layers the registry can't reconcile alone: `danger:"confirm"` gates only the agent/MCP dispatch source at runtime (`ActionService.ts`), while user-initiated dispatch is gated by `ConfirmDialog`s wired at individual call sites. `actionDefinitions.quality.test.ts` was supposed to hold the two sides together: assert every dangerous action has a `dangerRationale` and every `danger:"confirm"` action has an identified confirm call site.

## Problem

Both "enforcement" gates enforced nothing. The `dangerRationale` check only `console.warn`ed offenders with a `TODO(#8431): Promote to hard assert once...`, and the confirm-wiring reverse-coverage check was literally `expect(true).toBe(true)` with a `TODO(#8415)`, backed by a hand-maintained `CONFIRMED_WIRED` allowlist containing exactly two entries. CI stayed green through every unrationalized action and every unwired confirm. The kicker: #8431 and #8415 were both created AND closed on 2026-05-19 — the partial work that landed closed them same-day — so the promotion TODOs pointed at dead issues from the start and nothing would ever drive the flip. #9567 flagged both; #9578 hardened them on 2026-06-01.

## Root cause

The warn-then-promote pattern has no forcing function. Warnings live in CI logs nobody reads; an assertion-free test is indistinguishable from a passing one in every dashboard; and "promote once the backlog is clean" is blocked on cleanup nobody owns. Closing the tracking issue (which happens whenever partial work merges) orphans the TODO permanently. The original stub also rationalized itself: the in-code comment said a source grep for confirm wiring is "brittle against aliased imports and refactors" — treating imperfect enforcement as justification for none. Proof the rot is indefinite, not transitional: the description-length check in the same file is STILL assertion-free today (it only `console.warn`s, carries the same dead `TODO(#8431)`), two months after #8431 closed.

#9578's fix shape is the transferable part. Instead of auditing toward a future flip, it made the classification exhaustive immediately: every `EXPECTED_CONFIRM_DANGER` action must be in `CONFIRMED_WIRED` (a ConfirmDialog-family token and the quoted action ID co-located in one source file) or `BYPASS_WIRED` (per-row comment naming the actual mechanism — deferred-promise store, direct-IPC bypass, agent-dispatch-only), all hard-asserted by set algebra in vitest. The dynamic side — do the listed call sites still exist in source? — went into `scripts/codegen/confirm-wiring.mjs`, wired into `npm run check` alongside `check:ipc`/`check:help`. The contract held: both lists have since absorbed ~15 additions (forge._ writes, `logs.clear`, `artifact.applyPatch`) and the `git.snapshot_` removals in sync.

## Lesson

- **Never land a warn-only or `expect(true)` gate "to be promoted later"** — the promotion never happens once the tracking issue closes, which is typically the same day. Land the hard assert now; put current offenders in an explicit, per-row-documented allowlist (or backfill them — #9578's rationale backfill was a single PR's work).
- **Exhaustive two-list classification with a documented escape hatch beats deferred perfection.** `EXPECTED_CONFIRM_DANGER ⊆ CONFIRMED_WIRED ∪ BYPASS_WIRED` is hard-assertable today; every `BYPASS_WIRED` row names its real confirm mechanism and doc pointer, so the exemption is auditable instead of invisible.
- **`confirm-wiring.mjs` is a token co-location scan, not the dataflow audit the PR body claims.** It checks a file's text contains a `CONFIRM_TOKENS` member AND `"<actionId>"` — ts-morph only enumerates files (tests/`.d.ts` excluded). It proves the call site still exists, not that a modal actually gates the path. Don't extend it expecting aliased-import resolution.
- **New bespoke confirm-dialog components must join `CONFIRM_TOKENS`** (`ConfirmDialog`, `WorktreeDeleteDialog`, `GitPushConfirmDialog`, ...) or their actions false-fail the scan. When `check:confirm-wiring` fails, the WRONG fix is dumping the action into `BYPASS_WIRED` to silence it — that permanently exempts it from the existence check.
- **The three lists are mirrored by hand in two files** (`actionDefinitions.quality.test.ts` + `confirm-wiring.mjs`, "keep in sync" comments). Update both: a stale script-side mirror silently narrows the audit — its `unaccounted` check can't flag actions it doesn't know about.
- **Whole-source-tree invariants belong in a check-pipeline script, not vitest or ESLint.** Vitest keeps the registry-level set algebra and the runtime proof (agent dispatch of every `EXPECTED_CONFIRM_DANGER` action rejects without `confirmed:true`); cross-file existence scanning follows the `check:ipc`/`check:help` standalone-script pattern in `npm run check`.

## Applies when

- Adding or reclassifying a `danger:"confirm"` action — you must add it to `EXPECTED_CONFIRM_DANGER` in BOTH files plus `CONFIRMED_WIRED` or `BYPASS_WIRED`, and flip the audit row in `docs/architecture/destructive-action-safeguards.md`.
- `npm run check:confirm-wiring` fails — decide between restoring the co-located dialog, extending `CONFIRM_TOKENS`, or a genuinely documented bypass; never bypass-to-silence.
- Writing any quality/reconciliation gate and tempted to `console.warn` + `TODO(#issue)` instead of asserting — the description-length check in this same file shows that shape never graduates.
- Reviewing a test whose body can never fail (`expect(true).toBe(true)`, warn-only loops, no assertions) — treat it as a missing gate, not partial coverage.
- Introducing a new confirm-dialog component or renaming an existing one in `src/components/` — grep `CONFIRM_TOKENS` first.
