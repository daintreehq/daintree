## Context

`bootstrap.ts` runs `runBootMigrations()` before `await import("./main.js")`, and `main.ts` is where `initializeCrashLoopGuard()` is called (`electron/main.ts:175`). Boot migrations are forward-only one-shots that run before `app.whenReady()`; a deterministically-crashing migration must NOT retry on every boot, so `BootMigrationRunner` accepts an `isSafeMode` flag and short-circuits the whole run when set (`BootMigrationRunner.run()`, returns `skippedForSafeMode: true`).

## Problem

The safe-mode predicate was needed during the bootstrap phase, but the only reader was the stateful `CrashLoopGuardService.isSafeMode()` getter, which returns a meaningful value only AFTER `initialize()` runs — and that happens later, inside `main.ts`. A crashy migration could therefore brick installs because the gate it was supposed to honor wasn't computed yet at the point it ran (the original `bootstrap.ts` TODO called this out).

## Root cause

`CrashLoopGuardService.isSafeMode()` reads an in-memory `safeMode` field that is only populated by `initialize()`. The obvious fix — call `initializeCrashLoopGuard()` early in `bootstrap.ts` — is actively wrong: `initialize()` is a MUTATING side-effect on the sentinel, not a read. It appends the current launch timestamp to `launches`, flips `cleanExit = false`, and persists via `resilientAtomicWriteFileSync` (`CrashLoopGuardService.ts:102-114`). Running it twice (bootstrap + main) would record two launches per boot, corrupting the sliding-window crash count that safe-mode itself depends on.

## Lesson

When a persisted-sentinel-derived predicate is needed earlier in startup than the service that owns it, expose a stateless, side-effect-free reader that recomputes the predicate directly from the on-disk sentinel — don't move the stateful initializer earlier.

`isSafeModeActive(userDataPath?)` (`CrashLoopGuardService.ts:325`) is that reader: it `existsSync`/`readFileSync`/`JSON.parse`-es `crash-loop-state.json`, applies the SAME structural validation and `CRASH_WINDOW_MS` sliding-window threshold as `initialize()`, and returns a boolean WITHOUT writing anything. `bootstrap.ts:30` calls `runBootMigrations({ isSafeMode: isSafeModeActive() })`; `main.ts:175` still calls the mutating `initializeCrashLoopGuard()` later as the single state-advancing entry point. Two readers, one writer.

Sync `fs` + `app.getPath("userData")` before `app.whenReady()` is documented-safe (and required here — there is no async IO window yet); the file carries an `eager-import-allow` annotation for this reason.

Because the read-only reader and the stateful initializer duplicate the same threshold logic, they MUST stay in lockstep — both gate on `version === 1`, `cleanExit`, and `recentLaunches.length >= CRASH_THRESHOLD` over `CRASH_WINDOW_MS`. The same PR also made `initialize()` idempotent (`this.initialized` guard, `CrashLoopGuardService.ts:75-77`) so an accidental second call can't double-append a launch.

## Applies when

- A startup-ordering gate (boot migration, pre-`whenReady` decision) needs safe-mode / crash-loop state that the owning service computes only inside its `initialize()`.
- Tempted to call `initializeCrashLoopGuard()` / any state-advancing `initialize()` earlier to "make the flag available" — check whether that method mutates a persisted counter first.
- Adding a new consumer of `crash-loop-state.json`: use `isSafeModeActive()` for read-only checks, never instantiate a second `CrashLoopGuardService`.
- Editing either `isSafeModeActive()` or `initialize()`'s threshold/validation logic — change both or the two readers diverge.
