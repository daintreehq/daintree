## Context

`ProjectRoutingPanel` in `src/components/Settings/ForgeIntegrationsTab.tsx` shows the active project's git remotes and which forge provider plugin each routes to. Two house patterns meet here: the 400ms Doherty gate (`showRemotesLoading = useDohertyGate(remotesLoading)` — nothing shows for sub-400ms work) and name-the-next-action empty states ("{project} has no git remotes configured"). The remotes load effect resets `remotes` to `[]` and sets `remotesLoading` true on every mount and project switch.

## Problem

Every time the settings tab opened or the active project switched, the panel flashed the false claim "has no git remotes configured" before the real list appeared (#9990). Separately, when remotes existed but zero forge plugins were installed, an early return rendered only a note describing "No match" badges — while preventing the remotes list carrying those `RoutingBadge`s from rendering at all. The flash was easy to misread as an IPC data race; it was deterministic, by construction, on every load.

## Root cause

The panel branched on the gated flag: `if (loading) → "Loading remotes…"` then `if (remotes.length === 0) → empty state`. But `loading` was the Doherty-gated `showRemotesLoading`, which by design stays `false` for the first 400ms of any load. So during that window the observable state was: load in flight, `remotes === []` (the effect resets it at start), gated flag false — control fell straight through to the empty branch. The gate exists to suppress an indicator for fast work; behind it, "still loading" and "loaded and genuinely empty" are indistinguishable to any consumer of the gated flag. Using it for state discrimination bakes a 400ms false-empty window into every load.

A second, subtler layer: even the raw `remotesLoading` state flag is insufficient on identity switches, because effects commit after render. On the frame where `activeProjectId` has changed but the load effect hasn't run yet, `remotesLoading` is still false and `remotes` still reflects the previous project. The fix stamps `remotesLoadedForRef.current = activeProjectId` inside the load effect, so at render time `remotesLoadedForRef.current !== activeProjectId` marks that pre-effect frame. Combined: `remotesPending = remotesLoading || (activeProjectId != null && remotesLoadedForRef.current !== activeProjectId)`. The panel then renders nothing during the window — `if (pending && !loading && remotes.length === 0) return null;` — scoped to the empty case so an in-place refetch never blanks a resolved list, handing over to the loading text once the gate fires. The zero-providers early return was removed: the list always renders with its "No match" badges, and the no-plugins note moved inline, gated on `!providersLoading` so it never asserts "no plugins installed" before the provider list resolves. All of this is intact on current develop.

## Lesson

- **A Doherty/skeleton-gated flag gates the display of an indicator, never branch structure.** Any `if (gatedLoading) … else if (data.length === 0) → empty state` chain has a built-in 400ms false-empty window on every load. Keep two signals: a raw pending flag (state truth, drives which branch renders) and the gated flag (display truth, drives whether the indicator paints).
- **The correct sub-400ms render is nothing — and "nothing" includes the empty state.** The Doherty rule suppresses ALL feedback under 400ms, not just spinners; empty-state copy is a positive claim about the data and must wait for the load to complete. Implementation shape: `if (pending && !loading && data.length === 0) return null`.
- **A raw `isLoading` state flag still leaks one render frame on identity switches**, because the effect that sets it commits post-render. Record which identity the current state reflects in a ref stamped inside the effect (`remotesLoadedForRef.current !== activeProjectId` ⇒ pending) — that closes the mount frame and every project-switch frame.
- **Scope the render-nothing suppression to the empty case** (`remotes.length === 0` in the guard) so a refetch over already-resolved data keeps painting the old list instead of blanking it for the in-flight window.
- **Never assert absence from a list whose load is still in flight.** The "No forge plugins are installed" note gates on `!providersLoading`; any "no X configured/installed" copy needs its backing load to have actually completed, not merely its gated flag to be false.
- **Degraded-state copy must describe UI that actually renders.** The old zero-providers early return promised "each remote shows as unmatched" while suppressing the remotes list and its `RoutingBadge`. If copy references rows/badges, render them alongside it.

## Applies when

- Wiring `useDohertyGate` / `useDeferredLoading` / `useSkeletonGate` (≈35 consumer files under `src/`) into any component that also has an empty-state branch — verify the gated flag isn't the only thing standing between reset data and the empty copy.
- Diagnosing a flash of "no X configured/found" (or any empty state) on mount, tab open, or project switch that resolves to real content within ~half a second — it's likely this deterministic gate window, not a race.
- Reviewing a load effect that resets its data array to `[]` at start — walk through what the render tree shows in the frames before the gated indicator fires, and in the pre-effect frame after an identity change.
- Branching on `data.length === 0` in a component whose `loading` prop is fed from a Doherty/skeleton gate rather than the raw state flag.
- Adding "no plugins/remotes/providers installed" copy in Settings tabs — gate the claim on the backing load's completion, and render the UI the copy describes.
