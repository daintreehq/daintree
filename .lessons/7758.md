## Context

Several renderer Zustand stores (`panelStore`, `projectStore`, `worktreeStore`, `fleetArmingStore`) need to read each other in narrow places — e.g. `projectStore.buildOutgoingState()` snapshots panel state during a project switch, and `worktreeStore.applyWorktreeTerminalPolicy()` reads the fleet-armed set to keep cross-worktree terminals visible while fleet scope is active. Direct top-level imports between any pair form an ESM cycle.

## Problem

The old fix scattered module-bottom setter-injection (`setPanelStoreGetter(...)` etc.) across four store files. Two failure classes leaked from it: (1) a TDZ crash on boot (`ReferenceError: Cannot access 'X' before initialization`) if evaluation order inverted; (2) silent stale-state — accessor closures and a module-scope `fleetArming` panel-prune subscription stayed bound to the _previous_ store singletons after a test `destroyStoreOrchestrator()` + re-init, producing cross-test contamination and a module-scope subscription that was never torn down.

## Root cause

The accessor closures and the prune subscription lived at module evaluation scope, which runs exactly once per V8 context. Test teardown/re-init creates fresh store state but never re-runs module bodies, so closures pointed at stale singletons. The fix (`src/store/storeAccessors.ts`) is a dependency-free leaf module holding mutable getter slots; stores import readers from it unidirectionally (no cycle). The critical ordering: `initStoreOrchestrator()` (`rendererStoreOrchestrator.ts:42-69`) registers every `setXxxAccessor(...)` closure **before** the `if (cleanupFn) return cleanupFn;` idempotency guard at line 69, while all `store.subscribe()` reactions are registered **after** it inside a `DisposableStore`. That asymmetry is deliberate: accessors must rebind on every re-init (cheap, idempotent, must track fresh singletons), but subscriptions must register once. `destroyStoreOrchestrator()` calls `resetStoreAccessorsForTesting()` to null the slots so a consume-between-destroy-and-init path sees the documented null fallback, not a stale closure. Closures always call `store.getState()` inside the body — never capture a snapshot at registration (the lesson #5087 stale-closure rule).

## Lesson

- Route any cross-store read with cycle risk through `src/store/storeAccessors.ts` — add a `setXxxAccessor`/`getXxx` slot pair there; do NOT re-introduce module-bottom `setXxxGetter(...)` injection on a store file.
- Register the accessor closure inside `initStoreOrchestrator()` **before** the `if (cleanupFn)` idempotency guard; register `store.subscribe()` reactions **after** it in the `DisposableStore`. Accessors rebind per-init; subscriptions register once.
- Always read state via `store.getState()` inside the closure body, never close over a snapshot at registration time.
- Consumers must tolerate a `null` return — the orchestrator hasn't run when a store is imported standalone in a unit test.
- Never add a module-scope `store.subscribe()` for a cross-store reaction; move it into the orchestrator's `DisposableStore` (mirrors lesson #4754) so HMR/test teardown disposes it deterministically.
- Tests stub the accessor reader (or call `setXxxAccessor` from `storeAccessors`) — the old `setPanelStoreGetter` exports on `projectStore`/`worktreeStore` are gone.

## Applies when

- Adding a new cross-store read/write between renderer Zustand stores (`panelStore`, `projectStore`, `worktreeStore`, `fleetArmingStore`) where a direct import would cycle.
- Touching `src/store/storeAccessors.ts`, `src/store/rendererStoreOrchestrator.ts`, or `initStoreOrchestrator()` / `destroyStoreOrchestrator()`.
- Seeing `ReferenceError: Cannot access 'X' before initialization` at renderer boot, or `buildOutgoingState()` returning incomplete panel/worktree data on project switch.
- Diagnosing cross-test contamination where one store test's state or subscription bleeds into the next after `destroyStoreOrchestrator()` + re-init.
- Adding a module-scope `store.subscribe()` for fleet-arming/panel-prune-style cross-store reactions — relocate it into the orchestrator instead.
- Working on fleet-arming, project-switch outgoing-state, or worktree-selection snapshot logic that reads another store.
