## Context

#10175 (issue #9993) routed the worktree attach-issue flow through the provider-neutral forge layer: `IssuePickerDialog` moved from `githubClient`/`GitHubIssue` to `forgeClient.listIssues` + normalized `Issue`. Because the picker depends on debounced free-text search, the GitHub provider had to actually honor `opts.search` (previously advisory-ignored) via `SEARCH_QUERY`. The forge list path has TWO independent single-flight layers: the main-process IPC handler's `coalesce(`${cwd}::listIssues::${listOptionsKey(opts)}`)` (`electron/ipc/handlers/forgeData.ts`) and the provider's `dedupe(listIssuesInflight, key)`. At merge the provider code lived in `forgeProvider.ts`; split `e7000bca2` later moved `searchIssuesImpl`/`listIssuesImpl` → `readOps.ts`, `forgeIssueListCache` → `GitHubCaches.ts`, `listIssuesInflight` → `queryInfra.ts`.

## Problem

Review caught that `listOptionsKey` enumerated `state`/`cursor`/`perPage`/`labels`/`assignee`/`sort`/`direction` but not `opts.search`. With search now a real query dimension, two debounced picker keystrokes overlapping in flight ("auth" then "auth bug", 300ms debounce + network latency window) would coalesce onto ONE in-flight promise: the second query silently receives the first query's items. Wrong results, no error, intermittent — the classic shape of a key-completeness bug.

## Root cause

Single-flight coalescing asserts "same key ⇒ same answer". Omitting a dimension the query varies on turns that into aliasing: distinct queries collapse into one slot and every later caller gets the first caller's payload. The subtle part is why the renderer's defenses are useless here: `IssuePickerDialog.fetchIssues` has a textbook latest-wins guard (`fetchIdRef`, `if (id !== fetchIdRef.current) return`), but the wrong payload arrives ON the latest request's own promise, so `id === fetchIdRef.current` passes and stale data is accepted as fresh. Client staleness guards defend against out-of-order responses, never server-side aliasing — the fix has to be at the key (`opts.search ?? null` added to the tuple; regression tests assert distinct terms get distinct slots).

The second invariant is cache read/write isolation. `searchIssuesImpl` results are typed-input ephemera: they use a `search:`-prefixed dedupe key in the shared `listIssuesInflight` map (the prefix guarantees no collision with list-path keys) and are NEVER written to `forgeIssueListCache` — background pollers read that cache as THE canonical unfiltered list, so a search page written under a list key would later be served as the repository issue list. Conversely `listIssuesImpl`/`listPRsImpl` deliberately keep `search` OUT of `buildListCacheKey` (a key should reflect exactly what its query varies on), and their comments pair the omission with the wiring instruction so a future wire-up changes query and key together. `listPRsImpl` still ignores `opts.search` today.

## Lesson

- **Every dimension a query varies on must appear in EVERY coalesce/cache key on the request path — and there are two independent layers.** The IPC single-flight (`listOptionsKey`) and the provider `dedupe(listIssuesInflight, …)` alias independently; fixing one leaves the other. When adding a `ListOptions` field or promoting an advisory field to honored, grep every key builder in the chain.
- **A renderer latest-wins guard cannot catch server-side aliasing.** `fetchIdRef` passes wrong data because it arrives on the newest request's own promise. Test at the coalescing layer instead (`Promise.all` two calls differing only in the suspect dimension, assert two impl invocations).
- **Typed-input ephemera never write the canonical cache.** Search responses stay out of `forgeIssueListCache` and use a `search:` key prefix in the shared in-flight map — otherwise a background poll later serves a user's half-typed query as THE repository list. Any SWR layer serving both a polled canonical list and ad-hoc filtered queries needs this read/write split.
- **When a path deliberately ignores a dimension, keep it out of the key AND comment the pairing.** The `listPRsImpl` comment names both the ignored option and what wiring it requires, so query and key change together. A key dimension the query ignores is as wrong as a missing one — it fragments the cache and stamps filtered semantics on unfiltered data.
- **Key encoding matters too:** `listOptionsKey` JSON-encodes a fixed-order tuple (hardening from #9043) — `JSON.stringify(opts)` depends on property insertion order and splits identical queries; a `|`-join lets a value containing the delimiter collide distinct queries. Peripheral: GitHub caps search queries at 256 chars, so `searchIssuesImpl` truncates the free text to the budget left after qualifiers (appended unquoted — only branch refs need quoting).

## Applies when

- Adding a field to `ListOptions` in `shared/types/forge.ts`, or making a provider honor a currently-advisory option (e.g. wiring `opts.search` for `listPRsImpl`) — update `listOptionsKey` and the provider dedupe/cache keys in the same change.
- Diagnosing a debounced picker/search UI intermittently showing results for the PREVIOUS keystroke with no error — check for an in-flight coalesce key missing the search term before suspecting the component's staleness handling.
- Reviewing or adding any single-flight/SWR/in-flight-dedupe layer (`createSingleFlight`, `dedupe`, the `GitHubCaches.ts` caches) — audit key completeness in both directions and whether ad-hoc query results can leak into a cache a background poll reads.
- Assuming a component-level `fetchId`/latest-wins guard makes upstream coalescing bugs harmless — it structurally cannot.
