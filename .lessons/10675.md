## Context

`RepoFetchCoordinator` (`electron/workspace-host/RepoFetchCoordinator.ts`) runs background `git fetch` per repo commondir; state is shared across every sibling worktree via `WorkspaceService`. `classifyGitError` (`shared/utils/gitOperationErrors.ts`) buckets simple-git error messages into a `GitOperationReason` via an ordered regex table (`PATTERNS`), which the coordinator turns into a cached failure with a `retryAt`. PR #9740 (fixing #9736) had already added the manual "click to retry" action (`retryAuthFetch` → `clearAuthFailures`), but the other half of #9736 — a finite auto-retry window — was never shipped, leaving the underlying suspension logic broken until #10670 was filed and #10675 fixed it.

## Problem

The Forge "authentication failed" stripe (`UpstreamSyncBadge`) appeared on every worktree card in a project and stayed up indefinitely, even though Codeforge worked fine everywhere else. The only ways to clear it were an explicit badge click, re-saving the token, or restarting the app — none of which happen in normal use, so a single blip looked like a permanently broken integration. It was misleading a second way: GitHub secondary rate limits (HTTP 403) and a normal credential-helper hiccup ("could not read Username for") were classified identically to a genuinely revoked token, so a transient throttle read as a hard credential failure with no distinguishing UI signal.

## Root cause

`classifyForCache` assigned auth-class failures `retryAt: now + AUTH_FAILURE_TTL_MS` where `AUTH_FAILURE_TTL_MS = Number.POSITIVE_INFINITY` — a single classifier hit permanently froze the repo's fetch state, with no time-based recovery at all (contrast the network-failure branch's plain 60s window). Two things made this worse than one bad constant: `WorkspaceService` mirrors one commondir's failure onto every sibling worktree monitor, so one wrong classification alarmed every card, not one; and `classifyGitError`'s `auth-failed` regex matched the same `...error: 40[137]` fragment GitHub emits for secondary rate limiting, plus `could not read Username for` — a message background fetches routinely produce because they force `GIT_TERMINAL_PROMPT=0`/`GIT_ASKPASS=true`. A throttle and a routine credential-helper response both got funneled into the same "permanently suspend" bucket as an actually-revoked token.

The fix replaces the single-observation-to-`Infinity` jump with confirmation-over-time: `AUTH_FAILURE_BACKOFF_SCHEDULE_MS = [5,15,30,60]` minutes drives auto-retry, and `AUTH_FAILURE_CONFIRM_RETRIES = 3` gates the alarming stripe — `authFailed` only reads true once `failure.confirmed`, ~20 minutes and three retries in; pre-confirmation the card shows the softer `networkFailed` tooltip. `buildAuthFailureEntry` only increments `authRetryCount` when `now >= prior.retryAt` — a failure observed while the prior window is still open is the _same_ incident, not a new data point — stopping a cold start or force-retry burst from racking up 3 counts in milliseconds and confirming instantly. A new `rate-limited` reason was inserted into `PATTERNS` ahead of `auth-failed` (same "more specific wins the 403 tie" precedent as `lfs-quota-exceeded`), routed to a long-but-finite 45min+jitter backoff. `could not read Username for` was dropped from `auth-failed` entirely, since under `GIT_TERMINAL_PROMPT=0` it's routine, not evidence of anything broken.

## Lesson

- **Never let a single observation trigger a permanent/alarming state.** `Infinity` on the first auth-classified failure was the whole bug; require several independent, time-separated retries (`AUTH_FAILURE_CONFIRM_RETRIES = 3`) before the destructive UI shows, defaulting to the soft signal until confirmed.
- **Concurrent observations of the same incident must coalesce, or the confirmation threshold is fake.** `buildAuthFailureEntry` only advances the count once the prior backoff window elapses (`now >= prior.retryAt`); without that guard, sibling worktrees or a force-retry burst each count independently and confirm instantly regardless of the threshold.
- **When failure conditions share an underlying signal (HTTP status/message fragment), rank the more specific/actionable one first.** `rate-limited` and `lfs-quota-exceeded` both precede `auth-failed` in `PATTERNS` because GitHub reuses HTTP 403 for all three — check what else produces the same code/substring before trusting a bucket.
- **A message that's a normal side effect of your own configuration is not evidence of failure.** `could not read Username for` under `GIT_TERMINAL_PROMPT=0` is the credential helper behaving as configured — it was removed from the matcher outright rather than kept and misread as fatal.
- **"Don't retry too fast" and "never retry" are not the same constraint.** The prior code's own comment said auth failures "must NOT auto-retry" to avoid GitHub rate limits; the fix satisfies that with slow widening backoff (hourly steady state), not `Infinity` — check whether a no-retry rule is really a slow-retry rule in disguise.

## Applies when

- Touching `RepoFetchCoordinator.ts`, `WorkspaceService.ts`, or `classifyGitError`/`PATTERNS` in `gitOperationErrors.ts` — any path bucketing failures into transient vs. persistent categories.
- Adding a new HTTP-status or message-based classification to `PATTERNS` — verify no earlier, more generic reason already matches the same substring, and add an ordering test (see the "prefers X over auth-failed" test names already in the suite).
- Diagnosing a sticky error banner/stripe/badge that never clears on its own — suspect an `Infinity`/no-TTL `retryAt` or a confirmation threshold reachable from one observation.
- Designing retry/backoff/confirmation logic where multiple concurrent callers (sibling worktrees on one commondir, multiple panes, multiple pollers) observe the same failure — confirm they coalesce into one count.
- Reviewing a "transient vs. persistent" or auth/error escalation design — check the alarming UI requires multiple time-separated confirmations, not one classifier hit.
