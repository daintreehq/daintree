## Context

PTY terminals spawn a default shell via `getDefaultShellArgs(shell)` in `electron/services/pty/terminalShell.ts`. The environment is run through `ensureUtf8Locale()` (`EnvironmentFilter.ts`) which sets `LANG=en_US.UTF-8` when no UTF-8 locale is present. Agents emit box-drawing characters and emoji that need a UTF-8 console to render.

## Problem

On Windows, fallback shells (`cmd.exe`, `powershell.exe` 5.1) rendered agent output as mojibake — corrupted box-drawing and emoji. The `LANG` env var that "fixes" UTF-8 on POSIX did nothing here.

## Root cause

`LANG`/`LC_*` are POSIX `setlocale` variables; the Windows console driver ignores them entirely. Console encoding on Windows is process/host state, not an environment variable, so it can only be set **in-band** after the shell starts — and the mechanism differs per shell:

- `cmd.exe`: the active code page must be switched with `chcp 65001`, injected via `/K "chcp 65001 >NUL"` (the `>NUL` suppresses the "Active code page: 65001" banner from polluting the scrollback).
- `powershell.exe` (5.1) and `pwsh.exe` (7+): set `[Console]::OutputEncoding` and `$OutputEncoding` to a **BOM-less** `[System.Text.UTF8Encoding]::new($false)` via `-NoLogo -NoExit -Command`. The `$false` matters — `new($true)` (or the `[Console]::OutputEncoding = [Text.Encoding]::UTF8` default) emits a leading BOM that corrupts piped/native-tool output. Even though pwsh 7+ defaults its own strings to UTF-8, `[Console]::OutputEncoding` still governs how it decodes native tools (git, docker), so the bootstrap is applied to both PS hosts — not just 5.1.

Shell identity is matched by **basename-exact** comparison (`isPowerShellShell` / `isCmdShell` in `shared/utils/shellEscape.ts`), never substring, so a `COMSPEC`-resolved full path like `C:\Windows\system32\cmd.exe` matches but `C:\tools\powerwash.exe` does not.

## Lesson

- `ensureUtf8Locale()` / `LANG` is a POSIX-only fix. On Windows it is a no-op for console rendering — do not assume the cross-platform env approach covers Windows UTF-8.
- Force Windows console UTF-8 in-band through shell startup args, gated on the resolved shell basename: `cmd.exe` → `["/K", "chcp 65001 >NUL"]`; PowerShell hosts → `["-NoLogo", "-NoExit", "-Command", <BOM-less UTF8Encoding bootstrap>]`.
- Always use BOM-less `UTF8Encoding($false)` for `[Console]::OutputEncoding`; a BOM corrupts piped output. This same `WINDOWS_PS_UTF8_BOOTSTRAP` string is reused in `ProcessTreeCache.ts` for the `Get-CimInstance` probe.
- Match shell identity with basename-exact helpers, never `shell.includes("cmd"|"powershell")` — substring matching false-positives on tool paths and confuses `pwsh.exe` with `powershell.exe`.
- Unknown Windows shells (nushell, etc.) return `[]` — never inject another shell's args.

## Applies when

- Spawning PTY terminals on Windows or editing `getDefaultShellArgs` / `findWindowsShell` in `terminalShell.ts`.
- Debugging mojibake / corrupted box-drawing / emoji in Windows terminals or agent output.
- Building any PowerShell or cmd.exe subprocess that parses native-tool output (process-tree probes, git, docker) — set BOM-less `[Console]::OutputEncoding`.
- Touching `ensureUtf8Locale` / `LANG` for "UTF-8 safety" and assuming it helps on Windows.
- Classifying or branching on shell identity by name — use the basename-exact `isPowerShellShell` / `isCmdShell` helpers in `shared/utils/shellEscape.ts`.
