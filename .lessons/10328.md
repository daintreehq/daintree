## Context

The main process runs ~30 background tasks on a deferred-init queue that drains after the renderer reports first-interactive (`registerDeferredTask` in `globalServicesInit.ts`, drained by `drainNext` in `deferredInitQueue.ts`). Tasks run one at a time with a `setImmediate` between each so renderer IPC stays responsive during the drain. #10328 fixed two tasks that each stalled everything queued behind them — the `github-auth-validate` token check and the `prune-old-logs` fs sweep — both running right at first-interactive, exactly when the user starts interacting.

## Problem

On a slow or offline network, cold start hitched for up to 10s: monitors, `ResourceProfileService`, the MCP server, and the plugin service — all registered _after_ `github-auth-validate` — were delayed even though none read GitHub auth state. Separately, `prune-old-logs` walked and unlinked files with synchronous fs, freezing IPC, timers, and window events for the whole scan whenever the log dir had accumulated or AV/indexing slowed the unlinks. Both were bounded (post first-interactive), so they read as polish, not a crash — easy to underweight.

## Root cause

`drainNext` advances purely on the _return value_ of `task.run()`: `if (result instanceof Promise) result.catch(...).finally(scheduleNext); else scheduleNext();`. A `run()` returning a thenable gates every successor until it settles; a non-Promise schedules the next task immediately (via `setImmediate`). `github-auth-validate` was `run: async () => { await GitHubAuth.validate(token) ... }` — the `await` on a fetch bounded by `AbortSignal.timeout(GITHUB_AUTH_TIMEOUT_MS)` (`10_000`) meant `run()` returned a promise that could take 10s to settle, serializing the queue behind unrelated network. The fix returns void: `run: () => { void (async () => { ... })(); }` — the IIFE still validates, but `run()` returns `undefined` so the drain advances synchronously. Two _distinct_ failure modes: github idle-waits on network (loop free, only the queue blocked), whereas `prune-old-logs` ran `readdirSync`/`statSync`/`unlinkSync` and froze the _entire main loop_ for the whole scan — the inter-task `setImmediate` yields _between_ tasks, never _within_ one. The prune fix is a new `pruneOldLogsAsync` using `fs/promises` `opendir` + `for await` + `stat`/`unlink`, so each `await` yields mid-scan; the task still returns a promise (still gates the queue) but no longer freezes IPC.

## Lesson

- **A deferred-init task with no downstream reader that does unbounded I/O must float, not await** — return void from `run()` (`void (async () => {…})()`) so `drainNext` advances immediately. Awaiting serializes all ~30 successors behind its worst-case latency (here a 10s `AbortSignal.timeout`). Only keep a task awaited when a _real_ ordering constraint exists (registry-before-mcp-server, monitors-before-`ResourceProfileService`); unconstrained I/O should never gate the queue.
- **When you float a task that writes shared state on completion, capture an epoch/version token at registration and guard the write against it.** `github-auth-validate` captured `versionAtStart = GitHubAuth.getTokenVersion()` and passed it to `setValidatedUserInfo(...)`, so a mid-flight token rotation makes the stale completion a safe no-op. This `versionAtStart` epoch-guard is a repo idiom (also `prefetchHydrateCache.ts`, `GitHubTokenHealthService.ts`) — floating decouples completion from registration order, so any post-await state write can be stale.
- **A floated async IIFE needs its own `.catch()` / internal try-catch or its rejection becomes an unhandledRejection** — the drain's `.catch(reportDeferredTaskFailure)` only fires on promises the task _returns_. The PR's tests assert the floated task produces zero `unhandledRejection` even when `validate()` rejects.
- **Synchronous fs inside a single deferred task blocks the whole main loop, not just the queue** — `setImmediate` yields between tasks, never inside one. Convert to `fs/promises` `opendir` + `for await` (`pruneOldLogsAsync`) so each `await` interleaves IPC/timers mid-scan. Keep the sync twin only for genuinely-sync callers (`pruneOldLogs` is retained for `DiskSpaceMonitor` and `PeriodicCleanupService.ts`); the split was later applied to `pruneHeapSnapshotsAsync` too.
- **The `github-auth-validate` callsite has since moved** — GitHub is now a builtin forge plugin, so token validation lives under `plugins/builtin/github/main/` (`GITHUB_AUTH_TIMEOUT_MS` still `10_000`), not `globalServicesInit.ts`. But `drainNext` and the float pattern (live example: the pending-hibernation-store wire-up at `globalServicesInit.ts` ~L962) are unchanged — the transferable rule is the drain's return-value semantics, not that one task.

## Applies when

- Adding or editing a `registerDeferredTask` in `electron/window/globalServicesInit.ts` — decide whether `run()` returns a Promise (gates the queue) or void (floats); default to floating anything doing network/unbounded I/O with no downstream reader.
- Diagnosing a cold-start hitch or delayed monitors/MCP/plugin startup that correlates with slow/offline network or a large/slow userData dir.
- Reviewing any `run: async () => {…}` deferred task that does `fetch`, `AbortSignal.timeout`, or synchronous fs (`readdirSync`/`statSync`/`unlinkSync`) — the first serializes the queue, the second freezes the main loop.
- Floating main-process async work that writes cached/shared state on completion, or reasoning about why a deferred task blocked its successors — the `versionAtStart` epoch-guard plus an own-`.catch()`, and the `result instanceof Promise` branch in `drainNext`, are the load-bearing pieces.
