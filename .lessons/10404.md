## Context

The pty-host keeps a headless xterm per terminal (Unicode11 addon + `SerializeAddon` + up to 10k-line scrollback) for state detection and `get-serialized-state` reads; the renderer's `TerminalHibernationManager` (now removed) similarly held an on-screen xterm per pane. Both reclaim memory by calling `Terminal.dispose()` on exit/hibernate. #10404 (pty-host, resolves #10388) and #10407 (renderer hibernation, resolves #10387) landed together fixing the same leak class. Pin at the time: `@xterm/xterm 6.1.0-beta.221` (the beta line has since moved forward, now `6.1.0-beta.290` in `package.json`). #10407's `TerminalHibernationManager` was later removed wholesale by #10811 (per-terminal hibernation torn out; background terminals stay live), so that file is gone — but its mechanism is why the reclaim pattern below is shaped as it is.

## Problem

Memory never came back after "disposing." Preserved exited agent terminals held ~15-30MB of headless xterm each until the panel was trashed (#10388); hibernated panes pinned their full buffer graph until wake (#10387). Every `dispose()` call was present and correctly ordered, so it looked like disposal was working — easy to misattribute to app-side pooling. It scaled with the preserve-on-exit workflow (users park several completed agent runs), bleeding tens of MB of steady-state RSS.

## Root cause

xterm's `Terminal.dispose()` tears down listeners, the DOM/renderer, and the parser, but does NOT null the `CircularList`/`BufferSet` storage — the normal+alt buffers are `Uint32Array` BufferLines (~12 bytes/cell), 15-50MB when filled with scrollback. The disposed instance is inert but its buffer graph stays fully allocated, and remains GC-reachable as long as ANY reference to the `Terminal` survives. Two reference traps kept it alive: (1) app code kept the disposed instance on a field (`managed.terminal` in hibernation; a non-nulled `terminalInfo.headlessTerminal`), and (2) the eager addons captured a `_terminal` back-reference at `loadAddon()` time — the fit/serialize/search addons _alone_ pin the whole buffer graph even after you drop the Terminal field. Dropping one reference isn't enough; every edge into the disposed instance must be severed.

A subtler trap in the hibernation path (#10407): `terminal.options` is a LIVE getter proxy backed by `rawOptions`, and `dispose()` nulls `rawOptions.linkHandler` — so options the wake path needs must be captured with a spread `{ ...managed.terminal.options }` BEFORE `dispose()`, or you read a half-nulled object.

## Lesson

- **`Terminal.dispose()` is not a free.** At the 6.1.0-beta.221 pin this PR shipped against, it never nulls the CircularList/BufferSet buffer graph; the 15-50MB stays allocated and GC-reachable until you drop _every_ reference to the disposed instance. "Memory didn't come back after dispose()" means a surviving reference, not a missing dispose call — the opposite failure mode from #9546 (leak inside undisposed xterm internals). Re-check this against `package.json`'s current pin (now `6.1.0-beta.290`) before assuming it still holds verbatim.
- **Eager addons back-reference the Terminal from `loadAddon()` time.** fit/serialize/search each hold `_terminal`, so stale addon instances on your managed struct pin the disposed buffer graph even after you overwrite the Terminal field. #10407 re-pointed them via `setupTerminalAddons(placeholder)` — any dispose path keeping addons around must drop or re-point them too, not just the Terminal.
- **Reclaim = snapshot-then-dispose-then-drop-all-references.** #10404 (live, now `PreservedSnapshotCapture`): on preserved clean exit, `SerializeAddon.serialize()` once into an ANSI string (~1-3MB), cache on `terminalInfo.preservedSnapshot`, `disposeHeadless()`, then `serializeTerminal`/`serializeTerminalAsync` early-return the cached string for every later read. #10407 (removed): swap `managed.terminal` to a fresh un-opened placeholder `Terminal(options)` — never `open()`-ed, never given listeners — so the old instance goes GC-eligible while the field stays non-null.
- **Drain xterm's async parser queue before serializing/disposing.** Writes are async; disposing with queued writes throws against a torn-down core AND loses the tail of output. #10404 serializes inside a drain sentinel — originally `headless.write("", cb)`, now `headlessMirrorScheduler.flush(id, headless, cb)` since chunks can sit outside xterm's own write queue post-#10919. On serialize _failure_, KEEP the live instance — an existing buffer beats nothing.
- **The cached snapshot is runtime-only.** `TerminalInfo.preservedSnapshot` is NOT in `TerminalPublicState`, never crosses IPC, never persists. The pattern has since grown a worker-mode variant and an eviction cap (`preservedAt`/`onPreserved`, #10839; LRU via `preservedSnapshotLastAccessedAt`), but the serialize-once/dispose/serve-cached core from #10404 is unchanged.

## Applies when

- Touching pty-host terminal lifecycle — `TerminalProcess.snapshotAndDisposePreserved`, `PreservedSnapshotCapture`, `disposeHeadless`, or `serializeTerminal`/`serializeTerminalAsync` — and reasoning about when the live headless vs the cached `preservedSnapshot` is served.
- Disposing any xterm `Terminal` (headless or on-screen) to reclaim memory and finding the heap doesn't drop — audit surviving references (the instance field AND every addon's `_terminal` back-ref) before re-checking dispose ordering.
- Reading `terminal.options` around a `dispose()` boundary, or building any wake/rehydrate path needing config after disposal.
- Serializing an xterm buffer right before teardown — drain the async parser queue first (scheduler flush / sentinel `write("")`) or the tail output is lost and dispose can throw.
- Diagnosing steady-state pty-host RSS that scales with the count of exited/preserved agent terminals (~15-30MB each).
