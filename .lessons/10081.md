## Context

Cold-start hydration (`hydrateAppState` in `src/utils/stateHydration/index.ts`) restores the saved panel session by merging two inputs: the on-disk snapshots and the live backend terminals from `terminalClient.getForProject` (adopt running terminals, respawn the rest via `restorePanelsPhase`). The panel store then persists continuously — `saveNormalized` (`src/store/slices/panelRegistry/persistence.ts`, called from `core.ts` and every registry slice) fires `panelPersistence.save()` on nearly every mutation: add, remove, rename, focus-stamp, move, reorder. `panelPersistence` diffs each save against a per-project previous-snapshot cache (`persistedTerminalsByProject`) that hydration seeds via `primeProject`.

## Problem

Issue #9928: if `terminal:getForProject` rejected during cold start, the app silently skipped restoring the saved session — and then the first panel-store mutation after boot persisted the empty store, permanently overwriting the saved session on disk. No error surfaced; the only trace was a `logWarn`. The misleading part: pty-host down/timeout failures looked fine, because `PtyClient.getTerminalsForProjectAsync` (main process) already catches broker/host failures and resolves `[]` — only a genuine rejection thrown by the `terminal:getForProject` handler took the catastrophic path. The two failure modes of the same query had divergent semantics, so the bug hid behind the common case degrading gracefully.

## Root cause

The rejection was captured into a `terminalFetchError` variable, then rethrown inside the panel-restore block (`if (terminalFetchError) throw terminalFetchError`) into an outer catch that only logged. The rethrow skipped everything downstream of it: `panelPersistence.primeProject` (never seeded the diff baseline) and `restorePanelsPhase` (never respawned saved panels). That alone is just "session didn't restore this boot" — recoverable, since disk still holds the truth. What made it permanent is that the persistence layer is fail-open: `panelPersistence.save()` has no hydration-succeeded guard, and with `persistedTerminalsByProject` unseeded, the first `saveNormalized` diffed the empty store against nothing, saw a change, and wrote `[]` through `project:set-terminals`. The error handling itself destroyed the data — a transient IPC failure converted into irreversible loss by the very next mutation.

The violated invariant: **in a hydrate-then-persist store, the restore phase must always run and the previous-snapshot cache must be primed before any save can fire.** A failed input read must degrade the input (empty backend map), never skip the phase. The fix deletes the rethrow: the renderer-side `.catch()` on `getForProject` logs and returns `[]` (mirroring what the main-process timeout path already did), so `restorePanelsPhase` runs with an empty backend map, saved panels respawn from disk via the existing respawn-from-saved path, and `primeProject` seeds the cache so the first save diffs against the real snapshot. The asymmetry precedent was already in the same file: the tab-groups error path guards itself with `hydrateTabGroups([], { skipPersist: true })` — panels, the far more valuable state, had no equivalent.

## Lesson

- **A restore phase must run unconditionally; only its inputs may degrade.** Any `throw`/early-return between "hydration started" and "persistence cache primed" is a data-loss window in a store whose saves fire on every mutation. When adding error handling to hydration, ask what the throw skips — here it skipped `primeProject` + `restorePanelsPhase`, and that skip plus fail-open `save()` equals destruction.
- **Persist layers with a diff-against-previous cache must be primed before the first save, or the first save is the wipe.** `panelPersistence.save()` compares against `persistedTerminalsByProject`; unseeded, an empty store looks like a legitimate delete-everything. `primeProject` is the guard — any new hydrate path (new panel kind, new project-view boot path) must reach it even on failure.
- **When one failure mode of a fetch already degrades gracefully, verify the other modes take the same path.** `PtyClient.getTerminalsForProjectAsync` resolved `[]` on broker/host timeout, but a handler-thrown rejection bypassed that and hit the renderer raw. Divergent timeout-vs-rejection semantics on the same query is the trap signature — normalize at one choke point (here: the renderer `.catch(() => [])` at `stateHydration/index.ts:341`).
- **Fail-open beats fail-closed only when the open path is non-destructive.** Blocking persistence for the session (fail-closed) was the issue's fallback suggestion; the shipped fix is better because the empty-backend degrade makes the open path safe. If you can't make restore succeed, at minimum gate the save.
- **`panelPersistence` is a process-lived singleton and `primeProject` early-returns if an entry exists** — tests asserting priming must call `clearProjectSnapshotCache(projectId)` first (added in this PR) or the assertion silently reflects a previous test's cache.
- Signal ruling for this class: no toast/banner — a failed backend query at boot is a Tier-1 auto-recovering transient (panels come up in their normal reconnecting state, identical to a slow pty-host start) per the runtime-signals tiers.

## Applies when

- Touching `hydrateAppState` / `restorePanelsPhase` / `panelPersistence` — especially adding error handling, reordering phases, or adding a new restore phase that feeds a continuously-saving store.
- Writing any hydrate-then-persist store (load from disk → Zustand → save-on-mutation): the prime-before-first-save invariant applies to every one, not just panels.
- Diagnosing "my session/panels disappeared after restart" — check whether a hydration-phase failure preceded a save; the wipe happens on the first mutation after the skipped restore, not at the failure itself.
- Reviewing a `catch` that rethrows or early-returns out of a multi-phase init sequence — enumerate what downstream steps it skips and whether any skipped step guards a destructive path.
- Assuming "the pty-host-down case works, so query failure is handled" — the timeout and rejection paths of `terminal:getForProject` were separate code paths with opposite outcomes until #10081.
