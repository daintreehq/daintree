## Context

The adaptive fetch backoff (#8756) paces every worktree monitor's background git-fetch cadence against the GitHub GraphQL quota: `WorkspaceService.applyFetchThrottle(multiplier)` (now `electron/workspace-host/WorkspaceService.ts:3249`) multiplies fetch intervals so multiple Daintree instances sharing one token back off in step as the budget depletes. Its only feed was a `gitHubRateLimitService.onStateChange` subscription inside `electron/workspace-host.ts` — the utility process observed its own HTTP calls and throttled itself locally.

## Problem

The monitor fleet polled at full cadence straight into the rate-limit wall — exactly the failure #8756 was built to prevent. Nothing errored, no test failed, and #9054 later extended the throttle believing it was alive ("already consumed by `WorkspaceService.applyFetchThrottle`"). The relay had fired zero times in production for two weeks.

## Root cause

Three days after the throttle landed (c53cddb8e, 2026-05-20), the forge RPC bridge (#8870, df083b1d8) moved every GitHub HTTP call — PRs, issues, CI, rate limits — out of the workspace-host into main. `gitHubRateLimitService` is a module singleton, and **module singletons are per-process**: the instance imported in `electron/workspace-host.ts` is a different object from main's. With no HTTP left in the host, the host-local instance never received `update`/`updateFromGraphQL`; its only observed transitions were `clear()` calls from credential rotation. The `onStateChange` subscription stayed syntactically wired to a producer that had gone permanently silent, and no inbound `WorkspaceHostRequest` message existed to carry main's state the other way (`forge-rate-limit-changed` flowed host→main only; the bridge's `getRateLimit` omitted `throttleMultiplier` when unblocked). The multiplier therefore stuck at 1 — which is also the correct healthy-state value, so the deadness was observationally indistinguishable from "no throttling needed" until the fleet hit the wall. Unit tests couldn't catch it by construction: mocking the singleton puts producer and consumer in one module instance, erasing the per-process split.

The fix (#10170, closing #9987) inverts the flow: main relays `throttleMultiplier` from its rate-limit state-change subscription via a fire-and-forget `apply-fetch-throttle` request into every workspace host. Because hosts crash-restart and spawn late, the push is cached at two levels, following the `setLogLevelOverrides` precedent: `WorkspaceHostProcess.fetchThrottleMultiplierCache` replays on every `ready` (initial spawn and restarts — a restarted host would otherwise run unthrottled until the next state change, hours away), and `WorkspaceHostPool` keeps a pool-level cache seeding hosts created after the last state change.

Code has since moved under the forge-plugin abstraction: the relay origin is now `electron/services/forgeHealthRelay.ts` (provider-generic `healthEvents.onRateLimitChanged`, ~line 93), not `electron/ipc/handlers/github.ts`; the deduped `toRateLimitInfo` in `shared/utils/rateLimitUtils.ts` was re-homed into `plugins/builtin/github/main/rateLimitUtils.ts`. The host-side plumbing (`relayFetchThrottle` chain, `apply-fetch-throttle` at `electron/workspace-host.ts:604`) is unchanged.

## Lesson

- **When migrating functionality across a process boundary, audit every subscriber of the module singletons it fed.** A consumer in the old process stays subscribed to its own per-process instance, which simply goes silent — no error, no unsubscribe, no failing test. Grep for `onStateChange`/emitter subscriptions against any service whose producer moves, then either move the consumer or add an explicit cross-process relay.
- **A severed signal whose stuck default equals the healthy value is invisible.** Multiplier 1 means both "relay dead" and "budget healthy", so nothing looked wrong until the stress condition arrived. For signals that only modulate behavior under stress, assert the end-to-end fan-out (state change → relay → host request), not merely that the subscription registered.
- **Per-process singleton splits are unfalsifiable in unit tests** — mocks collapse producer and consumer into one module instance. The severed path here needed a cross-process-shaped test: #10170's `WorkspaceHostProcess.rateLimit.test.ts` asserts the actual `postMessage` traffic to the forked child.
- **Fire-and-forget state pushed into a restartable utility host must be cache-and-replay at two levels:** per-process cache replayed on every `ready` (covers crash restarts), plus a pool-level cache seeding hosts constructed after the last state change. `WorkspaceHostProcess` now has a five-member family of this pattern — log-level overrides, fetch throttle, monitor config, forge credentials, provider matchers — copy one of those, don't hand-roll.
- **Relay from the live callback argument, never a cached payload** — a stale payload can predate a token rotation (comment enforced at the relay site in `forgeHealthRelay.ts`).
- **The host→main `forge-rate-limit-changed` event path is emitter-less dead plumbing** (`shared/types/workspace-host.ts:710`, `WorkspaceHostEventRouter.ts:289`, `WorkspaceHostProcess.ts:1087`) — left deliberately in #10170 alongside the equally emitter-less `forge-token-health-changed`. Don't mistake the router case for a live signal source.

## Applies when

- Moving HTTP calls, polling, or any stateful service between main and a utility process (workspace-host, pty-host, plugin host) — especially when consumers of its events live in the origin process.
- Adding main-owned state that workspace hosts must track — use the `relayFetchThrottle`/`setLogLevelOverrides` cache-and-replay pattern in `WorkspaceHostProcess` + `WorkspaceHostPool`, never a bare one-shot `send`.
- Diagnosing GitHub rate-limit walls or worktree monitor fetch cadence that never backs off — trace `forgeHealthRelay` → `WorkspaceClient.relayFetchThrottle` → pool fan-out → `apply-fetch-throttle` → `applyFetchThrottle`.
- Seeing `forge-rate-limit-changed` in the workspace-host event union or router and assuming the host emits it — nothing has since #8870.
- Reviewing any migration PR where the moved producer's old subscribers still compile and their unit tests still pass — green tests prove nothing about per-process singleton wiring.
