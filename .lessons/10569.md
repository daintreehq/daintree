## Context

The Playwright E2E harness cold-launches Electron per spec via `launchApp` in `e2e/helpers/launch.ts`; each launch spawns the full helper tree (crashpad_handler, GPU, network-service, renderers). `playwright.config.ts` defines the `full-*` buckets. The `full-plugins` bucket sideloads a plugin per spec via `--daintree-e2e-sideload-plugin-dir`, so its ~10 specs each pay a fresh cold-launch. #10569 (resolving #10566, part of #10511) hardened it against running at scale and against orphaning processes when interrupted.

## Problem

Running the `full-plugins` specs in parallel made them fail at launch on macOS with EMPTY logs — the main process died before writing anything, so it read as a plugin/product defect. Separately, killing a run mid-launch (Ctrl+C locally, CI timeout) left orphaned Electron helper processes (network-service, GPU, renderer, crashpad) littering the machine, because teardown never ran.

## Root cause

Two independent platform mechanisms, both invisible until you know them.

1. **macOS Mach-port exhaustion under concurrent cold launches.** Every Electron cold-launch allocates Mach ports for its crashpad/GPU/network-service/renderer helpers; ~10 concurrent launches exhaust the OS allotment, and the symptom surfaces inside crashpad, not our code: `FATAL kr == KERN_SUCCESS` in `exception_handler_server.cc`, `mach_port_request_notification: (os/kern) invalid capability`, "Network service crashed", GPU crashes. The main process dies before writing a log, so the spec fails with an empty log that looks like a plugin bug but is purely environmental. It reproduces on **macOS local, not CI** — CI runners recycle Electron processes slowly enough to stay under the limit (`isMacLocal` forces global `e2eWorkers = 1` for exactly this). The fix is `workers: 1` on the `full-plugins` project entry, **baked into the project, not a CLI flag** — so the bucket stays serialized even under CI's `e2eWorkers: 2` and for a bare `npx playwright test --project=full-plugins`, mirroring the `demo` bucket.

2. **Playwright teardown does not run on signals.** Playwright's `globalTeardown` and worker-fixture teardowns run only on normal completion — a SIGTERM (CI timeout) or SIGINT (Ctrl+C) skips them entirely, so `closeApp` never fires and the Electron process tree leaks. The only reliable reaping path is module-scope `process.once("SIGINT" | "SIGTERM")` handlers registered by `registerExitCleanupHandlers()`, called once at the top of `launchApp` behind an idempotent boolean guard (`exitCleanupHandlersRegistered`).

## Lesson

- **Empty-log Electron launch crashes on macOS local under parallel E2E are almost always crashpad Mach-port exhaustion, not a product/plugin defect.** The tell is crashpad output (`FATAL kr == KERN_SUCCESS`, `mach_port_request_notification: (os/kern) invalid capability`), network-service/GPU crashes, and a dead main process that wrote nothing. Serialize the offending bucket before you go hunting in product code.
- **Serialize an Electron-launching bucket by baking `workers: 1` into the `playwright.config.ts` project entry, never via a CLI `--workers` flag.** A flag is bypassed by CI's `e2eWorkers: 2` and by anyone running the bucket directly; the project-level value survives both. Any new bucket that cold-launches Electron per spec (plugins, demo, screenshots) needs this.
- **Reap orphans on SIGNALS ONLY, never on the `exit` event.** A clean worker exit already ran `closeApp`, and broadcasting a system-wide `pkill` on `exit` would race a sibling project's live Electron when the `full` meta-suite runs buckets concurrently under `e2eWorkers: 2`. The signal handlers use `process.once` so a second Ctrl+C falls through to Node's default and force-terminates, and re-exit with the conventional 128+signal codes (`process.exit(130)` for SIGINT, `143` for SIGTERM).
- **Scope the reaper to e2e processes, and gate any un-scoped platform to CI.** `cleanupMacElectronE2eProcesses` matches `pkill -f "node_modules/electron.*daintree-e2e"` (the e2e `--user-data-dir`), so it never touches a dev's Daintree.app — always safe. The Windows path (`taskkill /F /IM electron.exe /T`) is broad and un-filtered, so `reapOrphanedE2eProcesses` runs it only when `process.env.CI` is set, to avoid killing a developer's local session.
- **Unit-test signal-handler wiring by listener bookkeeping, never by emitting the signal.** `launchCleanup.test.ts` asserts one-each SIGINT/SIGTERM registration and idempotency via `process.listenerCount` (with `__resetExitCleanupHandlersForTest` to re-exercise the guard); emitting the signals would fire the handlers' `process.exit()` and tear down the vitest worker.

## Applies when

- Diagnosing an E2E spec that fails at Electron launch on macOS local with an empty/missing log, or crashpad/`KERN`/network-service/GPU crash noise — suspect Mach-port exhaustion from parallelism before blaming the feature under test.
- Adding a new `full-*` bucket (or any Playwright project) that cold-launches Electron per spec — decide up front whether it needs `workers: 1` baked into `playwright.config.ts`.
- Finding orphaned Electron helper processes after a Ctrl+C or CI-timeout kill of an E2E run — the reaper must be a module-scope signal handler, because Playwright teardown/fixtures do not run on SIGINT/SIGTERM.
- Touching `e2e/helpers/launch.ts` cleanup (`registerExitCleanupHandlers`, `reapOrphanedE2eProcesses`, `cleanupMacElectronE2eProcesses`, `cleanupWindowsElectronProcesses`), or tuning `e2eWorkers` / per-project `workers` — confirm the change doesn't re-parallelize a bucket deliberately serialized against crashpad Mach-port contention.
