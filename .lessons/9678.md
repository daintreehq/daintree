## Context

The worktree sidebar search (`WorktreeSidebarSearchBar.tsx`) writes its query into `worktreeFilterStore`, whose project-scoped half persists to localStorage. Because `query` was both the persisted field and the live filter input, the search bar debounced every keystroke by 200ms before `setQuery` — the timer existed to throttle the localStorage write, but it sat in front of the visible filter too. `useSearchablePalette`/`useFleetPicker` already filtered instantly via `useDeferredValue`; the sidebar was the outlier (#9663, fixed by #9678).

## Problem

Typing in the sidebar search felt laggy: the filtered list updated only when the 200ms timer fired, even though the filter itself is a sub-millisecond in-memory `filter`/`sort` over an already-loaded list. The misleading part: the lag reads as "filtering is expensive" and invites memoization work, when the actual cost was a persistence throttle accidentally coupled into the render path — no amount of filter optimization would have removed the fixed 200ms floor.

## Root cause

One store field carried two unrelated responsibilities with different latency requirements: the UI filter wants 0ms, the localStorage write wants throttling. The fix splits the field into three representations with distinct consumers. `liveQuery` (transient, never persisted) updates on every keystroke and is the input's controlled value; `deferredQuery = useDeferredValue(liveQuery)` feeds the expensive filtering/sorting memos in `SidebarContent.tsx` so React can yield to input events; persisted `query` is written only by a 500ms debounce (`QUERY_PERSIST_DEBOUNCE_MS`) and is the cross-session source of truth.

The split's correctness lives in three non-obvious edges. (1) Hydration: the persist `merge` in `worktreeFilterStore.ts` seeds `liveQuery` from the restored `query` (the legacy-seed init does the same), otherwise a restored search shows an empty input over a filtered list. (2) Stale-closure resurrection: the debounce callback commits `setQuery(useWorktreeFilterStore.getState().liveQuery)` — the value **at fire time** — not the `value` captured at schedule time. The search bar's `hasActiveFilters` false-transition guard cancels pending timers on external `clearAll`, but when the typed-uncommitted query is the _only_ active filter, `hasActiveFilters()` never transitions (persisted `query` was still "") and the guard never fires; a closure-captured commit would silently resurrect the cleared text 500ms after "Show all worktrees". (3) External-change sync: the `[query]` effect cancels any pending write and syncs `liveQuery` whenever `query` changes from outside the input (hydration, resets, another window); during normal typing it's a no-op because `liveQuery` already matches by commit time.

## Lesson

- **When a fixed input delay shows up in front of a cheap local computation, look for a debounce doing double duty before optimizing the computation.** The 200ms lag was 100% persistence throttle, 0% filter cost.
- **Split by latency requirement, not by data: transient instant field for UI, debounced persisted field for storage, `useDeferredValue` between them for expensive derivations.** Partition consumers deliberately — urgent UI (input value, sort-disabled label, scope line `hasFilters`, empty-state gating, cycling keybindings in `worktreeCyclingOrder.ts`) reads `liveQuery`; heavy filter/sort memos read `deferredQuery`; nothing UI-facing reads persisted `query`. Cycling reading a different field than the sidebar renders would walk a different list than the user sees.
- **A debounced commit must read the store at fire time (`getState()` in the timeout), never the closure-captured argument** — external mutations between schedule and fire (clearAll, programmatic reset) are otherwise silently overwritten. Guard-based cancellation alone is insufficient when the guard's predicate (`hasActiveFilters`) can't observe the uncommitted value.
- **Seed the transient twin from the persisted field in the persist `merge` (and initial state)** — every code path that creates or restores the persisted value must establish the invariant `liveQuery === query`, including legacy-seed migration. `clearAll` must reset both.
- **Mirror derived store getters that read the persisted field.** `hasActiveFilters()` reads `query`, so the sidebar builds a local `hasFilters` from `liveQuery` + facets — reusing the store getter would delay the scope line and filtered-empty state by the persist debounce.

## Applies when

- Adding or tuning any debounce in front of a Zustand store write where the store field is persisted (localStorage `persist`, electron-store, sqlite) AND rendered — check which job the timer is actually doing.
- Diagnosing "search/filter feels laggy" in any list UI (sidebar, palettes, pickers) where the data is already in memory — measure whether the delay is a fixed timer, not compute.
- Touching `worktreeFilterStore.ts` (`query`/`liveQuery`/`setLiveQuery`/`clearAll`/persist `merge`), `WorktreeSidebarSearchBar.tsx`, or the query consumers in `SidebarContent.tsx`/`worktreeCyclingOrder.ts`.
- Writing any debounced-commit pattern — verify the callback reads current state at fire time and that every external-clear path either cancels the timer or is survivable by the fire-time read.
- Reviewing a change that adds a second consumer of a search query — decide explicitly whether it needs `liveQuery` (urgent, matches what the user sees) or `deferredQuery` (expensive derivation), and never persisted `query`.
