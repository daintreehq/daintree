## Context

`distributePortsToView` (`electron/window/portDistribution.ts`) mints a `MessageChannelMain` pair per window and hands the renderer end to the `WebContents` via `postMessage`, connecting the pty-host end via `PtyClient.connectMessagePort`; it's the transport `PtyClient` re-establishes on every pty-host restart or shard reroute, via `setPortRefreshCallback`'s per-window loop in `perWindowInit.ts`.

## Problem

Issue #10964: `npm run dev` reliably threw `Render frame was disposed before WebFrameMain could be accessed` from `distributePortsToView`, reached through `PtyClient.onPortRefresh` → `respawnPending` → `handleReady`. The throw was unhandled, so it aborted the rest of the `setPortRefreshCallback` loop in `perWindowInit.ts` for every remaining window — terminal respawn replay, IPC data-mirror re-enable, and `replayGlobalConfigToShard` silently never ran after a pty-host restart. It looked like a Vite-dev-only cosmetic error; it was actually a break in host-restart recovery for the whole fleet of windows.

## Root cause

`distributePortsToView` guarded the call with `!win.isDestroyed() && !targetWc.isDestroyed()` before calling `targetWc.postMessage(...)`. That guard is insufficient: during a renderer reload, Electron can dispose the frame (`WebFrameMain`) before `WebContents.isDestroyed()` flips to true, so the destroyed-check passes and `postMessage` throws anyway. A Vite full reload landing at the same moment as a pty-host ready/respawn event hit this window reliably in dev, but the same race exists in production on any renderer reload racing a port refresh.

The fix isn't just "add try/catch" — it's what the catch must NOT do. The port pair (`port1`/`port2`) is already stored on `ctx.services` and `port2` is already connected to the pty-host (`ptyClient.connectMessagePort`) _before_ the throwing `postMessage` call. Closing `port1` in the catch — the instinctive "clean up the broken thing" move — would fire the pty-host's port-close teardown (`electron/pty-host/handlers/connection.ts`, `disconnectWindow`) and sever the connection that was just re-established, compounding the failure instead of containing it. The correct move is to leave the pair wired and just log; `onViewReady` re-brokers a fresh pair once the frame finishes reloading, so the dangling pair self-heals. `distributeTerminalWorkerPortToView` gets the opposite treatment on the same race: its ports are lazy/best-effort per-terminal channels, so its catch calls `releaseTerminalWorkerPort` and returns `null` — the renderer's request timeout mints a fresh one on re-engage, and there's no "wait for re-broker" path for it to preserve.

The second half of the fix is a per-window try/catch inside the `setPortRefreshCallback` loop itself (`perWindowInit.ts`): even with `postMessage` guarded, any other per-window failure in that loop (`wc.send`, future additions) must not abort the loop for the other windows, since the caller (`respawnPendingForShard`) still owes respawn replay, data-mirror re-enable, and global config replay to whatever windows come after the one that failed.

## Lesson

- **`webContents.isDestroyed()` (and `browserWindow.isDestroyed()`) do not prove `postMessage`/frame access is safe** — the underlying `WebFrameMain` can dispose first during a reload. Any main-process `postMessage` call needs its own try/catch regardless of destroyed-checks upstream.
- **When wrapping a failure in a recovery/handshake path, decide per-callsite whether to clean up or leave wired** — don't reflexively close the resource on error. Here, closing the port would trigger the pty-host's own teardown handler and sever a connection the code had just re-established one line earlier; the two `postMessage` call sites in this same PR made opposite choices (leave wired vs. release) because one has a self-healing re-broker path (`onViewReady`) and the other doesn't.
- **A throw inside a per-window loop that drives multi-step recovery (respawn replay, data-mirror re-enable, config replay) takes down every window queued after the one that failed**, not just the failing window — wrap the loop body per-iteration, not just the risky call, so one bad window can't abort recovery for the fleet.
- **This was the only `webContents.postMessage` site in the main process** (per the PR/issue) — when adding a new one, apply the same try/catch-without-reflexive-cleanup pattern rather than assuming Electron's destroyed-checks are sufficient.

## Applies when

- Calling `webContents.postMessage`, `webFrameMain` APIs, or anything else that touches a frame directly from the main process, anywhere after an `isDestroyed()` check.
- Touching `electron/window/portDistribution.ts`, `perWindowInit.ts`'s `setPortRefreshCallback`, or any per-window loop inside pty-host restart/respawn recovery (`respawnPendingForShard`, `PtyClient.onPortRefresh`).
- Diagnosing "terminals don't respawn / IPC data mirror doesn't come back after a pty-host restart" — check whether a per-window exception silently truncated the recovery loop.
- Writing a catch block for a torn-down IPC transport — check whether closing the resource in the catch would itself trigger a teardown handler that undoes work already done earlier in the same function.
- Reviewing any multi-window broadcast/refresh loop in `electron/window/` for whether one window's failure can abort the rest.
