## Context

Each project gets its own `WebContentsView` + independent V8 context via `ProjectViewManager`, and under memory pressure `EvictionController.evictStaleViews` LRU-evicts idle views and cold-rebuilds them via `createView` on switch-back (`electron/window/ProjectViewManager.ts`). `src/lib/bootPromise.ts` caches the `app:boot` promise at module scope, so a fresh context has no cache and fires `app:boot` again from scratch, same as a real cold launch. `CrashRecoveryService` is a main-process singleton that captures a `pendingCrash` record once in `initialize()` and serves it back on every `app:boot` via `getPendingCrash()`, driving `useCrashRecoveryGate` to show the recovery dialog.

## Problem

Hours into a session, with no second crash, the crash-recovery dialog reappeared for a project the user switched back to (#10809). It only happened once, after heavy project-switching, which reads like a rare state-clearing race rather than something deterministic — but it is fully deterministic once you know the trigger is LRU eviction, not time or crash count. The dangerous part is the decline path: "continue without restoring" resets to a clean layout, which would have killed the hour-old live terminals in what was, by then, the actual current session — that branch was never pressed, but it is reachable by construction.

## Root cause

`getPendingCrash()` returned the same in-memory record unchanged on every call — there was no consume-on-read and no assignment back to `null` anywhere in `CrashRecoveryService`. Resolving the dialog cleaned up the on-disk backup files (`restoreBackup()` / `resetToFresh()`) but never touched the in-memory field. The first project view that boots after a crash reads `pendingCrash`, shows the dialog, and the user resolves it — but the singleton doesn't know the flow is "done." When that view is later LRU-evicted and the user returns, `createView` builds a genuinely fresh `WebContentsView` with its own V8 context; `bootPromise` is per-module-scope so it's empty in the new context, `app:boot` fires for real, the handler reads the still-non-null `pendingCrash`, and the gate replays the dialog against a project that is now mid-session with live terminals and a backup that no longer exists on disk.

The general shape: LRU eviction + cold recreate is architecturally indistinguishable from a fresh app launch from the renderer's point of view, but main-process singletons don't get restarted — they persist across the eviction and carry whatever state they had when the flow last touched them. Any "pending X, consumed once" pattern in main is a candidate for this replay unless resolution explicitly clears it.

## Lesson

- **A view eviction + cold recreate is a second boot, not a re-render.** Any main-process singleton handing data to `app:boot`, meant to be shown/consumed once, must be explicitly reset when its flow resolves — `initialize()`-time capture with no clear-on-resolve is the bug pattern. Contrast with the sibling one-shot fields the same `handleAppBoot` (`electron/ipc/handlers/app/state.ts`) already fans out to: `consumePendingSettingsRecovery()` (`electron/store.ts`) reads-and-nulls the value atomically in a single call — that read-clear-together shape is what `getPendingCrash()`/`clearPendingCrash()` should have been collapsed into instead of splitting the read from the clear across two separate call sites.
- **Clear on success paths, not on failure paths.** `crash-recovery:resolve` calls `service.clearPendingCrash()` on both restore-success and fresh, but deliberately not when `restoreBackup()` returns `false` — an unresolved failure must keep the record alive so a later LRU switch-back gives the user another chance to retry, rather than silently losing the crash forever.
- **Reload-triggered re-boot needs the same clear as direct resolve.** `recovery:reset-and-reload` (`electron/ipc/handlers/recovery.ts`) calls `resetToFresh()` then `clearPendingCrash()` before `win.loadURL(...)` — the reload itself fires `app:boot` again, so skipping the clear here reproduces the bug through a second surface even after the dialog path was fixed.
- **Idempotent clear, ordering matters.** `clearPendingCrash()` just nulls the field and is safe to call repeatedly; `recovery.handlers.test.ts` asserts `resetMock` fires before `clearMock` before `loadURL` — clearing before the disk reset settles, or loading before clearing, reopens the race.
- **Same replay hazard as #11157 (assistant eviction kill), one layer up.** There, LRU eviction killed live subprocesses because eviction wasn't distinguished from real shutdown; here, cold-recreate wasn't distinguished from real cold-launch for a state handoff. Any eviction-adjacent bug should ask "does main-process code assume this happens once per app lifetime?"

## Applies when

- Adding or auditing any main-process singleton that ships a "pending"/"once" payload to the renderer via `app:boot` or another boot-time IPC call.
- Diagnosing a dialog, banner, or one-time prompt that reappears after being resolved, especially if it correlates with project-switching or long sessions rather than a deterministic action.
- Touching `ProjectViewManager` eviction (`evictStaleViews`, `createView`) or `src/lib/bootPromise.ts` — remember a cold-recreated view is a genuine fresh V8 context, not a remount.
- Reviewing any handler that resolves a pending main-process flow (crash recovery, first-run, update-prompt) — confirm the in-memory state is cleared on every success path and intentionally left alone on retryable failure paths.
