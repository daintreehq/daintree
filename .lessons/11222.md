## Context

`readContainedDaintreeFile` in `electron/setup/protocols.ts` is the shared read core behind both `daintree-file://` (the in-app file viewer, opened by clicking a path in an agent terminal) and `daintree-html://` (sandboxed report/dev-preview asset loading, added in #11191).

## Problem

Clicking an image path from an agent terminal opened the file viewer but showed "Unable to display image" for anything over 512 KB — a normal screenshot or a Codex-generated PNG routinely exceeds that. The symptom looked like a viewer bug (bad MIME sniffing, broken `<img>` src) but the file was never even read: the protocol handler 413'd it before the viewer ever saw bytes.

## Root cause

`DAINTREE_FILE_MAX_BYTES = 512 * 1024` was a single blanket cap applied to every file the protocol served, copied for parity with the `files:read` IPC handler's `FILE_SIZE_LIMIT` (`electron/ipc/handlers/files.ts`). That cap is correctly sized for **text**: a large file becomes a large JS string held in the renderer, and 512 KB bounds that OOM risk. But a raster image is decoded by the browser's `<img>` element into pixels, not turned into a string — the OOM risk the cap exists to prevent doesn't apply, yet the cap was blocking it anyway because it was keyed to "is this a file," not "how will this file's bytes be used."

The fix parameterizes the cap two ways, both load-bearing. First, `maxBytesForFile(realFile, allowLargeImages)` picks `DAINTREE_IMAGE_MAX_BYTES` (25 MB) over `DAINTREE_FILE_MAX_BYTES` (512 KB) only when the MIME type is in `LARGE_IMAGE_MIME_TYPES` (png/jpeg/gif/webp/bmp/ico) — SVG is excluded even though it's an "image," because the viewer routes SVG through a separate sanitizing `files:read` path that keeps the tight cap; raw SVG through the raster ceiling would bypass that sanitization for no benefit. Second, the larger ceiling is gated by an `allowLargeImages` boolean the caller passes in: `createDaintreeFileProtocolHandler` passes `true` (the viewer is a direct, non-scriptable read), `createDaintreeHtmlProtocolHandler` passes `false` (a report/dev-preview document can execute script and re-request the same asset repeatedly, so a 25 MB allowance there becomes a cheap aggregate-memory DoS lever). Same shared function, two different threat models, disambiguated by the caller — not by MIME type alone.

The second load-bearing change is a post-read length check. The pre-read `fs.stat()` is advisory: nothing stops a file from growing (or being swapped for a larger one) in the window between `stat()` and the subsequent `fileHandle.readFile()`. `O_NOFOLLOW` on the open only rejects a final-component symlink swap — it does nothing about a regular file that changes size in place. So the fix re-checks `buffer.length > maxBytes` _after_ the read completes and 413s even then, discarding the oversized buffer before it reaches the renderer. Without this second check, an attacker (or just an unlucky concurrent write) could pass the stat gate on a small file and still deliver an oversized payload to the exact decode path the cap was built to protect.

## Lesson

- **Size a cap to how the bytes get consumed, not to "is this a file read."** Text becomes a JS string (OOM risk scales with byte count); an image becomes decoded pixels (risk profile is different, and a much larger byte ceiling is safe). A single `FILE_SIZE_LIMIT`/`_MAX_BYTES` constant reused across content types is a smell — check whether every consumer actually shares the same risk.
- **A pre-read `stat()` size check is advisory, not a guarantee** — always re-check the actual buffer length after the read completes, and reject then too. This is the only real ceiling; anything checked before the read can be invalidated by a grow-or-swap race in the gap between the two syscalls.
- **When two protocol/IPC handlers share a read core, don't let a broadened limit leak to a handler with a different threat model.** `daintree-file://` (direct navigation, non-scriptable) and `daintree-html://` (sandboxed but script-capable preview) call the same `readContainedDaintreeFile`; the raster-image allowance is threaded through as an explicit `allowLargeImages` parameter so the scriptable path can't inherit it and turn a display convenience into a repeat-request DoS amplifier.
- **`O_NOFOLLOW` only closes the final-component symlink-swap TOCTOU, not a same-path size change** — don't treat "we already have O_NOFOLLOW" as covering file-growth races too; they're independent gaps needing independent guards (containment vs. size).
- **When excluding a sub-type from a broadened allowance, state why in the code, not just in the PR description** — SVG is technically a raster-adjacent image but is excluded from the 25 MB ceiling because it has its own sanitizing read path; that reasoning lives in the comment above `LARGE_IMAGE_MIME_TYPES`, not just in this lesson.

## Applies when

- Adding or auditing a byte-size cap on any file/protocol/IPC read path (`electron/setup/protocols.ts`, `electron/ipc/handlers/files.ts`, or a new `daintree-*://` scheme) — ask what the bytes become downstream before picking or reusing a limit.
- Investigating "file/image won't load / shows a generic error" in the file viewer, dev-preview, or report panels where the file is legitimately large — check for a silent 413 before assuming a rendering or MIME bug.
- Adding a second consumer to an existing shared read/fetch helper — verify the new caller's threat model (scriptable vs. static, repeatable-request vs. one-shot) before it inherits any existing allowance.
- Reviewing any size/quota check that runs only before a read or write completes — ask whether the resource can change between the check and the operation, and whether a post-operation re-check is needed.
