## Context

A PTY-backed panel can run `npm`, then `claude`, then return to the shell, then run `codex` — chrome, agent capability, fleet eligibility, and focus routing must follow whatever is live in the PTY _right now_, not what it was launched as. Before #5790 the renderer stitched this together from four overlapping fields (`panel.kind`, `panel.agentId`, `terminal.type`, backend `detectedAgentType`), a split-brain where each subsystem read a different one.

## Problem

There is no single field that answers "what agent is running in this terminal at this instant" that all consumers can read. Reusing the persisted launch identity (`agentId`, now `launchAgentId`) as the runtime answer is the obvious-but-wrong move: it is durable spawn/restart intent, not live state, so it lies the moment the agent exits or a different process takes over the foreground.

## Root cause

Two genuinely different identities were conflated. **Launch identity** (`launchAgentId`, persisted: yes) is the command to restart as. **Runtime identity** (`detectedAgentId`, persisted: no) is what the backend `ProcessDetector` sees live. #5790 promotes `detectedAgentId?: BuiltInAgentId` to a first-class field on `PtyPanelData`/`TerminalInstance` (`shared/types/panel.ts`) fed straight from the backend `detectedAgentType` signal, narrowed at the IPC boundary by `narrowDetectedAgentId` (`electron/pty-host/handlers/terminalInfo.ts`), which delegates the validity check to `isBuiltInAgentId` (`shared/config/agentIds.ts`). The hard invariant: runtime identity is recomputed by the backend detector on every PTY attach, so it must **never** be persisted. The serializer omits it (`src/panels/terminal/__tests__/serializer.test.ts`), the respawn hydration builder strips it even if saved JSON somehow carries one (`buildArgsForRespawn`, `src/utils/stateHydration/statePatcher.ts`), and the renderer reducer clears it on `agent:exited` via `reduceAgentExited` (`src/store/listeners/panel/identityReducer.ts`). On reconnect it is rehydrated from the backend payload with `ptyTerminal.detectedAgentId ?? existing.detectedAgentId` (`src/store/slices/panelRegistry/addPanel.ts:407,456`) — prefer the fresh reconnect value, but keep an existing live detection because the live IPC event can land before the reconnect flush.

## Lesson

When a piece of state has both a durable "what was requested" form and a live "what is true now" form, model them as two separate fields with opposite persistence rules — do not overload one. The non-persisted runtime field is authoritative for chrome/eligibility/routing; the persisted field is _only_ a restart hint and must never decide UI. Guard the no-persist invariant in three places at once (serializer omit, hydration strip, exit clear) and repopulate exclusively from the live backend producer post-attach. This split is now the canonical terminal-identity model (`docs/architecture/terminal-identity.md`): `deriveTerminalRuntimeIdentity()` / `deriveTerminalChrome()` are the only sanctioned readers, with precedence `detectedAgentId` > `detectedProcessId` > shell, and `launchAgentId` explicitly barred from chrome.

## Applies when

Adding any panel/terminal field that distinguishes runtime detection from launch/restart intent; deciding whether a new identity field belongs in the project-JSON serializer; debugging stale agent chrome that survives an agent exit or wrongly resurrects after a project switch; wiring a consumer (fleet arming, focus nav, status badge, worktree sidebar row) that needs "is this an agent right now" — read derived chrome, never `launchAgentId`.
