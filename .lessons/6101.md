## Context

`resilientAtomicWriteFile` / `resilientAtomicWriteFileSync` (`electron/utils/fs.ts`) implement the crash-safe write pattern: write tmp with `flush: true`, then `rename` onto the target. The original atomic-write work (#4292) treated fsyncing the _file_ plus the atomic `rename` as sufficient for durability.

## Problem

A power loss immediately after the `rename` could leave the destination file existing in the directory but containing null bytes or stale-inode contents — corruption survives even though every individual step "succeeded". Worst on Linux ext4 `data=ordered`; smaller windows on APFS and NTFS.

## Root cause

`rename` is _atomic_ (target is old-or-new, never partial) but that is a different guarantee from _durable_. The rename only modifies the parent directory's entry; that directory block can sit in volatile cache. `fsync` on the renamed file flushes the file's data/inode but does NOT flush the directory entry that points to it. After a crash the directory may not yet record the new entry, or may record it pointing at not-yet-flushed data blocks. The missing step: open the parent directory and `fsync` it _after_ the rename, so the directory entry is durably committed.

## Lesson

Atomic ≠ durable. The complete crash-safe write is: write tmp → `fsync(file)` (via `flush: true`) → `rename` → **`fsync(parent dir)`**. Sync the directory by `open(dirname, "r")` then `fd.sync()` (async) / `openSync` + `fsyncSync` (sync), always closing the handle in `finally`.

Two cross-platform guards that are easy to miss:

- Skip entirely on `win32` — Windows has no directory-fd fsync and `open(dir)` fails.
- On POSIX, directory `fsync` can still throw `EPERM`/`EINVAL` on some filesystems (network mounts, certain virtual FS); treat those as unsupported and swallow them (`isUnsupportedDirectorySyncError`) rather than failing the whole write. Any other error propagates.

A passing fsync on the file plus a green test suite does not prove durability — the gap only manifests on real power loss, so it will never surface in normal unit tests (the PR's integration test had to drop the FS cache on Linux to exercise it).

## Applies when

- Reviewing or writing any temp-file-then-rename atomic write that must survive power loss (settings, SQLite sidecar files, persisted state, MCP config).
- Auditing durability claims: if code fsyncs the file but not the parent directory after rename, the durability gap is still open.
- Implementing directory fsync on Windows (no-op) or on POSIX network/virtual filesystems where `fsync(dir)` returns `EPERM`/`EINVAL`.
