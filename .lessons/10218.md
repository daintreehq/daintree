## Context

IPC handlers register through `electron/ipc/define.ts`: `op()` for plain handlers and `opValidated()` (backed by `typedHandleValidated` / `typedHandleWithContextValidated` in `utils.ts`) for Zod-validated handlers taking untrusted renderer payloads. `op()` constrains its return through `SafeResult<K> = ForbidIpcEnvelopeKeys<IpcInvokeMap[K]["result"]>`. `ForbidIpcEnvelopeKeys<T>` (`shared/types/ipc/errors.ts`) is a distributive conditional resolving to the branded `IpcHandlerEnvelopeViolation` type whenever `T` carries an `ok` or `success` key, so an envelope-shaped return fails to typecheck at the registration site. It exists because security.ts auto-wraps every handler return in `{ ok: true, data }` — a handler that itself returns `{ ok: false, ... }` nests inside the success envelope and the renderer's unwrap silently swallows the inner failure (the #6020 bug class).

## Problem

The validated variants applied the guard asymmetrically: `op()` got it, `opValidated()` did not. `ValidatedPayloadHandler` / `ValidatedContextPayloadHandler` in define.ts returned the bare `Promise<IpcInvokeMap[K]["result"]>` with no `ForbidIpcEnvelopeKeys` wrapper, so a channel whose result contained `ok`/`success` compiled cleanly through `opValidated()` while the identical channel through `op()` was rejected. The hole sat on exactly the handlers processing untrusted, renderer-supplied payloads — reopening the silent-swallow bug the guard exists to prevent (#9882).

## Root cause

Two things kept the guard from flowing to the validated path. First, the validated handler types in define.ts declared the bare result type instead of `SafeResult<K>`. Second — the subtler trap — the wrappers in `utils.ts` used `as unknown as (...) => Promise<ForbidIpcEnvelopeKeys<...>>` suppression casts. A cast through `unknown` is a type ASSERTION: it tells the compiler the wrapped function satisfies the guarded signature rather than PROVING the inner handler does, so even though the outer wrapper's type mentioned `ForbidIpcEnvelopeKeys`, the constraint never propagated back to the user's handler argument — the cast was the guard's off switch. The fix routed the validated return types through `SafeResult<K>` in define.ts and DELETED the casts in utils.ts; the async wrappers were rewritten with typed args (`IpcInvokeMap[K]["args"]`, not `unknown[]`) and an explicit `Promise<ForbidIpcEnvelopeKeys<...>>` return annotation, so the handler satisfies the guard directly and needs no cast. Type-level regression tests (`define.test.ts`) assert `opValidated()` rejects `{ok}`- and `{success}`-shaped returns on both plain and `withContext` forms, anchored by an `expectTypeOf<...>().toEqualTypeOf<IpcHandlerEnvelopeViolation>()` proving the chosen channel's result genuinely brands.

## Lesson

- **An `as unknown as` cast on a boundary type erases every compile-time guard baked into that type.** utils.ts asserted `as unknown as (...) => Promise<ForbidIpcEnvelopeKeys<...>>` instead of proving it, so the constraint never reached the user's handler argument and envelope-shaped returns compiled. Treat any suppression cast on an IPC/handler/preload boundary type as a review red flag — it is the guard's off switch.
- **A compile-time invariant must be enforced on EVERY variant of a handler API, not just the canonical one.** `op()` routed returns through `SafeResult<K>`; `opValidated()`/`typedHandleValidated`/`typedHandleWithContextValidated` used the bare result — and the gap was worst-placed, since validated handlers take untrusted renderer payloads. Grep for the guard type and confirm each sibling signature routes its return through it; the guard belongs on the shared return type, not added per-path where one gets forgotten.
- **Fix a suppression cast by making the honest type checkable, not by adding another cast.** Once the wrapper was written with typed args and an explicit `Promise<ForbidIpcEnvelopeKeys<...>>` annotation, the handler satisfied the guard directly and the cast became dead weight — an `as unknown as` usually marks a spot where the surrounding types were left loose enough to require it.
- **Regression-test type-level guards at the type level, and anchor every `@ts-expect-error`.** The tests pair `@ts-expect-error` on an envelope-shaped return with an `expectTypeOf` assertion that the chosen channel's result actually brands to `IpcHandlerEnvelopeViolation` — the anchor stops the negative test passing for an unrelated reason (e.g. a different type error). A bare `@ts-expect-error` is a false-confidence test.
- **Know why the shape is forbidden:** a handler returning `{ ok: false, ... }` becomes `{ ok: true, data: { ok: false } }` under security.ts's wrap, and the renderer reads the outer success and drops the inner failure. The guard forces `throw new AppError(...)` instead — the remediation is encoded in the `IpcHandlerEnvelopeViolation` property name pointing at #6020.

## Applies when

- Adding or reviewing a new IPC handler-registration variant in `electron/ipc/define.ts` / `utils.ts` — confirm its return type routes through `SafeResult<K>` / `ForbidIpcEnvelopeKeys`, matching `op()`; a bare `IpcInvokeMap[K]["result"]` reopens the double-envelope hole.
- Seeing `as unknown as` on any typed boundary (IPC handler, store accessor, preload bridge) — it silently strips whatever compile-time guard the target type carried; prove the value satisfies the target instead of asserting it.
- A handler's `{ok:false}` / `{success:false}` return appears silently swallowed by the renderer — suspect double-enveloping under security.ts's `{ok:true, data}` wrap (#6020).
- Writing a type-level test with `@ts-expect-error` — anchor it with an `expectTypeOf` assertion proving the tested type is in the expected state, or the negative can pass for the wrong reason.
- Enforcing any invariant across a family of overloads/variants (validated vs plain, withContext vs not) — put the guard on the shared return type, never per-path where one can be missed.
