## Context

Switching the active project moves several independent subsystems to the new project: the main-process project store (`getCurrentProjectId`/`setCurrentProject`), the git cache, the log buffer, the context tracker, and the PTY host's active-project mapping (`PtyClient.onProjectSwitch`). Two code paths exist: the legacy `ProjectSwitchService.performSwitch` and the production `ProjectViewManager.switchTo` driven from `electron/ipc/handlers/projectCrud/switch.ts`, where each per-project `WebContentsView` has its own V8 context.

## Problem

A worktree-load failure during a switch left a worse state than the failure itself. The old `performSwitch` catch block reverted _only_ the PTY mapping (`onProjectSwitch(previousProjectId)` / `setActiveProject(null)`), while the store, git cache, log buffer, and context tracker had already committed to the new project earlier in the same function. Separately, the worktree-load error was never visible: the only signal was a `worktreeLoadError` field piggybacked on the `PROJECT_ON_SWITCH` broadcast, which the production view-swap path never emits — so on the live path the renderer hung on an infinite loading skeleton with no banner.

## Root cause

Two independent traps:

1. **Partial rollback in a multi-commit operation.** The catch ran _after_ most subsystems had already moved forward. Rolling back one subsystem (PTY) produced a split-brain: PTY pointing at the old project, everything else at the new one. A half-revert is more corrupt than completing the switch.
2. **A feature field rode on an event the production path doesn't send.** `worktreeLoadError` was attached to `PROJECT_ON_SWITCH`, emitted only by `ProjectSwitchService`. Production switches go through `ProjectViewManager.switchTo` + `projectCrud/switch.ts`, which call `worktreeService.loadProject` themselves and never invoke `performSwitch`. The error field was dead on the live path — green tests, no runtime signal.

## Lesson

- In a multi-subsystem switch/commit, **do not roll back one subsystem from a catch that runs after others have already committed.** Either roll back _all_ of them (a real compensating transaction) or **forward-fail** to the new state and surface the failure for recovery. Daintree chose forward-fail: drop the PTY rollback, keep all subsystems on the new project, and emit a Tier 3 inline recovery banner (`WorktreeLoadErrorBanner` + `worktree.retryProjectLoad`).
- When a status/error field is consumed in the renderer, **verify which main-process path actually emits it.** Dual switch paths (legacy `ProjectSwitchService` vs production `ProjectViewManager`/`projectCrud/switch.ts`) are easy to confuse; a field can be wired and tested yet dead because the live path never fires the carrying event. Prefer a dedicated event (`PROJECT_WORKTREE_LOAD_STATUS`) that _both_ paths emit over piggybacking on an event only one path sends.
- On the production path use a **targeted `view.webContents.send`**, not `broadcastToRenderer` — broadcast also hits LRU-cached other-project views. The renderer must still guard: ignore a `worktree-load-status` payload whose `projectId` doesn't match the view's `currentProject`, but keep the guard _permissive_ (a cold-started view with null `currentProject` still accepts the targeted event so it isn't dropped). See `projectStore.applyWorktreeLoadStatus`.

## Applies when

- Editing `ProjectSwitchService.performSwitch` or `electron/ipc/handlers/projectCrud/switch.ts`, or anything in the project-switch / `ProjectViewManager.switchTo` flow.
- Adding a `try/catch` rollback around an operation that mutates multiple stores/caches/hosts in sequence — ask whether the catch runs after some have already committed.
- A renderer field (error/status/result) is populated but never appears at runtime; suspect it rides on an event only the legacy path emits.
- Adding any IPC event consumed during a project switch in a multi-window / WebContentsView-per-project setup — decide targeted-send vs broadcast and add a `projectId` guard against LRU-cached views.
- Surfacing a worktree-load or switch failure to the user (infinite loading skeleton in the sidebar is the symptom of a dropped status event).
