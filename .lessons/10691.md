## Context

Issue #10682 asked for a structured pass/fail signal over MCP so an assistant driving Daintree could route on "did the test/lint/build actually pass" instead of scraping terminal tail output and small-model-classifying it. #10691 added `lastCheckResult` to the `terminal.getStatus` MCP tool: a pure `CheckResultDetector.detectCheckResult()` scans the agent's semantic buffer for a recognized tsc/ESLint/Vitest/Jest summary line, `AgentStateService` attaches the result to `agent:state-changed` when the agent settles out of `working` (`CHECK_SETTLE_STATES = idle | waiting | completed | exited`), and it threads through IPC into `TerminalStatusEntry.lastCheckResult`.

## Problem

The obvious designs for this signal don't work. A real subprocess exit code would be authoritative, but `node-pty` only spawns and observes the agent CLI (`claude`, `codex`, `gemini`) — when that CLI runs `npm test` as its own child process, the exit code never crosses the PTY boundary; only bytes written to the pane are visible. Shell integration (OSC 133/9;4) would give a structured start/end/exit-code marker, but it doesn't fire for a subprocess spawned by an interactive CLI rather than a shell prompt, and injecting shell-integration sequences into the agent's own session is banned outright by the Agent Config Boundary (precedent #4100 — passive observation only).

## Root cause

The only observation surface below the agent CLI is its printed stdout/stderr, so `lastCheckResult.passed` has to be derived from recognized text, not a real exit status. `CheckResultDetector` is built deliberately **precision-over-recall**: `classifySummaryLine()` only fires on a handful of exact tool-summary shapes (`Found N errors.`, `✖ N problems (N errors, N warnings)`, Vitest/Jest `Tests ... passed|failed` count rows, and package-runner failure epilogues like `npm error Lifecycle script ... failed` / `ELIFECYCLE`), chosen because they rarely appear in agent prose, at the cost of missing checks whose summary format isn't one of the four. That asymmetry is baked into the result contract: a `null`/absent `lastCheckResult` means "no recognized summary was seen," not "it passed" and not "no check ran" — three states, not a boolean. `AgentStateService.detectCheckResultOnSettle` only attempts detection at the settle transition, and skips it entirely on `respawn`, whose buffer still holds the prior session's now-irrelevant summary.

The pessimistic-verdict handling for Vitest/Jest exists because the tool prints two adjacent summary rows per run ("Test Files" then "Tests"), and a bottom-up scan hits "Tests" first — which can read all-passed while a sibling file failed to _compile_ (0 tests ran in it, so "Tests" never even mentions it). `detectCheckResult` widens ±3 lines around a passing verdict and takes the pessimistic reading if a sibling row in the same run disagrees, specifically so a compile failure can't be laundered into a clean-looking "Tests ... passed" line.

## Lesson

- **When a signal you want to expose over MCP originates inside a subprocess of the agent CLI, assume there is no exit code and no shell-integration hook available** — the PTY only carries the parent CLI's own I/O. Design the contract around parsed text from the start rather than treating parsing as a fallback for a "real" signal you'll add later.
- **Encode the three-way epistemic state explicitly, don't collapse it to a boolean.** `lastCheckResult` absent means "nothing recognized," present-with-`passed:false` means "recognized failure," present-with-`passed:true` means "recognized pass" — collapsing "absent" into "false" would make every unrecognized check silently read as a failure, and collapsing it into "true" would make every genuinely-failed-but-unrecognized check silently read as a pass.
- **Don't inject observability aids into an agent-owned PTY session, even read-only-seeming ones like shell integration.** OSC 133/9;4 was considered and rejected specifically because of the Agent Config Boundary (#4100) — this is a standing constraint on this codebase, not a one-off judgment call for this feature.
- **When a tool prints a summary across multiple adjacent lines, take the pessimistic verdict across the group, not the first line a bottom-up scan hits.** Vitest/Jest's "Test Files" + "Tests" pair is the concrete case: a rollup line can read clean while a sibling row underneath disagrees. Scope the pessimism window narrowly (±3 lines here) so an unrelated earlier run isn't pulled in.
- **A precision-over-recall parser needs a documented fallback for "not in my recognized-format list."** `terminal.getStatus`'s MCP description tells callers to cross-check with `includeOutput`/`recentOutput` rather than treating `lastCheckResult`'s absence as a verdict.

## Applies when

- Adding any MCP-exposed signal that depends on state inside a process the agent CLI spawns (test runners, linters, builds, migrations) — exit codes and shell integration are both structurally unavailable, only parsed stdout is.
- Touching `CheckResultDetector.ts`'s summary patterns (`classifySummaryLine`, `classifyTestCountRow`, `SCRIPT_FAILURE_PATTERNS`) — adding a new tool means adding a new precision-first pattern, not loosening an existing one.
- Reasoning about whether to inject OSC sequences, hooks, or config into an agent's own terminal session to make it more observable — check the Agent Config Boundary (#4100) first; passive output/process-tree observation is the only sanctioned path.
- Debugging why `lastCheckResult` is missing after an agent visibly ran and failed a check — the summary format may simply not be one of the four recognized kinds, which is working as designed, not a bug.
- Designing any multi-line tool-summary parser where an aggregate/rollup line can disagree with a sibling detail line in the same output — apply the same narrow-window pessimistic-verdict pattern used for Vitest/Jest.
