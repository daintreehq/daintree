## Context

`provision` / `teardown` / `resume` / `pause` / `status` resource actions all run shell command chains and then write `lifecycleStatus` and `resourceStatus` onto the same `WorktreeMonitor`. They fire from two unsynchronized sources: explicit user/IPC requests and a background status poll (`ResourcePollTimer` → `onResourceStatusPoll` → `runResourceAction(..., { origin: "auto-poll" })`). Coordination now lives in the dedicated `ResourceActionExecutor` (`electron/workspace-host/ResourceActionExecutor.ts`), which owns a per-worktree `Map<string, PQueue>` and `Map<string, AbortController>`.

## Problem

A slow `status` poll overlapping a user `teardown` (or two user actions racing) interleaved their `setLifecycleStatus` / `setResourceStatus` writes, so the monitor settled on whichever command's await resolved last — a freshly-torn-down worktree could flip back to `ready`, or a provision could be clobbered by a stale status read. Worse, the worktree could be removed mid-command, leaving the post-await code writing to a monitor that no longer existed.

## Root cause

These are mutating actions sharing one mutable monitor, not idempotent reads — coalescing duplicates (the #4441/#4481 git-status pattern) is insufficient because the _results_ differ and each must apply atomically. Three distinct hazards: (1) no serialization across action types; (2) the background poll queueing behind a user action would either delay the user action's slot or stack a redundant run after it; (3) any monitor reference captured before an `await runCommands(...)` is stale after the command, because removal can interleave.

## Lesson

Serialize per-worktree with `PQueue({ concurrency: 1 })` — concurrency 1 is the lock; every action type shares the one queue so a `status` can never interleave with a `teardown`. Make the background poll _yield by skipping_, not by queueing: `if (options?.origin === "auto-poll" && (queue.pending > 0 || queue.size > 0)) return { success: true }`. A skipped poll is harmless (the next tick re-polls); a queued poll would either delay the user's action or fire a redundant run right after it. Re-fetch the monitor from the registry after _every_ await (`statusMonitor` / `finalMonitor` in the executor) and bail if it's gone — never write through a pre-await reference. The same applies to `projectRootPath`. Thread one `AbortController.signal` per worktree through `PQueue.add(fn, { signal })` AND down into `runCommands`/`runSingleCommand` (which check `signal.aborted` between commands and kill the child on `abort`). On worktree removal or dispose, `cleanupResourceActionState(id)` aborts the controller and `queue.clear()`s — clearing alone drops queued work but does not cancel the in-flight child, so the signal is what actually stops a running command.

## Applies when

A per-entity (worktree/project/session) operation MUTATES shared state, runs as a long shell/IPC chain, and is triggered by both a background timer and explicit user actions. Reach for a per-entity `concurrency:1` PQueue plus an AbortController; have the timer-origin call skip when the queue is non-empty; and re-read the entity from its registry after each await rather than trusting a captured reference.
