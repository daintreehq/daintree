## Context

`VoiceTranscriptionService` streams microphone audio to a realtime speech-to-text endpoint over a WebSocket. PR #7845 replaced the Deepgram SDK with a direct connection to OpenAI's realtime WS (`wss://api.openai.com/v1/realtime`), which authenticates via an `Authorization: Bearer <key>` upgrade header plus `OpenAI-Beta`. The connection runs in the main/utility process (Node), not the renderer. The code has since been refactored into a provider abstraction; the OpenAI path now lives in `electron/services/voice/OpenAITranscriptionProvider.ts`.

## Problem

Node 22+ ships a global `WebSocket`, so reaching for the `ws` npm package looks redundant. But authenticating to the OpenAI realtime endpoint requires custom upgrade headers, and the connection fails in a way that looks like an auth-token problem (401 / immediate close) rather than a transport-library problem — the request simply arrives with no `Authorization` header.

## Root cause

The WHATWG global `WebSocket` constructor signature is `(url, protocols?)` — there is no options argument and no API for custom request headers. Passing a third options object (e.g. `{ headers: { Authorization: ... } }`) is **silently discarded** with no error or warning, so the auth header never reaches the server. Header-authenticated WS endpoints therefore always fail. The `ws` package's constructor is `(url, options)` and supports `options.headers` for the HTTP upgrade request (this is also what the OpenAI SDK uses internally). Browser-context WebSockets (renderer) have the same WHATWG limitation, which is one reason the connection lives in the Node process.

## Lesson

- For any Node-side WebSocket that needs custom upgrade headers (bearer auth, beta flags, org/project IDs), import `WebSocket from "ws"` and use the 2-arg `new WebSocket(url, { headers: {...} })` form. Do NOT use Node's global `WebSocket` — it takes only `(url, protocols?)` and silently drops options.
- A verbatim warning comment is parked at `OpenAITranscriptionProvider.ts:139-143`; keep it when refactoring so the next person doesn't "simplify" back to the global.
- Header auth on a WS that fails to connect: before assuming the token/key is wrong, verify the transport actually sends the header. The symptom (401/close) misattributes a transport-library bug to credentials.
- Graceful stop of a realtime audio stream is not just "close the socket": send `input_audio_buffer.commit` to flush the trailing segment, then bound the wait with a `DRAIN_TIMEOUT_MS` (3s) that force-closes if the final `...transcription.completed` never arrives. (#7845 also added a 100ms drain-grace timer to absorb late `server_vad` auto-commits; that specific machinery was later superseded when the provider moved to client-side VAD — `hasServerVAD = false` — but the commit + bounded-timeout drain pattern remains.)

## Applies when

- Opening any WebSocket from the Electron main process or a utility-process host (pty-host, workspace-host) that needs custom HTTP upgrade headers — bearer tokens, `OpenAI-Beta`, org/project IDs, API keys.
- Authenticating to OpenAI realtime, Deepgram, or any header-auth streaming WS API and getting an immediate 401/close that looks like a bad credential.
- Touching `electron/services/voice/OpenAITranscriptionProvider.ts`, `DeepgramTranscriptionProvider.ts`, or `VoiceTranscriptionService.ts`.
- Reviewing a change that swaps `import WebSocket from "ws"` for the Node global, or "removes the redundant ws dependency."
- Implementing graceful shutdown of a streaming audio/transcription session — flushing trailing data with an explicit commit and a bounded force-close timeout rather than dropping the socket.
