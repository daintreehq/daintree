## Context

`HelpSessionService` (main process) provisions a sandboxed assistant backend per project: it mints a bearer token, writes a session-dir `.mcp.json`, and a help-flavored PTY spawns the agent CLI. The single-backend invariant requires at most one live assistant PTY per project, because an orphaned PTY keeps dispatching MCP tool calls under a still-valid bearer.

## Problem

On session restart/re-provision the renderer's cooperative cleanup paths (`removePanel`, `gracefulKill` on hibernate, `visibilitychange` teardown) issued a fire-and-forget kill IPC for the old PTY. A dropped call, a crash, a project switch, or a race against the new spawn left the old backend process alive while a new one started — two backends for one project, the orphan still executing tool calls under its (not-yet-revoked) bearer.

## Root cause

A lifecycle invariant was owned by the wrong process. The renderer can request cleanup but cannot guarantee it: fire-and-forget IPC has no delivery guarantee across drops, and even a delivered kill races a concurrently-arriving new spawn. The authoritative owner of the resource (the main process, which mints tokens and holds the `PtyKillClient`) is the only place that can make displacement atomic with provisioning. The fix moves enforcement to `doProvision`: `displacePriorSessions(projectId)` runs inside the per-path `provisionLocks` BEFORE writing the new `.mcp.json` (`HelpSessionService.ts:499`). It marks the prior record `revoked` FIRST — so any in-flight MCP call from the orphan 401s before the kill IPC even reaches the PTY host — then kills the bound PTY and tears down its MCP transport. Two more enforcement layers cover races the provision lock can't: `markTerminalForToken` (called from `lifecycle.ts:339` after spawn) kills any terminal still bound to the project slot, and a re-check of `record.revoked` after the `gracefulKill` await (`HelpSessionService.ts:861`) detects losing the slot to a sibling re-provision so cleanup doesn't clobber the winner.

## Lesson

- A cleanup invariant that must always hold belongs to the process that authoritatively owns the resource, not the process that happens to trigger the lifecycle event. Renderer-issued kill IPC is best-effort defense-in-depth, never the guarantee.
- Enforce "at most one X" by displacing the prior X at the moment you create the new one, under the same lock that serializes creation — don't rely on the previous owner having cleaned up.
- Revoke the credential before issuing the async kill, so an in-flight request from the doomed process fails authorization rather than completing during the kill window.
- After any `await` inside a teardown path, re-read the ownership flag before mutating shared maps: a concurrent provision may have legitimately taken over the slot while you were suspended.

## Applies when

- Adding or changing help-session / assistant-backend provisioning, revoke, or hibernate/resume in `electron/services/HelpSessionService.ts` or the terminal spawn handler `electron/ipc/handlers/terminal/lifecycle.ts`.
- Any "single live X per project/window/key" invariant where one process spawns/kills and another triggers cleanup (PTY processes, MCP transports, MessagePort channels, WebContentsView slots).
- Reviewing fire-and-forget `*.kill` / teardown IPC issued from the renderer that is assumed to have completed before a new resource is created.
- Symptoms: orphaned PTY still emitting output or MCP tool calls after a restart; two backends for one project; stale bearer/grants lingering until an idle reaper; a teardown clobbering a freshly-provisioned successor.
- Designing concurrency around `provisionLocks`-style per-key locks where displacement must be atomic with creation, and post-`await` race guards in teardown.
