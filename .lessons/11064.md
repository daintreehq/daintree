## Context

`mcpSpawnFocusGuard.ts` backs the ambient focus-suppression net for MCP-dispatched actions (#6959): `useMcpBridge` wraps every action the MCP bridge dispatches in `runWithMcpSpawnFocusSuppressed`, and while that wrapper is "open" any panel spawned indirectly (a handler that doesn't thread `focusPolicy` through its own args) resolves `focusPolicy` to `"preserve"` instead of stealing focus. Direct spawn actions (`recipe.run`, `terminal.new`, `agent.*`, etc., listed in `MCP_SPAWN_TAGGED_ACTIONS`) don't need this — `tagMcpSpawnSource` stamps `focusPolicy: "preserve"` onto their args explicitly; the guard exists only for the indirect cases that fall through that net. Each project gets its own long-lived `WebContentsView`/V8 context (`ProjectViewManager`), so any module-level state in this file lives for the whole life of that project view, not a single dispatch.

## Problem

In exactly one project, clicking the dock's `+` to launch an agent added the panel chip but the dock popover never auto-opened — every subsequent `addPanel` in that project silently behaved as if focus should be preserved. The same launch worked fine in every other open project, and restarting the app cleared it. That project-scoped, restart-clearing signature pointed at per-project state, not a global regression, which is why it took a while to trace back to a single shared module.

## Root cause

The guard was a plain module-level depth counter: `mcpSpawnFocusSuppressionDepth += 1` on entry, `Math.max(0, ... - 1)` in a `finally` on exit, `isMcpSpawnFocusSuppressed()` just checked `depth > 0`. That's correct only if every increment is guaranteed a matching decrement. It isn't: Main's MCP bridge (`electron/services/mcp-server/rendererBridge.ts`) abandons a dispatch after `MCP_DISPATCH_TIMEOUT_MS` (30s, `shared.ts`) if the renderer never replies, but it never cancels the renderer-side action promise. If that handler is awaiting something unbounded — a confirm dialog that never resolves, a hung IPC round-trip — the renderer's `await fn()` in `runWithMcpSpawnFocusSuppressed` never returns, its `finally` never runs, and the counter is stuck above zero for the remaining lifetime of that project's V8 context. Every later panel creation in that project then reads `isMcpSpawnFocusSuppressed() === true` and forces `focusPolicy: "preserve"` (consumed in `panelSpawning.ts`, `panelStore.ts`, `useAgentLauncher.ts`, `recipeStore.ts`) — the dock-popover-never-opens symptom, project-scoped because each project view is its own context, restart-clearing because a fresh context zeroes the module state.

The fix replaces the counter with a `Map<number, SuppressionLease>` keyed by a monotonically-increasing `nextLeaseId`, each lease stamped with `startedAt` and a `LEASE_TTL_MS` of 45s (30s main timeout + grace). `isMcpSpawnFocusSuppressed()` iterates leases and only counts ones younger than the TTL as suppressing; an aged-out lease logs a one-shot `logWarn` naming the hung action (`label`, threaded from `useMcpBridge`'s dispatch call) and is thereafter ignored for suppression, though it stays in the map — removed only by its own `finally: activeLeases.delete(leaseId)` if the handler eventually settles. A naive "just add a timeout" fix would miss this: a late settle must release _only its own_ lease, never decrement-and-underflow a shared counter the way the old code could.

## Lesson

- **A refcount/depth-counter guard around an RPC is only sound if every increment is provably paired with a decrement.** The moment one side of the RPC can time out or abandon without cancelling the other side, the counter can wedge permanently — replace it with per-call leases that expire on their own, not a shared mutable count.
- **Size the lease TTL off the call's own timeout budget, not an arbitrary guess.** `LEASE_TTL_MS = 45_000` is deliberately `MCP_DISPATCH_TIMEOUT_MS` (30s) plus grace — if the timeout constant ever changes, the lease TTL needs to move with it or it either expires before Main gives up (false negative) or lingers unnecessarily.
- **Module-level mutable state inside `src/store/` or `src/hooks/` is per-project-view lifetime, not per-call, per-window, or global** — Daintree's `ProjectViewManager` gives each project its own long-lived V8 context, so a leaked increment there survives until that project's view reloads or the app restarts, and reproduces in exactly one project while every other project looks fine. That "only one project, restart clears it" signature is itself diagnostic for this class of bug.
- **When you can't cancel the other side of an async boundary, expire your own side's assumption about it instead of trying to make cancellation reach across the boundary.** Main not cancelling the renderer dispatch on timeout is a fact to design around here, not a bug to fix in this PR — the lease TTL absorbs it.
- **Log the specific identifier that wedged, not just "a lease expired."** The `label` parameter threaded from `useMcpBridge`'s call site into the lease lets `logWarn` name the actual `actionId` that hung, turning a silent forever-stuck guard into a diagnosable one-shot warning if it recurs.

## Applies when

- Touching `src/store/mcpSpawnFocusGuard.ts`, `src/hooks/useMcpBridge.ts`, or the MCP dispatch path in `electron/services/mcp-server/rendererBridge.ts`.
- Diagnosing "works in every project except this one, and a restart fixes it" — that signature means per-project-view module state, not a global condition; check for an unpaired increment/decrement guard.
- Writing or reviewing any counter/flag that's incremented before an awaited async call and decremented in a `finally`, where the async call crosses an IPC or RPC boundary that can time out on the other side without notifying this side.
- Changing `MCP_DISPATCH_TIMEOUT_MS` in `electron/services/mcp-server/shared.ts` — the renderer-side `LEASE_TTL_MS` in `mcpSpawnFocusGuard.ts` is derived from it and needs to stay in lockstep.
- Adding a new ambient/ex-band suppression flag anywhere in the panel-spawn or focus-policy path (`panelSpawning.ts`, `panelStore.ts`, `useAgentLauncher.ts`, `recipeStore.ts`) — prefer a leased/expiring primitive over a raw counter or boolean from the start.
