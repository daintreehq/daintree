## Context

`CrashRecoveryService` (`electron/services/CrashRecoveryService.ts`) writes a `running.lock` marker on launch and a debounced `session-state.json` backup during the session. On the next launch, if the marker is still present the previous session crashed, so `consumeMarker()` reads the marker, preserves the backup for the recovery dialog, then deletes the marker.

## Problem

A kill (SIGKILL, OOM killer, force-quit, power loss) **during the recovery path itself** could silently drop crash detection. The old flow deleted the marker before durably preserving the backup, and used an in-memory snapshot. If the process died in that window the marker was gone (so the next launch saw no crash) while the live backup could still be clobbered by the new session's first backup tick — the very mechanism meant to survive crashes had a window where a crash erased its own evidence.

## Root cause

The recovery routine was not itself crash-safe. Two coupled ordering/atomicity bugs:

- **Delete-before-preserve ordering:** `deleteMarker()` ran before the backup was moved aside. A crash between the two ops removed the crash signal but left the backup exposed to overwrite.
- **Non-idempotent consumption:** there was no on-disk artifact a retried `consumeMarker()` could reuse, so a partially-completed recovery could neither be detected nor resumed.

The fix (`consumeMarker` / `preserveBackupForRecovery`, lines ~430-561):

- Reorders to **preserve-before-delete** — `preserveBackupForRecovery(marker.sessionStartMs)` runs first, `deleteMarker()` second.
- Renames the live backup to a deterministic `session-state.crashed-{sessionStartMs}.json` (the `sessionStartMs` key makes it **idempotent**: if a prior killed attempt already produced the file, `fs.existsSync(crashedBackupPath)` short-circuits and reuses it rather than re-renaming a now-missing source).
- Uses `resilientRenameSync` (stubborn-fs retry, ~500ms) for atomicity, with a **copy-then-unlink fallback** because on Windows `rename` transiently fails under antivirus/search-indexer locks (`EPERM`/`EBUSY`/`EACCES`) — a plain rename would lose the snapshot.
- Gates `hasBackup` on parseability and caches the parsed `SessionSnapshot` in memory so a concurrent overwrite/delete between consumption and the user clicking restore can't break the dialog.

## Lesson

Treat the crash-recovery path as code that must survive a crash mid-execution, not just code that runs after one:

- **Order durability-first:** preserve/move the recoverable artifact BEFORE deleting the signal that says "recovery is needed." Never delete the marker, lock, or sentinel before the thing it points at is durably safe.
- **Make consumption idempotent with a deterministic on-disk key** (here: `sessionStartMs` in the filename). A re-run after a partial kill must detect and reuse the in-progress artifact, never assume a fresh start.
- **Prefer atomic rename, but always provide a copy-then-unlink fallback on Windows** — `rename` is not reliably atomic there under AV/indexer locks (`EPERM`/`EBUSY`/`EACCES`); use `resilientRenameSync`/`resilientAtomicWriteFileSync` from `electron/utils/fs.ts`.
- **Cache the parsed payload in memory** once consumed so later UI steps don't re-read a file a concurrent session may have mutated.

## Applies when

- Editing `CrashRecoveryService` marker/backup lifecycle: `consumeMarker`, `preserveBackupForRecovery`, `deleteMarker`, `writeMarker`, `mutateMarker`, `cleanupOrphanedCrashedBackups`.
- Writing any "consume a sentinel on next launch" recovery flow — crash markers, `running.lock` files, restore-confirmation state, pending-operation journals, trashed-PID lists.
- Any code that deletes a flag/lock/marker and separately preserves the data it guards — check the ordering and what happens if the process dies between the two operations.
- Moving files aside on Windows where AV/indexer locks cause transient `EPERM`/`EBUSY`/`EACCES` on `rename`.
- Adding crash-cause attribution: `classifyCrashCause`, `hasRecentCrashpadDump` (scans Crashpad `new`/`pending`/`completed` for `.dmp` newer than `sessionStartMs`), `didSystemReboot` (`os.uptime() < elapsed`, reliable positively only — sleep/Fast-Startup pause uptime), `isHeartbeatStale` (>120s marker heartbeat ⇒ external kill).
