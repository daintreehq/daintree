## Context

Forge providers are plugin contributions: the manifest declares a `forgeProviders[].id`, and the runtime identity is the canonical `{pluginId}.{contributionId}` built by `makeForgeProviderId` (`shared/utils/forgeProviderIds.ts`, e.g. `BUILTIN_GITHUB_PROVIDER_ID = "daintree.github.github"`). Commit `4ea2532c6` (issue #8451, 2026-05-19) had already canonicalized the typed corridors — impl registry keys, credential storage, resolver, `projectSettingsCodec`, workspace-host wiring — and shipped `normalizeProviderId` for legacy persisted forms. The settings dialog's Code Forge tab (`CodeForgeSettingsTab`) routes per-provider subtabs and is deep-linked from all over the app via `app.settings.openTab` args.

## Problem

Entirely latent with one provider, broken the moment a second lands (issue #9968). The settings subtab routing, `selectedEntry` lookup, and React keys all used the bare `contribution.id`: two plugins each contributing `"gitlab"` would produce duplicate React keys and make the second provider permanently unreachable (`providers.find(...)` returns the first match). Worse, `GITHUB_ID = "github"` was hardcoded as the default subtab and icon match, so a third-party plugin whose contribution happened to be named `"github"` routed to the built-in `GitHubSettingsTab` — rendering GitHub branding and the real token form for an unrelated provider. Misleading part: the credential-storage code a few lines below in the same component was already canonical, so the file looked migrated at a glance.

## Root cause

Two mechanisms compound. First, bare contribution ids have no global uniqueness anywhere: `ForgeProviderContributionSchema.id` is validated only as a `SAFE_ID_PATTERN` string (≤64 chars), and the reserved-namespace `superRefine` in `electron/schemas/plugin.ts` applies to the plugin _name_, not contribution ids — `"github"` is a perfectly legal third-party contribution id today. Uniqueness exists only in the canonical composite, so any surface comparing, keying, or persisting the bare id is structurally collision-prone regardless of validation.

Second, the #8451 canonicalization sweep missed this surface because deep-link payloads are stringly typed. `app.settings.openTab` args carry `subtab: string`, so the literal `{ tab: "code-forge", subtab: "github" }` sat inert in ~8 call sites (`settingsTabRegistry`, `GitHubTokenBanner`, `GitHubStatsToolbarButton`, `UpstreamSyncBadge`, `useGitHubBadgeTooltip`, `useGitHubTokenExpiryNotification`, `gitOperationErrors` `RECOVERY_ACTIONS`, plus the `FORGE_CLASSIFY_PUSH_ERROR` IPC handler returning the bare resolved id) with zero compiler signal. #10109 flipped every site to `BUILTIN_GITHUB_PROVIDER_ID`, made the IPC classifier return `namespaceId` (the canonical id), and added `normalizeProviderId` at the `useSettingsDialog` read boundary so in-flight legacy bare ids still land.

## Lesson

- **Never key a cross-plugin surface on a bare `contribution.id`** — routing, selection lookups, React keys, persistence, IPC payloads all take `makeForgeProviderId(pluginId, contribution.id)`. The manifest schema will never enforce global uniqueness of contribution ids (only `SAFE_ID_PATTERN`), so uniqueness lives solely in the composite. This applies to any future contribution kind, not just forge providers.
- **A hardcoded well-known bare id in shared UI is a hijack vector.** `id === "github"` matched any plugin's `"github"` contribution and handed it the built-in card, branding, and token form. Special-case built-ins only via the canonical constant (`BUILTIN_GITHUB_PROVIDER_ID`); the reserved-namespace check on plugin names protects the _prefix_, and only the composite id inherits that protection.
- **Id-canonicalization sweeps die in the stringly-typed corridors.** #8451 got every typed registry key but left 8 deep-link/action-arg/IPC sites on the bare literal because `subtab` is `string`. When migrating an id space, grep for the literal in action args, `openTab`/deep-link payloads, IPC return values, and test fixtures — the compiler flags none of them.
- **Normalize legacy forms at read boundaries only, and pass unknowns through.** `normalizeProviderId` maps exactly the known legacy forms (`"github"`, `"builtin.github"`) to canonical, passes unrecognized non-empty strings unchanged (rewriting them would clear valid third-party overrides), and returns `null` for non-string/empty so callers get "no override" without a second guard. It now guards many boundaries beyond this PR: `forgeSettings`/`forgeData`/`forgeResolution` handlers, `projectSettingsCodec`, `WorkspaceHostPool`.
- **Current-state note:** `GITHUB_ID` and `getForgeIcon` are gone from `CodeForgeSettingsTab` — a later refactor made it fully provider-generic (icon via `contribution.slots?.icon`; an unknown subtab now falls back to General or the first registered provider, not GitHub). `ForgeProviderSelectorDropdown` still compares `BUILTIN_GITHUB_PROVIDER_ID` for the brand icon. The GitLab builtin (draft PR #11062) is the second provider that makes all of this live.

## Applies when

- Adding a forge provider plugin (GitLab #11062, Gitea, or third-party) or any code that compares, stores, or routes a forge provider identity — the id must be the canonical `{pluginId}.{contributionId}`.
- Deep-linking into settings with `app.settings.openTab` and `tab: "code-forge"` — the `subtab` arg is a canonical provider id or `"general"`; a bare id only survives via the `normalizeProviderId` shim in `useSettingsDialog`.
- Designing a new plugin contribution kind (panel, agent, toolbar button, settings section) and deciding what registries/UI/persistence key on — contribution ids are per-plugin-unique only, and the reserved-namespace check does not cover them.
- Performing or reviewing any id-space canonicalization — checklist beyond registry keys: action args, deep-link payloads, IPC return shapes (`shared/types/ipc/api.ts` doc contracts), React keys, default/fallback constants, and test fixtures.
- Tempted to special-case a built-in by matching its bare name (`id === "github"`) in a component third-party contributions also flow through.
