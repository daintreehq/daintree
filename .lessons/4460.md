## Context

Daintree polls `git status` across every worktree every 2-10s through a concurrency-limited poll queue, using `createHardenedGit` (`electron/utils/hardenedGit.ts`). The hardened factory passes a `HARDENED_GIT_CONFIG` (now `SAFE_GIT_CONFIG`) array of `-c` overrides to neutralize dangerous repo config (hooks, credentials, SSH, proxy) on every spawned git command.

## Problem

PR #4460 set `core.fsmonitor=true` and `core.untrackedCache=true` to speed up the polling hot path, on the theory that fsmonitor is a pure performance feature mistakenly grouped with the security overrides. In practice, enabling fsmonitor across many sibling worktrees corrupted status results: concurrent `git status` calls returned the wrong worktree's changed-file set, so a worktree could show another worktree's modifications. Commit `0869bef39` reverted both flags back to `false` and added a concurrent-worktree isolation regression test in `electron/utils/__tests__/git.test.ts`.

## Root cause

`core.fsmonitor` is not free or isolated per command. It starts (or attaches to) a long-lived `git fsmonitor--daemon` keyed by working-tree path, and the daemon's cached filesystem-event state is shared/raced when many worktrees run `git status` simultaneously under the poll queue. That shared daemon state bled across worktree boundaries, producing cross-contaminated status output — a correctness bug, not just a perf wash. `core.untrackedCache` was disabled in the same commit because it persists state into the index and offers no benefit once fsmonitor is off.

## Lesson

- **fsmonitor is stateful and shared, not a per-invocation flag.** It is safe for a single repo with a single status consumer, but in a multi-worktree polling system the daemon's cross-process cache makes concurrent status calls race. Treat it as a correctness risk, not a tuning knob.
- **The original "fsmonitor is just perf, safe to enable" framing was wrong here** — not because of security, but because of concurrency. Enabling a daemon-backed cache under N concurrent status pollers is the actual trap.
- **Throttle the pollers too.** The same commit routed `refreshAll()` through the poll queue (`concurrency: 3`) instead of unthrottled `Promise.all()`, limiting concurrent git processes at startup. Bounding concurrency is the durable fix; the config flags were a false shortcut.
- Current truth: `SAFE_GIT_CONFIG` pins `core.fsmonitor=false` and `core.untrackedCache=false`; tests assert both (`electron/utils/__tests__/hardenedGit.test.ts`).

## Applies when

You are tempted to enable `core.fsmonitor` / `core.untrackedCache` (or any daemon-backed git cache) to speed up status, AND multiple worktrees or repos run `git status` concurrently from the same process. The symptom is one worktree reporting another's changed files. Prefer bounding poller concurrency over a shared-state cache flag.
