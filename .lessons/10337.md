## Context

The marketing pipeline (`screenshots.yml`) ran the `screenshots` Playwright project to capture store PNGs on a hosted `macos-14` runner. That project's `testDir` was `./e2e/screenshots`, which also held two demo-engine specs (`demo-reel.spec.ts`, `demo-terminal-input.spec.ts`) that drive the in-app `window.electron.demo` API to record a 4K `.webm` and script terminal input. `demo-reel` asserts the recorded frame equals the 4K preset (`CAPTURE_W`/`CAPTURE_H`, the #10152 regression guard). #10334 was the tourniquet; #10337 is the structural fix; #10333 tracked it.

## Problem

The Marketing Screenshots workflow went red even though all six store PNGs captured and uploaded fine. `--project=screenshots` swept in the two demo specs — neither a marketing deliverable — and they failed hard on the hosted runner: `expect(dims.height).toBe(2160)` got `1940`, plus intermittent crashes on parallel launch. The red status pointed at the screenshot pipeline, but the screenshot output was perfect; the failing specs just happened to share a directory with it.

## Root cause

Three independent hosted-runner traps, coupled by one Playwright fact: **a project runs every spec under its `testDir`, so co-locating unrelated specs merges their pass/fail into a single workflow gate.** (1) The hosted `macos-14` runner's virtual display is only ~`1176x885` logical, so `getDisplayMedia` can never source a 2160-tall frame — the 4K dimension pin is physically unsatisfiable there and returned `1940`. (2) The specs ran under `workers: 2`; parallel _cold Electron launches_ contend on the **crashpad Mach port** (the crash reporter's port registration), a known first-launch flake source in this repo — see `e2e/helpers/launch.ts` ("Zombie crashpad helpers ... can hold Mach ports and contribute to first-launch flakes") and `e2e/screenshots/theme-review.spec.ts`'s crashpad/GPU mitigations. (3) `createBrushCmsRepo()` built a fixed-slug fixture at `/tmp/daintree-demos/brush-cms`; `store-reel` scene-2 and `demo-reel` both delete-and-recreate it, so concurrent workers raced the same path.

#10334 first scoped `screenshots.yml` to exact spec paths (not the bare `--project`). #10337 then split the specs into `e2e/demo/` + a dedicated `demo` project (`git mv`), baked `workers: 1` / `retries: 0` into it, worker-suffixed the fixture, and CI-gated the strict dimension assert — all still live in `playwright.config.ts` and `e2e/demo/demo-reel.spec.ts`. One drift: #10337's `e2e-demo` job in `nightly.yml` is gone (the cron test suite was replaced by `stabilize.yml`; only `nightly-publish.yml` remains cron), so `demo` now runs on-demand via `e2e.yml`'s `suite: demo` only.

## Lesson

- **A Playwright project is defined by its `testDir` — every spec in that directory runs under it and shares its workflow's red/green.** Don't co-locate a heavy/flaky non-deliverable spec next to a deliverable one; `--project=X` can't cherry-pick. Fix cheaply by scoping the workflow to exact spec paths (#10334), properly by moving specs to their own `testDir` + project (#10337). If a workflow's status disagrees with its artifact output, suspect an unrelated spec riding the same project.
- **Hosted CI runners have a small logical virtual display (~1176x885 on `macos-14`), so any screencast/`getDisplayMedia` capture is capped well below 4K — an exact 2160-tall assertion can never pass there.** Gate the strict dimension pin behind `!process.env.CI || process.env.DAINTREE_DEMO_STRICT_DIMS === "1"`; on hosted CI assert only a non-degenerate frame (`toBeGreaterThan(0)`). Compare `=== "1"` explicitly so `DAINTREE_DEMO_STRICT_DIMS=0` reads as off, not truthy. This keeps the #10152 regression guard alive for local + opt-in self-hosted runs.
- **`workers: 1` for cold-Electron-launch specs must be baked into the _project config_, not just passed as a CLI flag.** Parallel cold launches contend on the crashpad Mach port. A bare local `npx playwright test --project=demo` won't get `--workers=1` from CI, so the serialization has to live in `playwright.config.ts`; `e2e.yml` still passes `--workers=1` as belt-and-suspenders for `nightly`/`demo`.
- **Fixed-path `/tmp` fixtures race across specs and workers — suffix them per worker.** `createBrushCmsRepo(suffix = "")` now slugs `brush-cms-${suffix}` and `demo-reel` passes `TEST_WORKER_INDEX`; two specs that delete-and-recreate the same `/tmp/daintree-demos/<slug>` collide otherwise.
- **A capture/recording job that produces no release artifact must never gate the deliverable's workflow.** #10337 kept `demo` out of `publish.needs` — a 30-min screencast job can't block binary publish.

## Applies when

- Adding or moving a Playwright spec, or seeing a marketing/screenshot/publish workflow go red while its actual artifacts uploaded fine — check whether an unrelated spec shares the project's `testDir`.
- Writing any test that records a screencast or calls `getDisplayMedia`/`window.electron.demo` and asserts exact frame dimensions — the hosted runner's display can't reach 4K; gate strict dims behind `!CI || DAINTREE_DEMO_STRICT_DIMS=1`.
- Touching `playwright.config.ts` projects, `e2e/demo/`, or any suite that cold-launches Electron in parallel — bake `workers: 1` into the project (crashpad Mach-port contention), don't rely on a CLI flag.
- Diagnosing intermittent first-launch Electron flake in E2E — grep crashpad/Mach-port notes in `e2e/helpers/launch.ts`; serialization is usually the fix.
- Reusing `createBrushCmsRepo` / `createDemoRepo` or any `/tmp/daintree-demos/*` fixture across specs — pass a `TEST_WORKER_INDEX` suffix.
