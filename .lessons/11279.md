## Context

PR #11279 fixed two unrelated bugs found in one pass over `Panel/*`: rename fields sitting on a drag surface, and a pre-existing React Compiler violation in `DeletedWorktreeCard.tsx` (from commit `e24bf309b`). Panel drag-and-drop runs through `DndProvider.tsx`'s `NoDndMouseSensor`/`NoDndTouchSensor`, whose activators call `isNoDndTarget()` (`.closest("[data-no-dnd]")`) before arming a panel-move drag. The tab strip nests a SECOND, independent DndContext for tab reordering: `tabSensors` in `PanelHeader.tsx`, built from plain upstream `PointerSensor`/`TouchSensor`. Separately, `DeletedWorktreeCard.tsx`'s held-countdown display captured a value in a `useRef` written and read during render — flagged by the React Compiler and tracked per-file via `scripts/check-compiler-budget.mjs` (`npm run compiler-budget:critical`).

## Problem

Two symptoms. First: drag-selecting text inside a panel's or a tab's inline rename field could pick the whole panel/tab up and start a drag instead of selecting text — worse on touch, where a long-press to select text armed the drag. Second: `DeletedWorktreeCard.tsx` alone carried 9 of the codebase's 13 total `compiler-budget:critical` errors.

## Root cause

Two independent mechanisms landed in the same PR.

`data-no-dnd` is not a DOM/ARIA-level opt-out — it's a convention only understood by sensors written to check it. `NoDndMouseSensor`/`NoDndTouchSensor` call `isNoDndTarget()` inside their activator before invoking `onActivation`, so marking the panel-header rename `<input>` with `data-no-dnd` stopped the OUTER panel-move drag on both mouse and long-press. But the tab strip's reorder drag is a SEPARATE DndContext (`tabSensors` in `PanelHeader.tsx`) built from raw upstream `PointerSensor`/`TouchSensor` — neither has ever heard of `[data-no-dnd]`, because that check lives only in Daintree's `NoDnd*` subclasses, not upstream dnd-kit. A `touchstart` on `TabButton`'s rename field bubbled straight into the reorder sensor and armed a tab drag, even though the equivalent `pointerdown` was already guarded by an existing `handleInputPointerDown` stopPropagation — the fix for one input path did not cover the other because they run through two different sensor trees. The real fix stops propagation on the raw DOM event (`e.stopPropagation()` in a new `handleInputTouchStart`, wired to `onTouchStart`), not another data attribute, since the raw `TouchSensor` never looks for one.

The ref bug violates a real React invariant, not just compiler style: a ref write during render schedules no re-render, so if a later frame changes only via a ref mutation, a memoized subtree downstream has no signal to re-run and can freeze on a stale value indefinitely. `heldRemainingRef.current = {...}` written then read (`heldRemainingRef.current?.remainingMs`) in the same function body is exactly that shape. The fix moves the captured value into `useState`, conditionally calling `setHeldRemaining` inside the render body when a derived `holdKey` (built from props already in scope) changes — the "adjust state when a prop changes" pattern. React re-runs the component synchronously before paint, so there's no user-visible torn frame, and the compiler can see and memoize around it.

## Lesson

- **`data-no-dnd` only works against sensors explicitly written to check it** (`NoDndMouseSensor`/`NoDndTouchSensor`). A raw upstream `PointerSensor`/`TouchSensor`/`MouseSensor` — used by any nested DndContext, like the tab-reorder `tabSensors` in `PanelHeader.tsx` — ignores it completely.
- When an element sits inside more than one drag surface (a tab is covered by both the panel-move drag AND the tab-reorder drag), **audit every DndContext it's nested inside separately** — fixing the outer one and assuming the inner one inherited the fix is exactly the bug #11279 fixed.
- If a sensor can't be taught `[data-no-dnd]` (raw upstream sensors can't), **stop the event at the DOM level instead**, matched to the exact event name the sensor's activator listens for (`touchstart` → `onTouchStart` calling `e.stopPropagation()`).
- **A ref written and read within the same render is a genuine repaint hazard, not just a compiler nag**: the write schedules nothing, so a memoized consumer downstream has no way to learn the value changed. Before silencing the error, check whether the ref's value is derivable from current props/state.
- When it is derivable, **use the "adjust state when a prop changes" pattern**: conditionally call `setState` in the render body keyed off a derived comparison key (here `holdKey`), falling back to the freshly-derived value on the render where state hasn't caught up. `DeletedWorktreeCard.tsx` went from 9 errors to a clean `CompileSuccess` this way, not merely fewer bailouts.
- Contrast with #10426's `useColdNumberGap`/`useContentGridContext`: those deliberately read `ref.current`/`getState()` at render because the value is NOT derivable from tracked state, and correctly keep `"use no memo"`. Check derivability before assuming a render-time ref read belongs in that category.

## Applies when

- Adding an inline-editable control inside anything wrapped by a dnd-kit sortable/draggable — check EVERY ancestor DndContext's sensor list, not just the nearest one, for whether it's a `NoDnd*` variant or a raw upstream sensor.
- Touching `src/components/Panel/PanelHeader.tsx`'s `tabSensors`, `src/components/Panel/TabButton.tsx`, or `DndProvider.tsx`'s `NoDndMouseSensor`/`NoDndTouchSensor`/`isNoDndTarget`.
- A drag element with text-selection or click-to-edit behavior starts a drag on touch/long-press specifically, while the equivalent mouse path already works — suspect a second, unguarded sensor pairing, not a broken `data-no-dnd`.
- Seeing a React Compiler error on a `useRef` set and read in the component body — before adding `"use no memo"`, check whether the value is derivable from render inputs; if so, prefer the `setState`-in-render pattern from `DeletedWorktreeCard.tsx`.
- Investigating `compiler-budget:critical` regressions (`scripts/check-compiler-budget.mjs`) — a single file's ref pattern can dominate the whole codebase's error count (9 of 13 here).
