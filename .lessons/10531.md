## Context

`@daintreehq/plugin-sdk` is a types-only barrel published to plugin authors. It has two stacked re-export layers: the source-of-truth barrel `shared/types/plugin-sdk.ts`, and the npm package entry `packages/plugin-sdk/src/index.ts` whose line 1 is `export type * from "../../../shared/types/plugin-sdk.js"`. tsup builds it with `dts: { resolve: true }` — the emitted `dist/index.js` is effectively empty and `dist/index.d.ts` carries the whole surface (see the "Types-only barrel" comment in `packages/plugin-sdk/tsup.config.ts`). #10531 was adding forge domain types and the process-stream event/channel so authors could implement documented patterns (forge providers, process-streaming panels) against only the public SDK.

## Problem

`PLUGIN_PROCESS_STREAM_CHANNEL` (value `"process"`) looked correctly exported and type-checked in author code, but `plugin.on(pluginId, PLUGIN_PROCESS_STREAM_CHANNEL)` received `undefined` at runtime — the panel silently subscribed to no channel and never saw the child process's stdout/stderr/exit/crash stream. There was no compile error anywhere: the constant's type survived the re-export intact, so every `expectTypeOf` assertion passed while the actual value was gone.

## Root cause

`export type *` (and `export type { ... }`) is a _type-only_ re-export: at emit it strips ALL value bindings and re-exports only the types. A `const` surfaced through such a wildcard type-checks perfectly for consumers (the type is preserved) but its runtime value resolves to `undefined` — the emitted JS never binds it. `PLUGIN_PROCESS_STREAM_CHANNEL` was reaching authors through the `export type *` in `packages/plugin-sdk/src/index.ts`, so the string was erased. The fix is an explicit named _value_ re-export line per runtime const the SDK surfaces: `export { PLUGIN_PROCESS_STREAM_CHANNEL } from "...plugin-sdk.js"` in the package entry, plus a value (not `export type`) re-export in the source barrel `shared/types/plugin-sdk.ts`. Both layers matter — the value is erased at whichever layer uses `export type`.

A second, independent emit trap rides the same constant: `PLUGIN_PROCESS_STREAM_CHANNEL = "process" as const`. Without `as const`, the re-exported constant widens to `string` in the composite build's emitted `.d.ts`, which breaks the literal channel-key narrowing `plugin.on(pluginId, "process")` depends on. So the const needs two things that look redundant but aren't: a value re-export (so it survives to runtime) and `as const` (so the literal type survives declaration emit). This is not a regression — the barrel was always type-only; the bug was latent until a documented flow required a runtime const to cross the boundary.

## Lesson

- **`export type *` / `export type { X }` silently type-erases every value.** Any runtime `const`/`enum`/function surfaced through a type-only re-export compiles for consumers but is `undefined` at runtime, with NO compile error. When adding a runtime constant to a barrel that re-exports with `export type`, you MUST add a separate explicit `export { X } from "..."` value line — and do it at _every_ layer that re-exports with `export type` (here both `shared/types/plugin-sdk.ts` AND `packages/plugin-sdk/src/index.ts`).
- **Type tests cannot catch value erasure — only a runtime assertion can.** `expectTypeOf(X)` passes because the type survives; the value is what's gone. Guard each re-exported runtime const with a package-boundary runtime check like `expect(typeof PLUGIN_PROCESS_STREAM_CHANNEL).toBe("string")` in `shared/types/__tests__/plugin-sdk.test.ts` — asserting it is not `undefined` after the entry re-export.
- **A re-exported string literal needs `as const` to keep its literal type through `.d.ts` emit.** Without it the composite build widens `"process"` to `string` and breaks any channel-key narrowing (`plugin.on(pluginId, PLUGIN_PROCESS_STREAM_CHANNEL)`). Value survival (runtime) and literal survival (declaration emit) are separate concerns; fixing one does not fix the other.
- **This trap is structural and recurring, not a one-off.** The identical erasure hit `localAuthStubs` next (#10563) — a runtime const forge providers spread into their impl — and needed the same explicit value re-export in `packages/plugin-sdk/src/index.ts` plus the same runtime boundary test. Treat every new runtime const on the SDK surface as requiring the value-line + runtime-test pair.

## Applies when

- Adding any runtime constant, enum, or function to `shared/types/plugin-sdk.ts` or `packages/plugin-sdk/src/index.ts` (or any barrel that re-exports with `export type *` / `export type { }`) — it needs an explicit value re-export line at each such layer, not just a type export.
- Diagnosing a plugin/SDK symbol that "is exported and type-checks" but reads as `undefined` at runtime — e.g. `plugin.on(pluginId, SOME_CHANNEL)` subscribing to nothing, or a spread of an exported stub object yielding no methods.
- Reviewing changes to the `@daintreehq/plugin-sdk` public surface: confirm every runtime value has both a value re-export AND (for string/number literals used as keys) `as const`, and a runtime `typeof` boundary test.
- Writing tests for a package boundary — `expectTypeOf`/`@ts-expect-error` prove nothing about runtime value survival; add an explicit `typeof … !== "undefined"` assertion. The entry's `export type *` (not the source barrel) is the erasure point, so value re-exports must live in `packages/plugin-sdk/src/index.ts`.
