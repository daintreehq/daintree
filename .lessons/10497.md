## Context

The Worktrees-sidebar memory badge (`ProjectResourceBadge`) shows an aggregate "memory" figure sourced from `handleGetAppMetrics` in `electron/ipc/handlers/diagnostics.ts`, which sums `app.getAppMetrics()` across Daintree's Electron process tree. #8646 had already fixed the identical field-selection bug in `ProcessMemoryMonitor` and `ResourceProfileService` and documented the house rule (workingSetSize-only), but the diagnostics handler and the badge were a separate, independently-written code path that never adopted it — they still read `proc.memory.privateBytes ?? proc.memory.workingSetSize`. #10497 fixed the badge; sibling #10505 codified the same workingSetSize-only rule in the diagnostics export (`DiagnosticsCollector`).

## Problem

On macOS and Linux — two of three platforms — the badge summed to `0` and displayed a plausible-looking "0 MB", with no error. On top of that, the IPC catch path returned `{ totalMemoryMB: 0 }`, so a genuine read failure was indistinguishable from a true zero and also rendered as "healthy 0 MB" — the worst possible misreading for an IDE whose job is spawning memory-hungry agent CLIs. Severity was keyed to fixed absolute MB (elevated 500 / critical 800), so "critical" was noise on a 64 GB Mac Studio and meaningful on an 8 GB laptop.

## Root cause

`Electron.ProcessMetric.memory.privateBytes` (the shape `app.getAppMetrics()` returns) is **Windows-only**: on macOS/Linux the field is present but reported as `0`, not `undefined`. `0` is a valid number, so `privateBytes ?? workingSetSize` resolves to `0` and never falls through — see #8646 for the full mechanism. The non-obvious part here is not the trap itself but that it **recurred in a parallel call site after being fixed and documented**: a convention proven in `electron/services/` did not propagate to `electron/ipc/handlers/diagnostics.ts`, because nothing greps for the pattern and the loose `ProcessMetric.memory` types make `privateBytes ?? workingSetSize` still typecheck. The fix reads `proc.memory.workingSetSize` unconditionally in both `handleGetAppMetrics` and `handleGetProcessMetrics`; adds an `unavailable?: true` flag to `AppMetricsSummary` (`shared/types/ipc/system.ts`) so the catch returns `{ totalMemoryMB: 0, unavailable: true }` and the renderer suppresses the value (`if (appMetrics.unavailable) return null`) rather than painting a lie; scales thresholds to RAM (`computeThresholds` in `ProjectResourceBadge.utils.ts`: 20% elevated / 33% critical of `getHardwareInfo().totalMemoryBytes`, `FALLBACK_THRESHOLDS` 500/800 when the async probe fails); and routes both handlers through the shared 5s `getAppMetricsSnapshot` cache instead of re-sweeping the process table on every poll.

## Lesson

- **When you fix a cross-cutting API-misuse bug, grep every call site of the offending API, not just the service you were handed.** #8646 fixed `privateBytes ?? workingSetSize` in `ProcessMemoryMonitor`/`ResourceProfileService` and wrote it up, yet the same bug sat untouched in `handleGetAppMetrics` and the badge. A documented convention does not enforce itself; grep `app.getAppMetrics()` and `\.memory\.privateBytes` across `electron/` before declaring a metric bug dead.
- **A metrics catch that returns `0` renders as "healthy", which is the worst failure mode for a resource figure.** Distinguish read-failure from a genuine zero with an explicit `unavailable?: true` on the IPC payload; have the renderer suppress the number (return null / show last-good) instead of a plausible fake. `{ totalMemoryMB: 0 }` is a silent lie.
- **The badge counts only Electron's own process tree — node-pty-spawned agent CLIs (claude, node, python, git) are NOT in `app.getAppMetrics()`** and are frequently the dominant consumers, so the headline figure is honest-but-narrow. The popover header now says "Daintree memory" to scope it truthfully; the terminal-workload rows (pty-host `ps` slice) are surfaced separately, not folded into the headline. Don't relabel this number "system memory".
- **Severity thresholds for a user-facing memory readout must scale to total RAM, not fixed MB** — same rule as #8646 but now applied UI-side: `computeThresholds` derives 20%/33% of `getHardwareInfo().totalMemoryBytes`. Because that probe is async, keep a `FALLBACK_THRESHOLDS` (500/800) constant for the pre-resolve / probe-failure window so the badge never renders un-thresholded.
- **Fixtures with populated `privateBytes` mask this regression** — the handler tests now use the real macOS/Linux shape (`privateBytes: 0`, populated `workingSetSize`) and assert the sum uses `workingSetSize` even when `privateBytes` is large; a Windows-shaped fixture passes over the bug.

## Applies when

- Adding or displaying any memory/CPU figure from `app.getAppMetrics()` — read `workingSetSize`, not `privateBytes` (Windows-only, `0` elsewhere; #8646).
- Touching `electron/ipc/handlers/diagnostics.ts` (`handleGetAppMetrics`, `handleGetProcessMetrics`) or `ProjectResourceBadge` / its `.utils.ts` thresholds and trend logic.
- Writing an IPC handler whose `catch` returns a numeric default — decide whether `0`/`-1` is distinguishable from a real reading, and add an `unavailable`/`error` flag if not.
- Labeling or scoping a "memory"/"system" figure in the UI — Daintree's Electron tree excludes the node-pty agent process trees that usually dominate real footprint.
- Fixing a bug that spans a convention (metric field, error sentinel, threshold basis) — grep every parallel call site before assuming one edit closes it.
