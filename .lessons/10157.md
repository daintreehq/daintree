## Context

The Portal (docked browser pane for claude.ai etc.) is a native `WebContentsView` managed by `PortalManager` in main. Chromium composites child views above the base app view's entire DOM, so a DOM modal (settings, command palette, theme browser) renders _under_ the portal regardless of `z-index`. The #9207 arc set the invariant: while `useUIStore.overlayStack.length > 0` the portal view is parked offscreen (`OFFSCREEN_BOUNDS`, kept attached and CPU-throttled so page state survives) and `PortalVisibilityController` re-shows it when overlays clear.

## Problem

Closing, switching, or duplicating a portal tab while a modal was open (easy via command palette or context menu — both hold overlay claims) surfaced the portal `WebContentsView` on top of the modal — the exact #9207 failure, back through side doors. Issue #9972 found four renderer paths calling `window.electron.portal.show` with no overlay check: `restoreActiveTabAfterClose` (`portalStore.ts`), `activatePortalTab` (`portalHelpers.ts`), `portal.duplicateTab` (`portalActions.ts`), `devPreview.promoteToPortal` (`devPreviewActions.ts`). Only `ensureTabAndRestore` in `PortalVisibilityController` was guarded.

## Root cause

Two structural facts make this class of bug recur rather than being a one-off omission. First, **the invariant cannot be enforced in main**: `overlayStack` is renderer-only Zustand state, and `PortalManager.showTab` just attaches the view and sets bounds — it cannot know an overlay is open. The guard must live in the renderer at every call site, and nothing (types, lint, main-side validation) stops a new `portal.show` caller from skipping it. Second, **the existing defense is transition-edge, not steady-state**: the `PortalVisibilityController` overlay effect calls `portal.hide()` only when `hasOverlays` _becomes_ true and re-shows only when it _becomes_ false. A show issued while an overlay is already steadily open lands between edges and is never corrected.

Timing matters as much as the guard's existence. `activatePortalTab` and `restoreActiveTabAfterClose` await a bounds-retry loop (20 × 50ms, up to ~1s) before showing; an overlay can open during that wait, so an entry-time check reads stale state. The fix reads `overlayStack` at the actual show moment: shared helper `showPortalTabIfNoOverlay` (`portalHelpers.ts`) checks-then-shows at call time, and `portalStore.ts` places its inline guard _after_ the retry loop. No pending-show queue was built — the overlay-clear effect already re-shows the active tab, so suppression + existing reconciler covers recovery. Crucially, store mutations still run when suppressed (`setActiveTab`, `portal.create`, `markTabCreated`) — only the native show is gated — so the reconciler later restores from truthful state. The same invariant has sibling vectors guarded elsewhere in the arc: `PortalManager.updateBounds` bails on a `hidden` flag so a window resize mid-overlay doesn't pull the parked view back on-screen, and `portalStore.toggle` suppresses closed→open while an overlay is open.

## Lesson

- **DOM stacking can never contain a native view — the z-order contract for a `WebContentsView` is enforced by _not showing it_, and only the renderer knows when.** `overlayStack` lives in renderer Zustand and `PortalManager.showTab` is guard-free by necessity; every renderer path that can attach/position the view must check overlay ownership itself.
- **Route all shows through one guard helper; per-site inline checks are how the gap reappears.** Four sites missed the check independently. `showPortalTabIfNoOverlay` is the enforcement point — a new site calling `window.electron.portal.show` directly reintroduces #9972. Same recurrence shape as the `setBackgroundColor` white-flash lesson (#9576): without central enforcement, each new call site is a fresh regression chance.
- **Read guard state after the last await, immediately before the IPC call.** With up-to-1s bounds polling between intent and show, an entry-time check is stale — the `portalStore.ts` guard sits after the retry loop for exactly this reason; tests pin both directions (overlay opened during the wait suppresses, cleared during the wait proceeds).
- **Prefer suppress-plus-reconciler over a pending-show queue when a reconciling effect already exists.** The overlay-clear effect re-shows the active tab, so a dropped show self-heals. Precondition: keep the store honest — mutate `activeTabId`/`createdTabs` even when suppressing, so the reconciler restores the right tab.
- **Transition-edge effects defend transitions, not steady state.** A hide-on-rising-edge effect cannot undo a show issued mid-overlay; if an invariant must hold continuously, every actor able to violate it needs its own gate.

## Applies when

- Adding any renderer path that calls `window.electron.portal.show` (or any IPC that attaches/positions a native `WebContentsView`) — route through `showPortalTabIfNoOverlay` or replicate the show-time `overlayStack` read.
- Diagnosing "portal/browser view paints on top of a modal/dialog/palette" — never a CSS z-index problem; find the unguarded show or bounds-set path (resize → `updateBounds`, tab close → `restoreActiveTabAfterClose`, actions dispatched from palette/context menu while overlay claims are held).
- Writing guards around code with await gaps (bounds polling, IPC round-trips) — verify the guard reads state after the last await, not at entry.
- Tempted to queue a suppressed UI operation — first check whether an existing reconciler effect (`PortalVisibilityController` overlay-clear/tab-change/open-toggle) already recovers it.
- Touching `PortalVisibilityController` overlay effects, `PortalManager.hideAll`/`showTab`/`updateBounds`, or `overlayStack` semantics — the offscreen-park + edge-triggered re-show design is load-bearing for every guard site above.
