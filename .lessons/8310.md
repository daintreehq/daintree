## Context

Dev-preview (and browser) panels docked but not the active dock panel are frozen after 500ms by `useWebviewThrottle` (`src/hooks/useWebviewThrottle.ts`), which calls `Page.setWebLifecycleState` ("frozen") through the main-process CDP debugger. Freezing is a full JS-lifecycle freeze, stronger than `webContents.setBackgroundThrottling`. Separately, `DevPreviewPane` captures `window.scrollY` before the panel is evicted/unmounted so it can restore scroll on the next mount.

## Problem

When memory-pressure eviction (or a ref-cleanup branch switch) fired on a panel that had already been frozen, the scroll-capture promise never resolved. The panel's `src` was blanked to `about:blank` by eviction, and the user's scroll position was silently lost — restore landed at the top of the page.

## Root cause

The capture path used `webviewElement.executeJavaScript("window.scrollY")`. On a page frozen via `Page.setWebLifecycleState`, JS execution is suspended per the WICG frozen-state spec: `executeJavaScript` is scheduled as a _freezable task_ that does not run until the page is thawed. So the promise hangs indefinitely; eviction blanks the page before it ever resolves. It looks synchronous-ish but is queued behind a suspended task queue. A secondary tell: a returned scroll of `0` from this region is almost always "the page was still frozen," not a genuine top-of-page position.

## Lesson

- To read renderer/DOM state from a webview that may be frozen, use a CDP domain command that reads directly from Blink rather than `executeJavaScript`. PR #8310 added `webview.getScrollPosition` IPC backed by `wc.debugger.sendCommand("Page.getLayoutMetrics")`, reading `cssLayoutViewport.pageY`. CDP commands hit Blink layout state directly and bypass the suspended JS task queue.
- Guard the result with `> 0`, not just `Number.isFinite`: a CDP error path returns `0`, and persisting `{ scrollY: 0 }` would clobber a previously-captured position. The renderer in `DevPreviewPane.tsx` skips persist on `0`.
- Be deliberate about which capture paths can run on a frozen page. The `prevStatus === "running"` capture in `DevPreviewPane.tsx` still uses `executeJavaScript` on purpose — a running dev server is never frozen there. Only the eviction and ref-cleanup paths (which can fire post-freeze) were switched to CDP.
- Multiple capture sites (eviction `useEffect` + `setWebviewNode(null)` ref cleanup) can race; use a generation counter (`scrollCaptureGenerationRef`) so a stale resolved promise can't overwrite a newer captured value.

## Applies when

- Reading scroll position, DOM measurements, or any renderer state from a `<webview>` / `WebContentsView` that `useWebviewThrottle` may have frozen via `Page.setWebLifecycleState`.
- A `webview.executeJavaScript(...)` promise hangs or never resolves and the page is a hidden/dock/background dev-preview or browser panel.
- Scroll position (or other captured state) is silently lost across panel eviction, hibernation, project switch, or unmount of a dev-preview/browser panel.
- Adding new "capture state before eviction/unmount" logic to `DevPreviewPane.tsx` or similar webview-backed panels.
- Seeing a captured scroll/metric value of `0` after eviction and wondering whether the page was actually at top — it usually means the read ran against a still-frozen page or hit a CDP error.
- Working in `electron/ipc/handlers/webview.ts` adding CDP-backed read handlers (`wc.debugger.sendCommand`).
