## Context

Electron renders a blank white (or black) window during the period between `show` and the first React render completing. This is especially visible on first launch or after cache invalidation when V8 compilation takes longer.

## Problem

Users saw a blank window for a perceptible period at startup, giving the impression of a slow or broken app.

## Root cause

Any UI that depends on React (or any JS bundle) cannot paint until the renderer bundle is fetched, V8-compiled, and the first React commit lands — so the window stays at the BrowserWindow background color for that whole window. Nothing in the HTML paints earlier because there is no zero-JS content to draw. The fix has to live in `index.html` itself and render with no JavaScript so Chromium can paint it on the very first frame, before the bundle is even parsed.

## Lesson

Inline a skeleton UI directly in `index.html` using CSS custom properties that match the app's theme tokens. The skeleton loads with zero JavaScript, appearing the instant Chromium paints the first frame.

Key implementation details:

1. Use CSS custom properties for colors (`var(--theme-surface-*)`) so the skeleton respects both light and dark themes without JavaScript.
2. Gate the skeleton's entrance behind the 400ms Doherty anti-flicker threshold rather than showing it immediately — the container animation uses `animation-fill-mode: backwards` with a 400ms delay (`#startup-skeleton` runs `skeleton-doherty-gate 200ms ease-out 400ms backwards` in `index.html`) so sub-threshold loads never flash a skeleton, then fades in over 200ms. (The original PR used `forwards`/immediate visibility; that was reversed to honor the app-wide Doherty gate.) A visible stuck-state overlay (`.skeleton-stuck`, `skeleton-stuck-reveal` with `animation-delay: 6000ms`) surfaces at 6s if React never hydrates, replacing the earlier silent safety-fade.
3. Remove the skeleton after React's first render via `removeStartupSkeleton()` (`src/utils/removeStartupSkeleton.ts`): a double `requestAnimationFrame` waits for React's paint, then prefers the View Transitions API (`document.startViewTransition`) for a GPU crossfade — fading the `::view-transition-old(root)` snapshot out over `UI_EXIT_DURATION` via WAAPI — falling back to a plain CSS `.fade-out` opacity transition under reduced-motion / performance mode / older runtimes (no `startViewTransition`, hidden visibility).
4. Make the removal idempotent — the element may already be gone if called twice (`removeStartupSkeleton` no-ops the DOM removal when the node is absent, still flushing the first-interactive signal). The same call also drains CLS / perf marks (`flushFinalCls`, `flushPendingPerfMarks`) and notifies the main process (`notifyFirstInteractive`) so it can drain its deferred service queue; the separate `notifyViewPainted` fires before hydration so `ProjectViewManager` can swap WebContentsViews early.
5. Call the removal utility from `App.tsx` `useEffect` on mount, gated on hydration / pending-crash state (`if (isStateLoaded) removeStartupSkeleton()` and `if (crashState.status === "pending") removeStartupSkeleton()` around `src/App.tsx:512`/`525`).

The skeleton layout should approximate the real app structure (sidebar, toolbar, main content) to avoid a jarring layout shift when the real UI appears.

## Applies when

- Reducing perceived startup time for Electron apps
- Any BrowserWindow that shows a blank period before the React app renders
- Adding a new top-level window with a distinct layout
