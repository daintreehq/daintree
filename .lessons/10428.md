## Context

Daintree's theme tokens are authored as `rgba(...)` strings with alpha baked in — `border-subtle` is a hairline seam (`shared/theme/themes.ts:196`: `tokens["border-subtle"] ?? withAlpha(borderInk, dark ? 0.08 : 0.09)`), so a theme that doesn't override it inherits ~9% ink alpha. The quick-run input wrapper (`src/components/Project/QuickRun.tsx`) drew its border with the Tailwind utility `border-border-subtle/50`, reading as a mild softening of an already-subtle seam over the new near-white `--dock-input-bg` surface.

## Problem

The light-theme smoke E2E (`e2e/full/panels/core-light-theme-smoke.spec.ts`) failed on develop for the atacama theme: the quick-run input border contrast measured exactly `1.0` against a `>= 1.02` floor — the border was fully invisible. It was near-invisible in dark themes too, just above the test's detection threshold, so it read as a subtle-styling choice rather than a bug. The symptom pointed at atacama's palette, but atacama was only the theme where the near-white `#FDFBF7` background made the underflow cross zero visible contrast.

## Root cause

Tailwind v4 does NOT implement the `/N` opacity modifier as a separate alpha channel — it compiles `border-border-subtle/50` to `color-mix(in oklab, var(--color-border-subtle) 50%, transparent)`. `color-mix` with `transparent` is a linear blend, so the result's alpha is `0.5 × alpha(token) + 0.5 × 0` = **half the token's existing alpha**. The modifier assumes the token is opaque; `border-subtle` is already `rgba(39,33,25,0.09)`. So `/50` produced `~0.045` effective alpha — 4.5% ink over a near-white surface composites to essentially the background color. No type error, no build warning: the utility is valid, the token is valid, the product just underflows perceptually. Dark themes silently ran their seams at roughly half the designed `border-subtle` alpha for the same reason.

The one-line fix drops `/50` and uses the pre-baked token directly (the wrapper has since been hardened further to the more solid `border-border-default` — `QuickRun.tsx:397`). The PR flagged two live secondary hazards that still exist: (1) `src/index.css` `panel-state-compiling` composes `color-mix(in oklab, var(--color-border-subtle) 8%–10%, transparent)` for its rings (lines 1912–1915) — the same alpha-on-alpha underflow on any low-alpha light token; (2) the E2E color parser `parseColor()` returns opaque black `{r:0,g:0,b:0,a:1}` for any unrecognized color string (`e2e/helpers/theme.ts:139`), which can mask a regression as a false pass by fabricating high contrast from a parse miss.

## Lesson

- **Never stack a Tailwind opacity modifier (`/N`) on a theme token that carries its own alpha.** In Tailwind v4 `/N` is `color-mix(in oklab, token N%, transparent)`, which multiplies into the token's existing alpha — `/50` on `rgba(...,0.09)` yields ~4.5%, not "9% softened a bit." Apply opacity modifiers only to opaque tokens; for translucent tokens use the pre-baked variant (`border-subtle`, `border-default`) or author a dedicated token.
- **This underflow is silent — no type error, no lint, no build failure.** The utility and the token are each individually valid; only the composite is wrong, and only visibly wrong once the background stops hiding it. Reach for a rendered-contrast check (the light-theme smoke E2E), not the type-checker, to catch it.
- **Auditing `color-mix(in oklab, <token> P%, transparent)` in raw CSS carries the identical trap.** `src/index.css` still mixes `--color-border-subtle` at 8–10% for `panel-state-compiling` rings — that is 8% _of_ 9% alpha on light themes. When a token can be low-alpha, treat any further `color-mix(...transparent)` on it as an alpha multiply and compute the floor.
- **Distrust an E2E color helper that has an opaque fallback.** `parseColor()` returning opaque black on a parse miss means an unhandled color format silently reports maximum contrast — a regression passes. A contrast helper should throw or return transparent on unrecognized input, never a high-contrast default.
- **atacama is the canary for alpha/contrast bugs, not the cause.** Its near-white surfaces (`#FDFBF7`, `#FBF7F0`) push marginal-contrast defects past zero, so failures localize to atacama while the mechanism is theme-agnostic. Fix the token math, don't special-case the theme.

## Applies when

- Writing or reviewing any `border-*/N`, `bg-*/N`, `text-*/N`, `ring-*/N` Tailwind utility on a `--color-*` / `--theme-*` token — confirm the token is opaque before applying an opacity modifier.
- Touching translucent theme tokens (`border-subtle`, `overlay-*`, any `rgba(...)` in `shared/theme/`) or the `withAlpha` fallbacks in `shared/theme/themes.ts`.
- Diagnosing an invisible or too-faint border/ring that only shows up on light (atacama-family) themes, or a light-theme-smoke contrast E2E failing near `1.0`.
- Auditing `color-mix(in oklab, ... transparent)` in `src/index.css` (panel-state rings, ambient chrome) for alpha underflow on low-alpha tokens.
- Trusting an E2E screenshot/contrast assertion whose color parser (`e2e/helpers/theme.ts` `parseColor`) has an opaque-black fallback that can fabricate a passing contrast ratio.
