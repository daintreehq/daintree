## Context

Agent panels persist their original CLI launch flags in `agentLaunchFlags` (per #3175 for resume, #4222 for crash survival). On quit-restart the panel is respawned by `buildArgsForRespawn` (`src/utils/stateHydration/statePatcher.ts`) and on restart-in-place by `restartTerminal` (`src/store/slices/panelRegistry/restart.ts`). Each must reconstruct the launch command.

## Problem

Per-terminal flags like `--dangerously-skip-permissions`, `--yolo`, `--model <id>`, and recipe overrides were silently dropped on quit-restart, even though they were correctly persisted. The restarted agent ran with whatever the _current_ global agent settings produce, not the flags the session was launched with — the same capability-mismatch failure #3175 fixed, reappearing through a different door.

## Root cause

`buildArgsForRespawn` has THREE branches, not one: (1) session ID present and `buildResumeCommand` succeeds; (2) session ID present but resume returns undefined (expired/unavailable); (3) no session ID at all. #3175 only fixed branch 1 (the resume path). Branches 2 and 3 fell straight through to `generateAgentCommand(baseCommand, agentSettings.agents?.[agentId] ?? {}, ...)` — re-deriving the command from _current_ settings and discarding the persisted `agentLaunchFlags` entirely. The lesson "test every resume path" missed these because they are explicitly the _non_-resume paths. `restartTerminal` had the identical gap.

## Lesson

When a launch/resume reconstruction has multiple fallback branches, persisting the original args is necessary but not sufficient — every branch that builds the command must consume them. The fix added a third dedicated builder, `buildLaunchCommandFromFlags` (`shared/types/agentSettings.ts`), distinct from both `buildResumeCommand` (session token) and `generateAgentCommand` (current settings): it replays persisted flags verbatim, mirroring `buildResumeCommand`'s escaping (raw for `-`-prefixed tokens, `escapeShellArg` for positionals so a `--log /tmp/a;b.log` value can't shell-inject). Subtlety: runtime-dynamic flags that `buildAgentLaunchFlags` deliberately excluded at capture time (Gemini's `--include-directories <clipboardDir>`, which depends on the live tmp dir) must be re-injected at respawn — with dedup against a matching persisted entry but NOT against a different user-chosen directory. Non-Gemini agents take a sync fast path (no dynamic injection); Gemini still goes async to fetch the tmp dir. Backwards-compat fallback to `generateAgentCommand` is preserved only when `agentLaunchFlags` is empty (pre-fix panels).

## Applies when

- Adding or auditing any agent respawn / restart / reconnect path that reconstructs a launch command — confirm the no-session and resume-failed branches consume persisted flags, not just the happy resume branch.
- Debugging "agent lost its flags / re-prompts for permissions after quit-restart" when crash recovery and resume (#3175, #4222) are already fixed.
- Designing a command builder where some flags are static-at-capture and others are runtime-dynamic (must be excluded at capture and re-injected on replay).
