## Context

`TerminalResizeController` reconciles xterm's grid against the DOM (`ResizeObserver`/`fit`) and against PTY output held in `TerminalOutputIngestService`'s per-terminal ingest queue. Daintree runs one `WebContentsView` per project (`ProjectViewManager`), so switching projects hides a whole view's terminals at once while their agents keep running underneath. #10811 (hibernation removal) made this worse by design: every background terminal now stays fully live and streaming instead of being paused, so a hidden view accumulates real agent output the whole time it's off-screen.

## Problem

Switching back to a project view hidden ~6 minutes, with four agent terminals still streaming, froze the entire UI for 45-60 seconds. Misleadingly, main process and pty-host were completely healthy throughout — no `[ResourceGovernor]` backpressure pause, no pending IPC bytes — which pointed toward "renderer is just slow" rather than one specific synchronous call. Every MCP dispatch routed through the active view stalled the instant it was revealed, which was the clearest timeline signal once diagnostics were captured.

## Root cause

Two-phase accumulate/detonate mechanism spanning Chromium, IPC flow control, and xterm internals.

1. **Accumulate (while hidden).** Chromium throttles timers on hidden pages, which stalls xterm's `setTimeout`-driven parse pump. `TerminalOutputIngestService`'s MessagePort chunks keep arriving from the pty-host regardless (acks are parse-gated, not visibility-gated), so the queue piles up with minutes of agent output, unbounded, while the page is hidden.
2. **Detonate (on reveal).** The grid re-layout fires `applyResize`/`commitResize`, which called `flushHeldBytesBeforeResize` → `flushForTerminal` — a force-drain that deliberately bypasses the renderer's own 128KB in-flight watermark (`RENDERER_HIGH_WATERMARK_BYTES` in `TerminalOutputIngestService.ts`) — then `resizeTerminal`. xterm's `CoreTerminal.resize()` internally calls `WriteBuffer.flushSync()`, parsing everything just force-dumped into it in one unyielding main-thread task before reflowing the retained scrollback. Multiply by four or five terminals reattaching at once and the renderer is dead for the better part of a minute. The healthy pty-host was a red herring: the bytes were already delivered and sitting in the _renderer's_ queue; the wedge was 100% main-thread parse+reflow cost, not I/O.

The fix (`src/services/terminal/resizeFlushBudget.ts`) caps the pre-resize force-flush at `RESIZE_FLUSH_SYNC_BUDGET_BYTES` (1MB) via `exceedsResizeFlushSyncBudget(queuedBytes)`, applied at every flush call site in `TerminalResizeController` (`commitResize`, the `applyResize` settled-strategy branch, `flushResize`, the settled-resize commit path). Past budget, it skips the flush and — critically — does **not** call `resetForTerminal` (that deletes the queue, silently dropping output); instead it calls `dataBuffer.resumeFlush(id)` so the backlog drains incrementally with scheduler yields at the _new_ grid, the same wrap outcome as output arriving just after a normal resize. #10983 landed `PERF-112`, a permanent regression-guard benchmark reconstructing this exact incident (large backlog + reveal resize), asserting the over-budget arm stays flat regardless of backlog size — bypassing the budget blows it immediately (40.8ms measured against a 30ms ceiling in that PR).

## Lesson

- **A perfectly healthy main process / pty-host does not rule out a renderer wedge.** No backpressure pause and no pending IPC bytes just means the data already arrived — check for a synchronous parse/reflow cost living entirely inside the renderer's main thread before assuming it's an I/O or memory-pressure problem.
- **`Terminal.resize()` is not free — it internally calls `WriteBuffer.flushSync()` on whatever is already queued.** Any code path that force-drains a held ingest queue right before calling `resize()` (or otherwise triggering a reflow) inherits an unbounded synchronous cost; that force-drain needs its own byte budget, distinct from the steady-state watermark used during normal streaming.
- **Skipping a flush and clearing a queue are different operations — never conflate them.** `resetForTerminal` deletes the queue; call it only on the branch that actually flushed. The over-budget branch must resume normal (yielding) drainage instead, or output silently disappears.
- **Chromium throttles timers on hidden pages/views — a `setTimeout`-driven consumption loop stalls even though producers (MessagePort, IPC) keep running.** Any "backlog builds up while a view/tab is backgrounded, then something bad happens on reveal" bug should be read through this lens first.
- **Calls that route through "the active view" (MCP dispatch here) double as a free diagnostic tripwire** — they stall in lockstep with the wedge, the fastest way to timeline a renderer-side freeze against IPC/log traces.
- Bounding the _force-flush_ (this PR) is narrower than bounding the _ingest queue itself_ — #10957 explicitly left hidden-view queue growth and parse-while-hidden pacing out of scope as separate data-plane work; don't assume the underlying accumulation was also fixed here.

## Applies when

- Diagnosing a multi-second-to-minute UI freeze on project-view switch-back / reveal with several streaming agent terminals backgrounded for minutes.
- Touching `TerminalResizeController`'s flush call sites, `RESIZE_FLUSH_SYNC_BUDGET_BYTES`, or `resizeFlushBudget.ts` — re-run or extend `PERF-112` (`scripts/perf/scenarios/resizeReflow.ts`) rather than hand-verifying the budget.
- Adding any pre-`resize()`/pre-reflow force-drain of a held write/ingest queue in xterm-adjacent code — it needs the same bounded-flush-or-defer treatment, not an unconditional drain.
- A regression report says "main/pty-host logs look clean but the UI hung" — check for a synchronous main-thread parse cost in the renderer before widening to backpressure or memory.
- Reasoning about background-terminal behavior post-#10811 (hibernation removal) — hidden terminals stay fully live, so hidden-view output accumulation is now the default, not an edge case.
