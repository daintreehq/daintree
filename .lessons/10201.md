## Context

The dev-only demo/screencast engine (`DemoCursor.tsx`, driven over `window.electron.demo` by `demo:exec-click` / `demo:exec-drag` commands) animates a fake cursor and then _actuates real UI controls_ by dispatching synthetic DOM events at `document.elementFromPoint(cx, cy)`. #10201 fixed the click path; #10206 and #10210 complete the same cursor-realism arc (arc-path glyph coupling, velocity/overshoot).

## Problem

Recorded demos silently failed on certain controls: the cursor visibly moved and "clicked" a toolbar dropdown or a sortable panel handle, but nothing opened and no drag started — no error, no feedback. The failure was control-specific: plain `<button>`s actuated fine, which masked the bug and made it look like a coordinate/timing issue rather than an event-type issue.

## Root cause

Daintree's UI is **pointer-first**, but `demo:exec-click` dispatched only `MouseEvent`s (`mousedown` → `mouseup` → `click`). dnd-kit's default `PointerSensor` (`@dnd-kit/core@6.3.1`) activates on `pointerdown` and hard-gates on `isPrimary && button === 0`; Radix `DropdownMenu.Trigger` / `ContextMenu` open from `onPointerDown` (not `click`), and Radix `Select` reads `pointerType`. A mouse-only dispatch reaches controls that never listen for `MouseEvent` at all, so it no-ops. Plain buttons have _native_ activation on the trusted `click`, so mouse-only "worked" there — that's exactly why the bug hid.

The pre-existing `demo:exec-drag` path _did_ dispatch `PointerEvent`s, but constructed them without `pointerId` / `pointerType` / `isPrimary`. The `PointerEvent` constructor defaults `pointerId` to `0` and `pointerType` to `""`, which trips `setPointerCapture(e.pointerId)` and `pointerType === "mouse"` guard clauses inside the libraries — so even the "pointer-aware" path was subtly broken. The fix leads every mouse event with its pointer counterpart (`pointerdown` → `mousedown` → `pointerup` → `mouseup` → `click`) and stamps full primary-mouse metadata: `pointerId: 1, pointerType: "mouse", isPrimary: true, button: 0`. On the drag session `button` is per-event — `0` on down/up, **`-1` on move per the Pointer Events spec** (no button-state change) — while `buttons` is the held bitmask (`1` while dragging, `0` on release), and a single shared `pointerMeta`/`pointerId` runs the whole session so dnd-kit's pointer tracking stays coherent.

## Lesson

- **A `MouseEvent`-only dispatch actuates plain buttons but silently no-ops on pointer-first controls** (dnd-kit `PointerSensor`, Radix `DropdownMenu`/`ContextMenu`/`Select`). Any programmatic click/drag against real Daintree UI must **lead each mouse event with its `PointerEvent` counterpart** — never mouse-only.
- **Order and completeness matter:** a click is `pointerdown → mousedown → pointerup → mouseup → click`; a drag is `pointerdown` then per-frame `pointermove` then `pointerup`. Skipping the pointer half is the failure.
- **The pointer metadata is load-bearing, not decorative:** always set `pointerId: 1, pointerType: "mouse", isPrimary: true`. The constructor's defaults (`pointerId: 0`, `pointerType: ""`) break `setPointerCapture` and `pointerType === "mouse"` guards. dnd-kit's activation gate is literally `isPrimary && button === 0`.
- **`button` vs `buttons` are different fields with different rules:** `button: 0` on press/release, **`button: -1` on moves** (spec: no button changed), while `buttons` is the held bitmask (`1` while down, `0` released). Use one shared `pointerId` for the entire drag session — dnd-kit tracks by it.
- **Test against a real pointer-first control, not a bare `<button>`.** The original test asserted `["mousedown","mouseup","click"]` on a plain button and passed while the feature was broken in-app; the fix's tests assert the ordered pointer+mouse sequence _and_ the `isPrimary`/`pointerType`/`button` metadata precisely because a plain-button assertion can't catch this class of bug.
- **Coordinate coupling is a separate trap in the same file:** #10206 found the drag glyph teleported because synthetic `pointermove`s and the visible cursor `style.left/top` were driven from _different_ sources — the fix drives both from identical coordinates each `requestAnimationFrame` frame. If you simulate movement, the events and the glyph must read the same coordinate.

## Applies when

- Touching `src/components/Demo/DemoCursor.tsx` or writing any e2e/helper/action that _programmatically_ clicks or drags real UI controls (as opposed to Playwright's trusted input).
- Diagnosing "the demo cursor clicks but the dropdown never opens / the drag never starts," or any synthetic interaction that works on buttons but not on menus/sortables.
- Assuming `dispatchEvent(new MouseEvent(...))` actuates a control because it visibly works on a plain button — verify the target isn't a dnd-kit `PointerSensor` or Radix `onPointerDown` trigger first.
- Reviewing any `new PointerEvent(...)` construction — confirm it carries `pointerId`/`pointerType`/`isPrimary` and correct `button`/`buttons`, not the zeroed constructor defaults (other synthetic-click sites exist, e.g. `TerminalInstanceService.ts` and `panelContextMenu.ts`, which target plain/context-menu elements and are fine mouse-only — the pointer requirement is specific to dnd-kit/Radix targets).
