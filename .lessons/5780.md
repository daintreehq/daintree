## Context

`ProcessDetector` polls the PTY process tree (~2500ms) and emits `DetectionResult` via a single callback that carries multiple independent fields: the primary agent identity (`detected`/`agentType`/`processIconId`) plus secondary fields `isBusy` and `currentCommand`. Short-lived processes like `claude --version` or `gemini --help` appear for one poll, so the primary identity is now gated behind a hysteresis streak (`HYSTERESIS_THRESHOLD = 2` consecutive agreeing polls — `onStreak`/`offStreak`/`pendingDetected`) before it commits to `lastDetected`/`lastProcessIconId`.

## Problem

Adding the hysteresis gate to the primary agent-on/off transition did not stop the thrash. A one-poll blip still flashed the agent icon on and then cleared it, because two things route around the gate.

## Root cause

Two leaks, both non-obvious because the gate looks complete in isolation.

1. **Side-channel bypass.** `isBusy` and `currentCommand` are computed and emitted on their own `busyChanged`/`commandChanged` predicates, independent of the agent-identity streak. A single-poll blip of a short-lived process changes `currentCommand`, fires the callback, and the renderer promotes the panel to an agent — the agent-on transition never had to clear hysteresis. A gate on the primary field is meaningless if any secondary field on the same payload can fire the same callback.
2. **Mid-window teardown.** A real agent whose process exits while an `offStreak` is still in flight (count 1 of 2) never reaches the threshold, so the OFF transition never commits and the UI keeps showing a ghost agent after `stop()`.

## Lesson

A hysteresis/debounce gate must cover **every emission path that shares the sink**, not just the field you were thinking about. Here, suppress busy/command emissions while a transition is pending: `inPendingTransition = onStreak > 0 || offStreak > 0`, and `shouldEmitImmediate = (busyChanged || commandChanged) && !inPendingTransition`. Crucially this also means **not mutating** `lastBusyState`/`lastCurrentCommand` during the suppressed window — if you advance the comparison baseline while suppressing the emit, a later stable poll sees "no change" and the real transition is lost.

Pair the gate with a **teardown flush**: on `stop()`, if `offStreak > 0` and committed state still has an agent, synthetically emit the OFF result (and reset all streak/pending fields) so an in-flight transition can't leave ghost UI. Only flush when a streak is actually pending — guard against a second flush on repeated `stop()`.

The on/off paths are asymmetric and have since grown more so (#5809): shell-command-sourced evidence fast-commits on the first tick because it was already debounced at capture, and launch-anchored agents hold committed state on process-tree absence until an explicit lifecycle signal. The streak gate remains the floor for process-tree-only signals.

## Applies when

Any state machine driven by a polled/streamed signal that emits a multi-field payload through one callback, where you gate one field but other fields on the same payload can independently trigger the sink. Also any in-flight debounce/streak that must be flushed (not silently dropped) on teardown to avoid stuck UI. Check: does the comparison baseline advance during the suppressed window?
