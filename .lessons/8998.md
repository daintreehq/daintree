## Context

Terminal renderer/backend tier is driven by `TerminalRendererPolicy.applyRendererPolicy(id, tier)` (`src/services/terminal/TerminalRendererPolicy.ts`, owned by `TerminalInstanceService`). It is deliberately idempotent — a call with the same tier as `managed.lastAppliedTier` early-returns without re-sending anything to the backend. PR #8998 originally hit this as a hibernation bug: a hibernation-eligibility bypass keyed on a non-tier input (`usePanelStore.getState().backgroundedTerminals`) never fired because the tier itself hadn't changed. That whole hibernation system — `TerminalHibernationManager`, `isSafeToHibernate`, `scheduleHibernation`, `onPanelBackgrounded` — was removed with per-terminal hibernation in PR #10811 (terminals now stay fully live in the background instead of being torn down), but the same-tier no-op trap it exposed is not gone with it. `TerminalInstanceService.ts` still cites this lesson verbatim (near line 330, "the same-tier no-op re-arm trap from #8998") while describing a still-open instance of it, issue #9778.

## Problem

The PTY host tracks its own copy of a terminal's tier and can rewrite it independently of any renderer-driven transition (window connect/disconnect, project switch). When that happens, the renderer's `lastAppliedTier` is untouched, so a later `applyRendererPolicy` call for the _same_ logical tier sees "nothing changed" and skips re-sending "active" to the backend — the pane can end up frozen at a stale background tier that the renderer no longer believes it's in.

## Root cause

`applyRendererPolicy`'s equality check (`tier === currentAppliedTier`) only compares against the renderer's own record of what it last applied. It has no visibility into a _non-tier_ input drifting underneath it — here the backend's independently-tracked tier (`lastBackendTier`), previously also the user-intent flag (`backgroundedTerminals`) the original hibernation bypass depended on. Any behavior gated on "current tier" plus a second condition needs that second condition's own mutation path to independently re-enter the gated logic; the idempotent setter guarantees it won't do that on its own.

## Lesson

- When a tier/state-gated decision starts depending on an input that is NOT the gating key itself, mutating that input does not re-trigger the gated path — the idempotent tier setter (`applyRendererPolicy`) swallows the change. You must add an explicit re-arm hook fired by whatever mutates the new input.
- The surviving explicit re-arm hook is `TerminalRendererPolicy.reassertActiveTier(id)`, invoked as `reassertActiveBackendTier` from `TerminalReconciliationWatchdog` (`src/services/terminal/TerminalReconciliationWatchdog.ts`) when it detects `getBackendTier(id) === "background"` for a terminal the renderer still considers active: it bypasses the public `applyRendererPolicy`'s same-tier early-return and calls the immediate-apply path directly, so a backend tier that diverged out from under the renderer gets re-sent even though the renderer's own applied tier never changed. `onPanelBackgrounded`, the original hook this lesson was written against, did the same job for a different non-tier input (`backgroundedTerminals` membership) before the hibernation system it served was removed.
- Read the drifting input live at the moment you re-check, never a value captured earlier into a closure: `reassertActiveTier` re-reads `managed.lastAppliedTier` and the live `lastBackendTier` map rather than trusting whatever was true when the divergence was first detected. The original hibernation bypass followed the same rule (`getIsBackgrounded: (id) => usePanelStore.getState().backgroundedTerminals.has(id)`, read at fire time) so a restore between schedule and fire correctly dropped the bypass instead of tearing down a now-foreground live agent.
- An explicit re-arm path still has to respect the gated action's other guards — relaxing one condition is not license to skip the rest. `reassertActiveTier` bails if the backend tier isn't actually `"background"` and clears any pending hysteresis timer before repairing, mirroring how the original hibernation bypass still had to keep the unconditional `pendingWrites === 0` burst guard even while relaxing the agent-idle-silence exemption.

## Applies when

- Adding a new input to a tier-gated policy (`applyRendererPolicy` or a successor) that is not the `TerminalRefreshTier` itself — e.g. host-reported backend state, pin state, snapshot state, or a user-intent flag like the removed `backgroundedTerminals` hibernation bypass.
- Any policy gated by an idempotent tier/state setter where you later add a same-tier-relevant condition — audit whether mutating that condition needs an explicit re-arm; a same-tier `applyRendererPolicy` call will silently no-op (see the `TerminalInstanceService.ts` comment near line 330 and `TerminalRendererPolicy.reassertActiveTier`).
- Wiring renderer store actions (`background.ts`, panel-group actions) or watchdog repair paths that change terminal lifecycle/backend state without changing the renderer's own tracked tier.
- Debugging "a pane is stuck on a stale tier/state after a host-side rewrite" or "the bypass/policy change didn't take effect until something else forced a re-check" (the modern shape of issue #9778).
- Threading any host- or store-sourced state into a tier-policy dependency object (`RendererPolicyDeps`, `ReconciliationWatchdogDeps`) — read it live per-check, do not snapshot it into a `setTimeout` closure.
