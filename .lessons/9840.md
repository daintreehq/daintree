## Context

`waitForAttachSettled` only gates on visual attach (opened, not attaching, host connected, element present), so a multi-panel restore (project switch, wake from sleep) could "settle" while scrollback restore was still running — or after it had silently failed. Issue #9804 asked for a restore-aware primitive; #9840 added `waitForFullySettled(id)` and the batch `waitForAllFullySettled(ids)` (shared 30s `TERMINAL_BATCH_SETTLE_TIMEOUT_MS`, rejection names the still-pending panels, `Promise.all` hard-fails on mid-wait destroy), plus the scheduler-facing `notifyRestoreSettledWaiters` hook. The code landed in `TerminalInstanceService.ts` but now lives in `src/services/terminal/TerminalSettleWaiterRegistry.ts` (extracted by the #11022 controller split; the service keeps thin delegates, and `PaintFabricCompositor` fans batch waits out per-plane).

## Problem

The plan in #9804 suggested consulting `scrollbackRestoreState` post-restore to distinguish "settled successfully" from "settled with failure" — read literally, a predicate accepting only `"done"`. Implemented that way, any failed restore would strand its waiters for the full 30s timeout and then reject, behind a failure that is purely cosmetic (terminal fully usable, just blank scrollback plus an inline banner). Because restore failures are intermittent (write timeouts, IPC hiccups, project-switch aborts), the hang would have surfaced as unattributable slow project switches. The bug was caught during implementation, not production — the PR corrected the predicate before any consumer existed.

## Root cause

The restore FSM (`scrollbackRestoreState: "none" | "pending" | "in-progress" | "done"`, `src/services/terminal/types.ts`) has no failure state, and that is deliberate. The scheduler's admission gate is `managed.scrollbackRestoreState !== "none"` → skip (`scrollbackRestoreScheduler.ts`), so `"none"` is the re-entry gate: `retryFailedScrollbackRestoreBatch` works precisely because every failure path resets state to `"none"`, reopening the gate for re-submit. Three of the FSM's four exit paths land on `"none"` — swallowed replay failure (`fetchAndRestore` returns false, error stashed on `managed.lastScrollbackRestoreError`), the IPC-level catch, and bail-before-start (`isCurrent()` false or instance replaced mid-flight). Only clean success lands on `"done"`. A done-only predicate therefore waits for a state that most exit paths never produce.

The corrected predicate `isFullySettled` (`TerminalSettleWaiterRegistry.ts`) is attach-settled AND (`"done"` OR `"none"`) — i.e. "no longer in flux" (not `"pending"`, not `"in-progress"`), error-agnostic, with failure exposed separately via `lastScrollbackRestoreError`. Because the full predicate is compound (attach AND restore), notification had to come from both halves: the scheduler fires `notifyRestoreSettledWaiters` at all four exits, and `notifyAttachSettledWaiters` also drains fully-settled waiters to cover the restore-finished-before-attach ordering — otherwise a terminal whose restore completed while it was still mid-attach would never re-check the predicate.

## Lesson

- **Write settle predicates against every exit path of the state machine, not its happy-path terminal state.** Enumerate the exits in the scheduler/driver code first: here 3 of 4 (`swallowed failure`, `thrown IPC failure`, `bail-before-start`) reset to `"none"`; only success reaches `"done"`. A predicate matching the success state alone converts every non-success exit into a timeout-length hang.
- **An FSM that resets-to-initial on failure makes its initial state ambiguous by design — don't "fix" that by adding a failed state.** `"none"` simultaneously means never-scheduled, aborted, and failed-and-reset, because `"none"` is what reopens the scheduler's `!== "none"` admission gate for retry. Adding a `"failed"` value would silently close the retry path unless the gate and `retryFailedScrollbackRestoreBatch` are updated in the same change.
- **Settle means "no longer in flux", never "succeeded" — expose the error out-of-band.** A cosmetic failure (blank scrollback, banner shown) must not strand a startup gate; callers that care read `lastScrollbackRestoreError` after the wait resolves. Prefer negating the transient states over matching terminal ones — it stays correct if new terminal states are added.
- **A notification-driven wait over a compound predicate needs a notify hook at every component's completion site.** The scheduler fires on all four restore exits AND `notifyAttachSettledWaiters` drains fully-settled waiters (restore-before-attach race). Any missed site is an intermittent hang the timeout masks as slowness. If you add a new exit path to `scrollbackRestoreScheduler`, it must call `notifyRestoreSettledWaiters` or waiters strand.
- **Precondition trap for the first consumer: `"none"` also means never-scheduled, so a too-early wait false-settles instantly.** `waitForFullySettled` called before `scheduleScrollbackRestore` stamps `"pending"` resolves immediately with nothing restored. As of 2026-07 the primitive still has NO production consumer (#9804's consuming surface never landed) — whoever wires it must sequence the wait after scheduling, per the JSDoc precondition.

## Applies when

- Wiring the first production consumer of `waitForFullySettled` / `waitForAllFullySettled` (the #9804 multi-panel restore gate: project switch, wake, 8+ panel hydration) — respect the schedule-before-wait ordering or the wait is a no-op.
- Writing any waiter, gate, or settle predicate over `scrollbackRestoreState` — or over any Daintree FSM whose failure path resets to the initial state to reopen a retry gate.
- Diagnosing an intermittent `fully-settle timeout after 30000ms (restore: none)` rejection or a 30s stall in a settle-gated flow — check whether the waiter registered before restore was scheduled, or a notify site was missed.
- Adding or modifying exit paths in `scrollbackRestoreScheduler.ts` (new bail conditions, new error classes) — every exit must reset state deliberately and call `notifyRestoreSettledWaiters`.
- Tempted to add a `"failed"` value to `scrollbackRestoreState`, or to make a settle predicate reject on `lastScrollbackRestoreError` — both break the retry gate / strand waiters behind cosmetic failures.
