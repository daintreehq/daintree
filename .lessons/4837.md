## Context

Node exposes `enableCompileCache()` (from `node:module`) to enable V8 bytecode caching. The main process bootstrap already used this, but the UtilityProcesses (`pty-host`, `workspace-host`, and now `watchdog-host`) had no compile cache, so V8 re-parsed and re-compiled their import trees on every app launch.

## Problem

Both UtilityProcesses paid the full V8 parse/compile cost on every cold start. For long-running services like the PTY host this adds measurable startup latency.

## Root cause

`enableCompileCache()` must be called before any imports, at the very start of the entry point. The existing `pty-host.ts` and `workspace-host.ts` had substantial import trees that prevented retroactively adding the call — it had to be the first line of a new bootstrap file.

Additionally, the OS temp dir default for cache storage can cause permission conflicts in multi-user environments.

## Lesson

`enableCompileCache()` (from `node:module`) must be called before any `import`/`require` to be effective. The only clean way to retrofit it is a thin bootstrap wrapper that:

1. Reads `DAINTREE_USER_DATA` from `process.env`
2. Calls `enableCompileCache(path.join(userData, 'compile-cache'))`, falling back to `enableCompileCache()` (OS default) on error
3. Dynamic-imports the real entry point

The cache lives under `userData` (not OS temp) to avoid permission issues. Current bootstraps point all hosts at a shared `compile-cache` dir (cache files use content-hash filenames, so per-process subdirs aren't required).

The esbuild build (`scripts/build-main.mjs`) must add the bootstrap files as explicit `entryPoints`.

## Applies when

- Adding a new UtilityProcess entry point — always create a bootstrap wrapper with `enableCompileCache()` first.
- The `userData` path must be passed via environment variable (`DAINTREE_USER_DATA`) since `app.getPath('userData')` is only available in the main process.
