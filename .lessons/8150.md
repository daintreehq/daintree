## Context

xterm terminals run at one of several `TerminalRefreshTier` levels (BURST/FOCUSED/VISIBLE/BACKGROUND/...) that throttle how often the renderer repaints. `BURST` (16ms / 60fps) is the highest. The PTY data chokepoint is `TerminalWriteController.write()`, which invokes the `onWrite` hook that `TerminalInstanceService` wires to `TerminalBurstController.onPtyWrite()` — that's what drives the BURST tier from real output — and `TerminalRendererPolicy.applyRendererPolicy()` debounces tier downgrades with 500ms hysteresis (`TIER_DOWNGRADE_HYSTERESIS_MS`).

## Problem

Previously `BURST` was manufactured from focus state (XtermAdapter `useLayoutEffect` + two click/pointer handlers calling `boostRefreshRate`), making it a "user is looking at this pane" signal rather than a real-activity signal — wrong input for `isWebGLEligibleTier` and pool-pressure eviction. The obvious fix (drive BURST from writes, resetting a decay timer on each write) janks Chromium's timer queue: a 60fps+ output flood means hundreds of `clearTimeout`/`setTimeout` pairs per second, thrashing the timer table and creating GC pressure.

## Root cause

Two non-obvious constraints govern a write-driven decay window:

- **Timer churn.** Re-arming on every write is O(writes) timer-table touches. The fix (`TerminalBurstController.onPtyWrite()` / `scheduleWriteBurstDecay()`) keeps ONE `writeBurstTimer` and bumps an O(1) `writeBurstDeadline = Date.now() + WRITE_BURST_DECAY_MS` — both fields declared on `ManagedTerminal` in `src/services/terminal/types.ts` — on each write. When the single timer fires it re-checks the deadline and either reschedules for the remaining time (a write extended the window while it was pending) or reverts the tier via `managed.getRefreshTier()`. 100 back-to-back writes produce ≤2 `setTimeout` calls and zero `clearTimeout`.
- **Concurrent downgrade race.** `applyRendererPolicy(BURST)` must be called on EVERY write, not gated on the deadline. A focus-loss can schedule a downgrade (`tierChangeTimer` armed with 500ms hysteresis, `pendingTier` set) mid-burst. Re-asserting BURST hits the `tier === currentAppliedTier` early-return in `TerminalRendererPolicy.applyRendererPolicy`, whose load-bearing side-effect is `clearTimeout(tierChangeTimer)`. Skipping the re-assert on in-window writes leaves the downgrade to fire unopposed and strands the terminal at FOCUSED/VISIBLE/BACKGROUND until output stops.

Also: the `onWrite` hook fires synchronously in `TerminalWriteController.write()` AFTER the `isSerializedRestoreInProgress` deferred-restore early-exit but BEFORE `terminal.write()` — deferring it into the async write callback would render the first chunk at the slow tier (one frame late). Per-terminal hibernation, which used to gate this the same way, was removed in PR #10811 — the deferred-restore check is the only early-exit left on this path.

## Lesson

- For an activity-decay window driven by a high-frequency event, store a `deadline` timestamp and keep a SINGLE self-rearming `setTimeout`; extend the window by writing the timestamp (O(1)), not by clear+set. On fire, compare `Date.now()` to the deadline and reschedule the remainder if it moved.
- The no-op tier re-assert is intentional and required — `applyRendererPolicy(BURST)` on every write exists to cancel a racing downgrade timer via the matching-tier early-return, not to change the tier. Do not "optimize" it away by gating on the deadline.
- A synchronous activity hook that must affect paint cadence has to fire before `terminal.write()`, and only on the real write path (skip mid-restore via `isSerializedRestoreInProgress` — there's no hibernated gate to skip anymore).
- Keep the activity-window constant (`WRITE_BURST_DECAY_MS`, in `src/services/terminal/types.ts`) separate from the policy's downgrade debounce (`TIER_DOWNGRADE_HYSTERESIS_MS`, same file) even when they share a default — they live in different layers and are independently tunable.
- Clear `writeBurstTimer` and null `writeBurstDeadline` in `TerminalBurstController.destroy()` (called from `TerminalInstanceService.destroy()`); a self-rearming timer otherwise survives teardown.

## Applies when

- Adding or changing logic in `TerminalBurstController.ts` (owns `onPtyWrite`/`scheduleWriteBurstDecay`/`destroy`), `src/services/terminal/types.ts` (`WRITE_BURST_DECAY_MS`, `writeBurstDeadline`, `writeBurstTimer`), `TerminalWriteController.ts`, or `TerminalRendererPolicy.ts` — including the `TerminalInstanceService.ts` wiring that instantiates `TerminalBurstController` and forwards its `onWrite`/`destroy` calls — especially anything touching `onPtyWrite`, `scheduleWriteBurstDecay`, `applyRendererPolicy`, `tierChangeTimer`, or `TerminalRefreshTier`.
- Implementing any "decay back after N ms of inactivity" / debounce-on-high-frequency-event pattern in the renderer (terminal output floods, scroll, resize, input bursts) — reach for deadline-timestamp + single timer, not per-event clear/set.
- Investigating renderer jank, dropped frames, or GC pressure during heavy terminal output, or a terminal stuck at the wrong refresh cadence (too slow mid-stream, or too fast/never decaying).
- Touching the focus/click handlers in `TerminalPane.tsx` or `XtermAdapter.tsx` and tempted to re-introduce a focus-driven `boostRefreshRate` — BURST is intentionally write-driven now.
- Wiring a synchronous hook (`onWrite`-style) that must influence rendering before `terminal.write()` and must respect the `isSerializedRestoreInProgress` deferred-restore early-exit (hibernation was removed in PR #10811, so there's no hibernated gate left to respect).
