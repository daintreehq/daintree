## Context

PR #11180 added a per-section entry stagger to the empty-grid launcher (`ContentGridEmptyState.tsx`, six sections: hero, recipes, resume, quick actions, pulse, tip), replacing a single flat `animate-in fade-in duration-200` on the container. It's one of five same-day motion-polish PRs in this arc (#11173, #11175, #11177, #11181); this lesson covers the keyframe-animation-authoring trap, `11177.md` covers the reduced-motion/tailwind-merge traps from the sibling PRs.

## Problem

The obvious implementation — give each section `motion-safe:animate-in motion-safe:fade-in` plus Tailwind's `delay-75`, `delay-100`, `delay-150`... ladder utility — looks completely correct in the rendered class list and would pass any test that asserts the expected classes are present. It doesn't stagger anything: every section arrives at once. The failure is invisible in devtools' Elements panel too, since the classes are exactly the ones you'd expect.

## Root cause

Tailwind v4 core ships its own `delay-*` and `duration-*` utilities that set `transition-delay` / `transition-duration`. tw-animate-css (the plugin providing `animate-in`/`fade-in`/`slide-in-from-*`) defines same-named utilities meant to feed the animation's `--tw-duration`/delay custom properties, but Tailwind core's versions win when both are registered, so `delay-100` on an `animate-in` element sets a **transition** delay — and a `@keyframes`-driven `animation` property never reads `transition-delay`. The section fires immediately, ignoring the intended ladder. `duration-200` has the same problem from the other direction: it emits `transition-duration`, and since these wrapper elements have no `transition-property` set at all, that duration lands on CSS's `all` default — an unintended every-property transition nobody asked for, on top of the stagger still not working. The fix is to bypass both utilities and set the underlying custom properties directly: `motion-safe:[--tw-animation-duration:var(--duration-200)]` for duration, and a literal per-section `--tw-animation-delay` value for the ladder (`SECTION_ENTRY_MARKER` / `SECTION_ENTRY` in `ContentGridEmptyState.tsx`). A second, compounding trap: `animate-in`'s default `fill-mode` is `none`, so a section with a non-zero delay paints fully visible for the delay's duration, then snaps hidden, then fades in — a visible glitch, not a stagger — unless the class also carries `fill-mode-backwards` to pin the animation's `0%` frame (opacity 0) for the delay period.

Fill-mode choice itself has a second axis, drawn from the same-day #11175 (`SettingsCheckbox.tsx`'s `.animate-checkbox-check`, `src/index.css:1010-1029`): `backwards` is correct when the class stays on the element permanently (Radix mounts a fresh `Checkbox.Indicator` node per check, so the class never gets removed — `both` would park a permanent post-animation transform on every checked box). `both` (used by `.animate-agent-pulse` and friends) is correct only when the class is removed on `animationend`, since nothing then needs to hold the end frame open. Picking the wrong one either leaves a stuck visual effect (`both` + never-removed class) or a flash-before-hide (`none`/no fill-mode + delayed one-shot).

## Lesson

- **Never use Tailwind's `delay-*`/`duration-*` utilities on an `animate-in`/keyframe element.** They set `transition-delay`/`transition-duration`, which a `@keyframes` animation ignores; set `--tw-animation-delay` / `--tw-animation-duration` directly instead. Verify by checking compiled output or devtools computed styles for `animation-delay`, not just the class list — the class list looks right even when it's inert.
- **Every non-zero-delay one-shot animation needs an explicit fill-mode.** No fill-mode (default `none`) paints the visible end-state for the whole delay, then snaps to the animation's start frame — a flash-then-hide glitch masquerading as a stagger.
- **Fill-mode choice depends on whether the class outlives the animation.** Use `backwards` when the class is permanent (mounted-once elements, Radix `Indicator`-style remounts); use `both` only when something removes the class on `animationend` (see `.animate-agent-pulse`) — otherwise `both` leaves a stuck end-state transform on every future render.
- **A test asserting the class names are present does not prove the animation works.** This class of bug (present-but-inert classes) needs a structural/contract test instead: PR #11180's `launcherMotionContract.ts` asserts delays strictly increase by a uniform step, every non-zero delay carries `fill-mode-backwards`, and no `duration-*`/`delay-*` leaked into the transition system — assert behavior invariants, not literal class strings.
- **The reduced-motion marker for a keyframe animation is separate from the animation classes themselves.** `motion-safe:` only covers the OS `prefers-reduced-motion` query; Daintree's in-app "Reduce UI animations" toggle needs the element to also carry a marker class registered in `index.css`'s `@variant reduce-motion` block (`launcher-section-enter` here, same pattern as `.content-fade-in`) — omit it and the in-app toggle does nothing for that animation.

## Applies when

- Adding any staggered/sequenced entrance animation built on `animate-in`/`fade-in`/`slide-in-from-*` (tw-animate-css) anywhere in the app.
- Reviewing a diff that adds `delay-*` or `duration-*` classes alongside `animate-*` classes — check whether the target uses `transition` or `animation`, they are not interchangeable in Tailwind v4.
- A newly-added entrance/stagger animation "does nothing" or "all fires at once" despite the classes looking correct in the DOM inspector.
- Choosing between animation `fill-mode: backwards` vs `both` for any one-shot keyframe effect — check whether the triggering class is ever removed after the animation ends.
- Writing a motion-related test — prefer contract assertions (`launcherMotionContract.ts`, `animationUtils.test.ts`'s `discreteFeedbackSelectors`) over asserting a literal class-name string.
