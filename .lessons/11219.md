## Context

`ProcessMemoryMonitor.startAppMetricsMonitor` runs a two-tier memory-pressure mitigation: tier 1 (`destroyHiddenWebviews(1)` + `trimPtyHostState`) fires on a 5-minute cooldown (`TIER1_MITIGATION_COOLDOWN_MS`), tier 2 (`destroyHiddenWebviews(2)` + `evictCachedProjectViews` + `hibernateIdleProjects`) escalates on a separate 10-minute cooldown (`MITIGATION_COOLDOWN_MS`) when pressure persists after tier 1. Issue #11211 reported 9 reclaim passes in one session with deltas of 0, 6, 0, 29, 0, 0, 0, 0, 0 MB and asked for two new levers (`clearTextureAtlas()` on hidden terminals, a GC nudge after teardown) on the premise that the existing levers barely do anything.

## Problem

Reclaim passes fired on schedule, logged a before/after, and the delta was almost always ~0 with `pressureRemains: true` still set. The natural read was "our reclaim levers are weak, ship stronger ones." That read was wrong for most of the cited passes.

## Root cause

The mitigation's `beforeMb`/`afterMb` pair did not bracket the thing it claimed to measure. On the common path tier 1 had already fired on an earlier poll and its 5-minute cooldown blocks a rerun, so by the time tier 2 evaluates, `beforeMb` and the post-tier-1 `afterMb` get sampled back-to-back with **nothing acting in between** — a delta that's zero by construction, not by lever failure. Worse, tier 2 itself was never measured: the old code logged `memory-pressure-tier2-mitigation` with a `deltaMb` from that stale pair, then ran `destroyHiddenWebviews(2)`, `evictCachedProjectViews()`, and `hibernateIdleProjects()` **after** the log line, with no re-sample afterward — every one of tier 2's real actions was invisible to the telemetry the issue was quoting. The fix gives tier 2 its own bracket: run the levers, wait `RECLAIM_SETTLE_MS` (3s), re-sample, and emit a new `memory-pressure-tier2-reclaim` event with its own before/after/delta; `memory-pressure-tier2-mitigation` now logs escalation inputs (`tier1ReclaimMb`, `systemPressureRemains`) instead of a delta it can't back up.

Even with correct brackets, zero still isn't proof a lever did nothing: PartitionAlloc decommit is idle-driven and lazy, so a short settle window can genuinely miss a real win. The fix adds `portalTabsDestroyed` / `viewsEvicted` counts alongside the delta so a zero reads as "nothing eligible" or "levers ran, metric too fast" — previously indistinguishable. Each tier-2 lever is now isolated in its own try/catch too: a thrown `destroyHiddenWebviews(2)` used to skip every lever after it _and_ the measurement below, since the whole block was one unguarded sequence.

The two requested levers were investigated and rejected, not shipped blind. `clearTextureAtlas()` operates on a texture atlas that's a module-global shared by every terminal with matching font/theme/DPR — clearing it for "hidden" terminals blanks visible siblings until their next resize, already noted in first-party comments in `TerminalInstanceService.ts` / `TerminalWebGLManager.ts` (#9701) and deliberately avoided. The GC-nudge premise doesn't hold either: `global.gc()` returns memory to V8's free list, not the OS, so RSS/`workingSetSize` stay flat — it would measure as ~0 reclaimed, the exact symptom reported — and the existing `if (global.gc) global.gc()` in `electron/pty-host/handlers/stateConfig.ts` is dead code since the pty-host has no `--expose-gc` flag.

## Lesson

- **Before accepting "this mitigation frees ~0" from a delta log, check what the before/after sample actually brackets.** With independently-cooling escalation tiers, an earlier tier's cooldown can make a later tier's pair sample back-to-back with zero action in between — a delta of 0 meaning "nothing happened between two samples," not "the lever is weak."
- **Every escalation tier needs its own settle-then-resample bracket around its own actions**, not a shared pair computed before the tier-vs-tier branch decides what runs — reusing one measurement across tiers can leave a whole tier's actions permanently unmeasured, exactly what happened here.
- **A zero delta is not proof a lever did nothing** — OS-level decommit (PartitionAlloc) can be lazy/idle-driven, so a short settle window (`RECLAIM_SETTLE_MS` = 3s) can miss a real reclaim. Log action counts (tabs destroyed, views evicted) alongside the delta so a zero is attributable instead of ambiguous.
- **Isolate each lever in a multi-lever tier** in its own try/catch so one throwing doesn't silently skip the rest and blind the measurement below it.
- **Before proposing a reclaim lever, verify it can mechanistically move the metric you're gating on** — `global.gc()` frees to V8's internal pool, never the OS, and confirm the enabling flag (`--expose-gc`) even exists in the target process before assuming a `global.gc()` call does anything.
- **Check first-party in-code comments for "already tried, rejected" before re-proposing a shared-resource fix** — the texture-atlas sharing tradeoff was already documented and deliberately avoided (#9701).

## Applies when

- Investigating a report that a mitigation/reclaim pass "frees almost nothing" from logged before/after deltas — check whether the sampling window actually spans the action being blamed before trusting the delta.
- Adding an escalation tier to `ProcessMemoryMonitor.startAppMetricsMonitor` or any polling loop where an earlier tier already has its own cooldown (`TIER1_MITIGATION_COOLDOWN_MS`, `MITIGATION_COOLDOWN_MS`) — verify the new tier samples its own before/after, not a shared/reused pair.
- Touching `MemoryPressureActions` (`destroyHiddenWebviews`, `evictCachedProjectViews`, `hibernateIdleProjects`), `evictStaleViews` (`ProjectViewEvictionController.ts`), or `reclaimCachedViewsUnderPressure` (`ProjectViewManager.ts`, delegates to `evictStaleViews`) — all now return counts specifically so callers can attribute a zero delta.
- Proposing a GC-nudge, texture-atlas-clear, or other "obvious" native-memory reclaim lever — verify it reaches the OS-visible metric (RSS/`workingSetSize`) and any required runtime flag/precondition actually exists.
- Reviewing telemetry for any tiered/graduated system (memory, retention, notification escalation) where "zero delta" is used as evidence a path is ineffective — confirm the measurement window can even observe the actor's effect first.
