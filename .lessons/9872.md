## Context

The sidebar wrapper in `src/components/Layout/AppLayout.tsx` uses `overflow: clip` + `contain: "layout paint"` (the #9014 containment work) and carries `overflowClipMargin: "6px"` so the resize handle's overhang (`-right-1.5 w-3`, z-50 in `Sidebar.tsx`) can paint outside the clip boundary. Hide animates the wrapper's width to 0 via `transition-[width]`; the inner content div stays absolutely positioned at full `sidebarWidth`, so hiding relies entirely on the clip.

## Problem

With the sidebar hidden, a persistent 6px strip of it (background + focus corner marker) stayed visible at the left edge (#9864). It looked like an animation glitch or width rounding error, but it was a rest-state fact — the strip remained indefinitely after the collapse — and the margin couldn't simply be deleted because the resize-handle overhang needs it while the sidebar is visible.

## Root cause

`overflow-clip-margin` is a discrete (non-animatable) CSS property — it never interpolates. When the wrapper width transitions to 0, the clip boundary lands at `0 + 6px margin`, so the first 6px of the full-width inner content keeps painting forever; the geometry is simply wrong at rest. The fix is a state machine: `sidebarFullyHidden` gates the margin (`? "0px" : "6px"`), cleared immediately on show (the overhang must be live before the reveal animation) and set only after the collapse completes via a filtered `onTransitionEnd`.

The hard part: `transitionend` only fires when a transition actually runs, and Daintree suppresses this width transition through several independent mechanisms — each silently strands the state machine and leaves the strip. At PR time there were four, each needing a synchronous flush in the hide effect: (1) the in-app `reduceAnimations` toggle and (2) an active drag-resize (`isSidebarResizing`) remove the transition class in the `cn()` conditional, so they're visible to JS; (3) OS-level reduced motion arrives via the `motion-reduce:transition-none` Tailwind variant — the class stays in the DOM but the media query kills it, so JS must probe `window.matchMedia("(prefers-reduced-motion: reduce)")` separately; (4) performance mode: `body[data-performance-mode="true"] *` (`src/index.css` ~2435) sets `transition-property: color, background-color, opacity, outline-color, border-color !important` — it narrows, it does not disable. Cheap-property transitions still run and still fire transitionend, but a `width` transitionend never arrives, so a "transitions still work in perf mode" sanity check passes while the width-dependent state machine starves. Two days later #10327 (commit `782103ccb`) added a fifth suppression mode — `isSidebarWidthHydrating`, gating the transition during the async width restore — and had to extend the flush guard and its deps in the same commit: the enumeration is open-ended, and the class conditional + flush guard must evolve in lockstep.

## Lesson

- **`overflow-clip-margin` (and any discrete CSS property) does not follow animated geometry.** If a clip margin exists for a painted overhang, the collapsed rest state bleeds exactly that margin of content — gate it on a "fully hidden" state instead of leaving it static. And because discrete means it paints on frame one, initialize the state from the real visibility (`useState(() => !showSidebar)`) or a strip flashes on boot with the sidebar hidden.
- **`transitionend` is a completion signal only when a transition actually runs.** Before relying on it, enumerate every mode that suppresses the specific property's transition and flush the state synchronously in each: `reduceAnimations`, drag-in-progress, `prefers-reduced-motion` via matchMedia, `layout.performanceMode`, and (post-#10327) `isSidebarWidthHydrating`.
- **Performance mode narrows `transition-property`, it does not kill transitions.** Cheap properties still animate and fire transitionend under `data-performance-mode`; width/height/transform/box-shadow are stripped by the `!important` wildcard. Never conclude "transitions run, so my transitionend will fire" from observing a color transition.
- **`prefers-reduced-motion` is invisible to your class logic.** The `motion-reduce:transition-none` variant leaves the transition class in the DOM — JS sees a live transition that CSS has disabled. Probe `window.matchMedia` explicitly.
- **Adding a new transition-suppression condition to an element is a breaking change to every transitionend handler on it.** #10327 added hydration-window suppression and correctly extended the flush guard in the same commit; miss that step and the cleanup regresses. Audit `onTransitionEnd` wiring (sidebar handler, `handleAssistantTransitionEnd`, `ForgeStatsToolbarButton`) whenever you touch the suppression set.
- **Filter transitionend hard:** `propertyName === "width"`, `target === currentTarget` (ignores bubbled child transitions), and re-check the driving state (`!showSidebar`) — a hide reversed mid-animation otherwise clips the now-visible sidebar.

## Applies when

- Wiring `onTransitionEnd`/`transitionend` as a completion signal for any UI state machine in the renderer — the suppression-mode flush checklist applies verbatim.
- Using `overflow-clip-margin`, or pairing any discrete/non-animatable CSS property (`content-visibility`, `display`, grid placement) with animated geometry.
- Adding or removing a condition that gates a `transition-*` class (like `isSidebarResizing`/`isSidebarWidthHydrating`) — the paired synchronous-flush guard must change in lockstep.
- Diagnosing "a strip/edge of hidden UI stays visible at rest" or "cleanup only happens under some animation settings" — check which mode suppressed the transition before suspecting the handler.
- Touching the perf-mode wildcard in `src/index.css` — widening or narrowing its `transition-property` list changes which transitionend events exist app-wide.
