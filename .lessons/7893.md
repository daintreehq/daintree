## Context

`PtyPool` (`electron/services/PtyPool.ts`) keeps warm shells keyed by `(cwd, envHash)` so terminal spawns feel instant. Pool entries are abandoned on many paths: shell exit (`onExit`), `dispose()`, `drainAndRefill()` (cwd switch), LRU eviction, and the `ENOTTY` resize-fallback in `terminalSpawn.ts`. Every one of those paths used to call `entry.process.kill()` and consider the entry torn down.

## Problem

On macOS/Linux every pool-abandon path leaked a `/dev/ptmx` master fd. In isolation it was slow, but a single misconfigured `(cwd, envHash)` — a broken `.zshrc`, a failing `.envrc`, a dead `mise`/`asdf` hook — made the warmed shell exit immediately on spawn. The `onExit` handler then refilled the slot, which spawned another shell that exited immediately, an unbounded spawn→exit→refill storm. Combined with the per-cycle leak that was ~60 leaked fds per iteration, marching toward the system-wide `kern.tty.ptmx_max` (~511 on macOS) until all PTY creation failed across the entire system (even Terminal.app).

## Root cause

Two independent gaps that amplified each other:

- `node-pty`'s `kill()` only sends a signal to the child process. On Unix the master fd for `/dev/ptmx` stays open until `destroy()` is called (the native binding holds a reference; GC alone is not timely). `kill()` intuitively reads as "full teardown" but does not close the fd. Worse, `destroy()` is **not** on the exported `IPty` TypeScript interface — only on the concrete `UnixTerminal`/`WindowsTerminal` — so you cannot call it through the typed handle.
- `refillPool` had no crash-loop guard, so one doomed key turned the leak into an infinite loop. A related trap: the old liveness probe `entry.process.pid !== undefined` was always truthy because `pid` persists on the `IPty` JS wrapper after the child has exited — so dead pool entries passed the health check.

## Lesson

- To actually release a PTY fd, call `destroy()`, not just `kill()`. Wrap it in a `destroyPty(p: IPty)` helper that accesses `destroy` **structurally** (`(p as IPty & { destroy?: () => void }).destroy?.()`) with a `kill()` fallback for mocks/older versions, both in try/catch (either may throw `ESRCH`/socket-closed on an already-dead handle). `destroyPty()` in `PtyPool.ts` is the canonical fd-release primitive — it was later adopted by live (non-pooled) terminals too in `TerminalProcess.teardown()` (#9539). Call it on **every** path that abandons a PTY, not just the obvious exit path.
- This is the active-remediation counterpart to #3710's detect-only `FdMonitor`. #3710 deliberately said "do NOT auto-close leaked fds, cleanup happens on host restart"; that referred to fds whose owning JS handle is gone. When you still hold the `IPty`, `destroy()` is the correct close.
- Don't probe liveness with `pid !== undefined` — track a `boolean alive` flag set false in `onExit`.
- Guard any self-refilling pool/warm loop with a per-key circuit breaker: count exits faster than `FAST_EXIT_THRESHOLD_MS` (2s), trip after `MAX_KEY_FAILURES` (3), back off `KEY_BACKOFF_MS` (30s). Gate **only** the background warm paths (`refillPool`, `warmForKey`, `warmPool` — including the trailing `warmPool()` inside `drainAndRefill`); never gate explicit user-triggered `acquireByKey`, which must always fall through to a fresh spawn. Reset the count lazily on cooldown expiry, not eagerly on a single slow exit, or a borderline shell oscillates the breaker (same lesson as #518/#3333).
- When tearing down many entries (`dispose`), snapshot-and-clear the pool map BEFORE calling `destroyPty`, because `destroy()`→`kill()`→`onExit` can re-enter and double-process the same entry.

## Applies when

- Tearing down or recycling node-pty handles anywhere (`PtyPool`, `TerminalProcess`, `terminalSpawn`, pool eviction/drain paths); reviewing any code that calls `ptyProcess.kill()` and assumes the fd is gone.
- Diagnosing `EMFILE` / `posix_spawnp failed` / `forkpty: Device not configured` PTY spawn failures, or fd counts climbing across a long IDE session.
- Adding any self-refilling warm/pool/retry loop fed by a spawn whose target can fail deterministically (bad shell-init, broken env hook) — needs a per-key breaker gated on automatic refills only.
- Calling a node-pty method that TypeScript says doesn't exist on `IPty` (`destroy`) — access concrete-subclass methods structurally with a fallback.
- Writing a liveness check on a pooled/cached process handle — `pid` stays defined after exit; track an explicit `alive` flag.
