## Context

A hung (deadlocked) main process is the one crash class with zero self-recovery path: it can't run its own timers, IPC handlers, or restart logic, so nothing inside main can detect or fix the freeze. PR #6353 added an external watchdog `UtilityProcess` (`electron/watchdog-host.ts`, pure logic in `watchdog-host-core.ts`, managed by `MainProcessWatchdogClient`) that receives main's PID via `--main-pid=<pid>` argv, expects a `ping` every `HEARTBEAT_INTERVAL_MS` (5s), and `SIGKILL`s main after `MAX_MISSED` (3) missed beats (~15s). `CrashRecoveryService`/`CrashLoopGuard` then relaunch and attribute the kill via a sidecar `watchdog-kill.flag`.

## Problem

Two failure modes make a naive watchdog worse than none: (1) a **false-positive kill** — the watchdog SIGKILLs a healthy main during normal long pauses (V8 major GC, synchronous better-sqlite3 ops) or, far worse, on **system wake** after a laptop sleep; (2) the watchdog itself becoming a **runaway** that burns CPU restarting forever, or correlating its restarts with another crashing service. Killing a healthy main loses all unsaved work — false positives are categorically worse than missing a deadlock.

## Root cause

The wake false-positive is the non-obvious one. When the OS suspends, `setInterval` callbacks don't stop being scheduled — macOS and Windows both **deliver the suspended ticks as a packed burst at resume**. Each queued tick would call `watchdog.tick()` and increment `missedBeats`, crossing the kill threshold _before_ main's post-wake arming `ping` lands. Pausing the ping interval alone is insufficient because the tick interval lives in the watchdog process, not main. The fix has three layers:

- **`lastWakeTimestamp` grace window** (`watchdog-host-core.ts:80`): `tick()` no-ops if `now() - lastWakeTimestamp < HEARTBEAT_INTERVAL_MS`, absorbing exactly the burst. It uses **`performance.now()` not `Date.now()`** — monotonic clock is immune to wall-clock jumps from NTP/user time changes that a long sleep can introduce. The window only arms after a real `wake` (timestamp starts at 0) so it never masks a frozen-at-boot main.
- **Belt-and-suspenders pause** (`MainProcessWatchdogClient.pause()` + `powerMonitor.ts:52`): both stops the ping interval _and_ sends an explicit `sleep` message, so an out-of-order delivery on either path still suppresses the kill. `resume()` sends `wake` then an immediate `ping` to reset `missedBeats=0` and re-arm before the first post-wake tick.
- **Fail-open kill gating** (`watchdog-host.ts:76-93`): the kill closure re-probes `process.kill(pid, 0)` (POSIX existence check; Node maps it to `OpenProcess` on Windows) before firing, strict-parses the PID (`/^\d+$/`, rejecting `parseInt`-truncatable `"123abc"`), and the `watchdog-kill.flag` write swallows all errors so a disk failure never delays SIGKILL.

The runaway is guarded by a **time-windowed sliding crash counter** in `MainProcessWatchdogClient` (3 crashes in 5min trips the cap; a clean 5min stretch decays the window) — the comment notes this replaced an earlier 30s-uptime-reset that a slow loop (crash every 35s) defeated forever. Its full-jitter backoff floor/cap (`250/1500..5000ms`) is **deliberately decorrelated** from `PtyHostLifecycle`'s (`100/1000..10000ms`) so a shared trigger (OOM, signal) doesn't synchronize their restarts.

## Lesson

- A deadlocked main process can only be recovered by an **external process holding kill authority**. Put the kill logic in a `UtilityProcess` that owns nothing else; pass main's PID via named argv (`--main-pid=`), and have main keep the watchdog armed only via a heartbeat `ping`.
- **Any timer-based liveness check across system sleep MUST handle the wake-burst of queued `setInterval` callbacks.** Stopping the producer-side ping is not enough when the consumer-side interval lives in another process. Add a monotonic (`performance.now`) post-wake grace window of one interval, and gate it on having actually observed a `wake` so it can't mask a boot-time freeze.
- Around `powerMonitor` `suspend`/`resume`, suppress the watchdog on **both** the interval-stop path and an explicit `sleep`/`wake` message — out-of-order or dropped delivery on one path must not produce a kill.
- Treat the kill path as **fail-open**: re-verify the target PID is alive before SIGKILL, strict-parse the PID, and never let best-effort annotation writes gate the kill. A missed deadlock is recoverable by the user; a false kill destroys their session.
- When two services restart with jittered backoff, **decorrelate their floor/cap ranges** so a shared crash trigger doesn't synchronize their respawns into a collision.

## Applies when

- Adding or modifying any process-liveness, heartbeat, deadlock-detection, or self-healing supervisor in `electron/` (watchdog-host, `MainProcessWatchdogClient`, pty-host, workspace-host).
- Touching `electron/window/powerMonitor.ts` `suspend`/`resume` handlers, or anywhere a `setInterval`/timer must survive system sleep without false-firing on wake.
- Choosing `performance.now()` vs `Date.now()` for any interval that spans suspend, NTP adjustment, or user clock changes.
- Implementing SIGKILL / `process.kill` of another PID from a UtilityProcess, or parsing a PID/argument out of `process.argv` in a forked host.
- Designing full-jitter / exponential backoff restart loops for multiple co-resident utility processes (`PtyHostLifecycle`, `CrashLoopGuardService`) — avoiding correlated respawn collisions and slow-crash-loop counter defeats.
- Wiring crash attribution via sidecar flag files read on next launch (`CrashRecoveryService`, `watchdog-kill.flag`).
