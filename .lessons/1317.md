## Context

When a user types a prompt into an agent terminal, each keystroke is echoed back through the PTY. The ActivityMonitor's output-volume heuristic saw those echo bytes and flipped the agent into "busy" state while the user was still composing their message.

## Problem

Purely output-based busy detection cannot distinguish "agent is doing work" from "terminal is echoing my keystrokes". Character echo is indistinguishable from tiny agent progress updates at the byte level. Any heuristic that looks only at output bytes will false-positive on typing.

## Root cause

Output-driven busy entry had no way to recognize echo. The current fix splits the problem across two collaborators. (1) `InputTracker` (electron/services/pty/InputTracker.ts) recognizes echo before it can drive a transition: `isLikelyUserEcho()` returns true only when `isRecentUserInput(now)` is within the input-recency window, no input is pending confirmation, the chunk is under `ECHO_MAX_BYTES` (default 24), and it contains no ESC/CR/LF or other control chars. ActivityMonitor short-circuits on echo chunks and `becomeBusyFromOutput()` additionally refuses to enter busy from output when input is recent and not yet confirmed (`pendingInputUntil === 0 && isRecentUserInput(now)`). (2) CPU is no longer a busy-entry cross-check. `CpuHighStateTracker.isHighAndNotDeadlined()` (electron/services/pty/CpuHighStateTracker.ts) now gates IDLE-EXIT / hysteresis only: it keeps the monitor busy while the child's descendant CPU stays high, bounded by `maxCpuHighEscapeMs`, so prompt-fast-path, lexeme-stall, and timeout idle paths won't drop a genuinely working agent. With a null validator it fails open (no veto), so tests and CPU-less environments don't stall.

## Lesson

Output-based busy detection needs a corroborating second signal before it flips state: input recency (echo suppression), a pattern match against a known "working" indicator, output volume well above plausible echo rates, or CPU. CPU is a bounded busy-state backstop, not a busy-entry decider — use it to resist premature idle, not to manufacture or veto activity. A fail-open fallback is essential: when no validator is wired (e.g. in tests), don't block transitions, or you'll break unrelated flows. Keep input-driven transitions (keystrokes that correspond to submission, Enter) immediate so user-initiated state changes stay snappy.

## Applies when

Tuning ActivityMonitor heuristics, adjusting `InputTracker` echo suppression or `CpuHighStateTracker` hysteresis, adding a new signal source for agent state detection, or debugging "agent shows busy while I'm still typing" / "agent flips to idle while it's still working".
