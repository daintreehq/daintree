## Context

Daintree had duplicated file-viewer, diff-viewer, and review-hub UIs: one version as an in-grid panel (`FilePane`, `DiffPane`, `ReviewPane`) and a second as a hand-rolled modal (`FileViewerModal`, `FileDiffModal`, `ReviewHub.tsx`) opened via window `CustomEvent`s. #11247 introduced a `"dialog"` `PanelLocation` so the same panel component renders unmodified inside a modal, backed by a new `panelDialogStore` and `PanelDialogHost`. #11249 moved the diff/changeset review workspace onto it, and #11252 moved the review hub onto it — the arc is one design, discovered and corrected across three merged PRs in the same week (2026-07-19).

## Problem

The naive version of this design breaks in two ways that only surface once real usage hits it, not in the first PR's own testing. If the ephemeral panel record's lifecycle were owned by the presenting component's mount/unmount effects, the panel would be destroyed and recreated on the very first dev mount. Separately, #11252 found that routing the review hub through #11247's dialog store made clicking any file inside the review to read its diff destroy the review surface entirely — commit draft, file selection, filters, diff mode, readiness rail, all gone — because opening the per-file diff dialog superseded the review dialog hosting it.

## Root cause

Two non-obvious mechanisms compound here, plus one more found while evaluating an alternative fix.

1. **React 19 StrictMode double-invokes effects in development.** If panel create/destroy lived in a `useEffect` on the presenting component, the double-invoke would destroy and recreate the ephemeral record on the first mount. `panelDialogStore.openPanelDialog`/`closePanelDialog` do the create/destroy explicitly in store actions triggered by user intent, never inside `PanelDialogHost`/`PanelDialogFrame`'s own effects — those components only read `panelId` via a `useCallback`-scoped selector and render whatever the store already decided exists.
2. **A single-slot store self-defeats the moment a dialog opens a dialog.** #11247's `panelDialogStore` held one `panelId`; any new `openPanelDialog` removed the panel behind the previous one — correct for independent callers, but the review hub (#11252) is dialog-presented and itself opens a per-file diff dialog, its own child. Under the single-slot design, opening the child necessarily destroyed the parent. The fix was `dialogStack: string[]` plus an opt-in `pushPanelDialog(options, expectedParentId)` that layers instead of replacing; ordinary `openPanelDialog` still supersedes the whole stack, so every pre-existing caller is unaffected. `expectedParentId` is a compare-and-swap against the current top — if the parent closed or got superseded between render and the push resolving, the push is refused rather than resurrecting a dead surface.
3. **Re-parenting a mounted record between hosts remounts it and loses state anyway**, why "promote review to grid on drill-down" was considered and rejected in #11252: moving `location` from `"dialog"` to `"grid"` moves the record from `PanelDialogHost` to `GridPanel`, a different React parent, so React remounts the component and local state (draft, scroll, selection) is gone — same failure mode as the single-slot bug, different path. `PanelDialogHost` instead keeps every stack entry mounted (`dialogStack.map`, not just the top), with only the topmost frame focused and given the nested z-index tier.

## Lesson

- **Ephemeral UI-owned records must have create/destroy driven by explicit user-intent store actions, never a presenting component's mount/unmount effect** — StrictMode's dev double-invoke destroys-and-recreates anything effect-owned. `panelDialogStore.openPanelDialog`/`closePanelDialog`/`pushPanelDialog` are the pattern to copy.
- **Before making a "single active X" store host a caller that can itself open another X, check whether that caller nests.** A slot/pointer store (one dialog, one active tab, one focused overlay) works until something presented through it opens another instance of itself; #11252 hit this on the very next PR in the arc.
- **Prefer additive layering over retrofitting supersede semantics.** `pushPanelDialog` only fires for the one caller (the review hub's per-file diff) that needs nesting; every other `openPanelDialog` caller keeps its old supersede behavior, so the fix couldn't regress the many for the one.
- **Re-parenting a record across host components (grid ↔ dialog ↔ dock) is a remount, not a location update** — before "promoting"/"demoting" a live panel between presentation surfaces to fix a lifecycle problem, check whether the surfaces are different React parents; if so, state loss is identical to destroying it outright.
- **A field that must hold across every panel kind belongs on `BasePanelData`, not the narrowest type that first needed it.** `excludeFromPersistence` started narrowed to `PtyPanelData`; moving it to `BasePanelData` was required before a non-PTY dialog panel could rely on it, and `isEphemeralPanel` (`panelCount.ts`) is deliberately NOT kind-narrowed for the same reason.

## Applies when

- Adding any ephemeral, non-persisted UI record (a dialog, a wizard step, a preview) whose lifecycle must survive React 19 StrictMode's double-mount in dev.
- Designing or extending a "one active X" store (single dialog, single focused panel, single active tooltip) — ask whether X can trigger another X before shipping the single-slot version.
- Touching `panelDialogStore.ts`, `PanelDialogHost.tsx`, or adding a new `openPanelDialog`/`pushPanelDialog` caller — verify whether it can open a dialog from inside a dialog.
- Considering "promote/re-parent this component to a different host" as a fix for lifecycle/state-loss — confirm the hosts aren't different React parents before trusting it preserves state.
- Adding a flag like `excludeFromPersistence`/`isEphemeralPanel` that must hold across a family of panel kinds — confirm it's on the base shape and kind-agnostic at every read site.
