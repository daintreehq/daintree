## Context

Terminals render on two paths: the pooled WebGL addon (`TerminalWebGLManager`) and xterm's built-in DOM renderer, which takes over whenever WebGL isn't attached — fleet above the pool's upper threshold (static 12 at PR time; RAM-tiered since #11192, bootstrap 18/15 in `src/services/terminal/TerminalWebGLConfig.ts`), WebGL disabled (`DAINTREE_DISABLE_WEBGL=1`, GPU blocklist), or context loss. Separately, the `Terminal.dispose()` leak fix (#9546/#9547, upstream xterm #5818) forced the `@xterm/xterm` pin onto the 6.1.0 beta line — which is where this bug lives.

## Problem

Emoji and complex grapheme clusters rendered horizontally collapsed/overlapping in terminal output — agent status glyphs, progress spinners, branch names with emoji (issue #9812). The misleading part: it's fleet-size dependent. A 5-terminal session (WebGL) renders perfectly; open enough terminals to flip the pool to DOM mode and the same output collapses, so it presents as intermittent and machine-dependent rather than as a deterministic renderer bug.

## Root cause

Upstream xterm #5893, introduced in `6.1.0-beta.65` by the OffscreenCanvas WidthCache PRs (#5548/#5549): `OffscreenCanvas.measureText` returns wrong widths for multi-cell emoji and grapheme clusters, and the DOM renderer compensates by writing a negative inline `letter-spacing` (e.g. `-0.55px`) onto each `<span>` — that inline value is what collapses them, and `terminal.options.letterSpacing` cannot override it. The pin is wedged between two upstream bugs: downgrading below beta.65 reintroduces the dispose leak (#5818 is not backported), and the emoji fix ships only in the 7.0.0 milestone — no 6.1.0 release, including stable, will have it. So the mitigation is host CSS in `src/index.css`: `.xterm-rows span[style*="letter-spacing: -"] { letter-spacing: 0 !important; }`. Author-origin `!important` beats the library's non-important `element.style` declaration; matching only negative values spares xterm's correctly-measured positive corrections for wide CJK glyphs; clamping to `0` (not `initial`) matches the baseline because `src/config/xtermConfig.ts` sets `letterSpacing: 0` (`initial` would be `normal`).

The PR shipped with a latent assumption that broke later: the selector assumed Chromium serializes the inline style as `letter-spacing: -Npx` (space after colon). Nightly runs hit the other form, and `f4ef0e308` had to add a second selector `[style*="letter-spacing:-"]` plus a `normalizeZeroLetterSpacing` helper in the E2E test, because computed zero letter-spacing came back as `"normal"` in some environments and `"0px"` in others. Both hardenings are the same class of bug: string-matching against a serialization that was never contractually stable.

## Lesson

- **To defeat a style a library writes inline on every render, use author `!important`, not JS.** A same-origin author `!important` declaration beats a non-important `element.style` value with zero runtime cost — no MutationObserver, no re-write race with xterm's row recycling. Scope it tight (`.xterm-rows span`) and match only the broken direction (negative) so the library's legitimate corrections survive.
- **Never key a `[style*=...]` selector to one serialization of a declaration.** The text after the colon in a style attribute is not stable — both `letter-spacing: -` and `letter-spacing:-` have been observed, and the original single-form selector silently stopped matching until `f4ef0e308` doubled it. Any attribute-substring match against inline CSS must list both spacing variants.
- **Zero letter-spacing computes as `"0px"` or `"normal"` depending on environment** — assert computed-style zeros through a normalizer (see `normalizeZeroLetterSpacing` in `e2e/full/terminal/core-terminal-panels.spec.ts`), never raw string equality. The cascade itself is testable without rendering emoji: inject probe spans and read `getComputedStyle` synchronously inside one `evaluate` so re-renders can't race the assertion.
- **"Broken only with many terminals open" means the DOM renderer.** The WebGL pool flips the whole fleet to DOM above `getWebglUpperThreshold()` (RAM-tiered since #11192; don't hardcode the old 12). Reproduce DOM-renderer bugs by exceeding the threshold or launching with `DAINTREE_DISABLE_WEBGL=1` — and remember default CI runs GPU-less, so CI exercises the DOM path even when local dev doesn't.
- **The workaround has an explicit removal condition: `@xterm/xterm >= 7.0.0`.** Until then it must survive every 6.1 beta bump (still live at `6.1.0-beta.290`). On the 7.0.0 bump, delete the clamp rule in `src/index.css` and its cascade test together; keeping either alone leaves a dead rule or a failing test.

## Applies when

- Bumping any `@xterm/*` package — check whether the bump crosses 7.0.0 (remove the clamp + test) or stays on 6.1 betas (keep both, and never downgrade below `6.1.0-beta.65`: that trades this bug for the dispose leak of #9546).
- Diagnosing emoji, grapheme-cluster, or wide-glyph overlap/collapse in terminal output, especially when it only reproduces with a large fleet, on GPU-less machines, or in CI.
- Writing or reviewing any CSS override that matches inline styles via `[style*=...]` — the serialization-form trap applies anywhere in the app, not just xterm.
- Tempted to fix a library-written inline style with `terminal.options.*`, a MutationObserver, or JS post-processing — the cascade beats all of those here.
- Touching the xterm override block in `src/index.css` (`@layer base`, ~line 908) or the mode-flip thresholds in `TerminalWebGLConfig.ts`.
