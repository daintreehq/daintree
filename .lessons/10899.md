## Context

`PluginService` added live enable/disable for built-in plugins in #9304 (`_applyBuiltinToggle`): disable runs the full `unloadPlugin()` cascade, enable re-registers via `loadPlugin()` then calls `activatePlugin()`, all synchronously in-process. #10899 extends that same live-toggle path to user (non-builtin) plugins — renaming `_applyBuiltinToggle` to `_applyEnabledToggle` — because #10526 already routes every non-builtin `activate()` through a fresh `utilityProcess.fork()` per activation, eliminating the old rationale (Node's ESM module cache has no eviction API) for keeping user plugins on a restart-required path.

## Problem

Nothing user-visible had shipped broken; the PR body flags a bug it "widened" while extending scope, and fixes it in the same diff: a stale in-flight `activatePlugin(pluginId)` promise begun before a disable could resolve _after_ a fast disable→re-enable cycle had already loaded a brand-new generation under the same id, and mark that NEW generation as already-activated — short-circuiting its real worker-fork activation. Reachable symptom: toggle a user plugin off then immediately back on, and the fresh generation's contributions (panels, actions, forge providers) silently never resolve because `activatedPlugins.has(pluginId)` already reads true from the stale completion.

## Root cause

`activatePlugin()` caches results in two mutable collections keyed only by the plugin-id string: `activationPromises` (a `Map<string, Promise<void>>`, in-flight) and `activatedPlugins` (a `Set<string>`, settled-success fast path, checked at the top of every call). Before this PR's fix, the `_doActivate(pluginId).then()` success handler tested only presence — `if (this.plugins.has(pluginId))` — before adding to `activatedPlugins`. `unloadPlugin()` deletes the `pluginId` key from `this.plugins` synchronously on disable, and the subsequent `loadPlugin()` on re-enable inserts a BRAND NEW `LoadedPlugin` object back under that exact same key. A presence check can't tell "the id was torn down and reloaded as generation 2" from "generation 1 is still current" — both read `plugins.has(pluginId) === true`. So a generation-1 `_doActivate` promise settling after generation 2 has already loaded marks the CURRENT id as activated, even though generation 2's own worker-fork activation may still be mid-flight or never ran. The fix (`PluginService.ts:1774-1799`) captures the `LoadedPlugin` object reference (`plugin`) and the specific `Promise` reference (`promise`) at the top of `activatePlugin()`, then identity-compares both at completion: `this.plugins.get(pluginId) === plugin` gates the success branch, `this.activationPromises.get(pluginId) === promise` gates the rejection branch's cleanup. Only the generation that produced a given completion may mutate the shared maps; a stale generation's callback becomes a no-op. The race was inert under #9304 alone because built-in activation is synchronous and in-process — the window between "unload deletes the map key" and "reload sets a new object" was too narrow to lose in practice; #10899 made the window real by giving user-plugin activation a genuine OS process boundary (`utilityProcess.fork()` handshake), so the fix shipped in the same PR as the widened surface rather than after a bug report.

## Lesson

- When an async operation caches its result under a mutable string-keyed `Map`, and that key can be torn down and refilled with a NEW instance while the operation is still in flight, a presence check (`.has(key)`) cannot detect staleness — capture the object/promise reference at the start of the operation and identity-compare (`===`) at completion, exactly as `activatePlugin` now does against `plugin` and `promise`.
- **Widening the scope of an existing live-toggle pattern can turn a theoretical race into a practically-reachable one purely by adding latency** — going from in-process `activate()` (#9304) to a forked worker (#10526) is what made the disable→re-enable window wide enough to lose. Whenever a synchronous fast path is extended to cover a slower async case, re-audit every presence-based guard on the maps it shares.
- Both completion branches need the same staleness guard, not just the happy path — the PR fixes the `.then()` success handler (`activatedPlugins.add`) AND the rejection handler (`activationPromises.delete`), because a stale generation's rejection could otherwise evict the current generation's legitimate in-flight promise too.
- `enableTransitions` (the per-id chain from #9304 that serializes `setEnabled` calls) does NOT serialize against `activatePlugin` itself — lazy triggers (dispatch, panel-open, forge/decoration pull) call `activatePlugin` directly outside that chain. Serializing one entry point into shared state doesn't protect against a second, independent entry point into the same state.
- Before removing a restriction justified by a specific stated technical reason (here: "ESM cache staleness has no eviction API"), verify whether an earlier PR already removed the underlying cause, and cite it explicitly (#10526) — don't just assert the restriction is now obsolete.

## Applies when

- Touching `PluginService.activatePlugin`, `_applyEnabledToggle`, `unloadPlugin`, or `enableTransitions` — any change to plugin load/unload/enable ordering or timing.
- Adding or reviewing a cache/fast-path `Map` keyed by a reusable string id (plugin id, panel id, worktree id) where the underlying object can be torn down and recreated while an async operation still holds a reference to the old one.
- Extending a feature that was previously safe only because it was synchronous/in-process into an async or cross-process path (worker fork, IPC round-trip, subprocess spawn) — every presence-based (`.has`) guard along that path needs re-checking for identity.
- Removing a restart-required / session-fixed restriction that cites a specific technical reason — grep for the PR that actually fixed the cited cause instead of assuming it's stale.
- Diagnosing a plugin whose enable/disable toggle "sometimes doesn't take" after a rapid disable→re-enable — check whether `activatedPlugins` or `activationPromises` reflects a stale generation rather than the current one.
