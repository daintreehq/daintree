## Context

Panel kinds (terminal/browser/dev-preview plus plugin-contributed kinds) live in a registry that is shared _by source module_ between main and each renderer's V8 context: `shared/config/panelKindRegistry.ts` (`PANEL_KIND_REGISTRY`, metadata) and the renderer-only `src/panels/registry.tsx` (`PANEL_KIND_DEFINITION_REGISTRY`, the actual React component). `GridPanel`/`DockedPanel` resolve a panel's kind to a component; an unknown kind renders `PluginMissingPanel`. When a plugin loads at runtime it registers a new kind in main.

## Problem

A plugin registering or unregistering a panel kind at runtime mutated the registry silently. Because each process holds its _own_ copy of the module-level registry object, mutating it in main (or in one renderer) did not notify the other side. A panel whose kind had just been contributed stayed stuck on the `PluginMissingPanel` placeholder until a full window reload re-bootstrapped the renderer registry.

## Root cause

"Shared" here means _same source file_, not _same object_ — main, and every per-project `WebContentsView`, each evaluate the module independently and get a distinct `PANEL_KIND_REGISTRY` instance. There is no implicit propagation across the process boundary, and within a renderer a plain object mutation doesn't trigger React re-render. Three things were missing: (1) an event channel so registry mutations in main reach renderers, (2) a way for React to observe the renderer-side definition map, and (3) discipline about _which_ mutations emit. Several subtleties make this non-trivial:

- Built-in kinds register at module load _before any subscriber exists_, so emitting for them is pure noise; emission is gated on `config.extensionId !== undefined`.
- The shared registry stays browser-safe — listeners are plain `Set<>` (`registerListeners`/`unregisterListeners`), not a Node `EventEmitter`, because the renderer imports the module with no `events` polyfill.
- `unregisterPluginPanelKinds(pluginId)` fires the unregister listener once per removed kind, so `PluginService` coalesces a burst into a single `queueMicrotask` broadcast carrying the current snapshot (`schedulePanelKindsBroadcast`), and drops the pending microtask on `dispose()` to avoid leaking an emit across test boundaries.
- The renderer uses BOTH a mount-time pull (`plugin.getPanelKinds()` IPC, a safety net for cached `WebContentsView`s that missed a broadcast) AND push-on-change (`onPanelKindsChanged`). Push is authoritative: once a push arrives, a later-resolving mount pull is dropped (`pushReceived` guard in `usePluginPanelKinds`) so it can't roll back state.
- A plugin re-registering the same kind with `hasPty` flipped requires explicitly unregistering the stale _definition_ first, or the renderer keeps the old `TerminalPane` host while metadata says non-PTY.

## Lesson

For any registry shared by-module across the main/renderer process boundary (panel kinds, toolbar buttons, plugin actions), runtime mutation does NOT propagate — you must build the propagation explicitly:

- Add `onDid*Register`/`onDid*Unregister` emitters in the shared module using plain `Set` listeners (keep it browser-safe; no `EventEmitter`), and emit ONLY for plugin-owned entries, never bootstrap built-ins (gate on `extensionId !== undefined`).
- Bridge to renderers via a main-side service that subscribes to those emitters and broadcasts over IPC; coalesce same-tick bursts with `queueMicrotask` and cancel the pending broadcast on disposal.
- On the renderer, sync the shared metadata registry AND the renderer component-definition registry, and expose the definition map through `useSyncExternalStore` (replace the snapshot object, don't mutate it) so `GridPanel`/`DockedPanel` re-render and hot-swap `PluginMissingPanel` into the real component.
- Pair pull-on-mount (safety net) with push-on-change (authoritative); guard the pull so a late resolution can't overwrite newer push state.
- When metadata that selects the host component (`hasPty`) can change, unregister the stale definition before re-registering.

## Applies when

- Adding or changing a runtime-mutable registry that is imported by both `electron/` and `src/` (panel kinds, `toolbarButtonRegistry`, plugin actions, agent registry) and expecting one side's mutation to be visible on the other.
- A plugin/extension contributes a panel kind, toolbar button, or action at runtime and the UI doesn't update until reload (stuck on `PluginMissingPanel` or a missing button).
- Building any main→renderer broadcast for plugin lifecycle where multiple kinds register/unregister in one call (need coalescing) or where cached/background `WebContentsView`s may have missed a broadcast (need pull-on-mount + push-authoritative guard).
- Wiring `useSyncExternalStore` against a module-level registry in `src/panels/registry.tsx` or `src/registry/` and a component isn't re-rendering on registry change.
- Touching `shared/config/panelKindRegistry.ts`, `src/hooks/usePluginPanelKinds.ts`, or `electron/services/PluginService.ts`, especially the `extensionId`-gated emission or the `hasPty` flip handling.
