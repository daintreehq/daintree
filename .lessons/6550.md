## Context

The renderer drives terminal sizing through `terminalClient.resize` / `TerminalResizeController` (ResizeObserver + xterm fit), and spawns terminals through `terminalClient.spawn`. These are two independent IPC channels (`TERMINAL_RESIZE` and the spawn handler in `electron/ipc/handlers/terminal/lifecycle.ts`) with no ordering guarantee. In the main process, `PtyManager.resize()` looks the terminal up in `this.registry`, and `PtyManager.spawn()` constructs the `TerminalProcess` with `options.cols`/`options.rows` as the PTY's initial dimensions.

## Problem

Because the renderer's ResizeObserver fires as soon as the xterm DOM lays out — which is faster than the spawn IPC round-trip — `resize(id, ...)` routinely arrives before `spawn(id, ...)`. The terminal isn't in the registry yet, so the old code logged `"Terminal not found, cannot resize"` and silently dropped the dimensions. The PTY then booted at the spawn-options default size, and unless a later resize happened to fire, the terminal (and any TUI/agent inside it) ran at the wrong dimensions. This is a steady-state race on every spawn, not an edge case.

## Root cause

The renderer/spawn ordering is genuinely non-deterministic and the resize half usually wins. There is no point in the registry-based `resize()` path that can apply a size to a terminal that doesn't exist yet. The fix is a per-terminal `pendingResizes` map: a pre-spawn `resize()` buffers `{cols, rows}` (last-write-wins), and `spawn()` folds the buffered dims into `options` so the PTY boots at the correct size as **initial dimensions** — not as a post-start SIGWINCH, which avoids the resize-after-start TUI reflow churn.

The subtle correctness point is buffer lifetime. `spawn()` reads the pending entry at the top but deletes it (`this.pendingResizes.delete(id)`) only on line 295, immediately before `this.registry.add(id, terminalProcess)` — i.e. _after_ `acquirePtyProcess` and the `TerminalProcess` constructor have both succeeded. If either throws (orphaned PTY path), the buffer survives so a caller retry still applies the correct dims. `kill`, `trash`, `gracefulKill`, and `dispose` each clear the entry so stale dims can't leak into a later respawn of the same id. `resize()` also now rejects non-finite or non-positive dims before buffering.

## Lesson

- When two independent IPC channels touch the same entity with no ordering guarantee, do not assume the "create" call lands first. The renderer's layout-driven resize beats the async spawn round-trip routinely.
- Buffer the out-of-order signal main-side keyed by entity id (last-write-wins), and consume it as **initial construction state**, not as a post-construction mutation — for PTYs this means folding dims into spawn `options` so there's no SIGWINCH-after-start reflow.
- Place the buffer-clear _after_ the construction definitively succeeds (after the constructor that can throw), never at the top of the handler. Clearing early loses the buffered value on a spawn failure and breaks retry. Clear the buffer in every teardown path (`kill`/`trash`/`gracefulKill`/`dispose`) so it can't leak across an id reuse.
- A "not found, cannot X" warn that fires every spawn is a smell — it usually means a legitimate out-of-order signal is being dropped. Demote it to debug for the pre-create case and keep warn only for the genuine post-teardown case.

## Applies when

- Adding or changing handlers in `electron/services/PtyManager.ts` (`spawn`, `resize`, `kill`, `trash`, `gracefulKill`, `dispose`) or the `pendingResizes` map.
- A terminal or TUI/agent boots at the wrong size, or "Terminal not found, cannot resize" appears in logs on startup/spawn.
- Wiring any main-process service where one IPC channel creates an entity and another mutates it, and the renderer can fire the mutation before the create resolves (resize, write, focus, theme apply on a freshly-spawned PTY).
- Adding initial-state to a node-pty spawn where you're tempted to apply it as a follow-up call instead of as spawn options.
- Reviewing buffer/cache lifetime around an operation that can throw mid-way (orphaned PTY, constructor failure) and needs to survive for a retry.
