## Context

`DeletedWorktreeCard.tsx` renders ghost rows for worktrees that were deleted while their terminals are still alive, with an auto-cleanup sweep that closes them after a configurable TTL (`deletedWorktreeCleanupSeconds`). #11237 (the day before this PR) added a countdown UI to that row: a numeric seconds readout plus a depleting bar along the bottom edge, layered as `<div className="... border-b border-border-default">` with an absolutely positioned `<div className="absolute inset-x-0 bottom-0 z-10 h-[2px]">` child for the bar.

## Problem

Ghost worktree rows drew two stacked horizontal lines at the bottom instead of one — a full-width 1px separator plus, on top of it, a partial-width 2px countdown bar. Most visible right after deleting several worktrees at once, when `remainingFraction` is near 1 and the bar spans nearly the full row width, reading as one thick doubled rule rather than a progress indicator (#11262). It looked like a z-index or layering bug, but no z-index change could fix it — the two elements never occupied the same pixels to begin with.

## Root cause

Per CSS Positioned Layout Level 3, `bottom: 0` on an absolutely positioned element resolves against its containing block's **padding edge**, not the border box. The card had `border-b` (painted at the border-box edge) and zero bottom padding, so the countdown bar's `bottom-0` landed exactly one border-width _above_ that painted border — two boxes, non-overlapping by exactly the border width. That's why stacking, opacity, or z-index tweaks are structurally incapable of fixing it; it's a positioning-model fact, not a paint-order fact. #11265 removes `border-b` from the card root entirely and replaces it with a single always-rendered 1px track (`deleted-worktree-separator`, `bg-border-default`) that IS the bottom edge in every state; the countdown fill renders nested inside that track and drains along the same rule instead of floating a separate bar above it. A `-bottom-px` compensation offset was considered and rejected as brittle: Chromium rounds sub-pixel positioning independently per element at fractional device pixel ratios, so the coincidental alignment would drift.

Fixing it this way traded one bug for a second, subtler one that review caught before merge: a `background-color` on a plain div is stripped under `forced-colors: active` / Windows High Contrast, while a real `border` survives untouched — the same asymmetry `src/index.css`'s forced-colors block already patches elsewhere in the app. The new painted separator would have silently disappeared for HC users, a regression the old `border-b` never had. The fix adds `.deleted-worktree-separator { background-color: CanvasText }` and `.deleted-worktree-countdown-fill { background-color: Highlight }` inside `sidebar.css`'s existing `@media (forced-colors: active)` block, locked by a `forcedColorsStatusIndicators.contract.test.ts` assertion so a future edit can't drop them silently.

## Lesson

- **A border and an absolutely positioned `bottom-0`/`inset-x-0` sibling on the same box will never coincide** — the border paints at the border box, `bottom-0` resolves at the padding edge. A doubled rule/line at an edge shared by a real border and an abs-positioned overlay is a geometry bug, not a z-index or paint-order bug. Fix it structurally: one element owns that edge in every state, not a coordinate nudge.
- **Don't compensate with a negative offset** (`-bottom-px` or similar) to line up a border and an abs-positioned element — Chromium rounds sub-pixel positioning independently per element at fractional DPRs, so an offset that lines up at 1x/2x can drift at 1.25x/1.5x. Merge into one rule instead.
- **Replacing a real `border` with a `background-color` on a plain element is a silent forced-colors regression** — the UA strips `background-color` under `forced-colors: active` / Windows High Contrast but keeps `border`. Any such substitution needs an explicit repaint added to the component's `@media (forced-colors: active)` block (pattern: `src/index.css`, `sidebar.css`) and a lock in `forcedColorsStatusIndicators.contract.test.ts`.
- **This exact shape recurs elsewhere** — `WorktreeCard.tsx:712` gates its own `border-b` on `variant === "sidebar"` (the live-card sibling of this ghost card) and `TabButton.tsx:297` has an unconditional `absolute inset-x-0 bottom-0 h-0.5` active-tab indicator. Neither currently pairs a border with an abs-positioned bottom bar, but adding one to either needs the single-owner-of-the-edge pattern from this fix, not the pre-#11265 layering.
- Structural jsdom tests (`hasBottomBorderUtility` helper, the `bottom-edge ownership` describe block) assert the _arrangement_ — no `border-b` on the card root, exactly one separator element, countdown nested inside it — because jsdom can't measure real paint overlap; that's the right shape for a geometry bug, not a pixel-snapshot.

## Applies when

- Seeing a doubled/offset line, border, or divider at an edge shared by a CSS border and a sibling absolutely-positioned element, especially near `bottom-0`/`top-0`/`inset-x-0` combined with `border-b`/`border-t`.
- Touching `DeletedWorktreeCard.tsx`, `WorktreeCard.tsx`'s sidebar-variant `border-b`, or `TabButton.tsx`'s bottom active-indicator bar — or adding any new progress/countdown/active bar alongside an existing border.
- Replacing a real `border` with a painted `background-color` element for any visual-merge reason — check `src/index.css` and the relevant component CSS's `@media (forced-colors: active)` block and `forcedColorsStatusIndicators.contract.test.ts` before assuming parity.
- Reviewing a "just add z-index" or "just nudge the offset" fix proposal for a stacking/doubling bug — verify first whether the elements are even in the same coordinate space (border box vs. padding box) before accepting a paint-order fix.
- Writing jsdom tests for a bug that's fundamentally about geometry/paint overlap — assert structural arrangement (single owner element, containment) rather than reaching for pixel measurement jsdom can't provide.
