## Context

App theme and terminal `customSchemes` (user-authored color schemes) persist in the electron-store JSON config. The old design stored `customSchemes` as a `JSON.stringify`-d string field _inside_ the already-JSON config object — the renderer called `JSON.stringify(schemes)` before the IPC `set`, the main handler stored the raw string, and read-side `parseCustomSchemes()` did `JSON.parse` + a try/catch.

## Problem

A single escaping mistake anywhere in the double-encoding chain silently dropped the _entire_ `customSchemes` entry with no warning — all the user's custom themes vanished on next load. The read path's `try { JSON.parse } catch { return [] }` swallowed the failure and returned an empty array, so there was no signal that data had been lost vs. legitimately empty (#6057).

## Root cause

Double-encoding (a JSON string nested inside a JSON document) layers two escaping passes. Backslashes/quotes that survive one pass but get mangled by the other produce a string that `JSON.parse` rejects — and the only handling was a silent `catch → []`. There is no reason to stringify before storing in a store that already serializes its values: the inner encoding adds a fragile, invisible failure surface. The permissive try/catch made corruption indistinguishable from emptiness.

## Lesson

- Never store a `JSON.stringify`-d string as a field inside a config object the store already serializes. Store the **native array/object**; let the store do the single encoding pass.
- Split validation by direction: a **permissive read schema** (`appCustomSchemesReadSchema` in `electron/schemas/customSchemes.ts`) accepts BOTH the legacy string (via `z.string().transform` that JSON-parses) AND a native `z.array(z.unknown())` during the migration window; a **strict write schema** (`appCustomSchemesWriteSchema = z.array(appColorSchemeSchema)`) validates fully on write.
- Use `z.unknown()` for array elements on read so one corrupt entry doesn't drop the whole array — validate each element individually with `writeSchema.element.safeParse(...)` in `migrateCustomSchemes()`, collecting per-entry `console.warn` diagnostics instead of silently discarding. Visible warnings replace the silent `catch`.
- **Lazy migration on read**: when the stored value is still a string (or invalid), rewrite it back to the native array via `store.set("appTheme.customSchemes", ...)` so subsequent reads skip the parse. Mark `migrated: true` even when a broken legacy string parsed to `[]`, so the store gets cleaned up instead of re-failing every read. The migration write is wrapped in try/catch and is non-fatal (a parse-but-write-fail still returns the parsed value to the caller).
- Share one migration helper across both consumers (app theme + terminal config) parameterized by read/write schema — don't duplicate the parse logic per handler.

## Applies when

- Persisting user-authored collections (themes, color schemes, recipes, presets, keymaps) to electron-store or any JSON config, and tempted to `JSON.stringify` before storing.
- Adding/changing a field in `electron/store.ts`-backed config read through IPC handlers (`appTheme.ts`, `terminalConfig.ts`) where the renderer client (`src/clients/*Client.ts`) or hooks (`useAppThemeConfig.ts`, `useTerminalConfig.ts`) currently stringify a value.
- Seeing user data "silently vanish" or reset to empty after a load, especially when a read path has a `try { JSON.parse } catch { return [] }` that can't distinguish corruption from emptiness.
- Migrating a persisted field's storage format and needing a backward-compatible read while old configs still exist on disk — use the permissive-read/strict-write Zod split plus lazy migrate-on-read rewrite.
