## Context

`TerminalOutputIngestService` (renderer) receives PTY output chunks over a MessagePort and parses them into the xterm.js instance. Each terminal has a refresh tier (`FOCUSED`/`VISIBLE`/`BACKGROUND` — `TerminalRefreshTier` in `@shared/types/panel`); the pty-host throttles background polling (50ms active / 500ms background via `electron/pty-host/handlers/backpressure.ts`) but does not fully suppress output. `TerminalRendererPolicy` arbitrates wake/restore and tier transitions.

## Problem

Even after a pane is backgrounded, in-flight MessagePort batches keep arriving and get parsed straight into the hidden xterm instance. `xterm.write()` parses ANSI on the renderer main thread, so a pane the user can't see was still burning main-thread CPU (and could land a multi-MB write, related to #4853).

## Root cause

Producer-side throttling reduces but never eliminates output to a backgrounded pane — batches already in transit when the tier flips still land. The renderer had no consumer-side gate, so it parsed them anyway. Three non-obvious races make a naive gate insufficient:

- A drain can be triggered from multiple entry points: `enqueueChunk`/`bufferData`, `notifyWriteComplete` (low-watermark drain), `notifyParsed`, the scheduled ink-erase `setTimeout` drain, and `resumeFlush`. Gating only the enqueue path leaks parses through the ack/parsed callbacks.
- A `BACKGROUND→active` wake (`wakeAndRestore`) is async. If the pane is re-backgrounded before the promise resolves, the resolved callback would `refresh()` and flush into a now-hidden pane.
- A terminal that _starts_ in `BACKGROUND` has no recorded `lastBackendTier`, so `prevBackendTier` defaults to `"active"`; the first promotion isn't seen as a `BACKGROUND→active` transition and the wake/flush path is skipped entirely — held bytes would never drain.

## Lesson

- Gate the consumer, not just the producer. When a pane is backgrounded, push bytes onto the queue but return before parsing into xterm. Add the `isBackgrounded(id)` guard to **every** drain entry point — `notifyWriteComplete`, `notifyParsed`, `resumeFlush`, and the enqueue path — not just one.
- Drain held bytes on wake via a dedicated `resumeFlush(id)` routed through the normal capped path (`tryDrain`, 256KB `COALESCE_BATCH_CAP_BYTES`), never a single `forceDrain` — a backgrounded pane can accumulate megabytes and a one-shot write blocks the main thread.
- Flush **after** `wakeAndRestore` finishes its scrollback replay (it calls `terminal.reset()`); flushing earlier wipes the held bytes.
- Guard async wakes with a monotonic generation counter: `bumpWakeGeneration(id)` on **both** re-background and the start of a new wake, and bail out of the resolved/rejected callbacks if `wakeGeneration.get(id) !== captured`. This prevents a stale wake from refreshing/flushing into a re-hidden pane.
- For terminals that start in `BACKGROUND`, explicitly seed the renderer-policy backend tier (`initializeBackendTier(id, "background")`) so the first promotion registers as a real `BACKGROUND→active` transition and the flush path runs.

## Applies when

- Adding any new write/drain/flush path to `TerminalOutputIngestService` — it must respect the background gate (check `isBackgrounded`).
- Working on `TerminalRendererPolicy` tier transitions, `wakeAndRestore`, `needsWake`, or `wakeGeneration`.
- Investigating renderer main-thread CPU spikes from hidden/backgrounded terminals, or "background panes still consuming CPU" reports.
- Any async wake/restore callback that touches xterm — verify it cannot fire into a pane that was re-backgrounded mid-flight (generation-counter pattern).
- Terminals created directly in `BACKGROUND` tier (restored sessions, off-screen panes) that later get promoted — verify the first activation actually wakes and flushes.
- Reasoning about the pty-host producer gate (`backpressure.ts` tiered polling) being sufficient — it is not; in-flight MessagePort batches still arrive and need a consumer-side gate.
