## Context

Issue #11134 asked for a "type anywhere" rescue: press a plain printable key with nothing useful focused (clicked empty grid background, closed a panel, tabbed away) and route it into an agent's prompt draft instead of losing it to `document.body`. #11147 built this as one global, capture-phase `window` `keydown` listener (`useTypeAnywhere`) backed by pure decision logic in `src/lib/typeAnywhere.ts`, layered on top of the panel focus registry from #11132/#11150 and `terminalInputStore`'s draft state. The same listener also drives an "off-screen focus locator": when a real terminal legitimately owns focus but its pane has scrolled out of the grid viewport, the pane is scrolled back and pulsed instead of anything being rerouted.

## Problem

Before this, a stray keystroke landing on nothing (`document.body`, a detached element) was silently swallowed by the browser default, and users reasonably assumed the app or the agent CLI had eaten the character. A global always-on interceptor is a dangerous shape to add casually: get the gating wrong and it can steal keys from menus, modals, IMEs, or the wrong agent instead of fixing the original silent loss.

## Root cause

There is no bug here — this is a design lesson, and the forces that shaped the implementation are the reusable part.

The core hazard of any "rescue" interceptor is that a _consumed_ keystroke that fails downstream is a worse loss than the one it was meant to prevent. `useTypeAnywhere` sequences `inputStore.setDraftInput(...)` (the durable write) strictly before `e.preventDefault()`/`e.stopPropagation()` — everything after that point (revealing the pane, exiting maximize, focusing the input, polling `requestAnimationFrame` up to `FOCUS_ATTEMPT_FRAMES` times for real DOM focus to land) is best-effort polish. If the reveal or focus settling fails, the character is still safely in the draft; nothing is lost twice.

The second hazard is choosing a target among several candidates. `resolveRescueTarget` refuses outright (returns `null`) whenever there are zero or multiple plausible agent panels and no disambiguating signal — it never falls back to "the first one" or "the most recent." The disambiguator, `terminalInputStore.lastTypedAgentTarget`, is deliberately its own tracked signal, set only from real CodeMirror `input.type` transactions in an agent's hybrid editor — it does _not_ reuse the existing `lastFocusedTerminalByWorktree`, which updates on any panel-kind focus change (including file and browser panels) and would have misidentified the target as "whatever was last looked at" rather than "whatever was last typed into."

Two more gating details are Chromium-specific traps: `document.activeElement` retargets to a shadow host when focus is inside a shadow root, so a focused shadow-DOM input would look inert to a naive check and have its keystroke stolen — `getFocusTarget` reads `e.composedPath()[0]` instead. And AltGr-produced characters (e.g. `@` on a German layout) arrive with _both_ `ctrlKey` and `altKey` set, so a naive "no ctrl, no alt" printable-key test would refuse to rescue ordinary typing for those users — `isRescuableKeystroke` checks `e.getModifierState("AltGraph")` first.

## Lesson

- **Sequence "commit state, then consume the event" — never the reverse — for any global interceptor that can eat user input.** A downstream failure (focus didn't land, pane didn't reveal) should degrade to "state changed, UI hasn't caught up," never to "the keystroke is gone."
- **When a fallback path must pick one target among several plausible candidates, refuse on ambiguity instead of defaulting to one.** A silent wrong guess (typing into the wrong agent) is worse than declining and letting the key fall through untouched.
- **Don't reuse an existing "last focused X" signal as a proxy for "last acted-on X" if the two can diverge.** Track the actual action (`lastTypedAgentTarget`, set only from real input transactions) as its own field rather than assuming focus history is close enough.
- **`document.activeElement` is unreliable across shadow-DOM boundaries** — it reports the shadow host, not the focused node inside it. Any code inspecting "what actually has focus" for a routing or security decision should read `event.composedPath()[0]` instead.
- **A bare `ctrlKey`/`altKey` check is not a correct "no modifiers held" test** — AltGr layouts (common on Windows/Linux) set both for ordinary printable characters; use `getModifierState("AltGraph")` to distinguish real AltGr from a held Ctrl+Alt chord.

## Applies when

- Building or reviewing any global, capture-phase, window-level listener that can consume input (keydown/keyup rescue, shortcut interception, global paste/drop handling).
- Adding a fallback-routing or auto-focus feature that must choose a single destination among multiple live candidates.
- Reading `document.activeElement` in code that may run inside components using shadow DOM (custom elements, some third-party embeds) for a decision more consequential than styling.
- Debugging AltGr / international-keyboard-layout bugs where a "ctrl+alt = modifier chord" heuristic misfires for ordinary characters.
- Touching `src/lib/typeAnywhere.ts`, `src/hooks/useTypeAnywhere.ts`, or `terminalInputStore.lastTypedAgentTarget` / `lastFocusedTerminalByWorktree`.
