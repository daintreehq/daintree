## Context

Theme switching gained a View Transitions API-based circular clip-path animation that expands from the click coordinates. `runThemeReveal` (`src/lib/appThemeViewTransition.ts`) wraps `document.startViewTransition(mutate)`, and the `mutate` callback performs the actual DOM mutation (`injectSchemeToDOM`). Callers live at `ThemeBrowser.tsx` (`handleCommit`) and `AppThemePicker.tsx` (`handleSelect`).

## Problem

`document.startViewTransition(callback)` is asynchronous — the browser waits for the current frame to finish painting before invoking the callback. If the committed theme is read from store state at callback-execution time rather than locked in at gesture time, it can be stale. The theme picker's hover-preview path frequently mutates `previewSchemeId`/the active scheme between the user's click and when the transition actually fires, so a naively closured or late-read scheme would apply the last-previewed theme instead of the committed one.

## Root cause

Two distinct sources of staleness cross the async `startViewTransition` boundary: (1) hover-preview state (`previewSchemeId`) that `injectSchemeToDOM` consults, and (2) the target scheme itself, which must reflect the committed selection rather than whatever the store holds when the callback later runs.

The current pattern neutralizes both at gesture time, before `runThemeReveal` is called, rather than reading the store inside the callback. In `ThemeBrowser.tsx:267-275`: `setPreviewSchemeId(null)` clears the hover-preview source, then `commitSchemeSelection(targetId)` commits, then `resolveAppTheme(targetId, useAppThemeStore.getState().customSchemes)` eagerly resolves the target scheme object, which is captured in the `mutate` closure passed to `runThemeReveal`. `AppThemePicker.tsx` (`handleSelect`) uses the same eager-resolve-then-capture shape (no preview state to clear). `runThemeReveal` itself is store-agnostic — it only invokes the `mutate` callback it was handed. `appThemeStore.ts` keeps `commitSchemeSelection` (selection/recents bookkeeping) separate from `injectSchemeToDOM` (DOM write) precisely so the resolved scheme can be locked in before the async reveal.

## Lesson

When a state mutation is deferred across an async `startViewTransition` (or any rAF/timeout) boundary, lock the committed value in at gesture time. Two equivalent fixes work: read fresh `store.getState()` _inside_ the callback, OR eagerly resolve the target and capture it in the callback closure — the theme path uses the latter (`resolveAppTheme(targetId, getState().customSchemes)` captured in `mutate`). What you must NOT do is leave a value that another path (hover preview) can mutate between gesture and callback in play: neutralize the source of staleness (`setPreviewSchemeId(null)` before the call) and keep the reveal helper store-agnostic. The canonical inline proof lives at `ThemeBrowser.tsx:269` (`// ... could be undone (see PR #5087).`).

## Applies when

- Wrapping state mutations in `document.startViewTransition()`
- Any async animation callback (rAF, setTimeout, requestIdleCallback) that needs to apply a committed value
- Store values that can change between user gesture and its visual application (hover preview patterns)
