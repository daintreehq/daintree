## Context

`PluginInstaller.installPlugin` (`electron/services/plugin/PluginInstaller.ts`, factored out of `PluginService` after the original PR) is the ONLY path that writes to `~/.daintree/plugins/`. It extracts a `.dntr` archive (or copies a sideload dir), validates the manifest, and atomically swaps the result into the final plugin directory, leaving the filesystem in the pre-install state on any failure. The same primitives back uninstall, update-check, and a startup stale-leftover reaper.

## Problem

A directory-tree install that uses the obvious approach — `fs.mkdtemp(os.tmpdir())`, extract, then `fs.rename` into place — breaks atomicity and corrupts state in three non-obvious ways: (1) the rename can fail with `EXDEV` because the OS temp dir is frequently a different filesystem/mount than `~/.daintree`, making the "atomic" final step non-atomic or impossible; (2) a second app instance (multi-window / relaunch) can race the same plugin directory; (3) an upgrade that fails after the old version is torn down leaves the user with a half-installed or missing plugin.

## Root cause

- `mkdtemp` in `os.tmpdir()` can land on a different device than the destination. `rename(2)` is only atomic _within one filesystem_ and returns `EXDEV` across devices. The fix is to `fs.mkdtemp(path.join(this.pluginsRoot, ".install-tmp-"))` — a sibling of the final dir, guaranteed same filesystem, so `rename` is genuinely atomic. `_swapPluginDir` still special-cases `EXDEV` in its error message as a defensive signal.
- Cross-process safety needs `proper-lockfile` (a real production dep here), not an in-process mutex. Two traps: its `lock()` target must exist unless you pass `realpath: false` (it creates `install.lock.lock` adjacent); and `onCompromised` fires from a _timer_, so re-throwing inside it surfaces as an uncaught exception — you must instead set a `lockCompromised` flag and check it at the commit point (just before the irreversible swap), aborting then. A short stale TTL (`stale: 20_000`, `update: 10_000`) lets a crashed prior install's lock be reclaimed instead of held forever.
- The swap is park-old (`rename finalDir → finalDir.old-<uuid>`) → move-new-in (`rename tmpDir → finalDir`) → restore-old on failure. `swap_unrecoverable` is reserved for the _double fault_ (move-in AND restore both fail). Rollback must restore **runtime** state too: `unloadPlugin` already ran the disposer cascade, so on a recoverable `swap_failed` the caller `loadPlugin`+`activatePlugin`s the restored old dir — disk rollback alone leaves the previous version dead this session. The parked `.old-<uuid>` dir is kept until the new version _loads_, so a post-swap load failure can also roll back.
- Staging/parked dirs (`.install-tmp-*`, `.old-*`, `<pluginId>.old-<uuid>`) live inside `pluginsRoot`, so the load scan (`loadFromDir`) must skip dot-prefixed names AND the `<pluginId>.old-<uuid>` suffix (`STALE_PARKED_OLD_RE`) or a crash-leftover staging dir gets scanned as an installable plugin.

## Lesson

When installing/swapping a directory tree on disk:

- `mkdtemp` a **sibling of the destination** (under the same root), never `os.tmpdir()`, so the commit `rename` stays on one filesystem and is atomic. Treat `EXDEV` from the swap as a "wrong temp location" bug, not a transient error.
- Use a cross-process lockfile (`proper-lockfile`) for any directory a second app instance could touch. Pass `realpath: false` if the lock target need not pre-exist, set a finite `stale`/`update` so a crashed holder's lock self-expires, and NEVER throw inside `onCompromised` — flag it and abort at the commit point.
- Make the swap park-old → move-new → restore-old, and reserve an "unrecoverable" state strictly for the double fault. Rollback must reload/reactivate the old version, not just rename it back — tearing down runtime state is part of what you're undoing.
- Use `resilientRename` (`electron/utils/fs.ts`, stubborn-fs retry) for the renames so transient Windows `EPERM`/`EBUSY` lock holds retry instead of failing the swap.
- Any scan of the install root must filter out the installer's own staging/parked naming (dot-prefix + `<id>.old-<uuid>`), or crash leftovers leak in as fake plugins.
- Return structured `{ status: "failed", errors }` data across IPC rather than throwing — thrown Errors don't survive structured-clone with their fields intact.

## Applies when

- Adding install / update / uninstall / rollback flows for plugins or any on-disk artifact under `~/.daintree/` (`PluginInstaller`, `PluginService`, future F22–F26 install surfaces, epic #5651).
- Seeing `EXDEV` / "cross-device link not permitted" from a `rename`, or a rename that silently isn't atomic, or a half-written destination after a failed move.
- Introducing `proper-lockfile` or any cross-process file lock; debugging an uncaught exception traced to a lock's `onCompromised` callback, or a lock that never releases after a crash.
- Multi-window / multi-instance writes to the same directory needing coordination beyond an in-process mutex.
- A directory-scan (`loadFromDir`-style) picking up `.install-tmp-*`, `.old-*`, or `<name>.old-<uuid>` staging dirs as real entries.
- Extracting untrusted zip/`.dntr` archives — see `extractPluginArchive` for the zip-slip (backslash/absolute/`..`) and cumulative-uncompressed-size (zip-bomb) guards in the same PR.
