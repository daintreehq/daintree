## Context

`ProjectViewManager` keeps a per-project `WebContentsView` and attaches 6 persistent `webContents` listeners via `setupViewHandlers` (`will-navigate`, `will-redirect`, `will-attach-webview`, `before-input-event`, `did-finish-load`, `render-process-gone`) plus a `console-message` capture listener via `attachRendererConsoleCapture`. `setupViewHandlers`/`attachRendererConsoleCapture`/`detachRendererConsoleCapture` were later extracted out of `ProjectViewManager.ts` into `electron/window/ProjectViewHandlers.ts` and `electron/window/rendererConsoleCapture.ts` (#11004); `ProjectViewManager` itself now only holds the `ViewEntry.cleanupHandlers` slot. LRU eviction / project teardown calls `cleanupEntry` (now in `electron/window/ProjectViewLifecycleController.ts`), which previously only called `webContents.close()`.

## Problem

`close()` tears down the renderer process but does NOT remove the JS-side listeners registered with `wc.on(...)`. Chromium can dispatch an event that was already queued microseconds before eviction — a `did-finish-load` from an in-flight navigation, or a `render-process-gone` racing the close — AFTER eviction has started. The surviving closure then reads manager state (`this.webContentsToProject`, `this.activeProjectId`, `this.views`) and can call `onViewReady?.(wc)` or run crash-recovery against a view that no longer exists, stealing the PTY MessagePort from the currently visible view or acting on stale `activeProjectId`.

## Root cause

The per-event `wc.isDestroyed()` guard inside the handler is insufficient: the handler closes over manager state, not just `wc`, and post-eviction the view's `webContents` getter can return `undefined` (Electron #50249) so even the guard read is unsafe. Listener identity also wasn't retained — handlers were inline arrow functions, so `removeListener` couldn't target them even if called. Persistent listeners outlive the renderer unless explicitly removed; `close()` is not cleanup.

## Lesson

For any long-lived `webContents` with persistent `wc.on(...)` listeners, store named handler refs and build an idempotent `cleanupHandlers()` closure (one-shot `cleaned` flag) that captures `wc` directly and calls `removeListener` for each, then `detachRendererConsoleCapture(wc)`. Call `cleanupHandlers()` BEFORE `webContents.close()` / `removeChildView` so no queued event can land on a half-evicted entry. Capture `wc` in the closure rather than re-reading `view.webContents` at cleanup time (the getter may be undefined post-eviction). Helpers that attach listeners must export a matching `detach*` that removes by stored handler ref (`WeakMap<WebContents, Handler>`) and clears side state (rate-limit maps) — `attach` alone is a leak. Current shape: `setupViewHandlers` (`electron/window/ProjectViewHandlers.ts:35`) builds the `cleaned`-flag `cleanupHandlers` closure and assigns it to `entry.cleanupHandlers`; `attachRendererConsoleCapture`/`detachRendererConsoleCapture` (`electron/window/rendererConsoleCapture.ts`) hold the `WeakMap<WebContents, Handler>`; `cleanupEntry` (`electron/window/ProjectViewLifecycleController.ts:400`) calls `entry.cleanupHandlers()` before `removeChildView`/`close()`.

## Applies when

Adding or evicting a `WebContentsView`/`webContents` that holds persistent `wc.on` listeners (`ProjectViewManager` and its extracted `ProjectViewHandlers.ts`/`ProjectViewLifecycleController.ts`, portal/browser views), wiring teardown in `cleanupEntry`/`dispose`, or writing an `attachX`/`detachX` listener-capture helper — anywhere a queued navigation/crash event could fire after the view starts being torn down.
