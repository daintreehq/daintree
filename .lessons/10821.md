## Context

`AgentAvailabilityStore` (`electron/services/AgentAvailabilityStore.ts`) is the authoritative in-main-process cache of each agent's FSM state (`working`/`waiting`/`idle`/`completed`/`exited`), fed by `agent:spawned` and `agent:state-changed` events. MCP's `terminal.waitUntilIdle`/`waitUntilIdleBatch` (`electron/services/mcp-server/waitUntilIdle.ts`, `handleWaitUntilIdle`) read this store to let external agent consumers block until a terminal stops working. Issue #10816 reported that a crashed agent CLI (nonzero exit, signal kill, or a launch that never produced a process at all) got permanently reported as `agentState: "waiting"` instead of `exited`, so `terminal.awaitAll` counted the crash as "finished work" and tried to read structured output that never existed.

## Problem

Worst on a fresh relaunch under the same `agentId` after a prior session ended in `waiting`: the new session crashed on startup but the terminal kept reporting `waiting` forever, no exit code. It looked like a missing state transition, pointing at the FSM/output-parsing layer (`shared/utils/agentFsm.ts`) — the real defect was two levels away, in how the availability store handled `agentId` reuse across a respawn.

## Root cause

`handleWaitUntilIdle` subscribes to `events.on("agent:state-changed", ...)` _before_ reading `store.getState(agentId)`, the standard shape for avoiding the missed-event race (subscribe first, then check if the awaited transition already happened). That ordering is correct in isolation. The trap is the implicit assumption "if state isn't `working`, this run is already idle" — `agentStates` is keyed by `agentId`, and the `agent:spawned` handler updated `terminalToAgent`/`agentToTerminal`/`spawnedAt`/exit-metadata on respawn but never touched `agentStates`. A fresh session under a reused `agentId` inherited whatever state (`waiting`) the _previous_ session left behind. `handleWaitUntilIdle` subscribed, read that stale `waiting`, settled as "already-idle," and its `finally`-block `cleanup()` unsubscribed. When the new session's real `agent:state-changed{state:"exited"}` arrived moments later, nothing was listening.

A second, distinct failure mode compounds this for launch-time crashes: a failed-to-start spawn (`ptyManager.spawn` throwing `ENOENT`) never produces a PTY, so no exit event fires and `TerminalProcess` never emits `agent:spawned` either — no wire event exists for the store to react to. The fix in `electron/pty-host/handlers/lifecycle.ts` synthesizes `agent-spawned` then `agent-state(exited, previousState:"working", trigger:"exit")` before `spawn-result`, gated on `msg.options.launchAgentId` (plain shells get nothing synthetic). `AgentAvailabilityStore`'s `agent:spawned` handler now also resets `agentStates.set(agentId, "working")`, clears `waitingReasons`, and stamps `lastStateChange`, so a fresh spawn always reads genuinely busy and the post-subscribe check can't short-circuit on leftovers. On the renderer, `addPanel.ts`'s failed-spawn branch sets `agentState: "exited"` only when `_current.launchAgentId` is set, and `restart.ts` needed a `failedAgentLaunch = wasFailed && currentTerminal.command !== undefined` gate so a demoted shell (agent quit to shell, `command` cleared per #5807) whose restart then fails isn't wrongly re-promoted to an agent (#5764) just because it now also reads `agentState === "exited"`.

## Lesson

- **Subscribe-then-read avoids missed-event races only if "already settled" is trustworthy for the current logical session.** If the store key (`agentId`, `sessionId`) can be reused across respawns/reconnects, an unreset stale value makes the read lie about "already idle" and the pattern drops its own listener right before the real event arrives — invisible from the read site alone.
- **A store keyed by a reusable identity must define what a fresh spawn resets, not just what it clears.** The pre-existing `agent:spawned` handler already cleared `exitCodes`/`exitSignals` on respawn but forgot `agentStates`/`waitingReasons`/`lastStateChange` — clearing exit metadata but not state was itself half a fix that left the trap standing.
- **A failed-to-start process is the absence of any lifecycle event, not just "an exit with a bad code."** When the normal signal (a real PTY exit) can't fire because the process never existed, the layer that knows about the failure (`lifecycle.ts`'s spawn-error branch) must synthesize the downstream wire events consumers expect, gated on the same condition that would have produced them normally (`launchAgentId` set).
- **When patching an `isX` classification, audit every other branch keyed on that same field.** Making failed spawns carry `agentState: "exited"` was correct for MCP visibility, but `restart.ts`'s `isAgent = agentState !== "exited"` used that field to distinguish "agent" from "demoted-to-shell," so the fix needed a second condition (`command !== undefined`) to stop conflating "crashed agent" with "quit-to-shell."
- **Test the batch/plural variant of a wait primitive separately.** `handleWaitUntilIdleBatch`'s `mode: "all"` had the identical already-idle short-circuit and needed its own regression test — fixing the singular path didn't prove the batch path exercised the same fix.

## Applies when

- Writing or reviewing a "wait until state X" helper that subscribes then reads current state to check if it already happened — verify the read can't be satisfied by state left over from a different logical session under the same key.
- Touching `AgentAvailabilityStore`, `agent:spawned`/`agent:state-changed` handling, or `waitUntilIdle`/`waitUntilIdleBatch`.
- Diagnosing an MCP consumer (`terminal.awaitAll`, `waitUntilIdle`) that treats a crashed/hung agent as "finished" with no exit code — check whether the terminal respawned under a reused `agentId` and whether the store reset state on that respawn.
- Adding a failed-to-start/launch-error path in the pty-host spawn flow (`electron/pty-host/handlers/lifecycle.ts`) — check whether consumers rely on wire events a never-started process can't naturally produce.
- Changing what `agentState: "exited"` means on a panel (`addPanel.ts`, `restart.ts`) — re-check every branch reading `agentState !== "exited"` as a proxy for "still an agent" (the demoted-shell gate, #5764/#5807).
