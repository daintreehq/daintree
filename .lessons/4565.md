## Context

Rapid agent state changes (multiple completions within 2 seconds) triggered sound storms: multiple `afplay`/`paplay` subprocesses spawning simultaneously, overlapping audio, and potential resource exhaustion.

## Problem

`SoundService` spawned a subprocess for each `play()` call with no concurrency control. With 10 agents completing simultaneously, 10 subprocesses launched at once.

## Root cause

No dampening layer existed. Each call was fully independent.

## Lesson

Dampening layers on top of **two playback transports** (`SoundService.playDampened`, `electron/services/SoundService.ts`). Each `playDampened` call resolves a single transport based on whether a renderer window exists:

- **Primary — renderer Web Audio:** when `BrowserWindow.getAllWindows().length > 0`, broadcast `CHANNELS.SOUND_TRIGGER` (`"sound:trigger"`) with `{ soundFile, volume }` and **return early** (SoundService.ts:189-195). The renderer fetches via `daintree-file://` and does its own mixing (introduced in #4569).
- **Fallback — OS subprocess:** when no renderer window exists, spawn `afplay`/`paplay`/PowerShell via `playSound` (`electron/utils/soundPlayer.ts`).

The four dampening mechanisms split across these transports:

**1. Debounce (150ms) — both transports:** drop duplicate triggers of the same sound type within `DEBOUNCE_MS`. Key is the base sound name (`opts.debounceKey`), not the variant — prevents bypass via cycling through variants. Runs before the transport split, so it applies to Web Audio and OS fallback alike.

**2. Exponential volume decay — both transports:** `computeVolume` tracks consecutive sounds within a 2s window (`DECAY_WINDOW_MS`), each play at `DECAY_FACTOR` (0.7) of the previous (floor `VOLUME_FLOOR` 0.1), reset after 2s silence. The computed value is sent either as the `volume` field in the `SOUND_TRIGGER` payload (Web Audio path) **or** injected into subprocess args on the OS fallback: `afplay --volume <0.0-1.0>` (macOS), `paplay --volume <0-65536>` (Linux); PowerShell/`aplay` have no volume flag and ignore it (soundPlayer.ts:21,35).

**3. Max 3 concurrent voices with priority eviction — OS fallback ONLY:** `acquireVoiceSlot`/`activeVoices`/`pruneStaleVoices` with `MAX_VOICES = 3` only run after the early return, on the subprocess path. When full, evict the lowest-priority voice (highest number; tie → oldest) for a higher-priority incoming sound; equal/lower priority sounds are dropped, not queued. The Web Audio path returns before any voice-pool logic — the renderer owns mixing. `PRIORITY_MAP`: `error:1 > waiting:2 > chime/complete:3 > ping:4 > pulse:5` (default 4 for unmapped).

**4. Batch completion chording — both transports:** 2+ `complete`/`chime` sounds within 2s (`CHORD_WINDOW_MS`, `checkCompletionChord`) collapse to a single play at full volume (overriding decay) using the canonical base file. Resolved before the transport split.

**Preview/pulse bypass:** `preview`/`previewFile`/`playPulse` route through `playBypassed`, skipping all dampening — users testing a sound expect full volume every time. `playBypassed` still honors the two-transport split (Web Audio first, OS fallback otherwise), but the OS fallback there pushes a voice with `priority: 0` and no slot arbitration.

## Applies when

- Any feature that triggers audio as a side effect of rapid state changes
- Designing dampening that must apply uniformly across multiple playback transports (renderer Web Audio vs OS subprocess) — keep transport-agnostic gates (debounce, decay, chording) ahead of the transport split, and transport-specific limits (the subprocess voice pool) after it
- Implementing subprocess-based audio on macOS/Linux where concurrent process limits matter
- Designing notification or feedback systems where user perception degrades with repetition
