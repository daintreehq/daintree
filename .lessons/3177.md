## Context

Terminal scrollback is persisted to a `.restore` file via a debounced write owned by `SessionSnapshotter` (electron/services/pty/SessionSnapshotter.ts). Killing a terminal — a user closing a tab, closing a project, the idle "Close them" auto-close action, or app quit — tears down the PTY process; the `.restore` file is what a later resume (closed-terminal history, crash recovery) reconstructs the buffer from. (Per-terminal _hibernation_ — background/idle PTYs auto-killed to reclaim memory independent of any explicit close — was pulled in PR #10811; project-level hibernation and the idle auto-close path still route through the same kill machinery below.)

## Problem

Killing a terminal silently discarded scrollback. Users who came back to a closed-then-resumed terminal saw an empty buffer, even though the persistence system "worked" and the `.restore` file path was known.

## Root cause

Two bugs compounded. First, `kill()` cancelled the pending debounce timer (correctly freeing resources), so the most recent output never reached disk. Second, the persist path was guarded by `wasKilled === false` — so even manually persisting after kill was a no-op. The `wasKilled` guard was originally intended to prevent writes after the process exited naturally, but it also blocked the pre-kill flush path. Net result: the last in-memory state was always lost to the debounce/guard interaction.

## Lesson

For any debounced persistence tied to a process lifecycle, add a synchronous flush path that bypasses the `wasKilled`/`dirty` guard and runs BEFORE teardown. Put it inside `kill()` itself — ahead of teardown and before `wasKilled` is set — not in a per-resource loop owned by whatever orchestrator requested the kill (explicit user close, project close, idle auto-close, or the app-quit sweep). Once teardown disposes the writeQueue and aborts the process-tree killer, debounced writes are gone, so this is the genuine last chance:

```ts
// TerminalProcess.kill() — TerminalProcess.ts:1176, BEFORE teardown sets wasKilled
this.sessionSnapshotter.flushSyncOnKill(); // synchronous, persistSessionSnapshotSync, no wasKilled guard
if (!this.teardown(exitReason)) return;
terminal.wasKilled = true;
this.sessionSnapshotter.dispose();
```

`flushSyncOnKill()` (SessionSnapshotter.ts:201) is unconditional w.r.t. the guard — it serializes via `serializeForPersistence()` (banner-aware so a resume→re-kill cycle — reopening a closed terminal from history, or a project hibernate→restore→hibernate round-trip — doesn't bake the prior restore banner in) and calls `persistSessionSnapshotSync()` (terminalSessionPersistence.ts:189).

Cover the timer-never-fired path too. The alive→`dispose()` route — the pty-host process's own teardown sweep disposing any terminal that wasn't already killed via an explicit path — has its own variant `flushSyncOnDispose()` (SessionSnapshotter.ts:238), called from `TerminalProcess.dispose()` (TerminalProcess.ts:1457). Unlike the kill path it _keeps_ the `wasKilled` guard and adds a `dirty` guard — if kill/natural-exit already handled persistence, the guard correctly skips the rewrite.

Guards like `wasKilled` should gate _future_ writes, not the explicit flush-on-shutdown path. Test the sequence explicitly (SessionSnapshotter.test.ts): flush writes snapshot synchronously, then kill sets the guard, then a later debounced/event-driven write is blocked.

## Applies when

Any debounced write tied to a resource that can be killed: terminal scrollback, unsaved editor drafts, pending telemetry events, in-flight log batches. Also applies to the `before-quit` path and to any background suspend/idle-reclaim feature — both are the last chance to get state to disk before the resource is torn down out from under the debounce timer.
