## Context

`TerminalWebGLManager` (`src/services/terminal/TerminalWebGLManager.ts`) owns the WebGL renderer pool for xterm and statically imported `@xterm/addon-webgl` (~244KB raw / 33KB gzip). `useResourceProfile` (`src/hooks/useResourceProfile.ts`) — mounted from `App.tsx` on the eager critical path — needed only the pool-size constant and its setter, which happened to live in the same module as the addon. That single import edge (`App → useResourceProfile → TerminalWebGLManager → WebglAddon`) dragged the entire WebGL addon into the renderer entry chunk (#7452).

## Problem

The 33KB-gzip addon was fetched and parsed during initial renderer boot even though WebGL is only ever needed once a terminal actually opens and asks for a context. The bloat was invisible at the source level: nobody on the eager path referenced `WebglAddon` directly — they referenced a sibling constant in the same file, and the static `import { WebglAddon }` at the top of that file pulled the whole thing into the chunk graph.

## Root cause

A static `import` edge is module-granular, not symbol-granular: importing _any_ export from a module that also statically imports a heavy dependency pulls that dependency into the chunk. The eager consumer only wanted `MAX_CONTEXTS`/`setMaxContexts` (now `getWebglUpperThreshold`/`setWebglThresholds`), but they shared a file with `WebglAddon`, so the bundler had to include the addon. Tree-shaking can't drop a module with a side-effectful top-level `import` of a class that's instantiated elsewhere in the same module. The fix has three coupled parts:

1. **Extract the zero-xterm-import config** into `TerminalWebGLConfig.ts` (plain module-level `let` + getters/setters, no `@xterm/*` import). `useResourceProfile` now imports only from there and never touches the manager — verified by a cross-module test asserting the hook resolves config without loading `TerminalWebGLManager`.
2. **Dynamic-import the addon** via `import("@xterm/addon-webgl")` behind a module-level `WebglAddonClass` cache + `webglAddonLoadPromise`. Crucially, the call site (`ensureContext`/`queueAttach`) stays synchronous: if the class isn't loaded, the request is stored in a `pendingEnsures` Map keyed by terminal id (latest-wins dedupe) and replayed when the import resolves. `release`/`dispose`/`onTerminalDestroyed` delete the pending entry; a hardware-unavailable signal mid-load clears all pending; a load _rejection_ nulls `webglAddonLoadPromise` so a later call retries, while keeping pending so no request is lost.
3. **Isolate the chunk** with a `vendor-xterm-webgl` `manualChunk` (`vite.config.ts` matches `@xterm/addon-webgl` at higher priority than the broader `vendor-xterm` rule) so the lazy fetch is a clean isolated chunk, not mixed back into the eager `vendor-xterm`.

## Lesson

- Heavy optional dependencies (renderers, parsers, codecs) must live in their own module that _nothing on the eager path statically imports_. If a shared constant/setter is the only thing an eager consumer needs, hoist it into a separate zero-dependency config module — co-locating it with the heavy class re-couples the chunk.
- To keep a hot, synchronous call site (here `ensureContext`) callable before a lazy chunk resolves, use a module-level cached class + load-promise plus a **per-key pending queue replayed on resolve**. Get the lifecycle semantics right: release/dispose must discard pending entries; rejection must reset the load-promise (retry) without dropping pending requests; an "abort" signal (hardware unavailable, mode flip) must clear pending wholesale.
- Add a dedicated `manualChunk` rule (ordered by priority above the broad vendor rule) so the lazy dependency forms its own chunk instead of being re-absorbed into a larger eagerly-fetched vendor chunk.
- Guard the regression with a test that asserts the eager module resolves without loading the heavy one (cross-module singleton / import-graph assertion), and a build check that the entry chunk has zero static imports of the lazy chunk — source-level review won't catch a transitive same-module import edge.

## Applies when

- Adding or auditing any `@xterm/*` addon, terminal renderer, or other large optional dependency under `src/services/terminal/` and worrying about renderer boot cost.
- A bundle-size budget regresses (`renderer-bundle-size-baseline.json`, perf-budget CI gate) and the offending chunk grew without an obvious new feature — suspect a transitive static-import edge from an eager hook/component into a module that co-hosts a heavy dep.
- Writing or modifying `vite.config.ts` `manualChunks`, especially when a lazy dependency keeps landing in a larger eager vendor chunk.
- Any case where an eager consumer (mounted from `App.tsx`, a top-level hook, a store listener) needs only a constant or setter that lives in a file alongside a heavy class — extract the constant rather than importing the file.
- Converting a synchronous service API to load its backing implementation lazily while keeping the public method signature synchronous (pending-replay queue pattern with release/dispose/retry semantics).
