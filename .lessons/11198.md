## Context

The file panel already had a Source/Rendered toggle for Markdown; #11191 asked for the same for HTML files, rendered live (own scripts, relative assets resolving) rather than as inert text. #11198 added a dedicated `daintree-html://<token>/<relpath>` protocol scheme (`electron/setup/protocols.ts`), separate from the existing `daintree-file://` used by the Markdown viewer, serving pages through a `sandbox="allow-scripts"` iframe (no `allow-same-origin`, opaque origin) with a per-document CSP scoped to the exact token authority (`buildDaintreeHtmlDocHeaders`).

## Problem

Two failures surfaced around the same feature, one caught before merge and one after. During review of #11198, the token-scoped per-document CSP the handler had just built turned out to be getting silently replaced by the app's own CSP before the browser ever saw it — no error, just a widened effective policy (including `connect-src` back to `daintree-file:`, which the sandboxed doc is supposed to never reach). That was fixed inline pre-merge. Then #11198 itself shipped broken: every rendered HTML preview was a blank white iframe, in both development and production, in #11200. No CSP violation logged, no visible error at all — just nothing.

## Root cause

Both failures are the same shape: generic security machinery built for the trusted app shell, applied unconditionally via `<all_urls>`/session-wide hooks, colliding with a new deliberately _untrusted_ custom-protocol surface nobody had exempted yet.

1. **CSP overlay clobber.** Daintree registers `ses.webRequest.onHeadersReceived({ urls: ["<all_urls>"], types: ["mainFrame", "subFrame", "script"] }, ...)` in both `setupWebviewCSP` and `applyDaintreeAppCspToSession` to force the strict app CSP onto every document/worker response. Non-obvious Electron 42 / Chromium 148 fact: **`protocol.handle` responses flow through `onHeadersReceived` too** — your own custom-scheme handler is not exempt from the webRequest hook meant for network requests. A `daintree-html://` doc loads as a `subFrame` navigation, so `mergeCspHeaders(details, cspPolicy)` ran on it and replaced the just-built token-scoped CSP with the trusted app CSP. Fix in both call sites: an explicit early-return, `if (isDaintreeHtmlPreviewUrl(details.url)) { callback({ responseHeaders: details.responseHeaders }); return; }`, before the merge runs.
2. **COEP frame block.** Caught only after merge, in #11200: the trusted renderer document sets `Cross-Origin-Embedder-Policy: credentialless` on both the packaged `app://` scheme (`electron/utils/appProtocol.ts`) and the dev server (`vite.config.ts:1527`). Per the COEP spec, a document with COEP set can only embed `<iframe>`s whose own navigation response _also_ carries a compatible COEP header; otherwise Chromium blocks the frame with `ERR_BLOCKED_BY_RESPONSE`. `buildDaintreeHtmlDocHeaders` sent none, so despite CSP, sandboxing, and the token scheme all being correct, the iframe never rendered — no CSP violation, nothing renderer-side to grep for. A blank white iframe reads exactly like "the new CSP/token code is broken," pointing at the wrong subsystem; the fix was one unrelated header line. It briefly landed straight to `develop` as `1bfe074da`, got reverted (`e44ac6b21`) to go through a proper PR, and re-landed as #11200.

The regression shipped past review because a covering E2E case (added in the same #11198 diff, `e2e/full/panels/core-file-panel.spec.ts`) would have failed on it immediately — but PR/push CI here runs only typecheck/lint/format/unit/build; E2E runs solely in `stabilize.yml` and the release pipelines. A fully broken feature merged to `develop` and stayed broken until someone ran the suite manually.

## Lesson

- **A session-wide `webRequest.onHeadersReceived({ urls: ["<all_urls>"] })` overlay also fires for your own `protocol.handle` responses** in Electron 42/Chromium 148 — a custom scheme gets no automatic exemption. Any such overlay needs an explicit bypass keyed on the scheme/URL (the `isDaintreeHtmlPreviewUrl` pattern) for documents that ship their own security headers, or the overlay silently wins with zero error signal.
- **A blank/white iframe with no console CSP violation is the signature of a COEP block, not a CSP bug.** If the host document sets `Cross-Origin-Embedder-Policy` (`electron/utils/appProtocol.ts` and `vite.config.ts` both set `credentialless`), every document meant to be framed inside it needs a compatible COEP header on its own response or Chromium silently drops the navigation (`ERR_BLOCKED_BY_RESPONSE`, visible in devtools Network, not Console). Check this before assuming a frame-rendering failure is CSP/sandbox/token related.
- **New sandboxed/frameable content types need both audits, not just one** — CSP scoping and COEP compatibility are independent gates on whether framed content appears at all. #11198 got the CSP half right in review and still shipped fully broken because COEP wasn't checked.
- **A test in the same PR that would have caught the regression is not protection.** PR/push CI here is typecheck/lint/format/unit/build only; E2E is `stabilize.yml` and release-only. For a new sandboxed/cross-origin/security-header-sensitive surface, run the relevant spec locally before merging (`npx playwright test e2e/full/panels/core-file-panel.spec.ts`) per the repo's "Local E2E first" rule.
- **Fix urgent breakage through a PR, not a direct commit to `develop`,** even when the diagnosis is trivial — `1bfe074da` landed straight to `develop` and was reverted (`e44ac6b21`) purely to redo it as #11200.

## Applies when

- Adding a new `protocol.handle` scheme serving sandboxed/untrusted content with its own per-document CSP or security headers distinct from the app shell's.
- Debugging a blank/white `<iframe>`/`<webview>`/subframe where devtools Console shows no CSP violation — check Network for `ERR_BLOCKED_BY_RESPONSE` and check both ends' COEP headers.
- Touching `electron/setup/protocols.ts` (`setupWebviewCSP`, `applyDaintreeAppCspToSession`) or any global CSP/security-header `webRequest.onHeadersReceived` overlay on `<all_urls>`.
- Reviewing a PR adding a new frameable/embeddable document type — verify against the app's existing COEP/CORP posture, not just CSP.
- A PR's only regression coverage is an E2E spec — PR/push CI (`ci-ok`) never runs E2E; nothing catches a runtime-only break until `stabilize.yml` or a manual local run.
