## Context

`AutoUpdaterService.ts` drove automatic update checks (initial, periodic, retry, resume) through `autoUpdater.checkForUpdatesAndNotify()`, while `src/hooks/useUpdateListener.tsx` renders its own in-app "Update ready" toast off the same `update-downloaded` event. Each project in Daintree gets its own `WebContentsView` under LRU eviction (`ProjectViewManager`), so a project's renderer can be destroyed and rebuilt, or a second window opened, long after any given update event fired. #11141 (companion to #11129, same arc, issue #11111) fixed both.

## Problem

Two independent, easy-to-miss symptoms. Users occasionally got told about a downloaded update twice — the in-app toast plus a native OS notification — but only on signed, notarized release builds, so it was completely invisible in dev, which is presumably why it shipped. Separately, a project view rebuilt after LRU eviction, or a new window opened after an update was already staged, showed no install UI at all: the restart-to-update toast simply never appeared for that view even though the download was ready.

## Root cause

`checkForUpdatesAndNotify()` is `checkForUpdates()` plus an un-awaited `.then()` that fires electron-updater's own native OS notification on `update-downloaded` — the exact event `useUpdateListener` already toasts from. There is no flag to suppress only the native half (`formatDownloadNotification` only rewrites its text), so the fix is to call plain `checkForUpdates()` from every automatic path, matching what `checkForUpdatesManually` already did. It shipped unnoticed because Electron 42 silently fails (never throws) native notifications when the app isn't code-signed, so every dev build behaved as if the bug didn't exist.

The second bug is a broadcast/replay mismatch. `UPDATE_AVAILABLE` / `UPDATE_DOWNLOADED` are one-shot IPC broadcasts from main; nothing re-sends them, so any renderer that didn't exist at broadcast time has no way to learn an update is staged. The fix adds a pull path: `AutoUpdaterService.getLatestUpdate()` returns a replayable snapshot behind a new `update:get-latest` channel, mirroring the `store-update:get-latest` pattern `WindowsStoreNotifierService` already used for the same problem. `useUpdateListener` subscribes to the live events _before_ calling `getLatest()`; a `liveStateSeen`/`disposed` guard drops the pull's response once a live event has already won or the component has unmounted, otherwise a slow-resolving snapshot landing after `update-downloaded` already fired would clobber the live toast and strip its restart action. Suppression also became a reason (`"session-dedup"` vs `"dismiss-cooldown"`) rather than a boolean, checked dismissal-first, because a plain flag can't tell "not yet delivered to this viewer" apart from "user explicitly dismissed."

## Lesson

- **A `checkX()` + `checkXAndNotify()` pair from a third-party lib is a double-notification trap the moment your app renders its own UI for the same event.** Grep for an in-app toast/banner on the same underlying event before wiring the `AndNotify` variant into a new call site — there is often no flag to suppress just the native half.
- **A notification bug is invisible in dev if it depends on the native OS path.** Electron 42 silently no-ops unsigned notifications, so this class of bug reproduces only on a signed, notarized build; a clean dev-build pass proves nothing for anything routed through `Notification` or `checkForUpdatesAndNotify`.
- **Any one-shot main→renderer broadcast needs a pull-on-mount replay snapshot**, because per-project `WebContentsView` + LRU eviction guarantees renderers will mount after the fact. `getLatestUpdate()` / `update:get-latest` is the second instance of this pattern (`WindowsStoreNotifierService`'s `store-update:get-latest` was the first) — reach for it by default rather than assuming "the renderer was listening" holds.
- **Subscribe to live events before pulling the replay snapshot, and guard the pull's resolution against a live event already having won** (`liveStateSeen` in `useUpdateListener`) — a slow snapshot resolving after the real event fired must not clobber state the live listener already set, or the fix reintroduces a narrower version of the race it closes.
- **Register a replay-snapshot IPC handler eagerly, not inside the owning service's deferred `initialize()`.** The deferred-init queue drains on the renderer's own first-interactive signal, so a handler registered there would reject the very pull it exists to answer, since the renderer has already mounted and tried by then; `update:get-latest` is wired in `globalServicesInit` instead, reading through a service ref so the heavy `electron-updater` import stays deferred.

## Applies when

- Calling any `electron-updater` `checkForUpdates*` variant, or any third-party "and notify" convenience method, alongside custom in-app notification UI.
- Testing native-OS-notification-adjacent behavior on an unsigned/dev build and concluding it's fine — verify on a signed build for anything gated on `Notification` actually firing.
- Adding a new one-shot main→renderer broadcast in a codebase where views are LRU-evicted per project — pair it with a pull-on-mount snapshot from the start.
- Touching `src/hooks/useUpdateListener.tsx`, `AutoUpdaterService.getLatestUpdate()`, or deciding whether a handler belongs in `globalServicesInit.ts` versus a service's own deferred `initialize()`.
