## Context

Terminal panes route DOM keydown through `attachCustomKeyEventHandler` in `XtermAdapter.tsx` (the `customKeyEventHandler` installed at `managed.terminal.attachCustomKeyEventHandler(...)`, ~line 256). Returning `true` lets xterm process the key and emit its PTY sequence; returning `false` lets the event bubble to the renderer/DOM. Electron's application menu registers single-key accelerators in `electron/menu.ts` — notably `Toggle Full Screen` bound to `F11` on Linux/Windows (`process.platform === "darwin" ? "Ctrl+Cmd+F" : "F11"`).

## Problem

With a TUI focused, bare `F11` toggled Electron fullscreen on Linux/Windows instead of reaching the PTY as `\x1b[23~`. Same earlier symptom with `Tab`: it triggered Chromium native focus traversal instead of emitting `HT` (#9082, fixed by #9083). macOS was unaffected because its fullscreen accelerator is `Ctrl+Cmd+F`, not a bare function key.

## Root cause

xterm v6 changed screen-reader-mode behavior: it accepts and emits a key's PTY sequence but **no longer calls `preventDefault()`/`stopPropagation()` on keys it handles** in that mode. The DOM event therefore keeps propagating after xterm consumed it, bubbling up to Electron's menu accelerator (and to Chromium's native focus handling for Tab). The bug is NOT in the keybinding layer or the menu registration — both are correct; it's that returning `true` from the custom handler tells xterm to handle the key but does not, under screen-reader mode, suppress the native default. The renderer never cancels the DOM path, so a global accelerator wins the race.

## Lesson

For any single-key accelerator that Electron's menu binds AND a TUI legitimately consumes, add an explicit guard in `XtermAdapter`'s `customKeyEventHandler` that calls `event.preventDefault()` + `event.stopPropagation()` and returns `true` (so xterm still emits the sequence). Do not rely on xterm to cancel the DOM default — screen-reader mode won't.

- Match the key with a **triple-check**: `event.key === "F11" || event.code === "F11" || event.keyCode === 122`. Some input methods report `key === "Unidentified"` while `code`/`keyCode` stay intact, and xterm itself dispatches via `keyCode` — the guard must too or it desyncs from xterm's own emission.
- Gate on **bare** key only: require `!ctrlKey && !altKey && !metaKey && !shiftKey` so modified combos (`Ctrl+F11`, `Shift+F11`) still fall through to Electron/global shortcuts.
- This is a recurring class, not a one-off: the `Tab`/`Shift+Tab` guard (#9083, ~line 283) and this `F11` guard (~line 298) are the same pattern. Auditing `electron/menu.ts` for other bare-key accelerators (function keys, etc.) is the right way to find the next instance.

## Applies when

- A keystroke that works inside a normal text field is "stolen" by an Electron menu accelerator or Chromium native behavior only when a terminal/TUI is focused (fullscreen toggle, reload, zoom, focus traversal).
- The symptom is platform-split: Linux/Windows broken, macOS fine (because the macOS accelerator uses a different modifier combo).
- Working in `XtermAdapter.tsx` `customKeyEventHandler`, adding/reviewing key-passthrough guards, or after an `@xterm/xterm` major upgrade (v6+) where screen-reader/accessibility-mode keyboard handling changed.
- Adding a new single-key accelerator to `electron/menu.ts` — check whether any TUI binds it and whether a renderer guard is needed.
- A key reaches the PTY correctly via xterm but ALSO fires an unwanted DOM/menu side effect (the tell that xterm handled it without canceling the default).
