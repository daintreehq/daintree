## Context

`AuditService.getSignals()` (`electron/services/mcp-server/auditLog.ts`) computes four MCP anomaly kinds over the dispatch ring buffer: `latency-drift`, `failure-cluster`, `p95-z-score` (stateless recomputations) and `first-seen-combination` (the one stateful kind). Reading a first-seen signal is an _acknowledgment_: the `toolId+tier` combo is added to the persistent `knownCombinations` set so it fires exactly once, then stays quiet. Until #10282 the only reader was Settings → MCP Server → Audit Log, via `getAuditStats()`. #10282 (resolving #10022) adds a Tier 1 ambient surface — a warning pip on `ToolbarAssistantButton` plus a `McpAnomalyFooterLink` in `HelpPanel` (the footer link was later deleted as redundant by `6a4b4d8f4`, "declutter assistant footer status row," once the pip alone covered the signal — the pip and the `markSeen` plumbing below are still current) — fed by a 30s background poll (`useMcpAnomalyStats`) that distills stats into `mcpAnomalyStore`.

## Problem

The new ambient pip points the user _toward_ the Settings audit log when an anomaly fires — but its 30s poll wanted the same `getAuditStats()` read the Settings page uses, and that read acknowledges first-seen combos as a side effect. A naive implementation has the background poll consume the transient `first-seen-combination` signal on its own cadence, marking the combo seen before the user ever follows the pip. The observer destroys the very state it surfaces: by the time the user clicks through, the log is quiet. It is an observer-effect trap, not a crash — nothing errors; the signal silently vanishes from the user-facing surface.

## Root cause

The mechanism is a read API whose read mutates acknowledgment state. `getSignals()` iterated records and called `this.knownCombinations.add(key)` inline for each new combo, so _reading_ signals was also _consuming_ them, and any second caller sharing the API inherits the consumption. The fix threads a `markSeen` parameter (default `true`, preserving old behavior for every existing caller) end-to-end: `getSignals(markSeen)` → `getAuditStats(markSeen)` → `McpServerService.getAuditStats(markSeen)` → the IPC handler `getAuditStats(markSeen?)` → regenerated `generated.ts` (`args: [markSeen?: boolean]`) → the renderer poll calls `getAuditStats(false)`. Only the background poll opts out of acknowledgment; the Settings/Assistant tabs keep the default and still "fire once".

Two non-obvious subtleties fall out (both captured in the Lesson): the inline `knownCombinations.add` had doubled as a _within-call_ dedup that a passive read now breaks (fixed with a call-local `emittedThisCall` set), and the one-time baseline seed (`firstCall = this.knownCombinations.size === 0`) must still persist even on a passive read or every pre-existing combo false-positives as first-seen.

## Lesson

- **Before adding a background poller/subscription over an existing read API, check whether that read mutates "seen"/acknowledged state as a side effect.** If it does (here `getSignals` → `knownCombinations`), the poller's cadence silently consumes transient one-shot signals before the user's own surface reads them. The fix is an explicit passive-read flag, not moving the consumer.
- **Default the passive flag to the OLD behavior (`markSeen = true`) and opt only the new caller into `false`.** This keeps every existing caller and the IPC arg shape (`args: [markSeen?: boolean]`) backward-compatible. Thread it through the whole stack — service method, `McpServerService` facade, IPC handler, regenerated `generated.ts`, renderer call — a flag that stops at any layer leaks the side effect.
- **Making a side-effecting mutation optional breaks any dedup/idempotency that relied on it, and "passive" rarely means zero side effects.** `getSignals` used `knownCombinations.add` as its within-call dedup; once passive reads skip the persist, add a call-local set (`emittedThisCall`) so each combo emits once per read. Separately, the one-time baseline seed (`firstCall = knownCombinations.size === 0`) MUST still persist on a passive read, or every historical combo false-positives as first-seen on the first poll — `markSeen` gates per-combo acknowledgment only, so isolate flag-governed state from always-persist state.
- **Route diagnostic/background signals through the lowest tier and never `notify()`** — the ambient pip coexists with the user-facing "fire once" acknowledgment precisely because the poll no longer shares seen-state consumption. `mcpAnomalyStore.setFromStats` re-applies the Settings viewer's suppression rule (`!anomalySuppressed && anomalySignals.length > 0`) so both surfaces agree.

## Applies when

- Adding a background poll/subscription (like `useMcpAnomalyStats`) over an existing `get*` read that a user-facing view already consumes — especially one returning transient, one-shot, or "fires once" signals.
- Touching `electron/services/mcp-server/auditLog.ts` (`getSignals`/`getAuditStats`, `knownCombinations`, the `first-seen-combination` kind) or extending the `markSeen` plumbing through `McpServerService`/the IPC handler.
- Reviewing any read API that mutates acknowledged/"seen"/consumed state, or making a previously-unconditional mutation conditional — confirm every caller that must NOT acknowledge passes a passive flag threaded to the mutating layer, and audit whatever dedup/one-time-seed behavior depended on the mutation running every time.
- Diagnosing "the ambient indicator/badge/pip never showed even though the underlying signal fired" — suspect a poller or a second reader consuming the signal before the user's surface gets to it.
