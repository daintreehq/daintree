## Context

The forge-neutral refactor (#10347) moved the GitHub panel's connection gate from the legacy `secureStorage.get("userConfig.githubToken")` key to a provider-keyed `forgeCredentials` store entry (`store.get("forgeCredentials")[providerId]`), so any forge plugin (GitHub, GitLab, etc.) could report connection status uniformly through `forge.getCredentialStatus()` in `electron/ipc/handlers/forgeSettings.ts`. #11036 (resolving #11033) is the follow-up fix for what that cutover left behind.

## Problem

Users who saved a GitHub token before #10347 saw correct issue/PR counts in the toolbar pills but every GitHub panel showed "GitHub not connected" and prompted them to add a token they already had. The counts working was the misleading part — it made the integration look functional while the panel gate insisted it wasn't, which reads like a UI bug rather than a storage-migration gap.

## Root cause

#10347 changed the connection _gate_ (`getCredentialStatus`) to read `forgeCredentials`, but the token save/read path used everywhere else (`GitHubAuth.getToken()`, the toolbar count fetcher) stayed on the legacy `userConfig.githubToken` key. Existing tokens were never copied forward, so the two paths diverged: the legacy key held the real token and authenticated fine, while `forgeCredentials` was empty and the new gate correctly reported `hasCredential: false` from its own valid point of view. Neither path was "wrong" in isolation — the cutover was just incomplete, leaving two sources of truth instead of retiring the old one.

The fix could not be a read-time fallback (e.g. patching `getCredentialStatus` to also check the legacy key) because `forgeCredentials` isn't only a UI flag: `PluginHostFactory.registerForgeProvider` replays it into freshly bound provider implementations via `impl.setCredentials?.(storedCredentials)`, and utility-process hosts like `workspace-host` can't reach `secureStorage` at all. A read-time patch would fix the panel's empty state but leave that replay path empty, so the underlying plugin implementation would still be uncredentialed. The real fix had to _persist_ the token into the new store's shape via a one-time boot migration (`migration024`, `LATEST_SCHEMA_VERSION` bumped 23→24).

The migration also had to delete the legacy key, not just copy from it — `forge:clear-credential` (channel `FORGE_CLEAR_CREDENTIAL`) only ever deleted the `forgeCredentials` entry, never the legacy key. Left in place, a user who backfilled a token and clicked "Clear token" would have it silently resurrect on next boot via the plugin's `initializeTokenStorage()` reading the still-present legacy value. This is the general shape of a partial cutover: write path, read path, and delete path can each be migrated on a different schedule, and any one left behind reintroduces the old state.

## Lesson

- **When a storage cutover only moves the read gate, treat it as unfinished, not fixed** — grep every write site and every delete/clear site for the OLD key, not just the primary read site; #11036 found the toolbar-count read, the panel gate, and the clear-credential delete all disagreeing on which key was truth.
- **Never bridge a store migration with a read-time fallback if the new store is replayed into live objects** — `PluginHostFactory` calls `setCredentials()` from `forgeCredentials`, and utility-process hosts (`workspace-host`) can't reach `secureStorage` at all, so a fallback in one read site would leave those consumers permanently uncredentialed; persist into the new shape instead.
- **Guard the destination, not the source, when backfilling** — `migration024` only writes `forgeCredentials[providerId]` if `recordHasCredential()` says that slot is currently empty/blank, so a token saved post-cutover always wins over a stale legacy copy, and a replay after a partial migration failure can't clobber newer data.
- **Deleting the old key is not optional cleanup, it's required correctness** — if any code path can still write into a "cleared" new-store entry from the surviving legacy key (here, `initializeTokenStorage()` on next boot), the old key must be deleted in the same migration that backfills it, even when the destination is already populated (dead legacy data with no reader is still a liability).
- **A migration should duplicate the read-side logic it depends on rather than import it** — `migration024` reimplements a local `recordHasCredential()` instead of importing from `forgeSettings.ts`: a migration is a snapshot of the schema as it was and must not drift if the live reader's logic changes later, and importing the handler module would drag the IPC registry into the boot path.
- **Fix corrupt sibling data by repairing and warning, not throwing** — a non-object `forgeCredentials` or non-string legacy token is logged and replaced/dropped in place (matching `migration023`'s precedent); throwing mid-migration trips `MigrationRunner`'s restore-from-backup for the _entire_ chain, not just this step.

## Applies when

- Adding or auditing a provider-keyed credential/config store cutover (forge, agent config, MCP tokens) where an old flat key predates a new namespaced one.
- Diagnosing "the feature clearly works (counts/fetches succeed) but the UI says disconnected/not configured" — that split is the signature of two storage reads disagreeing, not a broken integration.
- Writing a boot-time `electron-store` migration (`electron/services/migrations/`) that backfills one key into another — check whether a corresponding clear/delete path also needs updating to prevent resurrection.
- Reviewing any migration that copies data forward — verify it guards the destination (skip if already populated) rather than unconditionally overwriting, and verify it deletes the source so stale data can't come back.
- Touching `electron/ipc/handlers/forgeSettings.ts`, `PluginHostFactory.ts` credential replay, or any `forgeCredentials`/`secureStorage` read site.
