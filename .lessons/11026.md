## Context

`TerminalOutputIngestService` holds non-participant background terminals' output on a 24ms recheck timer (`BACKGROUND_HOLD_RECHECK_MS`, capped at 250ms via `BACKGROUND_HOLD_MAX_MS`) during a live interaction, keeping parse work off the main thread mid-gesture — the same "focused feel beats background throughput" contract used for keystroke-echo protection. `TerminalBurstController` was the source of truth for "is a wheel gesture live, and on which terminal." #11026 added an opt-in Playwright benchmark (`e2e/full/terminal/scroll-perf.spec.ts`, PERF-125..127) measuring wheel-notch-to-paint latency for full-screen mouse-reporting TUIs (grok CLI, opencode, lazygit); its headline cell, `scroll-concurrent` (6 such apps scrolling at once), immediately found a real bug in that hold path.

## Problem

Scrolling one full-screen TUI was fine. Scrolling several at once (split panes, fleet review) made every one of them stutter: paced-notch p95 was 104ms (worst run 145ms), p99 was 161ms (worst 244ms), and a momentum-flick gesture left a ~343ms dead settle after the user stopped scrolling — the wheel analogue of "scrolling one TUI locks up everything." `scroll-solo`/`scroll-heavy-solo` (one TUI) and `scroll-fleet` (one TUI plus 12 background terminals) were all clean, so the bug was invisible to any test that didn't wheel-scroll more than one terminal at once.

## Root cause

`TerminalBurstController` tracked wheel-gesture liveness in exactly one slot, `lastActiveWheelId: string | null` plus a timestamp, and `getActiveWheelHoldId()` returned that one id (or null past `WHEEL_BURST_DECAY_MS` = 1000ms). `shouldHoldDrain` held every terminal whose id didn't match that single exempt id — correct for exactly one live gesture (the wheeled terminal's own redraws must drain inline, since deferring them stalls the PTY round-trip the user is driving) but wrong for two: each new `onActiveWheel(id)` call overwrote `lastActiveWheelId`, evicting the other terminal from the exemption. From each terminal's perspective it was now "background" relative to whichever pane last received a wheel event, so both got put on the 24ms hold — the very panes the hold exists to protect, holding each other. A momentum-flick coast lost its exemption the instant any _other_ terminal received a wheel event, producing the ~343ms settle. The mechanism was a single-active-consumer scheme applied to something not single-consumer — nothing in the wheel pipeline constrains gestures to one terminal at a time.

The fix replaced the scalar with `activeWheelAt = new Map<string, number>()`, splitting the query in two: `hasActiveWheelGesture()` (is _any_ gesture live — gates whether the hold regime applies) and `isWheelActive(id)` (is _this_ terminal a participant — gates its own exemption). `TerminalOutputIngestService`'s constructor mirrors that split as `hasInteractionHold`/`isInteractionParticipant`, folding in the pre-existing echo-pending hold so echo and wheel-scroll share one participant notion; `TerminalInstanceService` wires `hasActiveWheelGesture() || echoPending !== null` and `isWheelActive(id) || echoPending === id`. Post-fix, `scroll-concurrent` p99 fell from 161ms (worst 244) to 64ms and flick settle from 343ms to 67ms — at the solo floor, with solo/heavy-solo/fleet unchanged.

## Lesson

- **A "which one is active" single-slot tracker is a bug waiting for a concurrency test, not just a data-structure choice.** If the tracked interaction isn't inherently exclusive across instances, model it as a keyed collection from the start, not a scalar id + timestamp — ask "can two of these happen at once?" before writing `lastXId`.
- **Split "is the hold regime active at all" from "am I exempt from it."** `hasActiveWheelGesture()` vs `isWheelActive(id)` is the general shape for any gate that both decides whether to suppress a background class AND decides which members are exempt; conflating them into one query (the old `getActiveWheelHoldId(): string | null`) is what let the exemption collapse to size 1.
- **A protection mechanism that starts holding its own protected targets is the tell.** Stutter that gets WORSE as more of the "protected" thing happens concurrently is the signature of a single-active exemption self-defeating — the same shape as #10948's foreground-exemption trim inverting under load, here on the ingest hold path instead of the pty-host reclaim path.
- **Benchmark cells need a same-kind-concurrency case, not just kind-plus-background-load.** `scroll-fleet` (1 TUI + 12 background terminals) passed clean and would have shipped this; only `scroll-concurrent` (6 TUIs wheel-active simultaneously) caught it. A benchmark for a per-terminal interaction needs an N-simultaneous-instances cell even when a background-load cell already exists.
- **Anchor an async-round-trip probe to the observed event, not the input event.** The bystander echo probe desynced because a keyboard Enter's carriage return reaches the PTY without surfacing on xterm's `onData`; the fix snapshots expected text on the `onData` callback and resets state via `window.electron.terminal.write` instead of a simulated Enter.

## Applies when

- Touching `TerminalBurstController`, `TerminalOutputIngestService.shouldHoldDrain`/`shouldDeferDrain`, or `TerminalInstanceService`'s drain-priority wiring.
- Adding or reviewing any "track the currently-active X" field (`lastActiveWheelId`-shaped) that gates a hold/defer/suppress decision for other instances — check whether X can be plural at runtime.
- Diagnosing scroll stutter, redraw stalls, or "worse with more panes active" symptoms in mouse-reporting full-screen TUIs (grok, opencode, lazygit) in Daintree's terminal grid.
- Writing a Playwright perf benchmark for a per-terminal interaction (`e2e/full/terminal/`) — confirm the cell matrix covers concurrent instances of the SAME interaction, not just one instance plus unrelated background load.
