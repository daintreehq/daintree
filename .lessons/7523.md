## Context

When a renderer hits OOM, the main process destroys the old `BrowserWindow` and recreates it. Two paths do this: `setupBrowserWindow()` in `electron/window/createWindow.ts` and `ProjectViewManager` in `electron/window/ProjectViewManager.ts`. Both run inside a `setImmediate(() => { win.destroy(); onRecreateWindow()... })`. Separately, `appLifecycle.ts` registers `app.on("window-all-closed", ...)` which calls `app.quit()` on non-darwin platforms.

## Problem

The nightly memory-leak E2E test failed intermittently: the Electron process exited before the heap assertion ran. During an OOM recreate, the app called `app.quit()` mid-test — the replacement window never got a chance to register.

## Root cause

`BrowserWindow.destroy()` emits `window-all-closed` **synchronously**, inside the `destroy()` call itself — not on a later tick. In the recreate sequence `win.destroy(); onRecreateWindow()`, the destroy fires `window-all-closed` _before_ the (async) recreation has created the replacement window. At that instant the window count is zero, so the non-darwin handler runs `app.quit()` and the process exits mid-recreate. A naive boolean in-flight flag is also insufficient: in a multi-window session two windows can OOM concurrently, and the first recreation's `.finally()` would clear the flag while the second is still in flight.

## Lesson

- Treat `BrowserWindow.destroy()` as synchronously emitting `window-all-closed`. Any "destroy old, then async-create new" sequence must suppress the quit path across the gap.
- Use a **counter**, not a boolean, for the in-flight guard (`windowRecreationState.ts`: `beginWindowRecreating` / `endWindowRecreating` / `isWindowRecreating`). Increment _before_ `destroy()`, decrement in a `.finally()` after the recreation promise settles. Clamp the counter at zero so a stray double-decrement can't wedge it permanently false.
- The `window-all-closed` handler early-returns `if (isWindowRecreating()) return;` before its `app.quit()`.
- Critically, the suppression must be _replayed_ on genuine failure: in the recreate `.finally()`, if the recreation rejected and `!isWindowRecreating() && process.platform !== "darwin" && BrowserWindow.getAllWindows().length === 0`, call `app.quit()` yourself — otherwise the process hangs headless with no windows and no quit path.

## Applies when

- Adding or modifying any OOM / renderer-crash window recreation path in `electron/window/createWindow.ts` or `electron/window/ProjectViewManager.ts`.
- Touching the `window-all-closed` handler in `electron/lifecycle/appLifecycle.ts` or the quit/shutdown lifecycle generally.
- Any code that calls `BrowserWindow.destroy()` and then asynchronously creates a replacement (window swap, theme/profile reload, view recycling), especially in the multi-window / per-project `WebContentsView` architecture where concurrent recreations are possible.
- Debugging an Electron process that exits unexpectedly mid-operation, or hangs headless after a window recreation fails — particularly flaky exits in the nightly memory-leak E2E suite.
- Reviewing any boolean "in-flight" flag guarding a window/app lifecycle event where concurrent operations could overlap (use a counter instead).
