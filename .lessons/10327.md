## Context

`AppLayout` remounts fresh on every project switch — each project owns its own `WebContentsView` + V8 context (`ProjectViewManager`). `sidebarWidth` boots at `DEFAULT_SIDEBAR_WIDTH` (350px); the persisted value is applied ~50-100ms later by the `restoreState()` effect (`await appClient.getState()`). The sidebar wrapper carried its `transition-[width] duration-250 ease-out-expo` class from first paint.

## Problem

On every quick project switch the worktree sidebar popped to 350px then animated to its persisted width (e.g. 280px) — a jarring resize the user never triggered (#10321). The drag-resize path already suppressed the transition (`!isSidebarResizing`, #7627), so this looked isolated, but the initial-restore path had no equivalent guard.

## Root cause

Two facts combine. (1) The width is restored **after** mount by an async IPC round-trip, so `setSidebarWidth(clampedWidth)` fires ~50-100ms into the component's life. (2) The `transition-[width]` class is live from first paint. A state-driven width change under a live transition **is** an animation — the class can't tell hydration from a user action.

The fix (#10327) adds `const [isSidebarWidthHydrating, setIsSidebarWidthHydrating] = useState(true)`, gates the class on `!isSidebarWidthHydrating`, and clears the flag inside `restoreState`'s post-`await` block. The subtle part: the clear runs in the **same synchronous continuation** as `setSidebarWidth`, so React 19 batches both into one commit — the restored width arrives with the class already gone, no animation, **no `flushSync`**. Contrast the drag-start path, which _does_ `flushSync(() => setIsSidebarResizing(true))` because it races the browser's first `mousemove` frame; the post-await clear has no such race.

Two secondary traps the fix had to patch, both from suppressing a transition rather than a state value:

- **`transitionend` never fires while the transition is suppressed.** The `sidebarFullyHidden` clip-margin state machine (#9864) advances on the wrapper's width `transitionend`; during hydration no width transition runs, so `sidebarFullyHidden` strands at `false` and a 6px `overflowClipMargin` strip bleeds at the sidebar's left edge. `isSidebarWidthHydrating` had to be OR'd into that synchronous flush guard so a hide during hydration flushes directly.
- **The flag must clear unconditionally** — in the width-is-null branch AND in the `catch`, not just after a successful non-null restore. A boot-time suppression flag that clears only on the happy path becomes _permanent_ suppression: a session with no persisted width, or a failed `getState()`, leaves it true forever and every later user resize silently stops animating.

## Lesson

- **Any layout value hydrated by async IPC after mount replays as an animation if its CSS transition is live from first paint.** The fix is a `useState(true)` hydrating flag gating the transition class off until the restore lands — not reordering the restore. Suspect this whenever a width/height/offset/transform is `useState(DEFAULT)` then overwritten by an awaited `getState()` or store hydration.
- **Clear the suppression flag in the SAME synchronous post-`await` block as the value setter, and do NOT `flushSync` it.** React 19 batches the two setState calls into one commit, so the value arrives class-free in one paint. `flushSync` is only correct when class removal races a browser input frame (the #7627 drag-start path); in a post-await continuation it is a bug.
- **Suppressing a transition breaks every state machine that waits on its `transitionend`.** When you add a transition-suppression flag, audit every `onTransitionEnd` handler that advances state (here #9864's `sidebarFullyHidden` clip-margin guard) and OR the same flag into its synchronous-flush fallback — otherwise it strands, the transition-end effect never delivered.
- **A boot-time suppression flag must clear on every restore outcome — null value, empty state, and `catch`.** Clearing only after a successful non-null restore turns a temporary hydration guard into permanent suppression of all later user-driven animation. Prove the clear runs on the failure and no-op paths.
- **Once introduced, this hydration flag becomes load-bearing beyond its origin.** #10827 reused `isSidebarWidthHydrating` to release a grid-measurement lock (`unlockSidebarHydration`, `src/lib/layoutTransitionLock.ts`) so grid/pane subscribers measure against the restored `<main>` width, not 350px — backed by a `SIDEBAR_HYDRATION_UNLOCK_FALLBACK_MS = 5000` timeout, since a hung IPC would otherwise strand the flag true and the grid would never measure. Don't remove or short-circuit it without checking its consumers.

## Applies when

- Touching `src/components/Layout/AppLayout.tsx` sidebar width restore (`restoreState`, `isSidebarWidthHydrating`, `sidebarFullyHidden`, the `transition-[width]` gate) or the grid lock in `src/lib/layoutTransitionLock.ts`.
- Diagnosing a "panel/sidebar pops to default size then animates to the right one on load/switch" layout-shift, or any element that visibly animates from a hardcoded default to a persisted value.
- Adding a CSS transition to any dimension initialized to a default then overwritten by async IPC, Zustand hydration, or a store persist merge — gate it off during the hydration window.
- Reviewing any transition-suppression flag: confirm it feeds every `transitionend`-driven state machine's fallback and clears on the null/empty and error paths, not only on success — and needs `flushSync` only if it races a browser input frame (drag start), never in a post-`await` batch.
