## Context

Fleet broadcasting fans one payload out to every armed agent terminal. The primary Enter path (`tryFleetBroadcastFromEditor` → `executeFleetBroadcast` in `src/components/Fleet/fleetExecution.ts`) carries four load-bearing affordances: IPC batching for large pastes (`FLEET_LARGE_PASTE_BYTE_THRESHOLD` = 100KB across >5 targets, `FLEET_LARGE_PASTE_BATCH_SIZE` = 5, yielding via `setTimeout(0)` between batches), an `AbortSignal` checked at batch boundaries (the ribbon Cancel button), `fleetBroadcastProgressStore` updates, and synthetic directing-state calls (`terminalInstanceService.notifyUserInput`/`notifyEnterPressed`/`clearDirectingState`). Two secondary surfaces — the failure-banner retry and the broadcast preview — were built as private parallel implementations beside it.

## Problem

Retrying a failed large multi-target broadcast (#9950, the exact case batching exists for) re-fired through `broadcastFleetLiteralPaste`: one flat `Promise.allSettled` of `terminalClient.submit` calls — no batching (synchronous main-thread block), no Cancel, no progress counter, no directing indicator. Separately (#9954), the preview's private `detectUnresolved`/`resolveVariable` pair flagged unknown placeholders like `{{foo}}` as unresolved while the actual send via `replaceRecipeVariables` leaves them literal — the fleet preview contradicted both the payload and the identical recipe-surface preview. Neither bug was a coding error in its helper; each helper worked exactly as written. The drift WAS the bug.

## Root cause

Both are the same anti-pattern: a degraded parallel path created because the canonical path appeared to have one blocking incompatibility, when the canonical path already had (or could trivially grow) a mechanism for it. The retry needed verbatim replay without recipe-variable re-substitution — but `executeFleetBroadcast` already supported `perTargetOverrides`, so passing the stored payload as an override for every target with an empty draft bypasses substitution entirely (the empty draft is never resolved when every target has an override). The preview needed unresolved-variable detection — but the canonical `detectUnresolvedVariables` in `src/utils/recipeVariables.ts` already existed and was already imported by `fleetExecution.ts` for the payload itself; the private copy's `switch`-based `resolveVariable` returned `""` for unknown names, inverting the "unknown placeholders stay literal and are NOT unresolved" contract, and would silently mis-flag every future variable added to `recipeVariables.ts`.

The fix (#10158) extracted `runManagedFleetBroadcast` (`src/components/Fleet/fleetEnterBroadcast.ts`) — the single-flight wrapper owning `activeBroadcastController` lifecycle — and routed both Enter and retry through it. This matters beyond feature parity: `fleetBroadcastProgressStore` tracks exactly ONE run, so any dispatch outside the controller doesn't just lose Cancel, it races a concurrent Enter broadcast against the shared store. Post-merge history validates the consolidation: the helper has since grown run-record supervision (`useFleetRunStore.beginRun`/`applySubmissionResult`, plus `isRetry`/`draftPreview` opts, #10930 era) — capabilities the retry inherited for free, which a surviving `broadcastFleetLiteralPaste` would have missed, drifting again.

## Lesson

- **All fleet sends go through `runManagedFleetBroadcast` — never a bespoke `terminalClient.submit` loop.** The single-flight `activeBroadcastController` + one-run `fleetBroadcastProgressStore` make any out-of-band dispatch a race, not just a feature-poor sibling. A newer broadcast pre-empts the in-flight one via `abort()`; a parallel path is invisible to that pre-emption.
- **Verbatim replay through the canonical path = empty draft + `perTargetOverrides` for every target** (plus `draftPreview` so the run record still shows the literal). Don't fork a "no substitution" variant of the executor — the override mechanism already skips resolution when every target has one.
- **Eligibility filtering is caller-owned, deliberately not inside `executeFleetBroadcast`.** Every dispatch site must run `filterEligibleIds` at dispatch time (panes disarm/trash/lose PTYs between snapshot and send), and a zero-eligible result must return before dispatch so the progress store isn't spuriously activated. New callers of `runManagedFleetBroadcast` inherit batching/Cancel/progress but NOT this gate.
- **Any surface that previews or warns about `{{vars}}` must use the canonical `recipeVariables.ts` helpers** (`detectUnresolvedVariables`, `replaceRecipeVariables`, `hasRecipeVariables`). The contract: unknown placeholders stay literal and are excluded from "unresolved". A private resolver copy is a per-new-variable maintenance trap and makes two surfaces disagree on identical syntax (#10143).
- **When a secondary path (retry/preview/replay) needs one divergence from the primary, hunt for an existing parameter before writing a parallel helper.** Both bugs existed because one small incompatibility justified a fork; both fixes were "the canonical path already had the hook". A parallel helper's missing affordances don't fail tests — the stripped helper's own tests passed throughout.

## Applies when

- Adding any new fleet dispatch surface (action, MCP tool, scheduled/automated broadcast, replay) — route through `runManagedFleetBroadcast` in `src/components/Fleet/fleetEnterBroadcast.ts` and own the `filterEligibleIds` + zero-target gate in the caller.
- Touching `fleet.retryFailures` in `src/services/actions/definitions/fleetActions.ts`, `executeFleetBroadcast`, or the `activeBroadcastController`/`fleetBroadcastProgressStore`/`fleetRunStore` coordination.
- Building a preview, confirmation, or warning UI over recipe-variable text — resolve and detect with `src/utils/recipeVariables.ts` helpers only, and assert warning + payload agreement in the same test (see the #9954 regression cases in `fleetExecution.test.ts`).
- Tempted to write a stripped-down variant of an existing multi-affordance helper because one behavior (substitution, batching, state notification) doesn't fit — check for an existing bypass parameter (`perTargetOverrides`-style) first.
- Reviewing a PR that adds a second implementation of logic that already has a canonical home — ask what happens when the canonical one gains a feature or changes semantics; the duplicate won't fail any test when it drifts.
