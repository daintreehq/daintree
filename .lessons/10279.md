## Context

The pty-host's `ResourceGovernor` emits a `throughput-rate` reliability gauge (`terminal-reliability-metric`, a host-side telemetry sink, not UI-load-bearing) on its 2s `checkResources` tick. The rate is computed in `emitThroughputRateGauge` from a snapshot produced by `getThroughputSnapshot` in `electron/pty-host.ts`, which is **snapshot-and-reset**: it reads the closure-scoped `throughputAccumulator`, replaces it with a fresh `Map()` on every call, and returns `null` when nothing accumulated (`acc.size === 0`). #10279 (resolves #9903) fixed the rate math.

## Problem

After an idle stretch the first byte-producing tick underreported throughput by the length of the gap. A 10MB burst over 2s following a 60s idle window reported ~165KB/s instead of 5MB/s — off by the ~30x gap factor. Both `totalBytesPerSecond` and per-terminal `bytesPerSecond` were affected; `avgPacketSizeBytes` (a ratio, no time denominator) was fine. This is a measurement-only defect, but a dangerous one: it makes a real burst look like a trickle, hiding exactly the high-throughput events the reliability gauge exists to surface.

## Root cause

The numerator and denominator described different windows. `snapshot.totalBytes` is **window-bounded to one poll**: the accumulator is reset on every tick, so it only ever holds the last `CHECK_INTERVAL_MS` (2000ms) of bytes. But the denominator was `elapsedMs = snapshot.timestamp - prevThroughputTimestamp`, i.e. time since the last **emission** — and idle ticks return `null` and emit nothing, so `prevThroughputTimestamp` stayed stale across the whole gap. Dividing 2s of bytes by 60s of wall clock is the bug. The fix deletes the timestamp baseline entirely and uses `elapsedSec = this.CHECK_INTERVAL_MS / 1000` (a fixed 2s). Correctness now depends on an **implicit cross-file invariant**: the numerator's window is defined by the reset cadence in a _different file_ (`pty-host.ts`), and the divisor is a constant in `ResourceGovernor.ts` — the two must stay equal. If the accumulator ever stopped resetting every tick, the fixed divisor would become wrong.

Second, subtler trap in the same function: the delta counter `pauseCountDelta = snapshot.pauseCount - prevPauseCount`, whose baseline only advanced _past_ the `if (!snapshot) return` / `if (snapshot.totalBytes <= 0) return` early exits, folded idle-accrued pauses into the next active tick. The fix seeds `prevPauseCount` on the first snapshot (via a new `hasThroughputBaseline` flag, replacing the `prevThroughputTimestamp === 0` sentinel) and advances it on **every non-null snapshot**, above the `totalBytes <= 0` guard. Residual, stated honestly: `pauseCount` is read _inside_ `getThroughputSnapshot`, which returns `null` during true idle — so a pause in a byte-free window still isn't baselined until the next byte-bearing tick. Idle misattribution is reduced, not eliminated; the tests exercise it via a synthetic non-null zero-byte snapshot production never emits.

## Lesson

- **When a rate's numerator comes from a snapshot-and-reset accumulator, the denominator is the reset cadence, not the emit cadence.** The accumulator already defines the window; re-deriving it from `now - lastEmit` double-counts idle time. Divide by the fixed poll interval (`CHECK_INTERVAL_MS`). Emissions can be skipped (null/idle ticks), so time-between-emits is not the sampling window — conflating them is #9903.
- **The window invariant spans two files.** `getThroughputSnapshot` in `electron/pty-host.ts` owns the reset; `ResourceGovernor.ts` owns the divisor. Neither diff shows the coupling. Changing the accumulator's reset behavior (accumulate-across-ticks, conditional reset) silently invalidates the fixed divisor. The `dropAccumulator` data-loss counter in the same file resets every tick for the same reason (so toggling metrics on doesn't dump the backlog as one false regression) — treat "reset on EVERY tick" as a load-bearing metric-hygiene invariant.
- **Advance a delta baseline on every SAMPLE, not every EMISSION.** Any `delta = current - prevBaseline` where `prevBaseline` updates only past an early-return folds skipped-window deltas into the next emitted tick. Advance it before every conditional exit — and sample a monotonic counter on its own cadence rather than piggybacking another accumulator's snapshot, or it inherits that snapshot's null-gaps (why the pause fix here is partial).
- **`dispose()` must clear delta/baseline fields** (`hasThroughputBaseline = false; prevPauseCount = 0`), or a re-created governor inherits a stale baseline and emits a bogus giant first delta. Any object holding running counters needs its dispose to zero them whenever an instance can be re-instantiated in one process.

## Applies when

- Adding or editing any per-tick rate/throughput/delta gauge in `electron/pty-host/ResourceGovernor.ts` or a snapshot producer in `electron/pty-host.ts` (`getThroughputSnapshot`, `dropAccumulator`, `getQueueDepthSnapshot`).
- Computing bytes/sec, packets/sec, or any `X per unit time` from a counter reset each polling interval — verify the divisor equals the reset interval, not `Date.now() - lastEmit`.
- Diagnosing telemetry that under-reports after idle periods, or a counter delta that spikes on the first active sample after quiet (idle-window events misattributed to the next active tick).
- Reviewing any `delta = current - prevBaseline` metric — confirm `prevBaseline` advances before every `return`, and that the counter is sampled on a cadence independent of unrelated activity gates (null snapshots, `totalBytes <= 0`).
- Writing `dispose()` for any stateful sampler — confirm every baseline is cleared so a recreated instance starts clean.
