## Context

The panelRegistry slice of `usePanelStore` keeps three parallel structures: `panelsById`, the ordered `panelIds` list, and the per-worktree index `panelIdsByWorktreeId` (buckets keyed by worktreeId or `NO_WORKTREE`). Multi-panel spawns (recipe launch, hydration) run inside a batch window — `beginSpawnBatch`/`flushSpawnBatch`, the #5196 machinery in `core.ts` — and `addPanel`'s batched path (`isHydrationBatchActive()`) commits `panelsById` and the worktree index immediately but defers the `panelIds` append to flush via `collectPanelIdForBatch` → `commitPendingIds`. So for the whole batch window the store is deliberately torn: the index knows the panel, `panelIds` does not.

## Problem

Issue #9649: launch a recipe in a worktree and the agent terminal opened blank; switch to another worktree and back and it painted fine. The symptom read exactly like an xterm first-mount sizing race — `XtermAdapter`'s fallback fit bails on `clientWidth`/`clientHeight` of 0 — and was initially blamed on the v0.16.0 perf commits (rAF-throttled layout reads, visibility-gated timers). Both reads were wrong: the terminal was never in the render tree at all, and the bug was latent from when the batching landed (pre-0.15.0), not a fresh regression — hence `regression_of: null`.

## Root cause

Two mechanisms compound. First, the tear itself: `getTabGroups` built its ungrouped (virtual) groups by iterating `state.panelIds` alone, so a batched recipe panel — present in `panelsById` and the index, absent from `panelIds` — landed in no group and the grid derived empty. Second, the staleness lock-in: `useContentGridContext`'s `tabGroups` memo deps include `gridPanelIds` (sourced from `panelIdsByWorktreeId`, so it changes at commit time) but not `panelIds`. The memo therefore recomputed at exactly the wrong moment — mid-batch, against the stale `panelIds` — and when flush finally appended the id, no dep changed, so nothing recomputed again. The empty derivation persisted until an unrelated dep (`activeWorktreeId`) changed, which is precisely why switch-and-back "fixed" it. Single-terminal recipes were the clean repro because one ungrouped panel goes through the virtual-group path; a multi-terminal recipe landing in an explicit tab group reads `state.tabGroups` and dodges it.

The fix (#9655) makes the reader union both sources: `collectUngroupedCandidateIds` in `tabGroups.ts` iterates `panelIds` first (preserving committed order so drag-reorder via `reorderTabGroups` stays correct) then appends ids present in the index but not yet flushed — the concrete worktree's bucket plus the `NO_WORKTREE` bucket for a scoped query (dock-global panels must appear in every worktree's dock; the in-loop `panelMatchesWorktreeScope` filter keeps them out of grid queries), or every bucket when `worktreeId === undefined`. The symmetric-looking alternative — defer the index to flush so both lists move together — was explicitly rejected: `panelIdsByWorktreeId` is a live mid-spawn lookup, read during the batch by `applyWorktreeTerminalPolicy` (`worktreeStore.ts`) and by the `gridPanelIds` subscription. The asymmetry is load-bearing; the burden is on readers.

## Lesson

- **During a spawn batch, `panelIds` and `panelIdsByWorktreeId` intentionally disagree** — `panelsById` + index commit eagerly, `panelIds` appends at `flushSpawnBatch`. Any new selector or derivation over panel membership must union both sources (copy the `collectUngroupedCandidateIds` pattern, `panelIds` first for committed order) or it will see phantom-empty state for every batched spawn.
- **Never "fix" the tear by deferring the eager side.** `panelIdsByWorktreeId` must commit at panel creation because `applyWorktreeTerminalPolicy` and `gridPanelIds` read it mid-batch. When two store structures converge asynchronously by design, symmetrizing the commit is the tempting wrong move — audit who reads each structure inside the window before touching commit timing.
- **A memo that recomputes at the wrong time is worse than one that never recomputes.** The `tabGroups` memo fired on the eager dep (`gridPanelIds`) against stale `panelIds`, then went quiet when `panelIds` flushed (not a dep) — capturing the torn intermediate state until an unrelated dep changed. Adding `panelIds` to the deps would have masked this one symptom while leaving the two-source disagreement for every other reader; close the split at the derivation, not the dep array.
- **"Blank until worktree/project switch" is a stale-store-derivation tell, not a layout tell.** The recovery action worked only because `activeWorktreeId` is a memo dep that forces a re-derive. Before chasing xterm fit races or resize observers, check whether the missing element ever entered the derived structure that renders it.
- **Latent ordering bugs masquerade as release regressions.** The batching, the index-scoped selectors, and `useContentGridContext` all predate the release the bug was pinned to; the trigger (recipe launch = batched single ungrouped panel) just became common later. Verify on an older build before attributing to a release window's commits.

## Applies when

- Touching `src/store/slices/panelRegistry/` (`addPanel.ts`, `tabGroups.ts`, `core.ts`, `worktreeIndex.ts`) or writing any new reader of `panelIds` / `panelIdsByWorktreeId`.
- Adding a selector, memo, or derivation over panel membership that must be correct while `beginSpawnBatch` is open (recipe launch, hydration).
- Diagnosing a panel/terminal that renders blank or missing on first mount but appears after a worktree switch, project switch, or window resize.
- Tempted to change when `addPanel` commits either index, or to make the batched path commit both structures at the same time.
- Reviewing a `useMemo`/`useSyncExternalStore` whose deps cover only one of two store fields that converge asynchronously.
