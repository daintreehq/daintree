## Context

Daintree classifies destructive actions on a D0–D3 tier scale (`docs/architecture/destructive-action-safeguards.md`). Each `ActionDefinition` carries static `danger: "safe" | "confirm" | "restricted"` metadata. But some actions are safe at a small blast radius and destructive at a large one — e.g. `portal.closeAllTabs` / `portal.closeOthers` are routine at 1–2 tabs but lose real navigation history at 3+. PR #8469 introduced `deriveEffectiveTier(actionId, ctx)` as the single source of truth for per-invocation tier, and wired portal bulk-close as the first runtime-escalation consumer.

## Problem

Static `danger` metadata can only encode the worst case. Marking `portal.closeAllTabs` as `danger:"confirm"` would (a) strip it from the action-palette MRU/Favorites rail (`useActionPalette.ts:111-115` filters out every `danger:"confirm"` id) and (b) exclude it from `action.repeatLast`, punishing the common 1–2-tab case for a risk that only exists at 3+. Leaving it `danger:"safe"` is correct for the common case but then nothing gates the bulk close — and once a runtime confirm was wired, two latent bugs surfaced: `repeatLast` could replay a confirmed close past its gate, and `PortalDock.handleClose` collapsed the dock out from under the just-opened confirm dialog.

## Root cause

Three coupled mechanisms:

- **Metadata vs runtime tier are different axes.** `danger` classifies the worst case (drives MRU/repeatLast eligibility); the _effective_ tier for a concrete call depends on runtime context (tab count, `force` flag, branch protection). `deriveEffectiveTier` (a pure module — no store/React/IPC imports) computes the latter so the gating UI and the `run()` dispatch path can never disagree about whether a given invocation is high-tier. `WorktreeDeleteDialog`'s `isHighTier` and the portal `run()` bodies both consult it.
- **Keeping `danger:"safe"` re-opens the replay hole.** Because metadata stays `safe`, `ActionService` (`ActionService.ts:382-388`) would record the confirmed dispatch (`{ confirmed: true }`) as `lastAction`, letting `action.repeatLast` re-fire the close _past_ its confirm gate. The fix is `nonRepeatable: true` on the escalating action.
- **The escalation exposed a collapse race.** `PortalDock.handleClose` dispatched `closeAllTabs` then unconditionally `setOpen(false)`. When the action escalates, it leaves tabs intact and opens a confirm dialog instead — so collapsing the dock hid the portal (and its dialog) out from under the user. Fix: only collapse once the close actually happened (`if (usePortalStore.getState().tabs.length === 0) setOpen(false)`).

## Lesson

When an action's destructiveness scales with blast radius:

- Keep static `danger: "safe"` so the common low-blast case retains MRU/Favorites/`repeatLast` eligibility; escalate per-invocation in `run()` via `deriveEffectiveTier(actionId, ctx)`. Do NOT bump metadata to `"confirm"` just to get a sometimes-confirm.
- Any action that runtime-escalates to a confirm MUST also set `nonRepeatable: true` — otherwise `repeatLast` replays the confirmed dispatch past its gate.
- Route the confirm through an ephemeral pending-store (`portalPendingCloseStore`, modeled on `terminalPendingDestructiveActionStore`): the `run()` writes the pending snapshot and returns instead of acting; an app-level dialog host subscribes and re-dispatches with `{ confirmed: true }` on confirm. Mount the dialog host high (in `AppLayout`, not the panel) because the originating panel may be hidden when the keybinding/palette fires. The confirmed dispatch passes `confirmed` as an **arg** (read by the gate) not as `options.confirmed`, so the breadcrumb/repeat machinery never records it.
- Snapshot the preview list (tab titles) at request time — portal IPC can mutate titles while the dialog is open.
- After wiring any close-then-collapse / act-then-dismiss handler that calls an escalating action, gate the collapse/dismiss on the action having actually completed (check store state), not on the dispatch returning. The dispatch returning no longer implies the work happened.
- `deriveEffectiveTier` is purpose-built to be pure and unit-testable in isolation; add boundary tests at the threshold (0/1/2/3+ for portal; the #4927 tracked-only guard for worktree) rather than asserting through the dialog.

## Applies when

- Adding or modifying any `ActionDefinition` whose destructiveness depends on runtime context (count of affected items, `force` flag, branch protection, shared-vs-local target) — especially portal tab closes, worktree delete, terminal kill-all, bulk operations.
- Deciding between `danger:"safe"` and `danger:"confirm"` and worrying about MRU / Favorites / `repeatLast` eligibility (`useActionPalette.ts`, `ActionService.ts` `lastAction`).
- Wiring a confirm dialog for an action that is NOT classified `danger:"confirm"` at the metadata level (the pending-store + app-level dialog-host pattern: `portalPendingCloseStore`, `terminalPendingDestructiveActionStore`).
- Touching `PortalDock.handleClose` or any handler that dispatches an action and then collapses/hides/dismisses UI — verify the dismiss is gated on completion, not on dispatch return.
- Editing `deriveEffectiveTier.ts`, `docs/architecture/destructive-action-safeguards.md`, or reasoning about D0–D3 tier classification vs runtime escalation.
