## Context

`recomputeActivityTiers` in `electron/pty-host.ts` sets each terminal's `ActivityMonitor` polling cadence — 50ms "active" vs. the renderer's own cheaper 200ms (visible-unfocused) / 500ms (backgrounded) hints from `backendPollingIntervalForTier` in `src/services/terminal/TerminalRendererPolicy.ts`. Before PR #10811 ("Remove per-terminal hibernation; keep background terminals live"), it built a union of connected windows' active projects and demoted terminals outside that union to "background" (the #9778 rule). #10811 deliberately deleted that demotion branch as part of fixing the alt-screen wake-corruption bug (#10805/#10807: replaying a stale snapshot into a live TUI on wake) — it hard-pins `isBackgrounded` to `false` so the visual byte stream is unconditional and nothing ever goes stale that needs a lossy resync.

## Problem

Issue #10857: terminal scrolling got slower over long sessions with multiple project switches — not a crash, not a leak, a gradual event-loop cost. Misleading because it needed an actual long multi-project session to reproduce; a fresh single-project session showed nothing, and the trail initially looked like the same "scroll feels slow" family as the WebGL/DOM threshold bug fixed alongside it in #10860/#10858 (a different mechanism in the same subsystem).

## Root cause

After #10811, `recomputeActivityTiers()` took no arguments and looped `ptyManager.getAll()` — every terminal in every project — unconditionally calling `ptyManager.setActivityMonitorTier(terminal.id, "active", 50)` plus a `tier-changed` broadcast, on every call. It ran from three ordinary-workflow call sites: `connection.ts`'s `set-active-project` and `project-switch` handlers, and `pty-host.ts`'s `disconnectWindow` — project switches and window connect/disconnect, not rare events.

Because #10811 removed the demotion branch entirely, the function became strictly promote-only: it can force a terminal from "background" or "visible" up to "active," but nothing (post-#10811) ever sends it back down again. The renderer's own tier demotion only fires on a write, a visibility change, a focus change, a mount, or a reparent (call sites in `TerminalInstanceService.ts`) — a terminal that goes genuinely idle and stays backgrounded never re-triggers any of those, so once the host stomps it to "active" it stays there. `ActivityMonitor.runPollingCycle` (`electron/services/ActivityMonitor.ts` ~line 1266) runs its full scan — `getVisibleLines`, ANSI-strip, prompt-detection regex over up to 50 lines — every tick, unconditionally, regardless of whether new PTY data arrived. Every project switch in a normal multi-project workflow therefore pins strictly more terminals to that 50ms cadence than the last, in the same single-threaded pty-host event loop that forwards PTY output to the renderer, including the round trip full-screen mouse-reporting TUI scrolling depends on (paced separately in #10848). The ratchet only tightens: more switches over a session, more stuck-active terminals, nothing self-heals.

The fix (#10861) gave `recomputeActivityTiers` a `nextProjectId: string | null` parameter and swapped `ptyManager.getAll()` for `ptyManager.getTerminalsForProject(nextProjectId)`, so it only force-activates the terminals of the project that just became foreground; `nextProjectId === null` (the `disconnectWindow` call site) is now a documented no-op, since a disconnect never grows scope. Terminals in other projects, and global/undefined-project terminals, are left exactly as `TerminalRendererPolicy`'s own tier IPC last set them.

## Lesson

- **A function that can only promote and never demote is a ratchet under any repeated trigger** — every call adds cost, none removes it. Before stripping a demotion branch (as #10811 did to fix wake-corruption), check whether the remaining promote-only path is still properly scoped; the old self-correcting union logic had made unscoped iteration harmless, and removing demotion is exactly what turned "iterate everything" into a real bug.
- **Scope host-driven state resets to the event that actually changed**, not to `ptyManager.getAll()` / "every project" — the actual fix was threading `nextProjectId` through all three call sites (`connection.ts`'s two handlers, `pty-host.ts`'s `disconnectWindow`) and looping `getTerminalsForProject(projectId)` instead of every terminal in every project.
- **Don't assume the renderer will self-correct a host-side stomp.** `TerminalInstanceService.ts`'s tier-changed handler is deliberately passive (built for #9778/#8998, to avoid swallowing a legitimate active-tier resend) — it updates its local cache but never echoes a correction back. Only a write/visibility/focus/mount/reparent event re-asserts the renderer's desired tier, so an idle backgrounded terminal that the host force-activates has no path back down.
- **This symptom shape — gradual slowdown correlated with session length / event count (project switches here), not terminal count or memory — is a leak-shaped bug that isn't a leak.** Don't reach for heap snapshots first; grep for the recompute call sites and check whether they're scoped to the triggering event or iterate everything.
- **Copy the test pattern that would have caught this**: `electron/__tests__/pty-host.adversarial.test.ts`'s `TIER_MATRIX` and `RACE_FUZZER_TIER_QUIESCENCE_INVARIANT` seed the OPPOSITE tier before each assertion, so a pass only proves a genuine write or a genuine leave-alone, never a coincidental default — use seed-opposite-then-assert for any future scope-correctness fix in this file.

## Applies when

- Touching `recomputeActivityTiers`, `TerminalRendererPolicy.ts`'s tier push, or any pty-host activity/backpressure tier logic in `electron/pty-host.ts` or `electron/pty-host/handlers/connection.ts`.
- Diagnosing "scrolling/terminal output feels slower the longer a session runs" or "slows down after switching projects repeatedly" — distinguish from the #10858 WebGL/DOM-threshold cause (#10860) and the #10948 pty-host-memory-pressure-pause cause, which are different mechanisms in the same terminal-perf area.
- Reviewing any change that strips a demotion/cooldown branch from a previously bidirectional promote/demote function for a correctness fix elsewhere — the remaining promote-only path needs its own scope audit, it won't get one for free.
- Adding a new caller to `recomputeActivityTiers` or `setActivityMonitorTier` on a routine per-window/per-connection event — confirm it can't fire more broadly than the state that actually changed.
- Working anywhere in the hibernation-removal experiment surface (#10805/#10807/#10811) where "never go stale" was achieved by pinning something permanently active — check whether that something is now unbounded elsewhere.
