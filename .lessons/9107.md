## Context

`ProcessTreeKiller` tears down a PTY's process tree on terminal close: on POSIX it SIGTERMs every descendant bottom-up, kills the shell via `ptyProcess.kill()` (node-pty sends `SIGHUP`), then escalates to `SIGKILL` after a 500ms grace window (`sigkillSweep`). Dev servers run under these PTYs (`vite`, `next dev`) and rely on `SIGTERM`/`SIGHUP` handlers to release bound ports and reap child workers before exiting.

## Problem

If a descendant or the shell was suspended with Ctrl+Z (`SIGSTOP`), closing the terminal left orphaned ports and subprocesses. The stopped process never ran its shutdown handler, so the bound dev-server port and any child workers leaked after every close.

## Root cause

A `SIGSTOP`'d process does not run user code, so a catchable signal like `SIGTERM` (or `SIGHUP`) is _queued, not delivered_, while stopped. The killer sent `SIGTERM`, the stopped process ignored it (couldn't run a handler), the 500ms timer fired, and `SIGKILL` — which the kernel delivers to stopped processes directly and is uncatchable — terminated it without any handler ever running. The process effectively skipped the graceful path entirely.

## Lesson

To gracefully kill a possibly-stopped POSIX process, send `SIGCONT` after the catchable kill signal. `SIGCONT` resumes the process and the kernel delivers the queued `SIGTERM`/`SIGHUP` before any user-space code runs, so handlers fire. Specifics that are load-bearing:

- **Order is SIGTERM-then-SIGCONT, never the reverse.** Resuming first opens a window where the process runs freely and can `fork()` untracked children before the kill signal arrives — those children escape the descendant snapshot and orphan.
- **Skip SIGCONT when the preceding SIGTERM was rejected with a non-`ESRCH` error (e.g. `EPERM`).** There is no queued kill to deliver, so waking a process you couldn't signal just lets it run free with no pending termination. `ESRCH` (already gone) falls through harmlessly — the follow-up `SIGCONT` also `ESRCH`es silently.
- **Do NOT add SIGCONT before SIGKILL.** `SIGKILL` is uncatchable and is delivered to stopped processes by the kernel regardless; `sigkillSweep` is correctly left untouched.
- **The shell's SIGCONT is independent of the descendant gate** — it pairs with `ptyProcess.kill()`'s `SIGHUP` and is kept outside that try/catch so it still fires if `ptyProcess.kill()` throws (already-dead shell → silent `ESRCH`).
- A failed `SIGCONT` with `EPERM` warrants a `console.warn` (permanent orphan: stopped process holding an undeliverable queued kill); `ESRCH` is swallowed.
- POSIX-only: Windows uses `taskkill /T /F`, which needs no equivalent.

## Applies when

Writing or reviewing any process-teardown code that sends catchable signals (`SIGTERM`, `SIGHUP`, `SIGINT`) and must work against processes that may be job-control-stopped (Ctrl+Z) — PTY/process-tree killers, dev-server lifecycle, subprocess cleanup on shutdown. Recall whenever graceful-shutdown handlers "don't run" or ports/children leak after killing a process that could have been suspended.
