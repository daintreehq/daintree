## Context

Every pty-host backpressure/reliability signal funnels through one function, `emitReliabilityMetricWithTracking(payload, source, forceEmit)` in `electron/pty-host.ts`. It is dual-purpose: it forwards a `terminal-reliability-metric` wire event to Main AND mutates the closure-scoped `pausedTerminals` map that tracks per-source pause attribution. That map feeds `getPausedDurationsSnapshot`, which drives the "Paused for Xs" line in the pane tooltip and the renderer's `heldDurationMs`. When the IPC fallback queue drops a chunk at its hard byte cap (`ipcQueueManager.isAtCapacity`), the drop site emits a reliability pulse to report the data loss.

## Problem

While a terminal was genuinely paused by IPC backpressure and actively dropping data — the exact episode the held-duration gauge exists to describe — the "Paused for Xs" tooltip went silent and the renderer's displayed `heldDurationMs` was wiped to nothing. Nothing looked wrong at the drop site: the metric was emitted, the terminal really was paused, and the inline comment there literally claimed the funnel "doesn't touch the per-source tracking map."

## Root cause

In this funnel, `metricType` + `source === null` is not a label — it is a command discriminant. With `source === null`, a `pause-end` OR `suspend` metric is interpreted as a user/system force-resume and calls `clearAllPauseSources(terminalId)`, deleting the terminal's entire `pausedTerminals` entry. The drop site reused the existing `"suspend"` metricType with `source: null` to REPORT a data-loss pulse — so a pure telemetry report was read by the funnel as a state-transition COMMAND. The interleaving is real, not theoretical: `applyBackpressure` adds an `"ipc"` source entry at the 67% high watermark; an in-flight chunk then hits the 100% cap, runs the drop path, and the funnel wipes the whole entry; the later genuine `pause-end` from the IPC queue removes a source that is already gone (a silent no-op). Downstream, `getPausedDurationsSnapshot` reports the terminal as not paused, which silences the tooltip, and the renderer's `pause-duration-gauge` absent-loop in `src/store/listeners/panel/lifecycle.ts` treats any `suspend` as a canonical resume and clears `heldDurationMs` directly. One bad emit corrupted state across three components.

A second, independent defect at the same site: it omitted `forceEmit: true`, violating the funnel's documented "data-loss pulse bypasses the metric gate" contract — so with `DAINTREE_TERMINAL_METRICS` off (production default), the pulse never reached the wire at all. The genuine suspend in `BackpressureManager` passes `forceEmit=true`; this one did not.

The fix added a dedicated `"ipc-cap-drop"` metricType to the `metricType` union in `shared/types/pty-host.ts`; the drop site now emits that with `forceEmit: true`. The new type falls through the funnel with NO map mutation, so only a real force-resume (`coordinator.forceReleaseAll`) reaches the `clearAllPauseSources` arm.

## Lesson

- **When one channel carries both reports (telemetry) and commands (state transitions), the type field IS the command trigger — reusing the nearest existing type at a new emission site silently inherits its command behavior.** Reporting a drop by borrowing `"suspend"` executed the force-resume side effect the drop-site author never intended. Grep every consumer that `switch`es on the type before emitting an existing one from a new place.
- **The trigger here was `metricType` PLUS `source === null`, not the type alone.** The same `"suspend"` with a real `PauseSource` merely calls `removePauseSource` (correct); with `null` it means "user asked for a full resume, attribution is moot" and wipes all sources. A discriminant can be a compound of the type and a nominally-orthogonal field — read the funnel's full branch condition, not just the type.
- **A genuinely new event needs a new metricType, not an overload.** The one-line fix was `"ipc-cap-drop"` in `TerminalReliabilityMetricPayload`, chosen precisely because it has no funnel branch and no consumer that mutates the pause map — it falls straight through to the wire. Cheaper and safer than teaching every consumer to special-case a reused type.
- **Data-loss pulses must pass `forceEmit: true`.** The funnel gates non-load-bearing metrics on `metricsEnabled()`; a data-loss/drop signal must reach the wire even when metrics are gated off, or regression/discontinuity detection goes blind in production. Match the `forceEmit` behavior of `BackpressureManager.suspendVisualStream` for any new drop/loss pulse.
- **Trust the branch condition over the local comment.** The drop site's comment asserted the funnel left the tracking map alone; the funnel's `else if` matched the call exactly and cleared it. When a stale comment and the code disagree, the code wins.

## Applies when

- Emitting any reliability/backpressure pulse from a NEW site in `electron/pty-host.ts` via `emitReliabilityMetricWithTracking` — confirm the `metricType` (and whether `source` is `null`) does not trip a state-mutating funnel arm.
- Touching `emitReliabilityMetricWithTracking`, `clearAllPauseSources`, `addPauseSource`/`removePauseSource`, or the `pausedTerminals` map.
- Adding a value to the `metricType` union in `shared/types/pty-host.ts`, or reusing an existing one for a new meaning.
- Diagnosing the "Paused for Xs" tooltip going silent or `heldDurationMs` being wiped while a terminal is still paused and dropping data.
- Reviewing any typed event vocabulary where a consumer switches behavior on the type and the same channel mixes telemetry reports with state-transition commands — confirm a new emitter isn't inheriting command semantics.
