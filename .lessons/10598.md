## Context

Plugin settings carry a manifest-declared `scope` (`"user"` or `"project"`) in `contributes.settings`. The write side enforces it: `PluginSettingsManager.assertSettingDeclared` (called by `settings.set` and the UI bridge) rejects a write to a scope other than the one declared, so writes land in the correct store. The host `settings.get` handler lived in `PluginService.ts` (moved to `electron/services/plugin/PluginHostFactory.ts` by the file-split refactor #10997-#11009), and dev-worker plugins reach it through `pluginDevWorkerHostProxy` → `PluginDevWorkerMainBridge` across the utility-process boundary.

## Problem

A setting declared `scope: "project"` and read the obvious way — `host.settings.get(key)` with no scope arg — silently returned the `"user"`-store value (usually `undefined`), with no error. It bit the mock-forge test plugin: it declared a project-scoped `dataFile`, seeded the project store, and `get("dataFile")` read the empty user store, so the provider returned no data. The write went to the right place, the read to the wrong one, and nothing complained — a pure wrong-scope miss. A unit test wouldn't catch it either, because the mock host faithfully mirrored the same silent `"user"` default.

## Root cause

`settings.get` was typed `scope: PluginSettingsScope = "user"` — the read applied a hardcoded default instead of consulting the declaration, so read/write scope resolution were asymmetric: `set`/`onDidChange` honored the declared scope, `get` ignored it. That alone is a silent-failure footgun. The non-obvious half is the bridge: `pluginDevWorkerHostProxy.get` ALSO defaulted `scope = "user"`, and `SettingsGetParams.scope` was a _required_ field — so an omitted scope was coerced to an explicit `"user"` at the proxy hop and shipped across the process boundary as `"user"`. By the time the call reached main, the "caller omitted scope" signal was already destroyed, so fixing only the main-side resolver would have been defeated — main still received an explicit `"user"` for every dev-worker read. Worse, once the host learned to throw on an explicit-scope-vs-declaration conflict, a pre-defaulted `"user"` would make main _reject_ a project-scoped read outright. The fix: a single `PluginSettingsManager.getDeclaredScope(pluginId, key)` authority consulted on reads (`effectiveScope = declaredScope ?? scope ?? "user"`); an explicit scope conflicting with the declaration throws; the proxy forwards `scope?` (optional), `SettingsGetParams.scope` becomes optional, and the bridge forwards the raw (possibly `undefined`) value — so omission crosses the bridge intact. Undeclared keys keep the permissive `"user"` fallback (`getDeclaredScope` returns `undefined`), so manifests that declare no scope don't regress.

## Lesson

- **Omitted optional params must cross a process/IPC bridge as `undefined`, never pre-defaulted at an intermediate hop.** The dev-worker proxy defaulting `scope = "user"` erased the "caller omitted this" signal before main could act on it — a defaulted intermediate value is indistinguishable from a deliberate one at the far end. When a bridged API has a param whose default the _receiving_ side must compute (from a manifest, declaration, or context), the sending proxy AND the wire type (`SettingsGetParams`) must both keep it optional.
- **Read and write must resolve scope/target through ONE shared authority, not independent defaults.** The bug was the asymmetry: writes went through `assertSettingDeclared`, reads through a hardcoded `"user"`. Any API where one side enforces a declaration and the other applies a static default will silently diverge — route both through the same resolver (`getDeclaredScope`).
- **A "reasonable-looking" default that silently reads the wrong store is worse than an error — make the conflict loud.** The read returned `undefined`/wrong value with no diagnostic. The fix throws when an explicit scope contradicts the declaration; prefer a throw over a silent wrong-store hit anywhere a caller's intent can conflict with a declaration.
- **A mock that faithfully mirrors a production default reproduces the bug in tests too, so a green unit test is not evidence of correctness.** `createMockHost` mirrored the silent `"user"` default, so tests passed while behavior was wrong. The fix added opt-in `manifestSettings` for scope-aware reads (loose mode keeps the old default, so manifest-free tests are unaffected). When a mock encodes a default, give it an opt-in mode that exercises the declaration-aware path.

## Applies when

- Adding or changing any plugin `host.*` API param that a dev-worker plugin reaches through `pluginDevWorkerHostProxy` / `PluginDevWorkerMainBridge` — check both the proxy default AND the `*Params` wire type in `shared/types/pluginDevWorker.ts` preserve omission as `undefined`.
- Diagnosing a plugin setting that reads `undefined` or a stale/wrong value while the write clearly succeeded — suspect a scope/store mismatch between the read and write paths, not a persistence bug.
- Touching `settings.get`/`set`/`onDidChange` scope resolution or `PluginSettingsManager.getDeclaredScope` — reads and writes must resolve the declared scope through the same authority, and undeclared keys must keep the permissive `"user"` fallback.
- Reviewing any bridged/IPC API where an intermediate layer applies a default before the value reaches the component that owns the real default logic — the default belongs at the resolving end, not the forwarding hop.
