## Context

`PopoverContent` (`src/components/ui/popover.tsx`) wraps Radix Popover, which positions via Floating UI. To keep popovers from rendering behind the right-edge native panels (Portal/web-chat and Assistant `WebContentsView`s), it passes a `collisionBoundary` — a hidden fixed div whose width is `calc(100vw - var(--right-obstruction-offset, 0px))`. `AppLayout` (`AppLayout.tsx:430-452`) publishes `--right-obstruction-offset` = `max(portalWidth, assistantWidth)` on toggle, so the boundary div's effective width shrinks/grows as those panels open/close.

## Problem

When the right native panel toggled while a popover was already open, the popover kept its stale position — it could overlap or hide behind the panel that just opened, or sit offset after the panel closed. Toggling re-fired `--right-obstruction-offset`, which resized the boundary div, but the open popover never recomputed placement.

## Root cause

Floating UI's `autoUpdate` (which Radix uses under the hood) observes only the **reference element, the floating element, and their scroll ancestors** — it does **not** observe the `collisionBoundary` element. A boundary resize that changes the available space is invisible to it, so no re-layout fires. The boundary width is driven by a CSS custom property mutated from a sibling layout effect, not by any element autoUpdate watches.

## Lesson

- Floating UI / Radix `autoUpdate` will NOT re-position when only the collision boundary changes size. If your boundary is dynamic (CSS var driven, panel-toggle driven), you must trigger the re-layout yourself.
- The fix: attach a `ResizeObserver` to the boundary element and, on resize, bump a `repositionTick` state passed as a **`data-reposition-tick` attribute** on Radix `Content`. The attribute change re-runs Radix's positioning layout effect against the now-updated boundary — without remounting.
- Use a `data-*` attribute, **NOT `key=`**, to force the re-run. Changing `key` remounts `Content`, which destroys the open popover's DOM: focus is lost (breaks keyboard/a11y, the focus trap) and the open/close exit animation is killed. A `data-*` change is a cheap re-render that keeps the node mounted.
- Guard the observer: skip it when the caller supplied their own `collisionBoundary` (the internal portal boundary is then unused — nothing to observe), and guard `typeof ResizeObserver === "undefined"`. Spread `{...props}` BEFORE `data-reposition-tick` so the internal tick wins over any caller-supplied value (covered by the unit test "internal tick wins over a caller-supplied prop").

## Applies when

- Adding or debugging popovers, dropdowns, tooltips, or any Radix / Floating UI floating element that uses a `collisionBoundary` whose size is dynamic.
- A popover/overlay shows up in the wrong place ("stale position") after a panel, sidebar, or `WebContentsView` toggles — especially anything keyed off `--right-obstruction-offset` or `--portal-right-offset` (toaster, ReEntrySummary, GettingStartedChecklist, ThemeBrowser overlay all consume these vars).
- You're tempted to force a re-layout/re-position by changing a React `key` on a Radix `Content`/portal subtree — reconsider; prefer a `data-*` attribute bump to avoid focus loss and exit-animation breakage.
- Working in `src/components/ui/popover.tsx`, or any code touching `getPortalBoundary()` / `data-portal-boundary` / the obstruction-offset CSS vars in `AppLayout.tsx`.
