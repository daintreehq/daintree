## Context

`agent.launch` is an `ActionService` action (`src/services/actions/definitions/agentActions.ts`) reachable both from in-app UI (toolbar/palette clicks) and from the MCP tool surface (`electron/services/mcp-server/`) that external agents and the in-app assistant drive under. `useAgentLauncher.ts` resolves the target worktree from a `worktreeId` argument before spawning a terminal.

## Problem

Calling `agent.launch` with an unresolvable `worktreeId` (e.g. a branch name like `main` instead of the worktree's path id) came back as a plain success with no `terminalId` and no error. A model client can't distinguish "launched, but I lost the id" from "nothing happened" from that response, so it retried. One real session produced 34 consecutive no-op tool calls off a single bad ID, each one coming back looking exactly as unhelpful as the last.

## Root cause

`useAgentLauncher`'s worktree lookup did `worktreeMap.get(targetWorktreeId)`, found nothing, `console.warn`'d, and returned `null`. `console.warn` never reaches an MCP client — it's a dev-console-only signal. `agentActions.ts`'s `agent.launch` handler collapsed that `null` into its own `null` return, and the MCP session server serialized that as a non-error tool result: no `isError`, just an empty success. The declared output schema already required `terminalId: z.string()`, so the response was already violating its own contract — nothing in the pipeline enforced that, it just silently shipped a payload the schema said couldn't exist. The fix extracted a pure `resolveLaunchWorktree(targetWorktreeId, worktreeMap, isInitialized)` helper that throws `Worktree 'X' not found. Available worktree IDs: a, b, c` instead of returning null. That throw needed no new plumbing: `ActionService.dispatch()` already wraps every action's execution in a try/catch (`src/services/ActionService.ts` ~L487) that converts any thrown error into `{ok:false, error:{code:"EXECUTION_ERROR", message}}`, and `buildToolError` in `electron/services/mcp-server/shared.ts` already serializes that shape with `isError:true`. The "loud failure" infrastructure was already built for every action — this handler just wasn't using it.

## Lesson

- **A null/undefined return from an MCP-reachable action handler is not a safe "no-op" — it's a silent lie.** If the action's output schema declares a required field (`terminalId: z.string()`), a response missing that field must never reach the client as `ok:true`; the model has no console to read a warning from, so anything short of `isError:true` reads as success and gets retried.
- **Throwing inside an `ActionService` action is free error-propagation, not a new mechanism to build.** `ActionService.dispatch()`'s catch block already converts any thrown `Error` to `EXECUTION_ERROR` / `isError:true` on the MCP wire — when you find a handler returning `null`/`false`/an empty object to signal failure, that's very likely a handler that should just `throw` and let existing infrastructure carry it.
- **Error messages for model clients must enumerate the valid alternatives inline**, not just say "not found" — the fix's message lists `Available worktree IDs: wt-1, wt-2` so the model can self-correct on its next call without a human intervening; that's what actually kills the retry loop, not merely failing loudly.
- **A shared function used by both a UI event handler and an MCP action must be audited at every call site before you make it throw.** `resolveLaunchWorktree` runs inside `useAgentLauncher`'s `launchAgent`, which both call sites invoke: `agentActions.ts` reaches it via `callbacks.onLaunchAgent` (wired straight to `launchAgent` in `App.tsx`, so the MCP path's throw sails through untouched), while direct UI clicks go through `App.tsx`'s `handleLaunchAgent` — which needed a new `try { await launchAgent(type) } catch { logError(...) }` wrapper, or the new throw becomes an unhandled promise rejection in the renderer instead of the pre-existing quiet no-op it relied on for a stale-`activeWorktreeId` race.
- **Don't drop the "is the source of truth even loaded yet" guard when copying this pattern.** `resolveLaunchWorktree` only throws once `isInitialized` is true; before the worktree map has loaded, "not found" and "not loaded yet" are indistinguishable, so it falls through to `null` and lets the caller's `cwd` fallback handle it. Throwing unconditionally would misfire during startup races.

## Applies when

- Writing or reviewing an action definition in `src/services/actions/definitions/*.ts` that's reachable from the MCP tool surface — check every early-return path for a `null`/`false` "quiet failure" instead of a thrown error.
- A model-driven client (the in-app assistant, an external MCP agent) is stuck retry-looping the same tool call — check whether the tool's declared output schema is actually satisfied on the failure path, not just whether a response comes back.
- Extracting a pure helper out of a hook/store that's invoked from both a direct UI event handler and an MCP-driven action callback — the UI call site needs its own try/catch or a newly-added throw becomes an unhandled rejection there.
- Adding a "resource not found" error anywhere on the MCP surface — list the valid IDs/names in the message rather than a bare "not found", per the same self-correction principle used here.
- Diagnosing "the assistant/agent keeps calling the same tool over and over" — look for a success response missing a schema-required field before assuming a prompting or retry-logic problem.
