## Context

Panels are serialized to disk per-project and rehydrated on startup by `panelRestorePhase.ts`. The on-disk `PanelSnapshot` carries a `kind` string. When a panel kind is removed from the codebase (here the `notes` built-in, deleted with `NotesService`, `src/panels/notes/`, the IPC namespace, and the registry entry), users who had that panel in a saved layout still have the dead `kind` on disk. The renderer also supports plugin-provided panel kinds that may be absent at hydration time (plugin uninstalled or not yet loaded), for which it shows a `PluginMissingPanel` placeholder (#5580) rather than dropping them.

## Problem

Deleting the feature code is the easy 95%. The trap is that hydration of an unregistered `kind` now has THREE distinct meanings that must be told apart, and getting it wrong produces either ghost panels ("Unknown Panel Type" tiles for `notes`) or silent data loss (a temporarily-missing plugin's panel vanishing forever). A naive `if (!getPanelKindConfig(kind)) skip` drops missing-plugin panels; a naive "always restore unregistered kinds as placeholder" resurrects ghosts for the deliberately-removed built-in.

## Root cause

There is no flag on the snapshot saying "this kind was intentionally removed" vs "this plugin is just absent right now." The disambiguation has to be inferred from the kind string and adjacent fields. Current-format plugin panels carry `saved.pluginId`; legacy pre-#5580 plugin panels persisted their kind as `"${manifest.name}.${panel.id}"` — i.e. with a dot — and have no `pluginId`. A removed built-in kind (`notes`, `browser`, `dev-preview`) is a bare lowercase token with no dot and no `pluginId`. So the dot in the kind name is the load-bearing legacy signal that separates an orphaned plugin panel from a removed built-in.

## Lesson

When you remove a built-in panel kind, the code deletion is incomplete without a hydration guard for the persisted dead kind. The live guard in `panelRestorePhase.ts` (~line 353-368): restore an unregistered kind as a placeholder when `saved.pluginId` is set OR `kind.includes(".")` (legacy plugin), otherwise `logHydrationInfo(...)` and `return` to skip it. Only the non-dotted, pluginId-less case is treated as a removed built-in and dropped silently — exactly the shape of `notes`. Pair the skip with two more pieces: (1) bump any persist store that lists the kind by name (here `toolbarPreferencesStore` v5→v6 strips `"notes"` from button lists) so stale references don't render dead controls, and (2) a non-destructive idempotent main-process migration (`018-archive-notes.ts`) that renames `userData/notes` → `userData/notes_archived` so user-authored data survives the code deletion. Do NOT widen the skip to "any unregistered kind" — that re-breaks #5580 missing-plugin panels; and do NOT widen the placeholder path to bare kinds — that resurrects ghosts.

## Applies when

Removing or renaming a built-in panel kind (`terminal`/`browser`/`dev-preview`/future kinds), or any persisted discriminated-union variant whose dead value can still exist in saved user state. Also when touching the unregistered-kind branch in `panelRestorePhase.ts` — the `pluginId` / `kind.includes(".")` test encodes the removed-built-in vs missing-plugin vs legacy-plugin three-way split and must not be simplified to a single `getPanelKindConfig` check.
