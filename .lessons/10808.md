## Context

Each project gets its own `WebContentsView` + V8 context via `ProjectViewManager` (per CLAUDE.md's Multi-Window & Project Views section). Switching projects uses an "anti-flash bridge": `performSwitch` (now in `ProjectViewSwitchController.ts`) attaches the incoming view alongside the outgoing one and only detaches the outgoing view — via `deactivateEntry(previousEntry)` — after the incoming view signals a clean paint (`APP_VIEW_PAINTED`/`APP_VIEW_WARM_PAINTED`) or a hard timeout fires. All of this is meant to run serialized through `this.switchChain`, a chained promise so switches can't interleave.

## Problem

During a stress session of rapid project-view switching plus backgrounding/restoring the whole app, the forge/GitHub status toolbar rendered twice — two identical pill-groups side by side, each showing the red-line error state, offset from each other rather than overlapping. That "offset" detail read like a CSS/layout bug in `ForgeStatsToolbarButton.tsx`, but the toolbar mounts exactly once per renderer (`Toolbar.tsx` in `AppLayout.tsx`); duplication at that visual layer only makes sense if two entire `WebContentsView`s — two full renderer processes — were attached to `win.contentView` simultaneously (filed as #10806).

## Root cause

`HibernationService.destroyView` (called from a memory-pressure path, not from inside `switchChain`) can null `this.activeProjectId` while a paint gate for an in-flight switch is still pending. When the gate then resolves, it resolves as `"cancelled"` because the warm-path detach guard is `gateResult !== "cancelled" && this.activeProjectId === projectId` — and a cancelled gate deliberately skips tearing down its own outgoing view, on the theory that "the next switch will own the teardown." But the next switch's teardown only targets its own `previousEntry`, not the orphan left behind by the cancelled one. The orphaned view stays attached to `win.contentView` forever, and Chromium happily composites both children — two full app renderers paint side by side. The offset (not perfect overlap) has its own mechanism: `resizeHandler` only re-bounds `getActiveView()` and the pending gate's `outgoingView`, so the orphan — being neither — never gets bounds updates and drifts to a stale x-offset on the next resize/background-restore. `evictStaleViews` (eviction under memory pressure) is the other trigger path that also runs outside `switchChain`.

The generalizable shape: a serialized queue (`switchChain`) only protects invariants for state mutations that go _through_ it. A side service (`HibernationService`) that mutates the same shared field (`activeProjectId`) from outside the queue creates a race the queue's own guards can't see, because the guard condition (`activeProjectId === projectId`) becomes false for a reason unrelated to a legitimate supersession.

## Lesson

- **A serialized chain only enforces invariants on writers that go through it.** If any other code path (a background service, an eviction sweep, a hibernation timer) mutates the same state the chain guards (`activeProjectId`), the chain's cancellation/guard logic can misfire in ways its own tests won't catch unless the test explicitly drives that side path mid-gate.
- **"The next operation will clean up the previous one's leftovers" is false whenever operations only know their own state.** Here each switch only tears down its own `previousEntry` — a cancelled switch's orphan is nobody's `previousEntry` going forward. Any handoff-based cleanup design needs either a global sweep or an explicit chain of custody, not implicit "next one gets it."
- **The fix is a defensive, idempotent sweep, not tighter cancellation logic**: `pruneOrphanedChildren` (now an exported function in `ProjectViewLifecycleController.ts`, called from `ProjectViewSwitchController.ts` — moved off `ProjectViewManager` in a later file-split) walks `win.contentView.children`, keeps only the active view and any in-flight gate's outgoing view, and detaches everything else — parking registered entries via `deactivateEntry` (preserves cleanup handlers per #6085), hard-removing anything unregistered. Runs on every switch success path AND rollback, wrapped in try/catch that only logs — a sweep must never itself throw and break the switch it protects.
- **Filter compositor-wide sweeps to the exact subsystem, not "everything attached."** `pruneOrphanedChildren` only touches children present in `webContentsToProject` — portal-parked tabs (offscreen bounds while attached) and the welcome view are deliberately skipped, because a generic "reset all children's bounds/visibility" sweep would yank a hidden portal onscreen.
- **A visual "offset duplicate" is a resize-handler blind spot, not styling** — before touching CSS/layout for a doubled-UI symptom in a multi-`WebContentsView` architecture, check whether every code path that repositions views (`resizeHandler`, paint-gate bounds sync) actually enumerates ALL attached children rather than just the two it expects to exist.

## Applies when

- Touching `ProjectViewManager.ts`, `ProjectViewSwitchController.ts` (`performSwitch`, the warm/cold anti-flash bridge, `waitForPaint`), or `ProjectViewLifecycleController.ts` (`pruneOrphanedChildren`, `deactivateEntry`, `cleanupEntry`).
- Adding or modifying any service that reads/writes `activeProjectId`, `pendingPaintGate`, or view-attach state from outside `switchChain` — especially `HibernationService`, `ProjectViewEvictionController.evictStaleViews`, or any future memory-pressure/backgrounding hook.
- Diagnosing duplicated UI (toolbar, panel, any chrome) that "shouldn't be able to mount twice" in a multi-`WebContentsView` or multi-window Electron architecture — check for two attached views before suspecting React double-render.
- Reviewing any switch/transition design with an "anti-flash bridge," crossfade, or two-views-attached-briefly pattern — verify the teardown side has a sweep for cancelled/superseded transitions, not just a happy-path detach.
- Writing a resize/bounds-sync handler in a compositor with a variable number of attached views — confirm it enumerates all children, not just the ones the code currently expects.
