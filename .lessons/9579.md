## Context

`ActionService` (`src/services/ActionService.ts`) is the typed dispatch layer whose manifest doubles as the tool surface of the local MCP server (`electron/services/mcp-server/`). JSON Schemas are compiled lazily from Zod via `zodSchemaToJsonSchema` (options `{ io, unrepresentable: "any", reused: "inline", cycles: "ref" }`) into a per-id `schemaCache` on first `toManifestEntry()` — the #8614 cold-start optimization that keeps ~308 built-in schemas off the startup path — then served to every consumer (MCP session server, palette, plugin surfaces) on each `list()`/`get()`.

## Problem

No live bug — issue #9569 closed a latent hazard: `toManifestEntry` returned cached schemas through `{ ...schemas.inputSchema }` under a comment promising this "protects the shared schemaCache from downstream consumers." A shallow spread only isolates top-level keys; `properties`/`items`/`$defs` stayed live references into the cache, so any future consumer normalizing a schema in place (a typical MCP-adapter move) would silently poison every subsequent read for every consumer. `buildToolOutputSchema` (`electron/services/mcp-server/tierAuth.ts`) additionally hands `entry.outputSchema` out by raw reference, so it inherits whatever isolation `toManifestEntry` provides. `[...definition.examples]` had the same flaw one level down: each `ActionExample.args` object stayed aliased to the static definition.

## Root cause

Aliasing in two flavors. First, the spread: `{ ...cached }` copies references, so a write like `copy.properties.x.type = "string"` lands directly in the cached object — empirically confirmed; a top-level-write test would never catch it, which is why the original "isolation" test suite passed. Second, the raw plugin path: `rawInputSchema`/`rawOutputSchema` were cached as the definition's live object, coupling both ways — a plugin mutating its own schema object corrupts the cache, and (worse) any freeze applied to the cache would freeze the plugin's own object as a side effect on caller data.

The PR and issue also claimed an amplifier: that Zod 4's `reused: "inline"` makes a reused sub-schema "the same physical object at every occurrence," so one nested write corrupts multiple schema positions at once. Verified FALSE at lesson-authoring time against zod 4.0.0, 4.3.6, and the installed 4.4.3: `z.toJSONSchema` unconditionally finalizes through `JSON.parse(JSON.stringify(result))` (`node_modules/zod/v4/core/to-json-schema.js`), which de-aliases shared nodes and strips cycles — sharing exists only in zod's intermediate tree, never in the returned value. The in-code comment above the `toManifestEntry` return (~line 609) still repeats the false claim; the fix stands on the shallow-spread mechanism alone. That same round-trip is, ironically, the load-bearing safety guarantee the fix relies on: it's WHY `structuredClone` on a zod-derived cache entry can never throw on cycles or non-cloneable shapes.

## Lesson

- **A shallow spread (or a non-recursive `Object.freeze`) on a served cache is aliasing, not isolation** — nested nodes stay shared with the cache. Serve `structuredClone` per read, and put the clone on the read path (`list()`/`get()`), not compile time, so #8614's lazy compilation and cold start stay untouched.
- **Zod v4's `toJSONSchema` output never physically shares nodes or cycles, regardless of `reused: "inline"`** — it finalizes via `JSON.parse(JSON.stringify(result))` (verified 4.0.0/4.3.6/4.4.3). Don't propagate the physical-sharing claim from the `toManifestEntry` comment; do rely on the round-trip as the reason `structuredClone` is guaranteed-safe on zod-derived entries.
- **Clone unconstrained third-party objects BEFORE caching and freezing.** `computeSchemas` structuredClones raw plugin schemas first, so the cache never aliases the plugin's live object and the DEV freeze can't leak frozenness into caller-owned data — a dedicated test asserts the plugin's source object stays writable after compilation.
- **Give mutable-by-accident caches a DEV-only recursive freeze with a cycle guard.** `deepFreeze` (gated on `import.meta.env.DEV`, matching the `validateActionDefinition` convention) makes any future in-place mutator throw in tests instead of silently corrupting; the `WeakSet` guard exists because raw plugin JSON may legitimately cycle, unlike zod output.
- **Pin defaults you depend on:** `target: "draft-2020-12"` is Zod 4's current default and what MCP hosts expect — pinned explicitly in `zodSchemaToJsonSchema` so a future zod default flip can't silently reshape every tool schema.
- **Mutation-isolation tests must write to a NESTED field** after a read and assert the next read is clean (`src/services/__tests__/ActionService.test.ts`); top-level-write assertions pass against the broken shallow spread and prove nothing.

## Applies when

- Touching `toManifestEntry`, `computeSchemas`, `deepFreeze`, or `schemaCache` in `src/services/ActionService.ts`, or consuming `entry.inputSchema`/`entry.outputSchema` downstream (`buildToolOutputSchema` in `electron/services/mcp-server/tierAuth.ts` returns by reference — safe only because `toManifestEntry` clones per call).
- Reviewing any cache that "protects" itself with `{ ...cached }`, `[...cached]`, or a shallow `Object.freeze` — check whether consumers can reach nested nodes.
- Deciding whether `structuredClone` is safe on a zod-derived schema, or about to cite the `reused: "inline"` same-physical-object claim (false for the returned value).
- Caching or freezing plugin-supplied / user-supplied JSON anywhere — clone before both, and guard any recursion against cycles.
- Bumping `zod` — re-verify the `JSON.parse(JSON.stringify(...))` finalize still holds (it's the safety assumption under clone-on-read) and that `draft-2020-12` remains the target.
