## Context

Terminal output data was flowing: pty-host → main process (IPC serialization) → renderer. With 30–40 concurrent terminals producing heavy AI agent output, the IPC path became the primary bottleneck, causing silent data drops when the queue filled.

A zero-copy SharedArrayBuffer ring buffer architecture (`SharedRingBuffer.ts`, `PacketFramer`, `PacketParser`) was already implemented but permanently dead because `PtyClient.getSharedBuffers()` always returned empty arrays. Root cause: Electron's `UtilityProcess` does not support SharedArrayBuffer transfer.

## Problem

Two problems interacted:

1. SharedArrayBuffer cannot be transferred to/from `UtilityProcess` in Electron — the entire high-throughput path was dead code
2. The IPC fallback still serialized every data frame through the main process, creating GC pressure and latency

## Root cause

The `UtilityProcess` constraint (no SAB support) means the SAB-based zero-copy architecture is fundamentally blocked in Electron. The correct alternative is `MessagePort` — which CAN be transferred to a `UtilityProcess` — enabling direct pty-host → renderer data flow without a main-process hop.

## Lesson

**Electron `UtilityProcess` cannot transfer SharedArrayBuffers** — this is a hard platform constraint, not a configuration issue. If you see a SAB-based ring buffer in `pty-host/` that's always returning empty arrays, it's permanently blocked.

The correct high-throughput path for `UtilityProcess` → renderer is `MessagePort`:

- Transfer a `MessagePort` to the UtilityProcess at spawn time
- Never transfer a slab-aliased Buffer's `.buffer` directly. node-pty Buffers under 4KB share an 8KB pool slab; transferring such a buffer's `ArrayBuffer` detaches the whole slab and corrupts every other Buffer aliasing it — this produced blank terminals and was reverted in PR #4639 (the naive "ArrayBuffer frames CAN be transferred" approach). Binary transfer is safe ONLY for slab-escaped "owned" buffers (byteOffset 0, whole-buffer, allocated via `new Uint8Array(...)` at the ingestion site); otherwise copy into a freshly-allocated `Uint8Array`. See `mergeChunks` in `electron/pty-host/portBatcher.ts` — it copies by default and only fast-paths a single fully-owned chunk (the owned-transfer optimization landed in #8367).
- String `"ack"` backpressure messages still flow back over the port (`electron/pty-host/handlers/connection.ts`)
- Implement watermark-based backpressure (`PortQueueManager` in `electron/pty-host/portQueue.ts`, high/low watermarks) to coordinate PTY pause/resume with port buffer state
- Keep the IPC fallback for terminals spawned before the port is established

When adding port backpressure, the `PtyPauseCoordinator` (`electron/pty-host/PtyPauseCoordinator.ts`) must support multiple concurrent pause reasons via distinct `PauseToken`s (`port-queue`, `ipc-queue`, `resource-governor`, `backpressure`) so they don't interfere — the PTY only resumes when all tokens clear.

## Applies when

- Any high-throughput data path involving `UtilityProcess` — default to MessagePort, never SAB
- Transferring binary frames over a MessagePort — never put a node-pty (or any pooled) Buffer's `.buffer` in the transfer list; copy unless the buffer is provably slab-escaped and owned (see #4639, `mergeChunks`)
- Debugging blank/corrupted terminals under heavy agent output — suspect detached slab buffers from an over-eager transfer; also check port queue watermark thresholds
- Extending `PtyPauseCoordinator` — preserve multi-reason (multi-token) pause support
