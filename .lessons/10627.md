## Context

The plugin host API (the `host` object handed to a plugin's `activate(host)`) is a Promise-based surface: methods like `postToPanel`, `setPanelBadge`, `invalidateFileDecorations`, `showToast`, `sendToActiveAgent` all return Promises so plugins can `.catch()` validation and capability errors uniformly. It's implemented twice — the in-process main-side host (originally in `PluginService.createHost`, since extracted to `electron/services/plugin/PluginHostFactory.ts`) and the out-of-process dev-worker proxy (`pluginDevWorkerHostProxy.ts`), which forwards calls to main over a parent-port `notify()`. #10627 (resolving #10617, part of the 1.0 plugin hardening under #10511) tightened this contract.

## Problem

Several Promise-returning host methods checked liveness first (`if (!isBound()) return Promise.resolve()`) and then threw **synchronously** for validation errors — e.g. `postToPanel` on a bad channel, `setPanelBadge` on a malformed badge. Because the throw fired synchronously, it escaped the Promise entirely: a plugin doing `host.postToPanel(ch, p).catch(...)` (the documented error-handling model) never saw the error, and a non-awaited call crashed the plugin instead. Some errors resolved gracefully, others threw — an inconsistent, per-method contract that's a footgun for every plugin author.

## Root cause

The trap is which methods are declared `async`. Genuinely-`async` host methods (`showToast`, `showQuickPick`, `showInputBox`, `showConfirm`, `sendToActiveAgent` in `PluginHostFactory.ts`) already convert any internal `throw` into a rejection for free — the language does it. But `postToPanel`, `invalidateFileDecorations`, and `setPanelBadge` are **not** `async`: they wrap a synchronous fire-and-forget transport call (`broadcastToRenderer` on the main side, `notify()` on the dev-worker side) and hand back `Promise.resolve()`. They can't simply be made `async` — the transport is sync and has no result to await (the dev-worker comment spells this out: "notify() is fire-and-forget/sync, so this method can't simply be `async`"). So inside these three, a bare `throw` is a real synchronous throw that bypasses the Promise. The fix was surgical: convert only those three to `return Promise.reject(new Error(...))` after the liveness guard, on **both** host implementations, leaving the already-async methods and the registration-surface `broadcastToRenderer` (which genuinely throws sync during `activate()`) alone. The liveness no-op stays a silent `Promise.resolve()` — unload is not an error.

A second, unrelated constraint was documented rather than fixed: lazy manifest-declared command handlers (`contributes.commands` resolved from `src/{id}.ts`) get **only `args`, no `host`**. `ActionHandler = (args: unknown) => unknown | Promise<unknown>` (`shared/types/plugin.ts:1281`) is structurally single-argument, and `loadManifestCommandHandler` (`PluginService.ts:1414`) invokes the default export args-only. This is not an oversight: the host is scoped to `activate()` and revoked once activation returns, long before a command is first dispatched, so there's no live host to inject. The workaround is `host.registerAction()` inside `activate()` — that closure captures the live host, and an imperative registration for the same id supersedes the lazy file (it lands in `pluginActionHandlers`, which short-circuits the lazy-load branch).

## Lesson

- **On a Promise-returning method that is NOT `async`, every error path must `return Promise.reject(new Error(...))`, never `throw`.** A sync throw from a non-async function escapes the returned Promise, so the caller's `.catch()` never fires and a non-awaited call crashes. This is invisible in tests that assert `expect(() => host.foo()).toThrow()` — such a test _passes_ on the broken behavior; assert `await expect(host.foo()).rejects.toThrow()` instead.
- **A method that can't be made `async` is the tell.** `postToPanel`/`invalidateFileDecorations`/`setPanelBadge` wrap a synchronous fire-and-forget transport (`broadcastToRenderer` / dev-worker `notify()`) and return `Promise.resolve()`, so they can't be `async` and each internal throw must be hand-converted to a reject. Genuinely-`async` siblings (`showToast`, `showQuickPick`, `sendToActiveAgent`) don't need it — the runtime rejects for them. Before "fixing" a throw, check whether the method is already `async`.
- **The two host implementations must stay in lockstep.** Any validation/liveness change to a host method in `PluginHostFactory.ts` must be mirrored in `pluginDevWorkerHostProxy.ts` (dev-worker plugins) or the contract diverges by execution context. Both were changed together here.
- **This invariant is only partially held today — `postToPanel`'s `panelId` branch still throws synchronously** (`PluginHostFactory.ts:438`, `pluginDevWorkerHostProxy.ts:423`). That branch was added later by #10618's panel-targeting feature, _after_ #10627 fixed the channel branch in the same method, regressing the reject-not-throw rule. If you touch `postToPanel`, convert the `panelId` guard to `Promise.reject` to match its own channel guard.
- **Lazy manifest command handlers can't reach `host`** (`ActionHandler` is `(args) => ...`, host revoked post-`activate()`). If a command needs host APIs, register it imperatively via `host.registerAction()` in `activate()` — that supersedes the lazy `src/{id}.ts` file for the same id. Don't send a plugin author down the manifest-declared path for a command that calls `showQuickPick`/`settings.get`.

## Applies when

- Adding or editing any `host` method in `electron/services/plugin/PluginHostFactory.ts` or `pluginDevWorkerHostProxy.ts` — decide async-vs-not, reject-don't-throw on non-async, and mirror across both files.
- Writing tests for host-API validation — use `.rejects.toThrow()`, never `expect(() => ...).toThrow()`, which green-lights a sync throw that breaks the plugin `.catch()` contract.
- Diagnosing a plugin that crashes (or whose `.catch()` never fires) when it passes a bad channel/badge/scope to a host method.
- Touching `postToPanel` — its `panelId` guard is the remaining sync-throw that violates the #10617 contract (introduced by #10618).
- Building a plugin command that needs host APIs, or advising on the manifest-`contributes.commands` vs `host.registerAction()` choice — lazy handlers get `args` only because the host is revoked after `activate()`.
