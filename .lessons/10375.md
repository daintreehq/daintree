## Context

The pty-host's hottest path forwards raw terminal output to main as `agent:output` events, feeding agent-state detection and the MCP turn-outcome classifier. #10375 (a last-mile perf batch) "cooled" three of these hot paths: capping `SemanticBufferManager` pending accumulation, throttling `ActivityMonitor`'s full-buffer ANSI-strip + pattern scan, and coalescing the per-chunk `agent:output` IPC into 50ms batches (a burst that once emitted N events now emits one). The coalescing logic, originally inline in `TerminalProcess`, now lives in the extracted `AgentOutputForwarder` (`queue()` / `flush()`, `AGENT_OUTPUT_FLUSH_INTERVAL_MS = 50`).

## Problem

Naively coalescing output would silently corrupt agent-state classification without any crash or type error. The consumer that matters is `TurnOutcomeService` (`electron/services/mcp-server/turnOutcomeLog.ts`): its `appendOutput()` subscriber appends each `agent:output` payload to a per-terminal `recentOutput` ring, and `handleTransition()` reads that ring **synchronously** the instant an FSM transition fires (active→passive, or a watchdog stuck-timeout), then `classifyTurnOutcome()` scans the trailing chars to decide the turn's outcome (`agent-stuck`, `reasoning-loop`, normal completion). If the batch holding the turn's final output is still sitting in the 50ms window when the state-changed event fires, the classifier scans a ring missing exactly the tail that explains the transition.

## Root cause

Both `agent:output` and `agent:state-changed` ride the same ordered `events` bus and forward to main through the same `PtyEventsBridge`, so main sees them in emit order. Correctness therefore reduces to one pty-host rule: the coalesced output must be emitted before the state-transition event on the same synchronous call stack. `TerminalProcess` enforces it by calling `flushAgentOutput()` immediately before every `agentStateService.handleActivityState(...)` / `updateAgentState(...)` — at both activity-state callbacks, both watchdog `onWaitingTimeout` paths, the busy re-emit, `handleAgentDetection`, `kill`/`dispose`, and `emitTerminalExited`. `AgentOutputForwarder.queue()` also flushes the _previous_ agent's pending output when the incoming `agentId` differs, so a batch never spans two identities, and a `OUTPUT_BUFFER_SIZE = 2000`-char cap forces an immediate flush so a flood never waits the full 50ms. It is invisible-until-wrong: drop any one flush and batching still "works" and output still arrives, but turn outcomes for that path silently misclassify — no type error, happy-path tests still green.

## Lesson

- **When you coalesce/batch events on a hot path, find every consumer that reads state synchronously at a related event and force-flush the batch before that event fires.** The flush-before-transition IS the entire correctness argument for the 50ms `agent:output` batching: `TurnOutcomeService.recentOutput` is read the moment `agent:state-changed` lands, so pending output must be emitted first. Both `AgentOutputForwarder` and `turnOutcomeLog.ts` encode this in comments — never delete a `flushAgentOutput()` call to "simplify".
- **Adding a new agent-state transition path in `TerminalProcess` means adding a `flushAgentOutput()` immediately before it.** There are ~8 flush sites, one per transition emitter (activity-state ×2, watchdog-timeout ×2, busy re-emit, agent-detection, kill/dispose, exit). A new transition without a preceding flush reintroduces the reordering silently.
- **A batch must never span two identities.** `AgentOutputForwarder.queue()` flushes when `pendingAgentOutputAgentId` changes, so output is never misattributed across agents sharing a terminal slot — replicate this guard in any keyed coalescer.
- **Each hot-path "cooling" knob carries its own invariant, not just a threshold.** `ActivityMonitor`'s `PATTERN_SCAN_THROTTLE_MS = 30` throttle keeps a _trailing-edge_ run so the last chunk before quiet is still scanned (drop it and the final prompt/state is missed); `SemanticBufferManager` caps `pendingSemanticData` at `PENDING_SEMANTIC_DATA_MAX_CHARS = 64*1024` at accumulation time AND slices `processedLines` before `terminal.semanticBuffer.push(...processedLines)` because spreading a 500k-line flood into `.push(...)` overflows the call-stack argument limit (its own regression test guards exactly this).
- **Batching that collapses N side-effectful calls into one must re-port every per-call side-effect.** The sibling ReviewHub change here (`handleStageFiltered`/`handleUnstageFiltered` → `git.stageFiles`/`unstageFiles` batch channels, dodging the 30-call IPC rate limiter) had to add the previously-missing `invalidateStagingDiffStatCache(cwd)` to the batch handlers in `git-write.ts`, or the batch path skipped the cache bust and the follow-up refresh served stale stats.

## Applies when

- Touching `AgentOutputForwarder`, `TerminalProcess.queueAgentOutput`/`flushAgentOutput`, or any `agent:output` batching/coalescing — verify the flush precedes every state-transition emit.
- Adding or moving an agent state transition (`handleActivityState`, `updateAgentState`, watchdog timeout, agent detection) in the pty-host — a `flushAgentOutput()` must sit immediately before it.
- Debugging wrong or missing MCP turn-outcome records (`agent-stuck` / `reasoning-loop` misfires or no-fires) — check whether the explanatory output tail reached `TurnOutcomeService.recentOutput` before `handleTransition` ran.
- Tuning `ActivityMonitor.PATTERN_SCAN_THROTTLE_MS` or `SemanticBufferManager.PENDING_SEMANTIC_DATA_MAX_CHARS` — preserve the trailing-edge scan and the pre-`push` line slice, not just the numeric caps.
- Collapsing N per-item IPC calls / git spawns into a batch channel — audit the single-item handler for side-effects (cache invalidation, rate-limit accounting) the batch path must replicate.
