## Context

The plugin 1.0 freeze wave (#10459) audited every contribution point before freezing the manifest/IPC contract. This arc lands three findings, all flowing through `PluginService.dispatchHandler` and the `plugin:invoke` handler (`electron/ipc/handlers/plugin.ts`): #10482 (trust/isolation — the `plugin:invoke` ownership boundary), #10478 (schema validates fields the runtime ignores — the agent `detection` block), #10483 (observability — handler failures never reaching the audit pipeline).

## Problem

Three contract holes that all "worked" in the happy path. (1) `plugin:invoke` verified the sender frame was a trusted `app://daintree` renderer but never that the caller owned the `pluginId` — any plugin surface could invoke another plugin's channels by passing an arbitrary id. (2) `AgentContribution.detection` was heavily validated at parse time but `contributionToAgentConfig()` dropped it before runtime (`DetectionResult.agentType` is `BuiltInAgentId | undefined`) — declare detection, pass validation, get nothing. (3) Plugin handler throws were only `console.error`'d; two `TODO(#9232)` stubs left non-IPC callers with no durable failure trail.

## Root cause

The isolation hole is architectural: **every plugin renders in a single shared `app://daintree` WebContents in one JS realm**, so the host cannot bind an invocation to a plugin by sender identity — a `WebContents→pluginId` registry (proposed in #10462) can't tell two same-realm plugins apart. The only achievable guarantee: a sender may only address plugins the host has loaded. #10482 enforces `!this.plugins.has(pluginId) → throw PluginInvokeOwnershipError` inside `dispatchHandler` — the single chokepoint every invoke flows through, deliberately _not_ the IPC handler, so non-IPC callers (dev-worker, agent automation) are covered. It throws before activation, so impersonating an unloaded id never runs plugin code.

The `detection` field was a **frozen-promise violation** — validated but never consumed. #10478 cut it, relying on `.strict()` so a declared block now fails to load with `unrecognized_keys` instead of silently doing nothing. This cut was later _reversed_: #10587 (`6108f4d11`, two days after) re-added `detection` and wired it — mirroring the plugin-agent registry into the pty-host (`set-plugin-agent-registry`) so `getEffectiveAgentConfig` resolves plugin patterns in the process running the activity monitor. So `electron/schemas/plugin.ts` has `detection` again today; the durable lesson is the disposition rule (cut-or-wire, never freeze-as-noop), not the object-level state.

The audit fix (#10483) then risked double-counting — `dispatchHandler` and the outer `plugin:invoke` catch both audit — resolved by a `Symbol` marker (`pluginAuditMarker.ts`); the frozen-error gotcha is captured below.

## Lesson

- **When one realm hosts many principals, sender-identity isolation is impossible — scope the guarantee to what the realm can enforce, and say so in the error type.** `plugin:invoke` can only guarantee "the addressed plugin is loaded," not "the sender owns it." Don't reach for a `WebContents→pluginId` map; it can't distinguish same-realm callers. Document the achievable guarantee at the throw site (`PluginInvokeOwnershipError`) so the next agent doesn't mistake it for real isolation.
- **Put ownership/permission checks at the single dispatch chokepoint (`dispatchHandler`), not at one entry (the IPC handler).** Dev-worker channels and agent/recipe automation also reach `dispatchHandler`; a guard on the IPC entry leaks, one at the chokepoint covers every present and future caller.
- **A schema field that validates but is never consumed is a frozen-promise violation — cut it or wire it before freeze, never freeze a validated no-op.** With `.strict()`, cutting converts a silent no-op into a loud `unrecognized_keys` load failure. When you _do_ wire such a field, wire it end-to-end into the consuming process (here the pty-host activity monitor), not just parse-time. Don't blind find-replace: built-in `AgentConfig.detection` (the live PTY matcher) is a separate system, untouched.
- **When you tag a rethrown error to coordinate two catch boundaries, the tag must be best-effort, and split ownership by boundary.** A frozen/sealed error (or a thrown string/number/null) can't carry a `Symbol` — wrap the write in `try/catch` and degrade to a duplicate audit record, never a lost error. Inner `dispatchHandler` owns handler _throws_; the outer IPC boundary owns failures that never reach a handler (untrusted sender, schema/permission/no-handler), classifying an ownership rejection `"restricted"` not `"error"`.

## Applies when

- Adding any sender/ownership/permission check to a plugin IPC boundary — guard the `dispatchHandler` chokepoint; all plugins share one `app://daintree` realm, so per-sender binding is impossible.
- Freezing or reviewing a plugin manifest/schema field — confirm it is consumed at runtime (`contributionToAgentConfig`, the pty-host effective registry); a validated-but-dropped field is a cut-or-wire decision, and `.strict()` makes the cut fail loudly.
- Tagging a rethrown error with a Symbol/property to coordinate nested try/catch (`pluginAuditMarker.ts`) — guard the write, frozen/primitive errors reject it; the `"restricted"` vs `"error"` split at the `plugin:invoke` catch is load-bearing.
- Researching whether plugin agent `detection` works — cut (#10478) then re-added and wired into the pty-host (#10587 / `6108f4d11`); the schema field exists today.
