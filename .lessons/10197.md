## Context

Daintree's internal event bus is `export const events = new TypedEventBus()` in `electron/services/events.ts` — a module-level singleton, so each OS process (main, and every UtilityProcess: workspace-host, pty-host, plugin workers) instantiates its own isolated bus when it loads the module graph. `PullRequestService` (`electron/services/PullRequestService.ts`) runs inside the workspace-host UtilityProcess. When its PR-detection circuit breaker tripped after `MAX_CONSECUTIVE_ERRORS`, `handleError()` did `events.emit("ui:notify", { type: "warning", message: "PR detection paused…" })` intending a user toast, right beside the working `this.setDetectionState(true)`.

## Problem

The `ui:notify` emit was dead code that produced no toast and no inbox entry — but read as if it did, implying a user-facing notification that never existed (issue #9976). Anyone auditing the circuit-breaker path would assume the user gets told PR detection paused; they don't get told by this line.

## Root cause

Event-emission APIs are importable everywhere but consumed only in specific processes. The bus is process-local, and the only broad `ui:notify` subscriber is `EventBuffer`, `.start()`ed once **per-window in the main process** (`electron/window/perWindowInit.ts:341`, subscribing to `ALL_EVENT_TYPES`). No `EventBuffer` — and no other `ui:notify` listener — exists in the workspace-host, so the emit had zero subscribers and vanished. A second, deeper trap: even in the main process `EventBuffer` is a **recorder for the event inspector** (`onRecord` → `eventInspector.ts` → `webContents.send(CHANNELS.EVENT_INSPECTOR_EVENT_BATCH)`), not a toast dispatcher. The real toast system is the renderer's `notify()` (`src/lib/notify.ts`), reached over IPC — nothing on the `events.emit("ui:notify")` path ever renders a toast in ANY process. The event name is misleading. The correct user signal already existed on the right path: `setDetectionState(true)` emits the domain event `sys:pr:detection-state`, which `PRIntegrationService` (workspace-host) subscribes to and relays via callback over the worktree port to the renderer's `PRDetectionPausedIndicator` — the ambient tier the runtime-signal rules mandate for an auto-recovering state. #10197 removed the inert emit and asserted in the unit test that `ui:notify` fires zero times on breaker trip. The arc's second change — adding `timestamp: Date.now()` to a sibling `ui:notify` emit in `PreAgentSnapshotService` to satisfy `EVENT_META["ui:notify"].requiresTimestamp` (which `EventBuffer.validatePayload` `console.warn`s on) — is now moot: `PreAgentSnapshotService` was fully removed 2026-07-08 (`9cae70cce`).

## Lesson

- **Before `events.emit(...)` from any service, know which process it runs in and whether that process has a subscriber.** The bus is a per-process module singleton; a UtilityProcess (workspace-host, pty-host, plugin worker) emitting into it only does something if a listener was registered _in that same process_. Emits to a subscriber-less event are silent no-ops that leave code implying UX that doesn't exist.
- **`ui:notify` on the internal `events` bus never produces a toast — not even in main.** Its only broad subscriber is `EventBuffer`, which merely _records_ events for the event inspector. User-facing notifications come from the renderer's `notify()` (`src/lib/notify.ts`). If a main/utility-process service needs to tell the user something, route a domain event or IPC to the renderer and call `notify()` there; do not `events.emit("ui:notify")` and assume a toast.
- **Cross-process user signals go through an explicit relay, not the shared bus.** The workspace-host surfaces state to the renderer only for events `PRIntegrationService` explicitly subscribes-and-forwards over the worktree port (`sys:pr:detection-state`, `sys:issue:detected`, `sys:pr:cleared`, …). If your event isn't in that relay list, it does not leave the process.
- **`EVENT_META[type].requiresTimestamp` is validated only where `EventBuffer` records the event (main process).** A missing `timestamp` on a `ui:notify` triggers `EventBuffer.validatePayload`'s `console.warn` in main, but produces no warning from a workspace-host emit — nothing records it there. A quiet emit is not a correct one.
- **An auto-recovering / retrying state belongs at the ambient tier, not a toast** (runtime-signal rules) — `PRDetectionPausedIndicator` fed by `sys:pr:detection-state` is the right surface; a `ui:notify` toast would have been the wrong tier even if it had worked.

## Applies when

- Adding any `events.emit("ui:notify", …)` (or other UI event) from a service in `electron/services/` or `electron/workspace-host/` / `electron/pty-host/` — first confirm the emitting process has a consumer, and prefer the renderer's `notify()` for actual toasts.
- Diagnosing a "notification that never shows" where the emit call is clearly present and correctly shaped — check whether the emitter's process even has a subscriber for that event on its process-local bus.
- Wiring a new cross-process signal from the workspace-host or pty-host to the renderer — route a `sys:*` domain event through the relevant relay (`PRIntegrationService`-style port forwarding), never the shared `events` bus directly.
- Touching `PullRequestService.handleError()`'s circuit breaker, `EventBuffer.start()`/`validatePayload`, or `EVENT_META` `requiresTimestamp`/`requiresContext` validation.
- Reviewing code that assumes `events.emit("ui:notify")` renders a toast — it only ever fed the event inspector, and only in main.
