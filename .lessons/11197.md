## Context

`usePulseStore` (`src/store/pulseStore.ts`) backs the Project Pulse card and its collapsed strip with a per-worktree git-log scan (`fetchPulse` dispatches the `git.getProjectPulse` action); both `ProjectPulseCard` and the newly-added `ProjectPulseStrip` mount-fetch effect need to know "has this worktree ever been fetched" so they fetch once and leave the store's own retry/dedupe logic alone, and #11197 added a mount-fetch effect to `ProjectPulseStrip` (previously it only fetched when the user expanded it, per #11194) by copying the guard already used in `ProjectPulseCard`.

## Problem

Copying the existing guard also copied a latent bug that had shipped in `ProjectPulseCard` for some time: a worktree with a git repo that has never had a commit would, once its card was opened, keep re-dispatching `git.getProjectPulse` in a tight loop against git and IPC, forever, with no user-visible error and no backoff, and it only reproduces on a genuinely commit-less repo, which is rare, so it stayed latent until #11197's author traced the mount-fetch guard while adding the same pattern to a second, always-mounted component (the strip sits on the empty grid, so its version of the bug would fire far more often).

## Root cause

`pulseStore`'s `errors` map is `Map<string, string | null>` and `getError` returns `string | null | undefined` — three distinct states, not two: `undefined` (key absent) means never fetched, `null` means a fetch settled and `getUserFriendlyError` classified it as the deliberate "no commits yet" outcome (see the `noCommitsSignals` branch, `pulseStore.ts:44-53`), and a string means a real error the store already self-retries with exponential backoff (`PULSE_MAX_RETRIES`, `RETRY_BASE_DELAY`); both components guarded their mount-fetch effect with `if (!pulse && !isLoading && !error)`, and `!error` is true for both `undefined` and `null`, so it cannot distinguish "never tried" from "tried and settled on nothing."

On a no-commits repo, `fetchPulse` resolves with `pulses` untouched (so `pulse` stays `undefined`), `isLoading` set back to `false`, and `errors` set to `null` — the exact combination the guard requires to fire again; each re-fire flips `isLoading` `false → true → false`, which is in the effect's dependency array, so the effect re-runs, the guard re-passes, and it fetches again — an effect self-sustaining its own trigger condition purely through the store's success path, with no exception and no visible error to make it obvious in the UI. The fix (`error === undefined`) treats only the truly-never-fetched state as fetchable; a settled `null` is now recognized as "already attempted, nothing to show" and left alone, matching how the string-error case is already left to the store's own retry timer.

## Lesson

- **A tri-state sentinel (`undefined`/`null`/value or `undefined`/`null`/string) can never be safely narrowed with a truthiness check** — `!x` collapses two of the three states into one. If a field's `undefined` and `null` mean different things ("never happened" vs. "happened, resolved to nothing"), branch on `x === undefined` explicitly, not `!x`.
- **A mount-fetch guard that includes its own async result in its dependency array is a loop waiting for a state that satisfies it twice.** Before shipping `useEffect(() => { if (guard) fetch(); }, [...guard deps])`, walk every value the fetch itself can settle into and confirm none of them re-satisfy the same guard — here the "no commits" resolution silently reproduced the "never fetched" guard.
- **Copying a guard from a sibling component copies its bugs too.** `ProjectPulseStrip`'s effect was modeled on `ProjectPulseCard`'s pre-existing (already-shipped) guard; #11197 fixed both in the same PR specifically because tracing the new copy surfaced the bug in the original. When porting a data-fetch pattern between components, re-derive the guard from the store's actual state contract instead of trusting the existing call site.
- **An always-mounted component changes a latent bug's blast radius.** The same `!error` bug existed in `ProjectPulseCard` (only fetches when expanded) with low practical impact; adding an equivalent effect to `ProjectPulseStrip` (always mounted on the empty grid for the active worktree) would have made the infinite-loop case fire on every landing in an empty repo, which is what made it worth fixing instead of copying forward.

## Applies when

- Adding a fetch-on-mount / fetch-once effect against any Zustand store whose error or result field can be `undefined`, `null`, and a populated value — grep the store for `Map<string, string | null>` or a getter typed `... | null | undefined` before writing the guard.
- Reviewing any `if (!pulse && !isLoading && !error)`-shaped guard — check what the store sets `error` to on a successful-but-empty resolution, not just on a thrown error.
- Diagnosing repeated/looping calls to an action or IPC channel (e.g. `git.getProjectPulse`) with no thrown error visible in logs — suspect a mount-guard effect re-triggering on its own settled state rather than a real retry policy.
- Porting a data-fetch guard pattern from one component to a sibling (e.g. a collapsed/summary view gaining the same fetch logic as its expanded counterpart) — re-verify the guard against the store's actual type, don't just copy the conditional.
