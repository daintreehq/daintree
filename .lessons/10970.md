## Context

Startup-perf work (#10970) found that Rolldown's automatic chunking scattered the entry's static closure into 80 eager chunks (151 across the full first-render closure), each a separate `app://` request the main process has to answer during the busiest phase of boot. A new `boot` code-splitting group in `vite.config.ts` (`tags: ["$initial"]`, `priority: 1` so every vendor group claims its `node_modules` slice first, `maxSize: 400_000`) merges that scattered tail into a handful of larger chunks, cutting entry-eager chunks from 80 to 21 and the first-render closure from 151 to 96.

## Problem

Merging the chunks didn't just cut request count — it broke boot. `KeybindingService`'s module-scope singleton (`export const keybindingService = new KeybindingService()` at `src/services/KeybindingService.ts:723`) has a constructor that loops over `DEFAULT_KEYBINDINGS` (imported from `./defaultKeybindings`) at line 56, immediately at construction time. Under Rolldown's automatic chunking this had always worked; under the new merged `boot` chunk it didn't, because merging changed which module's top-level code ran first.

## Root cause

Nothing in the code enforced that `defaultKeybindings.ts` evaluate before `KeybindingService.ts` — it worked only because Rolldown's automatic per-module-set chunking happened to place them in an order where the definer ran first. That is a latent evaluation-order dependency: it typechecks, it passes every dev and vitest run (dev serves unbundled ESM in source order), and it looks like ordinary code. The new `boot` group changes the grouping rule from "automatic per-share-set boundaries" to "everything statically reachable from an entry that isn't already claimed by a vendor group" (`test` in vite.config.ts excludes virtual `\0`-modules, `.html` proxies, and `src/main.tsx` itself, keeps everything else; `priority: 1` so vendor groups claim `node_modules` first), and that regrouping reordered which module's top-level statements ran first — the singleton read `DEFAULT_KEYBINDINGS` before its defining module had evaluated. The fix was not to touch the singleton or its constructor: it was `output.strictExecutionOrder: true` in `vite.config.ts`, which makes Rolldown preserve the exact topological module-evaluation order across chunk boundaries regardless of how modules are physically grouped into files. It costs roughly 7% gzip growth on the affected chunks (ordering wrapper overhead), accepted because the request-count win dominated in the new `perf:launch-ab` A/B benchmark (cold first-interactive -25%, warm -8%).

## Lesson

- **A module-scope singleton whose constructor eagerly reads another module's exported value (`export const x = new XService()`, where `XService`'s constructor loops over an imported array/const) is an unenforced evaluation-order dependency**, even though it typechecks and passes every test today — the "it happens to work" order comes from the bundler's automatic chunk topology, not from anything guaranteed by the language or the type system.
- **Changing chunk _grouping_ (which modules land in the same physical file) is not perf-neutral — it can silently change evaluation _order_.** Treat a "merge these chunks for fewer requests" change with the same eval-order scrutiny as a refactor that reorders imports, especially for any entry/boot-critical code-splitting group.
- **`output.strictExecutionOrder: true` (the Rolldown/Vite build option) is the correct fix for this exact class of bug** — it forces exact topological module-eval order across chunk boundaries independent of physical chunk layout, so reach for it when a _chunking_ change (not a source change) exposes an eval-order bug, rather than reworking the singleton.
- **A boot-time `undefined`/TDZ-shaped error that reproduces only in a packaged build, never dev or vitest, points at chunk eval order, not app logic** — dev serves unbundled ESM in source order, so this bug class is invisible until you build.
- **Boot-critical external classic `<script src>` tags compete with the modulepreload storm for the `app://` protocol handler.** The same PR inlined `skeleton-ready.js`/`skeleton-stuck.js` (fire the `APP_SKELETON_PARSED` IPC gating `win.show()`) into `index.html` with sha256 CSP hashes wired through both the meta tag (`cspTransformPlugin`) and the header sidecar (`hostImportMapPlugin`'s `closeBundle`) — future boot-gate scripts should default to inline, not external-plus-`defer`.
- **A "safe when ambiguous" boot-time boolean must default to the expensive-but-correct path.** `wasStoreFreshAtBoot()` in `electron/store.ts` defaults `storeWasFreshAtBoot = false`, so in-memory-fallback and unresolved-config-path cases still replay the full migration chain instead of risking a wrong fast-path skip — copy this default-to-safe shape for any "can I skip the expensive boot work" flag.

## Applies when

- Adding, removing, or re-grouping a Rolldown/Vite `output.advancedChunks` / `codeSplitting.groups` entry, or touching the `boot` group or `strictExecutionOrder` in `vite.config.ts`.
- Reviewing any `export const x = new XService()` module-scope singleton whose constructor reads another module's exports at construction time — ask what guarantees it runs after the definer, because chunk topology is not that guarantee.
- Debugging a boot-time `undefined`/TDZ-style error that only reproduces in a packaged build (never dev, never vitest).
- Touching boot-gate scripts (`public/skeleton-*.js`) or the CSP hash plumbing (`cspTransformPlugin`, `hostImportMapPlugin`, `importmap-meta.json`) in `vite.config.ts`.
- Adding a new "skip expensive boot-time work when state X holds" fast path (migrations, cache warm, etc.) — verify the ambiguous/fallback branch defaults to the slow-but-correct path, never the fast one.
