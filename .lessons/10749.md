## Context

Issue #10744 found that backgrounded terminals ran the full per-chunk analysis pipeline (ActivityMonitor regex bank, headless xterm VT write, forensics/semantic buffers) at the same cost as foreground ones, so a noisy agent in a hidden project cost real host CPU regardless of visibility. #10747 answered this by adding a coalescing queue to `TerminalProcess`: backgrounded chunks were pushed onto `_backgroundChunkQueue` and the whole analysis pipeline deferred onto a self-rearming drain timer (`_armBackgroundDrain` / `_onBackgroundDrainTimer`), batching several PTY chunks into one `_runPtyPipeline` call to cut parse frequency roughly 20x.

## Problem

Within 12 hours of #10747 merging, every agent terminal in a backgrounded project started showing "waiting" within ~8s even while actively working — background monitoring looked broken. The misleading part: the per-chunk OSC 9;4 heartbeat tap was deliberately kept live (for the worktree dashboard), so it looked like that channel should have covered this, but OSC 9;4 is only emitted by Claude Code ≥2.0.56 — Gemini, Codex, older Claude, and plain shells emit nothing there, so it never protected the general case.

## Root cause

`_armBackgroundDrain` recomputed `_backgroundDrainDeadline = Date.now() + interval` on every incoming chunk — a classic soft, self-rearming debounce deadline. An agent producing continuous output (chunks arriving faster than the drain interval, e.g. 500ms) pushes that deadline forward forever, so `_onBackgroundDrainTimer`'s `remaining > 0` branch always rescheduled and the queue never drained short of the 256KB `COALESCE_MAX_BYTES` byte cap. Because `activityMonitor.onData` and the headless VT write only ran on drain, `lastActivityTimestamp` (refreshed only when the polled headless viewport content actually changed) went stale, and ActivityMonitor's `IDLE_DEBOUNCE_MS` gate (`now - lastActivityTimestamp >= IDLE_DEBOUNCE_MS`, 8s for agent terminals — still live at `electron/services/ActivityMonitor.ts:314`) fired the busy→idle transition, which `shared/utils/agentFsm.ts` maps to `working → waiting`.

#10749 fixed it with a hard, independent ceiling: `COALESCE_MAX_DEFER_MS = 1000`, tracked via `_backgroundOldestQueuedAt` (stamped when the queue goes empty→nonempty, reset on every drain/cancel), reschedule became `min(remaining, cap - deferredFor)` so a drain is forced at least once per second regardless of input density. Two tempting shortcuts were explicitly rejected in the PR body: refreshing liveness on every raw chunk (unfiltered bytes include cosmetic redraws, CPR/DSR replies, and OSC titles that `stripIdleTerminalSequences` in `electron/services/pty/IdleSequenceFilter.ts` exists specifically to discard — this flips the bug to falsely-"working" instead), and backing the idle gate with `terminal.lastOutputTime` instead of the analysis-derived timestamp (same unfiltered-bytes problem).

The whole subsystem was short-lived: #10811 (commit `eb9cd64a7`, merged 2026-06-27, 3 days after #10749) deleted `_backgroundChunkQueue`, `_armBackgroundDrain`, `COALESCE_MAX_DEFER_MS`, and every related field wholesale, together with per-terminal hibernation and wake/resync. That PR's own rationale: the suspend/defer model was the root cause of a worse bug class — recurring agent-TUI corruption across OpenCode, Codex, Gemini, and Claude (#10805, #10807) — for a saving of only ~0.1-1MB per backgrounded pane. `PtyDataPipeline.ts` now runs `runPipeline` unconditionally on every chunk regardless of activity tier, and `setActivityMonitorTier` only adjusts the headless poll cadence.

## Lesson

- **A self-rearming soft deadline (`deadline = now + interval`, recomputed on every event) never fires under input denser than the interval.** Pair it with a hard ceiling tracked from when the batch _started_ (`_backgroundOldestQueuedAt`), not from the last event, and reschedule with `min(remaining, cap - deferredFor)` — the concrete Daintree shape of what lodash calls `maxWait`. Any coalescing/debounce timer in this codebase without one has this exact starvation bug.
- **Never use raw, unfiltered per-chunk byte arrival as an agent-liveness proxy.** Cosmetic redraws, CPR/DSR replies, and OSC titles are exactly what `stripIdleTerminalSequences` exists to strip; refreshing liveness on them just flips which direction the bug points (false-"working" instead of false-"waiting").
- **A per-agent heartbeat is not a substitute for the general activity signal**, even when it's already wired and looks like the quick fix — OSC 9;4 only covers Claude Code ≥2.0.56, so leaning on it "since it's there" silently drops every other supported agent CLI.
- **Weigh new backgrounded/hidden-terminal special-casing against Daintree's own track record.** This exact class of idea (defer or suspend analysis work for terminals you can't see) was tried twice — hibernation, then coalescing — and both were reverted wholesale in #10811 for ~0.1-1MB/terminal against real correctness cost. The bar for reintroducing it is much higher than "it saves a little memory."
- **Verify before reusing**: `_backgroundChunkQueue`, `_armBackgroundDrain`, `COALESCE_MAX_DEFER_MS`, and `COALESCE_MAX_BYTES` no longer exist in `TerminalProcess.ts` — the mechanism this lesson documents was deleted three days after it shipped.

## Applies when

- Writing or reviewing any batching/coalescing/debounce timer that defers work in response to a stream of events — check for a hard max-defer ceiling independent of the soft reschedule-on-activity deadline.
- Diagnosing an agent that flips `working → waiting` while output is visibly still flowing — check `IDLE_DEBOUNCE_MS` in `electron/services/ActivityMonitor.ts` for anything upstream starving `lastActivityTimestamp`.
- Proposing to special-case backgrounded, hidden, or unfocused terminals to save memory or CPU — read #10811's revert rationale first; this idea has a track record of net-negative here.
- Touching `PtyDataPipeline.ts` or `TerminalProcess.setActivityMonitorTier`/`handlePtyData` and assuming background terminals get deferred handling — as of #10811 they don't; every chunk streams live through `runPipeline` regardless of tier.
- Reviewing any self-rearming `setTimeout` (deadline recalculated on each call) anywhere in the codebase for starvation risk under sustained input.
