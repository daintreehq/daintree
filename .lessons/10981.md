## Context

#10981 added a main-process-driven memory purge for cached (backgrounded, CPU-throttled) project views: `schedulePurge` fires `purgeMemoryWebContents` (`electron/utils/webContentsLifecycle.ts`) 20s after a view is cached and every 60s after that, cancelled the instant the view reactivates. `schedulePurge` lived inline in `ProjectViewManager.ts` at PR time; the #11004 oversized-file split later extracted it into `electron/window/ProjectViewLifecycleController.ts` (`deactivateEntry` → `schedulePurge`), so grep the controller file, not `ProjectViewManager.ts`, for the current call site. It's validated against the kitchen-sink memory A/B harness from #10973 (`e2e/full/resilience/memory-kitchen-sink.spec.ts`), which runs N full app lifecycles per arm and reports RSS/footprint means. Cached views run CPU-throttled (`CACHED_VIEW_CPU_THROTTLE_RATE = 4` in the same file) via `throttleCpuWebContents`, which is why the purge has to be driven from main rather than relying on a renderer-side idle callback.

## Problem

Two unrelated traps surfaced while building and validating this one feature. First, an early implementation reached for the obviously-named "nuke everything" CDP command and it reproducibly crashed the app — but only for cached views, and only under throttling, so it looked like a purge-timing bug rather than the command itself. Second, once the feature worked, the benchmark's headline memory number bounced by roughly a gigabyte between supposedly-identical baseline runs, which is bigger than any real win the PR produced — trusting it would have either buried a genuine improvement or manufactured a fake one depending on which run happened to land as "baseline."

## Root cause

`Memory.forciblyPurgeJavaScriptMemory` reproducibly SIGSEGVs a CPU-throttled, hidden `WebContentsView` on Electron 42 / Chromium 148 — exit code 11, roughly 200ms after the command lands, isolated and confirmed in an A/B probe (three short runs, command present vs. absent). It's the CDP command that sounds correct for "purge memory aggressively," and it isn't documented as unsafe anywhere Daintree would see it; the failure only shows up once you combine two conditions the happy-path smoke test doesn't hit together (hidden + throttled). The replacement this PR shipped was `Memory.simulatePressureNotification({ level: "critical" })` followed by `HeapProfiler.enable` / `collectGarbage` / `disable`, on the reasoning that the pressure notification is the same `NotifyMemoryPressure(CRITICAL)` Blink's own `MemoryPurgeManager` fires after backgrounding.

**Corrected 2026-09-03 — the pressure half never worked and has been removed.** `Memory.simulatePressureNotification` is not per-target despite riding a page target's debugger session: `MemoryHandler::SimulatePressureNotification` raises the level in the _browser_ process, `BrowserChildProcessHostImpl::OnMemoryPressure` forwards it off-Android only to the GPU process and the network service, and `RenderProcessHostImpl` forwards nothing to renderers at all. It never touched the cached renderer's Blink caches. What it did reach was `GpuChannelManager::OnReleaseMemory` → `SharedContextState::PurgeMemory` — Ganesh `purgeUnlockedResources` on the _shared_ GrDirectContext that every project view rasterises its DOM text through — fired 20s after each view was cached and every 60s per cached view thereafter. `purgeMemoryWebContents` now sends the `HeapProfiler` sequence alone, which is genuinely target-scoped.

Separately, on macOS, Chromium's GPU process holds "purgeable" IOSurface memory (tile/SharedImage caches, decoded-image and compositor backing stores) that the OS reclaims and re-grants opportunistically, independent of anything the app does. That swung the harness's aggregate `appFootprintKb` metric — `main + renderer + utility + gpu + crashpad` footprint summed in `takeSample()` — between roughly 0.8GB and 1.8GB across identical runs (measured baseline stddev ±573MB), which swamped every real signal the PR was trying to measure. The harness's per-process-class breakdown (`footprintByClass` / `rssByClass`, both keyed by `ProcessClass` with a dedicated `"gpu"` bucket) stayed stable across the same runs, because GPU noise is isolated in its own bucket instead of being summed into one number. The PR's own results table reports only per-class metrics (app RSS, utility footprint, pty-host working set, renderer footprint, renderer JS heap) — `appFootprintKb` doesn't appear in it at all.

## Lesson

- **Never call `Memory.forciblyPurgeJavaScriptMemory` on a throttled or hidden `WebContentsView`.** It's a SIGSEGV on Electron 42 / Chromium 148 (confirmed exit code 11). A unit test in `webContentsLifecycle.test.ts` asserts it's never sent, but that only guards the existing call site — it won't stop someone adding a new CDP purge call elsewhere and reaching for the same wrong command.
- **For any main-driven memory reclaim on a backgrounded view, `HeapProfiler.collectGarbage` is the whole toolbox.** There is no CDP command that drops a specific renderer's Blink caches from main: `Memory.simulatePressureNotification` looks per-target because it rides that target's debugger session, but it is raised in the browser process and forwarded only to the GPU and network processes. Blink's own `MemoryPurgeManager` fires on freeze, so on desktop the freeze path — not a CDP command — is what reaches renderer caches.
- **Verify which process a CDP command lands in before believing a per-target claim.** The debugger session you send it on is not evidence of scope. Reading `content/browser/devtools/protocol/*_handler.cc` for the command takes minutes and would have caught this at review time; instead the wrong claim sat in a doc comment for two months while the command purged the shared GPU raster context several times a minute.
- **On macOS, never trust an aggregate cross-process footprint number for a memory A/B test.** The GPU process's purgeable IOSurface memory can swing ~1GB between identical runs — read `footprintByClass` / `rssByClass` per `ProcessClass` in `memory-kitchen-sink.spec.ts` instead, and treat the `"gpu"` bucket as the noisy one to discount, not the whole sum. Postscript: some of that "OS noise" was self-inflicted — the pressure notification this PR added was purging the GPU process on a per-cached-view timer during the very runs whose GPU bucket looked unusably noisy. Noise that correlates with your own timers is a signal you have mis-attributed, so check what the app is doing to a process before writing its variance off as environmental.
- **A crash that only reproduces under two combined conditions (hidden AND throttled) will not show up in an ordinary manual check** — it needs an isolated A/B probe (run with the suspect command, run without) to attribute correctly, exactly as done here in three short probe runs before the real benchmark.

## Applies when

- Adding or modifying any CDP-based memory/GC command against an Electron `WebContents` or `WebContentsView`, especially one that's cached/backgrounded/CPU-throttled (`throttleCpuWebContents`, `ProjectViewManager` cached-view paths).
- Seeing an Electron utility/renderer process die with exit code 11 (SIGSEGV) around a memory-purge or GC-forcing call, particularly on a hidden or throttled view.
- Running or extending `e2e/full/resilience/memory-kitchen-sink.spec.ts` (or any new memory A/B harness) on macOS and seeing a headline metric swing between runs that don't otherwise differ.
- Reviewing a memory-optimization PR whose evidence is a single aggregate RSS/footprint number rather than a per-process-class breakdown — ask for the breakdown before trusting the delta.
- Designing any new steady-state memory reclaim path for cached/background Electron views — check whether the target is CPU-throttled first, since that's what rules out renderer-side `requestIdleCallback` approaches and forces a main-process CDP path.
