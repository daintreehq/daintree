## Context

`daintree-plugin dev` symlinks a plugin dir and writes a `.dev-marker`; #10340 (#9304) made those plugins hot-reload on every `dist/index.js` rebuild and let built-in plugins toggle enable/disable live without an app restart. Before this, `PluginService` loaded every plugin in-process via dynamic `import()` and disabling was persist-only. The PR added `PluginDevWorkerHost` (a `utilityProcess.fork` lifecycle modeled on `WorkspaceHostProcess`) and made `setEnabled` async.

## Problem

The naive hot-reload — unimport the module and re-import the rebuilt bundle in the same process — leaks: module-scope state accumulates across reloads (Vite #14438). With the worker approach, a quieter failure appears: a plugin whose `activate()` rejects, or whose `await import(bundleUrl)` fails (arch mismatch, bad rebuild), silently corrupts instead of reloading — the worker never posts `ready` and the reload never completes.

## Root cause

Two platform/version traps combine. **(1) Node ESM has no module-cache eviction API.** `import()` is URL-keyed and permanent, so any unimport+reimport loop re-runs new code while keeping old module-scope state alive (Vite #14438). The robust fix makes the OS process the cache boundary: run the plugin inside `utilityProcess.fork` and kill+respawn the worker per rebuild — process death IS the eviction (`PluginDevWorkerHost` watches `dist/index.js`, debounces 200ms, then `reload()` kills and re-forks). This is also why live enable/disable is built-in-only: a built-in re-runs its immutable bundled `activate()`, but a user plugin's on-disk code changes between toggles with no eviction API, so user plugins stay persist-only.

**(2) Electron 37+ (incl. 42) only WARNS on `unhandledRejection`/`uncaughtException` in utility processes — it does not crash them.** A worker with a throwing `activate()` or a failed dynamic import stays alive without ever posting `ready`, so `waitForReady()` hangs forever. The worker bootstrap must install its own `process.on(...)` guards that `setImmediate(() => process.exit(1))` — the delay lets Mojo IPC flush the posted error event first — converting the silent hang into an observable exit the parent's `exit` handler can supervise. Factored into `installBootstrapErrorGuard` (`electron/utils/bootstrapErrorGuard.ts`), shared by `pty-host-bootstrap.ts` and `workspace-host-bootstrap.ts`.

## Lesson

- **You cannot hot-reload an ESM module in place** — there is no `import()` cache eviction, so unimport+reimport leaks module-scope state (Vite #14438). Make the process the reload boundary: `utilityProcess.fork`, watch the bundle, kill+respawn per rebuild — a fresh process is a clean module graph.
- **In an Electron utility process, install your own `unhandledRejection`/`uncaughtException` → `process.exit(1)` guard** around the dynamic `import()` that loads your host module, or an async failure leaves the process alive-but-dead and `waitForReady()` hanging. `setImmediate` before exit so Mojo flushes the error event; reuse `installBootstrapErrorGuard`, and drop its returned cleanup once the host imports — the host installs its own handlers, so leaving the bootstrap guard on double-reports later crashes.
- **An intentional reload is NOT a crash.** `reload()` clears the crash-loop window (`crashTimestamps = []`) BEFORE killing, so rapid dev saves never trip the 3-in-30min cap (`CRASH_THRESHOLD` / `CRASH_WINDOW_MS`); only unintended exits accumulate. A fork failure is a hard non-start, not a crash-loop — don't emit `crash-loop` on it, or the bridge writes a second racy provenance entry over the real `loadError`.
- **Serialize live enable/disable per id via a promise chain** (`enableTransitions: Map<id, Promise>`), or a rapid disable→enable→disable interleaves mutations to `plugins` / `disabledPlugins` / `reservedNames`. In `_applyBuiltinToggle`'s re-enable path, release ONLY the name reservation up front but keep the `disabledPlugins` entry across the async `loadPlugin`, so a concurrent `setEnabled` still resolves the id as built-in and can't slip into the persist-only path mid-flight; wrap `loadPlugin` in try/catch so a throwing manifest restores the reservation.
- **A dev reload re-runs `activate()` but NOT manifest registration.** Clear only imperative (`host.registerAction`) registrations between reloads (`unregisterImperativePluginActions`), never all — wiping every action erases the plugin's manifest-declared palette commands after the first reload.
- **Symbols moved since merge:** the PR's `activateViaDevWorker` / `devWorkers` are now `activateViaWorker` / `pluginWorkers`, and `PluginDevWorkerHost` gained `mode: "prod"` — the fork-per-plugin model generalized to ALL plugins.

## Applies when

- Building any hot-reload / live-reload for JS/TS modules — reach for process-respawn, not `import()` cache tricks; there is no ESM eviction API and unimport+reimport leaks.
- Adding or debugging any Electron `utilityProcess.fork` worker (pty-host, workspace-host, plugin workers) that hangs without posting `ready` — check for a bootstrap rejection/exception guard (`installBootstrapErrorGuard`) first.
- Touching `PluginDevWorkerHost`, `PluginService` enable/disable (`setEnabled`, `_applyBuiltinToggle`, `enableTransitions`), or the plugin activation/reload path (`activateViaWorker`, `pluginWorkers`).
- Diagnosing a plugin that silently fails to load/reload, or a built-in whose toggle strands it in neither `plugins` nor `disabledPlugins`.
