## Context

Scratch workspaces (throwaway, no-worktree sessions) added a second workspace pointer, `currentScratch`, alongside the pre-existing `currentProject`. Main enforces the two as mutually exclusive: switching to a Scratch calls `clearCurrentProject()`, switching to a project clears the scratch. That single design choice, `currentProject === null` on a Scratch switch, is the seam this whole arc (#11072, #11080, #11082, #11083, #11088, #11089, tracked against issues #11068/#11075/#11076/#11079/#11084/#11085) walks through: nearly every feature written before Scratch existed had been gated on `currentProject` being non-null as its proxy for "a workspace is open."

## Problem

Six independent-looking bugs turned out to be the same invariant violated six times: the Daintree Assistant refused to launch in a Scratch with a misleading "Project state is still loading" error (#11068/#11072); the empty canvas always rendered the onboarding `WelcomeScreen` instead of the agent launcher (#11076/#11082); `terminal.new` and the dock's launch button silently spawned in `$HOME` instead of the scratch root (#11082); deleting a scratch left its agent terminals alive on screen reading as "still running" (#11079/#11083); the MRU project-cycle shortcut went dead and the switcher palette pre-highlighted the wrong row (#11085/#11089); and the toolbar's branch chip reserved blank space next to a workspace that could never have a branch (#11084/#11088). None of these looked related from the bug report alone.

## Root cause

`currentProject === null` answers two different questions and the codebase had been treating it as answering only one. Before Scratch, null truly meant "no workspace is open," so `if (!currentProject)` was a safe proxy for "show onboarding" / "there's nothing to do" / "cwd has nowhere to go." Scratch made null ambiguous: it now also means "a real, usable workspace is open, it just isn't a project." All six bugs are that ambiguity resolving the wrong way. The cwd case was the worst instance: the same fallback chain was hand-rolled independently in three places that each guessed a different order (`useAgentLauncher` checked the scratch before the project; `useActiveWorktreeSync` never checked the scratch at all; `ContentDock` ended its chain in `?? ""`, and since `""` is not nullish it silently beat the caller's own scratch fallback and won). #11082 consolidated all three into one `resolveWorkspaceCwd()` (`src/utils/workspaceCwd.ts`), project path first only to cover the brief transient window where a cached view hasn't processed a switch broadcast yet and both pointers are momentarily set. #11083 found the same shape one layer down: terminal ownership for kill-on-delete rode `PtyClient.activeProjectId`, a mutable last-write-wins global that goes null on a scratch restore and gets clobbered across windows, instead of being stamped at spawn time from the view's own immutable workspace id (`getViewWorkspaceId()` in `src/store/viewWorkspaceId.ts`, seeded per-`WebContentsView` at creation — contrasted in its own doc comment with `currentScratch`, which broadcasts to every view and can't answer "which workspace does _this_ view own").

## Lesson

- **A null workspace pointer is not evidence of no workspace once a second workspace kind exists.** Anywhere `currentProject` (or any single-kind identity pointer) gates a feature with `if (!currentProject)` / `currentProject === null`, check whether that condition means "nothing is open" or "something else is open" — Daintree's scratch/project split makes it the latter constantly. The fix pattern used across this whole arc is `resolveX(currentProject, currentScratch)`, project-first, falling through to scratch, falling through to the true empty case — see `resolveEmptyCanvas()` in `src/components/Terminal/emptyCanvas.ts` and `resolveWorkspaceCwd()` in `src/utils/workspaceCwd.ts` for the exact shape to copy.
- **A hand-rolled fallback chain duplicated in more than one call site will disagree.** #11082 found three separately-written project/scratch/home cwd chains that each ordered the fallback differently, and one that ended in `?? ""` — a non-nullish empty string that silently wins over a later `??`. Whenever you see the same `a ?? b ?? c` shape appear in a second file, extract it before writing a third; don't trust that copies stay in sync.
- **Ownership and ephemeral "what's currently displayed" state are different things — don't derive the former from the latter.** #11083's terminal-kill bug existed because ownership was inferred from `activeProjectId`, a global that answers "what is the user looking at right now" and mutates on every switch/restore. Anything that must survive past the moment of creation (which workspace owns this terminal, which view a panel belongs to) needs to be stamped once at creation time from an immutable id, not re-derived later from a global that has since moved on.
- **Per-view identity and globally-broadcast identity are not interchangeable, even when they usually agree.** `getViewWorkspaceId()` (seeded once per `WebContentsView`, immutable) and `useScratchStore().currentScratch` (broadcast to every view, including cached/background ones) look like they answer the same question and don't — a second window switching scratches can retarget the first window's pointer. Use the per-view id for anything that must not leak across windows.
- **When a feature only breaks in the newer of two mutually-exclusive states, search for every other place the older state's non-null-ness was used as a stand-in for "ready" / "usable" / "has an X."** All six bugs here were found by that search pattern (`grep` for `currentProject` gating), not by six separate bug reports arriving independently — several were caught in code review of one PR while building an unrelated feature (#11082's two cwd bugs, #11080's retry-duplication and toast-routing bugs).

## Applies when

- Adding or reviewing any renderer code that reads `currentProject` (or introduces a second mutually-exclusive workspace/session/context pointer alongside an existing one) and branches on it being null.
- Diagnosing a feature that works from a real project but silently fails, falls back to the wrong directory, or shows onboarding UI once a Scratch (or any non-project workspace) is active.
- Writing a cwd/path-resolution fallback chain — check `src/utils/workspaceCwd.ts` first instead of hand-rolling another one, and never terminate a nullish-coalescing chain in `""`.
- Wiring terminal or panel ownership to a global "currently active X" pointer — prefer stamping the owning id at creation time (`src/store/viewWorkspaceId.ts` pattern) over re-deriving it later.
- Touching MRU/palette navigation, toolbar chrome, or the empty-canvas router (`useEmptyCanvasContent`, `resolveEmptyCanvas`) and needing to confirm scratch and project are both exercised, not just project.
