## Context

Event loop lag monitoring (main) and long task / long-animation-frame monitoring (renderer via `PerformanceObserver`) were gated behind `DAINTREE_PERF_CAPTURE=1`. They only ran when a developer explicitly enabled them, so jank in production was never observed or logged.

## Problem

Performance regressions in production were invisible. The monitoring infrastructure existed but only developers running in perf-capture mode ever saw it, so real-world jank and slow interactions went unrecorded.

## Root cause

The threshold-warning path was tied to the same capture flag that controls detailed file output (`CAPTURE_ENABLED = DAINTREE_PERF_CAPTURE=1 && DAINTREE_PERF_METRICS_FILE`). Capture mode is heavy (it appends every mark to a metrics file via `appendPayload`) and is never on in production builds, so gating the lightweight warn-on-threshold check behind the same flag meant it never ran where it mattered. The two concerns — a cheap always-on "log a warning when we cross a jank threshold" probe versus an opt-in "dump every sample to a file for offline analysis" capture — needed to be decoupled.

## Lesson

Decouple the always-on warn-on-threshold behavior from the opt-in capture: the `DAINTREE_PERF_CAPTURE=1` detailed file output can remain gated, but the threshold warning should run unconditionally. `startEventLoopLagMonitor()` in `electron/utils/performance.ts` now always emits `logWarn("Event loop lag detected", ...)` when lag crosses the threshold, while the `markPerformance("event_loop_lag", ...)` file sample stays behind `CAPTURE_ENABLED`.

Always-on performance monitoring requires two safeguards to avoid being more harmful than helpful — both implemented as module constants `STARTUP_SUPPRESSION_MS` and `WARN_RATE_LIMIT_MS` in `electron/utils/performance.ts` (and mirrored in `src/utils/longTaskMonitor.ts`):

1. **Startup suppression** (5_000 ms): app startup is intentionally heavy — suppress warnings during the initial load (measured as `now - APP_BOOT_T0` in main, `now - RENDERER_T0` in renderer) to avoid flooding logs with false positives.
2. **Rate limiting** (10_000 ms / 1 warning per 10s): sustained jank should produce one log line, not thousands. A `lastWarnTime` guard prevents log flooding during worst-case scenarios.

The main process and renderer are separate monitoring domains:

- Main: `startEventLoopLagMonitor(intervalMs = 1000, thresholdMs = 100)` uses a `setInterval`-based lag detector (`lagMs = now - expected`); the timer is `unref()`'d so it never keeps the process alive.
- Renderer: `startLongTaskMonitor(thresholdMs = 100)` in `src/utils/longTaskMonitor.ts` uses `PerformanceObserver` with the `"long-animation-frame"` (LoAF) entry type and `durationThreshold: thresholdMs` — NOT the older `"longtask"` entry type. LoAF carries richer attribution (`scripts[]`, `blockingDuration`, `forcedStyleAndLayoutDuration`), which the monitor summarizes into the top 3 scripts. The default 100ms threshold is the always-on value; capture mode records the full sample via `markRendererPerformance("renderer_long_animation_frame", ...)`. It is wired up in `src/hooks/app/usePerformanceMonitors.ts`.

## Applies when

- Diagnosing unexplained jank or slow interactions that only happen in production
- Adding a new performance monitoring probe to either process
- Setting the always-on threshold for a new type of performance warning
- Deciding whether a new probe's behavior should be always-on (cheap warn) or gated behind `DAINTREE_PERF_CAPTURE=1` (heavy file sampling)
