## Context

`useResolvedForgeProvider` resolves the active forge provider for a project through the host's precedence chain (per-project override → global default → hostname match), caching the answer client-side in a module-level `resolutionCache: Map<string, ResolvedForgeProviderState>` keyed by `projectId` so the toolbar renders instantly instead of flashing unresolved. Server-side, `PullRequestService.resolveProvider()` layers its own sticky cache: #9997 made a resolved `no-match` permanent because polling a remote-less project every 5s cost ~17,000 git subprocess spawns a day. #11161 (issue #11155) closes the gap both caches created: adding a git remote to an already-open project left the forge PR/issue count pills hidden until a full reload.

## Problem

`git remote add origin ...` on an open project did nothing — no pills, no re-check, until the project was closed and reopened. This was misleading: main's `resolveProvider` IPC handler already re-reads the remote fresh on every call, so the bug looked backend-side. The actual break was upstream of that handler — two independent caches, each correct for the problem it solved, with no path for "the remote just changed" to reach either.

## Root cause

The renderer's `resolutionCache` only invalidated on two triggers: project switch and a plugin `onProvenanceChanged` event. Neither fires on a remote edit, and the toolbar component that reads the cache never unmounts across a project's lifetime — Daintree keeps one persistent view per open project, so there is no natural remount to fall back on. A module-level cache behind a component that never unmounts is cached _forever_, not "until refresh", unless something explicitly deletes the entry — #11155 existed because nothing in the enumerated trigger list was "git remote changed".

Fixing the renderer alone wasn't enough, because `PullRequestService`'s `no-match` cache from #9997 is sticky by design — even a correctly-invalidated renderer would ask a backend that had already decided not to look again. The fix threads one new, narrow signal end to end instead of widening either cache's existing triggers. `GitFileWatcher` (already watching `.git/config` for `git push -u` tracking-info) gained a second, file-specific callback (`onGitConfigChanged`) alongside its generic `onChange`, distinguishing a config write from any other git-status change. `WorkspaceService` coalesces every sibling worktree's report (they share one common `.git`) into one debounced (250ms) `getRemotes()` probe, diffs a stable remote _signature_ (name+fetch-URL pairs, kept host-side since fetch URLs can embed credentials), and fires only when it changed — `git push -u` also writes `.git/config`, so signature-diffing is what keeps #9997's sticky cache meaningful instead of reopening its 5s-forever spin. A real change fires two things: `sys:forge:remote-changed` in-process, releasing `PullRequestService`'s no-match pause, and a project-scoped `forge-remote-changed` event over the workspace-host→main→renderer bridge that tells `useResolvedForgeProvider` to drop that project's cache entry. Separately, since `fs.watch` fails silently (falls back to polling without saying so; Linux inotify exhaustion is a real failure mode), the chain also got a 5-minute backstop that stats `<commonDir>/config`'s inode+mtime+ctime+size as a fingerprint and only spawns git when it moved.

## Lesson

- **Treat a module-level cache behind a component in a persistent project view as permanent, not component-scoped.** Daintree keeps one view per open project (no remount to fall back on), so `resolutionCache`'s freshness is purely a function of its enumerated triggers — add new mutation sources to that list explicitly rather than assuming lifecycle will eventually re-run resolution.
- **Scope invalidation to the key that changed, not the whole cache.** The remote-change handler checks `payload.projectId !== projectId` then `resolutionCache.delete(projectId)`, unlike provenance's `resolutionCache.clear()` (provenance really is global). Wholesale-clearing on a per-project event would re-resolve every open project on any single one's remote edit.
- **Add a narrow, purpose-built event instead of widening a broad one that already has protective semantics.** `PullRequestService.handleForgeRemoteChanged` listens only to the new `sys:forge:remote-changed`, not `sys:worktree:update` — widening the latter would revive #9997's 17k-spawn/day spin, since the sticky no-match cache exists to ignore routine worktree updates.
- **`fs.watch` degrades silently here, so a signal whose correctness matters needs a stat-fingerprint backstop, not just the loud failure callbacks.** `GitFileWatcher` already has `onWatcherFailed`/`onInotifyLimitReached`/`onEmfileLimitReached` for hard failures; those miss a watcher that quietly dropped one event. The fingerprint (inode+mtime+ctime+size, `stat` only) keeps the periodic reprobe cheap.
- **Never let a raw git remote URL or its derived signature cross the workspace-host → renderer IPC bridge.** Only a bare `{ projectId }` signal reaches the renderer over `forge:remote-changed`; fetch URLs and the signature stay host-side, since https remote URLs can embed credentials.

## Applies when

- Touching `useResolvedForgeProvider.ts`, `PullRequestService.ts`, or `WorkspaceService`'s forge-remote detection (`readForgeRemotes`, `scheduleForgeRemoteReprobe`, `startForgeRemoteDetection`).
- Adding an invalidation trigger to a cache/store behind a component known not to unmount within a project view — verify it actually remounts before relying on lifecycle to refresh state.
- Wiring a new signal off `GitFileWatcher`/`WatcherController` — decide whether it rides the existing `onChange` or needs a file-scoped callback, and whether a stat-based backstop is warranted.
- Reviewing a change that widens an existing event handler's trigger set — confirm the existing narrowness isn't itself the fix for a prior regression (#9997) before loosening it.
- Passing git remote/config data across the workspace-host boundary — confirm raw URLs never reach the renderer given the credential-embedding risk.
