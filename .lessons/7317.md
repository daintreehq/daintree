## Context

`useUrlHistoryStore` (`src/store/urlHistoryStore.ts`) persists browser URL history per project to `localStorage` via `zustand/middleware` `persist`. PR #7317 added `sanitizeUrlForHistory` (`shared/utils/urlHistory.ts`) to drop sensitive URLs (OAuth callbacks, token fragments, signed AWS/GCS/Azure URLs, `user:pass@host`), strip tracking params (`utm_*`, `fbclid`, …), dedupe, cap `visitCount`, and prune entries older than 90 days. The hard part was cleaning data already sitting in users' `localStorage` from before the fix shipped.

## Problem

Sensitive URLs and PII-laden tracking params were already persisted on disk for existing users. Bumping `version: 0 → 1` and writing a `migrate()` to sanitize the old blob looks like the textbook approach — but it does not reliably run. A blob written by a pre-`version` build has no `version` field at all, and a blob already at the target version also skips `migrate()`. Either way the sanitizer never fires and the sensitive history survives.

## Root cause

Zustand v5's persist hydration (verified in `node_modules/zustand/esm/middleware.mjs:392`, v5.0.14) gates `migrate()` on:

```js
if (typeof deserializedStorageValue.version === "number" && deserializedStorageValue.version !== options.version) {
  if (options.migrate) { ... }
}
```

So `migrate()` runs ONLY when the stored version is a number AND differs from `options.version`. Two cases bypass it:

- **Unversioned legacy blob** — `version` is `undefined`, `typeof === "number"` is false, the `else` returns the raw state untouched.
- **Already-current blob** — version matches, migrate skipped.

`merge()` (line 417) runs **unconditionally on every hydration** that finds a stored value, regardless of version. It is the only path guaranteed to see both legacy-unversioned and current-version data. The fix therefore puts the real cleanup (`migrateEntries()` → sanitize/dedupe/prune) inside `merge`, and leaves `migrate` as an identity cast (`persistedState as UrlHistoryState`).

## Lesson

- For Zustand v5 persisted stores, treat `merge()` — not `migrate()` — as the catch-all for normalizing/cleaning EXISTING persisted data. `migrate()` is a one-shot version-transition hook; it never fires for unversioned blobs and never fires when the stored version already equals `options.version`.
- Put security/PII sanitization, dedupe, shape-coercion, and pruning of historical data in `merge`, which runs every hydration. Make `merge` defensive: validate `persistedState` is a non-null object, default missing slices to `{}`, and skip non-array/malformed entries (see lines 183-193 + `migrateEntries`).
- Use `migrate()` only for true version-to-version field renames/restructures where you can rely on the version number being present.
- Bumping the version number alone does NOT force old data through any code path for users whose blob predates the `version` field — don't assume a version bump cleans anything.

## Applies when

- Adding sanitization, PII/secret scrubbing, dedupe, capping, or pruning to data already persisted in `localStorage` by any Zustand `persist` store (`src/store/*` — e.g. `preferencesStore`, `portalStore`, `projectStore`, `worktreeFilterStore`, `notificationHistorySlice`, all of which define custom `merge`).
- Writing or reviewing a `migrate()` function and expecting it to clean up legacy/old persisted state for existing users.
- Bumping a persist `version` and assuming the bump itself reprocesses on-disk data.
- Hydration produces stale, malformed, or sensitive entries that "the migration should have removed."
- Designing the security boundary for a feature that records browsed URLs / user history to disk (sensitive-URL skip lives in `shared/utils/urlHistory.ts`, applied in both the live `recordVisit`/`updateTitle`/`updateFavicon` write paths and the `merge` hydration path).
