## Context

`src/panels/registry.tsx` wraps each lazily-imported panel component (browser, dev-preview, review, file, diff) in `<Suspense fallback={...}>` with a per-kind ghost skeleton. Six weeks earlier, PR #9040 added `useSkeletonGate`/`useSkeletonDisplayFloor` to `src/hooks/useDeferredLoading.ts` and left a comment above `useSkeletonGate` warning: "Never wire an `animate-pulse-delayed` skeleton as a Suspense fallback" — but that PR's own audit only verified "every Suspense in `App.tsx` uses `fallback={null}`", so the note was "preventive" documentation, not an enforced rule.

## Problem

Issue #10984: the very first time any lazy panel kind opened, the grid showed a placeholder shaped like the browser panel's toolbar (URL pill and all) no matter what kind was actually loading, sitting as static flat gray blocks before anything animated — reading as "broken", not "loading". Hard to pin down: the _second_ open of the same kind never reproduced it (chunk already in the module cache), and it was mostly invisible in production, which pushed the initial read toward "can't repro."

## Root cause

Two individually-reasonable anti-flicker mechanisms stacked instead of overlapping. React 19 hardcodes `FALLBACK_THROTTLE_MS = 300` in `react-reconciler` — any newly-suspended tree's fallback is throttled ~300ms before React even paints it. Separately, Daintree's skeleton bones used `animate-pulse-delayed`, whose `--anti-flicker-delay` custom property is `400ms` (`src/index.css`) — the Doherty-gate class from this repo's design rules. `registry.tsx` wired `BrowserPaneSkeleton`'s `animate-pulse-delayed` divs directly as the literal Suspense `fallback=` JSX, so the gates ran serially: React withholds the fallback ~300ms, then the CSS delay withholds the pulse another ~400ms, for ~700ms of inert flat blocks before any motion. Compounding it, every panel kind's wrapper reused the _same_ `BrowserPaneSkeleton` (URL pill, nav icons, toolbar row) regardless of what was loading, so dev-preview, review, and file panels all first rendered a browser-toolbar silhouette.

The non-obvious part: #9040 had already diagnosed this exact interaction and left a comment describing it almost verbatim, but the trap wasn't in the file that comment audited. `App.tsx`'s Suspense boundaries did use `fallback={null}`; `registry.tsx`'s per-panel-kind wrappers, an unaudited file, used the precise anti-pattern the comment warned against, and shipped that way for six-plus weeks (2026-05-24 to 2026-07-07) until #10984 made it user-visible. Production mostly hid the symptom for an unrelated reason: `firstRenderModulePreloadPlugin` in `vite.config.ts` (`apply: "build"` only, still at `vite.config.ts:1139`) injects `modulepreload` links for the eager chunk closure at boot, so the chunk is usually already fetched/compiled by the time a panel opens — the dev server has no such preload and transforms on demand, which is why the placeholder stayed visible long enough to notice there.

## Lesson

- **`Suspense fallback=` must never carry `animate-pulse-delayed`** (or anything gated by the 400ms `--anti-flicker-delay`) — the fallback is already throttled ~300ms by React 19's hardcoded `FALLBACK_THROTTLE_MS`, so stacking a second delay produces a longer dead zone, not a safer one. Use `animate-pulse-immediate`; `Skeleton`/`SkeletonBone` in `src/components/ui/Skeleton.tsx` take an `immediate` prop for exactly this.
- **A preventive comment describing an anti-pattern is not proof the anti-pattern is absent elsewhere** — it only covers what its author actually checked. The #9040 comment's claim ("every Suspense in App.tsx uses fallback={null}") was true for `App.tsx` and silently false for `registry.tsx`. Grep the whole tree for the violating shape when writing this kind of warning, rather than asserting a codebase-wide state from one file.
- **Comments don't enforce; co-located tests do.** The durable form is a test on each skeleton asserting zero `.animate-pulse-delayed` nodes and a nonzero `.animate-pulse-immediate` count (see `BrowserPaneSkeleton.test.tsx` / `ReviewPaneSkeleton.test.tsx`). There is no repo-wide grep-based check, so a brand-new skeleton still needs this test written by hand or it can silently reintroduce the stack.
- **Don't share one skeleton across panel kinds it doesn't visually resemble.** `registry.tsx` reused `BrowserPaneSkeleton` (URL pill + toolbar icons) for dev-preview, review, and file panels; dev-preview's reuse is legitimate (same `BrowserToolbar` component), but review/file got wrong-chrome placeholders until this PR added kind-specific skeletons. `registry.tsx` now wires five fallbacks (browser, dev-preview, review, file, diff) — give any new panel kind its own skeleton unless it genuinely shares chrome.
- **"Never reproduces on the second try" points at module/chunk caching, not flakiness** — reproduce `lazy()` bugs via a cold open specifically, and check for a build-only mechanism (here, `apply: "build"`-gated `firstRenderModulePreloadPlugin`) masking the symptom in production while it stays visible in dev.

## Applies when

- Adding a new lazy-loaded panel kind, or any `lazy()` import wrapped in `<Suspense fallback={...}>`, in `src/panels/registry.tsx` or elsewhere.
- Writing or reviewing a skeleton/ghost-loading component meant for `Suspense fallback=` — confirm `animate-pulse-immediate`, never `animate-pulse-delayed`, with a test asserting it.
- Touching `src/hooks/useDeferredLoading.ts` (`useSkeletonGate`, `useSkeletonDisplayFloor`), or the pulse/`--anti-flicker-delay` definitions in `src/index.css`.
- Diagnosing "the first time X opens it looks broken, but it's fine after that" — suspect module-chunk caching plus a build-only preload mechanism before assuming a race condition.
- Trusting a code comment asserting a codebase-wide invariant ("every X in this repo does Y") — verify with a grep across the tree, not by re-reading the file the comment lives in.
