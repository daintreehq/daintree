## Context

`electron/store.ts` exports a `store` Proxy over an electron-store v11 (`conf`) instance holding a ~35KB `config.json` in the main process. Everything durable-but-not-SQLite rides it — `appState`, forge/plugin settings, and (before this PR) several audit ring buffers. Callers treat `store.get(...)` like reading a field off an in-memory object.

## Problem

`store.get()` on hot main-process paths was a silent perf tax. A boot/memory audit (`547806799`) measured 2+ full-file disk parses per agent state-change event, more on every 60s crash-backup tick, and double parses per appended audit record. Nothing crashed or leaked; the abstraction _looks_ memory-backed, so nobody suspected each accessor was hitting the filesystem.

## Root cause

electron-store v11 (`conf`) has **no in-memory cache of its own** — `store.get(key)` reads the whole file, JSON-parses it, then dot-path-walks the result, on _every_ call. Writes are worse: `store.set(key, v)` re-reads and re-serializes the entire `config.json`, so the per-field loop in `handleAppSetState` (`store.set('appState.'+field, v)` per field) cost N full-file rewrites for one logical update. `conf`'s docs read like a synchronous map, which is exactly the trap: the API shape hides that it is disk-backed with zero caching.

The fix layered a lazy whole-store snapshot onto the Proxy `get` handler (`electron/store.ts:1094`): the first `store.get` after any write parses `instance.store` once into `storeValueCache`, and every subsequent `get` is a memory hit via `getCachedValue` (a dot-path walk mirroring `conf`'s `accessPropertiesByDotNotation`). Three invariants make it correct, each a separate landmine: (1) **object returns are `structuredClone`d** — `conf` hands back a freshly-parsed object per `get` and callers routinely mutate it, so serving the shared snapshot by reference would let one caller corrupt every other reader's view. (2) **the cache is nulled synchronously BEFORE any mutating method (`set`/`delete`/`clear`/`reset`, in `STORE_MUTATING_METHODS`) delegates** — safe only because main is single-threaded, so a pre-write snapshot can never be served after the write. (3) **the whole scheme is sound only because main is the sole writer of `config.json`** — the pty-host/workspace-host subprocesses never import `store.ts`, so no cross-process invalidation is needed. The one path that swaps `config.json` _behind_ electron-store's back — `MigrationRunner.restoreFromBackup` renaming `.bak` over the live file (`StoreMigrations.ts:153`) — bypasses the Proxy, so it calls the exported `invalidateStoreValueCache()` explicitly; miss that hook and reads serve stale pre-restore data.

Secondary wins rode along: `handleAppSetState` now reads `appState` once, merges all fields in memory, and does a single `store.set('appState', merged)` (dropping keys via `delete merged[field]`, because **electron-store v11 throws on `undefined` values** — you cannot `set` undefined). Migration 023 moved four remaining rings (`plugins.auditLog`, `forgeAudit.auditLog`, `runHistory.records`, `pluginMcpAudit.auditLog`) out of `config.json` into the lazy `audit-logs` store (mirroring 022), shrinking every remaining parse; and the `config.json.bak` refresh + chmod moved off the bootstrap critical path into `runDeferredStoreBackup()`, scheduled via `setImmediate` after `main.js` loads.

## Lesson

- **Treat `store.get()` as a synchronous disk read+parse, never a field access.** electron-store/`conf` has no read cache; every `get` re-parses the whole `config.json`, every `set` re-serializes it. Don't call it in loops or twice for two fields of one object — read once, destructure locally.
- **A Proxy-level value cache over a disk-backed store is only safe under three conditions — verify all three.** Invalidate synchronously _before_ delegating each mutation (single-threaded main guarantees no interleaving); confirm the process is the _sole writer_ of the file; and hook every path that swaps the file behind the library's back (`invalidateStoreValueCache()` in `restoreFromBackup`). The last is the cache-invalidation trap: a rename/copy over `config.json` leaves both the library's state and your cache pointing at stale bytes.
- **`structuredClone` object returns from a cached `get`.** `conf` contractually returns a fresh object per call and callers mutate it in place; returning the cached snapshot by reference silently corrupts the shared copy. Scalars can pass through; objects and arrays cannot.
- **Batch multi-field writes into one merged `set`, and never `set` an `undefined` value.** electron-store v11 throws on `undefined` — to drop a key, `delete` it from the merged object, then write the object once. A per-field `store.set` loop pays one full-file rewrite per field.
- **Shrink `config.json` by moving append-only ring buffers to the lazy `audit-logs` store** (migration 022/023: config _flags_ stay, _records_ move; services persist rings via an injected `logStore {read, write}`). Smaller file = cheaper for every remaining parse. Keep recovery housekeeping (`.bak` refresh, chmod) off the bootstrap critical path — the prior session's `.bak` stays valid in the deferral window, so `setImmediate`-after-`main.js` loses nothing.

## Applies when

- Touching `electron/store.ts` — the `store` Proxy, `storeValueCache`, `invalidateStoreValueCache`, `STORE_MUTATING_METHODS`, or any method that mutates `config.json`.
- Adding or reviewing main-process code that calls `store.get()`/`store.set()` on a hot path (per-event handlers, polling ticks, per-record appends) — assume it hits disk unless it goes through the cached `get`.
- Introducing a path that replaces/renames `config.json` (backup/restore, external swap, another writer) — it bypasses the Proxy and must call `invalidateStoreValueCache()`; a second _process_ writing the file breaks the sole-writer assumption entirely.
- Batching electron-store writes, hitting its throw on an `undefined` value, migrating a ring buffer out of `config.json` (follow 022/023 into `audit-logs`), or profiling boot/steady-state cost that traces to config parsing.
