## Context

`DemoCaptureBridge` records the in-app demo reel by acquiring a `getDisplayMedia` stream and feeding the video track straight into `MediaRecorder`. The `DemoStartCapturePayload` (`shared/types/ipc/demo.ts`) carries `width`/`height` in device pixels so a preset (1080p / 1440p / 4K) can pin the master's exact resolution. Originally those were passed to `getDisplayMedia` as `{ width: { ideal }, height: { ideal } }` and never enforced afterward.

## Problem

The `width`/`height` params were effectively no-ops. Chromium 148 delivered frames at the captured surface's native backing-store size regardless of the request, so the recorded resolution was whatever the window rendered at. The 1080p and 4K presets _looked_ correct purely by coincidence of the spec's `SCALE = ceil(OUT.width / LOGICAL_W)` math (`LOGICAL_W = 1920` makes the backing store equal the output for exactly those two). The 1440p preset was the concrete victim: `SCALE = ceil(2560/1920) = 2` renders a 3840×2160 backing store while the caller requested ideal 2560×1440 — so the "1440p" master was actually a 3840×2160 frame encoded against the **1440p bitrate budget (32 Mbps)**: wrong resolution _and_ under-bitrate for the real pixel count. Nothing caught it because the e2e spec asserted only `bytes > 10_000` and `frameCount > 3`, never the encoded dimensions.

## Root cause

For **display** capture (window/screen), the Screen Capture spec lets Chromium treat `width`/`height` on `getDisplayMedia` as advisory `ideal` hints only — it will not downscale the source to honor them, and passing `{ exact }` _at acquisition_ throws `TypeError`. So the constraints API accepts the request, returns a valid track, and silently ignores the size: a textbook silent-failure API-misuse shape. The one enforcement seam the spec _does_ exempt from the acquisition restriction is `track.applyConstraints()` **after** acquisition, which routes through Chromium's scaler. The fix (#10262, resolving #10152): keep `{ ideal }` at acquisition, then call `applyConstraints({ width: { exact }, height: { exact } })` on the acquired video track, read `track.getSettings()`, and **fail the whole capture** on any mismatch — rather than hand `MediaRecorder` a wrongly-sized track. That pin succeeds only when the requested ratio matches the surface (which is why the demo window is pre-sized to match) and rejects otherwise. Resolution is also made all-or-nothing: a partial request (one dimension, or a non-positive value) is rejected up front, because it would otherwise fall through to native size — the exact bug being guarded.

## Lesson

- **For `getDisplayMedia` (display/window/screen capture), width/height are advisory only — the delivered track is the surface's native backing-store size.** Camera (`getUserMedia`) capture honors them; display capture does not. Never assume the constraints you passed at acquisition took effect: read `track.getSettings()` and check.
- **The only seam that forces an exact display-capture resolution is `track.applyConstraints({ width: { exact }, height: { exact } })` AFTER acquisition** — the Screen Capture spec exempts `applyConstraints` from the acquisition-time constraint restriction and routes it through Chromium's scaler. `{ exact }` _inside_ the `getDisplayMedia` call throws `TypeError`; keep that call `{ ideal }` for soft acquisition and pin afterward.
- **On a size/format constraint that must be honored, verify then fail hard — don't trust the returned track.** `DemoCaptureBridge` calls `getSettings()` post-pin and aborts with a `Capture resolution mismatch: got WxH, wanted WxH` message rather than encoding wrong frames. A track that came back without error is not proof the constraint applied.
- **Treat partial constraint input as a hard error, not a soft default.** Accepting only width (or a non-positive value) silently fell through to native size — the very failure being guarded. Reject `wantWidth !== wantHeight` before touching the recorder.
- **A media test that asserts only byte-count and frame-count is tautologically green.** The regression guard parses the _actual encoded_ WebM dimensions via `ffmpeg-static` (`ffmpeg -i <file>` with no output exits non-zero but prints `Video: … WxH` to stderr — `ffmpeg-static` ships `ffmpeg`, not `ffprobe`, so probe stderr is the source) and compares to the preset. It is only _load-bearing_ when native ≠ target (1440p), so the spec logs `pin load-bearing` vs `no-op for this preset` per run — the default 4K/1080p presets assert correctness but structurally cannot catch a missing pin.

## Applies when

- Adding or touching any screen/window/display capture via `navigator.mediaDevices.getDisplayMedia` (demo recorder, future screen-share/preview features) and needing a specific output resolution or frame size.
- Diagnosing "the recording came out the wrong size / wrong bitrate for its pixels" where the requested `width`/`height` look correct in code but the encoded file differs — check for a missing post-acquisition `applyConstraints({ exact })` + `getSettings()` verification.
- Touching `src/components/Demo/DemoCaptureBridge.tsx`, the `DemoStartCapturePayload` contract in `shared/types/ipc/demo.ts`, or the `e2e/demo/demo-reel.spec.ts` resolution presets / `SCALE` math.
- Assuming a Web constraints API that returned a track without error actually applied the constraint — for display capture, `MediaTrackConstraints` width/height are silently advisory.
- Writing an e2e assertion for encoded media output — assert parsed dimensions/format, not just `bytes > N` and `frameCount > M`, and make the guard's load-bearing preset explicit so a coincidentally-passing preset doesn't mask a regression (`e2e/demo/demo-reel.spec.ts`; the spec moved here from `e2e/screenshots/`).
