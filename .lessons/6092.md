## Context

`electron/utils/lifecycle.ts` ports VS Code's `lifecycle.ts` subset (`IDisposable`, `toDisposable`, `DisposableStore`, `MutableDisposable`, `Disposable`) and is now the canonical teardown primitive across main + hosts: `WindowContext.cleanup` is a `DisposableStore` (`WindowRegistry.ts:36`), and `ProjectStatsService`, `IdentityWatcher`, `WorkspaceService`, `WatcherController` use `MutableDisposable` for their timer/watcher slots.

## Problem

The prior pattern was a raw `Array<() => void>` with no add-after-dispose protection, no re-entrancy safety, and no ordering contract — a late `cleanup.push()` (from a deferred event listener firing after teardown) silently leaked the resource, and a throwing cleanup aborted the rest of the array.

## Root cause

Aggregate cleanup has three non-obvious failure modes a plain array does not guard: (1) a child registered after `dispose()` is silently retained-and-leaked; (2) a child that throws or re-enters `dispose()` during teardown (e.g. disposes a sibling) corrupts in-flight iteration; (3) the _order_ children run is implicit. `DisposableStore.dispose()` sets `_isDisposed = true` first, then snapshots into `Array.from(...)` before iterating (so re-entrant `dispose()` is a no-op and sibling mutation can't skip entries), swallows per-child throws, and `add()` after dispose runs `o.dispose()` immediately + `console.error` instead of leaking. `MutableDisposable` auto-disposes the prior value on reassignment (collapsing the manual clearInterval-then-setInterval dance) and disposes any value assigned into an already-disposed slot. The disposal-order contract is real and load-bearing: in `main.ts:372` `pvm.dispose()` is registered into `ctx.cleanup` _before_ `setupWindowServices`, because the store disposes in registration order and the WebContentsViews must close before the per-window MessagePorts/EventBuffer they post to disconnect.

## Lesson

Use `DisposableStore`/`MutableDisposable` for any main-process or utility-host resource set; never hand-roll a cleanup array or a null-timer + clearInterval slot. Treat _registration order = disposal order_ as an invariant you must reason about — register a disposer before the thing whose teardown it must precede (views before ports). `clear()` keeps the store reusable (does not set `_isDisposed`) while `dispose()` is terminal; `MutableDisposable.value =` is the idiomatic stop-old/start-new. `IDisposable` is structurally compatible with node-pty's `IDisposable`, so pty handles drop into a store unwrapped. Per-child throws are swallowed by design — do not rely on dispose ordering for correctness beyond the documented sequence, and do not let a disposer throw expecting later ones to abort.

## Applies when

Adding teardown for per-window/per-view services, timers, watchers, or MessagePorts in `electron/`; deciding the order resources must close (especially views-before-ports / producers-before-consumers); or auditing a cleanup path that uses a raw array, a nullable `intervalId`/`timer`, or a `() => void[]` for add-after-dispose leaks and re-entrancy hazards.
