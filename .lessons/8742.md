## Context

`CrashLoopGuardService` (`electron/services/CrashLoopGuardService.ts`) persists a small JSON file `crash-loop-state.json` in userData tracking crash counts/launch timestamps to trip safe-mode boot. It is read on every boot (and by the pre-`app.whenReady` standalone `isSafeModeActive()`), validated against a `CrashLoopState` shape, and written via `resilientAtomicWriteFileSync` (write tmp → rename). This sits in the persistence/recovery family alongside `electron/store.ts` config handling and the atomic-write utilities.

## Problem

A corrupt or schema-invalid state file was silently replaced with `freshState()`, destroying the forensic evidence of _why_ a crash loop started. Worse, a state file whose numeric field overflowed (e.g. `"crashes": 1e309`) passed validation: `JSON.parse` happily produces `Infinity` for overflow literals, and `typeof Infinity === "number"` is `true`. The value then poisoned arithmetic, and on the next write `JSON.stringify(Infinity)` serializes to `null` — so the file silently self-corrupted _one boot later_, displacing the failure far from its cause. SIGKILL between an atomic write's tmp-write and rename also left `.tmp` residue, and a chronic crash loop could pile up unbounded `.corrupted.*` siblings in userData.

## Root cause

Two distinct traps:

1. **`typeof x === "number"` is not a finiteness check.** `JSON.parse` maps numeric overflow literals to `Infinity` (and `-Infinity`), which is a `number`. Naive structural validation accepts it. The poison is _displaced in time_: `JSON.stringify` emits `null` for `Infinity`/`NaN`, so the value that passed validation this boot writes back as `null` and fails validation next boot — the corruption surfaces nowhere near where it entered.
2. **Silent `freshState()` reset is lossy recovery.** Resetting on parse/schema failure restores boot but throws away the only artifact that explains the crash loop, and never tells the user.

## Lesson

- When validating persisted JSON numbers, pair `typeof x === "number"` with `Number.isFinite(x)` on **every** numeric field. `typeof`/`Array.isArray` alone lets `Infinity`/`NaN` through, and `JSON.stringify` later rewrites them as `null`, producing delayed self-corruption. Add the guard everywhere the same file is parsed — both `readState()` and the standalone `isSafeModeActive()` here.
- Quarantine corrupt state (rename to `.corrupted.<ts>` + best-effort `fs.chmodSync(0o600)`, POSIX-only — Windows ignores mode bits, so guard with `process.platform === "win32"`) instead of silently resetting. The **rename is the authoritative quarantine event**; if the chmod throws, the file is still moved and the path is still recorded. Mirror the existing `quarantineCorruptConfig` / `tightenFilePermissions` pattern in `electron/store.ts`.
- Bound the recovery debris: sweep stale atomic-write `.tmp` files past a TTL (5 min, matching `terminalSessionPersistence`) and prune `.corrupted.*` siblings beyond a small N (3). Run sweep + prune **before** the read/quarantine so the current boot's own quarantine file can never be pruned in the same run.
- All cleanup is best-effort: swallow `readdirSync`/`unlinkSync`/`renameSync` errors (ignore `ENOENT`) — boot must proceed even if cleanup fails.
- Surface the quarantine to the user only when it co-occurs with a user-visible failure (here: `safeMode === true`). A silent reset that didn't trip safe mode stays log-only per the `notify()` four-question gate; don't toast every silent recovery.
- Keep the pre-`whenReady` standalone reader (`isSafeModeActive`) read-only — letting it also quarantine would race with the service's `readState()`.

## Applies when

- Reading or validating any persisted JSON file with numeric fields in userData (crash-loop state, settings, session snapshots, panel/project state) — especially `electron/services/CrashLoopGuardService.ts`, `electron/store.ts`, terminal/session persistence.
- Writing structural validators that check `typeof === "number"` or `Array.isArray` on parsed JSON — audit for missing `Number.isFinite`.
- Debugging "the state file was fine yesterday and is `null`/corrupt today" or a recovery that loses the evidence of why it triggered.
- Adding atomic-write (`resilientAtomicWriteFileSync`) callers — consider `.tmp` residue from SIGKILL between write and rename, and bound any `.corrupted.*`/backup sibling accumulation.
- Designing corruption-recovery flows: deciding between silent reset vs. forensic quarantine, ordering sweep/prune vs. read, and gating the user notification on a co-occurring visible failure.
