## Context

The worktree view-store (`createWorktreeStore.ts`, one per project `WebContentsView`) consumes a stream of `worktree-update` / `worktree-removed` events from the `workspace-host` utility process over a MessagePort, plus periodic `get-all-states` snapshots. To resolve out-of-order delivery it stamps each applied event with a version and rejects anything older. Originally the version was a renderer-minted monotonic counter (`nextVersion()`), incremented locally each time the renderer applied an event.

## Problem

The `workspace-host` is a separate process that can crash and restart. When it restarts, its event emission sequence resets from its own point of view, but the renderer's local counter keeps climbing. The restart boundary was therefore invisible to the renderer: post-restart events carried no signal distinguishing "fresh authoritative state" from "stale", and the renderer's "reject anything not strictly newer than my counter" guard would silently drop the post-restart re-hydration, leaving the UI frozen on pre-crash worktree state.

## Root cause

Version provenance lived on the wrong side. A counter minted by the _reader_ can only express the reader's own apply-order; it carries zero information about the _writer's_ identity or lifecycle. Manufacturing causal order from a non-causal local counter forced contortions (e.g. eagerly minting a snapshot version before an `await` so a racing update would still win — #8079). The only entity that knows "I am a new process run" is the host itself. The fix moves the stamp to the host: a `randomUUID()` `epoch` minted once per `WorkspaceService` instance (= once per host process), plus a monotonic `seq` advanced on each authoritative event. The renderer compares tuples via `compareVersion` (`createWorktreeStore.ts:32`): **differing epoch → always accept (a host restart always wins) and re-hydrate**; same epoch → higher `seq` wins.

Several pieces are non-obvious and each was a review finding:

- **Equal seq must be accepted, not rejected.** The reject gate is `compareVersion(...) < 0`, so an _equal_ same-epoch stamp passes. `get-all-states` reports the host's current high-water `seq` _without advancing it_ (a snapshot describes existing state, it is not a new event — `WorkspaceService.getVersion()` reads `seq`, does not `++`). If equal were rejected, cold start (renderer at `seq 0`, host snapshot at `seq 0`) would never initialize, and an epoch-change re-hydrate could be swallowed.
- **Host restart resets `seq` to a _lower_ number**, so seq comparison alone is wrong across epochs — epoch must be compared _by identity first_ (UUIDv4 strings carry no ordering) and short-circuit the whole comparison.
- **Host-minted versioning makes update-after-remove resurrection newly possible.** Under the old renderer-minted scheme it was structurally impossible (applying anything bumped the local counter). Now the host can legitimately emit `update seq=42` then `remove seq=43`, and a reconnect can deliver them out of order. Solution: bounded-TTL tombstones (`TOMBSTONE_TTL_MS = 30_000`) recorded on remove, cleared wholesale on epoch transition (a rebuilt host starts clean), reaped lazily on write.
- **Renderer-synthesized overlay events (pr/issue detection) have no host seq.** They must reuse the _current_ stamp (`overlayVersion`), not advance it — advancing would claim a `seq` the host will later emit and shadow that real event.
- The post-reconnect `applySnapshot` wholesale-`Map`-replace is wrapped in `startTransition` so the cascade of `useSyncExternalStore` subscribers re-renders at non-urgent priority.

## Lesson

For any state stream from a restartable writer (utility-process host, worker, remote producer) to a renderer/consumer that dedupes by version:

- **Mint the version at the authoritative writer, not the reader.** A reader-local counter cannot detect that the writer restarted. Stamp every event with `{ epoch, seq }`: `epoch` = per-process-run identity (UUID), `seq` = monotonic within epoch.
- **Compare epoch by identity first; a differing epoch always wins** and triggers full re-hydration. Never compare `seq` across epochs — a restart resets it downward.
- **Snapshots report the high-water `seq` without advancing it**, and the apply guard must reject only _strictly older_ (`< 0`), so an equal same-epoch snapshot still applies (cold start, idempotent re-hydrate).
- **Host-minted ordering re-opens update-after-remove resurrection** that reader-minted counters made impossible. Add bounded-TTL tombstones, cleared on epoch change.
- **Reader-synthesized overlay events must reuse the current stamp, not advance it**, so they don't shadow a future real writer event landing on that seq.
- Precedent for `(epoch, seq)` in single-writer topologies: Kafka producer epochs (KIP-98), etcd/Raft term numbers, MongoDB change-stream resume tokens.

## Applies when

- Adding or changing events on the `workspace-host` → renderer worktree stream (`WorkspaceHostEvent`, `WorktreePortProtocol`, `worktree-update` / `worktree-removed` / `all-states`).
- Touching `createWorktreeStore.ts` `applySnapshot` / `applyUpdate` / `applyRemove`, `compareVersion`, the `tombstones` map, or `WorktreeStoreContext.tsx` event handlers and `fetchInitialState`.
- Designing dedup/last-write-wins versioning for any stream from a restartable utility-process host, worker, or MessagePort producer to a renderer consumer.
- Symptom: UI frozen on stale state after a host/worker crash-restart; re-hydration silently dropped; cold-start initialization never fires; a deleted entity reappears after a reconnect; out-of-order update-vs-remove delivery.
- Debugging why a "newer wins" version guard drops legitimate post-restart data, or why equal-version events are being rejected.
