## Context

`WorkspaceClient`/`WorkspaceHostPool` pools one `WorkspaceHostProcess` UtilityProcess per project; each pool entry holds an `initPromise` that resolves after `host.waitForReady()` + the initial `load-project` round-trip lands. On a host crash the pool catches the `restarted` event and runs `reloadProjectAfterRestart(entry)` — re-waiting readiness and re-sending `load-project` to the freshly spawned host. The powerMonitor `resume` handler (`electron/window/powerMonitor.ts`) debounces wake, then calls `workspaceClient.resumeHealthCheck()` and `await workspaceClient.refresh()` to repoll git/worktree state, gating that on `waitForReady()`.

## Problem

After a laptop sleep the workspace-host frequently crashes and restarts (its watchdog or a wake-burst kills it). On wake the resume handler awaited `waitForReady()` — which resolved against the entry's **original** `initPromise` — and immediately fired `refresh()`. But the restarted host had not yet replayed `load-project`, so `refresh()` raced ahead and committed stale worktree state into the renderer stores. Worse, `loadProject`'s reuse guard checked `initPromise` to detect a "poisoned" entry, so a host whose post-restart reload had _failed_ still looked healthy (its original init succeeded) and got reused — silently serving stale state.

## Root cause

A pooled host's readiness is not a one-shot fact; it has at least two distinct lifecycle outcomes — the original load and every subsequent restart-reload — and `initPromise` only ever records the first. `Promise.all([...].map(e => e.initPromise))` therefore answers the wrong question: "did this entry ever finish its first load," not "is the host currently loaded and serving fresh state." After a restart the original `initPromise` is permanently resolved while the host is mid-reload, so any gate built on it (the resume `refresh()`, the poisoned-entry reuse check) unblocks too early.

## Lesson

Split readiness into two fields with opposite mutability (`ProcessEntry` in `electron/services/workspace-client/types.ts`):

- `initPromise` — **immutable**, records the original load outcome; keep it only for diagnostics/audit.
- `currentReadyPromise` — **mutable**, starts as `initPromise` and is _reassigned_ to the `reloadProjectAfterRestart(entry)` promise inside the `restarted` handler, so it always tracks the host's most recent readiness.

Gate every "is this host usable now" decision on `currentReadyPromise`, never `initPromise`:

- `waitForReady()` awaits `currentReadyPromise` for every entry, so the powerMonitor resume `refresh()` blocks until the restarted host has actually replayed `load-project`.
- The `loadProject` reuse guard probes `existingEntry.currentReadyPromise.then(() => false, () => true)` to detect a poisoned entry; a failed restart-reload now disposes + recreates the host instead of reusing it as healthy.
- **Let the restart promise's rejection propagate into `currentReadyPromise`** (the `.catch()` that logs is on a _separate_ handle, `restartPromise.catch(...)`, not the stored one) — a false-positive "ready" must never unblock callers on a broken host. The next `restarted` event overwrites the field with a fresh promise, so a failed reload followed by a successful one recovers cleanly.

Second, orthogonal trap in the same wake path: in the resume handler compute `sleepDuration` and **clear `suspendTime = null` at the very top**, before the `try` block that calls into the clients (`powerMonitor.ts:67-68`). The original code cleared `suspendTime` at the _end_ of the try; a mid-handler throw (e.g. `refresh()` rejecting) skipped the reset and leaked the stale timestamp into the next wake cycle's `sleepDuration`.

## Applies when

- Adding/reviewing any pooled or cached UtilityProcess client (`WorkspaceHostPool`, `PtyClient`, watchdog) that can transparently restart its host and has a `waitForReady()` / "is-ready" gate.
- The host has a `restarted` event and a post-restart reload step (`load-project`, session replay) that callers must not race ahead of.
- A readiness or "healthy entry" check awaits a `Promise` field — verify it tracks the _latest_ lifecycle outcome, not a one-shot init that stays resolved through restarts.
- Touching the powerMonitor `suspend`/`resume` handler, especially any state (`suspendTime`, cycle ids) that must be reset even when the handler body throws.
- Bug reports of the shape "worktree/git state is stale after waking the laptop" or "stale state after a workspace-host crash," where the host recovered but the data did not.
