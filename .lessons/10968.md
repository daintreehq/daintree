## Context

`AgentPatternDetector.detect()` is the hot-path scanner `ActivityMonitor.scanPatternBuffer()` runs every `PATTERN_SCAN_THROTTLE_MS` (30ms) against the rolling pattern buffer to catch per-agent working-indicator lines (Claude's `✽ Deliberating…`, Codex's `• Working`, etc.), feeding `AgentStateService`'s idle/working FSM.

## Problem

Before #10968, every 30ms tick called `stripAnsi()` on the whole ~10KB rolling buffer and then sliced the last `scanLineCount` (default 10) lines of the stripped result — correct but wasteful, since only the tail is ever scanned for patterns. The perf sweep in #10968 (part of a larger hot-path/polling/renderer/startup batch, see PR body) inverted the order: window the last N lines of the _raw_ buffer first, then strip only that window, so a 30ms scan pays for stripping ~10 lines instead of ~10KB. That inversion is only safe if "last N raw lines" and "last N visible lines" are the same window.

## Root cause

`lastLinesOffset()` finds the window boundary by counting literal `\n` bytes backward through the _raw_ text. CSI/SGR sequences (`\x1b[...`) never contain `\n`, so for those the raw-line count and the stripped-line count always agree. OSC sequences (`\x1b]...BEL` or `\x1b]...\x1b\\`) are the one escape class whose _payload_ can legally contain literal newline bytes — e.g. a window-title or hyperlink OSC carrying an unusual title string. If an OSC payload happens to contain, say, 20 raw newlines, counting backward from the end can land the window boundary entirely inside that one OSC sequence — potentially before any of the real status lines that preceded it. The window is then stripped, the OSC sequence (now truncated at the slice boundary) may not even match `stripAnsi`'s `\x1b\][^\x07\x1b]*(?:\x07|\x1b\\)/g` pattern cleanly, and the working-indicator line that should have been in scope is silently excluded — a false-negative agent-state detection with no error, no test failure locally, just a missed state transition in production.

The fix detects the desync rather than trying to special-case OSC up front: after windowing raw-then-stripping, if the stripped window has fewer than `scanLineCount - 1` newlines, or if `windowStartsInsideOsc()` finds an unterminated `ESC ]` immediately before the raw offset, the code widens the raw window to `scanLineCount * 4`, strips that, and re-windows on the _stripped_ text to recover the exact last-N-stripped-lines semantics. This is a detect-and-recover fallback, not a guarantee the first pass is right — it accepts a 4x-wider strip in the rare case to keep the common case cheap.

## Lesson

- **Counting raw bytes (newlines) to window text you intend to ANSI-strip is only safe for escape classes that can never contain the delimiter.** CSI/SGR/simple escapes never embed `\n`; OSC payloads (window title, hyperlinks, OSC 52 clipboard, shell-integration paths) can. Before reordering "strip-then-window" into "window-then-strip" for any escape/control-sequence text, check whether the specific escape grammar you're stripping has a payload-carrying variant that can contain your window delimiter.
- **Detect the desync, don't just prevent it.** The fix here is a post-hoc check (`countNewlines(textToScan) < scanLineCount - 1 || windowStartsInsideOsc(...)`) plus a widen-and-rewindow fallback, not an upfront OSC-aware windower. This is the right shape when the fast path is correct 99.9% of the time and you can cheaply verify it after the fact — don't build the general case when a bounded retry covers the edge case.
- **A single regression test is load-bearing for this class of bug.** `AgentPatternDetector.test.ts` ("detects a working indicator followed by an OSC payload with embedded newlines") constructs `\x1b]0;${"\n".repeat(20)}\x07` after a real working-indicator line specifically because normal fixtures never produce raw newlines inside an escape sequence — this bug is invisible to every other test in the suite by construction.
- **The boot phase deliberately opts out of this optimization** — `ActivityMonitor.scanPatternBuffer()` keeps a full-buffer `stripAnsi()` pass while `!bootDetector.hasExitedBootState` (boot-complete patterns can sit anywhere in the rolling buffer, not just the tail) and only switches to the windowed raw-then-strip path in steady state via `detect(rawBuffer)` vs `detect(fullStripped, { alreadyStripped: true })`. Don't assume `detect()`'s windowing applies uniformly across the terminal lifecycle.

## Applies when

- Reordering a strip-then-window (or filter-then-slice) pipeline into window-then-strip for a hot-path perf win over terminal/PTY output.
- Touching `AgentPatternDetector.detect()`, `lastLinesOffset()`, `windowStartsInsideOsc()`, or `ActivityMonitor.scanPatternBuffer()`.
- Diagnosing a missed or delayed agent working/idle state transition where the raw terminal output clearly contains the expected status line — check whether an OSC sequence (title, hyperlink, clipboard) sits near the scan window boundary.
- Writing any new terminal-output scanner that windows to "the last N lines" before removing escape sequences — verify which escape grammars in play can embed the line delimiter.
- Reviewing a perf PR that claims a text-processing reorder is "equivalent" to the original order — confirm equivalence holds for every input shape, not just the common one exercised by existing tests.
