## Context

MCP-connected agents are gated by privilege tiers (workbench / action / system). Each tier's set of allowed action IDs lives in `shared/config/helpAssistantTierAllowlists.ts` (`WORKBENCH_TIER_TOOLS`, `ACTION_TIER_ADDONS`, `SYSTEM_TIER_ADDONS`) and `electron/services/mcp-server/shared.ts` (`MCP_TOOL_ALLOWLIST`). These feed `TIER_ALLOWLISTS[tier].has(actionId)` in `tierAuth.ts`, which decides whether a given agent at a given tier may invoke a given action.

## Problem

The allowlists were typed `readonly string[]` and wrapped in `new Set<string>(...)`. When an action ID was renamed (or removed) in the actions registry, the allowlist kept the old string as a dead, no-op entry — no build break, no test failure. The renamed action silently fell out of the tier it should have belonged to (an over- or under-privileged gap), while the stale string sat in the set matching nothing. The PR also found several IDs (`agent.terminal`, the `agent.focusNext*` family, `terminal.new`, `terminal.inject`, `git.snapshotRevert`, `git.snapshotDelete`) that had already silently drifted out of `BUILT_IN_ACTION_IDS` / the allowlists.

## Root cause

`ActionId = BuiltInActionId | (string & {})` (`shared/types/actions.ts:37`). The `(string & {})` arm makes `ActionId` — and any plainer `string` type — accept _any_ string literal, so TypeScript cannot tell a live action ID from a stale one. A `readonly string[]` allowlist or a `Set<string>` therefore has zero coupling to the actual `BuiltInActionId` union; renaming the canonical ID in `BUILT_IN_ACTION_IDS` leaves the old literal in the allowlist perfectly type-valid. The set lookup `.has(staleId)` just returns false at runtime — a correctness gap masquerading as a passing build.

## Lesson

For any list/set whose members must stay in lockstep with the `BuiltInActionId` union (tier allowlists, MCP exposure sets, capability maps), declare it `as const satisfies readonly BuiltInActionId[]` rather than `readonly string[]`, then derive the `Set` from that tuple: `new Set(MCP_TOOL_ALLOWLIST_ENTRIES)`. The `satisfies` clause forces every literal to be a current member of the union, so a rename that drops an ID becomes a compile error pointing at the stale entry — while `as const` preserves the narrow literal types. Do NOT widen the element type to `string` or annotate the set as `Set<string>` up front; that re-opens the `(string & {})` escape hatch. Mirror the same source-of-truth in tests: have tier tests iterate the production allowlist constants instead of hardcoding parallel arrays, so test expectations can't drift either.

## Applies when

- Editing MCP tier allowlists (`WORKBENCH_TIER_TOOLS`, `ACTION_TIER_ADDONS`, `SYSTEM_TIER_ADDONS`) or `MCP_TOOL_ALLOWLIST` in `electron/services/mcp-server/`.
- Renaming or removing an action ID in `BUILT_IN_ACTION_IDS` (`shared/config/actionIds.ts`) — check every allowlist/capability set that references it.
- Adding any new const array/set of action IDs, channel names, or other registry keys that must stay in sync with a discriminated string union.
- Any type involving `(string & {})` (the open-string idiom used by `ActionId`, theme tokens, etc.) — the union arm silently accepts arbitrary strings, so plain `string[]` typing gives no drift protection; use `as const satisfies` against the closed union.
- Reviewing security/privilege gating where a missing or stale entry over- or under-grants capability without any test failing.
