## Context

`TerminalWebGLManager` keeps live WebGL contexts attached to focused/visible terminals. The cap was set to 16, matching Chromium's documented limit. (The manager has since dropped the per-context LRU pool in favour of a count-based mode switch — a hysteresis between an upper and lower threshold flips the whole fleet between WebGL and DOM at once rather than evicting individual contexts — but the headroom reasoning below is unchanged.)

## Problem

When terminals filled the pool, the first non-terminal WebGL consumer in the renderer — a Notes editor embed, a dev-preview overlay, a future chart, anything — would force Chromium to drop an existing context via `webglcontextlost` on a random terminal. The evicted terminal silently fell back to DOM rendering mid-session.

## Root cause

Chromium enforces a hard limit of 16 simultaneously active `WebGLRenderingContext`s per renderer process by default. The cap is per-process, not per-document, and it's shared with any other WebGL consumer in the same renderer. Hitting the ceiling triggers Chromium's own LRU eviction (not ours), which fires `webglcontextlost` on the oldest context regardless of whether it's terminal or not. `<webview>` partitions have their own budget, but anything in the main renderer document shares this pool.

Daintree now raises that default rather than living under it: `electron/setup/environment.ts:208` calls `app.commandLine.appendSwitch("max-active-webgl-contexts", String(getMaxWebGLContextCeiling()))`, and `getMaxWebGLContextCeiling` (`electron/utils/webglContextBudget.ts`) RAM-tiers the effective ceiling to 24/28/32 with a guaranteed minimum of 24 — still well short of "unlimited," so the headroom principle still applies, just below a higher and machine-dependent number instead of a fixed 16.

## Lesson

Never claim the full WebGL budget in a single consumer, even after raising it. Reserve headroom so other renderer-resident WebGL code can attach without triggering eviction. Document the ceiling inline so the next person doesn't bump the cap back up against it. The live thresholds are resolved from the same ceiling via `resolveWebglThresholds` (`electron/utils/webglContextBudget.ts`) and pushed into the renderer at runtime via `useResourceProfile` (#11192); `src/services/terminal/TerminalWebGLConfig.ts` only holds the cold-start bootstrap defaults (`upperThreshold = 18`, `lowerThreshold = 15` — sized to the balanced profile at the guaranteed-minimum ceiling of 24) with the rationale comment, consumed by `TerminalWebGLManager` via `getWebglUpperThreshold()`/`getWebglLowerThreshold()`:

```ts
// Chromium silently evicts the oldest active WebGL context on overflow
// (webglcontextlost), so the upper threshold must stay a headroom margin below
// the effective per-renderer ceiling to leave room for devtools, OffscreenCanvas,
// and any non-terminal WebGL consumer. That ceiling is raised above Chromium's
// default 16 and RAM-tiered (see electron/setup/environment.ts), and the live
// thresholds are resolved from it and pushed in via useResourceProfile (#11192).

let upperThreshold = 18;
let lowerThreshold = 15;
```

## Applies when

Any renderer-process code that keeps long-lived WebGL contexts: terminal renderers, canvas chart libs, 3D previews. `<webview>` and `WebContentsView` each have their own renderer process with an independent budget, so the concern only applies within one document. Also applies whenever a hard platform default gets raised via a command-line switch or config knob: the raised ceiling is still finite, and any code sizing its own thresholds against it needs to derive from the same source of truth (here, `getMaxWebGLContextCeiling`) rather than hardcoding a fraction of the old default.
