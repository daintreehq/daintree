## Context

`AssistantContentMirror.syncAssistantContent` (added by #10971, hardened for symlink/traversal escapes there) mirrors user-authored commands/skills from `~/.daintree/assistant` and `<project>/.daintree/assistant` into the per-project help-session directory before every Codex/Claude/Copilot assistant launch, called from `HelpSessionService`'s `provision()`. #11258 added a Codex-only `.codex/skills` source lane and, while wiring it, rebuilt the sync's failure handling from one blanket try/catch into a three-way outcome taxonomy, plus fixed a bug where `HelpSessionError`'s typed `code` never survived the renderer's `contextBridge` crossing.

## Problem

Before #11258, every sync failure — an unreadable source folder, a symlinked directory blocking a copy, a stale file whose delete failed — was swallowed identically: `console.warn` and launch anyway, because "a broken user file must never block the assistant launch." That policy is correct for a new file that simply can't be added, but wrong for a file that should have been REMOVED: a deleted or superseded skill's old copy would keep sitting in the session directory, Codex would keep discovering it on every launch, and nothing told the user the sync had failed.

## Root cause

Two failure shapes look identical in code (a caught exception, a warn) but demand opposite responses, and the fix threads that distinction through the filesystem walk, the result type, and the launch gate.

1. **Absent vs. unreadable source.** `collectSourceFiles`/`walkDir` used to `catch { return }` on any read error, treating a missing directory and a permission-denied one the same way — "nothing here, safe to retire whatever used to mirror from it." #11258 splits them with `isAbsentError` (`ENOENT`/`ENOTDIR`): absent really does mean the skill no longer exists (safe to retire), but unreadable (`EACCES`, `EIO`, a symlink loop) means the desired state was never actually observed, so `syncAssistantContent` now throws instead of guessing. `WalkState.unreadableDirs` carries this signal up from `walkDir`.
2. **Stale-but-present vs. new-but-missing.** The manifest is now written **twice**: once as a superset (`desired ∪ every stale relpath`) before any delete or copy runs, then compacted after a verification pass that `lstat`s every destination. A path that should be gone but is still there (failed `rm`, a symlinked dir, a racing writer) becomes a `staleFailures` entry; one that should exist but whose copy failed and left nothing behind becomes `failedCopies`. `HelpSessionService.provision()` branches on the split: `omittedSkills`/`failedCopies` stay non-fatal warnings (worst case the assistant launches without content it never had), but any `staleFailures` throws `HelpSessionError("USER_CONTENT_SYNC_FAILED", ...)` and blocks launch — letting that slide means the session runs live against a deleted or superseded skill's instructions with no signal to anyone.

Separately, wiring the new code surfaced that `HelpSessionError`'s existing codes (`MCP_NOT_READY`, `MCP_SERVER_NOT_STARTED`, `MCP_PROBE_FAILED`) had never reached the renderer in production — `contextBridge` strips custom Error properties crossing the preload→renderer realm, the trap already documented in `#6116`/`#8583` for `AppError`/`GitOperationError`. `_reconstructHelpSessionError` in `electron/preload.cts` plus `extractHelpSessionErrorCode` in `src/utils/clientHelpSessionError.ts` apply the identical message-prefix fix — a third instance of a known pattern, not a new one.

## Lesson

- **Categorize sync failures by what's wrong on disk afterward, not by which code path threw.** "Wanted gone but still there" (stale) is categorically worse than "wanted present but missing" (merely absent) — the former runs live stale content invisibly, the latter just launches with less. `AssistantContentSyncResult.staleFailures` vs. `.omittedSkills`/`.failedCopies` encodes this three-way split; don't collapse it back to a single boolean "ok".
- **Absent and unreadable are not the same failure for a source feeding retirement decisions.** A bare `catch { return [] }` on a directory read silently retires content whose source you failed to read, not content that's actually gone — use `isAbsentError`'s `ENOENT`/`ENOTDIR` check and fail closed (throw) on anything else.
- **Write the ownership manifest as a superset before mutating, then compact to verified reality after.** A crash mid-copy leaves the manifest a strict superset of disk (superfluous entries are harmless no-op deletes next sync); compacting after verification retires successfully-removed paths so a later hand-placed file at the same relpath is never wrongly claimed as "ours to delete".
- **Don't trust a copy operation's reported success — re-verify the destination.** `destFileState` `lstat`s the actual path after `copyFile` resolves; a copy that "succeeded" but the file is gone or not a regular file (racing writer, symlink swap, or a case-only rename aliasing a stale relpath via `foldPath` + dev/ino) counts as `staleFailures`, not `copied`.
- **Reuse the established `contextBridge` discriminant-encoding pattern rather than rediscovering it.** `_reconstructAppError`/`_reconstructGitError`/`_reconstructHelpSessionError` in `electron/preload.cts` are three instances of the same message-prefix trick (`#6116`, `#8583`); a fourth typed error crossing the bridge should copy it, not reinvent it.

## Applies when

- Writing or reviewing any manifest-driven mirror/reconcile/sync in Main that deletes stale files and copies new ones from a stored ownership list — `AssistantContentMirror.ts` is the template, but the same shape would apply to any future `CopyTreeService`- or plugin-manifest-style content sync.
- Deciding how a sync/provisioning step should react to a partial failure — ask "is the wrong-on-disk state stale-but-present or merely new-but-missing" before picking warn-and-continue over throw-and-block.
- Touching `electron/services/AssistantContentMirror.ts` (`syncAssistantContent`, `readManifest`, `collectSourceFiles`/`walkDir`) or `HelpSessionService.provision()`'s launch gate.
- Diagnosing "the assistant/Codex session keeps using a skill or command I deleted" — check `staleFailures` in the sync result and the session directory's `.daintree-user-content.json` manifest before assuming the delete logic itself is broken.
- Adding a new typed Error thrown from Main that the renderer must branch on by `code` — check `_reconstructAppError`/`_reconstructGitError`/`_reconstructHelpSessionError` in `electron/preload.cts` first; it is established precedent, not novel design space.
