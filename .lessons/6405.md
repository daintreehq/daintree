## Context

`validateIpcInvokeEnvelope` in `electron/setup/security.ts` runs inside the `ipcMain.handle`/`handleOnce` wrapper (after sender-frame validation, before the listener) so even a trusted renderer can't push pathological payloads through the ~87 channels. It caps arg count at `MAX_IPC_ARG_COUNT = 8` and enforces per-category byte budgets (`fileOps`/`artifactOps` 4 MiB, `gitOps` 512 KiB, `terminalSpawn` 256 KiB, `DEFAULT_PAYLOAD_BUDGET` 1 MiB) keyed by `channelToCategory` in `electron/ipc/utils.ts`.

## Problem

The natural way to enforce a byte budget is `Buffer.byteLength(JSON.stringify(args))`. But `JSON.stringify` is a fundamentally unreliable proxy for the structured-clone wire size, and the failure modes are per-JS-type and asymmetric — several of them let a hostile or accidental payload either crash the gate, silently bypass it, or get wrongly rejected.

## Root cause

`JSON.stringify` mis-measures three classes of value, each differently:

- **Binary (`ArrayBuffer`/typed arrays):** serialize index-keyed (`{"0":...,"1":...}`), wildly *over*estimating size — a legitimate buffer would be falsely rejected.
- **`Map`/`Set`:** serialize to `{}`, *under*estimating to ~zero — a huge Map would sail straight through the gate.
- **`BigInt`:** `JSON.stringify` _throws_ `TypeError`. A naive gate wraps the call in try/catch and `return`s on failure (to tolerate circular refs / unserializable args), so dropping a single `1n` anywhere in the args makes the whole gate silently no-op — a clean bypass.

The fix is two-pronged and the design choice is the lesson: rather than try to measure the unmeasurable, `containsBinary` recurses (depth-bounded to 32) through plain objects/arrays and, if it finds any `ArrayBuffer.isView`/`ArrayBuffer`/`Map`/`Set`, _skips the byte check entirely and defers to Mojo's 128 MiB structured-clone ceiling_ (plus handler-level caps). Separately, a `bigintSafeReplacer` coerces BigInt to its string form so a stray BigInt can't trip the throw-then-bypass path. The remaining try/catch then only catches genuine circular refs.

## Lesson

When size-gating IPC/MessagePort payloads (or anything structured-clone-bound), do NOT treat `JSON.stringify(...).length` as the wire size:

- **BigInt makes `JSON.stringify` throw** — always pass a replacer coercing BigInt to string. At a _security_ gate this is load-bearing, not cosmetic: a bare try/catch around the stringify turns the throw into a silent bypass (one `1n` defeats the whole gate). (General BigInt-stringify crash trap is lesson #1548; this is the security-gate corollary — the throw is exploitable, not just a UI crash.)
- **Map/Set serialize to `{}` (under-count) and binary serializes index-keyed (over-count).** Don't try to estimate them. Detect them with a recursive, depth-bounded walk and _defer to the platform backstop_ (Mojo's 128 MiB clone ceiling, handler-level caps) for those args.
- Run the envelope check in BOTH the `handle` and `handleOnce` wrappers — `handleOnce` is easy to forget and had inconsistent `userMessage` scrubbing before this PR.
- Throw a stable `AppErrorCode` (`ARG_COUNT_EXCEEDED`/`PAYLOAD_TOO_LARGE`) so the error flows through the existing prod-strip + secret-scrub path; verify packaged builds strip `context` (budget/bytes must not leak to the renderer).

## Applies when

- Adding/modifying any IPC byte-budget, quota, or payload-size guard in `electron/setup/security.ts` or `validateIpcInvokeEnvelope`; adding a new channel category to `channelToCategory` / `PAYLOAD_BUDGETS` in `electron/ipc/utils.ts`.
- Anywhere code uses `JSON.stringify(...).length` / `Buffer.byteLength(JSON.stringify(...))` to approximate the size of arbitrary structured-clone data (IPC args, MessagePort messages, persisted state).
- Reviewing a try/catch that swallows a `JSON.stringify` failure on a security/validation boundary — confirm BigInt can't turn the catch into a silent bypass.
- Touching the `ipcMain.handle`/`handleOnce` wrappers in `enforceIpcSenderValidation` — both must apply the same envelope guards and the same `userMessage` scrubbing.
