## Context

The pty-host fans one terminal's output out to every renderer window over per-window MessagePort `PortBatcher`s (`RendererConnection` targets), with a shared SAB/IPC path as fallback. Multi-target fan-out is routine: a window whose `windowProjectMap` entry is `null` (no active project) receives every terminal alongside any project-scoped window. The `ptyManager.on("data")` handler in `electron/pty-host.ts` tracks whether a chunk reached a visual sink via a `visualWritten` flag; the renderer trusts that each chunk takes exactly ONE visual path, so there is no double-delivery.

## Problem

In multi-window mode a terminal streaming to two windows would show a permanent gap in output on ONE window while the other was fine — no resync, no error, no wake/snapshot triggered. It only reproduced when 2+ windows fanned out the same terminal and one window's port queue was at capacity while a sibling's accepted the same chunk. The starved window silently diverged with no drop accounting and no data-loss discontinuity marker (#9891).

## Root cause

Delivery was per-window but the delivered flag was global. The fan-out loop set `visualWritten = true` as soon as ANY target's `batcher.write()` returned true, while `PortBatcher.write()` returns `false` per-window when THAT window's queue is saturated. With `visualWritten` already true, the shared IPC fallback (`if (!visualWritten ...)`) never ran for the starved window — and all three safeguards (the fallback delivery, the `dropAccumulator` counter, the `terminal-status: "data-loss"` marker) live only on that IPC at-capacity path. So the saturated sibling lost the chunk with zero signal: the invariant the renderer trusted ("exactly one visual path via `visualWritten`") was global while delivery is per-window — a scope mismatch, not a tradeoff.

The fix computes saturation per destination: collect a `saturated: RendererConnection[]` in the loop, then — only when `visualWritten` is already true (a SIBLING accepted, so the IPC fallback is genuinely blocked) — account the drop and post a `data-loss` pulse on each starved window's OWN `port.postMessage(...)`, never `sendEvent` (which broadcasts to every window and would falsely flag the ones that received the data — the whole subtlety of #9891). A new `terminal-status` variant on `PtyHostToRendererMessage` (`shared/types/pty-host.ts`) carries the pulse; `terminalClient.installPortDataHandler` dispatches it to the same `onStatus` subscribers as the IPC broadcast (dual-subscribed, both cleaned up), with no ACK and no byte accounting.

## Lesson

- **In any fan-out loop, fallback / drop / loss decisions must be computed PER DESTINATION, never with one shared flag.** A single global "delivered" flag (`visualWritten`) that flips true the moment one sink accepts silently suppresses the fallback the other sinks still need — the fast sink starves the slow one. If you loop over N sinks, collect the rejects (`saturated[]`) and decide each one's fate individually.
- **Signal a per-target loss on that target's OWN channel, never a broadcast.** `sendEvent` reaches every window; a broadcast `data-loss` marker would falsely alert the windows that DID receive the chunk. Post the `terminal-status: data-loss` pulse on the saturated window's own MessagePort, FIFO-ordered with its data so the discontinuity marker lands where the gap actually is.
- **Only signal loss when the fallback is genuinely blocked.** A starved window truly loses the chunk only when `visualWritten` is already true (a sibling accepted, suppressing the shared IPC fallback). If NO window accepted, `visualWritten` stays false and the IPC path broadcasts to everyone — nothing is lost, so a pulse there would be a spurious discontinuity.
- **Account the drop UNCONDITIONALLY, even when metrics are gated off.** `dropAccumulator` and `recordTerminalDrop(id, byteCount)` fire regardless of the metric gate (mirroring the IPC at-capacity path) — regression detection depends on the counter even when wire emission is off. Use UTF-8 byte count (`byteCount` / `Buffer.byteLength(..., "utf8")`), not JS string `.length`, or CJK/emoji mis-reports the gap size.
- **Don't treat a non-visual side channel as a delivery path.** This PR's original guard `!ipcDataMirrorTerminals.has(id)` skipped the pulse for mirrored terminals, assuming the IPC data mirror would deliver the chunk anyway — wrong, and removed in `4211fbf86`: the mirror is sent as `data-mirror` (Main-process-only, feeds detectors like UrlDetector), never re-dispatched into the renderer's xterm, so a starved MIRRORED window really does lose the chunk. Verify a fallback actually reaches the VISUAL sink before leaning on it.

## Applies when

- Touching the pty-host fan-out loop (`electron/pty-host.ts`, the `ptyManager.on("data")` handler, `visualWritten`, the `RendererConnection` targets, `PortBatcher.write`) or the SAB/IPC fallback branches.
- Adding any new multi-destination delivery path in the terminal fabric / per-project pty-host sharding work (`DAINTREE_PTY_FABRIC`) — the same per-destination invariant applies to every shard/window sink.
- Diagnosing "one window shows a gap or diverges in terminal output while another window is fine" in multi-window mode, with no error surfaced.
- Reviewing any code that uses a single boolean to decide whether a fallback fires across multiple independent sinks — confirm the flag isn't global while the sinks are per-destination.
- Emitting a per-target status/error signal (`terminal-status`, data-loss, suspension) — broadcast (`sendEvent`) vs. per-channel (`port.postMessage`); a broadcast of a per-target condition falsely alerts the healthy targets.
