## Context

The content dock renders only panel kinds `isDockPanel` (`shared/types/panel.ts`) accepts: PTY kinds plus anything with `dockable: true` in `panelKindRegistry.ts` (`panelKindIsDockable`, only `file` at the time). Three separate mutation paths could still commit `location: "dock"` for ANY kind: the non-PTY branch of `addPanel` (`src/store/slices/panelRegistry/addPanel.ts`), the drag-and-drop cross-container commit in `DndProvider.tsx`, and the dock's `+` launch menu (`DockLaunchMenuItems.tsx`). Companion PR #11058, merged the same day, made browser panels genuinely dockable — but only fixed the render side for one kind, not the write side for any kind.

## Problem

Issue #11054: a browser panel (or any plugin kind without `dockable`) dragged onto the dock, or launched via the dock's `+` menu, just vanished — no error, no toast. It wasn't destroyed: it stayed in the persisted panel store across restarts, still counted against panel limits, and `addPanel`'s `activateDockOnCreate` even pointed `activeDockTerminalId` at the now-invisible panel. The panel-header move-to-dock button already hid itself for browser panels for exactly this reason (`core-panel-non-pty-rejection.spec.ts`: "Rendering it would silently strand the panel") — that guard covered only one of the three ways a panel could reach the dock.

## Root cause

`isDockPanel` / `panelKindIsDockable` is a **read-side** predicate gating what the dock will render. Nothing enforced it at the **write side** — where `panelData.location = "dock"` actually gets set. Fail-open write behind a fail-closed render gate produces state that's permanently invisible but never removed, since nothing treats `location: "dock"` + non-dockable kind as an error to clean up.

The `addPanel.ts` fix renames the naive `options.location || "grid"` to `requestedLocation`, then redirects to `"grid"` when `requestedLocation === "dock" && !panelKindIsDockable(requestedKind)`, placed before `shouldBackground`/`runtimeStatus` derivation so the redirect doesn't leave dock-flavored background state behind. Hydration on restart funnels every persisted non-PTY panel back through this same `addPanel` call (`buildArgsForNonPtyRecreation` → `addPanel`), so the write-time guard doubles as a migration: panels already stranded before this fix rehydrate through the identical branch and land back on the grid with zero dedicated rescue code.

That redirect broke an assumption one layer up: `panelStore.ts`'s create-focus wrapper decided grid-focus vs. dock-activation by branching on `options.location` — the **requested** location, not what `addPanel` committed. A redirected dock→grid panel failed `options.location === "grid"` (still `"dock"` in the caller's options) and fell into the dock-activation branch, which the registry's atomic commit never ran for it. The fix reads back `get().panelsById[id]` after `addPanel` resolves and branches on `committedPanel.location`, guarding `committedPanel !== undefined` for when the panel was removed during addPanel's async tail (a PTY prewarm await, a project switch, an explicit `removePanel`) — a missing panel is neither grid nor dock, not defaulted into one.

Drag-and-drop needed the same guard elsewhere: `cancelDrop` calls `isNonDockableDockDrop(targetContainer, kind)` (`dropResolution.ts`) to reject the drop, and `filterOutDockDroppables` strips the dock from dnd-kit's collision candidates mid-drag so the `SortableContext` doesn't reflow before rejection. `bulkMoveToDockByWorktree` got the same `panelKindIsDockable` filter `bulkMoveToDock` already had — simply missed earlier. Four sites, one predicate, no shared enforcement point.

Companion #11058 reuses pre-existing infra instead of inventing new preservation logic: the offscreen-container stable-wrapper + connected-path `moveBefore` relocation (`DockPanelOffscreenContainer.tsx`, from the file-panel precedent `6479b7a18`) already moves a panel's DOM subtree without unmounting it, which happens to preserve an Electron `<webview>` guest's state too, scoped to moves _within_ one portal host — a grid↔dock move still remounts into a different render host, reloading the webview once (accepted, not fixed).

## Lesson

- **A predicate that gates rendering (`isDockPanel`) must be enforced everywhere state reaches it, not just where it's read.** Grep every mutation path that can set the gated field (`location: "dock"`) — creation, drag-and-drop, bulk actions, launch menus; #11054 needed four separate guard sites for one predicate.
- **When a write-time guard redirects a value, treat hydration as just another caller of that path.** Hydration here replays through `addPanel`, so one guard fixes the live bug and every already-corrupted persisted record with no dedicated migration.
- **A redirect that changes committed state invalidates downstream code branching on the ORIGINAL request instead of the outcome.** `panelStore.ts`'s focus wrapper broke reading `options.location` after `addPanel` silently redirected it — re-read committed state (`get().panelsById[id]`) after any async action that can rewrite what you asked for, and handle "record no longer exists" explicitly instead of defaulting into a branch.
- **Fail-open write + fail-closed render on the same field yields invisible-but-persisted state, not a crash** — easy to miss in review, painful to diagnose (counts against limits, survives restart, no UI reaches it, no error anywhere).
- **Reusing an existing DOM-relocation mechanism (moveBefore + stable wrapper) for a new content type is close to free, but only within one render host** — a grid↔dock transition across separate portal roots still remounts.

## Applies when

- Adding a new panel kind or dock-eligible content — check `panelKindIsDockable` / `isDockPanel` usage for both the render gate AND every write path (`addPanel`, `DndProvider` drop/collision, `DockLaunchMenuItems`, bulk-move actions) before assuming `dockable: true` alone is sufficient.
- Reviewing any feature with a filter deciding what renders from persisted state — confirm the same filter is enforced at every place that writes the filtered field, not just where it's displayed.
- Debugging "the thing disappeared but didn't error" for panels or any persisted UI item — check for a location/kind mismatch against a render-side membership filter before assuming data loss.
- Adding a redirect inside a store action other code calls asynchronously and then branches on `options.*` afterward — audit every caller for request-vs-outcome drift.
