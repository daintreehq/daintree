## Context

Daintree ships plugins from two roots: `plugins/builtin/*` (GitHub forge) and `plugins/sample/*` (`hello-daintree`, `rich-daintree` — sideloaded into E2E via `DAINTREE_E2E_SIDELOAD_PLUGIN_DIR`, absent in prod). `scripts/build-main.mjs` turns each plugin dir into runtime output in two independent steps: `copySamplePluginManifests()`/`copyBuiltInPluginManifests()` copy `plugin.json` into `dist-electron/plugins/**`, and esbuild bundles each plugin's `main/index.ts` as an `entryPoints` member. #10567 (issue #10564, from the #10511 plugin-DX audit that tripped this on all 10 test plugins) closed two build gaps.

## Problem

Adding a new sample plugin appeared to build successfully — the build was green — but the plugin silently never loaded at runtime. Separately, a malformed `plugin.json` (bad `actionId`, unsupported `location`, missing required field) also sailed through a green build and only threw when the app actually loaded the plugin. "The build proves the plugin is loadable" was only half true.

## Root cause

The two halves of "build a plugin" were driven by **different mechanisms that silently drifted**. `copySamplePluginManifests()` auto-discovered sample dirs via `readdirSync`, so a new plugin's `plugin.json` was copied automatically. But the esbuild `entryPoints` array **hardcoded** `plugins/sample/hello-daintree/main/index.ts` and `plugins/sample/rich-daintree/main/index.ts` as literal strings (while `plugins/builtin/*` mains were already auto-discovered by `discoverBuiltInPluginMainEntries()`). Add a sample plugin and forget its entry, and the manifest ships but `main/index.js` is never emitted — a half-built plugin. Neither half errors when the other is missing, so the build stays green; the failure surfaces only as a runtime load miss. The fix added `discoverSamplePluginMainEntries()` mirroring the built-in discovery, spread into `entryPoints`.

The second gap: `build:main` copied `plugin.json` **verbatim** with zero validation, so the only schema enforcement was the runtime loader inside the app. #10567 added `scripts/validate-plugin-manifests.ts`, validating every `plugins/{builtin,sample}/*/plugin.json` against the same runtime Zod schema (`getPluginManifestSchema(isBuiltin)` in `electron/schemas/plugin.ts`), wired as `check:plugin-manifests` into `npm run check` and called from the build via `validatePluginManifests()` **before any clean or emit** so an invalid manifest neither wipes the prior `dist-electron` nor ships a broken plugin.

## Lesson

- **When one resource requires N parallel build steps, all N must share one discovery, or a hardcoded step silently drifts.** A plugin needs its manifest copied, its main bundled, AND its main typechecked. Manifest-copy was auto-discovered but the esbuild entry was a hardcoded list, so a new plugin got a copied `plugin.json` and no `main/index.js` — green build, non-loading plugin. Grep the build for any hardcoded per-plugin path list (`plugins/sample/<name>/...`) and replace it with a `readdirSync`-based discover fn mirroring `discoverBuiltInPluginMainEntries()` / `copySamplePluginManifests()`.
- **A green build does NOT prove a plugin is loadable — validate the manifest against the runtime schema at build, not first app load.** The build copied `plugin.json` verbatim; the loader was the only validator. `check:plugin-manifests` now runs `getPluginManifestSchema` (the exact runtime Zod schema) over every manifest in `npm run check`. Reuse the runtime schema — don't hand-write a build-time copy that drifts from what the loader enforces.
- **Validate sample plugins with `isBuiltin: true`, matching the runtime sideload path.** Sample plugins sideload via `PluginService` with `isBuiltin: true`, so the reserved `daintree.*` name namespace passes the guard; `defaultRoots()` flags BOTH roots `isBuiltin: true` for this reason. Validating a sample as `isBuiltin: false` would wrongly reject valid `daintree.*` manifests — a test explicitly guards this flag choice.
- **Gate the build on validation BEFORE clean/emit.** `validatePluginManifests()` (and later #10620's `validateCommandHandlerExtensions()` / `runPluginTypecheck()`) run at the top of `run()`, ahead of the `dist-electron` rm, so a failure leaves the prior build intact rather than half-destroying it.
- **Typecheck coverage is a sync point too.** #10567 wildcarded the sample-mains typecheck glob so auto-discovered entries get typechecked; that glob has since moved from `electron/tsconfig.json` to `tsconfig.plugins.json` (`plugins/sample/*/main/**/*.ts`), but the wildcard-not-per-plugin principle stands — add a discovery-driven build step, wildcard its typecheck include too.

## Applies when

- Adding a `plugins/sample/*` or `plugins/builtin/*` plugin, or a new plugin root — verify the main is auto-discovered (`discoverSamplePluginMainEntries` / `discoverBuiltInPluginMainEntries`), not hardcoded in `build-main.mjs` `entryPoints`.
- Diagnosing "the build is green but the plugin doesn't load / doesn't appear at runtime" — check whether `dist-electron/plugins/**/<name>/main/index.js` was actually emitted, not just the `plugin.json`.
- Touching `scripts/build-main.mjs`, `scripts/validate-plugin-manifests.ts`, `check:plugin-manifests`, or `getPluginManifestSchema` — keep build validation on the runtime Zod schema with `isBuiltin: true` for both roots.
- Adding any build step that turns a directory of resources into output — audit every parallel step (copy, bundle, typecheck) for the same discovery source, and run any new gate before clean/emit (shell out via `tsx` if the checker is TypeScript).
