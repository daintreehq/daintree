## Context

`ActivityMonitor` runs one poll loop per agent terminal (`runPollingCycle` on `setInterval`) to detect idle/busy/waiting state from visible-line diffing; `setPollingInterval(intervalMs)` lets callers (focus/visibility tiers) request a cadence, with a same-value early-return so repeated requests are cheap no-ops. `SessionSnapshotter.flushEventDriven` serializes scrollback on every agent transition to `waiting`/`completed`/`exited`. Issue #10906 flagged both as fixed-rate costs that scale with open-terminal count regardless of agent activity: 50ms polling never slows for an hour-idle agent, and every settle transition synchronously serializes up to 10000 lines on the shared pty-host event loop. PR #10914 added idle-driven polling backoff plus an async, epoch-gated flush path.

## Problem

The idle backoff needed to swap the _live_ polling interval to 2000ms once an agent settles, independent of whatever the visibility tier last asked for — but `setPollingInterval`'s existing no-op guard compared the incoming request straight against `POLLING_INTERVAL_MS`, the same field the backoff now also mutates. Ported naively, a visibility-tier request that happened to equal the backoff's live value (or any request arriving while backed off) would hit the guard and return early, permanently losing the caller's request until something else forced a resync. Not hypothetical: #8998, a separate PR in a different subsystem, hit the identical shape of bug — `TerminalHibernationManager` treated re-backgrounding a panel already at the `BACKGROUND` tier as a same-tier no-op (`applyRendererPolicy(BACKGROUND)`, guarded by `if (tier === currentAppliedTier) return`), so the reschedule the caller expected silently never ran, forcing `onPanelBackgrounded(id)` in as an explicit side channel. `TerminalHibernationManager` was later deleted whole (hibernation removal, `eb9cd64a7`, 2026-06-27, predates this PR) — but that tier-equality guard lives on in `TerminalRendererPolicy.applyRendererPolicy`, which still needs its own side-channel workaround today (`reassertActiveTier`), so the mechanism is still current, just relocated.

## Root cause

Both bugs share one invariant violation: an API exposes a field as "the current value" and short-circuits when a new request matches it, but a second, independent mechanism (idle backoff here, hibernation-tier collapse in #8998) can change what's actually live without going through that field's normal setter. Once two things write "current value," a same-value check has two possible meanings — "same as what I last asked for" vs. "same as what's actually running" — and they diverge exactly while the override is active, the one moment correctness matters. #10914's fix splits the field: `POLLING_INTERVAL_MS` stays "whatever `setInterval` is actually running at" (mutated by both callers and the backoff), while a new `requestedPollingIntervalMs` tracks only external asks. The no-op guard in `setPollingInterval` now reads `if (this.requestedPollingIntervalMs === intervalMs) return` — never `POLLING_INTERVAL_MS` — and while backed off, a changed request is recorded into `requestedPollingIntervalMs` but not applied live (`applyPollingInterval` is skipped); the wake path (`cancelFsmIdleBackoff(true)`, from `onData`/`becomeBusy`) restores the interval from `requestedPollingIntervalMs`, never a hardcoded default, so a tier change arriving mid-backoff is honored the instant the agent produces output.

## Lesson

- **Before adding a backoff/exemption/override layer to an existing rate- or tier-setting API, find every place that compares against "the current value" and check which value it means.** A same-value early-return almost always means "same as last requested" — once your new layer can independently change the live value, give "requested" its own field or the guard will swallow re-requests made while the override is live.
- **This is not a one-off: the same shape of bug already shipped once in #8998** (`TerminalHibernationManager`'s same-tier `BACKGROUND` no-op swallowing a needed reschedule). Treat "does a same-value/same-tier no-op guard exist here, and can something else now change this state out from under it" as a standing review question for any tiered/rate-limited subsystem.
- **The wake/restore path must read the requested value, never a hardcoded default.** `cancelFsmIdleBackoff(true)` restores `requestedPollingIntervalMs`, not the pre-backoff 50ms constant — a visibility change that arrived mid-backoff (e.g. 500ms) is what gets restored, not the original rate.
- **When gating a repeated expensive operation with both a dirty-check and a throttle, check the dirty flag first.** `flushEventDrivenAsync` checks `contentEpoch === lastFlushedEpoch` before the `EVENT_DRIVEN_SNAPSHOT_THROTTLE_MS` timestamp check, so an unchanged buffer returns without touching `lastEventDrivenFlushAt` — it never eats the throttle slot a later changed-content flush needs.
- **Converting a sync host callback to async on a shared event loop needs a post-await lifecycle re-check** — mirror the established `persistAsync()` pattern rather than inventing a new one: `flushEventDrivenAsync` re-checks `this.disposed || this.host.wasKilled` after awaiting `getSerializedStateAsync()`, so a kill/dispose during the await can't let a stale async write stomp the sync snapshot `kill()` already wrote.

## Applies when

- Adding any backoff, exemption, or override mechanism on top of an existing rate/tier/interval-setting API that already has a same-value no-op guard (`ActivityMonitor.setPollingInterval`, `TerminalRendererPolicy.applyRendererPolicy`'s tier-equality guard, or similar).
- Reviewing a PR that introduces a second writer to a field previously written only by one setter — ask whether any comparison against that field assumed single-writer semantics.
- Diagnosing "a visibility/tier/setting change I made isn't taking effect" where the target subsystem has any idle/background/settled state that can override live values independent of the caller.
- Touching `electron/services/ActivityMonitor.ts` polling cadence or `electron/services/pty/SessionSnapshotter.ts` event-driven flush — the requested/applied split and the epoch-before-throttle ordering are load-bearing, not incidental style choices.
- Adding a dirty-check alongside an existing throttle/debounce on a repeated expensive operation — order the checks so the cheap dirty-check runs first and never consumes the throttle window on a no-op.
