## Context

Daintree's UI is Tailwind v4 + React. Hundreds of interactive elements (buttons, inputs, Radix menu items, focusable rows) suppress the default browser outline with a Tailwind utility and paint their own focus indicator via a `ring-*` (box-shadow) or border-color shift. Windows High Contrast / `forced-colors: active` is a supported target — `src/index.css` has a dedicated `@media (forced-colors: active)` block that recolors focus via system color keywords (`Highlight`, `ButtonText`).

## Problem

A seemingly cosmetic Tailwind utility — `outline-none` — silently removed the visible focus indicator for keyboard users in forced-colors / Windows High Contrast mode across ~200 call sites in 96 files. Invisible in normal development and testing; only manifests when the OS forced-colors palette is active, where the UA strips `box-shadow` (so the `ring-*` fallback is gone too), leaving the element with no focus indicator at all.

## Root cause

Tailwind v3's `outline-none` emitted `outline: 2px solid transparent` — a real but transparent outline that forced-colors mode could recolor into a visible ring. Tailwind **v4 redefined `outline-none` to emit `outline-style: none`**, which removes the outline box entirely; there is nothing left for the system to paint. The v3 transparent-outline behavior moved to the new `outline-hidden` utility. So a same-named utility quietly changed semantics across a major version, and because the breakage is gated behind `forced-colors: active` it passes every normal review and test. The `ring-*` focus fallback doesn't save it: forced-colors strips `box-shadow`, so the transparent outline was the only thing keeping the focus ring visible.

## Lesson

- In Tailwind v4, **never use `outline-none` to merely hide the default outline** when the element supplies its own focus indicator. Use `outline-hidden` (preserves a transparent outline forced-colors can recolor). Reserve bare `outline-none` for the rare case of genuinely suppressing all focus indication (internal scrollbar regions, debug overlays).
- A `ring-*` (box-shadow) focus ring is NOT a forced-colors fallback — `box-shadow` is stripped under `forced-colors: active`. Any element that hides its outline must keep either `outline-hidden` or a same-element `focus:`/`focus-visible:`/`data-[macro-focus]:` indicator, AND chrome that relies on `box-shadow`/`background-color`/`border-color` to signal focus/selection needs an explicit `@media (forced-colors: active)` rule in `src/index.css` using system color keywords (`Highlight`, `ButtonText`, `SelectedItem`, `GrayText`).
- Two contract tests enforce this — keep them green and extend them, don't suppress: `outlineHidden.contract.test.ts` forbids any `\boutline-none\b` in non-test `src` files; `focusRingFallback.contract.test.ts` flags bare `outline-hidden` lacking a same-element focus indicator and treats `outline-none`/`outline-hidden`/`ring-0`/`border-transparent` as non-indicators (suppressors).
- Same trap class for any Tailwind v3→v4 utility whose name survived but whose emitted CSS changed — don't assume a familiar class name still means what it did.

## Applies when

- Adding or editing any Tailwind `className` that suppresses the browser focus outline (`outline-none`, `outline-hidden`, `focus:outline-*`, `focus-visible:outline-*`) on buttons, inputs, links, Radix menu/select items, or focusable rows.
- Building focus/selection indicators with `ring-*`, `box-shadow`, `background-color`, or `border-color` and needing them to survive Windows High Contrast / `forced-colors: active`.
- The `outlineHidden.contract.test.ts` or `focusRingFallback.contract.test.ts` contract tests fail in CI.
- Touching the `@media (forced-colors: active)` block in `src/index.css` (the macOS-only `prefers-contrast: more` block is separate and must stay separate).
- Upgrading Tailwind across a major version, or porting v3-era class strings — auditing utilities whose names are unchanged but emitted CSS differs.
- Accessibility/a11y review of keyboard focus visibility on Windows.
