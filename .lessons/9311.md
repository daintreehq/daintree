## Context

The React UI does not live in the `BrowserWindow`'s own `webContents`. It lives in a child `WebContentsView` (`appView` in `electron/window/createWindow.ts`), part of the WebContentsView-per-project architecture (#4672). The window is created with `show: false`; `loadRenderer()` calls `appWebContents.loadURL()` and then must reveal the window. In E2E mode the BrowserWindow's own webContents loads only an empty `data:` sentinel page so Playwright's CDP `electron.launch()` gets a target.

## Problem

Cold start showed a blank-window flash: the OS mapped the window before the React HTML skeleton had parsed, so users saw the bare window chrome/background before any content. The original code called `win.show()` immediately after `loadURL()` (show-before-paint). The e2e suite hid this by forcing `DAINTREE_EARLY_RENDERER=0` (a serial boot path), so tests exercised a path that diverged from production and never caught the race.

## Root cause

The canonical Electron fix — gate `win.show()` on `webContents.on("ready-to-show")` — silently does NOT work here. `ready-to-show` tracks the BrowserWindow's _own_ webContents first paint, but the React app paints in the child `WebContentsView`, whose webContents is a separate object (`appView.webContents`). The BrowserWindow's own webContents either never loads real content or loads the empty `data:` sentinel, so `ready-to-show` either never fires meaningfully or fires immediately on the empty page — neither correlates with the React skeleton being parsed. The correct signal is `dom-ready` on `appWebContents` (the WebContentsView's webContents). Secondary trap: the gate listener must be registered BEFORE `loadURL()`, because a cached/synchronous navigation can emit `dom-ready` synchronously and slip past a listener wired afterward.

## Lesson

- Under WebContentsView-per-project, `ready-to-show` is the wrong hook for "the app has painted." Gate `win.show()` on `dom-ready` of the child `appView.webContents`, not on any BrowserWindow-level event.
- Wire the `appWebContents.once("dom-ready", showOnce)` listener BEFORE calling `appWebContents.loadURL()` — a cached load can fire `dom-ready` synchronously inside/just-after `loadURL`.
- Always pair a paint-gated `show()` with a fallback timer (5s here) so a hung renderer can't leave the window permanently hidden (a stuck-hidden window is strictly worse than a brief blank). Clear the timer in `win.once("closed")` so the closure isn't held alive after an early close, and guard `showOnce` with a `shown` flag so the timer and `dom-ready` can't double-fire `win.show()`.
- Don't paper over a production boot race with an e2e-only env flag that selects a different code path (`DAINTREE_EARLY_RENDERER`). If tests pass only because they run a diverged boot path, the suite is testing a mock. Fix production so e2e can run the real path; keep test-only flags only for genuine harness coexistence constraints (e.g. `DAINTREE_E2E_DEFER_RENDERER_LOAD` for Playwright CDP target ordering on Windows).

## Applies when

- Adding or changing window-reveal / first-paint timing in `electron/window/createWindow.ts` (`loadRenderer`, `win.show()`, `setupBrowserWindow`).
- Reaching for `ready-to-show` to eliminate a blank-window / white-flash on startup in this app — it will not fire for the React UI because that UI is in a child WebContentsView.
- Touching the early-renderer boot path (`electron/window/windowServices.ts`, `electron/window/earlyRenderer.ts`) or the parallel-with-PTY-init renderer load.
- Debugging "window shows before content paints," cold-start flash, or a window that loads but stays hidden.
- Wiring any `dom-ready` / navigation-event listener around `loadURL()` and worrying about cached/synchronous navigations slipping past.
- Finding an e2e-only env flag (`DAINTREE_*`) that switches production code paths and wondering whether it masks a real bug.
