## Context

Dev Preview detects a dev-server URL on stdout, then `pollServerReadiness` calls `waitForServerReady` (`DevPreviewReadinessProbe.ts`) — HEAD/GET probes at 500ms intervals up to 30s — before flipping the session to `running`. Lesson #2265 established this poll-before-running pattern and the signal-identity guard. This PR refines what counts as "ready" and adds two faster/safer paths on top of it.

## Problem

A Next.js dev server returns HTTP 500 while it is still compiling — the listener is bound but the app is a not-ready shell. The original probe accepted any `status >= 100 && status < 600`, so a 500 compiling shell flipped the panel to `running` and rendered an error page as if startup succeeded. Separately, when a dev-server error (e.g. missing dependencies) was detected in `handleData`, the already-in-flight readiness poll was not cancelled — a slow HEAD that later succeeded would overwrite the freshly-set `error`/`installing` status with `running`. And cold starts paid the full 500ms poll interval even after the framework had already printed "ready".

## Root cause

"The HTTP listener answers" is not the same as "the app is ready". A bound socket returning 5xx is a compiling shell; only 2xx/3xx (and historically 4xx — a 401-gated or 405-to-HEAD server that is alive and routing) signal real readiness. The current code went further: `probeUrl` returns a three-state `ProbeResult` (`"ready" | "5xx" | "fail"`), and `waitForServerReady` requires a 5xx to be followed by a confirming `"ready"` before resolving (`hasSeen5xx`/`awaitingConfirmation`), because a server can flap 200→500→200 mid-compile. The in-flight-poll-clobbers-error bug is a classic async ordering race: the poll promise and the error-detection path both mutate session status, and whichever settles last wins — invisible until a slow probe happens to win.

## Lesson

- Treat 5xx as **not ready**, not as "reachable therefore ready". A bound listener returning 500 is a compiling shell. Only resolve on 2xx/3xx; if you must tolerate a 5xx blip, require a subsequent confirming success (`hasSeen5xx` then `"ready"`) rather than accepting the first 5xx.
- Fast-path the poll on framework stdout readiness markers (`UrlDetector.READY_MARKERS`: Vite `ready in N ms`, Next.js `✓ Ready in`, webpack `compiled successfully`), matched against ANSI/OSC-stripped output. On a marker, abort the sleeping poll and re-probe immediately instead of waiting out the 500ms interval. Keep the poll as the fallback for unrecognized frameworks so "no marker" means "no behavior change".
- Guard the marker fast-path with a one-shot flag (`session.markerSeen`) AND **reset it on every new URL** (port change starts a fresh poll that deserves its own acceleration). The flag prevents repeated abort/re-probe churn within one poll.
- When you detect a terminal error, **abort the in-flight readiness poll** (`session.readinessAbort?.abort(); readinessAbort = null; pendingUrl = null; markerSeen = false`) before setting `error`/`installing`. Otherwise a slow probe that wins the race flips the session back to `running` and clobbers the error state.
- This is additive to the #2265 signal-identity guard (`if (session.readinessAbort?.signal !== signal) return`). The identity guard stops a _stale_ poll from a superseded generation; aborting-on-error stops the _current_ poll whose error you just discovered.
- The readiness gate was later narrowed further (4xx no longer ready; 2xx/3xx only) and layered with an HMR-WebSocket handshake in #9317 — see it for the WebSocket/Origin-CVE/`ws` side of the same probe.

## Applies when

- Deciding what HTTP status counts as "ready" for any local dev server (Vite/Next.js/webpack) probe, or debugging a dev preview that flips to `running` while showing a compile-error page.
- Adding or tuning readiness/HMR/compile stdout markers in `UrlDetector.ts`, or touching `READY_MARKERS`/`COMPILE_MARKERS`/`markerSeen` and the marker fast-path in `DevPreviewSessionService.handleData`.
- Any place where an async poll promise and a synchronous state-mutation path (error detection, stop, restart) can both write the same session status — verify the slow async winner cannot clobber the newer state by aborting the poll, not just guarding the signal identity.
- Investigating why a `missing-dependencies` / dev-server error briefly shows then reverts to `running`, or why cold-start dev preview feels ~500ms slower than the framework's own "ready" line implies.
