## Context

Every terminal spawn — one-off or part of a fanout — goes through the same IPC path in `electron/ipc/handlers/terminal/lifecycle.ts` and shares one global rate limiter, `waitForBurstRateLimitSlot("terminalSpawn", 1_000, 6)` (added by #5352 to stop overload from rapid manual spawning or MCP-driven parallel launches). Recipes (`src/store/recipeStore.ts`, saved parameterized multi-agent launches) and bulk GitHub issue-worktree creation (`plugins/builtin/github/renderer/components/BulkCreateWorktreeDialog.tsx`) both fan out many terminal spawns through that exact same path and therefore the exact same limiter.

## Problem

Launching a 10-agent recipe took 6.1s: the limiter let 6 terminals through instantly (the burst), then throttled the remaining 4 to one per second. The obvious fix — raise the burst from 6 to 10 — didn't just fail to help, it made repeated launches worse: running the same recipe a few times in a row left later launches just as slow as before, because the limiter is a leaky bucket, not a per-call budget.

## Root cause

`waitForLeakyBucketSlot` in `electron/ipc/utils.ts` keeps one persistent `nextAvailableMs` per string key (here `"terminalSpawn"`) across every caller. Each reservation clamps the slot from below at `now - (burst-1) * intervalMs`, so the burst only controls how much _idle_ time can be banked — it does nothing once `nextAvailableMs` is already ahead of `now`. A 10-terminal fanout advances that watermark by 10 seconds of schedule; if the same recipe runs again before the bucket idles back down, the new spawns queue behind the OLD debt no matter what the burst constant is set to. Raising the ceiling doesn't erase accrued debt — the mechanism counts _mechanical spawn events_, and a legitimate bulk operation generates a lot of those in quick succession by design.

The fix changes what counts as one admission, not how many are allowed: `recipeStore.ts` assigns one `spawnBatchId` (`crypto.randomUUID()`) and a declared `spawnBatchSize` (PTY-only count, `dev-preview` panels excluded) to every panel in a bounded fanout, threaded through `shared/types/addPanelOptions.ts` → `electron/schemas/ipc.ts`'s `TerminalSpawnOptionsSchema`. In `lifecycle.ts`, `claimRecipeSpawnBatchAdmission` looks up the batch: the first caller for a given `batchId` requests exactly one slot from a _separate_ bucket key (`"terminalRecipeSpawnBatch"`, 1/s, burst 1), and every subsequent caller with the same `batchId` awaits that same already-in-flight promise instead of requesting its own slot. Two guards keep this safe: `batchSize` is capped (`MAX_TERMINALS_PER_RECIPE` = 10 for one recipe run, `MAX_TERMINALS_PER_RECIPE_ADMISSION_BATCH` = 30 for the bulk case added in #11044), and each admission record self-deletes after `RECIPE_SPAWN_BATCH_TTL_MS` = 30s so a partial/crashed fanout can't wedge the map forever. Ordinary one-off spawns never set a `spawnBatchId` and fall through to the untouched 6-burst/1s guard.

## Lesson

- **A leaky bucket keyed by a shared string persists debt across unrelated calls** — `nextAvailableMs` in `electron/ipc/utils.ts` doesn't reset per caller or per burst window, so raising the burst constant only raises how much idle time can be banked, not how fast an already-indebted key recovers. If "raise the limit" doesn't fix a batch slowdown (or makes repeats worse), suspect accrued state in a shared bucket key before tuning constants further.
- **Fix batch throttling by changing the unit of admission, not the ceiling**: identify the batch at its origin (`recipeStore.ts` assigns `spawnBatchId`/`spawnBatchSize` once, before dispatching each `addPanel` call), thread it through the whole IPC boundary, and have the handler claim exactly one limiter slot for the whole group (`claimRecipeSpawnBatchAdmission`). This is "rate-limit by confirmed user intent, not by mechanical action count" — reusable anywhere a legitimate bulk op shares a limiter with routine single actions.
- **A shared batch admission needs both a size cap and a TTL or it becomes a new hazard**: without `MAX_TERMINALS_PER_RECIPE_ADMISSION_BATCH` a caller could claim unlimited spawns through one slot; without the 30s expiry (`RECIPE_SPAWN_BATCH_TTL_MS`) a fanout that fails before every declared panel spawns wedges that `batchId` in `recipeSpawnBatchAdmissions` — any retry reusing the id would silently hang.
- **The pattern generalizes to a coarser unit, not just a bigger one**: #11044 reused it verbatim for bulk issue-worktree creation via `planBulkRecipeSpawnBatches` in `bulkCreateUtils.ts`, chunking above the 30-terminal cap into multiple admission batches instead of raising the cap further — "one confirmed operation" became "one issue's worth of terminals," still bounded and expiring the same way.
- **The same PRs also fixed a sibling "mechanical time" bug**: a fixed `VERIFICATION_SETTLE_MS` (800ms unconditional wait after bulk worktree creation) became event-driven `waitForPanelSpawns` plus a short settle (`VERIFICATION_SPAWN_WAIT_MS`=700 / `VERIFICATION_EXIT_SETTLE_MS`=100 in `bulkCreateUtils.ts`) — if a batch-admission fix alone doesn't make a bulk flow feel fast, check for a sibling fixed-delay wait on the same path.

## Applies when

- Adding a new bulk/fanout entry point that spawns multiple terminals through `terminal:addPanel` or any path gated by `waitForBurstRateLimitSlot("terminalSpawn", ...)` in `electron/ipc/handlers/terminal/lifecycle.ts`.
- Diagnosing "a batch operation is slow, and raising the burst limit didn't help (or made repeats worse)" — check `waitForLeakyBucketSlot` in `electron/ipc/utils.ts` for a persistent `nextAvailableMs` under the same key before assuming the constant is just too low.
- Touching `recipeStore.ts`'s recipe fanout, `BulkCreateWorktreeDialog.tsx` / `bulkCreateUtils.ts`'s `planBulkRecipeSpawnBatches`, or `MAX_TERMINALS_PER_RECIPE` / `MAX_TERMINALS_PER_RECIPE_ADMISSION_BATCH` in `shared/utils/recipeSanitizer.ts`.
- Reviewing any rate limiter shared between a routine single action and a legitimate bounded-batch action — confirm the batch path gets its own bounded, expiring admission group rather than one raw slot per action.
- Replacing a fixed post-batch settle-time wait with an event-driven completion signal — grep `VERIFICATION_..._MS` in `bulkCreateUtils.ts` for the precedent.
