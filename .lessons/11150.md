## Context

`panelFocusRegistry.ts` (renamed from `terminalFocusRegistry.ts` in #11132, which also fixed macro-grid Enter silently swallowing input on non-terminal panels, issue #11109) is a panel-id → "focus your primary target" handoff map, keyed by panel id and blind to panel kind. `TerminalPane` has always carried its own reactive `useEffect` that claims real DOM focus whenever it becomes `focusedId`; that effect is why terminal panes felt correct while the surrounding focus system was not. #11150 (issue #11133) is the follow-up that found the registry's existence was not the whole story.

## Problem

Users reported "I typed a prompt and it's not there": a pane looked selected (highlighted) but kept receiving no keystrokes, or keystrokes landed in a pane the user had left minutes earlier. It read like a text-input bug in one specific panel, which misdirected debugging — the actual divergence was between `usePanelStore`'s `focusedId` (which only paints a highlight) and `document.activeElement` (which is what the browser actually delivers keys to).

## Root cause

Three independent gaps stacked to produce the symptom.

1. **Registry invocation gap.** The registry was only _invoked_ by macro-grid Enter and in-group tab switches. Every other path that changes `focusedId` — arrow navigation, Cmd+1..9, `focusNext`/`focusPrevious`, agent-state cycling, worktree restore — just wrote the store field and stopped. `ContentPanel`, `ReviewPane`, and `PluginViewHost` had no reactive claim analogous to `TerminalPane`'s, so a non-PTY panel could become `focusedId` and never receive real focus. Fixed with `usePanelRootFocus`, a shared hook giving every non-PTY panel kind the same reactive claim, yielding when focus is already inside the panel (so it doesn't yank the caret out of FilePane's search box or a plugin's own input).
2. **`moveBefore` preserves focus into hidden containers.** `DockPanelOffscreenContainer.moveToDestination` parks a closed/backgrounded dock pane by relocating its wrapper element into an offscreen container that is `aria-hidden` and `content-visibility: hidden`, using Chromium's `moveBefore`. `moveBefore` is designed to carry DOM focus across the move — unlike `appendChild`, which drops it — so a focused dock pane that got closed kept the keyboard, now sitting inside a container the user cannot see or reach. The container being visually and semantically hidden does nothing to stop it receiving keystrokes. Fixed by blurring the active element (`active.blur()`) before parking whenever the destination is `null` and the moved wrapper currently holds focus, and by having `closeDockTerminal(expectedId)` reconcile `focusedId` onto a visible grid pane afterward.
3. **Liveness was assumed, not checked.** `isOpened` / instance-map membership was treated as "this pane can take focus," but it is `true` before an xterm has actually opened and stays `true` after detach. Handlers now report success only by checking that `document.activeElement` actually moved, never by trusting a boolean flag. Similarly, `focusWithCursorAtEnd` schedules its work in a `requestAnimationFrame` and can bail silently if the hybrid editor isn't mounted yet — it now returns whether it actually had an editor to focus, so a caller (like the grid's Enter handler) can decline the handoff instead of releasing keyboard control on a handoff that never happened.

## Lesson

- **A store field that only drives a visual "selected" state (`focusedId`) is not proof that real DOM focus moved** — audit every setter of that field, not just the ones that happen to invoke a focus registry, before trusting that "selected" means "receives keystrokes."
- **`moveBefore` carries DOM focus across an element relocation by design, including into `aria-hidden`/`content-visibility:hidden` containers.** Any code that reparents live subtrees (dock parking, portal moves, offscreen pooling) must explicitly blur before parking if the moved subtree might hold focus — `appendChild` silently drops focus, which is exactly why this class of bug hides until code is optimized to use `moveBefore`.
- **Registration/mount flags (`isOpened`, instance-map membership) are not liveness.** A component can be registered before it is actually focusable and remain registered after teardown. Verify a focus handoff succeeded against `document.activeElement`, never a boolean.
- **A focus-handoff function that schedules work in a `requestAnimationFrame` and returns `void` cannot report success to its caller** — make it return whether a real target existed to focus, so callers (e.g. "release the macro grid region only on success") can decline instead of silently going dead.
- **Give every panel kind the same reactive "claim focus when I become focused" hook** (`usePanelRootFocus`) rather than special-casing one kind (Terminal) and leaving every other kind to whichever code path happens to remember to call the registry.

## Applies when

- Touching arrow-key navigation, Cmd+1..9, `focusNext`/`focusPrevious`, agent-state cycling, worktree restore, or any other path that writes `usePanelStore`'s `focusedId` directly.
- Introducing or reviewing use of `moveBefore` anywhere in the codebase — assume it carries focus with it, hidden destination included.
- Diagnosing "I typed and it's not there," keystrokes landing in the wrong pane, or a visibly highlighted pane that receives no input.
- Adding a new `PanelInstance` kind — wire it through `usePanelRootFocus` (or its own registry handler like `ReviewPane`/`PluginViewHost`) or Enter/focus-follow will silently no-op for it.
- Reviewing any focus-handoff function that returns `void` where a caller downstream needs to know whether the handoff actually completed.
