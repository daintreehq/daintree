## Context

`PtyHostLifecycle` supervises the pty-host UtilityProcess. When the host exits, `handleExit(code)` and `classifyCrash(code, signal)` turn the numeric exit code into a `CrashType` and a synthetic signal string for `host-crash-details` telemetry. The UtilityProcess `exit` event gives a code but no signal, so the code historically inferred one from the POSIX convention `code = 128 + signum` (e.g. 143 → SIGTERM).

## Problem

On Windows the same numeric exit-code field carries an entirely different meaning: uint32 NTSTATUS values. `STATUS_ACCESS_VIOLATION` is `0xC0000005` = 3221225477. The unguarded `code > 128 ? \`SIG${code - 128}\``heuristic happily ran on Windows and emitted nonsense like`"SIG3221225349"`into crash telemetry, and`classifyCrash`mislabeled every large NTSTATUS exit as`SIGNAL_TERMINATED`instead of`UNKNOWN_CRASH`. The bad data was silent — nothing crashed, the telemetry was just wrong.

## Root cause

`code = 128 + signum` is a POSIX shell/wait convention, not a universal one. Windows does not signal-encode exit codes; large exit codes are NTSTATUS bit-fields. The heuristic was applied universally on a field whose semantics are platform-dependent, so the same arithmetic that decodes a signal on Linux/macOS corrupts a status code on Windows. The boundary value 140 even collides — it is a plausible POSIX `SIG12` and also a perfectly legal small Windows exit code — so there is no value-range test that disambiguates; only the platform does.

## Lesson

- Any time you decode a process exit code as a POSIX signal (`code - 128`, `code > 128 → SIGNAL_TERMINATED`, `SIG${...}` string synthesis), gate it on `process.platform !== "win32"`. On Windows let large codes fall through to `UNKNOWN_CRASH` / `null` signal rather than minting a fake signal name.
- Authoritative signals (the `signal` argument from `child-process-gone`) and special-cased codes (137 OOM, 134 SIGABRT) are still valid cross-platform and must be checked _before_ the platform-gated heuristic — don't let the Windows gate swallow them.
- Secondary takeaway from the same PR: supervisor backstop/restart/TTL timers (`disposeTimer`, `restartTimer`, `TerminalRegistry` trash TTL) must `.unref?.()` so a pending `setTimeout` never pins the Electron event loop alive past `app.quit`. Use `.unref?.()` (optional call) because the mocked timer in tests may not implement it.

## Applies when

- Editing `PtyHostLifecycle.classifyCrash` / `handleExit`, or any new code mapping a UtilityProcess/child-process exit `code` to a crash type or signal name.
- Adding crash/exit telemetry (`host-crash-details`, agent-exit classification) that derives a signal from a numeric code.
- Reviewing exit-code or signal-classification code for Windows correctness — watch for `code - 128`, `code > 128`, `SIG${...}`, or NTSTATUS values (3221225477 / 0xC0000005 and friends) leaking into logs.
- Auditing pty-host / supervisor timers for event-loop hygiene at shutdown (`setTimeout` handles that should be `.unref()`d).
