## Context

`ProjectStore.getAllProjects()` backs the ordered project list (`ORDER BY frecency_score DESC, last_opened DESC`) and is called far beyond "list projects on screen": `HibernationService`, `IdleBackgroundAutoCloseService`, `IdleTerminalNotificationService`, and `ProjectStatsService` poll it every few minutes, `menu.ts` rebuilds from it, `globalServicesInit.ts` reads it at startup, and two `app:state` IPC handlers return it directly. It also reconciles `status` to a singleton keyed on the current-project pointer on every call — demoting every other row's stale `"active"` status to `"background"` — because `setCurrentProject` deliberately leaves that reconciliation to the reader (`ProjectStore.ts:913`) rather than doing it eagerly on write. Issue #10907 named three main-process persistence paths (this one, the agent-session journal, `window-states.json`) slowing down as usage history grows across restarts; PR #10913 fixed all three.

## Problem

The app's main-process persistence got slower the longer a user had been using it — not a crash, not a correctness bug, just accumulating per-call cost with no code path that looked wrong in isolation. `getAllProjects()` full-table-scanned on an unindexed sort, and separately, every single call — even when every row's status was already correct — opened `db.transaction(fn, { behavior: "immediate" })` around the reconciliation loop. That looks like an ordinary read function; nothing in its signature or call sites signals "this takes a write lock."

## Root cause

better-sqlite3's `IMMEDIATE` transaction behavior acquires SQLite's write (RESERVED) lock the instant `BEGIN IMMEDIATE` executes, not lazily on the first actual write inside it. The old code wrapped the _entire_ per-row status-check-and-repair loop in one `db.transaction(callback, { behavior: "immediate" })`, so even the steady-state case — every row already correctly reconciled, the common case on a repeat read — still paid for a real BEGIN IMMEDIATE / COMMIT pair, because nothing checked first whether any row actually needed a change. With four+ periodic services plus menu/startup/IPC callers, that unconditional lock-per-call wasn't an edge case, it was the hot path.

The fix (current `ProjectStore.ts:715-767`) restructures this as check-then-transact: iterate the rows from the initial `SELECT`, push each drifted row into a `statusUpdates` array while mutating the in-memory row so the returned data is always reconciled, then call `db.transaction(...)` only `if (statusUpdates.length > 0)`. The common already-correct read now opens zero transactions. Separately, migration `0006` added `projects_path_idx` (equality index for `getProjectByPath`) and `projects_frecency_last_opened_idx` on `(frecencyScore, lastOpened)` — both declared in natural ascending order in `schema.ts`, even though the live query sorts both columns `DESC`. Not an oversight: SQLite can walk a compound index backwards when the ORDER BY terms are all reversed relative to its declared direction (all-DESC against an all-ASC index), so an ASC/ASC index still lets the planner skip the sort. The PR verified this with `EXPLAIN QUERY PLAN` rather than assuming a descending index definition was required.

## Lesson

- **Any function whose name reads like a query but that opportunistically repairs drifted state must check _before_ opening the write transaction, not wrap the check inside it.** `db.transaction(fn, { behavior: "immediate" })` takes the write lock the moment `BEGIN` runs, independent of whether `fn` ends up writing anything — wrap only the confirmed-dirty rows.
- **An unconditional write-lock inside a "read" is a hot path by construction wherever the function has wide fan-in.** `getAllProjects()` has 4+ periodic pollers plus menu/startup/IPC callers — before assuming a lock inside a read is cheap, check how many places call it and how often.
- **A compound sqlite/drizzle index doesn't need to match ORDER BY direction literally.** Declare it in natural ascending order (`index(...).on(colA, colB)`); SQLite reverse-scans a same-relative-direction index to serve an all-`DESC` sort. Confirm with `EXPLAIN QUERY PLAN` rather than assuming you need a descending index definition.
- **When you fix "opens a transaction unconditionally," assert the stronger claim.** This PR's test was upgraded from "empty transaction" (`vi.spyOn(db, "update")` only) to "no transaction opened" (`vi.spyOn(db, "transaction")` not called) — spying only on `update` would still pass against the old, slower code, since an empty transaction body never calls `update` either.
- **A read-through cache returning its backing array by reference must document that contract loudly.** `agentSessionHistory.ts`'s stat-gated cache (`historyCache`, keyed on file `size`+`mtimeMs`) returns the cached array _by reference_ on a hit; its comment warns callers must never mutate it in place, since a caller that sorts/splices the shared array would corrupt every later cache hit.

## Applies when

- Writing or reviewing any `ProjectStore.ts` accessor, or any drizzle/better-sqlite3 accessor elsewhere, that reads-and-reconciles (status normalization, frecency decay, similar drift-repair) — check whether its transaction opens unconditionally or only when something is actually dirty.
- Adding a sqlite/drizzle index meant to serve an `ORDER BY col DESC[, col2 DESC]` query — don't assume the index must be declared descending; verify with `EXPLAIN QUERY PLAN` whether an ascending index plus a reverse scan already avoids the sort.
- Diagnosing "the app gets slower the longer I've used it" complaints rooted in main-process persistence — check functions with heavy fan-in (periodic services, menu, startup, IPC) for locks or full scans that don't need to run on every call.
- Adding a stat-gated or any read-through cache over a JSON file that returns shared array/object references — confirm every consumer treats the result as read-only, or return a defensive copy instead.
- Reviewing a test asserting a transaction-skipping fix that only checks "the write call wasn't invoked" — confirm the stronger claim (the transaction itself was never opened) is what actually needs to hold.
