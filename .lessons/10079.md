## Context

The pty-host drops bytes (drop-don't-block) under heavy output and signals it to the renderer; `injectDataLossMarker` re-encodes that as private-use OSC 57301 (#8375) so `TerminalParserHandler` can call `drawDataLossMarker` — the yellow "Output dropped (~N bytes)" line, wired as the parser handler's 3rd ctor arg in `getOrCreate()`. In the hibernation era, `TerminalHibernationManager.unhibernate()` was a second full construction path rebuilding the xterm instance and parser handler on wake. This dual-path had already bitten once: #6674 extracted `TerminalListenerInstaller.ts` as the single canonical listener installer after the wake path silently lost three listeners (lesson `6674.md`).

## Problem

After any hibernate→wake cycle, the data-loss marker never rendered again for that terminal's life (#9907). No error, no garbled escape bytes, no console warning — pure absence of a signal the user didn't know to expect. Worse, the affected population was exactly the long-lived background terminals most likely to hit pty-host drops, so the warning died precisely where it mattered. Nothing pointed at the wake path; you had to diff the two `new TerminalParserHandler(...)` call sites by eye.

## Root cause

`unhibernate()` recreated `TerminalParserHandler` with only 2 of its 3 ctor args — `managed` and the buffer-exit resize callback — omitting `onDataLoss`. Three mechanisms compounded to make this invisible. (1) The ctor params are optional (`onBufferExit?`, `onDataLoss?`), so the omission type-checked clean. (2) The OSC 57301 handler consumes the sequence unconditionally — `this.onDataLoss?.(droppedBytes); return true;` — deliberately, so malformed payloads never leak into the buffer; but that same choice means a missing observer yields zero symptom instead of visible escape garbage. (3) Both hibernation suites `vi.mock`ed `TerminalParserHandler` with a 2-arg ctor, so no unit test could even observe production passing 2 of 3 args. Critically, this recurred the exact antipattern #6674 had structurally "fixed": the canonical installer covered xterm listeners, but parser-handler construction stayed duplicated outside its boundary — so it drifted the same way after #8375 widened the create path. The fix made `drawDataLossMarker` a required (non-optional) field on `HibernationManagerDeps`, mirrored the ctor call, and added a mock capturing the 3rd arg to assert it fires through to the dep.

Status: hibernation was removed wholesale by #10811, so `TerminalHibernationManager` / `HibernationManagerDeps` — including this fix — are gone; one `TerminalParserHandler` ctor site remains (`getOrCreate()`). But the enabling shape survives verbatim: the ctor callbacks are still optional, the OSC 57301 handler still always-consumes, `TerminalListenerInstaller` is still the canonical install surface, and new dual paths keep appearing (`TerminalRestoreController`, crash-recovery re-attach, `paintFabric/PaintFabricCompositor`'s parallel `injectDataLossMarker` plane).

## Lesson

- **A canonical shared function only prevents drift for wiring inside its boundary.** #6674 unified listener install after three listeners drifted; the parser-handler ctor stayed outside the installer and drifted identically months later. When unifying dual lifecycle paths, enumerate ALL per-instance wiring — listeners, parser handlers, addons, callbacks — and treat anything left outside the shared function as the next drift site, not as "done".
- **An optional callback on an always-consume handler is a perfectly symptomless failure mode.** `onDataLoss?.(droppedBytes); return true;` swallows both the signal and the escape sequence when nobody is wired — no marker AND no leaked bytes to notice. This shape still exists in `TerminalParserHandler` today. If a handler consumes unconditionally, its observer must be compile-required at some boundary; otherwise a missed hookup can never announce itself.
- **Express lockstep contracts as required deps fields, not convention.** The fix made `drawDataLossMarker` non-optional on the deps interface so a forgetful future path fails typecheck. "Mirror getOrCreate() exactly" comments did not hold; the type system did. A callback that multiple construction paths must wire belongs as a required member of every `*Deps` interface it crosses.
- **Mocking a class in every consuming suite hides ctor-arity drift.** Two suites mocked `TerminalParserHandler` with the old 2-arg signature, so the missing 3rd arg was untestable by construction. Keep at least one test capturing the real call's arguments, and update mock signatures whenever the real ctor widens.
- **Restore-path bugs concentrate in the population that most needs the broken feature.** Long-lived parked terminals both travel the rebuild path and are likeliest to hit data loss. When a signal exists for long-lived sessions, test it through the rebuild cycle, not just cold create.

## Applies when

- Adding any construction, restore, or rehydrate path that re-creates per-terminal handlers (`TerminalRestoreController`, crash-recovery re-attach, paint-fabric plane adoption, panel restore) — mirror `getOrCreate()`'s full wiring or route through a shared installer.
- Touching `TerminalParserHandler` ctor args, `TerminalListenerInstaller`, or any `*Deps` interface that exists to keep two paths in lockstep — new callback fields must be required, not optional.
- Diagnosing a terminal feature that works on fresh terminals but silently stops after a rebuild cycle (restore, renderer swap, plane migration) with zero error output — diff the construction call sites first.
- Reviewing a parser/OSC handler that returns `true` unconditionally while invoking an optional callback — that combination hides any missed hookup forever.
- Widening a mocked class's ctor — grep for every `vi.mock` of it; stale mock arities create suites that structurally cannot catch the drift.
