## Context

`PluginContributionBroadcaster` fires several similarly-named renderer broadcasts on behalf of `PluginService` — `plugin:panel-kinds-changed` (coalesced per-tick whenever a panel kind registers/unregisters) and `plugin:provenance-changed` (explicit, fired from install/uninstall/enable-toggle paths) are two of the nine distinct `plugin:*-changed` events across the plugin system (the other seven: `actions-changed`, `toolbar-buttons-changed`, `keybindings-changed`, `context-menu-items-changed`, `agents-changed` from the broadcaster, plus `decorations-changed` and `panel-badges-changed` fired directly by `PluginService`/`PluginHostFactory`). #11214 built a plugin-render-error diagnostics fallback (`PluginViewDiagnosticsFallback.tsx`, replacing the generic `ErrorFallback` at the plugin boundary per issue #11207) whose detail depth gates on the owning plugin's `devMode` flag rather than `import.meta.env.DEV`, since plugin authors build against a production Daintree install where the app's own build-mode flag is always false. The new `pluginRuntimeStore` mirrors per-plugin `devMode` in the renderer, refreshed on `plugin:provenance-changed` — the same signal `PluginsTab`/`usePluginManager` already followed.

## Problem

While reviewing the new store (not from a bug report), the author noticed that `daintree-plugin dev` — the CLI flow a plugin author actually uses while building the feature — attaches its plugin through `PluginService.loadDevPlugin()`. A store already initialized before that dev attach would never see the plugin's `devMode: true`, so its own error trace would render redacted forever. Invisible from reading the store alone: its subscribe-and-refresh logic is correct, the bug is entirely in which broadcast the producer fires, several layers away.

## Root cause

`loadDevPlugin()` calls `loadPlugin()` then `activatePlugin()` directly and returns — it never runs the `finally { this.broadcaster.broadcastProvenanceChanged(); }` block that the install/uninstall/enable-toggle paths use. `loadPlugin()` does register the plugin's panel kinds, which fires `onPanelKindRegistered` → `schedulePanelKindsBroadcast()` → `plugin:panel-kinds-changed`. So a dev-attached plugin produces exactly one of the two broadcasts a normal install produces, and it's the one nothing was listening to for this feature. Two channels that both mean "plugin set changed" are not interchangeable — one is provenance (install/uninstall/enable state, what `pluginMetaById.devMode` actually needs) and the other is panel-kind contributions — and the producer-side gap between them only shows up for the CLI dev-attach path, which is precisely the path the feature's target audience (plugin authors) uses.

The PR did not fix the broadcaster — filed as an open main-process follow-up (also noted: it leaves the Plugin Manager UI stale after a dev attach). Instead it fixed the _consumer_: `PluginViewFallback` calls `usePluginRuntimeStore().refresh()` in a `useEffect` on mount rather than trusting the store's cached snapshot. The reasoning is load-bearing — reaching this fallback means the plugin's view already rendered and threw, so the plugin is certainly loaded and listable by the time the diagnostics pane needs an answer, even though no event ever told the store that. `refresh()` is a separate method from `init()`: it re-pulls even when already initialized, guarded by the same `pullSeq`/`committedSeq` monotonic pair so a slow stale response can't clobber a newer one that already committed. At #11214 landing time `PluginViewFallback` lived in `PluginViewHost.tsx`; issue #11240 (`91191de7d`) later split that file, moving the fallback and its error boundary into the content-owning `PluginViewContent.tsx` — the mechanism is unchanged, only the file moved.

## Lesson

- **Don't assume sibling broadcast events fire together.** `plugin:panel-kinds-changed` and `plugin:provenance-changed` look like two views of "the plugin set changed" but have different, non-overlapping trigger sets — check `PluginContributionBroadcaster` and every call site of `broadcastProvenanceChanged()` / `schedulePanelKindsBroadcast()` in `PluginService.ts` before assuming one implies the other fired.
- **`daintree-plugin dev` / `loadDevPlugin()` is a narrower code path than a normal install** — it skips whatever broadcast isn't in its own direct call chain. Any renderer state keyed on plugin metadata (devMode, disabled, displayName) must be checked specifically against this path, not just the install/uninstall/toggle paths, before trusting it stays in sync for a plugin author's dev session.
- **When a subscription can't be trusted to have fired, pull fresh at the point where the answer is actually needed** rather than widening the subscription or racing to catch every producer path — `refresh()` here is only called from a fallback that provably renders after the plugin is loaded, so a synchronous pull there is guaranteed to see it, cheaply, without fixing the broadcaster.
- **A `refresh()` that pulls unconditionally still needs the same staleness guard as the passive subscription path** — reuse `pullSeq`/`committedSeq` (or equivalent) rather than add a second, uncoordinated fetch path; `refresh()` funnels through the same `pullPluginRuntimeSnapshot` the provenance listener uses.
- **A gap found by re-reading your own new code during review is still worth fixing even when it's not the bug in the linked issue** — this trap surfaced while building an unrelated feature and would otherwise have silently defeated that feature for its primary audience (plugin authors using `dev`), since normal installed-plugin flows never exercise `loadDevPlugin` and so never trip it.

## Applies when

- Adding renderer state that mirrors plugin metadata (`devMode`, `disabled`, manifest fields) and choosing which `plugin:*` broadcast to subscribe to — verify the producer path you care about (especially `loadDevPlugin`/CLI dev-attach) actually fires it.
- Touching `PluginContributionBroadcaster`, `PluginService.loadDevPlugin`, or any `plugin:*-changed` broadcast — check whether new call sites need `broadcastProvenanceChanged()` alongside their own event.
- Building a feature specifically for plugin authors (diagnostics, dev tooling, error surfaces) — test it against `daintree-plugin dev` attach, not just a normal sideloaded/installed plugin, since the dev path is structurally narrower.
- Debugging "this plugin-runtime state never updates for a dev-attached plugin but works fine for installed ones" — the mismatch is almost certainly which broadcast each path fires, not the consumer's subscribe logic.
- Deciding between subscribe-and-cache versus pull-on-demand for a value whose update signal might not cover every producer path — a late-binding read (only needed once something else already happened) favors pull-on-demand.
