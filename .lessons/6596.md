## Context

The content dock shows one active panel at a time. `activeDockTerminalId` in `usePanelStore` is the pointer to the open panel; `DockPanelOffscreenContainer` derives a filtered `dockTerminals` view (panels where `location === "dock"`, not trashed, not the help panel, and `worktreeId == null || === activeWorktreeId`) and runs a watchdog `useEffect` that calls `closeDockTerminal()` whenever `activeDockTerminalId` is set but points to a panel that is NOT in `dockTerminals`. The watchdog is correct in steady state — it closes the popover when the active panel is removed.

## Problem

Launching an agent into the dock (or adding a tab to a single docked panel) made the popover snap shut immediately on creation. The new panel was pruned from the dock the moment it appeared.

## Root cause

Creation was two separate store writes. `addPanel` committed `panelsById`/`panelIds` in one `set()`, then the call site fired a follow-up `openDockTerminal(newId)` that set `activeDockTerminalId` in a _second_ `set()` across a microtask/render boundary. In the gap, the watchdog effect could observe `activeDockTerminalId` already pointing at the new id while the filtered `dockTerminals` view had not yet recomputed to include it (the panel's `worktreeId` / location had not propagated through the selector). Seeing a pointer with no matching member, the watchdog concluded the panel was orphaned and called `closeDockTerminal()`. The watchdog itself was never wrong — the bug was purely the ordering window opened by setting the pointer and the membership in separate writes.

## Lesson

When a reconciling effect prunes state that _points outside a derived/filtered view_ (pointer-id must have a matching member or it's "orphaned"), never set the pointer and the membership in separate `set()` calls. Fold both into the single `set()` that commits the member. Concretely here: `addPanel` accepts `activateDockOnCreate` (`shared/types/addPanelOptions.ts`) and, when `location === "dock"`, writes `panelsById` + `panelIds` + `activeDockTerminalId` + `focusedId` in one snapshot (`addPanel.ts`), so the first state the watchdog can ever observe already has the panel present. Carry the activation _intent_ through the call chain (a typed option) rather than activating after the fact. Corollaries: (1) Renderer-side side effects that `openDockTerminal` used to perform (`terminalInstanceService.wake`, clearing waiting/working acknowledgements) must move into the same `addPanel` path, guarded by the flag. (2) `previousFocusedId` is metadata, not load-bearing for visibility, so it can be patched in a follow-up `set()` — only the visibility-determining fields must be atomic. (3) The atomic write alone is not always sufficient: paths that bypass the filter differently (the `worktreeId` clause in `dockTerminals`) still produced transient exclusions, so #7278 hardened the watchdog itself to re-check canonical `panelsById[activeDockTerminalId]` before pruning. Prefer BOTH the atomic write AND a canonical-store recheck in the reconciler.

## Applies when

- Adding or activating a panel in the content dock, or touching `activateDockOnCreate` / `openDockTerminal` / `closeDockTerminal` / `activeDockTerminalId`.
- Writing or modifying any Zustand store action where one field is a _pointer id_ and another field/collection is the _membership_ that pointer must resolve into (active-tab id + tab list, focused id + panel list, selected id + filtered view).
- Adding a `useEffect` watchdog/reconciler that prunes, closes, or resets state when a pointer "doesn't match" a derived/filtered selector — confirm the pointer and its member are committed atomically, and recheck the canonical (unfiltered) store before pruning.
- Symptom: a just-created panel/tab/popover collapses or closes immediately on creation; rapid successive creates lose one entry; a derived selector lags a pointer set across a render boundary.
- Refactoring create-then-mutate sequences (`await addPanel(...)` followed by a second store mutation) into a single committed write.
