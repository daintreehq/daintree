## Context

The pty-host emits "reliability metrics" through one canonical funnel, `emitReliabilityMetricWithTracking` in `electron/pty-host.ts`: pause lifecycle events (`pause-start`, `pause-end`, `suspend`, `pause-duration-gauge`) alongside high-volume diagnostic gauges (`throughput-rate`, `queue-depth-gauge`, `pending-bytes-gauge`, `data-loss-count`). Two renderer recovery surfaces (features #9807/#9808) consume a subset: `useForceResumeCycleWatchdog` promotes a terminal to a Tier-3 stall-escalation error banner after 3 consecutive `pause-end` with `durationMs >= 9900`, and the paused-flow pill's held-duration tooltip reads `heldDurationMs`, fed by `pause-duration-gauge` (`src/store/listeners/panel/lifecycle.ts`).

## Problem

A genuinely wedged renderer showed only the small ambient `Paused` pill forever — the Tier-3 escalation banner and the held-duration tooltip never appeared for any real user, exactly the case the "promote a stall past 30s to Tier 3 with a recovery action" rule exists for. Nothing looked wrong in review: the funnel was called correctly, the watchdog subscribed correctly, check/test/build were green. The whole escalation tier was structurally unreachable in production while looking fully wired in the diff.

## Root cause

The funnel terminated every emission with `if (!forceEmit && !metricsEnabled()) return;`, where `metricsEnabled()` (`electron/pty-host/metrics.ts`) reads `process.env.DAINTREE_TERMINAL_METRICS === "1"`, cached at module load. Nothing in the repo sets that variable — not the `utilityProcess.fork` env in `PtyHostLifecycle` (which only spreads `process.env`), not dev scripts, not e2e, not docs. So every reliability-metric wire emission was dropped in production, and the recovery UI on top of those events was dead on arrival. The load-bearing recovery signals shared a transport funnel with high-volume diagnostic gauges and silently inherited the diagnostic opt-in gate — correct for the gauges, catastrophically wrong for the recovery signals.

A second, independent defect in the same path: manual force-resume computed `pauseDuration` from `backpressureManager.getPauseStartTime(msg.id)`, a map only the SharedArrayBuffer transport populates. SharedArrayBuffer is unsupported inside Electron's `utilityProcess` (#7030) — the whole SAB/`FUTURE_SAB` branch is unreachable; production pauses record start times in the IPC/MessagePort queue maps. So `pauseDuration` was always `undefined` and the `pause-end` was skipped even with metrics enabled. The remedy split the gate with `isLoadBearingReliabilityMetric()` (`electron/pty-host/loadBearingMetrics.ts`) so the four `LOAD_BEARING_RELIABILITY_METRICS` types emit unconditionally, and routed force-resume `pause-end` through the funnel with `source: null`, deriving `durationMs` from the closure `pausedTerminals` map.

## Lesson

- **A load-bearing UI signal must not share a gated transport funnel with diagnostics** — it silently inherits the gate. When a user-facing recovery affordance depends on an event, that event's wire emission cannot sit behind a debug opt-in. Split at the funnel: `isLoadBearingReliabilityMetric()` marks the recovery-critical types (`pause-start`/`pause-end`/`suspend`/`pause-duration-gauge`) that bypass `metricsEnabled()`; everything else stays gated. Add a type to that set only when the renderer needs it.
- **Before trusting any feature behind an env flag, grep the repo to prove some production path sets it.** `metricsEnabled()` gates on `DAINTREE_TERMINAL_METRICS`; nothing (fork env, dev scripts, e2e, docs) ever set it. A gate no production path opens is equivalent to deleting the feature — the code compiles, the call sites exist, the behavior is unreachable.
- **Any pty-host code reading SAB-only state is dead in production (#7030).** SharedArrayBuffer is unsupported in Electron `utilityProcess`, so `getPauseStartTime()` and every `FUTURE_SAB`-marked branch never populate — grep the `FUTURE_SAB` marker to spot them. If you need a value the SAB path would have carried (here, pause duration), compute it from the live MessagePort/IPC closure maps (`pausedTerminals`).
- **A silent-failure feature born broken has no red test — pin the survival contract adversarially.** This shipped green because the emit call and the subscriber both existed; nothing asserted the event survived the funnel with metrics disabled. The new adversarial tests import the real `isLoadBearingReliabilityMetric` predicate (not a copy of the set) and drive it at `metricsEnabled: () => false`, so a drifted set fails the suite instead of silently re-breaking production.
- **Give recovery banners the same suppression parity as their siblings.** The stall banner now gates on `useShouldSuppressLocalError("backend-dependent")` like restart/spawn/reconnect — a banner whose only recovery action runs through the host must hide while a global host-recovery cause is active, or it offers a dead button.

## Applies when

- Wiring any renderer recovery affordance (banner, tooltip, Tier-3 escalation) that depends on a pty-host reliability metric — confirm the type is in `LOAD_BEARING_RELIABILITY_METRICS`, or it is dropped by `metricsEnabled()` in production.
- Touching `emitReliabilityMetricWithTracking`, `loadBearingMetrics.ts`, `ResourceGovernor.emitPausedDurationGauge`, or the `DAINTREE_TERMINAL_METRICS` gate; or adding a new reliability-metric type to the funnel.
- Diagnosing "the escalation banner / held-duration tooltip never shows" or a wedged terminal stuck on the ambient `Paused` pill.
- Reading pause-start/duration inside the pty-host from `getPauseStartTime()` or any SAB/`FUTURE_SAB` path — non-functional in `utilityProcess` (#7030); use the closure `pausedTerminals` map.
- Reviewing any feature gated behind an env flag or debug opt-in — grep that the flag is actually set on a production path before assuming the feature is live.
