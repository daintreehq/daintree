## Context

Deleting a worktree runs `git worktree remove` (via `worktreeClient.delete` → `WorkspaceService.deleteWorktree`). A worktree may simultaneously host a running dev-preview dev server, owned by `DevPreviewSessionService` (a main-process service keyed by `worktreeId`→session), plus open terminals. These services are independent and were never consulted by the delete path.

## Problem

On Windows, `git worktree remove` failed outright (#9084) when a dev server was still running in that worktree: the server process held the worktree directory open, and Windows refuses to remove a directory with an open handle inside it. The delete left a partial mess. On macOS/Linux the same removal succeeds despite the open handle, so the bug was invisible during normal dev.

## Root cause

`WorkspaceService.deleteWorktree` skipped `DevPreviewSessionService` entirely — there was no signal to stop the dev server before the filesystem removal ran. The directory-handle lifetime of the dev server process and the filesystem lifetime of the worktree are coupled, but that coupling only surfaces under Windows' mandatory file locking. POSIX unlink semantics mask it everywhere else. The fix is purely about _ordering across two independent services_: stop the process holding the handle, then remove the directory.

## Lesson

- Before `git worktree remove` (or any destructive filesystem op on a worktree dir), tear down every process that may hold a handle inside it: dev-preview sessions (`window.electron.devPreview.stopByWorktree({ worktreeId })`) and terminals (`closeTerminalsForWorktree`). Sequence is load-bearing — `stopByWorktree` must `await` to completion _before_ `worktreeClient.delete`.
- Call `stopByWorktree` _unconditionally_; it filters all sessions matching the worktreeId and no-ops when none match. Do NOT gate it on `getByWorktree`, which reflects only the worktreeId→session mapping's current head and misses multi-panel sessions sharing one worktreeId. Use `getByWorktree` only to decide whether to surface a UI toast.
- Wire this into _every_ delete entry point — the store path (`createWorktreeStore.ts`), the action definition (`worktreeCreateActions.ts`), and bulk remove (`useWorktreeBulkRemove.ts`). Missing one leaves the Windows hole open on that path.
- Surface the EXTERNAL case too: `WorkspaceHostEventRouter` emits `sys:worktree:remove` on `worktree-removed` so subscribers reconcile when a CLI/IDE removes a worktree out-of-band (the UI path can't pre-stop those).
- General rule: any "remove/move/rename a directory" op on Windows must first ensure no child process has a working dir or open file inside it. Don't trust POSIX-passing tests to catch this class.

## Applies when

- Adding or modifying any worktree delete / teardown / removal path (`WorkspaceService.deleteWorktree`, `worktreeClient.delete`, `createWorktreeStore` delete, `useWorktreeBulkRemove`, `worktree.delete` action).
- Adding a new long-lived process or resource keyed by `worktreeId` (dev servers, watchers, language servers, file indexers) that lives inside the worktree directory — it needs a `stopBy...` hook invoked before removal.
- Debugging a worktree delete that succeeds on macOS/Linux but fails on Windows with `EBUSY`/`EPERM`/"directory not empty"/`git worktree remove` errors.
- Reasoning about cross-process ordering dependencies between `DevPreviewSessionService` and the worktree lifecycle, or any case where one service's process holds a handle another service wants to delete.
- Deciding whether to gate a cleanup call on a lookup: prefer an unconditional, self-filtering `stopBy<key>` over a `get`-then-`stop` that can miss multi-instance state sharing the same key.
