## Context

`core-panel-tab-groups.spec.ts` uses `test.describe.serial` blocks. One test opens a panel overflow menu (Radix `DropdownMenu`, portaled to `document.body`), presses Escape, and ends. The next serial test ("restart confirmation flow works") types a command into the terminal via `runTerminalCommand`, expecting xterm to forward bytes to the PTY.

## Problem

The restart test failed intermittently on macOS CI. The trace showed `runTerminalCommand` succeeding all the way through click → focus assertion → `keyboard.type`, but the terminal buffer stayed at the bare prompt: the keystrokes never reached the PTY. Focus assertions on xterm's textarea passed, yet the command was lost.

## Root cause

Radix's `DropdownMenu` close is animated, so when Escape fires at the end of one test the menu portal does not unmount synchronously. The previous test ends and the next serial test begins while the menu's `FocusScope` is still mounted during its exit animation. The mounted FocusScope retains focus authority and its typeahead handler is still listening at `document.body` level — it intercepts the characters typed by the next test before xterm's textarea handlers see them. A focus assertion passing on xterm does NOT prove the keyboard path is clear: a still-mounted, animating overlay can shadow keystrokes even while a different element reports focused. The real gate is portal unmount, not focus state.

## Lesson

For serial E2E tests that open a Radix overlay in one test and type into another surface in the next, deterministically wait for the overlay portal to unmount at the END of the producing test — do not rely on focus assertions or a fixed settle delay:

```ts
await window.keyboard.press("Escape");
await expect(window.locator('[role="menu"]')).toHaveCount(0, { timeout: T_SHORT });
```

- The `toHaveCount(0)` on `[role="menu"]` is the load-bearing fix: it blocks until the FocusScope/typeahead is gone.
- A `window.waitForTimeout(T_SETTLE)` at the start of the consuming test is belt-and-suspenders only — `T_SETTLE` is just 500ms locally / 1–2s in CI (`e2e/helpers/timeouts.ts`), so on its own it is the flaky path, not the fix.
- This is cross-test contamination unique to `test.describe.serial`: residual overlay state from test N leaks into test N+1. Clean up overlays before a serial test ends, not (only) at the start of the next one.
- Distinct from #4486 (a _closing/dismissing_ menu eating the _opening_ click on Windows). This is the inverse: an _exit-animating_ menu that has not finished closing still swallowing keys destined for a different element.

## Applies when

- Writing or debugging Playwright E2E tests in `test.describe.serial` blocks where one test opens a Radix `DropdownMenu`/`Popover`/context menu and a later test types into xterm or any input.
- A terminal/input E2E test passes its focus assertion but the typed command never reaches the PTY (buffer stays at the prompt), especially intermittently on macOS CI.
- Any flaky E2E failure where keystrokes appear to vanish after a menu was recently open.
- Reaching for `waitForTimeout(T_SETTLE)` to fix menu-then-type flakiness — prefer a deterministic `toHaveCount(0)` on `[role="menu"]` (or the relevant portal selector) instead.
