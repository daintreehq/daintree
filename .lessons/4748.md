## Context

The project switcher palette wanted hover prefetch to make selecting a project feel instant. The first attempt (`prewarmHost()`, called on `onMouseEnter` per list item and also eagerly at app startup in `App.tsx`) spawned a UtilityProcess workspace host for the hovered project and ran its settings/runner detection inside that host.

## Problem

Each `prewarmHost()` call spawned a separate UtilityProcess workspace host — a full Node.js process with its own startup cost and memory footprint — and every host carried a multi-minute cleanup grace period before teardown. A worst-case list scan (mouse sweeping across the rows without committing to any) left 5+ abandoned long-lived hosts burning CPU and memory for projects the user never opened. The eager `App.tsx` startup call paid the same cost on launch regardless of whether the switcher was ever opened.

## Root cause

The prefetch coupled "warm the data" to "spawn a process." The expensive, slow-to-reclaim unit (a UtilityProcess host) was the thing being eagerly created on a cheap, high-frequency, speculative trigger (hover). Spawn frequency was unbounded by user intent and teardown was deferred by minutes, so speculative work accumulated instead of amortizing.

## Lesson

We tried hover prefetch, it backfired, and the durable takeaway is _what made it backfire_ — not "don't prefetch." Hover prefetch is back today, but rebuilt to prefetch a cheap, cacheable payload instead of a process:

1. Prefetch a serializable `HydrateResult` payload, never a process. `projectClient.prefetchHydrate` (`src/clients/projectClient.ts:135`) fires the `PROJECT_PREFETCH_HYDRATE` IPC; the handler (`electron/ipc/handlers/projectCrud/prefetch.ts`) builds the payload via `buildSwitchHydrateResult` and stores it in a main-process map (`electron/services/prefetchHydrateCache.ts`). No UtilityProcess host is spawned. The later `app:hydrate` consumes the cached entry (`consumePrefetchedHydrateResult`) or falls through to the full read path on a miss.
2. Debounce the speculative trigger. A 150ms trailing-edge timer (`PROJECT_HOVER_PREFETCH_DELAY_MS`) filters cursor traversal so a sweep across rows fires nothing; only intentional dwell prefetches.
3. Gate freshness so re-hover doesn't retry-storm. The renderer skips re-prefetch within 15s (`PROJECT_PREFETCH_FRESHNESS_MS`), deliberately shorter than the 30s main-process cache TTL (`PREFETCH_TTL_MS`) so a back-and-forth sweep doesn't keep re-firing the IPC.
4. Make failure invisible. The IPC is fire-and-forget; `prefetchHydrate` swallows errors and the cache layer logs-and-drops, so a failing build never surfaces to the user — the click-time hydrate just reads normally.
5. Singleflight + invalidate. Concurrent callers share one in-flight promise; `invalidatePrefetchCache` bumps a per-project version so a save during a build discards the stale result.

The general rule: when a speculative trigger (hover/focus) drives prefetch, prefetch a cacheable payload with a bounded TTL, not an expensive resource (process, connection, host) whose reclamation is deferred. Couple the cost to commitment, not to speculation.

## Applies when

- Adding hover/focus prefetch that could spawn or hold an expensive resource (UtilityProcess host, socket, view)
- Any speculative background trigger fired at high frequency without a debounce + freshness gate
- App-startup prewarming — validate the warm path is measurably faster before paying eager cost; prefer a cacheable payload over a live process
