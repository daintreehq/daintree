## Context

Daintree serves its built renderer bundle from a custom `app://` protocol handler (`electron/setup/protocols.ts`, header builder in `electron/utils/appProtocol.ts`). PR #3621 already enabled V8 code caching for this scheme by setting `codeCache: true` in `protocol.registerSchemesAsPrivileged()` (`electron/main.ts:111`) and `v8CacheOptions: "code"` in `webPreferences` (`createWindow.ts:242`, `ProjectViewManager.ts:982`).

## Problem

Despite both of those flags being set, `<userData>/Partitions/daintree/Code Cache/js/` never populated — the renderer recompiled all JS from scratch on every cold launch, and `RENDERER_READY` / `HYDRATE_*` perf marks showed no launch-2+ improvement.

## Root cause

`codeCache: true` and `v8CacheOptions: "code"` only enable the _capability_. Chromium 146's network stack decides whether to actually write a code-cache entry based on the HTTP cache semantics of the response, and the `app://` handler emitted no caching headers at all. With no `Cache-Control` (or an effectively `no-store` one) and no validator (`Last-Modified`/`ETag`), the resource is treated as non-cacheable, so the Code Cache dir stays empty and the compile cost recurs forever. V8 code-cache persistence is silently gated on the response being HTTP-cacheable — the privilege flags are necessary but not sufficient. A further trap: without a working `If-Modified-Since` → `304` path, every reload returns a fresh `200` that invalidates the existing bytecode entry, so the 304 short-circuit is part of the contract, not an optimization.

## Lesson

For a custom Electron protocol that serves JS you want V8-code-cached, the privilege flags from #3621 are step one; the handler must also return HTTP-cacheable responses:

- Emit a non-`no-store` `Cache-Control`. Content-hashed Vite assets under `assets/<name>-<hash>.<ext>` get `public, max-age=31536000, immutable`; unhashed files (`index.html`, `sw.js`) get `no-cache, must-revalidate` (revalidate, but still cacheable — never `no-store`).
- Emit a validator header (`Last-Modified` from `fs.stat().mtime`, RFC-7231 GMT via `date.toUTCString()`).
- Implement the `If-Modified-Since` → `304` short-circuit (`isNotModified()`); without it every reload's fresh `200` evicts the bytecode entry. Floor both mtime and the header to whole seconds — HTTP dates are second-precision and sub-second filesystem mtimes otherwise cause false `200`s.
- Distinguish immutable vs revalidate by path shape, not extension: only fingerprinted files under `assets/` are immutable. The `IMMUTABLE_ASSET_RE` matches an 8+ char base64url hash (covers Vite hex and rolldown xxHash) and handles Windows backslash paths.
- Leave genuinely-mutable handlers (`daintree-file://`) on `no-store` — caching there is wrong.

## Applies when

- Adding caching/headers to any custom Electron protocol handler (`app://`, `daintree-file://`, or a new scheme) that serves the renderer bundle or other JS.
- Cold-start / startup-perf work where V8 recompile cost shows up in `RENDERER_READY` / `HYDRATE_*` marks and the `Code Cache/js/` directory is empty despite `codeCache: true` being set.
- Touching `electron/utils/appProtocol.ts` `buildHeaders()` / `isImmutableAppAsset()` / `isNotModified()`, or the protocol handler in `electron/setup/protocols.ts`.
- Changing the Vite/rolldown asset hashing scheme or output layout (the immutable regex assumes flat `assets/<name>-<hash>.<ext>` output).
- Any time you set `codeCache: true` in a privileged scheme and the bytecode cache still isn't persisting — check the response headers, not just the flags.
