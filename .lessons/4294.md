## Context

Canopy persists session state (panel layout, open files, etc.) to disk and hydrates it on startup. Corrupted state can cause the app to crash immediately on every launch, trapping the user in an infinite crash-relaunch loop.

## Problem

If session state becomes corrupted in a way that causes a crash during hydration, the app relaunches, tries to hydrate the same corrupt state, crashes again — indefinitely.

## Root cause

State hydration was unconditional: the app always attempted to restore previous session state. There was no detection mechanism for repeated abnormal exits.

## Lesson

**Crash loop detection requires a persistent counter with a decay window.** The counter must be stored to disk (synchronously, using `writeFileSync`) so it survives process death — `CrashLoopGuardService` writes a `crash-loop-state.json` sentinel. Rather than a proactive "stability timer" `setTimeout`, the current implementation uses a lazy-evaluated sliding window (`CRASH_WINDOW_MS`, 30 minutes): at boot and at crash-record time it filters recorded launch timestamps to those inside the window, so stale crashes decay without a timer. This closes the slow-flap blind spot where a crash every 6+ minutes accumulated no strikes under the prior 5-minute reset.

**Safe mode must skip state hydration entirely** — not just show a warning banner. If corrupted state causes the crash, partial hydration still triggers the crash. Safe mode is entered once the windowed crash count reaches `CRASH_THRESHOLD` (3). The renderer's `src/utils/stateHydration/index.ts` reads the main process safe-mode flag (`hydrateResult.safeMode`, mirrored into `useSafeModeStore`) and skips restore when set.

**Clean shutdown must mark itself explicitly** (a separate marker file or flag) so that normal app quits don't increment the crash counter. Only abnormal exits (those that don't mark clean exit before quitting) increment the counter.

**Stop-relaunch threshold** (`HARD_STOP_THRESHOLD`, 5 crashes within the window): after this many crashes, don't even attempt relaunch — the auto-relaunch itself becomes a denial-of-service against the user's system. This is a second, higher gate above the safe-mode threshold (3).

Counter file corruption (invalid JSON) must be handled gracefully — treat it as a fresh start rather than crashing the crash guard.

## Applies when

- Any startup code that reads potentially corrupted state (settings, session, DB)
- Implementing crash recovery or safe mode for Electron apps
- Designing graceful shutdown sequences that distinguish clean vs. abnormal exit
