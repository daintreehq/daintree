## Context

`WorkspaceService`/`WorktreeMonitor` run per-project in the `workspace-host` utility process and stream git status to the renderer over dedicated MessagePorts (no main-thread involvement). Only the focused worktree got a recursive working-tree `fs` watcher; background worktrees got a cheap `.git/`-only watcher plus a 300s poll fallback, and a separate `startTopologyWatcher()` watched `.git/worktrees/` for external `git worktree add`/`remove`. #10956 audited this pipeline after noticing git-status updates were slow, and in the worst case a worktree an agent had just created never showed its changes at all.

## Problem

Two distinct silent failures, both invisible because nothing errored — the fast paths just quietly never did their job. First, an agent editing files in a background worktree never surfaced as a change until it staged or committed something. Second, the very first `git worktree add` in a project with zero existing worktrees took up to 90 seconds to appear anywhere in the UI. Neither looked like a bug from the outside — status just seemed "slow," which pointed investigation toward moving git work off the main thread (it was already correctly isolated in workspace-host, so that theory was a dead end).

## Root cause

Two unrelated fast-path assumptions were both wrong. (1) The 300s poll's stat pre-check (`WorktreeMonitor.updateGitStatus`, the logic now lives in `StatPrecheck.ts`) statted exactly four `.git` metadata files — `index`, `HEAD`, `refs/heads/<branch>`, `packed-refs` — and skipped the real `git status` call if none had changed. Those four files change on commit or staging, never on a plain unstaged file edit, so on any worktree without a recursive watcher (i.e. every background worktree) the skip condition was permanently satisfiable: nothing an agent did to source files would ever perturb the baseline. The fix wasn't smarter statting, it was a ceiling: `FULL_STATUS_MAX_AGE_MS = 120_000` now forces a real `git status` if 120s have passed since the last one actually ran, unless the worktree has a recursive watcher (which forces refreshes on its own). (2) `startTopologyWatcher()` returned early when `.git/worktrees/` didn't exist — exactly the state of a project with no linked worktrees yet — and nothing ever re-invoked it once that directory was created by the first `git worktree add`, so discovery fell through to a 90s safety-reconcile timer for the rest of the session. The fix is a cheap non-persistent `fs.watch` sentinel on the parent `.git` dir (`armMetadataSentinel`, now in `TopologyWatcher.ts`) that filters for the literal `worktrees` filename appearing, then hands off to the real watcher and forces an immediate reconcile — plus `ensureAlive()` (called after every reconcile) to catch the symmetric case where the watch root was deleted (last worktree removed) and the underlying subscription died without erroring.

Bundled into the same PR: a third, non-bug change wiring agent activity into the same elevation tier as focus (`WorktreeMonitor.isElevated = _isCurrent || _agentActive`, set via `WorkspaceService.setAgentActivity()` from a renderer broadcast). This exists because watching agents work is the product's core loop, and prior to this the freshest data went only to whichever single worktree the human happened to be looking at, not to the worktrees agents were actually changing.

## Lesson

- **A stat-based skip check is only as good as its statted set's coverage of real state changes.** `index`/`HEAD`/`refs/*`/`packed-refs` cover commit and staging, not working-tree edits — if you build a "skip the expensive check if these cheap signals are unchanged" fast path, first ask which real-world mutation would leave every one of those signals untouched. If the answer is "a plain file edit," the fast path is a permanent false-negative for that case, not an occasional one.
- **Give any indefinite skip an unconditional staleness ceiling.** `FULL_STATUS_MAX_AGE_MS` doesn't make the stat check smarter, it just bounds how long it's allowed to be wrong — a skip whose trust condition never independently expires needs a bound like this. `skipTrustworthy` in `StatPrecheck.ts` is `recursive watcher OR under 120s since last real pass`, never bare baseline-unchanged.
- **A watcher/subscription that legitimately no-ops on an absent precondition needs an explicit re-arm trigger for when that precondition becomes true, not just a slow periodic reconcile.** The 90s safety reconcile "worked," but 90s of silence for a project's very first `git worktree add` was the exact motivating symptom; `armMetadataSentinel` closes that hole with one cheap non-recursive `fs.watch` handle on the parent dir.
- **The same class of watcher can also die silently in reverse** (subscription still "held" but its watch root got deleted, e.g. the last linked worktree was removed) — a parcel-style watcher subscription doesn't necessarily error when this happens, it just stops reporting. `ensureAlive()` runs after every topology reconcile specifically to detect and rebuild that dead-but-not-erroring state.
- **When threading a new elevation signal through an existing focus-only fast path, grep every site that hardcoded the old boolean.** Adding `agentActive` alongside `_isCurrent` touched the pool-eviction budget, poll-queue priority, `forceRefresh`, and the initial-synchronous-status check — a partial migration would have left some of those still focus-only, silently reintroducing the same staleness for agent-active-but-unfocused worktrees.
- **This code has since moved:** the stat pre-check and its constant now live in `electron/workspace-host/StatPrecheck.ts` (unchanged name `FULL_STATUS_MAX_AGE_MS`), and the topology sentinel/self-heal now live in `electron/workspace-host/TopologyWatcher.ts` with the `Topology`/`Metadata` prefixes dropped from the method names (`armTopologyMetadataSentinel` → `armMetadataSentinel`, `ensureTopologyWatcherAlive` → `ensureAlive`) as part of the 2026-07 oversized-file split — look there first, not in `WorktreeMonitor.ts`/`WorkspaceService.ts` directly.

## Applies when

- Touching `electron/workspace-host/StatPrecheck.ts`, `WorktreeMonitor`'s poll/`updateGitStatus` path, or any "skip the real check if a cheap proxy hasn't changed" optimization.
- Touching `electron/workspace-host/TopologyWatcher.ts` or any watcher whose target directory may not exist yet at start time.
- Diagnosing "git status / worktree file changes don't show up," especially for background worktrees or a worktree an agent just created via `git worktree add`.
- Adding a new "deserves high-fidelity monitoring" signal (like agent activity) onto an existing focus-only tier — audit every consumer of the old boolean, not just the obvious ones.
- Reviewing any fast-path/cache-skip check gated on a small fixed set of file stats or timestamps — ask what real change wouldn't touch any of them, and whether the skip has an unconditional expiry.
