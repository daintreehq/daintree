## Context

`release-{macos,linux,windows}.yml` all fire on the same `v*` tag, and the composite action `.github/actions/publish-daintree/action.yml` runs `scripts/ci/check-version-monotonic.mjs` before uploading to R2 to stop a regressed update feed (electron-updater runs with `allowDowngrade = false`, so a downgrade strands every install — #7573). The documented recovery for a failed release is: fix on `develop`, merge to `main`, force-push the same tag, which re-runs all three per-OS workflows.

## Problem

During the v0.26.0 release (2026-07-15) a flaky unit test forced two re-tags of the same version. Each re-tag re-ran all three OS workflows, including the ones that had already published successfully on an earlier attempt of that tag. The gate failed those platforms with `new version 0.26.0 is not strictly greater than live 0.26.0`, identical to how it would report a genuine downgrade — a red build that actually meant "already shipped, nothing to do" was indistinguishable at a glance from a real regression (issue #11185).

## Root cause

The gate's `checkVersionMonotonic` only had two outcomes: fail closed unless `new > live`, so `new == live` (a re-tag of a version already live) hit the same failure path as `new < live` (an actual downgrade). Those are different situations that need different responses. The fix makes the check tri-state: `new > live` → publish, `new == live` → skip (log and exit 0, no re-upload), `new < live` or invalid semver → still fail closed.

Two non-obvious subtleties in the fix are the actual transferable content. First, the equality check uses **exact string identity, not `semver.eq`**: `checkVersionMonotonic("1.0.0+a", "1.0.0+b")` must still fail closed, because `semver.eq` ignores build metadata for precedence but `1.0.0+b` was never the artifact that actually published — treating it as "already live" would let a mismatched build skip verification it never earned. Second, the skip has to gate more than the upload step. `.github/actions/publish-daintree/action.yml` chains four steps after the gate: upload binaries, `verify-r2-uploads.mjs`, upload metadata, `verify-r2-metadata.mjs`. A re-tag rebuild is **not byte-reproducible** — same version string, different `sha512`/`Content-Length` in the freshly built local YAML versus what's already live on R2. If only the upload steps were skipped and the verify steps still ran, they'd fetch the live (already-published) artifact, diff it against the freshly rebuilt local one, and false-fail on a hash mismatch that has nothing to do with the release being broken — moving the false alarm one step later instead of removing it. All four steps gate on the same `steps.version-check.outputs.skip_upload != 'true'`; the final website-notify webhook step stays ungated because it's idempotent.

## Lesson

- **A binary pass/fail gate that conflates "equal" with "regressed" will misfire on any retry-the-same-input workflow.** If retries can legitimately re-present an identical input (a re-tag, a re-run), give the gate a third outcome (skip) distinct from both pass and fail — don't force retry-safety through the fail path.
- **Use exact value identity for "was this exact thing already published", never a library's semantic-equality helper.** `semver.eq` (and equivalents like deep-equal-ignoring-metadata) will treat inputs as the same when the underlying artifact differs; that's correct for precedence ordering but wrong for "did we already ship this," where a build-metadata-only difference means it was never actually live.
- **When a step gets skipped, trace every downstream step that reads that step's output as ground truth, not just the step that produces it.** Here skipping "upload" without skipping "verify" moved the failure from step N to step N+1; grep the whole composite action (or workflow) for steps that consume the same artifact/state before declaring a skip complete.
- **A rebuild of the same version is not guaranteed byte-identical.** Don't assume "same version tag → same artifact" is safe to re-verify against a stale copy; if a pipeline can rebuild the same version twice, any verify step comparing local-vs-live output needs to be gated by the same skip signal as the upload it's verifying.
- **Idempotent steps don't need the skip gate — only ones with a re-upload or re-verify cost do.** The website-notify webhook was deliberately left ungated in this PR; don't over-apply the skip condition to steps whose repetition is harmless, it just adds gate-maintenance surface for no benefit.

## Applies when

- Touching `scripts/ci/check-version-monotonic.mjs`, `shouldSkipUpload`, `writeSkipUploadOutput`, or any per-platform gate in `.github/actions/publish-daintree/action.yml`.
- Designing a CI/release gate that must tolerate re-running the same tag/version/input — distinguish "no-op repeat" from "regression" as separate outcomes, not folded into one failure branch.
- Adding a skip/short-circuit condition (`if: steps.<id>.outputs.<flag> != 'true'`) to one step in a multi-step composite action — audit every later step in the same job for whether it silently assumes the skipped step ran.
- Comparing a freshly rebuilt artifact against a previously published one (hash/size/content verification) — confirm the build is actually reproducible before treating a mismatch as a real failure.
- Reviewing any check that uses a semantic-equality library (`semver.eq`, deep-equal) where the real question is "is this the identical published thing," not "is this equivalent in ordering/precedence."
