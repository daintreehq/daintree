## Context

Both grid terminals and the Daintree Assistant (a `location: "overlay"` panel rendered persistently in `HelpPanel.tsx`) need a post-reveal repaint on project-view reactivation so a backgrounded xterm buffer re-syncs to real geometry. The shared owner is `wakeActiveWorktreeTerminals.ts`'s `repaintActiveWorktreeTerminals` sweep, which folds the Assistant's terminal id into its target list via `collectActiveWorktreeTerminalTargets` (added for #9637, the "frozen output until manual resize" bug) and drives every target through `revealUntilStable` down to `repaintForReveal` / `reconcileGeometryFresh` (now on `TerminalRevealController.ts` / `TerminalResizeController.ts` after a later file split).

## Problem

The Assistant panel intermittently duplicated and garbled already-printed agent output on view reveal/switch-back: a CLI's startup banner (version line, MCP-auth notice, tips blockquote) painted a second time, with box-drawing characters composited straight through existing words. It looked agent-specific at first glance but reproduced across every main-buffer CLI (Claude Code and others), never on alt-screen agents (OpenCode, Gemini) — pointing at a shared geometry path rather than any one agent's output.

## Root cause

`HelpPanel.tsx` carried its own local reveal cascade (an 8-frame width poll plus 1s/3s timer backstops, added under #10362) on top of the shared sweep, because the shared sweep's cadence was tuned for the CSS-grid layout and could land before the Assistant's slide-out overlay container had settled to real width, causing a false no-op. That was a real bug, but the fix compounded rather than replaced the shared owner — so two independent cascades could each call `reconcileGeometryFresh` for the same terminal id at different moments after the CLI had already committed output. xterm 6.x's buffer reflow is not safely re-entrant against live PTY writes: a second out-of-band resize measures its own fresh cols/rows and re-wraps the committed main-buffer scrollback while the CLI is still doing cursor-relative repaint math against the wrap layout from the first pass, corrupting `isWrapped` line-wrap metadata. That corruption is what surfaces as duplicated/garbled text. It's agent-independent because every main-buffer CLI hits the same reflow; alt-screen panes are shielded because `reconcileGeometryFresh` explicitly early-returns `true` for `managed.isAltBuffer` (the #10632 OpenCode protection) without touching them at all. It only reproduces on the Assistant because the overlay container settles a few frames later than the grid, making a genuine post-output column delta far more likely on its second, redundant pass — the grid's own reveal has nothing to race against.

## Lesson

- **A repaint/reconcile cascade must have exactly one owner per resource.** When a shared sweep's timing doesn't fit one caller's late-settling layout, the fix is to make the shared owner handle that case (retry/settle logic), not to bolt a second independent cascade beside it — even if the second one is cheap, idempotent, and individually well-tested (this one had a passing 4-test regression suite before the bug was found).
- **xterm 6.x buffer reflow is not safely re-entrant against live PTY writes.** Two geometry reconciliations for the same terminal at different moments, each measuring its own fresh cols/rows, can each trigger a resize; if either lands after output was committed, the CLI's cursor-relative repaint math (tuned for a stable width) races the reflow and corrupts `isWrapped` metadata. Treat any resize/reconcile entry point as needing a single call site per terminal, not "harmless because it's a no-op when unchanged" — the no-op only holds if nothing else already changed the geometry first.
- **Grep for the actual current owner before adding a parallel reveal/resize path.** `collectActiveWorktreeTerminalTargets` in `wakeActiveWorktreeTerminals.ts` already carries an explicit comment enumerating what it owns (grid panes + the Assistant's overlay terminal) specifically to prevent this class of duplication — check that comment (and its JSDoc, which post-#10866 explicitly says "This sweep is the SOLE reveal-repaint owner for the Daintree Assistant terminal too... HelpPanel must NOT re-add a parallel per-frame reveal cascade") before writing a component-local repaint effect for a terminal that's already in a shared sweep.
- **The retry mechanism to trust already exists: `revealUntilStable` / `MAX_REVEAL_FRAMES` in `src/services/terminal/revealUntilStable.ts`.** It bounds retries to ~10 frames and does a two-frame confirm-paint (`REVEAL_CONFIRM_PAINTS`) specifically to handle a container that isn't laid out yet on the first pass — the exact problem #10362's local cascade was reinvented to solve.

## Applies when

- Adding or debugging any reveal/repaint/resize path for a terminal (grid pane, Assistant, or a future overlay panel) — check whether the terminal is already covered by `collectActiveWorktreeTerminalTargets` / `repaintActiveWorktreeTerminals` before writing a component-local effect.
- Diagnosing duplicated, garbled, or doubled terminal output on view reveal/project switch-back, especially when it reproduces across multiple agent CLIs but only in one specific panel/container.
- Touching `reconcileGeometryFresh`, `repaintForReveal`, `applyDeferredResize`, or any xterm resize call and reasoning "this call is harmless because it early-returns when cols/rows are unchanged" — verify nothing else already changed the cached geometry first.
- Reviewing a fix that adds a parallel timer/backstop/poll cascade beside an existing shared sweep to handle a timing edge case — prefer extending the shared owner's retry logic instead.
- Working on `HelpPanel.tsx`, `wakeActiveWorktreeTerminals.ts`, `TerminalResizeController.ts`, or `TerminalRevealController.ts` and considering re-adding any `onViewRevealed`-driven cascade local to one panel.
