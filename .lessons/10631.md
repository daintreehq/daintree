## Context

Launching an agent from the toolbar `AgentButton` dispatches `agent.launch` as a fire-and-forget `void dispatch(...)` through `useAgentLauncher` (per-agentId reentrancy guard = `launchingAgentsRef: Set<string>`, `src/hooks/useAgentLauncher.ts:197,264-268`). The new `TerminalPane` mounts focused and, when the panel has an agent identity, resolves its focus target to `"hybridInput"` and schedules a one-shot RAF to call `inputBarRef.current?.focusWithCursorAtEnd()` (`TerminalPane.tsx:1007-1016`). The `HybridInputBar` (the CodeMirror composer over an agent PTY) is code-split: `LazyHybridInputBar = lazy(() => import("./HybridInputBar"))` inside `<Suspense fallback={null}>` (`TerminalPane.tsx:80-82`).

## Problem

Launching Claude from the toolbar, then pressing **Enter** at Claude Code's workspace-trust prompt ("1. Yes, I trust this folder"), spawned a **second** agent panel instead of confirming the prompt (#10541). Misleading part: the first diagnosis blamed the keymap, proposing `onSendKey("enter")` → `onSendKey("\r")`. That would have **broken** Enter — `sendKey("enter")` already maps to `\r` via `resolveKeySequence`'s `simpleMap` (`electron/services/PtyClient.ts`), whereas `"\r".trim()` is `""`, which hits the `if (!normalizedKey) return null` guard and drops the keystroke. The keymap path was never involved: CodeMirror never received focus at all.

## Root cause

Three independent facts compound into the duplicate spawn:

1. `AgentButton.handleClick` did `void dispatch(agent.launch)` with **no DOM focus handoff** — the native toolbar `<button>` keeps DOM focus after the launch.
2. `TerminalPane`'s one-shot focus RAF fires while the `React.lazy` `HybridInputBar` chunk is **still loading on a cold first open**, so `inputBarRef.current` is `null`. The optional-chaining call `inputBarRef.current?.focusWithCursorAtEnd()` **silently no-ops** — no error, no retry, no console noise. Focus is never claimed.
3. Because focus never left the button, when Claude's trust prompt renders and the user presses Enter, the browser **synthesizes a `click` on the focused `<button>` per the HTML activation spec** (Enter/Space activate a focused button). `handleClick` runs again → `agent.launch` again → second panel.

The per-agentId reentrancy guard can't catch it: `launchingAgentsRef` releases when the _first_ launch resolves, long before the trust-prompt Enter arrives. This is an API-looks-correct trap — a RAF-then-optional-chain focus handoff reads as safe, but the `?.` guarding a null ref converts "component not ready" into "focus silently lost" instead of surfacing it.

The fix is **defense-in-depth**, two independent layers: (a) `HybridInputBar` self-claims focus on mount — a `useEffect` gated on `isFocusedTerminal && preferredTerminalFocusTarget === "hybridInput"` calls `focusEditor()`. Ordering guarantees a live view: the `EditorView` is created in `useEditorFactory`'s `useLayoutEffect`, which flushes before this `useEffect` runs, so `focusEditor()` always finds a non-null `editorViewRef.current`. (b) `AgentButton.handleClick(e)` calls `e?.currentTarget?.blur()` on launch, so a stranded-focus Enter can't bounce back into any launch surface — closing the whole class, not just the lazy-chunk race. (In the current tree the mount claim is routed through a `claimMountFocusRef` to dodge a `react-hooks/exhaustive-deps` suppression, `HybridInputBar.tsx:564-579`, mechanism unchanged.)

## Lesson

- **A fire-and-forget launch from a native `<button>` MUST blur or explicitly hand off DOM focus** — otherwise the button keeps focus and the _next_ Enter/Space re-activates it (HTML spec: a focused button synthesizes `click` on Enter). Any toolbar/dock/recipe control that opens a panel on activate and does `void dispatch(...)` without a focus transfer is a latent duplicate-action bug; `e?.currentTarget?.blur()` in the handler is the cheap universal guard.
- **Never rely on an external one-shot RAF hitting a possibly-null ref to hand focus into a `React.lazy`/`Suspense` subtree.** `inputBarRef.current?.focus...()` on a not-yet-resolved chunk silently no-ops — the `?.` hides the failure. Make the lazy component **self-claim focus on mount** (gated on it being the focused panel + the preferred focus target), so it works regardless of whether the parent's RAF won or lost the chunk-load race.
- **`useLayoutEffect` in the child (editor factory) flushes before a sibling/parent `useEffect`** — that ordering is what lets `HybridInputBar`'s mount-effect `focusEditor()` assume `editorViewRef.current` is live. If you move editor creation to a plain `useEffect`, the self-focus claim races its own view and the fix silently rots.
- **When a symptom points at a keystroke/keymap path, verify the element even has focus first.** Here the entire duplicate-spawn lived in _focus_, not in `useEditorKeymap`/`sendKey`; the proposed keymap patch (`"\r"`) would have made Enter a silent no-op because `resolveKeySequence` trims the key before matching.
- **The E2E regression must launch a FRESH app instance** (`e2e/full/platform/core-hybrid-input-bar.spec.ts`, `#10541` block) — the race only exists while the `HybridInputBar` chunk is cold. A warmed-up app has the chunk cached, the RAF finds a live ref, and the bug can't reproduce. Assert three invariants: focus landed in the input bar on mount (no click), the `\r` reached the PTY (fake CLI flips to `FAKE_CLAUDE_READY`), and exactly one new panel exists (re-check after a settle window since the buggy second spawn was an async `addPanel`).

## Applies when

- Adding or reviewing any control that launches an agent / opens a panel via `void dispatch(...)` (`AgentButton`, dock launch menu, recipe/preset buttons) — confirm DOM focus is blurred or explicitly moved, or a stranded-focus Enter re-fires it.
- Handing keyboard focus into a `React.lazy` / `Suspense` component via a parent RAF and `ref.current?.focus()` — the ref can be null on cold chunk load; give the lazy component a mount-time self-focus claim instead.
- Diagnosing "pressing Enter spawns a duplicate terminal/panel" or any "the button fired twice / activated on Enter" symptom — check what holds DOM focus, not the keymap or `sendKey` path.
- Touching `TerminalPane`'s focus-target RAF (`getTerminalFocusTarget` → `"hybridInput"`, `inputBarRef.current?.focusWithCursorAtEnd()`), `HybridInputBar`'s mount focus claim, or `preferredTerminalFocusTarget` routing.
- Writing an E2E test for a lazy-load / cold-chunk race — reuse of a warm app instance will make it a false green; launch fresh so the chunk is uncached.
