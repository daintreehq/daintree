## Context

Terminals receiving output while the user is scrolled up needed a visual indicator. The implementation required an overlay that doesn't interfere with terminal mouse event handling.

## Problem

A naive overlay positioned over the terminal steals mouse events from xterm.js (text selection, middle-click paste, right-click context menu). The entire terminal interaction model breaks if mouse events are captured by an overlay.

## Root Cause

Not a bug — architectural constraint. Standard overlay pattern intercepts pointer events.

## Lesson

For overlays on top of xterm.js terminals: apply `pointer-events: none` to the overlay container and `pointer-events: auto` only to the specific interactive button within it (the wrapper `<div>` in `TerminalScrollIndicator.tsx` carries `pointer-events-none`; `pointer-events-auto` is baked into `ScrollPill` at `src/components/ui/ScrollPill.tsx`). This allows mouse events to pass through to the terminal except precisely where the button is. Scroll state should be derived from xterm's `onScroll` event plus output increments — wire it through `TerminalListenerInstaller` (`terminal.onScroll`) and `TerminalWriteController` (per-write increment) into a `TerminalUnseenOutputTracker`, exposed to React via `useUnseenOutput` + `useSyncExternalStore`. Do not attempt to measure scroll via DOM APIs on the terminal element. Give the indicator a stable accessible name (`aria-label="Scroll to latest output"`) for reliable E2E targeting.

## Applies when

- Any overlay UI (badges, indicators, action buttons) placed on top of an xterm.js terminal
- Any floating button positioned inside the terminal pane
