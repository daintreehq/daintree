## Context

Every grid panel kind is supposed to render inside `ContentPanel`, which owns the pane chrome (header, drag handle, context menu, close/trash) and the click-to-focus wiring in one place. `PluginViewHost` (built for non-PTY plugin panels back under #9287/#9229) instead mounted its lazy plugin view in a bare `div` and rolled its own `usePanelRootFocus` registration to at least get keyboard focus-delivery working. #11228 reported that a plugin-contributed grid panel (a Docker control panel in this case) rendered and worked, but clicking inside it left the previously-focused agent panel as Daintree's `focusedId`.

## Problem

Clicking inside the plugin panel did nothing to panel selection — the previously focused agent panel stayed focused. Because `Cmd+W` and "Close Terminal" resolve their target as `terminalId ?? state.focusedId ?? ...` in `terminalLifecycleActions.ts`, this meant closing the terminal while a plugin panel had visible mouse focus killed the _agent_ instead. The plugin panel also had no header, drag handle, or context menu, so it couldn't be dismissed through normal pane UI. It looked like a keyboard-focus bug (similar to prior fixes #11132/#11150) but the actual gap was upstream of that: nothing ever wrote `focusedId` on click at all.

## Root cause

`ContentPanel`'s `handleClick` is what calls `onFocus()` on any unhandled click — that's the entire focus-_selection_ mechanism app-wide. `usePanelRootFocus` is a different, later stage: it only pushes DOM focus into an already-focused panel (focus _delivery_, e.g. for macro-grid Enter). `PluginViewHost` had the delivery half via its own `usePanelRootFocus` call but never called `onFocus`, so a click inside plugin content never reached anything that could change `focusedId`. Every other panel kind gets both halves for free by rendering inside `ContentPanel`; `PluginViewHost` was the only grid-panel kind (besides `ReviewPane`, a documented standing exception — see `src/panels/review/ReviewPane.tsx:40`) that skipped it.

The fix is not just "add an onClick" — routing through `ContentPanel` properly has two easy-to-miss placement traps. First, `ContentPanel` has to wrap _outside_ the `ErrorBoundary`/`Suspense` tree, not inside it, or a still-loading/crashed plugin view has no chrome and can't be closed — stranded open exactly when the user most needs to dismiss it. Second, once `ContentPanel` wraps the host, `PluginViewHost`'s own `usePanelRootFocus({ id: panelId, ... })` call has to be deleted, not left alongside `ContentPanel`'s own registration (`ContentPanel.tsx:269`, `usePanelRootFocus({ id, isFocused, getNode: getRootNode, enabled: !isPtyKind })`). `registerPanelFocusHandler` in `panelFocusRegistry.ts` is a bare `Map<string, FocusHandler>` keyed by panel id — a second `register` call for the same id **silently overwrites** the first, no warning, no error. Two effects race on mount/unmount order, and whichever wins leaves the other's target permanently unreachable. Leaving the old registration in place would have quietly regressed the keyboard-focus fixes from #11132/#11150.

## Lesson

- **Route every grid panel kind through `ContentPanel`; don't hand-roll focus wiring.** `ContentPanel` is the only place `handleClick → onFocus()` (selection) exists — a bespoke root div with only `usePanelRootFocus` (delivery) looks like it works because keyboard/programmatic focus still functions, but mouse-click selection is silently absent. Reproduce by clicking inside the panel's content, not its root — the bug lives in whether interior clicks bubble up to the selection handler.
- **A duplicate `registerPanelFocusHandler(id, ...)` call is a silent last-writer-wins clobber, not an error.** When moving focus ownership from a component's own hook call into a wrapper that also registers, delete the old call in the same change — the registry (`Map.set`) gives no signal two owners are competing for one id.
- **Test the registry seam, not just its public API**, to catch a duplicate-registration regression: wrap `registerPanelFocusHandler` (as `PluginViewHost.test.tsx` now does via a `vi.hoisted` live-count map around the real module) and assert exactly one live registration per panel id across mount/unmount.
- **When wrapping loading/error boundaries in shared chrome, the chrome goes outside the boundary.** `ContentPanel` sits outside `ErrorBoundary`/`Suspense` in the fixed `PluginViewHost` so a loading skeleton or crashed view still has a header and a working close button.
- **A new panel-kind category needs an explicit branch in every type-guard-based menu, not just the panel itself.** `TerminalContextMenu` fell through to terminal-flavored items ("Duplicate terminal", "Kill terminal") for plugin panels until `isPlugin = Boolean(terminal.pluginId) && !hasPty` was added (`TerminalContextMenu.tsx:531`) — the `!hasPty` half matters because plugins can also contribute genuine PTY-backed kinds needing the real terminal menu.
- **`ReviewPane` is a known, still-live exception** (grep it for "renders no ContentPanel") — same click-to-focus gap this PR fixed for plugins, deliberately left out of scope.

## Applies when

- Adding a new grid panel kind (plugin-contributed or built-in) — verify it mounts inside `ContentPanel` rather than composing its own root + `usePanelRootFocus`.
- Touching `PluginViewHost.tsx` / `PluginViewContent.tsx` (split apart post-#11231 in commit `91191de7d`, but the ContentPanel-outside-boundary invariant is unchanged) or `ReviewPane.tsx`.
- Reviewing any change to `panelFocusRegistry.ts`, `usePanelRootFocus`, or anywhere a component both renders `ContentPanel` and independently calls `registerPanelFocusHandler`/`usePanelRootFocus` for the same panel id.
- Diagnosing "clicking inside a panel doesn't select it" or "Cmd+W / Close Terminal closed the wrong thing" — check whether the clicked panel's content ever reaches an `onFocus()` call, not just whether it can receive DOM/keyboard focus.
- Adding a new panel-kind category to `TerminalContextMenu` or any other kind-dispatching UI — confirm the new kind doesn't silently fall through to a default branch meant for a different kind.
