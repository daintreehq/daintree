## Context

Window-state persistence lives in `electron/windowState.ts`: per-project bounds are saved to `window-states.json` (`windowStatesStore`) and restored by `createWindowWithState()`, the single window factory called from `electron/window/createWindow.ts` (which also sets `minWidth: 800` / `minHeight: 600`). An earlier fix (issue #4710, external-monitor disconnect) had added an oversized/off-screen clamp to the restore path, with tests. #10180 (issue #10076) fixed the branch that clamp never reached.

## Problem

On any display whose work area is smaller than the 1200x800 default — a 1366x768 laptop with a taskbar has a work-area height under 800, plus 1280x720 panels, VMs, RDP sessions, scaled DPI — a first-run window came up centered but too large, its bottom and right edges off-screen. Windows/Linux only; on macOS it never reproduced. The misleading part: the clamp code existed, looked complete, and its #4710-era tests were all green.

## Root cause

Two independent mechanisms stacked. First, the guard in `createWindowWithState()` short-circuited to `win.center()` whenever `windowState.x` or `.y` was `undefined` — treating missing coordinates as corrupt state. But coordinate-less bounds are the COMMON case, not the edge case: `resolveWindowBounds()` returns `{ width: 1200, height: 800, isMaximized: false, isFullScreen: false }` with no `x`/`y` on every first run and defaults fallback. `win.center()` only repositions, it never resizes, so the size clamp in the `else` branch was skipped exactly on the path that ships the hardcoded 1200x800.

Second, platform masking: Electron auto-constrains larger-than-screen windows only on macOS — `enableLargerThanScreen` is a macOS-only option defaulting to `false`, meaning macOS silently shrinks the window to fit. Windows and Linux happily create larger-than-screen windows. So the primary dev platform auto-corrected the bug at the OS level, and it only manifested where nobody was looking. The test suite compounded this: the #4710 clamp tests only exercised the saved-x/y branch, and the "falls back to defaults" test ran against a 1920x1080 mock work area where a 1200x800 default needs no clamp — coverage looked complete while the coordinate-less + small-display combination was untested.

The fix (current code): a `hasSavedPosition` flag; the display is `screen.getPrimaryDisplay()` when there's no saved position (on a `show: false` window `getBounds()` returns placeholder coordinates, so `getDisplayMatching` would route there anyway — the direct call makes it explicit); the size clamp runs unconditionally before the position branch; saved-position windows then route through `clampToDisplay()` (replacing inline <50%-visible-area math) while coordinate-less ones `center()` after clamping. `clampToDisplay()` and the inline path both gained a `safeWorkArea` fallback: some Wayland/GNOME compositors report a zero-dimension `workArea`, and without the fallback to `display.bounds` the `Math.min` clamp produces a 0x0 window.

## Lesson

- **`win.center()` repositions but never resizes.** Any geometry-repair branch that ends in `center()` must run the size clamp first; a guard that short-circuits to `center()` for "missing" input silently skips clamping on exactly the path carrying hardcoded defaults.
- **A window-geometry bug verified only on macOS is unverified.** macOS auto-constrains larger-than-screen windows (`enableLargerThanScreen: false`, macOS-only); Windows/Linux spill. Off-screen/oversize bug reports from Windows, Linux, VMs, RDP, or scaled-DPI users that "don't reproduce" locally are this masking, not user error.
- **Coordinate-less saved state is the first-run happy path, not corruption.** `resolveWindowBounds()` returns no `x`/`y` for defaults (step 4) and some cold-start cases — model it as "needs centering after clamping", never as "skip validation".
- **Guard work-area math against zero dimensions.** Wayland/GNOME can report a `workArea` of `0x0`; every consumer must fall back to `display.bounds` (the `safeWorkArea` pattern now in both `clampToDisplay` and `createWindowWithState`) or the clamp emits a 0x0 window.
- **Clamp tests need a work area small enough to fire the clamp.** A defaults test on a 1920x1080 mock proves nothing about a 1200x800 default; add a sub-default work area (1280x720). And `clampToDisplay` re-fetches `getDisplayMatching` after the `setSize`, so screen mocks must use `mockReturnValue`, not `mockReturnValueOnce` — a Once mock lets the second fetch see a different display and silently bypass the code path under test.
- **Area-ratio repair thresholds leave usability holes.** The old "<50% visible → repair" math left a 75%-visible window at `x=-300` untouched, putting macOS traffic-light controls off-screen; edge-pinning via `clampToDisplay` repairs any off-work-area overhang, which is what "reachable title bar" actually requires.

## Applies when

- Touching `electron/windowState.ts` (`createWindowWithState`, `clampToDisplay`, `resolveWindowBounds`) or the window constructor options in `electron/window/createWindow.ts`.
- Diagnosing "window opens too large / cut off at bottom-right / partially off-screen" reports from Windows/Linux, VM, RDP, or scaled-DPI users that don't reproduce on a macOS dev machine.
- Writing or reviewing any geometry-validation branch that treats missing saved coordinates as an error case or ends in `win.center()`.
- Mocking `electron.screen` in `electron/__tests__/windowState.test.ts` — display mocks must survive re-fetches and work-area mocks must be smaller than the bounds under test.
- Adding new window-spawn paths (multi-window, per-project windows) that reuse saved bounds on a possibly different or smaller display.
