## Context

Daintree's main-process logger (`electron/utils/logger.ts`) writes every log line to disk and clones context into an in-memory `LogBuffer` ring (500 entries) for the in-app log viewer; the workspace host streams `worktree-update` snapshots through an in-process bus (`electron/services/workspace-client/WorkspaceHostEventRouter.ts`) that synchronously drives `PullRequestService.handleWorktreeUpdate` and MCP session listeners; the renderer logs through a parallel `src/utils/logger.ts` that historically forwarded every call to main over IPC. Issue #10769 was filed after telemetry showed real `Event loop lag detected` warnings (`electron/utils/performance.ts`) at 1000-1755ms, 73 times in one session, correlating with keystroke echo lag across several agent terminals at once — distinct from the per-pane freeze in #10660.

## Problem

Under multi-agent load, typing into any agent terminal went laggy — keystrokes and output still echoed, just behind, continuously rather than freezing. It hit multiple unrelated panes together, pointing away from a per-pane bug. Keystrokes ride a per-window MessagePort straight to the pty-host on the healthy path, not main-process IPC, so the obvious first guess (pty-host loop) didn't fully fit either — main-process synchronous work under the same load was the better-fitting suspect precisely because of the multi-pane signature.

## Root cause

Three independent hot paths compounded under multi-agent churn. (1) `writeToLogFile` called `appendFileSync` per non-error line at 150-300 lines/s under load, each costing 0.2-20ms including a periodic rotation `statSync`, and a single `worktree-update` event fanned out to several of these at once. (2) The `sys:worktree:update` bus had no coalescing, bursting at 10-50 events/s, each synchronously driving `PullRequestService` and MCP listeners, multiplying (1)'s cost. (3) `emitError` stringified the redacted context twice (once per transport), and `redactSensitiveData`/`redactArrayWithCycleDetection` had no bound on recursion depth, string length, or array length, so one large stack trace could cost unbounded CPU while being cloned into the 500-entry `LogBuffer` ring. (4) The renderer had no client-side level floor, so ~99 `logger.debug()`/`logger.info()` sites paid a full `ipcRenderer.invoke(LOGS_WRITE)` round trip even when main's `resolveEffectiveLevel` would discard the message on arrival.

The fixes (#10770, #10780, #10784) batch and gate rather than change algorithms: buffer non-error lines into `pendingLogLines`, flush once per event-loop turn via `setImmediate(runAsyncFlush)` into a single `fsp.appendFile` (ERROR stays sync for crash survival, flushing the pending buffer first for on-disk ordering; `ASYNC_FLUSH_MAX_PENDING_BYTES = 256 * 1024` is a safety valve); add a 50ms `SYS_WORKTREE_UPDATE_DEBOUNCE_MS` window scoped only to that internal bus; dedupe `emitError`'s stringify/scrub work and cap `redactSensitiveData` at `MAX_REDACT_DEPTH = 5`, `MAX_REDACT_STRING_CHARS = 2000`, `MAX_REDACT_ARRAY_ITEMS = 20`; mirror main's level floor into the renderer and batch renderer→main writes on a 16ms `LOG_BATCH_MS` timer into `LOGS_WRITE_BATCH` (60-entry `MAX_BATCH_ENTRIES` cap), with `warn`/`error` bypassing the timer.

The non-obvious trap sits inside the length cap: `clampLogString` runs `scrubSecrets` BEFORE truncating to `MAX_REDACT_STRING_CHARS`. Reversing that order would slice a secret's high-entropy tail off at the 2000-char boundary before the pattern matcher sees it, leaving a short unscrubbed prefix (e.g. `ghp_AAA…`) on disk — #10780's test places a `ghp_` token exactly straddling that boundary to pin the ordering.

## Lesson

- **Synchronous per-call work on Electron's main thread is a shared bottleneck across every pane, not a local cost.** `appendFileSync` at 150-300 calls/s (0.2-20ms each) stalled the whole event loop — exactly why keystroke lag hit multiple unrelated terminals at once, a signature a per-pane pty-host bug would not produce. When lag hits several independent panes together, suspect a shared main-thread sync path before per-pane pty/renderer code.
- **Async-ifying a per-call sync path isn't enough — batch it.** N `appendFileSync` calls/tick becoming N `fsp.appendFile` calls doesn't reduce the syscall count; the fix collapses buffered lines into one `appendFile` per event-loop turn (`pendingLogLines.join("")` in `runAsyncFlush`). Keep a sync escape hatch for crash-critical lines (ERROR) and a byte-size safety valve so an unflushed burst can't grow unbounded.
- **Scrub before you clamp, never the reverse, for any string that might carry a secret.** Truncating first can cut a secret's matchable tail off before the pattern scrubber runs, leaving an unredacted prefix on disk. Any redaction/truncation pipeline over logged strings needs a test with the secret straddling the length boundary, not just one safely inside it.
- **Gate at the call site before crossing a process boundary, not just at the receiving end.** The renderer paid a full IPC round trip for every sub-threshold `debug`/`info` call across ~99 sites; mirroring main's level floor locally (`resolveEffectiveLevel`) before the IPC call eliminated the wasted crossing, cheaper than making the receiving-side discard fast.
- **Debounce the internal consumer that doesn't need per-event freshness, not the whole event.** The 50ms `sys:worktree:update` coalescing window applies only to the bus feeding `PullRequestService`/MCP listeners; the direct per-view MessagePort fan-out and plugin bus are deliberately excluded because they drive live UI state, where coalescing would trade one kind of lag for another.

## Applies when

- Diagnosing input/echo lag that hits multiple agent terminals at once rather than one pane — grep `~/Library/Application Support/Daintree/logs/daintree.log` for `Event loop lag detected` before assuming a per-pane pty-host cause.
- Adding or touching a `logger.error`/`logInfo`/`logWarn` call in a hot path — check call frequency under multi-agent load and whether the write is synchronous; batch rather than leaving per-call sync IO on the main thread.
- Writing or extending a redaction/scrub/truncate pipeline over logged or persisted data (`redactSensitiveData`, `clampLogString`, `shared/utils/secretScrubber.ts`) — verify scrub-then-clamp ordering with a boundary-straddling secret.
- Adding new renderer-to-main logging or telemetry IPC call sites — confirm the renderer gates locally before invoking IPC rather than paying a round trip for something main will discard.
- Touching `WorkspaceHostEventRouter.ts` or any in-process bus fanning out to multiple synchronous listeners under load — confirm which consumers need per-event freshness before adding or removing coalescing.
