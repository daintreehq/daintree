## Context

Cold-boot font loading is a two-part optimization added by #6794 (issue #6781): `src/main.tsx` imports the JetBrains Mono Latin-400 woff2 via a Vite `?url` import and injects a `<link rel="preload" as="font">` at module eval (before `bootstrap()`), and the matching weight-400 `@font-face` in `src/index.css` uses `font-display: optional` so first paint never blocks on the font. The renderer document is served over the custom `app://` scheme, registered in `electron/main.ts` with `corsEnabled: true`. Terminals have a separate late-arrival repair path (`ensureTerminalFontLoaded` in `src/config/terminalFont.ts` → `repairFontGrid`, #9809); DOM/UI text has only the preload.

## Problem

The preload was never consumed by the request it existed to accelerate: Chromium logged "resource was preloaded but not used" and the woff2 downloaded twice. The real damage was worse than a wasted fetch — on a cold or uncached boot the `@font-face` fetch started from zero, `font-display: optional`'s ~100ms block period expired, and Chromium permanently committed that page to fallback system monospace for its entire lifetime. The optimization defeated itself, silently: no error, no broken layout, just the wrong font all session, and only on cold boots (warm caches masked it completely).

## Root cause

`ensureLatin400Preload()` (then inline in `main.tsx`) built the link with `rel`/`as`/`type`/`href` but no `crossorigin`. Two spec behaviors combine: (1) CSS `@font-face` fetches are always issued in CORS-anonymous mode (CSS Fonts Level 4 font-fetching requirements) — same-origin does not exempt them, and the `app://` scheme's `corsEnabled: true` keeps that true in our Electron renderer; (2) the HTML preload-matching algorithm keys on request mode, so a preload without `crossorigin` is a `no-cors` request that can never match the `cors` font request. The preload downloads, sits unused, and the parser issues a second, fresh fetch for the same bytes.

`font-display: optional` is what escalates this from a double-download nit to a visible product bug: it grants roughly a 100ms block period and a 0ms swap period, meaning if the font is not ready almost immediately, the browser renders fallback and never swaps — for the lifetime of the page. The preload is precisely the mechanism that makes `optional` viable; with matching broken, the design guaranteed fallback on every cold boot. The fix (#10187) is one property — `link.crossOrigin = "anonymous"` — with the helper extracted to `src/lib/fontPreload.ts` and regression-guarded by `src/__tests__/fontPreload.test.ts` and `e2e/full/terminal/font-preload.spec.ts`.

## Lesson

- **Every `<link rel="preload" as="font">` must set `crossorigin="anonymous"`, including for same-origin assets.** Font fetches are always CORS-mode by spec, preload matching keys on request mode, and a mode mismatch produces a silently wasted preload plus a duplicate download. The only runtime tell is DevTools' "resource was preloaded but not used" warning — treat that warning as a bug, never noise.
- **`font-display: optional` and its preload are a load-bearing pair — validate them together.** `optional` means "fallback forever if not ready in ~100ms"; it is only safe when a working preload wins that window. Anyone changing either half (the `@font-face` in `src/index.css` or `ensureLatin400Preload`) must confirm the other still matches, or cold boots regress to permanent fallback monospace with zero errors.
- **URL parity is a second silent dedupe-killer.** The preload href comes from a Vite `?url` import in `main.tsx`; the `@font-face` src comes from a `url()` in `index.css`. Both must resolve to the same hashed asset or matching fails again with identical symptoms. The E2E spec asserts parity by parsing `CSSFontFaceRule` src against the resolved link href — keep it when touching the font pipeline or bumping `@fontsource/jetbrains-mono`.
- **When asserting request counts during boot in Playwright/Electron, attach the listener to the BrowserContext, not the page, then reload.** The first revision of the E2E test bound a page-level listener after `launchApp()` returned — the preload request had already fired and resolved, so the test proved nothing. `app.context().on("request", ...)` catches requests from pages mid-navigation; a subsequent `reload()` gives a deterministic fetch sequence to count.
- **`ensureLatin400Preload`'s contract is skip-if-present, not patch-if-stale** — it returns if any preload link with that href exists and deliberately does not upgrade a stale crossorigin-less link. The unit tests pin this; a "helpfully patch the existing link" refactor either re-introduces the mode mismatch or duplicates the link. Only the terminal recovers from a late font (`repairFontGrid`/`onTerminalFontArrivedLate`, #9809, canvas ignores `font-display`); CSS-rendered UI text under `optional` never swaps after commit, so the preload is the DOM's sole defense.

## Applies when

- Adding or modifying any `<link rel="preload">` — fonts always, but any `as` type whose consumer fetches in CORS mode (ES modules, `fetch()`) has the same mode-matching trap.
- Touching `src/lib/fontPreload.ts`, the `@font-face` blocks or `font-display` values in `src/index.css`, or bumping `@fontsource/jetbrains-mono` (hash changes exercise the URL-parity assertion).
- Diagnosing "the app renders in the wrong/fallback monospace on a fresh install or cold boot" or seeing Chromium's "resource was preloaded but not used" console warning.
- Assuming same-origin assets don't need `crossorigin` — the `app://` scheme is registered `corsEnabled: true` and font fetching is spec-mandated CORS regardless of origin.
- Writing Playwright tests that count or observe network requests fired during app boot — listener attach timing versus `launchApp()` decides whether the test can see them at all.
