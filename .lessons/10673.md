## Context

`TerminalWebGLManager` gates WebGL with a fleet-wide, count-based mode switch per project view (`evaluateMode`/`flipToDom`/`flipToWebgl` in `TerminalWebGLManager.ts`): once the number of terminals that "want" a context exceeds an upper threshold (12/lower-10 at the time of this PR; later made RAM-tiered by #11192, cold-start defaulting to 18/15), the entire fleet flips to the DOM renderer and only the focus-pinned terminal keeps WebGL. `TerminalInstanceService.wantsWebGLAtTier` (now extracted into `TerminalWebGLPolicy.ts`) is the policy function that decides whether a given terminal registers a want.

## Problem

In a project with many worktrees running active background agents, clicking between two _visible_ agent terminals made them visibly flash/resize, and visible agents — including the Daintree Assistant — dropped to the DOM renderer (mangled block/box-drawing glyphs). A second project with few terminals and no background worktrees never showed it, which pointed investigation at click-handling/resize code instead of the real cause: off-screen terminals nobody was looking at were consuming the budget that visible ones needed.

## Root cause

`wantsWebGLAtTier` had no visibility precondition: any terminal with a `runtimeAgentId` at a WebGL-eligible tier (FOCUSED/BURST/VISIBLE) returned `true` regardless of `managed.isVisible`. Every PTY write applies `BURST` tier unconditionally in `onPtyWrite`, and a continuously streaming background agent never goes quiet — active-state agents aren't even hibernation-eligible until 5 minutes of silence — so a busy background worktree held its want indefinitely. With only ~4 visible agents, well under the then-cap of 12, the fleet still flipped to DOM because invisible streaming agents pushed the total over the threshold. A second bypass made this worse: `applyAgentPromotion` called `ensureContext` directly, gated only on `isOpened && isWebGLEligibleTier(...)`, skipping the policy function (and its visibility check) entirely. The restore path (`shouldRestoreWebGL`) already required `managed.isVisible` — only the want-_producing_ side was missing the gate, so contexts released correctly on hide, but hidden agents still counted toward the cap because the _want_ was independent of the active context. The same-day sibling PR #10674 found a second, unrelated failure mode in the same subsystem: once the fleet is legitimately in DOM mode, only the single focus-pinned terminal keeps a context, and the pin is set exclusively via `terminalInstanceService.setFocused()` → `webGLManager.pinFocus()`. `HelpPanel` (the Daintree Assistant) called `terminalInstanceService.focus()` — xterm DOM focus only — and never `setFocused()`, so the Assistant could never become the pin and was permanently stuck on DOM rendering with no user action able to recover it.

## Lesson

- **A shared, fleet-wide resource want must be visibility-gated at the single production point, not just at the release/restore point.** `shouldRestoreWebGL` had the visibility check from the start; `wantsWebGLAtTier` (the want-producing side) didn't — trace every caller that can register a want, including bypasses like `applyAgentPromotion`, not just the obvious release path.
- **Count-based/threshold circuit breakers over a fleet must only count participants the user can actually perceive.** An off-screen agent has a legitimate reason to keep streaming, but no reason to hold GPU-context budget; conflating "needs to keep processing" with "needs the expensive resource" is the bug pattern, not the threshold value.
- **When two near-identically-named methods exist on a service (`focus()` vs `setFocused()`), verify which one is load-bearing before trusting a call site.** `focus()` only does xterm DOM focus; `setFocused()` is the sole path to `webGLManager.pinFocus()` — a caller can look correct while silently never touching the pin.
- **`TerminalWebGLPolicy.ts` (this logic moved here from `TerminalInstanceService.ts` in a later refactor) now carries a class-level comment flagging 3 past incidents in exactly this code** (#10671 plus the DOM-mode pinned-context circuit breaker and bulk-attach staggering) — treat any edit to `wantsWebGLAtTier`/`shouldRestoreWebGL`/`shouldHaveActiveWebGL` as high-risk, not routine.
- **A hide-dwell/anti-churn timer needs its own guard when the want side changes.** Visibility-gating `wantsWebGLAtTier` meant a hidden-but-streaming agent's next tier-apply would release its context on frame 1 instead of after `WEBGL_HIDE_DWELL_MS` — fixed with a `managed.webGLHideTimer === undefined` guard that preserves the dwell without resurrecting the bug.

## Applies when

- Touching `wantsWebGLAtTier`, `shouldRestoreWebGL`, `shouldHaveActiveWebGL` in `src/services/terminal/TerminalWebGLPolicy.ts`, or `TerminalWebGLManager.ts`'s `evaluateMode`/`flipToDom`/`flipToWebgl`.
- Diagnosing visible-terminal flicker or unexpected DOM-renderer/glyph-mangling that correlates with background worktree/agent count rather than visible terminal count.
- Adding a caller that registers a resource want (WebGL or any fleet-wide budget) outside the central policy function — check it can't skip the visibility/eligibility gate the way `applyAgentPromotion` originally did.
- Wiring a non-grid terminal surface (the Assistant, or any future panel-hosted terminal) into focus-driven behavior — confirm it calls `setFocused()`, not just `focus()`.
- Reviewing any count-based circuit breaker over a fleet — confirm what's counted is gated on visibility/perceivability, not just liveness.
