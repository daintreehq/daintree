## Context

Agent busy/idle detection is passive output heuristics: `ActivityMonitor` (per-terminal, in `TerminalProcess`) feeds the agent FSM. #8701 added an OSC 9;4 progress-sequence side channel (`Osc94Parser`, fed raw PTY bytes in `TerminalProcess.handlePtyData`) because Claude Code ≥2.0.56 emits the ConEmu-spec progress sequence: state=1/3 (working) routes to `onOscProgressWorking` — a viewport-independent heartbeat that refreshes `lastActivityTimestamp`/`lastDataTimestamp` so small grid tiles don't starve the viewport-bound detector — and state=0 (remove/hide) routes to `onOscProgressIdle`.

## Problem

Issue #9866: the idle half of the channel did nothing. `onOscProgressIdle` armed a 200ms `OSC_IDLE_DEBOUNCE_MS` timer whose expiry callback only nulled its own handle — nothing anywhere read whether the timer was pending, so the handler was a behavioral no-op wearing load-bearing clothes: a named constant, `clearTimeout` calls in `onOscProgressWorking` and `dispose()`, and a detailed comment justifying the 200ms choice ("comfortably above Claude's inter-tool gap upper bound"). Meanwhile the agent's explicit done marker contributed nothing — busy→idle always waits the full 8s `IDLE_DEBOUNCE_MS` decay gate — which makes "wire state=0 into idle detection to make it faster" a standing temptation.

## Root cause

Claude Code emits OSC 9;4 state=0 between **every tool call**, not just at final completion — it means "hide the progress bar", not "I am done". Any authoritative handling (forcing idle, or feeding the elapsed debounce into the decay/completion paths — the rejected Option 2 of #9866) would flicker working→idle→working on every tool boundary and risk clobbering `workingHoldUntil`, which other signal paths set deliberately. There is an inherent asymmetry: working-direction signals (state=1/3) are cheap to trust because a false working self-corrects by natural decay through the 8s gate, but idle-direction signals are expensive because acting on a false idle means overriding holds with no self-correction. So the resolution (Option 1) deleted the timer machinery entirely and kept `onOscProgressIdle` as a documented `isDisposed`-guarded no-op — it must exist because `Osc94Parser`'s `onIdle` callback needs a sink — with a regression test asserting it mutates neither `lastActivityTimestamp` nor `lastDataTimestamp`.

The same PR corrected a stale data-flow claim repeated in four places (`Osc94Parser.ts` header, `IdleSequenceFilter.ts` header, the `TerminalProcess.handlePtyData` tap comment, `docs/architecture/agent-activity-monitoring.md`): that `stripIdleTerminalSequences` cleans a "renderer-bound" path. False — its only production call sites are the byte-length computations feeding `ActivityMonitor`'s byte-volume/activity gates (`ActivityMonitor.ts` ~637/687). The renderer receives raw bytes and xterm renders the progress bar, asserted intentionally by `TerminalProcess.osc.test.ts` ("forwards OSC 9;4 bytes to the renderer").

## Lesson

- **Never make OSC 9;4 state=0 (or any agent "done" marker with the same shape) an authoritative idle trigger.** It fires between consecutive tool calls, so authoritative handling flickers agent state and clobbers `workingHoldUntil`. Real idle is exclusively `lastActivityTimestamp` decay through the 8s `IDLE_DEBOUNCE_MS` gate in the simpleOutputState polling cycle. If asked to "speed up idle detection using the agent's own signal", this is the recorded rejection — don't relitigate it without new evidence that the emitter's semantics changed.
- **Trust signals asymmetrically by their failure mode.** state=1/3 is acted on (heartbeat, focus-suppression-gated per #8865, still bounded by the `MAX_WORKING_SILENCE_MS` safety net per #4974) because a false working decays away; state=0 is a no-op because a false idle would need to override holds. When adding a new activity signal, ask which direction it pushes and whether a false positive self-corrects.
- **A timer is load-bearing only if something reads its pending state or its expiry has effects.** The 200ms debounce read as real machinery — constant, clears, unref, justifying comment — but a comment describes intent, not behavior. When auditing debounce/timer code, grep for reads of the handle/pending flag before assuming the described behavior exists.
- **Keep the sink, document the contract.** Deleting `onOscProgressIdle` outright would have forced a signature change on `Osc94Parser`; instead it stays as an explicit advisory no-op with a test pinning the contract (no timestamp mutation). An intentional no-op with a test is durable; an accidental one invites "fixing".
- **`stripIdleTerminalSequences` strips only the ActivityMonitor byte-volume/activity-gate path — the renderer path is raw.** The docs name OSC 133/633 shell-integration parsing as a future landing zone on this tier (`docs/architecture/agent-activity-monitoring.md`); anyone building it must not assume renderer-bound stripping exists, and must strip (or not) per-consumer deliberately.

## Applies when

- Tempted to use OSC 9;4 state=0, or any per-tool-boundary progress/done sequence, to shortcut the 8s busy→idle decay gate in `ActivityMonitor` / the agent FSM.
- Touching `Osc94Parser`, `onOscProgressIdle` / `onOscProgressWorking`, `workingHoldUntil`, or the `IDLE_DEBOUNCE_MS` / `MAX_WORKING_SILENCE_MS` gates.
- Implementing OSC 133/633 shell-integration parsing or any new escape-sequence detector on the `TerminalProcess.handlePtyData` tap — checking which paths are stripped vs raw.
- Auditing or refactoring timer/debounce machinery anywhere — verifying the pending state is actually read before treating the debounce as behavior.
- Reviewing a change that makes a previously-advisory signal authoritative, or that mutates activity timestamps from a new signal path (the regression test in `ActivityMonitor.test.ts` pins the no-mutation contract).
