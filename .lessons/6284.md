## Context

`DiskSpaceMonitor` (`electron/services/DiskSpaceMonitor.ts`) polls free space and computes `writesSuppressed = status === "critical"`. That status was broadcast to the renderer for a warning UI (added in #4295), but the main process has many independent disk writers: telemetry/Sentry flush, file logger, `GitHubStatsCache`, frecency/`lastOpened` columns in `ProjectStore`, and the SQLite handle itself.

## Problem

On a critical-pressure volume the broadcast flag changed nothing in the main process — every writer kept flushing to disk, the exact behavior the signal was supposed to prevent. A broadcast is only a notification; it has no enforcement unless a consumer reads it.

## Root cause

`writesSuppressed` was produced and shipped but never _consumed_ by any writer. There was also a structural reason consumers couldn't easily check it: importing `DiskSpaceMonitor` to read its status creates an import cycle (`DiskSpaceMonitor` → `logger.ts` → … ). The fix is a dependency-free per-process flag module `electron/services/diskPressureState.ts` (`getWritesSuppressed()` / `setWritesSuppressed()`), which the monitor pushes to on every poll and any writer reads with zero coupling. Two non-obvious constraints fell out:

- **Tier discipline.** Not all writes are equal. Tier-2 ranking/diagnostic writes (frecency score, `lastOpened`, telemetry, caches) are dropped under pressure; tier-1 session state the user depends on (the `currentProjectId` pointer, project `active`/`background` status) stays _unconditional_ inside the same transaction — see `ProjectStore.ts:644-654` where `newScore` becomes `null` but the status update still runs. Blanket-suppressing all writes would lose the user's session pointer on recovery.
- **Read the flag at the write site, not at entry.** `ScratchCleanupService` and others re-read `getWritesSuppressed()` per iteration rather than caching it, because the monitor can flip it mid-operation. `GitHubStatsCache.save()` updates the in-memory cache _first_, then `if (getWritesSuppressed()) return;` skips only the disk write — so in-process reads stay consistent and the dropped data is persisted once pressure clears.

## Lesson

- Suppression signals are inert by construction. After wiring a "should I write?" flag, audit _every_ writer in the process and make each one opt in — the producer side is the easy half.
- Put the flag in a tiny dependency-free module so consumers don't import the monitor (avoids cycles through `logger.ts`).
- Classify each write before gating it: tier-1 session/config state must survive disk pressure (the device must not lose what the user relies on to recover); tier-2 telemetry/cache/ranking signals are the only safe drops. Within a mixed transaction, suppress columns selectively, not the whole statement.
- Update in-memory state before skipping the disk write so reads stay correct and the write replays on recovery.
- Re-read the flag at each write site (per loop iteration), never cache it at function entry — it flips on the monitor's poll cadence.
- The flag is per-process: `DiskSpaceMonitor` runs only in main, so pty-host/workspace-host keep `writesSuppressed=false`. Don't assume utility-process writers are covered.

## Applies when

- Adding or auditing any main-process disk writer (telemetry, logging, caches like `GitHubStatsCache`/`GitHubFirstPageCache`, SQLite via `persistence/db.ts`, `ProjectStore` frecency, scratch cleanup) and deciding whether it must respect disk pressure.
- Wiring any new broadcast/global signal (`writesSuppressed`, resource-governor state, memory-pressure level) and needing to confirm consumers actually act on it rather than just receive it.
- Touching `diskPressureState.ts` / `DiskSpaceMonitor.ts`, or seeing `getWritesSuppressed()` call sites — especially when adding a new writer that should gate on it.
- Classifying writes by criticality: deciding what is safe to drop under resource pressure vs. session/config state that must always persist so the user can recover.
- Investigating data loss or zero-byte/corrupt files appearing after a low-disk episode, or telemetry/cache writes that should have been suppressed but weren't.
