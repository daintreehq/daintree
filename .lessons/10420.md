## Context

Each project runs in its own `WebContentsView` under `ProjectViewManager`. Switching projects detaches the outgoing view from the window's `contentView` (`deactivateEntry` removes it) and marks its entry `state: "cached"`; under the efficiency profile those cached views are also CDP-frozen. The window's `resize` handler only ever re-laid-out the active view — cached views got nothing. Within the active project, offscreen terminals already resize their PTYs correctly via `TerminalResizeController` (cols/rows from cached cell metrics, no DOM reads), but a backgrounded project never received the signal that would trigger it.

## Problem

Resize the window while working in project A, and every terminal in backgrounded project B keeps its stale PTY width. Agents there keep wrapping output at the old width the whole time, restored scrollback comes back with that wrong wrapping baked in, and the switch-back wake path has to correct all the geometry after the fact — the hardest direction to fix from (the class #10070/#10160 were cleaning up). The renderer can't self-correct: a detached view gets no resize events, `setBounds()` does not propagate to it, and `ResizeObserver`s never fire in a hidden page — no layout signal to re-measure from.

## Root cause

A detached/backgrounded `WebContentsView` is severed from every geometry signal the renderer relies on. The design forces: (1) the renderer can't learn the new size on its own, so Main must push it; (2) you must NOT re-measure layout in the hidden view — derive terminal sizes numerically from the forwarded window bounds; (3) pushing to a frozen renderer is fine — IPC to a CDP-frozen/CPU-throttled `webContents` queues in Mojo and delivers on unfreeze, so no unfreeze/refreeze cycle is needed just to send a message.

The subtle trap is the scaling math. Scaling each terminal's _current_ size by an incremental ratio compounds error across repeated background resizes and mis-lands any terminal skipped in a given pass (e.g. resize-locked). The fix anchors to a per-background-session snapshot: `backgroundResizeSession` captures the basis once (`window.innerWidth/Height` — the stale viewport all `lastWidth/lastHeight` were laid out against) and each terminal's `origin` size the first time it's seen, then every event computes an **absolute** target (`origin * width/basis`). Repeated resizes never compound, and a skipped terminal still lands correctly next pass. The snapshot resets on `visibilitychange → visible` (`resetBackgroundResizeBasis`) since real layout owns geometry once reattached. Delivery goes through `resizePtyOnly`, which bypasses the normal `sendPtyResize` settled-strategy timer (that timer would schedule a `terminal.resize()` reflow inside a frozen renderer) and clears any superseded pending timer; the xterm buffer reflow is deferred to wake via `fullWakeForVisibilityRestore → applyDeferredResize`.

## Lesson

- **A detached `WebContentsView` is blind to geometry: no resize events, `setBounds()` doesn't propagate to it, and `ResizeObserver`s never fire in a hidden page.** If a backgrounded per-project view must track window size, Main has to forward the settled bounds over IPC (`ProjectViewManager.notifyBackgroundResize` → `project:background-resize`); the renderer cannot re-measure layout to recover it.
- **IPC to a CDP-frozen / CPU-throttled renderer queues in Mojo and delivers on unfreeze — you do not need to wake it just to send a message.** This lets background-resize forwarding skip an unfreeze/refreeze cycle. Debounce trailing-edge instead (`BACKGROUND_RESIZE_DEBOUNCE_MS = 300`) so you never spam frozen renderers mid-drag — and listen to the `resize` event, not `resized` (**Linux never emits `resized`**); the single debounce covers resize/maximize/unmaximize/fullscreen.
- **When scaling many elements across repeated resizes, anchor to a session snapshot and compute absolute targets — never scale the current size by an incremental ratio.** Relative scaling compounds rounding error and mis-lands anything skipped in a pass. `backgroundResizeSession` freezes the basis viewport + per-terminal origin sizes once; reset it (`resetBackgroundResizeBasis`) when the view returns to foreground and real layout takes over.
- **Don't reflow xterm in a hidden/frozen renderer.** `resizePtyOnly` sends the PTY resize directly (via `terminalClient.resize`, not `sendPtyResize`) so no `terminal.resize()` is scheduled in a frozen page, and clears the superseded settled timer; buffer reflow is reconciled at wake. Ratio-scaling PTY size is exact for 1fr grid tracks, at worst ~1 col off where fixed chrome doesn't scale.
- **Keep grid-layout knowledge in the renderer.** The rejected alternative — compute cols/rows in Main and resize PTYs directly — would duplicate renderer grid layout in the main process. Main forwards raw window bounds only; the renderer owns the size math.

## Applies when

- Making any backgrounded / detached / cached `WebContentsView` (or its terminals, PTYs, layout) react to window resize, maximize, fullscreen, or DPI change.
- Diagnosing terminals in a non-active project wrapping at the wrong width, or scrollback returning with stale wrapping after a project switch.
- Sending IPC to a frozen/CPU-throttled renderer and wondering whether you must unfreeze it first (you don't — Mojo queues it), or writing scaling math that reruns against the same elements (resize, zoom, reflow) — verify it computes absolute targets from a fixed anchor, not deltas off the current value.
- Touching `ProjectViewManager` resize/freeze handling, `TerminalResizeController.resizePtyOnly` / `resizePtyFromCachedCellMetrics`, `TerminalInstanceService.applyBackgroundWindowResize`, or `useBackgroundWindowResize` (registered in `useAppBootstrap`).
