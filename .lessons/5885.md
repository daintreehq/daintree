## Context

The `directing` agent state (user is composing a prompt at a waiting agent) is owned entirely by the renderer's `TerminalAgentStateController` (`src/services/terminal/TerminalAgentStateController.ts`). It is entered on keystroke and the _only_ clearance path was a per-keystroke debounce `setTimeout` (`directingTimers` map) plus Enter/Escape handlers. The backend agent-state machine never emits `directing` — it only sends canonical states (`working`/`waiting`/`completed`/`exited`) over IPC.

## Problem

`directing` could get stuck indefinitely. Any path that drops the in-memory controller while the panel-store `agentState` still reads `directing` — controller recreated on project-switch rehydration, WebContentsView LRU eviction, hot reload, or wake-from-hibernation — left a `directing` value with no timer tracking it and therefore no way to self-clear. The indicator stayed lit forever.

## Root cause

Two compounding facts make this unrecoverable without an explicit sweep. (1) `directing` was being persisted via `serializePtyPanel` (`src/panels/terminal/serializer.ts`), so it survived reloads into the panel store. (2) The IPC ingestion path explicitly refuses to let an incoming canonical state overwrite `directing`: `src/store/listeners/panel/identity.ts:93` short-circuits when `terminal.agentState === "directing" && state === "waiting"` (so a fresh `waiting` from the backend can't clobber an active local compose). That guard is correct for a _live_ compose, but for a _rehydrated_ `directing` it means no inbound event can ever clear it. The clearance owner (the debounce timer) is renderer-instance-local and does not survive the controller being recreated. So the persisted-state path and the timer-only-owner path together produce a dead state with no escape.

Compounding it on backgrounded views: Chromium's IntensiveWakeUpThrottling can delay a pending `setTimeout` up to ~60s, so even a surviving timer is not evidence of an active session.

## Lesson

A renderer-only ephemeral state must (a) be excluded from persistence — `serializePtyPanel` now drops `agentState === "directing"` so it can never rehydrate; and (b) have an owner-independent recovery sweep for any instance that already carries it. `checkStaleDirecting(id)` reverts a `directing` terminal that has no live `directingTimers` entry, and is wired into both `attach()` and the wake/post-restore path in `TerminalInstanceService.ts` (lines ~1303, ~1809). The wall-clock guardrail (`directingEnteredAt`, refreshed per keystroke; swept on `visibilitychange` when `now - enteredAt >= DIRECTING_MAX_WALL_MS` = 15s) handles the throttled-background case: treat the per-keystroke timestamp, not the pending timer, as the source of truth for "is this session still active", because the timer can be arbitrarily delayed.

## Applies when

You add a renderer-owned ephemeral UI state whose only clearance mechanism is a `setTimeout`/debounce living in a service instance that gets recreated on project-switch, LRU eviction, hot reload, or wake — especially if that state is persisted or if an IPC guard prevents external states from overwriting it. Verify there is a rehydration/wake sweep and that the state is excluded from `serializePtyPanel`. Also when reasoning about `setTimeout` reliability in backgrounded WebContentsViews — a pending timer is not proof of liveness under IntensiveWakeUpThrottling; use a wall-clock timestamp swept on `visibilitychange`.
