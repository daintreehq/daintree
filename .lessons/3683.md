## Context

Several Zustand selectors used `.filter()` inside `useShallow()` wrappers, creating new array references on every store change. This caused components consuming these selectors to re-render on unrelated state changes (focus changes, MRU updates, command queue changes).

## Problem

`useShallow` prevents re-renders by doing shallow comparison of the selector result. But `.filter()` always returns a **new array reference**, so `useShallow` must compare every element on every state change — O(N) work per selector per store update, even when the filtered items didn't change. With 5 affected selectors and frequent store updates, this was measurable overhead.

## Root cause

The `useShallow` + `filter` pattern looks correct but defeats the purpose: `useShallow` can't help when the selector body always allocates a new array. The fix is to drop the throwaway `.filter()`/`.map()`/`.find()` chains and accumulate the result in a single loop inside `useShallow`, so the cheap element-wise shallow compare runs against a freshly built but minimal result; for derived structures that must stay referentially stable across unrelated store updates, pull the raw input with a plain selector and post-process under `useMemo`.

## Lesson

**Anti-pattern** — `useShallow` + inline `.filter()` does NOT prevent re-renders:

```ts
// Allocates a new array on every store update, forcing useShallow to
// element-compare a freshly built throwaway array every time:
useTerminalStore(useShallow((s) => s.terminals.filter((t) => t.waiting)));
```

**Correct pattern** — accumulate in a single loop inside `useShallow` (no intermediate `.filter()`/`.map()` allocations), so the result is minimal and the shallow compare is cheap:

```ts
usePanelStore(
  useShallow((state) => {
    const out: PtyPanelData[] = [];
    for (const panel of getNarrowPanels(state.panelsById, state.panelIds)) {
      if (isPtyPanel(panel) && panel.agentState === "waiting") out.push(panel);
    }
    return out;
  })
);
```

When the derived value must stay referentially stable across unrelated store updates, pull the raw input with a plain selector and post-process under `useMemo` (see `useConflictedWorktrees` in `useTerminalSelectors.ts`).

For counting selectors that only return primitives, return the count from the loop directly (`{ waitingCount }`) rather than `.filter().length` — no intermediate arrays (see `useTerminalNotificationCounts`).

For ID lookups, use `Map.get(id)` over `Array.find()` — O(1) vs O(N).

Cross-store selector dependencies (e.g., `worktreeIds` from a separate store) need `useShallow` on the cross-store input to prevent metadata-change invalidation.

## Applies when

Any Zustand selector that calls `.filter()`, `.map()`, or `.find()` before passing to `useShallow`; performance profiling showing high re-render frequency in terminal-heavy views.
