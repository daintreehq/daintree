## Context

The docked-terminal popover height (`useDockStore.popoverHeight`, default 500px) got persistence in a direct commit (`3f3ed9a32`, 2026-01-16): a `dockedPopoverHeight` field on `AppState` (`shared/types/ipc/app.ts`), a `persistPopoverHeight` writer calling `appClient.setState`, and rehydration in `AppLayout`'s `restoreState` → `useDockStore.getState().hydrate(...)`. #9605 added E2E coverage for panel-layout choreography (#9595), including a spec asserting that height survives an app restart — which is how the bug surfaced.

## Problem

The round-trip failed: a value written through `appClient.setState({ dockedPopoverHeight })` never came back from `getState` after restart. Everything _looked_ wired — the type existed, hydration code existed, `npm run check` was clean, and the `setState` promise resolved without error on every write. The height had been silently resetting to the 500px default on every launch for ~4.5 months with nothing in any log. The misleading part: the renderer side was complete and correct, so reading the renderer code (store, client, hydration) could never find the bug — both missing pieces were in the main process.

## Root cause

`handleAppSetState` (`electron/ipc/handlers/app/state.ts`, channel `APP_SET_STATE = "app:set-state"`) is not a merge of the incoming partial — it is an explicit per-key allowlist. It builds an `updates` object only from `if ("key" in partialState)` branches (~16 today, `sidebarWidth` through `fleetScopeMode`), each with its own validation/clamp, then batch-writes `updates` to electron-store. A key with no branch never reaches `store.set`, and no error or warning fires — deliberate, because the renderer is untrusted and every accepted key must be validated. The pipeline is also asymmetric: `handleAppGetState` returns the whole stored `appState` object with no allowlist, so the read path works the moment the value is in the store and gives no hint the write path is dropping the key.

So a persisted app-state field has four wiring points: (1) the `AppState` type in `shared/types/ipc/app.ts`, (2) the `StoreSchema["appState"]` slot in `electron/store.ts`, (3) a validated branch in `handleAppSetState`, (4) a hydration consumer. TypeScript enforces only 1 and 4 — `setState` takes `Partial<AppState>`, so a payload whose key has no handler branch typechecks and resolves fine. `dockedPopoverHeight` had 1 and 4 but not 2 and 3. The fix (#9605) added the schema slot plus a clamped branch (300–2000, mirroring dockStore's min-300 / 80%-of-viewport clamp), and hardened `dockStore.hydrate`: it was `set({ ...state, isHydrated: true })`, which on a fresh profile spreads `popoverHeight: undefined` over the numeric default, breaking the `popoverHeight: number` contract — it now keeps `prev.popoverHeight` unless the persisted value is a `number`. Arc footnote: the resize gesture itself was dropped in the Jan-26 popover rewrite (`63e94b290`) and re-wired five days after this PR by #10174 (`useDockPopoverResize.ts`), so the spec's inline "no UI resize gesture wired to it yet" comment is stale — the persistence pipeline it exercises is unchanged.

## Lesson

- **Adding a persisted app-state field means touching all four wiring points** — `AppState` type, `electron/store.ts` schema, a `handleAppSetState` branch, and the hydration consumer. Grep `electron/ipc/handlers/app/state.ts` for an `in partialState` branch for your key before assuming persistence works; the compiler cannot tell you it's missing.
- **A resolved `appClient.setState` promise proves nothing.** The handler silently drops both unknown keys (no branch) and out-of-range values (branch validation fails — the spec asserts 299 and 2001 are swallowed). It never throws for a rejected key. The only positive signal is reading the value back via `getState`.
- **The only test that proves persistence is a two-session E2E round-trip on a shared `userDataDir`** — `launchApp({ userDataDir })` → write → `closeApp` + `waitForProcessExit` → relaunch → poll `getState`. Copy `e2e/full/panels/core-dock-height-persistence.spec.ts`. PRs don't run E2E (nightly/release only), so run the bucket locally (`npm run test:e2e:full-panels`).
- **Zustand `hydrate` must not spread a partial persisted state over defaults.** `set({ ...state })` clobbers required-typed fields with `undefined` on fresh profiles; guard each field (`typeof state.x === "number" ? state.x : prev.x`) as `dockStore.hydrate` now does.
- **The handler branch should mirror the renderer clamp**, not invent its own range — the 300–2000 bounds intentionally track dockStore's `POPOVER_MIN_HEIGHT`/`POPOVER_MAX_HEIGHT_RATIO`, and a comment ties them together so drift is visible in review.

## Applies when

- Adding any new persisted field to `AppState` / electron-store `appState`, or wiring a new store's value through `appClient.setState`.
- Diagnosing a setting that silently resets to its default on every app launch even though persistence code exists and nothing errors.
- Assuming a clean typecheck or a resolved `setState` call means a value round-trips — the allowlist gap is invisible to both.
- Touching `handleAppSetState` in `electron/ipc/handlers/app/state.ts` or reviewing validation branches there.
- Reviewing any Zustand `hydrate(state)` that spreads persisted partial state into `set()` — check what a fresh profile (all-undefined) does to typed defaults.
