## Context

Plugin panels push live data to their views over one shared transport, `plugin:{pluginId}:{channel}`, ridden by `host.broadcastToRenderer`, `host.postToPanel`, and the managed-process stream. On the renderer, `plugin.on(pluginId, channel, cb)` subscribed by adding a raw `ipcRenderer.on` per call. Separately, opening a plugin panel view calls `plugin:activate-for-view` → `PluginService.activatePluginForView` for first-use activation before `PluginViewHost` dynamically imports the view module. #10626 (issue #10618, part of 1.0 plugin-panel hardening #10511) fixed two independent gaps on this path.

## Problem

Two symptoms. (1) With two open instances of the same panel kind, every `postToPanel` push reached BOTH instances — cross-instance data leakage, making shared-panel-kind UIs impossible. A plugin had no way to target one instance. (2) When a plugin failed to activate as its view opened, the author saw a generic "import timed out" / "handler not found" in the view's ErrorBoundary — never the real activation cause (manifest collision, `activate()` throw, worker fork failure). The single `Promise.race` in `PluginViewHost` couldn't distinguish activation-failure from import-timeout, so the most useful error appeared at exactly the moment authors were debugging activation.

## Root cause

(1) The transport is keyed only by `(pluginId, channel)`, with no per-instance discriminant, and every `plugin.on` registered its own physical `ipcRenderer.on` — a single push hit every listener on the channel. This is the DEFAULT failure mode of any shared broadcast transport lacking an addressing field. (2) `activatePluginForView` returned `void`. Activation failures WERE recorded — persisted to the provenance `loadError` — but never crossed the IPC boundary, so the renderer got a resolved-to-void result and proceeded to `import()` an unactivated module whose handlers never bound. The error existed; it just wasn't RETURNED.

Two details make the fix non-obvious. `activatePlugin` never rejects (the contribution-point trigger contract), so the failure can't be caught with try/catch — it's read back from the persisted `loadError` AFTER the await (covers all three failure modes). And the result is a plain discriminated union `PluginActivationResult = {ok:true} | {ok:false;error;stack?}`, NOT a thrown `Error`, because #6116: custom `Error` properties are stripped a second time on contextBridge deserialize — only a plain object survives; the renderer re-throws an `AppError` (`PLUGIN_ACTIVATION_FAILED`) from `{ok:false}` on its own side, before the import.

## Lesson

- **On a shared push transport keyed only by identity, per-instance routing needs a wire ENVELOPE with a discriminant, not N raw listeners.** The fix wraps EVERY push in `PluginPanelEventEnvelope = {panelId, payload}` (`panelId: null` = broadcast) — `broadcastToRenderer`, `postToPanel`, AND the process stream all envelope, so the preload dispatcher sees one uniform shape. Adding the field to only some push sites would desync the multiplexer.
- **Collapse the N-listeners-per-channel pattern into ONE physical listener + a ref-counted multiplexer.** `_pluginPushOn` in `electron/preload.cts` keeps `Map<fullChannel, {handler, subscribers: Map<panelId|null, Set<cb>>}>`: one `ipcRenderer.on` per channel fans out by `panelId`; the physical listener tears down only when every panelId bucket empties (else an unmounted view leaks its channel listener). It snapshots the Set before dispatch (a subscriber may unsubscribe mid-callback) and wraps each subscription freshly. `plugin.on` → broadcast bucket (`null`); `plugin.onPanel(...,panelId,...)` → targeted bucket. Malformed envelopes degrade to a broadcast rather than crashing the dispatcher.
- **Reject an empty-string target LOUDLY at every layer.** `postToPanel`, the dev-worker proxy, and `plugin.onPanel` all throw on `panelId === ""` — the host rejects an empty target, so an empty subscription would be a silently-dead listener. `undefined`/`null` explicitly mean broadcast and must NOT throw.
- **An error you PERSIST but don't RETURN across a process boundary becomes a misleading downstream failure.** `activatePluginForView` wrote `loadError` but returned `void`, so the renderer imported an unactivated module and blamed the import. Cross-boundary surfacing is not "log it in the service" — it's "return a typed outcome the far side inspects." Return `PluginActivationResult` and have `PluginViewHost` throw BEFORE `import()`. And return a plain discriminated union, never a thrown `Error` (#6116). The SDK hook `usePluginPanelEvent` holds its handler in a ref so inline closures don't re-subscribe every render — only `pluginId`/`channel`/`panelId` changes tear down.
- **Know the coverage gap you're shipping:** built-in plugins have no persisted provenance record, so a built-in `activate()` failure reads back as `{ok:true}` and still falls through to the generic import error — surfacing it would need a separate in-memory built-in load-error map. A deliberate documented limitation, not a bug.

## Applies when

- Adding or changing any push over `plugin:{pluginId}:{channel}` (`host.postToPanel`, `broadcastToRenderer`, process stream) — every push MUST envelope with `{panelId, payload}` or the preload multiplexer in `electron/preload.cts` mis-routes.
- Building per-instance targeting on ANY shared broadcast transport where multiple subscribers share one identity key — reach for envelope-discriminant + single-listener multiplexer, not one raw listener per subscriber.
- Subscribing a plugin panel view to host pushes — `usePluginPanelEvent(pluginId, channel, panelId, cb)` for per-instance, `usePluginEvent` for broadcast; they do NOT cross-deliver.
- Surfacing a Main-side failure (activation, load, install) to the renderer — return a typed `{ok:false;error}` the renderer inspects, not a thrown `Error` (#6116); `activatePlugin` never rejects, so read the persisted `loadError` after the await.
- Diagnosing a plugin view showing a generic "import timeout" / "handler not found" — the real cause is likely a swallowed activation error, not the module load.
