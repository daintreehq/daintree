## Context

Forge provider selection is a three-tier precedence chain in the pure function `resolveForgeProvider` (`electron/services/forgeProviderResolver.ts`): per-project override (#8111, tier 1) → global default (#8110) → first hostname match. Three surfaces feed it their own inputs: `FORGE_RESOLVE_PROVIDER` in `forgeSettings.ts` (what the Preferences UI displays), the workspace-host PR-detection path (`WorkspaceHostPool.readForgeSettingsForProject` → `PullRequestService.setForgeSettings`), and `resolveForCwd` (`electron/ipc/handlers/forgeResolution.ts`) — the shared cwd→provider resolution behind every renderer-facing forge operation (`forge.ts` open/assign, `forgeData.ts` list/get; today also `forgeAuditService` and the `githubWorkIssue`/`githubCreateIssue` commands).

## Problem

The per-project provider override set in project settings was silently ignored by every actual forge operation (#9984). Observable even with only GitHub installed: set the override to GitHub on a repo whose remote hostname isn't `github.com` — Preferences reports "GitHub, active via override" while every forge call throws "No forge provider registered for this repository". With a second provider installed it's quieter and worse: operations route to the hostname/default pick instead of the user's explicit choice, with nothing signalling the divergence.

## Root cause

`resolveForCwd` called `resolveForgeProvider({ remoteUrl, forgeProviderOverride: null, globalDefaultProviderId })`. The function's doc comment says keeping one shared copy "means the precedence chain can't drift between the two surfaces" — which is true for its own two callers (`forge.ts` vs `forgeData.ts`) and useless against the other two resolution surfaces, each of which loads project settings independently and passed the real override. Sharing the pure resolver moved the drift from the precedence logic into the input plumbing, where no type error catches it: `forgeProviderOverride: null` is a perfectly valid input meaning "no override set".

Null-ing the input breaks two behaviors at once, because tier 1 is deliberately fail-closed: a set override searches the full registry (beating hostname matching entirely), and override-set-but-unregistered returns `NO_MATCH` with no fallthrough. So the null-passing path both ignores a valid override (mis-route) and voids the intentional block on an invalid one.

Why it was hardcoded at all: `resolveForCwd` only receives a cwd, which is frequently a linked-worktree subdirectory, and `ProjectStore.getProjectByPath` keys projects on the main worktree path — a naive exact-path lookup misses, so the original author skipped project resolution entirely. The fix derives `mainWorktreePath` via `gitService.listWorktrees().find(wt => wt.isMainWorktree)?.path` (git reports the main worktree from anywhere inside the repo), falling back through `getRepositoryRoot(cwd)` to the raw cwd, every step `.catch()`-degrading to the pre-fix null-override behavior so a broken worktree listing never breaks forge ops that previously worked. That resolved `mainWorktreePath` later became load-bearing a second time: #10563 stamps it as `repoRef.projectPath` for file/CLI-backed providers.

## Lesson

- **A shared pure function guarantees nothing about its inputs.** "One resolver so precedence can't drift" only covers callers of that copy; a call site stubbing an input (`forgeProviderOverride: null`) reintroduces the drift invisibly, since the stub is type-valid. When touching `resolveForgeProvider` inputs, grep every call site — there are three independent surfaces (forgeSettings display, WorkspaceHostPool → `PullRequestService.setForgeSettings`, `resolveForCwd`) and each loads project settings itself.
- **cwd→project mapping in the main process must resolve the main worktree path first.** `ProjectStore.getProjectByPath` keys on the main worktree path; IPC-supplied cwds are often linked-worktree subdirectories. Use the `resolveForCwd` pattern: `listWorktrees()` → `isMainWorktree` → `getRepositoryRoot(cwd)` fallback → raw cwd, each non-fatal. Reuse the already-resolved `mainWorktreePath` (it's also `repoRef.projectPath`) rather than recomputing.
- **Fail-closed precedence tiers make an ignored input doubly wrong.** Because a set-but-unregistered override intentionally returns `NO_MATCH` (no fallthrough), passing null doesn't just lose the preference — it converts "block" into "silently fall through to hostname". Any surface that skips the real value voids the fail-closed guarantee, not just the routing.
- **Settings display and settings effect are separate code paths — test the effect path.** `FORGE_RESOLVE_PROVIDER` honoring the override proved nothing about operations. `electron/ipc/handlers/__tests__/forgeResolution.test.ts` shows the pattern: assert the override actually reaches the resolver's inputs from the operation entry point, including the linked-worktree-cwd and fallback-chain cases.
- **Degrade added lookups to the pre-fix behavior.** Every new lookup in the fix catches to a null override, so the worst failure mode is the old behavior — never a new hard error on a path that used to work.

## Applies when

- Adding or consuming a per-project setting in the main process starting from a cwd or worktree path — any `projectStore.getProjectByPath(...)` fed by an IPC-supplied directory.
- Touching `electron/ipc/handlers/forgeResolution.ts`, `forgeProviderResolver.ts`, `forgeSettings.ts`, or the forge-settings plumbing in `WorkspaceHostPool` / `PullRequestService`.
- Diagnosing split-brain symptoms: "settings/preferences show provider X but operations fail or use Y", or an override/default that works in one surface and not another.
- Reviewing any shared pure resolver where a call site passes a literal `null`/`undefined` for an input other surfaces populate — especially when a comment claims the sharing itself prevents drift.
- Writing tests for a settings-driven behavior and tempted to assert only the display/read path rather than the operation path.
