## Context

`BrowserPane` and `DevPreviewPane` host Electron `<webview>` guests. `useWebviewEvents` listens for `did-navigate` / `did-navigate-in-page` and pushes each guest navigation into an undo-style history whose head is `history.present`. Both panes originally rendered `<webview src={currentUrl}>` with `currentUrl = history.present` — the idiomatic React controlled-prop shape, which is what made the bug invisible in review. #10185 fixed it (issue #9940 has the full diagnosis, verified against Electron's `42-x-y` source).

## Problem

Every link click inside the guest loaded the destination twice; SPA route changes (pushState/hash) became full reloads that wiped the previewed app's state; every navigation hit the user's dev server with duplicate requests. Programmatic navigations were also doubled (`commitNavigation` called `loadURL` while the state echo re-applied `src`). The misleading part: one of each doubled pair died with `ERR_ABORTED` (-3), which `loadWebviewUrl` swallowed as "benign" — masking the primary symptom of the double load.

## Root cause

Three layers, each individually reasonable, compose into a redundant reload:

1. On every committed guest navigation, `onLoadCommit` in Electron's `lib/renderer/web-view/web-view-impl.ts` syncs the `src` attribute to the new URL via `setValueIgnoreMutation` — so by the time `did-navigate` fires, the live DOM attribute already holds the destination and the observer never saw that write.
2. The `SrcAttribute` mutation observer in `lib/renderer/web-view/web-view-attributes.ts` deliberately converts observed `src` writes — including same-value writes — into a fresh load. Documented Electron behavior: assigning `src` its own value reloads the page.
3. React diffs the `src` prop against its previous vdom prop, not the live DOM attribute. Click A→B: attribute silently synced to B (step 1) → `did-navigate(B)` pushes `history.present = B` → React re-renders `src={B}`, sees prop A ≠ B, calls `setAttribute("src", B)` → to Electron a same-value write (step 2) → second `loadURL(B)` for a page already shown, destroying the guest's client-side state.

The fix inverts ownership: `src` is a mount-time seed only, all post-mount navigation is imperative `loadURL`. In `BrowserPane`, `initialUrlRef` captures `history.present` once; because `key={webviewPartition}` remounts the element when the partition resolves late (#9965), a `lastPartitionRef` compare during render re-seeds `initialUrlRef` to the current URL before JSX reads it — a mount-only capture would strand the remounted guest on the original URL. In `DevPreviewPane`, `lastSetUrlRef` had to be seeded to the mount URL (not `""`) so the `isWebviewReady` effect doesn't fire a redundant first-ready reload. `loadWebviewUrl.ts` now swallows only `errorCode === -3` and surfaces every other rejection via `onRejected`.

Drift since merge: `BrowserPane` still uses `initialUrlRef` + `lastPartitionRef`; `DevPreviewPane`'s seed became `webviewSeedUrl` state + `effectiveWebviewSeedUrl` (`src={effectiveWebviewSeedUrl}`), navigation/lifecycle now in `useDevPreviewNavigation.ts` / `useDevPreviewLoadLifecycle.ts`. Invariant unchanged in both.

## Lesson

- **Never bind `<webview src>` to navigation-driven React state.** The controlled-prop shape looks correct and passes review, but Electron owns the attribute post-mount (it self-syncs on every guest navigation). Seed `src` once at mount and route every subsequent navigation through imperative `loadURL`.
- **The trap is two diff layers disagreeing:** React compares old-prop vs new-prop; Electron compares against an attribute it already self-updated via `setValueIgnoreMutation`. A React write that "changes" the prop is a same-value attribute write to Electron — and same-value `src` assignment is a documented reload trigger.
- **A key-driven remount invalidates a mount-time seed.** When `key={webviewPartition}` remounts the element, the fresh guest must seed to the URL the user is on now, not the URL captured at first component mount — `BrowserPane` re-seeds `initialUrlRef` via a render-time `lastPartitionRef` compare, before JSX reads the ref.
- **Once `src` is seed-only, exactly one code path may own `loadURL` and its guard ref.** `DevPreviewPane` pre-set `lastSetUrlRef` in `handleNavigate` and the dev-server URL effect — harmless under a controlled `src`, but with imperative-only navigation it makes the nav effect skip and strands the guest. Write the guard ref only in the loading effect and in first-load-suppressing seed paths.
- **Swallowed `ERR_ABORTED` (-3) is a doubled-navigation smell, not noise.** -3 means a pending load was superseded; swallow only that exact code (`loadWebviewUrl.ts`) and surface everything else — the old blanket swallow hid this bug's clearest signal.

## Applies when

- Touching the `<webview>` JSX or its `src`/`key`/`partition` props in `BrowserPane.tsx` or `DevPreviewPane.tsx`, or adding a new webview-hosting panel kind.
- Adding navigation features (address bar, back/forward, dev-server origin change, restore-on-remount) to a webview pane — history state may track `history.present`, but must never feed back into `src`.
- Diagnosing doubled dev-server requests, SPA preview state lost on link click, pushState/hash routes turning into full reloads, or repeated `ERR_ABORTED` (-3) from a webview.
- Assuming a same-value attribute re-bind is a safe no-op — for `<webview src>` it is a documented reload command.
- Reviewing changes to `webviewSeedUrl` / `effectiveWebviewSeedUrl` / `lastSetUrlRef` seeding or `loadWebviewUrl`'s filtering.
