## Context

The Browser pane and the Dev Preview pane both host Electron `<webview>` tags with independent, hand-rolled `did-fail-load` handlers: Browser in `src/hooks/useWebviewEvents.ts`, Dev Preview in `src/components/DevPreview/useDevPreviewLoadLifecycle.ts` (extracted from `DevPreviewPane`). Each classifies Chromium net error codes into specific overlays (name-not-resolved, offline, cert range, connection-refused with exponential-backoff retry) plus a bottom catch-all that shows a "Page failed to load" overlay — without the catch-all the webview is just a blank white rectangle. The error-code constants are declared file-locally in each handler (in the Dev Preview they live _inside_ `handleDidFailLoad`); there is no shared net-error module.

## Problem

A main-frame load failing with `ERR_FILE_NOT_FOUND` — a `file://` target or a missing custom-protocol resource — left the Dev Preview webview blank: no overlay, no retry, nothing (#9966). The misleading part was double: the guard read `if (e.errorCode === -6) return;` under a `// Ignore cancellations` comment, directly below a correct `-3` return, so it looked like deliberate, reviewed policy — and the identical pattern had shipped in the Browser pane for months, lending it pedigree.

## Root cause

In Chromium's `net_error_list.h`, `-6` is `ERR_FILE_NOT_FOUND`. The actual cancellation code is `-3` (`ERR_ABORTED`), which the handler already ignored one line up. The `-6` guard was therefore dead as documented and harmful as implemented: every main-frame `ERR_FILE_NOT_FOUND` short-circuited before the catch-all overlay could render.

The archaeology is the real lesson. The mislabeled `-3`/`-6` pair originated in the iframe→webview migration (`13be270f9`, Jan 2026) inside BrowserPane. PR #6107 then copied it into DevPreviewPane, its commit message explicitly saying "matching BrowserPane pattern" — pattern-fidelity propagated the bug. PR #7369 later fixed the Browser side: removed the `-6` guard, promoted the magic number to a named `ERR_ABORTED` constant, and added a regression test asserting `-6` IS surfaced (`BrowserPane.webview.test.tsx` "surfaces ERR_FILE_NOT_FOUND (-6) instead of silently swallowing it") — but never touched the Dev Preview copy. For a month the two stacks disagreed on the same error code, with a green test in one proving the other wrong. #10131 deleted the guard so `-6` falls through to the catch-all, and hardened the catch-all to clear `failLoadRetryRef` and zero `failLoadRetryCountRef`, so a pending connection-refused retry (500ms·2^n backoff, 8s cap, `MAX_RETRIES` 5) can't fire `loadURL` after a terminal error overlay is already showing.

## Lesson

- **Only `-3` (`ERR_ABORTED`) is ever safe to swallow in a `did-fail-load` handler.** It fires for benign superseded navigations; every other negative code on a main-frame load is a real failure that must reach a specific overlay or the catch-all. Verify any numeric `errorCode` guard against Chromium's `net_error_list.h` — never trust the inline comment; the comment here named the wrong semantics and passed review for five months.
- **The webview error-code taxonomy is duplicated, not shared** — `useWebviewEvents.ts` (Browser), `useDevPreviewLoadLifecycle.ts` (Dev Preview, constants inside `handleDidFailLoad`), `useDevPreviewNavigation.ts` (swallows `ERR_ABORTED`-class `loadURL` promise rejections because `did-fail-load` is the source of truth), and main-process `ProjectViewFactory.ts` (string-matches `err.message.includes("ERR_ABORTED")`). Changing error-code behavior in any one obliges a diff against the siblings; there is no compiler or shared constant to catch drift.
- **When you fix a bug at a pattern's origin, grep for the copies before closing.** #7369 fixed BrowserPane and even added the `-6` regression test, but the copy #6107 had planted in DevPreviewPane survived another month. A sibling's test asserting the exact opposite of your code's behavior is the strongest available signal that one of the two is wrong — treat that disagreement itself as a bug.
- **A terminal error overlay must cancel cross-class retry state.** The connection-refused branch schedules `failLoadRetryRef`; without the #10131 hardening, a `-102` followed by a `-6` left the stale retry timer alive to re-issue `loadURL` underneath the failure overlay. Any handler that mixes per-error-class retry machinery with a terminal catch-all must clear the timers and counters in the catch-all.
- **A mislabeled magic number is worse than a bare one.** Reviewers check that code matches its comment, not that the comment matches Chromium. If a numeric code matters, name it (`const ERR_ABORTED = -3`) so the claim is greppable and falsifiable.

## Applies when

- Touching `did-fail-load` or load-failure handling in `useDevPreviewLoadLifecycle.ts`, `useWebviewEvents.ts`, `BrowserPane.tsx`, `useDevPreviewNavigation.ts`, or the main-process view factories (`ProjectViewFactory.ts`, `SurfaceViewManager.ts`).
- Adding a new webview-hosting panel kind (e.g. a plugin-contributed panel) that needs load-failure UX — copy the _current_ Browser taxonomy (ignore `-3` only, `isMainFrame` guard, catch-all overlay), not an old snapshot of it.
- Diagnosing a blank webview that shows no error overlay and schedules no retry — grep the handler for early returns on numeric `errorCode`s before suspecting the dev server or proxy.
- Reviewing any guard on a numeric Chromium/Electron error code, or writing a comment that names a net error constant — verify the number against `net_error_list.h`.
- Fixing a bug in one of a pair of copied handlers — search for the phrase or structure that was copied (`git log -S`) and patch every instance in the same PR.
