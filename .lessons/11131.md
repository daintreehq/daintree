## Context

Daintree is multi-window: each window gets its own `ProjectViewManager` tracking that window's active project (`WindowContext.services`). Two process-level pointers also exist for convenience: `electron/window/windowRef.ts` holds a single mutable `projectViewManager` slot that every new window overwrites and every window close nulls out, and `ProjectStore.getCurrentProjectId()` is a SQLite "last-focused project" pointer. Issue #11100 found that `typedHandleWithContext` (`electron/ipc/utils.ts`), the source of `ctx.projectId` for ~97 IPC handlers, resolved through the `windowRef.ts` global instead of the actual sender.

## Problem

In a two-window session, IPC from any window other than the most-recently-created one resolved `ctx.projectId` to `null`. That made the cross-project terminal write guard in `electron/ipc/handlers/terminal/io.ts` fail _open_ (a null id looked like "no conflict") while help handlers failed _closed_. The same shape recurred independently in five sibling PRs: hibernation/idle-notification treated a visible-but-unfocused second window as background and could tear down its terminals (#11123); CopyTree could inject window B's exclusion rules into window A's agent context (#11125); switching window B's project persisted its outgoing layout under window A's project id (#11127); notification watch/badge/title state was last-writer-wins across windows (#11146); and the File-menu "Close Project"/"Project Settings" gates matched whichever project last switched, not the focused window (#11152).

## Root cause

Two different process-global "current project" answers were used to answer a per-window or per-sender question, and both are structurally wrong for it: `windowRef.ts`'s single slot only knows the last-created window's view map, and `ProjectStore.getCurrentProjectId()` only knows the last-_focused_ window, not "what does this specific sender show right now." The correct source already existed and was underused: `webContentsRegistry`'s `viewToProject` map spans every window (`getProjectForWebContents(webContentsId)`), written/deleted in lockstep by every `ProjectViewManager` instance, so it answers "what project does this exact sender belong to" without touching any global. Fixing `ctx.projectId` exposed a second hole in the terminal ownership gate: `info.projectId != null && ctx.projectId != null && info.projectId !== ctx.projectId` treats a null id on _either_ side as a wildcard match, so an unbound sender could still reach a project-owned terminal port. Fixed to exact equality — `(info.projectId ?? null) !== ctx.projectId` — null is its own identity that must match null, not a bypass. A third recurring shape was TOCTOU: handlers resolved identity/settings, awaited something (a kill, a git probe, `getAllStatesAsync`), then used a stale reference afterward — by which point a window could have switched, closed, or been evicted. The fix (`activeProjectIds.ts`'s `collectActiveProjectIds`, the frozen `SwitchOperation` in #11127) is always: snapshot synchronously before any `await`, thread the frozen value through, never re-read a mutable pointer after the fact.

## Lesson

- **Never answer "what project is this for" from a process-global singleton** (`windowRef.ts`'s single-slot `projectViewManager`, or `ProjectStore.getCurrentProjectId()`) when the caller is a specific window or IPC sender — resolve via `getProjectForWebContents(event.sender.id)` (cross-window, in `webContentsRegistry`), or that window's own `WindowContext.services.projectViewManager` looked up lazily by window id at call time, never hoisted into a closure at setup time.
- **"Is this project visible/active anywhere" is a union across every window, not equality against one pointer.** `collectActiveProjectIds()` unions every window's `getActiveProjectId()` plus the outgoing-switch bridge id, isolating a throwing per-window manager so one bad window can't drop the rest of the set — use it for hibernation/idle-close/notification-suppression checks instead of `=== getCurrentProjectId()`.
- **A nullable-id ownership/ACL check must require exact equality, including null-vs-null** — `a != null && b != null && a !== b` silently treats "unknown" as "authorized." Grep for this shape anywhere a project/owner id gates access to a resource.
- **Resolve synchronously at handler entry, before any `await`, and thread the frozen value through** — re-deriving identity after an awaited call can pick up a different window's state if a switch/close/eviction happened mid-await; this independently bit CopyTree settings (#11125), project-switch persistence (#11127), and hibernation sweeps (#11123).
- **This is a known recurring bug class in Daintree's multi-window architecture** — precedent chain #5541 → #6016 → #8607 → this six-PR arc — so any new per-window feature should assume "the global pointer is close enough" is false by default and verify against a two-window test.
- **State keyed "per app" instead of "per owner" silently clobbers across windows** — `AgentNotificationService.watchedTerminals` was a single reassigned `Set`; #11146's fix keys by `event.sender.id` into `Map<ownerId, ...>`, since window id is too coarse (a window hosts cached background views too) and project id is wrong (null is a legitimate distinct identity, and one project can be open in two windows).

## Applies when

- Writing or reviewing main-process code that answers "what project is this for" or "which project is visible/active" — grep for `getCurrentProjectId()` or `getProjectViewManager()` outside a legacy/non-PVM fallback path.
- Adding a new IPC handler through `typedHandleWithContext` — trust the resolved `ctx.projectId`/`ctx.senderWindow`, never reach around it for a global.
- Adding an ownership/ACL check that compares two nullable ids — confirm null-vs-null is treated as a match requirement, not a bypass.
- Touching hibernation, idle-auto-close, idle-notification, or any "is this project in the background" gate — use the `collectActiveProjectIds` union pattern, not equality against one pointer.
- Diagnosing "wrong data in the second window" or "action in window B affected window A" — the process-global-pointer-as-identity pattern is the first thing to check.
