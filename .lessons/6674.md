## Context

Each renderer-side xterm `Terminal` has a set of terminal-bound listeners installed on it: buffer/scroll/selection tracking, `onData` input routing, `onTitleChange` state + observed-title forwarding, `onKey` Enter detection, and (on Linux) primary-selection copy-on-select. These listeners live on the xterm instance, not in the persistent `managed.listeners` IPC set, so they must be re-installed whenever the xterm instance is rebuilt. A terminal is built on the **create path** (`TerminalInstanceService.getOrCreate()`) and rebuilt on the **wake path** (`TerminalHibernationManager.unhibernate()`) after the xterm instance was disposed during hibernation.

## Problem

`getOrCreate()` and `unhibernate()` each hand-rolled the full listener set independently. They drifted: the wake path silently lost three listeners — Linux primary-selection copy-on-select, `observedTitle` forwarding to the panel store, and `onData` routing through `writeTerminalInputOrFleet` (fleet broadcast). The bug was invisible on a freshly-created terminal and only surfaced after a hibernate→wake cycle, where a woken terminal misbehaved (no copy-on-select, stale title, input not broadcast to the fleet) in a way create-path terminals never did. Drift like this has no compile error and no test unless one is written specifically for the wake path.

## Root cause

Two independent copies of the same imperative listener-install block. Adding a listener to the create path is the natural edit; remembering to mirror it into the wake path's parallel block is the easy-to-forget second edit. The two blocks diverged over time. The fix extracts `installTerminalBoundListeners(terminal, managed, id, deps)` in `TerminalListenerInstaller.ts` as the single canonical installer; both paths satisfy the `TerminalListenerInstallDeps` callback interface and call it identically, removing ~500 lines of duplication. Subtle detail preserved in the extraction: `lastReportedTitleState` is a **function-local closure**, not stored on `managed` — storing it on the managed record would make a post-wake report inherit the previous session's state and silently drop the first title transition after waking.

## Lesson

- When the same xterm instance is built on more than one path (create + hibernate-wake), the listener set MUST come from one shared install function. Never maintain two parallel imperative blocks — they will drift silently, and the drift only manifests post-wake.
- "Add a listener" should be a single-edit operation. If adding a listener requires touching both `TerminalInstanceService` and `TerminalHibernationManager`, that is the smell that the install logic needs extracting.
- Per-session listener state that resets each install (e.g. `lastReportedTitleState`) belongs in a function-local closure, not on the persistent `managed` record — otherwise a woken terminal inherits the prior session's state and drops the first transition.
- Distinguish the two listener tiers: terminal-bound listeners (on the xterm instance, rebuilt on wake) vs. IPC listeners in `managed.listeners` (survive hibernation). Only the former needs re-installing on wake.

## Applies when

- Adding, removing, or modifying any listener on a renderer-side xterm `Terminal` (`onData`, `onTitleChange`, `onKey`, `onScroll`, `onSelectionChange`, `onBufferChange`, `onWriteParsed`, `attachCustomWheelEventHandler`, or host-element `addEventListener`).
- Touching `src/services/terminal/TerminalListenerInstaller.ts`, `TerminalInstanceService.getOrCreate()`, or `TerminalHibernationManager.unhibernate()`.
- A terminal feature works on a freshly created terminal but breaks after hibernate→wake (e.g. copy-on-select gone, observed title stale, fleet broadcast missing, Enter/agent-state detection dead).
- Any subsystem with two construction paths (cold create + warm restore/wake/rehydrate) that each set up the same per-instance handlers.
- Debugging "this only happens on a backgrounded/hibernated terminal" symptoms.
