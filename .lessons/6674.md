## Context

Each renderer-side xterm `Terminal` has a set of terminal-bound listeners installed on it: buffer/scroll/selection tracking, `onData` input routing, `onTitleChange` state + observed-title forwarding, `onKey` Enter detection, and (on Linux) primary-selection copy-on-select. These listeners live on the xterm instance, not in the persistent `managed.listeners` IPC set, so they must be re-installed whenever the xterm instance is rebuilt. At the time of this bug there were two construction paths: the **create path** (`TerminalInstanceService.getOrCreate()`) and a **hibernate-wake path** (`TerminalHibernationManager.unhibernate()`) that rebuilt the xterm instance after it was disposed during per-terminal hibernation. Per-terminal hibernation was fully removed in PR #10811 (the WebGL context swap was kept) — `TerminalHibernationManager.ts` and `unhibernate()` no longer exist, and `getOrCreate()` is today the installer's only call site. The teaching still applies: it's now a standing guard against any _future_ second construction path (warm-restore, session-rehydrate, or similar) hand-rolling its own listener block instead of calling the shared installer.

## Problem

`getOrCreate()` and `unhibernate()` each hand-rolled the full listener set independently. They drifted: the wake path silently lost three listeners — Linux primary-selection copy-on-select, `observedTitle` forwarding to the panel store, and `onData` routing through `writeTerminalInputOrFleet` (fleet broadcast). The bug was invisible on a freshly-created terminal and only surfaced after a hibernate→wake cycle, where a woken terminal misbehaved (no copy-on-select, stale title, input not broadcast to the fleet) in a way create-path terminals never did. Drift like this has no compile error and no test unless one is written specifically for the second path.

## Root cause

Two independent copies of the same imperative listener-install block. Adding a listener to the create path was the natural edit; remembering to mirror it into the wake path's parallel block was the easy-to-forget second edit. The two blocks diverged over time. The fix extracted `installTerminalBoundListeners(terminal, managed, id, deps)` in `TerminalListenerInstaller.ts` as the single canonical installer; both paths satisfied the `TerminalListenerInstallDeps` callback interface and called it identically, removing ~500 lines of duplication. Subtle detail preserved in the extraction and still true today: `lastReportedTitleState` is a **function-local closure**, not stored on `managed` — storing it on the managed record would make a post-rebuild report inherit the previous session's state and silently drop the first title transition. A side benefit that only became visible later: because the listener set was already unified behind one installer, deleting the hibernate-wake path in PR #10811 was clean — there was no duplicated listener block left behind to notice and remove separately.

## Lesson

- When the same xterm instance can be built on more than one path (historically create + hibernate-wake; today just create, but the risk returns the moment a second path — e.g. warm-restore/rehydrate — is added), the listener set MUST come from one shared install function. Never maintain two parallel imperative blocks — they will drift silently, and the drift only manifests on the second path.
- "Add a listener" should be a single-edit operation: touch `installTerminalBoundListeners` and nothing else. If adding a listener ever requires touching a second call site's own hand-rolled block, that is the smell that the install logic needs extracting (again).
- Per-session listener state that resets each install (e.g. `lastReportedTitleState`) belongs in a function-local closure, not on the persistent `managed` record — otherwise a rebuilt terminal inherits the prior session's state and drops the first transition.
- Distinguish the two listener tiers: terminal-bound listeners (on the xterm instance, needing reinstall whenever the instance is rebuilt) vs. IPC listeners in `managed.listeners` (persistent, survive across the managed record's lifetime). Only the former needs re-installing if a second construction path ever exists again.

## Applies when

- Adding, removing, or modifying any listener on a renderer-side xterm `Terminal` (`onData`, `onTitleChange`, `onKey`, `onScroll`, `onSelectionChange`, `onBufferChange`, `onWriteParsed`, `attachCustomWheelEventHandler`, or host-element `addEventListener`).
- Touching `src/services/terminal/TerminalListenerInstaller.ts` or `TerminalInstanceService.getOrCreate()` — currently the installer's only caller.
- Introducing any new xterm-instance construction/rebuild path (warm-restore, session-rehydrate, or similar) — it must call `installTerminalBoundListeners` rather than hand-rolling its own listener set, even though the historical hibernate-wake path this lesson originated from is gone.
- A terminal feature works when freshly created but breaks after some other rebuild path, in a way create-path terminals never show (e.g. copy-on-select gone, observed title stale, fleet broadcast missing, Enter/agent-state detection dead) — the signature of a second hand-rolled listener block that drifted from the shared installer.
- Any subsystem with two construction paths (cold create + warm restore/rehydrate) that each set up the same per-instance handlers.
