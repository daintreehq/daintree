## Context

`CliAvailabilityService.checkAuth()` reads each agent's `AgentAuthCheck.envVar` (`shared/config/agentRegistry.ts`) to decide whether a detected CLI is `ready` or merely `unauthenticated` — 17 of the agents under `shared/config/agents/` (`claude.ts`, `codex.ts`, `gemini.ts`, `opencode.ts`, etc.) declare one. `CliAvailabilityService.test.ts` asserts the `unauthenticated`-when-no-config-file path, which requires clearing any of those env vars from `process.env` first or a real key on the machine flips the result to `ready`.

## Problem

The test passed on CI and failed locally with no code change involved — the classic inverted signal, since a failing local run is normally the one you trust less. The assertion under `beforeEach` cleared a hardcoded array of literal env var names (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `GITHUB_TOKEN`, `KIMI_API_KEY`, `AMP_API_KEY`, etc.) before checking that the CLI read as `unauthenticated`.

## Root cause

The hardcoded list was a hand-maintained snapshot of `authCheck.envVar` across the registry at some point in the past, not a live read of it. As agents were added to `shared/config/agents/`, the list was not updated in lockstep — at least one agent's `authCheck.envVar` was present in the registry but absent from the test's clear-list. On a developer machine with that real key exported (a totally normal dev setup), `checkAuth`'s env-var probe saw it, the CLI read as `ready`, and the `unauthenticated` assertion failed. CI never has any of these keys set, so the clear-list's incompleteness was unobservable there — the clean CI environment doesn't validate the isolation, it just never exercises the gap. Any hardcoded copy of data that a registry already owns has this shape: it only diverges silently, and the divergence is invisible in whichever environment happens to start clean.

## Lesson

- **Never hand-copy a list that a registry already enumerates — derive it.** The fix replaced the literal array with `getAgentIds().flatMap(id => getAgentConfig(id)?.authCheck?.envVar ...)`, so adding a new agent's `authCheck.envVar` to the registry automatically extends the test's isolation list; there is no second place to remember to update.
- **A test env-isolation list is a drift-prone artifact exactly like a hardcoded duplicate of a config file** — treat it the same way you'd treat a copy-pasted constant: the question isn't "is it correct now" but "what's the single source of truth this should read from instead."
- **CI passing does not mean a test is hermetic — it can mean the environment CI happens to run in never exercises the isolation gap.** CI here has zero auth env vars set by construction, so a clear-list missing an entry is invisible to it; the only place this can fail is an authenticated dev machine, which is backwards from where you'd normally look for a real regression.
- **When a test with `beforeEach` env-clearing fails locally but passes on CI, suspect an incomplete clear-list before suspecting the code under test** — check `process.env` for exported keys matching anything in the relevant registry (`authCheck.envVar`, credentials, tokens) that the test doesn't clear.
- Mirror the production code's own handling exactly when deriving the list: `checkAuth` treats `authCheck.envVar` as `string | string[]` (`Array.isArray(envVar) ? envVar : [envVar]`), and the test's derivation does the identical normalization — a derived list that doesn't match the production branch's shape reintroduces the same gap in a subtler form.

## Applies when

- Adding a new agent to `shared/config/agents/` with an `authCheck.envVar` — no test update is needed now, but verify `CliAvailabilityService.test.ts` still derives from `getAgentIds()` rather than having regressed back to a literal list.
- Writing or reviewing any test that clears/mocks environment variables, config files, or other machine-state before an assertion — ask whether the isolation list is copied from somewhere or read live from the same source the code under test reads.
- Diagnosing "test fails locally, passes on CI" (or the reverse) for anything auth-, credential-, or env-var-adjacent — check what's set in your shell versus what the test clears before assuming a logic bug.
- Reviewing a PR that adds a hardcoded array of names/keys/paths that shadows an existing registry, config, or enum — flag it as a drift risk and suggest deriving it instead.
