## Context

Daintree wraps many toolbar/sidebar controls in a Radix `Tooltip` (shared wrapper `src/components/ui/tooltip.tsx`). Several of those same controls also open a Radix overlay — a `DropdownMenu` (AgentButton chevron, AgentTrayButton, ProjectSwitcher dropdown), a `Popover` (ProjectSwitcherPalette), or a `ContextMenu` (AgentButton right-click). This "trigger that is both a tooltip anchor and a menu opener" shape produced the same bug repeatedly (#5153/#5171 Apr 2026, then AgentButton/ProjectSwitcher/Toolbar June 2026), which is why the resolution arrived in layers rather than one commit.

## Problem

Radix opens a tooltip on **focus, not just hover**. Focus lands on a trigger un-asked in several flows, and each opened a tooltip with no user intent — usually right on top of whatever the dismissal just opened:

- Closing the trigger's own overlay (Escape, click-away, item select): Radix's `onCloseAutoFocus` restores focus to the trigger.
- `webContents.focus()` when a project view becomes active again after a switch.
- OS window re-activation.

A sibling symptom (#6119): after a _mouse_ dismissal the trigger also kept a `:focus-visible` accent ring, because browsers treat the restored focus as focus-visible.

## Root cause

Two distinct facts compound. (1) Radix's tooltip open path is focus-driven, so any programmatic refocus reopens it. (2) There is no event property that reliably says "this focus is a restoration, not a real hover" — the first fix (#5171) tried `event.detail > 0` and it failed, because Radix doesn't contract `detail` and keyboard/programmatic closes carry `detail === 0`. The reopen sources also differ in kind: some (menu close) expose a close handler you can hook; others (view swap, window re-activation) do not.

## Lesson — the actual solution in the current code

The bug is resolved by a **two-layer defense**, because the reopen comes from more than one focus source and no single mechanism covers them all. Both layers are load-bearing; neither alone is sufficient.

**Layer 1 — global backstop in the shared `Tooltip` wrapper (`src/components/ui/tooltip.tsx`).** The Radix Root is _always_ controlled via internal "managed shadow state" (even for uncontrolled consumers), which is what lets any forced close actually take effect. On top of that:

- **`TOOLTIP_AUTO_DISMISS_MS = 2500`** — every open arms a timer that force-closes. This is the catch-all for focus-opens that have _no close handler to hook_ (project-view swap, window re-activation): they have no natural close, so the timer caps their lifetime. `autoDismiss={false}` opts out for tooltips whose body IS the content (TruncatedTooltip, rich hover cards).
- **`TooltipTrigger` pointer-vs-focus guard** (`pointerActiveRef` + `onFocusCapture` early-return, #8008) — when focus arrives via a pointer interaction _on the trigger itself_, skip priming so a plain click doesn't pop the tooltip. (Radix's own `isPointerDownRef` blocks its internal path in parallel.)
- **`FixedDropdownVisibleContext` + remount key** (#8001) — force-close and remount a portaled tooltip when its `keepMounted` `FixedDropdown` goes `<Activity mode="hidden">`, so it can't strand at (0,0).

Layer 1 alone is insufficient for the menu-close case: the auto-dismiss still lets the tooltip _flash for up to 2.5s directly over the freshly-opened menu_, which is the most frequent and most visible occurrence.

**Layer 2 — per-trigger focus-restore suppression, on each control that anchors a tooltip AND opens a Radix overlay** (`AgentButton`, `AgentTrayButton`, `ProjectSwitcher`, `Toolbar` project pill). This prevents the menu-close reopen from ever happening, rather than dismissing it after the fact. Four parts, all required:

- **Controlled tooltip state** (`tooltipOpen`) passed as `open`/`onOpenChange` — you cannot suppress an open you do not control.
- **`isRestoringFocusRef`**, with `handleTooltipOpenChange` dropping any `open === true` while it is armed.
- **`suppress…ForFocusRestore()`** (sets open false + arms the ref) called in the overlay's **`onCloseAutoFocus`**. For a `Popover` (ProjectSwitcher) it is threaded down as `onDropdownCloseAutoFocus`; the Toolbar pill wires the ProjectSwitcher's close to its own pill suppression.
- **Cleared on the trigger's next genuine `onPointerEnter`** — the real "user wants it now" signal.
- **Pointer-vs-keyboard focus return:** a `wasPointerCloseRef` set in `onPointerDownOutside` lets `onCloseAutoFocus` `e.preventDefault()` the focus restoration **only for pointer dismissals** — which also removes the leftover accent ring (#6119) — while keyboard/Escape closes keep default focus return for WAI-ARIA / WCAG 2.4.3.

**Why both layers, not one:** Layer 1's `pointerActiveRef` handles _click-on-trigger_ focus; Layer 2's `isRestoringFocusRef` handles _overlay-close_ focus restoration; Layer 1's auto-dismiss timer is the backstop for focus sources with _no close handler at all_. They cover non-overlapping focus origins. The auto-dismiss is genuinely part of the solution, not a substitute for it — its job is the un-hookable cases, while Layer 2 prevents the visible flash on the hookable ones.

**Remaining cleanup:** Layer 2 is the same ~four-part block copy-pasted across four components (the comments literally read "Same pattern as AgentButton"). The working solution would be cleaner as one shared primitive — a `useTooltipFocusRestoreSuppression()` hook returning `{ open, onOpenChange, suppress, clear }` wired once to the overlay's `onCloseAutoFocus`/`onPointerDownOutside` and the trigger's `onPointerEnter`. Until that exists, every new tooltip-anchored-trigger-with-a-menu must repeat the Layer 2 block or it reintroduces the reopen. If you add a fifth instance, prefer extracting the hook over copying it again.

## Applies when

- Adding or auditing any control that is BOTH a `Tooltip` anchor AND opens a Radix `DropdownMenu`/`Popover`/`ContextMenu`/`Select` — wire the Layer 2 suppression or the tooltip will reopen on close.
- A tooltip flashes on top of a menu/palette/dialog that just opened, or appears after switching projects / re-focusing the window (Layer 1 backstop territory — check `autoDismiss` isn't disabled).
- A dismissed menu trigger keeps a `:focus-visible` accent ring after a mouse click (#6119) — same root cause; the pointer-vs-keyboard `preventDefault` split is the fix.
- You are tempted to detect "restored focus" via `event.detail`, `relatedTarget`, or any `data-radix-*` internal — don't; use the armed-ref-in-`onCloseAutoFocus` pattern.
- Working in `src/components/ui/tooltip.tsx`, `AgentButton.tsx`, `AgentTrayButton.tsx`, `ProjectSwitcher.tsx`, `ProjectSwitcherPalette.tsx`, or `Toolbar.tsx`.
- Distinct from #8005 (portaled tooltip stranding at (0,0) inside `<Activity mode="hidden">`) and #8131 (native `disabled` killing tooltip hover) — separate tooltip failure modes; cross-check all three when reworking the wrapper.
