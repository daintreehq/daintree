## Context

`electron/services/persistence/db.ts` opens the shared `better-sqlite3` database (`daintree.db`) and runs `probeDb()` at startup before any writes. If `probeDb()` reports corruption, the file is quarantined and a `.bak` is restored (the recovery path added in #4290). `probeDb()` is the gate that decides whether the on-disk DB is trustworthy.

## Problem

The startup probe gave false confidence: corrupt databases passed `probeDb()` and the app then read/wrote on top of a broken file. Separately, the first migration that added a foreign-key clause was silently unenforced, and extended SQLite corruption error codes (e.g. `SQLITE_CORRUPT_INDEX`) slipped past the corruption classifier and were treated as healthy.

## Root cause

Three independent SQLite gotchas in one open path:

- **`PRAGMA schema_version` is not a corruption probe.** It reads a single integer from the database header and returns instantly without touching any page below the header. A file whose B-tree is corrupted mid-file still has a valid header, so `schema_version` returns a number and the probe reported "healthy." It never walks the structure. (#4290 shipped `schema_version` as the probe even though its own lesson claimed `quick_check` — the code and the doc disagreed.)
- **`PRAGMA foreign_keys` defaults to OFF and is per-connection.** SQLite does not persist this setting; it must be re-issued on every connection open. The pragma block in `openDb()` set `journal_mode`, `busy_timeout`, etc. but never enabled `foreign_keys`, so FK clauses in migrations were declarative-only.
- **Corruption codes have extended variants.** A `Set(["SQLITE_CORRUPT", "SQLITE_NOTADB"])` exact-match lookup misses `SQLITE_CORRUPT_INDEX`, `SQLITE_CORRUPT_VTAB`, etc. — SQLite emits extended result codes, and the constructor can throw any of them.

## Lesson

- Use **`PRAGMA quick_check`** (not `schema_version`, not `integrity_check`) as the startup corruption probe. `quick_check` walks the B-tree pages and returns the string `"ok"` when healthy; any other value (a multi-line error report) means corruption. Read it with `pragma("quick_check", { simple: true })` and compare `!== "ok"`. `quick_check` is the cheaper sibling of `integrity_check` (skips the expensive index-vs-table cross-check) and is the right tradeoff for a per-boot gate. `schema_version` reads only the header and is worthless for detecting page-level corruption.
- Set **`PRAGMA foreign_keys = ON` in the per-connection pragma block on every open** — it is off by default and not persisted. If you rely on FK enforcement anywhere, it must live alongside `journal_mode`/`synchronous` in `openDb()`.
- Match SQLite corruption error codes with **`code.startsWith("SQLITE_CORRUPT")`** (plus an explicit `=== "SQLITE_NOTADB"`), never an exact-match set, so extended codes like `SQLITE_CORRUPT_INDEX` are caught.
- Keep the **safe default for non-corruption errors**: a permission error or transient lock should return `true` (healthy) so the recovery path doesn't quarantine a perfectly good DB.

## Applies when

- Touching `electron/services/persistence/db.ts` — `openDb()`, `probeDb()`, the pragma block, or the corruption-recovery/quarantine path.
- Adding or auditing a startup corruption check for any `better-sqlite3` / SQLite database; deciding between `schema_version`, `quick_check`, and `integrity_check`.
- Writing migrations that declare `FOREIGN KEY` / `REFERENCES` clauses and expecting them to be enforced.
- Classifying SQLite error codes (matching `SQLITE_CORRUPT*`, `SQLITE_NOTADB`, `SQLITE_FULL`) anywhere in the persistence layer.
- Debugging a report that the app loaded a visibly broken/empty store without triggering restore-from-backup.
