## Context

`registerAppLifecycleHandlers` in `electron/lifecycle/appLifecycle.ts` wires the macOS `app.on("activate", ...)` handler that recreates a window when the Dock icon is clicked and no windows are open. It checks `opts.windowRegistry.size > 0` (falling back to `BrowserWindow.getAllWindows().length > 0`) and calls `opts.onCreateWindow()` when the count is zero — the standard macOS "reopen on Dock click" pattern.

## Problem

On a slow startup a user can click the Dock icon before `app.whenReady()` has resolved. That fires `activate` early, the handler runs `onCreateWindow()` → `createWindow()`, and Electron throws `Cannot create BrowserWindow before app is ready` as an `[UNHANDLED_REJECTION]` (seen on 0.18.2, issue #10381). The symptom is misleading: it only reproduces under startup latency and looks like a window-creation bug, when it is really an ordering bug between the OS event and the app-ready gate.

## Root cause

`activate` is an OS-driven event with no readiness contract — Electron delivers it whenever the user clicks the Dock, including during the window between process launch and `whenReady()`. The handler had no ready guard, so a pre-ready click drove straight into `BrowserWindow` construction, which is illegal before ready.

The subtle part is why the obvious fix is wrong. Deferring the work via `app.whenReady().then(() => createWindowIfNone())` reintroduces a worse bug: `main.ts` (line ~629) already calls `await createWindow(...)` **unconditionally** inside its own `app.whenReady().then()` block. A deferred activate callback and that startup callback are two independent `whenReady` observers that both fire once ready and both read a window count of zero — so both create the initial window, producing a double-window race. The correct fix is to **drop**, not defer: `if (!app.isReady()) return;` as the very first statement of the handler. Dropping is lossless precisely because `main.ts` guarantees the initial window gets created once ready regardless of the swallowed activation. The guard must also sit _before_ the `windowRegistry.size` / `getAllWindows()` read — enumerating windows pre-ready is itself unsafe, which is why the test suite asserts the handler doesn't touch the registry (a throwing `size` getter) when not ready.

## Lesson

- **Guard OS lifecycle events (`activate`, `open-file`, `open-url`) with a synchronous `app.isReady()` check, not a deferral.** These events can arrive before ready; `if (!app.isReady()) return;` at the top of `appLifecycle.ts`'s activate handler drops the too-early event. Deferring the same work via `app.whenReady().then()` is the tempting-but-wrong fix.
- **Deferring window creation into a second `whenReady().then()` double-creates.** `main.ts` already unconditionally creates the initial window in its own `whenReady` callback; a second deferred creator reads the same zero window count and races it. Dropping the pre-ready activation is safe _only because of_ that unconditional-create invariant in `main.ts` — if that ever becomes conditional, the drop silently loses the first window.
- **Put the ready guard before any window enumeration, not just before creation.** Reading `BrowserWindow.getAllWindows()` / `windowRegistry.size` pre-ready is also unsafe; the guard is the first line so nothing downstream runs early. The test locks this with a registry whose `size` getter throws.
- **`app.isReady()` is re-evaluated per call, so the guard self-clears** — a click before ready is dropped, a later click after ready creates normally. No queue, no flag, no cleanup needed.

## Applies when

- Touching `electron/lifecycle/appLifecycle.ts` or any `app.on("activate" | "open-file" | "open-url", ...)` handler that constructs a `BrowserWindow` or enumerates windows.
- Diagnosing `Cannot create BrowserWindow before app is ready` unhandled rejections, or intermittent double-window-on-launch, on macOS slow startups.
- Assuming the fix for a pre-ready lifecycle event is to defer it via `app.whenReady().then()` — check first whether another `whenReady` observer (like `main.ts`'s startup create-window) already owns that work.
- Changing `main.ts`'s startup so the initial `createWindow()` becomes conditional — the activate handler's drop-when-not-ready behavior depends on that create being unconditional.
