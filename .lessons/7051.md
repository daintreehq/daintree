## Context

Terminal scrollback is persisted to `<userData>/terminal-sessions/<id>.restore` by `persistSessionSnapshotSync`/`persistSessionSnapshotAsync` and replayed on cold start by `restoreSessionFromFile` (`electron/services/pty/terminalSessionPersistence.ts`). The file payload is the raw output of `SerializeAddon.serialize()` from `@xterm/addon-serialize` — an opaque ANSI-laden blob whose internal structure is owned entirely by the third-party addon, not by us.

## Problem

The persisted format is an _undeclared schema_. When `@xterm/addon-serialize` changes its serialization format across a version bump (xterm 6.0 already shipped large breaking changes), an old `.restore` file written by the prior addon and replayed by the new one produces a silently scrambled terminal — garbled escape sequences, wrong scrollback, no error. There is no marker to tell "format the current code understands" from "format some earlier code wrote."

## Root cause

A blob persisted to disk has a schema even when no schema is written: the schema is implicitly defined by whatever code/library version produced it. With no version tag on the file, restore code cannot detect a format mismatch — it just feeds stale-format bytes into the new parser. Because `serialize()` output is opaque ANSI, a mismatch doesn't fail loudly; it replays as corruption. The fix prepends a literal `DAINTREE_SESSION_v1\n` header on every persist (both sync and async paths) and parses it on restore via `extractSessionContent`, which: strips the header for the known version, _rejects_ (`return null` → `NULL_RESTORE`) any `DAINTREE_SESSION_v*` it doesn't recognize, rejects truncated header prefixes (a partial write that looks like a header start), and treats headerless legacy files as v0 (backward compat for sessions already on disk). Note the size guard also had to learn about the header: `stat.size > SESSION_SNAPSHOT_MAX_BYTES + SESSION_HEADER_BYTES`.

## Lesson

When you persist a blob whose byte format is owned by an external library (xterm serialize, a codec, a wire format), treat it as an undeclared schema and stamp an explicit version header you control:

- Prepend a fixed magic+version prefix (`DAINTREE_SESSION_v1\n`) on **every** write path — easy to add to one path and forget the other (sync vs async here).
- On read, branch explicitly: known version → strip and use; recognized-magic-but-unknown-version → **reject the restore, don't guess**; truncated/partial magic → reject; no magic at all → treat as the implicit v0 that legacy files were written under.
- A silent fallback to "just use the raw bytes" is only safe for the _legacy headerless_ case, never for an unknown future version — rejecting is the correct failure mode for corruption you can't interpret.
- Remember to update any size/length guards to account for the added header bytes.
- This is distinct from field-level schema validation (Zod on a JSON shape, e.g. #1581): the payload is opaque, so you can't validate fields — only the version stamp tells you whether the parser matches the producer.

## Applies when

- Persisting or restoring terminal sessions / scrollback (`terminalSessionPersistence.ts`, `.restore` files, `restoreSessionFromFile`, `persistSessionSnapshot*`).
- Upgrading `@xterm/xterm` or `@xterm/addon-serialize` and worrying about existing on-disk session files restoring as garbage.
- Writing any opaque blob to disk whose format is defined by a third-party library/codec rather than your own JSON schema (you can't Zod-validate it, so version-stamp it).
- Adding a new persisted file format and deciding whether/how to make it forward-compatible against future format changes.
- Auditing restore/hydration paths for silent corruption: a restore that feeds stale-format bytes into a new parser with no version check is the trap.
