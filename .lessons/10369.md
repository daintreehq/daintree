## Context

`WorktreeStoreProvider` (`src/contexts/WorktreeStoreContext.tsx`) wakes the active project's terminals when its `WebContentsView` returns to the foreground. On a warm switch-back Chromium fires the Page Lifecycle `resume` event immediately before `visibilitychange` in the same turn, so #9704 (issue #9702) added a `scheduleWake()` de-dupe coalescing both into ONE wake fan-out. That fan-out (`wakeActiveWorktreeTerminals` → `fullWakeForVisibilityRestore` → `applyDeferredResize` → `terminal.refresh()`) is the single point of repair for backgrounded terminals: at background tier `TerminalResizeController` skips `terminal.resize()` and only forwards the PTY resize, deferring the xterm grid reflow to wake time.

## Problem

After switching back to a project, agent terminals rendered with wrong line wrapping — lines ran on and broke in the wrong places (issue #10362, a recurrence of the #7741 geometry-divergence garble). Clicking any terminal healed it instantly, because focus triggers a fresh container measurement and `fitAddon.fit()` re-syncs the xterm grid to the PTY. The self-healing-on-click behavior is the tell: the data was fine, only the geometry the grid was fitted against was stale.

## Root cause

#9704 coalesced the wake with `void Promise.resolve().then(() => { wakePending = false; if (visible) wakeActiveWorktreeTerminals(); })` — a **microtask**. A microtask drains at the end of the current task, which on a just-thawed renderer is still **before the first layout pass and before Chromium re-runs its observers**. So the wake's geometry reads and `terminal.refresh()` executed while xterm's `IntersectionObserver` had not yet re-fired and its `RenderService` was still paused (the observer un-pauses the renderer only when the view actually un-occludes). The reflow therefore fitted the grid to stale dimensions and the xterm grid and PTY stayed diverged until a real fit — i.e. the click. The de-dupe was correct; the **timing tier** was wrong.

The fix defers `scheduleWake` behind a **double `requestAnimationFrame`**. Per the HTML update-the-rendering step, rAF callbacks run before that frame's ResizeObserver/IntersectionObserver callbacks and paint — so a single rAF is still pre-observer. The first rAF lands pre-observer/pre-paint; the SECOND is the next frame, post-paint, with settled layout (the `warmReactivationGate` idiom). `document.visibilityState` is re-checked inside the inner rAF (a quick re-hide is a no-op), and the pending `wakeRafId` is `cancelAnimationFrame`'d in the effect cleanup and on `app:view-cached` so an unmounted or LRU-evicted provider can't fire a stale wake.

## Lesson

- **To run work after a renderer thaws/reveals, a microtask is too early — defer with a double `requestAnimationFrame`, not `Promise.resolve().then()`.** A microtask fires before the first layout pass and before ResizeObserver/IntersectionObserver re-fire; any geometry read or `terminal.refresh()`/`fit()` in it uses stale dimensions. First rAF = pre-observer/pre-paint, second = post-paint/settled. This is the `warmReactivationGate` settle primitive — reuse it.
- **A "heals on click/focus" terminal-render bug is geometry divergence, not a data bug.** The click's fresh measurement + `fitAddon.fit()` re-syncs grid↔PTY; the payload was never wrong. Look at when the wake/reflow ran relative to layout settle, not at the byte stream.
- **When you defer wake work to rAF, cancel the pending frames on teardown AND on view-eviction (`app:view-cached`), and re-check `document.visibilityState` at execution.** A scheduled rAF outlives the reason it was scheduled; an evicted or re-hidden `ProjectViewManager` view must not receive a stale wake. `scheduleWake` clears `wakeRafId` in cleanup and in the `onViewCached` handler for exactly this.
- **Double-rAF settles layout but does not defeat paint culling — it is one piece of the reveal class, not the whole cure.** A plain warm detach/reattach emits NO lifecycle event (none fires for a `setVisible(false)` WebContentsView), so the wake is triggered by main via `onViewWarmActivated`; and while the view is occluded behind the #9679 anti-flash bridge Chromium culls the paint. Current code stacks a SEPARATE `scheduleRepaint` double-rAF gate plus timed backstops (`REVEAL_BACKSTOP_DELAYS_MS = [1000, 3000]`) on top of the wake, kept separate so a repaint can't be coalesced away by an in-flight wake.
- **Test rAF-gated code by injecting a frame queue, not by awaiting Promises.** The suites replace `globalThis.requestAnimationFrame` with a manual queue and a `flushWakeFrames()` helper draining exactly two frames; three #9702 resume tests had to switch from `await Promise.resolve()` to `flushWakeFrames()` when the tier changed. A wake test that flushes microtasks asserts the wrong scheduler.

## Applies when

- Touching `scheduleWake` / `scheduleRepaint` in `src/contexts/WorktreeStoreContext.tsx`, or any warm-reactivation / project switch-back fan-out that reads terminal geometry or calls `refresh()`/`fit()`.
- Diagnosing agent terminals that render with wrong line wrapping after a project switch-back and heal on the first click (issues #10362, #7741, #9702).
- Coalescing/debouncing work triggered by Page Lifecycle `resume`/`visibilitychange` or a WebContentsView reveal — use double-rAF; reject a microtask defer that runs pre-layout.
- Adding any rAF/timer-deferred side effect inside a per-project-view provider — wire `cancelAnimationFrame`/`clearTimeout` into both the effect cleanup and the `app:view-cached` handler so evicted views can't fire stale work.
