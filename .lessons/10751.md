## Context

Cold project switches hold the outgoing project's `WebContentsView` composited on top as an anti-flash bridge, releasing it only when the incoming view signals it's safe to reveal. `createWindow.ts` already used an early `APP_SKELETON_PARSED` signal (fired by `public/skeleton-ready.js`) to show the very first application window quickly, but the project-switch path (now split across `ProjectViewSwitchController.ts`/`ProjectViewPaintGateController.ts`, part of a later oversized-file refactor of the original `ProjectViewManager.ts`) had never listened for it on subsequent switches. This is one PR in the #10760 project-switch performance arc.

## Problem

Users reported cold project switching still didn't feel fast even after earlier skeleton work had merged. Log analysis of a real `daintree.log` session (the `gateChannel`/`visibleMs` fields on `projectview.coldstart` telemetry) showed the underlying mechanism really did complete in 130-150ms — yet the user experience was still a themed canvas frozen for up to ~480ms, or the outgoing project frozen for seconds on an actual cold boot. Two independent gates were each individually reasonable and each hid the other's fix.

## Root cause

Before this PR, the cold-switch reveal released on `APP_VIEW_PAINTED` — React's first structural paint after a full cold renderer boot, 1.5-4s away — even though the incoming view's own `#startup-skeleton` (an opaque themed cover over the view's themed canvas background) painted in a few hundred ms. The earlier, sufficient signal already existed and already fired; nothing listened for it on this path. #10751 added a scoped one-shot `webContents.ipc.once(CHANNELS.APP_SKELETON_PARSED, ...)` listener, mirroring `createWindow`, releasing on a new `"skeleton-painted"` channel. `signalViewPainted` still also releases `"skeleton-painted"` as a fallback if the skeleton signal is ever missed, so the worst case never regresses past the old behavior; a focus-intent switch deliberately keeps the legacy `"painted"` gate, because the renderer's focus-on-activate listener isn't mounted until React commits.

That fix alone was still invisible: the revealed skeleton's CSS opacity fade shared `index.html`'s 400ms Doherty `animation-delay`, built to suppress a skeleton flash on a sub-threshold INITIAL app launch. A ~150ms cold-switch reveal landed inside that delay, so the view showed a blank themed canvas until ~480ms elapsed — the shared gate silently defeated the paint-signal fix. #10760 closed this with an opt-in `instantReveal` option threaded through `buildSkeletonCss`/`injectSkeletonCss` (now called from `ProjectViewFactory.ts`) that overrides ONLY the `animation-delay` longhand via a user-origin `!important` (`#startup-skeleton { animation-delay: 0ms !important; }`) — never the `animation` shorthand, which would silently restore an `animation-name` that `prefers-reduced-motion` had set to `none`. `createWindow.ts`'s initial-launch path does not pass `instantReveal`, so the flash-suppression gate stays correct there.

A third, independent gate was closed at the renderer level: `projectStore.ts`'s `switchProject`/`reopenProject` set the busy-overlay flag and then ran the heavy synchronous `buildOutgoingState()` panel-graph snapshot in the same task, so the overlay couldn't reach the screen until the snapshot finished — the click read as unresponsive. #10760 added `yieldToPaint()` (`new Promise(resolve => setTimeout(resolve, 0))`, `src/store/projectStore.ts`) between the flag flip and the snapshot — a macrotask, not `queueMicrotask`, since Chromium paints between macrotasks and never between microtasks — guarded by a `projectTransitionRequestId` counter so a newer transition started during the yield isn't clobbered by the stale snapshot/IPC in flight from the one it superseded.

## Lesson

- **When gating a "ready to reveal" decision, check whether a narrower signal that's already sufficient exists before defaulting to the broadest "definitely done" one.** `APP_VIEW_PAINTED` was not the only usable signal; `APP_SKELETON_PARSED` already existed and was already wired into `createWindow.ts` — it just wasn't being listened for on this path.
- **A shared loading-affordance threshold is scoped to whichever call site invented it, not to every future fast path that reuses the same mechanism.** After speeding up a paint signal, grep every consumer of the shared gate (here, `buildSkeletonCss`/`injectSkeletonCss`) for whether it silently reapplies an old delay and hides the win; add an explicit opt-out (`instantReveal`) rather than lowering the shared threshold globally, since the original call site (initial launch) still needs the full gate.
- **Override the narrowest CSS property, not the shorthand, when patching around a `prefers-reduced-motion` rule.** `animation-delay: 0ms !important` survives `#startup-skeleton { animation: none }`; touching the `animation` shorthand would silently restore a name reduced-motion had suppressed.
- **A `setState(); doHeavySyncWork()` sequence in one task never lets the browser paint the state change first.** Yield via `setTimeout(resolve, 0)` (a macrotask) between them, not `queueMicrotask`/`Promise.resolve().then()` — paints happen between macrotasks, never microtasks — and guard the resumed work with a request-id check so a newer transition that starts during the yield isn't clobbered by a stale snapshot.
- **A fallback must degrade to the OLD behavior, never a worse one.** `signalViewPainted` still releases `"skeleton-painted"` if the skeleton signal is ever missed; any future change to this gate should preserve that "at worst, no better than before" property rather than introducing a new hang.
- **Validate perceived-latency work against a real session log field, not only synthetic benchmarks.** `gateChannel`/`visibleMs` on `projectview.coldstart` telemetry is what surfaced the Doherty-gate defeat here — a unit test on the gating logic alone would not have caught it.

## Applies when

- Touching `ProjectViewPaintGateController.ts`, `ProjectViewSwitchController.ts`, or `createWindow.ts`'s paint-gate wiring (`APP_SKELETON_PARSED`, `APP_VIEW_PAINTED`, `signalViewPainted`) — this logic used to live in one `ProjectViewManager.ts`; it has since been split out.
- Modifying `skeletonCss.ts` (`buildSkeletonCss`/`injectSkeletonCss`) or any shared Doherty-style loading-delay CSS reused across both the initial app launch and later project switches.
- Adding a `set()` followed by expensive synchronous work in `projectStore.ts` or any Zustand store action where a UI affordance needs to paint before the work starts — reach for the `yieldToPaint()` macrotask pattern, not a raw microtask.
- Diagnosing "the perf fix works in isolated tests but a user still says it feels slow" — check for a second, independently-tuned gate (loading-UX threshold, animation delay, another cache layer) sitting downstream of the fix.
- Reviewing any `prefers-reduced-motion` override that touches the `animation` shorthand instead of a specific longhand like `animation-delay`.
