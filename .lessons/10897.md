## Context

`@daintreehq/plugin-sdk` (still unpublished at `0.1.0`) is the public type surface third-party plugins compile against, built by `packages/plugin-sdk/tsup.config.ts` with two entry points, `.` (`dist/index.d.ts`) and `./react` (`dist/react.d.ts`). Issue #10889 asked for the surface to be frozen before publish, since nothing in CI noticed when a code change silently altered exported types — only runtime contract tests (hello-daintree) were gated. #10897 added that guard.

## Problem

The obvious tool for "freeze a package's public API surface" is `@microsoft/api-extractor`, and that's what #10889 originally asked for. Standing it up would have meant running a second declaration-generation pipeline alongside the already-tuned tsup build, which raised the question of whether that second pipeline could reproduce bugs the tsup config had already solved.

## Root cause

tsup's dts bundler (`rollup-plugin-dts`) has two documented quirks the plugin-sdk config already works around, and api-extractor's own declaration pipeline would have re-exposed both. First, `PluginChannelSchema` (`shared/types/plugin.ts`) is public surface typed as `z.ZodType<TArgs>` / `z.ZodType<TResult>`; if zod isn't kept external, `rollup-plugin-dts` inlines zod's CJS runtime and mangles the qualified `z.ZodType` reference into invalid `undefined<T>` syntax in the emitted `.d.ts` — no build error, just broken output shipped to consumers. The config sidesteps this with `external: ["zod"]`, emitting a clean `import type { z } from "zod"` instead (zod is a peer dependency plugin authors already have). Second, `rollup-plugin-dts` injects a deprecated `baseUrl` that trips TS5101 under TypeScript 6, worked around with `ignoreDeprecations: "6.0"` scoped only to `dts.compilerOptions` in `tsup.config.ts` — not the package's own `tsconfig.json`, which stays clean for `npm run typecheck`. `packages/daintree-plugin/tsup.config.ts` carries the identical `ignoreDeprecations` workaround independently, confirming it's a `rollup-plugin-dts` issue, not specific to plugin-sdk. Api-extractor also has no native dual-entry-point support (plugin-sdk ships two: `.` and `./react`) and enforces TSDoc completeness by default, meaning blanket suppression comments across the SDK just to build. So #10897 shipped `scripts/ci/check-api-surface.mjs`: builds the package with the real tsup config, then snapshots the actual shipped `dist/index.d.ts` / `dist/react.d.ts` bytes into git-tracked `packages/plugin-sdk/api-report/*.d.ts`, wired as `check:api-surface` in the root `npm run check` chain. `--check` fails CI with a `::error` annotation and a diff; no-flag mode regenerates (`npm run api-surface:update`).

## Lesson

- **`rollup-plugin-dts` (tsup's dts bundler) silently mangles `z.ZodType<T>`-shaped public exports into invalid `undefined<T>` syntax unless zod is listed in tsup's `external` array** — this is not a build error, the `.d.ts` just ships broken. Any package with zod in its public type surface must externalize zod; check `external: ["zod"]` survives before touching `packages/plugin-sdk/tsup.config.ts`.
- **Don't stand up a second declaration-generation pipeline (api-extractor) next to an already-tuned tsup dts build just because it's the "standard" tool** — a parallel pipeline re-exposes the same `rollup-plugin-dts` quirks (zod mangling, the deprecated-`baseUrl` TS5101 trip) that the tsup config was specifically tuned to avoid, and you'd have to re-solve them independently in api-extractor's own config surface.
- **Snapshot the tool's actual shipped output, not a re-derived one**, when guarding an API surface produced by a bundler-based dts pipeline. `check-api-surface.mjs` diffs the real `dist/*.d.ts` bytes consumers resolve, so the guard can never drift from what's actually published even if the build pipeline changes later.
- **`ignoreDeprecations: "6.0"` in a tsup `dts.compilerOptions` block is a targeted TS5101 workaround for `rollup-plugin-dts`'s injected `baseUrl`, not a blanket suppression** — it's deliberately scoped away from the package's own `tsconfig.json` so `npm run typecheck` still surfaces real deprecations. `packages/daintree-plugin/tsup.config.ts` needs the identical override removed in lockstep once TS 7 lands and tsup catches up (per its own comment) — don't fix one and forget the other.
- **Api-extractor was rejected for plugin-sdk specifically for two reasons: no native dual-entry-point support, and default TSDoc-completeness enforcement** — if a future agent is tempted to "upgrade" the hand-rolled snapshot guard to api-extractor, both blockers still apply unless api-extractor's dual-entry story or doc-comment defaults change upstream.

## Applies when

- Touching `packages/plugin-sdk/tsup.config.ts` or `packages/daintree-plugin/tsup.config.ts`, or adding a new zod-typed export to plugin-sdk's public surface (`packages/plugin-sdk/src/index.ts`, `src/react.ts`) — verify `external: ["zod"]` still holds.
- A published or consumer-facing `.d.ts` contains `undefined<T>` or otherwise mangled generic syntax — check whether zod (or another type-only peer) is missing from the producing tsup config's `external` array.
- Considering swapping `scripts/ci/check-api-surface.mjs` for `@microsoft/api-extractor` as the plugin SDK's API-surface guard.
- Debugging a TS5101 "deprecated baseUrl" error that comes from the tsup dts build step specifically, not from `npm run typecheck`.
- Adding a new dual- or multi-entry-point public package under `packages/*` that needs its own API-surface freeze/guard.
