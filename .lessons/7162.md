## Context

Daintree runs two parallel migration chains at boot. `StoreMigrations.ts` (`runMigrations`) applies numbered electron-store migrations (`migration002`..`migration021` in `electron/services/migrations/`), and Drizzle's `migrate()` (`drizzle-orm/better-sqlite3/migrator`, called in `electron/services/persistence/db.ts:96`) applies the `.sql` files in `electron/services/persistence/migrations/`. Both must survive being interrupted mid-run and replayed on the next boot.

## Problem

A migration that completes its body but dies before the version is recorded will re-run on next boot, corrupting data or hard-crashing. Concrete symptoms in #7100: replaying `0001_add_scratches.sql` threw `table scratches already exists` (fatal boot crash); replaying migration 008 overwrote notification-sound settings the user had changed since first run; replaying migration 012 re-overwrote already-pinned agents; and migration 003 silently swallowed `saveRecipes` failures, bumping `_schemaVersion` past it with orphaned data left behind.

## Root cause

The version write is a **separate statement** from the migration body. In `runMigrations` the loop does `await migration.up(this.store)` then `this.store.set("_schemaVersion", migration.version)` — two non-atomic operations (`electron/services/StoreMigrations.ts`, the `for (const migration of pending...)` loop). A crash, kill, or power loss between them leaves the body applied but the version un-bumped, so the runner re-applies that exact migration next boot. The Drizzle chain has the same property at the file level. There is no transaction spanning "do the work" and "remember it was done," so **every migration is effectively a function that may run more than once on the same data.** Separately, once a `.sql` file ships in a tagged release Drizzle has recorded its hash (the `_journal.json` entries in `meta/`, replayed via `__drizzle_migrations`); editing that file afterward makes the migrator throw a checksum mismatch and breaks boot for every existing install — released `.sql` files are immutable.

## Lesson

Write every migration as if it will run twice on the same store:

- **SQL CREATE/ALTER must be idempotent.** `CREATE TABLE IF NOT EXISTS`, not bare `CREATE TABLE` (the `0001_add_scratches.sql` fix). Same for index/column adds.
- **Guard the destination, not the source.** Before transforming, check whether the target shape already exists and bail (migration 008 returns early when `completedSoundFile !== undefined`; migration 012's `entryNeedsMigration` predicate skips entries already carrying `pinned`). A blanket "transform all and write" re-clobbers user edits made between the first run and the replay.
- **Track whether anything actually changed** and skip the persist when nothing did (migration 012's `changed` flag) so a pure replay is a true no-op.
- **Rethrow on failure; never swallow.** A migration that catches its own error and returns lets the runner bump `_schemaVersion` past a half-done migration. Let it throw so `runMigrations`'s backup-and-restore path (`backupStore`/`restoreFromBackup`) activates. Migration 003 was rewritten to narrow its `try` to only `saveRecipes` and rethrow, and to clear legacy `appState.recipes` only after a confirmed save.
- **Never edit a `.sql` migration after it ships in a tagged release.** Add a new file instead. Any `.sql` correction must land before the next `v*` tag, or you must cut a fresh migration. Edits to `0000_baseline.sql`..existing files are a boot-breaking change for upgraders.

## Applies when

- Adding or editing any file in `electron/services/migrations/` (numbered electron-store migrations) or `electron/services/persistence/migrations/*.sql` (Drizzle).
- Touching `runMigrations` / the version-bump loop in `electron/services/StoreMigrations.ts`, or the `migrate()` call in `electron/services/persistence/db.ts`.
- Reviewing a migration PR: check for bare `CREATE TABLE`, transforms that don't guard the destination shape, swallowed errors in `up()`, or any edit to an already-released `.sql` file / `meta/_journal.json` hash.
- Investigating boot crashes after an upgrade with symptoms like "table already exists", checksum/hash mismatch from the Drizzle migrator, settings reverting to defaults, or `_schemaVersion` advancing past data that wasn't actually migrated.
- Deciding release timing for a schema change — a `.sql` correction is time-sensitive and must precede the next tag.
