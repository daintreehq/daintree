## Context

The release build signs `Daintree.app` with a hardened runtime and a fixed set of entitlements in `build/entitlements.mac.plist`. Those entitlements relax codesign enforcement so V8 JIT and native `.node` modules (`pty.node`, `better_sqlite3.node`) can load. The entitlement list is hand-maintained and was last meaningfully reasoned about on a much older Electron.

## Problem

`com.apple.security.cs.allow-unsigned-executable-memory` was still in the plist on Electron 41. It had been unnecessary since Electron 12 (upstream electron PR #26331 stopped requiring it) but survived four+ major upgrades. Stale entitlements are invisible: they don't fail the build, don't fail notarization, and don't crash the app — they silently widen the app's security relaxation surface for no reason. The related `disable-library-validation` is similarly load-bearing-by-fear: nobody is sure it's safe to drop.

## Root cause

Two distinct macOS signing traps stack here:

1. **Entitlement rot.** Entitlements that map to a runtime requirement of an old Electron/V8 are never re-audited on upgrade because nothing observable breaks when they're left in. The only way to know `allow-unsigned-executable-memory` is dead is to track upstream Electron release notes, not to test the app.
2. **`codesign --deep` is not a Team-ID audit.** `disable-library-validation` exists to allow loading libraries signed by a _different_ Team ID. The safe condition for removing it is "every embedded Mach-O actually shares our Team ID" — but `codesign --verify --deep` only validates the main executable's signature/seal chain; it does NOT enumerate every nested Mach-O slice and assert a common `TeamIdentifier`. So you cannot prove the entitlement is droppable with the standard verify command.

## Lesson

- On every Electron major bump, re-audit `build/entitlements.mac.plist` against upstream release notes — do not assume an entitlement is still required just because it's present and the build is green. Entitlements are dead weight, not inert: each one relaxes codesign enforcement.
- To prove `disable-library-validation` is safe to drop, you must walk the bundle yourself: `find "$APP.app" -type f -print0`, filter by `file -b … | grep Mach-O`, run `codesign -dv` on each, and assert `TeamIdentifier=` equals the expected 10-char Team ID. `scripts/ci/verify-team-identifier.sh` does exactly this and is wired as a release-only gate in `release-macos.yml` (arm64, x64, universal). It is a _canary_ — it does not itself drop the entitlement, it establishes the precondition.
- Gate the audit on the `APPLE_TEAM_ID` secret and fail fast if empty; a missing secret would otherwise make the check vacuously pass.
- Leave the gating condition in a code comment at the entitlement itself (it's in the plist), so the next person knows the removal is intentionally deferred, not forgotten.

## Applies when

- Bumping Electron to a new major version (currently 41) and touching or reviewing `build/entitlements.mac.plist`.
- Working on macOS code signing, notarization, hardened runtime, or `release-macos.yml`.
- Considering removal of `disable-library-validation`, `allow-unsigned-executable-memory`, or `allow-jit`, or adding a new `com.apple.security.cs.*` entitlement.
- Any task that reasons about whether `codesign --verify --deep` is sufficient to validate a `.app` bundle — it is not, for per-slice Team ID.
- Adding native `.node` modules (node-pty, better-sqlite3, etc.) that ship embedded Mach-O binaries into the signed bundle.
