## Context

When a renderer becomes unresponsive (event loop blocked, e.g. infinite loop or sync deadlock), `createWindow.ts` shows a "Window Not Responding" dialog on the `win.on("unresponsive")` handler offering the user a restart. Separately, `appWebContents.on("render-process-gone")` (added in #4346) implements full crash recovery: `recordCrash`, crash-loop debouncing (`CRASH_LOOP_THRESHOLD` within `CRASH_LOOP_WINDOW_MS`), OOM window recreation, and auto-`reload()` for single transient crashes.

## Problem

The unresponsive dialog's "Reload" button called `appWebContents.reload()`. On an unresponsive renderer this hangs indefinitely — the user clicks Restart and nothing happens, leaving force-quit as the only escape. The recovery action depended on the exact thing that was broken.

## Root cause

`WebContents.reload()` initiates a navigation, and navigation away from the current document first runs that document's `unload`/`beforeunload` handlers in the renderer. But the renderer is unresponsive precisely because its main thread is blocked — those handlers can never fire, so reload waits forever. The intuitive recovery depends on the broken event loop.

`forcefullyCrashRenderer()` does not negotiate with the renderer: it kills the render process at the OS/Chromium level and synchronously fires `render-process-gone` with `reason: 'crashed'`. That lands in the existing `render-process-gone` handler, which records the crash, applies crash-loop debouncing, and (for a single non-OOM crash) calls `appWebContents.reload()` — and _that_ reload succeeds because the renderer is now freshly killed, not blocked. The fix reuses the crash-recovery path instead of inventing parallel restart logic; nothing new to wire.

## Lesson

- To recover an **unresponsive** (not crashed) renderer, never call `reload()`/`loadURL()` — they block on unload handlers the dead event loop can't run. Use `webContents.forcefullyCrashRenderer()` to forcibly terminate, which fires `render-process-gone { reason: 'crashed' }` and funnels into your existing crash-recovery handler. Let that handler own the actual reload, debounce, and loop detection.
- Treat "unresponsive" and "crashed" as the same downstream recovery: forcing the crash collapses unresponsive into the well-tested crash path (crash-loop protection from #4346 included for free), rather than maintaining a second, untested restart code path on the unresponsive branch.
- In multi-window/multi-view setups, target the _active_ view's webContents, not just the top-level `appWebContents` — the current code resolves `getProjectViewManager()?.getActiveView()?.webContents` and falls back to `appWebContents`, guarding `isDestroyed()` on both.
- Microcopy: label the button "Restart view" (not "Reload") — it's a forced terminate-and-recover, not a soft refresh.

## Applies when

- Wiring or changing the `win.on("unresponsive")` handler or its recovery dialog in `electron/window/createWindow.ts`
- Any Electron recovery path tempted to call `reload()` / `loadURL()` on a renderer that may be hung (blocked main thread), as opposed to one that has already crashed
- Adding restart/recovery logic for a `WebContentsView` or `BrowserWindow` and deciding whether to invent new logic or route through the existing `render-process-gone` handler
- Debugging a "Restart/Reload does nothing on a frozen window" symptom
- Touching crash-loop debouncing — note that a user-triggered `forcefullyCrashRenderer()` counts as a `reason: 'crashed'` event and feeds `rendererCrashTimestamps`, so repeated manual restarts can trip `CRASH_LOOP_THRESHOLD` and load the recovery page
