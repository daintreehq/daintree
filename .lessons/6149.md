## Context

The GitHub PR list (now `plugins/builtin/github/`, formerly `electron/services/GitHubService.ts` + `src/components/GitHub/`) shows a per-PR CI rollup tick. `enrichPRsWithRequiredStatus` re-derives an effective status from _required_ checks only, caching results in the backend `prRequiredStatusCache` (60s TTL, `GitHubCaches.ts:167`). The renderer caches whole list responses in `src/lib/githubResourceCache.ts` (`CACHE_TTL_MS`).

## Problem

After a push triggered a new CI run, the PR list kept showing a green tick for up to ~6 minutes. The stale green was both _delayed_ (TTLs) and, worse, _permanent_ (it would never flip back even after the TTLs expired).

## Root cause

Two independent failures compounded, neither visible from one layer alone:

1. **Stacked TTLs sum.** The renderer's list cache (then 5min) sat on top of the backend's 60s `prRequiredStatusCache`. Worst-case staleness is the _sum_ of the layers, not the max — a renderer cache hit never reaches the backend, so its TTL fully precedes the backend's. The frontend was set in isolation, oblivious to the backend layer below it.
2. **A monotonic optimization froze a stale-good value.** `enrichPRsWithRequiredStatus`'s candidate filter excluded `ciStatus === "SUCCESS"` to skip re-enriching already-green PRs. But the raw `statusCheckRollup` flips back to `PENDING`/`FAILURE` on a re-push, so a PR that had _ever_ been green was permanently skipped and could never be corrected — independent of any TTL. "Skip work when the state is already good" is the dangerous shape: it makes a stale-good result a fixed point.

The fix: (a) drop the `!== "SUCCESS"` clause so enrichment runs on every list query regardless of prior status (`GitHubPRs.ts:273-275`); (b) lower the renderer TTL to 45s, strictly below the backend's 60s so the frontend never adds staleness beyond the backend window (`githubResourceCache.ts:14`); (c) add `focus`-driven SWR revalidation, throttled 30s via `lastFetchAttemptRef`, so returning to the window after a push forces a fresh fetch (`useGitHubResourceListSWR.ts:478-507`).

## Lesson

- When two caches stack (renderer over main/host), reason about **summed** worst-case staleness, not per-layer. The upper cache's TTL must be set with the lower one in mind; keep the frontend strictly below the backend TTL so it never _extends_ the stale window.
- Any "skip the expensive recompute when the value already looks good/done" guard (`status !== "SUCCESS"`, `if (cached.complete) return`, dirty-flag short-circuits) can turn a transient correct value into a **permanent stale fixed point** once the underlying state regresses. Re-derive unconditionally and let the cheaper TTL cache absorb the cost, or key the skip on something that actually changes (commit SHA, updatedAt), never on the derived status itself.
- For status that flips on external events (CI, push), add `window`-`focus`/SWR revalidation throttled by a `lastFetchAttemptRef` timestamp. Note `visibilitychange` was later dropped (#8066) in favor of `useSystemWakeStore.wakeEpoch` for sleep-wake; in-tab visibility flips no longer trigger redundant fetches.
- Write a regression test that flips raw rollup `SUCCESS → PENDING` and asserts enrichment still runs (see `GitHubService.adversarial.test.ts` `LISTPRS_ENRICHES_PRS_EVEN_WHEN_RAW_ROLLUP_IS_SUCCESS`). A pure cache-hit-rate test passes while the tick stays frozen.

## Applies when

- Touching GitHub PR/issue CI status, `enrichPRsWithRequiredStatus`, `prRequiredStatusCache`, `githubResourceCache`, or the `useGitHubResourceListSWR` revalidation effect.
- Setting or reviewing a renderer-side cache TTL that sits in front of another cache in the main process or a host (any two-layer cache stack) — check the layers don't sum to an unacceptable stale window.
- Adding any "skip recompute when already in the terminal/good state" optimization to enrichment, derivation, or polling code.
- Debugging "CI tick / status badge stuck green (or stuck at any value) and never updates" or "stale data clears eventually but a previously-good value never corrects."
- Adding focus/visibility/wake-driven revalidation to a list that reflects external mutable state.
