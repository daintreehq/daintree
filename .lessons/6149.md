## Context

The GitHub PR list (now `plugins/builtin/github/`, formerly `electron/services/GitHubService.ts` + `src/components/GitHub/`) shows a per-PR CI rollup tick. `enrichPRsWithRequiredStatus` re-derives an effective status from _required_ checks only, caching results in the backend `prRequiredStatusCache` (60s TTL, `GitHubCaches.ts:330`). The renderer caches whole list responses in `src/lib/forgeResourceCache.ts` (`CACHE_TTL_MS`, since renamed in the forge-neutral refactor; entry type is now `ForgeResourceCacheEntry`).

## Problem

After a push triggered a new CI run, the PR list kept showing a green tick for up to ~6 minutes. The stale green was both _delayed_ (TTLs) and, worse, _permanent_ (it would never flip back even after the TTLs expired).

## Root cause

Two independent failures compounded, neither visible from one layer alone:

1. **Stacked TTLs sum.** The renderer's list cache (then 5min) sat on top of the backend's 60s `prRequiredStatusCache`. Worst-case staleness is the _sum_ of the layers, not the max — a renderer cache hit never reaches the backend, so its TTL fully precedes the backend's. The frontend was set in isolation, oblivious to the backend layer below it.
2. **A monotonic optimization froze a stale-good value.** `enrichPRsWithRequiredStatus`'s candidate filter excluded `ciStatus === "SUCCESS"` to skip re-enriching already-green PRs. But the raw `statusCheckRollup` flips back to `PENDING`/`FAILURE` on a re-push, so a PR that had _ever_ been green was permanently skipped and could never be corrected — independent of any TTL. "Skip work when the state is already good" is the dangerous shape: it makes a stale-good result a fixed point.

The fix: (a) re-key the candidate filter off the derived status — the guard is now `pr.ciStatus !== undefined && pr.ciSummary === undefined` (`GitHubPRs.ts:343`), so a PR is re-enriched whenever its required-checks summary is absent (which it is after a fresh raw fetch on re-push), never permanently skipped because it was once green; (b) lower the renderer TTL to 45s, strictly below the backend's 60s so the frontend never adds staleness beyond the backend window (`forgeResourceCache.ts:48`); (c) add `focus`-driven SWR revalidation, throttled 30s via `lastFetchAttemptRef`, so returning to the window after a push forces a fresh fetch (`useGitHubResourceListSWR.ts:638-668`).

## Lesson

- When two caches stack (renderer over main/host), reason about **summed** worst-case staleness, not per-layer. The upper cache's TTL must be set with the lower one in mind; keep the frontend strictly below the backend TTL so it never _extends_ the stale window.
- Any "skip the expensive recompute when the value already looks good/done" guard (`status !== "SUCCESS"`, `if (cached.complete) return`, dirty-flag short-circuits) can turn a transient correct value into a **permanent stale fixed point** once the underlying state regresses. Re-derive unconditionally and let the cheaper TTL cache absorb the cost, or key the skip on something that actually changes, never on the derived status itself. The current guard does exactly this: it keys on `ciSummary === undefined` (`GitHubPRs.ts:343`) — `ciSummary` is recomputed per enrichment and resets to undefined after a fresh raw fetch, so the skip can never wedge on a stale-green PR the way `ciStatus !== "SUCCESS"` did.
- For status that flips on external events (CI, push), add `window`-`focus`/SWR revalidation throttled by a `lastFetchAttemptRef` timestamp. Note `visibilitychange` was later dropped (#8066) in favor of `useSystemWakeStore.wakeEpoch` for sleep-wake; in-tab visibility flips no longer trigger redundant fetches.
- Write a regression test that exercises the skip-guard and required-status derivation directly, not just cache-hit rate — a pure cache-hit-rate test passes while the tick stays frozen. Coverage now lives in `plugins/builtin/github/main/__tests__/prRequiredCIStatus.test.ts` (asserts `deriveRequiredCIStatus` flips `ciStatus`/`ciSummary` per inputs, including downgrading a raw rollup to `PENDING`/`FAILURE`) and `plugins/builtin/github/main/__tests__/GitHubPRs.test.ts` (asserts enrichment populates required-only `ciSummary` and that the raw global aggregates do not pre-populate it, so the `ciSummary === undefined` candidate filter actually fires).

## Applies when

- Touching GitHub PR/issue CI status, `enrichPRsWithRequiredStatus`, `prRequiredStatusCache`, `forgeResourceCache`, or the `useGitHubResourceListSWR` revalidation effect.
- Setting or reviewing a renderer-side cache TTL that sits in front of another cache in the main process or a host (any two-layer cache stack) — check the layers don't sum to an unacceptable stale window.
- Adding any "skip recompute when already in the terminal/good state" optimization to enrichment, derivation, or polling code.
- Debugging "CI tick / status badge stuck green (or stuck at any value) and never updates" or "stale data clears eventually but a previously-good value never corrects."
- Adding focus/visibility/wake-driven revalidation to a list that reflects external mutable state.
