## Context

`useAgentLauncher`, `AgentButton`, and `AgentTrayButton` resolve which preset launches per agent via a per-worktree hierarchy: `worktreePresets[worktreeId]` → agent-level `presetId` → none (`resolveEffectivePresetId` in `shared/types/agentSettings.ts`). The new `worktreePresets?: Record<string, string>` field lives on `AgentSettingsEntry`, keyed by worktreeId, so a preset picked in one worktree doesn't silently become the global default for every other worktree.

## Problem

The generic persistence path `agentSettingsStore.updateAgent(agentId, updates)` merges updates **shallowly at the entry level**: `agents[agentId] = { ...previous.agents[agentId], ...updates }` (`src/store/agentSettingsStore.ts:358`). If the toolbar called `updateAgent(type, { worktreePresets: { [wtA]: presetX } })` directly, the spread would replace the **entire** `worktreePresets` object — every other worktree's saved pick is wiped on the next selection, because shallow merge overwrites a nested Record wholesale rather than merging into it.

## Root cause

A `Partial<Entry>` merge that is shallow at the top field level is destructive for any nested map/record field: writing one inner key requires replacing the whole submap reference, and the merge keeps the new (single-key) reference, discarding the old siblings. This is invisible at the type level — `updateAgent` accepts `{ worktreePresets: Record<string,string> }` happily — so the clobber only shows up at runtime when a second worktree's selection silently vanishes.

## Lesson

For any nested `Record`/map field on an entry that is persisted through a shallow `{ ...prev, ...updates }` merge, never write the field directly with a single-key object. Add a dedicated action that **reads the current submap, spreads it, mutates the one key, then writes the full merged map** — `updateWorktreePreset` (`src/store/agentSettingsStore.ts:397`) does `const current = ...worktreePresets ?? {}; const next = { ...current }; ...; updateAgent(agentId, { worktreePresets: next })`, and collapses to `undefined` when empty so the field disappears cleanly. Keep resolution in one shared helper (`resolveEffectivePresetId`) consumed by every call site (launcher + both toolbar buttons) so the override-vs-default precedence can't drift; and when a scoped value goes stale, clear only the scope that held it (worktree slot vs agent-level `presetId`) rather than blanket-resetting (`useAgentLauncher.ts:373-386`).

## Applies when

You're adding or updating a single key inside a nested object/Record field (`worktreePresets`, `customPresets` keyed maps, per-id override maps) that is persisted via a store action doing top-level shallow spread, or via an IPC handler that replaces the per-entity record wholesale — the trap is silent loss of sibling keys, not a type error.
