## Context

`AppDialog` and `AppPaletteDialog` (`src/components/ui/`) autofocus into dialog content on open and `restoreFocusTo` the trigger on close — both are accessibility requirements, not bugs. Radix `Tooltip` (`src/components/ui/tooltip.tsx`) opens on keyboard focus as well as hover, also intentional (keyboard users need tooltip content too). `FileChangeList`'s row tooltip and the diff viewer's header tooltip (then `FileViewerModal`, issue #11030) are two of several places where these two correct behaviors collided: closing the diff viewer restored focus onto the row that had been hovered, reopening its tooltip with nothing hovered; opening the viewer autofocused a header wrapped in a `Tooltip`, popping it with no interaction at all. (`FileViewerModal` was later deleted for a dialog-presented `DiffPane` panel, which keeps the same `Tooltip`/`AppDialog` wiring — the mechanism still applies.)

## Problem

Tooltips appeared or stayed stranded around dialog transitions with no hover involved, and this was the third time the shape showed up. A structurally identical bug already existed for the `ShortcutHint` teaching overlay (`z-toast`, above `z-modal`): `ActionService.emitShortcutHint` fires post-dispatch on a milestone cadence and can land on top of a palette the same click just opened. Four components had already grown one-off fixes for these two overlay systems — `ToolbarCommandPaletteButton` and `ResumeSessionsToolbarButton` used a controlled-tooltip + `isRestoringFocusRef` gate, `LauncherQuickActions` and `ResumeSessionLine` used a `.finally(() => shortcutHintStore.getState().hide())` — and `FileChangeList`'s row (`autoDismiss={false}`, no workaround at all) proved the pattern would keep recurring because nothing enforced it centrally.

## Root cause

Two overlay systems share the same trigger — a dialog's programmatic focus move — and neither had a mechanism scoped to "a dialog just transitioned," only ad hoc per-consumer patches; Radix ships no provider-level "close all tooltips" API to call even if a component remembered to. Dismissing alone is also insufficient: the same focus move that necessitates the dismiss reopens the tooltip synchronously afterward through Radix's focus-handling path, so a bare "close on transition" effect flickers open again the instant `el.focus()` runs in the dialog's close handler.

The fix is a module-level registry (`src/lib/tooltipDismissRegistry.ts`, modeled on `src/lib/dialogEscapeBackstop.ts`): every mounted `Tooltip` calls `registerTooltipDismiss`, and `dismissAllTooltips()` closes every registered tooltip and arms `suppressedUntil = Date.now() + 250ms` (`TOOLTIP_FOCUS_SUPPRESS_MS`). `Tooltip`'s `handleOpenChange` (on the Radix `Root`, not `TooltipTrigger`) checks `isTooltipFocusOpenSuppressed()` before honoring a focus-driven open. The window clears early on `notifyTooltipPointerActivity()` (fired by `pointerenter` and non-touch `pointermove` — Radix opens tooltips from `pointermove` too, so a resting pointer still gets a real hover on its next micro-move). `clearDialogOverlays()` (`dialogOverlayDismissal.ts`) bundles `dismissAllTooltips()` with `shortcutHintStore.getState().hide()`, wired into `AppDialog`/`AppPaletteDialog` on every `isOpen` transition (guarded by `wasOpenRef` so a re-render while closed doesn't misfire) and again right before `el.focus()` in the close-restore path, since the exit animation runs after the transition-effect clear already fired. `AppPaletteDialog` skips the clear on palette-to-palette handoff (`usePaletteStore.getState().activePaletteId`) since the incoming palette owns the overlays. The `ShortcutHint` half was fixed at its actual source instead of papered over again: a pre-existing `suppressShortcutHint` flag on `ActionDefinition` (`shared/types/actions.ts`), already read by `ActionService.dispatch` (`src/services/ActionService.ts` ~line 486) but never set, got flipped to `true` on the three actions that open a modal palette (`action.palette.open`, `panel.palette`, `terminal.resumeSessions`).

## Lesson

- **When two overlay systems can both be stranded by the same programmatic-focus trigger, build one lifecycle hook that clears both, not per-component, per-overlay-type patches.** Four components had already reinvented this fix before #11034 centralized it into `clearDialogOverlays()`.
- **Dismissing a focus-triggered overlay is not enough if the same focus move fires again afterward** — add a bounded suppression window (`isTooltipFocusOpenSuppressed`, 250ms) that blocks the _next_ focus-driven open, cleared early only by genuine pointer intent (`pointerenter`/non-touch `pointermove`), or the dismiss just flickers.
- **If a workaround exists to delay a dispatch-triggered side effect until after a modal opens, check whether the side effect already has a suppress flag before adding another `.finally()`.** `suppressShortcutHint` already existed and was already honored by `ActionService`; the fix was setting it on 3 action definitions.
- **A global "clear everything" mechanism still needs an explicit opt-out for content-is-the-point overlays.** `IssueBadge`/`PRBadge` rich hover cards opt out via `dismissOnDialogTransition={false}`, exempt from both the forced close and the suppression window.
- **Don't fold every focus-adjacent overlay into a fix scoped to one lifecycle.** `AgentButton`, `DockLaunchButton`, `DockedTerminalItem`, `DockedTabGroup`, and `useDismissableTooltip` were deliberately left alone — their overlays are dropdown/context-menu/popover/drag-driven, not `AppDialog`/`AppPaletteDialog` open/close, and wiring them in would misfire on unrelated interactions.

## Applies when

- Wrapping an interactive element inside `AppDialog`/`AppPaletteDialog` content in a `Tooltip`, or placing one on anything a dialog's `restoreFocusTo` can land on.
- Diagnosing "a tooltip is stuck open over a just-opened or just-closed modal with nothing hovered" — check whether it's a Radix `Tooltip` (`tooltipDismissRegistry`) or the `ShortcutHint` overlay (`z-toast` above `z-modal`, `suppressShortcutHint`) — they look identical but need different fixes.
- Adding a new action that opens a modal palette or dialog — set `suppressShortcutHint: true` on its `ActionDefinition` instead of adding a `.finally(hide)` to whatever button dispatches it.
- Reviewing a PR that patches a stranded-tooltip/hint bug locally in one component — check `tooltipDismissRegistry.ts`/`dialogOverlayDismissal.ts` first; the global mechanism likely already covers it.
- Building any new dialog-like primitive that moves focus programmatically (autofocus in, restore out) — nearby focus-triggered UI needs to be told about that transition explicitly.
