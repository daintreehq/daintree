## Context

`PortBatcher` (`electron/pty-host/portBatcher.ts`) batches PTY output chunks per terminal and flushes them to the renderer over MessagePort. `mergeChunks` concatenates the pending chunks into a fresh `Uint8Array(totalBytes)` so the result is a standalone buffer that can be transferred safely — required because node-pty Buffers under 4KB share an 8KB pool slab, and transferring a slab-backed buffer detaches the whole slab and corrupts every aliasing Buffer (the PR #4639 invariant). Under agent-output floods the dominant case is a single-chunk latency-mode flush, where that allocate-and-copy is pure overhead.

## Problem

Every flush minted a new `Uint8Array(totalBytes)` and copied into it, even for the common single-chunk case where the chunk could in principle be transferred directly. The intuitive fix — an ArrayBuffer arena/buffer pool to amortize the allocation — looked attractive, but #4639's "never transfer Buffer.buffer" rule made any direct-transfer optimization feel categorically unsafe.

## Root cause

Two non-obvious facts had to be established, not assumed:

1. **The buffer pool was not justified — measured, not guessed.** A `node:perf_hooks` `PerformanceObserver` GC soak (PERF-063 in `scripts/perf/scenarios/soak.ts`, `measureMinorGc` filtering on `constants.NODE_PERFORMANCE_GC_MINOR`) replayed 400k × 2048B allocate+copy flushes (~800MB transient churn, far beyond any realistic inter-flush burst) and found total minor-GC pause sub-millisecond/zero. Per-flush `Uint8Array` allocation is young-gen garbage that the scavenger reclaims essentially for free; there was no measurable pause for a pool to retire. Note the soak baselines the **cost being retired** (the old path), not the new fast path.
2. **Zero-copy transfer is safe only under a precise ownership predicate.** A chunk can be transferred without copying only when it provably owns its entire ArrayBuffer (it already escaped node-pty's shared slab via `new Uint8Array(...)` at the `pty-host.ts` ingestion site). The fast path in `mergeChunks` guards on `owned && chunks.length === 1 && chunk.byteOffset === 0 && chunk.byteLength === chunk.buffer.byteLength` — byteOffset/byteLength prove the view is not a slab subview. Critically, `owned` is gated upstream in `pty-host.ts` on `targets.length === 1`: a transfer detaches the ArrayBuffer, so with 2+ renderer targets one batcher's flush would neuter the shared chunk out from under siblings still waiting to copy it. `entry.owned &&= owned` accumulates across writes so any non-owned write to the same entry poisons the fast path.

## Lesson

- **Instrument the cost a perf optimization would remove before building the optimization.** Gate the build on a measured baseline (here: a GC observer soak), not on an intuition that "allocating per flush must be expensive." Young-gen allocation churn is frequently sub-millisecond and not worth a pool. Keep the measurement scenario in the perf matrix as the documented gate evidence.
- **#4639 says "never transfer `Buffer.buffer`" because of slab aliasing — the safe inverse is a transfer guarded by proof the buffer is standalone.** Require all of: sole batcher (`targets.length === 1` upstream → `owned`), single chunk, `byteOffset === 0`, and `byteLength === buffer.byteLength`. Any of these failing (slab subview, multi-chunk merge, multi-target) must fall back to allocate-and-copy.
- Default the `owned` parameter to `false`. The safe assumption is that a chunk is shared and must be copied; opt into zero-copy only where ownership is proven.

## Applies when

- Touching `PortBatcher`, `mergeChunks`, or `pty-host.ts` data-fan-out / `RendererConnection` targets, or changing how PTY chunks are batched/flushed to the renderer.
- Adding or modifying any MessagePort/IPC transfer of a `Uint8Array`/`ArrayBuffer` originating from node-pty — re-check the slab-ownership predicate (byteOffset 0, byteLength === buffer.byteLength) before adding a chunk to a transfer list.
- Tempted to add an ArrayBuffer/buffer pool, arena, or object-reuse cache "to reduce GC pressure" anywhere in the pty-host or hot output path — first write a `node:perf_hooks` GC-observer soak (see PERF-063) to confirm there's a measurable minor-GC pause to retire.
- Reasoning about whether a per-flush/per-frame allocation in a high-rate loop is actually a bottleneck; measure young-gen GC pause before optimizing.
- Multi-window / per-project fan-out where the same chunk goes to multiple renderer connections — zero-copy transfer is unsafe once more than one consumer holds the buffer.
