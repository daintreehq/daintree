## Context

The Daintree MCP server (`electron/services/mcp-server/`) is the inbound control surface that lets an external agent or the in-app help assistant drive the IDE via `ActionService.dispatch`. Every action goes through two gates in `tierAuth.ts`: `shouldExposeTool` (used by `tools/list`) and `isTierPermitted` (used by `tools/call`). For the `external` (API-key) tier, the enforced set is normally the curated `MCP_TOOL_ALLOWLIST` in `shared.ts` — a hand-picked list of ~90 vetted action ids. `fullToolSurface` is a per-session opt-in flag meant to widen that surface for trusted external callers.

## Problem

Both gates short-circuited to `return true` for `tier === "external" && fullToolSurface`, before ever consulting `MCP_TOOL_ALLOWLIST`. An audit of every action definition found this exposed **335 of 426 actions** — including `system.openExternal`, `system.openPath`, `env.global.set`/`env.project.set`, `project.cloneRepo`, `terminal.kill`, `app.quit`, and forge writes — to any external client that flipped the flag. It looked safe in review because `shouldExposeTool` still hard-denies `danger === "restricted"` and `mcpVisibility === "hidden"/"discoverable"`, so the bypass read as "gated by risk metadata." It wasn't: zero shipped actions actually use `danger: "restricted"` (only test fixtures do), and only ~8 use `mcpVisibility: "hidden"/"discoverable"`, so those two floors covered almost nothing. The curated allowlist was the _sole_ real barrier, and `fullToolSurface` discarded it entirely.

## Root cause

The MCP spec is explicit that tool annotations — and by extension a self-declared `danger` rating — are untrusted UX hints, not an access-control boundary. This code inverted that: it treated "not restricted, not hidden" as equivalent to "safe to expose to an external key," when `danger` is author-set at action-definition time by whoever wrote the action, with no adversarial review against the external-API threat model. Fixing this is the same bug class as #8331 (plugins self-declaring `danger` and the renderer trusting it verbatim) — anywhere a security-relevant classification is set by the object being classified rather than by the boundary enforcing it, the classification is a hint, not a gate. The fix (`shared.ts`) adds `MCP_FULL_TOOL_SURFACE_ALLOWLIST = unionSet(MCP_TOOL_ALLOWLIST, MCP_FULL_TOOL_SURFACE_ADDON_ENTRIES)` — an explicit, currently-empty vetted add-on seam — and both gates in `tierAuth.ts` now do `MCP_FULL_TOOL_SURFACE_ALLOWLIST.has(entry.id)` instead of `return true`. The allowlist is provably a superset of the curated one (tested), so the opt-in can only widen access, never bypass the boundary.

## Lesson

- **A self-declared risk field (`danger`, `mcpVisibility`, or any author-set metadata) is never itself the access-control boundary** — it's a UX/confirm-flow hint. The boundary is always the server-side allowlist/gate that consults it. If an opt-in path skips the allowlist "because low-risk items are already filtered by the metadata," check how many real entries actually carry that metadata before trusting the argument — here it was 0 and ~8 out of 426.
- **An opt-in that widens a permission surface must be an explicit superset, never a bypass.** `MCP_FULL_TOOL_SURFACE_ALLOWLIST` is structurally guaranteed (via `unionSet` + a test asserting `TIER_ALLOWLISTS.external ⊆ MCP_FULL_TOOL_SURFACE_ALLOWLIST`) to only add to the curated list, so a future edit can't accidentally shrink the default surface when the flag is on.
- **Fix both the exposure gate and the dispatch gate in lockstep** (`shouldExposeTool` and `isTierPermitted`) — a tool visible in `tools/list` but rejected in `tools/call`, or vice versa, is its own bug class (#7155) and was addressed by routing both through the same `MCP_FULL_TOOL_SURFACE_ALLOWLIST.has(...)` call.
- **When adding a new vetted entry to `MCP_FULL_TOOL_SURFACE_ADDON_ENTRIES`**, treat it as a deliberate, individually-reviewed security decision — the set starts empty specifically so newly-added `danger: "safe"` actions don't silently inherit external-API reachability.
- **Test the negative, not just the positive, and pin sentinels to ground truth.** `tierAuth.test.ts`'s `fullToolSurface allowlist invariants (#10701)` block first asserts each sensitive id (`system.openExternal`, `system.openPath`, `env.global.set`, `project.cloneRepo`) is a real `BUILT_IN_ACTION_IDS` member outside `TIER_ALLOWLISTS.external`, THEN asserts it stays unreachable with `fullToolSurface` on — so the regression guard can't quietly pass by testing against a renamed or nonexistent id.

## Applies when

- Touching `electron/services/mcp-server/shared.ts` (`MCP_TOOL_ALLOWLIST`, `MCP_FULL_TOOL_SURFACE_ALLOWLIST`, `TIER_ALLOWLISTS`) or `tierAuth.ts` (`shouldExposeTool`, `isTierPermitted`) — any change to tier gating or the external/API-key surface.
- Adding a new built-in action and deciding its `danger`/`mcpVisibility` — remember these gate the confirm UX and hidden-from-listing behavior only, not external-API reachability; reachability is controlled solely by allowlist membership.
- Reviewing any opt-in flag that "widens" a permission or exposure surface — verify it unions onto an existing allowlist (and is tested as a superset) rather than short-circuiting the check that would otherwise run.
- Reviewing plugin, agent, or external-API authorization code that reads a field the caller or the object itself set (`danger`, capability flags, self-reported roles) and trusts it as the security decision instead of an independently-enforced list — same class as #8331.
- Auditing MCP tool surface size/composition — grep `BUILT_IN_ACTION_IDS` against `MCP_TOOL_ALLOWLIST`/`MCP_FULL_TOOL_SURFACE_ALLOWLIST` membership rather than trusting `danger`/`mcpVisibility` counts as a proxy for what's actually gated.
