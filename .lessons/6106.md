## Context

Main-process settings (terminalConfig, appTheme, privacy, notifications, voiceInput, ai/agentSettings, onboarding, appState) persist through an electron-store instance (`electron/store.ts`), updated from IPC handlers in `electron/ipc/handlers/`. electron-store seeds a `defaults` object into `config.json` on first launch when keys are absent.

## Problem

Updating a single field used the idiomatic pattern `store.set("slice", { ...store.get("slice"), field: value })`. Because `store.get("slice")` returns the fully-defaulted object (defaults merged in at read time), every such write persisted the _entire_ slice — including every default value — back to `config.json`. Once written, those values are concrete on-disk entries, so any future change to a default in code is silently ignored for existing users: the stale first-launch default wins forever. Sibling fields were also rewritten on every unrelated update.

## Root cause

electron-store merges `defaults` over on-disk data at read time only. A read-modify-write of the whole slice promotes transient defaults into persisted data. The fix is surgical dot-path writes — `store.set("slice.field", value)` — which touch only the addressed leaf and leave unaddressed keys absent so defaults keep applying. Two non-obvious traps in the fix itself:

- Dot-path writes are NOT safe for records whose keys are user-controlled. `agentSettings.agents` is keyed by agent IDs that may contain dots; dot-prop (electron-store's path engine) would parse `agentSettings.agents.my.agent` as nested objects. So that record is written one level up, at `store.set("agentSettings.agents", updatedAgents)` — the whole `agents` map at once, but still NOT the whole `agentSettings` slice (avoiding sibling-default baking).
- Clearing a field can't reuse `store.set(path, undefined)` (electron-store v11 throws — see lesson #2727). `handleAppSetState` branches to `store.delete("appState.<field>")` for undefined values to match the old JSON.stringify-drops-undefined behavior.

## Lesson

When persisting a single field to an electron-store slice from a handler, write the leaf path (`store.set("slice.field", value)`), never spread-and-rewrite the whole slice. The bulk-spread pattern is the readable, obvious one and it silently freezes defaults — treat `store.set("slice", { ...store.get("slice"), ... })` as a review smell in persistence code. Exception: when the target is a record keyed by user-controlled strings (agent IDs, project paths, anything that can contain a `.`), write the record one level up (`store.set("parent.record", map)`), because dot-prop will mis-parse dotted leaf keys as nested paths. Intentional full-slice resets to defaults (e.g. `store.set("agentSettings", DEFAULT_AGENT_SETTINGS)`) are fine and should stay explicit.

## Applies when

- Adding or reviewing IPC handlers in `electron/ipc/handlers/` that write settings (terminalConfig, appTheme, privacy, notifications, voiceInput, ai, onboarding, app/state) or services like `AppAgentService` / `TelemetryService`.
- A code-default change (new default value in `electron/store.ts` or `DEFAULT_*` constants) "doesn't take effect" for existing users but works on a fresh install.
- Persisting into a map/record whose keys come from user input (agent types, project IDs, file paths) — decide whether dot-path is safe given the keys.
- Bumping electron-store and grepping for risky write patterns (`store.set("...", { ...store.get(`).
