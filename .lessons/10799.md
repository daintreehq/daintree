## Context

Docked panel chips (`DockedTerminalItem`, `DockedTabGroup`) and grid panel headers (`PanelHeader`) both need to be dnd-kit drag sources for the same subsystem: dragging a panel between the dock, the grid, and other worktrees. The shared plumbing is `useDragHandle()` / `DragHandleProvider` (`src/components/DragDrop/DragHandleContext.tsx`), which publishes dnd-kit's `DraggableSyntheticListeners` (`onMouseDown`, `onTouchStart`, `onKeyDown`, …) from the sortable ancestor down to whichever element should act as the physical drag handle. `PanelHeader` already consumed this correctly, spreading the full listener object onto its header element; the dock chips had grab-cursor CSS classes (`cursor-grab active:cursor-grabbing`) but never called `useDragHandle()` at all, so the listeners existed but were attached to nothing.

## Problem

Filed as #10797: docked panels could still be dragged INTO the dock from the grid, but a docked panel could not be dragged back out to the grid, to another worktree, or reordered within the dock — despite visibly having the grab cursor. The fix looked like a one-line omission (just call `useDragHandle()` and spread the listeners onto the chip `<button>`, mirroring `PanelHeader`), but a naive full-spread would have traded one bug for a worse one: it would silently break the chip's primary click action (opening the panel preview popover) for keyboard users.

## Root cause

dnd-kit's `KeyboardSensor` treats Space/Enter on the focused activator node as "pick up this draggable" and calls `event.preventDefault()` before doing so. `PanelHeader`'s drag surface is a non-interactive `<div>` promoted to `role="group"` / `tabIndex={0}` specifically for drag (see `headerHasDrag` / `headerActivatorRef` in `PanelHeader.tsx`), so there is no competing native semantic — Space/Enter picking up a drag IS the only thing that element does. The dock chip is a native `<button>` whose Space/Enter already has a job: firing `onClick` to open the `PopoverTrigger` preview. If the chip spread the full `dragHandle.listeners` object (as `PanelHeader` does), dnd-kit's `onKeyDown` would fire first, call `preventDefault()`, and the button's native activation would never happen — the ONLY keyboard path to the chip's primary action would silently stop working, with no error, no test failure in a naive "does the drag work" check, and no visual difference.

The fix filters the listener map before spreading it: `Object.fromEntries(Object.entries(dragHandle.listeners).filter(([name]) => name !== "onKeyDown"))`, forwarding pointer/touch only. This is a deliberate, permanent scope decision (not a TODO) — keyboard-driven reordering of dock chips is out of scope because the chip has no non-interactive surface to host it on, unlike the grid header.

## Lesson

- **Before spreading a dnd-kit `useDraggable`/`useSortable` listener object onto an element, check whether that element is already interactive (a native `<button>`/`<a>`/anything with its own Space/Enter semantics).** If it is, drop `onKeyDown` — dnd-kit's `KeyboardSensor` preventDefaults Space/Enter to start a keyboard drag pickup, which races the element's own activation and always wins.
- **Do not copy a working drag-handle pattern (`PanelHeader`'s full-listener spread) onto a differently-shaped element without checking the surface type.** `PanelHeader`'s surface is a purpose-built non-interactive `<div role="group">`; the dock chip is a real `<button>`. The same code that's correct on one is a keyboard-a11y regression on the other.
- **When you intentionally omit a listener for this reason, assert the omission in a test, not just the presence of the ones you kept.** `DockedTerminalItem.test.tsx` / `DockedTabGroup.mountGuard.test.tsx` fire `keyDown` with `"Enter"` and `" "` through a mocked `onKeyDown` and assert `not.toHaveBeenCalled()` — this is what actually guards against a future refactor reintroducing the full spread.
- **If keyboard drag genuinely needs to be supported on an interactive element later**, the pattern is not "forward onKeyDown anyway" — it needs a non-interactive activator surface (`setActivatorNodeRef` + `tabIndex`, as `PanelHeader` does) separate from the clickable control, or a distinct drag-handle affordance (grip icon) so the two gesture sets don't share a node.

## Applies when

- Wiring `useDragHandle()` / any dnd-kit `listeners` object onto a component that renders a native `<button>`, `<a>`, or other element with built-in keyboard activation.
- Adding drag-and-drop to a new panel-chip-like control and reaching for `PanelHeader.tsx` as the reference implementation — check its drag surface is a `<div>`, not a button, before copying the full listener spread.
- Debugging "drag works but the click/Enter/Space no longer opens X" on any dnd-kit-draggable interactive element.
- Reviewing a diff that spreads `{...dragListeners}` or `{...someHandle.listeners}` onto JSX — confirm `onKeyDown` is filtered when the target is natively interactive.
- Touching `src/components/DragDrop/DragHandleContext.tsx`, `DockedTerminalItem.tsx`, `DockedTabGroup.tsx`, or `PanelHeader.tsx` drag wiring.
