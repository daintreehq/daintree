## Context

Daintree exposes its Actions registry to MCP clients (Cursor, Claude Desktop) as tools. Each tool carries MCP `ToolAnnotations` (`readOnlyHint`, `idempotentHint`, `destructiveHint`, `openWorldHint`) built by `buildAnnotations` in `electron/services/mcp-server/tierAuth.ts`. Clients act on these hints — `destructiveHint: true` triggers mandatory confirmation modals and bypasses auto-approve. Separately, `ActionDefinition.danger` (`"safe" | "confirm" | "restricted"`) is a _renderer-side UX gate_: it controls whether a `ConfirmDialog` shows and whether the action is eligible for repeat/MRU rails.

## Problem

`destructiveHint` was originally derived from `entry.danger === "confirm"`. But `danger: "confirm"` only means "warn the human before running" — a read-only context dump (`copyTree.generate`) was gated on a _token-cost_ confirmation, not because it mutates anything. That false positive made MCP clients pop a destructive modal on a read-only operation, eroding trust in the hints.

## Root cause

`danger` and `destructiveHint` look interchangeable but encode different axes: `danger` is "should a human confirm in the UI", `destructiveHint` is "does this irreversibly mutate world state for an agent". Conflating them leaks UX-gating into agent-facing semantics. The codebase resolved this in two complementary ways: (1) `buildAnnotations` now derives hints purely from `kind` (`readOnlyHint`/`idempotentHint`/`!destructiveHint` all key off `kind === "query"`) and never reads `danger`; (2) over-broad `danger: "confirm"` classifications were downgraded to `safe` at the source (commit `0365f0f96`), and genuine exceptions are handled by an optional `ActionMcpAnnotations` override. The override merge uses **nullish-coalescing** (`overrides?.destructiveHint ?? !isQuery`) specifically so an explicit `false` override wins; `||` would silently fall through to the default on any falsy override.

## Lesson

- MCP `ToolAnnotations` are agent-facing **semantics**; `ActionDefinition.danger` is a renderer-side **UX gate**. Never derive one from the other. Hints should follow `kind` (`query` ⇒ read-only/idempotent/non-destructive) and category (`openWorldHint`).
- When the `kind`-derived default mis-describes an action's true semantics, add a per-action `mcpAnnotations` override (`shared/types/actions.ts` `ActionMcpAnnotations`) rather than reaching for `danger`. Prefer fixing the classification at the source — if an action is read-only it should be `kind: "query", danger: "safe"`, which makes overrides unnecessary.
- Merge overrides with `??`, never `||`. An explicit `false` override must beat a `true` default; `||` defeats that. There is a regression test guarding exactly this (`McpServerService.test.ts` — "explicit false overrides must win... would silently break if `??` were swapped for `||`").
- `mcpAnnotations` must be deep-copied when threaded through `ActionService.toManifestEntry` (`{ ...definition.mcpAnnotations }`) so caller mutations of a manifest entry can't poison the registered definition.

## Applies when

- Touching `buildAnnotations` in `electron/services/mcp-server/tierAuth.ts` or any code that maps an action to MCP `ToolAnnotations`.
- Adding or reclassifying an action's `danger` field and wondering whether it affects what MCP clients see (it must not).
- Adding a new `mcpAnnotations` override, or debugging why an MCP client (Cursor/Claude Desktop) shows a destructive-confirm modal on a read-only tool.
- Writing or reviewing any "use default when override absent" merge over boolean fields — the `?? vs ||` trap where an explicit `false` must survive.
- Working in `shared/types/actions.ts` on `ActionDefinition` / `ActionManifestEntry` fields that are consumed by the MCP server, and ensuring they are copied (not shared by reference) in `ActionService.toManifestEntry`.
