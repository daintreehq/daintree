## Context

`ActionService` is the typed dispatch layer for every action (keybindings, context menus, MCP tools, and the command/action palette). Each `ActionDefinition` has an optional Zod `argsSchema` and a `run(args, ctx)`. The command palette (`useActionPalette`) lists dispatchable commands and, when one is picked, calls `actionService.dispatch(id, {}, { source: "user" })` — always with empty args `{}`. To decide what's listable it filtered `kind === "command" && !requiresArgs`, where `requiresArgs` comes from `computeRequiresArgs` in `src/services/ActionService.ts`.

## Problem

Picking **Create Worktree with Recipe** from the palette threw `branchName is required when pullRequestNumber is not provided` instead of opening the New Worktree dialog. An audit found this was not a one-off: 18 actions passed the palette filter yet misbehaved when dispatched with `{}` — some threw, some silently no-oped, some did the wrong thing, and some ran a destructive D1 action with no confirmation. The misleading part: every one of these looked correctly registered and `requiresArgs` reported them safe.

## Root cause

`computeRequiresArgs` returns `true` only when the schema rejects **both** `undefined` **and** `{}`: `!schema.safeParse(undefined).success && !schema.safeParse({}).success`. So the flag answers a narrower question ("does the schema reject zero args") than the palette needs ("can this run with no inputs"). Any action whose real requirement lives outside the schema reports `requiresArgs: false` and leaks in: an all-optional schema whose `run()` resolves a focus/selection target and throws when none exists (`copyTree.generateAndCopyFile`, `devPreview.restart`), a `.refine()` cross-field rule that passes for `{}` but fails at runtime (`worktree.createWithRecipe`), or a headless action whose interactive counterpart is a separate dialog. The capability flag and the real requirement have **different sources of truth**, so the flag silently lies.

A second, worse failure hid in the same gap: `ActionService` gates `danger:"confirm"` only for `source:"agent"` and `"plugin"` — **not** `source:"user"`. So D1-destructive actions whose confirm is wired only at their component call site (`keybinding.resetAll`, `worktree.sessions.endAll`, `devPreview.restartAndClearCache`, `devPreview.reinstallAndRestart`) ran **unconfirmed** when picked from the palette, since a palette pick is `source:"user"` with no in-run gate. A validation-heuristic hole doubled as a destructive-safeguard hole.

## Lesson

- **A capability flag derived from one source of truth cannot gate a call surface whose requirement is enforced by another.** `requiresArgs` is computed from `argsSchema`; the requirement often lives in `run()`, a `.refine()`, or resolved-from-context focus/selection. If `run()` can still throw on the schema-"valid" input, the flag is answering the wrong question.
- **Fix palette-specific behavior with a palette-only field, never by tightening the schema.** The fix is `palette?: PaletteBehavior` on `ActionDefinition` (`shared/types/actions.ts`): `{ mode: "hidden" }`, `{ mode: "redirect"; to }`, `{ mode: "requireContext"; isReady; reason }`. `ActionService.toManifestEntry` projects it to `paletteHidden`/`paletteRedirectTo`/`paletteDisabled`/`paletteDisabledReason`, consumed **only** by `useActionPalette`; `dispatch()` and `get()` ignore it, so keybindings, context menus, and MCP are unchanged. Tightening `argsSchema` instead would have broken every MCP/context-menu caller that legitimately passes explicit args.
- **Evaluate a context precondition in the list/projection layer, never in `dispatch()`.** `requireContext.isReady(ctx)` runs in `toManifestEntry` at `list()` time and fails **closed** (wrapped in try/catch → `false` → disabled-with-reason row that no-ops on Enter). It is never consulted by `dispatch()`, so a context-menu or MCP caller passing an explicit target is not gated by the palette's focus/selection assumption.
- **A component-wired confirm is bypassable from the palette — pair it with `palette:{mode:"hidden"}` or move the gate into `run()`.** `ActionService` gates `danger:"confirm"` only for agent/plugin sources; a `source:"user"` palette pick of a component-confirm-only action runs it with no dialog. Any such action whose confirm lives at the call site (not in `run()`) must be palette-hidden and registered in `EXPECTED_CONFIRM_DANGER` + `BYPASS_WIRED` (`scripts/codegen/confirm-wiring.mjs`, `actionDefinitions.quality.test.ts`).
- **Redirect keeps a headless action searchable while running its interactive sibling.** `worktree.createWithRecipe` → `worktree.createDialog.open`; `git.commit` → `worktree.openReviewHub` (preserves the #7880 no-silent-commit-message rule). A redirect row surfaces even when `requiresArgs` is true, because it dispatches `to`, not itself. `actionPaletteBehavior.test.ts` keeps an `AUDITED_LEAKY_IDS` recurrence guard so a new leaky action forces an explicit palette decision. Known out-of-scope gap: `terminal.killAll` / `terminal.restartAll` / `worktree.sessions.restartAll` confirm only when running agents exist, so a palette pick with nothing running still skips the confirm.

## Applies when

- Adding a new action and deciding whether it belongs in the command palette — if `run()` reads focus/selection or has a `.refine()` cross-field rule, `requiresArgs` will not protect the palette; declare a `palette` behavior.
- Touching `computeRequiresArgs`, `useActionPalette`'s listable filter, or `ActionService.toManifestEntry` — anything mapping a schema-derived flag onto a UI capability.
- Wiring a `ConfirmDialog` at a component call site for a `danger:"confirm"` action — check it can't be reached unconfirmed via a `source:"user"` palette pick (ActionService gates only agent/plugin sources).
- Diagnosing "action X throws / does nothing / runs the wrong thing when picked from the command palette" while working fine from its button, keybinding, or MCP; or reviewing any code that gates one dispatch surface on a boolean computed by a different validator than the one enforced at execution time.
