## Context

`AutoUpdaterService.isTransientUpdateError()` (`electron/services/AutoUpdaterService.ts:267`) decides whether an update-check failure is worth retrying. electron-updater 6.3.x surfaces no categorized error type, so the classifier walks the error's `cause` chain (depth ≤ 5) inspecting Node-style structured fields: `err.code` (network/DNS), `err.statusCode` (HTTP). Transient → schedule a backoff retry; permanent (cert/TLS, 401/403/404) → stop so we don't loop on a misconfigured feed.

## Problem

Real network blips — Wi-Fi dropping, network changing, a brief connection reset — never triggered the retry schedule. The user was silently stuck on a stale version with no automatic recovery, because the failure was being classified as permanent and the backoff path was skipped entirely.

## Root cause

Electron's `net` stack is Chromium-backed, not Node's `http`/`net`. Its errors do NOT populate `err.code`, `err.statusCode`, or `err.cause` — the only signal is a `net::ERR_*` token embedded in the free-text `err.message` (e.g. `new Error("net::ERR_INTERNET_DISCONNECTED")`). A classifier that only reads the structured error shape sees `code === undefined`, finds nothing transient, and falls through to the fail-closed permanent branch. The transient data was present the whole time, just in a field the classifier never looked at.

## Lesson

- When classifying errors that may originate from Electron's `net` stack (auto-updater feeds, `net.request`, anything fetched through Chromium rather than Node), you MUST scan `err.message` for `net::ERR_*` tokens — `err.code`/`err.statusCode`/`err.cause` will be empty for these.
- Parse with an allowlist on the extracted token, not a substring match: `ELECTRON_NET_TOKEN_RE = /net::([A-Z0-9_]+)/g`, then test the captured token against `TRANSIENT_NET_ERROR_TOKENS` / `PERMANENT_NET_ERROR_TOKENS` sets. Fail closed — an unknown token (`ERR_SOME_UNKNOWN_VALUE`) stays permanent so you never loop on a genuinely broken feed.
- Preserve permanent-wins across the WHOLE walk: a cert/TLS token (`ERR_CERT_AUTHORITY_INVALID`, `ERR_SSL_PROTOCOL_ERROR`) must `return false` immediately, even if a transient token appeared earlier in the same message or at a shallower `cause` depth. Use `matchAll` to scan every token in a message — short-circuit on the first permanent one, only set the transient flag (deferred) so a deeper permanent signal can still override.
- Mirror the Node and Electron classifications: `ECONNREFUSED` (Node `code`) and `ERR_CONNECTION_REFUSED` (Electron message token) are the same recoverable condition and must classify identically.

## Applies when

- Adding or auditing error-classification / retry-decision logic in `AutoUpdaterService.ts` or any service consuming electron-updater error events.
- Handling errors from Electron's `net` module, `net.request`, `session.fetch`, `WebContentsView` loads, or anything that round-trips through Chromium's network stack rather than Node's `http`/`https`.
- A "transient vs permanent" classifier inspects only `err.code` / `err.statusCode` / `err.cause` and a network-dependent feature mysteriously never retries on real connectivity loss.
- You see `net::ERR_INTERNET_DISCONNECTED`, `net::ERR_NETWORK_CHANGED`, `net::ERR_CONNECTION_REFUSED`, or any `net::ERR_*` string in logs and need to decide whether it's recoverable.
- Writing tests for error classifiers — cover the message-only shape (token in `err.message`, no `code`), nested-cause detection, and permanent-wins both across cause depth and within a single multi-token message.
