## Context

Dev Preview allocates a free port per worktree and starts the user's dev command in a PTY, then a readiness poller probes the allocated URL and points the webview at it. `DevPreviewCommandNormalizer` rewrites the command before spawn so the server actually binds to the allocated port. `normalizeViteDevCommand` was added to handle Vite, SvelteKit, Astro, and Nuxt; it is chained after `normalizeNextjsDevCommand` at `DevPreviewSessionService.ts:1362-1363`.

## Problem

The allocated port reached the spawn environment as `PORT=<N>`, but Vite-based dev servers ignored it and bound to their framework default (Vite 5173, Astro 4321, Nuxt 3000). The webview pointed at the allocated URL, found nothing there, and the preview never came up — even though the same env approach works fine for Next.js.

## Root cause

Vite (and Vite-based frameworks: SvelteKit v2+, Astro, Nuxt) do NOT read `process.env.PORT`; the port must be passed as a `--port <N>` CLI flag. Setting it in the spawn environment is silently dropped. Two further traps:

- Without `--strictPort`, Vite drifts to the next free port on `EADDRINUSE` instead of failing, so the poller's allocated URL would be stale. `--strictPort` makes it fail fast and lets the poller trust the URL. But `--strictPort` is Vite/SvelteKit-only — Astro/Nuxt CLIs do NOT forward it to underlying Vite and error on the unknown flag. Hence the split: `VITE_STRICT_PORT_RE` (Vite/SvelteKit → `--port N --strictPort`) vs `VITE_SOFT_PORT_RE` (Astro/Nuxt → `--port N` only).
- Package-manager flag forwarding differs: `npm/pnpm/yarn run <script>` need a `--` separator to forward flags into the script; `bun run` and direct CLI invocations take flags inline. The normalizer resolves the underlying script body from `package.json` and inserts `--` vs ` ` accordingly.
- The bare `\bvite\b` pattern would match `vite-node server.ts`; `VITE_STRICT_PORT_RE` uses `\bvite(?![\w-])` to exclude hyphenated tools.

The PR also renamed `DevPreviewSessionState.assignedUrl` → `predictedUrl` across the IPC type and 11 files: the value is the allocator-derived starting point the readiness poller probes (and may revise), not an authoritative binding.

## Lesson

- Do NOT rely on `process.env.PORT` to pin a dev server's port for Vite-family frameworks — only Next.js (and similar) honor env `PORT`. Inject `--port <N>` as a CLI flag.
- Add `--strictPort` ONLY for Vite/SvelteKit so the server fails fast on collision and the readiness poller can trust the URL; never inject it for Astro/Nuxt (their CLIs reject it).
- Match framework patterns precisely — guard against hyphenated lookalikes (`vite-node`) with a `(?![\w-])` lookahead.
- Respect package-manager flag forwarding: `npm/pnpm/yarn run` need `--`, `bun` and direct CLI calls take inline flags. Resolve the script body from `package.json` to detect the real framework when the command is a `run <script>` wrapper.
- Name a poller's starting-point URL `predictedUrl`, not `assignedUrl` — the latter implies authority the value doesn't have.

## Applies when

- Adding a new framework to `DevPreviewCommandNormalizer` / `FRAMEWORK_DEFAULT_PORTS`, or debugging why a dev preview binds to the wrong port (5173/4321/3000) instead of the allocated one.
- A dev-preview session reaches the running PTY but the webview shows connection-refused / never loads because the server bound elsewhere.
- Reasoning about port allocation, `--strictPort`, or readiness-poller URL trust in `DevPreviewSessionService`.
- Writing command-normalization regexes that must distinguish a framework binary from a hyphenated sibling tool, or that must forward CLI flags through different package managers.
- Touching `DevPreviewSessionState` / `shared/types/ipc/devPreview.ts` and reasoning about whether a URL field is authoritative vs predicted.
