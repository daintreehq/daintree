## Context

Session-restore paths call `terminal.reset()` then `terminal.write()` on the xterm instance to replay serialized scrollback: `TerminalRestoreController.restoreFromSerialized` / `restoreFromSerializedIncremental`, exposed through `TerminalInstanceService` and invoked when a terminal attaches without visible buffer content (`XtermAdapter`'s `restoreOnAttach` path) or when a deferred incremental restore is scheduled (`scrollbackRestoreScheduler`). Per-terminal hibernation — and the wake cycle that used to drive this same replay on focus/visibility — was torn out in PR #10811; restore now runs purely off session/attach state, not a hibernate/wake lifecycle.

## Problem

Users scrolled back in an agent terminal would have their viewport snapped to the bottom every time its buffer was replayed on reattach (e.g. switching back to a project view), because `reset()` inherently clears the scroll position and `write()` auto-scrolls.

## Root cause

xterm's `terminal.reset()` destroys viewport state. There is no built-in "restore scroll" option — callers must capture and reapply it themselves.

## Lesson

Before any `reset()` + `write()` replay sequence on an xterm instance, capture `scrollBackOffset` (distance from bottom), then after the write completes call `scrollToLine` to reapply it. Gate the restore on `isUserScrolledBack` so users already at the bottom still get auto-scroll. This pattern applies to every restore path — sync restore, incremental restore, deferred-output restore — and is easy to miss when adding a new replay path.

## Applies when

Touching xterm restore/replay logic, adding a new serialization path, or anywhere `terminal.reset()` is called on a live xterm instance that the user may have scrolled.
