## Context

#10979/#10976 taught macOS to deliver Dock-dropped and Finder-opened folders into `handleDirectoryOpen` (`electron/menu.ts`), the same function behind `Cmd+O` and Recent Projects. #11281 asked for one more step: when the folder isn't a Git repo yet, route it into the existing renderer `GitInitDialog` (already reachable from the in-app add-project flow via `addProjectByPath` in `src/store/projectStore.ts`) instead of a dead-end native error box. #11284 made `handleDirectoryOpen`'s `catch` branch on `isAppError(error) && error.code === "NOT_A_GIT_REPO"` (code defined in `shared/types/appError.ts`, thrown by `electron/services/ProjectStore.ts`), replacing an old substring match on the error message, and push a new one-way `PROJECT_OPEN_GIT_INIT_DIALOG` event to the renderer to open that dialog.

## Problem

The Dock-drop path is the one entry point where the folder can arrive while the renderer hasn't loaded yet — dropping a new (non-repo) folder onto the Dock icon at cold launch is exactly how a user triggers this. A naive `webContents.send()` at that point would silently do nothing: no dialog opens, no error, no log — the event vanishes, and only a cold-launch Dock drop would ever show it, so a build that passes every warm-launch manual test can still ship this gap.

## Root cause

Electron discards `webContents.send()` calls made before the target frame finishes its navigation; there is no internal queue that replays them once the renderer's `ipcRenderer` listeners come online. The fix gates the send on `rendererTarget.isLoadingMainFrame()`, deferring via `rendererTarget.once("did-finish-load", sendOpenGitInitDialog)` when true, sending immediately otherwise. `src/store/projectStore.ts` registers its `onOpenGitInitDialog` listener at module scope (next to the pre-existing `onUpdated`/`onRemoved`/`onWorktreeLoadStatus` listeners), not inside a React effect, because module-scope code runs before `App` mounts and `did-finish-load` can fire before any component subscribes.

The repo already had one instance of this pattern — `electron/window/windowServices.ts`'s worktree-load-error send (`PROJECT_WORKTREE_LOAD_STATUS`, #8796) — gated on `statusTarget.isLoading()`, not `isLoadingMainFrame()`. Electron's own type declarations spell out the difference: `isLoading()` is "whether web page is still loading resources" (true while _any_ frame, including a subframe such as a dev-preview iframe, is loading), `isLoadingMainFrame()` is "whether the main frame (and not just iframes or frames within it) is still loading." `did-finish-load` fires only for the main frame's navigation, so if a subframe alone is keeping `isLoading()` true after the main frame settled, `windowServices.ts`'s `once("did-finish-load", ...)` is registered on an event that already fired and never fires again — the deferred send is lost, not delayed. #11284's own code comment calls this distinction out explicitly and deliberately picks `isLoadingMainFrame()`, but doesn't fix the older `windowServices.ts` call site, so both the correct and the latent-buggy version of the same gate now sit side by side in the codebase.

## Lesson

- **Any main-to-renderer `webContents.send()` that can fire before the renderer has loaded needs an explicit gate-and-defer, because Electron has no send queue** — check `isLoadingMainFrame()` and if true `once("did-finish-load", sendFn)`, else send immediately; read the flag as late as possible (right before the send, not before an intervening `await`) so a load that finishes mid-await isn't waited on forever.
- **Use `isLoadingMainFrame()`, never `isLoading()`, when the resume condition is `did-finish-load`** — `isLoading()` can stay true because of a subframe (dev-preview/browser-panel iframes exist in this app) after the main frame already fired `did-finish-load`, so the `once()` listener you register never fires and the send is lost forever, not just late. `windowServices.ts`'s `PROJECT_WORKTREE_LOAD_STATUS` send still uses `isLoading()` — treat it as a latent instance of this bug if touched, not as an established-good reference to copy.
- **Register the renderer-side listener for any cold-launch-reachable main event at module scope, not in a React effect** — `projectStore.ts`'s `onOpenGitInitDialog` subscribes before `App` mounts for the same reason the main side defers on `did-finish-load`: an effect-based listener can still lose the race against a send that fires the instant the frame finishes loading.
- **Branch renderer-bound error recovery on the structured `AppError.code`, not a message substring** — `isAppError(error) && error.code === "NOT_A_GIT_REPO"` survives the in-process throw intact (no IPC/structured-clone boundary, since `handleDirectoryOpen` calls `projectStore.addProject` directly) and correctly still shows the native dialog for an untyped `Error` that merely mentions "not a git repository" — a substring match would wrongly route that case into guided setup.
- **When duplicate arrivals of one-shot renderer state can race (drop several folders on the Dock at once), guard with "ignore if already open" rather than last-write-wins** — `applyOpenGitInitDialog` no-ops if `gitInitDialogOpen` is already true, because swapping the path mid-initialization would `git init` the first folder but hand the second to `handleGitInitSuccess`, leaving the first initialized-but-unadded and the second added-but-untouched.

## Applies when

- Adding any new main-process `webContents.send()` (or `getAppWebContents(win).send()`) that can be triggered before the target window's renderer has finished loading — cold launch, Dock/Finder drop, `--cli-path`, deep links.
- Touching `electron/window/windowServices.ts`'s `PROJECT_WORKTREE_LOAD_STATUS` send, or any other pre-existing "defer until loaded" send — check whether it uses `isLoading()` where `isLoadingMainFrame()` is correct.
- Diagnosing "an event/dialog/state update only fails on cold launch" or "only fails the first time, works if I retry" for anything crossing main → renderer.
- Adding a renderer listener for a main-pushed one-way IPC event that must not miss a cold-launch send — decide module-scope registration vs. a component effect.
- Reviewing a `catch` block that branches on error identity to route between a silent/guided path and a user-facing error dialog — confirm it keys on a structured code/type, not `error.message.includes(...)`.
