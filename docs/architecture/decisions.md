# Daintree Decisions

An agent that hits a decision it shouldn't make alone calls one MCP tool, `ask_human`, gets an immediate "queued" reply and ends its turn. Minutes or days later the user answers on their phone, and Daintree types a delimited, labelled answer into the exact terminal that asked, once that terminal is idle, resuming the agent session first if the pane is gone (#15996). The relay, the phone app and the wire protocol live in [daintreehq/decisions](https://github.com/daintreehq/decisions): a Cloudflare Worker, a Durable Object and an R2 bucket the user deploys into their own Cloudflare account. Questions, answers and screenshots are end-to-end encrypted between the user's computer and phone.

This doc is the contract for the Daintree side, written before any of it is built (#15997): where the service runs, how agents reach it, what is stored where, how an answer reaches a terminal, resume, Remote Hosts, and what Decisions costs when it is off. The lazy service, its entry module and its status read exist (#16001), as do each pane's state, its push and its mount read (#16016); every other new name below is marked with the child issue that adds it. Each child keeps this doc current as it lands. The relay [protocol](https://github.com/daintreehq/decisions/blob/08acc16585b78157c77af10a92e6a51aea2d37d4/docs/protocol.md) is normative for everything that crosses the network. The design started from the Decisions repository's [integration spec](https://github.com/daintreehq/decisions/blob/08acc16585b78157c77af10a92e6a51aea2d37d4/docs/daintree-integration-spec.md), which was checked against an older clone of this repository; where the two differ, this doc is what gets built here, and [Where this differs from the integration spec](#where-this-differs-from-the-integration-spec) lists each difference.

## Boundaries

- **One global setting.** Decisions is one switch for the user, in Settings → Integrations → Decisions, off by default. There is no per-project opt-in: turning the switch on, after consent that names it, is the opt-in that adds the Decisions server to every supported launch, a global opt-in as [Hard Line 2](../feature-curation.md#the-hard-lines) records. Remote Hosts are enrolled as devices of the same owner, automatically when they connect: they are never configured separately, and never get their own relay, relay URL or switch.
- **Supported agents are the ones with launch-time MCP.** An agent gets `ask_human` only through the additive launch-time MCP path (`capabilities.launchMcp`). Agents without it are listed as not supported, and Settings offers no manual setup line for them, because the standalone `decisions mcp` server has no pane identity and no way to type into a Daintree terminal, so a question asked through it could never be answered back into that terminal.
- **User-owned agent config is never modified.** Panes get the Decisions server beside the user's own servers, through the launch-time path only. Workflows that use the design-review gate are documented for users to add to their own skills; Daintree installs nothing into `~/.claude`, `~/.codex` or similar.
- **Observations, not interpretations.** UI and MCP results say what was observed ("Question q-42 is waiting for an answer"), never "agent is blocked".
- **Agents can't forge or downgrade.** Requirement levels come from trusted gates Daintree registers, pane identity comes from the bearer and never from tool arguments, and a proxy answer never satisfies `human-required`.
- **Hosted Features rules apply** ([feature-curation.md](../feature-curation.md#hosted-features)): off until enabled, consent that names what is sent and where, and gone entirely when off.
- **Out of scope:** a Daintree-operated server of any kind, replacing Canopy or [Answer from another device](../feature-curation.md#agents-and-attention), and a REST-only relay deploy with no Node toolchain.

### Libraries

The protocol, crypto, client and decision-model code is published from daintreehq/decisions as `@daintreehq/decisions-protocol`, `@daintreehq/decisions-crypto`, `@daintreehq/decisions-client` and `@daintreehq/decisions-model` and Daintree pins their first release, 0.1.0 (daintreehq/decisions#13). They are `dependencies`, bundled into the main build rather than shipped in the ASAR's `node_modules` (#16001). `electron/services/decisions/libraries.ts` binds all four, so their code lands in the service's lazy chunk and nowhere else; later children take what they need from that binding or import it beside the service. The relay socket uses the `ws` package main already depends on.

The client library owns signing, encryption, the relay client and socket protocol, the durable queues, the delivery state machine, the MCP handler and the decision model. Daintree supplies its host seams by implementing the library's interfaces: `LocalStore` (#16002), `KeyStore` (#16003), `PaneAuthenticator` (#16011), `TerminalSink` (#16015), `AgentResumeAdapter` (#16019) and a populated `PolicyRegistry` (#16013), with `ProxyEngine` from the model package (#16026). These are library contracts, checked against the pinned release, not Daintree symbols.

## Where it runs

Decisions runs in the main process of the machine that owns the pane: this machine's main for local panes, and the Host's own main process for panes on an enrolled Remote Host (#16022), where the agent, its MCP listener, its bearer and its PTY already live ([remote-hosts.md](./remote-hosts.md)). The renderer only reads state and writes the setting over IPC. Nothing runs in a project view, and nothing needs a window open.

The service follows the `deviceAnswer` precedent: a memoised lazy singleton, `getDecisionsService()` in `electron/services/decisions/index.ts`, and a boot step, `startDecisionsIfEnabled()`, run from a deferred task in `globalServicesInit.ts` that returns early unless `store.get("decisions")?.enabled` is true (#16001). It also starts and stops when the setting changes at runtime, and its shutdown is part of app shutdown. The service exposes its state as observed (off, not connected, connecting, connected, revoked), readable over IPC.

As built (#16001): `DecisionsService` runs one enabled lifetime from `start(settings)` to `stop()`, one transition at a time, and `dispose()` at quit is final. Each child acquires its resources in `start` and releases them in `stop`. Status listeners subscribe with `onStatusChanged`; they outlive a stop, not a dispose. Until a relay identity and socket exist (#16006, #16008), on reads as `not-connected`. Every runtime change to the switch goes through `setDecisionsEnabled`, which writes the setting through `writeDecisionsSettings`, keeping every other field, then starts or stops the service to match; a direct `store.set` would leave the service out of step, and nothing watches the store. The renderer reads `window.electron.decisions.getStatus()` (`decisions:get-status`, `shell` locality), which answers `off` from the store while the switch is off and asks the service otherwise; the status also carries the saved relay origin and consent time once there are any, and, while on, `keysStored` when the key file exists (read from its presence alone, so the status never asks the keychain). Settings turns it on and off with `window.electron.decisions.setEnabled({ enabled, consent })` (`decisions:set-enabled`, `shell`, #16004), which calls `setDecisionsEnabled`. Turning on is refused until the person has agreed in the consent dialog once (`consentedAt` in the setting, the first agreement's time), and turning off while nothing is on answers from the store without loading anything. There is no status push yet; the child that first needs live status adds one. Decisions' entry module is loaded only through `loadDecisionsModule` in `serviceRefs.ts`, which every loader calls after reading the switch as on, or, for the switch itself, once the person has turned it on. Quit seals it in the same synchronous step that halts deferred startup, then stops a load already under way before any terminal is captured, so quitting with Decisions off imports none of it.

**With the MCP server off** (#15999). Turning the MCP server setting off today disposes every queued wake and closes the listener (`McpServerService.setEnabled`), and `TerminalNotifyService.enqueueWake` refuses any wake with `notices-off` while the service is disabled. A user who wants phone answers but not the agent control surface would get neither. #15999 lets a feature hold the listener open and keep the wake engine accepting its own wakes while the server setting is off. In that state `/mcp` and `/mcp/plugin/` stay refused and the existing notice kinds stay off, exactly as with the server off today; the port and the Host and Origin checks are the same ones, not a second listener. With no feature holding it, turning the server off behaves exactly as now.

## What being off costs

With the setting off from startup, Decisions costs one setting read in a deferred boot task and two registered IPC reads, and nothing else:

- **No Decisions module is imported.** The boot step reads the setting before importing anything under `electron/services/decisions/` or any `@daintreehq/decisions-*` package. This is stricter than `deviceAnswer`, whose deferred task imports its small index module before checking. The eager import walk (`scripts/check-import-budget.mjs`) must not grow; it runs on demand, not in CI, so `scripts/decisions-lazy-boundary.test.ts` is the gate: it builds main as production does and fails if its startup graph reaches any module under `electron/services/decisions/` or any `@daintreehq/decisions-*` package (the import budget's `FORBIDDEN_EAGER_PATTERNS` carries the same rule), if Decisions code lands in a chunk main loads at startup, or if any module of its own joins the startup graph. Its status and pane-state reads are declared in `electron/ipc/handlers/deviceAnswer.ts`, a handler module startup loads anyway, so Decisions adds no module there; a later IPC op joins the same `decisionsNamespace`. The boot task's own test proves the off task reads only the setting, evaluates no Decisions module and leaves no new active resource.
- **No resources.** No listener hold, no `/mcp/decisions` handler (the path answers 404 while the MCP server keeps the listener up, and nothing listens otherwise), no socket, timer, file handle, `powerMonitor` subscriber or IPC push, and no renderer subscription or chip.
- **No change to launches.** Every agent launch is byte-for-byte what it is today (#16012).
- **Turning it off at runtime** closes the socket, clears the timers, closes `/mcp/decisions` and releases its listener hold, and stops delivery. Modules already evaluated stay in memory (ES modules can't be unloaded) but hold nothing. Panes launched while it was on keep their config entry until they relaunch, and their calls get 404 or find no listener. Stored data stays on disk (#16002) until the user deletes it (#16025).

Rollback for every child is the switch: with `decisions.enabled` false at startup the seams are empty and no Decisions module is imported.

## The setting

One `decisions` object in the electron-store schema (`electron/store.ts`, beside `deviceAnswer`), with `enabled` defaulting to false (#15998). It also holds the relay origin, the installation, device and host ids, and the non-secret preferences later children need (`autoEnrollHosts` among them, #16021), shaped so a field can be added later without another breaking migration. Loading sanitises it field by field, as `deviceAnswerSettings.ts` does for `deviceAnswer`, and never crashes: a value that isn't a usable object falls back to off. A store migration is added only if one is needed, self-contained and idempotent, after the latest in `electron/services/migrations/` (042 at the time of writing).

Every field is owned by the machine the user sets it on: `device` in `shared/config/settingOwnership.ts`, as `deviceAnswer` is, enforced at compile time through `electron/storeOwnership.ts`. A window bound to a Remote Host therefore never routes it to the Host, and its status and settings channels are `shell` in `channelLocality.ts`, like the device-answer channels. Pane state is the exception: it belongs to the machine that owns the pane, so `decisions:get-pane-state` and `terminal:decision-state` are `host`. No secret is ever stored in this object: not the claim secret, keys, tokens or the recovery passphrase.

## Asking: `/mcp/decisions`

### The route

Agents reach Decisions through three MCP tools served by the library's handler on its own route (#16011). It doesn't go on the control surface (`/mcp`): that is gated by a per-project tier that defaults to off, and putting `ask_human` there would tie a human-in-the-loop feature to granting agents the whole control surface. Plugin endpoints are the wrong trust model and can't type into a terminal.

The route is a listener hold (#15999): `DecisionsMcpRoute` (`electron/services/decisions/mcpRoute.ts`) takes `McpServerService.holdListener("decisions", …)` for `/mcp/decisions`, so it is served whether or not the MCP server is on, and serves the library's `createDecisionsMcpHandler` there with `path: "/mcp/decisions"`. `HttpLifecycle.handleRequest` rejects repeated security headers (400), then a `Host` other than `127.0.0.1:<port>` or `localhost:<port>` (403), then a mismatched `Origin` (403), before a held route sees the request. The handler then checks the `Host` again (fed from the listener's port), refuses any `Origin` at all, the listener's own loopback origins and `null` included, takes POST only, and authenticates by bearer before it reads the body. A path under `/mcp/` that no hold serves, outside `/mcp/plugin/`, answers 404 before any credential is read, so with Decisions off `/mcp/decisions` is never the control surface's and counts no 401.

The Decisions service opens the route once a relay connection has loaded its identity and bound the store, before its first attempt goes out (`RelayConnectionOptions.onQuestionsReady`), and keeps it through drops, backoff and a 4409's cooldown. It closes it when the connection stops for the lifetime (a keys, storage or other-relay problem), is revoked, is let go (disconnect, another relay) or Decisions turns off, and a stop waits for the hold to be released. Closing refuses every request at once (404) and the hold goes after. Without a relay identity there is no route: no host id, and nothing to sign or seal a question with.

### Authentication and identity

The route accepts only a valid Decisions pane bearer. API-key and help tokens are refused (an API-key client has no pane of its own), as are plugin grants and missing or foreign tokens. One consequence: the help panel's Assistant, which holds a help token, isn't offered `ask_human`. `isAuthorized` accepts any token in the pane-token map (`tierAuth.ts`), so the Decisions credential minted for a tier-off pane must never be one that `isAuthorized` would accept on `/mcp` (#16012).

The pane's identity is derived server-side from the bearer, never from tool arguments (`createPaneAccess` in `paneAccess.ts`): the pane id (`getPaneIdForToken`), its ownership principal (`getOwnershipPrincipalForToken`) and its launch workspace binding (`getPaneWorkspaceBindingForToken`), plus, from the terminal's strict record, its live generation (`getLiveGeneration` and `isLiveGeneration`, matched to the record's), agent incarnation, agent session, project and worktree. The host id is the setting's `hostId`, and the agent kind is the detected agent, else the launched one. A `PaneWorkspaceBinding` carries the workspace id and action context, not a worktree root, so the worktree root is recorded from the pane's launch facts: the directory it was launched in, local only. `workflow_gate_id` on the origin is trusted policy and is always null here; a gate the agent names can only make a question stricter. A pane that has exited, has no process, is trashed or is the Assistant, or whose record lacks an incarnation, agent, project or worktree, or lies outside its launch's project, is refused (401), as is any token once the run changed while it was read. A record that can't be read in time is a 500, so a slow host isn't taken for a bad credential.

The library's handler keeps no session: every POST is authenticated against the live pane-token map. So `revokePaneConfig`, which deletes the token in the same step as `revokePaneBearer` runs, ends the pane's Decisions access on its next request, with nothing more to close. Each call is checked again as it runs (host, principal and live generation still the ones it was let in with), since a request is authenticated before its body is read. The pane's open questions stay in the store bound to the run that asked, deliverable to it only.

### Tools

`ask_human`, `get_decision` and `cancel_question`, with the library's input schemas (`AskHumanInput`: question, context, options, attachments, `requested_requirement`, `workflow_gate_id`, `expires_at`, `correlation_id`). Each tool description is under 400 bytes; `mcpWireBudget.test.ts` measures only the action manifest, so `decisions/__tests__/mcpRoute.test.ts` measures these three from `tools/list`. They are not actions and sit on no MCP tier, so they don't touch the external-tier budget (`tierAuth.test.ts`).

`ask_human` writes the question and its origin to the local store before any network I/O, then returns at once with `Asked as q-<alias>. End your turn now (or continue with unrelated work); the answer will arrive as a message in this terminal.` The question is published to the relay when connected. The alias `q-N` is a cosmetic per-installation counter; wire ids are full unguessable identifiers. The call returns once the question is committed locally, without waiting on the relay or the human, so a CLI's tool timeout is never the answer's deadline. `get_decision` and `cancel_question` see only the calling pane's questions: the library matches host, pane, generation, principal, incarnation, session and worktree, and answers another pane's id as it does an unknown one. A pane holds at most 10 open questions, under the library's rate limit of 60 requests a minute per pane.

Relay attempts each get a bridge of their own, and there is none between them, so the handler is given a `QuestionBridge` (`questionBridge.ts`): each call goes to the started attempt's bridge when one is current, and otherwise to the `QuestionBridge` itself, a library bridge stopped before first use, which never pumps, publishes, receives or delivers, and asks under the identity the attempts last held. A question asked offline is committed with its outbox entry and published when the next attempt catches up. Asks run one at a time, because the library counts a pane's open questions and commits in separate steps. Once the connection has ended (revoked, or stopped for the lifetime) every call is refused and nothing falls back to the local bridge. The `QuestionBridge` asks under the lifetime's trusted policy, the same registry every attempt's bridge uses (#16013), so trusted gates and the proxy allowlist apply between attempts too: with no trusted gate and no allowlist a question is `human-required`, whatever `requested_requirement` asks.

The server key `daintree-decisions` joins `RESERVED_PLUGIN_SERVER_KEYS` so a plugin can't claim it; it fits the 25-character key limit, and Claude Code names the tool `mcp__daintree-decisions__ask_human`.

## Supported agents

Panes get MCP servers through the additive launch-time path: `preparePaneConfig` in `McpPaneConfigService`, called from the agent launch in `electron/ipc/handlers/terminal/lifecycle.ts` and rendered per CLI by `renderLaunchMcp`. A format that needs a file gets one written 0600 under `userData/mcp-pane-configs`; PTY exit revokes the bearer and deletes the file, best effort. Bearers travel in that file or the PTY env, never in argv.

Today a pane gets no config at all when its project's tier is off and no plugin is granted: `preparePaneConfig` refuses that case, and tier off mints no bearer. Off is the default tier, so most panes would never see `ask_human`. With Decisions on, #16012 gives every launch of an agent with launch-time MCP a `daintree-decisions` entry and its own bearer, whatever the tier. That bearer authorises `/mcp/decisions` only, never the control surface or a plugin route. With the tier off, the pane still gets no `daintree` control-surface entry. With Decisions off, launches are unchanged.

Supporting one of them means giving it a launch-time format in the agent registry, which is its own change.

## Origin and routing

Before anything touches the network, the bridge records the question's origin in the local store:

| Field | Where it comes from | Note |
| --- | --- | --- |
| `host_id` | Decisions' own id for this machine, minted at claim or enrollment, mapped to Daintree's `HostId` | `LOCAL_HOST_ID` (`"local"`) is unique only per machine |
| `pane_id` | the terminal id |  |
| `terminal_generation` | the spawn's `launchGeneration` (`PtyClient.getLiveGeneration`, checked with `isLiveGeneration`) | from a per-process ledger: monotonic within a run of the app, not durable across restarts |
| `ownership_principal` | `getOwnershipPrincipalForToken` | a fresh UUID on every launch; anything keyed by it ends with the run, as `TerminalNotifyService.revokeOwner` relies on |
| `agent_incarnation` | `agentIncarnation` on the panel | an observation, not proof of process identity |
| `agent_session_id` | `agentSessionId` | Claude's is assigned at launch (`--session-id`); others are learned passively, from output and teardown (`sessionIdCapture.ts`, `agentEndCapture.ts`), from a resumed run's argv (`agentRunArgv.ts`) or, for Codex, live attribution (`CodexLiveSessionAttribution.ts`). It may be unknown when the question is asked, and can be stale: Claude's own `/clear` and `/resume` switch conversations without telling Daintree |
| `project_id`, `worktree_id`, worktree root | the pane's launch | local only, never sent to the relay |
| `project_label`, `machine_label` | the project's and machine's display names | inside the encrypted content only; the phone shows them on every question |

On the wire, `origin_ref` is a salted hash of `(host_id, pane_id)`, used only for per-pane quotas.

**Routing rules.** An answer is typed only if host, pane, generation, ownership principal, observed agent incarnation, recorded agent session and worktree all still match the origin. That is a match against what Daintree observed, not proof of which conversation the CLI has open. Otherwise it goes to resume when that is available, or to needs-attention, and is never typed into a guessed same-named pane or project. Every spawn mints a new generation and principal, so an answer for a question asked before a relaunch or an app restart never matches the new run directly; resume can find the restored pane still running the same session and re-target the delivery to it, with the correlation to the original question recorded (#16017, #16019). Each answer carries its own question id and revision, and answers for one pane are delivered in question order.

## Policy and attachments

**Trusted gates** (#16013). As built: `electron/services/decisions/workflowGates.ts` defines the gates, and `createTrustedPolicy` registers them in the library's `PolicyRegistry`. `DecisionsService` makes one registry per enabled lifetime on its first start and hands that same registry to every `RelayConnection` attempt's bridge, so the inbox checks each answer against the gates its question was asked under, on every attempt and after a restart. Nothing an agent or a renderer can reach registers or edits a gate: the only ops are `decisions:get-policy` (copies of the gates, the proxy allowlist and the library's default expiry) and `decisions:set-proxy-allowlisted` (a boolean), both `shell` and refused while off. A question names a gate in `workflow_gate_id`. The origin's gate, set by the host and none today, is the floor, and a gate the agent names can only make a question stricter. With no trusted gate a question is `human-required`, unless the person has turned on the proxy allowlist (off by default), in which case it takes the level its agent asks for. An agent's `requested_requirement` never loosens a gate, and an unknown `workflow_gate_id` is treated as no gate. Changing the allowlist changes the running registry in place, so the next question is asked under it; questions already asked keep their level. Each save moves the policy's `revision` and pushes a status change, on which Settings in every window reads the policy again and keeps the higher revision, so another window's change shows and a late read can't roll one back. The switch's description says no decision model is connected; #16026 changes that line when it connects one.

The first gate is `design-review/final`: `human-required`, Approve or Reject and nothing else, and bound to the screenshots attached. It sets `allowText: false` explicitly, because with text allowed the library takes a note with no choice as an answer. Binding means a question under it must carry images, and `get_decision` reports `reviewed_digests_match`, true only for a human answer whose reviewed digests are exactly the attached images'. A proxy answer never satisfies `human-required`: the bridge refuses to run the proxy, and the inbox rejects a proxy-provenance answer whatever the relay says. An answer outside the gate's choices, with two choices or with text is rejected, and the question is marked needs-attention.

**Using the design-review gate.** A workflow lives in the user's own skill or runbook; Daintree installs nothing into agent config to provide one. It captures the final before and after screenshots, calls `ask_human` with them as `attachments` and `workflow_gate_id: "design-review/final"`, and ends its turn. When the answer arrives it calls `get_decision`, and continues only when `status` is `human-answered`, `provenance` is `human`, `choice` is `approve` and `reviewed_digests_match` is true. Changed screenshots are a new question: the same `correlation_id` with different images asks again, and no approval carries over. The gate requires attachments, not a before and after pair. The user guide (#16029) carries the recipe; `scripts/design-review-shots.mjs` is only a capture utility and implements no gate.

**Expiry.** An expired question authorises nothing: `get_decision` reports `expired` with no provenance, choice or text, and the typed notice says `authorised: no` and that the agent may not continue the gated step. Expiry comes from the relay's `decision.expired` event and isn't recomputed from the clock. The default expiry isn't a setting yet. The pinned release gives a question with no origin gate 7 days unless its agent asks for another time, at most 30 days, and has no host hook and no way to say "never" (daintreehq/decisions#15). Settings → Questions says what the wait and the cap are, read from the library's own `resolveExpiry` rather than copied from it, and the default-expiry control, with "never", waits on that release.

**Attachments** (#16014). An attachment's `local_resource_id` comes from the agent and is untrusted. It resolves relative to the pane's launch worktree with `realpath`, and anything outside the worktree, including through a symlink, is refused. Only PNG, JPEG and WebP, checked by magic bytes; SVG is refused. Limits: 20 MiB per file, 8 files and 64 MiB per question. Uploads are encrypted and spooled durably (the library's default spool is in memory), so they survive a restart before they finish, and the spool is cleaned once uploaded or cancelled. Refusals tell the agent what was wrong without echoing file contents.

## The relay connection

- **URL check** (#16005). Connection takes a relay URL and main checks it: `checkRelay` in the lazy entry, through `window.electron.decisions.checkRelay(url)` (`decisions:check-relay`, `shell`, refused while off). `relayOriginFromInput` (`relayCheck.ts`) gives a bare host `https://` and drops any path, query or fragment; it refuses plain http (loopback included, though the stored setting's sanitiser still reads a loopback origin), a user name or password, whitespace, control characters and backslashes, and sends nothing for them. Main then reads the unsigned `/health` and `GET /api/v1/info` through Electron's `net.fetch`, and reports one observation naming the read it came from: unreachable (timeout, DNS, refused, certificate or other, never the error's own text, which can carry the URL), an HTTP server error or rate limit, not a Decisions relay (a redirect, another status, or a body that isn't the relay's), protocol incompatible, claim secret not configured, unclaimed, or claimed. Only the normalised origin is echoed back. Every relay answer carries both sides' protocol range and worker version; Daintree's is the protocol package's range and version, since the worker and the libraries are released together. Ranges that don't overlap are incompatible, any difference at all diverges, and Connection prompts for whichever side is behind. Daintree never updates the Worker. No request goes from the renderer; requests follow no redirect, send no cookies, retry nothing, read at most 64 KiB and each have a 10 s deadline, and turning Decisions off or quitting cancels a check in flight. The URL isn't saved, since #16006 saves the origin with the ids it claims or restores. With a relay saved, Connection checks it when asked, and by itself once connected.
- **Claim or restore** (#16006, #16007). A fresh relay is claimed once with its claim secret, held in memory only, and this machine becomes the `owner-desktop`. A relay already claimed elsewhere is joined by restoring the identity from a recovery kit. Setup completes only after a recovery kit is saved and verified (#16007).
  - As built (#16006): `window.electron.decisions.claimRelay({ url, claimSecret, acceptWeakStorage? })` and `restoreIdentity({ url, kit, passphrase, acceptWeakStorage? })` (`decisions:claim-relay`, `decisions:restore-identity`, `shell`, refused while off) run `claimDecisionsRelay` and `restoreDecisionsIdentity` (`relayIdentity.ts`) behind the switch's transitions, so turning off waits for one to settle rather than cutting a claim off mid-flight; quitting aborts its requests. Each answers a `DecisionsConnectResult`, one observation: `saved`, `relay` (the unsigned check stopped it: unreachable, not a relay, incompatible, claimed when claiming, unclaimed when restoring), `refused` (wrong secret, already claimed, not configured, rate limited, rejected), `unreachable`, `kit-refused`, `conflict` (keys for another relay or identity are already sealed here, or a relay is already set up) or `key-storage` (the key store's kinds). Both read the existing keys, and check sealing (`check()`) before anything new is staged, sealed or sent, so a locked, missing or slow keychain stops a setup before the relay hears of it (taking up keys already sealed here seals nothing); Linux's fixed-key storage goes ahead only with `acceptWeakStorage`, after Settings asked. Then they rerun the unsigned check, and send only through Electron's `net.fetch` held to that origin: no redirect, cookie or cache, a 10 s deadline covering each body, read to 1 MiB, with only a fixed reason ever reaching the library's error text.
  - **Claim.** The library's `claimRelay` stages the new identity, sealed and marked `claimed: false`, before it posts the claim, so an answer lost on the way back can't leave the relay owned by keys nobody holds. Daintree removes that stage whenever this attempt made it and the relay can't have taken it: a refusal (`not_authenticated`, `not_configured`, `rate_limited`, a 4xx), or a request that never left this computer (DNS, refused, certificate, with no response begun). It stays, and the observation says `kept`, when the claim may have arrived (a timeout, a reset, a server error, a success whose body didn't arrive, a key-store failure after the stage saved), or when an earlier attempt made it, since a refusal now says nothing about whether that one arrived. A refusal whose body failed is still read by its status. The next claim of the same relay finishes with the stage, through the library's signed probe after `already_claimed`; the library removes a stage the relay then refuses only when this attempt made it, and an earlier attempt's stage stays until the person removes it (Remove keys). A claimed relay is claimed again only when this computer holds such a stage. A stage or identity for another relay is a `conflict`, never replaced. A complete identity for the same relay whose setting didn't save is taken up as it is.
  - **Restore.** Nothing is saved until everything is proven: the kit's outer file is bounded (256 KiB, 100 000 to 10 000 000 PBKDF2 iterations), it opens with the passphrase, it holds a confirmed `owner-desktop` identity for the relay that was checked with ids the setting can hold, its keys sign and verify, its exchange key pair agrees and it holds its current epoch's key, and the relay answers a request signed with them (`devices()`, no retries) listing them as its unrevoked owner under the same signing and exchange keys. Restore never replaces sealed keys: a kit for an identity already sealed here (the same ids, signing and exchange keys), with keys that work, is taken up as it is, since they may hold newer epochs; any other sealed keys, a broken copy of the same identity included, are a `conflict` until the person removes them.
  - **Recording it.** The keys are sealed first; then `writeDecisionsSettings` records the relay origin, installation and device ids, and a host id minted for this computer (`newId()`), and the running lifetime takes the new settings (`updateSettings`). A setting that fails to save leaves the keys for the next attempt to take up, and says so. Nothing else is written: the secret, the passphrase and the kit go nowhere.
  - **Disconnect.** `window.electron.decisions.disconnectRelay()` (`decisions:disconnect-relay`, `shell`) removes the key file, then the relay origin and ids from the setting, keeping the switch, consent and stored rows. It sends nothing to the relay, so the relay and its data are untouched; keys that can't be removed leave the setting as it was. The same call removes an unfinished setup's keys when no relay is recorded. When the socket (#16008) exists, disconnecting closes it.
  - **Settings.** Connection takes the claim secret once a check reads `unclaimed`, and a recovery kit file (read in the renderer, capped at 256 KiB) and passphrase once it reads `claimed`; with `keysStored` it also offers to finish a claim from this computer on a claimed relay. Each secret is handed to main as the attempt starts and cleared from every field at once, whichever form sent it, success or not, and a kit file still being read when another is chosen or a form is sent is dropped. A check a setup reran replaces the one shown, so the forms follow what the relay is now. Disconnect relay, and Remove keys for keys no relay is recorded for, sit behind a destructive confirm that says what goes with the keys: if no recovery kit or other computer holds the identity, the relay's past questions and answers can't be read again and nobody can reconnect to it as its owner.
- **The socket** (#16008). One outbound WebSocket to the relay's Durable Object, which uses Cloudflare's hibernation API so an idle connection costs almost nothing: no inbound port and no polling. The lifecycle is the protocol's: a single-use ticket, then `hello`, `sync` and `caught_up`; each event is verified, persisted and only then acknowledged, with the cursor advanced over contiguous sequence numbers; the text frame `ping` every four minutes and no application-level heartbeat. Close code 4409 (another process using this identity) backs off and warns; 4401 (this device revoked) stops for good and shows "revoked", with no reconnect loop; anything else reconnects with jittered exponential backoff from 1 s to 5 min. It reconnects on app start, on `powerMonitor` resume, on a network change and on re-enable, always resyncing from the stored cursor. The socket URL carries the ticket and is never logged.
  - As built (#16008): `DecisionsService` runs one `RelayConnection` (`relayConnection.ts`) per enabled lifetime once the store is open and the setting records a complete, unrevoked identity; a claim or restore starts one, a disconnect stops it before the key file goes, and a stop or quit stops it before the store and keys close. It loads the identity from the lifetime's `SealedKeyStore` (which may wait on a keychain prompt; nothing waits on it), refuses keys for another relay or device, and refuses a store whose ledger belongs to another identity: the first connection records the origin and ids in the store's meta (`daintree:relay-binding`), since another identity's sequence numbers would collide with the stored ones and its sync would start past events it never sent. Each attempt builds its own `DecisionsBridge` over that store, with a `RelayClient` on the origin-bound `net.fetch` wrapper (no retries: the outbox keeps its own retry times) and a socket through Electron's `net.WebSocket`, so the socket follows the system proxy and trust store as the HTTP does, held to the relay's own origin. A stopped bridge can't start again, and restarting its socket while a ticket request is out would open two sockets on one identity, so a drop retires the attempt (bridge stopped, requests aborted, store and keys refused to it from then on, socket detached) and Daintree schedules the next itself: `max(1 s, floor(rand × min(5 min, 1 s × 2^failures)))`, reset by a `hello`, which is also how the next attempt's time is known (the library keeps its own delay to itself). An attempt that hears no `hello` within 45 s is a failure. The socket's close codes are observed before the library acts on them: 4409 waits a random 150 to 300 s before trying again, and neither resume nor a network change cuts that short; 4401, a `revoked` frame, a ticket refused as `forbidden`, or the ledger's own revocation of this device record `revokedAt` in the setting against that identity, so no later lifetime connects with it, and nothing reconnects. The keys stay until the person disconnects. Electron's main process has no network-change event, so while a connection is wanted `watchNetwork` compares `net.isOnline()` and the external interface addresses every 5 s and reconnects when they change and the machine is online; a change only of route, DNS or proxy shows nothing there. A resume or network change within 2 s of an attempt's start joins it. A store that stops taking writes (`isFaulted()`) stops the connection rather than letting the inbox mark events it couldn't keep. The library persists an event and acknowledges it before it verifies it (verification and application follow, in order), so an acknowledgement is durable receipt, not acceptance. Until delivery lands (#16017), every bridge runs with a holding sink: every pane reads as present but busy, so answers stay saved and undelivered, nothing is typed, and no question's status changes. Logs carry close codes and delays only. Status reaches Settings on `decisions:status-changed` (`shell`, this machine's own windows only), each status carrying a `revision` so a read that lands after a newer push can't roll it back.
- **Phones** (#16009, #16010). Devices → "Pair a phone" shows a QR code for a one-time invitation; both screens then show the same six digits, and the user confirms they match. Revoking a device rotates the epoch key, so the relay holds new grants for every remaining device, and content the phone already downloaded can't be recalled.
  - As built (#16009): `window.electron.decisions.listDevices()`, `startPairing()`, `getPairing(pairingId)`, `approvePairing({ pairingId, code })` and `declinePairing(pairingId)` (`decisions:list-devices`, `decisions:start-pairing`, `decisions:get-pairing`, `decisions:approve-pairing`, `decisions:decline-pairing`, `shell`, refused while off) go through one `OwnerDevices` (`pairing.ts`) per recorded identity and enabled lifetime. It opens the sealed owner identity once and signs through the same capped `net.fetch` a setup uses, with no retries; claiming, restoring, disconnecting, deleting local data, turning off and quitting each drop it, which aborts its requests and forgets its invitations. Anything a signed request can't do is an observation: `not-set-up`, `unreachable`, `refused` (`not-recognised`, `rate-limited`) or `key-storage`.
  - **The list** is the relay's `GET /devices` through the library's `verifiedDevices`, so a device whose certificate doesn't verify against the owner key isn't shown; this computer and revoked devices are left out. Each device carries its certificate's label and role, when the relay registered it, its last authenticated request (`last_seen_at`) and `push_enabled`, which is whether the relay holds an enabled push subscription for it (it turns one off when the push service refuses it for good). Settings reads it when Devices mounts and after a pairing.
  - **An invitation** is the library's `createPairingInvite` for the `phone` role: five minutes less five seconds, at most three open on the relay at once (`busy`), and none once the relay holds its twelve devices (`full`). Main keeps it in memory; the link, whose fragment carries the one-time secret, goes to the renderer for the QR code and the copyable text and is kept nowhere. While Settings shows it, the renderer reads it every two seconds; main asks the relay's `GET /pairing/pending` and, once a phone has answered, returns the six digits computed here from the phone's keys (`localShortCode`), never the relay's.
  - **Approving** names the code the person saw, and main approves only the candidate that code was computed from, so a different answer arriving between the read and the click is never approved; if the relay's own code for those keys disagrees with this computer's, main rejects the invitation instead. The library then issues the device certificate and seals the current epoch key to the phone. Declining, closing the dialog while an invitation is open, or a code that didn't match rejects it on the relay, so neither the phone nor anyone holding the link can use it; main forgets it first, so it can't be approved from here whatever the relay answers.
  - **QR rendering** is `uqr`, imported only inside `PairingQrCode`, so it is a renderer chunk of its own that loads when a pairing starts and never at startup or with Decisions off. It draws dark modules on white with the four-module quiet zone in every theme, since many phone scanners read only that polarity.

## Delivering an answer

### The `decision` wake

Answers are typed through the same wake engine as Daintree's own notices, which waits for the terminal to settle, spaces lines per pane, and aborts if the pane is withdrawn or re-owned (#16015). `LaneWake.kind` has five kinds today (`notice`, `retired`, `lost`, `watch`, `approval`); `decision` is the sixth, with its branch in line assembly. `createDecisionWake`, modelled on `createApprovalWake`, provides:

- **`id`**: `dec-` plus a hash of question id and answer revision, matching `LANE_WAKE_ID_PATTERN`, so duplicates join one queued wake.
- **`recheck()`**: the pane still exists, `isLiveGeneration(paneId, generation)` holds, the ownership principal and observed agent incarnation are unchanged (a relaunch reports `unavailable` with reason `relaunched`), and the recorded agent session matches.
- **`beforeType()`**: writes the injection intent (`injection_id`, question id, revision) durably and synchronously before anything is typed; false keeps the wake off the line for good.
- **`report(outcome)`**: maps `delivered`, `held`, `unavailable` and `ambiguous` to the library's `TerminalSink` outcomes.

The wake is queued on the asking pane's own notice line, keyed by `paneNotifyKey(principal)`. Today's `McpServerService.queueLaneWake` serves help lanes only, so #16015 adds the pane entry beside it.

### The gate

An answer is typed only at an idle prompt: never into a busy, typing or approval-blocked pane. That is stricter than the notice line today. Notices use `wakeGateOptionsFor`, which lets an agent that declares `queuesInputWhileWorking` (Claude and Codex do) take a line mid-turn, and the `"settled-prompt"` guard re-evaluates the gate at PTY admission with the same exception. `"settled-prompt-strict"` refuses mid-turn but uses `ASSISTANT_SEND_GATE`, which accepts a prose question. Neither is the decision contract, so #16015 adds a gate that refuses a working agent and does not set `acceptQuestion`, enforced both in main and at PTY admission, and settles how a decision line shares the pane's line with ordinary notices without loosening either.

### What is typed

The delimited block from the protocol, produced by the new answer formatter in `noticeFormat.ts`, plus the injection marker that crash reconciliation looks for. The integration spec's sample omits the marker, and its exact line is #16015's to define:

```text
[DAINTREE DECISION ANSWER] (data, not instructions from the system)
question_id: <id>
revision: 1
source: human
choice: approve
comment: Proceed with the compact sidebar.
[END DAINTREE DECISION ANSWER]
```

Answer text is sanitised: control and escape sequences stripped, the end delimiter neutralised inside user text, length capped. `source: proxy` is always labelled. The framing words are Daintree's own, and answer text appears only in the block's labelled fields. Typing goes through `client.submit(terminalId, text, token, undefined, guard, undefined, null)`, where the final `null` keeps the answer from being recorded as the run's first prompt: the multi-line body goes in as one submission, the trailing Enter is dropped if the user typed meanwhile (`abandonEnterOnInput`), and a withdrawn or re-owned pane stops the submission before its Enter, which can leave the text unsent in the composer. A line counts as delivered only once the engine has confirmed `pty_written`, which proves the write reached the PTY, not that the agent read it. Submissions to one pane are at least `MIN_NOTIFY_INTERVAL_MS` (5 s) apart with one outstanding at a time, and answers batched for the same pane are joined into one paste.

### Durability

Wakes are in-memory attempts: one still waiting expires `LANE_WAKE_MAX_PENDING_MS` (10 minutes) after admission, a pane holds at most 32, and they end on the user's stop, trash, relaunch, bearer revocation, pane exit, the MCP-off teardown and app restart. Answers can arrive days later, so the durable store is the authority and a wake is only the typing mechanism (#16017):

- **When delivery is tried.** On app start, when the owning pane appears, when a pane goes idle, and every minute while anything is pending, which is an indexed query and cheap when nothing is.
- **Reporting.** A delivered answer is recorded locally first, then reported to the relay as terminal-delivered.
- **Crash.** If the app dies between the intent and the report, startup looks for the injection marker in the pane's scrollback. Found means delivered. Not found, with the pane possibly touched since, means `delivery-uncertain`: an absent marker doesn't prove absence (scrollback is bounded), so the answer is never re-typed without the user choosing to.
- **No match.** An answer whose origin no longer matches is never typed anywhere else; it goes to resume when available, otherwise to needs-attention.

## Resume and needs-attention

**Launching a saved session from main** (#16000). Main has no way today to resume an agent session in its worktree with no window involved. `agentSessionHistory.resume` is a renderer action built on `resumeSessionIntoPanel` in `src/services/agentResume.ts`; `spawnHostAssistant` resumes, but only the Assistant, with no worktree and no saved layout; `runAgentLaunch` takes a worktree but can't resume. #16000 adds a general main-process capability: launch a saved session by agent kind and session id as a new pane in a given project and worktree, through the normal launch path so the pane gets its usual launch-time MCP config, a fresh bearer and a fresh generation; save it in the project's layout so it appears when the project is opened; return the pane's identity and let the caller wait, with a timeout, for an idle prompt; refuse with a reason when the worktree is gone, the agent has no resume support or no session id is known; and return the existing pane when one already has that session open, as `findLiveResumePanelId` does in the renderer. Nothing in it is Decisions-specific.

**Resuming to deliver** (#16019). Claude (`--resume <id>`) and Codex (`resume <id> -C .`) only. Resume runs when the origin Host is this machine and reachable, the worktree still exists at the recorded path, the agent has a resume block, and a session id is known. It launches through #16000, waits for an idle prompt within a bounded time, records the new pane, generation and session as the delivery target, then delivers. Claude's sessions are stored per folder and don't survive a move; Codex resumes by session id from any folder. Many other registry entries have a `resume` block, but a block isn't proof of exact-session resume (kinds include rolling history and project-scoped resume, and Gemini's CLI is retired), so every other agent reports unsupported, with a reason, until its resume is proven against the installed CLI.

**Needs attention** (#16020). Answers that can't be delivered on their own (relaunched, worktree removed, resume failed, delivery uncertain) are listed with their alias, origin, reason and an answer preview. **Copy answer** copies the delimited block. **Try resume** runs #16019 and reports what happened. **Choose destination** lets the user pick another live pane, behind a confirmation that names both panes, and records the reassignment in the audit trail. A `delivery-uncertain` answer says "This answer may or may not have been delivered" and offers Copy.

## Remote Hosts

An agent on a Remote Host keeps its MCP listener, bearer, notices and terminal on that Host, and the Host keeps running agents while the owner's machine sleeps. Forwarding questions from the Host through the owner's machine would fail exactly then, so each Host is its own relay device of the same owner (#16021, #16022). The user's effort is the same as with a single hub: setup happens once, on the owner's machine, and every Host the owner connects to is enrolled with no step on either side.

- **Roles.** The machine where the user ran setup is the `owner-desktop`: it claims the relay, holds the epoch keys and approves phones. Every enrolled Host is a `desktop-host`.
- **Enrollment.** A connected Host is enrolled over the already authenticated link with a new session CALL, `decisions.enrollHost` (in `electron/remote/decisions/linkMethods.ts`, with a zod schema checked on the Host and a validated result on the Shell, like `electron/remote/deviceAnswer/linkMethods.ts`). The Host generates its keys and returns only the public halves; the owner signs a device certificate and an epoch grant sealed to the Host's exchange key and registers them with the relay; the Host stores its identity sealed by its own keychain. Private keys never cross the link. A Host too old to know the method answers unsupported, and Devices says it needs updating. (`ClientEndpoint.request` in `electron/ipc/endpoint.ts` is the Host-to-renderer reverse request, not the Shell-to-Host CALL path; enrollment uses session CALLs as the device-answer client does.)
- **Automatic by default.** Only the `owner-desktop` enrolls, since only it holds the signing key; a second Shell that connects to a Host enrolls nothing. While Decisions is connected on the owner, it enrolls each Host that isn't enrolled yet when that Host's link comes up, and every already connected Host once setup completes. One Host's enrollment failing never holds up another's, and a failure is shown in Devices and tried again on the Host's next connection, never in a loop. Each enrolled Host can decrypt every question and answer, as every device can, which is acceptable without asking per Host because a Remote Host already runs the owner's agents, holds their code and shows their terminals. The consent on first enable says connected Hosts are enrolled. A device-owned `autoEnrollHosts` field in the `decisions` setting, defaulting to true (a sanitiser default, no migration), turns this off for a user who connects to machines they don't own; with it off, Devices offers **Enroll** per connected Host instead.
- **Revoke is the undo.** Enrolled Hosts are listed in Devices beside phones. Revoking one uses device revoke with key rotation, and the owner records the Host's id in its local store (#16002) so it is never enrolled automatically again; **Enroll** in Devices enrolls it again and clears the record.
- **An identity, not settings.** The Host has no relay URL field or switch of its own; the relay origin comes with the identity it was given. It runs Decisions for its own panes whenever the owner has Decisions on. When the owner disables Decisions or revokes the Host, the Host stops, removes its delivery credentials and shows the reason; a revocation reaches a Host the Shell isn't connected to through the relay (4401), and how a disable reaches one is #16022's to settle.
- **Its own work only.** A Host acts only on questions it created and ignores events targeted at other devices. It receives the same ciphertext as every device, which is acceptable because every device belongs to one owner. A Host that was offline catches up through `sync`; pending answers wait in the relay meanwhile.
- **Topology.** macOS and Linux Hosts are reached over ssh; Windows is a Shell only, driving Linux Hosts inside WSL distros, and a WSL Host enrolls the same way. A WSL distro stops about 15 s after its last `wsl.exe` client exits, and its keeper (`wslKeepalive.ts`) lives only as long as Daintree on Windows, and closing the last window quits Daintree on Windows (it can't be a Host), so a WSL Host's agents and its Decisions service can stop once Daintree on Windows is closed.
- **Shell view.** The Shell's Decisions page shows each enrolled Host's connection state as observed. Pane state (the `terminal:decision-state` push and the `decisions:get-pane-state` read) has `host` locality, so a window on a Host reads its own panes' state from that Host.

## What is stored where

| What | Where | Child |
| --- | --- | --- |
| The `decisions` setting: enabled, relay origin, ids, non-secret preferences | electron-store, `device`-owned | #15998 |
| Owner signing key, epoch keys, device keys | one file, `userData/decisions/keys.bin` (0600, in a 0700 directory), sealed with `safeStorage`; kept when Decisions is turned off | #16003 |
| Questions and their origins, outbox, inbound event log and cursor, injection intents, audit trail | the app database (better-sqlite3), the `decisions_*` tables from migration 0022 | #16002 |
| Encrypted attachments waiting to upload | a file spool under the user-data directory, removed once uploaded or cancelled | #16014 |
| A pane's `daintree-decisions` entry and bearer | the existing pane config (`userData/mcp-pane-configs`, 0600) or the PTY env; the bearer is revoked on PTY exit and the file deleted, best effort | #16012 |
| Decision-model history | the model's own local store, only with learning on | #16026, #16027 |
| On a Host: its sealed identity and its own store | the Host's own user-data directory | #16021, #16022 |
| On the owner: the ids of Hosts the user revoked, so they aren't enrolled automatically again | the owner's local store | #16021 |
| Never on disk, in logs, the audit trail or telemetry | claim secret, recovery passphrase, Cloudflare token, socket ticket URL; the guided deploy pane's screen, which shows the claim secret | #16003, #16006, #16007, #16023 |

**The local store.** As built (#16002): `DaintreeLocalStore` implements the library's `LocalStore` over the shared app-database connection, in six raw-SQL tables (`decisions_meta`, `decisions_questions`, `decisions_outbox`, `decisions_inbound_events`, `decisions_injection_intents`, `decisions_audit`) from `0022_decisions_store.sql`, used through `sqlite.prepare` as `0017_assistant_sender_credentials.sql` is. Question content arrives sealed (`content_sealed`, the published envelope) and answer entries are sealed one by one inside `answers_json`, so no row holds question or answer text in clear; the library's legacy plaintext column has no counterpart here, and the store refuses a non-null `legacy_content_json`. The origin keeps its optional project and machine labels. None of it goes in logs or anything that leaves the machine; the audit trail carries ids, requirement level, gate, provenance, outcome and timestamps only, in Decisions' own table rather than an MCP audit ring.

- **Batching.** Calls queue in the order made and run together on the next turn of the event loop, in one transaction, each inside its own savepoint, at most 256 to a transaction: a call that fails on its own (a duplicate question) rolls back alone, and no call resolves before the transaction holding it has committed, so a question is on disk before `ask_human` publishes it and an intent is on disk before a terminal is touched. Concurrent calls and bursts share one commit. The library's socket handler awaits each frame's writes in turn before acknowledging it (stored, then acked), so successive frames can't share a commit without acknowledging what isn't on disk; merging them would need a bulk-ingest change in the library. A read with nothing queued ahead of it runs at once.
- **Durability.** A transaction with writes in it commits with `synchronous = FULL`, as the library requires, and the connection goes back to the app's `NORMAL` straight after, so other writers keep their cheaper commits. State survives a restart, undelivered answers included.
- **Disk pressure.** While `getWritesSuppressed()` is on, every write is refused with `DecisionsStoreUnavailableError` (`disk-pressure`), audit records included, never dropped: a question is either committed or its caller is told it wasn't. The first refused write, or any storage error on a read or a write, stops that store writing for the rest of its lifetime (`isFaulted()`); reads keep working, and the next enabled lifetime opens a fresh store. This matters because the library's inbox marks an event processed after a failed apply: once an answer's question can't be read or its write is refused, the mark must be refused too, or the answer would be lost. The relay connection stops once the store reports a fault (#16008); recovering without a restart or a toggle belongs to #16017.
- **Lifetime.** `DecisionsService.start` opens the store through `openDecisionsLocalStore` (lazily, and never once the lifetime has been disposed, so quitting can't reopen the database), and `getStore()` hands it to later children; `stop` and `dispose` close it, committing what was queued. Closing never closes the shared connection, and shutdown stops Decisions long before `closeSharedDb`. Disabling Decisions leaves the data in place. `eraseDecisionsData(sqlite)` deletes every Decisions row in one transaction, committed with `synchronous = FULL`, and nothing else; Data → delete (#16025) runs it with the store closed, so calls still queued can't write rows back (see [Data](#setup-data-and-the-decision-model)).
- **Tests.** `daintreeLocalStore.contract.test.ts` ports the library's store contract at v0.1.0 (its `LocalStore contract` and `atomic intent settlement` blocks, which the package doesn't export) and runs it against this store; an upgrade of the pinned release re-ports it from the new tag.

**Keys.** Core Daintree has no encrypted secret store: `SecureStorage` is plain text by design. The plugin secret cipher and the Decisions `SealedKeyStore` (`keyStore.ts`, #16003) both seal through `osKeychain.ts`: the async `safeStorage` API, a 60 s deadline, and one process-wide record of a keychain that gave no key this session. The plugin cipher refuses Linux's `basic_text` backend with no override. The key store refuses it with a reason (`weak-storage-unconfirmed`) until setup calls `confirmWeakStorage()` after the user accepts the weaker storage; the file records that protection, so later saves on that machine keep working, and the next save once a keyring answers seals it properly. A real keyring that answers with the fixed-key fallback is a keychain failure, never weak storage. Only a missing file is "no keys", read without asking the keychain; a keychain that can't open existing keys is reported as `locked`, `unavailable` or `timeout`, and a file it can't explain as `unreadable` or `unsupported-format`. `save` opens the existing keys before replacing them (a recovery import's overwrite included), so none of those ever overwrites them; only an explicit `clear()` removes the file. `check()` tells setup what sealing would use before it saves anything. The service makes the store on first use in an enabled lifetime, so turning Decisions on asks no keychain, and closes it on stop. Claim secrets, recovery passphrases and Cloudflare tokens are matched by `redactSecrets.ts` (screens that leave the machine) and the shared `secretScrubber.ts` (logs, telemetry, the MCP audit summary), and `passphrase` joins the sensitive key names in the logger and the MCP argument summary, as a backstop: nothing writes them anywhere in the first place.

## What leaves the machine

This is what the consent shown on first enable names (#16004), and what [feature-curation.md](../feature-curation.md#hosted-features) records:

- **To the user's own relay**, in their Cloudflare account: the question, its context and options, attached screenshots and the answers, all end-to-end encrypted between the user's computer and phone; signed protocol events and delivery acknowledgements; and routing metadata the relay can read (ids, timestamps, requirement level, sizes).
- **To each enrolled Remote Host**: an epoch grant sealed to the Host's own key and registered with the relay, which lets it decrypt every question and answer so it can serve its own panes. Hosts are enrolled automatically when they connect unless the user turns that off (#16021).
- **Push endpoints.** Each paired phone registers its own with the relay, which sends Web Push to the phone app (a PWA the same Worker serves). A push says only that a question needs input, never the question.
- **Voice dictation**, if the user turns it on in the phone app, is not end-to-end encrypted: the audio streams through the relay to a speech provider (xAI or OpenAI, `/voice/ws`), and correction sends the raw transcript with the question and its option labels to a model provider (Anthropic or OpenAI, `/voice/correct`). Daintree on the desktop sends nothing for it, and the answer the user then sends is encrypted like any other.
- **The decision model** runs on the desktop. History goes to an external model provider only through an adapter the user chose, under its own consent (#16027).

Question content comes only from what an agent puts in a question; Decisions never reads a terminal to send it. Answers, signed events, delivery acknowledgements and routing metadata cross the network as listed above, and decision history reaches a model provider only under its own consent. No Daintree-operated server is involved at any point.

## The renderer

- **Settings → Integrations → Decisions** (#16004), a global tab on every platform and in settings search, modelled on the `mcp` entry in `settingsTabRegistry.tsx`. It isn't inside Hosts, where Answer from another device lives, because Decisions isn't a Remote Hosts feature. One enable switch; turning it on the first time shows the consent above, and the switch stays off unless the person agrees. Behind it, Connection, Devices, Questions, Policy, Voice (an explanation only) and Data, each its own component in `src/components/Settings/Decisions/` so each child adds to its own section; the Decision model section is #16027's. Connection shows the service state as observed ("Not connected" with why when a relay that's set up can't be used, "Connecting to <host>", "Connected to <host>", "Reconnecting to <host>" with the next attempt's clock time, "Replaced by another connection" and "Revoked by <host>" as warnings), pushed live (#16008), and claims, restores and disconnects (#16006, see [The relay connection](#the-relay-connection)). The Data section shows the same list of what leaves the machine that the consent dialog does (`DecisionsDisclosure`), so the two can't drift. Questions says how long a question waits, as the library sets it, and that an expired one authorises nothing (#16013); its default-expiry control waits on daintreehq/decisions#15. Policy lists the trusted gates read-only and holds the proxy allowlist switch (#16013).
- **`terminal:decision-state`** (#16016), a per-pane push modelled on `terminal:notify-state` and registered everywhere a push event must be, with `host` locality. Its `PaneDecisionState` carries the pane's open questions (`queued` or `open`: id, alias, asked at, expiry), what is waiting to be typed (an answer, or only an expiry notice, with its delivery status) and what needs attention (`needs-attention` or `delivery-uncertain`, with the library's `error_code` as the reason when it is a code, `unspecified` otherwise), and a revision that rises with every change and never falls behind the wall clock in milliseconds, so a Remote Host restarted under a Shell's live views outranks its previous run. It is projected field by field from the store's question rows (`projectPaneDecisionStates`), never reading question content or sealed answers, so it carries no question, option or answer text. Imported history shows nowhere, and a pane is routed to the project of its newest question, settled or not. The renderer reads a pane's current state on mount with `window.electron.decisions.getPaneState` (`decisions:get-pane-state`), and `decisionsClient.watchPaneState` subscribes before it reads and keeps the higher revision. The state lives in `DecisionsService` for an enabled lifetime: it is fed every question row with `observeQuestions(rows)`, once from the store when the lifetime starts and again after each write commits, and only panes whose state changed are pushed. Both feeds are `QuestionRowsFeed` (`questionFeed.ts`, #16011): one read when the store opens, and one after each question write that commits through the connection's store (`observeQuestionWrites` wraps `commitNewQuestion`, `updateQuestion` and `settleIntent` for the attempts and the `QuestionBridge` alike), coalesced to one read at a time and fed nothing once the lifetime stops. Nothing is fed, emitted or subscribed while Decisions is off: the read answers null from the store without loading Decisions, turning it off pushes each pane that showed something one empty state, and quit pushes nothing.
- **The pane chip** (#16018) beside `TerminalNotifyChip`, saying what was observed: "Question q-42 is waiting for an answer", "Answer received, delivering when this terminal is idle", "Answer needs attention", with a count for several questions. Needs-attention surfaces in Canopy's needs-you tier (`CANOPY_NEEDS_YOU_PRIORITY`); routine states never raise toasts ([notification-system.md](./notification-system.md)). The chip, tab and list use the Decisions mark (#16028).

## Setup, data and the decision model

- **Deploy** (#16023). With no relay set up, Connection offers "Don't have a relay yet?": what either route creates in the user's account (a Worker, its Durable Object and a private R2 bucket) and that Cloudflare's free plan is enough for one person. **Deploy to Cloudflare** opens the official deploy page (`https://deploy.workers.cloudflare.com/?url=https://github.com/daintreehq/decisions`) through `system.openExternal`, says it asks for one secret, `CLAIM_SECRET`, and hands focus to the URL field. **Guided deploy** closes Settings through the tab's close (`needsOnClose`, whose `afterClose(true)` runs once the dialog has gone and handed focus back; a close unsaved settings hold runs nothing, and a reopen before the exit finished answers `afterClose(false)`), then opens a focused pane titled "Deploy Decisions relay" in the active worktree's grid, running `npx --yes @daintreehq/decisions-cli@<version> deploy --name <name> --bucket <name>` (`npx.cmd` on Windows, which PowerShell's default script policy doesn't block) from the user's home folder, so no project's npm config applies. The CLI is pinned to the protocol package's version (`DECISIONS_CLI_VERSION`, held equal to it by a test), since its `deploy` uploads the relay of its own version. Each guided deploy gets a fresh `daintree-decisions-<8 hex>` Worker and bucket name, because the CLI treats a Worker that already exists under its name as an update, and Daintree never updates a deployed Worker; the official page can deploy a newer relay, which the compatibility check then reports. No token, account or `--claim` flag is passed: Wrangler signs in through the browser and keeps its own login, and Daintree never sees a Cloudflare token. The guided route needs a local window with a project or scratch open: a Remote Hosts window's terminals run on the Host, where Wrangler's sign-in callback can't reach this browser. The pane's id starts with `DECISIONS_DEPLOY_TERMINAL_PREFIX`, and `isScreenNeverSaved` (with the throwaway prefix) makes both session snapshot writers refuse it, so the screen showing the claim secret never reaches disk and a restart brings back an empty shell. `addPanel` keeps no command on a pane with that prefix (the spawn alone runs it), so a restart, duplicate, restored layout or saved recipe never runs the deploy again under the same Worker name, and `ShardRecoveryCoordinator` drops its stored spawn before a pty-host crash replay or migration, as it does a throwaway run's, reporting it lost; no renderer channel carries that loss yet, so the pane keeps its last screen but takes no input after such a crash. The pane carries a banner whose **Connect relay…** opens Settings → Decisions and leaves a request (`requestRelayUrl`) that Connection takes when it renders, after status loads and after Decisions is turned on within that opening of Settings, landing on the relay URL field. A request is dropped when the Decisions page that claimed it closes without taking it, or when no page claims it within ten seconds. Either route then goes URL → check → claim, with the claim secret typed once into the claim form, which keeps no copy. Nothing reads the terminal's output for the URL or the secret.
- **Full-loop check** (#16024). Setup is complete only when relay health, the claim, an encrypted attachment round trip, a socket connect, the push configuration and a test question to paired phones have all passed, with the test answer delivered into a labelled diagnostic pane that runs no agent, and the recovery kit is verified. It reruns later as a doctor.
- **Data** (#16025). Export writes the decision history archive to a file the user picks. Delete relay data removes the relay's stored content after a typed confirmation that says what stays (the Worker, and anything already on paired devices). Delete local data removes this machine's store and keys and leaves the relay untouched.
  - As built: three `shell` ops in `decisionsNamespace`, refused while off, each answering one observation rather than a thrown string where a person can act on it.
  - **Export** (`decisions:export-data`, `{ passphrase }`; `dataExport.ts`). Behind the switch's transitions, the library's `exportDecisions` reads the lifetime's store and opens every question and verified answer with this computer's epoch keys (which may show the keychain's prompt), then encrypts the zip under the passphrase (the library's recovery-bundle scheme, at least 12 characters, kept nowhere). The library is handed the store through a proxy that counts what `listQuestions` and `listAudit` return, so the counts reported are of exactly what was archived. The save dialog opens over the asking window outside the transitions, so turning off or quitting never waits on it, and an archive whose store has closed meanwhile (Decisions turned off, even if on again since, local data deleted, or quit) is dropped unwritten, so deleted history is never written out. The file is written atomically with mode 0600. Plaintext export isn't offered, and nothing is fetched: the paired devices' public keys, which only the relay lists, and attachment bytes aren't in it. Content its keys can't open fails the export rather than being left out. Observations: `saved` (path and counts), `cancelled`, `no-identity` (no keys, or an unfinished claim's), `key-storage`, `store-unavailable`.
  - **Delete relay data** (`decisions:delete-relay-data`, `{ origin }`; `relayData.ts`). Scope `questions`, the decisions CLI's default: the relay empties its attachment bucket, then deletes questions, answers, events, deliveries and receipts in one transaction, keeping its owner, its devices, their key grants and push subscriptions, and the Worker. Scope `everything` is never sent: it would unclaim the relay and strand this computer's identity, which only the person removes (Disconnect). The confirmed origin must still be the relay set up here (`changed` otherwise), and the request is signed with this computer's finished owner identity for it (`no-identity` otherwise), through the same origin-bound `net.fetch` as setup with a 60 s deadline. It is sent once (`maxRetries: 0`): another device can add content between two attempts, so a repeat waits for the person. Only the relay's `{ ok: true, scope: "questions" }` reads as `deleted`; a request that never left this computer is `not-sent`; a refusal is `refused` (`not-recognised`, `rate-limited`, `rejected`); anything else after the request may have arrived (a timeout, a reset, a server error, an answer that isn't the relay's) is `unconfirmed`, since the relay deletes attachments before its rows and doesn't stop when the answer is lost. Turning off waits for the answer, and quitting aborts it. Settings gates it on typing the relay's host.
  - **Delete local data** (`decisions:delete-local-data`; `localData.ts`, `DecisionsService.eraseLocalData`). In the service's own queue, the relay connection stops (as on a stop, which closes `/mcp/decisions` and fences its writes), the pane-state feed stops, and the store and the key store close (committing what was queued), then the key file is renamed to `keys.bin.erasing`, every row is deleted in one transaction, the relay's origin and ids are cleared from the setting, and the set-aside file is unlinked; an empty store then opens, the feed reads from it, and every pane that showed something is told it has nothing. A deletion that changed nothing reconnects on the same identity; one that forgot the relay has none to connect to. Every window gets the new status. It never asks the keychain and sends nothing. A failure before the rows' transaction commits puts the keys back (`failed`: `disk-pressure`, `storage`, `keys`). The set-aside file is the record that a deletion began, and whether any row is left says whether it committed, so the rename and the unlink are made durable (the parent directory synced, except on Windows) and `finishInterruptedErase` runs before every store opens and at the start of every deletion: rows left put the keys back, none left finish the deletion (and a deletion that finishes one that way reports `deleted`), and keys sealed since mean the set-aside ones are dropped. A last step that fails, or an earlier deletion that still can't be resolved, reports `incomplete` (with `erased` when the rows are gone) and leaves the store closed, since a row written meanwhile would read as one the deletion never reached. Quit waits for a deletion under way, and refuses one still waiting its turn. The switch and consent stay.
  - **Limits.** The app database's rolling backup (`daintree.db.backup`, rewritten on the maintenance tick every five minutes) can hold deleted rows until its next refresh, sealed under keys that are gone; freed pages and the WAL aren't scrubbed (`VACUUM` and `secure_delete` would reach the whole shared database), and copies outside the app (a user's exports, filesystem snapshots) are untouched.
- **Decision model** (#16026, #16027). Off by default, with its own consent and an evaluation report shown before the proxy may answer anything. It answers only questions whose level and gate allow it, never `human-required`, design-review gates or anything on its hard-block list, and its answers are labelled `source: proxy` in the typed block, the audit trail and on the phone.

## Where this differs from the integration spec

The integration spec was checked against an older clone. Where it and this doc disagree, this doc reflects the code and the programme's decisions:

- **Package scope.** `@daintreehq/decisions-*`, not `@daintree/decisions-*` (daintreehq/decisions#13).
- **Scope of the setting.** No per-project enablement or per-project opt-in, and no Host-scoped settings: one global switch, and Hosts get an identity (#15996).
- **Unsupported agents.** No manual `decisions mcp` setup line in Settings (#15996).
- **Request order.** Repeated security headers are rejected before the Host and Origin checks. `setPluginRouteHandler` is a method of `HttpLifecycle`, called from `McpServerService.ts`; `revokePaneBearer` is on `McpServerService`.
- **Session binding.** Core sessions bind with `bindSessionCredential`; the plugin route has its own credential index rather than calling it.
- **Bearers.** Tier off mints no bearer today, and every pane token passes `isAuthorized`; the Decisions-only bearer is new (#16012), injected for every supported launch rather than "panes whose project has Decisions enabled".
- **The wake gate.** `decision` is the sixth `LaneWake` kind, not the fifth, and reusing `"settled-prompt"` unchanged would type into a working Claude or Codex pane; #16015 adds the stricter gate.
- **Workspace binding and generations.** `PaneWorkspaceBinding` holds no worktree root, and spawn generations come from a per-process ledger, so neither is a durable identity on its own.
- **Local plaintext.** The spec says question text isn't stored in plaintext beyond the decision model's history. The pinned release goes further: it seals question content and each answer entry before handing a row to the store, so the local store holds no question or answer text in clear (#16002).
- **The typed block.** The spec's sample block has no injection marker, though its crash reconciliation searches scrollback for one.
- **Store and migration names.** `settingOwnership.ts` is `shared/config/settingOwnership.ts`. `0020_decisions.sql` and `043-decisions-settings.ts` were the next free numbers when the spec was written, not reserved names: the store's tables landed as `0022_decisions_store.sql`, and the settings migration exists only if one is needed.
- **Timeouts.** `MCP_CONFIRMABLE_CALL_MAX_MS` is the confirmable-call deadline (640 s), not plain dispatch (30 s). Neither matters, since `ask_human` returns at once.
- **Remote Hosts.** `ClientEndpoint.request` is the Host-to-renderer reverse request; enrollment is a session CALL. The spec has the Shell initiate enrollment without saying when; here the owner enrolls each connected Host automatically unless the user turned that off (#16021).
- **Question defaults.** The spec's Questions section has a default expiry, and its gate shape a `defaultExpiryMs`. The pinned release has no host hook for a question with no origin gate (daintreehq/decisions#15), so Settings shows the library's own wait and offers no control until it has one. The spec's gate fields `allowText` and `bindArtifacts` exist as the library names them; `onApprove` doesn't.
- **Import budget.** `scripts/check-import-budget.mjs` is a local check, not a CI gate.
- **Open items in the spec's §14.** The route is its own (#16011), not a core action. Each Host enrolls as its own device (#16021) rather than forwarding through the owner. The curation decision is recorded in [feature-curation.md](../feature-curation.md#decision-log) (#15997). The libraries publish under the `@daintreehq` npm scope. No agent gains launch-time MCP in this programme. Push through the user's own relay answers the push question #14023 left open: Daintree operates no relay.

## Verification

Each child ships CI-safe tests with no real relay. Together they cover: the route refusing missing, API-key, help, plugin and foreign tokens, DNS-rebinding and bad-Origin requests; a question defaulting to `human-required` and an agent unable to downgrade it; the origin persisted before network I/O; the wake deduping, rechecking generation and principal, reserving before typing, and never typing into a busy, typing or approval-blocked pane; ordering and spacing; restart re-arming undelivered answers; crash reconciliation by marker or `delivery-uncertain` without re-typing; the resume adapter's success, missing session, deleted worktree and timeout; Host enrollment over a fake link; 4401 stopping delivery; and the off state proving no import, listener, timer or socket.

Some guarantees can only be proven with a real phone and real CLIs, against a real relay (#16030): delivery to the correct terminal across an app restart, a lost connection and a busy pane; several questions in one pane arriving in order; proxy flows with the design-review gate refusing a proxy; attachments and a design-review approval bound to the reviewed screenshots; WSL and ssh Hosts answering for their own panes; Claude Code and Codex resume against the installed versions; answers surviving a 48-hour desktop outage; no measurable overhead when off; and a revoked phone seeing no new questions.
