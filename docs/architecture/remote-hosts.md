# Remote Hosts

A Daintree window can drive another machine's Daintree over the system `ssh`. The window's machine is the **Shell** (screen, keyboard, device preferences); the other machine is the **Host** (agents, terminals, worktrees, git, files, plugins, MCP, and the accounts and settings that go with them). Every Daintree process is both: it can drive hosts, and with Host mode on it also serves Shells. Everything specific to the feature lives in `electron/remote/**`; core code meets it through a handful of seams (the IPC dispatcher, the endpoint registry, the drive lease, the operation registry, the viewless MCP executor).

The hard rule behind every seam: **someone who never adds a host sees exactly today's behaviour.** No remote service dials or listens until a host is configured or Host mode is on, the dispatcher's routing is a single null check with no router installed, local keys and paths are unchanged, and new UI stays hidden until a second host exists (the Settings → Hosts tab is the one deliberate exception, as the entry point for adding the first host).

## Roles and scope

- **One host per window.** A window is bound to exactly one host through `WindowHostBinding` (`electron/remote/client/WindowHostBinding.ts`); Cmd/Ctrl-click in the host menu opens a new window instead of rebinding. `LOCAL_HOST_ID` (`"local"`, `shared/types/remoteHosts.ts`) names this machine.
- **Switching.** A window is only ever rebound together with the view it shows (`RemoteHostsClient.switchWindowHost`). A switch that names no project (the host menu's row, **Just switch host**, an overview card, `host.switch` with a `hostId`) opens the project this machine last showed on that host: the host remembers it per Shell install (`host.note-active-project` / `host.last-active-project` session CALLs, keyed by the `deviceId` a Shell mints once into its own user data and sends in its HELLO, so it outlives a Shell relaunch and two installs that share a machine name stay apart; a Shell that sends none falls back to its machine name; in memory for the host's life); for this machine it is the window's own history, else the most recently opened project. With nothing to return to the window stays put and the switch answers `choose-project`, and the view shows that host's project list (`HostProjectPicker`); a new window opens on this machine with the host's list on offer, so it moves to the host only once a project is picked: the client records the offer for that window, and the view takes it once (`remote-hosts:take-project-offer`) when its picker host mounts, since a send before the view listened would be lost; a `project-offer` event covers a view already up. A window is never bound to a host without a view of that host's behind it, since a view's host is fixed when it is created. A project has one view in the app, a host's as much as this machine's (`projectOwner`, over `findOtherProjectOwner` with the view key): a switch or new-window request naming a project another window already shows brings that window forward and answers `focused-elsewhere`, and one another window holds in its cache is shown there again first; a switch back to this machine that names no project passes over local projects another window has. A second view of a host's project would be a second endpoint on the same terminals, the two taking the lease from each other whenever one claimed it. Every switch the client makes is recorded in the window's "previous workspace" history, remote workspaces by host-scoped key, so the toggle crosses hosts.
- **Restoring windows.** A window that was showing a host's project when the app quit is saved as `<hostId>:<projectId>` in the open-windows manifest, opens on this machine's picker at launch and switches back once Remote Hosts is up (`electron/window/remoteWindowRestore.ts`), unless the person has put it to use first. If the host can't be reached, the window stays on the picker with a Retry, keeps its place on the host for the next launch, and moves back by itself once the host is reachable: it is tried again when the host's link moves into connected (never on the pings of a link already connected), and the host is dialled again while a window waits, from 30 s backing off to 5 minutes (`REMOTE_RESTORE_REDIAL_MS`, `REMOTE_RESTORE_REDIAL_MAX_MS`), since a host that quit cleanly parks its link and nothing else would dial it. A host that refused the ssh login or runs a build this one can't talk to isn't dialled again, though the window still moves back if it connects; a switch the person starts in the window always wins, and a project gone from the host lets the window go. A window's background host projects are saved the same way in its `backgroundProjectIds`, capped apart from its local ones (`MAX_BACKGROUND_HOST_PROJECTS_PER_WINDOW` beside `MAX_BACKGROUND_PROJECTS_PER_WINDOW`) so they never cost a local project its slot (#13932). At launch they bypass the local restore queue, which only resolves paths on this machine (`takeHostBackgroundRestores`). Once the window's own project has had its try, they come back as cached views it never shows (`RemoteHostsClient.restoreHostProjectInBackground`, `ProjectViewManager.restoreInBackground`): one at a time per host, dialling only the hosts the window had views on, with no rebinding, claim or activation, and none where another window already has the project. Until a host connects its projects stay pending in the tracker, so every save, the quit's included, keeps them. They wait on the same connect-triggered retry and redial as the window's own project, and drop out only when restored, gone from the host, held by another window, or their host is removed; at the window's warm-view ceiling the rest wait for the next launch.
- **Opening folders.** A window on a host opens the host's folders, never this machine's. **File › Open Project…** and **Open Project in New Window…** there hand off to the renderer's `project.add` / `project.openInNewWindow`, so the host picker chooses and the host opens. A folder on this machine reaching such a window (Open Recent, its failure recovery, a cached view the window still owns) brings the window back to this machine through `switchWindowToLocal`, binding and view together; a folder with no repository opens in a window on this machine instead, where its git-init prompt acts locally. Every switch back to this machine (those, the host menu, the previous-workspace toggle) activates the project as a local open does — current project, view notice, workspace and worktree ports, PTY port — through `completeLocalProjectActivation` (`electron/window/localProjectActivation.ts`), since showing the host's view retired the window's local terminal pair and parking a view closed its producer ports. Dock drops, Finder and the CLI never reuse a host window as empty or current (`onRemoteHost` in `windowOpenPolicy.ts`), and a host view's "open in new window" for one of its projects opens it in a new window on the same host (`routeNewWindowRequest`, which goes by the asking view's own host rather than its window's). Main reads a window's host through `electron/window/windowHost.ts`.
- **Remote views.** A remote-bound window's project views are keyed by `toHostScopedKey(hostId, projectId)` (`<hostId>:<projectId>`; local keys stay the bare id) in `ProjectViewManager`, and get `--daintree-host-id=<id>` (`HOST_ID_ARG` in `electron/window/ProjectViewFactory.ts`), surfaced to the renderer as `window.__DAINTREE_HOST_ID__`. A view's host comes from its key, so a local project view inside a remote-bound window still runs locally; a view with no project follows its window's binding.
- **Host mode** is a capability of the running app, not a second backend: the same process listens on a Unix socket for Shells. The single-instance lock still guarantees one backend per `userData`.
- **macOS and Linux Hosts, in any pairing over ssh; Windows as a Shell only**, driving Linux Hosts in WSL distros on the same PC (see [Windows: a Shell for WSL](#windows-a-shell-for-wsl) and [WSL](#wsl-12830)).

## Windows: a Shell for WSL

- **Runtime gates, one per role.** `isRemoteShellSupported()` (this machine drives other hosts) and `isRemoteHostSupported()` (other machines drive this one), with `isEitherRemoteRoleSupported()` for what both need — main: `electron/remote/buildGate.ts`; renderer: `src/lib/remoteHosts.ts`; all delegate to `isRemoteShellSupportedOn` / `isRemoteHostSupportedOn` in `shared/config/remoteHostsSupport.ts`. Every platform is a Shell; only macOS and Linux are Hosts. The Shell gate covers the host chip and menu, Settings → Hosts, switching, the overview and the host actions (`host.switch`, `host.add`, `host.forwardPort`, `project.openOnHost`, `host.overview.open`). The Host gate covers Host mode's launch flags and switch (`--host-mode`, `--enable-host-mode`, `--host-mode-handoff`), start at login and `--attach-stdio`, and Host mode's settings, which a Windows build never shows.
- **One connection kind per platform.** `remoteConnectionKindOn` (same module) says how a Shell reaches hosts: WSL distros on Windows, ssh everywhere else (Windows' OpenSSH has no ControlMaster, which the ssh transport is built on). `requireSupportedConnection` (`electron/remote/client/connection.ts`) refuses any other kind, `UNSUPPORTED`, when a host is added, set up or dialled; a record of another kind (an ssh host in a settings file carried to Windows) is kept but never run.
- **Build gates.** `__DAINTREE_REMOTE_HOSTS__` (the feature at all) is true for every target; `__DAINTREE_REMOTE_HOST_ROLE__` (the Host role) is false for win32 targets, set in `scripts/build-main.mjs`, with both read in `vitest.config.ts` (ambient declarations in `electron/types/buildDefines.d.ts` and `src/types/env.d.ts`). `__DAINTREE_BUILD_COMMIT__` is baked the same way for the handshake. The Host role loads only behind `if (__DAINTREE_REMOTE_HOST_ROLE__)`: the Host half of the remote boot (`electron/remote/hostBoot.ts`: Host mode's service, its listener, AppImage moves), the attach CLI in `electron/bootstrap.ts`, and the headless-host takeover in `electron/main.ts`.
- **Tree-shake rule.** esbuild folds only a direct `if (__DAINTREE_REMOTE_HOSTS__) { await import("…/remote/…") }`; a boolean imported from another module does not drop the chunk. So core code (anything outside `electron/remote/**`) never statically imports a remote module, except the four core-safe files: `buildGate.ts`, `runtime.ts`, `pendingHandler.ts`, `handshakeInfo.ts`. `main.ts` loads `./remote/boot.js` through that direct form; boot registers services into `runtime.ts` (`registerRemoteService`, with each module augmenting the `RemoteServices` interface), and core code reaches them with `getRemoteService(key)` / `requireRemoteService(key)`. Core seams take injected hooks instead of imports (`dispatcher.setRemoteRouter`, `setRemoteBoundViewFilter`, `setRemoteViewHooks`, `setMcpDriveTargetResolver`). The Shell may import only the Host's pure contracts (the attach preamble, the discovery file, socket paths, link method schemas, the Host mode status file, unit templates), never a listener or service.
- **Proof.** The tree-shake test, `scripts/__tests__/remoteHostsTreeShake.test.ts`, bundles the main-process entries the way `build-main.mjs` does in three configurations and reads the metafile: with the feature off, no file under the gated `electron/remote/` directories may be in the bundle and only the four core-safe files may be reached from core; with only the Host role off (a Windows build), every Shell directory and the WSL transport are in and no Host module is, beyond the pure contracts above; with both on, the Host's runtime is there too. On the renderer side, `materialize.ts` and `LazyUploadConfirmHost.tsx` load the remote-only upload modules under the feature check, pinned by a static-import walk from `src/main.tsx`.

## Transport

- **How a host is reached.** A host record carries `connection: HostConnection` (`shared/types/remoteHosts.ts`), a discriminated union: `{ kind: "ssh"; target }`, or `{ kind: "wsl"; distro }` for a Linux Host in a WSL distro on this Windows machine (see [WSL](#wsl-12830)). Addresses are shown only through `formatHostConnection` (`Ubuntu-24.04 (WSL)` for a distro); distro names compare without regard to case, as WSL looks them up. The transport (`initClient.ts`), the setup channel (`HostSetupService`) and everything that exists only over ssh (a ControlMaster, `-O forward`, scp, the editor's SSH remote) switch on `connection.kind`; a kind without the capability gets `unsupportedConnection` / `requireSshTarget` (`electron/remote/client/connection.ts`), an `UNSUPPORTED` refusal naming the capability. The store key is read tolerantly: a record saved by a development build with the old `sshTarget` string is read as an ssh connection and written back in the new shape on the next change.
- **System `ssh` only** — no SSH library, no new npm dependency, and no separate bridge binary on the host (the stdio bridge below is a mode of the host's own Daintree). `SshTransport` (`electron/remote/client/sshTransport.ts`) runs the user's own `ssh`, so `~/.ssh/config`, agents (1Password, Secure Enclave keys) and Tailscale SSH apply unchanged; nothing overrides identity, host-key or agent settings. The binary is `ssh` from PATH unless `DAINTREE_SSH` names an absolute path to run instead (`sshExecutable.ts`; scp gets the same binary through `-S`); PATH alone can't choose it, because startup replaces PATH with the login shell's, where macOS's path_helper puts `/usr/bin` first. Every call uses `BatchMode=yes`, `ForwardAgent=no` and `ForwardX11=no` (Daintree opens sessions on its own, so the user's interactive forwarding never rides along), and one `ControlMaster=auto` connection per host (`ControlPersist=10m`, `ControlPath=<userData>/rh/cm3-%C`, or a short per-target hash when `%C` would overflow `sun_path`; the `cm3-` prefix changes whenever the options a master starts with change, so a master an older build left running (a `cm2-` one, say) is never reused), plus `ServerAliveInterval=5` and `ServerAliveCountMax=4` so a master whose connection died is noticed in about 20 s. sshd answers those keepalives even while the host's main loop is stalled, so they are what tells a link its host is really gone (see Reconnect). Calls that may create the master also get `ClearAllForwardings=yes`. A mux `-O forward`/`-O cancel` would otherwise send every forward the user's config declares for that host along with Daintree's own, and ClearAllForwardings would drop Daintree's `-L` too, so those commands name the master by the path `ssh -G` expands and run with `-F /dev/null`. Config forwards still apply in two places: the dedicated `-N -L` fallback used when no master is running, and a mux command whose master path `ssh -G` couldn't print as a plain absolute path (it then names the master the usual way).
- **Connect sequence.** (1) `ssh <target> 'echo; uname -s; id -u; echo "$HOME"'` derives where the host's discovery file lives from its last three lines, so what the user's shell startup files print for a command (a `~/.zshenv` echo, a `~/.bashrc` line above its interactive guard) comes before them; (2) `ssh <target> sh -c '…' sh <discovery file>` prints the file between `@@dt:discovery` marker lines, the only text parsed (`parseDiscoveryRead`), and exits 3 when there is no file, which reads as Host mode off whatever the host's locale; it carries the socket path and token, and the socket path must be exactly the one beside that file and free of `${`, `%` and `:` (ssh expands `${VAR}` and `%u`-style tokens in `-W`/`-L` paths against this machine's environment before sending them, so a path the host chose could read the Shell's environment back out); (3) `ssh -W <remote.sock> <target>` through the master opens one channel to the host socket with nothing sent, and reads the server's answer in ssh's own words (checked on the first connect, and again after a forwarded connection closes having carried nothing); (4) `ssh -O forward -L <local.sock>:<remote.sock> <target>` asks the master to forward a fresh local socket (unique per attempt) to the host socket, falling back to a dedicated `ssh -o ControlPath=none -o StreamLocalBindUnlink=yes -o ExitOnForwardFailure=yes -N -L …` when there is no master; (5) the client dials the local socket and authenticates.
- **Stdio fallback.** A server with `AllowStreamLocalForwarding no` still accepts `-O forward -L` (`-L` binds on this side, and ssh exits 0); what it refuses is each channel through it, so the socket closes with nothing read and the refusal appears only in the master's log. Step 3 is how the Shell sees it: through a master ssh prints `Stdio forwarding request failed: Session open refused by peer`, on its own connection `channel 0: open failed: …` / `stdio forwarding failed` (`isStreamLocalRefusal`; OpenSSH words a missing socket the same way, and the bridge then reports that). Refused, the link runs over `ssh <target> -- <command> --attach-stdio` through the same master (`buildAttachArgs`), where `<command>` is the argv the host published in its discovery file (`command`: its executable, plus its app folder when unpackaged), and a `createCommandStreamTransport` carries the link over that ssh's stdin and stdout. Only a refusal counts: an ssh without `-W <socket>` support or a check that times out keeps the forward. A socket path ssh would read as forwarding syntax (a home folder with `:`, `${` or `%` in its name) goes straight over the bridge, which never names the socket to ssh, and is refused only when the host published no command to run. TCP port forwards still go through the master with `-O forward`.
- **Command stream transport.** `createCommandStreamTransport(spawn)` (`electron/remote/client/commandStreamTransport.ts`) runs a command per connection attempt and uses its stdio as the link. The bridge's first line is a preamble, `daintree-attach 1 <token>`; lines before it (a shell startup file printing to stdout) are skipped, up to 64 KiB, and a command that exits first is reported with its own stderr. `ChildStdioDuplex` is the stream the link reads and writes: writes complete only once the child's stdin took them, so its own high-water mark is the link's backpressure, reading pauses the child's stdout, and letting go closes the child's stdin and stops the child only if it hasn't exited 2 s later. `LinkTransportConnection.socket` and `LinkSession` take any Node `Duplex`, so a socket and a command's stdio are the same to the link.
- **The attach bridge.** `daintree --attach-stdio` (`electron/remote/host/attachStdio.ts`, pure Node; the CLI mode is `attachStdioCli.ts`) reads this build's discovery file (`hostLocation()`), connects to its own socket, writes the preamble and pipes stdin and stdout to the socket byte for byte, with `pipe()` backpressure both ways. It exits when either side closes (the host closing, or its stdin ending plus a 2 s grace for the host to close), with exit codes that say what was observed (2 no discovery file, 3 the socket refused). The entry point (`electron/bootstrap.ts`) dispatches it before boot migrations, the store and `main.js`, so it never touches state the running host owns and never takes the single-instance lock (which would make it a second instance handed to the running one as a launch); it runs nothing else: no window, no logger, no backend. Its console goes to stderr since stdout carries the link; it hides from the Dock and, on Linux without a display, uses headless Ozone like `--host-mode`. It needs a running host and works beside it.
- **A master is open to this user.** While a master runs (and for ControlPersist's 10 minutes after its last use), any process running as this user on this machine, local agents included, can open sessions to the host through its control socket without a fresh authentication prompt (a 1Password, Secretive or FIDO confirmation happens once, when the master starts). That is how ssh multiplexing works; the control folder is 0700, so other users can't.
- **Masters close at quit.** ControlPersist keeps a host's master across reconnects while the app runs. Every master this process used (the link's, setup's) is recorded by control path, and `stopRemoteHosts` runs `ssh -O exit` for each, together, 1 s apiece, after the port forwards and links are cancelled on them, so no ssh outlives the app.
- **Host socket.** macOS: `app.getPath("userData")/host.sock`. Linux: `/run/user/<uid>/daintree/host.sock` (`daintree-dev` for unpackaged builds), derived from the uid rather than `$XDG_RUNTIME_DIR` because minimal SSH sessions often don't export it; a missing `/run/user/<uid>` fails with a clear error. `hostSocketPath.ts` also derives the same location from the client side, and asserts the path fits `sun_path` (104/108 bytes).
- **Discovery file.** `host.json` next to the socket carries the socket path and a per-launch 32-byte token (64 hex). Written atomically 0600 (`wx` + rename) into a 0700 directory, and removed at shutdown only if it still carries this launch's token (claimed by rename, re-read, linked back if a newer launch owns it). Tokens are compared timing-safe.
- **Direct transport.** `createDirectTransport` (`electron/remote/client/transport.ts`) dials a Unix socket path directly, from a `{socketPath, token}` or a discovery file. Tests and the integration harness use it instead of ssh.
- **Reconnect.** `LinkClient` reconnects with capped, jittered exponential backoff, presenting its previous session id; `HostServer` resumes the session (same id, `resumed: true`) if it comes back within the 10-minute grace with the same client id and the resume secret that session's last WELCOME carried (32 random bytes, new on every WELCOME, compared in constant time), or the one it resumed with until the Shell sends anything on the resumed session, so a WELCOME lost on its way doesn't strand it; the session id itself appears in lease and summary records every Shell sees, so it alone resumes nothing. A HELLO claiming the client id `local`, which names the host's own windows to the lease, is refused. A fresh session whose HELLO names a Shell install (`deviceId`) ends that install's parked sessions at once (`HostServer.supersede`, cause `session-replaced`): a relaunch or a crashed launch can't resume them, and held for the grace they would keep their views' drive leases and the assistants pinned to them (#13909). An attached session of the same install is left alone, since it may be another launch sharing that id, and a resume ends nothing. A version mismatch stops retrying; an unreachable host reports what was observed (ssh's stderr, the rejection, the last-heard time), never a guessed cause. A link hears its peer whenever any bytes arrive, not only when a frame completes, so a frame larger than the idle window's worth of a slow link (a terminal snapshot at 8 KiB/s) is neither cut off nor called quiet halfway. A connected link that has heard nothing for 7 s carries `quietSince` (the host chip reads "no reply") until the next frame. Silence alone doesn't end a link, because the host answers pings on its main loop and a host paging under memory pressure can miss them for a minute and catch up (#14366): a host that is really gone ends the link through its transport (the process exiting closes the socket; a dead connection ends ssh through its keepalives). The idle timeout is only a 2-minute ceiling for a host stuck for good; it is judged after the loop has polled for input, so a side whose own loop stalled reads what arrived meanwhile before calling its peer silent, and it closes without a GOODBYE, so the host parks the session for resume rather than ending it. When a link closes, it reports connecting at once, before the old forward's release, which a stalled master can hold. A "Host mode off" answer from a host heard from within the last 2 minutes (`HOST_RESTART_GRACE_MS` in `LinkClient.ts`) still reads as a restart, since the host removes `host.json` on the way down and writes it again on the way up, so it is retried rather than parked.

## The link

One multiplexed byte stream per session, framed in `electron/remote/link/frames.ts`: `u32 bodyLength | u8 lane | u8 kind | u32 streamId | payload` (10-byte header, 16 MiB max frame, reassembled by a bounded `FrameDecoder` that returns copied payloads).

- **Lanes and priority.** `CONTROL > INTERACTIVE > RPC > EVENTS > BULK` (`LANE_PRIORITY`). `LaneScheduler` (`scheduler.ts`) serves at most `INTERACTIVE_BURST_FRAMES` (32) interactive frames, or `INTERACTIVE_BURST_BYTES` (128 KiB) of them, whichever comes first, back to back before letting one waiting lower-lane frame through, so RPC can't starve: terminal output comes in 64 KiB+ batches, and on a 2 MiB/s link 32 of them held a request's answer for seconds (p95 8.8 s with one flooding terminal, 1.1 s after). Each lane has header-inclusive byte and frame caps; the hard cap is absolute (a refused frame never gets a drain callback) and drain callbacks fire at half high-water. Bulk payloads are cut into 64 KiB chunks (`BULK_CHUNK_BYTES`) so keystrokes interleave with uploads. Within a lane, frames enqueued under a flow key take turns a frame each and stay in order within their flow; each terminal's output (`TERMINAL_OUT`, `TERMINAL_RESET`) is its own flow (`terminalFlow`), everything else shares one. The host's `TerminalStreamBridge` holds a terminal back from a busy interactive lane only while that terminal already has frames waiting in it, so an echo beside other terminals' floods goes straight in and leaves next: with eight host terminals flooding, a keystroke's echo in a ninth went from ~258 ms to ~12 ms (p50) on a LAN host.
- **Encoding.** `encoding.ts` is a bounded tagged binary encoding (Uint8Array, undefined, Map/Set/Date/bigint/Error, lone-surrogate-safe strings, decoded in bulk) with caps on depth (64), size (64 MiB), container length (1M), total nodes (2M) and bigint digits (1024); no prototype pollution, and decoded Errors never carry a local stack. Errors that leave a process have every absolute path and pattern-known secret scrubbed (`transportSafeError.ts`), and a push on a channel nobody classified never reaches a remote view.
- **Messages** (`messages.ts`, validated by zod in `schemas.ts` on send and on receive; an invalid body ends the session with GOODBYE): CONTROL `HELLO/WELCOME/REJECT/PING/PONG/ENDPOINT_OPEN/ENDPOINT_REBIND/ENDPOINT_CLOSE/HOST_SUMMARY/LEASE_CHANGED/GOODBYE`; RPC `INVOKE/INVOKE_RESULT/SEND/REVERSE_REQUEST/REVERSE_RESULT/CALL/CALL_RESULT`; EVENTS `EVENT`; INTERACTIVE `TERMINAL_OUT/TERMINAL_IN/TERMINAL_RESET/WORKTREE_PORT`; BULK `TRANSFER_BEGIN/CHUNK/END/ABORT/ACK`. New features add session-level CALL methods (each module's `linkMethods.ts`) rather than new kinds.
- **Handshake.** Before HELLO nothing else is accepted: the host reads at most 64 KiB per frame (`HANDSHAKE_MAX_FRAME_BYTES`) and refuses any frame that isn't a handshake kind before decoding it, and at most 16 sockets may wait to say HELLO at once (`MAX_PENDING_HANDSHAKES`); past that a new connection is closed. HELLO carries the token and `HostHandshakeInfo {version, commit, protocolVersion, platform, arch}` from `getLocalHandshakeInfo()` (`electron/remote/handshakeInfo.ts`). Only a different protocol (`REMOTE_PROTOCOL_VERSION`) blocks the link (`isBlockingMismatch`); a different app version or source commit connects best effort, with the difference shown. Platform and arch may differ. A blocking mismatch is a REJECT, surfaced as the `version-mismatch` connection state and `HOST_VERSION_MISMATCH`. Two builds on the same protocol can still disagree on schemas, channel locality or lease policy, so any change to a security contract bumps the protocol.
- **RPC timeouts.** INVOKE has no timeout by default; CALL and REVERSE_REQUEST default to 60 s. A timeout, or a link that drops with a request in flight, resolves `OUTCOME_UNKNOWN` (never a guessed failure).
- **Bulk transfers** (`transfer.ts`): the sender announces size and sha256 in `TRANSFER_BEGIN`; a 1 MiB window with an ack every 256 KiB; a receive cap of 4 GiB and 8 concurrent transfers; 60 s inactivity and 120 s commit timeouts on both sides. The receiver verifies the digest before a sink commits. Sinks register by destination prefix with `addSinkProvider` (`daintree-upload:`, `daintree-bundle:`), so features share a session without overwriting each other.

## Dispatcher and endpoints

- **`IpcDispatcher`** (`electron/ipc/dispatcher.ts`, `getIpcDispatcher()`) holds every invoke and send handler, transport-independent. `ipcMain` feeds it for local views through the existing `security.ts` sender validation; the host's `SessionHost` feeds it for remote endpoints through `invokeForEndpoint` / `sendForEndpoint`, which return the same envelope local IPC gets.
- **`ClientEndpoint`** (`electron/ipc/endpoint.ts`) is who a handler is talking to: `{endpointId, clientId, projectId, kind: "local-view" | "remote-view", handle, send(frame), request(method, payload, opts), onClose, isClosed}`. `handle` is the WebContents id for a local view and a negative number for a remote one, so it never resolves through `webContents.fromId`. `send` pushes events; host→Shell questions (MCP dispatch, plugin prompts, consent, clipboard) go through `request()`, where the endpoint owns correlation, timeout and abort, and settles pending requests with `HOST_DISCONNECTED` on close. `IpcContext` carries `endpoint` and `client`; for a remote call `event` and `senderWindow` are null and `webContentsId` is the negative handle, so host code replies through `sendToRendererContext(ctx, …)`, never `senderWindow`. Local endpoints (`electron/ipc/localEndpoint.ts`) are created lazily on first read of `ctx.endpoint`.
- **`EndpointRegistry`** (`electron/ipc/endpointRegistry.ts`) lists every endpoint; the broadcast helpers in `electron/ipc/utils.ts` deliver to remote endpoints from it (project-scoped helpers use `getForProject`). Remote endpoints are `RemoteViewEndpoint`s owned by the session id (`remote:<sessionId>:<clientEndpointId>`), so they survive a dropped link and close only when the session is given up. A Shell that stops reading its EVENTS lane (hard-cap refusal, or over high water for 5 s) has its events dropped and is told to resync once the lane drains; the view gets `resync-required` and refetches.
- **`RemoteRouter`** (`electron/remote/client/RemoteRouter.ts`) is installed on the Shell's dispatcher only on first connect or window switch. For a sender whose view is remote-bound: `host` channels forward to the host and its envelope comes back verbatim; `shell` channels run locally; `hybrid` channels run their registered `HybridSplit`; an unregistered hybrid is refused with `CHANNEL_NOT_REMOTABLE` (never silently local); unclassified channels are refused. Sends follow the same rule except that hybrid sends stay local.
- **Hybrid splits** (`electron/remote/hybrid/`) receive `local(args?)` and `remote(channel?, args?)` legs that take replacement args (so a setter can send device fields locally and host fields remotely) and resolve to unwrapped values; the dispatcher wraps the merged result once. Splits exist for hydrate, boot and app state, `events:push` filtering, project switch and activation, notifications, keep-awake, settings bundles (refused in remote windows), native pickers, clipboard capture, editor/open/reveal, dev preview and plugin install. On the host, a hybrid channel is refused over the link unless a split admitted its host leg with `allowHybridOverLink(channel)` (`admitHybridHostLegs()` in `hostListener.ts`). Link calls also refuse `shell` and unclassified channels and any channel with no context handler.
- **Error envelopes.** Errors cross the link under the packaged-build policy whatever the build (`linkErrorEnvelope`, `electron/remote/link/envelopes.ts`): paths, tokens, stacks, cause and free-form context are stripped; `code` and allowlisted `details` (`AppErrorDetails`, currently the plugin host errors) survive to the renderer.

## Channel locality

`electron/ipc/channelLocality.ts` classifies every channel as `host` (the work: projects, terminals, git, files, agents, plugins, forge, MCP, persistence), `shell` (the machine you're at: windows, menus, theme, keybindings, sound, native notifications, updates, voice, browser surfaces) or `hybrid` (needs a split). `CHANNEL_LOCALITY` is total over `ChannelName`, so an unclassified channel fails typecheck; `EVENT_LOCALITY` covers event-only names; `NAMESPACE_LOCALITY` gives the Remote Hosts namespaces by prefix; dynamic `plugin:{id}:{channel}` is `host`. `getChannelLocality` returns `"host" | "shell" | "hybrid" | null`. `npm run check:channel-locality` (part of `npm run check`) fails on any channel string registered outside `CHANNELS` that isn't classified. A new channel needs an entry here as well as in `CHANNELS`.

The `mcp:` request/response bridge and the plugin prompt and consent bridges are `shell` although the work is host work: they join a machine's main process to its own views, and a host reaches a remote view through the link's reverse requests, which that view's Shell answers over them.

## Terminal and worktree streams

- **Host.** `TerminalStreamBridge` (`electron/remote/terminal/`) connects each remote endpoint to the pty-host as a synthetic window (the negative handle is the port holder id), so it gets the same batching, project filtering and ack-based flow control as a local view. Output is stamped `{incarnation, seq}` (incarnation is the PTY's launch generation) and kept in a bounded per-terminal ring (4 MiB each, 64 MiB host-wide `RingBudget`, at most 4096 streams, dead terminals swept). While the Shell is attached acks are end to end; while it is away the bridge acks for it so no PTY stalls. A Shell past about 1 MiB unacked on one terminal, 8 MiB across the endpoint, or silent for 2.5 s is dropped to a snapshot resync. Input, resizes and acks are accepted only for terminals the endpoint's project owns; input and resizes also only from the driving endpoint (acks from any attached endpoint, so a watcher never stalls a PTY). A resuming Shell whose position the bridge can't vouch for (the host's listener restarted, or the stream was retired) gets a snapshot reset for any terminal its project still owns, so nothing emitted while no bridge existed is silently missing.
- **Replay.** On reconnect `ClientTerminalRelay` asks `terminal.resume` with `{incarnation, lastSeq}` per terminal; the host replays from the ring, or sends `TERMINAL_RESET` with a full snapshot (cols, rows, serialized state) when the ring no longer covers the gap or the incarnation changed. The snapshot boundary is fenced in the pty-host (`serialize-fence`), so output is never lost; a tiny duplicate at the boundary is possible. Snapshots over 8 MiB reset to a cleared screen. The renderer treats a reset as a restore with the snapshot's geometry and bumps a per-terminal ack generation so stale write callbacks can't ack new data.
- **Shell.** The client installs a port override (`installClientTerminalPortOverride`) that hands a remote view a `MessageChannelMain` through the same `terminal-port-token` / `terminal-port` messages `portDistribution.ts` uses, so the renderer's port API is unchanged. The relay advances `lastSeq` only after posting to a live renderer port, holds refused input in order (bounded by bytes and count) and retries it when the link is writable.
- **Worktree port.** The worktree RPC port is bridged the same way over `WORKTREE_PORT` (`electron/remote/worktreePort/`); requests are validated against a complete per-action schema, any `rootPath` must resolve to the endpoint's project, and the host bridge retries (250 ms to 5 s, 40 tries) until the workspace host is ready. While a view holds no worktree port (cached, reloading, or given none by a new session), its relay sends the host `{type: "view-port", open: false}` inside `WORKTREE_PORT`, and the host bridge stops forwarding that endpoint's workspace events (replies still go) until `open: true` or any request from the view arrives; the relay sends `open: true` from `setRendererPort`, before the view holds its end, so it is ordered ahead of the returning view's refetch, and retries a report the full lane refused when the link drains. Each session starts with events flowing, and an older host fails the id-less message's request check and ignores it.
- **Recovery with no window on the host.** Worktree Retry and restart from a remote view act on the endpoint's project: restart restarts that project's workspace host; Retry reloads it through the same host activation a switch runs, connects the endpoint to the reloaded host, then asks the view's Shell (`worktree:redeliver-port` reverse request) to post the view a fresh relayed port and waits for the renderer's receipt, as a local Retry does. The receipt channel (`worktree:port-ack`) is `shell`: it confirms a port this machine posted to its own view.

## Operations

Long-lived mutations (push, clone, CopyTree, project moves, uploads) carry a client-minted `opId` (`OperationId` in `shared/types/remoteHosts.ts`). `OperationRegistry` (`electron/services/operations/`) dedups by opId, ties an id to its kind, scope, project and a request fingerprint (reuse for a different request is `VALIDATION`), reports progress to the operation on `operations:event` (at most every 100 ms), and retains settled outcomes for 10 minutes (up to 200; 64 running; 32 aliases per operation). A remote caller sees and cancels only its own project's records. The renderer mints an opId only in a remote window (`mintRemoteOperationId`), so local calls take the old untracked path. Worktree creation is one of them: `worktreeClient.create` names the create in a remote window, the host records it as a `worktree-create` operation with its stages as progress, and a create whose answer was lost is resolved by id before any retry is offered.

A request whose link dropped mid-flight is `OUTCOME_UNKNOWN`, not a failure. The client resolves it with `operations:get-status` once reconnected (`resolveUnknownOutcome`, `runHostOperation` in `src/hooks/useHostConnection.ts`) before showing anything; the UI says "Checking with <host>…" meanwhile. "Push, then continue" is the same idea over the project link: the source host keeps each push's outcome by opId (`HostPushRecords`, 10 minutes, host-wide so a fresh session can ask), and a push whose answer was lost is looked up with `projects.push-status` once the link is back. A push the host stopped because its link closed is `interrupted`; with no settled record the Shell asks the host to observe (`projects.push-observe`: the branch tip and the remote's tip from `ls-remote`) and reports what it saw (`push-unconfirmed`) unless the remote already has the tip.

## Drive lease

One endpoint drives a host project at a time. Every attached view watches its terminals live, since terminal output streams to all of them, and follows the driver's panels by reading the host's saved state back rather than by mirroring: after the driver's terminal-layout and tab-group saves (`electron/ipc/handlers/terminalLayout.ts`) and a confirmed terminal spawn, `DriveLeaseService.notifyPanelsChanged` sends the project's watching views one coalesced `panels-changed` event (`PANELS_CHANGED_DELAY_MS`), and each runs a follow pass (`useHostConnection`) that re-reads the host's terminals and then its saved project state (below), as it also does when it starts watching. Watching views also follow where the driver is: the driving view reports its navigation (`drive-lease:report-navigation`, sent from `src/store/hostDriverNavigation.ts`, and only from a view that drives under the lease it names). That navigation is the active worktree, the focused grid or dock panel, focus mode (the hidden worktree sidebar) and a maximized panel or tab group. The host keeps the latest in memory per project and sends watchers one coalesced `navigation-changed` event (`NAVIGATION_CHANGED_DELAY_MS`). It also carries the navigation on every lease view as `driverNavigation`, so a view that starts watching or takes over begins from it. A watcher applies it without persisting: the worktree first, then focus mode, the maximize (checked against that worktree's grid) and the focused panel. An id it doesn't have yet is skipped, and a follow pass applies the newest navigation again once it has adopted the driver's panels. Overlays, scroll position and per-screen state (zoom, panel sizes, sidebar widths, theme, the column count to restore on unmaximize) are never followed. A takeover reads the project back, moves to the previous driver's navigation, and only then reports its own. The navigation is not saved: after a host restart, watchers fall back to the saved state until the driver next moves. `DriveLeaseService` (`electron/services/DriveLeaseService.ts`) arbitrates on the host. A `DriveLeaseHolder` carries a monotonic `leaseId` (work stamped with an older lease is stale after a takeover) and the one `endpointId` that drives. That endpoint is the target of MCP reverse dispatch and plugin prompts, and the only source of terminal input and resizes: the bridge drops input from non-drivers, the pty-host enforces a lease table (`set-drive-leases`) on port writes and resizes, and `electron/ipc/handlers/terminal/io.ts` gates the IPC paths, refusing submit with `DRIVEN_ELSEWHERE`. The resize lease follows the drive lease, so a watching view draws each terminal at the PTY's grid instead of its own pane's: `TerminalInstanceService` holds every pane's geometry while the lease snapshot says another endpoint drives, seeds the grid from each terminal's live `ptyCols`/`ptyRows` (`terminal.getInfo`) and follows the driver's `terminal:resize-result` echoes, and an oversized grid is clipped by the host element rather than reflowed. Taking the project over releases the holds and re-fits every pane in one resize pass, which then resizes the PTY. A Canopy panel reading the host from another machine sizes the terminal it shows as a local panel does, while its machine may type into it (#14497), and only when the host's watch answer says `holdsSize`, so an older host is never asked: the host publishes the terminals such a panel holds (`terminal:canopy-size-holds-changed`, hydrated by `canopy:get-size-holds`), its own views hold those panes at the PTY's grid as a watching view does, and when the panel lets go (another run, Canopy closed, the link dropped) or loses the drive, the PTY gets its own pane's size back and the panes re-fit. The same lease gates project mutations in general: `CHANNEL_LEASE_POLICY` (`electron/ipc/channelLeasePolicy.ts`, total over the host and hybrid channels, so a new one must declare it) marks each channel `free` (reads, attachment, host-wide settings, taking the lease), `driver` (worktrees, git, terminal lifecycle, the saved layout and drafts, project settings) or `handler` (terminal input, gated per terminal in `io.ts`). The dispatcher refuses a `driver` call from anyone but the holder with `DRIVEN_ELSEWHERE` (`createDriveLeaseGate`, installed by Host mode): every link call from a remote view, and a host-locality call from this machine's own views; a local view's hybrid call carries this machine's fields too and is not gated, nor is the viewless executor, which acts where MCP routing already consulted the lease. The worktree port carries the same rule for a remote endpoint: its mutating requests (`requiresDriving`: create and delete a worktree, setting the active worktree, which the host saves and the driver's window follows, resource actions other than `status`, lifecycle setup and approval, environment switch) go through only while the endpoint holds the lease or nobody does. A watcher can't set the active worktree itself; its selection follows the driver's navigation instead. A clone or worktree placement started over the link can be followed and cancelled only by the session that started it (`HostOperationOwners`, host-wide: an id is claimed once the host accepts the start, a refused start claims nothing, a running operation's claim is never evicted, and ownership follows the work, so a start the registry folds into another session's running operation owns nothing of it); a Shell back on a fresh session sees its earlier operation as unknown. Over IPC, the project's driver may cancel an operation in that project whoever started it, as the lease gives it. Over IPC, a remote view sees and cancels only its own project's operations, and one with no project sees none.

A remote view is also held to its own project on reads that name a target by argument (`CHANNEL_REMOTE_SCOPE`, `electron/ipc/channelRemoteScope.ts`, gated in the dispatcher beside the lease): terminal snapshots and replay, agent subagent lists and transcripts, Codex session lookups, diff images, git history, diffs, status and project pulse, branch lists, remotes, dev-preview state (by project or worktree), and `git:mark-safe-directory` (which also allows a folder in no project, since it recovers an add that failed before the repository became one), each traced through the host's own records as the lease traces its targets. A path two projects own (a worktree of one kept in the other's folder) is either's. A terminal of another project, one that exists with no project, or an id a handler would trim into another is refused; an id with no record passes, since a restore names terminals that have gone. A Codex session search for a pane's folder in another project is refused too, so a pane moved between projects searches from its new one. Semantic search over terminal buffers returns only the view's project's matches. An untracked file's diff shows a symlink as its target path, as git does, and refuses a file reached through a linked folder, so a diff can't read outside the worktree. This keeps a view to its project; it is not a wall between Shells, each of which holds the host user's token. Inventories stay host-wide (terminal lists and info, for the processes list; project lists, settings and saved state, for the switcher; run history), and reads are not lease-gated: any attached Shell can watch a project another drives.

Reading the lease never gives it to anyone new: `getHolder` and every read built on it (the metrics sampler, the fleet check, `drive-lease:get`) only start or stop a departed holder's grace, or move a held lease on to the holder's own client or install (below). Only a change in who is attached grants a lease nobody holds, so a project only the Host's own windows show is held by nobody and all of them drive it. Opening a host's project takes it over unless another machine drives it or someone is using the Host's own screen on it, and only from the holder the view read: `drive-lease:take-over` with `ifLeaseId` grants only while the lease is still that one, so two Shells opening at once can't take it from each other; a refused claim leaves the view read-only. The Host's screen is in use while the project is the active view of a focused window and the person there isn't away (`readUserPresence`); the lease view reports it as `hostScreenInUse`, the opening view skips its claim, and the Host refuses a conditional claim on its own as well, so an older Shell can't take it either (a project nobody holds then goes to that window). Takeover is explicit and visible on both screens: the driven-elsewhere banner (`src/components/Recovery/DriveLeaseBanner.tsx`) names the driver, says this view is read-only, and offers Take control, on the host's own screen too. A holder whose link drops keeps the lease for a 15 s grace (`DEFAULT_DRIVE_LEASE_RELEASE_GRACE_MS`), cancelled by a resume. While a holder is away, another window of its client carries on driving at once. So does an endpoint of the same Shell install on a new launch once the holder's endpoint is gone for good (closed, its session ended, or a reservation restored after a host restart): the lease keeps the `deviceId` its holder's HELLO named, host-side only and in the reservations file, so a quit and relaunch takes back its projects with no read-only gap (#13909). A holder still there, or one whose link merely dropped, is never taken from this way, so two launches sharing an install's id still arbitrate per endpoint and a resume inside the grace keeps the lease, and when a grace runs out the lease goes to the holder's own client or install before anyone else; a Shell that names no install, or another install, waits out the grace or takes control. This machine's own windows drive together whenever the local client holds, exactly as before, and a project no remote client touches is never arbitrated; `peekDriveLeaseService()` keeps local-only apps from ever consulting it. After taking over, and after a fresh session (`resync-required` with `reconnected`, or a reconnect after an explicit disconnect), the view reads the host's saved project state back through `app:hydrate` (`src/store/hostProjectRehydrate.ts`): panels it lacks are added (never a terminal, which the terminal resync adopts only if it is running), and nothing live is closed. After a takeover, or while another screen drives, the host's order, tab groups, active worktree and drafts win, and the driver's reported navigation wins over the saved active worktree; the driver back on a fresh session keeps what it changed while away and only fills gaps.

## Host bootstrap and Host mode

- **Windowless backend.** `startHostRuntime` (`electron/boot/hostRuntime.ts`, `hostBootstrap.ts`, `hostServices.ts`) brings up global services, IPC, the pty-host, the workspace pool, MCP and the plugin host with no `BrowserWindow`, using the same once-only starts as the window path. A `--host-mode` launch is windowless; on Linux with no `DISPLAY`/`WAYLAND_DISPLAY` it also appends `ozone-platform=headless` and `disable-gpu` (`electron/setup/environment.ts`). Closing the last window doesn't quit while Host mode is active, a second instance with no live window opens one, and a second `--host-mode` launch hands off to the running process and starts it listening without a window. `--enable-host-mode` (host setup from another machine, on this launch or handed off) switches Host mode on through the same path as the Settings switch, with start at login, and runs the keychain preflight. `--host-mode-handoff` only hands its flags to a running Daintree: with none running it exits (code 3) instead of becoming the backend, so setup can use it from an SSH session.
- **`HostModeService`** (`electron/remote/host/HostModeService.ts`, registered by boot as the `hostMode` service) is the "Allow this machine to be a host" switch. On: `startHostListener` (`hostListener.ts`) takes a lock per socket path (`hostSocketLock.ts`), clears a stale socket, binds 0600 in a 0700 directory, writes `host.json`, and installs the session host, stream bridges, file, upload, port, project, plugin and metrics services and the MCP drive-target resolver. Off: the socket closes, every Shell's session drops, `host.json` goes, and the start-at-login unit is removed. Quitting stops listening but keeps the setting. Once it has been switched or listened, the service records the saved setting, start at login (installed, or the host's own error), the keychain check and the build it runs in `host-mode.json` beside the socket (`hostModeStatusFile.ts`), which setup reads back over SSH without a link.
- **Start at login** (`startAtLogin.ts`), only with explicit consent: a Daintree-owned LaunchAgent on macOS, limited to the Aqua session (a login item can't pass `--host-mode`), and a Daintree-owned `systemd --user` unit on Linux (enabled, not started, with `loginctl enable-linger` shown for the user to run). An AppImage running without FUSE (`APPIMAGE_EXTRACT_AND_RUN=1`) keeps that variable in its unit. When the updater installs a versioned AppImage under the new version's name (`host/appImageRelocation.ts`), the unit's program follows it during the install, and at the next launch a unit left on a versioned AppImage gone from the running image's folder is pointed at the running one; the build marker beside the image moves with it (emptied) and is rewritten by the build that starts from it, unless the image changed after that build started. Removal deletes the file and disables the unit and never unloads a running job, which may be this process.
- **Advertise** (`advertise.ts`): `_daintree._tcp` via `dns-sd -R` on macOS or `avahi-publish-service` on Linux, advertising the SSH port with a TXT record of platform and architecture only (never the build). It has its own switch, **Advertise on this network** (on by default; `hostMode.advertise`), for networks the person doesn't trust; names found by discovery are shown as plain text beside their SSH target. `NSLocalNetworkUsageDescription` and `NSBonjourServices` are in the macOS plist.
- **Keychain preflight** (`keychainPreflight.ts`) checks whether plugin secrets can be stored, using async `safeStorage` under a 10 s timeout, so a keychain that doesn't answer reads as unknown, never a hang. A headless Linux host reports no keyring and plugin secret fields say so.
- **Power.** `setAttachedFrontendCount` in `PowerSaveBlockerService` keeps a host awake, within its keep-awake and battery settings, while agents work or a Shell is using it: a Shell counts only while it has a view open on the host and has used it (opened a view, moved one to another project, typed in or resized a terminal) within the activity window, 5 minutes by default (`SessionHost`). A link with no view never counts, and an open window stops counting once its last use expires.
- **Adding and updating hosts** (`HostSetupService`): discovery from `tailscale status --json`, `netbird status --json` and dns-sd/avahi (a missing tool is an empty list), a `BatchMode` probe (platform, installed build read from the build marker, Host mode status and `host-mode.json`; whether the host matches this machine's build is decided by the build a live listener recorded there, since that is what the handshake meets, and by the installed build only when nothing is listening, start at login on disk, keyring presence, linger, FUSE), and install/update as a tracked operation (`hostInstaller.ts`): same-platform bundle push or host-side fetch of the client's exact build from the client's release channel, falling back to downloading it here and copying it over when the host can't reach the feed. A download is checked against the sha512 the feed's update manifest lists before anything opens it (the host's own fetch with `sha512sum`/`shasum` on the host; `curl -q --proto =https --proto-redir =https`, or `wget --https-only --max-redirect=0`, which falls back to this machine's download if the feed ever redirects; `umask 077`). A build the feed lists no checksum for is refused rather than fetched unverified: anything but its current release. The Linux manifest lists the .deb beside the AppImage, so both are checked against the feed's sha512 (a release published before the manifest listed its .deb has none, and a host on the deb is then told to update it itself). A fresh Linux host gets the AppImage by default and a host already on the deb keeps it, since an AppImage beside the deb would install and never run. This machine's own downloads of a build or a manifest follow redirects by hand, refusing any hop that isn't https. A feed that can't be read is reported as that, not as a missing build. Every copy's sha256 is checked on the host; staging is 0700 until the build checks out; a downloaded Mac build must meet this machine's own Developer ID requirement (a Developer ID Application certificate chained to Apple with this machine's team as its OU, not just a TeamIdentifier field) when this machine is a signed build, and otherwise be validly signed and accepted by Gatekeeper (a copy of this machine's own bundle needs neither, and a failed look at this machine's own signature stops the install); the deb command the user is shown checks the package's sha256 before `sudo apt install`; the AppImage on a fresh Linux host and the deb on one already using it, refusal while agents work (or wait until idle), a staged swap with `.old` backups, rollback on a failed start or wrong build, and a handshake check before the backup goes. A host on another build refuses the link but its refusal carries the agents it observed working (`RejectMessage.observed`, only after the token checks out), so "Update when idle" works on exactly the hosts that need updating; unknown stays unknown. Turning Host mode on (`hostModeBootstrap.ts`) launches `open -n … --enable-host-mode` into a Mac's logged-in session; on Linux it writes and enables the same `systemd --user` unit the host writes for itself, asks for `loginctl enable-linger` (a refusal is shown in the host's words; never on a WSL host, see below), starts the unit and hands `--enable-host-mode` over with `--host-mode-handoff`. Success is reported only once `host-mode.json` and the start-at-login item read back as on. Probe, install and bootstrap reach the host only through a `HostCommandChannel` (run a line of `sh`, feed stdin, send a file; `remoteShell.ts`), chosen by the connection's kind, with ssh as the one implementation. Forgetting a host closes its SSH master with `ssh -O exit`.
- **A resource environment's box** (#13742). A resource `status` that reports `"ready"` may name its box's ssh target in an `ssh` field (`{ "status": "ready", "ssh": "dt-feature-x" }`), held to `isValidSshTarget` (`shared/utils/sshTarget.ts`) when it is read in `ResourceActionExecutor` and cleared by a successful pause or teardown. The environment popover then offers **Open on its machine** (`worktree.resource.openOnHost`, `src/components/Hosts/resourceHostHandoff.ts`), behind a confirm, on a Shell that reaches hosts over ssh and from a window on this machine. It probes first and adds nothing ssh can't reach. A host already in the list for that target is used as it is; otherwise one is added carrying `ownerWorktreeId`. With a live listener it connects straight away, skipping install and Host mode setup, since a box without `systemd --user` never confirms start at login; without one, Settings → Hosts opens that host's setup. Placement is the ordinary switch dialog on the worktree's own branch. `watchOwnedHostCleanup` (`ownedHostCleanup.ts`) removes an owned host through `RemoteHostsClient.forget` once that worktree's resource teardown succeeds or the worktree is deleted; re-pointing the host at another machine in Settings drops the owner. The provision script owns the ssh side: a target port or identity goes in a `Host` block the script writes to a file the user's `~/.ssh/config` `Include`s, behind `Match all` when the `Include` is appended, since otherwise it lands inside the last `Host` block. A per-environment `UserKnownHostsFile` that `teardown` deletes lets a box reprovisioned at the same address be trusted again, which `StrictHostKeyChecking accept-new` alone refuses. A script that starts Host mode itself as root passes `--no-sandbox` beside `--ozone-platform=headless`; as another user it needs `/run/user/<uid>` to exist.

## Files and the inbox

- **Host-scoped protocols.** A remote view's previews use `daintree-file://host/<hostId>/<capability>/load?path=…&root=…` (likewise `daintree-media` and `daintree-pdf`), parsed in `electron/setup/protocols.ts`. Local URLs are unchanged. A protocol request has no sender, so main mints a per-view capability (`ViewFileCapabilities`, 16 random bytes, dies with the view; the renderer fetches it through `fileTransfer.getPreviewCapability`); the proxy checks it is live and bound to that host, and the host checks only that view's endpoint, project and lease. Range requests get 206/416. Response headers are this machine's, as a local preview's would be: the type comes from the scheme and the requested path, with `nosniff`, a sandbox CSP for file and media previews, and for `daintree-pdf` always `application/pdf` with this machine's `Content-Disposition` (as locally, no CSP). The same refusals a local preview makes come first (a non-media path under `daintree-media`, a non-`.pdf` path under `daintree-pdf`). Only a 200 or a 206 is passed on, and only its length and range headers are taken from the host, each checked (one spelling, digits, a range whose bytes add up and match the length, which a range sets when the host gives none); a GET's bytes must arrive as a stream, a HEAD never carries one, and the body is cut off past the announced length or the local preview's size ceiling (512 KB, 25 MB for raster images, 50 MB for PDFs, none for streamed audio and video), or when it ends short. Request, stream and download slots and buffered bytes are reserved before any filesystem work.
- **Containment** (`electron/remote/files/hostContainment.ts`): the walk starts at the project folder or a worktree and opens one component at a time with `O_NOFOLLOW`, serving from the descriptor it ends on. On Linux each step opens relative to the parent's descriptor through `/proc/self/fd` (openat). A symlink is never opened through: its target is resolved against the real directory reached and must land inside the same root, and the walk restarts along it, so in-project links work and escaping ones are refused. Link-side `files:read` / `files:search` require a root inside the endpoint's project or worktrees.
- **Clicked files** (`grantClicked` in `HostFileService.ts`). A file path the person clicks in a remote view's terminal (or opens from a terminal or composer selection's **View file**) can be outside the project: before the viewer asks for it, the Shell sends `files.grant-clicked` for that exact path (`grantClickedHostFile`, `src/services/terminal/clickedHostFile.ts`, skipped for a file inside a worktree), and the host lets that endpoint preview, read and download whatever regular file is at that path, for its current project, for an hour (a click again starts the hour over; 64 per endpoint; gone when the endpoint closes). Held by path, not identity, so a log that grows or a file an editor saves over still refreshes. The grant needs the drive lease and refuses a folder, a missing file or a symlink; reads open the last component with `O_NOFOLLOW` from the file's real folder, and a text read must name the file's own folder as its root, so nothing beside the file becomes readable. A host agent's `file.view` never mints one, so it stays inside the project.
- **Downloads and pickers.** The remote host file picker (`src/components/HostFilePicker/`) lists host directories (2000-entry cap); native pickers are split so the dialog opens on this machine for a host path. Downloads open with `O_NOFOLLOW`, hash and send from that descriptor, and verify sha256 and length before placing the file in Downloads, named for the file that was asked for (never the host's name for it), with control and bidi formatting characters stripped, and on macOS tagged `com.apple.quarantine`, best effort, so Gatekeeper checks it before it first opens. CopyTree copy-as-file downloads the bundle to a private temp dir; the host grants that one exact bundle file to that endpoint for 10 minutes.
- **Materialize.** Every drop, paste and attach goes through `materialize` (`src/services/materialize.ts`): locally it is the identity (paths as given, clipboard images saved to `daintree-clipboard` as before, now 0700/0600); in a remote window the lazy remote materializer uploads bytes and inserts the host path. Uploads read only files the person chose in that window (recorded by the preload's `files.getDroppedFilePaths` over `file-transfer:grant-local-sources` and by the attach dialog, 30 minutes per window).
- **Inbox** (`hostInbox.ts`): `<host tmpdir>/daintree-inbox/clipboard/clipboard-<stamp>-<id>.<ext>` and `…/files/<stamp>-<id>/<name>`, outside every worktree. Directories 0700 and lstat-checked, files 0600 via `O_EXCL|O_NOFOLLOW`, `<id>` is the start of the content's sha256 so the same bytes reuse the existing file, entries expire after 24 h, the newest 50 clipboard images are kept, and the inbox stays under 1 GB. Gemini's include directory follows the host inbox in remote windows.
- **Uploads** (`HostUploadService.ts`): a prepared upload is bound to the endpoint, project, size and sha256; bytes are placed only after the transfer verifies the digest. Over 50 MB asks first (`UPLOAD_CONFIRM_BYTES`), over 500 MB is refused (`UPLOAD_REFUSE_BYTES`); folder upload is not available (the 5,000-file / 500 MB folder caps are declared for it). Retries under the same opId are answered from the host's record (15 minutes, 1,000 entries). **Add to project** (Option/Alt-drop, remote windows only) writes through the containment walk and replaces an existing file only with a single-use replace token the host minted for that exact file, lease and endpoint.
- **Ctrl+V** in an agent terminal of a remote window is intercepted (setting on by default, remote mode only) so the agent gets this machine's clipboard image as an inbox path; plain shells and local windows are never intercepted.

## Port forwards

`PortForwardManager` (`electron/remote/ports/`) keeps one local port per (host, remote port). A forward goes through the host's ControlMaster with `ssh -O forward -L 127.0.0.1:<local>:localhost:<remote>` (`sshForward.ts`), with a local relay holding `[::1]` beside it; with no master it uses a local listener whose connections ride the link as streams (`streamForwarder.ts`, session CALLs `ports.open/data/end/close`, 256 KiB window per stream). The host port number is kept when it is free here. A forward counts only while the session it rides is open; an ssh forward is retired when its session closes and re-added, with a fresh free-port probe, on the next one.

Forwards are made on demand for dev preview and browser panels (the dev-preview proxy asks only the host that owns a preview origin), from **Forward port…** and the Ports view, and for a CLI sign-in callback (a localhost link clicked in a remote terminal is forwarded and opened locally, closing after 10 minutes idle). In a remote-bound view, the webview gate (`electron/window/webviewSrcGate.ts`), guest navigation checks and a per-session request filter admit loopback only for address/port pairs a live forward holds (`isBoundLoopbackUrl` in `shared/utils/urlUtils.ts`); the request filter also resolves every DNS name through the guest session's own resolver (no cache of its own; concurrent lookups for a name share one, and a session with 64 names in flight refuses the next) and refuses one that answers with loopback or an unspecified address, or that fails, answers nothing usable, or takes over 5 s. It also keeps Chromium's Local Network Access rule, which Electron 42 leaves off, for remote guests: a request to this computer's network (private, link-local, ULA or CGNAT, by address or resolved name) goes through only as a top-level navigation or from a document that is itself on that network, judged by the asking frame's effective origin (an about:blank or srcdoc frame asks as its creator) and by where that origin was when its document loaded, never by what its name answers now, so a host's page or an internet page can't load from the LAN or a tailnet, even by rebinding its own name. It records, per guest, a generation that moves with each top-level navigation and whether anything the guest has loaded since it was created came from this computer's network (`guestDocument`); that never clears, since a navigation away can fail and leave such a page up. Browser and dev-preview partitions in a remote window carry the host's id with the project's (`partitionProjectKey`, an injective escape of both, a short hash past 64 characters so the name stays a valid directory, so no two hosts share one), and a portal tab opened from a remote window runs in that host's own portal partition (`remotePortalPartition`, allowed the portal's clipboard writes) with the same request filter and popup rule, never in `persist:portal`.

## Projects across hosts

Projects move between hosts through git, not file copies (`electron/remote/projects/`, `electron/services/projectAcrossHosts/`). The target host matches by normalised remote URLs, checks the branch with `ls-remote`, and otherwise clones as itself under a single-use destination token, into a temp folder renamed into place, then offers a worktree for the branch; an unpushed branch prompts a push first (the preview lists the commits), and a local-only repo travels as a git bundle. Credentials are stripped from remote URLs before they leave either machine. The flow is `project.openOnHost` and the `hostSwitch` namespace, with `projectMatch` on the host.

What the source machine says about the target is checked on the target. Its repository name is one plain folder name (never a path; leading dots dropped). A home-relative path is mirrored only under a folder where code lives (`~/Projects`, `~/code`, `~/src`, the target's own projects folder, …) with no hidden segment, and only if it still is once links in its parents are resolved, so `~/bin`, `~/.config/autostart` and `~/Library/LaunchAgents` are never suggested. A worktree path from the other machine's new-worktree form is used only inside the project or in a sibling named after it (`<project>-worktrees`), else the target's own pattern. A cloned project always gets a fresh identity, so a committed `.daintree/project.json` id never adopts an unavailable local project's settings, sessions or plugin trust. A default setup recipe is preselected only when the source is this machine and only from the recipes it lists, and the recipe the person picked runs on the target only after a dialog there shows everything that decides what it runs (commands, dev commands, arguments, environment and agent prompts, read from the cloned repository) and only if it is unchanged when they answer. The dialog opens the project without a question only when the source is this machine and a person opened it. A bundle carries HEAD (when it names a commit), branches and tags only, never the stash, filter-branch backups or notes, and branch names read back from a bundle are validated and passed after `--end-of-options`.

## Plugins

A plugin's main code runs on the host; its views render in the driving window and their bundles are fetched from the host (`electron/remote/plugins/`, `__dth-<hostId>` paths cached by host, plugin and generation, revalidated on every read). No view file is served to this machine's renderer until this machine says so: `PluginViewGate` (`electron/remote/plugins/pluginViewGate.ts`) holds every file to the exact bundle the person here allowed, recorded as the digest of the host's list of the plugin's files and their sha256 (`plugins.view-manifest`), asked in a native dialog owned by main before the view imports anything (`remote-hosts:prepare-plugin-view`); answers live in `remoteHostPluginViewConsent` and are reset in Settings → Hosts → Plugin views (see `docs/plugins/trust-model.md`). The host serves a view's files only to the window driving its project, so a watching window says so and offers Take control, and loads the view once it has it. A sheet dismissed because its window closed holds no answer. `plugin:invoke` runs on the dispatcher, so a call from a remote view carries `ctx.origin: { kind: "remote", … }`.

- **Person-facing calls** — prompts, toasts, capability consent, clipboard, and `host.dispatch()` and the action catalog — go to the project's driving endpoint by reverse request (`shellRequests.ts`, `hostRouting.ts`). Each call's caller is carried in `AsyncLocalStorage` (and tagged through the dev worker), so interleaved calls from two projects route correctly. A prompt records the lease it was asked under; when the driver changes it is taken down and re-asked, and an approval from a former driver is never returned. With nobody attached a prompt fails with `NO_FRONTEND_ATTACHED` or waits in an opt-in queue, a dispatch answers `NO_FRONTEND_ATTACHED`, and first-use consent is a denial.
- **Account sign-in** (#14111): `plugin:account-connect` is hybrid. The Shell's split notes the sign-in for its view, host, plugin and connection under a fresh id (`expectAccountSignIn`, `electron/remote/plugins/accountSignIn.ts`) and forwards the call with that id appended; the host runs it in `PluginAccountService` with a broker (`remoteAccountSignIn`) that sends a `plugin.account-sign-in` reverse request to the calling endpoint, never the project's driver. The Shell answers it only against that note (the id and its scope must both match, so a superseded click's late request can't claim a newer one), once, and only for a public `https:` code request with an S256 challenge and no redirect: it adds its own loopback redirect, opens the browser here and answers with the code. The host keeps the verifier, accepts only a literal `http://127.0.0.1:<port>/oauth/callback` redirect back, and exchanges and stores the tokens itself. The note and its loopback come down when the call settles, however it ends; a host-side cancel, a newer Connect, Disconnect or unload aborts the reverse request, and a dropped link fails it (`HOST_DISCONNECTED`). Once the code is back the host finishes the exchange whatever happens to the link. `plugin:account-set-token` and `plugin:account-cancel-connect` are host channels.
- **Clipboard** requests need the view's window focused, the view in front, bound to the asking host, and a Shell-owned grant per host, plugin and access, asked once in the capability consent dialog; answers persist in `remoteHostPluginClipboardGrants` (device-owned) and can be reset per host in Settings → Hosts → host (`HostClipboardGrants.tsx`). The host's wait covers the consent dialog's lifetime (`REMOTE_CLIPBOARD_TIMEOUT_MS`).
- **Copy settings** (`electron/remote/settingsCopy/`, catalog in `shared/config/portableSettings.ts`): Settings → Hosts → host → Copy settings pushes this machine's portable settings, by category, over two session CALLs (`settings.copy.preview`, `settings.copy.apply`), so it works with no window on the host. The catalog is a positive list down to fields, shared with Export/Import Configuration; ownership never implies a setting may travel. Credentials, consent and trust, per-project and run state and plugin installs never travel; secrets are withheld on this machine by value and, inside env maps, by name, and the host merges env maps per name and presets per id so its own secret stays. Global environment variables and permission bypass are opt-in and never written to a file; theme and shortcuts are a separate device category, with shortcuts previewed as the host's platform reads them. The host validates and diffs against its live settings and keeps the payload under a per-session ticket with a revision of everything those sections could change; apply writes exactly that payload through the shared config write queue, refuses with `SETTINGS_PREVIEW_STALE` if the revision moved, then reloads the agent registry, menu and services and broadcasts `config-bundle:imported`, which remote windows now accept from the host. A host that predates it answers `UNSUPPORTED`; one that doesn't know a section reports it. The host page also shows, on opening and on Refresh only (`settings.copy.status`, no ticket), how many categories a copy of everything copyable would change, counting the preview's accepted adds and updates so leaves the host would refuse never read as drift, and the last copy the host received: the source's handshake `clientName` (attribution, not identity), when, and the applied and skipped counts per section (#13347). `settings.copy.undo` takes that copy back leaf by leaf under the write queue, latest section first: a leaf still holding what the copy wrote gets its earlier value back (or goes, if the copy added it), and anything changed since stays and is listed. It writes each section from its current value with only those leaves swapped, and recipes change in place in one recipe-queue turn, so nothing added since is lost. The earlier values are kept on the host alone, in an owner-only `settings-copy/last-copy.json` under userData rather than the settings store, so no backup, export or copy carries them; one record, capped at 4 MiB (a larger copy keeps no undo), and its values are dropped once undone. The assistant's agent and terminal behaviour don't travel yet (#13345; terminal settings hydrate once per window).
- **Parity and install-on-host** (`electron/remote/plugins/parity/`, `electron/services/plugin/parity/`): Settings → Hosts → host → Plugins diffs the two machines; Install/Update on host sends this machine's package over RPC chunks and runs the host's normal install path after a platform and blocklist preflight, never downgrading. A missing plugin fails with `PLUGIN_NOT_ON_HOST`; one that can't run fails with `PLUGIN_INCOMPATIBLE` and a reason (`engine`, `platform`, `remote-unsupported`, `untrusted`, `unconfigured`), carried as `details` across the link and the contextBridge. In a remote window, dispatching an unregistered action of a plugin this view saw before, or one the parity diff lists as only here, returns `PLUGIN_NOT_ON_HOST` with the plugin and host (`ActionService.dispatch`). An engine mismatch is reported but the plugin still loads. Nothing syncs automatically.

Site preview drives the dev-preview guest through this machine's CDP, but a remote-bound view's adapter is allowed only when its plugin is loaded on the view's host (asked over the `plugins.parity.loaded` session call), not on this machine.

Author-facing behaviour is in [plugins/host-api.md](../plugins/host-api.md#remote-hosts--when-nobody-is-sitting-at-this-machine), [plugins/distribution.md](../plugins/distribution.md#plugins-on-remote-hosts), [plugins/trust-model.md](../plugins/trust-model.md#plugins-on-a-remote-host) and [plugins/manifest.md](../plugins/manifest.md#remote).

## Metrics, overview and fleet

- **Sampling.** A host samples every 5 s (`HOST_METRICS_INTERVAL_MS`) while at least one Shell is connected, a summary-only link included: CPU %, memory pressure (macOS memorystatus, Linux PSI), memory and swap, thermal, Linux CPU PSI, observed agent counts, project and worktree counts, the driver, installed agent CLIs, and each forge provider's connection as the host's own settings and provider report it (`forges`: credential saved or not, and the account the provider reported; never the credential; `electron/remote/metrics/hostForges.ts`) (`HostMetricsSummary`). Unmeasured fields are null, never zero. Summaries go out as `HOST_SUMMARY` on CONTROL.
- **Summary-only links.** At launch the Shell dials only the hosts whose notifications are on; every other host is dialled when something needs it (a window, a switch, an operation, a forward, the hosts overview). A connected host sends summaries over a host-level connect that installs no router, and the Shell keeps about 15 minutes per host (`HostMetricsClient`, `electron/remote/metrics/client.ts`). A user with no hosts dials nothing. A summary-only session never counts as an attached frontend for power.
- **Hosts overview** (`src/components/Hosts/Overview/`, action `host.overview.open`): a card per host with sparklines, agent CLIs, plugin parity, the Ports view, other hosts' worktrees and least-loaded placement for new worktrees (which hands over through `project.openOnHost`). Its **Add project…** clones a URL onto the host (`clone-url`) or opens a repository already there, picked with the host's own file picker (`open-folder` → `projects.open-folder`): any repository's main folder is registered as it is, with no remote to match, and a folder the host already has as a project is opened unchanged.
- **Cross-host fleet** (`src/components/Fleet/crossHostFleet.ts`): other hosts' agents can be armed from the overview and receive the draft exactly as typed over each host's link. A vacant lease is allowed; one held by another client is refused with `DRIVEN_ELSEWHERE`. Each target submit carries an opId the host keeps for 10 minutes after it settles (`shared/config/fleetSubmitRetention.ts`; at 10,000 live records it refuses new submits rather than forget one). A submit whose answer was lost is retried under the same opId only within 5 minutes of its first send; after that the failure banner says the outcome is unknown, Retry leaves it out, and sending again is a fresh submit the person confirms. Target lists carry `complete`, false when a pty-host shard didn't answer or the list hit its cap, and a watching fleet run only marks a missing target gone on a complete list. Keys typed straight into a pane's terminal never reach them: raw input fans out over this view's own PTYs only, so while any are armed the focused armed pane says how many agents its typing skips, and on which host (`FleetRawInputNotice`), while its composer's Enter still sends to the whole fleet (#14957).
- **Notifications.** A remote window's own host always notifies it: the host detects the event and sends `notification.show` with a category, and the Shell plays its own sound and applies its own session mute. Which events alert the Shell and when are the Shell's (#14701): it sends its on/off switch, its completed and waiting switches and its escalation switch and delay (`notification.policy`, `electron/remote/hybrid/notificationPolicy.ts`) on every session it opens to a host and whenever they change, and the host applies them to what it sends that Shell's views (`AgentNotificationService.settingsFor`), with the host project's own overrides still applied over them, while its own windows keep the host's settings. Quiet hours follow the Shell's clock, so the Shell applies them as notifications arrive: they hold back a completion and keep an attention event to the inbox, and a waiting agent pages through, as it does locally. The Shell's on/off switch and quiet hours are checked before a notice counts against the host's budget. A host from before this answers the policy `UNSUPPORTED` and keeps deciding by its own settings, and a Shell from before it never sends one, so the host still judges for it. The Shell titles a notification with this device's name for the host and strips control and bidi formatting characters from the host's text. Each host has one budget of six notices a minute (`hostNoticeBudget.ts`), shared by these notifications, its plugins' toasts (shown as plain text) and its attention events (whose project and agent names are stripped the same way). Attention events from other hosts are opt-in per host (`HostDescriptor.notificationsEnabled`, off by default), judged by the Shell's own switches and quiet hours, and go to one window, never one already showing that host. A burst of waiting agents, completions or Canopy asks, and a grouped reminder, only ever groups agents whose notifications go to the same machine, and a host's attention reminders cool down per Shell. The all-clear flash a host forwards still carries the host's own verdict.

## Assistant control

A Shell's assistants reach a host through two tools, `host.list` and `host.call` (#13493). `host.list` reports every host the Shell knows, as observed, with each connected host's projects (the `projectId`s `host.call` takes) while the person's per-host "assistant control" switch (`HostDescriptor.assistantControlEnabled`) is on. A controlled host this Shell holds no link to (the idle release lets an unused one go after five minutes) is dialled first, as `host.call` would dial it, and listed as it is once connected or after 8 s; one whose link reported why it is down, or one the person disconnected (until something dials it again), is not redialled. `host.call` runs one of the host's own Daintree tools in one of its projects for the calling assistant, over session-level calls that ride every session, a summary-only one included (`electron/remote/assistant/linkMethods.ts`).

| Method | Direction | Payload | Answer |
| --- | --- | --- | --- |
| `assistant.authenticate` | Shell → Host | the Shell's sender credential for this host | null |
| `assistant.mcp-call` | Shell → Host | `{helpSessionId, projectId, tier, callId, resend, tool, args, runMs}` | `done` with the tool's result, `unknown`, `conflict`, or `refused` |
| `assistant.relay-notices` | Host → Shell | notices a relayed call armed, by `callId` | null |
| `assistant.relay-notice-status` | Shell → Host | the calls whose notices the Shell still awaits, `{helpSessionId, callId}` each | per call `watching`, `settled`, or `unknown` (no record, as after a restart) |
| `assistant.relay-approve` | Host → Shell | one confirm-gated relayed call to put to the person | the decision |

- **Who is asking.** No payload names a sender. Each Shell mints a 32-byte credential per host (`AssistantSenderCredentials`, table `assistant_sender_credentials`) before it first presents it, and a session authenticates with it once. The host derives the sender id as a one-way hash of the credential and binds it to that session and its session id, so neither a resumed transport nor a second call can prove another sender (`hostSenders.ts`, `SenderSessions`). A host admits each relayed call through a real MCP session of its own for that sender and help session, bound to the one project (`hostMcpRelay.ts`), so its tier, grants, ownership, drive lease and audit are the host's own gates. A call runs at most once per `callId` (`RelayCallLedger`); `host.call` answers `ambiguous` for a lost answer, and a resend under the same `callId` never runs twice.
- **This machine's other projects.** `host.list` names this machine first, as `hostId: "local"`, with its projects but the caller's own and no load sample or tally, and `host.call` under `local` reaches them in process, with no link, sender credential or switch (#14024, `localMcpRelay.ts`). Each call is admitted as a host admits another machine's, through the same executor (`mcpRelayExecutor.ts`): a real MCP session for the caller's help session bound to the one project, `external` origin with the `*Owned` tools, ownership under the relay principal `relay\0local\0<helpSessionId>`, at most once per `callId`, and the caller marked `local` by main alone, never by anything a call or link carries. Its standing is this machine's own views': a change runs through a view here that shows or drives the project or, with none, through the host's own form of the action (reads too), and is refused `DRIVEN_ELSEWHERE` while another machine drives it; it never takes the lease (`relayWriteRule.ts`). Its notices and confirm-gated questions come back into the runtime as a host's do, typed into the run that made the call and asked in that assistant's window; a call that runs in the target's own view asks in that view. A call to the caller's own project is refused (`policy_rejected`), since its own tools already reach it. Its sessions and its hold on what it made go when its help session ends, though not on a relaunch onto a new PTY.
- **Project inventory** (#14457). `projects` is a page of at most 50 per host, names cut to 256 characters, and every page across the answer's hosts fits 32 KiB, or less when the hosts' own fields leave less of the answer's 48 KiB, cut from the longest page first; a lone page keeps one project, so a walk always advances. Each host's `projectInventory` is null exactly when `projects` is (the read failed, timed out, or isn't made: disconnected, control off); otherwise it gives `complete` (this answer names every matching project, so a later page of a long list is never complete; a walk to a null `nextCursor` has named them all), `total`, `offset`, `omitted` and a `nextCursor`. `host.list` takes `hostId` to list one host and `projectQuery` (a case-insensitive name match) to find a project past the first page; `projectCursor` continues one host's pages under that host and query, and a call naming another host or query beside it is refused. A cursor holds no list and no authority, only the host, query, offset and a revision of the matching ids (`electron/remote/assistant/hostProjectInventory.ts`); a list that changed since gives its first page again with `listChanged: true`. A host sends at most 2000 projects and says nothing past that, so a full 2000 leaves `total` and `omitted` null and `complete` false: absence there is never proven.
- **Agent directory** (#14160). `host.list` takes `includeAgents` (and an optional `projectId` filter) and then adds `agents` to each host: its workers and Daintree Assistants as one typed list (`shared/types/agentDirectory.ts`, collected passively in `electron/services/agentDirectory.ts`). Role (`worker` or `assistant`) is separate from `agentId`; a live entry's subject is `hostId`, scope, `terminalId` and `incarnation` (the run's launch generation, new when a terminal id is reused), plus the `lane` of a project assistant. A conversation main holds only a resume pointer for is a separate `resumable` entry with no terminal or incarnation, and a live lane wins over its own pointer. Each host's `coverage` is `ok`, `stale` (a failed read answers with the last directory under its original `observedAt`), `unreachable` (no link and nothing known, or a control gate is off) or `unsupported` (a host from before remote reads); `complete` is false when a pty shard did not answer, and `omitted` counts entries cut by the 256-entry and 48 KiB budgets, so only `ok` with `complete` and no `omitted` may be read as "nothing else runs". Entries carry no terminal text, paths or handback text, grant no authority, and assistants stay out of the fleet, worker and plugin listings. No global-scope entry exists until a global session does. A remote host's directory (#14455) is read over the session-level `assistant.agents` method, which the host answers from its own directory under its `acceptRemoteControl` consent and the Shell asks only while its own control switch for that host is on; the Shell rewrites `hostId` to its id for the host, keeps the last read per host and filter as the `stale` fallback (forgotten on refusal, control off or removal), and shares the 48 KiB budget across every host's directory in the answer. It opens no MCP session there and borrows nothing from Canopy viewers; with no hosts nothing is read.
- **Link, build and CLIs** (#14461). Each `host.list` entry keeps the old `connection` enum and adds `link`, `build` and `agentClis`, projected in `electron/remote/assistant/hostObservations.ts`. `link` copies the flags the link itself set (`status`, `attempt`, `restarting`, `hostModeOff`, `stoppedRetrying`, `quietSince`, a build `mismatch`) plus `disconnectedByPerson`, so a host the person disconnected, one not listening in Host mode, one that stopped retrying and one on another protocol no longer read alike; an unreachable link's `detail` is raw transport text and never leaves the Shell. `build` is the handshake the link is talking to (`connected`), the one it refused (`rejected`), the descriptor's last one (`last-seen`), or `unknown`; `local` reports none. `agentClis` is the host summary's installed CLIs, capped at 32 with the rest counted in `omitted`: `observed` only on a live link with a sample inside the load's staleness bound, `stale` otherwise, and `unknown` with no summary or an empty list, since a host that hasn't run detection yet reports none. It is binary presence only and never a sign-in, quota or readiness verdict. Nothing new is sampled, dialled or polled to fill these fields.
- **Delegating to a host's assistant.** There is no inbox: a Shell's assistant talks to a host's assistant the way it talks to any agent, through `host.call` (#13496). `assistant.list` finds the other assistants in the call's project with their terminal id, run `generation`, observed state and whether the caller started them; `assistant.start` starts one in a vacant slot with no view, past its folder-trust question for its own session folder and no other (`electron/services/assistants/assistantLaunch.ts`), recording who asked on the help session (`HelpSessionRecord.startedBy`) for as long as it runs, and reports one that runs but isn't at its prompt yet rather than letting the caller start another. The rest is agent messaging (relayed, through the `*Owned` forms, which reach an assistant the caller started): `terminal.sendCommand` with `handback: true` and the `generation`, `notify: true` or `terminal.notifyWhenIdle` / `terminal.waitUntilIdle`, `terminal.getStatus`, `terminal.readLastMessageOwned`, `terminal.interrupt`, and `terminal.close` for an assistant the caller started. The same tools work on this machine for its own assistants, within the caller's project.
- **Assistant targets.** Assistant terminals stay out of every generic terminal path (`isAssistantTerminalRecord`): no grid pane, fleet target, plugin target, journal or listing. The tools above reach one only through main's `AssistantTerminalControl` (`electron/services/assistants/`), which `sessionServer` routes an assistant terminal id to before any ownership ledger or view, for an assistant caller alone: one of this machine's help sessions, or another machine's assistant reaching this one as a relay principal. A worker pane, an api-key client or a plugin naming an assistant's terminal id is answered as if no such terminal exists, on every tool, and the viewless executor refuses one too. Only an assistant in the caller's own project resolves, never the caller itself.
- **Generation, busy and drafts.** A send names the `generation` it was listed with and is refused (`ASSISTANT_RESTARTED`) once that run was restarted or replaced, checked again after the terminal is read, so a prompt for one run never lands in the next. A send to an assistant that is mid-turn, stopped on a question or an error, or has anything typed into its prompt since it settled is refused with its observed state (`ASSISTANT_BUSY`) rather than queued, on a host and here alike (`evaluateWakeGate` with mid-turn input not accepted), and the submission rides the `settled-prompt-strict` guard, which takes no mid-turn input even from a CLI that queues it, so the lane drops it if a person starts typing or another brief starts a turn before it is written. A draft stays the person's; nothing is typed over it.
- **Provenance.** Daintree leads every prompt one assistant sends another with where it came from, "From the Daintree Assistant on <machine>", and frames it as an orchestrator's brief: the receiver's own work, not to delegate again unless the brief says so, with anything it quotes as data. The machine name is this machine's display name, or the relaying Shell's handshake name, stripped of control, zero-width and bidi characters and cut to 80 characters (`shared/utils/assistantProvenance.ts`). The handback instruction follows the brief, so a host assistant that needs the hub ends its turn with the question and the hub's watch sees it waiting. Nothing a host's assistant starts reaches a Shell on its own.
- **Reading a reply.** `terminal.readLastMessageOwned` answers another assistant from its screen, whatever agent it runs, never from a transcript or an agent's own config (`AssistantTerminalControl.readReply`): an `observed` result quoting the screen up to the handback marker its current prompt printed, matched by what the marker said so an earlier turn's never ends the quote, or that marker's summary once it scrolled away, or the latest screen marked `source: screen` before any handback. A Codex assistant's answer reads the same as a Claude one's.
- **Notices.** A relayed call's notices belong to its relay principal, not the link it came in on: a link session that expires keeps them, and they go back to the call's sender over whichever of its sessions is open, a resumed one by its session id or a new one once it authenticates again (`RelayNoticeOutbox`), for the 24 hours the Shell takes them (#13930). They are typed into the pane of the run that made the call, never one that replaced it, with the host's name (#13500). The Shell keeps the host's link open while a call's notices are awaited, and on each new session, and shortly after notices arrive, proves its sender and asks `assistant.relay-notice-status`: `settled` lets the link go, and `unknown` for a call the host answered means the host lost its notices (it restarted), so the run that made the call is told once in its pane, naming the host and the terminals. Pair them with polling: a notice is best effort.
- **Quota.** `agent.readQuota` reads this machine's Codex account quota as Codex reports it there, so `host.call` reads a host's. Claude Code's usage is never read.
- **Consent.** The person's per-host "assistant control" switch on the Shell decides whether its assistants reach that host at all, finding, starting and messaging its assistants included; it is on for an SSH host, since that Shell can already run anything as the host's user, and kept across a change of target. The host's own "Accept tools run for other machines' assistants" (`helpAssistant.acceptRemoteControl`) decides whether it takes any. A change a call makes itself is held to the drive rule like any other: refused while another machine drives the project.
- **Retired exchanges.** v0.44 delegated through an inbox of exchanges; this build takes none. A host ends every exchange still open when it first runs as `failed` with outcome `messaging_retired`, under a new revision, and keeps answering the reads a v0.44 Shell makes of its own (`assistant.get-exchange`, `assistant.list-exchanges`, `assistant.cancel-exchange`, `assistant.get-responses`, and a resend of a known `assistant.send`) from those records, read-only (`RetiredExchangeStore`), so work it accepted reads as ended, never as silently gone; anything new is `UNSUPPORTED`, which that Shell reads as "this host doesn't support assistant messaging". The hourly sweep expires and purges the records as before. A Shell with sends still open in its journal types one fixed line into the first of its own assistants that can take it, naming each host and how many will get no reply and saying their work may already have run, then forgets the journal (`installRetiredSendsNotice`); until an assistant has taken it, the records stay for the next run.
- **Runbooks.** Every runbook request carries `Daintree-Host-Control: 1`, naming this model, for runbook servers older than the inbox catalog's retirement; current servers serve the host-control catalog to everyone. No request reports this Shell's hosts (`Daintree-Hosts`, #14458): the CLI holds its headers from launch, so a reported state would go stale the moment a host is added, connected or let go, and hide that host's procedures until the assistant relaunched. Search keeps every host procedure eligible; `host.list` and `host.call` read and check the live hosts.

## Settings ownership

`shared/config/settingOwnership.ts` is the one declaration: for every key of the settings file, and every field of the keys whose fields differ (`terminalConfig`, `appState`), plus the window-states and audit-logs stores, it names the owner (`host` or `device`) and the scope (`global`, `project`, `host` for this machine's answer per paired host, or `global-or-project`), grouped by the file it is kept in. Main's tables in `electron/storeOwnership.ts` (`STORE_KEY_OWNERSHIP`, where a key whose fields differ is `split`, and the field tables the hybrid splits route by) are derived from it and held exactly to the store schemas, so a new key or field without an owner fails typecheck. The renderer reads an owner with `settingOwner("terminalConfig.fontSize")`, never from `electron/`. The catalog also declares every key the renderer keeps in `localStorage` and `sessionStorage` (`renderer-local-storage`, `renderer-session-storage`): a key ending in `*` declares a prefix family, a store's `.__bak` backup inherits its owner, and all of them are `device`, because every view on this machine shares the `persist:daintree` partition. The renderer looks one up with `rendererStorageDeclaration`, and `npm run check:renderer-storage` (part of `check:guards`) fails on an undeclared key, a key it cannot read, or a declaration nothing uses; a call whose key comes from a parameter names it in a `// storage-key: <key>` comment above the statement. Host: agents, accounts, environment, MCP, plugins, forge, run history, per-project state, panel layout and the terminal list. Device: theme, keybindings, terminal appearance, the hybrid input and its "Focus first" choice (Settings > CLI agents > General > Input), scrollback and performance mode, notifications (which events alert, escalation, quiet hours, sounds, the flash and grouping, #14701), toolbar agent pins, window geometry, voice, privacy, updates, log-level overrides (their `logs:*` channels are `shell`), keep-awake, the host list (`remoteHosts`, `hostMode`, `remoteHostsPreferences`, `remoteHostPluginClipboardGrants`). Input, scrollback and performance mode follow the machine at the keyboard (#14697): every host's projects in a window on this Mac use this Mac's values, a local window on a host uses that host's own, and a change in a remote window never writes to the host. Scrollback there is how much history this screen's terminals show; the host's pty-host still sizes and trims its own buffers from its own value (`ResourceGovernor`), and resource monitoring and the memory-leak settings stay the host's. Each machine always kept its own copy, so nothing migrates: a value set earlier from a remote window simply stays the host's own. Notifications work the same way: a remote window's Notifications page edits this machine's settings, and a host's own copy decides only for its own windows (and for a Shell from before #14701). Copy settings lists Notifications under using a host directly for that reason. An agent on a host can't call `terminalConfig.set*` through a Shell's view: no setter is in `HOST_DISPATCHABLE_ACTION_IDS`, so the call is refused as "cannot be run from a remote host" rather than reaching into this machine's settings, while an agent in the host's own window sets the host's values as before. Toolbar agent pins are the screen's too (#14702): they live in this machine's `agentToolbarPins` (`electron/services/agentToolbarPins.ts`), read and written over `shell` channels and carried in the Shell's half of a hydrate, so every host's projects in a window on this Mac show this Mac's pins and a local window on a host shows the host's. A pin outlives its agent's CLI, so an agent pinned here but not installed on a host reads as unavailable there, as it does locally. Migration 039 moved each machine's own `agentSettings.agents[id].pinned` into it unchanged (unset stays unset, and pins from before `settingsVersion` 1, which were never shown, don't carry), and a fresh install pins its first agents from its own first complete CLI check. `pinned` is no longer agent configuration: Copy settings and Export leave it out, and the agent-settings write and the bundle merge drop it. The device keys the feature adds are optional and absent from store defaults, so a non-user's settings file is untouched. Each settings tab declares an `owner` in `src/components/Settings/settingsTabRegistry.tsx`; in a remote window the header chip and section badges say whose settings are being edited (`src/hooks/useSettingsOwner.ts`). Nothing syncs between hosts. One display-only exception lives in the renderer: the toolbar's issue and PR counts are repo-level facts, so the Shell keeps one record of them per repository origin (`forge-host/owner/repo`, whichever forge account a host is signed in as) in device `localStorage`, and every view of that origin, on any host and in any window, shows it in place of its own host's counts (`src/lib/sharedRepoStats.ts`, #14199, #15546). Each view publishes its host's fresh readings there, ordered by when this Shell received them so a host's clock can't pin the record, and follows other views' publishes through the `storage` event. A view asks its host for the origin (`forge:get-repo-key`, no forge request) before painting anything, so even the first switch to a host shows the record rather than that host's own seed. Counts with no single origin (an issues provider blending another tracker's count) stay unshared. It runs only in a remote view or once a host is paired, and no host ever reads it.

## Security model

- **Trust boundary.** A Host trusts a Shell that presents its token over a socket only its own user can reach (0600 socket, 0700 directory, owner-checked), which in practice means the Shell's user can already SSH in as that user. A Shell trusts a Host no further than its own views: every inbound message is zod-validated, oversize frames end the session, and every Shell-side action a host asks for is validated and scoped to the asking view's project.
- **Host-initiated dispatch.** A host can run renderer actions in a Shell's view only from `HOST_DISPATCHABLE_ACTION_IDS` (`electron/remote/client/hostDispatchableActions.ts`, enforced in `viewRequests.ts`), a default-deny list of terminal, worktree, agent, recipe and context actions and the forge reads (which ask the host's own forge, their channels being `host`), plus `browser.captureScreenshot` (PNG bytes of a browser panel in the view the host drives; an agent's capture in a remote window is refused for a page on this computer's own network, by address or resolved name, for a guest that has ever loaded anything from it, and when the page navigates while the capture is taken), `file.view` (shows a host file in the view's ephemeral read-only dialog, read from the host, which serves only files inside the project and its worktrees; `file.openPanel` stays out because it persists a panel and takes capacity), `host.switch` (`danger: "confirm"`, so the person at the Shell approves any move) and `project.openOnHost` (opens the switch dialog, where every step is the person's click: a dialog an agent or plugin asked for never opens the project by itself, even when there is nothing to decide); a new action stays out until added. The list also carries tools the host's MCP server answers in its own main process (the `*Many` batches, `terminal.notifyWhenIdle`, `mcp.surface`, `help.displayImage`, `skills.*`), whose view definitions only throw, so the host's session keeps them while a Shell drives; `diagnostics.openReview` (this Shell's diagnostics) and `copyTree.generateAndCopyFile` (this Shell's clipboard) stay out. Calls go out unconfirmed (confirm-gated actions raise the Shell's own dialog naming the host), origin is always `external`, and no reusable approval is returned. The one exception is the host assistant's confirmations preference, which is host-owned: a call the host confirmed for its own assistant (`sessionOrigin: "help"`, `authorization: "skip-preference"`) runs without the Shell's dialog, unless it is approval-only or one of `HOST_ALWAYS_ASKS_ACTION_IDS` (`host.switch`, `project.openOnHost`), which always ask. The Shell's own assistant's relayed call follows the Shell's own preference instead (#15698): the host names the call (`relayCall`: its `callId` and help session), and the Shell runs it without a dialog only when the view's own registry says it would ask, the call is one of its own still out to that host from the run that made it, in the project that view shows, with exactly that action and arguments (an `*Owned` tool as the action it stands in for), the control switch is on, and that assistant's Daintree confirmations resolve to skip on the Shell, read then; nothing the host sends turns it on. The Shell's answer then says `authorization: "skip-preference"`, which the host's audit records for that relayed call, and the Shell's `host.call` record says the same. A host's audit records `skip-preference` only when no dialog was raised; a skip-stamped call the Shell still asked about records only the person's decision, and the audit viewer never labels such a row as skipped. The manifest a host sees is filtered by the same list, and so are `actions.search`, `actions.list` and `actions.getSchema` answers. A workspace-bound host session is sent `tools/list_changed` when its project's driver changes (#13350).
- **The host's MCP key.** A remote window learns that the host's MCP server has a key, never the key: `mcp-server:get-status`, `set-enabled` and `set-port` answer it empty with `apiKeyRedacted`, `rotate-api-key` answers empty after rotating, the config snippet carries a placeholder, and the settings page says to copy the config on the host, since the key is a reusable bearer for the host's server that would outlast the link.
- **Viewless MCP.** A host runs the orchestration loop itself when no frontend is attached (`electron/services/viewless/`, #13495): `agent.launch` and `agent.listAvailable`; `terminal.new`, `list`, `getOutput`, `getStatus` (named terminals, or with none named the fleet a view would pick: the saved layout's panels joined with the pty-host's, by worktree and location), `sendCommand`, `sendKeys`, `interrupt` and `close`; `worktree.create`, `createWithRecipe`, `list`, `waitUntilReady` and `delete`; `project.getAll` and `detectRunners`; and the forge reads, `forge.getPR`, `getPRs`, `listPRs`, `getIssue`, `listIssueComments`, `listIssues`, `getCIStatus` and `getChecks` (#13501, #15399), which take their renderer actions' arguments (a parity test holds the keys together), resolve their worktree among the project's own, and hand back results through the same result schemas a view's dispatch parses them with; and discovery, `actions.list`, `search` and `getSchema`, over the catalog a help session with no view is listed (`getViewlessHelpBaseManifest`), through the same list and ranking code as a view's (`shared/utils/actionIntrospection.ts`), narrowed to the caller's surface by main as a view's answer is. The owned twins and the batches reach these through main's own delegation. `viewlessActionCatalog.ts` names each with its renderer definition's danger (a parity test holds the two together), and one admission gate refuses anything that is, or whose arguments make it, confirm-gated without an approval main already holds, with `confirmationChannel: "unavailable"`. Each action runs through the host IPC handler a view's call reaches (`viewlessInvoke.ts`) and shares its pure logic with the renderer action through `shared/` (the launch plan, preset merge, interrupt assessment, key table, worktree summary, PTY snapshot serializer), so a launch, a close and a read mean the same thing with or without a view. A launch or close is recorded in the saved project state as a view's persistence would record it, which is what the next frontend to attach hydrates. What only a view can draw or keep is refused rather than reinterpreted: browser and dev-preview panels, overlays, `excludeFromPersistence`, `removeOnExit`, a delete's `closeTerminals`, a `createWithRecipe` that names a recipe (refused before anything is created), and its "Assign issue to me" default (with no `assignToSelf` given the issue is left unassigned and the result says why). Anything else is `NO_FRONTEND_ATTACHED`. A call another machine's assistant relays through its Shell's `host.call` (#13493) changes a project only while that Shell's own view drives it, or while nobody does (#13501): then the host runs it itself as that Shell, never taking the lease, and `ViewlessActionRequest.checkWrite` asks again right before each host call the action makes, so a view that takes the lease in between stops it with `DRIVEN_ELSEWHERE` naming the holder (`relayWriteRule.ts`; `project.runCheck` and `project.runCommand` ask the same right before their spawn). A lease held by anyone else still refuses. A relayed call is a read when the view's manifest says so, or, with no view to describe the project, when the host's generated catalog does; one the host can't run alone in a project nobody drives or shows is `NO_FRONTEND_ATTACHED`, not `DRIVEN_ELSEWHERE`. With no view to ask, a relayed `worktree.delete` or `worktree.deleteOwned` is put to the person at the hub, in the window of the assistant that made the call: the host reads the delete's preview itself (`get-delete-preview`, the same three reads a view's dialog makes, formatted by the shared `worktreeDeletePreview.ts`) and sends `assistant.relay-approve` over the link, naming the call, the action and the canonical hash of exactly the arguments it will run; the Shell answers only for a call of its own still in flight to that host from the run that made it, about exactly that call, once, and raises the action's own dialog approval-only with the host's lines and the host named (`hostPreview`), unless that assistant's Daintree confirmations resolve to skip on the Shell, when it asks nobody and answers `skip-preference` (#15698), which the host runs under as an approval and audits as the skip, and the Shell's `host.call` record says the same; a host from before it reads that answer as none and refuses the call. The answer must echo the ask's id and hash and arrive within 40 s, covers that one call until then, and is never kept, so a change the call hasn't reached by the deadline is refused. An older Shell answers `UNSUPPORTED`, which leaves the call refused as before; a force delete still needs a typed name and stays refused. `ViewlessActionRequest.requestApproval` is that seam; absent, an unapproved confirm-gated call is refused with `confirmationChannel: "unavailable"`. This only happens once Host mode installs the drive-target resolver (`isMcpHostRoutingEnabled`), so a plain local app routes MCP exactly as before, except for a `local` relay (#14024), which runs here in a project no view shows.
- **Hygiene.** Error envelopes are stripped of paths, stacks, tokens and context (above). Transfer failures cross as fixed reason codes. The host inbox, clipboard dir and SSH control directory are owner-only. Terminal contents and file contents are never logged.

## Decisions taken

These were open questions with defaults chosen; each matches the code today.

- One host per window; Cmd/Ctrl-click opens a new window.
- One driver per project with explicit takeover — and exactly one driving **endpoint**, not every window of the driving client. Watching views see terminal output live, follow the driver's panels from the host's saved state and its navigation from its reports, and stay read-only.
- The terminal list is host-owned; the grid layout (strategy and count), zoom, sidebar widths, panel sizes and palette habits stay per client.
- Credentials are per host; nothing is synced. File export/import is refused in remote windows; settings move to a host only through Copy settings, an explicit one-shot push from this machine (below). No host-to-this-machine or host-to-host copy, no "copy project setup", and project ids are never auto-committed.
- A headless Linux host accepts that plugin secrets are unavailable, and the UI says why.
- Linux installs default to the AppImage, which needs no root; a host already on the deb keeps the deb.
- The assistant is an agent PTY and runs on the host like any agent; `help-assistant:*` is host-owned. A remote view's help session is provisioned on the host for the view's own project (session folder, bearer and MCP config under the host's userData, pointing at the host's MCP server), pinned to the view's endpoint handle so the assistant's tool calls go back to that view, and revoked when the endpoint moves to another project. When the endpoint closes (eviction, a deliberate Shell close, a link down past its resume grace) a running assistant is detached instead of killed, like the host's grid agents: its PTY and bearer stay, its session is pinned to no view (`NO_VIEW_HANDLE`) with its transports retired, and the view that drives the project next takes it over, which re-pins the session and retires its MCP transports again so the client reconnects onto the new view (#13360). With no view, its tool calls run on the host through each action's viewless form (`dispatchActionWithoutView`, bound at handshake in `sessionViewlessHelpMap` and listed from the generated base manifests): a change runs only while nobody drives the project, checked again right before it lands, and is refused `DRIVEN_ELSEWHERE` naming the holder otherwise; confirmations are the assistant's own skip preference or `confirmationChannel: "unavailable"`; anything only a view can do stays `NO_FRONTEND_ATTACHED` (#13511). An assistant that has once run with no view (`outlivesView`) is detached again, not ended, when a view of this machine's own that took it over is evicted, crashes or its window closes; project close and sleep still end it. The host does that itself as soon as such a view attaches or gains the lease, or an assistant is left with no view while one already drives (`helpDetachedAdoption.ts`), panel open or not, a window on the host itself included (#13511), so an assistant left working regains its Daintree tools when the Shell comes back (#13389); the renderer's `help:adopt-detached-session` then binds a pane to it without retiring the transports again, and keeps the panel's restore-on-open intent.
- Cross-host notifications are opt-in per host; `notificationsEnabled` governs other hosts only, and a remote window's own host always notifies.
- Ctrl+V image interception is on by default, in remote windows' agent terminals only.
- Uploads confirm at 50 MB and refuse at 500 MB (5,000 files per folder, declared for folder upload).
- "Add to project" drop ships.
- Hosts follow the client's release channel for installs. A host whose Daintree has never run there (the probe finds no settings file, so nobody has chosen a channel) takes the client's update channel when setup turns Host mode on (`--update-channel=<stable|nightly>` beside `--enable-host-mode`), so its own updater follows the same feed: left on the default, a nightly host would "update" to the stable release its version sorts below. A host where Daintree has run keeps its own channel. A check that began on the old feed and answers after the switch never stages its download.
- Viewless MCP execution is gated to Host mode, not the plain local app.
- `project.runCommand` answers a Shell's assistant reaching a host through `host.call` at either in-app tier (#13501), as it answers the host's own assistant: `host.call` is only offered to a Shell's assistant in one of its own windows, which already reaches a shell on the host through any agent it launches and drives with the owned sends (and at `full` through a `terminal.new` of its own), so the runner adds structured output and an audited command, not authority. The relayed session keeps its `external` origin, and the call is held to the drive rule like any other change. A host on a build from before the runner joined `core` still refuses a core-tier relay with `TIER_NOT_PERMITTED`. This is what a Shell assistant runs `git status` with on a host with no window open.
- Settings → Hosts is visible on macOS and Linux as the single entry point for adding the first host; everything else stays hidden until a host exists.
- Framing runs in main, not a utility process (see [Testing](#testing)); no separate bridge binary on the host: the stdio fallback runs the host's own Daintree with `--attach-stdio`.
- Locally, clipboard images keep the `daintree-clipboard` directory; only remote windows use the host inbox.
- Keep-awake is device-owned: each machine keeps itself awake for its own agents.

## Known limits

- **Start at login.** A unit argument (the app's path) with a line break or NUL is refused rather than quoted, and an `APPIMAGE` variable counts only when this binary runs from inside the `APPDIR` mount it names.
- **Lease continuity by client id and install id.** A drive-lease reservation left by a departed holder is taken back by the next endpoint with the same client id, which other Shells can see, or with the same self-reported `deviceId`, which a fresh session also uses to end the install's parked sessions. Any attached Shell can take a lease over openly, so this hands over nothing an explicit takeover doesn't; it is not proof of identity.

- **macOS containment.** Node has no `openat` on macOS, so each containment step is a before-and-after device/inode check rather than a descriptor-relative open, and once the walk ends every held folder is checked again against its path; a process on the host that swaps a folder for a link and back between two of those checks still has a small window. Such a process could already read those files. Hard links into a project are followed everywhere. The legacy `files:read` and plugin asset readers open without following a last-component link and without blocking (so a FIFO can't hold a filesystem worker), then require the descriptor to be a regular file and the same file the contained real path names; the matcher reads `.git/config` the same way. They still resolve the path before opening it, so a folder swapped for a link between the two can land the open outside the root with both checks agreeing; moving them onto the anchored walk is the fix.
- **Shared temp folders.** CopyTree bundles and project bundles live in per-user folders (`daintree-context-<uid>`, `daintree-bundles-<uid>`); the CopyTree folder must be a real directory this user owns and is kept 0700, or nothing is written there, and a bundle offered for download is the very file CopyTree wrote (by device and inode), not one put in its place. The host inbox keeps its shared name (agents are told it by that name) and refuses a folder another user owns, so on a multi-user Linux host another user who takes the name first can stop uploads there, but not read or change them.
- **Forwarded ports.** A preview forward keeps the host's port number when it is free here, so a host can take a local port another app would have bound next; and like any `ssh -L`, a `127.0.0.1` forward is reachable by every user on this machine. `ports.open` on the attach-stdio route isn't subject to sshd's `AllowTcpForwarding`.
- **DNS to loopback.** A remote view's guest request to a name is held until the session's resolver answers, and refused when that answer is loopback; a name that changes its answer between that lookup and Chromium's own connection can still get through. Local windows don't check names.
- **This computer's network.** A top-level navigation in a remote window's browser panel can still reach this computer's LAN, as Local Network Access allows, so a host dev server on its LAN or tailnet address keeps working when opened directly; a host's restored history can make that navigation, as it is a typed-URL prompt and not a boundary. Such a page is never handed to the host as a screenshot. WebRTC and WebTransport connections don't pass through `webRequest`, so the Local Network Access rule doesn't cover them; reaching a LAN device that way needs it to speak those protocols. A plugin view the person allowed runs with the renderer's trust, so it can capture without the host flag.
- **Self-minted grants.** A Shell can request a host-minted clone destination token or checkout offer for itself; the host validates the folder and branch itself, since it can't verify a person's confirmation. Likewise a clicked-file grant: the host can't see the click, only that the view drives the project, and a view that drives can already read any file the host user can through that project's terminals.
- **Persisted clipboard answers.** Plugin clipboard grants and denials persist in `remoteHostPluginClipboardGrants`; they are reset per host from Settings → Hosts → host, not from the plugin's own settings.
- A macOS case-only path difference can get past the in-process clone reservation (the non-overwriting rename still protects content).

## Unverified on real hardware

Covered by unit tests with injected spawners, the direct-socket harness and the local real-ssh test, but not yet exercised for real:

- A real remote machine, and a Linux host over ssh. `ssh -L` socket forwarding through a ControlMaster and `ssh -O forward` port forwards are verified against a real OpenSSH `sshd` on macOS (a private user-mode `sshd` on 127.0.0.1, `electron/remote/__tests__/ssh.e2e.test.ts`), but only on the same machine.
- `--attach-stdio` launched as the real Electron binary over ssh: the e2e runs the real bridge module as a Node script instead. Starting a packaged app's binary from an ssh session (a Mac's Dock and window-server access, an AppImage's mount, headless Ozone on a box with no display) is untested.
- A real LaunchAgent at login (including Background Items approval) and a `systemd --user` unit with linger on a headless box.
- `dns-sd` and `avahi-publish-service` advertising on a LAN, and the Local Network prompt in a signed build.
- A multi-file drop through the real preload `files.getDroppedFilePaths` bridge (the binding is tested through `electron/utils/droppedFilePaths.ts`, not the loaded preload).
- A Linux host socket under `/run/user/<uid>` (descriptor-relative containment runs only on Ubuntu CI).
- Host installs (bundle push, host fetch, deb and AppImage) and stop/rollback on a live host.
- Real cross-machine latency.

## WSL (#12830)

WSL as an execution environment has the same shape as Remote Hosts, which is how VS Code and Zed do it: Windows draws the UI as a Shell, and git, worktrees, terminals and agents run in a Linux Host inside the distro. Projects live on the distro's filesystem (`/home/<user>/…`), with its own git, tools and agent accounts.

- **The connection.** `{ kind: "wsl"; distro }`, the distro's name as `wsl.exe -l` lists it, run as the distro's default user. `isValidWslDistroName` keeps it to what wsl lists (letters, digits, `.`, `_`, `-`, inner spaces, starting with a letter or digit, so never an option).
- **Every program goes through one argv** (`electron/remote/client/wslCommand.ts`): `wsl.exe -d <distro> --cd ~ --exec <absolute program> <args…>`, System32's `wsl.exe` (`windowsSystemTool`), `windowsHide`, `WSL_UTF8=1`. `--exec` hands the argv to the Linux program exactly; `--` would run the line through the user's login shell, which splits and expands it again. `--cd ~` starts in the distro user's home rather than the Windows working directory under `/mnt/c`. The pipe is byte-clean (verified with 4 MiB of random bytes) and carries stdin EOF through. When wsl.exe itself fails (no such distro, the service down) it exits `4294967295` with its message on **stdout**, so `withWslDiagnostics` moves that to stderr, where failures are read.
- **The link** (`electron/remote/client/wslTransport.ts`): one `/bin/sh -c` prints the first live Host's discovery file (only one whose socket exists and whose pid runs counts) from `/run/user/<uid>/daintree` (and `daintree-dev` for a development Shell); then `wsl.exe --exec /usr/bin/env -u DISPLAY -u WAYLAND_DISPLAY <the Host's published command> --attach-stdio --ozone-platform=headless` starts the Host's own bridge, which reads its socket and token from that file and carries the link over its stdio (`createCommandStreamTransport`, with `stdoutInFailure` so wsl's own words reach the user). The bridge runs headless and without WSLg's display so Chromium never reaches for the distro's compositor; the Host's own unit keeps the display, so GUI programs started in its terminals still open through WSLg. No Host listening is a `HostModeOffError`, and its user service is started through `ensureRunning`, as for an ssh host. Port forwards ride the link's stream forwarder (no ssh master); the editor opens files through VS Code's WSL remote (`vscode://vscode-remote/wsl+<distro>/…`, also Insiders, Cursor and Windsurf), and reveal and open with the default app go through `\\wsl.localhost\<distro>\…` (`shared/utils/wslPath.ts`), refusing paths Windows can't name (trailing dots or spaces, device names), and opening with the default app applies the launcher's executable deny-list to the path and to what it resolves to.
- **Distro lifetime** (`electron/remote/client/wslKeepalive.ts`). WSL stops a distro about 15 s after its last `wsl.exe` client exits, and everything in it goes, Host and agents included; systemd services and linger don't keep it up. Nor does linger matter while it runs: WSL holds the user's login session open for the distro's whole life, so setup neither asks a WSL host for lingering nor advises it, gives no sleep advice (the distro sleeps only with this PC), and instead says how long the distro runs. The Host's own Host mode rows say the same when its kernel is WSL's (`isWslKernel`). While a link is open its bridge is such a client, but a reconnect gap, an idle link release or the moments between setup's commands are not, so each wanted distro gets a keeper: `wsl.exe --exec /bin/cat` reading a stdin this process never writes. Two holds keep it running: a host's distro is **wanted** from its first link attempt until the host is forgotten or re-pointed or the app stops (a Disconnect or an idle release leaves it running, as a remote machine stays up when a Shell lets go), and each setup command **touches** its distro for a minute after it starts and after it ends, which carries a probe, an install and Host mode's start into the link that follows and lets a distro that was only checked, never added, stop on its own. A link dialled while its host is being removed or re-pointed never holds the distro again. Ending stdin lets the keeper go, and so does this process dying, since the pipe closes with it. A keeper that exits on its own (`wsl --shutdown`) is started again by the next attempt. **Known limit:** quitting Daintree on Windows lets the distro stop about 15 s later, ending the Host's terminals and agents, as quitting ends local ones; keeping them across a Shell restart would need a keeper that outlives the app.
- **Setup.** On Windows, `remoteHosts.discover()` lists the installed distros (`discoverWslDistros`: `wsl.exe --list --verbose`, default first, Docker Desktop's left out, WSL 1 listed with its version so the dialog can say it can't run a Host); listing never starts a distro. The probe, install and Host mode bootstrap run unchanged through `createWslCommandChannel` (`/bin/sh -c <script>` through `--exec`, files over stdin), each command holding the distro up first. The Linux install path is the ssh one: the Host fetches the Linux AppImage (or deb) for this client's exact version from the release feed, since a Windows client has no bundle of its own to push. The probe also reports whether systemd is PID 1, and setup stops at the check for a distro without it, pointing at `/etc/wsl.conf`; Daintree never edits it.
- **Paths.** Host paths stay POSIX in every message and in the renderer, which reads them with the host's platform (`useHostPlatform`); they become Windows paths only at this machine's edge (reveal, open, the editor). Dropped, pasted and attached files go up to the host inbox as for any remote host.
