# Remote Hosts

A Daintree window can drive another machine's Daintree over the system `ssh`. The window's machine is the **Shell** (screen, keyboard, device preferences); the other machine is the **Host** (agents, terminals, worktrees, git, files, plugins, MCP, and the accounts and settings that go with them). Every Daintree process is both: it can drive hosts, and with Host mode on it also serves Shells. Everything specific to the feature lives in `electron/remote/**`; core code meets it through a handful of seams (the IPC dispatcher, the endpoint registry, the drive lease, the operation registry, the viewless MCP executor).

The hard rule behind every seam: **someone who never adds a host sees exactly today's behaviour.** No remote service dials or listens until a host is configured or Host mode is on, the dispatcher's routing is a single null check with no router installed, local keys and paths are unchanged, and new UI stays hidden until a second host exists (the Settings → Hosts tab is the one deliberate exception, as the entry point for adding the first host).

## Roles and scope

- **One host per window.** A window is bound to exactly one host through `WindowHostBinding` (`electron/remote/client/WindowHostBinding.ts`); Cmd/Ctrl-click in the host menu opens a new window instead of rebinding. `LOCAL_HOST_ID` (`"local"`, `shared/types/remoteHosts.ts`) names this machine.
- **Remote views.** A remote-bound window's project views are keyed by `toHostScopedKey(hostId, projectId)` (`<hostId>:<projectId>`; local keys stay the bare id) in `ProjectViewManager`, and get `--daintree-host-id=<id>` (`HOST_ID_ARG` in `electron/window/ProjectViewFactory.ts`), surfaced to the renderer as `window.__DAINTREE_HOST_ID__`. A view's host comes from its key, so a local project view inside a remote-bound window still runs locally; a view with no project follows its window's binding.
- **Host mode** is a capability of the running app, not a second backend: the same process listens on a Unix socket for Shells. The single-instance lock still guarantees one backend per `userData`.
- **macOS and Linux only**, in any pairing. Windows builds carry none of the feature (see [Windows exclusion](#windows-exclusion)).

## Windows exclusion

- **Runtime gate.** `isRemoteHostsSupported()` — main: `electron/remote/buildGate.ts`; renderer: `src/lib/remoteHosts.ts`; both delegate to `isRemoteHostsSupportedOn` in `shared/config/remoteHostsSupport.ts`. The eleven Remote Hosts IPC namespaces register only inside it; host actions (`host.switch`, `host.add`, `host.forwardPort`, `project.openOnHost`, `host.overview.open`) register only inside it; the Settings → Hosts tab is added to the registry only inside it.
- **Build gate.** `__DAINTREE_REMOTE_HOSTS__` is a define, false for win32 targets, set in `scripts/build-main.mjs`, `vite.config.ts` and `vitest.config.ts` (ambient declarations in `electron/types/buildDefines.d.ts` and `src/types/env.d.ts`). `__DAINTREE_BUILD_COMMIT__` is baked the same way for the handshake.
- **Tree-shake rule.** esbuild folds only a direct `if (__DAINTREE_REMOTE_HOSTS__) { await import("…/remote/…") }`; a boolean imported from another module does not drop the chunk. So core code (anything outside `electron/remote/**`) never statically imports a remote module, except the four core-safe files: `buildGate.ts`, `runtime.ts`, `pendingHandler.ts`, `handshakeInfo.ts`. `main.ts` loads `./remote/boot.js` through that direct form; boot registers services into `runtime.ts` (`registerRemoteService`, with each module augmenting the `RemoteServices` interface), and core code reaches them with `getRemoteService(key)` / `requireRemoteService(key)`. Core seams take injected hooks instead of imports (`dispatcher.setRemoteRouter`, `setRemoteBoundViewFilter`, `setRemoteViewHooks`, `setMcpDriveTargetResolver`).
- **Proof.** The tree-shake test, `scripts/__tests__/remoteHostsTreeShake.test.ts`, bundles the main-process entries the way `build-main.mjs` does with the define on and off and reads the metafile: with it off, no file under the gated `electron/remote/` directories may be in the bundle, and only the four core-safe files may be reached from core. On the renderer side, `materialize.ts` and `LazyUploadConfirmHost.tsx` load the remote-only upload modules under the same direct check, pinned by a static-import walk from `src/main.tsx`.
- Preload namespaces exist on Windows but are inert: their handlers are never registered.

## Transport

- **System `ssh` only** — no SSH library, no new npm dependency, and no bridge binary on the host. `SshTransport` (`electron/remote/client/sshTransport.ts`) runs the user's own `ssh`, so `~/.ssh/config`, agents (1Password, Secure Enclave keys) and Tailscale SSH apply unchanged; nothing overrides identity, host-key or agent settings. Every call uses `BatchMode=yes` and one `ControlMaster=auto` connection per host (`ControlPersist=10m`, `ControlPath=<userData>/rh/cm-%C`, or a short per-target hash when `%C` would overflow `sun_path`).
- **Connect sequence.** (1) `ssh <target> 'uname -s; id -u; echo "$HOME"'` derives where the host's discovery file lives; (2) `ssh <target> cat <discovery file>` reads the socket path and token; (3) `ssh -O forward -L <local.sock>:<remote.sock> <target>` asks the master to forward a fresh local socket (unique per attempt) to the host socket, falling back to a dedicated `ssh -o ControlPath=none -o StreamLocalBindUnlink=yes -o ExitOnForwardFailure=yes -N -L …` when there is no master; (4) the client dials the local socket and authenticates.
- **Host socket.** macOS: `app.getPath("userData")/host.sock`. Linux: `/run/user/<uid>/daintree/host.sock` (`daintree-dev` for unpackaged builds), derived from the uid rather than `$XDG_RUNTIME_DIR` because minimal SSH sessions often don't export it; a missing `/run/user/<uid>` fails with a clear error. `hostSocketPath.ts` also derives the same location from the client side, and asserts the path fits `sun_path` (104/108 bytes).
- **Discovery file.** `host.json` next to the socket carries the socket path and a per-launch 32-byte token (64 hex). Written atomically 0600 (`wx` + rename) into a 0700 directory, and removed at shutdown only if it still carries this launch's token (claimed by rename, re-read, linked back if a newer launch owns it). Tokens are compared timing-safe.
- **Direct transport.** `createDirectTransport` (`electron/remote/client/transport.ts`) dials a Unix socket path directly, from a `{socketPath, token}` or a discovery file. Tests and the integration harness use it instead of ssh.
- **Reconnect.** `LinkClient` reconnects with capped, jittered exponential backoff, presenting its previous session id; `HostServer` resumes the session (same id, `resumed: true`) if it comes back within the 10-minute grace with the same client id. A version mismatch stops retrying; an unreachable host reports what was observed (ssh's stderr, the rejection, the last-heard time), never a guessed cause.

## The link

One multiplexed byte stream per session, framed in `electron/remote/link/frames.ts`: `u32 bodyLength | u8 lane | u8 kind | u32 streamId | payload` (10-byte header, 16 MiB max frame, reassembled by a bounded `FrameDecoder` that returns copied payloads).

- **Lanes and priority.** `CONTROL > INTERACTIVE > RPC > EVENTS > BULK` (`LANE_PRIORITY`). `LaneScheduler` (`scheduler.ts`) serves at most `INTERACTIVE_BURST_FRAMES` (32) interactive frames back to back before letting one waiting lower-lane frame through, so RPC can't starve. Each lane has header-inclusive byte and frame caps; the hard cap is absolute (a refused frame never gets a drain callback) and drain callbacks fire at half high-water. Bulk payloads are cut into 64 KiB chunks (`BULK_CHUNK_BYTES`) so keystrokes interleave with uploads.
- **Encoding.** `encoding.ts` is a bounded tagged binary encoding (Uint8Array, undefined, Map/Set/Date/bigint/Error, lone-surrogate-safe strings) with caps on depth (64), size (64 MiB), container length (1M), total nodes (2M) and bigint digits (1024); no prototype pollution, and decoded Errors never carry a local stack.
- **Messages** (`messages.ts`, validated by zod in `schemas.ts` on send and on receive; an invalid body ends the session with GOODBYE): CONTROL `HELLO/WELCOME/REJECT/PING/PONG/ENDPOINT_OPEN/ENDPOINT_REBIND/ENDPOINT_CLOSE/HOST_SUMMARY/LEASE_CHANGED/GOODBYE`; RPC `INVOKE/INVOKE_RESULT/SEND/REVERSE_REQUEST/REVERSE_RESULT/CALL/CALL_RESULT`; EVENTS `EVENT`; INTERACTIVE `TERMINAL_OUT/TERMINAL_IN/TERMINAL_RESET/WORKTREE_PORT`; BULK `TRANSFER_BEGIN/CHUNK/END/ABORT/ACK`. New features add session-level CALL methods (each module's `linkMethods.ts`) rather than new kinds.
- **Handshake.** Before HELLO nothing else is accepted. HELLO carries the token and `HostHandshakeInfo {version, commit, protocolVersion, platform, arch}` from `getLocalHandshakeInfo()` (`electron/remote/handshakeInfo.ts`); `compareHandshake` requires the same protocol (`REMOTE_PROTOCOL_VERSION`), app version and source commit. Platform and arch may differ. A mismatch is a REJECT, surfaced as the `version-mismatch` connection state and `HOST_VERSION_MISMATCH`.
- **RPC timeouts.** INVOKE has no timeout by default; CALL and REVERSE_REQUEST default to 60 s. A timeout, or a link that drops with a request in flight, resolves `OUTCOME_UNKNOWN` (never a guessed failure).
- **Bulk transfers** (`transfer.ts`): the sender announces size and sha256 in `TRANSFER_BEGIN`; a 1 MiB window with an ack every 256 KiB; a receive cap of 4 GiB and 8 concurrent transfers; 60 s inactivity and 120 s commit timeouts on both sides. The receiver verifies the digest before a sink commits. Sinks register by destination prefix with `addSinkProvider` (`daintree-upload:`, `daintree-bundle:`), so features share a session without overwriting each other.

## Dispatcher and endpoints

- **`IpcDispatcher`** (`electron/ipc/dispatcher.ts`, `getIpcDispatcher()`) holds every invoke and send handler, transport-independent. `ipcMain` feeds it for local views through the existing `security.ts` sender validation; the host's `SessionHost` feeds it for remote endpoints through `invokeForEndpoint` / `sendForEndpoint`, which return the same envelope local IPC gets.
- **`ClientEndpoint`** (`electron/ipc/endpoint.ts`) is who a handler is talking to: `{endpointId, clientId, projectId, kind: "local-view" | "remote-view", handle, send(frame), request(method, payload, opts), onClose, isClosed}`. `handle` is the WebContents id for a local view and a negative number for a remote one, so it never resolves through `webContents.fromId`. `send` pushes events; host→Shell questions (MCP dispatch, plugin prompts, consent, clipboard) go through `request()`, where the endpoint owns correlation, timeout and abort, and settles pending requests with `HOST_DISCONNECTED` on close. `IpcContext` carries `endpoint` and `client`; for a remote call `event` and `senderWindow` are null and `webContentsId` is the negative handle, so host code replies through `sendToRendererContext(ctx, …)`, never `senderWindow`. Local endpoints (`electron/ipc/localEndpoint.ts`) are created lazily on first read of `ctx.endpoint`.
- **`EndpointRegistry`** (`electron/ipc/endpointRegistry.ts`) lists every endpoint; the broadcast helpers in `electron/ipc/utils.ts` deliver to remote endpoints from it (project-scoped helpers use `getForProject`). Remote endpoints are `RemoteViewEndpoint`s owned by the session id (`remote:<sessionId>:<clientEndpointId>`), so they survive a dropped link and close only when the session is given up. A Shell that stops reading its EVENTS lane (hard-cap refusal, or over high water for 5 s) has its events dropped and is told to resync once the lane drains; the view gets `resync-required` and refetches.
- **`RemoteRouter`** (`electron/remote/client/RemoteRouter.ts`) is installed on the Shell's dispatcher only on first connect or window switch. For a sender whose view is remote-bound: `host` channels forward to the host and its envelope comes back verbatim; `shell` channels run locally; `hybrid` channels run their registered `HybridSplit`; an unregistered hybrid is refused with `CHANNEL_NOT_REMOTABLE` (never silently local); unclassified channels are refused. Sends follow the same rule except that hybrid sends stay local.
- **Hybrid splits** (`electron/remote/hybrid/`) receive `local(args?)` and `remote(channel?, args?)` legs that take replacement args (so a setter can send device fields locally and host fields remotely) and resolve to unwrapped values; the dispatcher wraps the merged result once. Splits exist for hydrate, boot and app state, `events:push` filtering, project switch and activation, notifications, keep-awake, settings bundles (refused in remote windows), native pickers, clipboard capture, editor/open/reveal, dev preview and plugin install. On the host, a hybrid channel is refused over the link unless a split admitted its host leg with `allowHybridOverLink(channel)` (`admitHybridHostLegs()` in `hostListener.ts`). Link calls also refuse `shell` and unclassified channels and any channel with no context handler.
- **Error envelopes.** Errors cross the link under the packaged-build policy whatever the build (`linkErrorEnvelope`, `electron/remote/link/envelopes.ts`): paths, tokens, stacks, cause and free-form context are stripped; `code` and allowlisted `details` (`AppErrorDetails`, currently the plugin host errors) survive to the renderer.

## Channel locality

`electron/ipc/channelLocality.ts` classifies every channel as `host` (the work: projects, terminals, git, files, agents, plugins, forge, MCP, persistence), `shell` (the machine you're at: windows, menus, theme, keybindings, sound, native notifications, updates, voice, browser surfaces) or `hybrid` (needs a split). `CHANNEL_LOCALITY` is total over `ChannelName`, so an unclassified channel fails typecheck; `EVENT_LOCALITY` covers event-only names; `NAMESPACE_LOCALITY` gives the Remote Hosts namespaces by prefix; dynamic `plugin:{id}:{channel}` is `host`. `getChannelLocality` returns `"host" | "shell" | "hybrid" | null`. `npm run check:channel-locality` (part of `npm run check`) fails on any channel string registered outside `CHANNELS` that isn't classified. A new channel needs an entry here as well as in `CHANNELS`.

The `mcp:` request/response bridge and the plugin prompt and consent bridges are `shell` although the work is host work: they join a machine's main process to its own views, and a host reaches a remote view through the link's reverse requests, which that view's Shell answers over them.

## Terminal and worktree streams

- **Host.** `TerminalStreamBridge` (`electron/remote/terminal/`) connects each remote endpoint to the pty-host as a synthetic window (the negative handle is the port holder id), so it gets the same batching, project filtering and ack-based flow control as a local view. Output is stamped `{incarnation, seq}` (incarnation is the PTY's launch generation) and kept in a bounded per-terminal ring (4 MiB each, 64 MiB host-wide `RingBudget`, at most 4096 streams, dead terminals swept). While the Shell is attached acks are end to end; while it is away the bridge acks for it so no PTY stalls. A Shell past about 1 MiB unacked on one terminal, 8 MiB across the endpoint, or silent for 2.5 s is dropped to a snapshot resync. Input, resizes and acks are accepted only for terminals the endpoint's project owns; input and resizes also only from the driving endpoint (acks from any attached endpoint, so a watcher never stalls a PTY). A resuming Shell whose position the bridge can't vouch for (the host's listener restarted, or the stream was retired) gets a snapshot reset for any terminal its project still owns, so nothing emitted while no bridge existed is silently missing.
- **Replay.** On reconnect `ClientTerminalRelay` asks `terminal.resume` with `{incarnation, lastSeq}` per terminal; the host replays from the ring, or sends `TERMINAL_RESET` with a full snapshot (cols, rows, serialized state) when the ring no longer covers the gap or the incarnation changed. The snapshot boundary is fenced in the pty-host (`serialize-fence`), so output is never lost; a tiny duplicate at the boundary is possible. Snapshots over 8 MiB reset to a cleared screen. The renderer treats a reset as a restore with the snapshot's geometry and bumps a per-terminal ack generation so stale write callbacks can't ack new data.
- **Shell.** The client installs a port override (`installClientTerminalPortOverride`) that hands a remote view a `MessageChannelMain` through the same `terminal-port-token` / `terminal-port` messages `portDistribution.ts` uses, so the renderer's port API is unchanged. The relay advances `lastSeq` only after posting to a live renderer port, holds refused input in order (bounded by bytes and count) and retries it when the link is writable.
- **Worktree port.** The worktree RPC port is bridged the same way over `WORKTREE_PORT` (`electron/remote/worktreePort/`); requests are validated against a complete per-action schema, any `rootPath` must resolve to the endpoint's project, and the host bridge retries (250 ms to 5 s, 40 tries) until the workspace host is ready.

## Operations

Long-lived mutations (push, clone, CopyTree, project moves, uploads) carry a client-minted `opId` (`OperationId` in `shared/types/remoteHosts.ts`). `OperationRegistry` (`electron/services/operations/`) dedups by opId, ties an id to its kind, scope, project and a request fingerprint (reuse for a different request is `VALIDATION`), reports progress to the operation on `operations:event` (at most every 100 ms), and retains settled outcomes for 10 minutes (up to 200; 64 running; 32 aliases per operation). A remote caller sees and cancels only its own project's records. The renderer mints an opId only in a remote window (`mintRemoteOperationId`), so local calls take the old untracked path.

A request whose link dropped mid-flight is `OUTCOME_UNKNOWN`, not a failure. The client resolves it with `operations:get-status` once reconnected (`resolveUnknownOutcome`, `runHostOperation` in `src/hooks/useHostConnection.ts`) before showing anything; the UI says "Checking with <host>…" meanwhile.

## Drive lease

One endpoint drives a host project at a time; there is no mirroring. `DriveLeaseService` (`electron/services/DriveLeaseService.ts`) arbitrates on the host. A `DriveLeaseHolder` carries a monotonic `leaseId` (work stamped with an older lease is stale after a takeover) and the one `endpointId` that drives. That endpoint is the target of MCP reverse dispatch and plugin prompts, and the only source of terminal input and resizes: the bridge drops input from non-drivers, the pty-host enforces a lease table (`set-drive-leases`) on port writes and resizes, and `electron/ipc/handlers/terminal/io.ts` gates the IPC paths, refusing submit with `DRIVEN_ELSEWHERE`. The resize lease follows the drive lease.

Takeover is explicit and visible on both screens: the driven-elsewhere banner (`src/components/Recovery/DriveLeaseBanner.tsx`) names the driver and offers Take over, or Take back on the host's own screen. A holder whose link drops keeps the lease for a 15 s grace (`DEFAULT_DRIVE_LEASE_RELEASE_GRACE_MS`), cancelled by a resume. This machine's own windows drive together whenever the local client holds, exactly as before, and a project no remote client touches is never arbitrated; `peekDriveLeaseService()` keeps local-only apps from ever consulting it.

## Host bootstrap and Host mode

- **Windowless backend.** `startHostRuntime` (`electron/boot/hostRuntime.ts`, `hostBootstrap.ts`, `hostServices.ts`) brings up global services, IPC, the pty-host, the workspace pool, MCP and the plugin host with no `BrowserWindow`, using the same once-only starts as the window path. A `--host-mode` launch is windowless; on Linux with no `DISPLAY`/`WAYLAND_DISPLAY` it also appends `ozone-platform=headless` and `disable-gpu` (`electron/setup/environment.ts`). Closing the last window doesn't quit while Host mode is active, a second instance with no live window opens one, and a second `--host-mode` launch hands off to the running process and starts it listening without a window.
- **`HostModeService`** (`electron/remote/host/HostModeService.ts`, registered by boot as the `hostMode` service) is the "Allow this machine to be a host" switch. On: `startHostListener` (`hostListener.ts`) takes a lock per socket path (`hostSocketLock.ts`), clears a stale socket, binds 0600 in a 0700 directory, writes `host.json`, and installs the session host, stream bridges, file, upload, port, project, plugin and metrics services and the MCP drive-target resolver. Off: the socket closes, every Shell's session drops, `host.json` goes, and the start-at-login unit is removed. Quitting stops listening but keeps the setting.
- **Start at login** (`startAtLogin.ts`), only with explicit consent: a Daintree-owned LaunchAgent on macOS, limited to the Aqua session (a login item can't pass `--host-mode`), and a Daintree-owned `systemd --user` unit on Linux (enabled, not started, with `loginctl enable-linger` shown for the user to run). Removal deletes the file and disables the unit and never unloads a running job, which may be this process.
- **Advertise** (`advertise.ts`): `_daintree._tcp` via `dns-sd -R` on macOS or `avahi-publish-service` on Linux, advertising the SSH port with a TXT record of build info only. `NSLocalNetworkUsageDescription` and `NSBonjourServices` are in the macOS plist.
- **Keychain preflight** (`keychainPreflight.ts`) checks whether plugin secrets can be stored, using async `safeStorage` under a 10 s timeout, so a keychain that doesn't answer reads as unknown, never a hang. A headless Linux host reports no keyring and plugin secret fields say so.
- **Power.** `setAttachedFrontendCount` in `PowerSaveBlockerService` keeps a host awake while Shells are attached or agents work.
- **Adding and updating hosts** (`HostSetupService`): discovery from `tailscale status --json` and dns-sd/avahi (a missing tool is an empty list), a `BatchMode` probe (platform, installed build read from the build marker, Host mode status, keyring presence), and install/update as a tracked operation (`hostInstaller.ts`): same-platform bundle push or host-side fetch of the client's exact build from the client's release channel, deb preferred with an AppImage fallback on Linux, refusal while agents work (or wait until idle), a staged swap with `.old` backups, rollback on a failed start or wrong build, and a handshake check before the backup goes. Forgetting a host closes its SSH master with `ssh -O exit`.

## Files and the inbox

- **Host-scoped protocols.** A remote view's previews use `daintree-file://host/<hostId>/<capability>/load?path=…&root=…` (likewise `daintree-media` and `daintree-pdf`), parsed in `electron/setup/protocols.ts`. Local URLs are unchanged. A protocol request has no sender, so main mints a per-view capability (`ViewFileCapabilities`, 16 random bytes, dies with the view; the renderer fetches it through `fileTransfer.getPreviewCapability`); the proxy checks it is live and bound to that host, and the host checks only that view's endpoint, project and lease. Range requests get 206/416. Request, stream and download slots and buffered bytes are reserved before any filesystem work.
- **Containment** (`electron/remote/files/hostContainment.ts`): the walk starts at the project folder or a worktree and opens one component at a time with `O_NOFOLLOW`, serving from the descriptor it ends on. On Linux each step opens relative to the parent's descriptor through `/proc/self/fd` (openat). A symlink is never opened through: its target is resolved against the real directory reached and must land inside the same root, and the walk restarts along it, so in-project links work and escaping ones are refused. Link-side `files:read` / `files:search` require a root inside the endpoint's project or worktrees.
- **Downloads and pickers.** The remote host file picker (`src/components/HostFilePicker/`) lists host directories (2000-entry cap); native pickers are split so the dialog opens on this machine for a host path. Downloads open with `O_NOFOLLOW`, hash and send from that descriptor, and verify sha256 and length before placing the file in Downloads. CopyTree copy-as-file downloads the bundle to a private temp dir; the host grants that one exact bundle file to that endpoint for 10 minutes.
- **Materialize.** Every drop, paste and attach goes through `materialize` (`src/services/materialize.ts`): locally it is the identity (paths as given, clipboard images saved to `daintree-clipboard` as before, now 0700/0600); in a remote window the lazy remote materializer uploads bytes and inserts the host path. Uploads read only files the person chose in that window (recorded by the preload's `files.getDroppedFilePaths` over `file-transfer:grant-local-sources` and by the attach dialog, 30 minutes per window).
- **Inbox** (`hostInbox.ts`): `<host tmpdir>/daintree-inbox/clipboard/clipboard-<stamp>-<id>.<ext>` and `…/files/<stamp>-<id>/<name>`, outside every worktree. Directories 0700 and lstat-checked, files 0600 via `O_EXCL|O_NOFOLLOW`, `<id>` is the start of the content's sha256 so the same bytes reuse the existing file, entries expire after 24 h, the newest 50 clipboard images are kept, and the inbox stays under 1 GB. Gemini's include directory follows the host inbox in remote windows.
- **Uploads** (`HostUploadService.ts`): a prepared upload is bound to the endpoint, project, size and sha256; bytes are placed only after the transfer verifies the digest. Over 50 MB asks first (`UPLOAD_CONFIRM_BYTES`), over 500 MB is refused (`UPLOAD_REFUSE_BYTES`); folder upload is not available (the 5,000-file / 500 MB folder caps are declared for it). Retries under the same opId are answered from the host's record (15 minutes, 1,000 entries). **Add to project** (Option/Alt-drop, remote windows only) writes through the containment walk and replaces an existing file only with a single-use replace token the host minted for that exact file, lease and endpoint.
- **Ctrl+V** in an agent terminal of a remote window is intercepted (setting on by default, remote mode only) so the agent gets this machine's clipboard image as an inbox path; plain shells and local windows are never intercepted.

## Port forwards

`PortForwardManager` (`electron/remote/ports/`) keeps one local port per (host, remote port). A forward goes through the host's ControlMaster with `ssh -O forward -L 127.0.0.1:<local>:localhost:<remote>` (`sshForward.ts`), with a local relay holding `[::1]` beside it; with no master it uses a local listener whose connections ride the link as streams (`streamForwarder.ts`, session CALLs `ports.open/data/end/close`, 256 KiB window per stream). The host port number is kept when it is free here. A forward counts only while the session it rides is open; an ssh forward is retired when its session closes and re-added, with a fresh free-port probe, on the next one.

Forwards are made on demand for dev preview and browser panels (the dev-preview proxy asks only the host that owns a preview origin), from **Forward port…** and the Ports view, and for a CLI sign-in callback (a localhost link clicked in a remote terminal is forwarded and opened locally, closing after 10 minutes idle). In a remote-bound view, the webview gate (`electron/window/webviewSrcGate.ts`), guest navigation checks and a per-session request filter admit loopback only for address/port pairs a live forward holds (`isBoundLoopbackUrl` in `shared/utils/urlUtils.ts`).

## Projects across hosts

Projects move between hosts through git, not file copies (`electron/remote/projects/`, `electron/services/projectAcrossHosts/`). The target host matches by normalised remote URLs, checks the branch with `ls-remote`, and otherwise clones as itself under a single-use destination token, into a temp folder renamed into place, then offers a worktree for the branch; an unpushed branch prompts a push first (the preview lists the commits), and a local-only repo travels as a git bundle. Credentials are stripped from remote URLs before they leave either machine. The flow is `project.openOnHost` and the `hostSwitch` namespace, with `projectMatch` on the host.

## Plugins

A plugin's main code runs on the host; its views render in the driving window and their bundles are fetched from the host (`electron/remote/plugins/`, `__dth-<hostId>` paths cached by host, plugin and generation, revalidated on every read). `plugin:invoke` runs on the dispatcher, so a call from a remote view carries `ctx.origin: { kind: "remote", … }`.

- **Person-facing calls** — prompts, toasts, capability consent, clipboard — go to the project's driving endpoint by reverse request (`shellRequests.ts`, `hostRouting.ts`). Each call's caller is carried in `AsyncLocalStorage` (and tagged through the dev worker), so interleaved calls from two projects route correctly. A prompt records the lease it was asked under; when the driver changes it is taken down and re-asked, and an approval from a former driver is never returned. With nobody attached a prompt fails with `NO_FRONTEND_ATTACHED` or waits in an opt-in queue, and first-use consent is a denial.
- **Clipboard** requests need the view's window focused, the view in front, bound to the asking host, and a Shell-owned grant per host, plugin and access, asked once in the capability consent dialog; answers persist in `remoteHostPluginClipboardGrants` (device-owned) and can be reset per host in Settings → Hosts → host (`HostClipboardGrants.tsx`). The host's wait covers the consent dialog's lifetime (`REMOTE_CLIPBOARD_TIMEOUT_MS`).
- **Parity and install-on-host** (`electron/remote/plugins/parity/`, `electron/services/plugin/parity/`): Settings → Hosts → host → Plugins diffs the two machines; Install/Update on host sends this machine's package over RPC chunks and runs the host's normal install path after a platform and blocklist preflight, never downgrading. A missing plugin fails with `PLUGIN_NOT_ON_HOST`; one that can't run fails with `PLUGIN_INCOMPATIBLE` and a reason (`engine`, `platform`, `remote-unsupported`, `untrusted`, `unconfigured`), carried as `details` across the link and the contextBridge. An engine mismatch is reported but the plugin still loads. Nothing syncs automatically.

Author-facing behaviour is in [plugins/host-api.md](../plugins/host-api.md#remote-hosts--when-nobody-is-sitting-at-this-machine), [plugins/distribution.md](../plugins/distribution.md#plugins-on-remote-hosts), [plugins/trust-model.md](../plugins/trust-model.md#plugins-on-a-remote-host) and [plugins/manifest.md](../plugins/manifest.md#remote).

## Metrics, overview and fleet

- **Sampling.** A host samples every 5 s (`HOST_METRICS_INTERVAL_MS`) while at least one Shell is attached: CPU %, memory pressure (macOS memorystatus, Linux PSI), memory and swap, thermal, Linux CPU PSI, observed agent counts, project and worktree counts, the driver, and installed agent CLIs (`HostMetricsSummary`). Unmeasured fields are null, never zero. Summaries go out as `HOST_SUMMARY` on CONTROL.
- **Summary-only links.** With any host configured, the Shell dials every known host at launch for summaries (a host-level connect that installs no router) and keeps about 15 minutes per host (`HostMetricsClient`, `electron/remote/metrics/client.ts`). A user with no hosts dials nothing. A summary-only session counts as an attached frontend for power.
- **Hosts overview** (`src/components/Hosts/Overview/`, action `host.overview.open`): a card per host with sparklines, agent CLIs, plugin parity, the Ports view, other hosts' worktrees and least-loaded placement for new worktrees (which hands over through `project.openOnHost`).
- **Cross-host fleet** (`src/components/Fleet/crossHostFleet.ts`): other hosts' agents can be armed from the overview and receive the draft exactly as typed over each host's link. A vacant lease is allowed; one held by another client is refused with `DRIVEN_ELSEWHERE`. Each target submit carries an opId the host keeps for 10 minutes after it settles (`shared/config/fleetSubmitRetention.ts`; at 10,000 live records it refuses new submits rather than forget one). A submit whose answer was lost is retried under the same opId only within 5 minutes of its first send; after that the failure banner says the outcome is unknown, Retry leaves it out, and sending again is a fresh submit the person confirms. Target lists carry `complete`, false when a pty-host shard didn't answer or the list hit its cap, and a watching fleet run only marks a missing target gone on a complete list.
- **Notifications.** A remote window's own host always notifies it: the host decides and sends `notification.show` with a category, and the Shell plays its own sound and applies its own session mute. Attention events from other hosts are opt-in per host (`HostDescriptor.notificationsEnabled`, off by default) and go to one window, never one already showing that host.

## Settings ownership

`electron/storeOwnership.ts` declares an owner for every store key (`STORE_KEY_OWNERSHIP`: `host`, `device` or `split`), every `terminalConfig` field and every `appState` field, plus the window-states and audit-logs stores; the records are total, so a new key without an owner fails typecheck. Host: agents, accounts, environment, MCP, plugins, forge, run history, per-project state, panel layout and the terminal list. Device: theme, keybindings, terminal appearance, window geometry, voice, privacy, updates, keep-awake, the host list (`remoteHosts`, `hostMode`, `remoteHostsPreferences`, `remoteHostPluginClipboardGrants`). The device keys the feature adds are optional and absent from store defaults, so a non-user's settings file is untouched. Each settings tab declares an `owner` in `src/components/Settings/settingsTabRegistry.tsx`; in a remote window the header chip and section badges say whose settings are being edited (`src/hooks/useSettingsOwner.ts`). Nothing syncs between hosts.

## Security model

- **Trust boundary.** A Host trusts a Shell that presents its token over a socket only its own user can reach (0600 socket, 0700 directory, owner-checked), which in practice means the Shell's user can already SSH in as that user. A Shell trusts a Host no further than its own views: every inbound message is zod-validated, oversize frames end the session, and every Shell-side action a host asks for is validated and scoped to the asking view's project.
- **Host-initiated dispatch.** A host can run renderer actions in a Shell's view only from `HOST_DISPATCHABLE_ACTION_IDS` (`electron/remote/client/viewRequests.ts`), a default-deny list of terminal, worktree, agent, recipe and context actions; a new action stays out until added. Calls always go out unconfirmed (confirm-gated actions raise the Shell's own dialog naming the host), origin is always `external`, and no reusable approval is returned. The manifest a host sees is filtered by the same list.
- **Viewless MCP.** A host executes a small set of agent actions itself (`terminal.new`, `terminal.sendCommand`, `worktree.create`) when no frontend is attached (`electron/services/viewless/`); anything else is `NO_FRONTEND_ATTACHED`. This only happens once Host mode installs the drive-target resolver (`isMcpHostRoutingEnabled`), so a plain local app routes MCP exactly as before.
- **Hygiene.** Error envelopes are stripped of paths, stacks, tokens and context (above). Transfer failures cross as fixed reason codes. The host inbox, clipboard dir and SSH control directory are owner-only. Terminal contents and file contents are never logged.

## Decisions taken

These were open questions with defaults chosen; each matches the code today.

- One host per window; Cmd/Ctrl-click opens a new window.
- One driver per project with explicit takeover, no mirroring — and exactly one driving **endpoint**, not every window of the driving client.
- Panel layout and the terminal list are host-owned; zoom, sidebar widths, panel sizes and palette habits stay per client.
- Credentials are per host; nothing is synced. No settings export/import across hosts (config-bundle export/import is refused in remote windows), no "copy project setup", and project ids are never auto-committed.
- A headless Linux host accepts that plugin secrets are unavailable, and the UI says why.
- Linux installs prefer the deb, with an AppImage fallback.
- The assistant is an agent PTY and runs on the host like any agent; `help-assistant:*` is host-owned.
- Cross-host notifications are opt-in per host; `notificationsEnabled` governs other hosts only, and a remote window's own host always notifies.
- Ctrl+V image interception is on by default, in remote windows' agent terminals only.
- Uploads confirm at 50 MB and refuse at 500 MB (5,000 files per folder, declared for folder upload).
- "Add to project" drop ships.
- Hosts follow the client's release channel for installs; a host's own updater channel is untouched.
- Viewless MCP execution is gated to Host mode, not the plain local app.
- Settings → Hosts is visible on macOS and Linux as the single entry point for adding the first host; everything else stays hidden until a host exists.
- Framing runs in main, not a utility process (see [Testing](#testing)); no bridge binary on the host.
- Locally, clipboard images keep the `daintree-clipboard` directory; only remote windows use the host inbox.
- Keep-awake is device-owned: each machine keeps itself awake for its own agents.

## Known limits

- **macOS containment.** Node has no `openat` on macOS, so each containment step is a before-and-after device/inode chain check rather than a descriptor-relative open; a process on the host that swaps folders fast enough has a small TOCTOU window. Such a process could already read those files.
- **DNS to loopback.** A public hostname that resolves to 127.0.0.1 (for example `localtest.me`) passes the guest gate, because `webRequest` exposes the name, not the resolved address. This matches local windows.
- **Self-minted grants.** A Shell can request a host-minted clone destination token or checkout offer for itself; the host validates the folder and branch itself, since it can't verify a person's confirmation.
- **Persisted clipboard answers.** Plugin clipboard grants and denials persist in `remoteHostPluginClipboardGrants`; they are reset per host from Settings → Hosts → host, not from the plugin's own settings.
- A macOS case-only path difference can get past the in-process clone reservation (the non-overwriting rename still protects content).

## Unverified on real hardware

Covered by unit tests with injected spawners, the direct-socket harness and the local real-ssh test, but not yet exercised for real:

- A real remote machine, and a Linux host over ssh. `ssh -L` socket forwarding through a ControlMaster and `ssh -O forward` port forwards are verified against a real OpenSSH `sshd` on macOS (a private user-mode `sshd` on 127.0.0.1, `electron/remote/__tests__/ssh.e2e.test.ts`), but only on the same machine.
- A real LaunchAgent at login (including Background Items approval) and a `systemd --user` unit with linger on a headless box.
- `dns-sd` and `avahi-publish-service` advertising on a LAN, and the Local Network prompt in a signed build.
- A multi-file drop through the real preload `files.getDroppedFilePaths` bridge (the binding is tested through `electron/utils/droppedFilePaths.ts`, not the loaded preload).
- A Linux host socket under `/run/user/<uid>` (descriptor-relative containment runs only on Ubuntu CI).
- Host installs (bundle push, host fetch, deb and AppImage) and stop/rollback on a live host.
- Real cross-machine latency.

## Testing

- **Integration harness.** `electron/remote/__tests__/e2e.harness.test.ts` with helpers in `electron/remote/__tests__/harness/` (`remoteHarness.ts`, `fakeElectron.ts`, `fakePtyHost.ts`, `fakeView.ts`, `fakeWorkspaceHost.ts`, `fakePluginService.ts`, `harnessState.ts`, `poll.ts`) runs a Host and a Shell in one process joined by a real Unix socket, started by the real `startRemoteHosts` with Host mode on; the Shell dials this process's own listener through the direct transport instead of ssh (`startRemoteHosts` takes `createTransport` and `hostLocation` for this). Scenarios: boot and Host mode status, hydrate through the real split, typed invoke with error details, event delivery, terminal I/O and acks, resize scoping, the resize lease (a non-driver ignored until it takes over), worktree-port RPC and events with host-side request validation, a host-file preview through the host-scoped protocol with a media Range, an upload through the renderer's materializer into the inbox with sha256 and dedup, plugin invoke with push and a prompt answered by the driving view, a prompt with no frontend attached, viewless `terminal.new` with every renderer detached, reconnect with exactly-once replay and snapshot reset on ring overflow, a fresh session after the host's listener restarts (endpoint reopened, resync, terminal repainted from a snapshot), a clone whose reply was lost resolving by operation id, and latency. - **Latency.** The latency scenario measures keystroke echo round trips idle and under back-to-back 32 MiB dropped-file uploads through the real upload path into the host inbox plus an output flood (about 250 MiB/s), and prints a `[remote-harness] keystroke RTT ms {...}` line.
