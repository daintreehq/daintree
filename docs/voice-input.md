# Voice dictation & transcription pipeline

Daintree can dictate directly into a terminal (or the Daintree Assistant) input: real-time streaming transcription, client-side voice-activity detection (VAD), push-to-talk, a pause state, target-follows-focus routing, and an optional whole-passage AI cleanup pass. The feature spans both processes — microphone capture and editor injection live in the renderer, while WebSocket transport, segmentation, and the OpenAI/Deepgram/Grok backends live in the main process. This doc captures how the pieces fit so the flow doesn't have to be reverse-engineered from ~2,500 LOC across the two sides.

For how these IPC channels are registered and dispatched, see [ipc-services.md](./architecture/ipc-services.md).

## Mental model

There are two long-lived singletons, one per process, talking over a small set of `voice-input:*` IPC channels:

- **Renderer:** `voiceRecordingService` (`src/services/VoiceRecordingService.ts`, ~1500 LOC) owns the microphone, the `AudioContext`/worklet capture graph, session lifecycle (arming → connecting → recording → finishing), all keyboard wiring (PTT, Escape, blur), and **all editor injection**. It pushes raw PCM16 chunks to the main process and applies the delta/complete/file-token/paragraph events it gets back to the focused terminal's draft.
- **Main:** `VoiceTranscriptionService` (`electron/services/VoiceTranscriptionService.ts`) is a thin selector + event-forwarder over a pluggable `TranscriptionProvider`. The provider owns its own WebSocket, auth, audio encoding, segmentation, reconnection, and drain. Three providers exist today: `OpenAITranscriptionProvider`, `DeepgramTranscriptionProvider` and `GrokTranscriptionProvider`.

The renderer never knows which backend is in use; the main process never touches the editor. The IPC handler (`electron/ipc/handlers/voiceInput.ts`) is the seam — it forwards provider events to the renderer, runs post-processing (dictation commands, paragraph splitting, file-link detection), and exposes correction + mic-permission RPCs.

```text
 RENDERER (src/)                          MAIN (electron/)
 ┌────────────────────────────┐          ┌──────────────────────────────────────────┐
 │ voiceRecordingService      │          │ voiceInput.ts (IPC handler)                │
 │  AudioContext 24kHz        │  audio   │   getService() → VoiceTranscriptionService │
 │  pcm-processor worklet ────┼─chunk───►│     ├─ OpenAITranscriptionProvider          │
 │  RMS level → glow          │  (raw    │     │    └─ openaiVadWorker (Silero v5)      │
 │                            │  PCM16)  │     └─ Deepgram… (server-side VAD)          │
 │  onDelta / onComplete  ◄───┼─events───┤   provider.onEvent → applyDictationCommands │
 │  onParagraphBoundary   ◄───┤          │     → split → send delta/complete/boundary  │
 │  onFileTokenResolved   ◄───┤          │   detectFileLinkTokens → VoiceFileLinkResolver
 │  onError / onStatus    ◄───┤          │   correct() → VoiceCorrectionService        │
 │                            │          │                                            │
 │  injects into terminal     │  correct │                                            │
 │  draft (terminalInputStore)├─RPC─────►│                                            │
 └────────────────────────────┘          └──────────────────────────────────────────┘

```

## End-to-end flow

1. **Invoke.** A keybinding, palette, menu, or toolbar press hits `voiceInput.toggle` / `voiceInput.toggleAssistant` / `voiceInput.togglePause` (`src/services/actions/definitions/voiceActions.ts`). Toolbar callers use `voiceRecordingService.toggle()` directly; hotkey callers route through `toggleFocusedPanel()` / `toggleAssistant()`, which resolve the target (see "Target routing") and call `startOrToggle()`.
2. **Arming.** `toggle()` synchronously sets `status: "arming"` in the store (`setArming`) so the target panel border and toolbar paint a pre-recording cue within ~50ms, before any `await`. A second press during arming aborts (`cancelArming()` bumps `startRequestId` so the in-flight `start()` bails at its next staleness check).
3. **Permission + capture.** `start()` checks/raises OS mic permission via IPC (`checkMicPermission` / `requestMicPermission` / `openMicSettings` — macOS `systemPreferences`, Windows `ms-settings`, Linux best-effort), then `getUserMedia`, then builds a 24kHz `AudioContext`, loads the `pcm-processor` worklet (`/pcm-processor.js`), and connects a silent keep-alive oscillator so Chromium doesn't suspend the capture-only context when backgrounded. Capture starts **eagerly**, before the WebSocket is open, and startup audio passes through three holders in turn: the renderer's per-attempt queue holds chunks until it sends the `voiceInput.start` request (normally nothing, since capture attaches just before; a retarget waiting on the previous session's drain can hold seconds), then sends them straight after it; the session's `preStartAudio` in main (`electron/ipc/handlers/voiceInput.ts`) holds them while it loads the service and assembles keyterms; and the provider's pre-connect buffer holds them until the session is ready. The invoke and the sends share one ordered IPC pipe, and `handleStart` publishes the session with its buffer armed before its first `await`, so no chunk can reach a previous session's provider.
4. **Stream.** Each worklet message carries an `ArrayBuffer` of PCM16. The renderer computes RMS for the UI glow (`setAudioLevel`, throttled to one RAF) and ships the chunk via `voiceInput.sendAudioChunk` (`ipcRenderer.send`, fire-and-forget). Main forwards it to the active provider.
5. **Segment + transcribe.** The provider commits utterance segments (VAD-driven for OpenAI, server-side for Deepgram) and emits `delta` / `complete` events back through the handler.
6. **Inject.** The handler reads dictation commands over the whole utterance rather than each provider segment, then post-processes each `complete` (paragraph splitting, file-link detection) and sends `delta` / `complete` / `paragraph_boundary` / `file_token_resolved` to the renderer. `voiceRecordingService` writes them into the focused terminal's draft through `terminalInputStore`. A segment whose commands still hang on what comes next (one ending in "send", "send it", "new" or "new line", or an opening "slash" still waiting for its name) is held in main, its preview still showing, until the utterance shows what it was (`electron/services/voiceUtteranceCommands.ts`, #14801). Break commands are read where a segment closed at a pause (Deepgram `speech_final`; an OpenAI VAD speech-end commit, marked `endsAtPause` even when the speaker went on before its transcript landed) or at a stop; one cut mid-speech that more words follow stays words. An utterance that ends speech (Deepgram `speech_final`, which can arrive as an empty final that only marks the end; for OpenAI, the last acknowledged commit with the VAD hearing silence) in "send it" has the phrase stripped, however the provider split it, and the last `complete` carries `send`. Deepgram's 300ms endpoint can fall inside a sentence, so main holds such a Deepgram completion for another 700ms (1.5s after a `SpeechStarted`): more words in that time release it with "send it" kept literal and no send, and a stop or a dying provider releases it stripped with no send. While still recording, the renderer hands that to the panel's composer (`voiceRecordingService.onSpokenSend`, registered by `useVoiceWaitSubmit`), which runs Enter's dictation path: stop, wait for the correction, send. A draft under three words that doesn't open with a command (`/compact`), a disabled composer, or no composer only stops dictation. A spoken opening command and a trailing "send it" in one utterance ("slash compact, send it") write the command and send it: the send comes off first, so it is never read as the command's argument. "send it" the speaker went on past, or in a clause that is negated or a question ("don't send it", "where should the handler send it"), stays literal, even when an earlier segment opened that clause.
7. **Stop + correct.** A graceful `stop()` first posts `{ type: "flush" }` to the worklet, which sends the partial chunk it is still filling and then a `{ type: "flushed" }` marker and stops emitting. Port messages arrive in order, so once the marker lands every chunk has been forwarded (bounded by `WORKLET_FLUSH_TIMEOUT_MS`). Only then is capture torn down and the remote stop sent, so it reaches main behind the last chunk. Main drains the provider gracefully. A stop that lands while the session is still `starting` (loading the service or assembling keyterms) with audio already held waits for the start to hand that audio to its provider, then drains it through the provider's stop-before-ready path instead of discarding it. With nothing held, the session ends as `cancelled` before any socket opens. The renderer then flushes any trailing interim text and — if AI correction is enabled and the stop was deliberate — fires one whole-passage correction pass (`runCorrection`) over the dictated range.

### Text-injection model (important)

Interim `delta` text is **never** written into the editor document. It accumulates only in `liveText` in `voiceRecordingStore` (or, for a delta flagged `replace`, overwrites its item's preview: Deepgram's interims are whole revisions of the span since its last final, not additions) and is rendered as a CodeMirror ghost-widget decoration (`useVoiceDecorations`, `src/components/Terminal/hooks/useVoiceDecorations.ts`), outside the doc model. Only a `complete` event writes real text, so the editor's undo history records **one transaction per utterance** rather than one per token (#9172). The service tracks several draft offsets per panel buffer to splice correctly:

- `sessionDraftStart` — where the whole session's dictated text begins (anchor for `runCorrection`).
- `draftLengthAtSegmentStart` — where the current segment begins; a `complete` slices back to here and replaces, so re-firing is idempotent.
- `activeParagraphStart` — paragraph anchor for boundary handling.

A leading separator space is inserted via `getVoiceInsertMetadata` when the existing draft doesn't end in whitespace.

## TranscriptionProvider abstraction

`electron/services/voice/TranscriptionProvider.ts` defines the contract. A provider owns its own WebSocket connection, authentication, audio encoding, server-event parsing, reconnection, and any timers its protocol needs. `VoiceTranscriptionService` only selects one (from `settings.transcriptionProvider`), subscribes, and forwards — it holds no transcription logic itself and tears the previous provider down on every `start()` so a provider switch or plain restart can't leak a socket or listener.

```ts
interface TranscriptionProvider {
  readonly hasServerVAD: boolean; // false → provider drives client-side segmentation
  start(settings): Promise<VoiceStartResult>;
  sendAudioChunk(chunk: ArrayBuffer): void;
  commitParagraphBoundary(): void; // flush at a user-driven Enter boundary; no-op for server-VAD
  stopGracefully(): Promise<void>; // drain pending transcripts, then close
  stop(): void; // hard stop
  destroy(): void;
  onEvent(listener): () => void;
}
```

`VoiceTranscriptionEvent` is the neutral event union: `delta` / `complete` / `paragraph_boundary` / `error` / `status`. A `complete` may carry `uncertain`: character spans of the words in its `text` the provider scored below its own cut-off. Deepgram fills it from each final's `words[].confidence`, below 0.65 (Deepgram's guidance for its calibrated scores); OpenAI's transcription model reports no word confidence, so its completions carry none. See [Unsure words](#unsure-words).

| Provider | `hasServerVAD` | Endpoint | Audio on wire | Segmentation | Keep-alive |
| --- | --- | --- | --- | --- | --- |
| `OpenAITranscriptionProvider` | `false` | `wss://api.openai.com/v1/realtime?intent=transcription`, model `gpt-live-transcribe` | base64 JSON `input_audio_buffer.append` | client-side Silero VAD process + 15s cap on continuous speech | ping/pong heartbeat (20s idle, seconds once audio is unanswered) |
| `DeepgramTranscriptionProvider` | `true` | `wss://api.deepgram.com/v1/listen`, model `nova-3`, `punctuate` + `smart_format` + `interim_results` | raw binary frames, `linear16` @ 24kHz | server-side `endpointing=300`; each span between finals is one item | `KeepAlive` frame (5s) |
| `GrokTranscriptionProvider` | `true` | `wss://api.x.ai/v1/stt`, model `grok-voice-transcribe-2.0`, `interim_results` (+ `format` for a language xAI formats) | raw binary frames, `pcm` @ 24kHz, held until `transcript.created` | server-side `endpointing=300`; each utterance is one item, completed by its `speech_final`, which restates the whole utterance | 100ms of silence after 3s with no audio (a paused dictation) |

All three buffer up to `AUDIO_BUFFER_MAX_CHUNKS` (150) chunks / `AUDIO_BUFFER_MAX_BYTES` (720,000 bytes, 15s) while connecting or reconnecting, then flush on session-ready. The cap matches the renderer's own startup queue (`MAX_QUEUED_CHUNKS`), and the IPC handler's pre-start buffer uses the same one. A stop before the session is ready waits up to `STOP_CONNECT_TIMEOUT_MS` (3s) for it, then flushes, commits and drains. OpenAI skips a final commit under 100ms (`MIN_COMMIT_BYTES`), which it would reject. WebSocket URLs accept env overrides (`DAINTREE_REALTIME_WS_URL`, `DAINTREE_DEEPGRAM_WS_URL`, `DAINTREE_GROK_WS_URL`) for testing.

Grok's utterance final restates the whole utterance, chunk finals (`is_final` alone, sent at a phrase break) included, so the provider never completes a chunk final: interims and chunk finals replace one preview, and the utterance final completes it once. Grok times a chunk final from the utterance's start though it holds only its own words, and an interim from the end of the chunk before it, so the preview keeps the locked chunks in the order they end and places an interim after the chunks that end where it starts. An utterance final starts at the utterance's start too, so its own timing can't say which chunks it restates; its words' timing can, since Grok times a word the same in a chunk final and in the final restating it. The locked chunks that start before its first word land ahead of it, and so do all of them when it holds under half the words of those it claims to restate. Without word timing, a run of chunks counts as restated when its first chunk and the run as a whole open the final (three in four of their words, in order). A final that carries less than its chunks, or comes back empty, never takes their words with it, and a warning logs how many chunks were kept. `transcript.done`'s tail is read the same way. An interim cut mid-phrase ends in "..." or a dash that the next interim drops, so the preview strips it; a final keeps its own. Chunk finals still confirm replay audio, and on a reconnect the open utterance's chunk text is carried ahead of the new connection's results, since that audio isn't resent. Grok sends no speech-started event, so the provider emits `speech_started` itself when the outgoing audio rises to speech level after 200ms of quiet, and again straight after an utterance final if the speaker is already talking; the handler holds a Grok "send it" exactly as it holds Deepgram's.

### Adding a provider

1. Implement `TranscriptionProvider` in `electron/services/voice/`. Set `hasServerVAD`; if `false`, drive your own commit cadence and implement `commitParagraphBoundary()` to flush mid-utterance.
2. Add the literal to `VoiceTranscriptionProvider` in `shared/types/ipc/api.ts` and to `VALID_TRANSCRIPTION_PROVIDERS` in `electron/ipc/handlers/voiceInput.ts`.
3. Add the `case` to `VoiceTranscriptionService.createProvider`.
4. Give it an API-key field (`<issuer>ApiKey` on `VoiceInputSettings`) and an entry in `VOICE_TRANSCRIPTION_PROVIDERS` (`shared/config/voiceProviders.ts`); the configured check and the settings key row both read from there.
5. If the backend scores each word, pass its words and your own cut-off to `flagUncertainWords` (`shared/utils/voiceUncertainWords.ts`) and put the spans on `complete` as `uncertain`. Calibration differs between providers, so don't borrow Deepgram's cut-off. Otherwise leave it off.

## OpenAI session config

`OpenAITranscriptionProvider` sends one `session.update` on open (and re-sends the identical payload on every reconnect, rebuilt from the frozen settings snapshot):

```jsonc
{
  "type": "session.update",
  "session": {
    "type": "transcription",
    "audio": {
      "input": {
        "format": { "type": "audio/pcm", "rate": 24000 },
        "transcription": {
          "model": "gpt-live-transcribe",
          "languages": ["en"], // array supersedes the deprecated singular `language` — never send both
          "delay": "low",
          "keywords": ["Daintree"], // omitted entirely when nothing survives sanitising
          "prompt": "Keywords: Daintree",
        },
        "turn_detection": null,
      },
    },
  },
}
```

`languages` is a one-element array built from the single language code in settings, falling back to `["en"]` when unset. `delay` (`minimal` | `low` | `medium` | `high` | `xhigh`) governs how long the server buffers before emitting a partial `...transcription.delta`. It isn't only a preview setting: at `low` the final `...completed` is the deltas joined, not a second pass over the committed buffer (#14852), so a higher tier gives the words that reach the draft more context too. It stays `low` because the replay clips didn't reward more: `npm run perf voice-tuning` found `medium` and `high` level with `low` session for session on word error and term recall, for a median 31ms and 99ms more before the last final (#14625). The tier lives in `OPENAI_TRANSCRIPTION_TUNING` (`openaiTranscriptionTuning.ts`) beside the segmentation it is measured with.

The types for `keywords` and `languages` are hand-written in the provider: the installed `openai` SDK's `AudioTranscription` has no `keywords` field and its `model` union predates `gpt-live-transcribe`. `language?: never` on the local type makes reintroducing the deprecated singular field a compile error.

## OpenAI client-side VAD

The OpenAI provider sends `turn_detection: null` explicitly and segments itself. The explicit `null` matters: omitting the field makes the server apply a default VAD, after which it acks commits but emits no transcription. Every documented `gpt-live-transcribe` example still shows `null`, and whether the model would accept a server-VAD block is unverified — adopting one would be its own change, with the error response checked first.

The old approach committed on a blind 2-second interval, which cut words mid-pause and added up to ~2s of end-of-speech latency. It's replaced by a Silero VAD v5 side-chain (`electron/services/voice/openaiVadWorker.ts`, via the `avr-vad` package) running in a dedicated `utilityProcess` child (`openaiVadProcess.ts`, one per voice session, `serviceName` `daintree-voice-vad`) so ONNX inference (~every 32ms) never jitters the Electron main loop — and, since ONNX Runtime can abort in native code (#12577), so an abort ends that child instead of main. The same 24kHz mono PCM16 stream sent to OpenAI is also fed to the child, which resamples to Silero's 16kHz internally.

Retiring a VAD posts `destroy` and waits: the child drains its in-flight model load and inference, releases the ONNX session, reports `drained` and exits 0. A child still alive `VAD_RETIRE_KILL_MS` (3s) later gets a raw SIGKILL — `UtilityProcess.kill()` blocks main on macOS (#11069), and only that process dies either way. App quit gives outstanding drains `VAD_DRAIN_BUDGET_MS` (1s) inside the cleanup phase. Any exit the provider did not ask for, like a native abort, drops it into degraded mode: no speech events, commits every `BLIND_COMMIT_MS` (8s) alone, dictation keeps working.

### VAD worker protocol

`electron/services/voice/openaiVadWorkerProtocol.ts`:

- **Main → VAD (`VadWorkerInbound`):** `audio` (PCM16 `ArrayBuffer`, structured-cloned across the process boundary) | `destroy`.
- **VAD → main (`VadWorkerOutbound`):** `ready` | `speech-start` | `pause` | `speech-end` | `drained` | `error`.

A `VADMisfire` (sub-`minSpeechFrames` blip) is reported as `speech-end` so the provider always returns to not-speaking. VAD defaults: 512-sample frames, ~768ms redemption holdover, 0.5/0.35 positive/negative thresholds — tuned for dictation. `pause` is a short break inside speech, once per break: avr-vad's own end-of-speech count reaching 5 of its 24 frames (~160ms), counted as avr-vad counts it (frames under 0.35, starting over on a speech frame).

### Commit / barge-in gating (`OpenAITranscriptionProvider`)

- **`speech-end`** → commit the segment (`maybeCommitSegment`) so it streams back.
- **`speech-start`** → **barge-in clear**: drop the silence the server buffered since the last commit (`input_audio_buffer.clear`), then replay a ~300ms pre-roll (`VAD_PRE_ROLL_BYTES`) so the utterance onset survives the clear. This clear is gated on `vadHasEndedSpeech` — the very first speech-start of a (re)connection must **not** clear, because audio captured before the worker was ready might be real speech, not confirmed silence.
- **Cap** (`OPENAI_TRANSCRIPTION_TUNING.maxSegmentMs` = 15s): while speaking, force a commit once a segment has run this long, so the server buffer stays bounded. Every such cut lands wherever the speaker is and costs the words around it, so it is long: on the replay clips 15s halved the long clips' word error against the old 8s, at no cost after the stop (#14625).
- **`pause`** → commit, only when the tuning sets `minSegmentMs` and the segment has run that long. Off in production: on synthesised speech it did no better than the 15s cap, because the commit takes everything sent up to the chunk the pause was heard in, and a ~200ms synthesised pause is short enough for that to clip the next word. It stays as a `voice-tuning` arm for recordings. A cut there never counts as a pause (`endsAtPause`), so break commands and a spoken send still wait for the end of speech.
- **Degraded mode:** if the worker fails to spawn / load / crashes, the provider falls back to a periodic `BLIND_COMMIT_MS` (8s) commit with no speech gating — dictation still works, just without speech-aware boundaries.
- **`MIN_COMMIT_BYTES`** (4800 ≈ 100ms): OpenAI rejects an undersized commit with a fatal error, so sub-threshold commits are skipped.

Audio always streams to OpenAI continuously regardless of speech state; the VAD only governs _when_ to commit and _when_ to clear, so an under-detecting VAD can never strand audio — the backstop and final commit still flush it.

### Connection resilience

Exponential backoff with full jitter (`RECONNECT_INITIAL_MS` 150 × `1.5^attempt`, capped 3s, up to `RECONNECT_MAX_ATTEMPTS` 5). A ping/pong heartbeat detects half-open sockets and terminates them. It checks every `HEARTBEAT_TICK_MS` (2s): idle, it pings every 20s and allows 20s for the answer. Once audio has gone out since the server was last heard from, it pings at once and allows `HEARTBEAT_ACTIVE_MS` (3s), so a dead socket that is swallowing speech is noticed in about 8s while streaming. Any server frame counts as an answer. Each ping also gets the time its backlog needs at `HEARTBEAT_FLOOR_BYTES_PER_MS` (64, the audio stream's own wire rate): the bytes sent since the last ping a pong answered, which TCP ordering proves delivered. A ping queued behind seconds of reconnect flush on a slow uplink therefore isn't a false timeout, while steady streaming adds only a couple of seconds. Write completion isn't used, since Node batches buffered frames and completes them together. Every connection callback re-checks `sessionId` and socket identity before it touches shared state or timers, so a stale timer, message or late close can't act on a newer connection (the #4850/#4851 stale-callback guard). The drain finishes precisely when `pendingCommits` hits zero. Each commit yields exactly one terminal result: `...transcription.completed`, `...transcription.failed`, or a `conversation.item.done` that carries text (an empty `.done` is a placeholder and leaves the drain waiting). Results are deduped by `completedItemIds`, with `DRAIN_TIMEOUT_MS` (3s) as a backstop.

Audio whose transcript hasn't landed is kept in a replay ledger: each commit as a segment, tagged with its item once `input_audio_buffer.committed` acknowledges it, plus the uncommitted tail. A tagged segment is released when its item's transcript is emitted; an ack without an item id releases its segment at once, and so does the ack of an item whose transcript beat it. On a drop everything still waiting, acknowledged or not, survives the reconnect and is resent first, each segment followed by its commit, then the reconnect-window audio. `gpt-live-transcribe` streams deltas before the commit, under the item id its ack later reports, so a dropped item usually has a preview showing either way. An acknowledged item's text goes with its segment; the unacknowledged ones pair off with the remaining audio in commit order (segments the cap evicted, then untagged segments, then the tail). Those previews stay up through the reconnect and are retired (an empty `complete` for the old item) as the replay goes out, which transcribes the words again under new items. Each segment keeps whether the VAD closed it at a pause, and its replayed commit says so again, so the new item's transcript still carries `endsAtPause`; text settled from an old connection's interim words carries `incomplete`. A finished transcript queued behind a replayed segment is replayed with it, so the draft keeps commit order. Each stretch of replayed audio keeps the old text as a fallback until its own new transcript is emitted: a session that ends first (reconnect exhausted, a fatal error, a stop whose drain times out) lands the better of that and the new interim text, in commit order, and so does a drop while the stop is draining, which doesn't reconnect. A tail the VAD had already called silence is cut to its last 2s (`REPLAY_SILENCE_KEEP_BYTES`), and the ledger is capped by `replayMaxBytesFor` at the reconnect window's 33s plus a segment at the cap and 12s to notice the drop (60s at the 15s cap): the oldest segment goes whole, never replayed without its start, and its item settles with its interim text at the drop; only the open tail is cut chunk by chunk. The new connection's VAD never hears the replayed audio, so a one-shot `BLIND_COMMIT_MS` backstop commits it if no live speech takes over.

`classifyOpenAIError` / `classifyCloseCode` are pure, exported, and unit-tested. Transient codes (`rate_limit_exceeded`, `server_error`; close codes 1006/1011/1012/1013) keep the session alive and reconnect; everything else is fatal and tears down.

## Recording modes & session states

`VoiceInputStatus` (`shared/types/voice.ts`): `idle | arming | connecting | recording | paused | reconnecting | finishing | error`. `arming` is renderer-only (the backend never emits it). `isActiveVoiceSession()` deliberately excludes `arming` and `error` so a second hotkey press during arming completes the start instead of being read as a stop.

- **Tap or hold (the default).** `recordingMode: "tap-or-hold"`. Recording starts on key down through `toggle()`, so taps behave exactly like toggle mode and the arming cue shows at once. A release more than 400ms (`HOLD_THRESHOLD_MS`) after the press stops the session, but only if speech was heard during the hold: at least two ~100ms capture chunks at speech level (`isSpeechLevel`, ~-40 dBFS RMS), so a click or room noise doesn't count. Transcript deltas aren't used, because a session still draining can deliver its text after the next press started. Releasing before any speech counts as a tap, so a thumb lingering on Cmd doesn't end the session. The decision is made once, at release; speech heard afterwards never stops a tap. Migration 038 moved stored `"toggle"` values here, since electron-store had written the old default to every install. The macOS default key is Cmd+D; Windows keeps Ctrl+. and Linux Ctrl+Alt+, because Ctrl+D is a shell's EOF.
- **Toggle.** Press to start, press again to stop and keep the text. `recordingMode: "toggle"`.
- **Escape cancels.** Once every overlay, menu and focused widget has had its turn (`registerEscapeFallback`, or the target composer handing it over), Escape ends the session and takes the dictation's text back out of the draft (#14631). The pieces it removes come from the session's `dictationRangeStore` record: each utterance with its separator, each paragraph break, and the space a caret dictation (#14634) gave the words ahead of the text after them (`separatorAfter`) while it is untouched and still right after something removed, so text typed before, between or after them stays and a dictation mid-draft leaves the text on both sides as it was. Each removal is written with `expectDraftChange`, so other sessions' ranges follow the text actually removed, and a caret the composer last showed stays on the text it was in. Main ends the session through `voiceInput.cancel` without draining it, and the renderer drops anything the session still had in flight, so no final, file link or correction lands afterwards. If any of those pieces was edited (a file-reference swap counts, since it rewrites the words), Escape stops and keeps instead, like the dictation key. In the composer the removal is one undo step, so Cmd+Z brings the text back even when the cancel emptied the draft. A rewrite's instruction (#14635) is cancelled the same way: it never reached the draft, so nothing comes out, and the selection is released untouched. A push-to-talk or tap-or-hold press still held when Escape cancels is let go, so its release afterwards stops nothing.
- **Push-to-talk.** `recordingMode: "push-to-talk"`. Capture-phase `keydown` records the trigger key's `code`; `keyup` of that key (or of `MetaLeft`/`MetaRight`, because macOS swallows the trigger keyup while a modifier is held) stops. Push-to-talk and tap-or-hold share this listener, and a release only acts on a press that started (or resumed) a recording: the dispatched action claims the press (or, when the global keybinding listener ran the action first, leaves a claim the keydown takes if it was made after `event.timeStamp`), so a press that completes a chord such as Cmd+K Cmd+D, or one that stopped a session, does nothing on release. A `blur` listener is the safety net — Chromium dispatches no synthetic keyup on focus loss, so a Cmd+Tab mid-press would otherwise leave the session running. Non-keyboard entry points (palette, menu, agent) fall back to stop-on-second-invoke via `startOrToggle()`; toolbar callers keep calling `toggle()` directly and are unaffected by the mode.
- **Paused.** `pause()` posts `{ type: "setPaused", value: true }` to the worklet (PCM emission stops), freezes the elapsed counter, and keeps the WebSocket open. A 60s auto-stop (`PAUSE_AUTO_STOP_MS`) terminates an abandoned pause so an idle Realtime session isn't billed. `resume()` re-enables emission and folds the paused duration into the elapsed offset. `togglePause()` is exposed as `voiceInput.togglePause`. A renderer subtlety: the local `paused` override is invisible to the backend, so benign backend `recording`/`reconnecting` status ticks are **suppressed** while paused (`onStatus`) to avoid silently exiting pause.
- **Target-follows-focus.** The hotkey is a global stop first: if a session is active (or arming) anywhere, `toggleFocusedPanel()` ends it via `stopAnySession()` without consulting focus or the lock, so a press never moves a recording (#12832). Only when idle does it resolve the dictation target at the instant the hotkey fires (synchronous reads, before any `await`, for #6959/#8887): a pinned `lockedTarget` wins; else if the Assistant input owns focus (`isAssistantFocused()` via `macroFocusStore`, not `panelStore.focusedId`) it routes there; else the focused PTY panel. Only PTY-backed panels are eligible (`panelKindHasPty`) — browsers/dev-preview have no input surface. `recentTargets` (MRU, max 3) and `lockTarget`/`unlockTarget`/`recallRecentTarget` back the context-menu recall affordances.

### Lifecycle teardown triggers

`stop()` is idempotent (single in-flight `stopPromise`) and is also driven by: PTT keyup/blur, panel close (`panelStore` subscription), project mismatch, system suspend/wake (`systemSleep.onSuspend`/`onWake`), backend `idle` status, and fatal errors. HMR disposes the singleton (`import.meta.hot.dispose → destroy()`) so old `ipcRenderer.on` listeners don't double-fire deltas.

## AI text correction

`electron/services/VoiceCorrectionService.ts`. On by default, and effective whenever an OpenAI API key is configured (migration 037 turned it on once for existing installs). After a **deliberate** graceful stop (not error, cancel-to-restart, or backend teardown) the renderer fires one whole-passage cleanup over the dictated range (`runCorrection` → `voiceInput.correct` IPC → `VoiceCorrectionService.correct`). It marks the range with the `cm-voice-pending-ai` decoration, sends the full passage at reasoning effort `none` to the cleanup model picked under AI text correction, `gpt-6.1-terra` by default or `gpt-6-luna` (`VOICE_CLEANUP_MODELS`; spoken rewrite of a selection uses the same one; a stored `correctionModel` outside the list goes back to `VOICE_CLEANUP_AI_MODEL` on read, and migration 040 moved every existing install to Terra once) via the OpenAI Responses API with a strict JSON schema (`CORRECTION_RESULT_SCHEMA`), and swaps the result in only if the region is still intact and unambiguous — otherwise it keeps the raw text. Best-effort throughout: the timeout is 7s for a short passage and scales with length up to 60s, and any failure leaves the raw text.

Prompt construction lives in `shared/config/voiceCorrection.ts`:

- `CORE_CORRECTION_PROMPT` — fixed cleanup rules aimed at the message the speaker would have typed to the agent (fillers, false starts, verbal tics and empty hedges taken out, run-ons broken into sentences, explicit self-corrections resolved, counted lists laid out as numbered lists, mishearings fixed, every instruction kept in the speaker's own words, and the same words kept where they carry meaning: a "Yeah" answering the agent, "just" meaning only, a guess, a thing that only partly works, an "obviously") and a name the context spells or the speaker spells out written that way, in every mention before the spelling as well as after, with a spelling kept as hyphened capitals (`T-E-R-R-A`) (#14873) + a `<terms>` phonetic dictionary (`cube netties → Kubernetes`, `type script → TypeScript`, etc.). Aliases that are ordinary English ("rejects", "jot", "roll up") are kept out of the table, and the rest apply only where the words make no sense as plain English. Those are `gpt-6.1-terra`'s rules; `gpt-6-luna` keeps the earlier, more literal `LITERAL_CORRECTION_PROMPT` word for word (both name `<recent_prompts>`, #14855), since under the firmer ones it reworded passages and dropped words that carried meaning, and `correctionInstructionsFor(model)` picks between them.
- `buildCorrectionSystemPrompt(context)` — layers project context, the user's custom dictionary (PREFERRED TERMS), and custom instructions, ending with a fixed guardrail suffix. What the project, dictionary and workspace blocks say their names are for follows the rules' `contextNames`: Terra's say they spell a name the passage mishears, while Luna's and the rewrite prompt keep the tiebreak wording they were measured with, byte for byte. Ordered fixed-first so the OpenAI prompt cache (`prompt_cache_key`, prefix `voice-correction-v15`) hits. The fixed `CORE_CORRECTION_PROMPT` prefix is kept above OpenAI's 1,024-token cache floor, and `VoiceCorrectionService` sends it as the first `developer` message in the `input` array (not the top-level `instructions` field) so the prefix is actually cache-eligible.
- For a terminal on this machine, the prompt also names the worktree being dictated in, with its issue and pull request titles as its record has them (the title read off the branch name when neither has been fetched; nothing is fetched for this), and the repository's names (#14854). Both come from reads the keyterms already make at the session's start: the names whole from the same `readPaneKeytermReads` snapshot the repository tier tokenizes, scope dropped and screened by `screenCorrectionRepositoryNames` to at most 60, and the worktree from `gatherDictationContext`, which finds it in the worktree states the workspace names are read from (the terminal's `worktreeId`, else the deepest worktree holding its cwd; the Assistant gets none). `screenDictationWorktree` drops a title holding a credential, defuses tag brackets and caps it at 200 characters. They follow the keyterms' ownership rule: a terminal another project owns, a dictation outside the view and a passage naming no session get none, and a pane on a remote host keeps what it had (#14782). They are read once per session, within the start's budget, and kept with it, so the warm-up and every passage send the same prompt. Terra's prompt treats them as the spelling of a name the passage mishears (#14873) and Luna's as evidence for choosing between readings of a word; neither treats them as words to add, and the rewrite prompt never carries them.
- The terminal output rides in the user message as `<terminal_output>`, never the system prompt, so the cacheable prefix stays stable. `readTerminalOutputForCorrection` (`electron/services/voiceTerminalContext.ts`) reads the dictated terminal's snapshot only for the terminal `resolveKeytermTarget` accepts (so none for a terminal another project owns), runs it through `redactSecretShapedLines`, cuts lines to 300 characters, and keeps the newest 150 lines within 6,000 characters. The read has a 500ms budget; a slow or failed read means cleanup runs without it. Terra's prompt reads it as the spelling of a name the passage mishears (#14873) and Luna's as evidence for choosing between readings of a misheard word; neither reads it as text to add. Logs carry its length only.
- The prompts recently sent to the dictated terminal ride first in the user message, as `<recent_prompts>` (#14855), so a dictation after a send still has the conversation it continues. Every send a terminal takes is recorded as the composer wrote it (`recordSentPrompt` in `terminalInputStore`), in the order the sends went: `useTokenResolution` notes one as it goes and takes it back if the terminal turns it down, and a fleet broadcast notes each target as its submit lands. It is kept apart from recall history, which reorders repeats. The record is keyed by the terminal sent to within the view, so the pane and a Canopy reply typing to the same agent share it, and a prompt is cut to 1,000 characters when it is recorded. A cleanup request carries the last few, oldest first and verbatim (`selectRecentPrompts` in `src/services/voiceRecentPrompts.ts`): up to six, in a window whose start moves three sends at a time, less any sent over an hour ago. They are read as each request goes out, so a prompt sent while a dictation ran counts. Main drops them outside the view and for a terminal another project owns, the terminal output's rule. Each prompt is a content block of its own marked with `prompt_cache_breakpoint`: since GPT-5.6 OpenAI reuses a cached prefix inside the user message only up to a marked block, writes the last three marks and looks up at every one. Measured: unmarked, two Terra requests that shared the system prompt and three recent prompts and differed only in the target hit 2,965 cached tokens, the developer message alone; marked, the same pair hit 4,807 on both cleanup models, and a request with one more prompt than the last read all of the last one's prompts from the cache. So the cache survives a send until the window moves on; only the two cleanup models are sent the marks. Terra's prompt treats the prompts as the spelling of a name the passage mishears (#14873) and Luna's as evidence for choosing between readings of a word, never as words to add or instructions to follow, and the rewrite prompt never carries them. Logs carry their count and total length only.
- The words the recogniser was unsure of are wrapped in `<uncertain>` inside `<target>`, by position (`annotateUncertainSpans`), so a repeated word is tagged only where it was flagged; words flagged side by side share one tag. Cleanup runs whether or not any word was flagged: a word heard confidently can still be the wrong identifier.

Meaning beats polish, so `VoiceCorrectionService` checks every replacement before it is applied (`electron/services/voiceCorrectionGuard.ts`) and keeps the exact raw text when one fails. References, backticked spans, URLs, paths, flags and numbers (digits, spoken English numbers and Han numerals) must come back byte for byte and in order, and the model may not invent a new flag, reference, URL or backticked span, except a flag the speaker spelled out ("dash dash watch" as `--watch`), in the place they said it. A symbol typed for its spoken name ("origin slash develop" as `origin/develop`, "project underscore id" as `project_id`) stands for the word it replaces rather than counting as an edit, and a sentence's own full stop or colon never stands for a spoken "dot" or "colon" (`CorrectionGuardLimits.spokenSymbols`). Beyond that, a negation may not be added, dropped or moved to another word; and a result that adds or removes more words than a cleanup would (15% of the passage, with a small floor for short ones) is treated as a rewrite. Two edits may drop more, each only where the raw text shows why: the words an explicit self-correction ("no wait", "scratch that", "I mean", "or rather", a bare "no" or "sorry" between commas) takes back, and the counting words of a spoken list the cleanup laid out as one. Dropped words are located by aligning the two passages, the retracted words start at the last copy of the replacement's first word, and neither allowance may drop a negation, a number or a protected span, so such a self-correction is left as spoken. Negations are only recognised in English, and a single swapped word still gets through: the checks are structural, not semantic. A replacement the model marks low-confidence is never applied. A passage over 12,000 characters is deliberately left raw, the output budget scales with the passage, and a reply cut off at that budget (`status: "incomplete"`) is discarded whole rather than parsed. Rejections log a reason code and lengths, never the text.

`electron/services/__tests__/fixtures/dictatedPrompts.ts` holds dictated agent prompts with their expected cleanups. The guard tests check every expected cleanup (and every worked example in the prompt) passes the guard; `npm run test:integration -- VoiceCleanup.eval` judges the live prompt against them with an `OPENAI_API_KEY`.

`npm run perf voice-cleanup` compares models, reasoning efforts and cleanup prompts over a 179-passage corpus (the replay clips as OpenAI, Deepgram and Grok mishear them, context-bound mishearings, passages dictated in a worktree whose title or repository names settle a word or must not pull one, passages dictated after prompts that settle a word or must not pull one, each one it should settle beside the same passage dictated without it, names the terminal spells or the speaker spells out letter by letter and the words that only sound like them, long rambles, filler and tics, lookalikes where the same words carry meaning, clean passages and the prompts above), lands every reply under each edit budget offline, and scores agent-ready text, repairs, exact fixes, words lost or added, guard catches, round-trip latency and cost per cleanup; `scripts/perf/README.md` has the details. Cleanup moved from `gpt-6-luna` to `gpt-6.1-terra` on its numbers (#14793): over 810 streamed requests Terra repaired 76% of misheard reference words against Luna's 64%, landed 52% of exact written fixes against 46%, and matched the reference on 82% of passages against 76%, at about seven times the cost, still well under a tenth of a cent per cleanup. Latency was a wash: a p50 round trip of 1.5 s for both, 1.8 s against 1.9 s from 140 characters up, and the first corrected text at 1.1 s against 1.2 s; across three full runs the gap changed sides, so it's network noise. Terra is better at misheard names and context words ("x term", "codecs", "whisper flow"); Luna is better at spelling out dictated paths ("origin slash develop") and resolving an "I mean". Settings offers both, each with what it's better at, so someone who wants Luna's speed and price can have it. At `low` effort Terra lost no words at all but took 2.2 s at p50 on prompt-length passages. Terra doesn't know its own name: it read "GPT 6.1 Terra" as "there" or dropped it in four of six tries, and in one of six even with "Terra" in the dictionary. Predicted Outputs, which could have cut the latency of a cleanup that mostly hands its input back, isn't available: the Responses API rejects `prediction`, and Chat Completions rejects it for both models. How hard cleanup corrects was set the same way (#14786), over four live rounds on the 129 passages the corpus held then: on Terra, the passages that came back as the message the speaker would have typed went from 58.5% to 75.6% (filler taken out 53% to 97%, misheard words fixed 60% to 70%, run-ons broken up 33% to 67%, word error after cleanup 3.0% to 1.1%), with the same two risky trials either side, both Terra's known trouble with its own name. Most of the gain is the prompt; the rest is the guard, whose 15% budget was never what held cleanups back: symbols typed for their spoken names were, and widening the budget to 25% or more let a dropped clause through. On Luna the firmer rules doubled the risky trials, so Luna keeps the earlier ones. Names got the same treatment (#14873): Terra's rules had read the terminal, the session's names, recent prompts and the dictionary as a tiebreak at most, so "GPT 6.1 Tera" stayed misheard with `gpt-6.1-terra` on screen and even after the speaker spelled it out. With a name the context spells, or the speaker spells letter by letter, taken as that word's spelling, over the 163 passages the corpus already had (two repeats on Terra) the ready passages went from 72.7% to 78.2%, misreads fixed from 57 to 65 of 92 and risky trials from 6 to 4, with the same clean passages kept; over the 15 added for it, ready went from 46.7% to 86.7% and every misread was fixed, with every lookalike keeping its word. The same rules taught with names the corpus doesn't have landed the added passages just as well, so the rule carries to names it wasn't shown, but without the Terra example Terra wrote its own name as `gpt-6.1-terra` or "terra" in the older passages. Luna's prompt is unchanged, byte for byte.

`voiceContextKeyterms.ts` (`assembleKeyterms`, `sanitizeOpenAIKeywords`, `formatKeytermPrompt`, branch/project/terminal tokenizers) builds a dynamic keyterm list from the target project's vocabulary and the custom dictionary plus six sources tied to the terminal being dictated into, which the renderer names in `voiceInput.start(sessionId, { terminalId })`. In rank order: its owning project's name; names from that project's repository; the workspace names a person points at, sent whole (`voiceContextNames.ts`: the project's worktrees, plus host and project names when the target is the Assistant, screened by `screenDictationNames` to at most 12); the spoken names of the commands the agent it runs accepts (at most 12); the branch of the worktree it's filed under; and identifiers from its recent output. The repository tier (`voiceRepoKeyterms.ts`) reads the root and workspace package names, top-level directory names and dependency names from the owning project's root, derives them fresh per session and never stores them, and adds at most 6 terms. Its reads are bounded: a manifest is resolved through symlinks and read only when it is a regular file inside the project root of at most 256KB, only the first 20 workspace patterns are tried (`dir/*` and literal paths, either separator, nothing that climbs out), and no read starts once the 500ms assembly budget is spent. The project vocabulary and the dictionary share one budget of at most 36 of the 74 slots, project terms first (`RESERVED_CONTEXT_KEYTERMS` is 38: project 4, repository 6, workspace names 12, commands 12, branch 4), so those tiers always fit. Every assembled term, repository names included, is sent to the transcription provider, and cleanup gets the same derived names whole. A terminal main doesn't track, or one another project owns than the requesting view, contributes nothing. Derived terms pass through `voiceKeytermSecrets.ts` first: a line holding a credential (a known secret format, a key-shaped run, or a value assigned to a credential name) is emptied along with the line after it, and opaque IDs and bare credential names are blanked from the rest. The project vocabulary and the dictionary are hand-entered and aren't filtered. The voice-input start handler assembles it at session start and injects it into the snapshotted settings; both providers consume it, and both reconnect paths reuse the frozen list unchanged. `GrokTranscriptionProvider` sends it as repeated `keyterm=` URL params within xAI's 100 terms of 50 characters (a longer term is skipped) and the same 6,000-character query budget, retrying a rejection, an HTTP 400 or an `error` before `transcript.created`, with the first 20 terms and then none, as Deepgram's does. `DeepgramTranscriptionProvider` sends it as repeated Nova-3 `keyterm=` URL params, dropping the lowest-priority terms that would take the encoded query past 6,000 characters or an over-estimate of the tokens past 450: Deepgram fails the upgrade on more than 500 keyterm tokens, and its retry keeps only the dictionary. `OpenAITranscriptionProvider` sends it twice over — as the native `transcription.keywords` array and as a bounded `transcription.prompt` (via `formatKeytermPrompt`) — both built from one `sanitizeOpenAIKeywords` pass, so a term rejected from `keywords` can't reach `prompt`.

Sanitising is not optional: the Realtime API rejects the **entire** `session.update` if any keyword contains `<`, `>`, CR, or LF, so one bad term from terminal output (shell redirects, JSX, diff markers) would kill the whole dictation session. Offending terms are dropped whole rather than stripped — deleting `<` from `<div>` yields `div`, a different literal that would bias transcription toward a word the user never had on screen. The 74-term (`MAX_KEYTERMS`) / 100-char caps are Daintree's own conservative bounds, shared with the Deepgram path; OpenAI documents neither limit.

Neither field is sent empty — when nothing survives sanitising, both `keywords` and `prompt` are omitted rather than sent as `[]` / `""`. The `session.update` log deliberately records only shape (model, languages, delay, keyword count, `hasPrompt`, whether `turn_detection` came back null), never contents: keyterms carry the user's branch names, repository names and terminal output, and these logs are readable by agents.

### Unsure words

The spans travel by position at every hop, never as word text, and a span any rewrite reached is dropped rather than moved:

1. **Provider.** `flagUncertainWords` places each recognised word in the transcript with `locateWords`: matched in order at the cursor from the start, then from the end, so words smart formatting rewrote in the middle ("twenty five dollars" written "$25") are left unplaced, and a run of words with no space between them counts only once it reaches a space or the end. Prose punctuation stays outside a span.
2. **Main.** The utterance reader (`voiceUtteranceCommands.ts`) keeps each segment's spans inside what a stripped "send it" and the break commands leave (both rewrite only the end), and moves them into an opening command that merges segments. `emitCompletion` splits them by paragraph piece, maps them through the heard-as rules' own replacements (the rewriter's optional `edits` collector), and through an opening command's copied arguments (`planSpokenCommand`). Each completion sends `uncertain` for `text`, `heardUncertain` for `heard`, and `commandUncertain` for `commandText`, each only when non-empty.
3. **Renderer.** Each utterance in `dictationRangeStore` keeps its spans relative to its words, which hold while its range is unedited, the only time correction reads them. They survive only writes that say what they changed (`expectDraftChange`: the voice writes and breaks, scratch, cancel and the stop-time rewrite). Any other draft change is diffed, and a diff can't say which copy of repeated text an edit took, nor see the separate edits one update holds, so it drops the draft's spans rather than risk one landing on another copy of its word. Cleanup then runs untagged, as before. The stop-time heard-as pass maps them from the words as heard through its own replacements into the merged utterance.
4. **Correction.** `collectCorrectionPassages` gives each passage its spans, `voiceInput.correct` carries them as `uncertain`, and `VoiceCorrectionService` shifts them past the whitespace it trims.

They are transcript content: they go in the cleanup request and nowhere else. Logs carry a count at most.

### File-link resolution

When AI correction and `resolveFileLinks` are both on, every `complete` utterance is scanned for file-reference commands ("link to the input bar component", "at file…"). Two stages, both `gpt-6-luna`, both best-effort and abortable via the session `AbortController`:

1. **Detect** — `VoiceCorrectionService.detectFileLinkTokens` runs a permissive regex pre-filter (`FILE_LINK_TRIGGER_RE`, biased to false positives), then the model extracts `{ description }` tokens.
2. **Resolve** — `electron/services/VoiceFileLinkResolver.ts` queries `fileSearchService`, scores candidates with a token-overlap heuristic (high-confidence shortcut at `NL_CONFIDENCE_THRESHOLD` 0.67 with ≥2 matching tokens), else AI-reranks. The handler sends `file_token_resolved` with `@<path>` (or `@?<description>` on miss); the renderer best-effort-replaces the spoken description in the draft.

## Settings, errors, accessibility, IPC

- **Settings** — `VoiceInputSettings` (`shared/types/ipc/api.ts`) is stored under the `voiceInput` key. `getVoiceSettings()` (`electron/ipc/handlers/voiceInput.ts`) merges defaults, migrates legacy `apiKey`/`correctionApiKey` into the unified `openaiApiKey`, normalizes stale provider/model values **without** force-resetting valid user choices (the #9175 fix), and honors `WHISPER_API_KEY` / `DEEPGRAM_API_KEY` / `XAI_API_KEY` env overrides. `setSettings` writes only the fields it lists in `WRITABLE_VOICE_FIELDS`. The UI is `src/components/Settings/VoiceInputSettingsTab.tsx`; saving dispatches `VOICE_INPUT_SETTINGS_CHANGED_EVENT` (`src/lib/voiceInputSettingsEvents.ts`), which makes the renderer service `refreshConfiguration()` live.
- **Dictionary** — `dictionary` holds `VoiceDictionaryEntry` records (written `term`, `heardAs` forms, `source` of `manual` / `learned` / `imported`, `addedAt`), oldest first, unique ignoring case. Main owns it and the `suggestedDictionary` queue: the renderer changes them only through `window.electron.voiceDictionary` (`add`, `remove`, `update`, `acceptSuggestion`, `dismissSuggestion`, `recordSuggestions`), each one synchronous read-modify-write in `electron/ipc/handlers/voiceDictionary.ts` that returns the state main now holds. The pure model is `shared/utils/voiceDictionary.ts`; keyterm assembly and correction still take the plain list of written terms (`dictionaryTerms`). Migration 036 moved the old `customDictionary` word list into entries.
- **Project vocabulary** — each project has its own entries in `ProjectSettings.voiceDictionary`, edited under Project settings → Context and changed only through `voiceDictionary.getProject` / `addToProject` / `removeFromProject` / `updateInProject`. A project that keeps its settings in the repo reads and writes the vocabulary in `.daintree/settings.json` (committed as `{ term, heardAs }`), so a teammate's terms arrive with a pull; any other project keeps it locally (`electron/services/projectVoiceDictionary.ts`). A whole-settings save keeps the stored list rather than its own copy, carrying the committed field over verbatim from any file that parses. Turning in-repo settings on adopts a committed list when there is one and commits the local list otherwise; turning them off copies the list in use into the local one. A session uses the vocabulary of the project that owns the target panel (none for a terminal another project owns than the asking view): its terms take the dictionary keyterm budget ahead of the global list, and correction gets `sessionDictionary(global, project)`, project entries first.
- **Error model** — `VoiceInputError` (`shared/types/voice.ts`) is a plain serializable shape (crosses `contextBridge`) with a stable `code` and `severity`. Branch on `code`, not `message`. Transient errors keep the session alive while the main process reconnects (renderer just stores them for tooltip context); fatal errors tear down and surface an action-free error toast.
- **Accessibility** — `src/components/Terminal/VoiceRecordingAnnouncer.tsx` renders an `aria-live="polite"`, `role="status"` `sr-only` region driven by `store.announce(text)`. Status transitions ("Dictation started in …", "paused", "Reconnecting…", errors) are announced once each.
- **IPC channels** — `voice-input:*` in `electron/ipc/channels.ts`; the renderer surface is `window.electron.voiceInput` (`electron/preload.cts`). Request RPCs: `getSettings`, `setSettings`, `start`, `stop`, `flushParagraph`, `checkMicPermission`, `requestMicPermission`, `openMicSettings`, `validateApiKey`, `correct`. Fire-and-forget: `sendAudioChunk` (`ipcRenderer.send`, the audio hot path). Push events: `onTranscriptionDelta`, `onTranscriptionComplete`, `onParagraphBoundary`, `onFileTokenResolved`, `onError`, `onStatus`. The handler registers a `destroyed` listener on the sender so a renderer crash stops the active session.
